# 표준 시나리오 (Standard Scenarios)

[UsageCases.md](UsageCases.md)(추상 유스케이스)와 [Requirements.md](Requirements.md)를 **구체적인 표준 사용례**로 풀어 쓴 문서이다. 목적은 두 가지다.

1. 시스템이 실제로 어떻게 쓰이는지를 간략한 단계 시퀀스로 보여준다.
2. 각 단계에 근거(UC/FR/OD)를 태깅하여, **설계가 이 사용례들을 지원하는지 기계적으로 검사**할 수 있게 한다.

## 계층 (2026-09-03 확정, 2026-10-01 S8 승격)

- **기본(MVP)**: S0~S6, **S8**, **S11**(2026-10-13 추가). 설계가 반드시 **지원**해야 하는 사용례. 지원/미결/갭 규칙을 적용한다. S8(Best-of-N)은 2026-09-03에 확장으로 등록되었으나 2026-10-01 오너 결정(Requirements OD-21)으로 MVP에 승격되었다 — 태그 안정성을 위해 번호는 유지한다.
- **추가 사항(확장, Post-MVP)**: S7·S9·S10. 문헌 조사([reviews/2026-09-03](reviews/2026-09-03-StandardScenarios-LiteratureReview.md))에서 도출된 확장 사용례. MVP에서 구현하지 않되, **설계(인터페이스)가 이를 막지 않아야** 한다(NFR-6 확장성의 적용). 확장 호환 규칙을 적용한다.

## 검사 규칙

설계 변경 시(또는 새 시나리오 추가 시) 각 시나리오의 모든 단계에 대해:

**기본(MVP) 시나리오**
- **[지원]** 근거 FR이 존재한다.
- **[미결]** 근거는 있으나 세부가 Open Decision(OD)으로 등재되어 있다. → 허용 (설계 단계에서 확정).
- **[갭]** 근거 FR도 없고 OD 등재도 안 되어 있다. → Requirements에 FR/OD를 추가하거나 시나리오를 out-of-scope로 명시해야 한다.

**추가 사항(확장) 시나리오**
- **[확장 호환]** 현재 FR/OD/인터페이스(STATE, spec, 도구, 레이아웃)가 해당 단계를 **막지 않는다**. 필요한 확장 고려사항이 관련 OD에 "확장 고려" 메모로 등재되어 있으면 통과.
- **[갭]** 현재 설계가 해당 단계를 구조적으로 배제한다(예: 인터페이스가 후보 1개를 하드코딩). → 인터페이스를 일반화하거나 OD에 확장 고려를 등재해야 한다.

검사 결과는 본 문서 말미 §검사 결과에 기록한다 — 기록 규약(판정이 바뀐 재검사만 이력에 남김)은 그 절 첫머리에 있다.

## S0. 기본 전제 시나리오 (Canonical Flow) — 2026-09-02 사용자 정의

시스템 설계 전 가장 간단히 생각해볼 수 있는 표준 사용 흐름이다. **유일한 사용 흐름은 아니지만, 이 사용례를 지원할 수 있어야 함이 설계의 기본 전제다.** S1~S6은 이 흐름의 변주(모드·재개·큐레이션·감사 관점)로 볼 수 있다.

1. 적용될 **Hardware Specification 선택** (Documentation 포함 — 문서는 복제 저장이 아닌 소스 등록). 대상은 외부 타사 HW일 수도, 자사 개발 중 HW일 수도 있다. (UC-0·UC-1, FR-13·**14**; 온보딩 세부 = OD-26)
2. 적용될 **Neural Network Model 선택** (Transformer 기반 LLM 포함). (UC-1; 입력 포맷 = OD-9 미결)
3. *(사용자 선택)* **기존 유사/동일 최적화 사례 입력** — 내부 Storage 및 외부 연구 논문 Link 등. 이 정보는 HIL이 **"참고사항"으로만 사용**하며 "Ground Truth"로 받아들이지 않고, 특히 기존 최적화 사례가 **"최종 목표"가 되어서는 안 된다**. 가설을 직접 주거나 논문 링크에서 도출하게 할 수도 있다(→ S11). (FR-**15**; FR-7 랭킹에도 동일 원칙 적용)
4. Claude Code CLI 호출로 해당 Model을 해당 Hardware에서 **동작시키기 위한 코드 생성**. (FR-5; **라운드 0 = bring-up + baseline**은 FR-1에 명시됨)
5. 생성된 코드를 주어진 환경(**Simulator 혹은 실제 연결된 Hardware**)에서 시험. (FR-1·10)
6. 시험 결과 **분석·프로파일링**, 개선 사항(correctness, performance, overhead 등) 파악, 시험 결과 저장. 라운드가 가설을 시험했다면 가설마다 판정과 원인을 기록하고 사례로 저장한다. (FR-1·6·9·11·17·18; 필드·파일 = OD-30)
7. **지속 개선/정지 결정** — 미리 결정한 수준 도달 혹은 더 이상 개선 불가능 판정 시 정지. 단, 추후 Continue할 수 있도록 **Checkpoint 저장**. 정지 시 저장 후 종료. (FR-3 target 조기종료·budget, UC-7 비수렴 판정, FR-6 checkpoint·재개)
8. 지속 개선 포인트에 대해 프로파일 결과·기존 코드·주어진 자료로 **개선 방향 결정 및 문서화**(e.g., `.md` 생성) — 가설·근거·예상 효과를 가설 레코드로 남기고, 같은 키의 과거 사례를 참조한다. (FR-11 결정 로그, FR-17·18; 코더 spec 페이로드 = OD-6 확정분 [ADR-0002](decisions/ADR-0002-od6-codegen-spec.md))
9. Claude Code CLI 호출로 **코드 개선 시도**. (FR-5)
10. **goto 5**. (FR-1 라운드 루프)

## S1. 새 HW에 모델 커널 첫 최적화 (인터랙티브)

**액터**: 배포 엔지니어

1. 새 NPU(외부 타사 또는 자사 개발 중)의 hw_profile(HW 출처 포함)과 문서 소스 포인터, sim/board 도구 접근 정보를 시스템에 등록한다. (UC-0, FR-14 ④; 세부 = OD-26)
2. *(HW, 모델, target=latency 최소화, budget=20 라운드, gate=board 첫 투입 전, checkpoint 모드, N=1, tolerance = 사용자가 명시(기본값 없음; 예: `rtol`·`atol`))* 로 Loop instance를 시작한다. (UC-1, FR-2·3·4·9, FR-1 N)
3. 시스템이 데이터 plane의 `runs/<run_id>/` 작업공간과 STATE를 만들고, 라운드 0(bring-up + baseline 측정)을 수행한다. (UC-1, FR-1 라운드 0, FR-13; baseline 선택 = OD-28)
4. 라운드 반복: 카탈로그에서 기법을 랭킹·선택 → 코더(`claude -p`)에 spec 위임 → compile → sim + correctness 검증. (UC-2, FR-1·5·7·9)
5. board 첫 투입 gate에서 정지, 사용자가 승인한다. (UC-2, FR-4)
6. board 측정 + correctness 재검증 → profile → evaluate → 결과 commit. (UC-2, FR-1·9·10·11)
7. budget 소진 시 best 커널 유지로 종료한다. (UC-1, FR-3)

### S1-b. 자사 개발 중 HW에서의 첫 최적화 (sim-only, revision 갱신) — S1 변주

**액터**: HW 온보딩 담당 → 배포 엔지니어

1. 실리콘이 아직 없는 자사 개발 중 NPU를 hw_profile(출처 = 자사 개발 중)·문서 소스·simulator 접근 정보만으로 등록한다. (UC-0, FR-14 ④; sim-only 온보딩 허용 여부 = OD-26)
2. S1-2~4와 같이 instance를 시작하되 board 단계 없이 sim 측정으로 라운드를 돈다. (UC-1·2, FR-1·10; sim 측정의 최종측정·best/baseline 인정 여부 = OD-26, OD-15; README "Simulator/Emulator In The Loop")
3. 개발 진행으로 simulator·문서가 갱신된다. 온보딩을 갱신하고 기존 이력의 귀속을 처리한다. (UC-0 대안 흐름; 갱신 흐름·귀속 규칙 = OD-26; revision·toolchain 버전 변경 = 새 키, OD-4 확정분 [ADR-0001](decisions/ADR-0001-od4-key-schema.md))
4. 갱신 후 이전 best를 다시 측정해 기록값과 대조한다. (UC-4·6, FR-6·10; 측정 계약 변경 시 incumbent 재측정 = NFR-7 ①/OD-11 제안; 환경 변화 감지 = S10/UC-E4 확장)

## S2. 야간 무인 최적화 (CI)

**액터**: CI / 헤드리스 배치

1. CI가 `claude -p`로 *(HW, 모델, target=throughput, budget=wall-clock 8h + 토큰 상한, autonomous)* instance를 기동한다. (UC-3, FR-2·3·4)
2. 무정지로 라운드를 반복하며 매 라운드 STATE·산출물을 commit한다. (UC-3, FR-1·6·13, NFR-1)
3. 도중 프로세스가 죽어도 cron 재기동이 마지막 commit 지점에서 이어간다. (UC-3·4, NFR-1)
4. 비수렴 시 기법군을 자동 전환(N회)한다. (UC-7)
5. any budget 소진 → best 유지 종료 + 사용자에게 알림. (UC-3·7, FR-3·**16**)

## S3. 완료된 run에서 추가 최적화 재개

**액터**: 배포 엔지니어

1. 과거 run 목록에서 완료된 run(또는 중간 라운드)을 선택한다. (UC-4·6, FR-6)
2. 시스템이 해당 지점의 STATE·산출물을 복원한다. (UC-4, FR-6·13)
3. 새 budget과 다른 기법군(또는 다른 target)으로 분기하여 탐색을 잇는다. (UC-4, FR-2·3·6; 분기·재개한 run의 표현 = OD-8 하위 질문)
4. 이후 흐름은 S1/S2와 동일하다.

## S4. 외부 논문의 기법을 카탈로그에 반영

**액터**: 기법 큐레이터

1. 외부 논문/코드를 deep-research로 이해한다. (UC-5, FR-12)
2. 신규 기법을 *선택 기준(Skill 트리거) + 적용 지침(카탈로그)* 하이브리드 형태로 추가한다. (UC-5, FR-8·12)
3. 다음 run의 기법 랭킹에 새 기법이 후보로 반영된다. (UC-5, FR-7)

## S5. 과거 이력 조회·감사

**액터**: 배포 엔지니어

1. 특정 (hw_profile, op_signature)의 run 이력을 조회한다. (UC-6, FR-13; 키 → run 색인 = OD-8 하위 질문)
2. 라운드별 프로파일·정확도·점수와 best를 비교하고, 실패 라운드도 확인한다. (UC-6, FR-6·11)
3. 결정 로그로 "어떤 기법을 왜 골랐는지"를 확인한다 — 가설·예상 효과·판정·원인과 참조한 과거 사례를 포함한다. (UC-6, FR-11·17·18, NFR-2; 필드·파일 = OD-30)

## S6. 두 번째 run에서 더 빨라진 최적화 (크로스런 학습)

**액터**: 배포 엔지니어 / CI

1. 같은 (hw_profile, op_signature) 키로, 또는 유사한 hw_profile의 새 HW에서 같은 연산으로 instance를 시작한다. (UC-1; 같은 키 = MVP 최소분, 정확 일치 [ADR-0001](decisions/ADR-0001-od4-key-schema.md); 유사도 매칭 = OD-4 잔여 미결)
2. 시스템이 그 키의 가설–결과 사례(지지·기각·실패)와 사례 통계를 조회해 가설을 세우고 기법 후보를 랭킹하며, 참조한 사례를 결정 로그에 남긴다. 과거 사례는 우선순위 힌트일 뿐이다. (FR-7·11·15·17·18, UC-5 환류; 싣는 사례의 선택·양 = OD-30, 통계 환류 = OD-7 미결)
3. 이전 run보다 적은 라운드로 수렴한다. (FR-18; 아래 수용 기준)
4. 이번 run의 가설·판정과 성공/실패도 사례와 통계에 반영되어 자산이 누적된다. (FR-6·13·18)

**수용 기준**(오너 결정 2026-10-13: 측정 가능한 기준을 둔다 — 아래 지표 정의는 제안이며 확정 = OD-30; 같은 키의 경우): 같은 키·target·tolerance·N·budget으로 시작한 두 번째 run이 첫 run의 best에 도달하기까지 — 검증된 결과의 측정이 첫 run의 best의 측정과 견주어 측정 정책의 차이 판정 규칙([ADR-0007](decisions/ADR-0007-od13-measurement-policy.md) 결정 7)으로 `not different`이거나 목표 방향으로 `different`(방향 = OD-1)일 때까지 — 쓴 **라운드 수**가, 첫 run이 그 best를 얻기까지 쓴 라운드 수보다 **적어야** 한다. 두 번째 run의 결정 로그에는 첫 run의 사례 참조가 하나 이상 있어야 한다(없으면 빨라진 것이 사례 덕인지 말할 수 없다). 그때까지의 board 측정 횟수와 토큰 지출을 함께 기록한다(NFR-5). 이 잣대는 시스템의 수용 시험에만 쓰며 run의 목표가 아니다 — run의 목표는 사용자가 정한 target이고 과거 성능은 목표가 되지 않는다(FR-2·15). 경계 사례(첫 run의 best가 라운드 0·1에서 나온 경우)·run 사이의 측정 drift·반복 수·대조군 = OD-30.

## S8. 라운드 내 다중 후보 탐색 (Best-of-N) — 2026-10-01 MVP 승격

**액터**: 배포 엔지니어 / CI

1. instance 파라미터로 라운드당 후보 수 N(초기 UI 선택 범위 1~5)을 지정한다. (UC-1, FR-1; board 승격 수 k의 결정 방식 = OD-29)
2. 기법 랭킹 상위 N개(또는 같은 기법의 N개 변형)를 N개의 코더 호출로 위임한다. (FR-5·7; 병렬/순차 = OD-29, spec의 후보 식별 = OD-6 확정분 [ADR-0002](decisions/ADR-0002-od6-codegen-spec.md))
3. compile → sim + correctness로 스크리닝하고 상위 k개만 board 측정한다. (FR-1·9·10, C-4; 승격 기준 = OD-15) *(확장: LLM 검증자 스크리닝 = OD-16)*
4. best 채택, 나머지 후보도 실패/중간 산출물로 저장하여 통계에 반영한다 — board 미승격 후보는 "sim만 평가됨"으로 구분한다. (FR-6·7·13; 레이아웃의 후보 차원 = OD-8 확정분 [ADR-0004](decisions/ADR-0004-od8-data-plane-layout.md), 아카이브 필드 = OD-20)
5. 토큰·HW 비용을 후보별로 집계한다. (NFR-5; 후보별 상한 = OD-19·OD-29)

## S11. 외부 가설 주입 (논문 링크 등) — 2026-10-13 추가

**액터**: 배포 엔지니어 / CI

1. instance를 시작하면서 가설을 직접 쓰거나, 가설을 도출할 외부 자료(연구 논문 링크 등)를 준다. (UC-1, FR-15; 형식·기록 자리 = [ADR-0075](decisions/ADR-0075-od30-injection-at-instance-start.md))
2. 시스템이 그것을 출처가 "주입"인 가설 레코드로 만들고, 근거가 된 자료를 식별자+버전으로 기록한다. (FR-12·14 ②·15·17; 자료에서 가설을 도출하는 주체 = OD-30, 코더의 직접 검색 = OD-12)
3. 주입된 가설은 시스템이 세운 가설과 같은 라운드 루프에서 실험·검증·판정된다 — 우선순위 힌트일 뿐 검증을 면제받지 않는다. 주입이 있어도 시스템은 결과에서 교훈을 얻어 스스로 추가 가설을 세우며, 라운드마다 다른 가설을 시험할 수 있다. (FR-1·9·15·17; 주입 가설과 시스템 가설의 배분 = OD-30)
4. 판정과 원인이 출처와 함께 사례로 저장되어 같은 키의 이후 run이 참조한다. (FR-18; 지지된 주입 가설의 카탈로그 반영 = UC-5, 경계 = OD-30·OD-24)
5. *(checkpoint 모드; MVP 포함 여부 미결 — OD-30)* gate에서 방향 수정으로 가설을 추가한다. (UC-2, FR-4·15; instance 시작 뒤의 주입 = OD-30)

# 추가 사항 (확장 시나리오 — Post-MVP)

문헌 조사([reviews/2026-09-03](reviews/2026-09-03-StandardScenarios-LiteratureReview.md))에서 도출한 확장 사용례. MVP 구현 대상이 아니며, 설계가 이를 막지 않는지([확장 호환])만 검사한다. 관련 보강 제안(B2~B8)은 각 OD의 "확장 고려" 메모([OpenDecisionProposals.md](OpenDecisionProposals.md))로 등재되어 있다. 단, B1(검증 강건성)의 **최소 조항은 MVP FR-9에 반영**되었다 — 검증 우회는 후보 1개인 S0 루프에서도 발생하며 저장 자산(FR-6·7)을 오염시키기 때문이다. S8은 2026-10-01에 기본 계층으로 승격되어 위로 이동했다.

## S7. 검증 우회·퇴화 해 탐지 (Adversarial Correctness)

**액터**: 시스템 (autonomous/checkpoint 공통)

1. 코더가 생성한 커널이 기본 검증(고정 입력·tolerance)을 통과한다. (FR-9)
2. 강화 검증: 최적화 중 노출되지 않은 shape/seed로 격리 하네스에서 재검증(MVP 최소 조항 = FR-9), 추가로 정밀도 하향 여부·스트림 동기화 후 타이밍·정적 검사(금지 패턴). (FR-9, OD-16 확장, NFR-4)
3. 강화 검증 실패 → 해당 라운드를 실패로 기록하고 실패 유형(연산 제거/하드코딩/저정밀/캐시 재사용 등)을 태깅. (FR-6·11)
4. 다음 라운드 코더 spec에 해당 금지 패턴을 명시적으로 추가. (FR-5, OD-6 확장 고려)
5. 반복 발생 시 gate/알림으로 에스컬레이션. (FR-4·16, UC-7)

## S9. Board 장애·측정 노이즈 대응

**액터**: 시스템 → 배포 엔지니어

1. board 측정 중 hang/timeout/예약 경합 발생. (C-4, OD-10)
2. 타임아웃 후 재시도 또는 다른 board 예약; 반복 실패 시 sim 결과로 대체하고 "board 미검증" 표시. (FR-10, OD-10)
3. 정상 측정 시 반복 측정·신뢰구간을 계산하고, 노이즈 범위 내 차이는 "개선 아님"으로 판정한다. (NFR-3; 반복·대표값·차이 판정 규칙 = OD-13 확정분 [ADR-0007](decisions/ADR-0007-od13-measurement-policy.md) — board에는 초기값, paired 재측정은 OD-13 잔여, 개선의 방향 = OD-1)
4. 장애 이력을 hw_profile에 기록해 이후 랭킹·스케줄에 반영. (FR-13·14)

## S10. 결과 재현 (Reproduce)

**액터**: 배포 엔지니어 / CI

1. 과거 run의 best를 선택한다. (UC-6, FR-6)
2. instance.json의 source-repo commit + artifacts 해시(CAS) + 참조 자료 스냅샷으로 코드·바이너리·참조 맥락을 복원한다. (NFR-2, A-1/A-2, FR-13, FR-14 ②; `artifacts.json` 레코드 = OD-8 확정분 [ADR-0005](decisions/ADR-0005-od8-artifacts-record.md), 다른 머신으로의 blob 동기화 = C-3 `blob.fetch`·#5 B-2)
3. 같은 hw_profile에서 재측정하여 기록값과 대조한다. (FR-10, NFR-3)
4. 차이가 노이즈 범위를 넘으면 환경 변화(드라이버/펌웨어/호스트)를 의심하고 새 hw_profile 키 후보로 표시한다. (FR-14, OD-4 확장 고려(S10); revision 처리 = OD-26)
