# 표준 시나리오 (Standard Scenarios)

[UsageCases.md](UsageCases.md)(추상 유스케이스)와 [Requirements.md](Requirements.md)를 **구체적인 표준 사용례**로 풀어 쓴 문서이다. 목적은 두 가지다.

1. 시스템이 실제로 어떻게 쓰이는지를 간략한 단계 시퀀스로 보여준다.
2. 각 단계에 근거(UC/FR/OD)를 태깅하여, **설계가 이 사용례들을 지원하는지 기계적으로 검사**할 수 있게 한다.

## 계층 (2026-09-03 확정, 2026-10-01 S8 승격)

- **기본(MVP)**: S0~S6, **S8**. 설계가 반드시 **지원**해야 하는 사용례. 지원/미결/갭 규칙을 적용한다. S8(Best-of-N)은 2026-09-03에 확장으로 등록되었으나 2026-10-01 오너 결정(Requirements OD-21)으로 MVP에 승격되었다 — 태그 안정성을 위해 번호는 유지한다.
- **추가 사항(확장, Post-MVP)**: S7·S9·S10. 문헌 조사([reviews/2026-09-03](reviews/2026-09-03-StandardScenarios-LiteratureReview.md))에서 도출된 확장 사용례. MVP에서 구현하지 않되, **설계(인터페이스)가 이를 막지 않아야** 한다(NFR-6 확장성의 적용). 확장 호환 규칙을 적용한다.

## 검사 규칙

설계 변경 시(또는 새 시나리오 추가 시) 각 시나리오의 모든 단계에 대해:

**기본(MVP) 시나리오**
- **[지원]** 근거 FR이 존재한다.
- **[미결]** 근거는 있으나 세부가 Open Decision(OD)으로 등재되어 있다. → 허용 (설계 단계에서 확정).
- **[갭]** 근거 FR도 없고 OD 등재도 안 되어 있다. → Requirements에 FR/OD를 추가하거나 시나리오를 out-of-scope로 명시해야 한다.

**추가 사항(확장) 시나리오**
- **[확장 호환]** 현재 FR/OD/인터페이스(STATE, spec, 도구, 레이아웃)가 해당 단계를 **막지 않는다**. 필요한 확장 고려사항이 관련 OD에 "확장 고려" 메모로 등재되어 있으면 통과.
- **[갭]** 현재 설계가 해당 단계를 구조적으로 배제한다(예: 인터페이스가 후보 1개를 하드코딩). → 인터페이스를 일반화하거나 OD에 확장 고려를 등재해야 한다.

검사 결과는 본 문서 말미 §검사 결과에 기록한다.

## S0. 기본 전제 시나리오 (Canonical Flow) — 2026-09-02 사용자 정의

시스템 설계 전 가장 간단히 생각해볼 수 있는 표준 사용 흐름이다. **유일한 사용 흐름은 아니지만, 이 사용례를 지원할 수 있어야 함이 설계의 기본 전제다.** S1~S6은 이 흐름의 변주(모드·재개·큐레이션·감사 관점)로 볼 수 있다.

1. 적용될 **Hardware Specification 선택** (Documentation 포함 — 문서는 복제 저장이 아닌 소스 등록). 대상은 외부 타사 HW일 수도, 자사 개발 중 HW일 수도 있다. (UC-0·UC-1, FR-13·**14**; 온보딩 세부 = OD-26)
2. 적용될 **Neural Network Model 선택** (Transformer 기반 LLM 포함). (UC-1; 입력 포맷 = OD-9 미결)
3. *(사용자 선택)* **기존 유사/동일 최적화 사례 입력** — 내부 Storage 및 외부 연구 논문 Link 등. 이 정보는 HIL이 **"참고사항"으로만 사용**하며 "Ground Truth"로 받아들이지 않고, 특히 기존 최적화 사례가 **"최종 목표"가 되어서는 안 된다**. (FR-**15**; FR-7 랭킹에도 동일 원칙 적용)
4. Claude Code CLI 호출로 해당 Model을 해당 Hardware에서 **동작시키기 위한 코드 생성**. (FR-5; **라운드 0 = bring-up + baseline**은 FR-1에 명시됨)
5. 생성된 코드를 주어진 환경(**Simulator 혹은 실제 연결된 Hardware**)에서 시험. (FR-1·10)
6. 시험 결과 **분석·프로파일링**, 개선 사항(correctness, performance, overhead 등) 파악, 시험 결과 저장. (FR-1·6·9·11)
7. **지속 개선/정지 결정** — 미리 결정한 수준 도달 혹은 더 이상 개선 불가능 판정 시 정지. 단, 추후 Continue할 수 있도록 **Checkpoint 저장**. 정지 시 저장 후 종료. (FR-3 target 조기종료·budget, UC-7 비수렴 판정, FR-6 checkpoint·재개)
8. 지속 개선 포인트에 대해 프로파일 결과·기존 코드·주어진 자료로 **개선 방향 결정 및 문서화**(e.g., `.md` 생성). (FR-11 결정 로그; 코더 spec 페이로드 = OD-6 확정분 [ADR-0002](decisions/ADR-0002-od6-codegen-spec.md))
9. Claude Code CLI 호출로 **코드 개선 시도**. (FR-5)
10. **goto 5**. (FR-1 라운드 루프)

## S1. 새 HW에 모델 커널 첫 최적화 (인터랙티브)

**액터**: 배포 엔지니어

1. 새 NPU(외부 타사 또는 자사 개발 중)의 hw_profile(HW 출처 포함)과 문서 소스 포인터, sim/board 도구 접근 정보를 시스템에 등록한다. (UC-0, FR-14 ④; 세부 = OD-26)
2. *(HW, 모델, target=latency 최소화, budget=20 라운드, gate=board 첫 투입 전, checkpoint 모드, N=1, tolerance = 사용자가 명시(기본값 없음; 예: `rtol`·`atol`))* 로 Loop instance를 시작한다. (UC-1, FR-2·3·4·9, FR-1 N)
3. 시스템이 데이터 plane의 `runs/<run_id>/` 작업공간과 STATE를 만들고, 라운드 0(bring-up + baseline 측정)을 수행한다. (UC-1, FR-1 라운드 0, FR-13; baseline 선택 = OD-28)
4. 라운드 반복: 카탈로그에서 기법을 랭킹·선택 → 코더(`claude -p`)에 spec 위임 → compile → sim + correctness 검증. (UC-2, FR-1·5·7·9)
5. board 첫 투입 gate에서 정지, 사용자가 승인한다. (UC-2, FR-4)
6. board 측정 + correctness 재검증 → profile → evaluate → 결과 commit. (UC-2, FR-1·9·10·11)
7. budget 소진 시 best 커널 유지로 종료한다. (UC-1, FR-3)

### S1-b. 자사 개발 중 HW에서의 첫 최적화 (sim-only, revision 갱신) — S1 변주

**액터**: HW 온보딩 담당 → 배포 엔지니어

1. 실리콘이 아직 없는 자사 개발 중 NPU를 hw_profile(출처 = 자사 개발 중)·문서 소스·simulator 접근 정보만으로 등록한다. (UC-0, FR-14 ④; sim-only 온보딩 허용 여부 = OD-26)
2. S1-2~4와 같이 instance를 시작하되 board 단계 없이 sim 측정으로 라운드를 돈다. (UC-1·2, FR-1·10; sim 측정의 최종측정·best/baseline 인정 여부 = OD-26, OD-15; README "Simulator/Emulator In The Loop")
3. 개발 진행으로 simulator·문서가 갱신된다. 온보딩을 갱신하고 기존 이력의 귀속을 처리한다. (UC-0 대안 흐름; 갱신 흐름·귀속 규칙 = OD-26; revision·toolchain 버전 변경 = 새 키, OD-4 확정분 [ADR-0001](decisions/ADR-0001-od4-key-schema.md))
4. 갱신 후 이전 best를 다시 측정해 기록값과 대조한다. (UC-4·6, FR-6·10; 측정 계약 변경 시 incumbent 재측정 = NFR-7 ①/OD-11 제안; 환경 변화 감지 = S10/UC-E4 확장)

## S2. 야간 무인 최적화 (CI)

**액터**: CI / 헤드리스 배치

1. CI가 `claude -p`로 *(HW, 모델, target=throughput, budget=wall-clock 8h + 토큰 상한, autonomous)* instance를 기동한다. (UC-3, FR-2·3·4)
2. 무정지로 라운드를 반복하며 매 라운드 STATE·산출물을 commit한다. (UC-3, FR-1·6·13, NFR-1)
3. 도중 프로세스가 죽어도 cron 재기동이 마지막 commit 지점에서 이어간다. (UC-3·4, NFR-1)
4. 비수렴 시 기법군을 자동 전환(N회)한다. (UC-7)
5. any budget 소진 → best 유지 종료 + 사용자에게 알림. (UC-3·7, FR-3·**16**)

## S3. 완료된 run에서 추가 최적화 재개

**액터**: 배포 엔지니어

1. 과거 run 목록에서 완료된 run(또는 중간 라운드)을 선택한다. (UC-4·6, FR-6)
2. 시스템이 해당 지점의 STATE·산출물을 복원한다. (UC-4, FR-6·13)
3. 새 budget과 다른 기법군(또는 다른 target)으로 분기하여 탐색을 잇는다. (UC-4, FR-2·3·6; 분기·재개한 run의 표현 = OD-8 하위 질문)
4. 이후 흐름은 S1/S2와 동일하다.

## S4. 외부 논문의 기법을 카탈로그에 반영

**액터**: 기법 큐레이터

1. 외부 논문/코드를 deep-research로 이해한다. (UC-5, FR-12)
2. 신규 기법을 *선택 기준(Skill 트리거) + 적용 지침(카탈로그)* 하이브리드 형태로 추가한다. (UC-5, FR-8·12)
3. 다음 run의 기법 랭킹에 새 기법이 후보로 반영된다. (UC-5, FR-7)

## S5. 과거 이력 조회·감사

**액터**: 배포 엔지니어

1. 특정 (hw_profile, op_signature)의 run 이력을 조회한다. (UC-6, FR-13; 키 → run 색인 = OD-8 하위 질문)
2. 라운드별 프로파일·정확도·점수와 best를 비교하고, 실패 라운드도 확인한다. (UC-6, FR-6·11)
3. 결정 로그로 "어떤 기법을 왜 골랐는지"를 확인한다. (UC-6, FR-11, NFR-2)

## S6. 두 번째 유사 HW에서 더 빨라진 최적화 (크로스런 학습)

**액터**: 배포 엔지니어 / CI

1. 유사한 hw_profile의 새 HW에서 같은 연산(op_signature)의 instance를 시작한다. (UC-1; 유사도 매칭 = OD-4 잔여 미결 — P1은 정확 일치만, [ADR-0001](decisions/ADR-0001-od4-key-schema.md))
2. 시스템이 과거 (hw_profile, op_signature) 사례 통계를 근거로 기법 후보를 랭킹, 이전 run보다 적은 라운드로 수렴한다. (FR-7, UC-5 환류; 통계 환류 = OD-7 미결)
3. 이번 run의 성공/실패도 통계에 반영되어 자산이 누적된다. (FR-6·13)

## S8. 라운드 내 다중 후보 탐색 (Best-of-N) — 2026-10-01 MVP 승격

**액터**: 배포 엔지니어 / CI

1. instance 파라미터로 라운드당 후보 수 N(초기 UI 선택 범위 1~5)을 지정한다. (UC-1, FR-1; board 승격 수 k의 결정 방식 = OD-29)
2. 기법 랭킹 상위 N개(또는 같은 기법의 N개 변형)를 N개의 코더 호출로 위임한다. (FR-5·7; 병렬/순차 = OD-29, spec의 후보 식별 = OD-6 확정분 [ADR-0002](decisions/ADR-0002-od6-codegen-spec.md))
3. compile → sim + correctness로 스크리닝하고 상위 k개만 board 측정한다. (FR-1·9·10, C-4; 승격 기준 = OD-15) *(확장: LLM 검증자 스크리닝 = OD-16)*
4. best 채택, 나머지 후보도 실패/중간 산출물로 저장하여 통계에 반영한다 — board 미승격 후보는 "sim만 평가됨"으로 구분한다. (FR-6·7·13; 레이아웃의 후보 차원 = OD-8 확정분 [ADR-0004](decisions/ADR-0004-od8-data-plane-layout.md), 아카이브 필드 = OD-20)
5. 토큰·HW 비용을 후보별로 집계한다. (NFR-5; 후보별 상한 = OD-19·OD-29)

# 추가 사항 (확장 시나리오 — Post-MVP)

문헌 조사([reviews/2026-09-03](reviews/2026-09-03-StandardScenarios-LiteratureReview.md))에서 도출한 확장 사용례. MVP 구현 대상이 아니며, 설계가 이를 막지 않는지([확장 호환])만 검사한다. 관련 보강 제안(B2~B8)은 각 OD의 "확장 고려" 메모([OpenDecisionProposals.md](OpenDecisionProposals.md))로 등재되어 있다. 단, B1(검증 강건성)의 **최소 조항은 MVP FR-9에 반영**되었다 — 검증 우회는 후보 1개인 S0 루프에서도 발생하며 저장 자산(FR-6·7)을 오염시키기 때문이다. S8은 2026-10-01에 기본 계층으로 승격되어 위로 이동했다.

## S7. 검증 우회·퇴화 해 탐지 (Adversarial Correctness)

**액터**: 시스템 (autonomous/checkpoint 공통)

1. 코더가 생성한 커널이 기본 검증(고정 입력·tolerance)을 통과한다. (FR-9)
2. 강화 검증: 최적화 중 노출되지 않은 shape/seed로 격리 하네스에서 재검증(MVP 최소 조항 = FR-9), 추가로 정밀도 하향 여부·스트림 동기화 후 타이밍·정적 검사(금지 패턴). (FR-9, OD-16 확장, NFR-4)
3. 강화 검증 실패 → 해당 라운드를 실패로 기록하고 실패 유형(연산 제거/하드코딩/저정밀/캐시 재사용 등)을 태깅. (FR-6·11)
4. 다음 라운드 코더 spec에 해당 금지 패턴을 명시적으로 추가. (FR-5, OD-6 확장 고려)
5. 반복 발생 시 gate/알림으로 에스컬레이션. (FR-4·16, UC-7)

## S9. Board 장애·측정 노이즈 대응

**액터**: 시스템 → 배포 엔지니어

1. board 측정 중 hang/timeout/예약 경합 발생. (C-4, OD-10)
2. 타임아웃 후 재시도 또는 다른 board 예약; 반복 실패 시 sim 결과로 대체하고 "board 미검증" 표시. (FR-10, OD-10)
3. 정상 측정 시 반복 측정·신뢰구간을 계산하고, 노이즈 범위 내 차이는 "개선 아님"으로 판정한다. (NFR-3; 반복·대표값·차이 판정 규칙 = OD-13 확정분 [ADR-0007](decisions/ADR-0007-od13-measurement-policy.md) — board에는 초기값, paired 재측정은 OD-13 잔여, 개선의 방향 = OD-1)
4. 장애 이력을 hw_profile에 기록해 이후 랭킹·스케줄에 반영. (FR-13·14)

## S10. 결과 재현 (Reproduce)

**액터**: 배포 엔지니어 / CI

1. 과거 run의 best를 선택한다. (UC-6, FR-6)
2. instance.json의 source-repo commit + artifacts 해시(CAS) + 참조 자료 스냅샷으로 코드·바이너리·참조 맥락을 복원한다. (NFR-2, A-1/A-2, FR-13, FR-14 ②; `artifacts.json` 레코드 = OD-8 확정분 [ADR-0005](decisions/ADR-0005-od8-artifacts-record.md), 다른 머신으로의 blob 동기화 = C-3 `blob.fetch`·#5 B-2)
3. 같은 hw_profile에서 재측정하여 기록값과 대조한다. (FR-10, NFR-3)

S8-3의 N개 후보는 타이밍 실행에서는 시도마다 실행 파일이 따로이므로 같은 심볼이 한 프로그램에서 만나지 않는다(6차 구절이 하네스 메커니즘으로 남긴 부분 가운데 타이밍 실행의 답; 검증 실행은 미결 그대로). S0-5·S1-6의 "실제 연결된 Hardware / board"가 LAN의 원격 머신일 때의 경로(#5 A-7 ③, C-7 ⑤)는 이 기록이 정하지 않았으나, 실행 파일과 인자·표준 출력만으로 이루어진 실행은 그것을 막지 않는다. 네이티브 Windows를 지원하지 않는 것은 C-7(POSIX 전제) 안이다. 이미 얻은 측정값을 쓰기만 하는 단계들은 샘플을 얻는 방법에 기대지 않으며 판정이 종전과 같다(기본 시나리오 S0·S1·S2·S5·S6·S8은 지원(미결) 그대로 — S2-4의 비수렴 기준 = UC-7·OD-19, S6-2의 통계 환류 = OD-7, S8-5의 비용 집계 = OD-19·OD-29; 확장 시나리오의 S7-3·S10-4는 확장 호환 그대로). 확장 시나리오 S9-1·2(측정 중 hang·timeout, 재시도)도 확장 호환 그대로다 — ADR-0009는 시간 초과·비정상 종료로 끝난 타이밍 실행을 측정으로 치지 않을 뿐이고, 그 뒤의 재시도·대체와 타임아웃 계층은 OD-10·OD-14에 남겨 막지 않는다. simulator와 board에서 샘플을 얻는 방법은 이 기록의 범위 밖이다(sim·board = #5 B-2·B-3 이후, OD-13 하위 질문 ③) — 이 기록은 `cpu_standin`의 메커니즘만 정하고 다른 실행 지점의 방법을 닫지 않는다. 따라서 기본 시나리오의 S1-b-2·4는 지원(미결) 그대로이고, 확장 시나리오 S9-3·S10-3·4는 확장 호환 그대로다. S7-2의 타이밍 강화 검증(스트림 동기화 후 타이밍)과 S7-3의 "캐시 재사용" 유형 태깅도 OD-16 확장으로 남아 확장 호환 그대로다 — ADR-0009는 한 측정의 반복이 같은 입력을 다시 쓰고 비계측 실행의 시간을 읽지 않도록 정했으나 위협 B ⑷⑸의 방어를 채택도 기각도 하지 않았고, 급감 탐지나 steady-state 라벨링이 채택되면 그 결정 6을 다시 연다고 적어 두었으므로 막지 않는다. S10-3의 재측정이 기록된 측정과 같은 입력 값을 쓰는지는 하위 질문 ⑦에 남으며, 어떤 시나리오 단계도 그것에, 또는 보고 줄의 형식·시계의 종류·비계측 실행 여부에 기대지 않는다. **2026-10-07 (8차, OD-18 중 FR-10 도구의 노출 형태와 호출 규약 확정 — [ADR-0010](decisions/ADR-0010-od18-tool-exposure-form.md))**: 규칙을 다음 네 묶음에 재적용했고 **판정 변화는 없으며 갭도 없다**. ⑴ FR-10을 인용하는 단계(S0-5, S1-6, S1-b-2·4, S8-3, S9-2, S10-3) — OD-18을 인용하는 단계는 없다. ⑵ 그 밖에 에이전트가 도구 패키지를 통해 실험을 수행하거나 저장소를 쓰는 단계(S0-4·6·7, S1-3·4, S2-2·3, S3-2·4, S7-1·2·3, S8-4, S9-1·3, S10-2). ⑶ gate·budget·무인 기동처럼 나중의 강제 계층(hook)과 닿는 단계(S1-5·7, S2-1·5, S7-5, S8-5). ⑷ 도구 접근 정보를 등록하는 단계(S0-1, S1-1, S1-b-1). ⑴·⑵의 기본 시나리오 단계는 종전대로 FR-1·FR-9·FR-10·FR-13 근거의 지원이다 — FR-10이 "MCP/Bash로 노출"이라고만 하고 OD-18에 남겼던 호출 형태가 확정분이 되었다: 도구는 패키지 안의 도구 함수로 한 번 정의되고, 에이전트는 stdio MCP 서버의 타입 있는 도구(`mcp__hilclaw__sim_run` 등)로, 사람·스크립트·테스트는 명령줄로 같은 함수를 호출한다. 각 도구의 인자·결과·실패 종류·재시도(PLAN P1-1, OD-10), 오라클(#5 A-7 확정 대기)·tolerance(#5 B-7), 이벤트 종류(PLAN P1-8, OD-17)는 종전의 미결 그대로이며, 어느 에이전트가 어느 도구를 호출하는지도 OD-23 그대로다. S1-6·S8-3처럼 한 단계가 측정과 correctness를 함께 말하는 경우에도 규약은 도구마다 요청 하나·결과 하나만 정했을 뿐 호출의 순서나 묶음을 정하지 않아 막지 않는다. S0-7·S2-3·S3-2의 재개와 복원은 commit된 파일에 기대며 호출 형태와 무관하다 — 다만 MCP 서버 프로세스는 시작할 때 읽은 코드를 계속 쓰므로(수명은 등록 방식에 따라 세션 또는 sub-agent이며 등록 방식은 정해지지 않았다) 교체된 도구 계층이 언제 적용되는지는 라운드 = 프로세스 경계(#8 M4, OD-18 잔여)와 함께 남는다. ⑶의 단계는 판정이 종전과 같다: ADR-0010은 hook·gate·allowlist·격리 수단을 채택하지도 기각하지도 않았고, S1-5의 gate 정지(FR-4; gate 목록 = OD-3)와 S1-7·S2-5·S8-5의 budget 집행·집계(FR-3, NFR-5; OD-19·OD-17)는 그 기록에 기대지 않는다 — 타입 있는 도구 호출은 나중의 hook이 이름과 요청을 볼 수 있게 남겨 두며, 명령줄을 통한 호출은 그렇지 않다는 것이 OD-18 하위 질문 ②로 등재되었다. S2-1의 무인 기동(`claude -p`)은 막히지 않는다 — 서버가 프로젝트의 `.mcp.json`에 등록되어 있으면 `-p` 세션은 그것을 승인 프롬프트 없이 연결하고, 문서가 예고한 대로 `--bare`가 `-p`의 기본이 된 뒤에는 `--mcp-config`로 서버를 넘기면 된다(문서 확인, 실제 세션 미확인; 표준 라이브러리만으로 쓴 서버의 동작 확인은 하위 질문 ①). ⑷의 등록 단계가 적는 것은 백엔드에 닿는 방법(endpoint·quota·예약, OD-26·#5 B-2)이며 도구가 1층에 노출되는 형태가 아니므로 영향이 없다. 확장 시나리오의 S7-1·2·3·5, S9-1·2·3, S10-2·3은 확장 호환 그대로다: 규약은 도구 집합을 닫지 않고(등록표; NFR-6), 실패한 실험을 결과로 돌려주는 구분은 S9-2의 재시도·대체(OD-10)나 S7-3의 실패 유형 태깅(OD-16 확장)을 막지 않는다. S10-2의 `blob.fetch`는 이름의 대응만 정해졌고 계약과 백엔드는 C-3·#5 B-2 그대로다. 어떤 시나리오 단계도 서버 이름, 도구의 MCP 이름 표기, 오류 객체의 형식, 한 호출의 시간 제한(하위 질문 ③)에 기대지 않는다. **2026-10-07 (9차, OD-17 중 저널 대상 단계의 기록과 지출 계상 확정 — [ADR-0011](decisions/ADR-0011-od17-journal-and-spend.md); #8 M7의 규약 포함)**: 규칙을 다음 세 묶음에 재적용했고 **판정 변화는 없으며 갭도 없다**. ⑴ 재개·checkpoint에 기대는 단계(S0-7, S2-2·3, S3-1~4, S1-b-4). ⑵ budget을 지정·소진·집계하는 단계(S0-7, S1-2·7, S2-1·5, S3-3, S8-5). ⑶ 비싼 측정을 얻거나 다시 하는 단계(S0-5·6, S1-6, S1-b-2, S8-3, S9-1·2, S10-3)와 그 기록을 읽는 단계(S5-2). OD-17을 인용하는 단계는 없다. ⑴ S2-3의 "마지막 commit 지점에서 이어간다"는 NFR-1 근거의 지원 그대로이고, 4차 구절이 OD-17·PLAN P1-8에 남긴 "재개한 턴이 로그를 어떻게 쓰는지" 가운데 **저널 대상 단계의 판정과 이중 지출 방지**가 확정분이 되었다 — 도구 계층이 단계 앞뒤로 시작 줄·끝 줄을 남기고, 끝 줄이 있으면 재개한 턴은 그 단계를 건너뛰고 줄에서 결과를 얻으며, 같은 식별의 호출은 다시 실행되지 않고, `phase` 마커와 로그가 다르면 로그를 따른다. 시작 줄만 남은 "열린" 단계를 어떻게 회복하는지(재실행·대기·포기)는 OD-10과 OD-17 잔여(재시도)이고, cron 재기동이 겹쳐 두 턴이 동시에 도는 경우의 방어(lock·fencing)도 OD-17 잔여이며, `phase`의 값과 `STATE.json`의 멤버는 PLAN P1-8이므로 S2는 지원(미결) 그대로다. S0-7의 checkpoint 저장과 S3-1·2의 복원은 commit된 지점을 대상으로 하므로 종전과 같다(줄은 고치거나 지우지 않고, 저장된 지출 뷰는 같은 commit의 로그를 넘는 위치를 가리키지 않는다). S1-b-4의 "이전 best 재측정"이 저널 대상 단계라면 이전 라운드에 관한 단계가 되어 조회가 저장된 위치 앞의 줄을 필요로 한다 — OD-17 하위 질문 ①로 등재되었고 판정은 지원(미결) 그대로다. ⑵ budget 단계는 종전대로 FR-3 근거의 지원이다. 로그를 거쳐 계상되는 금액은 이제 정본(끝 줄의 `spend`)과 합계를 얻는 방법(라운드 종료 때 `STATE.json`에 둔 뷰 + 꼬리의 fold)을 가지며, 죽은 라운드의 지출이 합계에서 빠지지 않는다. 그러나 ADR-0011은 축을 하나도 이름 짓지 않았다 — S1-2의 "20 라운드", S2-1의 "wall-clock 8h + 토큰 상한"이 어떤 축이고 로그를 거쳐 계상되는지(라운드 수와 경과 시간은 다른 기록에서 얻을 수 있다), 토큰을 오케스트레이터와 코더로 합산하는지(#5 A-8), HW quota 축(OD-2)은 종전의 미결 그대로이고, S1-7·S2-5의 "소진 → 종료"를 실제로 일으키는 수단은 OD-19다(합계가 예산을 넘어도 그 기록만으로는 아무 일도 일어나지 않는다; 열린 단계의 금액은 알 수 없어 합계는 하한이다). S3-3의 "새 budget"이 출발점 run의 지출과 어떤 관계인지는 분기·재개의 표현(OD-8 하위 질문 ①)과 함께 남는다. S8-5의 후보별 집계는 끝 줄이 `round`·`candidate`·`attempt`를 싣게 되어 후보별로 접을 수 있게 되었으나, 코더 호출이 저널 대상 단계인지와 토큰이 로그를 거치는지는 정해지지 않았고 후보별 상한은 OD-19·OD-29 그대로다. ⑶ 측정 단계는 종전대로 FR-1·FR-10 근거의 지원이다 — 출처가 이름 준 저널 대상 단계는 board 측정 하나이고(#4 §3b, C-4), 그 밖의 어떤 도구의 단계에 두 줄이 남는지와 요청·결과의 멤버는 PLAN P1-1이다. S5-2의 이력 확인은 막히지 않는다(실패로 끝난 단계도 끝 줄로 남는다). 확장 시나리오 S9-1·2(board hang·timeout, 재시도)는 확장 호환 그대로다: 중단된 측정은 열린 단계 또는 `failure`로 끝난 단계로 로그에 남고, 다시 실행하는 것은 더 큰 `execution`의 새 식별로 표현할 수 있어 막히지 않으며, 재시도할지와 그 횟수는 OD-10·OD-17 잔여다. S10-3의 재측정도 확장 호환 그대로다 — 새 run이면 그 run의 로그에 남고, 같은 run의 이전 라운드에 관한 것이면 위 하위 질문 ①에 해당한다. 어떤 시나리오 단계도 두 종류의 이름, `execution` 번호, 스냅샷이 라운드 종료에만 움직인다는 것, `STATE.json` 전체가 뷰인지 여부에 기대지 않는다. **2026-10-07 (10차, OD-8 잔여 중 런타임 `STATE.json`의 파일 틀·라운드 포인터·저장된 지출 뷰 확정 — [ADR-0012](decisions/ADR-0012-od8-runtime-state-file.md))**: 규칙을 다음 세 묶음에 재적용했고 **판정 변화는 없으며 갭도 없다**. ⑴ STATE를 만들거나 쓰거나 복원하는 단계(S1-3, S2-2, S3-2). ⑵ 그 밖에 재개·checkpoint에 기대는 단계(S0-7, S2-3, S3-1·3·4, S1-b-4). ⑶ budget을 지정·소진·집계하는 단계(S0-7, S1-2·7, S2-1·5, S3-3, S8-5). ⑴ S1-3의 "작업공간과 STATE를 만들고"는 FR-13 근거의 지원 그대로이며, 시작 시점의 파일이 무엇을 담는지가 확정분이 되었다(`round` 0, 빈 지출 뷰) — 그 첫 파일을 무엇이 언제 쓰는지는 OD-8 하위 질문 ⑩으로 등재되었다. S2-2의 "매 라운드 STATE·산출물을 commit"은 FR-13·NFR-1 근거의 지원 그대로다: 라운드를 끝내는 쓰기가 `round`를 다음 라운드로 옮기고 지출 뷰를 뜨며 그 라운드의 commit이 이를 가져간다 — 그 쓰기와 commit 사이에 죽은 경우를 새 턴이 어떻게 아는지는 하위 질문 ⑪이다. S3-2의 복원은 commit된 지점의 파일을 대상으로 하므로 종전과 같고, 그 파일의 `round`가 그 지점에서 끝나지 않은 라운드를 말한다. ⑵ S2-3의 "마지막 commit 지점에서 이어간다"는 NFR-1 근거의 지원 그대로이고, 새 턴이 어느 라운드를 이어 가는지가 확정분이 되었다(`round`가 가리키는 라운드; 그 안에서 끝난 단계는 9차 구절대로 로그가 정한다). 그러나 `next_action`·`phase`의 값·lock·gate 상태는 이 기록이 정하지 않았으므로(OD-23·OD-29·OD-17 잔여·OD-3) 버전 1의 두 멤버만으로는 라운드를 돌릴 수 없고, S2는 지원(미결) 그대로다. S0-7의 "정지 시 Checkpoint 저장"과 run이 끝났는지의 표시도 같은 미결에 남는다 — `round`는 턴이 실제로 도는지를 말하지 않는다. S3-1·3의 중간 라운드 선택과 분기는 OD-8 하위 질문 ① 그대로이며(같은 run의 뒤 번호 라운드라면 `round`에서 이어지고, 새 run이라면 새 파일이다), S3-4는 S1/S2의 흐름을 잇고, S1-b-4는 9차 구절과 같다. ⑶ budget 단계는 종전대로 FR-3 근거의 지원이다. 9차 구절이 PLAN P1-8에 남긴 저장 형식이 확정분이 되었을 뿐 축은 여전히 하나도 이름 지어지지 않았고(#5 A-8·OD-2), 집행은 OD-19다. S8-5의 후보별 집계는 저장된 뷰에 들어 있지 않다 — `totals`는 축별 합계뿐이므로 후보별 값은 줄을 접어 얻으며(끝 줄이 번호를 싣는다, 9차 구절) 그 방법과 상한은 OD-19·OD-29 그대로다. 로그를 거치지 않는 축의 누계를 어디에 두는지도 정해지지 않았다. 확장 시나리오는 영향이 없다: 어떤 확장 단계도 `STATE.json`의 멤버를 말하지 않으며, 최상위가 열려 있어 뒤의 기록이 멤버를 더하는 것을 막지 않는다(NFR-6). 어떤 시나리오 단계도 멤버 이름, 열린 단계의 정렬 순서, 합계의 크기 제한 여부, 바이트 오프셋의 유무에 기대지 않는다. **2026-10-07 (11차, OD-8 잔여 중 런타임 `STATE.json`을 디스크에서 바꿔 쓰는 방법 확정 — [ADR-0013](decisions/ADR-0013-od8-state-file-replacement.md))**: 규칙을 다음 두 묶음에 재적용했고 **판정 변화는 없으며 갭도 없다**. ⑴ STATE를 만들거나 쓰거나 복원하는 단계(S1-3, S2-2, S3-2). ⑵ 그 밖에 재개·checkpoint에 기대는 단계(S0-7, S2-3, S3-1·3·4, S1-b-4). `STATE.json`이 어떻게 디스크에 쓰이는지를 직접 말하는 시나리오 단계는 없다. ⑴ S1-3의 "작업공간과 STATE를 만들고"는 FR-13 근거의 지원 그대로다 — 첫 파일도 뒤의 쓰기와 같은 교체 절차(같은 디렉토리의 임시 파일 → 한 번의 이름 바꾸기)로 쓰이고 그 교체가 run 디렉토리를 만들 수 있다는 것이 확정분이 되었으며, 누가 언제 첫 파일을 쓰는지는 종전대로 OD-8 하위 질문 ⑩이다. S2-2의 "매 라운드 STATE·산출물을 commit"은 FR-13·NFR-1 근거의 지원 그대로다: 파일이 그 기록의 교체로만 쓰이는 한 작업 트리의 `STATE.json`은 어느 시점에도 온전한 내용 하나이므로 commit은 언제 떠도 온전한 파일을 가져가고(그 절차를 따르지 않는 쓰기와 history에서 파일을 되돌리는 것은 이 보장 밖이다), 임시 파일과 죽은 작성자가 남긴 것은 commit에 들지 않는다 — 어느 단계가 commit하는지와 라운드 종료를 쓴 뒤 commit 전에 죽은 경우(하위 질문 ⑪)는 종전의 미결 그대로다. S3-2의 복원은 commit된 지점을 대상으로 하므로 종전과 같다(commit에는 임시 파일이 없다; history에서 파일을 되돌리는 것은 작성자의 교체가 아니며 누가 언제 하는지는 ADR-0012가 남긴 대로 미정이다). ⑵ S2-3의 "도중 프로세스가 죽어도 … 이어간다"는 NFR-1 근거의 지원 그대로이고, 10차 구절이 요구로만 적었던 "쓰는 도중 죽어도 이전 내용이나 새 내용이 온전히 남는다"가 절차를 얻었다 — `STATE.json`을 쓰는 중에 죽은 뒤의 새 턴은 이전 내용이나 새 내용을 읽으며, 남은 임시 파일은 읽지 않고 그 때문에 디렉토리를 나열하지도 않는다. 그 약속은 프로세스 사망까지이고(머신·전원 손실은 #5 A-3대로 마지막 commit), cron 재기동이 겹친 두 작성자는 종전대로 OD-17 잔여(lock)이며, `next_action`·`phase`·gate 상태가 정해지지 않았으므로 S2는 지원(미결) 그대로다. S0-7의 checkpoint 저장, S3-1·3·4, S1-b-4는 10차 구절과 같다. 이 절차는 C-7의 POSIX 환경(Linux·macOS·WSL)의 네이티브 파일 시스템에서 성립하며, 데이터 repo가 네트워크 파일 시스템이나 WSL에서 본 Windows 드라이브에 있는 경우는 한계로 적혀 있다 — 어떤 시나리오 단계도 데이터 repo가 그런 곳에 있음에 기대지 않는다(S2-1의 CI 기동 포함). 절차는 작성자가 run 디렉토리에 항목을 만들고 바꿀 수 있기를 요구하며 이는 격리 수단에 넘겨졌다(하위 질문 ⑭) — ADR-0013은 격리 수단(후보 ①/②)도, 누가 그 쓰기를 수행하는지(OD-23)도 정하지 않았고, 어떤 시나리오 단계도 그 선택에 기대지 않는다. 확장 시나리오는 영향이 없다: 어떤 확장 단계도 파일을 쓰는 방법을 말하지 않으며, S10-2의 복원은 commit된 파일만 쓴다. 어떤 시나리오 단계도 임시 파일의 이름, flush 여부, 남은 임시 파일의 제거 여부, 모르는 멤버의 보존(하위 질문 ⑫, 미결 그대로)에 기대지 않는다. **2026-10-07 (12차, OD-8 하위 질문 ⑮ — `artifacts.json`과 `db/`의 키 레코드 파일이 디스크에 쓰이는 방법 확정 — [ADR-0014](decisions/ADR-0014-od8-whole-file-writes.md))**: 규칙을 다음 세 묶음에 재적용했고 **판정 변화는 없으며 갭도 없다**. ⑴ blob 레코드를 쓰거나 읽는 단계(쓰기: S0-6·7, S1-6, S2-2·3, S6-3, S8-4; 읽기: S3-2, S5-2, S10-2). ⑵ 키 레코드를 쓰는 단계 — hw_profile의 등록과 새 키(S0-1, S1-1, S1-b-1·3), 그 키 아래의 첫 instance(S1-3, S6-1). ⑶ 키로 조회하는 단계(S5-1, S6-1·2, S9-4, S10-3·4). 두 종류의 파일이 어떻게 디스크에 쓰이는지를 직접 말하는 시나리오 단계는 없다. ⑴ 저장 단계는 FR-6·FR-13 근거의 지원 그대로다. S2-3의 "도중 프로세스가 죽어도 … 이어간다"는 NFR-1 근거의 지원 그대로이고, `artifacts.json`을 쓰다 죽은 뒤의 새 턴은 이전 레코드들이나 새 레코드들을 온전히 읽는다 — 3차 구절 때에는 그 쓰기가 제자리 쓰기여서 죽으면 마지막 commit 뒤에 더한 레코드를 모두 잃고 파일을 사람이 되돌려야 했다. 약속은 프로세스 사망까지이고(머신 손실은 #5 A-3대로 마지막 commit), 저장소와 파일 사이의 원자성은 더해지지 않았으므로 저장된 blob의 레코드가 빠질 수 있다는 것(ADR-0005 결정 10)과 cron 재기동이 겹친 두 작성자의 갱신 손실(OD-17 잔여)은 종전 그대로다. S8-4의 class 배정(OD-20·OD-29·OD-23)과 S10-2의 복원(commit된 파일만 쓴다; `blob.fetch` = C-3·#5 B-2)은 3차 구절과 같다. ⑵ 등록 단계는 FR-14 ④ 근거의 지원(미결) 그대로다 — 키 레코드 파일을 쓰다 죽어도 일부만 쓰인 파일이 그 키를 막지 않게 되었고(레코드 파일 없음 = 저장되지 않은 키, 또는 온전한 레코드), 누가 언제 키를 처음 등록하는지와 등록 스키마는 종전대로 OD-26이다. S1-b-3의 갱신은 새 키의 새 파일이므로(ADR-0001) 저장된 레코드를 바꾸는 쓰기가 아니며, 저장된 속성을 바꿀 수 있는지는 ADR-0014가 정하지 않았다(OD-26) — 그 기록의 마지막 단계는 있는 레코드 파일을 교체하지 못하므로 그 미결을 어느 쪽으로도 닫지 않는다. ⑶ 조회 단계는 판정이 종전과 같다: 읽는 쪽은 최종 이름만 열고 남은 임시 파일을 읽지도, 그 때문에 디렉토리를 나열하지도 않는다. S5-1의 키 → run 색인(하위 질문 ②)과 S6-1의 유사도 매칭(OD-4 잔여)은 그대로이고, 색인이 키 디렉토리를 나열하게 되더라도 임시 파일의 이름에는 점이 있어 키 디렉토리 이름과 섞이지 않는다. 확장 시나리오 S9-4(장애 이력을 hw_profile에 기록)는 확장 호환 그대로다 — 키 디렉토리에 파일을 더하는 것은 열려 있고(OD-20·OD-7), 이 기록은 그런 파일의 쓰기도 이름도 정하지 않았다. S10-3·4는 영향이 없다. 환경의 한계는 11차 구절과 같고, 키 레코드 파일의 마지막 단계는 하드 링크나 교체하지 않는 이름 바꾸기를 주는 파일 시스템을 요구한다(C-7 환경의 네이티브 파일 시스템) — 어떤 시나리오 단계도 데이터 repo가 그렇지 않은 곳에 있음에 기대지 않는다. 절차가 작성자에게 요구하는 권한은 격리 수단에 넘겨졌고(하위 질문 ⑯), ADR-0014는 격리 수단도 누가 쓰는지(OD-23)도 lock도 정하지 않았다. 어떤 시나리오 단계도 임시 파일의 이름, 마지막 단계의 수단, 남은 임시 파일의 제거 여부, 이 세 파일 밖의 파일이 쓰이는 방법(정해지지 않음)에 기대지 않는다. **2026-10-07 (13차, OD-18 중 모든 FR-10 도구 계약이 공유하는 틀 확정 — [ADR-0015](decisions/ADR-0015-od18-tool-contract-frame.md))**: 규칙을 다음 세 묶음에 재적용했고 **판정 변화는 없으며 갭도 없다**. ⑴ 에이전트가 도구를 호출해 실험을 수행하거나 저장소를 쓰는 단계 — FR-10을 인용하는 단계(S0-5, S1-6, S1-b-2·4, S8-3, S9-2, S10-3)와 8차 구절의 둘째 묶음(S0-4·6·7, S1-3·4, S2-2·3, S3-2·4, S7-1·2·3, S8-4, S9-1·3, S10-2). ⑵ 비싼 결과를 남기거나 재개에 기대는 단계(S0-5·6·7, S1-6, S1-b-2·4, S2-2·3, S3-1~4, S8-3, S9-1·2, S10-3). ⑶ 나중의 강제 계층(hook)과 닿는 단계(S1-5·7, S2-1·5, S7-5, S8-5). OD-18을 인용하는 단계는 없다. ⑴의 기본 시나리오 단계는 종전대로 FR-1·FR-9·FR-10·FR-13 근거의 지원이다 — 8차 구절이 PLAN P1-1에 남긴 "각 도구의 계약" 가운데 **모든 도구에 공통인 부분**이 확정분이 되었다: 도구는 설명·입력 스키마와 함께 등록되고, 요청의 검사는 도구 함수가 하며(거절 = `invalid_request`), 데이터 루트는 요청이 아니라 진입점 프로세스의 설정에서 호출마다 얻고, run과 가리키는 대상은 `run_id`·`round`·`candidate`·`attempt`·`execution`이라는 같은 이름으로 싣는다. 각 도구의 인자·결과 멤버·실패 종류·`step` 값, 백엔드와 그 선택(#5 B-2·OD-26), mock의 고장 주입, 오라클(#5 A-7 확정 대기)·tolerance(#5 B-7)는 종전의 미결 그대로이므로 판정은 달라지지 않는다. 데이터 루트를 요청이 싣지 않으므로 어느 시나리오 단계에서도 에이전트가 쓸 트리를 고르지 않는다 — S3-2의 복원과 S10-2의 다른 머신 복원은 그 머신의 설정이 가리키는 데이터 plane을 대상으로 하며, 한 세션의 MCP 서버와 명령줄이 같은 트리를 쓰려면 두 프로세스의 환경 변수가 같아야 한다는 것이 한계로 적혔다. ⑵ S2-3의 재개는 NFR-1 근거의 지원 그대로이고, ADR-0011이 OD-18 잔여로 남긴 "두 줄을 hook이 쓰는지 진입점 아래 코드가 쓰는지"가 확정분이 되었다 — 저널 대상 도구의 도구 함수가 조회·시작 줄·끝 줄을 수행하므로 MCP 서버를 통한 호출과 명령줄을 통한 호출이 같은 줄을 남기고, 재개한 턴이 같은 요청(같은 `execution`)을 다시 보내면 어느 진입점으로든 끝난 단계는 끝 줄의 결과를, 열린 단계는 `step_open`을 받는다. 이는 세션에 hook이 등록되어 있는지에 기대지 않으므로 S2-1의 `claude -p` 기동이나 sub-agent의 호출에서도 같다. 어느 도구가 저널 대상인지(출처가 이름 준 것은 board 측정 하나), 열린 단계의 회복(OD-10·OD-17 잔여), lock, 쓸 수 없는 run에 대한 답(OD-18 하위 질문 ④)은 미결 그대로다. S1-b-4·S10-3의 재측정이 이전 라운드에 관한 단계일 때의 조회는 9차 구절대로 OD-17 하위 질문 ①이고, 저장된 `round`보다 큰 라운드를 가리키는 요청을 거절하지 않는다는 한계가 같은 질문에 더해졌다 — 어떤 시나리오 단계도 아직 시작되지 않은 라운드의 측정을 요구하지 않는다. ⑶의 단계는 판정이 종전과 같다: ADR-0015는 hook을 하나도 채택하지 않았고, 정한 것은 저널 대상 단계의 두 줄을 hook이 쓰지 않는다는 것뿐이다. S1-5의 gate 정지(FR-4; OD-3), S1-7·S2-5의 budget 집행(FR-3; OD-19), S8-5의 집계(NFR-5; OD-19·OD-29), S7-5의 에스컬레이션은 그 기록에 기대지 않으며, 호출 전 검사를 hook에 둘지 도구 계층에 둘지는 OD-18 잔여 그대로다(요청이 대상을 같은 이름으로 싣게 되어 나중의 hook이 도구마다의 표 없이 읽을 수 있다). 확장 시나리오 S7-1·2·3·5, S9-1·2·3, S10-2·3은 확장 호환 그대로다: 틀은 도구 집합을 닫지 않고(등록표에 정의를 더한다; NFR-6), 예약된 `kind` 다섯은 닫힌 목록이 아니어서 S9-2의 실패 분류(OD-10)나 S7-3의 실패 유형 태깅을 막지 않으며, 다시 측정하는 것은 더 큰 `execution`을 실은 요청으로 표현된다(누가 그것을 정하는지는 OD-10·OD-17 잔여). 어떤 시나리오 단계도 예약된 `kind`의 이름, 멤버가 최상위에 놓인다는 것, `execution`이 필수라는 것, 설명·스키마의 내용, 공급자가 호출마다 불린다는 것에 기대지 않는다. **2026-10-08 (OD-18 중 FR-10 HW 도구의 백엔드 틀 확정 — [ADR-0016](decisions/ADR-0016-od18-backend-frame.md))**: 규칙을 다음 세 묶음에 재적용했고 **판정 변화는 없으며 갭도 없다**. ⑴ HW 도구가 sim이나 board에서 호출되는 단계(S0-4·5·6, S1-3·4·6, S1-b-2·4, S2-2, S3-4, S8-3, 확장 S7-1·2, S9-1·2·3, S10-3). ⑵ HW가 등록되거나 선택되는 단계(S0-1, S1-1·2, S1-b-1·3, S2-1, S6-1, 확장 S10-4). ⑶ mock에 기댈 수 있는 단계 — 해당하는 단계가 없다. ⑴의 단계는 FR-1·FR-10 근거의 지원 그대로이고, 2026-10-07 13차 구절이 미결로 든 백엔드와 그 선택 가운데 모든 HW 도구에 같은 부분이 확정분이 되었다: 백엔드는 도구 함수 아래에서 한 `accelerator`의 대상에 실험을 수행하고 도구의 계약 그대로만 답하며, run에 관한 호출에서 호출의 백엔드는 요청이 가리킨 run의 hw_profile의 `accelerator`로 정해진다. 따라서 어느 시나리오 단계에서도 에이전트가 호출의 백엔드를 고르지 않는다 — S0-5의 "Simulator 혹은 실제 연결된 Hardware"와 S8-3의 sim 스크리닝·board 측정의 구분은 호출된 도구(`sim.run`·`board.run`)가 말하고, 어느 백엔드인지는 S1-2에서 instance를 시작할 때 선택한 hw_profile의 `accelerator`가 정한다(한 hw_profile 아래 여러 장비 가운데 어느 것인지와 그 선택을 위해 요청이 무엇을 실을 수 있는지는 #5 B-2·OD-10 그대로다). 각 도구의 계약, 백엔드에 닿는 방법(#5 B-2), 시뮬레이터(#5 B-3), 오라클·tolerance는 종전의 미결 그대로다. 2026-10-02 구절이 적은 대로 S0-5·S1-6의 "실제 연결된 Hardware / board"는 MVP 초기에 `cpu_standin`으로 충족되나, 그 실행이 `sim.run`으로 불리는지 `board.run`으로 불리는지(`cpu_standin` 백엔드가 네 도구 가운데 어느 것을 제공하는지)는 출처가 없어 OD-18 하위 질문 ⑦로 등재되었다 — 등재되었으므로 규칙상 미결이다. S3-3의 분기가 새 run(새 `instance.json`)인지 같은 run의 연장인지는 OD-8 하위 질문 ① 그대로다. ⑶의 단계는 각 단계의 근거 그대로다: S5는 run들의 이력·라운드별 결과·결정 로그를 읽으며, 레이아웃 버전이 run마다 기록되어 다른 버전의 run이 나란히 있을 수 있다는 것은 OD-8 확정분(ADR-0004 결정 9)이고 그 표식의 자리가 확정분이 되었다 — 표식은 run의 트리의 경로를 말할 뿐 파일의 내용도, 트리가 실제로 그 레이아웃인지도, `db/`·`blobs/`도 말하지 않으며(S5-1의 키 → run 조회가 읽는 `db/`의 레이아웃을 뒤의 레이아웃 버전에서 무엇이 말하는지는 하위 질문 ㉒), 다른 버전의 run의 이력을 읽는 것은 OD-11 그대로다. 확장 S10-1·2는 확장 호환 그대로다: 복원은 `source_commit`과 `artifacts.json`의 해시에 기대고 표식은 그 가운데 어느 것도 바꾸지 않았다. 어떤 시나리오 단계도 표식이 독자 멤버가 아니라 `schema_version`에서 따라 나온다는 것에 기대지 않는다. **2026-10-08 (10차, OD-8 잔여 중 `instance.json`이 최종 이름 아래에 오는 절차 확정 — [ADR-0025](decisions/ADR-0025-od8-instance-file-write.md))**: 규칙을 다음 세 묶음에 재적용했고 **판정 변화는 없으며 갭도 없다**. ⑴ instance가 시작되는 단계(S1-2·3, S1-b-2, S2-1, S3-3, S6-1, S8-1). ⑵ 끝났거나 중단된 run을 재개하거나 잇는 단계(S0-7, S2-3, S3-1·2·3). ⑶ run의 이력을 읽거나 결과를 재현하는 단계(S5-1·2·3, 확장 S10-1·2). `instance.json`이 어떻게 디스크에 쓰이는지를 직접 말하는 시나리오 단계는 없다. ⑴의 단계는 각 단계의 근거 그대로 지원(미결)이다: S1-3의 "작업공간과 STATE를 만들고"는 FR-13 근거 그대로이고, 그 작업공간의 `instance.json`이 최종 이름 아래에 오는 절차(내용 전체를 먼저 갖춤 → 같은 run 디렉토리의 임시 파일 → 안정 저장소 → 최종 이름이 없을 때에만 그 이름을 주는 마지막 단계)가 확정분이 되었다 — 이 절차로 쓰는 프로세스가 죽어도 그 이름 아래에는 파일 없음이나 온전한 파일이 남는다. 무엇이 언제 그 파일을 쓰는지는 OD-8 하위 질문 ⑰(첫 부분)·⑩, OD-23 그대로이고, 절차는 run 디렉토리나 run의 다른 파일이 있을 것도 없을 것도 요구하지 않으므로 첫 `STATE.json`과의 선후를 어느 쪽으로도 정하지 않는다. 절차는 유효성과 쓰는 형식 밖의 것을 내용에 더하거나 확인하지 않으므로, S1-2의 "tolerance = 사용자가 명시(기본값 없음)"가 instance의 시작에서 확인되는지(하위 질문 ⑲)와 소스 commit·반복 상한에 관한 질문(⑳·㉑)은 미결 그대로다. S3-3의 분기가 새 run(새 `instance.json`)인지 같은 run의 연장인지는 하위 질문 ① 그대로다: 마지막 단계는 있는 파일을 교체하지 못하므로 이 절차의 쓰기는 이미 있는 `instance.json`을 바꾸지 않고, 뒤의 기록이 이 파일을 다시 쓰게 하는지는 정하지 않았다. 최종 이름이 이미 있을 때 쓰기의 호출자가 무엇을 하는지와 쓰이고 있는 `run_id`로의 두 번째 시작의 의미는 하위 질문 ㉓으로 새로 등재되었다(지원(미결) 그대로). ⑵의 단계는 각 단계의 근거(FR-6·13, NFR-1) 그대로다: S2-3의 "도중 프로세스가 죽어도 … 이어간다"에서, 이 절차로 `instance.json`을 쓰다 죽은 뒤의 새 턴에서 그 파일을 읽는 쪽은 그것을 없는 파일로 보거나 온전히 읽는다(일부만 쓰인 파일은 이 절차를 따르는 작성자의 사망에서 생기지 않는다) — 없는 `instance.json`을 만난 호출이 답하는 `kind`는 OD-18 확정분(ADR-0019) 그대로이고, 그 뒤에 무엇이 따르는지는 정하지 않았다(하위 질문 ⑰·㉓). 약속은 프로세스 사망까지이고 머신 손실은 #5 A-3대로 마지막 commit이다. ⑶의 단계는 달라진 것이 없다: 읽는 쪽은 최종 이름만 열고 남은 임시 파일을 읽지도 그 때문에 디렉토리를 나열하지도 않으며, commit에는 임시 파일이 들지 않고, 확장 S10-2의 복원은 commit된 파일만 쓴다. 환경의 한계는 2026-10-07 12차 구절이 키 레코드 파일에 대해 적은 것과 같다(C-7 환경의 네이티브 파일 시스템; 마지막 단계는 하드 링크나 교체하지 않는 이름 바꾸기를 주는 파일 시스템을 요구한다) — 어떤 시나리오 단계도 데이터 repo가 그렇지 않은 곳에 있음에 기대지 않는다. 절차가 쓰는 쪽에게 요구하는 권한은 격리 수단에 넘겨졌고(하위 질문 ㉓), ADR-0025는 격리 수단도 무엇이 쓰는지(OD-23)도 lock도 정하지 않았다. 어떤 시나리오 단계도 임시 파일의 이름, 마지막 단계의 수단, 남은 임시 파일의 제거 여부, 최종 이름이 이미 있을 때의 보고의 형식에 기대지 않는다. **2026-10-09 (1차, OD-18 중 시작 줄·끝 줄의 추가가 실패한 호출의 답 확정 — [ADR-0026](decisions/ADR-0026-od18-failed-step-line-append.md); OD-18 하위 질문 ⑨)**: 규칙을 다음 세 묶음에 재적용했고 **판정 변화는 없으며 갭도 없다**. ⑴ run에 관한 도구가 호출되는 단계(S0-4·5·6, S1-3·4·6, S1-b-2·4, S2-2, S3-4, S8-3, 확장 S7-1·2, S9-1·2·3, S10-3). ⑵ run이 재개되거나 단계가 반복되는 단계(S0-7, S1-b-4, S2-3, S3-1·2·3·4, 확장 S9-2, S10-3). ⑶ budget이 세어지는 단계(S0-7, S1-7, S2-5, S3-3, S8-5). ⑴의 기본 시나리오 단계는 FR-1·FR-10 근거의 지원 그대로이고, 2026-10-08 4차 구절이 OD-18 하위 질문 ⑨로 등재되었다고 적은 것이 확정분이 되었다: 저널 대상 도구의 호출에서 단계 줄의 추가가 파일 시스템이나 로그 자리에 있는 것 때문에 실패하면 호출은 예약된 `kind` 둘 가운데 그 순간의 것인 도구 실패로 답한다 — 시작 줄이면 `start_line_failed`(그 호출은 단계를 부르지 않았다), 끝 줄이면 `end_line_failed`(그 호출은 단계를 끝까지 실행했고 답은 산출을 싣지 않는다)이며, 어느 쪽도 식별이 두 상태(앞의 것은 줄 없음·열림, 뒤의 것은 열림·끝남) 가운데 어느 것인지는 말하지 않고, 로그가 그 호출이 남긴 그대로가 아니면 식별에 대해 아무것도 말하지 않는다. 어느 도구가 저널 대상인지는 각 도구의 계약 그대로다(PLAN P1-1). 그 답을 받은 라운드 루프·역할·사람이 무엇을 하는지(열린 단계를 다시 실행하는지·추가 `execution`·재시도·알림)는 기록이 정하지 않았고 등재되어 있다 — OD-10·OD-17 잔여·OD-19·OD-23·OD-27, PLAN P2. ⑵ S2-3의 재개는 NFR-1 근거의 지원(미결) 그대로다: 실패한 호출의 답은 어디에도 보관되지 않으므로 재개한 턴은 같은 요청의 호출의 조회에서만 상태를 안다 — 줄이 없으면 그 호출의 시작 줄이 추가될 때 단계가 실행되고, 열려 있으면 `step_open`이며, 끝났으면 저장된 답이 돌아온다(OD-17 확정분, ADR-0011 결정 3 그대로이고 기록은 더한 것이 없다). 열린 식별에 대해 그 턴은 단계가 실행되었는지를 그 호출에서 알 수 없고, 열린 단계의 회복은 OD-10·OD-17 잔여 그대로다. S0-7·S3-1·2·3의 checkpoint·선택·복원·분기는 FR-6·13 근거 그대로이고 기록은 복원을 다루지 않는다; S3-4의 이후 흐름과 S1-b-4·S10-3의 재측정은 ⑴과 같다. ⑶의 단계는 각 단계의 근거(FR-3, NFR-5) 그대로다: `end_line_failed` 뒤에 열린 채 남은 단계의 금액은 어느 줄에도 없어 계상되지 않고 합계는 하한이다 — OD-17 확정분(ADR-0011 결정 6·7) 그대로이며 기록은 규칙을 더하지 않았다. 그런 금액을 나중에 어떻게 세거나 바로잡는지는 OD-17 하위 질문 ②·OD-19, 끝 줄이 실패한 뒤 프로세스가 아직 가진 산출과 금액을 무엇이 보존하는지는 OD-18 하위 질문 ⑪로 새로 등재되었고(지원(미결) 그대로), budget의 축·단위·집행은 OD-2·OD-19 그대로다. 확장 시나리오의 단계(S7-1·2, S9-1·2·3, S10-3)는 모두 확장 호환 그대로다: 두 `kind`는 로그에 줄을 추가하는 일의 실패에 관한 것이고 대상에서의 고장에 관한 것이 아니어서, S9-1·2의 board 장애 분류·재시도·다른 board 예약(OD-10·#5 B-2)을 정하지도 막지도 않는다. 어떤 시나리오 단계도 두 `kind`의 이름이나 그 수에 기대지 않는다. **2026-10-09 (2차, OD-8 잔여 중 시스템이 만드는 `run_id`의 형식 확정 — [ADR-0027](decisions/ADR-0027-od8-run-id-form.md))**: 규칙을 다음 세 묶음에 재적용했고 **판정 변화는 없으며 갭도 없다**. ⑴ instance가 시작되어 run이 생기는 단계(S1-2·3, S1-b-2, S2-1, S3-3, S6-1, S8-1). ⑵ run을 재개하거나 분기하거나 잇는 단계(S0-7, S2-3, S3-1·2·3). ⑶ run을 찾아 이력을 읽거나 결과를 재현하는 단계(S5-1·2·3, 확장 S10-1·2). `run_id`가 어떤 형식인지를 직접 말하는 시나리오 단계는 없다. ⑴의 단계는 각 단계의 근거 그대로 지원(미결)이다: S1-3의 "`runs/<run_id>/` 작업공간과 STATE를 만들고"는 FR-13 근거 그대로이고, 그 `run_id`를 시스템이 만들 때의 형식(`<time>-<random>` 33자 — 만드는 순간의 시계를 UTC로 초까지 읽은 값과 운영체제 난수원의 64비트)이 확정분이 되었다. 무엇이 언제 id를 만드는지는 OD-8 하위 질문 ⑩·⑰(첫 부분), OD-23 그대로다. 형식은 확인도 예약도 아니어서, 시작이 `runs/<run_id>/`가 이미 있는지를 보는지와 있을 때 무엇을 하는지는 하위 질문 ㉓ (가) 그대로이고, 시스템이 만들지 않은 id로 run을 시작할 수 있는지는 하위 질문 ㉔로 새로 등재되었다(지원(미결) 그대로). S3-3의 분기가 새 run인지 같은 run의 연장인지는 하위 질문 ① 그대로이며, 기록은 어떤 일이 새 id를 부르는지를 말하지 않는다. P1은 단일 run 전제(C-2)이고 형식은 동시에 도는 run을 안전하게 하지 않는다(lock = OD-17 잔여). ⑵의 단계는 각 단계의 근거(FR-6·13, NFR-1) 그대로다: 기록은 재개가 id를 유지하는지 바꾸는지를 말하지 않으며, S2-3의 재기동이 어느 run을 이어갈지를 어떻게 아는지도 정하지 않았다 — 어떤 구성요소도 이름의 순서에 기대서는 안 되므로 이름의 순서는 그 수단이 아니다. S3-1의 "과거 run 목록"은 FR-6 근거 그대로다: `runs/`의 나열에서 형식의 이름들은 시각 부분의 순서로 놓이나 그것은 규칙으로 만든 id에서 id를 만든 시계의 값의 순서이고, id는 run에 대해 아무것도 말하지 않으므로 목록이 run에 대해 보여 주는 것은 그 run의 파일에서 온다. ⑶의 단계는 달라진 것이 없다: S5-1의 키 → run 조회는 하위 질문 ② 그대로이고 id는 hw_profile도 연산도 싣지 않으며(run이 자기 hw_profile 키를 적는 자리는 `instance.json`, ADR-0018), 확장 S10-1·2는 확장 호환 그대로다 — 복원은 id의 형식에 기대지 않는다. 형식이 유효성 규칙이 아니므로 이 기록에 의해서는 이 단계들에서도 id가 그 형식이 아니라는 이유로 run이 거부되거나 달리 다뤄지지 않는다. 데이터 repo의 두 clone에서 생긴 run들을 합치는 단계는 어느 시나리오에도 없다(두 clone을 맞추는 방법과 repo 하나를 넘는 유일성은 OD-25). 어떤 시나리오 단계도 id의 길이, 두 부분의 표기, 난수 비트의 수, 이름의 순서에 기대지 않는다. **2026-10-09 (3차, OD-8 잔여 중 `instance.json`에서 라운드당 후보 수를 적는 멤버 확정 — [ADR-0028](decisions/ADR-0028-od8-instance-record-candidates-per-round.md))**: 규칙을 다음 세 묶음에 재적용했고 **판정 변화는 없으며 갭도 없다**. ⑴ instance가 파라미터와 함께 시작되는 단계(S1-2, S1-b-2, S2-1, S3-3, S6-1, S8-1). ⑵ 라운드가 후보를 만들고 평가하는 단계(S0-4·5, S1-3·4·6, S1-b-2, S2-2, S8-2·3·4). ⑶ 비용과 budget이 세어지는 단계(S1-7, S2-5, S8-5). ⑴ S1-2의 "N=1"과 S8-1의 "instance 파라미터로 라운드당 후보 수 N(초기 UI 선택 범위 1~5)을 지정한다"는 FR-1 근거의 지원 그대로이고, run이 그 N을 적는 자리(`instance.json`의 최상위 멤버 `candidates_per_round`, 1 이상의 정수)가 확정분이 되었다; S1-b-2는 S1-2를 따르고, S2-1·S3-3·S6-1은 N을 들지 않는다. 유효한 파일에 그 멤버가 없을 수 있고 그때 값이 대신 들어가지 않는다(1도 아니다) — instance의 시작이 N 없이 시작하기를 거부하는지와 instance가 N을 적었는지를 어디서 확인하는지는 OD-8 하위 질문 ㉕ (가)로 새로 등재되었다(지원(미결) 그대로). S3-3의 분기가 다른 N으로 이어질 때 한 번 쓰이는 파일과 어떤 관계인지는 OD-8 하위 질문 ① 그대로다. ⑵의 단계는 각 단계의 근거(FR-1·5·7·9·10) 그대로다: S8-2의 "N개의 코더 호출"에서 spec의 후보 식별은 OD-6 확정분(ADR-0002) 그대로이고, 기록은 멤버와 spec의 `id.candidates` 사이에 규칙을 더하지 않았다 — 두 수가 같아야 하는지·어느 라운드에서 그런지·무엇이 확인하는지는 ㉕ (나)로 새로 등재되었다(OD-23·OD-28·OD-29와 함께; 지원(미결) 그대로).
