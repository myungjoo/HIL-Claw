# Open Decision 제안 상세 (Proposals)

[Requirements.md](Requirements.md)의 Open Decisions 등록부에 등재된 각 항목의 **구체 제안·근거 본문**을 같은 번호 절에 둔다. 등록부에는 한 줄 요약만 남겨 표가 읽히도록 유지한다.

- **정본 분담**: 항목의 **상태·논의 위치**는 등록부(Requirements.md)가 정본, **제안 본문**은 본 문서가 정본이다. 제안이 바뀌면 본 문서를, 상태가 바뀌면 등록부를 같은 커밋에서 갱신한다.
- 제안은 결정이 아니다. 확정은 오너가 #4/#5에서 내리거나 설계 수준 OD에 한해 [PROCESS/DRIVER.md](../PROCESS/DRIVER.md) §9의 경로(ADR + 리뷰어 Approve + 오너 통지)로 내리고, 등록부 상태가 `확정`으로 바뀐 뒤 본문(FR/NFR)에 반영된다.
- 출처 표기: **#4** = 아키텍처 결정 스레드, **#5** = 사용자 입력 대기 목록, **#7** = 외부 조사(상설; `§n` = S-1 조사 본문 절, `보충 §2(n)` = S-1 보충 코멘트), **#8** = 모순 트래커, **(Bn)** = [reviews/2026-09-03](reviews/2026-09-03-StandardScenarios-LiteratureReview.md) 보강 제안.
- **기록 규칙**(2026-10-16 정리): ADR이 확정한 내용은 ADR 파일이 정본이며 본 문서에 다시 서술하지 않는다. 각 절에는 열린 제안 본문, 하위 질문의 문구, 채택된 ADR마다 한 줄(`- **채택분** [ADR-NNNN](…) — 다룬 것 (답함: 하위 질문 ⑮)`)만 둔다. 하위 질문이 일부·전부 답해지면 날짜별 주석을 덧붙이지 않고 그 질문 끝의 상태(`→ 부분 답: [ADR]…. 남음: …` / `→ 답함: [ADR]` / `→ 미결.`)와 bullet 머리의 상태어(미결 / 일부 답함 / 답함)를 그 자리에서 고쳐 쓰고, 질문의 문구는 답해진 뒤에도 남긴다. 등록부 행의 글을 옮겨 오지 않는다. 지난 서술은 git 이력에 있다.

## OD-1

**Objective type 메뉴** — #5 A-4. **MVP 메뉴의 틀 확정(2026-10-13, [오너 답변 HQ-0009](https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6136238336))** — type의 전체 목록·throughput의 양과 단위·결합 규칙은 #5 A-4 대기 그대로다.

- **확정분(2026-10-13, 오너 답변 HQ-0009; 오너의 결정이며 이의 기간의 대상이 아니다)**: instance는 objective type의 **목록**(type마다 선택적 weight 또는 priority; 방향은 type의 것)과 constraint type의 **집합**을 말한다. 둘 이상의 objective를 결합하는 규칙(priority order, weighted sum, Pareto)이 A-4에서 정해질 때까지 instance는 objective를 정확히 하나 말하고 weight도 priority도 말하지 않는다 — 그 멤버들은 뒤에 스키마가 바뀌지 않도록 있다. 메뉴의 **최소분**(목록이 아님): ① latency 최소화 — 하네스 타이밍 실행이 재는 커널 호출의 시간, 낮을수록 좋음. 이것은 초기 개발의 출발점일 뿐이다: latency 최소화와 throughput 최대화 둘 다 제공 대상이고 어느 것을 말할지는 instance마다 사용자가 run 시점에 고른다(FR-2). 다만 throughput의 양과 단위가 정해지지 않았고, instance는 양과 단위가 정해진 type만 말할 수 있으므로 그때까지 instance가 말할 수 있는 type은 latency 최소화뿐이다. ② 제약 type 메모리 상한 — 그것을 재는 실행 지점에서 커널 실행이 쓰는 메모리(피연산자 포함)의 바이트 단위 상한; 상한을 넘은 후보는 infeasible이며 objective로 비교하지 않고, 라운드 루프가 그 후보에 하는 일은 같은 실행 지점에서 correctness 검사가 실패했을 때 FR-1이 하는 일이다; 제약은 instance마다 선택 사항이고 첫 커밋 예시는 값을 싣지 않는다; 그 밖의 제약 type은 뒤의 기록이 #5 A-4 아래에서 첫 사례를 바꾸지 않고 더한다. 아래 제안 "단일 목적 + 선택적 제약(메모리 상한)"은 **확정되지 않았다**. README의 목표(속도와 동시 서빙 용량)는 최종 목표로 남고 MVP는 그 부분집합이다(#8 M15). 오너의 주: 시스템의 최종 목표는 대규모 시스템에서의 대규모 모델 서빙의 최적화이고, 고정 shape의 GEMM은 대상 모델의 여러 연산 가운데 하나다 — 어떤 기록도 다른 연산이 무시할 만하다거나, latency와 throughput이 일반적으로 일치한다거나, objective 어휘가 커널 latency로 좁혀졌다고 가정하지 않는다. 반영 기록: [ADR-0050](decisions/ADR-0050-od6-task-objective-members.md) (spec의 `task.objective` 표기, OD-6 절) · [ADR-0052](decisions/ADR-0052-od13-memory-ceiling-measurement.md) (첫 사례의 로컬 구성에서 메모리 상한을 대신하는 측정, OD-13 절 — `memory_ceiling`은 그 기록의 조건이 채워질 때까지 허용되지 않는다) · [ADR-0053](decisions/ADR-0053-od8-instance-record-objective.md) (`instance.json`의 `objective` 멤버, OD-8 절). 이 기록들은 아래 잔여의 어느 것도 정하지 않았다.
- **잔여(#5 A-4 대기 — 오너 전용)**: type의 전체 목록, throughput 최대화의 양·단위, 동시 서빙 capacity, 결합 규칙과 weight·priority의 타입·뜻·값, 아래 *확장 고려(B2)*. 개선 인정의 여유(δ)와 방향 너머의 순서는 OD-13·OD-1 그대로다.
- 제안: MVP는 "단일 목적 + 선택적 제약(메모리 상한)"만, 가중조합/Pareto는 후속. 후보 메뉴: latency 최소화 / throughput 최대화 / 동시 서빙 capacity 최대화 / 메모리 상한 내 latency 최소화(제약형).
- *확장 고려(B2)*: HW 이론 한계(speed-of-light/roofline) 대비 달성률을 target·정지 어휘에 포함할지. "이전 대비"가 아닌 "HW 한계 대비" 평가는 2025~26 커널 생성 시스템의 공통 요소(#7 S-2 사실 요약).
- README의 다목적 목표("속도 향상 및 동시 서빙 용량 증대")와의 관계는 A-4 확정 시 Scope 또는 README에 명시(#8 M15).

## OD-3

**Gate 후보 목록 + 강제 안전 gate** — #5 A-5 · #7 §6.

- 제안: **비-설정형 최소 gate 4종** — 승격 게이트 / 신규 바이너리 첫 실물 실행 / board health 실패 / roofline 위반. "autonomous"는 탐색에 gate 없음이지 실물 승격에 없음이 아님.

- (2026-10-15) [오너 결정](https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6182984913) 2항: 툴체인·환경 변경의 허락 요청은 autonomous를 포함한 모든 gate 모드에서 run을 멈춘다(FR-4). autonomous에서도 강제되는 정지가 적어도 하나 있다는 것만 답해졌고, 위 제안의 gate 4종과 모드별 기본 구성은 채택도 기각도 아니다.

## OD-4

**hw_profile / op_signature 키 스키마** — #4 코멘트 · #7 §6. 확정분은 아래 채택분(ADR이 정본)과 [등록부](Requirements.md) 행을 본다.

- **채택분** [ADR-0001](decisions/ADR-0001-od4-key-schema.md) — 키 스키마의 P1 최소분(정확 식별층, 정확 일치 조회; hw_source는 키가 아닌 속성)
- **채택분** [ADR-0008](decisions/ADR-0008-od6-gemm-kernel-contract.md) — 첫 `layout` 값 `row_major`(OD-6 절의 `gemm` 계약 기록; GEMM 12개 op_signature의 이름은 그 기록의 결정 9)
- **채택분** [ADR-0035](decisions/ADR-0035-od4-cpu-standin-hw-key-values.md) — `cpu_standin` hw_profile의 hw 키 필드 값을 얻는 방법
- **채택분** [ADR-0036](decisions/ADR-0036-od4-cpu-standin-host-os-macos-version.md) — macOS에서 제품 버전 줄에 공백·탭이 든 경우의 `host.os`
- **제안으로 남는 부분(미확정)**: 유사도 벡터층과 "최근접 = prior로만", 아래 *확장 고려(S10)*, op의 "정규화 IR 구조해시"(IR 부재 — OD-9). 첫 인스턴스에 대해 미정인 것: 실제 머신의 값(기록들은 가상의 예만 담는다), `hw_source`의 값(레코드를 만드는 쪽이 말하고 머신에서 읽지 않는다; `cpu_standin`의 hw_profile이 그 CPU가 무엇이든 항상 정해진 한 값을 말하는지, 그렇다면 어느 값인지는 OD-26), 누가 언제 등록하는지(OD-26), SDPA의 shape 멤버(ADR-0001 Boundaries), `cpu_standin`이 아닌 accelerator의 키 필드 값.
- 제안: **2층 구조**. 정확 식별층(op: 정규화 IR 구조해시 + 전체 인자튜플 + dtype/layout; hw: 칩 + 리비전 + **펌웨어·드라이버·툴체인 버전**) + 유사도 벡터층(FLOPs, 이동 바이트, arithmetic intensity, working set ÷ SRAM …). 정확 일치 = 캐시 히트, 최근접 = **prior로만**. TVM/TenSet 선례.
- hw 식별층 필드 후보: **HW 출처(hw_source: 외부 타사 / 자사 개발 중)** 와 revision — 자사 개발 중 HW는 revision마다 성능 특성이 바뀌므로 이력 귀속 키가 필요(FR-14 ④, OD-26).
- *확장 고려(S10)*: 재현 시 노이즈 범위를 넘는 차이가 나면 환경 변화(드라이버/펌웨어/호스트)를 새 hw_profile 키 후보로 표시.
- **첫 구체 인스턴스(#5 B-4, 2026-10-02)**: hw = `cpu_standin`(오너 로컬 PC, Windows/WSL; 이후 LAN 머신) · op = Llama 3.2 1B 디코더 projection GEMM — gate/up(2048→8192), down(8192→2048), QKV(2048→3072), O(2048→2048), M∈{1, 32, 512}, fp32(layout은 B-4에 없음 — [ADR-0008](decisions/ADR-0008-od6-gemm-kernel-contract.md)이 `row_major`로 확정); 2차 = 같은 모델의 KV cache 포함 SDPA(GQA 16/8, head_dim 64, causal). → 설계 함의(제안): op_signature는 (op 종류, M·N·K 또는 seq·head 구성, dtype, layout)을 담고 **M(토큰 수)이 instance 파라미터**임을 키 설계가 수용해야 한다.

## OD-5

**정확도-성능 trade-off 정책** — **확정(2026-10-01, #5 A-6)**: hard floor.

- 결정 내용: 정확도는 게이트. tolerance는 사용자 instance 파라미터(어휘는 B-7 후 확정). 실패 = repair/탈락, best·통계 미반영. sim·board 양쪽 동일 floor. FR-3 ④ 조기 종료는 승격 게이트 수준 재검증 후 인정. 정확도의 목적 축 승격은 A-4 다목적과 함께 후속.
- 근거(#7 §5 G1): 목적 축으로 두면 옵티마이저에 정확도를 팔 권한을 명시 부여하는 것. Sakana 정정 후 집계 speedup 3.13× → 1.49×; METR: KernelBench 최적화의 73.8%가 프록시 지표만 개선, 예산이 클수록 악화(10스텝 26.4% → 100스텝 57.8%).
- 귀결: 더 느슨한 tolerance에서 더 빠른 후보가 있으면 시스템은 보고만 하고 채택하지 않는다 — 채택은 사용자가 tolerance를 바꾼 새 instance로(FR-9에 반영).
- 잔여: tolerance 어휘(#5 B-7) — **첫 사례(`cpu_standin`·`gemm`·fp32·C 커널)에 한해 오너가 답했다**([HQ-0004 답변](https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6052377983), 2026-10-08; 반영: FR-9, [ADR-0017](decisions/ADR-0017-od16-cpu-standin-verification-run.md) 결정 5·6): 어휘는 원소별 `rtol`·`atol`(둘 다 instance 파라미터)이고 출력의 모든 원소에서 |out − ref| ≤ atol + rtol·|ref|일 때만 통과하며, 출력의 NaN·무한대는 실패다(전제: 이 사례의 검증 입력은 유한하게 뽑는다). 기본값은 없다 — instance가 `rtol`·`atol`을 둘 다 명시하고 하네스는 기본값을 갖지 않는다. 이 답은 그 사례에 한한 것이고 B-7의 일반 답이 아니다: 다른 dtype의 tolerance, downstream 지표 임계(MLPerf식 99%/99.9% 등), 벤더 golden output, user-defined 검사는 #5 B-7 답변 후 확정 그대로다. per-kernel 검사와 downstream 지표 floor의 병행 여부도 그때 어휘와 함께 정한다.

## OD-7

**기법 통계 환류 경로** — #4 코멘트 · #7 §6.

- 제안: 빈도 카운트가 아니라 **contextual bandit**(OpenTuner AUC-Bandit: 최근 개선 빈도 곡선의 AUC + UCB). latency 모델 없이 1라운드부터 동작.
- **흡수: 카탈로그 진입 기준**(#7 보충 §2(4)) — 등재 자격 = (held-out correctness 통과) ∧ (실 board 측정) ∧ (격리 평가자 PASS). selector·coder의 주장만으로는 불가. **검증 없이 쌓으면 카탈로그가 부패한다**(Voyager ablation: 자가검증 제거 시 버그 코드가 스킬 라이브러리에 축적). ExpeL식 `cases/`(불변 사례) + `insights/`(가변 규칙, ADD/EDIT/UPVOTE/DOWNVOTE + `supported_by` 출처) 분리 검토.
- *확장 고려(B6)*: 저장 단위를 통계에 더해 "변환 전/후 코드 쌍 + 개선 이유 요약"으로 확장.
- N후보(S8, MVP)에서는 board 미승격 후보의 sim 결과도 통계 입력이 되므로 "sim만 평가됨 vs board 평가됨"을 구분해 집계(OD-20 단계별 분리 평가 필드).
- **확정분(오너 결정 2026-10-13)**: 통계와 별개로 **가설–결과 사례**(가설·판정·원인, 기각·실패 포함)를 키 디렉토리에 저장하고 같은 키의 이후 run이 조회한다(FR-18). 위 ExpeL식 분리에서 `cases/`(불변 사례)에 해당하는 쪽이 요구가 되었고, 그 필드·파일은 OD-30이다. bandit 등 랭킹 신호, 카탈로그 진입 기준, `insights/`(가변 규칙)는 본 항목에 남는다.

- **후보 ①「레이아웃 = 권한 모델」**: 에이전트마다 **쓰기 루트 1개**를 지정하고 **그 외 전부 read-only**(읽기는 무제한 — 읽기 제한은 채택하지 않음). *(OD-16과의 관계: OD-16이 은닉이 아닌 **위조 불가능성** 기반으로 개정되어 충돌 없음. 단 **런타임 시드·입력 값은 파일로 존재하지 않아야** 한다 — 이것이 읽기 개방의 유일한 전제. 또한 **코더/평가 프로세스 분리**가 OD-16 위협 A(조작 계열)를 담당한다.)*

  2. 폴더 모델 **밖의 특수 케이스 3**: `.git/`(에이전트 전원 쓰기 금지 — 이력 재작성 = 감사 로그 파괴, NFR-2), `events.ndjson`(도구 계층이 append하므로 에이전트 쓰기 권한 불필요), `TMPDIR`·빌드 캐시(쓰기 루트 안에 둘 것 — 누락 시 빌드 실패).
  3. 쓰기 루트는 **라운드로 파라미터화하되 에이전트가 선택 불가**, supervisor가 주입.
  4. 강제 백엔드 2개(정책은 하나): 코더 = **OS 경계**(저장소 read-only 마운트 + scratch, 셸 허용), in-process subagent = **`PreToolUse` 경로 검사**(→ Bash 금지, 특권 동작은 타입 있는 도구로: `sim.run`/`board.run`/`coder.run`). *(#5 B-6으로 Windows는 WSL 전제이므로 OS 경계는 Linux/macOS/WSL 공통 수단으로 구현 가능; 컨테이너(Docker/Podman)를 C-7의 머신 모두에서 쓸 수 있고 MVP가 요구해도 된다는 것은 [오너 답변 HQ-0010](https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6136555026). 앞 절반(코더 = OS 경계)은 첫 사례의 코더 호출 하나에 대해 [ADR-0049](decisions/ADR-0049-od8-coder-call-isolation-means.md)가 컨테이너 형태로 채택했다 — "저장소 read-only 마운트"는 요구로 채택하지 않았다(체크아웃을 안에서 읽기 전용으로 보이는지는 ㉝ (다)). 뒤 절반(`PreToolUse` 경로 검사)과 1의 강제·5는 남고, 2·3은 코더 프로세스에 대해서만 채택되어 다른 행위자에 대해서는 남는다.)*
  5. **흡수: per-agent tools allowlist**(#4 §6) — frontmatter 도구 허용목록은 경로 정책의 도구 단위 표현이므로 본 후보와 함께 확정.
- **이점**: 권한이 문서가 아니라 디렉토리 구조에 새겨져 git diff 검증이 자명해지고, `.claude/` 재귀 문제(강제 장치가 강제 대상 안에 있음)가 부수적으로 해소되며, **OD-14와 사실상 같은 결정으로 수렴**.
- **전제조건**: 대상 toolchain의 **out-of-tree 빌드 지원 여부**(#5 B-1) — 인플레이스 빌드 강제 시 저장소를 scratch로 복사 후 diff 반입하는 우회 필요(라운드마다 복사 비용).
- **후보 ②「scratch 복사 + diff 반입」**(2026-10-02, C-7에서 파생한 **통합자 제안** — 후보 ①과 비교 대상, 선택되지 않음): 코더에게는 커널 소스·spec·빌드 스크립트 등 **필요한 파일만 scratch 디렉토리로 복사**해 주고 결과를 diff로 반입한다. 하네스·reference·측정 스크립트는 애초에 복사되지 않으므로 "코더가 하네스를 수정할 수 없다"가 마운트 권한이 아닌 **구조**로 보장되고, Linux/macOS/WSL 어디서나 동일하게 동작한다(컨테이너·read-only 마운트 불필요). 후보 ①의 "쓰기 루트 1개" 원칙과 양립하며(scratch가 곧 쓰기 루트), 라운드마다 복사 비용이 들지만 커널 소스는 작다. 읽기 개방 원칙(OD-16)은 "코더가 저장소를 읽을 수 있다"가 아니라 "읽어도 방어가 성립한다"이므로 후보 ②가 읽기를 제한하는 것은 아니다 — 필요한 참고 자료는 spec으로 동봉(OD-6). *(복사해 넣고 결과를 반입하는 것은 첫 사례의 코더 호출 하나의 경계 통과 방법으로 [ADR-0049](decisions/ADR-0049-od8-coder-call-isolation-means.md)가 채택했다 — 경계 자체는 후보 ① 4의 앞 절반(컨테이너)이다. "컨테이너 불필요"라는 성질은 쓰지 않았다: 본 후보만으로는 같은 사용자의 셸을 가진 코더 프로세스의 쓰기를 막지 못하고 다른 곳에 쓴 것이 산출물로 읽히지 않게 할 뿐이다. 반입되는 것은 첫 사례에서 diff가 아니라 온전한 파일이다([ADR-0055](decisions/ADR-0055-od23-coder-output-form.md)).)*
- 잔여(제안 유지): **격리 수단 후보 ①「레이아웃 = 권한 모델」(OS 경계: read-only 마운트 + scratch) / 후보 ②「scratch 복사 + diff 반입」(하네스·reference를 복사하지 않아 구조적으로 격리; C-7 크로스플랫폼에 유리)** — 첫 사례의 코더 호출 하나는 [ADR-0049](decisions/ADR-0049-od8-coder-call-isolation-means.md)가 답했고(컨테이너 가용성은 [오너 답변 HQ-0010](https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6136555026)), 남은 것은 후보 ①의 나머지(1의 강제·다른 행위자에 대한 2·3·4 후반·5)와 하위 질문 ㉝이며 #5 B-1이 답해지면 그 수단을 다시 판단한다; 이벤트 종류와 페이로드, `STATE.json`의 나머지 멤버(gate 상태 = OD-3, `best_ref` = OD-20, lock = OD-17 잔여, `phase`·`next_action` = OD-23·OD-29)와 `instance.json`의 나머지 멤버·결과 파일의 필드·스키마, `run_id`에 관해 남은 것(시작에서의 확인과 시스템이 만들지 않은 id), 그리고 하위 질문 ①~㊱의 남은 부분(각 항목의 상태) — 상세는 위 "제안으로 남는 부분".

## OD-14

**샌드박스·격리·보드 안전 정책** — #7 §5 G1.

- 제안: **1 후보 = 1 프로세스**(치명적 오류를 겪은 디바이스 컨텍스트는 오염되어 이후 측정 전부 무효) · **계층 타임아웃**(커널 워치독 < 호출 < 서브프로세스 SIGKILL < 라운드 < run) · 디바이스 메모리/그리드 상한 선언 · 후보 간 health check와 reset 에스컬레이션 · 보드를 멈춘 후보는 **content hash로 영구 blacklist**(FR-6 재개도 준수 — FR-6 본문에 단서 필요, #8 M6).
- 기록과의 관계: [ADR-0009](decisions/ADR-0009-od13-cpu-standin-timing-run.md)·[ADR-0017](decisions/ADR-0017-od16-cpu-standin-verification-run.md)은 `cpu_standin`의 타이밍·검증 실행을 별도 프로세스로 정했고 [ADR-0052](decisions/ADR-0052-od13-memory-ceiling-measurement.md)는 메모리 상한을 자원 상한으로 강제하지 않고 측정으로 판정하도록 정했다 — 모두 메커니즘의 선택일 뿐 위 제안("1 후보 = 1 프로세스" 포함)의 채택도 기각도 아니며, 그 프로세스는 보호되지 않는다(커널이 프로세스 밖에 닿는 것을 막는 것이 없다 — ADR-0017 결정 10). 샌드박스·격리·자원 상한·타임아웃 계층은 미결 그대로다.
- **쓰기 범위 정책은 OD-8 후보 ①/②와 동일 결정으로 수렴** — 거기서 함께 확정. C-7(#5 B-6): 격리 수단은 POSIX(Linux/macOS/WSL) 전제다. 컨테이너 가용성은 [오너 답변 HQ-0010](https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6136555026)으로 답해졌고, 첫 사례의 **코더 호출 하나의 쓰기 범위**는 [ADR-0049](decisions/ADR-0049-od8-coder-call-isolation-means.md)가 정했다(컨테이너 안에서 쓰기 가능한 호스트 경로는 그 호출의 scratch 디렉토리 하나뿐). 그 수단은 생성된 커널의 빌드·실행을 덮지 않고(그 기록의 L3) 시간·자원 상한도 두지 않으며(L7), 보호되지 않는 프로세스가 컨테이너 런타임을 통해 사용자 자신의 파일보다 더 많은 것에 닿을 수 있다는 한계(L11 — 확인하지 않음)를 남긴다. 본 절의 제안(1 후보 = 1 프로세스, 계층 타임아웃, 자원 상한, health check, blacklist)은 채택도 기각도 아니다.
- **오너 결정(2026-10-15, [1·2항](https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6182984913))**: 툴체인, 그리고 커널의 빌드·correctness 실행·타이밍 실행은 격리 환경 — 코더 호출처럼 컨테이너([ADR-0049](decisions/ADR-0049-od8-coder-call-isolation-means.md)) — 을 쓴다. qemu·chroot·venv는 이 격리 수단이 아니다. 툴체인·환경의 변경은 무엇이 왜 필요한지 사용자에게 알리고 허락을 받은 뒤에만 설치·갱신하며(컨테이너는 그 이미지), 허락이 없으면 아무것도 바꾸지 않는다; 허락 요청은 모든 gate 모드에서 run을 멈춘다(FR-4; OD-8 ㉝).
- **통합자 주(2026-10-15)**: 정해진 것은 수단의 종류와 허락의 규칙뿐이다. 빌드·실행을 호스트의 보호되지 않는 프로세스로 적은 기록([ADR-0009](decisions/ADR-0009-od13-cpu-standin-timing-run.md)·[ADR-0017](decisions/ADR-0017-od16-cpu-standin-verification-run.md) 결정 10·[ADR-0052](decisions/ADR-0052-od13-memory-ceiling-measurement.md)·[ADR-0056](decisions/ADR-0056-od18-correctness-check-verification-executable.md), 그리고 측정되는 빌드가 호스트의 것이라는 ADR-0049 L3·L6)과 코드(`local_run`·`clang_build`)는 아직 바뀌지 않았다 — 아래 ①이 답해지면 그것들을 대체하는 기록이 필요하다. 위 제안(1 후보 = 1 프로세스, 계층 타임아웃, 자원 상한, health check, blacklist)은 채택도 기각도 아니다. qemu는 격리 수단은 아니지만 다른 아키텍처의 에뮬레이션·sim 백엔드 후보로는 남는다([ADR-0038](decisions/ADR-0038-od18-cpu-standin-execution-points.md); OD-18 절).
- **채택분** [ADR-0117](decisions/ADR-0117-od14-cpu-standin-time-limits.md) — 첫 사례 `cpu_standin`의 검증 빌드·프로세스와 타이밍 빌드·실행의 시간 제한의 출처와 첫 값 — 계층 타임아웃 가운데 호출 수준 (부분 답: OD-18 하위 질문 ⑲ (라)의 시간 제한)
- **하위 질문(오너 결정 2026-10-15에 딸린 것, 2026-10-15 등재, 미결)**: ① 빌드·실행 컨테이너의 설계 — (가) ADR-0049의 성질 P1~P4 가운데 무엇이 그대로 적용되는지와 네트워크 차단·자원 상한, (나) 이미지 — 무엇이 들어 있고 누가 만들고 갱신하는지, 빌드와 실행이 같은 이미지를 쓰는지, 코더 호출의 이미지와 같은 이미지인지(ADR-0049 L6, PLAN P2-2), 이미지 식별을 빌드 설정과 함께 기록하는지(NFR-2; `build.json` — ADR-0004 결정 3), (다) 호출마다 컨테이너를 새로 띄우는지 재사용하는지(ADR-0056의 호출마다 빌드와 함께), (라) 데몬 권한(rootless·Podman)과 macOS·WSL에서 어느 런타임을 쓰는지, 그리고 macOS·WSL에서 코더 컨테이너와 측정 컨테이너가 같은 OS·아키텍처인지(ADR-0049 L6; OD-8 ㉝ (라)와 함께), (마) 컨테이너 안에서 얻은 타이밍·최대 resident set이 ADR-0009·ADR-0052의 수치와 같은 것인지(OD-13 ⑪과 함께)와 `cpu_standin` hw 키 값이 기술하는 머신([ADR-0035](decisions/ADR-0035-od4-cpu-standin-hw-key-values.md): 커널을 빌드하고 실행하는 머신; macOS의 `host.os`는 [ADR-0036](decisions/ADR-0036-od4-cpu-standin-host-os-macos-version.md))이 컨테이너 안인지(OD-4와 함께), (바) 실 board에서 커널을 실행할 때의 격리(보드 안전과 함께).

## OD-15

**sim→board 승격 기준** — #7 §6.

- 제안: **고정 임계값 금지**. (hw_profile, op_class)별 **rank correlation·recall@k를 측정해서** 승격 폭 k 결정. compute-bound와 memory-bound는 다른 k 필요. **sim이 거부한 후보용 ε-greedy 슬롯 상시 확보**(없으면 sim 편향을 영구히 감지 불가) · 매 라운드 sim/board 상관 추적, 열화 시 gate 발동 · **board 측정만이 기록(record)을 세울 수 있음**.
- **correctness 관점의 sim 검증**(FR-1 ⑶ 연동): sim 통과·board 실패는 triage 후 sim 결함으로 분류되면 escalate되어 sim 개선 입력이 된다. 그러나 **반대 방향(sim 실패·board 정상 = false negative)은 구조적으로 관측되지 않는다** — sim이 거부한 후보는 board에 올라가지 않으므로. 정상 커널을 계속 repair하는 낭비가 보이지 않게 발생할 수 있으므로, **ε-greedy 슬롯이 성능뿐 아니라 correctness false negative 탐지도 겸하도록** 설계.
- N후보(OD-21 확정)에서 k의 결정 방식은 OD-29에서 본 항목의 상관 기반 방식과 고정 파라미터 방식 중 택한다.

## OD-16

**측정·검증의 위조 불가능성(anti-reward-hacking)** — #7 §5 G1. **본 조사 최대 리스크.** 확정분은 아래 채택분(ADR이 정본)과 [등록부](Requirements.md) 행을 본다.

- **원칙(2026-07-31 개정): 은닉이 아니라 위조 불가능성.** 전부 읽혀도 성립하는 방어만 채택한다(Kerckhoffs). 유일한 예외는 **런타임 시드·입력 값이 파일로 존재하지 않을 것** — 알고리즘은 읽혀도 되고 값만 없으면 된다. → **읽기 제한은 채택하지 않으며 OD-8 후보 ①과 충돌하지 않는다.** 근거: 성능 최적화 시스템에서 정답을 알아도 **베끼면 speedup 1.0이라 이길 수 없고**, harness 은닉은 security-by-obscurity이며(루프홀은 소스를 읽어야만 발견되지 않는다 — 없애는 것이 진짜 방어), 문서·기존 커널 읽기는 저밀도 언어 대응(FR-14)과 콜드스타트(OD-22)에 오히려 필요하다.
- **MVP 최소분(FR-9에 반영됨)**: 코더에 노출되지 않은 입력(shape/seed)으로 코더가 수정할 수 없는 격리 하네스에서 재검증; 실패 결과는 best·통계 미반영; 조기 종료 전 재검증.
- **위협 A — 조작 계열**(출력 버퍼 절도 · harness/타이머 패치 · 점수 레코드 조작 · 감사 로그 조작): **코더와 평가를 별도 프로세스로 분리 + 쓰기 격리**로 소멸한다(OD-8 후보 ① / OD-14). Sakana 사건의 버퍼 절도는 reference와 후보가 같은 프로세스에서 버퍼를 공유했기 때문에 성립했다. (첫 사례에서 코더 프로세스가 자기 호출 동안 하는 harness·타이머 패치와 점수·로그 조작은, 컨테이너에 주어진 파일 시스템을 통한 것에 한해 [ADR-0049](decisions/ADR-0049-od8-coder-call-isolation-means.md)의 컨테이너 경계로 막는다 — 경계의 성립은 런타임 인수 항목. 위협 A는 소멸하지 않았다: 경계 밖에서 빌드·실행되는 커널의 같은 조작, 컨테이너 런타임을 부릴 수 있는 사용자 권한, 네트워크로 닿는 서비스를 통한 변경, 버퍼 절도는 OD-14·OD-16 잔여.)
- **위협 B — 산출물 퇴화 계열**(생성 커널이 일을 하지 않음): 치팅이 코더의 정당한 산출물인 소스 안에 있으므로 **격리로는 잡히지 않고 측정 설계로 잡는다**. ⑴ 하드코딩 출력 → **매 trial 런타임 무작위 입력**(값 비파일화) ⑵ 계산 누락 → 오라클 강화(FP32/FP64 CPU 레퍼런스 · opschema 기반 퍼징 · per-(op,dtype) tolerance · 코너케이스 subnormal/zero/inf/NaN/catastrophic cancellation) ⑶ 벤더 라이브러리 디스패치 → **정적 검사**(규칙이 읽혀도 무방 — 우회하려면 위반해야 하고 위반은 탐지된다) + **프로파일러로 해당 커널의 실제 실행 확인** ⑷ 다른 큐/스레드로 회피 → 전체 디바이스 배리어 + 호스트 wall-clock 교차검증 + **roofline(speed-of-light) 상한** ⑸ **타이밍 반복 구간 캐싱**(정확도는 입력을 바꾸지만 성능 측정은 같은 입력을 N회 반복하는 것이 정상이라 열리는 틈) → 매 trial 새 버퍼 할당 · 캐시 플러시 · **1회차 이후 시간 급감 탐지** ⑹ **순서 의존성 테스트**(reference→candidate와 candidate→reference 결과가 다르면 실격).
- **`private_metrics` 재정의**: 은닉 지표가 아니라 **일반화 측정 지표** — 평가에는 쓰되 최적화 대상에는 넣지 않는다. 실배포에서는 대상 shape 분포를 코더에게 알리는 편이 맞다(벤치마크와 위협 모델이 다름).
- **방어가 여전히 필요한 이유**: 코더가 악의를 갖기 때문이 아니라 **탐색 루프가 가장 싼 경로를 고르기 때문**이다. 루프홀이 있으면 결국 선택되고, 그 결과는 board 시간 낭비 · **크로스런 통계 오염(FR-7)** · 잘못된 바이너리 승격이다.
- **흡수: 조기 종료 재검증**(#7 보충 §2(2), #8 M18) — FR-3 ④의 target 조기 달성은 해킹된 결과의 전형적 징후이므로 조기 종료 인정 전 승격 게이트 수준의 재검증을 강제(FR-9에 반영됨).
- **확장(S7, B1/B8)**: 정밀도 하향 검사, warm-up·stream sync·클록 고정 타이밍, 정적 검사·금지 패턴, LLM 검증자, 검증·프로파일 스크립트 보호, 금지 fallback 패턴, 코더 웹 검색 차단(OD-12). 실패 유형 태깅과 다음 라운드 spec의 금지 패턴 주입(OD-6 확장 고려).
- **하네스 자체의 수용 기준**(#7 S-2 N8): Kernel Contracts의 3-상태 캘리브레이션(위반 구현이 실제로 잡히는지 증명)을 하네스 완료 조건으로 채택 검토 — hacker-fixer 루프와 상보.
- **채택분** [ADR-0003](decisions/ADR-0003-od16-harness-calibration.md) — 3-상태 캘리브레이션을 검증 하네스의 수용 기준으로 채택(P1 필수 위반 부류는 위협 B ⑴ 하나)
- **채택분** [ADR-0017](decisions/ADR-0017-od16-cpu-standin-verification-run.md) — `cpu_standin` 검증 실행(`gemm`·fp32·C 커널; 오라클·tolerance 어휘·기본값 없음은 오너 답변 HQ-0004)
- **채택분** [ADR-0107](decisions/ADR-0107-od16-verification-and-timing-build-relation.md) — 첫 사례와 mock의 run에서 한 시도의 검증 빌드와 타이밍 빌드의 관계(실행 파일 수와 설정의 같음) (부분 답: 하위 질문 ⑥)

ExpeL식 분리(OD-7)에서 본 항목의 사례는 `cases/`이고 `insights/`는 OD-7·OD-24에 남는다.
- **라운드 0**: bring-up은 기법 적용이 아니므로 가설 레코드를 요구하지 않는 것을 제안한다. baseline 측정이 이후 가설의 `basis`가 된다.
- **조회해 싣는 사례의 선택과 양(일부 답함)**: 정확 일치 키의 사례가 적을 때는 전부 읽으면 되지만 쌓이면 선택 규칙(판정별·기법별 요약, 최근성, 상한)이 필요하다 — 선택 단계의 컨텍스트 비용과 맞바꾼다. 코더 spec에 다른 run의 사례를 싣는 자리도 미정이다(ADR-0002의 `feedback.attempts`는 같은 run의 시도만 가리킨다). 사례를 쓴 소스 commit·하네스 버전이 지금과 다를 때의 취급은 OD-11과 함께. → 부분 답: [ADR-0073](decisions/ADR-0073-od30-case-lookup-and-case-basis.md)(MVP 형태). 남음: 사례가 쌓일 때의 선택 규칙(판정별·기법별 요약, 최근성, 상한), 코더 spec에 싣는 자리, 소스 commit·하네스 버전이 다른 사례(OD-11).
- **가설 주입의 시점과 형식(일부 답함)**: ① instance 시작 시 — FR-15의 입력. `instance.json`은 한 번 쓰이는 파일이므로 주입 가설과 자료 포인터를 그 파일에 적을지 run의 다른 파일에 적을지. ② checkpoint의 gate — UC-2의 "방향 수정" 입력에 흡수하는 것을 제안. ③ autonomous run 도중 — gate가 없으므로 경로가 없다; 라운드 경계에서 읽는 입력 자리를 둘지, 지원하지 않을지. ②·③을 MVP에 넣을지는 범위 결정이므로 [PROCESS/DRIVER.md](../PROCESS/DRIVER.md) §9의 드라이버 ADR로 닫지 않고 오너에게 확인한다(HQ). → 부분 답: [ADR-0075](decisions/ADR-0075-od30-injection-at-instance-start.md)(①). 남음: ②·③과 그 MVP 포함 여부(오너, HQ).
- **주입 가설과 시스템이 세운 가설의 배분**: 주입이 있어도 시스템이 스스로 추가 가설을 세운다는 것은 요구다(FR-17, [오너 2026-10-13 보충](https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6136597638)). 미결은 그 순서와 비율 — 주입 가설을 먼저 시험하는지, 같은 라운드의 N후보에 섞는지, 선택 단계의 판단에 맡기고 규칙을 두지 않는지.
- **자료에서 가설을 도출하는 주체**: 논문 링크만 준 경우 누가 읽어 가설로 만드는가 — 오케스트레이터 쪽(코더의 직접 검색을 막는 OD-12 제안과 정합) vs 큐레이터 흐름(UC-5)을 먼저 거침. 자료가 불가용일 때는 FR-14 ③.
- **주입 가설과 카탈로그의 경계**: 주입된 가설이 지지 판정을 받았을 때 그것을 카탈로그의 기법으로 올리는 경로(UC-5 큐레이션, OD-7의 카탈로그 진입 기준, OD-24).
- **S6 수용 기준의 지표 정의·경계 사례·반복 수·대조군**: 오너가 정한 것은 "측정 가능한 수용 기준을 둔다"까지이고, S6에 적은 지표(같은 키·target·tolerance·N·budget의 두 번째 run이 첫 run의 best에 도달하기까지의 라운드 수가 더 적을 것, 사례 참조 하나 이상)는 **제안**이다. 미결: ① 경계 사례 — 첫 run의 best가 baseline(라운드 0)이거나 라운드 1에서 나왔으면 "더 적은 라운드"를 충족할 수 없다; 그런 쌍을 시험에서 빼는지, 지표를 바꾸는지(예: 같은 라운드 수에서의 best 비교). ② "도달"의 판정 — ADR-0007 결정 7은 두 표본 집합이 `different`인지 `not different`인지만 말하고 어느 쪽이 나은지는 말하지 않으며(방향 = OD-1) 측정 사이의 drift를 상쇄하지 않는다; 서로 다른 run의 측정을 견주려면 첫 run의 best를 다시 재야 하는지(OD-11의 incumbent 재측정 제안, OD-13 잔여의 paired 재측정). ③ 모델 출력이 비결정적이므로 한 쌍의 비교는 우연일 수 있다 — 몇 쌍을 돌려 어떻게 판정하는지, 사례 조회를 끈 대조 run을 둘지, 그 비용(C-7의 구독 한도)을 어디까지 쓸지.
- 위험: 과거 사례에의 anchoring(FR-15 원칙으로 막음), 검증 없는 축적으로 인한 부패(#7 보충 §2(4) Voyager — FR-9·FR-17의 "검증된 결과에만 기댄 지지 판정"으로 막음).

## OD-31

**LLM end-to-end 목표(C-6 개정)의 세부** — 오너 2026-10-19, 채팅: 목표는 **Llama 3.2 1B**를 end-to-end로 실행할 수 있는 수준이다(모델에 필요한 연산을 각각 instance로 최적화하고, 그 커널들로 forward pass가 돌아 토큰을 생성하며 reference와 맞는다; 그래프 수준 합성·fusion은 후속). 정밀도는 **bf16/fp16**. 오너가 정한 것은 이 문단까지이며 아래는 열린 하위 질문이다(제안 없음). 각 질문 끝의 귀속은 [PROCESS/DRIVER.md](../PROCESS/DRIVER.md) §9 기준이다 — "드라이버"는 §9의 ADR 경로로 닫을 수 있는 설계, "오너"는 #5 A·B 항목·C-6·OD-25에 닿아 HQ로 묻는 부분.

- **하위 질문(2026-10-19 등재, 미결)**: ① **연산 목록과 shape** — forward에 필요한 연산 종류(GEMM/GEMV, attention, RMSNorm, RoPE, SwiGLU, softmax, embedding, 그 밖)와 각 op_signature, prefill·decode, 시퀀스 길이·배치. [#5 B-4 답변](https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-5944412285)이 출발점을 정해 두었다: decoder 층의 projection(gate/up 2048→8192, down 8192→2048, QKV 2048→3072, O 2048→2048; lm_head는 첫 run에서 제외), M ∈ {1, 32, 512}, attention은 KV cache 포함·Llama 3.2 1B의 구성·causal, 두 번째 spec은 seq_len ∈ {128, 2048}의 prefill·decode SDPA. 그 답변의 "16 heads / 8 KV heads"는 hidden 2048 = heads × head_dim 64와 QKV 2048→3072에 맞지 않아(32 heads면 맞는다) 확인이 필요하다. 첫 kind `gemm`의 계약은 [ADR-0008](decisions/ADR-0008-od6-gemm-kernel-contract.md)이고 다른 kind의 계약은 OD-6 하위 질문 ①의 연장이다. (귀속: 드라이버 — B-4 답변의 값을 바꾸는 부분은 오너) → 미결.
- **하위 질문(2026-10-19 등재, 미결)**: ② **bf16과 fp16의 선택** — 오너의 답은 "bf16/fp16"이다. 둘 중 하나인지, 모델·연산마다 고르는지, 누적·중간값의 정밀도, `cpu_standin`에서의 표현과 변환. (귀속: 오너 — C-6 개정의 범위) → 미결.
- **하위 질문(2026-10-19 등재, 미결)**: ③ **연산별 oracle·tolerance** — 첫 사례의 NumPy float64 reference와 `rtol`·`atol`([HQ-0004 답변](https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6052377983))은 fp32 `gemm`에 한정된다. bf16/fp16과 다른 kind의 reference, 허용 오차 어휘, 입력 분포. (귀속: 오너 — #5 B-7; reference가 새 외부 의존성이면 A-13) → 미결.
- **하위 질문(2026-10-19 등재, 미결)**: ④ **모델 실행기** — instance가 낸 커널을 엮어 forward pass를 돌리는 부분의 자리(2층 도구인지, 그 밖인지)와 언어, 커널을 고르는 방법(키마다의 best), 커널이 없는 연산의 처리. (귀속: 드라이버 — 새 외부 의존성이면 A-13) → 미결.
- **하위 질문(2026-10-19 등재, 미결)**: ⑤ **가중치·토크나이저의 입수와 저장** — 모델 파일의 출처·포맷, gated 라이선스의 동의 주체(런타임 사용자 — 개발 드라이버는 그런 자격 증명을 요구하지 않는다, D16), 저장 위치(CAS·데이터 plane), base/instruct 변형. (귀속: 오너 — #5 B-5·OD-9, OD-25, #5 A-1·A-2; 데이터 plane 스키마 변경이면 A-13) → 미결.
- **하위 질문(2026-10-19 등재, 미결)**: ⑥ **모델 수준 정확도의 판정** — "reference와 맞는다"의 reference(어느 구현·정밀도)와 비교 지표(토큰 일치, logit 오차, 그 밖), 프롬프트·생성 길이, 연산별 검증(FR-9)과의 관계. (귀속: 오너 — reference의 선택은 #5 A-7의 선례, 프롬프트·평가 데이터는 #5 B-8) → 미결.
- **하위 질문(2026-10-19 등재, 미결)**: ⑦ **새 외부 의존성** — 가중치 읽기, 토크나이저, reference 구현에 필요한 패키지. (귀속: 오너 — A-13의 BLOCKED 사유) → 미결.
- **하위 질문(2026-10-19 등재, 미결)**: ⑧ **산출물** — 엮인 모델 실행이 C-6의 "whole-model 바이너리"인지, 별도의 산출물인지. (귀속: 오너 — C-6) → 미결.
- **하위 질문(2026-10-19 등재, 미결)**: ⑨ **모델 수준 성능** — 모델 수준에서 성능을 재는지(토큰당 latency·throughput), 연산별 측정(OD-13)만으로 충분한지. (귀속: 오너 — #5 A-4) → 미결.
- **하위 질문(2026-10-19 등재, 미결)**: ⑩ **이 목표의 시나리오** — 모델을 연산별 커널로 엮어 실행하는 흐름을 StandardScenarios에 새 시나리오로 둘지(S0 4단계의 알려진 약점과 함께), 둔다면 MVP 계층인지 — C-6 개정이 이 목표를 MVP 범위 안에 둔 것은 통합자 독해이므로, 이 질문의 답이 그 독해의 확인이기도 하다. (귀속: 오너 — C-6) → 미결.
