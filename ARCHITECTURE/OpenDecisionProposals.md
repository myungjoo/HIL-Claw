# Open Decision 제안 상세 (Proposals)

[Requirements.md](Requirements.md)의 Open Decisions 등록부에 등재된 각 항목의 **구체 제안·근거 본문**을 같은 번호 절에 둔다. 등록부에는 한 줄 요약만 남겨 표가 읽히도록 유지한다.

- **정본 분담**: 항목의 **상태·논의 위치**는 등록부(Requirements.md)가 정본, **제안 본문**은 본 문서가 정본이다. 제안이 바뀌면 본 문서를, 상태가 바뀌면 등록부를 같은 커밋에서 갱신한다.
- 제안은 결정이 아니다. 확정은 오너가 #4/#5에서 내리거나 설계 수준 OD에 한해 [PROCESS/DRIVER.md](../PROCESS/DRIVER.md) §9의 경로(ADR + 리뷰어 Approve + 오너 통지)로 내리고, 등록부 상태가 `확정`으로 바뀐 뒤 본문(FR/NFR)에 반영된다.
- 출처 표기: **#4** = 아키텍처 결정 스레드, **#5** = 사용자 입력 대기 목록, **#7** = 외부 조사(상설; `§n` = S-1 조사 본문 절, `보충 §2(n)` = S-1 보충 코멘트), **#8** = 모순 트래커, **(Bn)** = [reviews/2026-09-03](reviews/2026-09-03-StandardScenarios-LiteratureReview.md) 보강 제안.

## OD-1

**Objective type 메뉴** — #5 A-4 대기.

- 제안: MVP는 "단일 목적 + 선택적 제약(메모리 상한)"만, 가중조합/Pareto는 후속. 후보 메뉴: latency 최소화 / throughput 최대화 / 동시 서빙 capacity 최대화 / 메모리 상한 내 latency 최소화(제약형).
- *확장 고려(B2)*: HW 이론 한계(speed-of-light/roofline) 대비 달성률을 target·정지 어휘에 포함할지. "이전 대비"가 아닌 "HW 한계 대비" 평가는 2025~26 커널 생성 시스템의 공통 요소(#7 S-2 사실 요약).
- README의 다목적 목표("속도 향상 및 동시 서빙 용량 증대")와의 관계는 A-4 확정 시 Scope 또는 README에 명시(#8 M15).

## OD-4

**hw_profile / op_signature 키 스키마** — #4 코멘트 · #7 §6. **P1 최소분 확정(2026-10-06, PROCESS/DRIVER.md §9)**: [ADR-0001](decisions/ADR-0001-od4-key-schema.md). **첫 `layout` 값 확정(2026-10-07, 같은 경로)**: [ADR-0008](decisions/ADR-0008-od6-gemm-kernel-contract.md) — `row_major`.

- **채택분(ADR-0001)**: 아래 제안의 정확 식별층(hw: 칩 + 리비전 + 펌웨어·드라이버·툴체인 버전, op: 전체 인자튜플 + dtype/layout)에 용어집의 호스트 환경을 더한 것 — hw 키는 accelerator + revision + toolchain(구성요소별 버전) + host, op 키는 kind + 전체 shape(M 포함) + dtype + layout — 과 "정확 일치 = 히트"(P1은 정확 일치만 조회). hw_source는 키가 아닌 필수 속성으로, revision은 키 필드로 정했다. 키의 정규형·디렉토리 이름 유도·`schema_version`은 ADR이 새로 정했다.
- **제안으로 남는 부분(미확정)**: 유사도 벡터층과 "최근접 = prior로만", 아래 *확장 고려(S10)*, op의 "정규화 IR 구조해시"(IR 부재 — OD-9), 첫 인스턴스의 layout 값(row-major는 통합자 가정 그대로) — *이 마지막 항목은 2026-10-07 [ADR-0008](decisions/ADR-0008-od6-gemm-kernel-contract.md)로 확정되었다: 값 이름 `row_major`, 뜻 = 모든 피연산자가 r·c개 원소의 연속 배열 하나이고 원소 (i, j)는 i·c + j번째(패딩·stride·offset 없음, 전치·packing 없음). `layout` 어휘는 열려 있으며 다른 저장 형태는 새 값 = 새 키다. hw 쪽 값은 미정 그대로다.*
- 제안: **2층 구조**. 정확 식별층(op: 정규화 IR 구조해시 + 전체 인자튜플 + dtype/layout; hw: 칩 + 리비전 + **펌웨어·드라이버·툴체인 버전**) + 유사도 벡터층(FLOPs, 이동 바이트, arithmetic intensity, working set ÷ SRAM …). 정확 일치 = 캐시 히트, 최근접 = **prior로만**. TVM/TenSet 선례.
- hw 식별층 필드 후보: **HW 출처(hw_source: 외부 타사 / 자사 개발 중)** 와 revision — 자사 개발 중 HW는 revision마다 성능 특성이 바뀌므로 이력 귀속 키가 필요(FR-14 ④, OD-26).
- *확장 고려(S10)*: 재현 시 노이즈 범위를 넘는 차이가 나면 환경 변화(드라이버/펌웨어/호스트)를 새 hw_profile 키 후보로 표시.
- **첫 구체 인스턴스(#5 B-4, 2026-10-02)**: hw = `cpu_standin`(오너 로컬 PC, Windows/WSL; 이후 LAN 머신) · op = Llama 3.2 1B 디코더 projection GEMM — gate/up(2048→8192), down(8192→2048), QKV(2048→3072), O(2048→2048), M∈{1, 32, 512}, fp32(layout은 B-4에 없음 — row-major는 통합자 가정이었고 2026-10-07 ADR-0008이 `row_major`로 확정; 12개 op_signature 디렉토리 이름은 그 기록의 결정 9); 2차 = 같은 모델의 KV cache 포함 SDPA(GQA 16/8, head_dim 64, causal). → 설계 함의(제안): op_signature는 (op 종류, M·N·K 또는 seq·head 구성, dtype, layout)을 담고 **M(토큰 수)이 instance 파라미터**임을 키 설계가 수용해야 한다.

## OD-5

**정확도-성능 trade-off 정책** — **확정(2026-10-01, #5 A-6)**: hard floor.

- 결정 내용: 정확도는 게이트. tolerance는 사용자 instance 파라미터(어휘는 B-7 후 확정). 실패 = repair/탈락, best·통계 미반영. sim·board 양쪽 동일 floor. FR-3 ④ 조기 종료는 승격 게이트 수준 재검증 후 인정. 정확도의 목적 축 승격은 A-4 다목적과 함께 후속.
- 근거(#7 §5 G1): 목적 축으로 두면 옵티마이저에 정확도를 팔 권한을 명시 부여하는 것. Sakana 정정 후 집계 speedup 3.13× → 1.49×; METR: KernelBench 최적화의 73.8%가 프록시 지표만 개선, 예산이 클수록 악화(10스텝 26.4% → 100스텝 57.8%).
- 귀결: 더 느슨한 tolerance에서 더 빠른 후보가 있으면 시스템은 보고만 하고 채택하지 않는다 — 채택은 사용자가 tolerance를 바꾼 새 instance로(FR-9에 반영).
- 잔여: ~~tolerance 어휘(per-dtype rtol/atol, downstream 지표 임계 — MLPerf식 99%/99.9% 등, user-defined 검사)는 #5 B-7 답변 후 확정.~~ → **첫 사례(`cpu_standin`·`gemm`·fp32·C 커널)에 한해 오너가 답했다**([HQ-0004 답변](https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6052377983), 2026-10-08; 반영: FR-9, [ADR-0017](decisions/ADR-0017-od16-cpu-standin-verification-run.md) 결정 5·6): 어휘는 원소별 `rtol`·`atol`(둘 다 instance 파라미터)이고 출력의 모든 원소에서 |out − ref| ≤ atol + rtol·|ref|일 때만 통과하며, 출력의 NaN·무한대는 실패다(전제: 이 사례의 검증 입력은 유한하게 뽑는다). 기본값은 없다 — instance가 `rtol`·`atol`을 둘 다 명시하고 하네스는 기본값을 갖지 않는다. 이 답은 그 사례에 한한 것이고 B-7의 일반 답이 아니다: 다른 dtype의 tolerance, downstream 지표 임계(MLPerf식 99%/99.9% 등), 벤더 golden output, user-defined 검사는 #5 B-7 답변 후 확정 그대로다. per-kernel 검사와 downstream 지표 floor의 병행 여부도 그때 어휘와 함께 정한다.

## OD-6

**codegen spec 페이로드 + repair resume** — #4 §4 첫 항목 · #7. **P1 최소분 확정(2026-10-06, PROCESS/DRIVER.md §9)**: [ADR-0002](decisions/ADR-0002-od6-codegen-spec.md). **잔여 중 `gemm` 종류의 동작 계약 값(C 커널) 확정(2026-10-07, 같은 경로)**: [ADR-0008](decisions/ADR-0008-od6-gemm-kernel-contract.md) — 다른 연산 종류·dtype·layout·언어의 계약과 하위 질문 ②~④는 미확정 그대로다.

- **채택분(ADR-0002)**: 아래 제안 중 "resume = #4 §3b"(repair는 코더 재호출이며 라운드는 `coded` 체크포인트에서 재진입), **후보 식별**(run·라운드·후보·시도 번호, 라운드의 후보 수 N과 후보들의 관계 — 같은 기법의 변형 / 서로 다른 기법), 그리고 여러 이전 시도를 나란히 실을 수 있는 **구조**(`feedback.attempts` 배열, 시도별 실패 리포트·프로파일 자리). spec의 단위(코더 호출 1회 = spec 1건, 불변), repair 호출의 입력(실패 리포트를 실은 새 spec; 이전 코더 세션을 이어 쓰지 않음), 구획·필드 표, 두 키 레코드의 동봉 방식(전체 + 키 이름), `schema_version`, 첫 GEMM 페이로드 예시(출처 없는 값은 자리표시)는 ADR이 새로 정했다.
- **제안으로 남는 부분(미확정)**: 대조적 제시의 **선택 규칙**(top-k/bottom-k, k, 필수 여부, 순서), 아래 *확장 고려* 전부 — (B4) 프로파일 요약 구조는 `profile` 자리만, (S7) 금지 패턴·(B5) 문서 발췌와 문서 부재 정보·참고 코드 포인터(FR-15)는 `ext` 자리만 있고 내용은 정하지 않았다 — 와 coder-driver 계약의 출력 쪽(OD-23).
- **하위 질문(ADR-0001이 넘긴 것, 2026-10-06 등재)**: ① **연산 종류의 동작 계약**(피연산자·역할·호출 규약) — 확정: spec의 `task.contract`(언어, 진입점 prototype, 피연산자별 역할·dtype·shape)에 싣는다. ~~미결: 그 값(하네스 쪽 계약 — PLAN P1-3), 첫 GEMM의 prototype·피연산자 저장 순서.~~ **값 확정(2026-10-07, [ADR-0008](decisions/ADR-0008-od6-gemm-kernel-contract.md))** — `gemm`·fp32·`row_major`·C에 한해: 연산은 순수한 곱 C = A·B(스케일·누적·전치 플래그·bias 없음), 가중치는 k×n 행렬 B(`[in, out]` 순서)로 전달, prototype은 `void hilclaw_gemm(size_t m, size_t k, size_t n, const float *restrict a, const float *restrict b, float *restrict c);` 한 줄(모든 shape에 같은 문자열), 피연산자 항목은 a `[m, k]` input · b `[k, n]` input · c `[m, n]` output, 호출 시 보장(m·k·n ≥ 1, 세 배열은 겹치지 않음, 정렬은 `float`의 정렬만, 진입 시 c의 내용은 미정, 한 프로세스에서 여러 번 호출 가능)과 커널의 의무(입력 불변, c의 모든 원소를 씀, 포인터를 보관하지 않음, 결과는 이번 호출의 인자에만 의존, 반환 시 작업 완료), 커널 소스는 `hilclaw_gemm` 정의 하나를 외부 링크로 제공하고 `main`을 두지 않는다. 미결 그대로: 다른 연산 종류·dtype·layout·언어의 계약, 호출 메커니즘(링크/로드/별도 프로세스 — PLAN P1-3), op_signature 밖의 차원 값이 전달되는지(OD-16 하위 질문 ①), 가중치를 `[out, in]` 순서로 받는 layout 값을 둘지(오너 통지의 확인 항목). ② **후보별 빌드 설정**(컴파일러 플래그·스레드 수)의 기록 위치 — 확정: 오케스트레이터가 지정하는 설정은 spec의 `task.build`, 실제로 쓰인 설정은 spec 밖(빌드·측정 결과와 함께). 미결: `task.build`의 멤버 이름, 코더가 설정을 스스로 고를 수 있는지, 쓰인 설정을 담는 레코드(OD-23 출력 쪽·OD-8) — 위치는 확정: 시도별 `measure/…/build.json`과 그 설정을 쓴 단계의 기록([ADR-0004](decisions/ADR-0004-od8-data-plane-layout.md)), 필드는 미결. ③ 한 instance가 여러 M을 다룰 수 있는지 — 미결: spec 1건은 op_signature 하나(M 하나)만 싣고(ADR-0002), instance 쪽은 `instance.json` 스키마(OD-8)에서 정한다. ④ *(ADR-0008이 넘긴 것, 2026-10-07 등재, 미결)* **계약 변경과 키** — op_signature 키에는 prototype도 커널 언어도 들어 있지 않다. 확정(ADR-0008 결정 8): 저장된 커널에는 그 spec이 남고 spec의 `task.contract`는 계약 가운데 언어·prototype 문자열·피연산자 항목만 싣는다 — 같은 op_signature의 두 커널에서 `task.contract`가 다르면 계약이 다른 것이지만 그 역은 성립하지 않는다(prototype 문자열을 바꾸지 않는 보장·의무 변경은 spec에 보이지 않는다); 저장 형태의 변경은 새 `layout` 값 = 새 키다. 미결: 저장 형태가 아닌 계약 변경(인자 순서·보장·심볼 이름)이 있을 때 그 (hw_profile, op_signature) 쌍의 best·통계를 어떻게 다루는지, prototype 문자열에 드러나지 않는 변경 전후의 커널을 어떻게 구분하는지, 같은 op_signature의 다른 hw_profile 사례(커널 언어가 다를 수 있다)를 힌트로 쓸 때의 취급, 새 키가 필요하다면 기존 수단(`layout` 값, `ext` 멤버, 스키마 버전) 중 무엇을 쓰는지.
- resume 여부는 #4 §3b에서 "phase=coded 체크포인트 resume"으로 정리됨.
- 제안: spec을 coder-driver **입출력 계약의 부분집합**으로 흡수(OD-23 연동). 직전 라운드만이 아니라 **top-k/bottom-k 시도와 프로파일을 대조적으로** 실을 것(CUDA-L1 근거).
- MVP 수용 항목: **후보 식별**(S8 — 라운드·후보 id, N개 후보가 같은 기법의 변형인지 다른 기법인지).
- **첫 페이로드 예시(#5 B-4, 2026-10-02)**: Llama 3.2 1B projection GEMM(위 OD-4 인스턴스)의 커널 명세 + `cpu_standin` hw_profile + 직전 라운드 프로파일/에러 + 기법 지침. 참고 코드(nntrainer 커널, FR-15 참고 입력)는 spec에 포인터로 동봉할 수 있고(발췌 동봉은 B5 확장 고려), 코더의 직접 검색 허용 여부는 OD-12.

- 하위 질문(UC-0 대안 흐름, PR #10): 가용 HW 문서의 범위와 **문서 부재 정보**를 spec에 반영할지 — 코더가 없는 문서를 가정하지 않도록 "이 HW의 문서는 여기까지"를 spec이 말해 줄지.

## OD-8

- **채택분(ADR-0004)**: 아래 "MVP 요구"의 후보 차원과, 후보 ① 1.의 **소유자별 분할을 경로의 성질로만** 채택했다 — 라운드 아래를 작성 역할(`decision/`·`coder/`·`measure/`·`eval/`)로 먼저 나누고 그 아래에 `candidates/<CC>/attempts/<AA>/`를 둔다(역할 우선: 한 역할의 한 라운드 파일이 접두 경로 하나를 공유하므로 후보 ①·② 어느 쪽에서도 쓰기 루트 1개가 성립한다). 역할은 에이전트가 아니며 누가 맡는지는 OD-23이다. 그 밖에 ADR이 새로 정한 것: run 직속 파일 4개(`STATE.json`·`instance.json`·`events.ndjson`·run당 1개의 `artifacts.json`), 라운드 번호(`0000` = bring-up, 최소 4자리)와 후보·시도 번호(`01`부터, 최소 2자리)의 표기, ADR-0002의 식별 튜플 → 경로 대응(spec = `…/coder/candidates/<CC>/attempts/<AA>/spec.json`), 시도 단위 산출물(`output/`, `build.json`, `sim.json`·`board.json`·`profile.json`, `eval.json`), `db/` 키 디렉토리의 전체 키 레코드 파일(`hw_profile.json`, `op_signature.json`), 데이터 plane에 파일로 두지 않는 것, `run_id`의 디렉토리 이름 제약(형식은 미정), 레이아웃 버전 1(run별로 `instance.json`에 기록).
- **채택분(ADR-0005, `artifacts.json`의 blob 레코드)**: C-3(#5 A-2)이 이름만 준 다섯 항목과 `gc_at`의 표기를 정했다 — 파일은 `schema_version`(1)과 `artifacts` 배열(추가 순서, 레코드는 한 줄씩)을 가진 객체 하나, 레코드는 `sha256`(64자리 소문자 16진수 — `hilclaw.cas`의 digest 그대로)·`size`(바이트)·`type`(ADR-0001의 *name* 형식만, 값 목록 없음)·`round`(ADR-0002의 `id.round`)·`retention_class`(`best`/`final`/`intermediate`/`failed`)가 필수이고 `gc_at`은 GC 뒤에만 있다(시각 표기는 미정). 레코드의 식별자는 `sha256`이며 한 파일에 한 번만 나온다(같은 내용을 다시 만들면 레코드를 더하지 않고 첫 생산의 `round`·`type`을 유지; 같은 해시가 여러 run의 파일에 있을 수 있다). 허용되는 변경은 `retention_class` 교체와 `gc_at` 추가뿐이고 레코드는 지우거나 옮기지 않는다. blob을 먼저 저장하고 레코드를 쓴다 — 레코드는 "기록 시점에 로컬 저장소에 있었다"만 말하며 현재 존재를 보장하지 않는다. class는 항상 호출자가 주며(기본값 없음) 누가·언제 정하고 바꾸는지는 정하지 않았다(OD-20·OD-29·OD-23). GC 도구·유예기간·`blob.push`/`blob.fetch`도 정하지 않았다(C-3 후속, #5 B-2).
- **채택분(ADR-0006, `events.ndjson`의 줄 형식·봉투)**: 한 줄이 무엇이고 모든 줄이 무엇을 싣는지만 정했다 — 이벤트 종류는 하나도 이름 짓지 않았다. 한 줄은 줄바꿈 없는 JSON 객체 하나와 LF 하나이고(UTF-8, BOM·빈 줄·헤더 줄 없음, 첫 줄도 이벤트), 없는 파일과 빈 파일은 "이벤트 없음"이다. 봉투는 닫힌 집합이다: `schema_version`(1, 줄마다)·`time`(`YYYY-MM-DDThh:mm:ssZ` — 줄을 추가하는 도구가 읽은 UTC 시각, 순서의 근거가 아님)·`kind`(ADR-0001의 *name* 형식만, 값 목록 없음; 모르는 값은 오류가 아님)·`data`(종류별 페이로드 객체, 비어 있어도 됨)가 필수이고, 무엇에 관한 줄인지는 `round`·`candidate`·`attempt`(ADR-0002의 정수; `candidate`는 `round`와, `attempt`는 `candidate`와 함께만)로 적으며 셋 다 없으면 run 전체에 관한 줄이다. 순서는 추가 순서이고 순번·식별자 멤버는 없다. 완결된 줄은 고치거나 지우거나 옮기지 않으며 뒤늦은 사실은 새 줄이다. 추가 도중 프로세스가 죽어 LF 없이 남은 꼬리는 줄도 이벤트도 아니다 — reader는 건너뛰고, writer는 다음 추가 전에 그 바이트만 지우며, commit은 꼬리가 없는 파일만 한다(따라서 commit된 내용은 지워지지 않는다). 그 밖의 손상된 줄은 마지막 줄이어도 오류다. 비싼 결과의 줄은 결과 파일을 가리키지 않고 **결과 자체를 싣는다**(결과 파일은 측정 역할이 나중에 쓰므로 그 전에 죽으면 가리킬 것이 없다); 로그가 결과 파일을 대신하지는 않는다. `schema_version`은 줄 형식·봉투만 덮고 `kind` 값이나 페이로드가 바뀌어도 올리지 않는다. 추가가 끝난 줄은 프로세스 사망을 견디지만 commit 전의 머신 손실은 견디지 못한다(#5 A-3). 동시 writer 제어·결과 파일이나 `STATE.json`과의 원자성·완전성 검사는 없다. OD-17 제안(`intent`/`result`·idempotency key·fold·스냅샷)은 채택도 기각도 하지 않았고 봉투가 이를 막지 않는다는 것만 보였다 — #8 M7은 열려 있다.
- **채택분(ADR-0012, 런타임 `STATE.json`의 틀·라운드 포인터·저장된 지출 뷰)**: #4 초안이 이름 준 일곱 멤버 가운데 다른 미결에 걸리지 않은 둘(현재 라운드, `budget_spent`)과 파일의 틀만 정했다. 파일은 JSON 객체 하나다(UTF-8, BOM 없음, 같은 멤버 이름이 두 번 나오지 않음, 쓰는 쪽은 LF와 끝의 줄바꿈·정해진 멤버 순서를 지키고 읽는 쪽은 어떤 순서든 받는다). `schema_version`(1)은 이 파일의 최상위에 둔다(레이아웃 버전과 별개). 필수 멤버는 `schema_version`·`round`·`budget_spent`이고 **최상위는 버전 1에서 열려 있다** — 읽는 쪽은 모르는 멤버를 해석하지 않되 오류로 보지도 않으며, 뒤의 기록이 없어도 되는 멤버를 더하는 것은 버전을 올리지 않고, 멤버를 필수로 만들거나 이 기록의 멤버를 바꾸거나 `budget_spent` 안에 멤버를 더할 때 올린다(1층의 작성자와 2층의 검증기가 따로 교체될 수 있으므로 — NFR-7 ①; 대가: 없어도 되는 멤버의 오타는 잡히지 않는다). 없는 파일은 "이 run의 상태가 아직 쓰이지 않았다(어떤 라운드도 시작되지 않았다)"이고(다른 파일은 있는데 이 파일만 없을 때의 의미는 하위 질문 ⑩) 빈 파일은 유효하지 않은 파일이다. **`round`**(ADR-0002의 `id.round`)는 **run이 서 있는 라운드** — 아직 끝나지 않았고 다음 턴이 실행하거나 이어 가는 라운드 — 를 가리킨다: 시작 시 0이고, 라운드를 끝내는 쓰기(저장된 뷰를 뜨는 바로 그 쓰기)에서만 바뀌어 다음 정수가 된다(다음 라운드 = 다음 정수는 ADR-0004에 대한 이 기록의 해석). 따라서 0부터 `round` − 1까지의 라운드는 끝났고 그보다 큰 번호의 라운드는 시작되지 않았음을 목록 조회 없이 안다. 턴이 실제로 도는지(run의 종료·정지·대기), 무엇이 라운드를 끝내는지, 라운드 안에서 어디까지 끝났는지는 이 멤버가 말하지 않는다. **`budget_spent`**는 ADR-0011의 지출 뷰를 그대로 담는 닫힌 객체다: `totals`(축 *name* → 합계 — 부호·소수·지수 없는 십진 정수이고 **크기 제한이 없다**: 금액은 ADR-0001의 *integer*지만 그 합은 범위를 넘을 수 있고 뷰는 정확해야 하므로; 끝 줄이 이름 준 축은 합계가 0이어도 적는다), `position`(접은 완결 줄의 수), `open_steps`(식별 객체의 배열 — `step`·`execution`과, 줄이 실은 `round`·`candidate`·`attempt`만; 없는 번호는 적지 않고 `null`은 없다; 같은 식별은 한 번만; 쓰는 쪽은 `round`·`candidate`·`attempt`·`step`·`execution` 순으로 정렬하되 순서에 뜻은 없다). 시작 값은 `{}`·`0`·`[]`이고 세 멤버는 항상 있다. 끝난 뒤 다시 시작된 식별이 열린 단계에 드는지(T-0041이 ADR-0011의 개정에 남긴 질문)는 정하지 않았고 이 형식은 두 답 모두를 담는다. **바이트 오프셋은 두지 않는다** — 위치는 줄 수 하나뿐이고, 읽는 쪽은 파일 처음부터 줄바꿈을 세어 그 위치에 간다(지나가는 바이트는 run 길이에 따라 늘지만 해석하는 줄은 늘지 않는다); 오프셋은 같은 위치의 두 번째 진술이라 어긋날 수 있고, 줄 수와 대조하려면 결국 세어야 한다. **쓰기와 읽기**: 유일한 작성자(Round-Manager)가 파일을 통째로 바꿔 쓰고, 라운드를 끝내지 않는 쓰기는 `round`와 `budget_spent`를 그대로 옮기며, 쓰는 도중 프로세스가 죽어도 이전 내용이나 새 내용 중 하나가 온전히 남아야 한다(기법은 정하지 않음). 유효하지 않은 파일(인코딩·JSON 객체·멤버 이름 중복·필수 멤버와 그 형식 — 줄바꿈과 순서 같은 쓰기 형식은 작성자만 묶고 유효성에 들지 않는다)은 로그의 손상과 같이 오류다 — 읽는 쪽은 보고하고 아무 멤버도 쓰지 않으며 고치지 않고, 복구는 마지막 commit의 파일에서 한다(#5 A-3; commit된 줄은 지워지지 않으므로 그 파일의 지출 뷰는 작업 트리의 로그에 대해서도 접두부의 뷰다). 이 파일만 보는 검증기는 뷰가 로그의 fold인지, `position`이 로그 끝을 넘는지, `round`가 맞는지 확인할 수 없다. 보호하지 못하는 것(두 작성자, 라운드 사이에 포인터나 뷰를 옮기는 쓰기, 라운드 종료를 쓰고 commit하기 전의 사망, commit 전 머신 손실, 틀린 포인터)은 기록의 결정 7에 있다. gate 상태·`best_ref`·lock·`phase`의 값과 단위·`next_action`·시각 멤버·`instance.json`·축과 단위·누가 fold하는지는 정하지 않았다.
- **채택분(ADR-0013, `STATE.json`을 디스크에서 바꿔 쓰는 방법)**: ADR-0012 결정 6이 요구만 하고 기법을 정하지 않은 "쓰는 도중 프로세스가 죽어도 이전 내용이나 새 내용 중 하나가 온전히 남는다"를 충족하는 절차만 정했다 — 파일의 멤버·형식·유효성 규칙은 하나도 바꾸지 않았고, 누가 그 쓰기를 수행하는지(에이전트가 패키지의 도구를 거치는지)도 정하지 않았다(OD-23). **절차**(다섯 단계): ① 작성자는 파일 시스템을 건드리기 전에 새 내용 전체를 바이트로 갖추고 그것이 ADR-0012 결정 6에 따라 유효해야 한다(유효하지 않은 내용은 쓰지 않는다 — 교체는 작업 트리의 마지막 유효한 내용을 없애므로), ② 같은 디렉토리 `runs/<run_id>/`에 임시 파일을 **새로 만들어**(있는 파일을 열지 않는다) 내용 전체를 쓰고, ③ 그 내용을 안정 저장소로 내린 뒤(`fsync` 또는 동등한 것) 닫고, ④ 있는 파일을 한 단계로 교체하는 이름 바꾸기(POSIX `rename`)로 `STATE.json`에 옮기며 — 최종 이름이 가리키는 것을 바꾸는 단계는 이것뿐이다 —, ⑤ 살아 있는 동안 어느 단계가 실패하면 자기 임시 파일을 지우고 실패를 보고한다. 최종 이름을 쓰기용으로 열지 않고 백업 사본이나 표식도 두지 않는다. 사망 시점별로: 임시 파일이 완성되기 전과 완성된 뒤·옮기기 전에는 최종 이름에 이전 내용(첫 파일이면 없는 파일)이 그대로 있고(완성된 임시 파일이 남았어도 그 교체는 일어나지 않은 것이다 — ADR-0006 결정 6의 "끝나지 않은 추가"와 같다), 옮긴 뒤에는 새 내용이 있다; 최종 이름에 내용의 일부만 있는 시점은 없다. **임시 파일**: 자리는 최종 파일과 같은 디렉토리(같은 파일 시스템이어야 이름 바꾸기가 한 단계다), 이름은 `STATE.json.<token>.tmp`(`<token>` = `[a-z0-9-]{1,64}`, 두 교체가 같은 이름을 쓰지 않도록 작성자가 고른다 — 만드는 방법은 코드 task) — 고정된 이름 하나를 쓰면 두 작성자가 한 임시 파일에 섞어 써서 최종 이름에 섞인 내용이 올 수 있어, ADR-0012 결정 7이 그 경우에 대해 적은 한계("나중 쓰기가 이긴다")보다 나빠지기 때문이다. run 직속 파일 네 개나 `rounds`와 혼동되지 않고 `layout.RUN_FILES`의 멤버가 아니다. **ADR-0004에 대한 이 기록의 해석**: 결정 2("run 바로 아래에는 run 직속 파일 네 개와 `rounds/`가 있다")는 **트리** — 뜻이 있고, 읽는 쪽이 찾고, commit이 담는 파일 — 에 대한 문장이며 임시 파일은 그 어느 것도 아니다(모든 commit에서 run 디렉토리는 결정 2가 열거한 것만 담는다; 작성자의 임시 파일이 트리의 파일이 아닌 선례로 `hilclaw.cas`가 blob 옆에 만드는 것이 ADR-0004 결정 6에 있다 — 다만 그쪽은 통째로 무시되는 디렉토리 안이고 이쪽은 추적되는 파일들 옆이다). 결정 7이 격리 수단과 함께 정한다고 한 것은 행위자가 작업하는 scratch·임시·빌드 캐시 **디렉토리**의 위치이고, 이 임시 파일은 그런 자리가 아니라 한 파일의 쓰기의 한 단계다 — **scratch·빌드 캐시 디렉토리가 체크아웃 밖인지 안의 무시되는 이름인지는 이 기록이 정하지도 좁히지도 않았다.** 레이아웃 버전은 1 그대로다(결정 9: 경로·파일 이름·번호 표기가 바뀌지 않았다). 임시 파일은 **commit하지 않는다** — 이 규칙은 commit하는 단계를 묶으며(어느 단계인지는 미정), 데이터 repo의 `.gitignore`에 이미 있는 `*.tmp`(D7로 만들어진 사실)는 둘째 방어일 뿐 규칙이 거기에 기대지 않는다; 데이터 repo는 바꾸지 않았고 바꿀 필요도 없다. **남은 것(leftover)**: 교체가 더는 진행 중이 아닌데 남아 있는 임시 파일(작성자가 옮기기 전에 죽었거나 지우기 전에 죽음)은 내용의 일부든 온전한 유효 내용이든 **상태가 아니다** — `STATE.json`이 없거나 유효하지 않을 때에도 그 대신 읽지 않고, 최종 이름으로 옮기지도 않으며(그 교체는 끝났고 최종 파일이 더 새것일 수 있다), commit하지 않는다. 읽는 쪽은 최종 이름만 열므로 남은 것 때문에 디렉토리를 나열하지 않는다(#4 §1). 죽은 작성자가 남긴 것은 그 파일의 작성자가 지워도 되지만(찾으려면 경로가 알려진 run 디렉토리 하나를 나열한다) **의무는 아니다** — 어떤 규칙도 그것이 없어졌음에 기대지 않는다(대가: 작성자가 죽을 때마다 작은 파일 하나가 누군가 지울 때까지 남는다). **약속하는 것과 하지 않는 것**: 약속은 쓰는 프로세스(와 그 쓰기를 요청한 에이전트)의 사망까지다. 교체 도중의 읽는 쪽은 옛 파일이나 새 파일을 보고 섞인 것을 보지 않는다. 머신·전원·작업 트리의 손실은 약속하지 않는다(#5 A-3, ADR-0006 결정 10) — 그래도 ③은 필수로 두었다(없으면 전원 손실 뒤 최종 이름에 빈 파일이나 일부만 있는 파일이 올 수 있고, 비용은 작은 파일의 flush 한 번이다); 디렉토리 항목의 flush는 필수가 아니다(없으면 전원 손실 직후 이전 내용으로 돌아갈 수 있을 뿐이고 그것은 온전하다). 규칙이 성립하는 곳은 한 디렉토리 안의 이름 바꾸기가 한 단계인 곳 — C-7 환경의 네이티브 파일 시스템 — 이며, 네트워크 파일 시스템, WSL에서 본 Windows 드라이브, 네이티브 Windows(C-7 밖)에서 무엇이 성립하는지는 이 기록이 말하지 않는다. 두 작성자의 동시 쓰기는 한계로 남는다(lock, OD-17 잔여). **첫 파일**: 파일이 없을 때 "이전 내용"은 없는 파일(ADR-0012 결정 2)이고 첫 파일도 같은 다섯 단계로 쓴다 — 사망은 파일 없음이나 온전한 첫 파일을 남긴다. 교체는 `runs/<run_id>/`가 없으면 **만들 수 있고** 다른 파일이 먼저 있기를 요구하지 않는다(요구하면 다른 파일이 먼저 쓰인다고 정하는 셈이다). 디렉토리를 만든 뒤 옮기기 전에 죽으면 ADR-0004의 파일이 하나도 없는(또는 남은 임시 파일만 있는) run 디렉토리가 남는데, ADR-0004 결정 1("디렉토리는 무언가 쓰였을 때에만 존재한다")을 이 기록은 commit된 트리와 읽는 쪽이 기댈 수 있는 것에 대한 문장으로 읽는다 — git은 빈 디렉토리도 임시 파일도 담지 않으므로 어떤 commit에도 그런 디렉토리는 없고, `STATE.json`을 읽는 쪽에게 그것은 없는 파일이다. **모르는 멤버**: 교체 자체는 아무것도 보존하지도 버리지도 않는다 — 최종 이름에 오는 것은 ①의 내용 그대로이고, 그 교체를 수행하는 패키지 함수는 호출자가 준 것만 쓴다(`run_state.dump`가 지금 하는 대로; 이전 파일을 읽어 멤버를 옮기지 않는다). 격리 수단, lock, 어느 단계가 commit하는지, `artifacts.json` 등 다른 파일의 쓰기는 정하지 않았다.
- **채택분(ADR-0014, `artifacts.json`과 키 레코드 파일이 디스크에 쓰이는 방법 — 하위 질문 ⑮의 답)**: 세 파일(`runs/<run_id>/artifacts.json`, `db/<hw_profile_key>/hw_profile.json`, `db/<hw_profile_key>/<op_signature>/op_signature.json`)의 바이트가 최종 이름 아래에 오는 방법만 정했다 — ADR-0005·ADR-0001의 멤버·값 목록·유효성 규칙은 하나도 바꾸지 않았고(`hilclaw.artifacts.validate`와 `hilclaw.keys`가 받는 것이 그대로다), 누가 쓰는지(OD-23)도 정하지 않았다. **`artifacts.json`**: 첫 파일을 포함한 모든 쓰기가 ADR-0013 결정 2의 다섯 단계에 따른 교체다(ADR-0005 결정 2·3·6에 따라 유효한 새 내용 전체를 먼저 갖추고 → run 디렉토리의 새 임시 파일 → 안정 저장소 → 한 번의 이름 바꾸기 → 실패 시 자기 임시 파일 제거). 새 내용이 무엇인지는 ADR-0005 그대로다(이전 레코드들 + 추가 하나 또는 허용된 수정 하나); 이전 파일이 유효하지 않을 때의 규칙은 더하지 않았다. 없는 파일이 "이전 내용"이고(= 기록된 blob 없음) 교체는 run 디렉토리를 만들 수 있다. `STATE.json`의 경우보다 더 얻는 것: 이 파일은 commit 사이에 쌓이므로, 제자리 쓰기에서는 한 라운드의 k번째 레코드를 쓰다 죽으면 작업 트리에서 앞의 k − 1개도 잃지만 교체에서는 남는다("blob 먼저, 레코드 나중"은 그대로 — 옮기기 전의 사망은 레코드 없는 blob을 남길 뿐이다). 기각한 대안: 제자리 쓰기 + 마지막 commit(지금), 일부만 쓰인 파일을 저장소나 라운드 파일에서 다시 짓는 복구 규칙(저장소에는 `type`·`round`·class가 없고 다른 run의 blob과 구분되지 않으며, blob을 해시로 가리키는 파일들은 정의되지 않았다 — ADR-0005 결정 8·10), 추가 전용 형식(ADR-0005 결정 2의 변경). **키 레코드 파일**: 다시 쓰이지 않고 한 번만 생기는 파일이다(패키지는 저장된 레코드를 고치거나 교체하거나 지우지 않는다; 속성 갱신 여부는 OD-26). 요구: 쓰는 프로세스의 사망은 레코드 파일 없음이나 온전한 레코드를 남기고 일부만 쓰인 파일(사람이 지울 때까지 그 키를 막는다)을 남기지 않는다. 단계 ①~③·⑤는 ADR-0013과 같다(임시 파일은 그 레코드의 키 디렉토리에). **마지막 단계는 최종 이름이 없을 때에만 한 단계로 완성된 파일에 그 이름을 주고, 있으면 아무것도 바꾸지 않는다 — 교체하는 이름 바꾸기는 이 단계가 아니다**: 교체는 작성자의 확인 뒤에 나타난 레코드 위에 자기 레코드를 놓게 되는데, 정규형이 같고 속성이 다르면 OD-26이 허용한 적 없는 속성 갱신이고 정규형이 다르면 ADR-0001 결정 3이 "아무것도 쓰지 않는다"고 한 자리의 쓰기다. 지금 모듈의 배타적 생성이 이미 이 성질을 가지며(둘 중 하나가 실패하고 아무것도 교체되지 않는다) 요구는 그것을 지킬 뿐 더하지 않는다 — lock이 아니다(순서를 정하지도 기다리게 하지도 않는다). 수단: POSIX `link()`(임시 이름 → 최종 이름, 최종 이름이 있으면 실패) 뒤 임시 이름 제거, 또는 플랫폼의 교체하지 않는 이름 바꾸기 — 어느 것을 쓰는지는 코드 task. **교체하는 이름 바꾸기로의 대체는 없다**: 그런 단계가 동작하지 않는 곳(하드 링크 없는 파일 시스템)에서는 쓰기가 오류로 실패하고 아무것도 저장하지 않는다. 마지막 단계에서 이름이 이미 있으면 작성자는 그 아래에 아무것도 쓰지 않았고 자기 임시 파일을 지운다(그 이름 아래의 레코드에는 ADR-0001 결정 3이 그대로 적용된다 — 정규형이 다르면 오류; 보고의 형태만 코드 task). 쓰기는 없는 상위 디렉토리(`db/`, hw_profile 디렉토리, op_signature 디렉토리)를 만들 수 있고, 디렉토리를 만든 뒤 마지막 단계 전에 죽으면 레코드 파일 없는(비었거나 남은 임시 파일만 있는) 키 디렉토리가 남는다 — ADR-0004 결정 1과 결정 5의 "디렉토리가 만들어질 때 쓰인다"를 ADR-0013 결정 6과 같이 commit된 트리에 대한 문장으로 읽었다(어떤 commit에도 그런 디렉토리는 없고, 이 창은 지금도 있다); 읽는 쪽에게 그것은 저장되지 않은 키다(`hilclaw/key_records.py`의 규약 "레코드 파일이 있을 때에만 저장된 키"를 규약으로 인용 — 남은 것이 있어도 바뀌지 않는다). **임시 파일**: 자리는 최종 파일의 디렉토리, 이름은 `<최종 이름>.<token>.tmp`(`artifacts.json.<token>.tmp`·`hw_profile.json.<token>.tmp`·`op_signature.json.<token>.tmp`; `<token>` = `[a-z0-9-]{1,64}`, 쓰기마다 다름 — ADR-0013 결정 3의 형식 그대로). run 디렉토리에서는 `layout.RUN_FILES`의 멤버가 아니고, 키 디렉토리에서는 이름에 점이 있어 키 디렉토리 이름이 될 수 없다(ADR-0004 결정 5) — hw_profile 디렉토리를 나열해 op_signature 디렉토리를 찾는 쪽은 `hw_profile.json`을 지나치듯 그것을 지나친다. 이 기록은 어떤 이름도 예약하지 않았다 — 뒤의 기록이 트리의 파일에 이 형식의 이름을 주려면 그 파일을 남은 것과 어떻게 구분하는지를 말해야 할 뿐이고, 그런 파일의 이름은 그 기록의 몫이다. **ADR-0004에 대한 해석**: `runs/`는 ADR-0013 결정 3의 해석(결정 2·7)을 그대로 따르고, 그 기록이 다루지 않은 **`db/`에도 같은 해석을 적용했다** — 결정 5가 열거한 것과 "키 디렉토리의 그 밖의 파일은 OD-20·OD-7"은 뜻이 있고 읽는 쪽이 찾고 commit이 담는 파일에 대한 것이고 임시 파일은 그 어느 것도 아니므로 OD-20·OD-7의 어떤 것도 정하거나 좁히지 않았다; 결정 7은 행위자가 작업하는 디렉토리에 대한 것이다. **scratch·빌드 캐시 디렉토리의 위치는 정하지도 좁히지도 않았다.** 레이아웃 버전은 1 그대로다. 임시 파일은 `runs/`에서도 `db/`에서도 commit하지 않는다(데이터 repo의 `*.tmp`는 둘째 방어일 뿐; 데이터 repo는 바꾸지 않았고 바꿀 필요도 없다). **남은 것**: 레코드가 아니다 — 최종 파일이 없거나 유효하지 않아도 그 대신 읽지 않고, 최종 이름을 주지 않으며(`artifacts.json`이라면 최종 파일에 남은 것에 없는 레코드가 있을 수 있다), commit하지 않는다. 읽는 쪽은 최종 이름만 열어 디렉토리를 나열하지 않는다(#4 §1). 지워도 되지만 의무는 아니다. `link()`를 쓴 경우 링크 뒤·제거 전의 사망은 저장된 레코드 파일의 둘째 이름인 임시 이름을 남기는데, 이것도 남은 것으로서 지울 수 있고 레코드는 최종 이름을 유지한다. **약속하는 것과 하지 않는 것**: 약속은 쓰는 프로세스의 사망까지이고 쓰는 도중의 읽는 쪽은 두 상태 중 하나만 본다. 머신·전원 손실은 약속하지 않는다(#5 A-3) — 그래도 내용의 flush는 세 파일 모두 필수다(두 모듈은 지금도 쓰기마다 flush하므로 더해지는 것은 쓰기마다 생성 한 번과 이름 바꾸기(또는 링크와 제거) 한 번이다). `artifacts.json`의 비용: run이 처음 기록하는 blob마다, class 변경마다 파일 전체 쓰기와 flush 한 번 — 라운드당 몇 번인지는 어떤 기록도 말하지 않으며(어떤 바이너리가 blob인지는 OD-23) 재지 않았다; 통째로 다시 쓰는 것과 레코드 수에 따른 증가는 지금도 있고 ADR-0005 결정 2의 형식에서 온다. 환경의 한계는 ADR-0013 결정 5와 같고, 키 레코드 파일은 파일 시스템이 교체하지 않는 단계를 주어야 한다. **두 작성자는 한계로 남는다**(lock, OD-17 잔여; C-2): `artifacts.json`은 나중의 옮기기가 이기고 그 사이 다른 작성자가 더한 레코드는 blob이 저장되어 있어도 빠진다 — 이 갱신 손실은 지금도 있고 그대로 남으며(ADR-0005 결정 10), 달라지는 것은 파일이 두 쓰기의 섞임이 되지 않는다는 것뿐이다; 키 레코드 파일은 지금처럼 먼저 쓴 쪽의 레코드가 남고 다른 쪽은 아무것도 쓰지 않는다. 저장소와 파일 사이, 이 파일과 `STATE.json`·`events.ndjson` 사이, 두 키 레코드 파일 사이, 파일과 commit 사이의 원자성은 더하지 않았다. **다른 파일**: 이 기록은 세 파일만 다루며 "데이터 plane의 모든 파일"에 대한 규칙이 아니다 — `instance.json`·`spec.json`·결과 파일·`best.json`·`technique_stats.json`이 이 방법으로 쓰이는지는 정하지 않았다(내용·작성자·다시 쓰이는지가 미결: OD-20·OD-7·OD-23·OD-11); 그런 파일의 기록은 ADR-0013과 이 기록을 가리키면 된다.
- **제안으로 남는 부분(미확정)**: **격리 수단** — 후보 ①의 2.~5.(특수 케이스, 쓰기 루트 주입, 강제 백엔드, tools allowlist)와 그 이점·전제조건, 후보 ② 전체. 둘 중 어느 것도 선택되지 않았고 트리는 어느 쪽도 배제하지 않는다(컨테이너 가용성·#5 B-1 대기, OD-14와 같은 결정). scratch·TMPDIR·빌드 캐시의 위치도 여기에 속한다 *(2026-10-07: ADR-0013이 `STATE.json` 옆에 두는 임시 파일은 이 위치 결정에 들지 않는다 — 그 기록의 결정 3; 격리 수단에 넘긴 요구는 하위 질문 ⑭)*. `artifacts.json`(ADR-0005로 확정)과 `events.ndjson`의 줄 형식·봉투(ADR-0006으로 확정)를 뺀 각 파일의 필드·스키마(PLAN P1-8, OD-17·OD-20·OD-7·OD-11)와 `run_id`의 형식도 미정이다 — `events.ndjson`의 이벤트 종류와 종류별 페이로드(PLAN P1-1·P1-3·P1-8, OD-13·OD-10·OD-23), `STATE.json`의 나머지 멤버, `instance.json`·결과 파일의 필드가 여기에 남는다. *(2026-10-07: `STATE.json`은 파일 틀·`round`·`budget_spent`가 ADR-0012로 확정되었다. 남은 멤버와 그것이 걸린 곳 — gate 상태: OD-3 / #5 A-5(오너 전용) · `best_ref`: OD-20 · `lock{owner, heartbeat}`: OD-17 잔여 · `phase`의 값과 단위(라운드·후보·시도 중 어느 것의 마커인지): OD-29·OD-23 · `next_action`의 형식과 어휘: OD-23(PLAN P2-1) · 시각 멤버: 하위 질문 ⑨.)*
- **하위 질문(ADR-0004가 넘긴 것, 2026-10-07 등재, 미결)**: ① 분기·재개의 표현 — 트리에는 분기 레벨이 없고 라운드 번호는 run 안에서 한 번만 쓰인다. 분기·재개(FR-6, S3-3)가 새 run인지 같은 run의 뒤 번호 라운드(출발점은 ADR-0002의 `feedback.base`)인지, 출발점(run·라운드)을 어떻게 가리키는지는 미결이며 트리는 둘 다 허용한다(OD-20 계보와 함께). *(2026-10-07: 분기·재개한 run의 새 budget이 출발점 run의 지출 — [ADR-0011](decisions/ADR-0011-od17-journal-and-spend.md)의 지출 뷰 — 과 어떤 관계인지도 본 질문과 함께 정한다.)* ② 키 디렉토리에 그 키를 쓴 run의 색인 파일을 둘지, 조회가 run들을 읽을지(S5-1; OD-20과 함께). ③ run의 후보가 아닌 baseline(벤더 라이브러리 커널 등)의 측정을 어디에 기록할지(OD-28). ④ 참조 자료 발췌 스냅샷(FR-14 ②)의 위치(OD-12). ⑤ 한 단계가 한 시도에 기록을 둘 이상 남길 때(반복 측정·재측정·board 재시도)의 파일 이름(OD-13·OD-10·OD-11).

- **채택분(ADR-0009, `cpu_standin` 타이밍 실행)**: 하네스의 C 드라이버 프로그램(`hilclaw/harness/` 아래, `main` 제공)과 커널 하나의 소스를 `clang_build.build` 한 번으로 한 실행 파일로 만들고, Python 쪽이 `local_run.run`으로 **별도 프로세스**로 실행한다(실행 파일마다 커널 하나이므로 같은 심볼이 만나지 않는다). 시계는 `clock_gettime(CLOCK_MONOTONIC)`이고 두 읽기 사이에는 커널 호출 하나만 있으며, 드라이버는 구간 길이를 ns 정수로 보고한다 — 그 수에서 측정량을 얻는 방법은 OD-1 그대로다. 세 버퍼는 `malloc` 세 번(`float` 정렬 외에는 약속하지 않음), 입력은 호출자가 준 시드로 드라이버 안에서 한 번 채우고(유한, 크기 [0.5, 1), 파일로 쓰지 않음), 반복 루프와 중단 규칙은 드라이버가 수행한다: `n_min`·`cv_max`는 Python 쪽이 `measurement.py` 상수에서 넘기고, 규칙을 구간 길이에 적용할지 그 역수에 적용할지는 호출자의 파라미터다(기본값 없음 — OD-1). Python 쪽은 보고된 순서 전체에 `stopping_state`를 다시 적용해 일치할 때만 측정으로 받아들인다. 보고는 프로세스가 시작할 때 받은 표준 출력으로 나가는 줄(`resolution_ns`, 반복마다 `interval_ns`, 마지막 `stop converged`/`stop not_converged`)이며 데이터 plane의 파일·필드가 아니다 — 드라이버가 첫 커널 호출 전에 그 채널을 따로 잡고 1번 디스크립터를 표준 오류로 돌리므로, 커널이 표준 출력에 쓰는 것은 보고를 깨지 않는다(ADR-0008의 계약에 의무를 더하지 않음). 완료되지 않은 실행(비정상 종료, 시간 초과, `stop` 줄 누락·형식 위반, 0 구간, 불일치)은 보고된 구간이 규칙을 채웠더라도 측정이 아니고, 그 뒤의 처리는 OD-10·OD-14다. 빌드 플래그·스레드 수·시간 제한 값은 정하지 않았다. 네이티브 Windows는 지원하지 않는다(C-7).
- **하위 질문(ADR-0009가 넘긴 것, 2026-10-07 등재, 미결)**: ⑦ 타이밍 입력의 시드 정책 — 고정인지 실행마다 새로 뽑는지, 실행 뒤 기록하는지 — 와 타이밍 실행의 입력이 같은 시도의 검증 실행의 입력과 같아야 하는지(OD-16과 함께; 하네스 검증 쪽 설계 PLAN P1-3). (2026-10-08) [ADR-0017](decisions/ADR-0017-od16-cpu-standin-verification-run.md)는 이 질문을 **닫지 않았다** — 검증 실행은 타이밍 실행과 별개의 프로그램·프로세스이고 시드도 따로 받는 호출자의 파라미터(기본값 없음)이며, 두 실행의 입력을 같게도 다르게도 만들지 않는다. 검증 쪽 시드의 출처와 실행 뒤 기록 여부는 OD-16 하위 질문 ⑤로 함께 등재되었다. ⑧ 한 번의 호출이 시계 해상도에 가까운 커널(이후의 연산 종류·작은 shape)에서 반복당 호출 수를 늘릴지 — 늘리면 instance별 기록이 필요하다(OD-11 제안).

## OD-15

**sim→board 승격 기준** — #7 §6.

- 제안: **고정 임계값 금지**. (hw_profile, op_class)별 **rank correlation·recall@k를 측정해서** 승격 폭 k 결정. compute-bound와 memory-bound는 다른 k 필요. **sim이 거부한 후보용 ε-greedy 슬롯 상시 확보**(없으면 sim 편향을 영구히 감지 불가) · 매 라운드 sim/board 상관 추적, 열화 시 gate 발동 · **board 측정만이 기록(record)을 세울 수 있음**.

## OD-16

**측정·검증의 위조 불가능성(anti-reward-hacking)** — #7 §5 G1. **본 조사 최대 리스크.** **하네스 수용 기준 확정(2026-10-07, PROCESS/DRIVER.md §9)**: [ADR-0003](decisions/ADR-0003-od16-harness-calibration.md) — 방어책 채택 범위는 미확정 그대로다. **잔여 중 `cpu_standin`에서 `gemm` C 커널의 검증 실행 확정(2026-10-08, 같은 경로; 오라클·tolerance 어휘·기본값 없음은 오너 답변 HQ-0004)**: [ADR-0017](decisions/ADR-0017-od16-cpu-standin-verification-run.md) — FR-9 최소 조항을 수행하는 메커니즘이며, 그 너머의 방어책은 채택도 기각도 하지 않았다.

- **원칙(2026-07-31 개정): 은닉이 아니라 위조 불가능성.** 전부 읽혀도 성립하는 방어만 채택한다(Kerckhoffs). 유일한 예외는 **런타임 시드·입력 값이 파일로 존재하지 않을 것** — 알고리즘은 읽혀도 되고 값만 없으면 된다. → **읽기 제한은 채택하지 않으며 OD-8 후보 ①과 충돌하지 않는다.** 근거: 성능 최적화 시스템에서 정답을 알아도 **베끼면 speedup 1.0이라 이길 수 없고**, harness 은닉은 security-by-obscurity이며(루프홀은 소스를 읽어야만 발견되지 않는다 — 없애는 것이 진짜 방어), 문서·기존 커널 읽기는 저밀도 언어 대응(FR-14)과 콜드스타트(OD-22)에 오히려 필요하다.
- **MVP 최소분(FR-9에 반영됨)**: 코더에 노출되지 않은 입력(shape/seed)으로 코더가 수정할 수 없는 격리 하네스에서 재검증; 실패 결과는 best·통계 미반영; 조기 종료 전 재검증.
- **위협 A — 조작 계열**(출력 버퍼 절도 · harness/타이머 패치 · 점수 레코드 조작 · 감사 로그 조작): **코더와 평가를 별도 프로세스로 분리 + 쓰기 격리**로 소멸한다(OD-8 후보 ① / OD-14). Sakana 사건의 버퍼 절도는 reference와 후보가 같은 프로세스에서 버퍼를 공유했기 때문에 성립했다.
- **위협 B — 산출물 퇴화 계열**(생성 커널이 일을 하지 않음): 치팅이 코더의 정당한 산출물인 소스 안에 있으므로 **격리로는 잡히지 않고 측정 설계로 잡는다**. ⑴ 하드코딩 출력 → **매 trial 런타임 무작위 입력**(값 비파일화) ⑵ 계산 누락 → 오라클 강화(FP32/FP64 CPU 레퍼런스 · opschema 기반 퍼징 · per-(op,dtype) tolerance · 코너케이스 subnormal/zero/inf/NaN/catastrophic cancellation) ⑶ 벤더 라이브러리 디스패치 → **정적 검사**(규칙이 읽혀도 무방 — 우회하려면 위반해야 하고 위반은 탐지된다) + **프로파일러로 해당 커널의 실제 실행 확인** ⑷ 다른 큐/스레드로 회피 → 전체 디바이스 배리어 + 호스트 wall-clock 교차검증 + **roofline(speed-of-light) 상한** ⑸ **타이밍 반복 구간 캐싱**(정확도는 입력을 바꾸지만 성능 측정은 같은 입력을 N회 반복하는 것이 정상이라 열리는 틈) → 매 trial 새 버퍼 할당 · 캐시 플러시 · **1회차 이후 시간 급감 탐지** ⑹ **순서 의존성 테스트**(reference→candidate와 candidate→reference 결과가 다르면 실격).
- **`private_metrics` 재정의**: 은닉 지표가 아니라 **일반화 측정 지표** — 평가에는 쓰되 최적화 대상에는 넣지 않는다. 실배포에서는 대상 shape 분포를 코더에게 알리는 편이 맞다(벤치마크와 위협 모델이 다름).
- **방어가 여전히 필요한 이유**: 코더가 악의를 갖기 때문이 아니라 **탐색 루프가 가장 싼 경로를 고르기 때문**이다. 루프홀이 있으면 결국 선택되고, 그 결과는 board 시간 낭비 · **크로스런 통계 오염(FR-7)** · 잘못된 바이너리 승격이다.
- **흡수: 조기 종료 재검증**(#7 보충 §2(2), #8 M18) — FR-3 ④의 target 조기 달성은 해킹된 결과의 전형적 징후이므로 조기 종료 인정 전 승격 게이트 수준의 재검증을 강제(FR-9에 반영됨).
- **확장(S7, B1/B8)**: 정밀도 하향 검사, warm-up·stream sync·클록 고정 타이밍, 정적 검사·금지 패턴, LLM 검증자, 검증·프로파일 스크립트 보호, 금지 fallback 패턴, 코더 웹 검색 차단(OD-12). 실패 유형 태깅과 다음 라운드 spec의 금지 패턴 주입(OD-6 확장 고려).
- **하네스 자체의 수용 기준**(#7 S-2 N8): Kernel Contracts의 3-상태 캘리브레이션(위반 구현이 실제로 잡히는지 증명)을 하네스 완료 조건으로 채택 검토 — hacker-fixer 루프와 상보.
  - **채택분(ADR-0003, 2026-10-07)**: 3-상태 캘리브레이션을 검증 하네스의 수용 기준으로 채택한다. 대상은 하네스 모듈이고, 증명 단위는 하네스가 검증하는 **연산 종류**다. 세 상태 = 적합 / 실패 / "기능 테스트(미리 고정된 입력에서의 기본 검사, S7-1)는 통과하지만 계약(FR-9 최소 조항 — 알 수 없었던 입력에서도 tolerance 안)을 위반". P1 필수 위반 부류는 **위협 B ⑴(미리 알려진 입력에서만 맞는 출력)** 하나이고, 나머지 부류(위협 A, B ⑵~⑹, S7·B1·B8 확장)는 잡아 줄 방어가 채택되지 않았으므로 요구하지 않는다. "잡힌다" = correctness 판정이 실패인 것까지이며 원인 식별(실패 유형 태깅, S7-3)은 요구하지 않는다. 캘리브레이션 커널은 하네스 테스트의 손으로 쓴 fixture(코더 산출물·카탈로그 항목 아님)이고, 테스트는 패키지의 일반 테스트 스위트에 속하며 tolerance를 인자로 넘긴다(오라클·tolerance 값과 무관하게 성립). 통과가 증명하는 것은 "나열된 위반이 잡힌다"까지다.
  - **채택하지 않은 것**: 위 위협 A·B와 확장의 방어책 어느 것도 ADR-0003으로 채택되거나 기각되지 않았다. hacker-fixer 루프 실행 여부도 그대로 미결이다. [ADR-0009](decisions/ADR-0009-od13-cpu-standin-timing-run.md)(2026-10-07, `cpu_standin` 타이밍 실행)도 같다 — 한 측정의 반복이 같은 버퍼와 입력을 다시 쓰고 첫 반복 전의 비계측 실행 1회의 시간을 읽지 않도록 정했을 뿐, 위협 B ⑷⑸의 방어(매 trial 새 버퍼, 캐시 플러시, 급감 탐지 등)는 채택하지도 기각하지도 않았다. 다만 "1회차 이후 시간 급감 탐지"가 채택되면 비교할 첫 실행의 시간이 필요하므로 ADR-0009 결정 6을 다시 연다.
- **잔여 미결**: 정적 검사 규칙의 범위 · roofline 모델 산출 방법(op_signature별 FLOPs/바이트) · 승격 전 적대적 재검증의 강도 · hacker-fixer 루프로 자기 harness를 사전 강화할지.
- **하위 질문(ADR-0003이 넘긴 것, 2026-10-07 등재, 미결)**: ① 검증 실행이 op_signature의 shape 밖의 shape도 뽑는지 — FR-9는 "shape/seed"라 하지만 spec은 op_signature의 shape을 코더에 노출한다(ADR-0002). 뽑는다면 "알려진 shape에서만 맞는 커널"이 필수 부류에 더해진다(하네스 설계, PLAN P1-3). (2026-10-08) [ADR-0017](decisions/ADR-0017-od16-cpu-standin-verification-run.md)는 이 질문을 **닫지 않았다**: 검증 실행 하나는 호출자가 준 `m`·`k`·`n` 하나를 쓰고 메커니즘은 그 값을 ADR-0008보다 좁히지 않으므로 어느 답에도 바뀌지 않지만, 호출자가 op_signature 밖의 차원을 넘기는지는 — 어떤 shape을 뽑을지, shape에 특화된 커널을 원하는지(위 `private_metrics` 항)가 확정된 입력에 없어 — 미결 그대로다. ② 캘리브레이션을 연산 종류의 dtype·layout마다, 백엔드·실행 지점(sim/board)·커널 언어마다 반복하는지. ③ 측정 쪽(타이밍)에도 캘리브레이션을 둘지(OD-13과 함께 — [ADR-0007](decisions/ADR-0007-od13-measurement-policy.md)은 측정 정책의 P1 최소분만 정했고 이 질문은 미결 그대로다). ④ run이 pin한 하네스 버전과 그 버전의 캘리브레이션 증거를 잇는 방법(OD-11).
- **채택분(ADR-0017, 2026-10-08, `cpu_standin` 검증 실행)**: 대상은 `cpu_standin`·`gemm`·fp32·C 커널(ADR-0008)의 빌드된 시도 하나의 검증 실행이고, FR-10 도구 계약이 아니다(`correctness.check`에서 하네스와 백엔드를 나누는 선은 [ADR-0016](decisions/ADR-0016-od18-backend-frame.md) 결정 3대로 그 도구의 계약에 남는다). **오너 답변([HQ-0004](https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6052377983))**: 오라클은 NumPy float64 — 뽑은 fp32 입력을 float64로 넓혀 곱한 값을 하네스의 Python 쪽에서 계산하고, 커널을 실행하는 프로세스는 reference도 비교도 갖지 않는다(`numpy`는 `hilclaw`의 첫 런타임 의존성으로 승인되었고 핀은 코드 task가 더한다); 비교는 원소별 `rtol`·`atol`, 출력의 NaN·무한대는 실패, 검증 입력은 유한하게 뽑는다; 기본값은 없다(OD-5 절). **ADR의 설계(오너 미확정, 통지 후 7일 이의 기간)**: 하네스가 `main`을 가진 **두 번째 C 소스(검증 프로그램, 타이밍 드라이버와 별개)**를 `hilclaw/harness/` 아래에 두고 커널 하나와 `clang_build.build` 한 번으로 한 실행 파일로 만들어 `local_run.run`으로 별도 프로세스로 실행한다 — ADR-0009의 결정 5·6·8은 다시 열리지 않으며, 대신 한 시도를 두 번 빌드하고 검증된 실행 파일과 타이밍된 실행 파일이 서로 다르다. 입력은 호출자가 준 시드(명령줄 인자; 파일 없음)와 결정적 생성기로 뽑고 크기는 [0.5, 1)·양 부호다(ADR-0009와 같은 범위 — 0·subnormal이 없고, 출력 원소의 정확한 값이 `k`로 유계여서 비유한 출력은 정답일 수 없다). **Python 쪽은 같은 시드로 입력을 다시 생성**해 reference를 계산하므로(생성기는 C와 Python 두 구현이 같은 `float` 비트를 내야 한다) reference는 커널의 프로세스가 말하는 어떤 것에도 기대지 않는다; 두 구현의 불일치를 fail로 만들지 않도록 프로그램이 호출 전에 입력의 검사값을 보고하고 Python 쪽이 대조한다. 프로그램은 호출 전에 `c`를 NaN으로 채우고(쓰지 않은 원소는 비교에서 실패), 호출 뒤 `c`의 바이트를 보고 채널(ADR-0009 결정 8과 같은 방식으로 따로 잡은 표준 출력)에 쓴다 — 파일은 쓰지 않고, tolerance는 프로그램에 넘기지 않는다. draw 수 `draws`(≥ 1)·시드·`rtol`·`atol`·프로세스의 시간 제한은 기본값 없는 호출자의 파라미터다(시간 제한은 프로세스만 묶고 Python 쪽 작업의 상한은 정하지 않았다 — OD-14). 부호가 섞인 입력이라 출력 원소는 서로 상쇄하는 `k`개 항의 합이므로 `atol` = 0인 tolerance에서는 적합한 커널도 실패할 수 있다는 관찰을 적었다(값도 기본값도 아니다). 완료된 실행(시간 초과 없음, 종료 상태 0, 형식 일치, 검사값 일치)의 판정은 모든 draw의 모든 원소가 통과하면 pass, 아니면 fail이고, 완료되지 않은 실행은 **pass도 fail도 아니다**(그 뒤의 처리는 OD-10·OD-14). Python 쪽은 완료된 실행에 대해 판정과 draw별 실패 원소 수(그 가운데 비유한 원소 수 포함)를, 완료되지 않은 실행에 대해 어느 조건이 어긋났는지와 runner가 잡은 것 가운데 보고를 뺀 나머지를 돌려준다. 하네스 자신은 입력·reference의 값을 반환값에 넣지 않지만 runner가 잡은 것은 거르지 않는다 — 표준 오류에는 커널이 찍은 것(입력 포함)이, 명령줄에는 시드가 들어 있으며 그 보관 여부는 하위 질문 ⑤·OD-10이다. 보고 형식은 하네스 두 부분 사이의 내부 인터페이스이며 데이터 plane의 파일·필드가 아니다. ADR-0003의 "미리 고정된 입력의 기능 테스트"는 테스트에 적어 둔 시드의 검증 실행으로 할 수 있다(고정 입력 모드를 더하지 않는다). 위협 A·B의 방어책과 OD-14의 제안은 어느 것도 채택되거나 기각되지 않았다.
- **하위 질문(ADR-0017이 넘긴 것, 2026-10-08 등재, 미결)**: ⑤ 검증을 부르는 쪽의 정책 — 시드를 어디서 누가 뽑는지, 한 라운드의 검증과 승격 게이트 수준의 재검증(FR-3 ④)이 draw를 몇 개 쓰는지, 실행 뒤 시드나 runner가 잡은 것(시드가 든 명령줄, 커널의 표준 오류)을 기록하는지(OD-13 하위 질문 ⑦·OD-10과 함께; PLAN P1-8). ⑥ 한 시도의 검증 실행 파일과 타이밍 실행 파일이 같은 플래그로 빌드되어야 하는지, 또는 하나의 실행 파일이어야 하는지 — 커널은 두 프로그램을 구분해 검증될 때만 제대로 계산할 수 있다(빌드 설정과 함께; 하나의 실행 파일로 답하면 ADR-0017 결정 2와 ADR-0009를 다시 연다). 비유한·코너케이스 입력을 뽑을지는 새 질문이 아니라 위 위협 B ⑵의 제안과 #5 B-7에 그대로 남는다(오너 답변 HQ-0004 (2)).
- **확정분(2026-10-02, #5 A-12) — 하네스 단일 단위**: 채점 장치(입력 생성·f64 reference·tolerance 비교·타이밍·프로파일·eval/event 기록)는 도구 패키지 안의 **한 하위 모듈**(`harness/`)에 모여 있고, 코더 scratch에 포함되지 않으며, P1 버전 = 소스 commit 해시(OD-11).
- (통합자 해석) 위 확정은 OD-8 후보 ①/② 어느 쪽에서도 성립하며, 위협 A(조작 계열) 방어의 **전제 조건**이다 — 보호는 위치가 정해진 것에만 걸 수 있다. 3-상태 캘리브레이션(#7 S-2 N8)도 이 단위를 대상으로 하게 된다.

**실행 내구성 정책** — #4 코멘트 · #7 §5 G4. **저널 대상 단계의 기록과 지출 계상 확정(2026-10-07, PROCESS/DRIVER.md §9)**: [ADR-0011](decisions/ADR-0011-od17-journal-and-spend.md) — lock·fencing과 재시도 정책은 미확정 그대로이며, 등록부의 상태는 `제안됨` 그대로다.

- **채택분(ADR-0011)**: 아래 제안에서 **지출 전·후 두 이벤트**, **idempotency key**, **`budget_spent`를 로그의 fold로 유도**하는 것과 **스냅샷 + tail 재생**을 채택했다. 제안과 달라진 점: 종류 이름은 `intent`·`result`가 아니라 `step_started`·`step_ended`(도구 실패로 끝난 단계의 줄이 ADR-0010의 "결과"를 싣지 않으므로), 스냅샷은 "라운드 N마다"가 아니라 **매 라운드 종료 시** `STATE.json` 안에 둔다(#4 §3c가 이미 그때 `budget_spent`를 갱신한다). ADR이 새로 정한 것: **저널 대상 단계**(반복하면 제한된 자원을 쓰거나, 결과가 프로세스 사망을 견뎌야 하는 단계의 실행 1회 — 출처가 이름 준 것은 board 측정 하나)의 정의; 시작 줄은 자원을 쓰기 전에 완결되고 끝 줄은 결과가 생기는 즉시 추가되며 둘 다 도구 계층이 쓴다(hook인지 진입점 아래 코드인지는 OD-18 잔여 — *2026-10-07, 그 뒤: [ADR-0015](decisions/ADR-0015-od18-tool-contract-frame.md)(OD-18)가 진입점 아래의 도구 함수로 정했고, 요청이 식별을 싣는 방법(최상위 멤버 `round`·`candidate`·`attempt`·`execution`, `step`은 도구의 계약)도 그 기록이 정했다*); **식별** = 줄의 봉투 번호(`round`·`candidate`·`attempt` 중 해당하는 것) + `data.step`(*name*, 값 목록 없음) + `data.execution`(1부터의 정수) — 호출자가 주고 파일만으로 유도할 수 있어야 하며 봉투는 바뀌지 않는다; 끝 줄의 `data`는 `spend`와, `result`(호출의 결과 자체 — 실패한 실험을 보고하는 결과 포함) 또는 `failure`(결과 없이 끝난 도구 실패의 `kind`·`message`) 중 정확히 하나를 싣는다; **반복 호출의 규칙** — 도구 계층은 단계를 시작하기 전에 로그에서 식별의 상태를 확인해, 줄이 없으면 실행하고, 끝났으면 실행하지 않고 끝 줄이 실은 것(`result`, 또는 `failure`였다면 같은 도구 실패)을 돌려주며, 열려 있으면(시작 줄만 있음) 실행하지 않고 도구 실패로 "열림"을 알린다(한 식별은 두 번 시작되지 않고, 다시 실행하려면 더 큰 `execution`의 새 식별이 필요하다); 재개한 턴이 내릴 수 있는 결론(없음 = 실행, 끝남 = 건너뛰고 줄에서 결과를 얻음, 열림 = 건너뛰지도 그 식별로 실행하지도 않음 — 자원이 쓰였는지·얼마인지·결과가 있었는지는 알 수 없다); `phase` 마커는 남되 저널 대상 단계에 대해서는 **로그가 정본**이다(마커가 뒤처졌으면 로그를 따르고, 마커가 앞서 있으면 마커가 틀린 것으로 보고한다); **지출의 정본** = 완결된 `step_ended` 줄의 `spend`(축 *name* → 음이 아닌 정수; 축 목록·단위·측정 주체는 정하지 않음), `budget_spent`는 (로그를 거쳐 계상되는 금액에 한해) 독립된 기록이 아니라 로그 접두부의 **지출 뷰**(축별 합계, 접은 위치 = 완결된 줄의 수, 그 위치에서 열려 있는 단계)이고, 저장된 뷰는 라운드가 끝날 때만 움직이며, 현재 값 = 저장된 뷰 + 그 뒤 꼬리의 fold다 — 꼬리는 직전 라운드 종료 뒤에 추가된 줄(진행 중인 라운드의 줄과 이전 라운드에 관한 늦은 줄)로 한정되어 해석·합산하는 줄의 수가 run 길이에 따라 늘지 않는다(위치까지 건너뛰는 것은 줄바꿈을 세는 일이며, 바이트 오프셋을 함께 둘지는 PLAN P1-8); 로그를 거치지 않는 축의 누계를 어디에 두는지는 정하지 않았다; 뷰와 로그가 다르면 로그가 이기고, 첫 줄부터의 fold는 언제나 허용되지만 턴 진입에 요구되지 않는다; fold는 도구 계층의 결정적 계산이며 턴이 로그를 컨텍스트로 읽어 합산하지 않는다; 열린 단계의 지출은 기록되지 않고 지어내지도 않으므로 합계는 하한이고 뷰가 열린 단계를 함께 보인다; "`STATE.json` 전체가 재생성 가능한 뷰"는 채택도 기각도 하지 않았다(`next_action`·`best_ref`·gate 상태·lock은 다루지 않음). 보호하지 못하는 것(동시에 도는 두 턴, commit 전 머신 손실, 줄을 쓰지 않고 지출하는 도구, 결과와 끝 줄 사이의 창, `execution`을 스스로 올리는 호출자)은 기록의 결정 2·9에 있다.
- **제안으로 남는 부분(미확정)**: `lock{owner,heartbeat}`와 **CAS push fencing**, 도구별 **선언적 재시도 정책**, 열린 단계의 회복(재실행·대기·포기 — OD-10과 함께). ADR-0011은 이들을 채택하지도 기각하지도 않았다. 예산 집행(OD-19)·gate(OD-3)·토큰 계상의 범위(#5 A-8)·HW quota 축(OD-2)도 같다.
- **하위 질문(ADR-0011이 넘긴 것, 2026-10-07 등재, 미결)**: ① 이전 라운드나 run 전체에 관한 저널 대상 단계(예: 나중의 재측정)는 저장된 위치 앞에 줄이 있어 식별 조회가 로그를 첫 줄부터 읽는다 — 그런 단계가 있는지, 색인이 필요한지(OD-13 하위 질문 ①·OD-20과 함께). *(2026-10-07: 저장된 `round`보다 큰 라운드에 관한 식별 — ADR-0012 결정 3에 따르면 아직 시작되지 않은 라운드 — 을 요청이 실은 경우도 이 질문에 함께 둔다. ADR-0015는 그런 요청을 거절하는 규칙을 더하지 않고 한계로만 적었다: 지금의 조회는 그 라운드가 저장된 라운드가 된 뒤 그 줄들을 보지 못한다.)* ② 도구 계층이 금액을 말할 수 없는 채로 끝난 단계의 기록과, 이미 기록된 금액의 정정 방법(줄은 고치지 않는다). ③ 저장된 뷰를 첫 줄부터의 fold와 언제·누가 대조하는지(PLAN P1-8·OD-23).
- 제안: 지출 전 `intent` + 후 `result` 이벤트를 **idempotency key**로 묶기 · **`budget_spent`를 저장값이 아니라 `events.ndjson` fold로 유도**(STATE.json은 재생성 가능한 materialized view; #4 §1 "전 디렉토리 스캔 금지"와의 긴장은 라운드 N마다 fold 스냅샷 + tail 재생 규약으로 **해소 제안(미확정)** — #8 M7은 A급 모순으로 열려 있으며 규약 확정 후 OD-17 본문·#4 §1을 함께 갱신해야 한다) · `lock{owner,heartbeat}`는 fencing 없는 lease라 불안전하므로 **읽은 STATE commit SHA를 expected parent로 CAS push**하여 git을 fencing 수단으로 사용 · 도구별 **선언적 재시도 정책**(모델 판단 금지).
- (2026-10-07) `events.ndjson`의 줄 형식과 봉투는 OD-8 잔여분으로 [ADR-0006](decisions/ADR-0006-od8-events-log.md)에서 정해졌다. 그 기록은 위 제안의 어느 부분도 채택하거나 기각하지 않았고(봉투가 이를 막지 않는다는 것만 보였다), 본 항목의 상태는 `제안됨` 그대로다. *(같은 날 뒤에 ADR-0011이 위 채택분을 정했다 — #8 M7의 규약은 그 기록의 결정 6이며, #8의 체크와 #4 §1 문구 갱신은 이의 기간 뒤 통합자 후속이다.)* *(그 뒤 [ADR-0012](decisions/ADR-0012-od8-runtime-state-file.md)(OD-8)가 ADR-0011이 PLAN P1-8에 넘긴 `budget_spent`의 저장 형식을 정했다 — 위치는 줄 수만 두고 바이트 오프셋은 두지 않으며, 합계는 크기 제한 없는 정수다. 본 항목의 확정분·잔여는 달라지지 않았다.)*

## OD-18

**강제 계층(hooks) 및 라운드 경계 정의** — #4 코멘트 · #7 §5 G5. **FR-10 도구의 노출 형태 확정(2026-10-07, PROCESS/DRIVER.md §9)**: [ADR-0010](decisions/ADR-0010-od18-tool-exposure-form.md) — hook·라운드 경계·불변식 목록은 미확정 그대로다. **모든 도구 계약이 공유하는 틀 확정(2026-10-07, 같은 경로)**: [ADR-0015](decisions/ADR-0015-od18-tool-contract-frame.md) — 저널 대상 단계의 두 줄을 쓰는 위치만 정했고 그 밖의 hook은 미확정 그대로이며, 등록부의 상태는 `제안됨` 그대로다. **HW 도구의 백엔드 틀 확정(2026-10-08, 같은 경로)**: [ADR-0016](decisions/ADR-0016-od18-backend-frame.md) — 어떤 도구의 계약도, 백엔드에 닿는 방법(#5 B-2)도 정하지 않았고 등록부의 상태는 `제안됨` 그대로다.

- 제안: `SessionStart`(STATE·예산·gate 주입) · `PreToolUse`(board.run 예산·중복·gate 검사, harness 경로 deny) · `PostToolUse`(**결과 저널링은 모델 행동이면 안 됨**) · `Stop`(commit 강제) · `PreCompact` 차단 · `AGENT_STOP` kill switch · **default-FAIL 계약**과 **Write 권한 없는 fresh-context 평가자**.
- **`.claude/agents/`가 세션 중 재탐지되지 않으므로 NFR-7①은 "1 round = 1 OS process = 1 turn = 1 commit"일 때만 성립**. UC-3의 `/loop`(동일 프로세스 반복)과의 관계 정리 필요(#8 M4).
- **흡수: CLAUDE.md 불변식 목록**(#4 §6) — 세션 기동 시 강제할 규범 목록 확정. 현재까지 나온 것: "agent-memory 전체를 삭제해도 FR-6·FR-7·NFR-2가 성립한다" · "전 디렉토리 스캔 금지, STATE.json이 유일 진입점"(#4 §1).
- **흡수: FR-10 도구의 노출 형태 — 질문 이관**(#5 A-12, 2026-10-02): ~~MCP 서버 vs Bash CLI 중 무엇으로 1층에 노출할지는 OD-18에서 결정한다(A-12는 "미결, OD-18과 함께"로만 기록).~~ → [ADR-0010](decisions/ADR-0010-od18-tool-exposure-form.md)으로 확정(2026-10-07): 둘 다, 한 패키지의 두 진입점으로 — 에이전트는 MCP 서버의 타입 있는 도구를 호출하고, 명령줄은 사람·스크립트·테스트용이다.
- **채택분(ADR-0010, FR-10 도구의 노출 형태와 호출 규약)**: 도구는 패키지 안에서 **도구 함수** 하나로 정의된다 — 요청(JSON 객체 하나)을 받아 결과(JSON 객체 하나)를 돌려주거나 도구 실패를 낸다. 바이너리는 요청·결과에 싣지 않고 CAS 해시로 가리킨다(C-3). 도구 이름 → 도구 함수의 **등록표**는 프로세스 시작 시 만들어지고(MVP는 고정 집합, #5 A-12), 진입점은 디코드 → 등록표 조회 → 호출 → 인코드만 한다(도구 함수에 도달한 호출에 대해서는 진입점이 도구 논리·기본값·검사·부수 효과를 갖지 않으므로 두 진입점의 동작이 같고, P1-1의 적합성 테스트가 같은 요청을 두 진입점에 넣어 비교한다; 모르는 도구 이름이나 요청이 아닌 입력처럼 진입점이 스스로 답하는 경우는 진입점마다 방식이 다르다). **MCP 진입점**: stdio 서버(세션에 줄지 sub-agent에 줄지 — `.mcp.json`·`--mcp-config`·에이전트 정의의 `mcpServers` — 는 정하지 않았다), 서버 이름 `hilclaw`, 도구의 MCP 이름은 FR-10 이름의 `.`을 `_`로 바꾼 것(에이전트에게는 `mcp__hilclaw__sim_run`·`…board_run`·`…profiler_collect`·`…correctness_check`·`…blob_push`·`…blob_fetch`), 요청 = `tools/call`의 `arguments`, 결과 = `isError` false + 결과의 JSON 텍스트를 담은 텍스트 블록 하나, 도구 실패 = `isError` true + 오류 객체. **명령줄 진입점**: 패키지의 명령 하나에 도구 이름(FR-10 표기 그대로)이 유일한 인자, 요청은 표준 입력, 종료 상태 0 = 표준 출력에 결과 객체 하나, 그 밖의 종료 상태 = 도구 실패(`{"error": {"kind": …, "message": …}}` — 모르는 도구 이름과 JSON 객체가 아닌 입력도 같은 방식으로 보고하며, 출력이 비는 것은 진입점이 보고조차 못 한 경우뿐), 표준 오류는 해석하지 않는 진단. **결과와 도구 실패의 구분**: 실험·동작이 확인한 것은 그 실패까지 포함해 결과이고(검증에 실패한 후보, 미수렴 측정 등), 도구 실패는 아무 결과도 얻지 못했다는 뜻이다 — `kind`는 형식(*name*)만 정했고 값 목록은 없다. 데이터 루트는 기존 `hilclaw.config.load_data_repo()` 그대로(새로 정한 것 없음). 규약에는 버전 멤버가 없고 소스 commit이 pin이다(OD-11 확정분). MCP 서버는 한 호출의 결과가 이전 호출에서 서버 프로세스가 간직한 상태에 기대지 않아야 한다(다시 만들 수 있는 연결·캐시는 해당하지 않으며, 백엔드 연결의 수명과 board 예약·잠금은 #5 B-2·OD-10·OD-17 그대로다) — 서버 프로세스(수명은 등록 방식에 따라 세션 또는 sub-agent)가 바뀌어야 교체된 도구 계층이 에이전트에게 적용되며, 라운드 = 프로세스 경계 여부(#8 M4)는 정하지 않았다. 새 외부 의존성 없이 표준 라이브러리만으로 구현한다(MCP SDK는 A-13의 오너 결정 사항이므로 선택지에서 제외). Claude Code·MCP에 관한 사실은 기록의 Context 표에 문서 확인(2026-10-07)/미확인으로 구분해 두었다 — 실제 세션에서 시험한 것은 없다.
- **채택하지 않은 것(ADR-0010)**: 위 제안의 hook 어느 것도(`SessionStart`·`PreToolUse`·`PostToolUse`·`Stop`·`PreCompact`·kill switch·default-FAIL), 라운드 = 프로세스 경계도, 불변식 목록도 채택되거나 기각되지 않았다. OD-8 후보 ①/②·OD-14의 격리 수단, OD-23의 로스터·per-agent allowlist, gate(OD-3)도 같다. 기록은 선택한 형태가 무엇을 가능하게 남기는지만 적었다: 후보 ① 4.(in-process 에이전트에 Bash 없음)는 가능하고(그런 에이전트의 `tools`에 MCP 도구를 하나씩 적을 수 있다), 후보 ②는 형태와 무관하며, 나중의 hook은 타입 있는 도구의 이름·요청·호출한 에이전트를 볼 수 있으나 **명령줄 진입점을 통한 호출은 Bash 명령 문자열로만 본다**. 따라서 모든 경로에서 성립해야 하는 검사와 ADR-0006 결정 7의 이벤트 추가를 hook에 둘지 진입점 아래의 도구 계층에 둘지는 미결이다. *(2026-10-07: [ADR-0011](decisions/ADR-0011-od17-journal-and-spend.md)이 정한 시작 줄·끝 줄의 추가와 반복 호출의 확인도 같은 배치 질문에 놓인다 — 그 기록도 고르지 않았다.)* *(2026-10-07, 그 뒤: [ADR-0015](decisions/ADR-0015-od18-tool-contract-frame.md)가 이 배치 질문 가운데 **저널 대상 단계의 조회와 시작 줄·끝 줄**에 답했다 — 진입점 아래, 그 도구의 도구 함수 안이다. 비싼 결과에 대한 ADR-0006 결정 7의 추가는 그 끝 줄이므로 함께 답해졌다. 호출 전 검사(예산·gate, 그리고 이 조회 밖의 중복 검사)를 hook에 둘지 도구 계층에 둘지, 두 줄 밖의 이벤트를 누가 추가하는지는 미결 그대로다 — 저널 대상 단계의 중복 확인은 이 조회이므로 위치가 정해졌다.)*
- **채택분(ADR-0015, 모든 도구 계약이 공유하는 틀)**: 어떤 도구의 인자·결과 멤버·실패 종류·`step` 값도, 어느 도구가 저널 대상인지도 정하지 않고 모든 도구에 같은 부분만 정했다. ① **도구 정의**: 등록표는 도구마다 이름·도구 함수·`description`(비어 있지 않은 문자열)·`input_schema`(`type`이 `object`인 JSON Schema 객체)를 한 곳에 두고, 진입점은 자기 문구나 스키마를 갖지 않는다(MCP 진입점은 등록표의 것을 그대로 `description`·`inputSchema`로 나열한다). 스키마는 호출자에게 알리는 것이고 **패키지의 어느 부분도 요청을 스키마에 대조하지 않는다** — 요청은 도구 함수가 스스로 검사하며(진입점 아래), 스키마는 도구 함수가 받아들이는 요청을 모두 허용해야 한다(JSON Schema 검증기는 표준 라이브러리에 없고 새 의존성은 오너 결정이며, 패키지가 직접 구현한 부분집합은 *name*·`run_id`·번호의 짝 규칙을 표현하지 못해 검사가 둘이 된다). ② **예약된 `kind`**(모든 도구에서 한 뜻): `invalid_request`(도구 함수가 요청을 거절함 — 데이터 루트를 묻기 전, 아무것도 읽거나 쓰거나 소비하기 전), `no_data_root`(데이터 루트를 얻지 못함), `step_open`(그 식별의 단계가 열려 있음 — 코드의 관례였던 것을 예약), `tool_crashed`·`bad_result`(도구 함수의 결함 — 같음). 닫힌 목록이 아니며 그 밖의 종류는 도구마다의 계약 그대로다. 명령줄 진입점이 설명·스키마를 사람에게 보여 주는 방법을 둘지는 코드 task에 남겼다. ③ **데이터 루트**: 요청의 멤버가 아니고 호출하는 에이전트가 고르지 않는다. 데이터 plane이 필요한 도구 함수는 등록표를 만들 때 **데이터 루트 공급자**(인자 없이 불려 데이터 루트를 돌려주거나 실패하는 것 — 패키지의 두 진입점에서는 기존 `hilclaw.config.load_data_repo()`, 테스트에서는 자기 것)에 묶이고, 공급자는 필요한 호출마다 불리며 그 답을 다음 호출을 위해 간직하지 않는다(세션만큼 사는 MCP 서버와 호출마다 새 프로세스인 명령줄이 설정 변경 뒤에도 같은 트리를 쓰도록). 기록은 ADR-0010 결정 2("요청 하나를 받는다")를 글자 그대로 두고, 결정 5의 "진입점이 그 호출자"를 "데이터 루트는 진입점 프로세스와 함께 — 그 프로세스의 설정 파일과 두 환경 변수에서만 — 들어온다"로 읽었다(진입점 모듈이 호출 전에 설정을 읽는다는 뜻으로 읽지 않음: 그러면 진입점이 검사와 자기만의 실패, 어느 도구가 트리를 쓰는지에 대한 지식을 갖게 된다). ④ **run과 식별**: 요청의 다섯 멤버 이름 `run_id`·`round`·`candidate`·`attempt`·`execution`은 모든 도구에서 한 뜻이고(봉투와 같은 이름·같은 짝 규칙, 없는 번호는 뺀다) 최상위에 둔다. 저널 대상 도구의 요청은 `run_id`·`execution`과 그 단계가 가리키는 번호를 싣고, **`execution`은 필수이며 기본값이 없다**(식별은 호출자가 준다 — ADR-0011), **`step`은 요청에 싣지 않고 도구의 계약이 정한다**(두 도구가 같은 `step` 값을 쓰지 않는다; 값 목록은 없다). 유효하지 않은 run·식별은 `invalid_request`다. ⑤ **두 줄의 위치**: 조회·시작 줄·단계·끝 줄은 **진입점 아래, 저널 대상 도구의 도구 함수 안**에서 수행한다(`hilclaw.journaled_step.run`이 이미 있는 라이브러리 형태; 도구 함수마다 쓸지 등록 때 한 부분을 씌울지는 코드 task) — 등록표에는 그것을 돌아 단계에 닿는 길이 없어야 한다. `PostToolUse` 하나로는 시작 줄을 단계 전에 완결할 수도 반복 호출의 답을 정할 수도 없고 도구 실패로 끝난 호출에는 발동하지도 않으며, `PreToolUse`+`PostToolUse` 쌍은 명령줄 호출을 보지 못하고, 끝난 단계에 대해 호출을 막을 수만 있을 뿐 저장된 결과를 돌려주게 할 수 없고, `claude -p` 자식은 자기 세션의 hook을 따른다(Claude Code·MCP 문서 확인 2026-10-07, 실제 세션 미확인). 보호하지 못하는 것(접근 통제 없음, 틀린 식별이나 스스로 올린 `execution`, 저장된 `round`보다 큰 라운드에 관한 식별, 동시의 두 호출, 틀을 쓰지 않는 도구, 두 진입점 프로세스의 환경이 다른 경우)은 기록의 결정 7에 있다.
- **채택분(ADR-0016, HW 도구의 백엔드 틀)**: 어떤 도구도 어떤 백엔드의 메커니즘도 정하지 않고 모든 HW 도구·모든 백엔드에 같은 부분만 정했다(ADR-0015가 다음 기록에 넘긴 항목 — 도구 없이 먼저 왔다: `blob.push`/`blob.fetch`는 #5 B-2·A-3, `correctness.check`는 오라클·tolerance, 나머지 셋은 빌드 주체·결과 파일·샘플 형태·지출 축이 정해지지 않아 이 기록에서 계약을 줄 수 있는 도구가 없다). ① **백엔드**: 한 `accelerator`의 대상(board·시뮬레이터·스탠드인)에서 HW 도구(FR-10의 네 도구)의 실험을 수행하는 패키지의 부분이다. 이름은 그 `accelerator` 값이고(ADR-0001 결정 1의 "accelerator or backend"; `cpu_standin`이 두 뜻으로 쓰인다), 제공하는 HW 도구마다 **동작(operation)** 하나를 갖는다(어느 도구를 제공하는지는 ④). **백엔드 표**(이름 → 백엔드)는 등록표처럼 등록표를 만들 때 만들어지며 MVP에서는 소스에서만 만들어진다(그 뒤 온보딩 등록부에서 항목이 생기게 할지는 OD-26이며 틀은 막지 않는다 — NFR-6). 백엔드는 HW 도구의 도구 함수 아래에 놓이고 HW 도구는 백엔드를 통해서만 대상에 닿는다. 요청의 검사·데이터 루트·저널 경로·선택·결과의 형식과 `kind`는 모든 백엔드에 대해 도구 함수의 몫이고, 백엔드의 몫은 한 대상에서 실험을 수행해 도구의 계약이 허용하는 것을 돌려주는 것이다. ② **호출의 순서**: 요청 검사 → 데이터 루트 → (저널 대상이면) 조회 — 끝났거나 열린 식별은 로그에서 답하고 **백엔드를 선택하지도 부르지도 않는다** → 백엔드 선택과 호출된 도구의 동작 찾기 → (저널 대상이면) 시작 줄 → 동작 호출 → 끝 줄·결과. 선택에서 실패한 호출은 어느 대상에서도 아무것도 소비하지 않았고 줄을 남기지 않는다 — ADR-0011 결정 3의 "줄 없음" 경우와 ADR-0015 결정 5의 순서(시작 줄 → 단계 → 끝 줄)를, 그런 호출은 `invalid_request`·`no_data_root`로 거절된 호출처럼 단계를 시작하지 않은 것으로 읽었다(두 기록은 고치지 않음; 조회 뒤에 두는 이유: 저장된 결과는 표가 바뀐 뒤에도 얻을 수 있어야 한다; 시작 줄 앞에 두는 이유: 단계 안에서 실패하면 그 식별이 `failure`로 끝나 고친 뒤의 호출이 더 큰 `execution`을 요구한다). ③ **백엔드는 도구의 계약 그대로만 답한다**: 자기만의 결과 멤버나 실패 종류를 더하지 않는다(계약이 이름 준 산출을 덜 쓸 수는 있다) — "transport 무관"의 백엔드 쪽 뜻이며, mock으로 돌린 계약 테스트의 경우가 곧 모든 백엔드가 지켜야 하는 경우가 된다. 백엔드가 진입점 프로세스에 간직한 상태에 결과가 기대지 않는다(ADR-0010 결정 7; 다시 만들 수 있는 연결·캐시는 해당하지 않고 연결의 수명·예약·잠금은 #5 B-2·OD-10·OD-17 그대로). 두 단계 줄은 도구 함수가 쓰고 백엔드는 그 두 줄을 쓰지 않으며(다른 종류의 줄을 누가 쓰는지는 ADR-0015가 남긴 대로 미결 — PLAN P2-4), 그 밖의 파일(blob, 시도의 결과 파일)을 누가 쓰는지는 도구마다의 계약이다. ④ **예약된 `kind` 둘 추가**: `no_backend`(호출의 hw_profile의 `accelerator`에 해당하는 항목이 표에 없음), `not_offered`(선택된 백엔드가 호출된 도구의 동작을 제공하지 않음) — HW 도구만 내고, HW 도구가 아닌 도구(`blob.push`·`blob.fetch` 포함)도 두 이름을 다른 뜻으로 쓰지 않는다. ADR-0015 결정 2의 표를 모든 도구 계약의 공통 부분이며 닫힌 목록이 아닌 것으로 읽어 공통 부분에 더했다(그 이름을 쓰는 도구 계약은 없다; ADR-0015는 고치지 않음). 모든 백엔드가 네 도구를 다 제공해야 하는지는 정하지 않았다(sim-only 온보딩 = OD-26). `blob.push`/`blob.fetch`는 HW 도구가 아니며 C-3이 말하는 그 "백엔드"는 저장소다(#5 B-2·A-3). ⑤ **선택**: 백엔드를 이름 주는 것은 없다 — 요청의 멤버도, 호출하는 에이전트도, 진입점 프로세스의 설정·환경도, 프로세스가 간직한 값도 아니다. 호출의 백엔드는 **호출이 가리키는 hw_profile의 `accelerator`**로 표에서 정해지고(다른 키 필드는 백엔드를 고르지 않는다 — 컴파일러 갱신이나 다른 호스트는 같은 백엔드의 새 키), run에 관한 호출에서는 그 hw_profile이 **요청이 가리킨 run의 것**(instance 시작 때 선택된 것 — FR-14 ④)이고 호출마다 데이터 plane에서 읽는다(run에 관한 것이 아닌 호출은 규칙이 없다 — 하위 질문 ⑥) — 그래서 run에 관한 HW 도구의 요청은 저널 대상이든 아니든 ADR-0015의 뜻으로 `run_id`를 싣는다. 한 hw_profile 아래 여러 장비(같은 `host` 값의 두 머신은 한 키를 공유한다) 가운데 어느 것으로 가는지와 그 선택을 위해 요청이 무엇을 실을 수 있는지(예약 등)는 백엔드에 닿는 방법이어서 정하지 않았다(#5 B-2·OD-10). 요청이 백엔드나 hw_profile 키를 이름 주면 호출하는 에이전트가 한 run의 시도를 다른 대상에서 측정할 수 있고, ADR-0011 결정 3이 단계의 두 줄에 정한 멤버 가운데 측정된 대상을 이름 주는 것이 없어 결과가 어디서 측정되었는지 드러나지 않은 채 그 run의 hw_profile의 지식으로 들어간다(#5 A-7이 `cpu_standin`을 따로 키잉한 이유, ADR-0015 결정 3이 데이터 루트를 요청에 싣지 않은 이유와 같다). run이 자기 hw_profile을 어느 파일의 어느 멤버에 적는지는 출처가 없다 — `instance.json`은 멤버가 정해지지 않았고(PLAN P1-8) 시도의 `spec.json`은 레코드 전체를 싣지만(ADR-0002) 코더 호출마다만 있고 역할이 조립한 사본이다: 어느 쪽도 고르지 않았고 멤버도 정의하지 않았다(하위 질문 ⑥). 읽을 수 없거나 유효하지 않은 hw_profile은 `no_backend`가 아니라 쓸 수 없는 run이다(하위 질문 ④). ⑥ **mock 백엔드**: 뒤에 하드웨어·시뮬레이터·다른 프로세스·네트워크가 없는 패키지의 백엔드이고, `default_registry`가 만드는 모든 등록표의 백엔드 표에 들어 있다("항상 갖는다"의 해석). **위 ⑤의 규칙으로만 선택된다** — 그 항목은 자기만의 예약된 이름을 갖고, `accelerator`가 그 이름인 hw_profile을 통해서만 닿는다(요청의 멤버나 진입점의 변수 같은 둘째 길은 실제 대상에 관한 호출을 mock 산출로 답하는 길이 된다). 그 산출을 실제 대상의 지식과 떼어 놓는 것은 `cpu_standin`을 NPU와 떼어 놓는 것과 같다: 자기 hw_profile, 그 키 아래의 지식, 그 이름으로 시작하는 키 디렉토리 이름(ADR-0001 결정 3). 이름의 표기는 코드 task에 남겼고 그런 레코드의 값은 하나도 정하지 않았다. **무엇을 낼지는 표를 만들 때 묶인 스크립트가 정한다** — 스크립트는 호출(호출된 도구·요청·hw_profile)에서 동작이 하는 일로 가는 함수이고 동작이 불릴 때 물어진다. 테스트는 자기 스크립트에 묶인 mock으로 등록표를 만들고(자기 데이터 루트 공급자를 묶듯이), 두 진입점의 기본 등록표는 소스에 고정된 스크립트 하나에 묶인 mock을 갖는다(그 스크립트가 도구마다 무엇을 답하는지는 그 도구의 계약과 함께 쓴다). 스크립트가 표현할 수 있어야 하는 것: 도구의 계약 아래 백엔드가 돌려줄 수 있는 모든 것(결과, 실패한 실험을 보고하는 결과, 계약이 백엔드에 허용한 도구 실패 `kind` 각각), 그리고 저널 대상 도구에서는 백엔드가 일으킬 수 있는 사망 지점 하나(동작 도중의 프로세스 사망 — 시작 줄 뒤·끝 줄 앞). `not_offered`·`no_backend`는 어떤 동작도 불리기 전의 답이어서 스크립트의 일이 아니다 — 테스트는 그 도구의 동작 없이 만든 mock을 넣은 표, 또는 그 항목이 없는 표로 만든다. 기본 등록표의 mock은 그 등록표의 모든 HW 도구를 제공한다. **실제 board나 시뮬레이터의 고장은 하나도 열거하지 않았다**(OD-10·#5 B-2·B-3). mock 호출의 산출은 스크립트와 그 호출에만 기댄다(시계·난수·횟수·자기 파일 없음) — "처음엔 실패, 다음엔 성공"은 호출 횟수로 쓰지 않고, 요청이 `execution`을 싣는 도구에서는 그 멤버로 쓴다. 보호하지 못하는 것(접근 통제 없음 — 다른 run을 가리키는 호출자와 하위 질문 ⑥의 자리를 쓸 수 있는 자; **닿은 대상이 키가 기술한 장비인지 확인하지 않음** — 선택은 `accelerator`만 읽는다; 계약을 지키지 않는 백엔드; 한 대상에 대한 동시의 두 호출; mock 산출을 실제 것으로 여기는 일; 서버 프로세스와 명령줄의 표가 다른 소스에서 온 경우)은 기록의 결정 6에 있다.

## OD-19

**예산 집행(enforcement) 정책** — #7 보충 §2(1), #8 M5.

- **C-7(#5 B-6) 반영 — 제안**: Claude Code를 Max 구독으로 쓰므로 희소 자원은 달러가 아닌 **플랜 사용 한도(rate limit)** 다. 한도 도달("rate limited")은 run 실패가 아니라 **일시정지 → 한도 회복 후 재개**(NFR-1·OD-17의 재개 경로 재사용) 조건으로 정의하고, 야간 무인 run(S2)은 이를 전제로 설계한다. 중첩 `claude -p` 코더가 같은 한도를 공유하므로 단일 원장은 토큰 수와 함께 한도 소진율을 추적한다.
- NFR-5는 "집계할 수 있어야 한다"까지만 요구하여 **다음 지출을 막는 경로가 요구사항 어디에도 없다**. 제안: 검사를 **다음 지출의 경로 위에** 둘 것 · run 예산과 별도로 **라운드당 상한 + 코더 호출 횟수 상한**(FR-1 ⑴ repair 복귀 상한 포함; N후보 시 후보별 상한) · 오케스트레이터와 모든 중첩 `claude -p`를 **단일 원장**에 합산하고 spawn 전 확인(중첩이 비용 증폭 경로) · 원장을 세션 밖에 영속(재개된 run이 자기 예산을 0으로 리셋 불가) · **무진전 서킷브레이커**(N라운드 연속 미개선 시 중단).
- (2026-10-07) [ADR-0011](decisions/ADR-0011-od17-journal-and-spend.md)(OD-17의 한 부분)은 지출을 **어디에 적고 합계를 어떻게 얻는지**만 정했다 — 재개한 턴의 합계는 저장된 뷰와 로그 꼬리에서 나오므로 0으로 돌아가지 않는다. 위 제안의 어느 것도(다음 지출 경로 위의 검사, 라운드당·코더 호출 상한, 단일 원장, 서킷브레이커, rate limit 일시정지) 그 기록으로 채택되거나 기각되지 않았고, 합계가 예산에 닿거나 넘어도 그 기록만으로는 아무 일도 일어나지 않는다. 금액을 알 수 없는 "열린 단계"를 예산에 어떻게 반영할지도 본 항목에 남는다.
- 하위 질문(UC-3 대안 흐름, PR #10): 검증 실패가 반복될 때 비수렴 판정(UC-7)과 어떻게 연동할지 — 검증 전건 실패 라운드를 "무진전 라운드"로 세어 서킷브레이커 대상에 넣을지, 별도 카운터를 둘지.

- **MVP 전제(2026-10-02, #5 A-12)**: 런타임 도구 생성 없음 → 각 에이전트의 도구 집합과 per-agent tools allowlist(OD-8 후보 ① 5.)는 run 시작 시 고정된 **정적 목록**이다. 로스터 결정은 "누가 어느 고정 도구를 쓰는가"로 단순해지고, 동적 등록은 NFR-6 확장 호환으로만 남긴다. *(2026-10-07: allowlist에 적을 수 있는 FR-10 도구의 이름 — `mcp__hilclaw__sim_run` 등 — 은 [ADR-0010](decisions/ADR-0010-od18-tool-exposure-form.md)이 정했다. 누가 어느 도구를 쓰는지와 allowlist 자체는 그 기록으로 정해지지 않았다.)*

## OD-24

**agent-memory → db 승격 트리거** — #4 §6 · #4 데이터 계층 코멘트.

- 불변식(확정): "agent-memory 전체를 삭제해도 FR-6·FR-7·NFR-2가 성립한다"(→ OD-18 CLAUDE.md 불변식 목록).
- 인접: OD-7(기법 통계 환류 — 승격된 신호의 소비처), OD-20(아카이브 스키마 — 정량 신호의 저장 형식). 세 항목을 함께 볼 것.
