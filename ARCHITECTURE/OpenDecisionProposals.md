# Open Decision 제안 상세 (Proposals)

[Requirements.md](Requirements.md)의 Open Decisions 등록부에 등재된 각 항목의 **구체 제안·근거 본문**을 같은 번호 절에 둔다. 등록부에는 한 줄 요약만 남겨 표가 읽히도록 유지한다.

- **정본 분담**: 항목의 **상태·논의 위치**는 등록부(Requirements.md)가 정본, **제안 본문**은 본 문서가 정본이다. 제안이 바뀌면 본 문서를, 상태가 바뀌면 등록부를 같은 커밋에서 갱신한다.
- 제안은 결정이 아니다. 확정은 오너가 #4/#5에서 내리거나 설계 수준 OD에 한해 [PROCESS/DRIVER.md](../PROCESS/DRIVER.md) §9의 경로(ADR + 리뷰어 Approve + 오너 통지)로 내리고, 등록부 상태가 `확정`으로 바뀐 뒤 본문(FR/NFR)에 반영된다.
- 출처 표기: **#4** = 아키텍처 결정 스레드, **#5** = 사용자 입력 대기 목록, **#7** = 외부 조사(상설; `§n` = S-1 조사 본문 절, `보충 §2(n)` = S-1 보충 코멘트), **#8** = 모순 트래커, **(Bn)** = [reviews/2026-09-03](reviews/2026-09-03-StandardScenarios-LiteratureReview.md) 보강 제안.

## OD-1

**Objective type 메뉴** — #5 A-4 대기.

- 제안: MVP는 "단일 목적 + 선택적 제약(메모리 상한)"만, 가중조합/Pareto는 후속. 후보 메뉴: latency 최소화 / throughput 최대화 / 동시 서빙 capacity 최대화 / 메모리 상한 내 latency 최소화(제약형).
- *확장 고려(B2)*: HW 이론 한계(speed-of-light/roofline) 대비 달성률을 target·정지 어휘에 포함할지. "이전 대비"가 아닌 "HW 한계 대비" 평가는 2025~26 커널 생성 시스템의 공통 요소(#7 S-2 사실 요약).
- README의 다목적 목표("속도 향상 및 동시 서빙 용량 증대")와의 관계는 A-4 확정 시 Scope 또는 README에 명시(#8 M15).

## OD-4

**hw_profile / op_signature 키 스키마** — #4 코멘트 · #7 §6. **P1 최소분 확정(2026-10-06, PROCESS/DRIVER.md §9)**: [ADR-0001](decisions/ADR-0001-od4-key-schema.md).

- **채택분(ADR-0001)**: 아래 제안의 정확 식별층(hw: 칩 + 리비전 + 펌웨어·드라이버·툴체인 버전, op: 전체 인자튜플 + dtype/layout)에 용어집의 호스트 환경을 더한 것 — hw 키는 accelerator + revision + toolchain(구성요소별 버전) + host, op 키는 kind + 전체 shape(M 포함) + dtype + layout — 과 "정확 일치 = 히트"(P1은 정확 일치만 조회). hw_source는 키가 아닌 필수 속성으로, revision은 키 필드로 정했다. 키의 정규형·디렉토리 이름 유도·`schema_version`은 ADR이 새로 정했다.
- **제안으로 남는 부분(미확정)**: 유사도 벡터층과 "최근접 = prior로만", 아래 *확장 고려(S10)*, op의 "정규화 IR 구조해시"(IR 부재 — OD-9), 첫 인스턴스의 layout 값(row-major는 통합자 가정 그대로).
- 제안: **2층 구조**. 정확 식별층(op: 정규화 IR 구조해시 + 전체 인자튜플 + dtype/layout; hw: 칩 + 리비전 + **펌웨어·드라이버·툴체인 버전**) + 유사도 벡터층(FLOPs, 이동 바이트, arithmetic intensity, working set ÷ SRAM …). 정확 일치 = 캐시 히트, 최근접 = **prior로만**. TVM/TenSet 선례.
- hw 식별층 필드 후보: **HW 출처(hw_source: 외부 타사 / 자사 개발 중)** 와 revision — 자사 개발 중 HW는 revision마다 성능 특성이 바뀌므로 이력 귀속 키가 필요(FR-14 ④, OD-26).
- *확장 고려(S10)*: 재현 시 노이즈 범위를 넘는 차이가 나면 환경 변화(드라이버/펌웨어/호스트)를 새 hw_profile 키 후보로 표시.
- **첫 구체 인스턴스(#5 B-4, 2026-10-02)**: hw = `cpu_standin`(오너 로컬 PC, Windows/WSL; 이후 LAN 머신) · op = Llama 3.2 1B 디코더 projection GEMM — gate/up(2048→8192), down(8192→2048), QKV(2048→3072), O(2048→2048), M∈{1, 32, 512}, fp32(layout은 B-4에 없음 — row-major는 통합자 가정); 2차 = 같은 모델의 KV cache 포함 SDPA(GQA 16/8, head_dim 64, causal). → 설계 함의(제안): op_signature는 (op 종류, M·N·K 또는 seq·head 구성, dtype, layout)을 담고 **M(토큰 수)이 instance 파라미터**임을 키 설계가 수용해야 한다.

## OD-5

**정확도-성능 trade-off 정책** — **확정(2026-10-01, #5 A-6)**: hard floor.

- 결정 내용: 정확도는 게이트. tolerance는 사용자 instance 파라미터(어휘는 B-7 후 확정). 실패 = repair/탈락, best·통계 미반영. sim·board 양쪽 동일 floor. FR-3 ④ 조기 종료는 승격 게이트 수준 재검증 후 인정. 정확도의 목적 축 승격은 A-4 다목적과 함께 후속.
- 근거(#7 §5 G1): 목적 축으로 두면 옵티마이저에 정확도를 팔 권한을 명시 부여하는 것. Sakana 정정 후 집계 speedup 3.13× → 1.49×; METR: KernelBench 최적화의 73.8%가 프록시 지표만 개선, 예산이 클수록 악화(10스텝 26.4% → 100스텝 57.8%).
- 귀결: 더 느슨한 tolerance에서 더 빠른 후보가 있으면 시스템은 보고만 하고 채택하지 않는다 — 채택은 사용자가 tolerance를 바꾼 새 instance로(FR-9에 반영).
- 잔여: tolerance 어휘(per-dtype rtol/atol, downstream 지표 임계 — MLPerf식 99%/99.9% 등, user-defined 검사)는 #5 B-7 답변 후 확정. per-kernel 검사와 downstream 지표 floor의 병행 여부도 그때 어휘와 함께 정한다.

## OD-6

**codegen spec 페이로드 + repair resume** — #4 §4 첫 항목 · #7. **P1 최소분 확정(2026-10-06, PROCESS/DRIVER.md §9)**: [ADR-0002](decisions/ADR-0002-od6-codegen-spec.md).

- **채택분(ADR-0002)**: 아래 제안 중 "resume = #4 §3b"(repair는 코더 재호출이며 라운드는 `coded` 체크포인트에서 재진입), **후보 식별**(run·라운드·후보·시도 번호, 라운드의 후보 수 N과 후보들의 관계 — 같은 기법의 변형 / 서로 다른 기법), 그리고 여러 이전 시도를 나란히 실을 수 있는 **구조**(`feedback.attempts` 배열, 시도별 실패 리포트·프로파일 자리). spec의 단위(코더 호출 1회 = spec 1건, 불변), repair 호출의 입력(실패 리포트를 실은 새 spec; 이전 코더 세션을 이어 쓰지 않음), 구획·필드 표, 두 키 레코드의 동봉 방식(전체 + 키 이름), `schema_version`, 첫 GEMM 페이로드 예시(출처 없는 값은 자리표시)는 ADR이 새로 정했다.
- **제안으로 남는 부분(미확정)**: 대조적 제시의 **선택 규칙**(top-k/bottom-k, k, 필수 여부, 순서), 아래 *확장 고려* 전부 — (B4) 프로파일 요약 구조는 `profile` 자리만, (S7) 금지 패턴·(B5) 문서 발췌와 문서 부재 정보·참고 코드 포인터(FR-15)는 `ext` 자리만 있고 내용은 정하지 않았다 — 와 coder-driver 계약의 출력 쪽(OD-23).
- **하위 질문(ADR-0001이 넘긴 것, 2026-10-06 등재)**: ① **연산 종류의 동작 계약**(피연산자·역할·호출 규약) — 확정: spec의 `task.contract`(언어, 진입점 prototype, 피연산자별 역할·dtype·shape)에 싣는다. 미결: 그 값(하네스 쪽 계약 — PLAN P1-3), 첫 GEMM의 prototype·피연산자 저장 순서. ② **후보별 빌드 설정**(컴파일러 플래그·스레드 수)의 기록 위치 — 확정: 오케스트레이터가 지정하는 설정은 spec의 `task.build`, 실제로 쓰인 설정은 spec 밖(빌드·측정 결과와 함께). 미결: `task.build`의 멤버 이름, 코더가 설정을 스스로 고를 수 있는지, 쓰인 설정을 담는 레코드(OD-23 출력 쪽·OD-8) — 위치는 확정: 시도별 `measure/…/build.json`과 그 설정을 쓴 단계의 기록([ADR-0004](decisions/ADR-0004-od8-data-plane-layout.md)), 필드는 미결. ③ 한 instance가 여러 M을 다룰 수 있는지 — 미결: spec 1건은 op_signature 하나(M 하나)만 싣고(ADR-0002), instance 쪽은 `instance.json` 스키마(OD-8)에서 정한다.
- resume 여부는 #4 §3b에서 "phase=coded 체크포인트 resume"으로 정리됨.
- 제안: spec을 coder-driver **입출력 계약의 부분집합**으로 흡수(OD-23 연동). 직전 라운드만이 아니라 **top-k/bottom-k 시도와 프로파일을 대조적으로** 실을 것(CUDA-L1 근거).
- MVP 수용 항목: **후보 식별**(S8 — 라운드·후보 id, N개 후보가 같은 기법의 변형인지 다른 기법인지).
- **첫 페이로드 예시(#5 B-4, 2026-10-02)**: Llama 3.2 1B projection GEMM(위 OD-4 인스턴스)의 커널 명세 + `cpu_standin` hw_profile + 직전 라운드 프로파일/에러 + 기법 지침. 참고 코드(nntrainer 커널, FR-15 참고 입력)는 spec에 포인터로 동봉할 수 있고(발췌 동봉은 B5 확장 고려), 코더의 직접 검색 허용 여부는 OD-12.
- *확장 고려*: (B4) 프로파일 요약의 구조(병목 유형·점유율·memory/compute bound 판정), (S7) 금지 패턴 목록, (B5) **HW Documentation 발췌·같은 카테고리 예시 커널의 검색증강 전달** — 코더의 직접 검색을 금지할지가 OD-12 미결이므로 "Orchestrator가 동봉"을 MVP 요구로 승격하지 않는다.
- 하위 질문(UC-0 대안 흐름, PR #10): 가용 HW 문서의 범위와 **문서 부재 정보**를 spec에 반영할지 — 코더가 없는 문서를 가정하지 않도록 "이 HW의 문서는 여기까지"를 spec이 말해 줄지.

## OD-7

**기법 통계 환류 경로** — #4 코멘트 · #7 §6.

- 제안: 빈도 카운트가 아니라 **contextual bandit**(OpenTuner AUC-Bandit: 최근 개선 빈도 곡선의 AUC + UCB). latency 모델 없이 1라운드부터 동작.
- **흡수: 카탈로그 진입 기준**(#7 보충 §2(4)) — 등재 자격 = (held-out correctness 통과) ∧ (실 board 측정) ∧ (격리 평가자 PASS). selector·coder의 주장만으로는 불가. **검증 없이 쌓으면 카탈로그가 부패한다**(Voyager ablation: 자가검증 제거 시 버그 코드가 스킬 라이브러리에 축적). ExpeL식 `cases/`(불변 사례) + `insights/`(가변 규칙, ADD/EDIT/UPVOTE/DOWNVOTE + `supported_by` 출처) 분리 검토.
- *확장 고려(B6)*: 저장 단위를 통계에 더해 "변환 전/후 코드 쌍 + 개선 이유 요약"으로 확장.
- N후보(S8, MVP)에서는 board 미승격 후보의 sim 결과도 통계 입력이 되므로 "sim만 평가됨 vs board 평가됨"을 구분해 집계(OD-20 단계별 분리 평가 필드).

## OD-8

**P1 디렉토리 레이아웃** — #4 §2 초안 · #5 A-1/A-2/B-4 확정. **P1 최소분(디렉토리 트리) 확정(2026-10-07, PROCESS/DRIVER.md §9)**: [ADR-0004](decisions/ADR-0004-od8-data-plane-layout.md) — 격리 수단(후보 ①/②)은 미확정 그대로다. **잔여 중 `artifacts.json`의 blob 레코드 확정(2026-10-07, 같은 경로)**: [ADR-0005](decisions/ADR-0005-od8-artifacts-record.md).

- **채택분(ADR-0004)**: 아래 "MVP 요구"의 후보 차원과, 후보 ① 1.의 **소유자별 분할을 경로의 성질로만** 채택했다 — 라운드 아래를 작성 역할(`decision/`·`coder/`·`measure/`·`eval/`)로 먼저 나누고 그 아래에 `candidates/<CC>/attempts/<AA>/`를 둔다(역할 우선: 한 역할의 한 라운드 파일이 접두 경로 하나를 공유하므로 후보 ①·② 어느 쪽에서도 쓰기 루트 1개가 성립한다). 역할은 에이전트가 아니며 누가 맡는지는 OD-23이다. 그 밖에 ADR이 새로 정한 것: run 직속 파일 4개(`STATE.json`·`instance.json`·`events.ndjson`·run당 1개의 `artifacts.json`), 라운드 번호(`0000` = bring-up, 최소 4자리)와 후보·시도 번호(`01`부터, 최소 2자리)의 표기, ADR-0002의 식별 튜플 → 경로 대응(spec = `…/coder/candidates/<CC>/attempts/<AA>/spec.json`), 시도 단위 산출물(`output/`, `build.json`, `sim.json`·`board.json`·`profile.json`, `eval.json`), `db/` 키 디렉토리의 전체 키 레코드 파일(`hw_profile.json`, `op_signature.json`), 데이터 plane에 파일로 두지 않는 것, `run_id`의 디렉토리 이름 제약(형식은 미정), 레이아웃 버전 1(run별로 `instance.json`에 기록).
- **채택분(ADR-0005, `artifacts.json`의 blob 레코드)**: C-3(#5 A-2)이 이름만 준 다섯 항목과 `gc_at`의 표기를 정했다 — 파일은 `schema_version`(1)과 `artifacts` 배열(추가 순서, 레코드는 한 줄씩)을 가진 객체 하나, 레코드는 `sha256`(64자리 소문자 16진수 — `hilclaw.cas`의 digest 그대로)·`size`(바이트)·`type`(ADR-0001의 *name* 형식만, 값 목록 없음)·`round`(ADR-0002의 `id.round`)·`retention_class`(`best`/`final`/`intermediate`/`failed`)가 필수이고 `gc_at`은 GC 뒤에만 있다(시각 표기는 미정). 레코드의 식별자는 `sha256`이며 한 파일에 한 번만 나온다(같은 내용을 다시 만들면 레코드를 더하지 않고 첫 생산의 `round`·`type`을 유지; 같은 해시가 여러 run의 파일에 있을 수 있다). 허용되는 변경은 `retention_class` 교체와 `gc_at` 추가뿐이고 레코드는 지우거나 옮기지 않는다. blob을 먼저 저장하고 레코드를 쓴다 — 레코드는 "기록 시점에 로컬 저장소에 있었다"만 말하며 현재 존재를 보장하지 않는다. class는 항상 호출자가 주며(기본값 없음) 누가·언제 정하고 바꾸는지는 정하지 않았다(OD-20·OD-29·OD-23). GC 도구·유예기간·`blob.push`/`blob.fetch`도 정하지 않았다(C-3 후속, #5 B-2).
- **제안으로 남는 부분(미확정)**: **격리 수단** — 후보 ①의 2.~5.(특수 케이스, 쓰기 루트 주입, 강제 백엔드, tools allowlist)와 그 이점·전제조건, 후보 ② 전체. 둘 중 어느 것도 선택되지 않았고 트리는 어느 쪽도 배제하지 않는다(컨테이너 가용성·#5 B-1 대기, OD-14와 같은 결정). scratch·TMPDIR·빌드 캐시의 위치도 여기에 속한다. `artifacts.json`(ADR-0005로 확정)을 뺀 각 파일의 필드·스키마(PLAN P1-8, OD-17·OD-20·OD-7·OD-11)와 `run_id`의 형식도 미정이다.
- **하위 질문(ADR-0004가 넘긴 것, 2026-10-07 등재, 미결)**: ① 분기·재개의 표현 — 트리에는 분기 레벨이 없고 라운드 번호는 run 안에서 한 번만 쓰인다. 분기·재개(FR-6, S3-3)가 새 run인지 같은 run의 뒤 번호 라운드(출발점은 ADR-0002의 `feedback.base`)인지, 출발점(run·라운드)을 어떻게 가리키는지는 미결이며 트리는 둘 다 허용한다(OD-20 계보와 함께). ② 키 디렉토리에 그 키를 쓴 run의 색인 파일을 둘지, 조회가 run들을 읽을지(S5-1; OD-20과 함께). ③ run의 후보가 아닌 baseline(벤더 라이브러리 커널 등)의 측정을 어디에 기록할지(OD-28). ④ 참조 자료 발췌 스냅샷(FR-14 ②)의 위치(OD-12). ⑤ 한 단계가 한 시도에 기록을 둘 이상 남길 때(반복 측정·재측정·board 재시도)의 파일 이름(OD-13·OD-10·OD-11).
- **하위 질문(ADR-0005가 넘긴 것, 2026-10-07 등재, 미결)**: ⑥ `type`의 어휘 — 형식(*name*)만 정해졌고 값 목록이 없어 두 도구가 같은 종류를 다른 이름으로 적을 수 있다. 어떤 바이너리가 blob이 되는지와 함께 정한다(OD-23). ⑦ 레코드가 후보·시도를 적을지 — 지금은 `round`만 있어 레코드 → 시도의 역방향 조회는 그 라운드의 파일에서 해시를 찾아야 한다. blob을 해시로 가리키는 파일들이 정해질 때 다시 본다(OD-23·OD-20; 시도에 속하지 않는 blob = OD-28). *(GC 설계에 속하는 질문 — `gc_at`의 시각 표기, GC 뒤 같은 내용이 다시 저장될 때의 레코드, 여러 run이 같은 해시를 다른 class로 기록했을 때의 처리 — 은 C-3 후속이며 등재된 OD가 없다.)*
- 전제: A-1(별도 repo `HIL-Claw-data`), A-2(CAS + `artifacts.json`) 확정분 반영. B-4(첫 대상 커널 + spec 예시)는 2026-10-02 확정(Llama 3.2 1B GEMM/SDPA, `cpu_standin`) — 사용자 입력은 모두 확보됨.

## OD-15

**sim→board 승격 기준** — #7 §6.

## OD-16

**측정·검증의 위조 불가능성(anti-reward-hacking)** — #7 §5 G1. **본 조사 최대 리스크.** **하네스 수용 기준 확정(2026-10-07, PROCESS/DRIVER.md §9)**: [ADR-0003](decisions/ADR-0003-od16-harness-calibration.md) — 방어책 채택 범위는 미확정 그대로다.

- **원칙(2026-07-31 개정): 은닉이 아니라 위조 불가능성.** 전부 읽혀도 성립하는 방어만 채택한다(Kerckhoffs). 유일한 예외는 **런타임 시드·입력 값이 파일로 존재하지 않을 것** — 알고리즘은 읽혀도 되고 값만 없으면 된다. → **읽기 제한은 채택하지 않으며 OD-8 후보 ①과 충돌하지 않는다.** 근거: 성능 최적화 시스템에서 정답을 알아도 **베끼면 speedup 1.0이라 이길 수 없고**, harness 은닉은 security-by-obscurity이며(루프홀은 소스를 읽어야만 발견되지 않는다 — 없애는 것이 진짜 방어), 문서·기존 커널 읽기는 저밀도 언어 대응(FR-14)과 콜드스타트(OD-22)에 오히려 필요하다.
- **MVP 최소분(FR-9에 반영됨)**: 코더에 노출되지 않은 입력(shape/seed)으로 코더가 수정할 수 없는 격리 하네스에서 재검증; 실패 결과는 best·통계 미반영; 조기 종료 전 재검증.
- **위협 A — 조작 계열**(출력 버퍼 절도 · harness/타이머 패치 · 점수 레코드 조작 · 감사 로그 조작): **코더와 평가를 별도 프로세스로 분리 + 쓰기 격리**로 소멸한다(OD-8 후보 ① / OD-14). Sakana 사건의 버퍼 절도는 reference와 후보가 같은 프로세스에서 버퍼를 공유했기 때문에 성립했다.
- **위협 B — 산출물 퇴화 계열**(생성 커널이 일을 하지 않음): 치팅이 코더의 정당한 산출물인 소스 안에 있으므로 **격리로는 잡히지 않고 측정 설계로 잡는다**. ⑴ 하드코딩 출력 → **매 trial 런타임 무작위 입력**(값 비파일화) ⑵ 계산 누락 → 오라클 강화(FP32/FP64 CPU 레퍼런스 · opschema 기반 퍼징 · per-(op,dtype) tolerance · 코너케이스 subnormal/zero/inf/NaN/catastrophic cancellation) ⑶ 벤더 라이브러리 디스패치 → **정적 검사**(규칙이 읽혀도 무방 — 우회하려면 위반해야 하고 위반은 탐지된다) + **프로파일러로 해당 커널의 실제 실행 확인** ⑷ 다른 큐/스레드로 회피 → 전체 디바이스 배리어 + 호스트 wall-clock 교차검증 + **roofline(speed-of-light) 상한** ⑸ **타이밍 반복 구간 캐싱**(정확도는 입력을 바꾸지만 성능 측정은 같은 입력을 N회 반복하는 것이 정상이라 열리는 틈) → 매 trial 새 버퍼 할당 · 캐시 플러시 · **1회차 이후 시간 급감 탐지** ⑹ **순서 의존성 테스트**(reference→candidate와 candidate→reference 결과가 다르면 실격).
- **`private_metrics` 재정의**: 은닉 지표가 아니라 **일반화 측정 지표** — 평가에는 쓰되 최적화 대상에는 넣지 않는다. 실배포에서는 대상 shape 분포를 코더에게 알리는 편이 맞다(벤치마크와 위협 모델이 다름).
- **방어가 여전히 필요한 이유**: 코더가 악의를 갖기 때문이 아니라 **탐색 루프가 가장 싼 경로를 고르기 때문**이다. 루프홀이 있으면 결국 선택되고, 그 결과는 board 시간 낭비 · **크로스런 통계 오염(FR-7)** · 잘못된 바이너리 승격이다.
- **흡수: 조기 종료 재검증**(#7 보충 §2(2), #8 M18) — FR-3 ④의 target 조기 달성은 해킹된 결과의 전형적 징후이므로 조기 종료 인정 전 승격 게이트 수준의 재검증을 강제(FR-9에 반영됨).
- **확장(S7, B1/B8)**: 정밀도 하향 검사, warm-up·stream sync·클록 고정 타이밍, 정적 검사·금지 패턴, LLM 검증자, 검증·프로파일 스크립트 보호, 금지 fallback 패턴, 코더 웹 검색 차단(OD-12). 실패 유형 태깅과 다음 라운드 spec의 금지 패턴 주입(OD-6 확장 고려).
- **하네스 자체의 수용 기준**(#7 S-2 N8): Kernel Contracts의 3-상태 캘리브레이션(위반 구현이 실제로 잡히는지 증명)을 하네스 완료 조건으로 채택 검토 — hacker-fixer 루프와 상보.
  - **채택분(ADR-0003, 2026-10-07)**: 3-상태 캘리브레이션을 검증 하네스의 수용 기준으로 채택한다. 대상은 하네스 모듈이고, 증명 단위는 하네스가 검증하는 **연산 종류**다. 세 상태 = 적합 / 실패 / "기능 테스트(미리 고정된 입력에서의 기본 검사, S7-1)는 통과하지만 계약(FR-9 최소 조항 — 알 수 없었던 입력에서도 tolerance 안)을 위반". P1 필수 위반 부류는 **위협 B ⑴(미리 알려진 입력에서만 맞는 출력)** 하나이고, 나머지 부류(위협 A, B ⑵~⑹, S7·B1·B8 확장)는 잡아 줄 방어가 채택되지 않았으므로 요구하지 않는다. "잡힌다" = correctness 판정이 실패인 것까지이며 원인 식별(실패 유형 태깅, S7-3)은 요구하지 않는다. 캘리브레이션 커널은 하네스 테스트의 손으로 쓴 fixture(코더 산출물·카탈로그 항목 아님)이고, 테스트는 패키지의 일반 테스트 스위트에 속하며 tolerance를 인자로 넘긴다(오라클·tolerance 값과 무관하게 성립). 통과가 증명하는 것은 "나열된 위반이 잡힌다"까지다.
  - **채택하지 않은 것**: 위 위협 A·B와 확장의 방어책 어느 것도 ADR-0003으로 채택되거나 기각되지 않았다. hacker-fixer 루프 실행 여부도 그대로 미결이다.

- **하위 질문(ADR-0003이 넘긴 것, 2026-10-07 등재, 미결)**: ① 검증 실행이 op_signature의 shape 밖의 shape도 뽑는지 — FR-9는 "shape/seed"라 하지만 spec은 op_signature의 shape을 코더에 노출한다(ADR-0002). 뽑는다면 "알려진 shape에서만 맞는 커널"이 필수 부류에 더해진다(하네스 설계, PLAN P1-3). ② 캘리브레이션을 연산 종류의 dtype·layout마다, 백엔드·실행 지점(sim/board)·커널 언어마다 반복하는지. ③ 측정 쪽(타이밍)에도 캘리브레이션을 둘지(OD-13과 함께). ④ run이 pin한 하네스 버전과 그 버전의 캘리브레이션 증거를 잇는 방법(OD-11).
- **확정분(2026-10-02, #5 A-12) — 하네스 단일 단위**: 채점 장치(입력 생성·f64 reference·tolerance 비교·타이밍·프로파일·eval/event 기록)는 도구 패키지 안의 **한 하위 모듈**(`harness/`)에 모여 있고, 코더 scratch에 포함되지 않으며, P1 버전 = 소스 commit 해시(OD-11).
- (통합자 해석) 위 확정은 OD-8 후보 ①/② 어느 쪽에서도 성립하며, 위협 A(조작 계열) 방어의 **전제 조건**이다 — 보호는 위치가 정해진 것에만 걸 수 있다. 3-상태 캘리브레이션(#7 S-2 N8)도 이 단위를 대상으로 하게 된다.

## OD-19

**예산 집행(enforcement) 정책** — #7 보충 §2(1), #8 M5.

- **C-7(#5 B-6) 반영 — 제안**: Claude Code를 Max 구독으로 쓰므로 희소 자원은 달러가 아닌 **플랜 사용 한도(rate limit)** 다. 한도 도달("rate limited")은 run 실패가 아니라 **일시정지 → 한도 회복 후 재개**(NFR-1·OD-17의 재개 경로 재사용) 조건으로 정의하고, 야간 무인 run(S2)은 이를 전제로 설계한다. 중첩 `claude -p` 코더가 같은 한도를 공유하므로 단일 원장은 토큰 수와 함께 한도 소진율을 추적한다.
