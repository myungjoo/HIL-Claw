## Decision

Whose a sentence is: **owner** where K1, K2, O1 to O4 or an owner's answer to an HQ is named; **cited** where another source is named; **this record's own** otherwise.

### 1. Scope

- **The runs** are those of [ADR-0076](ADR-0076-od8-instance-start-required-members.md) decision 1 whose hw_profile names `cpu_standin` — the first case (`gemm`, fp32, a C kernel built with clang) — carried out locally, on the machine of C-7 that runs the tool package.
- **The four**: the verification build and the verification process of an operation of `correctness.check` (cited: ADR-0056 decision 4; ADR-0017 decision 2), and the timing build and the timing process of an operation of `sim.run` or `board.run` (cited: ADR-0009 decision 2; ADR-0107 decision 3). "A build" and "a process" below mean one of these four.
- **Not in scope**: the coder call and its container (ADR-0049; Boundaries), the mock (it is given no setting and its default script "stands for no kernel language, no source, no build and no flag" — cited: ADR-0044 decision 3, as ADR-0060 decision 3 cites it), a real board (① (바)), and any other backend, toolchain or run.

### 2. (가) The properties, for a build and for a process

The means is a container of the machine's container runtime (**owner**, K1), with these properties, adapted from P1 to P4 of ADR-0049:

- **Q1 — everything inside (P1, taken).** The compiler and every process it starts, and the executable and every process it starts, run inside the container from their start to their end. **No build and no process of the four runs on the host** (decision 4). What stays on the host is the tool package's own work: the reader of ADR-0055, the copies of Q3, the judging, and the start, end and removal of the containers.
- **Q2 — one host path, the build directory (P2, taken with one change).** Exactly one directory of the host is given to the container, and it is writable: the build directory of the call (cited: ADR-0056 decision 4 — made by the operation for that one call, outside both checkouts). No other host path is given by the operation: no second mount, no checkout, no part of the tool package, no means to direct the container runtime (its socket or its program), no added privilege (E4: a privileged container "is not a securely sandboxed process"). Files the container runtime places inside of its own accord (Docker's documentation read here does not list them) are no path the operation gives; that none of them lets a process inside change the host is part of runtime acceptance item (xlviii). **The build directory stays writable for the process too**: it is the working directory of the verification and the timing process (cited: ADR-0056 decision 4), so what a process writes under a relative name lies there and is removed, as on the host; a read-only mount for the process was weighed and not taken, because a kernel that writes a temporary file would then fail in the container and not on the host, and the executable, the only thing there the process could change, is used by no later build or process. **The change against P2**: the network is part of the property here (Q5), where ADR-0049 L4 left it out for a coder call, which needs Anthropic.
- **Q3 — crossing by copy (P3, taken).** **In**, before the build and on the host: copies with their own bytes — never a link — of the kernel files the reader of ADR-0055 found at that call (R2: the regular files directly below `output/` whose names are admitted, so the compiled set and the kernel's own headers, R3 and R5) and of the harness program of the build (the verification program or the timing driver, cited: ADR-0017 decision 2; ADR-0009 decision 2), placed in the build directory. **The kernel's copies lie apart from everything else**: they are placed in a sub-directory of the build directory that holds nothing else, and the harness program's copy and the executable lie outside it, so that no admitted name of a kernel file (ADR-0055 decision 5, N1 and N2) can be the path of the harness program's copy or of anything the build makes — a kernel file named like the harness program (`verification_program.c` and `timing_driver.c` are admitted names; observation) is then a second file, never a replacement of it. The kernel's own headers are found as before, beside the kernel sources that include them. The names of the sub-directory and of the other entries are the code slice's. Nothing else of the attempt is copied (R6). The executable is written by the build into the build directory and is there for the process of the same call. **Out**: nothing crosses as a file. What a build or a process says reaches the operation as the exit status and the bytes of standard output and standard error of the program the operation started (decision 3) — the same channels as today. **Why copy and not a read-only mount of `output/` and of the harness**: one host path instead of three, so no path of either checkout is visible inside; what is built is the bytes copied at that call, not what lies below `output/` when the compiler opens each file; and on Docker Desktop, whose daemon runs in a Linux VM (D3 of ADR-0049), only the build directory's location then has to be reachable from that VM (this record's reading; not verified). The cost: the kernel files are read and written once more per build (one source and some headers; this record's estimate is kilobytes).
- **Q4 — removed afterwards (P4, taken).** Each container is removed when its build or its process has ended, and at once when it is ended at its time limit (decision 3). The build directory is removed by the operation as ADR-0056 decision 4 says (cited), and only **after the last container of the call has been removed**, so that nothing inside can still write to it; when that removal fails, ADR-0096 holds (cited). Anything else this record makes on the machine for a call is removed at the same time; the installed runtime and the images stay (**owner**, O3, "the installed runtime package and pulled images stay" — this record's reading extends O3 from the coder call to these containers, as K1's "as for the coder call (ADR-0049)" suggests).
- **Q5 — no network.** A build or a process reaches no network from inside: on Docker the container is started with the `none` network, inside which "only the loopback device is created" (E2). Reasons: no build or process of the four needs a network (the compiler reads the build directory; the harness programs read no network — cited: ADR-0009 decision 2 and ADR-0017 decision 2, "nothing beyond the C library" and POSIX); and a generated kernel that could reach the host's or the LAN's services (C-7 ⑤) or the internet could act there or send what it read, which ADR-0049 L4 had to leave open for the coder and need not here.
- **Q6 — the processes run as the user who runs the instance.** On a POSIX host the build and the process run inside with the numeric user and group id of the operation's process (E6: the default inside is root; `--user` sets it), so that what they create in the build directory belongs to the user who removes it (Q4; ADR-0049 L6 named that ownership as not verified on Linux). **They hold no capability and cannot gain a privilege**: every capability is dropped and new privileges are refused (E11), so that a set-user-ID program or a `sudo` the image may hold cannot make a process inside root, and no process inside can create in the build directory a file owned by another user or group (root among them), a set-user-ID or set-group-ID file of such an owner, or a device node — which a root process in a rootful Docker could, and which a host process of that user could not, so the container would otherwise open a way the host design did not have. A set-user-ID file that the user owns can be made inside as on the host (an owner may set that bit on its own file); it gives nothing the host design did not give. The image must allow this (decision 5).
- **Q7 — no resource bound.** No bound on processor, memory, processes or disk is set (E9: by default none is); the build directory can fill the disk it is on, as ADR-0049 L7 says of a scratch. Resource ceilings stay with the rest of OD-14; the memory ceiling of a candidate stays a measurement, not a bound (cited: ADR-0052).

**What these properties give, and what they do not.** For the runs of decision 1, a generated kernel, when it is built or run, can change through the file systems its container is given only the build directory of its own call, and reaches no network — **this record's expectation, not verified** (L1 of ADR-0049 applies with the same words; Consequences). It no longer shares a host with the harness's Python process as a host process does: whether a process in a container can reach the memory of a host process is a question of the container runtime and is not verified. **Not removed**: the kernel shares its process with the harness program (cited: ADR-0009 decision 10, "No protection against forged timing"; ADR-0017 decision 10), so threat A inside the process and threat B of OD-16 stay where they are; and L11 of ADR-0049 — the user who runs the instance controls a container runtime — holds for these containers too.

### 3. (다) One container per build and per process, and the time limits

- **One new container for each build and each process**: a call of `correctness.check` starts two (its verification build, then its verification process), a call of `sim.run` or `board.run` two (its timing build, then its timing run). No container serves two of them, and none outlives its build or process.
- **Three ways were weighed.**
  - **(a) One per build or process.** Each time limit of ADR-0117 bounds one build or one process (cited: decision 1, "A limit is the most time … one build or one process may take before it is ended"), and here bounds one container; removing it at the limit ends its main process (E5) and, as this record expects of a container runtime, every other process inside with it, not only the one started — which would close for these runs the code's limit "only the process it started is killed, not that process's children" (observation; not verified — runtime acceptance item (l), Consequences). A process a build leaves behind is expected to end with the build's container, so it does not run beside the process that follows (the same expectation). The cost: two container starts per call.
  - **(b) One per call, the build and the process started inside it one after the other.** One start per call; but a process left behind by the compiler would share the container with the measured process, the container would have to stay alive between two started programs, and the two time limits would bound two programs inside one container rather than its whole life.
  - **(c) One reused across calls.** It would be state between calls, against the ground of ADR-0056 decision 4 (a), built at each call: "No outcome depends on anything an earlier call left" (cited: ADR-0056 decision 4 (a), from ADR-0016 decision 2 (c)), and anything a kernel left inside would meet the next attempt's build. It would also outlive the work it was made for, against O3 (**owner**).
- **The choice is (a).** The two builds of an attempt run in two containers but of one image (decision 5), so they keep ADR-0107 decision 3's "one compiler, one list of flags, one list of trailing flags and one environment" (cited); a new container per build adds no difference between them.
- **How a build or a process is started and ended.** The operation starts one program on the host per build or process: **the container runtime's command-line program** (for Docker, `docker run`), which starts the container, waits for it, and passes on the program's standard output, standard error and exit status (E7). Reasons: the Python standard library holds no client of a container runtime, and a library would be a new external dependency (CLAUDE.md A-13); a command-line program fits the way `clang_build` and `local_run` already start one host program. **Which daemon the client reaches** is set by the client's own environment and configuration, not by this record (how Docker's client chooses it was not read here); the operation hands it nothing to choose another, and the build directory it mounts is a path of the machine that runs the operation, so a client that reached the daemon of another machine would build and run there, under this machine's `cpu_standin`. That this does not happen is a runtime acceptance item ((xlviii)); whether the start must also fix the daemon is ① (라). The operation names each container, so that it can end it, with a name used for that one build or process only and never again — not by another call, run or instance on the machine — so that a removal by name can reach no other container (for example a name with a random part that cannot be guessed; the form is the code slice's). **At the time limit** the operation ends the program it started, as the code does today, and then removes the container by its name, by force (E5); it does not rely on the ending of the program it started to end the container. If the program is ended before the container runtime has created the container, no container of that name may exist yet when the removal is tried, and one may still be created after it; what the operation does then is not decided here (with the leftovers of Boundaries; runtime acceptance item (l)). **When the build or the process ends by itself** the container is removed with it (on Docker, E4's `--rm`).
- **ADR-0117's limits cover the container's start.** Each limit is applied to the program the operation starts, from its start to its end, so the start of the container and its removal on a normal end lie inside the limit; the forced removal at the limit lies after it. That holds the condition of ADR-0117 decision 1 for the part this record decides — **no image pull and no install are part of a build or process** (decision 5) — and states its other part, that a container's start "adds seconds", as **not verified** (Consequences). If it adds more, ADR-0117 decision 1 says its decisions 3 and 4 are revisited (cited).
- **Two consequences of the program started being the client, stated, not decided further.**
  - **The exit status.** On Docker, 125, 126 and 127 can be the container runtime's own ("the error is with Docker daemon itself", the command "can't be invoked", "can't be found"), and every other value is the program's (E7). A compiler or a kernel can itself end with 125 to 127, so the status alone does not tell the two apart. **This changes how two rows of ADR-0060 decision 4 are observed**, where "What the operation observes decides the row" (cited): on the host a compiler that cannot be found or started (S6, `compiler_unavailable`) and an executable that cannot be started (S10, `executable_unstartable`) show as a start that fails, apart from any status; through the client both show as a status, 127 or 126 (E7), which read as ADR-0060 decision 4 reads a status would be S7 (`build_exit_status`) or a process that ended with a non-zero status — broken results, not tool failures. Reading 125 to 127 as S6 or S10 instead is not safe either: the kernel's process can end with those statuses and write the client's words (E7 shows one such line) to standard error itself, and would so turn its own broken result into a tool failure, a way the host design did not have. **Which way a code slice reads these statuses, and whether another means tells the container runtime's failure from the program's, is not decided here** (decision 7; Boundaries): it belongs to the answers of OD-18 ⑱ and ⑲ and to the defences of OD-16. This record states it as a limit and adds no answer or kind. What a call answers for a failure of the container runtime is not decided either (decision 7).
  - **The memory figure.** The child process the operation waits for is the client, not the timing process, so "the resource usage the operating system returns with the wait for the ended child process" (cited: ADR-0052 decision 4) is not the figure of the timing run. The harness code that takes the figure that way is on `main` (observation: T-0173; `hilclaw/harness/timing.py` hands `local_run`'s `max_rss` to `hilclaw/harness/memory_ceiling.py`, which applies the unit rule by the host's `sys.platform`); applied unchanged to a run in a container it would make the client's usage the figure, by a unit rule read from the host, which under Docker Desktop is not the container's system. A code slice does not apply it unchanged to a build or process of this record. How the figure is taken inside a container, and whether it is the figure ADR-0052 defines, is ① (마) (Boundaries). So condition (a) of ADR-0052 decision 7 — "the harness slice that takes the figure as decision 4 says" (cited), one of the conditions under which `memory_ceiling` is admitted — is met by that code for host runs only, and for the runs of decision 1 is read as **not met** until ① (마) is answered; the memory figure that the owner's answer to HQ-0025 counts among what the run tools return (Context) waits on ① (마) as well; the timing samples do not.
- **Standard error.** What the client writes of its own goes to the same standard error as the compiler's diagnostics (observation of the channel; the page of E7 shows one such line, and the full set was not read). Whether the compiler's log of [ADR-0078](ADR-0078-od18-correctness-check-compiler-log-file.md) must exclude it is not decided here; HQ-0026 is not crossed.

### 4. The frame of (라): Docker first, and no fallback to the host

- **Docker first.** The first implementation is Docker-based: ADR-0049 "Docker first" (cited) and O3 (**owner**: "If the means chosen is Docker-based, the record may take it without asking the owner again"), which this record reads as extending to these containers by K1's "as for the coder call (ADR-0049)"; E1 to E12 are Docker's, and nothing of Podman was read. Podman is admitted when Q1 to Q7 are shown for it, as ADR-0049 says of P1 to P4 (cited).
- **No build or process on the host, ever, for these runs.** Where no container runtime is available to the user who runs the instance, or the image is not there (decision 5), no build and no process of the four is started; nothing falls back to a host process. **The reading of K1 that grounds it**: "use an isolated environment: a container" names how these builds and runs are carried out, not a preference; a fallback would make the results of some runs come from unprotected host builds with the host's compiler and stand beside the others (FR-7, FR-18), as ADR-0049's Alternatives say of a coder fallback (cited). What a call then answers is not decided (decision 7); what asks the user to install a missing runtime, and when, is OD-8 ㉝ (가).
- **Not decided**: rootless Docker, Docker Desktop, and the runtime inside WSL beyond "Docker first" (Boundaries).

### 5. The image, as far as a code slice needs it

- **One image for the four.** The verification build, the verification process, the timing build and the timing process of every attempt of a run use one image. For the two builds this is ADR-0107 decision 3's "one compiler … one environment" (cited). For each process, it runs against the C library its build linked with, which is the image's; a process run in another image would run an executable against a C library and a loader it was not built with. **Not decided**: whether it is the image of the coder call (① (나); ADR-0049 L6).
- **What the image must hold, by function** (no product, distribution or version is named):
  - a clang compiler that the image's own environment finds under the name `clang` (#5 A-7 ②: "clang as the single toolchain"), able to compile and link the flags of ADR-0116 decision 3 (cited: `-std=gnu11 -O2 -ffp-contract=off`, trailing `-lm`) into an executable for the image's own platform;
  - a C library with its mathematics library and headers, and the POSIX.1-2008 interfaces the harness programs use (observation: both define `_POSIX_C_SOURCE 200809L` and include `<unistd.h>`; the timing driver also includes `<time.h>`), and the headers a kernel may include (cited: ADR-0008 decision 7 — the C standard library, `<omp.h>` and the SIMD intrinsics headers of the target; of these, `<omp.h>` is left to the next words); **OpenMP is neither required nor forbidden** (`<omp.h>` and its runtime: HQ-0034, owner-only, not decided);
  - a platform that runs natively on the machine's processor: an image run by emulation is not taken, since its timings would not be those of the processor `cpu_standin` stands for (this record's reading; K1 names qemu as no isolation means). The operation does not check it; it is a requirement on the image the user names, and whether the runtime checks it goes with ① (나). Docker Desktop's VM on macOS and Windows is not emulation of another processor; whether its timings are those of ADR-0009 is ① (마);
  - nothing that needs the network, a `claude` program, a user name of its own, a capability or a gained privilege: the processes run as a numeric user and group with no capability (Q6) and with the environment of the image (below);
  - no entrypoint that the start depends on: the start overrides the image's entrypoint (E12), so that the program started inside is the compiler or the executable itself and no program of the image runs before it or changes its environment.
- **The compiler is the image's `clang`.** This gives, for these runs, the source ADR-0060 decision 3 left open for the compiler — "of the compiler with the isolated environment of O4, whose design is OD-14 sub-question ①" (cited) — and it stays the backend's own: no tool function hands it over. Whether it must agree with the `toolchain` of the hw_profile is ADR-0060's sub-question ⑱ (가) (cited) and ① (마).
- **The environment of a build and a process is the image's.** The operation hands no variable of its own environment into the container; what is inside is what the image and the container runtime set (E8 names `HOME`, `HOSTNAME`, `PATH` for a Linux container). This is the value of "in the container the one OD-14 sub-question ① gives it" (cited: ADR-0116 decision 5), and it is one environment for the build and the process (cited: ADR-0107 decision 3). Which variables an image sets is the image's; this record names none. Its cost, stated as ADR-0116 decision 5 (a) states its own: no commit names the environment.
- **No concrete image is adopted.** This record names no base image, registry, Dockerfile or package; adopting one is a new external dependency of the runtime and needs the owner (CLAUDE.md A-13).
- **How the runtime is told which image: the user names it in one environment variable of the process that runs the operation.** The variable holds one image reference in the container runtime's own form (a name with a tag, or a name with a digest, E10). No file of either repository names the image and no value is committed. Its name and its check are the code slice's. **Four sources were weighed.**
  - **(a) A constant of the package source** (the pattern of ADR-0116 decision 2): a commit would name the image, but the constant would have to name a concrete image, which this record may not adopt.
  - **(b) A member of `hilclaw.config.json`.** That file is committed and shared by every checkout (observation: T-0012, under #5 A-1 detail 2), so a value committed there adopts a concrete image (CLAUDE.md A-13), and a value written there per machine leaves a tracked file changed in every checkout that uses it. Not taken; the file is not changed.
  - **(c) An environment variable**, the way `hilclaw/config.py` already lets a machine override the committed binding (observation: `HILCLAW_DATA_REPO_URL`, `HILCLAW_DATA_REPO_LOCAL_PATH`). It names a machine's image without a committed value and is no data-plane file. Its cost is that of ADR-0116 decision 5 (a) (cited): no commit names the image, and two processes started from different shells can name different images — two builds of one attempt with different images are then a case of ADR-0107 Limit 3 (cited). The environment of an MCP server process is fixed for its life (cited: ADR-0116 decision 5), so within one such process the image named does not change. **Two earlier records refused this source for their settings**: ADR-0116 decision 2 (b) — "A user or an agent can edit the file or the variable between calls; the runtime does not ask for anything, and nothing stops it" and "No commit names the values" (cited) — and ADR-0117 decision 2 (d), which "fails NFR-7 ③ and O4 item 2 as ADR-0116 decision 2 (b) found" (cited). **Why the outcome differs here**: for flags and time limits a constant of the package was open to those records and passed both tests; for the image it is not, because a committed value adopts a concrete image (CLAUDE.md A-13), and neither is a committed file (b). So the choice is between a source that fails NFR-7 ③ and no source at all. **The cost under NFR-7 ③, stated as those records state it**: no commit names the image, and so none names the compiler, its C library or the image's environment; which image made a result is not traced until its identity is recorded (① (나)). **Under K2**: a change of the variable installs and updates nothing — the runtime uses only an image already present (below) — and this record reads it as the user's own choice among what the user has installed, not an install or update by the runtime, as ADR-0116 decision 5 reads a change of the shell's environment (cited). If the owner reads such a change as one K2 asks the runtime to seek approval for, that is an objection to this decision. **An agent** could change it only by starting another process with another environment, which needs a shell: the main session of a first-case turn has no `Bash` (cited: ADR-0139 decision 4) and the coder-driver has none (**owner**, the answer to HQ-0040, https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6306222689: "The coder-driver has no Bash"); whether any other agent is given a shell is OD-23 and OD-18, and an agent that has one could start a command-line call naming another image — a limit this record states and does not close.
  - **(d) A member of `instance.json` or of another data-plane file**: a data-plane schema change (CLAUDE.md A-13); not taken.
- **The choice is (c).** Whether and where the identity of the image used (its digest, for example) is recorded with a run or a build is not decided (① (나); NFR-2; no data-plane member).
- **One reference is not always one image.** A tag can be moved to another image, or an image rebuilt under the same name, between two builds of one attempt without any change of the variable; the two builds then use two images and nothing detects it — a further case of ADR-0107 Limit 3 that its list does not name. A reference by digest names one image (E10). Whether the reference must be a digest goes with the recording of the image's identity (① (나)) and is not decided here.
- **The runtime never pulls, builds or updates an image as part of a build or process.** It uses an image that is already in the container runtime's image store; on Docker with the pull policy `never`, which does not pull "even if it's missing" and "produce[s] an error if the image does not exist in the image cache" (E3) — the default `missing` would pull a missing image (E3), which is an install without the user's approval. An install or an update of an image happens only after the user's approval (**owner**, K2: "only after approval does it install or update (for a container, its image)"); what part of the runtime asks, at which moment, and how it obtains the image then are not decided (OD-8 ㉝ (가); ① (나)).

### 6. The requirements the code slices inherit

- **Of the image** (decision 5): clang as `clang`, the C and mathematics libraries, POSIX.1-2008, native platform, runnable as a numeric user and group with no capability and no gained privilege, no entrypoint relied on.
- **Of the start of a container** (decisions 2, 3, 5), on Docker: the build directory as the one bind mount, writable, at a fixed path inside, which is the working directory (cited: ADR-0056 decision 4); the `none` network (E2); the pull policy `never` (E3); the numeric user and group of the operation's process (E6); every capability dropped and no new privileges (E11, `--cap-drop ALL`, `--security-opt no-new-privileges=true`); the image's entrypoint overridden, so that the program started is `clang` or the executable (E12); a name chosen by the operation for that one build or process only; removal when the program ends (E4); no `--privileged`, no added capability, no mount of the runtime's socket, no variable handed in; no resource bound. These name Docker's documented options for the properties; another option of the same documented effect serves as well.
- **Of the operation**: the copies of Q3 before the build, never a link, the kernel's copies in a sub-directory of their own apart from the harness program's copy and the executable; the forced removal at the limit (decision 3); the removal of the build directory only after the last container of the call is gone (Q4); no host process as a fallback (decision 4).

### 7. What a call answers where no container can be had

**Nothing is decided.** No container runtime available, no image named, no such image in the store, a container that cannot be started, a container that cannot be removed: each is a situation of the tools' contracts whose answer and kind are OD-18 sub-questions ⑱ and ⑲ (the check's situations under ADR-0056 decision 5 and the run tools' under ⑲ (나)), and this record adds none. HQ-0021 (T-0210) and HQ-0026 (T-0243) are not crossed. A code slice that meets one registers it under those sub-questions rather than choosing an answer.

### Walk-through (one call of `correctness.check` at a run of decision 1; no step names a module)

1. **Before.** The tool function hands the operation the output path (cited: ADR-0056 decision 3). The operation applies the reader on the host; it finds the compiled set `kernel.c` and a header `kernel.h`. It makes the build directory outside both checkouts, copies `kernel.c` and `kernel.h` into a sub-directory of it that holds nothing else, and copies the verification program beside that sub-directory, each with its own bytes.
2. **The build.** It starts the client: a new container of the image the environment variable of decision 5 names, not pulled, with the build directory as its only host path, no network, running as the user's numeric id with no capability, and with `clang` started in place of the image's entrypoint. Inside, `clang` of the image compiles the copies with the flags of ADR-0116 and writes the executable into the build directory. The compiler ends; the container is removed with it; the client returns the compiler's status and output.
3. **The process.** A second new container, with the same image and the same one host path, runs the executable in the build directory with the arguments of ADR-0017. The kernel tries to open a file of the source checkout: no such path is visible inside, and no host path but the build directory is writable (Q2, expectation). It tries to reach a LAN service: inside, only the loopback device exists (E2). The program ends; the container is removed; the report reaches the operation through the client's standard output.
4. **Judging and removal.** The operation judges as before. Both containers are gone, so it removes the build directory (ADR-0056 decision 4; ADR-0096 if that fails).
5. **A process that does not end.** At the limit of ADR-0117 the operation ends the client and force-removes the container by its name (E5), which is expected to end every process inside, children included (runtime acceptance item (l), Consequences); then it removes the build directory.
6. **No image.** The image named is not in the store: the runtime pulls nothing (E3), no build is started and nothing runs on the host. What the call answers is decision 7's open question.

## Alternatives considered

| Alternative | Why not |
|---|---|
| Builds and processes on the host, as the earlier records and the code have them | K1 (**owner**). |
| The host as a fallback where no container runtime or no image is there | Decision 4: some results would come from unprotected host builds with the host's compiler. |
| One container per call, or reused across calls | Decision 3 (b), (c). |
| Read-only mounts of `output/` and the harness instead of copies | Decision 2, Q3: three host paths, the checkouts visible, and what is built not fixed at one moment. |
| The network left reachable, as for a coder call | Nothing of the four needs it (Q5). |
| A memory, processor or disk bound | Values and the rest of OD-14 are not this record's; a memory bound would also change what ADR-0052 measures. |
| The image named in the package source, in `hilclaw.config.json`, or in `instance.json` | Decision 5 (a), (b), (d). |
| Docker's default pull policy | It pulls a missing image (E3): an install without approval (K2). |
| A library client of the container runtime instead of its command-line program | A new external dependency (A-13); decision 3. |
| Podman first | Nothing of it was read; ADR-0049 "Docker first" and O3. |

## Consequences

- **Slices for the planner** (code mode; no module or signature is decided here), each bound to nothing when it lands: (1) the start and end of one build or process container behind a seam that tests replace with a stub runtime (D16) — the properties of decision 6, the name, the forced removal at the limit, the client's status and streams handed back; (2) the copies of Q3 into the build directory, refusing links, beside the reader; (3) the reading of the environment variable that names the image (decision 5); (4) the operations of `cpu_standin` for `correctness.check`, `sim.run` and `board.run` built on (1) to (3) — they still wait on decision 7's open answers (OD-18 ⑱, ⑲; HQ-0021, HQ-0026) and their memory figure, which the owner's answer to HQ-0025 counts among their results, waits on ① (마): the landed harness code of the figure is not applied unchanged to a container run (decision 3). (1) to (3) need no container runtime to test.
- **Runtime acceptance items** (CLAUDE.md "개발 드라이버와 런타임의 구분"; not driver tasks — to be recorded by DRIVER §8, reason `runtime-acceptance`), on each kind of machine of C-7 with Docker, after the code slices land: **(xlviii)** that the daemon the client reaches is that of the machine that runs the operation, that the build directory, where the code slice places it, can be given to a container (on Docker Desktop, reached from its VM), that it is the only host path writable from inside a build or process container — no file the container runtime places inside of its own accord changing the host either — and that no path of either checkout is visible there (Q2, Q3); **(xlix)** that a process inside reaches no address of the host, of the LAN or of the internet (Q5); **(l)** that a process inside cannot create in the build directory a file owned by another user or group, a set-user-ID or set-group-ID file of such an owner, or a device node (Q6), that after a forced removal at a time limit no process of that build or process is left running and no container of it is created afterwards, and that the build directory and everything in it can then be removed by the user who runs the instance (Q4, Q6); **(li)** that the start and removal of a container add seconds and no more to a build or process, and that the pull policy `never` makes a missing image an error with no pull (decision 3, E3); **(lii)** that the client hands back the compiler's and the program's exit status and output bytes unchanged, and which statuses and what text the client adds of its own (decision 3). Whether the timings and the memory figure taken inside a container are those of ADR-0009 and ADR-0052 is ① (마), a design question, not one of these items.
- **A-13 reading.** Document mode. No dependency is added: Docker is a requirement of the runtime permitted by O1 and K1, and no image is adopted. No data-plane file, member, kind, value or version is added, and no file of either repository names an image; `hilclaw.config.json` is not changed. Nothing is required of the development machine (O4; D16).
- **Sentences of earlier records that are now less exact** (none edited; found by reading the records of Context and by grep on 2026-10-21 for "not sandboxed", "unprotected", "on the host" and "OD-14 sub-question ①"): ADR-0060 decision 2 ("until OD-14 sub-question ① designs it and a record replaces the host process, ADR-0056 decision 2 holds as written, and this record's list of situations is read from the host code" — this is that record for the first case; the list S1 to S10 of ADR-0056 decision 5 is not changed by it, but how S6 and S10 are observed is (decision 3), and the situations a container adds are registered under OD-18 ⑱ and ⑲, decision 7); ADR-0060 decision 4 (the rows S6 and S10 and the paragraph "What the functions on `main` report, against the rows": through a client, a start that fails shows as a status, decision 3); ADR-0117 decision 1 ("on the host, as the records still say, or in the container of O4" — now in the container; and "a container started per call" — now per build and per process) and ADR-0116 decision 1 ("on the host, as the records still say (…), or in the container of O4"); ADR-0116 Context ("`hilclaw.config.json` is a local file the source repository ignores (`.gitignore`)" — not exact: the file is committed) and the row (b) of its decision 2 ("The file is ignored by git"); [ADR-0021](ADR-0021-od18-correctness-check-split.md) decision 6 ("The kernel's process holds the seed during the check and is not sandboxed" — it is now in a container, and still holds the seed); ADR-0052 Alternatives (the row that quotes ADR-0009 decision 2's "as unprotected as `local_run` says") and decision 7, condition (a) (decision 3); the docstrings of `hilclaw/harness/timing.py` and `hilclaw/harness/memory_ceiling.py` (T-0173), which take the figure from the waited process (decision 3); ADR-0096 decision 4 ("whether the build directory is then a host directory, a mount or a path inside the container … their records say whether decision 2 holds there" — it is a host directory given to the container as its one mount, and ADR-0096 decision 2 holds for it, Q4); ADR-0009 decision 2 ("started by the Python side through `local_run.run`" — now through a container) and decision 10 ("Untimed cost is still spent: process start …" — a container start is among it); ADR-0017 decision 2 ("started through `local_run.run`") and decision 10 ("a kernel that reaches outside it (the memory of the Python process, for example) is not stopped by anything here"); ADR-0049 L3 ("Code a coder wrote can therefore do, when it is built or run, everything G1 keeps the coder process from doing — and possibly more (L11)" — for these runs, under Q1 to Q7, it can less), its Boundaries ("the isolation of the execution of a generated kernel") and the OD-14 parts of L7; ADR-0052 L3 (the descendants a wait accounts for) and L7 (the premise of a POSIX system with clang, now the image's); ADR-0056 decision 2 ("A survivor of a build or of a verification process can hold the build directory" — for these runs the forced removal ends it) and decision 4 ("Sources and the artefact are handed to the compiler as absolute paths" — paths inside the container, of the copies); ADR-0035 decision 2 ("the build and the run are local processes of the machine the package runs on" — they run in a container on that machine; which machine the values describe is ① (마)); ADR-0060 decision 3 ("The source and the values are open … of the compiler with the isolated environment of O4" — the compiler's source is now the image) and its settings table; ADR-0107 decision 3 ("its image, lifetime and runtime stay there" — the lifetime and the first runtime are now decided); ADR-0116 decision 5 ("in the container the one OD-14 sub-question ① gives it" — now given: the image's) and its Status ("a target-specific flag after OD-14 sub-question ①" — still open); ADR-0117 decision 1 (the condition "adds seconds and no install or image pull", now held in its second part and an acceptance item in its first); the docstrings of `hilclaw/clang_build.py` and `hilclaw/local_run.py` describe host processes, which stay true of those functions.
- **The cost, plainly.** Every build and every process needs a container runtime and an image the user has prepared and named; a call starts two containers; on macOS and Windows the kernel is built and run in Docker Desktop's Linux VM, not on the platform the user sees, and its timings are those of that VM (item 3 of the owner decisions of 2026-10-15 (the comment of K1 and K2), "inside the VM of Docker Desktop on macOS or Windows/WSL", already treats such timings as possibly imprecise); and the user who runs an instance must control a container runtime (ADR-0049 L11).

## Boundaries (not decided here)

- **① (나), the rest of the image**: whether it is the coder call's image (ADR-0049 L6); who makes it and how the runtime obtains or updates it after approval (with OD-8 ㉝ (가)); **whether and where its identity is recorded** with a build or a run (NFR-2; `build.json` — ADR-0004 decision 3; no data-plane member here).
- **① (라), the rest of the runtime**: daemon rights and rootless mode, whether the start fixes the daemon the client reaches (decision 3), Podman, and which runtime on macOS (Docker Desktop or another) and on Windows with WSL (inside the distribution or Docker Desktop) beyond "Docker first"; whether the coder container and the measuring container share an OS and architecture there (with OD-8 ㉝ (라)).
- **① (마)**: whether the timings and the maximum resident set taken inside a container are those of ADR-0009 and ADR-0052, how the memory figure is taken there (decision 3), and which machine the `cpu_standin` hw key values describe — the host or the container, `host.os` on macOS among them (ADR-0035, [ADR-0036](ADR-0036-od4-cpu-standin-host-os-macos-version.md); with OD-13 ⑪ and OD-4).
- **① (바)**: the isolation of a kernel run on a real board.
- **What each tool answers** where no container runtime, no image or no container can be had, and any kind for it (decision 7; OD-18 ⑱, ⑲; HQ-0021 and HQ-0026 not crossed); **how the client's statuses 125 to 127 are read** against the rows S6, S7 and S10 of ADR-0060 decision 4 and against a broken process, and whether another means tells the container runtime's failure from the program's (decision 3; OD-18 ⑱, ⑲; OD-16).
- **OpenMP** on `cpu_standin` and whether the image provides its runtime (HQ-0034, owner-only).
- **The settings of ADR-0116 the image may affect**: whether the flags of decision 3 hold for every image that meets decision 5, a target-specific flag, and a list of variables of the image's environment to remove or set (ADR-0116 decision 6).
- **The rest of OD-14**: resource ceilings (Q7), the kernel watchdog and the rest of the timeout hierarchy, health checks, reset escalation and the blacklist.
- **Leftovers**: how a later turn finds and removes a container or a build directory left by an operation's process that died (with OD-8 ㉝ (나), OD-17), and what the operation does with a container created after its client was ended at the limit (decision 3).
- **The coder call's container**, its sign-in and image (ADR-0049; HQ-0053); the parts of a turn that start containers for anything else.
