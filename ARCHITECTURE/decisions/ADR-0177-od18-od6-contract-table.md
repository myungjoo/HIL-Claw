- **Where "covered" is read today** — four places, each bound to `hilclaw.gemm_contract.covers`, the predicate of ADR-0041 decision 5 (observation): the instance start (`hilclaw/start_instance.py`, ADR-0115 decision 2 over `hilclaw.instance_start.prepare`), `spec.write` (`hilclaw/spec_tool.py` check 5, and its composition, which calls `gemm_contract.task_contract(m, k, n)`; ADR-0138 decision 2), `correctness.check` (`hilclaw/check_definition.py`, ADR-0070 decision 4) and `sim.run` / `board.run` (`hilclaw/run_definition.py`, ADR-0167 decision 4).

ADR-0041 decision 5 reads "covered" for the contract of ADR-0008 and says "Another kind, dtype, layout or language has another contract, defined by its own record" (cited, from ADR-0008 decision 1).

A run that a tool does not cover is stopped at the step that calls it (cited: ADR-0142 decision 1).
- **The catalog.** An entry's `## Applies to` is exactly the four lines `kind: gemm`, `dtype: fp32`, `layout: row_major`, `language: c` (observation: `hilclaw.catalog.APPLIES_TO`), and an entry may be given only to a spec of its kind, dtype, layout and language (cited: ADR-0150 decision 4).
- **The model executor** keeps its own tables of kinds and dtypes for its binding (observation: `hilclaw/model_binding.py`, ADR-0157); it is not a place that admits a run and is not changed here.

## Decision

### 1. (a) One table of the contracts, in `hilclaw/contract_table.py`

- **The one place in the package that lists the contracts a run may be about is the mapping `TABLE` of the module `hilclaw.contract_table`, keyed by (`kind`, `dtype`, `layout`, `language`).** Its seven entries, in this order:

| Key | Contract module | Record | `checked` after this slice | `timed` after this slice |
|---|---|---|---|---|
| `gemm`, `fp32`, `row_major`, `c` | `gemm_contract` | ADR-0008 | yes | yes |
| `gemm`, `bf16`, `row_major`, `c` | `gemm_bf16_contract` | ADR-0156 | no | no |
| `rmsnorm`, `bf16`, `row_major`, `c` | `rmsnorm_bf16_contract` | ADR-0158 | no | no |
| `elementwise_add`, `bf16`, `row_major`, `c` | `elementwise_add_bf16_contract` | ADR-0159 | no | no |
| `swiglu`, `bf16`, `row_major`, `c` | `swiglu_bf16_contract` | ADR-0160 | no | no |
| `rope`, `bf16`, `row_major`, `c` | `rope_bf16_contract` | ADR-0161 | no | no |
| `sdpa_kv_cache`, `bf16`, `row_major`, `c` | `sdpa_kv_cache_bf16_contract` | ADR-0162 | no | no |

- **What an entry gives.** The contract module itself, so that no constant of a contract is copied (the key is read from the module's `KIND`, `DTYPE`, `LAYOUT` and `LANGUAGE`), and two flags: `checked` — `correctness.check` judges a run of the contract; `timed` — `sim.run` and `board.run` time a kernel of it. Through the module it gives:
  - **"covered", read per contract**: the module's `covers`, the predicate of ADR-0041 decision 5 read with the contract's own binding and shape rules (ADR-0156 to ADR-0162 each give theirs: every dimension at least 1, `d` even for `rope`, `l` ≥ `m` and `h` a multiple of `h_kv` for `sdpa_kv_cache`). **A record is covered by the table when some entry's `covers` answers `True`; a record that matches no entry, or matches one whose `covers` refuses it, is not covered.** A record the key rules refuse (ADR-0001) is refused as before, by `hilclaw.keys.InvalidRecordError`.
  - **The `task.contract` of a stated record's shape**: the module's `task_contract` called with the record's `shape` members in the order of that function's parameters (`m`, `k`, `n`; `m`, `n`; `m`, `h`, `d`; `m`, `l`, `h`, `h_kv`, `d`).
- **At most one entry per `kind`, `dtype` and `layout`.** A stated record never names the kernel language (cited: ADR-0041 decision 5; ADR-0031 decision 2), so the table can tell two entries apart only by what the record shows. A second language for the same three would need a record saying how a run states it (OD-6 sub-question ④, OD-18 sub-question ⑩, the language part); the key keeps `language` so that such a record has a place.
- **The predicates bound to the places** are functions of the module, each exactly a `bool`: `covers` (any entry), `check_covers` (a `checked` entry), `run_covers` (a `timed` entry) and `start_covers` (an entry that is both). A later slice changes a flag of the table, not a binding of a place.

### 2. (b) Which contracts each place admits, after this slice and after each later slice

- **The rule for the instance start.** It admits a contract only when every tool round 0 calls admits it: `spec.write`, `correctness.check` (both points) and `board.run` (cited: ADR-0142 decisions 3 to 5). So `start_covers` asks the entries that are both `checked` and `timed`. Reason: a start that admitted a contract `correctness.check` or `board.run` refuses would start a run whose round 0 stops at that step with `op_signature_not_covered` and never yields a baseline (ADR-0119 decision 4) — a run that can only fail. `sim.run` is not called in round 0, but a later round of these runs may call it (ADR-0142 decision 4: "a record that gives a round ≥ 1 a sim measurement adds it"), and the `timed` flag covers both run tools at once, so the rule needs no third flag.
- **The rule for `spec.write`.** It admits every contract in the table, from this slice on. Reason: composing a spec needs only the contract's `task.contract` (cited: ADR-0002 decision 6 (a), the spec "carries the contract and does not define it"), which every entry gives; nothing in a spec depends on a judge or a timing run. Admitting more than the start does is harmless: through the start no run of a bf16 contract exists until the start admits it, and a `spec.write` that is ready lets the later slices land without touching it. The checks of ADR-0138 decision 3 and ADR-0151 decision 3 stay, in their order; only the predicate of check 5 and the source of `task.contract` change.
- **The rules for `correctness.check` and the run tools**: each admits what its flag says; a flag becomes `yes` in the slice that makes the tool serve the contract on both backends of its table (the mock and `cpu_standin`, ADR-0070 decision 3, ADR-0167 decision 3).

| Place | Predicate | After slice 1 (this record) | After slice 2 | After slice 3 | After slice 4 |
|---|---|---|---|---|---|
| `spec.write` | `covers` | all seven | all seven | all seven | all seven |
| `correctness.check` | `check_covers` | fp32 `gemm` | + bf16 `gemm`, `rmsnorm`, `elementwise_add`, `swiglu`, `sdpa_kv_cache` | + `rope` | same |
| `sim.run`, `board.run` | `run_covers` | fp32 `gemm` | fp32 `gemm` | fp32 `gemm` | + the bf16 contracts the timing record covers |
| instance start | `start_covers` | fp32 `gemm` | fp32 `gemm` | fp32 `gemm` | the contracts both checked and timed |

- **What follows for this slice**: every answer the instance start, `correctness.check`, `sim.run` and `board.run` give is the same as before for every record — a valid bf16 record is refused as not covered (`OutOfScopeError` at the start; `op_signature_not_covered` at the tools) exactly as it was refused by `gemm_contract.covers`.

### 3. (c) What `correctness.check` takes and returns for a contract other than fp32 `gemm` (what it takes decided here, built in slices 2 and 3; the result as the owner answered, HQ-0077)

- **Dimensions**: all `shape` members of the stated record, those of its kind (ADR-0001 decision 2 as the contract records extend it). ADR-0041 decision 2 is read per kind: the source stays the `op_signature` of the run's `instance.json` (choice (b) there), and "a check uses the three shape members" becomes "a check uses the shape members of its kind". For fp32 `gemm` nothing changes.
- **Covered**: `check_covers` (decision 1), in the place ADR-0041 decision 5 gives the predicate, with the same tool failure `op_signature_not_covered`.
- **Seed, draws and tolerance**: through the same path as for the first case — the seed from the source of the default registry (ADR-0070 decision 4; ADR-0048), `draws` and `tolerance` (`rtol`, `atol`) from `instance.json` (ADR-0041; ADR-0020). The tolerance is an instance parameter for every kind with no default (**owner**, HQ-0066 (2)); the path chooses no value, and the values stay with OD-16 sub-question ⑤ and the user (Boundaries).
- **The judge**: the Python side of the kind's verification run, never a new one — bf16 `gemm`, `rmsnorm`, `elementwise_add` and `swiglu`: ADR-0163 (`hilclaw.harness.bf16_verification`, with the kind and the dimensions); `rope`: ADR-0164 (`hilclaw.harness.bf16_rope_verification`); `sdpa_kv_cache`: ADR-0165 (`hilclaw.harness.bf16_sdpa_kv_cache_verification`). The verdict classes (completed, broken, pass, fail) and the element-wise predicate are those records'.
- **The `rope` start position.** ADR-0164 decision 4 makes the start position P "a parameter of the run, given by the caller with no default"; the stated record does not hold it, and "whether an m = 1 check runs both T = 1 rows" is OD-16 sub-question ⑤ (cited: ADR-0164 Boundaries). **A check of `rope` therefore waits on the record that gives P its source** — slice 3 —, and slice 2 leaves `rope` not `checked`. No P is chosen here.
- **What the operations are handed.** Beside the request, the hw_profile and the output path (ADR-0043 decision 2, unchanged): the seed, the number of draws, the table key of the covering entry (its `kind` and `dtype` suffice, decision 1) and the dimensions in the order of the contract's `task_contract` parameters, which is the order of the kind's verification command line (ADR-0163 decision 3; ADR-0164 decision 7; ADR-0165 decision 3). The Python form (a widened `CheckParameters` or a second type) is the slice's, **provided the operations keep receiving `m`, `k`, `n` for fp32 `gemm` as today**.
  - **`cpu_standin`** builds the kind's verification program (one per kind, ADR-0163 decision 2) with the attempt's kernel and runs it as ADR-0163 to ADR-0165 say. **Build settings**: the fixed set of ADR-0116 decision 2 (flags `-std=gnu11 -O2 -ffp-contract=off`, trailing flags `-lm`), read here as holding for the verification build of the bf16 kinds at `cpu_standin` as well — no flag names a kind, `-ffp-contract=off` keeps the rounding steps the contracts fix, and `-lm` is the trailing flag ADR-0160 decision 9 relies on for `expf`. The runtime acceptance item of that set (RA-0008, HQ-0033) covers these builds unchanged. OpenMP stays deferred (HQ-0034).
  - **The mock** is handed the same values. Its default script for a bf16 entry stands for a conforming kernel of that contract: it writes the report of ADR-0163 decision 8 (ADR-0164 decision 10, ADR-0165 decision 8 for their kinds) from the harness's own arrays modules, so that the judge passes it under any tolerance the calibration admits; a test script can stand for any other kernel (cited: ADR-0038 decision 6, "Which kind, dtype or kernel a script of the mock stands for is the script's").
- **The result: a data-plane schema change, decided by the owner (HQ-0077).** No member list of ADR-0042 fits a check of another kind: its `shape` is "an object with exactly the three members `m`, `k` and `n`" (cited: ADR-0042 decision 5), which no kind but `gemm` has, and its `counts` entries hold `failed` and `non_finite` only (cited: ADR-0042 decision 4), while an SDPA pass also needs "no element of either allocation differs" (cited: ADR-0165 decision 8). Changing that closed list (ADR-0042 decision 7) is "read as ADR-0060 read it", a data-plane schema change put to the owner (cited: ADR-0063 A-13 reading; ADR-0060; HQ-0020), and ADR-0100 decisions 3 and 4 make any change of a result definition take new `step` values (cited). The question went to the owner as HQ-0077.
  - **Owner** (chat, 2026-10-28, HQ-0077), as recorded in the `decision` of HQ-0077 in `PROCESS/STATE.json`: "(a) - 오너(채팅, 2026-10-28): bf16 kind의 검사는 새 `step` 값 둘(sim·board 지점)을 쓰고, 그 결과 목록은 ADR-0042의 목록에서 `shape`를 기록된 op_signature의 그 kind의 shape 멤버 전부로, SDPA의 `counts` 항목에 `cache_differs`를 더한 것으로 한다. fp32 `gemm`의 기존 값·결과는 그대로." — a check of a bf16 kind uses two new `step` values, one for the sim point and one for the board point (ADR-0100 decision 3); its result list is ADR-0042's list (as the records that amend it leave it) with `shape` holding all shape members of that kind in the stated `op_signature`, and with each `counts` entry of an `sdpa_kv_cache` check gaining a member `cache_differs`; fp32 `gemm` keeps `correctness_check_sim` and `correctness_check_board` and its result list unchanged.
  - **Read here** (this record's own, within that answer): `shape` has the member names and values of the stated record's `shape` for its kind (ADR-0001 decision 2 as the contract records extend it), each an integer of at least 1, so the two can be compared as ADR-0042 decision 5 has it for `gemm`; `cache_differs` is a JSON integer of at least 0, the number of cache elements over both allocations that differ in that draw — the count ADR-0165 decision 8 has the Python side return (cited); `counts` entries of the other five bf16 kinds keep exactly `failed` and `non_finite`. Every other member, presence rule and meaning is ADR-0042's, the bound "`failed` ≤ m·n" read as "≤ the number of output elements of the kind".
  - **The two values** (this record's own, DRIVER §9; ADR-0100 decision 3 fixes no spelling, only "a *name* of ADR-0001 not used before"): `correctness_check_bf16_sim` for the sim point and `correctness_check_bf16_board` for the board point, shared by the six bf16 kinds, as one list serves both values of ADR-0040 (ADR-0100 decision 3, second bullet). A search of the repository on 2026-10-28 found neither value used, as ADR-0040 and ADR-0062 checked theirs. A third value for a later dtype (fp16, HQ-0065 (1)) is that dtype's record's.
  - **Which value a call takes, and where in the order of a call** (this record's own, DRIVER §9). The `step` is part of the identity looked up in ③ (cited: ADR-0040 decision 7), and the op_signature is taken only in ④ (cited: ADR-0041 decisions 3 and 8), so the covering entry is not known when the value is needed. The value therefore follows from `point` and from the read of ⓢ: when the file read whole in ⓢ states an `op_signature` whose record's `dtype` is `bf16`, the call takes the bf16 value of its point; in every other case — no op_signature stated, or any other `dtype` — the value of ADR-0040 decision 3 that `point` gives, so every call of such a file is answered as today. ④ is unchanged otherwise: it reads the file again (ADR-0030 decision 4), takes the dimensions from that read (ADR-0041 decision 3), and answers `op_signature_not_stated` or `op_signature_not_covered` as ADR-0041 decision 8 orders them; **a record covered in ④ whose `dtype` is not the one the `step` was taken for** — the file changed between ⓢ and ④ — **is answered `op_signature_not_covered`**, with no line, nothing consumed and no seed drawn, so that a line under a bf16 value always holds a bf16 result and a line under an existing value an fp32 one. A bf16 record that `check_covers` refuses (the `rope` entry before slice 3; a shape outside a contract's set) is answered `op_signature_not_covered` in ④ under the bf16 value, which writes no line either. A repeated call whose file has changed its `dtype` meanwhile looks up another identity — the case ADR-0100 decision 5 states for any change of value.
  - **What a result does not say.** As under ADR-0042 decision 5, a result holds no `kind`, `dtype` or `layout`: the `step` says bf16 and `shape` says the dimensions, but three kinds share the shape members `m` and `n` (`rmsnorm`, `elementwise_add`, `swiglu`). A reader takes the kind from the stated `op_signature` of the run's `instance.json`, the source of the dimensions (ADR-0041 decision 2); a file changed between two checks of one run can make that reading wrong, as it can for the shape of a stored `gemm` pass (ADR-0041 decision 9). Adding a member for it is outside HQ-0077's answer and is not done here (Boundaries).
  - **Pass and fail of an `sdpa_kv_cache` check.** "A completed run passes iff, in every draw, every element of `out` meets the predicate … and no element of either allocation differs" (cited: ADR-0165 decision 8). So in such a result that reports pass every `failed` and every `cache_differs` is 0, and in one that reports fail at least one `failed` or one `cache_differs` is 1 or more — not, as ADR-0042 decision 4 derives for `gemm`, at least one `failed`. The outcome of such a check is judged over both counts.
  - Slices 2 and 3 build it; slice 1 does not.

- **The binding of the model executor from an instance's kernels** or from a key's best (**OD-20**, **OD-7**); the executor keeps its own tables (Context). Whether those tables are later read from the contract table is the slice's of that binding.
- **The orchestration text**: a search of `orchestration/` and `.claude/agents/` for `gemm` and `fp32` on 2026-10-26 found no prompt that names `gemm` or `fp32`; nothing is named here.

### 5. (e) The later code slices, in landing order (for the planner)

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 1 | Keep a predicate per place, each naming its contract modules | Four lists to keep in step; the D21 pins already show four places bound to one module. One table makes "which contracts exist" one fact. |
| 1 | Copy each contract's key, shape members and prototype into the table | A second statement of each contract record; a change of a contract module would not reach it. |
| 1 | Key the table by (`kind`, `dtype`, `layout`) only | A later contract in another language for the same three has no place, and ADR-0008 decision 1 binds a contract to a language. The key keeps it; the lookup by record uses the three the record shows. |
| 1 | Read the shape parameters' order from a table of the module | The order is already the `task_contract` signature's; a second copy could disagree. |
| 2 | Let the instance start admit all seven now | Its round 0 would stop at `correctness.check` with `op_signature_not_covered` (ADR-0142 decision 1): a run that can only fail. |
| 2 | Let `spec.write` admit only what the start admits | It would have to be touched again in slices 2 to 4 for no gain; composing a spec needs only the contract. |
| 2 | Admit a contract at the start once it is `checked`, before a timing run exists | Round 0 calls `board.run` (ADR-0142 decision 4); the run would stop there. |
| 3 | Decide the result's `shape` per kind and an SDPA cache count here, reading it as no schema change | It changes the closed list of ADR-0042; ADR-0063's A-13 reading and ADR-0100 put such a change to the owner, who answered HQ-0077 with (a). |
| 3 | Widen ADR-0042's list under the two existing `step` values (HQ-0077 (b)), or fold the cache differences into `failed` (HQ-0077 (c)) | Not the owner's answer (HQ-0077: (a)). |
| 3 | One pair of new `step` values per bf16 kind | The owner's answer gives two values (HQ-0077); one list serves the six kinds, as one serves both points of ADR-0040. |
| 3 | Choose a `rope` start position now (for example P = 0) | It is a value of the check's inputs that ADR-0164 leaves to the caller and OD-16 ⑤; choosing it here would invent it. |
| 3 | A new judge in the tool function for bf16 kinds | The harness records already define each judge; a second one could disagree. |
