## Context

- ADR-0004 decision 9: "The version is recorded **per run, in `instance.json`**: a finished run is not rewritten into a newer layout, because its history is its audit record (NFR-2), so runs of different versions can stand side by side. The path `runs/<run_id>/instance.json` is the same in every layout version: a reader finds the version there before it uses any other path of the run."
- ADR-0024 fixed how the file states the version — "A reader of this record has the layout version of a run only when the file of that run is valid and its `schema_version` is `1`", and "Nothing stands in for a stamp that cannot be had" (decision 4) — and left the order open: "This record changes no order of any call and decides nothing for a tool. Whether the sentence of ADR-0004 binds the order in which a reader uses the files of a run is not decided (sub-question ㉒, first part)" (decision 5). ADR-0018 decision 4 had left the same read open: "Whether a call reads the file for another member, such as the layout version stamp (ADR-0004 decision 9, OD-11), is the record of that member."
- **What opens a file below `runs/<run_id>/` on `main`** (established from the calls of the file system in `hilclaw/` on 2026-10-09):
  - *The frame of a tool call.* The lookup of a journaled call reads `STATE.json` and then `events.ndjson` (`hilclaw/journaled_step.py`), and the call appends its two step lines to that log. The selection of a journaled HW tool asks a reader that is a parameter of the builder for the hw_profile of the run (`hilclaw/hw_tool.py`); `hilclaw.instance.hw_profile_of`, which reads `instance.json`, has its call form. A journaled tool that selects no backend (`hilclaw.journaled_tool.tool_function`) reads `instance.json` at no moment. No tool is registered (`hilclaw.tools.default_registry` is empty).
  - *Functions of the package that read or write files of a run and are bound to no caller*: `hilclaw.instance` (`read` and the six readers of one member, `layout_version_of` among them), `hilclaw.run_journal` (`read_state` reads `STATE.json`; `current` and `step_state` read it and then the log), `hilclaw.events`, `hilclaw.artifacts`, and the three writers `hilclaw.run_state_file.replace`, `hilclaw.instance_file.write` and `hilclaw.spec_file.write`. None of the three writers reads another file of the run; nothing calls `layout_version_of`; `hilclaw.layout.LAYOUT_VERSION` is compared with nothing.
  - `hilclaw/layout.py` builds every path by formatting and opens nothing.
- **What a call does today** (run on a temporary data root on 2026-10-09; the table of the Walk-through). A journaled HW tool reads `instance.json` in ④, for an identity with no line only. A journaled tool that selects no backend appends its start line, runs its step and appends its end line whatever the state of `instance.json`, a missing file included. An ended or an open identity is answered from the log by both, whatever the state of the file.
- Fixed and not re-decided: ADR-0004 decisions 1, 9 and 10; ADR-0024 as a whole; "a version 1 reader reports an unsupported version and interprets nothing (OD-11)" and what a missing file means (ADR-0018 decision 2); the moments ① to ⑦ and the reasons for the place of ④ (ADR-0016 decision 2); the four kinds and the sentence each carries (ADR-0019 decision 2); that nothing is kept between calls (ADR-0010 decision 7); that exactly one layout version exists; that the `schema_version` of `STATE.json`, of a log line and of `artifacts.json` is independent of the layout version (ADR-0012 decision 2, ADR-0006 decision 8, ADR-0005 decision 9).

## Decision

A statement is **cited** when a record is named with it. Every other statement is **this record's own** choice or reading — among them that the sentence of ADR-0004 is made a rule for the calls of decision 1 and for no other user, what "uses a path" means, the moment ⓢ, that the four kinds are answered there, that ⓢ and ④ are two reads, that the stamp is compared with nothing, and the list of limits.

### 1. Scope and the readers this record speaks of

- This record answers one question: whether the sentence of ADR-0004 decision 9 binds the order of **a call of a tool whose tool function carries out the lookup of a journaled tool or the selection of a HW tool about a run, or both** — the calls ADR-0019 decision 1 is about — and how such a call meets it. Below, "a call" is such a call.
- **It speaks for no other user of a path of a run**: not for the functions of the package as such, which are handed a `run_id` by a caller this record does not know; not for the step of a tool or for a tool that carries out neither the lookup nor the selection; not for what a person or a script opens by other means; and **not for whatever writes the first files of a run** — the stamp cannot be read before `instance.json` is written, and which of `instance.json` and the first `STATE.json` is written first, by what, is not decided (OD-8 sub-questions ⑩ and ⑰). Whether the sentence is a rule for any of them is not said: this record neither binds them nor says that they are free (sub-question ㉗).
- It defines no tool, adds no kind and changes no member or validity rule of any file.

### 2. What "uses a path" means

- **Building a path is not using it.** A path built by formatting reads nothing and cannot be ordered against a read (`hilclaw/layout.py`).
- **To use a path of a run is to open a file or a directory at it — to read, write, create or list it.** A read and a write are both a use. This is this record's reading of ADR-0004's words: that record names "a reader", and a call that appends to the log of a run relies on where that log is as much as a call that reads it.
- "Any other path of the run" is every path below `runs/<run_id>/` other than `instance.json` itself.

### 3. For a call the sentence is a rule, met at one new moment

- **For a call, this record takes the sentence of ADR-0004 decision 9 as a rule and not as a description of what the fixed path makes possible.** ADR-0024 decision 5 left both readings open. ADR-0004 fixes "paths and file names" (its decision 1) and calls the tree "a naming convention" (its decision 10); however its sentence is read for other users of a path, it is this record that lays the rule on a call, and it lays it on nothing else (decision 1).
- **A call has the stamp of the run its request names before it uses any other path of that run.** "Uses" is that of decision 2, applied to a call only. The call gains one moment, written **ⓢ** here, **after ② and before ③**; for a call of a HW tool that is not journaled, after ② and before ④. In ⓢ the tool function reads `runs/<run_id>/instance.json` of the data root of the call, as a whole, and has the stamp exactly when ADR-0024 decision 4 says a reader has it: the file is valid and its `schema_version` is `1`. The moments ① to ⑦ keep their numbers and their order (cited: ADR-0016 decision 2), and ④ stays where it is.
- **Nothing is kept between calls** (cited: ADR-0010 decision 7): every call reads the file in ⓢ.
- **Why a rule.**
  - *The words and what the stamp is for.* The version is recorded per run so that "runs of different versions can stand side by side" (cited: ADR-0004 decision 9). A call that opens `runs/<run_id>/STATE.json` without the stamp of that run has taken the layout its own source builds for the layout of the run. ADR-0024 decision 4 says that nothing stands in for a stamp that cannot be had, the constant of the reader's source included, and its decision 3 says, where it explains why the two versions of this file are coupled, that the file is at the one path a layout version cannot change, "so its version is read before anything else of the run is interpreted". The first sentence is about what the layout version of a run is and the second about the version of that file; **that they carry over to the order of a call is this record's reading**, not theirs.
  - *What the answers of a call state.* `run_file_missing` for `STATE.json` carries "no state was written for this `run_id` … : no round has begun" (cited: ADR-0019 decision 2, from ADR-0012 decision 2). A call can say that of a run only when the path it looked at is the path of that run's layout, and without the stamp it does not know that.
  - *A write.* A journaled tool that selects no backend appends a start line to the log of a run without reading `instance.json` (Context). Nothing in such a call keeps it from a run that states no layout version.
  - *Who can hold the rule.* A source that does not read the stamp first cannot be given the rule later by a record it does not know, and a process runs the source it loaded (cited: ADR-0010 decision 7). The rule is therefore stated while the sources that exist are the sources of one layout version. This is a reason for stating it now and no rule about another version.
- **What it costs, and how it stands to #4 §1.** One more read of one small file at a path known from the `run_id` alone, at each call; nothing is listed or scanned and nothing is kept. #4 §1 makes one small `STATE.json` the entry point from which a turn loads only what is referred to; this record speaks of the frame of a tool call and not of what a turn reads, `instance.json` holds nothing of where a run stands, and the lookup still reads `STATE.json` and the log as before. A repeated call for an ended step (NFR-1, FR-6) is answered with the stored `result` as before whenever the run's file is a valid version 1 file; the cells in which it is no longer answered are in the Walk-through. **Why that is accepted**: a run in those cells could start no new step of a journaled HW tool before this record either (the rows of ④); no line of its log is changed or lost (NFR-2), so the stored outcome is kept and only the answer of a call is withheld; and a call that returned it would state, as the outcome of a step of that run, what it read at a path the run does not state. What anybody does after the answer is not decided (OD-10, the rest of OD-17).

### 4. What a call answers in ⓢ, and the read of ④

- **When the stamp cannot be had, the call is a tool failure of one of the four kinds of ADR-0019 decision 2, by the rows that its decision 3 has for `instance.json`**: `run_file_missing` (the file is not there), `run_file_unreadable`, `run_file_invalid`, `run_file_unsupported` (a `schema_version` that is an *integer* other than `1`). **No kind is added and no meaning changes.** The sentence of ADR-0019 decision 2 holds for a kind answered in ⓢ as it stands: this call appended no line, selected or called no backend, did not run the step and consumed nothing at any target. The borders of its decision 4 and the rule for the message of its decision 6 apply to this read as to the read of ④.
- **A kind answered in ⓢ says nothing about the identity.** The lookup was not carried out, so whether the identity has no line, is open or is ended, and whether an earlier call ran its step, is not established — as ADR-0019 decision 2 says of a kind of ③. A caller cannot tell from the kind whether it was answered in ⓢ or in ④; before this record a kind for `instance.json` implied that the lookup of that call had found no line.
- **④ is unchanged: the selection reads the file again** (cited: ADR-0018 decision 4, "In ④ the tool function reads `runs/<run_id>/instance.json`"). The hw_profile of the call — and for `correctness.check` the tolerance, from the same read (cited: ADR-0021 decision 4) — is taken from a content that is itself a valid version 1 file. A file that is there and valid in ⓢ and is gone, unreadable, invalid or of another version in ④ is answered in ④ as ADR-0019 decisions 3 and 4 have it; the identity then has no line. Letting one read serve both moments is not chosen: it would change what ADR-0018 decision 4 and ADR-0021 decision 4 say of the read of ④, and no call can observe the difference unless the file changes during it.
- **The same request again**: answered as if the failed call had not been made (cited: ADR-0019 decision 3) — after ②, by ⓢ again, and then by the lookup.

### 5. Against what the stamp is held

- **Against the pairing a record fixes for the `schema_version` the reader knows, and against nothing else** (cited for the pairing: ADR-0024 decision 3). A call that has the stamp has layout version 1, the only pairing a reader of this record knows, and the frame then uses the paths ADR-0004 fixes for version 1.
- **`hilclaw.layout.LAYOUT_VERSION` is compared with nothing by this record.** A source of layout version 1 and a stamp a version 1 reader can have cannot differ, and a source that builds another layout is not defined. Whether a source holds the stamp against the layout it builds is left to the record that defines a second layout version (sub-question ㉗, second part).

**Read, and standing as written:**

- ADR-0018 decision 4: "A call answered in the lookup … does not read it for the hw_profile" — it reads it for the stamp, the read that sentence left to "the record of that member".
- ADR-0011 decision 3, "The repeated call", and ADR-0015 decision 5: their sequence begins once the state of the identity is established. A call answered in ⓢ has not established it, like a call answered in ① or ② or with a kind of ③ (the reading ADR-0016 decision 2 and ADR-0019 already make). "The outcome of a call thereby depends on the data plane only" (ADR-0011 decision 3) holds: `instance.json` is a file of the data plane.
- ADR-0016 decision 2, "Why ④ lies between the lookup and the start line": ④ is not moved, and a stored result stays obtainable "when the table has changed since" — ⓢ asks the table nothing. It is no longer obtainable through a call when the file of the run states no layout version to the source that reads it (decision 7).
- ADR-0024 decision 5, "This record changes no order of any call": true of that record.

### 7. Limits

- **The file can change or go between ⓢ and a later read of the same call.** The reads of one call are not atomic and no lock is taken (cited: ADR-0004 decision 10; ADR-0019 decision 7). A call can have the stamp and then meet a situation in ④, or read the log of a run whose file went after ⓢ.
- **Nothing checks the tree against the stamp** (cited: ADR-0024 decision 2). A call that has the stamp knows what the run states, not what is on disk.
- **The stamp needs a file that is valid as a whole** (cited: ADR-0024 decision 4). For a run whose `instance.json` is missing or damaged, every call that passes ② is answered with a kind in ⓢ, a call for an ended identity included, though its log may be sound. Where one source takes a file as valid that another refuses (cited: ADR-0018 decision 6, "Two processes, two validators"), calls through the second are answered `run_file_invalid` for every identity of that run.
- **Two processes of two sources**: only a source that carries this rule holds it. A process that loaded an earlier source reads and appends without the stamp, and nothing detects it.
- **Everything outside the frame**: the step of a tool, the functions of the package called directly, a person, a script. They open paths of a run without this rule (decision 1).
- **No call passes ⓢ for a run before its `instance.json` is under its final name.** That follows from decision 3. It already held for the selection and is new for a journaled tool that selects no backend, whose step could run in a run without the file before this record (Walk-through). So the step of a call of decision 1 cannot be what first writes the `instance.json` of the run its request names, as the lookup already keeps the step of a journaled call from being what first writes `STATE.json`. It orders nothing between that file and the first `STATE.json`: a journaled call needs both, and what else writes either, and in which order, is not said here.
- **A caller that could tell "no line" from a kind for `instance.json` no longer can** (decision 4).

### Walk-through

A file that cannot be read follows the rows of the missing file with `run_file_unreadable` (not run as a case). Two cells outside the table: with no run directory at all, the answer is `run_file_missing` today and by this record, and the message names `instance.json` where it names `STATE.json` today; with a file that is valid in ⓢ and not in ④, the answer is the kind of ④ as today. And one case the table does not hold, since it assumes a `STATE.json` and a log that can be read: where a situation of ③ and a situation of `instance.json` hold at once, the call answers the kind of `instance.json` where it answers the kind of ③ today, for both tools (decision 6, the row of ADR-0019 decision 4; today, with an empty `STATE.json` and no `instance.json`, both answer `run_file_invalid`).

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 3 | (A) The sentence binds no order: it says where the stamp is and that finding it needs no knowledge of the layout | The words of ADR-0004 can be read this way: that record fixes paths and names and calls the tree a naming convention (its decisions 1 and 10). This record does not settle how ADR-0004 is read for every user; it lays the rule on a call itself, for these reasons. Without it the cost ADR-0024 paid for the coupling buys nothing where a call is answered from the log or appends without a selection: such a call takes the layout of its source for that of the run. Nothing would keep a version 1 source from reading or appending at version 1 paths in a run that states no layout version, and the record that defines a second layout version could not add the guard to a source already running. What today's call gives without a rule — the read in ④ before the start line of a HW tool — covers neither the reads of ③ nor a journaled tool that selects no backend. |
| 3 | (C) It binds a write only: the reads of ③ need no stamp, and nothing is appended by a call that has not had it | Its case is strong: it changes one kind of cell only ("Plain, no line"), a journaled HW tool meets it already, the sentence of ADR-0019 decision 2 counts lines and consumption and no read, and it keeps what ADR-0016 decision 2 wanted of the place of ④ — "a stored result must stay obtainable" (its NFR-7 ①; NFR-1 is this record's addition) — also for a run whose file is damaged or is refused by a stricter validator (decision 7), which (B) gives up. Not chosen, for three reasons: ADR-0004's subject is "a reader", so a rule that leaves out the reads leaves out what the sentence names; a kind of ③, and a stored result, would still be stated of a run from a path that run does not state (decision 3); and what ADR-0016 guards is a change of the table of the source, which ⓢ does not ask. The cost (B) pays for this is in decisions 3 and 7. |
| 1, 3 | The sentence read as a rule for every user of a path of a run, the writers included | It would fix that `instance.json` is written before the first `STATE.json` (sub-questions ⑩ and ⑰) and bind the step of every tool (OD-18). Registered as sub-question ㉗. |
| 2 | "Uses" means a read only, or a write only | A read only would let a call append to a run whose stamp it has not had; a write only is (C), above. |
| 3 | The stamp read in a front or in `hilclaw.tools.call` | A front holds no check (ADR-0010 decision 3), and that level does not know whether a tool is about a run. |
| 4 | A kind of its own for a stamp that cannot be had | The four kinds already say what was found in that file; a fifth would give one situation of one file two names. |
| 4 | The stamp needs `schema_version` only, not a valid file | ADR-0024 decision 4: an invalid file states no layout version — "though it may hold `"schema_version": 1`" (its Walk-through). |
| 4 | One read of the file for ⓢ and ④ | See decision 4. |
| 5 | A call compares the stamp with `LAYOUT_VERSION` and refuses a difference | No difference can arise in what is defined; what a reader does with one is a rule about another layout version (OD-11). |
