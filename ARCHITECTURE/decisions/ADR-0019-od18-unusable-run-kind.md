## Context

- Three records left the same point open. ADR-0015 decision 7: "A run that cannot be used — no valid `STATE.json`, a damaged log — is a tool failure (ADR-0010 decision 4) whose kind this record does not fix", registered as sub-question ④ with "a stored position beyond the log" and "whether the frame reserves a kind for it". ADR-0016 decision 4: "A hw_profile that cannot be read or is no valid record is not `no_backend`: the run cannot be used, and that kind is open". ADR-0018 decision 4: the file "is missing; it cannot be read; it is invalid by decision 2 …; its `schema_version` is an *integer* other than `1` … Which tool-failure kind such a call answers is not decided".
- **What the code does today.** `hilclaw/journaled_step.py`, `hilclaw/journaled_tool.py`, `hilclaw/hw_tool.py` and `hilclaw/instance.py` give no kind to such a run: the error of the reader or of the lookup passes through the tool function unchanged (the classes are in the table of decision 3), and `hilclaw.tools.call` turns every exception that is no `ToolFailure` into the reserved kind `tool_crashed`, whose meaning is that the tool function "raised something that is no tool failure" — "the tool is defective" (ADR-0015 decision 2). A caller cannot tell a missing or damaged run from a defect of the tool layer, and the tests of these paths do not pin the kind.
- **Fixed and not re-decided.** That such a call is a tool failure (ADR-0015 decision 7; the form: ADR-0010 decision 4). The seven reserved kinds and their meanings (ADR-0015 decision 2, ADR-0016 decision 3). The order of a call (ADR-0016 decision 2): ① the request, ② the data root, ③ the lookup, ④ the selection, ⑤ the start line, ⑥ the step, ⑦ the end line. What makes each file missing, invalid or of an unsupported version: `STATE.json` (ADR-0012 decisions 2 and 6), `events.ndjson` (ADR-0006 decisions 2, 6 and 8; a stored position beyond the log: ADR-0011 decision 6), `instance.json` (ADR-0018 decision 2). No reader repairs anything, and nothing is kept between calls (ADR-0010 decision 7).
- No fact about Claude Code or MCP is used beyond F1 to F14 of ADR-0010 and ADR-0015.

## Decision

A value below is **cited** when a source is named with it; every other value is **this record's own** choice — among them the term as a property of one call, the four kinds and their names, which situation gets which kind, the conventions adopted in decision 3, the borders of decision 4, the level of decision 5 and the rule for the message.

### 1. Scope and the term

- This record is about a call of a tool whose tool function carries out **the lookup** of a journaled tool (ADR-0015 decision 5) or **the selection** of a HW tool about a run (ADR-0016 decision 4), or both. The **frame files** are the three files of `runs/<run_id>/` that the frame reads at those two moments: `STATE.json` and `events.ndjson` at the lookup, `instance.json` at the selection (cited: ADR-0011 decision 6, ADR-0012; ADR-0018 decision 4). It defines no tool, and the terms of ADR-0015 and ADR-0016 are used unchanged.
- **A run cannot be used at a call** when the lookup or the selection of that call finds one of the situations of decision 3 in a frame file it reads. It is **a property found at that call, from what that call reads**. Nothing stores it: no file marks a run, and no process remembers an earlier answer (cited: ADR-0010 decision 7). The same run can therefore answer one request and not another, and one call and not the next (decision 7).
- **Not a situation** (cited): a torn tail of the log, which is skipped and is no damage (ADR-0006 decision 6); a missing or an empty `events.ndjson`, which means "no event recorded" (ADR-0006 decision 2), unless the stored position is beyond it (a log that is not there because the data root is gone: decision 4); a top-level member a reader does not know (ADR-0012 decision 2, ADR-0018 decision 2).
- **Two moments.** A situation of `STATE.json` or of the log is found **in the lookup, before it can answer**: the state of the identity is not established, so neither an ended nor an open identity is answered. A situation of `instance.json` is found **in the selection only** — for a journaled tool, that is for an identity with no line: an ended or an open identity of the same run is still answered from the log, since the file is not read for it (cited: ADR-0016 decision 2, ADR-0018 decision 4).

### 2. The frame reserves four kinds

Reserved in the sense of ADR-0015 decision 2: one meaning in every tool, raised for no other situation. Only a tool function raises them, and only at the lookup or the selection. For each of them it also holds that **this call appended no line, selected or called no backend, did not run the step and consumed nothing at any target**. Whether an earlier call ran the step of the identity is not said by a kind of ③: the lookup did not establish it (decision 1).

| `kind` | Meaning, in every tool |
|---|---|
| `run_file_missing` | A frame file the call needs is not there |
| `run_file_unreadable` | The file system failed the read of a frame file for a reason other than its not being there; its content was not judged |
| `run_file_invalid` | A frame file is invalid by the record that defines it, a complete line of the log is damaged or is a step line that breaks ADR-0011, `STATE.json` stores a position beyond the log, or what stands in the place of a frame file is no regular file |
| `run_file_unsupported` | A frame file, or a line of the log, has a `schema_version` that is an *integer* other than the one this source reads; nothing of it was interpreted |

- No reserved kind and no name in `hilclaw/` collides with the four (checked on 2026-10-08); each is a *name* of ADR-0001.
- **Why reserve at all** (the test of ADR-0015 decision 2). None of the situations belongs to one tool: they are found by the part every journaled tool and every HW tool about a run shares. The only kind they reach a caller with today says the tool is defective, and it is not. And a reserved kind carries the sentence above the table for every tool: as with `step_open` (ADR-0015 decision 2), a kind each tool named itself could also stand in the `failure` of an end line, and a call that did not start the step could not be told from a step that ended.
- **Why four.** ADR-0016 decision 3 split its two kinds where "a caller acts differently on each". This record does not say how a caller acts (Boundaries); it splits where the fixed records already say something different of each case, so that a caller can tell which of these holds without knowing the tool and without reading the message:
  - *missing* — "no state was written for this `run_id` … : no round has begun" (ADR-0012 decision 2), "no instance record was written for this `run_id`" (ADR-0018 decision 2). This is not established where decision 4 answers the same kind for a data root or a file that went during the call.
  - *invalid* — "Invalidity is an error, as damage of the log is"; the reader "uses no member of the file and repairs nothing", and what is recovered is "what was committed, from the history of the data repository" (ADR-0012 decision 6, ADR-0006 decision 6; for the position, ADR-0011 decision 6). Of an invalid `instance.json` ADR-0018 decision 2 says only that a reader reports it, uses no member of it and repairs nothing — not what is recovered. No record says any of this of a step line that breaks ADR-0011 or of a path that is no regular file; both are counted here by decision 3.
  - *unsupported* — "is not damage" in all three records; reading another version is OD-11.
  - *unreadable* — no content was judged, so none of the three statements is established. It is a fact about that process on that machine at that call: another process may read the same file.
- **What a kind lets a caller tell is all this record says of it.** What a caller, a role or a person does on any of the four is not decided (Boundaries).
- **How this reads ADR-0015 and ADR-0016.** The table of ADR-0015 decision 2 is "the part of every tool's contract that is common, not a closed list", and "a later record of the frame may add to the common part as long as no tool's contract uses the name, and none exists" (ADR-0016 decision 3); no tool exists (`hilclaw.tools.default_registry` is empty). ADR-0016 decision 4, "a hw_profile that cannot be read or is no valid record", is read with ADR-0018: the hw_profile of a run is the `hw_profile.record` of its `instance.json`, and one that is no valid record makes that file invalid (ADR-0018 decisions 2 and 3). Neither record is edited.

### 3. Which situation gets which answer

"Class today" is what the tool function raises for the situation on `main`, to be mapped by the code task (decision 5); `UVE` stands for the `UnsupportedVersionError` of the named module.

| Moment | Situation, and the record that defines it | Kind | Class today |
|---|---|---|---|
| ③ | `STATE.json` is not there (ADR-0012 decision 2) | `run_file_missing` | `run_journal.MissingStateError` |
| ③ | `STATE.json` is invalid, an empty file included (ADR-0012 decision 6) | `run_file_invalid` | `run_state.InvalidStateError` |
| ③ | `STATE.json` has another `schema_version` (ADR-0012 decision 6) | `run_file_unsupported` | `run_state` `UVE` |
| ③ | A complete line of the log that the lookup reads is damaged (ADR-0006 decision 6) | `run_file_invalid` | `events.CorruptEventsError` |
| ③ | A complete line that the lookup reads has another `schema_version` (ADR-0006 decisions 6 and 8) | `run_file_unsupported` | `events` `UVE` |
| ③ | A complete line that the lookup reads is a `step_started` or `step_ended` line whose `data` breaks ADR-0011 decisions 3 and 7 (this record's own reading, below) | `run_file_invalid` | `journal.JournalError` |
| ③ | The position `STATE.json` stores is beyond the log, a missing log below a data root that is there included (ADR-0011 decision 6) | `run_file_invalid` | `events.PositionBeyondLogError` |
| ④ | `instance.json` is not there (ADR-0018 decisions 2 and 4) | `run_file_missing` | `instance.MissingInstanceError` |
| ④ | `instance.json` is invalid: empty, partial, a `hw_profile` that breaks ADR-0018 decision 3 | `run_file_invalid` | `instance.InvalidInstanceError` |
| ④ | `instance.json` has another `schema_version` (ADR-0018 decision 2) | `run_file_unsupported` | `instance` `UVE` |
| ③, ④ | The read of a frame file fails in the file system for a reason other than its not being there (for `instance.json`: ADR-0018 decision 4, "it cannot be read") | `run_file_unreadable` | an `OSError`, unchanged |

- **What was read.** In ③: the data root was asked, `STATE.json` was looked for and, when it could be read, the log. In ④: `instance.json` was looked for — for a journaled tool after both were read and the identity was found to have no line. Nothing was written in either (the sentence of decision 2; for ④ cited: ADR-0018 decision 4).
- **The same request again.** The failed call left nothing in the data plane and nothing in a process. A later call with the same request, the same `execution` included, is therefore answered as if the failed one had not been made: in ③ by what the lookup then finds — a situation still, or no line, open or ended — and in ④ by the lookup again and, for an identity that still has no line, by the selection, which reads the file again. How a situation comes to hold no longer is not this record's.
- **A step line that breaks ADR-0011** — a line with a valid envelope and one of the two kinds whose `data` does not hold the members of ADR-0011 decisions 3 and 7 in their forms, as `hilclaw/journal.py` checks them — is given `run_file_invalid` by this record: the lookup can establish the state of no identity over it, and the sentence of decision 2 holds. This fixes the kind a call answers and adds no rule about damage: ADR-0006 decision 6 defines damage for the envelope only, and ADR-0011 does not say what a reader does with such a line. The same class is raised for an invalid identity of a request; that is refused in ① as `invalid_request` (ADR-0015 decision 4) and is no situation. The row is about the `data` as ADR-0011 has it: how a later change in the `data` of the two kinds is told apart from such a line stays open (OD-8 sub-question ⑧), and the record that answers it says then what a call answers.
- **Conventions of the readers, adopted here** (this record's own; the code has them): a missing run directory, and a file in the place of a directory above the frame file, are "not there" (for the directory, cited: ADR-0004 decision 1); what stands in the place of a frame file and is no regular file is `run_file_invalid` (a symbolic link is not followed). This too fixes the kind a call answers, not the validity of a file: ADR-0006, ADR-0012 and ADR-0018 are unchanged and say nothing of such a path.
- **More than one situation at once**: the call answers the one it finds first. That the lookup comes before the selection is cited (ADR-0016 decision 2); the order inside the lookup is the code's (today `STATE.json`, then the log).
- **Not in the table: a failure inside the append of the start line or of the end line** (⑤, ⑦). The sentence of decision 2 cannot be said of it: after a failed start line the identity has no line or is open, and after a failed end line the step has run and the identity is open or ended (`hilclaw/journaled_step.py`, `hilclaw/events.py`). This record gives it none of the four kinds and no other. Registered as sub-question ⑨; until it is answered such a failure reaches a caller as the code has it today.

### 4. The borders to the existing kinds

- **`invalid_request`**: a well-formed `run_id` that names no run is **not** a refused request. A refusal comes before the data root is asked, reads nothing and is "the same on every machine" (cited: ADR-0015 decision 2); that a run has no file is found only by reading. It is `run_file_missing`.
- **`no_data_root`** is the answer of ② and of no later moment: it is "raised before anything is read or written" (cited: ADR-0015 decision 3). A data root that was an existing directory at ② and is gone at a later read of the same call — of `STATE.json`, of the log or of `instance.json` — is answered like a missing run: no frame file is there, and the answer is `run_file_missing`. A repeated call asks the source again in ② and, while the directory is still gone, is answered `no_data_root` there. The readers check the data root again at each read (today a `FileNotFoundError` or `NotADirectoryError` of their own); answering `no_data_root` from that check would be no better than the first, since the directory can go after it too.
- **Missing or unreadable.** For `STATE.json` and `instance.json`, "not there" is `run_file_missing` at whatever read of the call it is found, a file removed between a check and the read of one call included; a log that is not there below a data root that is there is no situation by itself (decision 1), a log removed between a check and the read of one call included: the lookup goes on as for a log that is not there. Every other failure of the file system at the read of a frame file is `run_file_unreadable`. The class `OSError` alone therefore does not decide the kind (noted in the review of `hilclaw/instance.py`, task T-0067). Whether such a failure is a property of the run, of the machine or of the moment is not judged: the kind says only that no content was judged.
- **`tool_crashed`** stays what ADR-0015 decision 2 made it, and stays the answer for an exception that is no tool failure and no situation to which decisions 3 and 4 give one of the four kinds: a reader handed to the tool function of a HW tool that returns what is no valid record although the file is valid (`hilclaw.keys.InvalidRecordError` from `hilclaw.backends.select`), or raises anything that is no such situation; such an exception out of the step, which leaves the step open; a defect of the path itself; a failed append reaches a caller this way today and is not decided here (decision 3, sub-question ⑨). **`bad_result`** is untouched.
- **`step_open`, `no_backend`, `not_offered`** are unchanged. The order in which one call can meet the kinds is that of the moments: `invalid_request` (①); `no_data_root` (②); a situation of ③; else the stored `result` or `failure`, or `step_open`; else, for an identity with no line, a situation of ④; then `no_backend`; then `not_offered`.

### 5. Where the answer is given

- **Below the fronts** (cited: ADR-0010 decision 3 — a front holds no check), **in the tool function, at the lookup and at the selection**, as ADR-0015 decision 5 placed the lookup and ADR-0016 decision 2 the selection.
- **The property is fixed, not the code**: a call that meets a situation to which decisions 3 and 4 give one of the four kinds is a tool failure of that kind, alike through both fronts, and none of them reaches a caller as `tool_crashed`. How the classes of the table are mapped, in which module, and whether the readers change, is the code task's (as ADR-0015 decision 5 left the journaled path).
- **Not in `hilclaw.tools.call`, for every tool**: that level does not know at which moment an exception arose. The same classes can come out of the step (⑥), where the step has started and stays open, and out of an append (⑤, ⑦); mapped there by class, they would be answered with a kind that says the call did not run the step.
- **For which tools.** Every tool function that carries out the lookup answers the rows of ③, and every one that carries out the selection for a call about a run answers the rows of ④, journaled or not (ADR-0016 decision 4: such a request carries `run_id` either way). On `main` the two builders are `hilclaw.journaled_tool.tool_function` and `hilclaw.hw_tool.tool_function`; a HW tool that is not journaled has no builder yet. A tool whose request carries `run_id` and that carries out neither meets none of these situations.

### 6. What the message carries

`error.message` stays a string for a reader (ADR-0010 decision 4), and no member is added to the error object. **The message names the frame file by its path relative to the data root and says what was found** — the broken rule, the line number of a damaged line, the version met, or what the file system reported — as the readers' messages already do (`hilclaw/run_journal.py`, `hilclaw/events.py`, `hilclaw/instance.py`). The `journal.JournalError` of the lookup names the line and no file, and an `OSError` carries the path as the system gives it; for those two rows the code task composes the message. The wording is the code's. A caller tells the cases apart by the kind and never by the message.

### Walk-through

One call of the journaled HW tool `example.tool` (a placeholder, as in ADR-0015, ADR-0016 and ADR-0018) with the request `{"run_id": "r1", "round": 3, "candidate": 2, "attempt": 1, "execution": 1, …}`, through either front.

| Moment | What is found, and the answer |
|---|---|
| ① ② | As ADR-0015: `invalid_request`, `no_data_root`. No file of `r1` is looked at |
| ③ `runs/r1/STATE.json` is not there (no such run, or its state not written yet) | `run_file_missing`; `instance.json` is not looked at |
| ③ `STATE.json` is empty, or line 12 of the log is damaged and lies after the stored position, or the stored position is 40 and the log has 37 complete lines | `run_file_invalid`, also when the identity has an end line: the lookup did not answer |
| ③ The log ends in a torn tail | No situation: the tail is skipped (ADR-0006) and the lookup answers |
| ③ The lookup answers: ended, or open | The stored `result` or `failure`, or `step_open`. `instance.json` is not read, whatever its state |
| ④ No line; `runs/r1/instance.json` is not there, or cannot be read, or is partial, or has `schema_version` 2 | `run_file_missing`, `run_file_unreadable`, `run_file_invalid`, `run_file_unsupported`; no backend, no line |
| ④ The file is valid | `no_backend`, `not_offered`, or the start line, as ADR-0016 |
| The same request after the file is there and valid | The lookup finds no line and the call goes on to the selection, with `execution` 1 |

### 7. Limits

- **Nothing repairs or marks the run**, and no access control exists (ADR-0010 decision 8): a caller that names another run is answered for that run (ADR-0015 decision 7).
- **Found only in what a call reads.** For an identity of the stored `round` the lines before the stored position are not interpreted, so damage or another version among them is not found; for every other identity (another round, or none) the log is read from its first line and they are (`hilclaw/journaled_step.py`; whether such steps exist is sub-question ① of OD-17). One run can thus answer one request and refuse another. A file the call does not read — the result files of an attempt, `artifacts.json`, the stored key records — is not looked at.
- **Two processes can judge one file differently**: an MCP server runs the source it loaded at its start and a command-line call the source as it is now (cited: ADR-0010 decision 7; ADR-0018 decision 6), so one can answer `run_file_unsupported` or `run_file_invalid` where the other reads the file; two processes can also differ in what the file system lets them read. A content one interpreter cannot read (nesting, a long integer) is reported as invalid by the readers though the file may be sound. A stored `result` that parses but is nested too deeply to copy at the call depth of the lookup is no such situation: it still reaches a caller as `tool_crashed` (`hilclaw/journaled_step.py`, Limits).
- **A file that changes during a call**: the reads of one call are not atomic and no lock is taken (ADR-0004 decision 10). A call can pass the lookup and then fail an append (sub-question ⑨), or answer `run_file_missing` for a file that is there a moment later.
- **A step or a tool that states one of the four kinds for something else** is not detected (as ADR-0015 decision 7 says of every reserved kind).

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 2 | (a) No reserved kind; each tool names the situations itself | They belong to no tool; a caller and a conformance test would need a table per tool, and the name could stand in an end line (decision 2). |
| 2 | (b) One kind for every situation, the message saying which | The meaning would be "one of four unlike things", and a caller would have to parse a string that ADR-0010 gives no form in order to tell "nothing was written" from "the content is wrong" from "this source does not read it". |
| 2 | (c′) Three kinds, "cannot be read" counted as invalid | It would say of a file whose content nobody judged that it is invalid. |
| 2 | (d) The situations stay `tool_crashed` | Its reserved meaning is false for them, and a caller cannot tell a missing run from a defect of the tool layer. |
| 2 | A kind per file (`STATE.json`, the log, `instance.json`) | Which file it is is told by the message; what differs for a caller is what was found, not where. |
| 3 | The four kinds also for a failed append | See decision 3: after it the identity can be open or ended, and the step can have run. |
| 4 | `no_data_root` also at a later read | Its meaning says nothing was read, which is false once a file of the run was read; and the readers' second check can be overtaken as well. |
| 4 | A `run_id` that names no run is `invalid_request` | A refusal reads nothing and is the same on every machine. |
| 5 | The mapping in `tools.call`, by exception class | See decision 5: the moment is not known there. |
| 6 | A member of the error object that names the file or the rule | A change of the form of ADR-0010 decision 4, which this record does not make. |

## Consequences

- **The code slice that can now be cut** (code mode, within the size cap; whether it is one task or two is the planner's): the four kinds beside the seven of `hilclaw/tools.py` and in `RESERVED_KINDS`; the mapping of the rows at the lookup and at the selection in the path of a journaled tool and of a HW tool — at the moment, not by class at the level of `tools.call`, with "not there" told from the other `OSError`s, and with the three `UnsupportedVersionError` classes of `run_state`, `events` and `instance`; and the tests that today assert only that the kind is none of `invalid_request`, `no_data_root`, `step_open` (and, for a HW tool, `no_backend`, `not_offered`) — `tests/test_journaled_tool.py`, `tests/test_hw_tool.py`, `tests/test_instance.py` — which can then pin the kind of each row.
- **Docstring sentences that then change**: in `hilclaw/hw_tool.py`, "pass through unchanged with no kind given here (OD-18 sub-question 4, open)"; in `hilclaw/journaled_tool.py`, "passes through with no kind given here (OD-18 sub-question 4, open)"; in `hilclaw/journaled_step.py`, "An error of that read, of the read of the log or of the lookup passes through", if the mapping is placed there; in `hilclaw/instance.py`, "it gives no kind to a run whose hw_profile cannot be had (OD-18 sub-question 4)"; in `hilclaw/tools.py`, the comment that names the records of the reserved kinds.
- **What the conformance tests of P1-1 gain**: each row of the table produced by files on disk, through both fronts, with its kind pinned, the data plane unchanged, and the same request answered afterwards.
- **Not edited and now less exact** (follow-ups for the integrator): the table of ADR-0015 decision 2 and of ADR-0016 decision 3, which no longer hold every reserved kind; ADR-0015 decision 7 (last bullet) and its Boundaries ④; ADR-0016 decision 4 ("that kind is open") and its Boundaries; ADR-0018 decision 4 (last sentence), the last row of its Walk-through, its Consequences ("stays unpinned") and Boundaries. No sentence of UsageCases became false.
- **A-13 reading**: document mode; no code, dependency, settings file or schema file changes. The record continues the interface between layer 1 and layer 2 (as ADR-0015 and ADR-0016 did) and names no member of a data-plane file: what makes `STATE.json`, `events.ndjson` and `instance.json` missing, invalid or unsupported is cited and unchanged, and the error object keeps the form of ADR-0010.

## Boundaries (not decided here)

- **What anybody does after the answer**: repair or re-creation of a file, restoring it from the history, a restart of the run, a further `execution`, a retry policy, a health check, marking a run as broken, notifying a person (OD-10 — it needs #5 B-2; the retry part and the sub-questions of OD-17; OD-23; OD-27; PLAN P2-1, P2-4).
