## Decision

### 1. Scope

The CUDA target on this PC's GPU and the PLAN P3-16 demonstration: a test-placed fp32 `gemm` kernel through build, `correctness.check` at `sim` and `board`, `board.run` and the run's record with the real `nvcc` and GPU. Other GPUs, other machines and every vendor target but CUDA are outside.

### 2. The target `cuda_gpu` and its hw_profile

- **`accelerator`**: `cuda_gpu` (a name of ADR-0001 decision 1).
- **`revision`**: `<product name> sm_<major><minor>` of the machine's one GPU, for example `NVIDIA GeForce RTX 4070 sm_89`, from the first line of `nvidia-smi --query-gpu=name,compute_cap --format=csv,noheader`, read **on the host** (devices are read on the host, ADR-0194 decision 7). *Why*: the compute capability is what `nvcc -arch=native` builds for and what the kernel's speed depends on; the product name alone can name several boards. **A machine with more than one GPU line has no record** (which device a run uses is not decided; Boundaries).
- **`toolchain`**, three members of the open map (ADR-0001 decision 6; HQ-0093 ②): `nvcc`, the release line as `cuda_adapter.interpret_probe` reads it (`Cuda compilation tools, release 13.1, V13.1.115`); `gcc`, the first line of `gcc --version` (nvcc's host compiler, which compiles the C harness and the kernel's host code); and `nvidia_driver`, the `driver_version` of the same query as `revision` (`617.14`). **Where read**: `nvcc` and `gcc` where the kernels are built — in one new container of the named image when an image is named, else on the host, as ADR-0186 reads `clang`; `nvidia_driver` always on the host, since the driver is the host's even inside a container.
- **`host`** and **`hw_source`**: `cpu_standin`'s rules ([ADR-0035](ADR-0035-od4-cpu-standin-hw-key-values.md) decisions 4 and 8).
- **Data plane**: `cuda_gpu` is a new value of the name field `accelerator` (not a closed list, as ADR-0193 Consequences reads it), and the three member names are names of an open map. **No frame changes.**

### 3. The target-table entry

| Member | Value | Why |
|---|---|---|
| `flags` | `("-O2", "-arch=native")` | `cpu_standin`'s optimisation level; `-arch=native` builds for the GPU the build sees (checked on this machine), so the build container is given the GPU (decision 7) |
| `trailing_flags` | `()` | `nvcc` links the CUDA runtime itself |
| `waiter_flags` | `("-O2",)` | the waiter (ADR-0145) is C that `nvcc` hands to `gcc`; `cpu_standin`'s `-std=gnu11` and `-ffp-contract=off` are no `nvcc` options |
| `env` | `None` | as `cpu_standin` |
| `build_time_limit_s` | `120` | `nvcc` runs `gcc`, `cicc` and `ptxas` per file; twice `cpu_standin`'s 60 |
| `process_time_limit_cap_s` | `cpu_standin`'s | the same ADR-0117 cap |
| `contracts` | the one contract of decision 4 | |
| `memory_limit_bytes` | `None` | a Docker memory bound does not bound GPU memory; no GPU memory figure (HQ-0090) |
| `unit`, `units_per_ns` | `ns`, `1` | the host monotonic clock (ADR-0194 decision 4) |
| `model_run` | `False` | HQ-0096 (integrator's reading) |
| `instance_start` | `False` until slice 6, then `True` | HQ-0096's addition opens it; no instance starts before a CUDA kernel can be recorded in a run (decision 5) |
| `coder_loop` (new) | `False` | below |

- **"Given-code evaluation only, not the coder's round loop" is a new `Target` member `coder_loop`**, exactly a `bool`: whether a run of the coder's round loop may start on the target. `cpu_standin` and `virtual_npu` get `True`, `cuda_gpu` `False`. The instance start of the round loop (`hilclaw.new_run`) refuses an accelerator whose `coder_loop` is false; the given-code command (`hilclaw.given_eval`) reads `instance_start` only and is unchanged. A `Target` member is package source and no data-plane value (`hilclaw/targets.py`), so **this is no frame change**. *Why not `instance_start` alone*: one boolean cannot hold "open to given code, closed to the coder" (HQ-0096's reading). *Why not a refusal keyed on the name `cuda_gpu`*: the next vendor target would need the same, and the table is the place for a target's properties (ADR-0193 decision 3).
- Values the slice finds refused by the real `nvcc` are corrected there and recorded in its `Result`; they are no data-plane value.

### 4. The first contract, the kernel interface and the harness

- **Contract**: a new entry of the contract table, kind `gemm`, dtype `fp32`, layout `row_major`, language **`cuda`**, with fp32 `gemm`'s shapes, operands, inputs and reference ([ADR-0008](ADR-0008-od6-gemm-kernel-contract.md), [ADR-0177](ADR-0177-od18-od6-contract-table.md)), checked and timed. The oracle is that reference with the user's tolerance (HQ-0096 ② (a)). Adding an entry is the approved open list "커널 계약 표" of DRIVER §3 (D23). *Why fp32*: `tests/cuda_fixtures/timing.cu` already times fp32 `gemm` on this GPU, fp32 `gemm` has hand-written C programs, and bf16 on the GPU adds `__nv_bfloat16` conversions that the demonstration does not need. *Why not the language `c` entry*: its prototype takes host memory and its language names the kernel's language (ADR-0008), which a CUDA kernel is not.
- **Kernel interface**: the kernel's source defines `extern "C" void hilclaw_gemm(size_t m, size_t k, size_t n, const float *a, const float *b, float *c);` once and no `main`, as ADR-0008 decision 7 asks of a C kernel. **`a`, `b` and `c` are device pointers.** The function launches its work on the default stream and may return before it completes; it allocates no device memory that outlives the call and copies nothing between host and device.
- **The harness owns memory and transfers**: it creates the context, allocates device memory (`cudaMalloc`), copies the inputs before the first repeat and the result after the last (`cudaMemcpy`), and waits for the device (`cudaDeviceSynchronize`) as ADR-0194 decision 4 says: before the start reading outside the interval, before the end reading inside it. Transfers stay outside the interval.
- **Programs**: two **hand-written C** files against the CUDA runtime's C interface (`cuda_runtime_api.h`; ADR-0194 decision 8), a verification program and a timing driver with the command lines and report forms of `hilclaw/harness/verification_program.c` and `timing_driver.c` (ADR-0017, ADR-0009), so the Python halves — inputs, reference, comparison, the timing report — are reused unchanged. *Why not generated* (ADR-0193 decision 6): one contract; the generator emits host-memory programs, and teaching it device memory now is hardening beyond the demonstration (D31 ②). A second CUDA contract brings that change.

### 5. Where a CUDA kernel's source sits in a run — asked

- **Today's frame** admits `.c` and `.h` names below an attempt's `output/` and compiles the `.c` files (ADR-0055 N1, N2, R3); given code is one C file placed as `given.c` (ADR-0200 decision 2); an `instance.json` without `candidate_kind` is a C kernel run ([ADR-0198](ADR-0198-od32-compile-settings-candidate-kind.md) decision 4; HQ-0089 ④). A CUDA kernel fits none of these.
- **Weighed.** (i) **A `.cu` attempt file at `cuda_gpu`**: the honest record — the name says the language and `nvcc` compiles it as CUDA by its suffix; it changes ADR-0055's admitted names and compiled set and needs a reading of the run's candidate kind, so it is a data-plane frame change (D23) and the owner's. (ii) **Inside today's frame**: the kernel as `kernel.c` with `-x cu` among the target's flags. No frame changes, but a file named `.c` and a run read as a C kernel hold CUDA C++, and `-x cu` applies to every input of the call, so the C harness would also be compiled as CUDA C++. ADR-0055 L2 ("an admitted name is a name, not a kind") allows the bytes and not the misreading of every reader of the data. (iii) **No run record**: stop the demonstration at the backend's build, check and timing on a test's own directory, which narrows PLAN P3-16 ("기록까지") and is the owner's too.
- **Choice: (i), asked as an HQ** (T-0572 `Result`, recommended option (a)). **The same HQ asks the CUDA C++ given-code bundle** (one CUDA C++ file placed as `given.cu`), the other-language bundle HQ-0096's reading leaves to the task that needs it: with `coder_loop` false the given-code command is the only way into a `cuda_gpu` run, so slice 6 needs both. (ii) is refused for the misreading; (iii) is offered as an option, not chosen. Until the answer, slices 2 to 5 proceed: none of them records a CUDA kernel in a run. A test places the kernel; the coder's path stays closed (`coder_loop` false; HQ-0088 ① (c) is not asked again).

### 6. `device_unavailable` (HQ-0097 (a) (i))

- **The kind**: `device_unavailable` joins `hilclaw.check_failure.BACKEND_KINDS` and `hilclaw.run_failure.BACKEND_KINDS` and `hilclaw.vendor_adapter.KINDS`; its message is a fixed text of the probe that shows no output or path (ADR-0060 decision 5). **This record is the record that names it** for both contracts (ADR-0047 decision 5; ADR-0068 decision 5). The two sets are not made open lists (HQ-0097, integrator's reading).
- **The probe**: `hilclaw.cuda_adapter.check_device`, the device query of `device_probe` read by `device_outcome`. **A usable device** goes on. **No device** (`ABSENT` with `NO_DEVICE`: statuses 6, 9 and 12), **the query program absent** (`ABSENT`), and **a query that cannot be read** (`UNREADABLE`: a time limit, another status, no device line) are the tool failure `device_unavailable` with the probe's message. *Why the unreadable query too*: the operation cannot confirm a usable device, and nothing about the attempt is established (HQ-0097's reason). In a container run (slice 5) the query runs in a probe container of the same image and device options, so a container that cannot be given the GPU (status 125) is also found before the attempt's process.
- **When**: each `correctness.check`, `sim.run` and `board.run` operation of `cuda_gpu` runs it first, before the build and before the attempt's process (ADR-0194 decision 3). **No status or output of the attempt's process is read as it** (ADR-0168 decision 3, ADR-0110 decision 3). **A device lost after the probe went on is a run failure**: broken, `exit_status` (ADR-0194 decision 3).
- **Class (i) of ADR-0110 decision 2**: the probe ends before the verification executable is started, so a `device_unavailable` end line counts neither for nor against the attempt; a later check after the device returns can verify it. `hilclaw.check_standing.UNSTARTED_KINDS` holds it.
- **The orchestrator's handling — the existing tool-failure rules, no new rule**: the end line's `failure` holds the kind and message as raised (ADR-0047 decision 4, ADR-0068 decision 4); the round's agents report "a failure kind" and round 0 goes to its closing steps (`orchestration/round-manager.md` steps 3 to 5; ADR-0185 decision 2; ADR-0142 decision 6); the given-code command tells it as `check_failed` or `board_run_failed` ([ADR-0202](ADR-0202-od33-given-attempt-in-feedback.md) decision 2). No retry rule is added (OD-17). **No line of `orchestration/round-manager.md` or of an agent file names a backend kind, so none is changed.**

### 7. The runtime's container and the GPU (OD-33 ⑨'s rest; OD-14 ①)

- **Means**: Docker's `--gpus all` with the **NVIDIA Container Toolkit**, on every build and process container of `cuda_gpu` (the build because of `-arch=native`, decision 3) and on the probe container (decision 6). The CUDA on WSL User Guide says that with the toolkit "only `--gpus all` is supported" on WSL 2.
- **ADR-0144 Q2 is amended for `cuda_gpu`'s containers only.** "The build directory is the only host path" becomes: the build directory is the only host path the operation chooses and the only one writable; `--gpus all`, an option the operation passes, makes the toolkit add the GPU's device nodes (`/dev/nvidia*` on Linux, `/dev/dxg` on WSL 2), read-only mounts of the driver's user-space libraries and utilities (on WSL 2 below `/usr/lib/wsl`), and the toolkit's hooks. No checkout path, no runtime socket and nothing else of the host is added. The image's own `NVIDIA_VISIBLE_DEVICES` and `NVIDIA_DRIVER_CAPABILITIES` stay the image's.
- **Unchanged from ADR-0144 decision 6**: the build directory as the one bind mount of the operation's choosing, the working directory; `--network none`; `--pull never`; the numeric user and group; `--cap-drop ALL` and `--security-opt no-new-privileges=true`; the entrypoint overridden; one name per build or process; removal at the end and forced removal at the limit; no `--privileged`, no added capability, no runtime socket, no resource bound; no variable handed in by the operation.
- **The isolation reading** (NFR-4; owner 2026-10-15): the kernel is still built and run only inside the container, with no host path but the build directory writable and no network. What it gains is the target device and its driver interface, which is what evaluating a GPU kernel means; it gains no checkout path, socket or network, and no writable host path. **This record reads it as no departure from the owner's principle**; the added attack surface (the host GPU driver through its device node) is listed for the owner in Consequences. A GPU on another machine stays OD-14 and #5 B-2.
- **What this machine lacks**: the NVIDIA Container Toolkit. **Source**: NVIDIA's apt repository `https://nvidia.github.io/libnvidia-container/stable/deb/` as the [installation guide](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html) gives it (read 2026-11-14; version `1.20.1-1` there), then `nvidia-ctk runtime configure --runtime=docker` and a daemon restart. It is an NVIDIA tool from NVIDIA's official site, pre-allowed for the driver (D29); slice 5 installs it on this machine, configures Docker with it and restarts the daemon, and records the paths in its `Result`. **On a user's machine the runtime installs nothing and changes no Docker configuration**: a missing toolkit is a fact the environment check reports, and installing it or changing the daemon's configuration is the user's permission (FR-4, NFR-4; owner 2026-10-15, item 2); until then every `cuda_gpu` operation answers `device_unavailable` (decision 6).
- **The image**: `nvidia/cuda:13.1.2-devel-ubuntu22.04` from NVIDIA's repository on Docker Hub (`https://hub.docker.com/r/nvidia/cuda`), digest `sha256:d8332c008e2ef270e82d286e5245e771f839645683075bba21ad9e4fa59dbcbb` as the registry listed it on 2026-11-14 (not pulled): the CUDA 13.1 of the WSL host, `nvcc`, `gcc` and Ubuntu 22.04. Slice 5 pulls it by digest and tags it `cuda:13.1.2` ([ADR-0195](ADR-0195-p3-14-storage-cleanup-and-cas-gc.md) decision 10). The runtime names its image by an environment variable, as `HILCLAW_STANDIN_IMAGE` (ADR-0144 decision 5); **the runtime's acquisition of it stays the user's permission** (NFR-4; HQ-0094 ①).
- **NVIDIA documentation read on 2026-11-14**: the installation guide above; [Specialized Configurations with Docker](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/docker-specialized.html) (`--gpus`, `NVIDIA_VISIBLE_DEVICES`); [Support for Container Device Interface](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/cdi-support.html) (JIT-CDI on WSL 2); [CUDA on WSL User Guide](https://docs.nvidia.com/cuda/wsl-user-guide/index.html) ("only --gpus all is supported", NVML not all queries).

## Consequences

- **A-13 reading.** Slice 1 adds the backend kind `device_unavailable` to the end line's `failure` vocabulary of `correctness.check`, `sim.run` and `board.run`: **a frame change the owner approved** (HQ-0097 (a) (i)). Nothing else here changes a frame: `cuda_gpu` is a value of the name field `accelerator`; `nvcc`, `gcc` and `nvidia_driver` are member names of the open map `toolchain`; `coder_loop` is package source; the `cuda` contract is an entry of the approved open list "커널 계약 표" (DRIVER §3, D23), whose values go into the members that list names. **The frame change this record needs and does not make** is the record of a CUDA kernel in a run (decision 5), asked as an HQ.
- **Answers**: of OD-33 ④, the points of `cuda_gpu` in the design (with HQ-0095 ②); of ⑥, `device_unavailable`'s placement and handling; of ⑨ and OD-14 ①, the GPU in the runtime's container on a machine with an NVIDIA GPU and the toolkit; of OD-4, `cuda_gpu`'s hw key values; of OD-26, `cuda_gpu`'s table entry and where its `toolchain` members are read (ADR-0194 decision 7 left them to the target's task). OD-33, OD-14, OD-4 and OD-26 stay open.
- **Readings for the owner to check**, listed in the #5 notice: ADR-0144 Q2 amended for `cuda_gpu` (decision 7), and the toolkit install with Docker's configuration and a daemon restart on this machine (slice 5); `coder_loop` as the table's way to open given code only (decision 3); `cuda` as a new contract language with device pointers (decision 4); an unreadable device query as `device_unavailable` and the kind in class (i) (decision 6); `--gpus all` on build, process and probe containers read as no departure from the isolation principle, with the added surface of the host GPU driver (decision 7).
- **Runtime acceptance items** (D22), after slice 5 lands, on each C-7 machine kind with an NVIDIA GPU and Docker: that `--gpus all` gives the process container the GPU while no checkout path is visible, the driver mounts are read-only and the other ADR-0144 properties hold; that a container that cannot be given the GPU makes the probe container end with 125 and the operation answer `device_unavailable` before any attempt process; that on Docker Desktop (macOS has no NVIDIA GPU, so `cuda_gpu` there is always `device_unavailable`) and on native Linux the same reading holds. T-0572's `Result` hands them to `PROCESS/RuntimeAcceptance.md`.
- **Less exact, not edited**: ADR-0194 decision 3 ("Until V6 (a) is answered, the probe's finding is an outcome of interpret that no operation of the default table returns") — answered; ADR-0200 decision 5's list for a vendor target — `device_unavailable` is now landed; ADR-0144 decision 2, Q2 ("one host path") — amended for `cuda_gpu`'s containers by decision 7. ADR-0194 decision 8's "the rest of ⑨, for the target task's record" gains a pointer to this record.
- **UsageCases and StandardScenarios**: no use case step changes; S12's notes name OD-33 ⑥ and ⑨, both still open in part. Verdict unchanged, no gap.
