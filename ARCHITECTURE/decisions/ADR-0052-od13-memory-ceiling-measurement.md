## Decision

Whose a sentence is: **the owner's** where O2 or HQ-0005 is named; **cited** where another source is named (each citation was checked against the text of its source on 2026-10-13); **this record's own** otherwise.

### 1. Scope and terms

- **The first case in the local configuration** of ADR-0038 decision 1: `cpu_standin`, kind `gemm`, fp32, a C kernel, built and run on the machine of the tool function. Nothing is said of a simulator, a board, a remote machine, another accelerator or the foreseen non-native configuration (OD-18 sub-question ⑫).
- **The figure**: the one number of bytes of decision 2. **A verdict**: one of *within*, *over* and *not judged* (decision 4). The terms of ADR-0009 (driver program, timing run, Python side, completed, broken) and of ADR-0038 (execution point, sim point, board point, the run tools) are used unchanged.

### 2. Limits

Each limit stands before the decisions it limits and is referred to there by its number.

- **L1 — A record, not code; nothing was run.** What an operating system reports is taken from its documentation alone. Whether a machine of C-7 reports the figure in the documented unit, and how large the parts of L2 are, is not known (Consequences).
- **L2 — The figure is a property of a whole process, and the kernel is not the whole process.** It contains what is not the kernel's: the driver program, the C library, the sample array of the driver, and whatever the loader maps. On Linux it has in addition a floor that is not of the run at all: Linux folds the peak of the address space a process had before the program was loaded into the process's maximum (cited: `fs/exec.c` of the Linux source, `setmax_mm_hiwater_rss(&current->signal->maxrss, old_mm)` in `exec_mm_put_old`; that the address space before the load is of the order of the resident set of the starting Python process is this record's reading and was not observed). **In this direction the figure lies above the memory of the kernel's execution with its operands, so a ceiling is stricter than the owner's words**: a candidate can be called over that the owner's sentence would call within, by the harness's share.
- **L3 — The figure also leaves out what the kernel's execution uses.** A resident set counts pages in physical memory (this record's reading of the term, which the cited pages use and do not define): pages the process had and the system moved to swap at the moment of the peak are not in it, and memory the kernel's code holds in another process is never added to it. On Linux the usage returned with a wait is that of the process together with the descendants it waited for, and their peak enters as a maximum, not as a sum (cited: Linux source, `kernel/exit.c`, `getrusage(p, RUSAGE_BOTH, wo->wo_rusage)`, and `kernel/sys.c`, where that case starts from `sig->cmaxrss` and then takes the larger of it and `sig->maxrss`); for a descendant that was not waited for, and for macOS, no documentation was found (L1). **In this direction a ceiling is looser than the owner's words.** Memory reserved and never touched is not counted either (the same reading); whether the owner's "uses" includes it this record does not read — if it does, a ceiling is looser in this respect too.
- **L4 — The kernel shares the process and can evade the figure.** It can spread its memory over processes of its own (L3), hold its memory only in a run that is not measured, or tell a timing run from another run (cited: ADR-0009 decision 10, "The kernel shares the process with the driver"; ADR-0017 decision 10). Because the figure is read by the operating system and reaches the Python side through no channel the kernel writes to (decision 4), a kernel cannot state it; it can only keep memory out of it. It needs no other process for that: on Linux a process can write the value that will "Reset the peak resident set size ("high water mark") to the process's current resident set size value" to its own `/proc/pid/clear_refs` (cited: Linux proc_pid_clear_refs(5), value 5, since Linux 4.0). No defence is adopted or rejected (rest of OD-16).
- **L5 — One figure is one run.** It depends on the machine, the page size, the allocator, the thread count, the build flags and the run-time library, none of which this record fixes; on Linux on the state of the process that starts the run (the floor of L2, which is not of the run and may differ from one start to the next; not observed); and on the number of kernel calls of the run (one untimed and 5 to `n_max` timed, ADR-0009), which matters for a kernel that keeps memory between calls. It moves in whole pages, while a `bound` is in bytes (cited for Linux: `kernel/sys.c`, `r->ru_maxrss = maxrss * (PAGE_SIZE / 1024)`). It says nothing of another run of the same attempt.
- **L6 — Two points on one machine.** "Two points on one machine exercise no difference between a simulator and a board" (cited: ADR-0038 decision 8). A candidate within at one point and over at the other differs by what L5 lists, the floor of L2 among it, and by nothing that tells a simulator from a board.
- **L7 — Platforms.** The premise is the one of ADR-0009 decision 3 (a POSIX system with clang; Linux, macOS, WSL). On native Windows and on any system this record names no rule for, there is no figure (decision 4). Nothing holds for another backend, kind, dtype or kernel language.
- **L8 — A verdict is believed, and the caller acts on it.** Nothing here makes a caller ask for a verdict or obey one; that is FR-1, PLAN P2-1 and the gates (OD-3, OD-18), as for the point a call states (cited: ADR-0038 decision 8).
- **L9 — No instance can state a ceiling until the path of decision 7 exists.** ADR-0050 L6 lasts until then.
- **L10 — The condition of decision 7 ties the instance's ceiling to a verdict, not the spec's.** Whether a spec and its instance agree is checked by nothing (ADR-0050 L2).

### 3. The quantity

- **Owner** (O2): the memory ceiling is "an upper bound, in bytes, on the memory the kernel's execution uses at the execution point that measures it, operands included."
- **The figure is the maximum resident set size of the process of one timing run of the attempt, over the whole life of that process, as the operating system reports it for the ended process, in bytes.** One timing run is one process that holds one kernel (cited: ADR-0009 decision 2, "The kernel runs in a process of its own").
- **What it contains** (from the source of the driver and ADR-0009 decision 5; subject to L2 and L3): the three operand arrays `a`, `b` and `c`, which the driver obtains with "three separate `malloc` calls" — the driver fills `a` and `b`, and `c` is resident because a kernel must write every element of it (cited: ADR-0008 decision 6); what the kernel allocates and touches itself, including state it keeps between calls ("a started thread pool, scratch memory of its own" — cited: ADR-0008 decision 6); the touched stacks of its threads; the pages in use of a run-time library it brings. So "operands included" (owner) holds by construction, and no operand is exempted.
- **What it contains that is not the kernel's**: L2. **What it does not contain**: L3. The figure is therefore a stand-in, which is what the owner's sentence asks a record to choose ("Which measurement of the first case stands for that memory"), and not the quantity itself.
- **It is one number.** No baseline is subtracted and no share of the harness is estimated and removed: an estimate would be a value no source gives, and removing too much would let a candidate over its ceiling count as within.

### 4. How it is taken

- **In the timing run of ADR-0009, as a by-product; no run of its own and no change of that run.** The timing run is the execution whose intervals are the quantity of the objective (cited: ADR-0050 decision 3), so the memory that is judged and the time that is compared come from the same process. Beside the operands the driver holds one array the verification program does not, its samples; that is part of the harness's share (L2). The timing run's decisions are not reopened: the driver program gets no new argument, line or call.
- **The Python side reads it, not the C program.** It is the resource usage the operating system returns with the wait for the ended child process: `wait4`, whose `rusage` "will be filled with accounting information about the child" (cited: Linux wait4(2)), reached from Python as `os.wait4`, which returns "the child’s process id, exit status indication, and resource usage information" and is available on Unix (cited: Python 3.11 library reference, `os`; the project requires Python 3.11 or later). The member is `ru_maxrss`. **This is no new external dependency**: it is the Python standard library over an interface of the platforms. It is not POSIX — POSIX requires of `struct rusage` only `ru_utime` and `ru_stime` (cited: POSIX.1-2017, `<sys/resource.h>`), and `wait4` is "nonstandard" (cited: Linux wait4(2)) — which is why the rule of units below is per platform and closed.
- **The unit, and the rule that converts it to bytes.** On Linux `ru_maxrss` is "the maximum resident set size used (in KiB)" (cited: Linux getrusage(2)): the figure is the value times 1024. On macOS it is "the maximum resident set size utilized (in bytes)" (cited: getrusage(2) of the XNU source, `bsd/man/man2/getrusage.2`; an older copy of that page in Apple's archive says "in kilobytes", so this unit is an assumption of the record until observed — L1; if a machine reported kilobytes, the figure would be 1024 times too small and a candidate over its ceiling would be called within, nothing in this record makes that check come first — it is item (i) of the runtime acceptance items, closed by the owner by hand or by the runtime self-check, and it must be confirmed before a verdict on macOS is relied on): the figure is the value. WSL is taken by the Linux rule, on the assumption of this record that it presents the Linux interface; no documentation of what WSL 1 reports was found (L1). **On any other platform there is no rule and therefore no figure.** Which platform the Python side runs on it reads from the interpreter (`sys.platform`); how is the code task's.
- **A reported value that is not a positive integer yields no figure.** A process that holds operands has a resident set; a zero would be an operating system that does not report the member, not a kernel that uses no memory.
- **When, and how often.** Once, after the process has ended; the peak covers the preparation of the operands, the untimed call and every repeat. It is not read during the run and not per repeat.
- **Nothing of ADR-0007 applies to it.** That policy is about "the sequence of samples" of a measured quantity (cited: its decision 1); the figure is not a sample, has no repeats, no stopping rule and no summary statistic, and the difference rule of its decision 7 is not applied to it: a constraint is not an objective, and this record compares no two candidates on memory (its own reading; the owner's sentence in O2 is about a candidate over its ceiling, which "is not compared on the objectives"). Whether the figure of a run is kept in a result file is part of sub-question ⑩.
- **A run that is not completed yields no figure.** *Completed* is the word of ADR-0009 decision 8 (no timeout, exit status 0, a report of the fixed form, the replay agrees), whichever state the run reports (`converged` or `not_converged`: the memory of an execution does not depend on the spread of its timings; what a "not converged" measurement is worth for the objective stays with OD-13). A broken run yields no figure even where the operating system reported a usage for it: the usage of a process that crashed or was killed is of an execution that did not do the work.
- **The cumulative figure for all children is not used.** `getrusage(RUSAGE_CHILDREN)` gives "the resident set size of the largest child" among all children waited for (cited: Linux getrusage(2)), the compiler among them, and cannot be tied to one run.
- **How `hilclaw/local_run.py` hands the usage of the process it waited for to the Python side of the harness is the code task's.** It stays an interface inside the package; on a platform without `wait4` the runner has nothing to hand on. An observation for that task: the runner waits through `subprocess.run` today, which returns no usage, so the slice changes how `local_run.run` waits for its process and ends it at the time limit.

### 5. The verdict

- **Owner** (O2): "an upper bound, in bytes"; "A candidate over its ceiling is infeasible and is not compared on the objectives".
- **A verdict is of one timing run and one `bound`, and has exactly three outcomes**: **within** — the run yielded a figure and the figure is less than or equal to `bound`; **over** — it yielded a figure and the figure is greater than `bound`; **not judged** — it yielded no figure (a broken run, a platform without a rule, a value that is no positive integer). That equality is within is this record's reading of "upper bound".
- **"Not judged" is never "within".** Cited: ADR-0050 decision 5, "the absence of a verdict is never \"within the ceiling\"". No part of what follows this record may map *not judged*, an absent verdict or an absent figure to *within*, and none may leave the three outcomes as two.
- **No margin, no tolerance, no rounding in the candidate's favour, no statistic over runs.** The comparison is of two integers. This record gives no rule by which the verdict of a second run replaces an *over* of a first, and none may be read into it. That the figure errs to the strict side by L2 is stated and not corrected.
- **The comparison is made on the Python side**, outside the kernel's process, which is handed neither the `bound` nor the figure.
- **What follows a verdict is not written here.** *Over* is the owner's "infeasible" (O2). What follows *not judged* is not written here either (OD-10, OD-14; PLAN P2-1); the principle above binds it.

### 6. The execution points

- **Owner** (O2): the memory is the one used "at the execution point that measures it", and what the round loop does with a candidate over its ceiling "is what FR-1 does with a failed correctness check at the same execution point." **Owner** (HQ-0005 (1)): at `cpu_standin` "the two carry out the same local run; nothing but the execution point distinguishes the two operations."
- **In the local configuration the ceiling is judged at each execution point at which a timing run of the attempt is carried out, with the figure of that run** — which, since the two operations "carry out the same local run" (owner), is at both points or at neither; that consequence is this record's reading of the owner's sentence. It is not judged once for both: a verdict belongs to the point whose run gave the figure, as a check belongs to the point its call states (cited: ADR-0038 decision 4).
- **Why both.** The owner's sentence ties the ceiling to "the execution point that measures it", and in the local configuration nothing makes one point measure and the other not. A ceiling judged at the sim point alone would leave a board-point run whose figure is over the bound with no verdict; judged at the board point alone it would spend the board step on a candidate the sim-point run had already shown to be over (C-4). The owner made the same choice for correctness (HQ-0005 (3): "two checks per attempt, one as the sim-point check and one as the board-point check, also where both are the same local run"). It costs no further run (decision 4). L6 applies.
- **Which case of FR-1 — by citation only.** For a candidate *over* at the sim point the owner's sentence selects what FR-1 does with a failed check there: "⑴ **sim 실패 → 실패 리포트를 첨부해 코드 생성 단계로 복귀**". For a candidate *over* at the board point it selects what FR-1 does with a failed check there: "⑵ **board 실패 → 해당 후보 탈락**", and FR-1 ⑶ speaks of "sim 통과·board 실패". **This record does not read further**: whether a candidate within at the sim point and over at the board point is a case of ⑶, what a failure report of a ceiling holds, the repair bound (OD-19), the promotion (OD-15, OD-29) and every step of the loop are FR-1's and PLAN P2-1's. No procedure of the round loop is written here.

### 7. What carries the figure and the verdict, and from when `memory_ceiling` is admitted

- **Inside the harness**: for a completed timing run the Python side has the figure beside the intervals; for any other run it has none. This is an interface between parts of the package of one source commit, as the report of ADR-0009 decision 8 is, and "is not a file or a field of the data plane" (cited, same decision). The driver's report does not change.
- **Which call at an execution point is the one whose execution is measured: no landed record says.** It is the call that carries out a timing run of the attempt at that point. `correctness.check` is defined in the terms of the verification run (cited: [ADR-0021](ADR-0021-od18-correctness-check-split.md) decision 1), which "is not the timing run" (cited: ADR-0017 decision 1). For the run tools, what the local run is "is the contract of the run tools and is not decided here" (cited: ADR-0038 decision 2). This record does not decide it either, and **names no member** of a request, of a result, of `instance.json`, of `STATE.json`, of an event or of a result file. What is left is registered as **sub-question ⑩ of OD-13** (Boundaries); the contracts of the run tools (PLAN P1-1) and the instance record (PLAN P1-8) close it.
- **One requirement binds those contracts**: a call that carries out a timing run about a run whose instance states a memory ceiling returns the verdict of decision 5 for that point to its caller, with *not judged* as an outcome of its own, for the `bound` the run recorded (condition (c) below).
- **`memory_ceiling` is admitted — check 4 of ADR-0050 may accept the value in `hilclaw/spec.py` — only when all of the following are on `main`**, and not at a date: (a) the harness slice that takes the figure as decision 4 says; (b) the verdict of decision 5 as code; (c) a record and its code by which a call that carries out a timing run at an execution point returns the verdict to its caller, at both points, **with the `bound` taken from what the run itself has recorded of its instance and not from a value the caller of that call chooses** — which includes the record and the code of whatever states a constraint for a run (no record gives `instance.json` such a member: ADR-0050 L2; PLAN P1-8). A `bound` that a caller hands in a request would not meet (c): unlike the execution point, a bound is something a caller could use to make an attempt pass (the distinction is the one of ADR-0038 decision 4, cited). This is a property the answer to sub-question ⑩ must have; it names no member. **The harness slice alone is not enough.** With (a) and (b) only, a valid spec could state a ceiling that is judged only if some caller chooses to hand a bound to a function: nothing would tie the stated bound to a verdict (cited: ADR-0050 L2, "Nothing ties the value to the instance"), and keeping the ceiling from counting as met would again rest on a rule of the round loop, which is what ADR-0050 decision 5 declined. ADR-0050's remark that "the harness code that follows it does" judge is read as naming what is necessary, not what suffices. The round loop itself (PLAN P2-1) is not part of the condition: a verdict that reaches the caller leaves no path to *within* but a caller that disobeys O2 and FR-1 (L8).
- **What the condition does not cover** (L10): that a spec carries the constraints its instance states. "Nothing ties the value to the instance" (cited: ADR-0050 L2) stays true until a record of what writes a spec says otherwise (PLAN P1-8; OD-23); the verdict of (c) goes by what the run recorded, so a ceiling that stands in a spec and not in the run's record is judged by nothing. The agreement of a spec with its instance is not made a fourth condition: the validator checks the form of one document (cited: ADR-0050 L1), the same gap holds for the objective a spec states, and closing it is the record of what writes a spec; by the principle of ADR-0050 decision 5 it may not be treated as met by anything either, which is a requirement on what is written later and not a description of code.
- **The admission raises no version**: it is the case "a new value of the `type` of an objective entry or of a constraint entry is admitted" (cited: ADR-0050 decision 6 (a), which marks the rule as the owner's). This record admits nothing itself.
- **The cost** (L9): the constraint type the owner's vocabulary has stays unusable until the run tools have a contract, which is later than the harness slice; and check 4 cannot be cut as the next code task.

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 3 | A figure the driver program reads about itself (`getrusage(RUSAGE_SELF)`) and writes to its report | The same number with a worse path: it passes through the process the kernel shares and a channel the kernel can write to (ADR-0009 decision 10), and it reopens ADR-0009 decision 8. |
| 3 | An account of allocations only (the driver's own `malloc` calls, or an interposed allocator) | Sees no stack, no thread, no mapping the kernel makes itself and no run-time library; a kernel is not bound to any allocator. It would be looser than the owner's words in a way a kernel chooses. |
| 3 | A figure computed from the operand sizes alone, 4·(m·k + k·n + m·n) | Measures nothing of the kernel: every candidate of one shape would have one figure. |
| 3 | The figure minus a baseline (an empty kernel, or the floor of L2) | A second run and a value no source gives; an over-estimate of the baseline lets a candidate over its ceiling pass. |
| 4 | The verification run of ADR-0017 | Holds the same operands, but is not the execution the objective is taken from ("The verified executable is not the timed one", its decision 10), makes `draws` calls instead of the calls that are timed, and would tie the ceiling to `correctness.check`. |
| 4 | A run of its own for memory | A third build or run per point, and the memory judged would be of an execution that is neither timed nor verified. |
| 4 | Sampling the resident set during the run | A second process or thread beside a timed interval, and a peak between two samples is missed. |
| 4 | A figure also for a broken run | The usage of an execution that did not complete; an *over* from it would be right only by accident, and a *within* from it would be wrong. |
| 5 | A margin for the harness's share, or the lowest figure of several runs | Each lets a candidate over its ceiling count as within. |
| 6 | The board point only (the final verdict) | A candidate known to be over is promoted and spends the board step; see decision 6. |
| 6 | The sim point only (the early filter) | A board-point figure over the bound would have no verdict. |
| 7 | Admit `memory_ceiling` once the harness slice has landed | See decision 7: nothing would tie a stated bound to a verdict. |
| 7 | Admit it only when the round loop exists | The loop is the caller, bound by O2 and FR-1; waiting for it adds nothing a returned verdict does not give. |
| — | Enforce the ceiling with a resource limit on the process (`setrlimit`) instead of measuring it | A resource limit is a registered proposal of OD-14 that no record has adopted or rejected; ADR-0009 decision 2 took the process "as unprotected as `local_run` says". A limit would also turn *over* into a crash, which a broken run cannot tell from another crash. |

## Consequences

- **Code slices for the planner** (no function, member name or module layout is decided here), in this order. **(1) The harness slice**: `hilclaw/local_run.py` hands on the usage of the process it waited for; the Python side of the timing run (`hilclaw/harness/timing.py`) yields the figure for a completed run; the verdict of decision 5. `hilclaw/harness/timing_driver.c` is not touched.
