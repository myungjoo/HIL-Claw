## Decision

Whose a sentence is: **the owner's** where O1 to O8 is named; **cited** where a fact number, a requirement or a record is named; **this record's own** otherwise.

### 1. Scope and terms

- **The self-check** (the *check*) is "a self-check of the `hilclaw` package that the instance bring-up (P2-1, round 0) runs on the runtime machine" (**owner**, O1); that it is one command of the package is this record's own. **The D16 line: the runtime starts `claude`; the driver that builds the check never does** (cited: D16; the second half is also the **owner's** O4).
- It is **not an FR-10 tool and not in the registry**: a tool is a definition the registry holds, called by an agent through a front with a request (cited: ADR-0015 decisions 1 and 2), whereas the check runs before any agent has a tool, starts a session of its own and spends plan usage; an agent that could call it could spend a session per call. It reaches no backend, the mock included (cited: ADR-0016 decision 5). It is not a hook, not a test of the development driver, not the nightly end-to-end run of D17, and not the owner's check by hand (part b-1 of the answer).
- **Session**: the one `claude -p` process of O3. **Wire copy**: decision 6. **Outcome**: one value of the closed list of decision 6. **Report**: decision 7.

### 2. Limits (each holds for every statement below)

- **L1 — Not code, nothing run.** Every statement about what `claude` does is K1 to K15 or is marked not verified.
- **L2 — A pass is one observation.** It shows one version of Claude Code, one machine, one moment, one model and one way of giving the server (decision 9).
- **L3 — The model's part is not deterministic.** A session in which the model made no call is not a pass and says nothing against the front (decision 6).
- **L4 — The start says nothing of the end.** A command line that is logged in at the bring-up can lose its login during the run (K12; decision 10).
- **L5 — The check spends plan usage** (cited: C-7 ②): one session per bring-up.
- **L6 — The check sees what its environment shows it.** Whoever can replace the `claude` found on the `PATH`, or set the environment of the bring-up, decides what the check sees; a credential in the environment outranks the login (K13). The check authenticates nothing and defends against neither.
- **L7 — "Logged in" is the command line's own word.** Step one passes for any `authMethod` other than `none`, an API key included, although C-7 ② excludes API cost; what an instance does about that belongs to the credential form the **owner** left open (O8) and is registered (sub-question ⑯ (다)).

### 3. Step one — the login

- **The call** (**owner**, O2): `claude auth status`. That it is passed no further option and is started as a child process with a time limit is this record's own (the value is the code task's).
- **How the answer is read** (own): the exit status carries it (K1), and the output is read only to confirm it. **Logged in**: exit status 0 and an output that is one JSON object whose `authMethod` is a string other than `none`. **Nothing is logged in**: exit status 1. **Everything else** — exit status 0 with another output, any other exit status, the time limit — is the outcome `login_unreadable`, and no `claude` that can be started is `no_claude`: **neither is ever read as logged in, and after either no session is started**. An exit status 1 that has another cause is read as nothing logged in all the same: the instruction is then wrong, and still nothing reads as logged in. The member `loggedIn` (K2) is not used: no page carries it.
- **Nothing is logged in** (**owner**, O2): the check "stops with the instruction to run `claude auth login`" — no session is started, and the report carries that instruction as a fixed text of the package.
- **The check never runs `claude auth login` itself** (own): the sign-in is the user's act in a browser (K3), it writes the user's credentials, and an unattended bring-up has nobody to complete it.
- **The report repeats nothing of the status output except the value of `authMethod`, and that only when it is one of the six values of K1** (otherwise the word `other`). The output may name an account, an organisation, an e-mail address or a directory under the user's name (`configDirectory`), and where the report is kept is not decided (O7): what is not in it cannot leak from wherever it is later stored.

### 4. Step two — the session

**The owner's** (O3): one throwaway `claude -p`; `--mcp-config` naming the package's own MCP front; `--strict-mcp-config`; a narrow permission mode; never a bypass flag. **This record's own**, each a provisional choice:

| Choice | Why | Weighed against |
|---|---|---|
| `--permission-mode dontAsk`, passed explicitly | It denies whatever would prompt and never waits for input (K5), so the session cannot hang on a question; an explicit mode overrides a `defaultMode` of the settings files (K5). | `default` (may wait); `plan`. Never `bypassPermissions`, `--dangerously-skip-permissions` or `--allow-dangerously-skip-permissions` (**owner**: "never with a bypass flag"). |
| `--allowedTools` naming exactly the two MCP names of decision 5 | In `dontAsk` only pre-approved calls run (K5). That a call of an MCP tool outside the list is denied is this record's reading of K5, not verified. | The server as a whole (`mcp__hilclaw`): wider than needed. |
| `--tools ""` | No built-in tool: the session can read, write and run nothing on the machine (K6). | The default set, narrowed by the permission mode alone. |
| `--no-session-persistence` | Nothing of a throwaway session stays on the disk (K7). | — |
| `--setting-sources project`, with the working directory of the next row | With no project there, no settings file of the user or of a checkout is read — this record's reading of K7 — so no hook, no allow rule and no `env` block of theirs reaches the session. Not verified: that the login is still read, and what managed settings add (K7). | The default (all sources): the user's hooks and allow rules would act on the session. |
| Working directory: a directory created for the check, outside both checkouts, removed after it | A `-p` session takes hooks, servers and instructions from its project (K10); the check is about the front, not about a checkout. It also holds the configuration file and the wire copy. ADR-0049 decision 3 puts a coder's scratch outside both checkouts for like reasons; the **owner's** sentence on cleaning up (HQ-0010) speaks of coder calls and is an analogy only. | A checkout as the working directory. |
| `--output-format stream-json` (with `--verbose`, as every example of the page has it) | The `system/init` event is where the session says which servers connected and which tools it has (K8). | `json`, `text`: one final answer, no statement about the server. |
| Neither `--restricted` nor `--safe-mode` | Both are on the page and overlap with the `--tools` and `--setting-sources` rows: `--restricted` "loads only managed settings and `--settings`, refuses `bypassPermissions`" and removes the built-in tools that run commands ("Requires Claude Code v2.1.248 or later"); under `--safe-mode` "MCP servers … do not load" while "Authentication, model selection, built-in tools, and permissions work normally". Not verified: whether a server passed by `--mcp-config` connects under either, and whether the login is read under `--restricted`. `--safe-mode` is not taken for that reason; `--restricted` is the first candidate if the rows above prove too weak, and taking it now would rest the check on a flag whose effect on the server no page states. | Those two rows, whose options the owner's check by hand (b-1) also names. |
| No `--model`, no `--bare`, no `--max-turns` | The default model is what a run would meet, and naming one is not this record's; bare mode reads no login (K11); the number of turns a session needs is not known (K14). | — |
| A time limit bounds the session; **exactly one session per check, no retry** | A hung session must not hold the bring-up; a retry spends a second session (L5), and whether to try again is the caller's. The value is the code task's. | A bounded retry inside the check. |

- **The configuration file** is written by the check into that directory and removed with it. It holds one stdio server entry (`command`, `args`, `env` — cited: ADR-0010 F1) under the name `hilclaw`. **That entry holds only values the check itself made** — the two tokens, the place of the wire copy, what the server process needs to find the package — **and never a copy of the environment of the bring-up**, which may hold a credential (K13, L6): no credential is written to the disk by the check. **The directory is removed whatever the outcome**, the time limit and a fault of the check itself included; only a check whose process is killed leaves it behind, with the configuration file, the wire copy and the two tokens in them — nothing of further use and no credential. **It is no registration for a run**: giving the server by `--mcp-config` to one throwaway session is a use of one of the ways ADR-0010 lists, not the choice of one (decision 9) — the reading T-0106's pre-check consultation reached, confirmed here.
- **The prompt** asks the model to call each of the two tools once and to repeat in its reply what each returned; its text is the code task's.
- **The environment** of the session is the one the check was started in; the check adds no credential and removes none (L6). Tool search is left at its default (K14): setting `ENABLE_TOOL_SEARCH=false` would show a session other than the one a run's agents get.

### 5. Which server and which tools

- **The server is the unchanged `hilclaw.mcp_front`** — "the package's own MCP front" (**owner**, O3) — **over a registry that holds only two tools of the check itself**, started by an entry of the package that calls `mcp_front.main` with that registry. No rule of the front is changed.
- **The two tools** (own; names provisional): `selfcheck.token`, which returns a result holding a token, and `selfcheck.fail`, which raises a tool failure whose message holds a second token. The session sees them as `mcp__hilclaw__selfcheck_token` and `mcp__hilclaw__selfcheck_fail` (cited: ADR-0010 decision 4; neither registry name contains a `_`). The two tokens are random values the check creates for one session and hands to the server entry; **they are never in the prompt**, so a reply that holds them shows that the result and the failure reached the model — as far as the model has no other way to them (decision 6).
- **These tools never appear in the registry of a run**: `default_registry` is not edited, and a tool is added there "in the source, and in no other way" (cited: `hilclaw/tools.py`).
- **Weighed.** (a) *The registry of a run with its real tools*: today that is `blob.push` and `blob.fetch`; a call that returns a result would write into the blob store or depend on its content, the check would need a data root and a run, and it would write a data-plane file (against O7). (c) *Both*: the cost of (a) plus a wider session. (b) is chosen. **What (b) leaves unshown**: how the description and the input schema of any real tool are shown to the model, a request with real arguments, a result of real size, and the data root (decision 9).

### 6. What is observed, where it is read, and the outcomes

**Three sides.** *The server side*: the entry of decision 5 gives `mcp_front.main` streams that pass every line through unchanged and copy it, with its direction, to a file in the check's directory — the **wire copy**. The front is not changed; `main` takes its streams as arguments (cited: `hilclaw/mcp_front.py`). *The session side*: the events on the session's standard output (K8). *The model side*: the text the model wrote in its reply — the final response text of the `result` message (K8) — and no other part of the session's output.

| What the owner lists (O3) | Read from |
|---|---|
| `server/discover` | The wire copy: whether that request came before `initialize`, the revision it names, and the error the front answered (K15: -32601). Its absence is not a fault. |
| The `initialize` revisions | The wire copy: the revision asked for and the one answered. |
| `tools/list` | The wire copy: the request and that the answer listed both tools. |
| The tool listing | The session side: the `mcp_servers` and `mcp_server_errors` members and the tool names of the `system/init` event (K8). |
| One call | The wire copy (a `tools/call` of `selfcheck_token`, answered with `isError` false) and the model side (the first token in the reply). |
| One tool failure | The wire copy (a `tools/call` of `selfcheck_fail`, answered with `isError` true) and the model side (the second token in the reply). |

| `no_call` | The session ended by itself with exit status 0, its `result` message and a wire copy holding the `initialize` request were read and the `system/init` event shows `hilclaw` as `connected`, but something `passed` needs of the tool names, the calls or the tokens is missing: the tool names were not in that event, the model did not call, or it did not repeat what it was given. The name is provisional and says the commonest case; the report says which. | Which names, calls and tokens were seen. It says nothing against the front (L3). |
| `session_failed` | **Every other case**: the session could not be started, ended with a non-zero exit status or by the time limit, wrote no `system/init` event or an output the check cannot read, left no readable wire copy or one without an `initialize` request (the server process did not start, or did not start in time — K4), showed the server with a `status` word that is neither `connected` nor of the list of `front_refused` (b) — `pending` included — or named it in `mcp_server_errors` — a usage limit, the network, an expired login, an option the installed version does not know. | How far the session got (decision 7). It says nothing about the front. |

- **No path reads as passed without the model.** `passed` needs both tokens in the text the model wrote. The tokens are in the server process, in the configuration file and, after a call, in the wire copy; they are not in the prompt, and with `--tools ""` the model has no tool that reads a file (K6). That Claude Code shows the `env` of a server entry to the model is not expected and **not verified** (a runtime acceptance item). **The tokens are looked for in the model's own text only — the final response text of the `result` message, the last line of the stream (K8) — never in an event that carries a tool result, and never in the session's output as a whole**, where they stand whether or not the model read them; which member of that message holds the text is not read from a page (K8) and is a runtime acceptance item. Hence a check that was not carried out, a session that never reached the model and a session in which the model made no call each end in another row.
- **Something the check did not foresee** — a request method beyond `server/discover`, `initialize`, `notifications/initialized`, `ping`, `tools/list` and `tools/call` — does not by itself change the outcome: the front answers a method it does not serve with -32601, as it did the probe of K15, and whether the client goes on shows in the rows above. The report names every such method (decision 7).
- **What follows an outcome.** The **owner** fixed two: `not_logged_in` stops, and `front_refused` fails the bring-up. **What round 0 does after any of the other five — `passed` included — is PLAN P2-1's and is not decided here** (sub-question ⑯ (가)). The check itself only reports.

### 7. The report

- **Where** (**owner**, O7): "its standard output and the instance's log", and "no data-plane file". No record defines the instance's log; this record defines none. The check writes the report to its standard output; how the same report reaches the instance's log — and what that log is — is P2-1's (sub-question ⑯ (나)). **The check writes no data-plane file, no line of `events.ndjson`, and no member of `STATE.json` or `instance.json`**; the files of decision 4 are outside both checkouts and are removed.
- **Form** (own): one JSON object on one line ended by one LF — the form of a process output, as the command-line front writes a result (cited: ADR-0010 decision 4), **not a data-plane schema**. Lines of free text were weighed: a caller would have to parse prose to learn the outcome.
- **Members** (own; their names are the code task's): the outcome; the fixed instruction text when the outcome is `not_logged_in`; the `authMethod` value under the rule of decision 3; the Claude Code version as the client states it in `clientInfo` of its `initialize` request (K15) — absent when no wire copy exists, since the check makes no further call to learn it; the name and release of the operating system and the Python version as the interpreter states them, **without the host name**; the revisions asked for and answered, and what was seen of `server/discover`; the tool names of the `system/init` event that begin with `mcp__hilclaw__`; for each tool, whether its call and its token were seen; every unforeseen method name; how far a failed session got (started, `system/init` read, server started, `result` message read) and its exit status.
- **Strings the client supplied are bounded.** The version of `clientInfo`, a tool name of the `system/init` event and an unforeseen method name come from the `claude` program, which L6 does not trust. Each is put into the report only when it is short and made of letters, digits and the characters `.`, `_` and `-` — for a method name also `/`; otherwise the word `other` stands in its place, as for `authMethod` (the length is the code task's).
- **Built from named members, never copied text.** No line of the status output, of the session's output, of the session's standard error or of the wire copy is copied whole into the report, and the model's reply is not in it: any of them may hold an account name or a path under the user's name. The check does not pass the child's standard error on. The cost: a `session_failed` report says how far the session got and not why; the user repeats the command by hand to read the reason.
- **Exit status** (own): 0 for `passed` and for nothing else; a non-zero value for every other outcome, never 1 or 2 (the interpreter's own, as `hilclaw/__main__.py` avoids them). The values are the code task's.

### 8. The precondition

- **Owner** (O5): "the runtime user's command-line login is a precondition of an instance", derived from C-7 ② and ③. This record's own reading of the derivation: every model call of the runtime is made by a `claude` session of that user.
- **What this record adds**: nothing but where it is stated here (UsageCases UC-1) and that step one is how an instance start observes it. **What it does not say**: which credential form satisfies it for an unattended run, and "whether the command line is updated before the owner's check" (**owner**, O8, open); a minimum version; anything of the development machine (D16).

### 9. The `--mcp-config` way against the way of a run

The check gives the server to one `-p` session by `--mcp-config` (**owner**, O3, O6). How a run gives it to its agents — "a `.mcp.json` at the repository root with the approval of F1", `--mcp-config`, or `mcpServers` of a sub-agent (cited: ADR-0010 Consequences, "Registration") — **stays open**. A pass therefore leaves unshown, at least: the approval of a project-scoped server; an inline `mcpServers` server of a sub-agent; a call made by a sub-agent rather than by the main session; hooks of the project's settings on the tool call; a session inside the container of ADR-0049; a session in bare mode; a later Claude Code version than the one checked; a long call (OD-18 sub-question ③); and what decision 5 lists for the real tools.

### 10. Weighed and not decided

- **(i) A login that expires during a run.** The pages say that Claude Code tries to renew the stored login by itself and that, once it cannot, "each model request fails … until you sign in again" (K12); under `-p` such a session ended with an error result in the one case observed (K9). A coder call or an agent would then fail in that way; the check, which ran at the start, shows nothing of it (L4). The question belongs to recovery (OD-10), to notification (OD-27) and to the round loop (PLAN P2-1), and is registered (sub-question ⑯ (바)). **No rule is made here.**
- **(ii) `--bare` as the default of `-p`.** Re-checked on 2026-10-13: bare mode reads neither the stored login nor `CLAUDE_CODE_OAUTH_TOKEN` (K11), as the **owner** read on 2026-10-12. If the default changed, a `claude -p` started as this record designs it — and every `claude -p` the runtime starts under C-7 ② and ③ (PLAN P2-2) — would have no subscription credential, unless that release also offers a way to leave bare mode; no page read names one (K11). **Said plainly: the check as designed would then not pass.** Step one would still report logged in, the server could still connect (K11), and the session would be expected to end with an authentication error — `session_failed`, which is a true report and not a pass. **This record chooses no option for the runtime** and passes none for bare mode itself; what the runtime does about the announcement is open (sub-question ⑯ (바); with O8, the credential form).

### 11. OD-18 sub-question ①

- ADR-0010 had the sub-question "settled by the first code task of the MCP front". **That route no longer exists**: no driver task starts `claude` (D16). The **owner** replaced it by two routes that are not driver tasks: the owner's check by hand (b-1) and this check at every bring-up (b-2).
- **The sub-question stays open in the register until an observation exists.** This record is a design; a pass of the check is a fact of one run on one machine (L2) and edits no document. The owner's observation, when it is posted, is recorded by the separate document task the owner ordered; the F10 row of ADR-0010 is not edited (**owner**, b-1).

### Walk-through (no step names a file or a value beyond this record)

1. **Not logged in.** `claude auth status` ends with status 1. The check writes a report with the outcome `not_logged_in` and the instruction to run `claude auth login`, and ends with a non-zero status. No session was started and no plan usage was spent.
2. **A pass.** Status 0 and `authMethod` `claude.ai`. The check creates its directory, the two tokens and the configuration file, and starts the session. The wire copy shows the probe answered -32601, `initialize` and `tools/list` answered, and one call of each tool; the `system/init` event shows `hilclaw` connected with both names; the reply holds both tokens. The report says `passed`; the directory is removed; exit status 0.
3. **The model calls nothing.** Connected, no `tools/call` on the wire: `no_call`.
4. **The client drops the server after `initialize`.** The wire copy holds the answered `initialize` and no `tools/list`, the session ends by itself, and the `system/init` event does not name `hilclaw` at all, or names it as `failed`: `front_refused`. Had the event named it with a word the list does not hold, the outcome would be `session_failed`; had the server process never started, the wire copy would hold no `initialize` request: `session_failed` as well.
5. **The usage limit is reached.** The session ends with a non-zero exit status: `session_failed`, unless its evidence also meets a condition of `front_refused`.

## Consequences

- **Code slices for the planner** (code mode; possible once CI runs again; no module, entry or value is named or decided here): the two tools and the server entry with its wire copy; step one; step two with the outcome table; the report. Each is tested against a stub `claude` executable that the tests write (**owner**, O4) — its script, and whether it is a Python or a shell file, are the code task's; the rules of #5 D12 apply and the slice must work on the machines of C-7. A hint, nothing decided: the guard of PR #105, once registered, refuses a shell command that starts `claude` in development sessions, so tests reach their stub through the test runner and not through a command an agent types. How the server process finds the package from a working directory outside the checkout is the code task's.
- **Runtime acceptance items** (D16: facts only a real `claude` on a runtime machine can establish; none was tried, none is required of the development machine, none is closed by a driver task; what the owner already took on in part b-1 — the handshake, the listing, one call and one failure with the T-0106 fixture — is not repeated here). On each kind of machine of C-7: (i) `claude auth status` exits 0 or 1 as K1 says and its output is a JSON object with `authMethod`; (ii) a session started with the options of decision 4 reads the stored login although only the `project` settings source is loaded (K7), and no managed setting changes what the check assumes; (iii) with `--tools ""` and tool search at its default, the model can call an MCP tool named in `--allowedTools` (K14); (iv) in `dontAsk`, a call of a listed MCP tool runs without a prompt (K5); (v) the `system/init` event carries the members decision 6 reads, which words `status` takes for a server that connected, is still connecting, failed or was dropped (`failed` above all), which member of the `result` message holds the final response text apart from any tool result, and that the exit status tells a failed session from one that ended well (K8, K9); (vi) the session ends by itself after the reply and leaves no file outside the check's directory; (vii) the server process started from that directory finds the package; (viii) nothing of the configuration file's server entry — the tokens above all — is shown to the model by Claude Code itself.
- **The README sentence** the owner asked for (O5) is a follow-up; README is not edited here.
- **Sentences of earlier records that are now less exact** (none edited): ADR-0010 decision 3 ("if the first code task of the MCP front finds …"), Consequences ("② the MCP front … which also settles F10") and Boundaries ("① … settled by the first code task of the MCP front"). Each stays true of what it reopens; only the route changed (decision 11).
- **A-13 reading.** Document mode; no code, dependency, settings or schema file changes; **no data-plane file, member or event is defined**. The report is the output of a process.
- **The cost, plainly.** Every bring-up spends one session of plan usage and waits seconds to minutes before a run starts; a `no_call` or a `session_failed` leaves the front neither confirmed nor refused.
