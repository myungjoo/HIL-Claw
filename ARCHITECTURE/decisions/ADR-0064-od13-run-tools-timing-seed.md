## Decision

A sentence is **cited** when a requirement or a record with its decision is named with it; it then says what that source says and adds nothing. Every other sentence is **this record's own** — among them that the seed is drawn and not fixed, who draws it, how often, the property and range taken for it, that no request carries it, its place, the kind and its sharing, the message rule, that it is recorded nowhere, the answer to the relation with the verification inputs, and every weighing. No sentence is the owner's.

### 1. Scope and terms

- **A call of `sim.run` or `board.run` about one attempt of a run of ADR-0061 decision 1, whose identity has no line and which was given none of the answers of ④** (the order of ADR-0062 decision 6). A call answered at ①, ②, ⓢ, ③ or ④ draws nothing.
- The terms of ADR-0009 (timing run, driver program, Python side), ADR-0010 (result, tool failure), ADR-0011 (identity, start line, end line, open), ADR-0016 (backend, operation, the moments ① to ⑦), ADR-0021 (the cut), ADR-0048 (the source, a seed, the draw, a draw that yields no seed, its two cases), ADR-0045 (a raised request to end) and ADR-0061 (the read of ④) are used unchanged. **The timing seed** is the seed the operation is handed for the timing run of the call (cited: ADR-0061 decision 3).
- It fixes **five points**: the source and frequency (decision 2), the place (decision 3), the answer for a draw that yields no seed (decision 4), recording (decision 5) and the relation to verification inputs (decision 6).

### 2. Source and frequency: drawn for each call, by the tool function

- **The timing seed is drawn, not fixed: the tool function draws it once for each call that reaches the draw, and the operation is handed that seed.** A further `execution`, the call of the other point and a call about a repaired attempt each draw their own: nothing carries a seed from one call to the next (cited: ADR-0010 decision 7, "the outcome of a call does not depend on state the server process kept from an earlier call").
- **Above the cut, not at the backend.** "The seed is an input the operation does not choose" (cited: ADR-0061 decision 3). Drawn in the tool function it is the same code for every backend, and over the mock the same draw runs — the reasoning of ADR-0021 decision 3, "Not the backend" (cited for the reasoning).
- **The property of the source**, as a property and not an algorithm, is that of ADR-0021 decision 3, taken here for the timing seed: "a source whose output nobody can predict or influence before the draw — not derived from the request, the identity, any file of the data plane or of the source, a clock, a counter or anything an earlier call left" (cited for the wording). **The range** is the whole range of seeds the harness accepts for a timing run: 0 <= seed < 2**64 (observation: `hilclaw.harness.timing.driver_arguments`). Whether the code binds the same source as for the check, how a registry binds it and whether a test binds its own is the code task's (the manner of ADR-0021 decision 3).
- **No request member carries it, and no calling agent chooses it or learns it before the run.** The request of these tools is the one of ADR-0062 decision 4 and gains no member.
- **Five ways were weighed** against four tests: (i) whether the seed or the input values then exist as a file, against the principle of OD-16 that no runtime seed exists as a file (as ADR-0009 decision 5 and ADR-0021 decision 3 cite it); (ii) whether the author of the attempt or a calling agent can know the timed inputs before the attempt is written or timed; (iii) whether it needs a member of a data-plane file (a CLAUDE.md A-13 BLOCKED reason); (iv) what it gives back.

| Way | (i) File | (ii) Known before | (iii) Member | (iv) What it gives |
|---|---|---|---|---|
| (a) Drawn per call by the tool function | no | no | no | one rule with the check; costs the answer of decision 4 |
| (b) A constant in the harness source | yes: a seed value in a file of the source | yes: the source is readable | no | the same inputs at every run |
| (c) A seed per run, stated in `instance.json` | yes | to whoever reads the file | yes | the same inputs within a run |
| (d) Derived from the identity or the run | the values follow from files | yes: the attempt's numbers are known | no | the same inputs for one identity |
| (e) A request member, chosen by the calling agent | no | yes, to the calling agent | no | a caller could choose inputs, or re-time until it likes them (ADR-0062 Limit 1) |

- **The choice is (a).** (b) and (c) break the principle of test (i), (c) also needs a member, and (b) to (e) let the timed inputs be known before the timing, so a kernel could be written for them. **What (b) to (d) would give, equal inputs, buys no reproducible outcome**: an outcome "is not a function of its request" — its samples vary and a second run "is a measurement of its own" (cited: ADR-0062 decision 2) — so equal inputs reproduce no measurement. ADR-0009 Alternatives row 5 rejected a seed fixed in the driver source because it "would decide what sub-question ⑦ leaves open" (cited); this record decides it the other way.
- **This adopts no defence of OD-16.** A timing run checks no output, and a kernel can forge its timing (cited: ADR-0009 decision 10) — by this record's reading, however its inputs are drawn. That nobody can know the timed inputs in advance is a property of the inputs, not a protection of the figure. In particular, test (ii) is not the adoption of the registered defence of threat B ⑴ of OD-16 ("매 trial 런타임 무작위 입력", against hard-coded output): that defence is about outputs that are checked, it stays a proposal, and nothing here adopts or rejects it.

### 3. The place of the draw: before the start line

- **The tool function draws the timing seed after the last answer of ④ and before it appends the start line of ⑤.** A call that reaches the draw asks the source once; what it yields is the seed of the call or is no seed, and **no value stands in**: no second answer of the source, no other source, no constant.
- **The two orders, weighed as ADR-0048 decision 3 weighed them** (both tools are journaled — cited: ADR-0062 decision 2):

| Test | Before the start line | After the start line |
|---|---|---|
| A draw that yields no seed | No line; the same request can be repeated and is carried out as any call whose identity has no line | A complete start line stands; the identity is ended with a `failure` or stays open — "may have run; outcome and amount unknown" (cited: ADR-0011 decision 2) — though no operation was called |
| A further timing run of that attempt at that point | Needs no rule | Needs a further `execution`, and who may ask for one stays with OD-10 and the retry part of OD-17 (cited: ADR-0062 decision 3) |
| A seed drawn and handed to no operation | When the start line cannot be appended (`start_line_failed`, cited: ADR-0026 decision 3) | None by design |
| The start line | Holds no seed: its `data` is exactly `step` and `execution` (cited: ADR-0011 decision 3; ADR-0062 decision 6) | The same |

- **The choice is before the start line**, for the reason ADR-0048 decision 3 gave for the check: a source that yields no seed says nothing about the attempt or a target, and after the start line it would use up an identity, or leave one open, in which the tool function knows that nothing ran. **Its cost**: a seed can be drawn and never used (Limits).
- **The output path is not placed here**: ADR-0062 decision 6 also leaves where the tool function forms it, and this record says nothing of it.

### 4. A draw that yields no seed: the tool failure `seed_not_drawn`

- **Such a call is answered before the start line with a tool failure of the kind `seed_not_drawn`, and appends no line.** For both cases of ADR-0048 (the source fails; it names no seed), alike. The call called no operation, built and ran nothing, consumed nothing at any target and appended no line; the same request can be repeated and is answered by what its own call then finds. A tool failure "says that no outcome was established" (cited: ADR-0010 decision 4, as ADR-0048 decision 4 cites it).
- **The answers weighed** are those of ADR-0048 decision 4, and they fall the same way here: `tool_crashed` would use "the frame's net for a defect" as a designed answer (cited: ADR-0045 decision 3, as ADR-0048 quotes it), and an end line or an open identity exists only after the start line (decision 3).
- **A kind of the run tools' contract, not reserved, with the spelling and the meaning of ADR-0048's.** Kinds the frame does not reserve stay "each tool's" (cited: ADR-0015 decision 2), and the kinds of the run tools' contract already serve both tools "with one meaning in both" (cited: ADR-0061 decision 4). **How three tools share it**: no record forbids two contracts from defining the same value with the same meaning; a value is reserved only by a record of the frame. So `correctness.check` keeps its own `seed_not_drawn` (ADR-0048 decision 5) and the run tools' contract defines `seed_not_drawn` of its own, for the same situation and with the same sentence a caller may rely on: *in this call the source of seeds was asked and yielded no seed; this call called no operation, consumed nothing at any target and appended no line.* A caller that knows the contracts reads one situation under one name.
- **Why not reserved — provisionally.** The test as ADR-0048 decision 5 applied it, "the situation belongs to one tool, and the kinds the frame reserved were reserved because their situations belong to no one tool" (cited), **no longer carries the choice**: the situation now belongs to three tools of two contracts. What remains is that `profiler.collect` has no contract, so a reserved kind would be a rule of the frame for a tool whose contract does not exist (the reasoning of ADR-0041 decision 4, cited); this part of the choice is provisional, as ADR-0041 decision 4 marked its own ("carries over less far, and this part of the choice is provisional" — cited), and a record of the frame that gives every HW tool one rule for what its tool function draws revisits it. The cost of ADR-0048 decision 5 stays, now for two contracts: a later record of the frame "may add to the common part as long as no tool's contract uses the name" (cited: ADR-0016 decision 3), so a reservation of this situation takes another name or amends both records.
- **Why not another spelling** (for example `timing_seed_not_drawn`): no landed record says anything different of the draw of a check and of a timing run when no seed comes, and two names for one situation would have a caller learn which tool answered before reading the kind.
- **Never on an end line of these tools by this contract**, which raises it only at the draw. What the tool function does with an operation that raises a tool failure of this kind belongs to the slice that says which tool failures stand as the `failure` of an end line (ADR-0061 Consequences items (4) and (6)); **this record asks of that slice that no end line of either tool holds `seed_not_drawn` as its `failure` kind**, so that the kind keeps telling that no line was appended (the argument ADR-0019 decision 2 took from `step_open`, as ADR-0048 decision 5 met it).
- **A raised request to end** from the source is not answered with this kind and passes through (the manner of ADR-0048 decision 5, cited); no line was appended before it.
- **The message** follows ADR-0048 decision 6, taken here: it says that the draw yielded no seed and which case it was, and may name the kind of the returned value or raised error; it carries nothing a source returned and nothing of what a source raised. The tool function writes neither to a file and does not hand the error of a source or its traceback on as its answer. The wording is the code's; "a caller tells the cases apart by the kind and never by the message" (cited: ADR-0026 decision 6).
- **The name** is a *name* of ADR-0001. Checked on 2026-10-15 in `hilclaw/`, `tests/` and `ARCHITECTURE/`: it occurs as the kind of `correctness.check` only, and it equals no reserved kind, no kind of the run tools' contract (`objective_not_stated`, `objective_not_covered`), no `step` value and no member name.

### 5. Recording: the seed is recorded nowhere

- **After a run, the timing seed is kept nowhere by the tool layer**: the tool function puts it into no result, no message of a tool failure, no line of the log and no file, and keeps it after the call in no process. This is the answer to the clause of ⑦ "is it recorded after the run", and it ends the "until OD-13 sub-question ⑦ is answered" of ADR-0061 decision 7 and ADR-0063 decision 8 for these runs: **a result never holds the seed**, and no longer only until an answer.
- **The closed member list of ADR-0063 decision 9 is unchanged.** No member is added to a result, a line of `events.ndjson`, `instance.json`, `STATE.json` or a result file.
- **Why.** (1) The principle of OD-16, as test (i) of decision 2: a recorded seed would be a runtime seed in a file — the end line and a result file are files — and the input values follow from it. This record reads that principle, for the timing seed, as holding after the run too; ADR-0021 decision 3 noted that the principle says this "without saying for how long" (cited). (2) Recording would reproduce no measurement (decision 2). (3) Under decision 2 a recorded seed tells nothing about a later one, so the reason ADR-0061 decision 7 gave the "until" — what "a caller could use to pick the seed of a later run" — does not ask for one either. (4) **NFR-2**, which pulls toward recording — "결과에서 그것을 만든 도구·설정 버전을 역추적할 수 있어야 한다" (cited: NFR-2), which ADR-0021 decision 3 weighed among the fixed inputs that "do not carry the answer" (cited) — is weighed and read as not asking for it: the seed is an input of one run, not a tool or a setting; the trace from a result to its tool and settings is unchanged by this record (a result reaches its source commit through the instance — cited: ADR-0063 Limit 8); and for a timing the seed would not let one reproduce the outcome (decision 2), where for a check a fail "cannot be reproduced without its seed" (cited: ADR-0021 decision 3). ADR-0009 Consequences asks that a record of a measurement "should be able to hold what the source commit does not determine — the parameters of decision 9 the caller chose" (cited), and its next sentence leaves "whether a seed may be recorded after a run" to sub-question ⑦ (cited); this record answers that the seed is not among what such a record holds. The cost is Limit 4.
- **What recording would have needed, not written**: a member of a result, and so a change of the closed list of ADR-0063 decision 9 stored in `events.ndjson`, which that record reads "as ADR-0060 read it" (cited: ADR-0063 Consequences) — a data-plane schema change and a BLOCKED reason. It was weighed as an alternative and not taken on its merits (Alternatives).
- **What this does not close.** The seed reaches the kernel's process on the command line (cited: ADR-0009 decision 5), and a kernel can put a value it holds, the seed among them, into what a result reports about it (cited: ADR-0063 Limit 6). This record binds what the tool function writes and does not make the seed a value no path may carry to the log; the members of ADR-0063 are therefore not reopened under the sentence of its decision 8, and the path stays with OD-16. What a backend keeps at its target is not restricted here.

### 6. The relation to the verification inputs of the same attempt

- **For these runs the inputs of a timing run are not tied to the verification inputs of the same attempt**: they come from the timing seed of decision 2, drawn by its own call, and are neither required to equal nor required to differ from the inputs of any check. That is the answer to the second clause of ⑦ on the timing side.
- **Why.** (1) Equal inputs would need the seed of a check to reach a timing call — kept between calls, which ADR-0010 decision 7 excludes, or recorded, which is the check-side clause of OD-16 sub-question ⑤ and is not answered here. (2) Even an equal seed is not promised to give equal inputs: of the verification generator, "Whether it is the generator of the timing driver is not promised" (cited: ADR-0017 decision 3). (3) What equal inputs might be wanted for — that the computation timed is the one verified — they would not give: a timing run checks no output (decision 2), and a kernel can act differently in the two runs whatever their inputs.
- **The check side is untouched**: whether the seed of a check is recorded, its draw count and re-verification at the promotion gate stay with OD-16 sub-question ⑤. A record that answers ⑤ in a way that needs equal inputs reopens this decision.

### 8. Limits

1. **A record, not code; nothing was built or run.**
2. **A source that draws badly without failing is not detected** (cited for the check: ADR-0048 Limits, from ADR-0021 decision 6); how hard a seed is to predict is what the source gives.
3. **A seed can be drawn and never handed to an operation** (decision 3); a death of the process after the draw leaves it in no file.
4. **A timing run cannot be repeated on the same inputs**, to look into a surprising figure; nothing records them (decision 5). The two runs of one attempt time different inputs, as they time different builds (cited: ADR-0061 decision 2); a kernel whose speed depends on its input values shows that as a difference between runs.
5. **Nothing in the log shows a call answered `seed_not_drawn`**, and a caller cannot tell from the answer whether the fault is lasting (as ADR-0048 Limits for the check).
6. **The seed can reach the log through the kernel** (decision 5; ADR-0063 Limit 6); nothing here closes it.
7. The limits of ADR-0061 decision 8, ADR-0062 decision 7 and ADR-0063 decision 11 stand unchanged.
