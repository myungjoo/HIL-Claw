## Context

- **The function** (code, as observation): `hilclaw.coder_call.call(request, *, source, runtime)` performs the call of ADR-0126 decision 3 with the read of ADR-0136 decision 5; its docstring lists the kinds in the order of `FAILURE_KINDS` and says "there is no default runtime" and "Nothing calls it yet". `runtime` is an object with `available()` and `run(scratch_root, coder_model=...)`; the real one is slice (d), which no code holds.

## Decision

A sentence is **cited** when a source is named with it. Every other sentence is **this record's own**.

### 1. Scope

- **The coder calls of the runs of ADR-0120 decision 1** that ADR-0126 decision 1 covers, reached through the front O1 gives.
- **Outside**: slice (d) and everything in ADR-0126 "Open parts of the start" (HQ-0053); the time limit of a call (OD-14); the coder's token budget and usage (#5 A-8, HQ-0041 (2)); calls that do not end normally and repair calls (OD-19); N > 1 (OD-29) and a second call for one tuple (OD-23 ① (가)); hooks (OD-18, PLAN P2-4); the rest of the roster.

### 2. (a) The tool `coder.run`

- **The registry holds the tool `coder.run`**, MCP name `mcp__hilclaw__coder_run` (cited: ADR-0010 decision 4, as ADR-0126 decision 3 names it); no `_` in the name, so the mapping stays reversible. Its tool function performs `hilclaw.coder_call.call` with the request it was given, the data-root source the registry was built with, and the runtime of decision 3, and returns what that function returns.
- **It adds nothing to the call's contract.** The request members, the result and the kinds in their order are ADR-0126 decision 3 with ADR-0136 decision 5, as `FAILURE_KINDS` holds them (cited); they are not restated. `invalid_request` and `no_data_root` are the reserved kinds of ADR-0015 decision 2 (cited: ADR-0126 decision 3, "Under (T)"). The exceptions the function propagates are the function's; the tool adds no handling of them.
- **Not journaled** (cited: ADR-0126 decision 7), and it writes nothing of the data plane except what the bring-in writes below `output/` (cited: same; ADR-0055 decision 5). It is reachable through the command-line front for people, tests and scripts (cited: ADR-0010 decision 3).
- **Left to the code slice**: the module that holds the definition, the description, the input schema and the message texts, as ADR-0140 left them for `timings.compare`.

### 3. (b) The runtime the registered tool gets while slice (d) is absent

- **`default_registry` registers `coder.run` now, bound to a runtime of the package whose `available()` returns false**, in the source and by no option, variable or entry point (cited: #5 A-12 point 3, as ADR-0138 decision 3 cites it; the `default_registry` docstring). Every call that passes the checks before `no_container_runtime` therefore fails with that kind, having created and consumed nothing (cited: ADR-0126 decision 3); `run` is never reached. The kind reads true from the package's side: with slice (d) absent it has no container runtime it can use. **The message stays the function's** ("no container runtime is available", `hilclaw/coder_call.py`): the tool adds no handling (decision 2), and this record changes no text of the function. Nothing asks the user to install anything: which part asks stays OD-8 ㉝ (가) (cited: ADR-0126 Walk-through). **Until slice (d) lands the kind, and its text, also mean "the start is not built"**, on a machine that has a container runtime as well; so the record that answers ㉝ (가) must tell the two apart by more than the message text — for example by asking only once slice (d) has replaced this binding — before anything asks the user for an installation, which stops the run (cited: the owner decisions of 2026-10-15, point 2, https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6182984913).
- **`default_registry` keeps its signature.** The tool's definition function takes the data-root source and a runtime; `default_registry` passes the package's runtime, and a test passes a stub. **Slice (d) replaces the binding in the source**, as ADR-0126 slice 3 foresees, and no other change of this record's tool is needed for it.
- **What P2-5's stub-`claude` verification then needs** (D16): a test that wants a call to bring in a kernel builds a registry with `coder.run` bound to a stub runtime — one whose `run` writes the files of `output` into the scratch and returns a status — and serves it with `hilclaw.mcp_front.main(registry=...)` or calls the function directly; such a stub is given by tests only. A run whose server is started by the turn loop gets `default_registry`, so before slice (d) its round-0 call ends in `no_container_runtime`; a verification of P2-5 that needs a kernel brought in through a turn session's own server needs slice (d) and a stub container program of its tests, which is slice (d)'s.
- **No part of slice (d) is designed here**: no image, container flag, sign-in, prompt text or permission mode of the coder's `claude -p` (ADR-0126 "Open parts of the start"; HQ-0053).

### 4. (c) The MCP idle window and the delegation's wait: the turn session's idle check and background tasks are turned off

- **This record reads O1's parenthetical "(server timeout or progress notifications)" as naming candidates, not as limiting the means**; both are weighed below, beside the session-side variable it chooses.
- **The turn loop starts every turn session with the environment of the calling process plus `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` set to `0`**, replacing any value the caller had. By M1 and M2 this disables the idle check, so a `coder.run` call that sends neither a response nor a progress notification for 30 minutes or more is not aborted for idleness. Nothing else of the environment, the server entry or the front changes.
- **What can still override it** (M6): a settings file the session reads that sets the same variable. With `--setting-sources project` (cited: ADR-0139 decision 7) those are the definition's `.claude/settings.json`, which sets none (the definition holds no `settings.json`; `hilclaw/turn_definition.py`, "no settings"), and managed settings, which are a fact of the runtime machine that this record neither presumes nor overrides, as ADR-0139 decision 6 treats them. That the runtime user's own `settings.json` is not among them is ADR-0139's reading of P6 (decision 7), item (xl). The Desktop and self-hosted precedence of M6 does not arise: the turn loop starts the session itself. So item (xli) is stated for a machine whose managed settings do not set the variable.
- **What bounds the call then** is the wall-clock limit of M3: `MCP_TOOL_TIMEOUT` as the calling process's environment gives it, about 28 hours when unset. **This record chooses no value of it and no time limit of a coder call**: that stays OD-14 and ADR-0126 "Open parts of the start". What it decides is only that the session does not cut off a long call before that limit.
- **Its reach, confined.** The variable acts on every tool call of the session, and the session has the one server `hilclaw` (cited: ADR-0118 decision 6, `--strict-mcp-config`). So no tool of that server is aborted for idleness any more. No record chose the idle window as a limit of any tool (cited: ADR-0010 decision 8, "No time limit and no size limit of a call are decided"), so no decided limit is lost; the cost is that a hung tool call now holds its turn up to the wall-clock limit. **The front's protocol behaviour, which every other tool sees, does not change.** The runtime self-check's session (ADR-0054, ADR-0057) is not a turn session and is unchanged.
- **The delegation must not end first.** A long call is cut off as surely if the coder-driver is abandoned while it waits. By M7 a sub-agent of a `-p` session starts in the background unless Claude chooses to wait, and its report would then reach the Round-Manager only in a later turn; after the Round-Manager's last reply the run waits for it (M8). So **the turn loop also puts `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS` set to `1` into every turn session's environment**, replacing any value the caller had: by M7 Claude then waits for every subagent, the coder-driver's delegation runs in the foreground and the Round-Manager gets its report in the same turn, which decision 6 relies on. Its reach: every delegation of the session, the evaluator's (ADR-0128) included, runs in the foreground; the main conversation's MCP calls are no longer moved to the background (M7, mcp); background Bash commands are off, which no agent of the definition has (ADR-0139 decision 4). The ceiling of M8 then has no background work to apply to, and is not set. **The turn loop also removes `CLAUDE_AUTO_BACKGROUND_TASKS` from that environment**: set to `1` it "force-enable[s] automatic backgrounding", moving a subagent to the background after about two minutes (cited: env-vars, `CLAUDE_AUTO_BACKGROUND_TASKS`), and no page says which of the two variables wins when both are set. The precedence of M6 applies to these variables as to the first.
- **The stall timer of M9 is not set.** That it does not count the coder-driver's wait on `coder.run` is said by the pages of workflow agents only; any value set here would be a limit on a silent sub-agent, which this record does not choose. It is item (xlii); if it fails, the record that answers it sets the variable and says so as a limit (OD-14).
- **Why not progress notifications from the front.** By M5 a server may send them only for a token the request carried, and no page read says that Claude Code puts one on `tools/call`; the means would rest on an unestablished fact. It also needs a front change: the front handles one message at a time and sends no notification, so it would need a second thread or a timer writing `notifications/progress` while the tool function runs, and a shared writer for standard output — a protocol behaviour of the front, to be confined to `coder.run` by a rule of the front. A later record may still adopt it, for example if item (xli) fails.
- **Why not a per-server `timeout` in the `--mcp-config` entry.** By M3 it is a hard wall-clock limit on every tool of the server, so any value is a time limit of a call (OD-14); and whether the field is read from a `--mcp-config` file is not established.
- **Why not ask the Round-Manager to wait, or raise the ceiling of M8, alone.** A prompt can ask (M7, "when you ask"), and decision 6's step does ask; but by M7 the waiting is then Claude's judgment, a rule of the prompt only. `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0` would keep a background coder-driver's run open, but its report would arrive in a later turn of the session, after the Round-Manager's step had gone on, and a background subagent has a smaller built-in tool set (M7).
- **Why not the definition's settings file.** It would work as documented: an `env` member of `orchestration/settings.json`, which the turn loop puts at `.claude/settings.json` (cited: ADR-0118 decision 5; `hilclaw/turn_definition.py` `LAYOUT`), is applied at the start of a `-p` session and overwrites the caller's value (M6); managed settings would override it just as they override the process environment. The effect is the same, so the choice is where the value lives. **The process environment is chosen** because it is a start condition of the session process like the options of ADR-0139, and stays with them in the tested code that builds the session — this record's application of ADR-0139 decision 8's "Every permission of a turn session is on its command line, built by tested code" — and because the definition holds no `settings.json` yet, whose members are the hooks of PLAN P2-4 (cited: `hilclaw/turn_definition.py`, "no skills, no settings, hooks or permissions (PLAN P2-4"); starting that file for one variable would anticipate their design. A later record that creates the file may move the variable into it.

### 5. (d) The coder-driver definition

- **`orchestration/agents/coder-driver.md`** (cited: ADR-0126 decision 6), with `name` `coder-driver` and **`tools` exactly `mcp__hilclaw__spec_write, mcp__hilclaw__coder_run`**: the write of ADR-0138 decision 3 and the call of decision 2. **No `Bash`** (O1), no file tool, and no `Agent`. Its frontmatter holds no `background` member: by M7 `background: true` keeps a subagent in the background, and decisions 4 and 6 rely on a foreground delegation; the test of slice 3 checks it.
- **No read tool either** (`Read`, `Grep`, `Glob`). Its inputs are the delegation message (cited: ADR-0126 decision 6) and its outputs are what the two tools return; it judges nothing and composes nothing (cited: ADR-0126 decision 2; K3 of ADR-0126). A read tool would give it nothing its rule uses. This is the least-privilege list (NFR-4; the `tools` frontmatter as the per-agent means, K1 of ADR-0139), not a restriction of reading in the run: the owner premise "읽기 제한은 채택하지 않는다" (cited in ADR-0139 Status, K2) concerns what agents that read may read. A later record that gives it a reason to read adds the tools.
- **Its fixed rule**, ADR-0126 decision 6 with the order of ADR-0138 decision 3 (cited), and what this record adds:
  1. With the run id and the tuple of the delegation, call `mcp__hilclaw__spec_write`.
  2. If it succeeds, call `mcp__hilclaw__coder_run` once with the same run id and tuple, and report its result — `taken` and `scratch_removed` — or its kind to the Round-Manager.
  3. If it fails with any kind but `spec_exists`, request no call and report the kind (cited: ADR-0138 decision 3).
  4. **If it fails with `spec_exists`, request no call and report the kind.** This is this record's interim rule and **not an answer** to whether a call may follow a spec already there, or to what a second call for one tuple means (OD-8 ㉖ (가), OD-23 ① (가); ADR-0138 decision 3 leaves both open). It is the choice that consumes nothing and makes no second call; the alternative, a call over the spec already there, is weighed in Alternatives. A later record that answers them changes the rule.
  5. Never call either tool twice in one delegation, never retry, code nothing, and write nothing of the run by any means but the two tools (cited: ADR-0126 decisions 2 and 6).
- **The permission derivation carries the entry with no change** (checked against ADR-0139): both entries are exact `mcp__hilclaw__<name>` names, which decision 3 accepts and pre-approves, and the file gains `Agent(coder-driver)`; the agent names no built-in tool, so the built-in set of decision 4 is unchanged; its tools are those of the session's pool narrowed by its list, in the session's mode (decision 5). That is decision 9's "(T)" branch, "nothing else changes" (cited). **The limit of ADR-0139 decision 5 applies**: the pool is shared, so the Round-Manager *can* call `mcp__hilclaw__coder_run`, and that it does not (cited: ADR-0126 decision 2, "The Round-Manager issues no coder call itself") rests on its prompt until a hook of PLAN P2-4 checks the calling agent.

### 6. (e) The Round-Manager's delegation step

- **In round 0 only, a step 2 follows step 1 of "The round steps"**: the Round-Manager delegates to `coder-driver` with the `Agent` tool and waits for its report (decision 4 makes the delegation a foreground one), its message naming its run id and the tuple `round` 0, `candidate` 1, `attempt` 1 and no place (cited: ADR-0126 decision 6; ADR-0123 decisions 2 and 4). The tuple is the only one `spec.write` accepts (cited: ADR-0138 decision 3) and the first attempt of round 0's one candidate, whose bring-up code is the baseline's (cited: ADR-0119 decision 2, `0000/01/01`).
- **Whatever the coder-driver reports** — a result with any `taken`, or any kind — the Round-Manager reports it in one line and **comes to the present stop**, which now follows step 2 in round 0 and step 1 in other rounds: it reports that the following steps are not yet defined and ends the session, writing nothing further. In that turn it delegates no second time, issues no call itself, writes no spec or kernel by any other means and asks for no repair.
- **Why only this far.** What follows the call in round 0 — the checks of the attempt, its board run as the baseline (ADR-0119 decisions 2 and 4), the evaluator's work (ADR-0128) and the round's end — is not defined, and what a failure kind or an empty `taken` means for the round is OD-19's and PLAN P2-1's (cited: ADR-0126 Walk-through). **Left open and named**: the steps after the call in round 0; any coder call in a round ≥ 1 (its spec is the rest of OD-6, its tuple OD-23 ① and OD-29); what the Round-Manager does with each kind beyond reporting it.
- **A later turn of the same round 0** repeats steps 1 and 2 (cited for step 1: ADR-0134 decision 5, "whether the round is begun or gone on with"): `spec.write` meets `spec_exists`, and by rule 4 no call is made. So a round 0 gets at most one call through this step, which is the interim rule's effect and not an answer to OD-23 ① (가).
- **No token accounting waits here**: no coder session is spent until slice (d) lands, and slice (d) itself waits on #5 A-8 (cited: ADR-0126 Consequences, slice 3).

| After slice (d), a call that brings in `kernel.c` | The result `{"taken": ["kernel.c"], "scratch_removed": true}` is reported; the stop; the attempt's checks wait for later steps |
| A call that runs 3 hours without a progress notification | Not aborted for idleness, and the coder-driver's delegation stays in the foreground (decision 4); the stall timer is item (xlii); bounded by `MCP_TOOL_TIMEOUT`, about 28 hours unset (M3); that a real session behaves so is item (xli) |
| The coder ends non-zero | `coder_not_ended`, nothing brought in (cited: ADR-0126 decision 3); reported; the stop; no repair (OD-19) |
| A round ≥ 1 | No delegation; the stop after step 1, as today |
| The coder-driver names another run's id | The function serves that run (cited: ADR-0126 Walk-through); a hook could see `run_id` in the request (cited: ADR-0010 decision 6), and none exists (PLAN P2-4) |
| A test of a call that brings in files | A registry with `coder.run` bound to a stub runtime, served by `mcp_front.main(registry=...)` (decision 3); no real `claude`, no container (D16) |

## Alternatives considered

| Point | Alternative | Outcome |
|---|---|---|
| (b) | Register now, bound to a runtime that reports no container runtime | **Chosen**: the front, the coder-driver and the Round-Manager's step can land and be tested now; every call costs nothing and says why it failed; slice (d) changes one binding |
| (b) | `default_registry` takes a runtime, none by default | Rejected: the servers that matter are started by the turn loop and the command line with the default, so the parameter would only reach in-process tests, which the definition function already reaches; with none given, the tool would be absent or need a fallback, and a later wish to choose the runtime from outside would meet the rule that nothing "chooses what it is bound to" |
| (b) | Register only when slice (d) lands | Rejected: the coder-driver's list would name a tool the server lacks, and the definition, the step and their tests would wait on HQ-0053 for no gain |
| (c) | `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT=0` in the turn session's environment | **Chosen** (decision 4): documented (M1, M2), no front change, chooses no limit |
| (c) | The same variable with a finite value | Rejected: any value would be a time limit of the call (OD-14) |
| (c) | Progress notifications from the front | Rejected for now: rests on a `progressToken` no page says Claude Code sends (M5), and needs a concurrent front |
| (c) | A per-server `timeout` in the `--mcp-config` entry | Rejected: a hard limit on every tool (M3), so a time limit; its use from `--mcp-config` is not established |
| (c) | Leave sub-agents in the background; ask in the prompt, or set the ceiling of M8 to `0` | Rejected as the means (decision 4): waiting stays the model's judgment, or the report arrives a turn later; the prompt asks as well |
| (c) | Leave the 30-minute window | Rejected: O1 assigns the point to this record; a cut-off call can leave a container and a scratch behind (cited: ADR-0126 Walk-through; ADR-0049 L9) |
| (c) | The same variable in the definition's `settings.json` | Rejected (decision 4): same effect (M6); the value stays with the tested session start, and the file is P2-4's |
| (d) | On `spec_exists`, call `coder.run` all the same | Rejected for now: the function would refuse an existing `output` (`output_exists`) and check the spec's `id`, but where no `output` exists it would start a coder over a spec this delegation did not write and nothing compares with what `spec.write` would compose (cited: ADR-0138 decision 3) — a second call for the tuple whenever an earlier one brought in nothing or failed, which is OD-23 ① (가) |
| (d) | Add `Read`, `Grep`, `Glob` | Rejected: no step of the rule reads; a later record can add them |
| (e) | Delegate in every round | Rejected: `spec.write` accepts only `0`/`1`/`1`, and a later round's spec is open |
| (e) | Define the rest of round 0 | Rejected: beyond this record (checks, baseline run, evaluator, round end are PLAN P2-1) |

  - **(xli)** In a `-p` turn session whose environment holds `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT=0`, on a machine whose managed settings do not set that variable (M6) and with item (xl) holding, an `mcp__hilclaw__coder_run` call from the `coder-driver` sub-agent that sends neither a response nor a progress notification for more than 30 minutes is not aborted, and its result reaches the coder-driver (the version in use reads the variable, M2).
  - **(xlii)** With `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` in that environment (and the same conditions on settings, with `CLAUDE_AUTO_BACKGROUND_TASKS` removed), the Round-Manager's `Agent` delegation to the coder-driver runs in the foreground and returns the coder-driver's report in the same turn; and the sub-agent stall timer of M9 does not abort the coder-driver while its `coder.run` call is pending, which the pages say of workflow agents only.
  - **(xliii)** While the single-threaded front serves one long `coder.run` call, the session neither aborts that call nor marks the server failed because of any request it sends the server meanwhile (a `ping` among them).

- **The cost, plainly.** Until slice (d) lands, every call ends in `no_container_runtime` and no kernel is produced, so P2-5's round 0 produces no baseline through a turn session. With the idle check off, a hung tool call of any kind holds its turn until the wall-clock limit. **Once `spec.write` has succeeded for a run, rule 4 leaves its round 0 with no later call**, whatever followed: a turn that died before `coder.run`, or a call that failed with any kind, consuming nothing (`no_container_runtime`, `coder_model_not_stated`, a `run_file_*` or `spec_*` kind) or not (`coder_not_ended`). In particular **every run whose round-0 turn runs before slice (d) lands never gets a round-0 coder call**, after slice (d) as well, until a record answers OD-23 ① (가) and OD-8 ㉖ (가).

## Boundaries (not decided here)

- **Slice (d)** and everything in ADR-0126 "Open parts of the start": image, container flags, sign-in (HQ-0053), permission mode and prompt of the coder's `claude -p`, the output stream.
- **The time limit of a call** and every other level of the timeout hierarchy (OD-14); the value of `MCP_TOOL_TIMEOUT`.
- **The coder's tokens** (#5 A-8, HQ-0041 (2)); calls that do not end normally and repairs (OD-19); N > 1 (OD-29); a second call or spec for one tuple (OD-23 ① (가), OD-8 ㉖ (가)).
- **Hooks** (OD-18, PLAN P2-4); the steps of round 0 after the call and of every later round (PLAN P2-1); the rest of the roster (OD-23).
