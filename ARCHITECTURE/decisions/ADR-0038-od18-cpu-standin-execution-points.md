## Decision

A sentence marked **owner** renders the HQ-0005 answer and quotes it. A value is **cited** when another source is named with it. Everything else is **this record's own** — among it the definition of an execution point, the reading of "the same local run", that `cpu_standin` offers `correctness.check`, the form in which a call states its point, what that means for an identity, and the reading of ADR-0020 decision 2 in decision 6.

### 1. Scope and terms

- This record is about **the first backend `cpu_standin`** and, in decision 6 only, **the mock backend**. It is not about a simulator, a board, a remote machine or any other accelerator, and it is the contract of no tool.
- The terms of ADR-0010, ADR-0015, ADR-0016 (HW tool, backend, operation, target, script) and ADR-0021 (the cut, a check — "one call that reaches ⑥") are used unchanged. **The first case** keeps the meaning of ADR-0021 decision 1: `cpu_standin`, kind `gemm`, fp32, a C kernel.
- **Execution point**: one of the two places of the round loop of FR-1 at which an attempt is run and its correctness is checked — the **sim point** ("sim(조기검증) + correctness", the early filter) and the **board point** ("board(최종측정) + correctness", the final verdict; cited: FR-1, FR-9). In this record a point is a place in the loop, not a machine: under the answer of decision 2 both points of `cpu_standin` can lie on one machine.
- **Offers**: a backend offers a HW tool when it has an operation for it (cited: ADR-0016 decisions 2 and 3). **The run tools**: `sim.run` and `board.run`.
- **The local configuration**: what the answer calls "the first case (the owner's local PC, native build and run)" — the kernel is built and run on the machine of the tool function. The owner's parenthesis is narrower than "the first case" of ADR-0021 in one respect, the place, and this record keeps the two apart by this name.

### 2. Which HW tools `cpu_standin` offers

- **Owner** (HQ-0005 (1), answer (c)): `cpu_standin` offers "both `sim.run` and `board.run`. In the first case (the owner's local PC, native build and run) the two carry out the same local run; nothing but the execution point distinguishes the two operations."
- **How this record reads "the same local run"** (its own reading). The answer says "the two carry out" and the question's option (c) was "both, each carrying out the same local run": each of the two operations carries out the run by itself when it is called, and the two are the same in kind and mechanism. It is not read as one run that is carried out once for both calls. State kept in a process could not hold the outcome of such a run for the second call in any case (cited: ADR-0010 decision 7; ADR-0016 decision 2 (c)). **Whether a call of one run tool reads anything of the data plane that a call of the other left** depends on result files and members no record defines and is the contract of the run tools; this record says nothing of it.
- **What follows** (this record's own, from the answer and ADR-0016 decision 3). Neither `sim.run` nor `board.run`, called about a run whose hw_profile names `cpu_standin`, is answered `not_offered` by a backend table whose `cpu_standin` entry is built as the answer says. They stay two tools with two operations (cited: ADR-0016 decision 2, "for each HW tool it offers it has one operation"); that the two operations may be one piece of code is the code task's. **What the local run is** — its mechanism, the request and the result of either tool, whether either is journaled — is the contract of the run tools and is not decided here.
- **`cpu_standin` offers `correctness.check`** (this record's own, from the answer of decision 4): two checks of each attempt are made on `cpu_standin`, a check is a call that reaches the operation (cited: ADR-0021 decision 1), and a call reaches an operation only at a backend that offers the tool (cited: ADR-0016 decision 3).
- **`profiler.collect` was not asked and stays open**: whether `cpu_standin` offers it is the rest of sub-question ⑦.
- **Owner — foreseen, and not decided** (HQ-0005 (1)): "a configuration in which the board is a machine of a non-native ISA and `sim.run` is an emulated run of **the board's ISA** on the local host (for example aarch64 under qemu-user on x86-64), so that the sim point is a functional simulator and the board point is the measurement. That configuration needs an emulator as a new external dependency (CLAUDE.md A-13), a hw_profile for a kernel built on one machine and run on another (ADR-0035 Boundaries, OD-4) and remote access (#5 B-2); it is to be registered as an open point and settled with those, not in T-0088." This record registers it as sub-question ⑫ (Boundaries) and decides nothing of it; what is said below of the two points on one machine is said of the local configuration.

### 4. The two checks of an attempt, and how a call states its point

- **Owner** (HQ-0005 (3), answer (b)): "two checks per attempt, one as the sim-point check and one as the board-point check, also where both are the same local run." And: "How a call states its execution point is the record's design."
- **A call of `correctness.check` is about exactly one execution point, and the two checks of an attempt are two calls.** A check is one call that reaches the operation (cited: ADR-0021 decision 1), so two checks are two such calls; and FR-1 places what follows the sim-point check — the return to code generation, the promotion — before the board point is reached, so one call could not hold both.
- **The call states its point in a member of the request.** The member is required and has no default, and it has exactly two values, one for the sim point and one for the board point. A request without it, or with another value, is a refused request (cited for the kind: `invalid_request`, ADR-0015 decision 2). **The name of the member and the spelling of its two values are the second record's** (ADR-0021 Boundaries: "every member of a request"); this record names neither.
- **Why a member of the request.** The calling agent is the one that knows at which place of the loop it stands; no record gives a file of the data plane a member that says it, and no outcome of a call may depend on state a process kept from an earlier call (cited: ADR-0010 decision 7; ADR-0016 decision 2 (c)). Unlike a seed, a tolerance or a hw_profile, the point is not something a caller could use to make an attempt pass: the judging is the same code at both points (cited: ADR-0021 decision 2), and what a point changes is what FR-1 has the caller do with the outcome. What a caller that states the wrong point does is in decision 8.
- **If the tool is journaled, the two checks of one attempt are two identities, and they differ in `step`.** The identity of a step is the envelope numbers with `step` and `execution` (cited: ADR-0011 decision 3). The two checks are about the same attempt, so their envelope numbers are equal; with one `step` value and `execution` 1 the second call would find the identity ended and be answered with the stored result of the first (cited, same decision), and no second check would take place. `execution` does not tell them apart: it "counts the executions of that step" and "is 1 unless a decision outside this record asked for a further execution" (cited, same decision) — the board-point check is not a further execution of the sim-point check, and a real further execution of either would collide with it. **A journaled contract of this tool therefore has two `step` values, one for each point, and the `step` of a call follows from the point its request states.** This record lists no value.
- **How this reads ADR-0015 decision 4** ("`step` is not a member of a request: the tool's contract fixes it"). The request still carries no `step`: the contract fixes the two values and which point each belongs to, and neither value is shared with another tool (cited, same decision). The reason that decision gives — "A request that named the step could record one tool's execution under the name of another" — is kept, since both values are this tool's. ADR-0015 is not edited.
- **Whether the tool is journaled is not decided here.** The form above can be stated without it: the member is the same either way, and the sentence about `step` applies only if the tool is journaled. It is the second record's, with the meaning of `execution` for this tool.
- **Not decided**: whether an operation of this tool is handed the point. In the local configuration nothing at the target differs between the two checks; a target whose two points are two machines would need it, and that is not this record's (#5 B-2, B-3; the second record).

### 5. "동일 검증을 반복한다"

- **Owner** (HQ-0005 (3), answer (i)): "\"동일 검증을 반복한다\" means the same harness, predicate and tolerance with inputs drawn anew for each check; the reading of ADR-0021 decision 3 is confirmed and is not reopened."
- This record therefore **cites ADR-0021 decision 3 as it stands**: the tool function draws the seed once for each check; the seed is no member of a request, is not kept and is written to no file before or during the check; the check at the other point draws its own. **No sentence of ADR-0021 is replaced**, and no carrier of a seed from one call to the next is introduced. The member of decision 4 carries a point and nothing from which an input follows.
- The confirmation is the owner's for what was asked — the two checks of an attempt on `cpu_standin`. This record reads it, with decision 6, as holding for a run at the mock as well, since the same contract answers that run; it says nothing of any other backend (#5 B-7). Whether a seed is recorded after a check, and `draws`, stay with OD-16 sub-question ⑤, which the answer does not touch.

### 6. A run whose hw_profile names the mock

- **Owner** (HQ-0005 (4), answer (a)): "a run whose hw_profile names the mock is answered by the first case's `correctness.check` contract: the oracle of the HQ-0004 answer, and the `tolerance` member of `instance.json` with the meaning ADR-0020 decision 2 gives it for `cpu_standin`, so that the contract tests of P1-1 run the whole judging over the mock. The mock's script stands in for the kernel, not for the reference: it may compute the product for the seed of the call, and the reference stays with the tool function. What the default script answers is the second record's."
- **What follows by citation.** The condition under which ADR-0021 decision 2 wrote "What the cut means for the mock, if a run at the mock is answered by this contract" now holds. So, as that decision says: the whole judging runs over the mock as over a real backend, because it is not the backend's; a script of this tool must be able to express each thing an operation may return; "A report that passes must hold the right product for the seed of that call"; and a script of this tool is asked with what the contract hands an operation, not with the request and the hw_profile alone. The four points of ADR-0021 (the cut, the seed, the tolerance and `tolerance_not_stated`, the classes of outcome) and decision 4 above hold for such a call as they do for a call about a run of the first case.
- **How this reads ADR-0020 decision 2** (this record's own reading). That decision gives the member `tolerance` its meaning "for a run of the first case and gives it no meaning for any other run". The owner's answer gives the member the same meaning, in the same form, for one more class of run. The form and the meaning of the member do not change and no member is added, so this record reads the answer as raising no version of `instance.json` (the rule of ADR-0018 decision 2 is about a change of "its type, form or meaning"). ADR-0020 is not edited; its sentence is less exact for the mock.
- **Not answered, and not decided here**: the rest of sub-question ⑩ — a run of another accelerator that is not the mock, a run at `cpu_standin` of another kind, dtype or kernel language, how an operation comes to the verification executable, the tool-failure kinds of a backend. Which kind, dtype or kernel a script of the mock stands for is the script's and the second record's. **The oracle, the tolerance vocabulary and the defaults of every other backend stay with #5 B-7.**

### 7. What this gives the next records

Of the list of ADR-0021 decision 1 ("a second record must add at least"), this record answers two items: **which of `sim.run`, `board.run` and `correctness.check` the `cpu_standin` backend offers** (all three); and **how a call says at which execution point it is made** (a required member of the request with two values; two `step` values if the tool is journaled). Of sub-question ⑩ it answers one clause: **that a run at the mock is answered by this contract**. It answers nothing else of that list or of that sub-question. Still the second record's: whether the tool is journaled, its `step` values and the meaning of `execution`; the name and values of the member of decision 4 and every other member of the request, the input schema and the description; where `draws`, the dimensions, the kernel of the attempt, the flags and the time limits come from; the members of the result and the tool-failure kinds a backend may raise; the spend; the operation and the default script of the mock.

### Walk-through

One attempt of a run of the first case in the local configuration. No member name, `step` value or result member is shown; "the sim point" and "the board point" stand for the two values of the member of decision 4. The order of the calls inside one step of FR-1, and everything a caller does with an outcome, are FR-1's and PLAN P2-1's.

| Place in the loop (FR-1) | The call | What it answers |
|---|---|---|
| sim step | `sim.run` | Reaches the operation of `cpu_standin` — not `not_offered`. What the local run is and what the call returns: the contract of the run tools |
| sim step | `correctness.check`, stating the sim point | The tool function reads the tolerance, selects, draws a seed, calls the operation and judges the report (ADR-0021 decisions 2 to 5): a result that reports pass, fail or broken |
| after a fail at the sim point | — | FR-1 ⑴: return to code generation (bound: OD-19). A check of the repaired attempt is a check of another attempt |
| promotion | — | OD-15, OD-29 |
| board step | `board.run` | Reaches the other operation of `cpu_standin`, which carries out the same local run itself (decision 2). What the call returns: the contract of the run tools |
| board step | `correctness.check`, stating the board point | A second check: the same harness, predicate and tolerance; **a seed drawn anew**. If the tool is journaled this call has another `step` than the sim-point call and is not answered from the log of that call |
| sim point passed, board point failed | — | FR-1 ⑶ applies as written. What the cause can be in the local configuration: decision 8 |
| a request that states no point | `correctness.check` | `invalid_request`; nothing read, drawn or consumed |
| the hw_profile of the run names the mock | `correctness.check`, stating either point | The same path and the same judging; the script stands in for the kernel and is asked with the seed of the call; the reference is computed by the tool function |

### 8. Limits

- **Two points on one machine exercise no difference between a simulator and a board.** In the local configuration a sim-point pass followed by a board-point fail can come, among other things, from the inputs drawn anew or from a tolerance changed between the two checks (both cited: ADR-0021 decision 6), or from what differs between two runs of one attempt on one machine — threads, memory contents, load, a second build if each call builds (not decided: ADR-0021 decision 2), a fault of that machine. None of these is a difference between a simulator and a board: nothing there tells a "board 결함" from a "시뮬레이터 결함" of the triage of FR-1 ⑶, so the stand-in exercises the form of that path and not that distinction (the triage: OD-10; PLAN P2-1).
- **In the local configuration the promotion compares a run with a run of the same kind.** There both run tools carry out the same local run, and nothing in the answer makes the sim point cheaper or less exact than the board point; whether the two calls measure alike is the contract of the run tools (Boundaries). The stand-in is therefore not known to exercise the cost difference of C-4 or the question whether a sim result predicts a board result (OD-15). Each attempt that reaches the board point is run at both points and checked twice.
- **The path of a target that lacks a point is not exercised by `cpu_standin`.** `not_offered` is reached by a test that builds a table whose mock lacks the operation (cited: ADR-0016 decision 5 (d)); the rule of the loop for it is not answered (decision 3).
- **The point a call states is believed.** Nothing checks that a call stating the board point follows a sim-point pass or a promotion, that both points are checked, or that the point stated is the place the caller stands at: there is no access control (cited: ADR-0010 decision 8), and the order of the loop is its caller's (PLAN P2-1; hooks and gates: rest of OD-18, OD-3).
- **The judging over the mock proves the tool function and not a kernel or a backend.** A script that computes the product is a second multiplication, written for a test. If it shared code with the reference of the harness, a passing test would show nothing about that code; the answer keeps the two apart in role ("stands in for the kernel, not for the reference"), and what a script is built from is the second record's and the code task's.
- The limits of ADR-0016 decision 6 and ADR-0021 decision 6 stand unchanged, among them: a mock outcome is told apart by its hw_profile only, and two checks of one attempt can disagree by their inputs alone.
