## Decision

A value is **cited** when a source is named with it. Everything else is **this record's own** design: the lookup's rules, the treatment of the reader's own run, the order, the members `case` and `cases_read` with their types and validity rules, the choice of the decision log's place, and the reading of FR-11's "참조한 과거 사례" as every case the selection was given (decision 3).

### 1. The lookup

- **The reader is the selection role** of the round (cited: ADR-0004 decision 4, the role that owns `decision/`; FR-18 "가설 수립·기법 선택"). Which agent or tool holds the role or performs the lookup for it is OD-23.
- **When**: the selection of **every round ≥ 1** of a run takes the lookup's output as input before it writes the round's `hypotheses.json` — FR-17 has the selection learn from past cases "라운드마다", and cases of other runs may be promoted while the run goes on. Round 0 has no technique selection and no hypothesis record (ADR-0059 decision 5); whether its bring-up uses cases is not decided (Boundaries). How it is enforced that a selection took the output is OD-18 and OD-23.
- **The key** is that of the run's instance: the records its `instance.json` states in `hw_profile` and `op_signature` (cited: ADR-0018 decision 3, ADR-0031 decision 3). A run that states no op_signature has no key to look up, and nothing is substituted (cited: ADR-0031 decision 5).
- **A hit of ADR-0001 decision 4 yields the cases of that key directory; nothing else yields a case.** A miss — no key directory, or a missing key record file (`db/<hw_profile_key>/hw_profile.json` or `op_signature.json` of the key directory, ADR-0004 decision 5; the window of ADR-0014 decision 3) — yields no case: cases below a key that is not stored are not read. A stored canonical form that differs (ADR-0001 decision 3) or a record file that is not valid is reported and yields no case.
- **Which files count**: every file directly in the key directory whose name begins `case-` and ends `.json`. No subdirectory is looked into, and a temporary file of a case write (`….json.<token>.tmp`) never counts (ADR-0072 decision 1). Each such file is read by ADR-0072 decision 2: a file **not valid** there — its name not formed from its `run_id` and `round` included — is reported, none of its members is used and nothing is repaired; a file whose own `schema_version` or a copy's is an *integer* other than `1` is **set apart** and reported, not called damage (OD-11). One such file does not hide the others: the rest are read.
- **Which cases, and how many: every valid case of the key directory, except those of the reader's own run.** No cap, no recency window, no filter by verdict and no summary in the MVP form. Reasons: the OD-30 proposal's own position for few cases ("적을 때는 전부 읽으면 되지만"); a filter by verdict would drop the rejected and failed cases FR-18 stores for this use ("통하지 않은 것의 기록이 이후 run의 헛된 라운드를 줄인다"); recency has no basis today — a `run_id` states no time and no component may depend on its order (ADR-0027 decisions 3 and 4), and a case holds no time of its own; and no landed record gives a number for a cap. The cost is the context of the selection, which grows with the cases of the key; **the rule for when cases accumulate is not decided** (Boundaries).
- **Cases of the reader's own run are left out**, recognised by a `run_id` equal to the reader's. A run reads its own earlier rounds from its own tree (FR-17: "다음 라운드 결정은 앞선 판정을 입력으로 삼는다") and cites their attempts by `attempt` (decision 2), so an own case would be a second copy of an input the selection already has. A kind that cites an earlier hypothesis or verdict of the run itself stays open (ADR-0059 Boundaries) and `case` is not that kind. Whether a run's rounds are promoted while it runs is open (Boundaries); this rule holds either way.
- **What a case yields**: the parsed document of the case, whole — both copies, every member, unknown top-level members included, which the reader passes over. A case without `verdict_record` is read with no verdict, never as `inconclusive` or another value (cited: ADR-0072 decision 3).
- **The lookup reads no file of a source run** and no file outside the key directory beyond the key record files of the hit: a case is readable from the key directory alone (cited: ADR-0072 decision 3), `runs/` may be absent, unshared or gone where `db/` is read (ADR-0072 decision 3; #5 A-1; OD-25), and the *refs* inside a case stay names of the source run's attempts, which the lookup does not resolve. The copies are not checked against `runs/`.
- **The lookup is deterministic**: its output depends only on the key of the run's instance, the two key record files and the cases of that key directory, and the reader's `run_id`, not on a model's choice of what to open — so the same directory gives the same input (NFR-2), and it relies on no agent memory (FR-18, OD-24). The cases are given **in ascending byte order of their file names** (ASCII: the form of ADR-0072 decision 1 with a `run_id` of ADR-0004 decision 8). The order is fixed only for that reason and **claims no meaning** — not recency, not rank. That the names of ids built by ADR-0027 follow clock readings does not make it a time order: reading a time from an id is barred (ADR-0027 decisions 3 and 4), and each case carries its `run_id` whatever the order, so no order would hide it. The cost: a model may still weigh position, or read ids of the ADR-0027 form as a time order, which is not controlled here (OD-7, P2-8). Ranking from cases is OD-7 (FR-7).
- **How the output is used** is FR-15's and FR-18's (cited): a case is a hint, "과거의 기각이 재시도를 금지하지 않고 과거의 성능이 목표가 되지 않는다". This record adds no rule of its own about it.

### 2. The `basis` kind `case`, admitted

- **`kind` `case` is admitted** (ADR-0059 decision 3) with exactly these members, which only entries of this kind carry (*string*, *integer*, *name* of ADR-0001 decision 1; *text* of ADR-0002 decision 2):

| Member | Type | Meaning |
|---|---|---|
| `kind` | `case` | — |
| `case` | object with exactly `run_id`, `round` and `hypothesis` | The stored hypothesis the entry rests on: `run_id` (*string*) and `round` (*integer* ≥ 1) of the case, `hypothesis` (*name*) the `id` of a hypothesis in its `hypothesis_record`. |
| `text` | text | What of that case the hypothesis rests on: the stored hypothesis, its verdict and cause, an attempt its evidence names. |

- **Why a hypothesis and not a case as a whole**: a reference of this form names one stored hypothesis and its verdict (ADR-0072 Consequences), and everything a case holds belongs to at least one hypothesis — every candidate of a round tests one (ADR-0059 decision 4), and a verdict's evidence is of its hypothesis. A reference to the round alone would not say which.
- **The key is not restated**: the lookup is by exact match, so every case a run can read is in the key directory of its own instance (decision 1), and a restated key could only repeat it or disagree. **A later record of similar-key lookup** (OD-4 residue) would have to add the two key directory names to the reference and to the entries of decision 3 — a change inside a `basis` entry, which the exemption of ADR-0059 decision 2 does not cover — and say how a case of another key is a hint at all.
- **In-file rules** (one `hypotheses.json` shows them): the forms above; **`case.run_id` differs from the file's `run_id`** — a case of the run's own round is never cited by `case`, its attempts are cited by `attempt` (decision 1), and a kind for its own earlier hypotheses or verdicts is open (Boundaries); and **the (`run_id`, `round`) of every `case` entry is an entry of the file's `cases_read`** (decision 3) — a hypothesis rests only on a case the selection read.
- **Rules between files**, checked by no write (ADR-0059 decision 1: the write reads no other file): the named case is a valid case in the key directory of the run's instance, and its `hypothesis_record` holds a hypothesis whose `id` is `case.hypothesis`. A reader that holds both files can check them while `db/` holds the case; a pair that breaks them is reported. What checks them and when is not decided (with ADR-0071 decision 1's same item; OD-23, OD-18). Whether a case may later go away is retention (Boundaries).
- **Any stored hypothesis can be named, whatever its verdict or none**: a refuted or inconclusive case is a reason as much as a supported one, and a past rejection forbids no retry (FR-18, FR-15). A hypothesis resting on a case keeps `origin` `system` (cited: ADR-0059 decision 3: "including a hypothesis it draws from a stored case").
- **Version**: admitting a value ADR-0059 defines, with the members only its entries carry, does not raise the version of `hypotheses.json` (cited: ADR-0059 decision 2) — unlike a new kind that cites a verdict, which ADR-0071 Boundaries says would raise it, `case` is a value ADR-0059 defines. The cost is that decision's: a reader built before the admission refuses a file that uses the kind.

### 3. The identification of the cases a selection read (FR-11)

- **Place: an optional top-level member `cases_read` of the round's `hypotheses.json`** — the place ADR-0059 decision 2 names for it, in the file the selection role writes once, at the moment of the choice it records. An array of objects with **exactly** `run_id` (*string*) and `round` (*integer* ≥ 1), each naming one case the lookup of decision 1 gave this selection; the array may be empty; no entry twice; no entry whose `run_id` is the file's `run_id`; the order carries no meaning.
- **Read versus rested on**: `cases_read` lists **every case the selection was given** — what it read, whether or not a hypothesis rests on it. The `case` entries of `basis` name the stored hypotheses a hypothesis **rests on**, a subset of the cases read (decision 2). An audit (S5, NFR-2) needs the first: a lookup that gave cases none of which was used must still be visible, and so must a lookup that gave none. A tool for S6 can count from either; which one the S6 criterion counts is its metric (P2-8, OD-30).
- **Present and empty**: the selection read no case, whatever the reason — a miss, a run that states no op_signature, a key record that was reported (decision 1), a key directory without valid cases of other runs. **Absent**: the file records no identification — never read as "no case read" (the rule of ADR-0071 decision 1 for an absence, read for this member). This record reads FR-11's "그 결정이 참조한 과거 사례" as every case the lookup gave the selection, read whether or not a hypothesis rests on the case; so read, FR-18 and FR-11 require a selection of the runtime to record those cases. The member is still optional in the file's validity, and how its presence is enforced is OD-18 and OD-23 (as ADR-0059 leaves FR-17's "가설 없는 기법 선택을 허용하지 않는다").
- **Rules between files**: each entry names a valid case in the key directory of the run's instance, and the entries are what the lookup gave — the second cannot be checked afterwards, since later promotions add cases. Checked by no write, as decision 2.
- **Version**: a top-level member that may be absent and may be passed over does not raise the version (cited: ADR-0018 decision 2, as ADR-0059 decision 2 reads it). A reader that passes over `cases_read` misreads no hypothesis; it loses only the identification. The in-file rule of decision 2 ties the member to `case` entries only: a file without `case` entries is valid with or without it, every file valid before this record stays valid and means the same unless it holds a top-level member named `cases_read`, which nothing writes today (name check below), and a reader built before it refuses `case` entries anyway — so the member is not made required in the sense of ADR-0018 decision 2. Its entries are closed: adding a member to them raises the version.

### Example

Round 1 of a later run of the key of the ADR-0072 Example, which reads that case and rests `h1` on its hypothesis `h1` and on its own round 0. The later run's `run_id` is a placeholder of the form of ADR-0027 decision 2, given by no source; `NOT-DECIDED-HERE` stands for text no source gives; the `attempt` entry assumes a round-0 attempt `0000/01/01` of the later run, which no record yet says exists (OD-28), as ADR-0059's Example does. The key directory, `db/cpu_standin-b0d8610d8f470856/gemm-c43e96fb16cc3f35/` (ADR-0001 decision 7, "not the names of the real first instance"), holds `case-20261009t012331z-9f3a6c1e0b7d4a52-0001.json` and no other case. Path: `runs/20261020t093000z-0f1e2d3c4b5a6978/rounds/0001/decision/hypotheses.json`.

```json
{
  "schema_version": 1, "run_id": "20261020t093000z-0f1e2d3c4b5a6978", "round": 1, "candidates": 1,
  "cases_read": [{"run_id": "20261009t012331z-9f3a6c1e0b7d4a52", "round": 1}],
  "hypotheses": [
    {"id": "h1", "statement": "NOT-DECIDED-HERE",
     "basis": [
       {"kind": "case", "case": {"run_id": "20261009t012331z-9f3a6c1e0b7d4a52", "round": 1, "hypothesis": "h1"}, "text": "NOT-DECIDED-HERE"},
       {"kind": "attempt", "ref": {"round": 0, "candidate": 1, "attempt": 1}, "text": "NOT-DECIDED-HERE"}],
     "expected": [{"metric": "latency_minimisation", "direction": "lower"}],
     "origin": "system", "tested_by": [1]}
  ]
}
```

The `attempt` entry names attempt `0000/01/01` of the later run; the same *ref* inside the stored case names attempt `0000/01/01` of run `20261009t012331z-9f3a6c1e0b7d4a52` (ADR-0072 decision 3). Had the stored `h1` been refuted, the entry would be the same.

## Consequences

- **Code slices can be cut** (code mode, P2-7): admitting `case` with the in-file rules of decision 2 and accepting `cases_read` by decision 3 in `hilclaw/hypotheses.py` (and its counterpart in `hilclaw/hypotheses_file.py` if its text rules cover the new member); a deterministic lookup over a key directory by decision 1 that uses the hit of `hilclaw/key_records.py` and `parse` of `hilclaw/cases_file.py`, listing only the key directory; a check of the rules between files of decisions 2 and 3 for a reader that holds both. Names and call forms are those tasks'. Binding them to an agent, a prompt or a hook is not part of them.
- **A-13 reading**: document mode. The admission of `case` is the step ADR-0059 decision 2 provided for and raises no version; `cases_read` is an optional top-level member at the open top level of `hypotheses.json` and raises none (decision 3). No member, value or version of `verdicts.json`, `eval.json`, `STATE.json`, `instance.json`, `spec.json`, `artifacts.json`, `events.ndjson`, `hw_profile.json`, `op_signature.json`, `best.json`, `technique_stats.json` or the case file changes; no file or path is added and the layout version stays 1. **The case file is reached indirectly**: a case copies `hypotheses.json` whole (ADR-0072 decision 3), so a case of a later round may hold `cases_read` and `case` entries. Its schema and version, and the copy's `schema_version` 1, do not change. The rule of the copy (whole, unchanged, valid by its own record — ADR-0072 decisions 2 and 3) is unchanged, so its version raise does not apply. A case reader built before this record refuses such a case as invalid; that is the cost of ADR-0059 decision 2, carried over to the reader of a case. The copy is also checked by the in-file rules of decisions 2 and 3, since a copy is valid by its own record (ADR-0072 decision 3). Nothing was built or run, and no `claude` process was started.
- **The round-1 gap of ADR-0059 decision 3 narrows**: where round 0 left no attempt of the run (OD-28), a round-1 hypothesis can rest on a case if its key has one; with no case and no material it is still not recordable.
- **Names checked on 2026-10-16 in `hilclaw/`, `tests/` and `ARCHITECTURE/`.** `cases_read` occurs nowhere. `case` as a member name occurs once, in a test of `tests/test_hypotheses.py` that builds a refused entry `{"kind": "case", "case": "synthetic", …}`; the member defined here has the same name on purpose and a different form, and the code slice changes the tests of `tests/test_hypotheses.py` that use `case` as an unadmitted kind. `hypothesis` is the member of a verdict entry naming a hypothesis `id` (ADR-0071 decision 3), taken here on purpose for the same meaning; `run_id` and `round` are the top-level members of the case and of both copies, with the same meanings.

## Boundaries (not decided here)

- **A selection rule for many cases** — by verdict, by technique, by a bound, a summary, or by recency, which needs a time a case does not record today (a further member of a case, ADR-0072 Boundaries) — and the context cost that would call for it (OD-30 "조회해 싣는 사례의 선택과 양"); any bound needs a derivation or a source.
- **Similar-key lookup** and cases of another key (OD-4 residue; FR-18); **ranking** of cases or of techniques from cases and the statistics of `technique_stats.json` (OD-7, FR-7); the candidate archive and `best.json` (OD-20); `insights/` and agent memory (OD-24).
- **Carrying cases to the coder**: any spec member that would hold cases of another run — a change of `spec.json` (ADR-0002 `feedback.attempts` names attempts of the same run only).
- **Injection in any form** — at instance start, at a gate or during a run — the admission of `origin` `injected`, the identification of injected hypotheses (FR-11), who derives a hypothesis from material, and the distribution of injected and system hypotheses (owner, HQ, per the OD-30 section; FR-15).
- **Promotion**: when, by whom and whether every round is promoted, so whether a run's own cases appear while it runs (OD-29, OD-23, OD-17, NFR-1, with ADR-0072's same item); **retention and removal** of cases, so whether a cited case can go away (OD-11; #5 A-1 at P2).
- **Owner-only (DRIVER §9)**: OD-25 — sharing of cases across forks or data repositories and two repositories that hold one `run_id`; #5 A and B items, C-6, OD-3. Nothing of them is touched.
- **Reading a case of another version** — of the case, a copy, the source run's layout — or whose source commit or harness differs from the reader's, which a case does not record (OD-11); further members of a case (ADR-0072 Boundaries).
- **A `basis` kind that cites an earlier hypothesis or verdict of the reader's own run** (ADR-0059 Boundaries; OD-30 "판정을 가리키는 `basis` 종류") — `case` is not that kind.
- **Round 0's use of cases** in bring-up; how a report of a set-apart or invalid case is carried and whether a selection may go on after it; what checks the rules between files of decisions 2 and 3 and when; how a selection is made to take the lookup's output and record `cases_read` (OD-18, OD-23).
- **The S6 metric**, its boundary cases, repetitions and control (P2-8), and the runtime acceptance of P2-9.
- Code, tests, schema files and prompts (P2-7's later slices); any change to an accepted record or to the `HIL-Claw-data` repository; any new external dependency.
