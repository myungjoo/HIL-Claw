## Decision

A sentence is **cited** when a source is named with it. Every other sentence is **this record's own**.

### 1. Scope and terms

- **The sessions**: every `claude -p` turn session that the turn loop of ADR-0118 decision 3 starts for a run of ADR-0118 decision 1, in either mode — the autonomous form and the checkpoint form in which the gate ends the session (ADR-0118 decisions 2 (ii) and 3). Inside such a session: **the main session** (the Round-Manager, ADR-0118 decision 2) and **the sub-agents defined under `orchestration/agents/`** — today the evaluator (ADR-0128 decision 7).
- **Outside**: an interactive checkpoint session whose permission prompt is the gate (UC-2 비고; ADR-0118 decision 3) — its mode rides on the gate layer (OD-3, #8 M3) and nothing here is required or allowed of it; the coder's own `claude -p` in its container (ADR-0049; HQ-0053); the self-check's session (ADR-0054, ADR-0057), whose command line is unchanged; runs outside ADR-0118 decision 1.
- **The coder-driver** is not defined yet; decision 8 states only the rule by which its entry is added.
- **Pre-approved list**: the value of `--allowedTools`. **Built-in set**: the value of `--tools`.

### 2. (a) The permission mode: `dontAsk`, passed explicitly

- **Every turn session is started with `--permission-mode dontAsk`.** A call that is not pre-approved and would prompt is denied, and the session never waits for input (P1). An explicit mode overrides any `defaultMode` of a settings file (P2), so no settings file on the runtime machine can turn a turn session into `acceptEdits`, `auto` or `bypassPermissions`.
- **Why not leaving the mode unset.** From v2.1.302 a `-p` run without a mode starts in `default` and denies calls needing approval as well (P2). But that is a version-dependent default and a `defaultMode` of a settings file would replace it; an explicit `dontAsk` states the behaviour on the command line, and it is the mode the self-check already runs with (ADR-0054 decision 4; ADR-0057).
- **A denial is not a failure of the turn**: the model receives the denial and goes on (P1). What the Round-Manager then does is its definition's; this record adds no rule to it.

### 3. (b) The pre-approved tools: exact names, from two sources

- **Form.** Every MCP entry is an exact `mcp__hilclaw__<name>` (P3; ADR-0010 decision 4). **Neither `mcp__hilclaw` nor `mcp__hilclaw__*` nor any other wildcard** is pre-approved: the registry already holds tools no agent of the definition names (`blob.push`, `blob.fetch`, and `spec.write` until a coder-driver exists), and every tool registered later would become callable without a record naming its caller. Built-in entries are bare names (decisions 4 and 6); the delegation entries are `Agent(<name>)` (P3).
- **Source 1 — the Round-Manager: a fixed list in the layer-2 code.** The main session's prompt carries no machine-readable tool list, and a scan of its text for MCP names would also grant every name it mentions only to forbid. So the code that builds the command line holds the Round-Manager's list: today `mcp__hilclaw__state_read`, `mcp__hilclaw__instance_read`, `mcp__hilclaw__run_fresh`, `mcp__hilclaw__state_write`, `mcp__hilclaw__run_commit`, `mcp__hilclaw__key_store`, `mcp__hilclaw__case_write` and `mcp__hilclaw__round_end` — exactly the tools the records give it (cited: ADR-0124 decision 3; ADR-0127 decision 2; ADR-0133 decision 6; ADR-0134 decisions 2 and 3; ADR-0135 decisions 2 and 6). A later record that gives the Round-Manager a tool adds it to this list in the same code slice that edits its prompt.
- **Source 2 — the sub-agents: derived from the definition the turn actually has.** Before each turn starts, after the definition has been copied (ADR-0118 decisions 4 and 5), the code reads every agent file in the session directory's `.claude/agents/`. From each it takes the frontmatter `name` and `tools`. The pre-approved list gains `Agent(<name>)` for each agent, and every entry of each `tools` list. So the list follows the definition a turn runs with: an agent or tool added under `orchestration/` is pre-approved at the next turn, and one removed is not.
- **What the code refuses**, before the session starts and with a fixed text, as the turn loop already refuses a bad place: an agent file with no `tools` list (an omitted list inherits every tool, P8); a `tools` entry that is neither an exact `mcp__hilclaw__<name>` nor one of the built-in names `Read`, `Grep`, `Glob` (decision 6), a wildcard or another server's name among them; and a `permissionMode` in the frontmatter (it could set a mode other than the session's, P8). The frontmatter is read without a new external dependency; the accepted text form is the code slice's.
- **The list is the union of both sources**, sorted and without repeats (the order is the code's). It is passed as one `--allowedTools` argument joined by commas, as the self-check passes its list (ADR-0057; its item (x)).

### 4. (c) The main session's built-in tools: closed by `--tools`

- **Every turn session is started with `--tools` naming exactly `Agent` — when `.claude/agents/` holds at least one agent — and the built-in names that the agents' `tools` lists hold** (today `Read`, `Grep`, `Glob`). With no agent the value is `""`, as the self-check passes it. `--tools` restricts the built-in tools and leaves MCP tools alone (P5), so the `hilclaw` tools stay reachable.
- **So the main session has no `Bash`, `Write`, `Edit`, `NotebookEdit`, `WebFetch` or `WebSearch`**: the shell and writing half of the Round-Manager's "not Bash or file tools" (ADR-0124 decision 2; ADR-0127 decision 2; ADR-0133 decision 6; ADR-0134 decisions 2 and 3; ADR-0135 decisions 2 and 6) is **no longer held by its prompt alone** but by the session's tool set, which is what the owner premise "프롬프트만으로 쓰기 구역을 주는 것은 너무 약하다" asks of a write zone (K2). The reading half stays a rule of its prompt: it has `Read`, `Grep` and `Glob` (decision 6), and reading is not restricted (K2). The rule of ADR-0127 decision 2 that the Round-Manager commits by no other means than `run.commit` gets the same support: no shell, so no `git`.
- **Why a closed list and not `--disallowedTools`.** A deny list must name every tool to remove, and a built-in tool added by a later Claude Code version would stay; `--tools` names what there is. A bare name in `--disallowedTools` also removes the tool from the sub-agents' pool (P5, P8), so it could not take a tool from the main session alone either.
- **Why `Agent`.** It is the tool by which the Round-Manager delegates to the evaluator (cited: ADR-0128 decision 2; P8, renamed from Task). Without it in the built-in set no delegation is possible.

### 5. (d) How sub-agents get their permissions

- **Two filters and one rule set.** A sub-agent's tools are those of the main session's pool — the built-in set of decision 4 and the `hilclaw` MCP tools — narrowed by its `tools` list (P8; ADR-0010 F3). Its calls run in the session's mode, because no definition sets `permissionMode` (decision 3) and an unset one inherits the main conversation's (P8). **This record reads** that its calls are approved by the session's pre-approved list as the main session's are — the documentation says so of built-in sub-agents (P8) — and makes that reading item (xxxvii).
- **What each part does.** The `tools` list decides **which tools a sub-agent has**: the evaluator has no `Write`, `Edit` or `Bash` and "no tool that delegates further" (cited: ADR-0128 decision 3) and cannot call `mcp__hilclaw__state_write` even though the session pre-approves it for the Round-Manager. The session's list decides **which calls run without a prompt**: a tool in an agent's `tools` list but not pre-approved would be denied in `dontAsk` — which decision 3's derivation prevents for every listed tool.
- **What it does not do: separate the main session from its sub-agents' MCP tools.** The pool is shared, so the session pre-approves the evaluator's tools for the main session too: the Round-Manager *can* call `mcp__hilclaw__correctness_check` or `mcp__hilclaw__verdicts_write`, and that it does not rests on its prompt (cited: ADR-0128 decision 2, "The Round-Manager evaluates nothing itself and calls no HW tool"). This record states it as a limit, not as a rule it keeps by a prompt: a later hook can tell the calling sub-agent by `agent_type` (cited: ADR-0010 decision 6) and is PLAN P2-4's (Boundaries).
- **Delegation to an agent that is not the definition's.** `Agent(<name>)` is pre-approved only for the agents of the definition. Whether a delegation to a built-in agent (`general-purpose`, `Explore`, `Plan`) is denied under `dontAsk` depends on whether the `Agent` tool needs approval at all, which no page read states; it is item (xxxviii). Such an agent would in any case have no built-in tool beyond decision 4's set.

### 6. (e) The evaluator's unrestricted reading

- **The built-in names `Read`, `Grep` and `Glob` are pre-approved as bare names**, which match every call of those tools (P3), because a read outside the working directories is approved by nothing else: read-only tools need no approval only inside them (P4), and `dontAsk` denies what would prompt (P1). Without this a `Read` of the data checkout — which is no working directory of the session (ADR-0124 decision 2 gives no `--add-dir`) — would be denied, against "what it reads besides, by `Read`, `Grep` or `Glob` wherever it finds a path, is not restricted" (cited: ADR-0128 decision 4) and the owner premise "읽기 제한은 채택하지 않는다" (K2). Whether a pre-approved bare `Read`, `Grep` or `Glob` then reads outside the working directories without a prompt is item (xxxix).
- **The Round-Manager gets the same reads** today: the three names are in the built-in set (decision 4) and pre-approved for the session (decision 3) because the evaluator's `tools` list holds them. A definition whose agents named none of them would leave the main session no read tool: the prompt's "Reads elsewhere are not restricted" (`orchestration/round-manager.md`) grants none by itself.
- **What stays denied**: reads from network paths, which `dontAsk` denies even when allowed (P1); and anything a managed setting or a `blockReadsOutsideWorkingDirectories` of a source the session reads fences off (P10) — a fact of the runtime machine, which this record neither presumes nor overrides.
- **Why not `--add-dir` of the data checkout.** It would cover one directory, not an unrestricted read, and it is not given (cited: ADR-0124 decision 2).

### 7. (f) The setting sources: `--setting-sources project`

- **Every turn session is started with `--setting-sources project`**, as the self-check is (ADR-0057). The project is the session directory, so what loads is the definition's `.claude/settings.json`, where the hooks of PLAN P2-4 would live (ADR-0118 decision 5), and no `settings.json` of the runtime user's `~/.claude/` and no `settings.local.json`. **This record's reading of P6**: the user's hooks, allow rules, `defaultMode`, `env` and other settings keys then do not act on a turn session.
- **Against ADR-0118 item (ii).** That item asks which files of the user's `~/.claude/` a session loads "and what the flags the definition picks exclude of them". This flag is that pick for settings files. What it does to the user's `CLAUDE.md`, agents and skills, and whether managed settings still apply, stay item (ii); items (xxxiv) and (xl) add the parts this record relies on.
- **The login.** Whether a session started with `--setting-sources project` still reads the stored login is not stated (P6; ADR-0054 K7). It needs no separate claim here: the self-check runs with the same value before the first turn of every start (ADR-0125 decision 2), so a start whose check passed has shown, on that machine and version, that the login is read under it (one observation, ADR-0054 L2).

### 8. (g) The session directory's settings carry no permission rule; nothing is written into the user's configuration

- **The definition's `.claude/settings.json` carries no `permissions` member** (and none exists: `orchestration/` holds no `settings.json`). Its allow rules would not be used in a directory never trusted (P7) and would start to act if the user ever trusted that path, so one definition would act differently with the machine's trust state. Every permission of a turn session is on its command line, built by tested code.
- **No write into the runtime user's configuration** is made or presumed: no trust record in `~/.claude.json` (P9), no edit of `~/.claude/settings.json`. The means does not need trust: the flags of decisions 2 to 7 are what the documentation shows for `-p` runs with no trust step (P1, P7), and whether they take effect in a never-trusted directory is item (xxxiv).
- **The command line** of a turn is then `claude -p <prompt> --mcp-config hilclaw-turn.mcp-config.json --strict-mcp-config --setting-sources project --tools <built-in set> --permission-mode dontAsk --allowedTools <pre-approved list>`; the part up to `--strict-mcp-config` is as ADR-0118 decision 6 and the code have it, and the order of the options after it is the code slice's.

### 9. The coder-driver's entry, under either answer to HQ-0040

- **Its definition adds its entry by the rule of decision 3**: `orchestration/agents/coder-driver.md` with a `name` and a `tools` list. Its MCP entries — `mcp__hilclaw__spec_write` (ADR-0138 decision 3) and, under (T), the tool of the call (ADR-0126 decision 3) — are pre-approved by derivation, with no change of this record or of the code. Under (T) nothing else changes.
- **Under (B)** its list holds `Bash`, which decision 3 refuses. **The record that answers the coder-driver's form adds `Bash` to the accepted built-in names together with the pattern its pre-approval takes** — a `Bash(<entry command> *)` form rather than the bare name, so that `dontAsk` denies every other command (P1, P3). It weighs then what this record states now: `Bash` would join the built-in set of decision 4 and so be the main session's too (P8), with only the entry's commands pre-approved for both; and a pattern matches strings (ADR-0010 decision 3, "Permission rules of the session can narrow commands by pattern, but they are not per agent and match strings"). This record chooses neither (B) nor (T).

### 10. No bypass

- **No turn session is started with `--dangerously-skip-permissions`, `--allow-dangerously-skip-permissions` or `--permission-mode bypassPermissions`**, and decision 2's explicit mode keeps a settings file from setting one. In `bypassPermissions` allow rules have no effect and every tool not denied runs (P2), which would undo decisions 3 to 6. The owner's "never with a bypass flag" was said of the self-check (K3); this record takes it for turn sessions as its own choice (Status).
- **A means without a bypass flag exists**: the documented `dontAsk` with pre-approved tools (P1), which the owner's own check by hand and the self-check already use (K3; ADR-0057). No owner-only item and no write into the user's configuration is needed.

## Alternatives considered

| Alternative | What it gives | Outcome |
|---|---|---|
| `dontAsk` with exact pre-approved tools, from a fixed list and the agents' `tools` lists, built-ins closed by `--tools` | Calls the definition names run; nothing else runs and nothing waits | **Chosen** |
| The same, but the server as a whole (`mcp__hilclaw` or `mcp__hilclaw__*`) | Every registered tool, `blob.*` and every later tool included, runs without a record naming its caller | Rejected (decision 3) |
| `default` mode, or no mode | From v2.1.302 also denies what needs approval in `-p`, but version-dependent and replaceable by a settings file's `defaultMode` (P2) | Rejected (decision 2) |
| `acceptEdits` | Approves file edits and common filesystem commands in the working directories (P2), which no agent of the definition needs; a sub-agent's own mode would then be ignored (P8) | Rejected |
| `auto` or `plan` | `auto`: a classifier's checks, not a fixed list, whose verdicts the driver has seen vary on one setting (DRIVER §1-5, HQ-0001); `plan` is no working mode | Rejected |
| Permission rules in the session directory's `.claude/settings.json` | Allow rules not used without trust (P7), and used once the path is trusted | Rejected (decision 8); deny rules there stay possible for a later record |
| `--settings` with a generated file or inline JSON | The same rules as the flags, one more artefact per turn; whether its allow rules need trust is not stated | Not taken; the first fallback if item (xxxiv) shows the flags ignored |
| A trust record in `~/.claude.json` | A write into the user's configuration (against ADR-0118 decision 4); per path, while the loop makes a new directory per turn; would also switch on project allow rules | Rejected |
| A bypass flag or `bypassPermissions` | Everything not denied runs; allow lists have no effect (P2) | Rejected (decision 10) |
| `--disallowedTools` instead of `--tools` | An open deny list; a bare name also empties the sub-agents' pool | Rejected (decision 4) |
| The main thread as an agent (`--agent round-manager`) with its own `tools` | Would narrow the main session's MCP tools, but the sub-agents draw on the main conversation's pool (P8), so its list would have to name the evaluator's tools anyway; moves the prompt out of `CLAUDE.md`; nothing on it read for `-p` | Not taken; per-agent separation goes to the hooks (P2-4) |
| `--restricted` or `--bare` | `--restricted` confines file tools to the working directories and loads no project settings (P9), against decision 6 and the P2-4 hooks; `--bare` reads no OAuth credential (ADR-0054 K11) | Rejected |
| `--add-dir` of the data checkout for reads | One directory, not unrestricted reading; not given (ADR-0124 decision 2) | Rejected (decision 6) |
| Leave it open | No turn session can call a tool: P2-5's run, the nightly run of P2-10 and P2-14 wait | Rejected |

## Consequences

- **Code slices for the planner** (code mode; tests with a stub `claude` that checks the exact argument list, never a real one — D16; each within the D4 cap):
  1. **The command line of `hilclaw/turn_loop.py`**: the options of decisions 2, 4, 7 and the list of decision 3, built after `put_definition` from the session directory's `.claude/agents/` and the fixed list, with the refusals of decision 3 (a new module for the frontmatter reading and the list, with its test file, if the slice prefers). It makes false the docstring sentence "No permission, model, turn-limit, setting-source or bypass option is passed: how a turn session is given its permissions is not decided (ADR-0118 decision 4, "Workspace trust")", the "and nothing else" of "**The command line**", and "no permissions" under "Not done here"; the slice rewrites them. `hilclaw/turn_start.py` needs no change unless the slice puts the fixed list there.
  2. **When the coder-driver is defined** (after HQ-0040): nothing for (T); for (B), the record of that slice per decision 9.
- **Runtime acceptance items** (D16; nothing was tried, nothing is required of the development machine). **Item (vii) of ADR-0118 now has its means: decisions 2 to 8.** Whether the means works is still that runtime acceptance item, now split into the items below; ADR-0128 item (xviii) and ADR-0138 item (xxxiii) ("under whatever permission means item (vii) gets") refer to this means. **New**, numbered after the last on `main`, ADR-0138 (xxxiii):
  - **(xxxiv)** In a session directory never trusted, a `-p` turn session started with the command line of decision 8 applies `--permission-mode dontAsk`, `--tools`, `--allowedTools` and `--setting-sources project` (P7 is silent on flags).
  - **(xxxv)** The main session calls each pre-approved `mcp__hilclaw__` tool without a prompt, and a call of a `hilclaw` tool not on the list is denied without a wait while the session goes on.
  - **(xxxvi)** `--tools` accepts `Agent`, `Read`, `Grep` and `Glob` by those names; the session then has no other built-in tool that runs commands or writes files; and the `hilclaw` tools stay reachable under tool search (ADR-0054 K14). A self-check that passed shows the last part only for `--tools ""`.
  - **(xxxvii)** A sub-agent of the definition with no `permissionMode` runs in `dontAsk`, its calls of tools in its `tools` list run when the session pre-approves them, and a tool in its list that the session does not pre-approve is denied.
  - **(xxxviii)** `Agent(evaluator)` lets the Round-Manager delegate to the evaluator; whether a delegation to a built-in or user agent is denied; and, on Windows where `claude` may be a command script, that the parentheses and commas of the list reach Claude Code as written (as ADR-0057 item (xiv) asks for its own arguments).
  - **(xxxix)** Pre-approved bare `Read`, `Grep` and `Glob` read files outside the working directories — the data checkout among them — without a prompt in `dontAsk`.
  - **(xl)** Under `--setting-sources project`, no hook, allow rule, `defaultMode` or `env` of the runtime user's `~/.claude/settings.json` acts on the session, while the session directory's `.claude/settings.json` is read (with item (ii) of ADR-0118 for the rest of `~/.claude/`).

UC-2 비고 ("도구 권한 승인 UI가 곧 HIL gate로 동작한다") concerns the interactive checkpoint session, which is outside (decision 1). StandardScenarios: no verdict changes (S0, S1, S2 rechecked).

- **The cost, plainly.** The per-agent separation of MCP tools is held for sub-agents by their `tools` lists, but for the main session by its prompt: the Round-Manager can call any tool the evaluator may, `verdicts.write` and `correctness.check` among them, until a hook tells callers apart. Every turn session can read any local file its OS user can — the user's Claude Code credentials included — because reading is not restricted (K2); keeping such files from a session is not decided. Whether a delegation to a built-in agent is refused is unknown. Every new agent or tool reaches a session only through a definition change, and a definition with a tool outside the accepted forms stops every turn until fixed. If the flags prove ignored in an untrusted directory (xxxiv), `--settings` is the first fallback and this record is revisited.
