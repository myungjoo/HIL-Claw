## Decision

A sentence is **cited** when a source is named with it. Every other sentence is **this record's own**.

### 1. Scope

- **One spec**: that of the first coder call of round 0 — `round` 0, `candidate` 1, `attempt` 1 — of a run of ADR-0120 decision 1 whose `instance.json` states `candidates_per_round` 1 and an `op_signature` that ADR-0041 decision 5 covers (`gemm`, `fp32`, `row_major`, every dimension at least 1), so that the contract of ADR-0008 applies.
- **Outside**: every other spec — later rounds, other candidates, repair attempts, runs whose N is not 1 — and everything under Boundaries. Nothing here is required or allowed of them.

- **(a) The objective.** The spec carries the objective and the constraints its instance states, because its `task.objective` is that member, read at the same call. **This answers the § OD-6 point "spec이 자기 instance가 적은 objective·제약을 싣는지" for this spec, by construction**: no separate check of a stored spec against its instance is added, and a spec written by any other means is checked by nothing (ADR-0053 decision 6 stays true for it). A run whose file states no `objective` gets no spec (decision 3, ⑥): nothing is substituted (cited: ADR-0053 decision 5, "not `latency_minimisation`").
- **(b) The technique list: empty, with these grounds.** Round 0 "applies no technique" (cited: ADR-0059 decision 5, which adopts the OD-30 proposal on that ground and gives round 0 no hypothesis record); its first round is "not '기법 적용'" but bring-up (cited: G1); and FR-1 places "기법 선택" in the round loop and round 0 beside it as bring-up and baseline (cited). The baseline is that bring-up code (cited: ADR-0119 decision 2). So `guidance.techniques` of this spec is the empty array, whose form ADR-0002 gives ("may be empty"). **What the empty list says stays what ADR-0058 decision 1 says**: no technique to apply in this call, and no more. **This record does not say** whether a coder that gets none may choose a technique itself (OD-23, OD-12), which techniques any later round selects or how (FR-8, OD-7), or anything of the catalog (OD-22): it names no catalog entry.
- **(c) What the spec does not carry, and why that is not a decision about round 0.** No reference, stored case or injected input reaches this spec, because version 2 has no field for them and names no `ext` member that would carry one (cited: ADR-0002 decision 7, reference pointers "go into `ext` until a later record makes them fields"). **This is a limit of the schema, not an answer** to whether round 0 uses injected inputs or cases (OD-28; FR-15; ADR-0073, ADR-0075 Boundaries): a later record that decides it names the field or the `ext` member, and the tool of decision 3 changes with it.
- **No verification input** is in the spec: every shape it holds is the op_signature shape or follows from it (cited: ADR-0002 decision 2; ADR-0008 decision 5).

### 3. (b) What composes and writes it, and when: the registry tool `spec.write`

- **The role stays the coder-driver's** (cited: ADR-0126 decision 4; ADR-0004 decision 4, `coder/` "writes the spec before the call"). **The coder-driver has the spec written by calling the tool `spec.write` through the package's MCP front**, with the run id and the tuple its delegation gave it (cited: ADR-0126 decision 6), **before** it requests the coder call in the form HQ-0040 gives. The tool composes and writes; the coder-driver composes nothing and writes no file of the run with its own file tools (K2, K3; ADR-0126 decision 2).

| Part | Content |
|---|---|
| Name (MCP name) | `spec.write` (`mcp__hilclaw__spec_write`); no `_` in the name, so the mapping of ADR-0010 decision 4 stays reversible |
| Request | Exactly `run_id`, `round`, `candidate`, `attempt`, all required, with the meaning and form of ADR-0015 decision 4. Any other member, one missing, or a tuple other than `round` 0, `candidate` 1, `attempt` 1 is `invalid_request` (the precedent of ADR-0133 decision 3, which refuses `round` 0) |
| Result | The empty object, as `state.write` returns it (ADR-0124 decision 3) |
| Checks, in order | ① the request (`invalid_request`, ADR-0015 decision 2); ② the data root (`no_data_root`); ③ the run's `instance.json` read and parsed as a whole, as `instance.read` reads it (`run_file_missing`, `run_file_invalid`, `run_file_unsupported`, `run_file_unreadable`); ④ `candidates_per_round` stated (`candidates_per_round_not_stated`) and equal to 1 (`candidates_per_round_not_covered`); ⑤ `op_signature` stated (`op_signature_not_stated`) and covered by ADR-0041 decision 5 (`op_signature_not_covered`); ⑥ `objective` stated (`objective_not_stated`); ⑦ the document of decision 2 composed and encoded, and the content in the written form of ADR-0029 decision 2 (a final line feed, no carriage return), accepted by `hilclaw.spec_file.parse` (which applies `hilclaw.spec.validate`) and given its final name by `hilclaw.spec_file.final_name` (`spec_invalid`); ⑧ the content written by `hilclaw.spec_file.write`, the steps of ADR-0029 decision 4 (`spec_exists` for a taken final name, `spec_not_written` for any other failure of the file system, a data root gone since ② among them) |

- **Every check before ⑧ creates nothing**, and only the run's `instance.json` is read, at this call, with nothing kept (cited: ADR-0018 decision 4; ADR-0053 decision 7). **Reading is the tool's step, not the write's**, as ADR-0133 decision 3 has it for `case.write`: `spec_file.write` still "reads no other file and checks the content against none" (cited: ADR-0029 decision 4). `STATE.json` is not read, so no order against it is fixed (OD-8 ㉖ (다) stays open); the order "after `instance.json`" follows from ③ and is already that of ADR-0120 decisions 2 and 3 and ADR-0134 decision 5 (cited).
- **⑦ cannot refuse today**: a valid file's members are valid records and a valid objective, the member's form is the spec's (cited: ADR-0018, ADR-0031, ADR-0053 decision 4), and the `run_id` passed ① in the form of ADR-0015 decision 4. It is kept so that a later record that widens one form without the other is answered with a kind and not written. Because ⑦ checks the very content ⑧ writes, every refusal `spec_file.write` has for a content is met before it, and ⑧ can fail only on the name or the file system.
- **A taken final name** (ADR-0029 decision 4): `spec_exists`; nothing is written and nothing under the name is read or compared (cited: same decision, "compares nothing"). **This record decides no more about it.** Whether the coder-driver then requests the call with the file already there — a file this tool may not have composed, which nothing compares with what it would compose — what the Round-Manager does, and what a second write for a tuple means stay open (OD-8 ㉖ (가); OD-23 ① (가)).
- **After any other kind the coder-driver requests no call**: no spec of the tuple was written by this call, so a call would read none (`spec_unreadable`, ADR-0126 decision 3) or one this record does not vouch for. In every case it reports the kind to the Round-Manager (cited: ADR-0126 decision 6).
- **Kinds.** Reused with their meanings: `invalid_request`, `no_data_root` (ADR-0015 decision 2); the four `run_file_*` kinds of ADR-0019 decision 3 — **this record widens ADR-0019 decision 2's "only at the lookup or the selection" to this read**, as ADR-0124, ADR-0133 and ADR-0134 did; the property holds: such a call appended no line, selected no backend, ran no step and consumed nothing; `op_signature_not_stated` and `op_signature_not_covered` (ADR-0041 decisions 4 and 5) and `objective_not_stated` (ADR-0061 decision 4), the same names for the same situations of the run's file on purpose; `spec_invalid` (ADR-0126 decision 3), here for the composed content. **New**: `candidates_per_round_not_stated` (31 characters), `candidates_per_round_not_covered` (32), `spec_exists`, `spec_not_written`, each a *name* of ADR-0001 decision 1, formed like `tolerance_not_stated`, `case_exists` and `case_not_written`. Searched on 2026-10-21 in `hilclaw/`, `tests/`, `orchestration/` and `ARCHITECTURE/`: `spec.write`, `spec_write` and the four new names do not occur. **Each kind is a name of the tool layer, not a value of the data plane**; none is reserved.
- **Not journaled**: it costs no limited resource, and its outcome is the file (as ADR-0124 decision 3 reads `state.write`); no `step` value (ADR-0100) and no event kind is added. It is a tool of the registry beside the FR-10 tools, added to `default_registry` in the source and in no other way (cited: #5 A-12 point 3), and reachable through the command-line front for people, tests and scripts (ADR-0010 decision 3). It does not check the hw_profile's accelerator: it is defined for, and given to, the coder-driver of these runs only, as ADR-0134 decision 3 reads `key.store`.
- **Left to the code slice**: the module, the description and input schema, the message texts, and the encoding of the document into bytes in the written form (cited: ADR-0029 decision 2, as ADR-0051 carries it).

### 4. (c) Why the means holds under either answer to HQ-0040

- **HQ-0040 asks how the coder-driver reaches the coder-call function** — (B) a command-line entry through its Bash tool, or (T) the registry tool `coder.run` through MCP (cited: ADR-0126 decision 3, Q1). **The spec write is a separate step with its own tool**, and a sub-agent of a turn session can be given a tool of the package's MCP server in either case: the server is the session's (cited: ADR-0118 decision 6), and a per-agent allowlist names an MCP tool alone (cited: ADR-0010 decision 3). Under (T) the coder-driver uses the MCP front for both steps; under (B) it uses it for the write and Bash for the call.
- **Under (B) nothing of the write moves to Bash**, so the answer (B) to OD-18 sub-question ② and its consequence for ADR-0010 decision 3 (cited: ADR-0126 Consequences, Q1) concern the call only. A write made through the MCP front keeps what ADR-0010 decision 6 gives a typed tool: a hook sees `run_id` and the tuple as data. Under (B) nothing stops the coder-driver from running the tool's command-line front through its shell instead ("the shell as a whole", ADR-0010 decision 3); the definition tells it to use the MCP front, which is a rule of the definition and no guard (K4).
- **Why not fold the write into the coder-call function.** The function and its failure kinds are fixed by ADR-0126 decision 3, which takes the spec file as already written (`spec_unreadable` for a missing one); folding would change that record, and the composition would then reach the coder-driver through whichever front Q1 gives. Kept apart, this record changes nothing of ADR-0126, and its code slice does not wait on Q1.

It fits the D4 cap.
  2. **After HQ-0040**: the definition `orchestration/agents/coder-driver.md`, given `mcp__hilclaw__spec_write` by the means the record of that slice chooses (ADR-0118 decision 6 leaves it open; the coder-driver's allowlist is rest of OD-23), with the order "write the spec, then request the call; no call after a failure other than `spec_exists`" — what follows `spec_exists` waits on ㉖ (가), and until then the definition says only that the kind is reported — and the delegation step of `orchestration/round-manager.md` (ADR-0126 Consequences, slice 2; PLAN P2-1).
