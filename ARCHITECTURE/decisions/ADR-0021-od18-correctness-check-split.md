## Decision

A sentence marked **owner** renders the HQ-0004 answer and quotes it. A value is **cited** when another source is named with it. Every other value is **this record's own** choice — among them the place of the cut, what crosses it, who draws the seed and when, the moment of the tolerance, the kind `tolerance_not_stated`, the class of a broken run and the order of its conditions, and the reading of FR-9's "동일 검증" in decision 3.

### 1. Scope and terms

- This record is about **a call of `correctness.check` about one attempt of a run of the first case** — `cpu_standin`, kind `gemm`, fp32, a C kernel (ADR-0017 decision 1) — and of the contract of that call it fixes **four points and nothing else**: the split (decision 2), the seed (decision 3), the tolerance (decision 4) and the classes of outcome (decision 5).
- **It is not the whole contract.** Before the tool can be registered a second record must add at least: whether the tool is journaled, its `step` value or values and the meaning of `execution` for it; how a call says at which execution point it is made, and which HW tools `cpu_standin` offers (OD-18 sub-question ⑦); the members of the request, the input schema and the description; where `draws`, the dimensions, the kernel of the attempt, the flags and the time limits come from; the members of the result and the tool-failure kinds a backend may raise; the spend; the operation and the default script of the mock. All of these are Boundaries here.
- The four points are stated so that they hold **whether or not the tool is journaled and at either execution point**, and they rest on nothing that only one backend has. The moments ① to ⑦ are those of ADR-0016 decision 2; a sentence about ③, ⑤ or ⑦ applies only if the tool is journaled.
- The terms of ADR-0010, ADR-0015, ADR-0016 (backend, operation, target, script) and ADR-0017 (verification run, draw, report, check value, completed, broken, pass, fail) are used unchanged. **The cut**: the line between the tool function's part and the operation's part of one call. **A check**: one call that reaches ⑥.
- **Which runs.** Of what makes a run one of the first case, its `instance.json` states the accelerator, in its `hw_profile`, and does not state the kind, the dtype or the kernel language (cited: ADR-0020 decision 2). **A run whose hw_profile names another accelerator — the name reserved for the mock included (ADR-0016 decision 5 (b)) — is not a run of the first case, and what a call answers for it is not decided here**: the oracle and the tolerance vocabulary of another backend are owner-only (#5 B-7; ADR-0017 Boundaries), ADR-0020 decision 2 gives the member `tolerance` a meaning for a run of the first case only, and whether a run at the mock is answered by this contract is sub-question ⑩. What a call answers for a run at `cpu_standin` of another kind, dtype or kernel language, which the file does not show, is not decided either (the same sub-question).

### 2. The split between the one harness and a backend

- **The operation's part: the kernel is carried out at the target on inputs the target draws from the seed of the call, and what the kernel's process reported is returned, uninterpreted.** In the terms of ADR-0017: starting the process of the verification executable with the dimensions, `draws` and the seed, under its time limit, and capturing its report. An operation computes no reference, compares nothing and gives no verdict.
- **The tool function's part, the same code for every backend**: besides what ADR-0016 decision 2 (a) already gives it, drawing the seed (decision 3); reading the tolerance (decision 4); and, on what the operation returned, **all of the judging** — whether the report has the form of a complete report for the dimensions and `draws` of the call, regenerating the inputs of each draw from the seed, comparing the check values (the input check of ADR-0017 decision 4), computing the float64 reference, applying the owner's predicate with the tolerance of the run, deciding completed or broken and pass or fail (ADR-0017 decisions 4, 5 and 7, unchanged). It is carried out by the code of the harness sub-module (FR-9), in the process of the tool function.
- **The build of the verification executable is not the tool function's part.** It needs the compiler and the flags of one target, and the tool function is the part that is the same for every backend (cited: ADR-0016 decision 2 (a)). Whether an operation builds at each call or is given something built, by whom and from which source, is not decided (ADR-0004 decision 3; OD-23; sub-question ⑩); neither is what a call answers when no verification executable can be had.
- **What an operation of this tool is handed**, beyond the request and the hw_profile (cited: ADR-0016 decision 2), as classes: (i) **the seed of the call**; (ii) **`draws` and the dimensions** `m`, `k`, `n`; (iii) **what it needs to obtain and run the verification executable of the attempt at its target** — the kernel of the attempt or something built from it, flags, the time limit of the process, the environment. For (iii) this record says only that the operation's side needs it; whether the tool function hands it over or the backend obtains it otherwise, and whether an operation is handed the data root (ADR-0016 decision 2 (d)), is the second record's. **An operation is never handed the tolerance, a reference or an expected output**, and nothing in a request of this tool carries one to it (decision 4).
- **What an operation returns**, as classes, exactly one of: (A) **the report** — what the process wrote on its report channel, unchanged, when the process ended by itself with exit status 0 within its time limit; (B) **that there is no such report, and which of two conditions failed** — the time limit, or a non-zero status or a signal (told apart no further than ADR-0017 decision 7 does); a process that was ended for its time limit is reported as the time limit. An operation does not judge the form or the content of a report. A backend may also raise a tool failure where the complete contract lets it (decision 5); this record names no such kind. **Whether anything else the process wrote — its standard error — crosses the cut is not decided** (decision 3, the open question). The spelling of what is handed and returned is the second record's and the code task's; how a report is represented when the target is another machine, whose `float` bytes need not be those of the host of the tool function (ADR-0017 decision 7: "both sides run on one machine"), is not decided (#5 B-2).
- **Which side needs which parameter of ADR-0017 decision 9 for its own part**:

| Parameter | Tool function | Operation |
|---|---|---|
| `m`, `k`, `n`; `draws` | yes — the form of the report, the regeneration | yes — the draws, the size of the report |
| Seed | draws it (decision 3); regenerates from it | yes — handed by the tool function |
| `rtol`, `atol` | yes — reads them (decision 4), compares | **never** |
| Time limit of the process; environment and working directory | no | yes |
| Flags, compiler, build time limit, path of the executable | no | the operation's side, or whoever builds (not decided) |

- **Where `draws`, the dimensions, the flags and the time limits come from is not decided** (Boundaries); the table says only which side needs each. The Python-side work stays bounded by nothing (cited: ADR-0017 decision 10).
- **Why here.** *One harness, the same verification* (FR-9): what decides a verdict — the form check, the generator of the reference side, the reference, the predicate, the tolerance — exists once and runs for every backend this contract is answered by and at every execution point; a backend cannot hold a variant of it. *The owner's sentence*: the kernel's process holds neither the reference nor the comparison — and by this cut no backend holds them either, so the property carries over to a target that is not the host, the reason the owner gave for a host-side reference ("the form that carries over to an NPU target"). *ADR-0016 decision 2 (b)*: "the cases a contract test runs over the mock are the cases every backend is held to" — if a run at the mock is answered by this contract (sub-question ⑩), the whole judging runs over the mock as it does over a real backend, because it is not the backend's. *A backend that does not answer the contract* cannot make an attempt pass by saying so: a pass needs the right product for the inputs the tool function regenerates itself. What it still can do is decision 6.
- **What the cut means for the mock, if a run at the mock is answered by this contract** (sub-question ⑩; ADR-0016 decision 5 (d), (e)). For this tool a script must be able to express each thing an operation may return: a report that the tool function judges a pass; one it judges a fail; a report whose form is wrong; a report with a check value that disagrees; no report for a time limit; no report for a non-zero status; each tool-failure kind the complete contract lets a backend raise; and, if the tool is journaled, the death of the process while the operation runs. **A report that passes must hold the right product for the seed of that call**, so a script of this tool is asked with what this contract hands an operation, not with the request and the hw_profile alone. **How this reads ADR-0016 decision 5**: "its call" in "The outcome of a mock call depends on its script and its call alone" includes, for a tool, what that tool's contract hands an operation ("What else an operation is handed and how the call is written are each tool's contract and the code task's", its decision 2); the seed reaches the script as a part of its call, and a script reads no random source itself. Its decision 5 (c) — "a function from a call — the called tool, the request, the hw_profile — to what the operation does" — and the row of its Walk-through ("The script is asked with the tool, the request and the hw_profile") list what a call holds by the frame alone; for this tool the call holds more, and both sentences are less exact for it. ADR-0016 is not edited. The default script and the rule by which it derives a report are the second record's.

### 3. The seed of a call

- **The tool function draws the seed, once for each check, after ④ and after the answer of decision 4, and before the operation is called.** A call that does not reach ⑥ draws no seed.
- **The seed is not a member of a request, and no calling agent chooses or learns it before the check.** Reason: "The seed must be one the author of the attempt could not know" (cited: ADR-0017 decision 3), and every input follows from the seed (cited: ADR-0017 decision 7). A calling agent that named the seed could know every input before the attempt is written, or hand it to the author of the attempt — the reasoning by which ADR-0016 decision 4 keeps the hw_profile, and ADR-0020 decision 5 the tolerance, out of the request.
- **Not the backend**: a seed drawn at the target would have to be believed by the tool function; drawn above the cut, it is the same code for every backend, and the obligation of FR-9 has one holder.
- **The source, as a property and not an algorithm**: the seed comes from a source whose output nobody can predict or influence before the draw — not derived from the request, the identity, any file of the data plane or of the source, a clock, a counter or anything an earlier call left — and it is drawn over the whole range of seeds the harness accepts. In a registry that `default_registry` builds, no request, option or variable of the front process sets it. How the source is bound, and whether a test binds one of its own, is the code task's.
- **It is not kept and is written to no file before or during the check**: nothing is kept between calls (cited: ADR-0010 decision 7), and no runtime seed exists as a file (cited: the principle of OD-16; ADR-0017 decision 3). If the tool is journaled, its start line holds no seed: the `data` of a start line is exactly `step` and `execution` (cited: ADR-0011 decision 3).
- **What follows for two checks, and how this reads FR-9** (the reading is this record's own). Nothing carries a seed from one call to the next — it is in no request, kept by no process and in no file — so two checks that are two calls each draw their own: a further `execution`, a check of a repaired attempt and, **if the checks at the two execution points are separate calls** (how a call relates to an execution point is the second record's — OD-18 sub-question ⑦), the check at the other point. FR-9's "동일 검증을 반복한다" is read here as the same harness, predicate and tolerance, not the same drawn values. What that costs is in decision 6: two checks of one attempt can disagree by their inputs alone. A record that needs equal inputs at two points must reopen this decision. Knowing the seed of a finished check tells nothing about the inputs of a later one.
- **This is about a call of the tool about a run.** The harness keeps its seed parameter (ADR-0017 decision 9): a verification about no run — the calibration tests, whose functional test can use a seed written in the test (ADR-0017 decision 8) — passes its own.
- **Whether the seed is recorded after the check is left open.** The fixed inputs do not carry the answer: NFR-2 asks that a result can be traced back to the tool and settings that produced it, and a fail cannot be reproduced without its seed; the principle of OD-16 says the runtime seed is no file, without saying for how long; ADR-0017 decision 7 leaves the question whether a caller may keep the command line or the standard error of a run to its sub-question ⑤ and OD-10; and where it would be recorded is a member of a result or of a file, which this record may not name. The exact question, which stays with **OD-16 sub-question ⑤**: *after a check has ended, may its seed — or what the kernel's process wrote besides the report, which can hold the seed and the inputs — be returned in the result, kept in a line of the log or written to a result file, and if so by whom and readable by which role?* **Until it is answered**: this record gives a result and a tool failure no content that holds the seed or that standard error (decision 5), and the tool function writes neither to any file. What the operation's side keeps at its target after a check is not restricted by this record (decision 6).
- **`draws` is not decided**: how many a check of a round or a promotion-level re-verification uses stays with OD-16 sub-question ⑤.

### 4. The tolerance in a call, and a run that states none

- **The tool function reads the tolerance** — it is the side that compares (decision 2) — **by the rule of ADR-0020 decision 5** (cited): the tolerance that decides the verdict is the one stated in the member `tolerance` of `runs/<run_id>/instance.json` of the run the request names; no default (**owner**, HQ-0004 (3): "none"), no value kept from an earlier call and no value carried by a request stands in for it. Observation: the reader on `main` is `hilclaw.instance.tolerance_of`; this record binds no code.
- **Where in the order of a call: in ④, from the same read of `instance.json` from which the hw_profile of the call is taken** (ADR-0018 decision 4) — after the lookup and before the start line, if the tool is journaled, and in every case before any operation is called. ADR-0020 decision 5 leaves it to the call's contract "whether it reads it once for several members"; this contract reads it once. A call answered before ④ — a refused request, `no_data_root`, a situation of the lookup, an ended or an open identity — does not read the file.
- **Why one read, there.** The hw_profile and the tolerance of a check are then those of one content of the file. The call knows whether it has a tolerance before anything is consumed at a target and before a start line could be appended. And no situation of the file is met at a moment for which ADR-0019 has no answer: a second read after the selection or inside the step would be "a frame file it reads at another moment" (ADR-0019 Boundaries), and inside a journaled step a missing tolerance would end the identity with a `failure`, so the corrected run would need a further `execution` (the reason ADR-0016 decision 2 gave for placing the selection).
- **`instance.json` missing, unreadable, invalid or of another version at this read**: the four kinds of ADR-0019 decision 2, by the rows of ④ of its decision 3. **This is this record's reading of ADR-0019 Boundaries and extends nothing**: the read is the read of the selection, which those rows are about; a file whose `tolerance` breaks ADR-0020 is invalid as a whole (cited: ADR-0020 decision 3) and is `run_file_invalid`, the reading ADR-0020 Consequences already states. ADR-0019 is not edited.
- **A valid file that states no tolerance: a tool failure of this tool's own kind `tolerance_not_stated`.** It is answered after the selection has succeeded — after `no_backend` and `not_offered`, so the order of ADR-0019 decision 4 stands and this kind follows it — and before the start line, if the tool is journaled. **For it, this call called no operation, consumed nothing at any target, drew no seed and appended no line**; the same request can be repeated and is answered by what the file then states. This contract raises the kind in no other situation and never as the `failure` of an end line. The name is a *name* of ADR-0001; no reserved kind and no name in `hilclaw/` collides with it (checked on 2026-10-08).
- **Why this class and this kind.** *Not a result*: no outcome was established about the attempt (cited: ADR-0010 decision 4), and a result of any shape could be taken for a verdict. *Not `invalid_request`*: the request is not at fault, and a refusal reads nothing and is "the same on every machine" (cited: ADR-0015 decision 2; ADR-0019 decision 4). *Not a kind of ADR-0019*: the file is there, was read, is valid and is of the supported version (cited: ADR-0020 decision 3). *Not a new reserved kind*: the situation belongs to one tool, and the kinds the frame reserved were reserved because their situations belong to no one tool (cited: ADR-0016 decision 3; ADR-0019 decision 2). *Not a check under some other tolerance*: "No path yields a default" (cited: ADR-0020 decision 3).
- **OD-8 sub-question ⑲**, as far as a call goes: it is checked at every call of this tool that reaches ④ — not at the first only, since nothing is kept — and what the call answers is the kind above. **Whether the start of an instance checks it, and what anybody does after the answer, stay open** (OD-8 sub-questions ⑰ and ⑲, OD-23, OD-10).

### 5. Which outcomes are results and which are tool failures

- **Pass and fail are results** (cited: ADR-0010 decision 4, "a candidate that fails verification"; ADR-0017 decision 7).
- **A broken run is a result that reports it — one class for all four conditions** of ADR-0017 decision 7: no report for a time limit or for a non-zero status or a signal (found by the operation, decision 2 (B)), a report of the wrong form, and a check value that disagrees (both found by the tool function). **It is neither pass nor fail** (cited: ADR-0017 decision 7), and nothing counts as verified by it (FR-9).
- **Why a result.** The experiment was carried out at the target, and what it established is an outcome in the sense of ADR-0010 decision 4 ("whatever else a tool's contract defines as an outcome"): this attempt did not complete a verification under these parameters. A tool failure says "the tool could not do its work"; said of a kernel that crashes or hangs, it would have a caller read a property of the attempt out of a failure of the tool. **Why one class**: the conditions cannot be split by cause. Each of them can be caused by the kernel, which shares its process with the verification program (cited: ADR-0017 decisions 4 and 10); the input check is "there to catch" a defect of the harness and a kernel "can cause a disagreement as well". A split that made some conditions tool failures would claim a cause the harness cannot establish. ADR-0017's requirement for the input check — "never a fail" — is kept: a broken result is no fail.
- **What the choice means, weighed.** *A stored outcome of a repeated call* (if the tool is journaled): either class ends the identity, and a repeated call returns what was stored; a further run is a new `execution` in both. *A caller that must not count it as verified*: it must read which of three the result reports, as it must for a fail; only a pass counts (FR-9). *A defect of the harness against a defect of the kernel*: not told apart by either class; the condition is reported so that whoever acts on it can look.
- **What a result of this tool must at least let a caller tell apart**: which of **pass, fail, broken** it reports — exactly one — and, for broken, **which one of the four conditions**: the first that fails in the order in which ADR-0017 decision 7 lists the conditions of a completed run — the time limit, the exit status, the form of the report, a check value. That decision fixes no order; taking this one is this record's own, and it is the order `run_verification` tests them in today. Whether it holds more (the per-draw counts of ADR-0017 decision 7, the dimensions, `draws`, the tolerance used) and every name and type are the second record's.
- **What it must never contain** (cited: ADR-0017 decision 7): an element of the inputs or of the reference. And, until the question of decision 3 is answered: the seed, the command line or the standard error of the kernel's process, none of which is free of them.
- **Tool failures of this contract so far**: the reserved kinds at their moments (ADR-0015, ADR-0016, ADR-0019), and `tolerance_not_stated`. Which tool failure a backend may raise when it cannot carry out the experiment at all — a target that cannot be reached, a fault of a board — is not listed (OD-10, #5 B-2).
- **What anybody does after a fail or a broken run is not decided** (FR-1, OD-10, OD-14, OD-19).

### 6. Limits

- **A backend that returns outputs the kernel did not produce.** A backend holds the seed and can compute the product itself; the cut keeps a defective backend from passing an attempt by accident, not a dishonest one (cited: ADR-0016 decision 6 — a backend that does not answer the contract is not detected by the frame).
- **The kernel's process holds the seed during the check** and is not sandboxed (cited: ADR-0017 decision 10; OD-14). So does everything on the way to it, when the target is another machine (#5 B-2).
- **No access control** (ADR-0010 decision 8), and **whoever can write `instance.json` changes the gate** (cited: ADR-0020 decision 7); a file changed between two checks gives them two tolerances.
- **A pass says that the output is right, not how it was produced**, and only for the drawn range and shape (cited: ADR-0017 decision 10).
- **What crosses the cut is large**: 4·m·n bytes per draw, 16 MB for the largest output of the first instances (cited: ADR-0017 decision 10), held at once for all draws. How it travels from another machine is not decided (#5 B-2).
- **A fail cannot be reproduced** as long as the seed is not recorded (decision 3).
- **Two checks of one attempt can disagree by their inputs alone.** A kernel that is right for some inputs and wrong for others can pass one check and fail the next: a repeated call if the tool is not journaled, a further `execution`, or the check at the other execution point if that is a separate call. A sim pass followed by a board fail, whose cause FR-1 ⑶ treats as not established and has classified (triage) as a defect of the candidate, of the board or of the simulator, can then come from the drawn inputs. Such a kernel breaks the contract (ADR-0003 decision 2) and is a defect of the candidate, but nothing here tells that case apart for the triage (FR-1, OD-10).
- **The outcome of a call is not a function of its request**: the same request is judged on other inputs at each check. That "one request gives the same outcome through both fronts" (ADR-0015 decision 6) holds for this tool over a stored result, or where a test binds the source of seeds.
- **What the operation's side keeps after a check.** A backend is handed the seed and captures what the process wrote. The rule of decision 3 ("until it is answered") binds the tool function and what a call returns; a backend or a target that keeps the seed, a log of the process or its standard error after the check is not stopped by anything here. It belongs to the same open question (OD-16 sub-question ⑤) and to how a backend is reached (#5 B-2, OD-10).
- **A source that draws badly** — predictable, or bound by a test and left in — is not detected by anything here.

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 2 | (b) The operation calls the harness as a library and returns a verdict | Every backend would hold the comparison and be handed the tolerance; over the mock a script would answer "pass" and no contract test would run the judging; a backend that returned a verdict it did not earn would pass an attempt. "One harness" would rest on each backend calling it. |
| 2 | (c) The operation returns the inputs it used together with the outputs | The reference would rest on bytes that passed through the target (the reason ADR-0017 gave against the pipe — its Alternatives, point 4), and the gate/up instance adds 68 MB per draw. |
| 2 | The operation judges the form of the report | A second implementation of the form per backend; a backend could cut or pad a report into form. |
| 2 | The tool function builds the verification executable | The tool function would hold the compiler and flags of each target; who builds an attempt is open (ADR-0004 decision 3, OD-23). |
| 3 | The seed is a member of the request | See decision 3: the calling agent knows every input before the check. |
| 3 | The backend draws the seed and returns it | The tool function would regenerate from a value the target chose; a target could choose one it has outputs for. |
| 3 | Derived from the identity or from a file of the run | Predictable by whoever can read the request or the data plane, the author of an attempt included (OD-16: nothing is hidden by a read restriction). |
| 3 | The checks of one attempt at the two execution points share one seed, so that "동일 검증" means equal inputs | It needs a carrier from one call to the next — a request member, kept state or a file, each excluded by decision 3 — or one call for both points, which is the second record's (OD-18 sub-question ⑦). |
| 3 | Decide here that the seed is recorded in the result | Names a result member and settles ADR-0017's sub-question ⑤ on inputs that pull both ways. |
| 3 | Decide here that it is never recorded | NFR-2: a fail could never be reproduced; no fixed input says so. |
| 4 | The tolerance is read in a second read, after the selection or inside the step | See decision 4: a moment ADR-0019 does not cover, and inside a journaled step it would use up the identity. |
| 4 | A valid file without a tolerance is `invalid_request`, a `run_file_*` kind, a new reserved kind, or a result | See decision 4. |
| 4 | `tolerance_not_stated` before `no_backend` and `not_offered` | A call whose backend cannot be selected reaches no check, whatever the file states. Answered after the selection, the kind says that the tolerance is the one thing missing. |
| 5 | A broken run is a tool failure | See decision 5; if the tool is journaled it would also be stored as a `failure`, the form ADR-0011 gives a step that "ended without an outcome". |
| 5 | Timeout and exit status are results, form and check value are tool failures | A cause the harness cannot establish: a kernel can write to the report channel or damage the generator's state. |
| 5 | Leave the class of a broken run open | The mock's script cases and the conformance tests are written against it, and ADR-0010 decision 4 with ADR-0017 decision 7 carry an answer. |

## Consequences

- **What the second record of this contract must add**: the list of decision 1. Its planner asks the owner the sim / board half of OD-18 sub-question ⑦ first.
- **Code slices.** *Possible after this record alone* (code mode, within the size cap): the judging half as a function of the harness that takes what an operation returns — the form check and the loop over the draws that are inside `run_verification` today — with `run_verification` kept for a verification about no run (the calibration tests); and a source of seeds with the property of decision 3. A conformance test that compares the outcomes of two calls binds the source (decision 6). *Possible once both records exist* (for the slices over the mock, once sub-question ⑩ is answered for it): the tool function of `correctness.check` (over `hilclaw.hw_tool.tool_function` or otherwise), the operation of the mock and its script cases, the default script, the conformance tests of P1-1, and the operation of `cpu_standin` with its own record or task.
- **Observations for those slices** (not decisions). If the tool is journaled and built over `hilclaw.hw_tool.tool_function`: that builder has one reader call before the start line, hands what the reader returned to the selection as the hw_profile record and to the step, and has no place between the selection and the start line. The tolerance of decision 4 and the answer `tolerance_not_stated` need a place there, so the builder changes or another is written; `hilclaw.instance.read` returns both members from one read. The operations of `hilclaw/mock_backend.py` take exactly the request and the hw_profile; an operation of this tool is handed more.
- **Docstring sentences that become less exact** (not edited): in `hilclaw/mock_backend.py`, "A script is a function from a call - the called tool, the request and the hw_profile" and "called as `operation(request, hw_profile)`, with exactly these two positional arguments", for this tool; in `hilclaw/harness/verification.py`, none is false — the module still describes a run on one machine — but "what a caller may keep of them is not decided here" now has decision 3 beside it; in `hilclaw/instance.py`, "where it is checked that an instance states one is open (OD-8 sub-question 19)", of which the half about a call is answered; in `hilclaw/hw_tool.py`, none.
- **Not edited and now less exact** (follow-ups for the integrator): ADR-0016 decision 3 and its Consequences ("the contract of each HW tool"), which call open what this record answers in part, and its decision 5 (c) with the script row of its Walk-through (decision 2 above); ADR-0015 decision 6 ("one request gives the same outcome through both fronts", decision 6 above); ADR-0017 decision 1, Consequences and Boundaries ("the harness / backend split"), ADR-0019 Boundaries and ADR-0020 decision 5 ("Not said here") and Boundaries, each of which likewise calls open what this record answers in part. No sentence of UsageCases became false.
- **A-13 reading**: document mode; no code, dependency, settings file or schema file changes. The record continues the interface between layer 1 and layer 2 and the inner structure of layer 2, as ADR-0015, ADR-0016 and ADR-0019 did. **It names no member of a data-plane file** — not of `instance.json`, `events.ndjson`, `eval.json` or a spec — and no member of a request or a result; the one name it adds is a value of `error.kind`.

## Boundaries (not decided here)

- **The identity and the execution point**: whether the tool is journaled; its `step` value or values; the meaning of `execution` for it; how a call says whether it is the check at the sim point or at the board point (FR-9, FR-1); which of the four HW tools `cpu_standin` offers and at which point its check is called (**OD-18 sub-question ⑦** — its sim / board half is to be asked of the owner); the spend of a check and its axes (OD-2, OD-19).
- **The request and the result**: every member of a request beyond what decisions 3 and 4 keep out of it (the frame members of ADR-0015 decision 4 are cited, not re-decided); the input schema and the description; every member, name and type of a result; whether a tolerance or a detail of a verdict is shown to the coder (ADR-0002 Boundaries; OD-6).
- **Where the other parameters come from**: `draws` and the policy of a round or of a promotion-level re-verification, and whether a seed or a standard error is recorded after a check (rest of OD-16 sub-question ⑤); the dimensions and shapes outside the `op_signature` (OD-16 sub-question ①; no member of `instance.json` names the op_signature of a run — ADR-0018 Boundaries); where the source of an attempt is and who builds it (ADR-0004 decisions 1 and 3; OD-23); flags, the language standard, threads (OD-6 sub-question ②; OD-16 sub-question ⑥); time limits and their hierarchy (OD-14; OD-18 sub-question ③).
- **The mechanism of any backend**: the operation of `cpu_standin` and which functions of `hilclaw/harness/` it calls; how a backend is reached and how a report travels from another machine (**#5 B-2 — owner-only**, A-7 ③); the simulator (**#5 B-3 — owner-only**); board faults and recovery (OD-10); the sandbox (OD-14); the default script of the mock and the mock in a live session (OD-18 sub-question ⑧).
- **Owner-only (DRIVER §9)**: any tolerance vocabulary, oracle or check beyond the first case (#5 B-7; rest of OD-5); any default; whether non-finite or corner-case inputs are drawn; the objective (OD-1, #5 A-4); gates (OD-3); OD-25; C-6.
- **Everything of OD-16 beyond the FR-9 minimum**: strengthened oracles, static checks, order dependence, timing defences; the relation of verification inputs to timing inputs (OD-13 sub-question ⑦).
- **Files**: any member of `instance.json`, `events.ndjson`, `STATE.json`, a spec or a result file; what `eval.json` holds and who writes it (OD-23, OD-20; PLAN P2-3). **How a candidate that would pass under a looser tolerance is found and reported** (FR-9; ADR-0020 Boundaries): by this cut the outputs of a check are in the process of the tool function, so a second evaluation there is possible without a second run at the target; nothing is decided.
- **What follows an outcome**: repair, dropping a candidate, triage, retry, a further `execution`, recovery of an open step (FR-1, OD-10, OD-17, OD-19). Whether the start of an instance checks that a tolerance is stated (OD-8 sub-questions ⑰ and ⑲).
- **Sub-question this record raises** (registered under OD-18): ⑩ For the second record of this contract — how an operation of `correctness.check` comes to the verification executable of the attempt (handed by the tool function or obtained by the backend; built at the call or before it) and what a call answers when none can be had; which tool-failure kinds a backend may raise; and what a call answers for a run that is not of the first case — one whose hw_profile names another accelerator, which the file shows, or one of another kind, dtype or kernel language, which it does not state; in particular whether a run whose hw_profile names the mock is answered by this contract, its `tolerance` member read with the meaning ADR-0020 decision 2 gives it for the first case, so that the contract tests of P1-1 can run over the mock (with ⑦; OD-23; OD-10; #5 B-7 — an HQ if it needs the owner's reading of HQ-0004).
- Any change to ADR-0001 to ADR-0020, to `hilclaw/`, to tests, to CI, to `pyproject.toml`, to any settings file, or to the `HIL-Claw-data` repository; any new external dependency.
