## Decision

A sentence marked **owner** renders an HQ answer through the record named. A sentence is **cited** when a source is named with it. Every other sentence is **this record's own**. "As ADR-0163 decision n" applies that decision to kind `sdpa_kv_cache` with the substitutions stated, and nothing else of it.

### 1. Scope and terms

- The **verification run of one built attempt** of a C kernel of ADR-0162 (`sdpa_kv_cache`, bf16) at `cpu_standin`; the terms of ADR-0017 decision 1, with **draw** meaning one set of values of `q`, `k_new`, `v_new` and of rows 0 … P − 1 of both caches, used for one call. P = l − m throughout (ADR-0162 decision 3).
- **Not covered**: the **bf16 timing run**, with whether ADR-0107's rule extends to it, as ADR-0163 decision 2 leaves it.
- Not an FR-10 tool contract (as ADR-0163 decision 1); ADR-0017, ADR-0162, ADR-0163, ADR-0164 and the first case are unchanged.

### 2. Program and process

- **A sixth verification program** under `hilclaw/harness/`, calling `hilclaw_sdpa_kv_cache_bf16` (ADR-0162 decision 9), **as ADR-0163 decision 2**: one kernel per executable built by one call of `clang_build.build` with the caller's flags, a process of its own through `local_run.run`, every identifier besides `main` of internal linkage, the shared header reused, no floating-point arithmetic and no math library of its own.
- **ADR-0017 decision 9 holds**: the program takes its parameters on the command line and reads no standard input, no file and no environment variable. Every value the kernel receives is drawn from the seed (decision 4) or is a constant of the mechanism (decision 5), so nothing needs handing over; ADR-0164 decision 3 departed from the rule for `rope` only, because its table rows are built, not drawn.

### 3. Command line

| Kind | Arguments, in this order |
|---|---|
| `sdpa_kv_cache` | `<m> <l> <h> <h_kv> <d> <draws> <seed>` |

- The dimensions in the prototype's order (ADR-0162 decision 9), then `draws` and the seed, with the spelling and checks of ADR-0163 decision 3, and the rules between dimensions of ADR-0162 decision 11: each dimension ≥ 1, **l ≥ m** and **h a multiple of h_kv**. Both sides refuse a set that breaks one — the Python side before a process is started, the program with exit status 2 (the command line). P is not an argument: both sides derive it as l − m, so no value can contradict the two (ADR-0162 decision 3's reason). A set whose allocations (decision 5) do not fit in `size_t` or cannot be allocated ends the program with status 3, as ADR-0163's programs.

### 4. Drawn inputs

- **As ADR-0163 decision 4**, with b = 8 over `sdpa_kv_cache_bf16_contract.INPUT_PATTERNS`: each element takes one word of the shared generator, its top 8 bits index the set, and the pattern of index r is element r of the tuple (checked for all 256 indices; computed). Every element takes its own word, so all operands are drawn independently and no element is derived from another — the draws over which ADR-0162 decision 13's facts were computed ("each element chosen uniformly from the set").
- **One sequence per draw, in the order of the prototype's array parameters**: `q` (m·h·d elements, element (i, j, e) at (i·h + j)·d + e), `k_new`, `v_new` (m·h_kv·d each), then rows 0 … P − 1 of `cache_k` and of `cache_v` (P·h_kv·d each, element (t, g, e) at (t·h_kv + g)·d + e; ADR-0162 decisions 4 and 5) — m·(h + 2·h_kv)·d + 2·P·h_kv·d elements, the last term zero at P = 0. Reason: it is the order the code already uses (first operand, then the next) applied to five operands, and the cached rows are input only in their first P rows.
- **The cached rows are drawn, not computed by an earlier call.** The contract lets the kernel assume only that rows 0 … P − 1 hold bf16 patterns "that earlier calls of the same layer wrote, or the verification placed" (ADR-0162 decision 4), so any values of the set serve, and a draw needs one kernel call, not P earlier ones.
- Seed and `draws`: as ADR-0163 decision 4 (parameters of the run with no default; their source and number stay OD-16 sub-question ⑤).

### 5. The cache allocations and the output before the call

- **Each cache is one allocation of l + 2m rows** of h_kv·d elements: m guard rows, the l rows of the operand, then m guard rows. The kernel receives the address of the first operand row, so the operand is exactly ADR-0162 decision 10's `[l, h_kv, d]` and the guard rows lie outside it on both sides. The address is aligned for `uint16_t`, which is all the contract promises (ADR-0162 decision 11). **These allocations are a harness buffer, not the model program's cache capacity**, which stays unchosen (ADR-0162 Boundaries; ADR-0153 decision 4).
- **Before each call**, in each allocation: rows 0 … P − 1 receive the draw (decision 4), and **rows P … l − 1 and all 2m guard rows are set to `0x7FC0`**, the bf16 NaN of ADR-0163 decision 5, written as an integer. **`out` is set to `0x7FC0` as ADR-0163 decision 5.** Every draw sets the whole allocations anew, so nothing a kernel left from the previous draw survives.
- **What the fill shows.** A kernel that reads a row P … l − 1 before writing it, or a guard row, and lets the value reach a weight or a value sum produces a NaN in the output rows that use it, which fails as non-finite under every tolerance (**owner**, HQ-0004 (2) through ADR-0017 decision 5: "any NaN or infinity in the output fails"). A write into a guard row, rows 0 … P − 1 or rows P … l − 1 with other values shows in the cache comparison (decision 8). A read whose value reaches neither is not seen (decision 12).
- **The fill is not an input.** The owner's finite inputs (HQ-0066 (3); HQ-0004 (2)) govern the values the operation reads: `q`, `k_new`, `v_new` and rows 0 … P − 1 (the "Inputs" row of ADR-0162 decision 11). The content of rows P … l − 1 on entry is unspecified and must not be read before it is written (same decision) — the status `out` has on entry, which ADR-0163 decision 5 already fills with this NaN; the guard rows lie outside every operand, where the kernel accesses nothing (ADR-0162 decisions 4 and 11, "Memory", as ADR-0008 decision 6). So no input is non-finite and no obligation is added. Listed for the owner.
- **Why m guard rows on each side**: m is the length of the block the kernel writes. Any displacement of that block by up to m rows in either direction stays inside the allocation and shows in the comparison: an off-by-one reaches the first guard row, and a kernel that reads l as the positions cached before the new tokens (Meta's `start_pos`, P = l) writes rows l … l + m − 1, exactly the trailing guard. Without guards such a write leaves the allocation, with behaviour undefined — a crash, which is a broken run and never a fail (ADR-0017 decision 7), or silent damage. More rows would add report bytes for displacements no named fault produces. Cost: decision 12.

### 6. The reference

- **Widening** as ADR-0163 decision 6. **The keys and values are the Python side's own**: K is its regenerated rows 0 … P − 1 of `cache_k` followed by its `k_new`, and V the same for `cache_v` and `v_new` — the caches as the contract requires them after the write (ADR-0162 decisions 4 and 6). **No part of the reference rests on the reported caches.**
- **Formula** (**owner**, HQ-0066 (1), through ADR-0154 decision 3; the operation of ADR-0162 decision 6), in NumPy float64 on the widened arrays, with no bf16 emulation: for each query head j, g = ⌊j / (h / h_kv)⌋; scores (Q_j · K_gᵀ) · c with c the float64 value of 1 / `math.sqrt(d)` (exactly 2^−3 at d = 64); for row i the positions t > P + i set to −∞, so their weights are exactly 0; the row maximum subtracted; `numpy.exp`; division by the row sum; the result times V_g.
- **Evaluated per query head**: one m × l score array at a time, 33,554,432 bytes at the largest shape, where the full m × h × l array would be 1,073,741,824 bytes (m = l = 2048, h = 32). Per KV head or per block of rows would serve as well; per query head keeps one matrix product for each of the two products.
- **Its own error is negligible against ε**: the scores are exact (products are multiples of 2^−16 below 1 and 64 of them fit 53 bits, ADR-0162 decision 13; the scale 2^−3 is exact at d = 64). Against Python `decimal` at 50 digits the evaluation above differed by at most 1.8·10^−16·Σ p·|V| (heads 0, 5 and 31, all 64 columns, of rows 0, 1, 64 and 127 at prefill S = 128 and of the one row at decode S = 2048; decision 4's generator, seed 7, draw 0; computed), about 1.5·10^−12 of the smallest ε of ADR-0162 decision 7 (1.22·10^−4, at n = 1 as A tends to 0; computed). As ADR-0017 decision 5, it is not accounted for.
- **Cost** (computed with Python 3.14.4, NumPy 2.5.2, Windows 11 on Intel Family 6 Model 183; seed 12345, draw 0): at prefill S = 2048, 1.03 s and a traced peak of 188,746,139 bytes per draw (the widened arrays, one score array and the 33,554,432-byte result); at decode S = 2048, 0.011 s and 23,069,152 bytes.

### 7. The input check value

- **As ADR-0163 decision 6, over the whole allocations**: before each call, the CRC-32 of `q`, `k_new` and `v_new`, then the l + 2m rows of the `cache_k` allocation (guard rows, rows 0 … P − 1, rows P … l − 1, guard rows), then those of `cache_v`, each in memory order — 2·(m·h·d + 2·m·h_kv·d + 2·(l + 2m)·h_kv·d) bytes. The Python side computes it over its regenerated arrays and the fills; a disagreement makes the run **broken**, never a fail.
- **Why the fills and guards are covered**: every byte the cache comparison expects after the call is then a byte whose content before the call the check confirmed, so a fill that differs between the two sides — which would make a conforming kernel's guard rows differ — shows as broken, never as a failing kernel (decision 8). `out`'s fill is not covered, as ADR-0163 decision 6: a conforming kernel writes every element, so that fill cannot fail it.

### 8. The report, the cache comparison and the verdict

- **Channel** as ADR-0163 decision 8. **Content**, in this order and nothing else: for each draw, the check value (4 bytes) before the call; after the one call has returned, the m·h·d elements of `out`, then the l + 2m rows of the `cache_k` allocation, then those of `cache_v`, all as the bytes of their `uint16_t` patterns in memory order; after the last draw, an end mark. **A complete report has draws · (4 + 2·m·h·d + 4·(l + 2m)·h_kv·d) + E bytes**, E the end mark's length; its length follows from the dimensions and `draws` alone.
- **The cache comparison**, on the Python side, bit for bit and with no tolerance: after the call each allocation must hold `0x7FC0` in its 2m guard rows, its drawn patterns in rows 0 … P − 1, and in rows P … l − 1 the patterns of `k_new` (for `cache_k`) or `v_new` (for `cache_v`), row P + i equal to row i (ADR-0162 decision 4). The expected arrays come from the Python side's own arrays and constants, never from the report. A comparison in the program is rejected: it would put an expected result and a comparison in the kernel's process, which holds neither (**owner**, HQ-0004 (1), through ADR-0017 decision 4).
- **Completed, broken, pass and fail** as ADR-0163 decision 8 with the length above. **A completed run passes iff, in every draw, every element of `out` meets the predicate of decision 9 and no element of either allocation differs from what is expected**; otherwise it fails.
- **Why a cache difference is a fail, never broken**: in a completed run the check value agreed, so every expected byte held before the call what the Python side expects (decision 7); a difference was made by the call — the kernel, or something in its process (ADR-0017 decision 10). **A harness defect the check value covers stays out of fail**: generators or fills that differ give a check disagreement, and a crash or a timeout a broken run (ADR-0017 decision 7). A defect the check value does not cover — the address or the dimensions passed to the kernel, the report written at a wrong offset, a wrong expected array, a wrong comparison — is not caught by the verdict classes, as for `out` in ADR-0163. The conforming kernel at the functional test's shape and its run at P > 0 (Consequences) show absent the defects that would fail a conforming kernel, the second failing kernel shows that rows P … l − 1 are compared (decision 10), and a comparison that omits the guard rows or rows 0 … P − 1 is left to the judge's own tests.
- **The Python side returns**, per draw, the counts of ADR-0163 decision 8 for `out` and **the number of cache elements, over both allocations, that differ**, and no index, element or region. The verdict needs only whether one differs; naming the region is diagnosis, which calibration does not assert (ADR-0003 decision 4). Whether more is returned stays as ADR-0017 decision 7 leaves it.

### 9. The comparison of `out`

- **As ADR-0163 decision 7**, with `out` of m·h·d elements: element-wise `rtol` and `atol` (**owner**, HQ-0066 (2)), never passed to the program.
- **For whoever sets a tolerance** (no value, no default):
  - **The cache comparison has no tolerance**; the tolerance applies to `out` only.
  - **y cancels**, so an `rtol` with `atol` = 0 can fail a conforming kernel: a compliant output may differ from y by more than a relative 2^−8 on 35.6 % to 100 % of the elements of ADR-0162 decision 13's draws, exact outputs reaching down to 6.7·10^−9 (same decision); a binary32 evaluation with round-to-nearest-even output reached a relative 0.0113 at prefill S = 128 (decision 4's generator, seed 3, draw 0; computed; the figure varies with the seed).
  - **An absolute bound every compliant output meets** on the value sets at d = 64: |out − y| ≤ 2^−9 + ε(l, 8, 64)·(1 − 2^−8), that is 2.154·10^−3 at l = 128 and 2.382·10^−3 at l = 2048 (computed with ε of ADR-0162 decision 7). Reasons: on the set A < 8 (ADR-0162 decision 13) and n ≤ l, and ε grows with both; Σ p·|V| ≤ max |V| = 1 − 2^−8; so |v| < 1 and the round-to-nearest-even output adds at most half a unit in the last place of [0.5, 1), 2^−9 (ADR-0162 decisions 7 and 8). A binary32 evaluation with that output reached 1.953·10^−3 at prefill S = 128 and S = 2048 (seed 3, draw 0; computed).

### 10. Calibration

- **ADR-0003 holds for this kind** as ADR-0163 decision 9 applies it: hand-written C kernels — conforming, violating (V1, right on the functional test's seed and shape, its output and its cache, wrong elsewhere) and failing — added with the change that makes the harness verify `sdpa_kv_cache` (ADR-0003 decision 6 (a)); the tests pass their own `rtol`, `atol`, seed and `draws`.
- **The functional test's shape**: (m, l, h, h_kv, d) = (128, 128, 32, 8, 64), so **P = 0** — the prefill S = 128 op_signature shape of ADR-0162 decision 14.
- **Failing: query head j served by KV head j mod h_kv** in place of ⌊j / (h / h_kv)⌋ (ADR-0162 decision 13: 87.0 % to 87.3 % of elements by a relative 2^−6 or more). **Why it is outside**: at P = 0 row 0 attends position 0 alone, so y(0, j, e) = `v_new`(0, g, e) exactly, and a compliant output equals it, since |v − y| ≤ ε(1, 8, 64)·|y| ≤ 1.87·10^−4·|y| is below half the gap from y to either bf16 neighbour (at least 2^−10 on the set, at |y| = 0.5); the faulty kernel gives `v_new`(0, j mod 8, e) in the same way. The mapping differs at 28 of the 32 heads, and their pairs (⌊j / 4⌋, j mod 8) connect all 8 KV heads, so every faulty element of column e stays within 1 of y only if the 8 values `v_new`(0, ·, e) share a sign — probability 2^−7, and 2^−448 for all 64 columns of a draw. Otherwise one element differs by |a| + |b| ≥ 1 while |y| ≤ 1 − 2^−8: it is outside under every tolerance with atol + rtol < 1, except on a share of draws ADR-0003 decision 4 calls a negligible exception. The conforming kernel passes under every tolerance with atol ≥ 2.154·10^−3 (decision 9), so the two ranges meet. Computed: over seeds 0 to 1999 the largest such difference was never below 1.914, and a binary32 evaluation gave both row-0 outputs exactly.
- **The cache gets a required case of its own: a second failing kernel** that computes `out` as the conforming one, from `q`, `k_new`, `v_new` and rows 0 … P − 1, and writes no cache row. Its output passes and the cache comparison fails on every draw at every shape: rows P … l − 1 keep `0x7FC0`, a pattern outside `INPUT_PATTERNS`. Reason: the other three kernels are judged through `out`, so a harness that skipped the cache comparison would pass them all, while the cache rows are part of the result (ADR-0162 decision 11). A write at wrong positions, into rows 0 … P − 1 or into a guard row goes through the same comparison and needs no kernel of its own; the code task's tests of the judge construct such reports to show each region compared.
- **No test may require these to fail**: Meta's probability rounding, which changes the output on 41.9 % to 43.1 % of the elements and is detected only under a tolerance tight enough (ADR-0162 decision 7); blocked and online softmax orders, fused multiply-adds, any association, a reciprocal for the division and the scale applied before the product, all compliant where they meet the bound (same decision), so no test separates them; truncation in place of round-to-nearest-even, detected only under a tolerance below a unit in the last place; the sign of a zero output, not fixed, and on the draws of ADR-0162 decision 13 no exact output is zero (ADR-0162 decision 8); a read of rows P … l − 1 before their write or of a guard row whose value reaches neither `out` nor the cache (a maximum taken with `fmaxf`, which ignores a NaN, for example); a write into `q`, `k_new` or `v_new`, against ADR-0162 decision 11 but not observed, since they are neither reported nor compared and every draw sets them anew; and errors of the binding — a wrong P, V copy or call site in the model program, RoPE left out — which the kernel does not make.

### 12. Limits

1. **As ADR-0163 decision 11, items 1 and 5**: the kernel shares its process with the program, a pass says the output and cache are right and not how, nothing is sandboxed (OD-14, OD-8, threat A of OD-16); one machine, so the report travels in host byte order.
2. **What the set cannot detect** is decision 10's list, together with accesses farther than m rows outside the operand, which leave the allocation with behaviour undefined (no memory protection; OD-14); no zero, subnormal or non-finite input is drawn and none outside D (#5 B-7, OD-16).
3. **The computed facts of ADR-0162 decision 13 and the bound of decision 9 hold for d = 64 and l ≤ 2048**; a run outside is a valid run whose shares were not computed, and for d above 256 the set can give A above 16, outside D, where the contract defines no bound (A < √d on the set).
4. **Cost at the largest shape** (m = l = 2048, h = 32, h_kv = 8, d = 64; computed): a report of 20,971,524 bytes per draw (8,388,608 of `out`, 12,582,912 of the two allocations of 6,144 rows each), all held by the runner at once; at decode S = 2048, 4,202,500 bytes. The program's arrays total 33,554,432 bytes. The draw has 6,291,456 elements, under 302 MB at the existing array code's peak of under 48 bytes per drawn element (`bf16_verification_arrays.py`), and the reference costs decision 6's figures per draw. **The Python side is bounded by nothing here** (OD-14).

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 2 | Inputs handed over on standard input, as for `rope` | Every input is drawn; nothing is built outside the program (ADR-0164 decision 3's reason does not hold). |
| 4 | Cached rows written by earlier kernel calls | P calls per draw, and the kernel under test would make its own inputs; the contract admits placed rows. |
| 5 | Rows P … l − 1 left as allocated, or holding drawn values | Stale memory, or a read-before-write detected only through the tolerance; the NaN shows it under every tolerance. |
| 5 | No guard rows | A write past row l − 1 leaves the allocation: undefined behaviour, at best a broken run. |
| 5 | Guard pages with memory protection | Page granularity and a signal on access, which makes the run broken, never a fail (ADR-0017 decision 7). |
| 5 | Drawn finite guard content | Attention past l would show only through the tolerance and the weights; the NaN shows under every tolerance. |
| 5 | One guard row, or guards past l only | Misses the `start_pos` reading (rows l … l + m − 1) or a block displaced below row 0. |
| 6 | One float64 score array for all heads | 1 GiB at the largest shape, for no gain in accuracy. |
| 7 | Check value over the operands' inputs only | A guard fill that differs between the sides would fail a conforming kernel. |
| 8 | Cache compared in the program | An expected result and a comparison in the kernel's process (HQ-0004 (1)). |
| 8 | Only rows P … l − 1 reported, or a CRC of each region | Misses writes into rows 0 … P − 1 and the guards, or hides a change behind a collision and gives no count. |
| 8 | A cache difference as broken | It is the kernel's result (ADR-0162 decision 11); the check value has already excluded the harness. |
| 10 | No scale, no normalisation or no mask as the failing kernel | With the maximum subtracted, row 0 at P = 0 has the single weight 1 and shows neither of the first two; without the mask row 0 becomes a weighted mean that need not differ much; each is detected on a share of elements only. |
| 10 | The cache left to the judge's own tests | A harness that skipped the comparison would still pass the calibration. |
