## Context

- ADR-0080 decision 4 kept open "an `OSError` raised after the compiler process was created and before it ended, and the removal error passed on in its place (M3), which by class cannot be told apart from an error before the start". Its alternatives table declined S6 and S9 for it because "It comes in the same classes as errors before the start (M3, M4), so an operation could not apply either; telling it apart is a code change."
- Task T-0249 (PR #158, `065113b`) made that change and placed the new class in no row.
- **Observations at `065113b`** (`hilclaw/clang_build.py`; no code is bound):
  - **K1.** `build` wraps only the call `_communicate(process, timeout_s)`. "Any other `OSError` raised while the process runs is raised as `CompilerRunError`, an `OSError` subclass without `result`; when removing the temporary file then fails too, the removal's error is its `removal_error`" (docstring). The class docstring: "It has no `result`: the output read so far is not kept." The removal error no longer takes the place of the run's error.
  - **K2.** `_communicate` runs the process in `with process:`. When the time limit passes, it kills the process and then reads it again (Windows) or waits for it (elsewhere), and returns no return code. On any other exception it kills the process and re-raises. So an `OSError` from that kill, read or wait in the time-limit branch leaves `_communicate` too, and **a `CompilerRunError` can come from a build that passed its time limit**. In the other branch, an `OSError` from the kill takes the place of the exception it handles: T-0249's test of it has the kill's error as `__cause__` and the read's error as its `__context__` (taken from T-0249's Result). A kill of a compiler that has already ended does nothing, and when the kill fails, the exit of `with process:` waits for the compiler without a limit, so that compiler ends by itself and the call can outlast the time limit (T-0249's Result: with a stub that does not end, that exit "would wait the full 30 s"). Neither the class, its members nor the docstring say which branch it came from, whether a time limit passed, or what the compiler wrote. **The exception chain does, in part**: `build` raises the class `from` the run's error, and in the time-limit branch that error is raised while `subprocess.TimeoutExpired` is handled, so it holds that `TimeoutExpired` as its `__context__`. In CPython's POSIX `communicate` (read in the installed 3.11.9), its `output` holds what was read so far; in the Windows one it holds nothing. An `OSError` from the exit of `with process:` (closing the pipe or waiting) does not hold it as its own `__context__`; after a failed kill of the time-limit branch it lies deeper in the chain.
  - **K3.** `CompilerRunError` and `CompilerNotStartedError` share the private base `_UnendedBuildError`. Neither is a subclass of the other or of the three classes raised after the end (`ArtefactNotPlacedError`, `ArtefactNotCheckedError`, `TemporaryNotRemovedError`). All five are `OSError` subclasses.
  - **K4.** **An `OSError` that `build` raises and that is none of its five classes** comes from one of two places. (i) A line of `build` before `subprocess.Popen` is called: the source and output path tests (ADR-0080 M4), forming the absolute paths, `_resolve` and the temporary name. (ii) Removing the temporary file, when an exception that is no `OSError` left the block that creates and runs the compiler before its end was recorded. The `finally` then raises the removal's error in that exception's place. T-0249 kept a test of this path after a `KeyboardInterrupt` after the start (taken from T-0249's Result); the same path is taken by an exception of that kind from inside the construction of `Popen`, whether or not a process exists yet. No other line raises an `OSError` outside the five classes: every other `OSError` of the stat test, the move and the removal after the end is caught and raised in one of them.
- No owner comment on #5 speaks to ADR-0079, ADR-0080, S6, S9 or ⑱ (마) (checked on 2026-10-17; every comment since 2026-10-16 carries the driver tail).

## Decision

### 1. Scope and terms

- A call of `correctness.check` as ADR-0079 decision 1 and ADR-0080 decision 1 have it: the one build of ADR-0056 decision 4, through `clang_build.build` directly or through `build_verification_executable`, which passes everything on (ADR-0079 N4). The six kinds, S1 to S10 and the keeper are as ADR-0079 decision 1 has them. **The mock** builds nothing and is unchanged.

### 2. The row of `CompilerRunError` stays open under (마)

- **What the operation can observe from the class alone** (K1 to K3): the compiler process was created, so the start of ADR-0060 decision 4's S6 succeeded; then the call failed to talk to it, and its end was not seen; no log and no return code reach the operation. The time-limit branch is not told apart (K2).
- **No row fits that observation.** "What the operation observes decides the row" (cited: ADR-0060 decision 4). S6 is "The compiler is not found, or its process cannot be started", at "the start of the build", and the process was started. S9 starts with "Status 0", at "the build ended", and no status is known. S7 and S8 are results (O1, **the owner's**: "One each: `build_exit_status` for S7 and `build_time_limit` for S8."). The class shows neither a non-zero status nor a passed time limit, but some calls of the class are S8 (K2). A tool failure of any kind would turn such an S8 build into a tool failure, against O1, as ADR-0079 declined for `TemporaryNotRemovedError` ("for S7 and S8 against O1"). S8 for every call would answer a passed time limit that was never seen. Alternatives considered weighs each candidate.
- **What would let it be placed** (named, not written here):
  - **A code change** of `clang_build.build` that tells the time-limit branch apart, by a class or by a member of the error, and keeps the output read so far. Then a record can weigh S8 with its log for that branch. Without it, a later record that reads `build` by what it states meets the same stop. **The exception chain (K2) is not used here**: it is an implicit context that `build` does not state, its `output` exists on POSIX only, and the chain does not say from which call the error came. A code change that states it would be a change of this kind.
  - **A record for the other branch**, a compiler the call lost while it ran. No wording of S3 to S10 names it, so that record either reads one row's wording to cover it, or adds the situation to the list of ADR-0056 decision 5. The second may need a new value of `error.kind`, which this record does not add.
- **Until then**, an operation that lets the error pass meets the landed rules: an error it lets pass that is no tool failure is answered `operation_answer_invalid` (cited: ADR-0045 decisions 4 and 5). As ADR-0060 decision 4 says of the errors it lists, "That says what the landed rules do with it; it is no answer of this record." It is no answer of this record either. **The cost, stated**: `operation_answer_invalid` is a tool failure, so a call of the class whose build passed its time limit (K2) is still answered by a tool failure, against O1, as (a) would answer it. This record leaves the row open because no answer of its own should go against O1, not because the outcome of such a call differs.
- **The `removal_error`** changes nothing of this. A `CompilerRunError` with a `removal_error` is open exactly as one without, and whatever row a later record gives applies to both. The failed removal is in no answer and no message, as ADR-0080 decision 2 has it for `CompilerNotStartedError`: the file left behind is a file of the build directory, whose removal is ADR-0056 decision 4's and whose failure is ⑰ (다).

### 3. The log

- ADR-0078 decision 2 keeps "The log of every build whose compiler process was started and has ended — by itself, or killed for its time limit". **Every `CompilerRunError` is such a build except one whose compiler the call killed for its own error**, and except one from the exit of `with process:` (closing the pipe or waiting), whose end is not seen and which is practically unreachable: the compiler may have ended by itself before the failed read, or after a failed kill while the call waited, or have been killed for its time limit (K2). Its log reaches neither the operation nor the keeper, because the class keeps no output (K1). A compiler killed for the call's own error is a case that sentence does not name; this record reads the sentence as not reaching it, and its output read so far is lost as well. The class does not tell these cases apart (K2).
- **The cost, stated.** For every check whose build raised `CompilerRunError` and whose compiler ended by itself or was killed for its time limit, the log that ADR-0078 decision 2 keeps is lost, against its letter. Where the build passed its time limit, it is S8, and the loss is also against O2 (**the owner's**: "Kept, not returned: in a file of the attempt, never in the result or in `events.ndjson`"), which ADR-0060 decision 5 applied to the log of S7 and S8 builds. The missing file then says that the log "did not reach the tool function" (cited: ADR-0078 decision 2). A caller cannot tell this from no compiler having run. The case needs a read, kill or wait that fails with an `OSError` after the compiler was started. Leaving the row open does not lose more: no row, chosen or open, would bring the log back. The code change of decision 2 brings it back.

### 4. What an `OSError` of `clang_build.build` outside its own classes now means

- **An `OSError` that `build` raises and that is none of its five classes no longer comes from the run** (K4): neither from talking to the started compiler (K1) nor from a removal that replaces such an error. It comes from before the creation of the compiler process (K4 (i)), or it is a removal error raised in place of an exception that is no `OSError` (K4 (ii)).
- **What it answers of ADR-0080 decision 4's open list.** The first entry, as far as it is an `OSError` while the process runs and the removal error after it: the class now tells these apart (decision 2 leaves only the row open). It also tells the operation that an `OSError` of another class from the path tests (ADR-0080 M4) is no error from talking to the compiler.
- **What it does not answer.** It gives no row to any such `OSError`. The path tests' classes remain errors of two rows, S5 for a source and S3 for the output path (cited: ADR-0060 decision 4). The other classes those tests raise on 3.11, and on 3.12 and 3.13 as ADR-0080 Context took from T-0246's Result, still lie before the start, but this fact gives them no row. A removal error of K4 (ii) does not say whether a process was created: by class it is told apart neither from a path error nor from a failed removal after an interrupted run.

### 5. How far (마) is answered

- **Answered now, for `correctness.check` of the first case and of the mock**: that `CompilerRunError` is told apart from errors before the start and its `removal_error` from it, with its row left open for the reason of decision 2; what a plain `OSError` of `build` means (decision 4).
- **Open under (마)**: the row of `CompilerRunError` (decision 2); the removal error raised in place of an exception that is no `OSError` (K4 (ii)); the classes of the path tests of ADR-0080 decision 4; and the other entries ADR-0079 decision 5 names, as ADR-0080 decision 4 lists them.

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 2 | **(a)** S6, `compiler_unavailable` | S6 is "its process cannot be started", at "the start of the build". The class shows that the process was created (K1). It would also answer a build that passed its time limit (K2), which is S8, with a tool failure, against O1. ADR-0080 decision 2 accepted S6 with its cost for the case inside the construction of `Popen` (M5), which is "practically unreachable" (T-0247's Result, as ADR-0080 M5 quotes it) and has no time-limit branch; neither holds here. |
| 2 | **(b)** S9, `build_output_missing` | S9 starts with "Status 0" at "the build ended". No status reaches the operation, and the call may have ended a build past its time limit. The same stop as (a) for S8. |
| 2 | **(c)** Answer by the build the error interrupted (S8 after a failed kill, otherwise a row by the moment) | The class carries no build, and nothing `build` states tells the time-limit branch apart (K2), so the operation cannot apply it. The exception chain tells it in part, but decision 2 does not rest an answer on it. S7 and S8 are results whose log ADR-0078 decision 2 keeps, and no log reaches the operation (K1). It needs the code change of decision 2. |
| 2 | **(d)** `operation_answer_invalid` | It says that what the operation returned or raised "was neither a report nor one of the two conditions of ADR-0043 decision 4, and no tool failure" (cited: ADR-0045 decision 4). It is the tool function's own kind, which a backend may not raise. As an answer it would make the operation let the error pass on purpose, and the caller would read a fault of the backend's answer. It stays what the landed rules do without an answer (decision 2). |
| 2 | **(d′)** Another existing kind (`build_directory_unusable`, `build_input_missing`, `settings_refused`, `executable_unstartable`) | Each names a situation before the build or at the start of the process (cited: ADR-0060 decision 4), none of which the class shows. Each has the stop of (a) for S8. |
| 2 | **(e)** Leave it open (chosen) | It gives no answer that the class cannot support, and it names the code change and the record that would let a later record place it. The cost: until then the landed rules answer it with a tool failure, so a call past its time limit is still answered against O1, as under (a) (decision 2). |
| 3 | Read ADR-0078 decision 2 as reaching a compiler killed for the call's own error too | The sentence names a compiler that ended "by itself, or killed for its time limit", and a kill for the call's own error is neither. Reading it in would add a loss to the cost without changing any answer. The code change of decision 2 keeps that output too. |
| 4 | Give a plain `OSError` of `build` the row S3 or S5 now | It still comes in one class for a source (S5) and for the output path (S3), and as a removal in place of another exception (K4 (ii)). The fact narrows where it comes from but places it in neither row. |

## Consequences

- **Code** (code mode, D12 rules; names and modules are the code task's; **this record binds no code**): the operation of `cpu_standin` for `correctness.check`, when it is written, applies ADR-0079, ADR-0080 and this record, and leaves `CompilerRunError` to the landed rules until a record places it. A code task may tell the time-limit branch apart and keep the output read so far (decision 2). Telling the removal error of K4 (ii) apart is another code task.
- **Not edited and now less exact.**
  - ADR-0080 M3 ("Any other `OSError` raised while the process runs is passed on as it is, unless removing the temporary file then fails too, whose error is passed on instead" — "in the same classes as the errors before the start").
  - ADR-0080 decision 4's open list ("an `OSError` raised after the compiler process was created and before it ended, and the removal error passed on in its place (M3), which by class cannot be told apart from an error before the start").
  - The row of ADR-0080's walk-through "Reading the pipe fails while the compiler runs" ("that `OSError`, no `result`").
  - The last row of ADR-0080's alternatives table ("It comes in the same classes as errors before the start (M3, M4) … telling it apart is a code change").
  - ADR-0060 decision 4 ("while one raised once it has started anything is an `OSError` of the two-row entries above"), for the classes K1 and K3 name.
  - ADR-0078 decision 2 ("The log of every build whose compiler process was started and has ended — by itself, or killed for its time limit — is kept"), for the time-limit branch of `CompilerRunError` (decision 3).
- **A-13 reading.** Nothing of the data plane is added or changed: no member, no value of `condition` or `error.kind`, no file, no version.
- **Runtime acceptance items**: none. Which of these errors a real machine produces is the code tasks' observation.
