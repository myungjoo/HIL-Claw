## Context

- ADR-0018 decision 2: "**How the file comes to be on disk is not decided.** ADR-0014 decision 7 left it open for this file, and it goes with what writes it (sub-question ⑰). Until then nothing excludes a partial file after the death of a writer; such a file is invalid by the rule above and is reported." ADR-0014 decision 7 lists `instance.json` among the files for which the question is "not decided" and adds: "A later record for such a file may refer to ADR-0013 and to this record instead of repeating them."
- Sub-question ⑰ asks three things: what writes `instance.json`; "by which steps it comes to be under its final name (the once-only step of ADR-0014 decision 3, the replacement of ADR-0013, or another) so that a death of the writer leaves no partial file"; and what a run directory that holds other files and not this one means. This record takes the second.
- ADR-0013 fixed how `STATE.json` is replaced, and ADR-0014 how `artifacts.json` and the two key record files are written. `instance.json` differs from `STATE.json` and `artifacts.json` in one fact: ADR-0004 calls it the "immutable instance record", written by "The start of the instance, once" (the tree, the path table, decision 4), and the records of its members rest on that ("file is written once (cited: ADR-0004)" — ADR-0020 decision 6, ADR-0022 decision 3). A partial file under the final name is therefore not replaced by a next write, as a partial `STATE.json` would be: every call of a HW tool about the run that reaches the selection of the backend answers `run_file_invalid` ([ADR-0019](ADR-0019-od18-unusable-run-kind.md) decision 3) until someone removes or restores the file, and no record gives anyone that step.
- Facts of the code and of the data repository, none of them changed here. `hilclaw/instance.py` reads and validates the file; its docstring says "It writes, creates and removes no file and composes no content", and no module of `hilclaw/` writes the file. `hilclaw/key_records.py` holds the once-only step of ADR-0014 decision 3 as landed (a temporary file `<final name>.<token>.tmp`, `os.fsync`, `os.link`, removal of the temporary name) and `hilclaw/run_state_file.py` the replacement of ADR-0013 (`os.replace`). `hilclaw.layout.RUN_FILES` holds the four run-level names. The `.gitignore` of `HIL-Claw-data` holds `blobs/sha256/` and, under "Local scratch", `*.tmp` and `.DS_Store`.
- Unchanged inputs: NFR-1 covers the death of a process, and the local commit is the durability boundary (#5 A-3); P1 assumes one run (C-2) and the lock is the rest of OD-17; the environments of C-7 are POSIX; no directory is scanned at the entry of a turn (#4 §1). POSIX `link()` creates a new name for an existing file in one step and fails when that name exists; POSIX `rename()` replaces an existing name in one step.
- What is open around this file and is not an input: what writes it (first part of ⑰; OD-23); the order against the first `STATE.json` (⑩); where the values of its content come from and whether a start must state `tolerance`, `source_commit` or `n_max` (⑱ to ㉑); the form of a `run_id` and how its uniqueness is obtained (ADR-0004 decision 8); how a branch or a continuation of a run relates to a file that is written once (①).

## Decision

A value below is **cited** when a source is named with it; every other value is **this record's own** choice — among them the requirement, that this file takes steps 1 to 3 and 5 of ADR-0013 decision 2, that its last step is one that cannot replace an existing name and has no replacing fallback, what a write that finds the name taken reports and what it leaves open, the rule for the run directory, the name form of the temporary file, that the readings of ADR-0004 made by ADR-0013 are followed for this file, the rules for a leftover, and that the flush is required.

### 1. Scope

This record fixes how the bytes of `runs/<run_id>/instance.json` come to be under their final name: the "by which steps" part of sub-question ⑰. It fixes **nothing else**: no member, type or validity rule of ADR-0018, ADR-0020, ADR-0022, ADR-0023 or ADR-0024 changes, and nothing `hilclaw.instance.parse` or `hilclaw.instance.validate` accepts changes. It says nothing of what performs the write, of when it is performed, of what the content holds beyond its validity, or of any other file. The other two parts of sub-question ⑰ stay open.

### 2. The requirement and the content

- **Requirement**: the death of the writing process leaves **no file under the final name or the whole one**, never a part of one. It is the requirement of ADR-0014 decision 3 for a key record file, taken for this file because both are written once (cited for this file: ADR-0004).
- **The content first.** The writer holds the whole content as bytes before it touches the file system. That content is valid by the records that define the file as they stand at the write — today ADR-0018 decisions 2 and 3, ADR-0020, ADR-0022 and ADR-0023, with a `schema_version` of `1`, the only version a record defines; today's implementation of that validity for bytes is `hilclaw.instance.parse`, cited as today's code, which has the conventions and limits of its docstring (it also refuses a content its interpreter cannot read) — and it is in the written form of ADR-0018 decision 2 (cited: "LF line ends and a final line feed bind the writer"; no member order). A content that is not valid is not written: nothing rewrites the file (cited: ADR-0004), so an invalid file would stay.
- **The write adds, substitutes and checks nothing beyond that.** The bytes that come under the final name are exactly those held first. The write puts no member into the content and takes none out, and it fills in no value: no tolerance, no commit, and not the 10 of ADR-0007 decision 8. A valid content may lack `tolerance`, `source_commit` and `n_max` (cited: ADR-0020 decision 3, ADR-0022 decision 5, ADR-0023 decision 4), and the steps of this record neither require nor refuse such a content. **Whether the start of an instance may write one is sub-questions ⑲ to ㉑ and is not narrowed here in either direction.** A valid file is still "not thereby enough to start a run" (cited: ADR-0018 decision 2).
- Whether a function of the package takes the content as bytes or builds the bytes from a document it is given is the code task's; in both cases the bytes it writes are held whole, valid and in the written form before the file system is touched.

### 3. The steps; a last step that cannot replace

1. **The content first** (decision 2).
2. **A new file beside the final one.** The writer creates the temporary file of decision 6 in `runs/<run_id>/` — as a new file, never by opening an existing one — and writes the whole content into it.
3. **Stable storage.** The writer asks the operating system to bring the content of the temporary file to stable storage (`fsync` or its equivalent) and closes it.
4. **The last step gives the final name to the complete file only if that name does not exist, in one step, and otherwise changes nothing.** A rename that replaces is **not** this step. POSIX `link()` from the temporary name to the final name, followed by the removal of the temporary name, is such a step (cited: it fails when the final name exists); an operation of the platform that renames without replacing is another. Which one is used is the code task's. **There is no fallback to a replacing rename**: where no such operation works (a file system without hard links), the write fails with an error and writes nothing under the final name.
5. **A failure while the writer lives.** If a step fails before the final name is given, the writer removes its temporary file and reports the failure; the final name is as it was. Once the final name is given, the write has happened: with `link()`, a removal of the temporary name that fails leaves a leftover (a second name of the file, decision 6) and is not a failure of the write.

Steps 1 to 3 are those of ADR-0013 decision 2 with this file's values, and so is step 5 for a failure before the final name is given; its second sentence is this record's own. Step 4 is that of ADR-0014 decision 3. The writer never opens the final name for writing.

**Why the last step cannot replace** (this record's own). The file is written "once" and is "immutable" (cited: ADR-0004), and nothing enforces either (cited: ADR-0004 decision 10; ADR-0018 decision 6). With the replacing rename of ADR-0013, every write by the technique would be a means to replace the record a run was started with: silently, with the earlier content gone from the working tree and nothing reported to either writer. The calls of the run would from then on be about another hw_profile, tolerance or bound — the case ADR-0018 decision 6 states as a limit ("two calls of one run can be about two hw_profiles"). The step of this record is not to be such a write. A look at the final name followed by a replacing rename does not help: they are two steps, and a file that appears between them is replaced. The step is not a lock: it orders nothing and makes no writer wait. **Whether a later record ever lets this file be rewritten is not decided** (sub-question ① asks how a continuation relates to a file that is written once); such a record would state its own steps.

### 4. When the last step finds the name taken

- **The write has written nothing under the final name**, removes its temporary file, and **reports to its caller that the name was taken and that its content was not written** — never as a write that happened. Reason: the file under the name was not put there by this write, and the write does not establish whether its content is the one the writer held; a caller that was told the write happened would take its own content for the record of the run without that.
- **This record decides no more about that report.** By this record the write does not read the file under the name, compares nothing and takes no content there for "the same" as its own. No record gives this file a rule like ADR-0001 decision 3 for a key record (an equal canonical form is the same key): no record defines a canonical form for this file, and no member order is fixed and its top level is open (cited: ADR-0018 decision 2), so equal bytes are not what equal contents would mean and no record says what equal contents are. The form of the report (an exception, a returned value) is the code task's.
- **For a reader nothing changes**: the file under the name is the `instance.json` of that `run_id` as ADR-0018 decision 2 has it, whatever wrote it.
- **Not decided** (sub-question ㉓, first part): what the caller does then — whether it reads the file and takes some content for its own write (a start whose writer died after the last step and before its report, tried again), stops, or uses another `run_id`; and **what a second start with a `run_id` that is in use means**. The step is not, by this record, the means by which a `run_id` is unique within `runs/` (ADR-0004 decision 8 leaves open how uniqueness is obtained): it concerns one file name, a run directory may hold other files without this one (third part of ⑰), and nothing here says that a start begins with this write.

### 5. The run directory

- **The write may create `runs/<run_id>/`** (and `runs/` above it) when it does not exist: "a directory exists only when something was written into it" (cited: ADR-0004 decision 1), and this is such a write. **It requires neither that the run directory is missing nor that it is there, and neither the presence nor the absence of any other file of the run.** Requiring that the directory is missing would fix that this file is written before every other file of the run, and requiring that it is there would fix that another file is written first; when this file is written in relation to the first `STATE.json` is sub-question ⑩ (cited: ADR-0018 decision 2), and ADR-0013 decision 6 made the same cut from the other side. No sentence of this record fixes that order.
- **What a death leaves of the directory.** A death after the directory was created and before the last step leaves a run directory that holds no file of ADR-0004, or a leftover only — or, when other files were there, those files and no `instance.json`. This record follows the reading of ADR-0004 decision 1 in ADR-0013 decision 6 without change (a statement about the tree as it is committed and as a reader may rely on it). For a reader of `instance.json` each of these is a missing file (cited: ADR-0018 decision 2). Whether a failed write removes the directories it created is the code task's.

### 6. The temporary file and a leftover

- **Place and name**: the run directory (one file system, the condition of `link()` as of `rename()` — cited: ADR-0013 decision 3, ADR-0014 decision 4), and the name `instance.json.<token>.tmp`, with `<token>` matching `[a-z0-9-]{1,64}` and different for every write. This is the form of ADR-0014 decision 4 with this final name, and "why the name differs per write" holds as ADR-0013 decision 3 has it.
- **It cannot be mistaken for a file of the tree**: the name is none of the four run-level names and is not `rounds`, and it is no member of `layout.RUN_FILES`, so `layout.run_file` refuses it.
- **Readings of ADR-0004.** ADR-0013 decision 3 read decisions 2 and 7 for a temporary file in `runs/<run_id>/`; this record follows both readings without change. **Where scratch and build-cache directories are is not decided or narrowed here.** The layout version (ADR-0004 decision 9) is unchanged, version 1: no path, file name or number form changes. What a file states through its `schema_version` (ADR-0024 decision 3) is unchanged, and a temporary file states nothing.
- **Git.** A temporary file is **never committed**. The rule binds whatever step commits; which step that is stays undecided. The `*.tmp` line of the data repository's ignore file matches the form (cited as a fact): a second guard, on which the rule does not rest. **No change to the data repository is made or required.**
- **A leftover** — a file of this name form whose write is no longer running — is ADR-0014 decision 5's, with this final name. It is not the instance record: it is never read in the place of `instance.json`, not when that file is missing and not when it is invalid, and it is **never given the final name**, also when it holds a whole valid content: the write it belonged to is over, and one that did not reach the last step did not happen. It is never committed. A reader opens the final name only, so no directory is listed because of a leftover (#4 §1). A writer removes its own temporary file on a failure; a leftover of a dead writer **may** be removed, and nothing requires it; a reader removes nothing. With `link()`, a death between the link and the removal leaves the temporary name as a second name of the written file: it is removed like any other leftover and the file keeps its final name; no write of this record opens an existing temporary name, so it is not written through by one.
- **A run directory that holds a leftover and no `instance.json`** states what a missing file states — "no instance record was written for this `run_id`" (cited: ADR-0018 decision 2) — and nothing more. This record gives a leftover no meaning: it is no sign that a start was tried, and no reader looks for it.

### 7. What the rule promises and what it does not

Whenever the writing process dies (the final name not taken before the write):

| The writing process dies | On disk | The next reader of `instance.json` finds |
|---|---|---|
| Before the temporary file is complete (steps 2 and 3) | No file under the final name. A temporary file holds a part of the content | A missing file |
| After the temporary file is complete and before the last step | The same, and the temporary file holds the whole content | A missing file. The write did not happen; the leftover is not used (decision 6) |
| After the last step | The final name holds the whole content. With `link()`, a death before the removal leaves the temporary name as a second name of the file: a leftover | The whole content |

At none of these moments does the final name hold a part of a content. When the name was taken before the write, it holds at every moment what it held.

- **Promised — the death of the writing process**, at any moment: the final name holds nothing or the whole content. **A reader during the write** finds a missing file or the whole file and never a part (cited: POSIX `link()` gives the name in one step).
- **Not promised — the loss of the machine, of power or of the working tree** before the next commit (cited: #5 A-3). The flush of step 3 is required nevertheless, for the reason of ADR-0013 decision 5 (a file system may make the name durable before the content), which weighs more here: no next write would replace an empty or partial file. The directory entry need not be flushed. The cost is one flush of a small file per write.
- **The environments**: as ADR-0014 decision 6 has it for a key record file — the native file systems of the POSIX environments of C-7 that give the non-replacing step of decision 3 of this record; a network file system, a Windows drive seen from WSL and native Windows are limits about which nothing is stated.
- **Two writers at once are a limit, not solved here** (the lock, rest of OD-17; C-2). Each writes its own temporary file; the last step of one gives the name and the other finds it taken (decision 4). Which of the two that is, is not ordered, and the file is never a mixture of the two. A writer that removes leftovers can remove the temporary file of a live writer, whose last step then fails and changes nothing.
- **"Once" is kept by this step only against another write by these steps.** Nothing prevents a process from writing, replacing or removing the final name by other means (cited: ADR-0004 decision 10; ADR-0018 decision 6), and after a removal a write by these steps gives the name again. "Immutable" stays ADR-0004's word, which nothing enforces.
- **Not said**: that the content is right or complete. Step 1 checks validity and the written form and nothing more. No atomicity is added between this file and `STATE.json`, any other file or a commit. A death after the last step and before the report leaves the whole file and a caller that was not told (sub-question ㉓). Bringing the file back from the history is not a write of this record.

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 2 | No check of the content before the write | An invalid content given the name in one step is still an invalid file, and nothing rewrites it. |
| 2 | The write requires `tolerance`, `source_commit` or `n_max`, or fills in a default | It would answer sub-questions ⑲ to ㉑, which are open and are not about how a content reaches the disk. |
| 3 | The replacing rename of ADR-0013 | See decision 3: every write would be able to replace the record a run was started with, silently. |
| 3 | A look at the final name, then the replacing rename | Two steps; the file looked at is not necessarily the file replaced (as ADR-0014, Alternatives, point 3). |
| 3 | Exclusive creation of the final name in place (what a writer without a rule would do) | Nothing is replaced, but a death inside the write leaves a partial file under the final name: the case the requirement excludes, and one nothing repairs. |
| 3 | A replacing rename, or an in-place creation, where the non-replacing step is unavailable | The same write would keep or lose a property depending on the file system, silently (as ADR-0014). |
| 4 | A taken name whose file has the same bytes, or parses to an equal document, is reported as written | No record says what "the same content" is for this file, and it would decide that a second start with an equal content is the first one continuing (sub-question ㉓). A caller can read the file itself. |
| 4 | A taken name is reported like any other failure of the file system | The caller could not tell "another content is the record of this run" from "the disk failed", which call for different acts whatever those are. |
| 5 | The write refuses when the run directory exists, as a means to keep a `run_id` unique | It would fix that this file is written before the first `STATE.json` (⑩) and choose the means ADR-0004 decision 8 left open. |
| 5 | The write refuses when the run directory is missing | It would fix that another file is written first (⑩). |
| 6 | One fixed temporary name; a hidden name; a subdirectory | As ADR-0013 (Alternatives, point 3). |
| 6 | A whole valid leftover is given the final name by the next writer or reader | The write it belonged to did not happen (ADR-0013 decision 4), and it would make a reader a writer. |
| 7 | Drop the flush because the file is written once per run | Without it a power loss can leave an empty file under the final name, which no next write replaces. |

## Consequences

- **A code slice can now be cut** (code mode, within the size cap): a function of the package that writes a valid content of `instance.json` by the steps of decision 3. Where it lives, its name, its call form and what it raises are that task's. `hilclaw/instance.py` is at 550 lines; `_store` of `hilclaw/key_records.py` and `replace` of `hilclaw/run_state_file.py` hold the two landed techniques, and whether a helper is shared is that task's choice. It needs to report: a content that is not valid or not in the written form (before the file system is touched), a failure of the creation, the write, the flush or the giving of the final name (with its temporary file removed; a failed removal of the temporary name after the final name was given is no failure of the write — decision 3), a name found taken (decision 4, told apart from the other failures), and a data root that does not exist (the convention of the package's other writers, which never create it). **Binding the function to a tool, to a start of an instance or to any caller is not part of that slice.**
- **Docstring sentences that then change**: in `hilclaw/instance.py`, "It writes, creates and removes no file and composes no content", if the function lands in that module. The sentence of its last paragraph, "says nothing of what writes the file, of when, or of a run directory without it (OD-8 sub-questions 10 and 17)", stays true.
- **The steps need a process that can create, flush, link or rename, and remove a file.** Whether that makes the writer go through a tool of the package is not concluded here (OD-23).
- **Handed to the isolation decision** (sub-question ㉓, second part, beside ⑭ and ⑯): whatever writes `instance.json` must be able to create, link or rename, and remove entries of the name form of decision 6 in the run directory, and to create that directory and `runs/` when they are missing. Neither candidate is chosen or excluded by this.
- **As long as the file is written by the steps of this record only, a commit taken at any moment takes no `instance.json` or a whole one.** A write that does not follow this record is outside that statement.
- `hilclaw/instance.py` and `hilclaw/layout.py` are consistent and unchanged: the reader opens the final name only, reports a missing file and follows no symbolic link, and `RUN_FILES` keeps its four names. The rows of ADR-0019 decision 3 for `instance.json` are unchanged: a partial file is still invalid, and it no longer comes from the death of a writer that follows these steps.
- **Not edited and now less exact** (follow-ups for the integrator): ADR-0018 decision 2 ("How the file comes to be on disk is not decided … Until then nothing excludes a partial file after the death of a writer"), its Status ("what writes the file, when and by which steps"), its Consequences ("Writing the file is not part of that slice: it needs the answers to sub-questions ⑩ and ⑰" — the steps no longer wait; who writes and when still do) and its Boundaries (the text of ⑰); the Boundaries of ADR-0020, ADR-0022, ADR-0023 and ADR-0024, each of which lists "what writes `instance.json`, by which steps" as open; ADR-0014 decision 7 as far as it lists `instance.json`; ADR-0013 Boundaries ("how `artifacts.json`, the key record files or any other file is written"); ADR-0004 decisions 1 and 2 as ADR-0013 Consequences list them. No sentence of UsageCases became false: UC-1 and UC-3 say nothing of how the file is written.
- **A-13 reading**: document mode; no code, dependency, settings file or schema file changes. No member, type or validity rule of `instance.json` changes and no file changes its validity, so this is not a schema change of the data plane: the record adds a rule about how the file comes to be on disk, as ADR-0013 and ADR-0014 did for theirs.

## Boundaries (not decided here)

- **Owner-only or waiting for the owner (DRIVER §9)**: OD-3, OD-25, C-6, the #5 A and B items. **No reading of #5 A-1, A-7, B-4 or of HQ-0004 is made here.**

- **Sub-question this record raises** (registered under OD-8): ㉓ in two parts.
