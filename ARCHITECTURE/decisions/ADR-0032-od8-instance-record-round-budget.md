## Context

A vocabulary of four axes; the values are given by the user at run time; when several are given, the run ends when any is used up; the default end keeps the best.
- **Owner** (#5 B-4), under the heading "**First spec example (GEMM, MVP round 1)** — cost is controlled by instance parameters (FR-3), not by model choice": "Initial run caps: N = 1–2 candidates per round, budget 5–10 rounds, measurement repeats adaptive per OD-13 with an initial upper bound of 10." Of the owner's comments on #5 no other speaks of a budget of rounds. Two of the three values of that line have a member (`candidates_per_round`, ADR-0028; `n_max`, ADR-0023); the third has none.

StandardScenarios: S1 step 2 starts an instance with "budget=20 라운드" and step 7 ends it with "budget 소진 시 best 커널 유지로 종료"; S2 step 1 starts one with "budget=wall-clock 8h + 토큰 상한" — two axes, neither of them rounds; S3 step 3 goes on "새 budget과 …으로 분기하여".

ADR-0012 decision 3: `STATE.json` holds `round`, "the round the run is at".

ADR-0011 "names no axis, no unit and no party that measures" (decision 1), leaves open "whether a given axis is accounted through the log at all … a count of rounds or an elapsed time can be obtained from other records" (decision 7), and "stops nothing" (decision 9). ## Decision

A sentence marked **owner** renders the line of #5 B-4 or its heading, both quoted in Context. A value is **cited** when another source is named with it. Every other value is **this record's own** choice — among them the reading that the loop iteration of FR-3 ① is the round, the name `round_budget`, its place, the written form, that the rule of validity starts at 1 and has no end below the *integer* range, that the member may be absent, that an absent member means "not stated" and never "unlimited", a default or zero, that a present and invalid member makes the file invalid, that what counts against the budget is left open, that no rule ties the member to `STATE.json`, to the spend view or to another member, and the list of limits.

### 1. Scope

This record fixes one thing of `runs/<run_id>/instance.json`: the member in which a run states its budget of rounds. Nothing else of the file is fixed and nothing of any other file. **A file that holds what ADR-0018, ADR-0020, ADR-0022, ADR-0023, ADR-0024, ADR-0028, ADR-0031 and this record define is still not a complete instance record, and no run can be started from it alone** (ADR-0018 decision 1).

### 2. What the member states, and its unit

- **The member states the budget of loop iterations (FR-3 ①) the instance was started with, as a number of rounds.** That such a budget exists and that its value is given by the user at run time is cited (FR-3); this record gives it a place and adds nothing to it.
- **The unit is the round.** **Owner**: "budget 5–10 rounds" — the owner counts the budget of the initial runs in rounds, under a heading that names FR-3 with the instance parameters that control cost. That the "loop-iteration" of FR-3 ① is the round of FR-1 is **this record's reading**; no source says it in one sentence. It rests on FR-1, which names the loop it defines the "HIL 라운드 루프" and its iteration the round ("다음 라운드 결정"), on S1 step 2 ("budget=20 라운드"), on ADR-0004 decision 2 (cited: one sequence of rounds per run, the number of "turn ≡ Round") and on the owner's line. This agrees with ADR-0023 decision 2 and ADR-0028 decision 2, which read the same line as naming "budget 5–10 rounds" beside the repeats and N and apart from them, and the same heading as speaking of instance parameters that control cost: the round budget is such a parameter, and it is an axis of the vocabulary of FR-3, which `n_max` and N are not.
- **What a reader of this record may conclude** from a file that states the member: that the run states this number of rounds as its budget of loop iterations. No more.
- **What it may not conclude.** The member is not N (`candidates_per_round`), not `n_max`, and not a number of coder calls, of specs, of attempts or of repair calls (FR-1 ⑴; OD-19). It is no amount of tokens or of time and no target metric (the other axes of FR-3), and no amount of hardware quota (OD-2) (Boundaries). It does not say that the run had, has or will have that many rounds. That a stated budget used up ends the run is FR-3's; this record adds no rule that ends a run when a count reaches the number, and nothing compares anything with it (decisions 5 and 6). A run may end earlier on another axis, on a target or on the user's word (FR-3; UC-2), and the file does not say which other axes the instance was given. It does not say that the value lies within the owner's 5 to 10.
- **What counts against the budget is not decided here.** The inputs carry a number of rounds and no rule of counting. They do **not** carry, and this record does not decide: whether round 0 (bring-up and baseline) counts (OD-28; ADR-0002 Boundaries, "what round 0 does beyond FR-1"); whether a round that is cut short or given up counts (OD-19; ADR-0012 decision 3 does not define "whether a round can be given up"); which number the budget is compared with — the `round` of `STATE.json` or a count obtained otherwise —, at which moment and by what (OD-19, OD-23). They are registered (sub-question ㉙ (i)). **The member has its meaning without them**: it records what the instance was started with (cited: ADR-0004), as the owner's "budget 5–10 rounds" and the "budget=20 라운드" of S1 state a budget without a rule of counting. The cost, plainly: until that rule exists, two readers can differ in what the stated number allows, and this record gives neither of them the answer.
- **One value per run.** The file is written once (cited: ADR-0004 decision 4) and the member is one integer. How a continuation or a branch under a new budget (S3 step 3; FR-6) relates to a file that is written once, and to the spend of the run it starts from, is OD-8 sub-question ① and is not decided: a new run has its own file; for later rounds in the same run no record gives a place to a second budget (decision 6).

### 3. The member

- **The member is `round_budget`**, a top-level member: an *integer* of ADR-0001 (0 to 2^53 − 1, the form ADR-0018 decision 2 uses for `schema_version`) that is **at least 1**.
- **Written form**: that of ADR-0023 decision 3 — a JSON number in decimal digits without sign, fraction or exponent. **`10.0` and `1e1` are no values**, though both denote ten: one spelling per value, as `hilclaw/instance.py` has it for `n_max` and `candidates_per_round` (exactly an `int`).
- **Nothing else is a value**: `true`, `false`, `null`, a string (`"10"` and `"unlimited"` included), an array, an object, `0`, `-0`, every negative number and an integer above 2^53 − 1.
- **The name** is this record's choice: "budget" is the word of FR-3 and of the owner's line, "round" is the unit (decision 2), and together they say what is stated and in what it is counted. Weighed against it:
  - `rounds`, `max_rounds`, `round_limit`: the first reads as the number of rounds a run had; the other two name a limit that something keeps, and this member stops nothing (decision 6). `max_rounds` would also stand beside `n_max`, which is no bound of rounds.
  - **A name shared with an axis of the spend view** (`budget_spent.totals`): no axis is named (cited: ADR-0011 decision 1), and whether rounds are accounted through the log at all is open (cited: ADR-0011 decision 7). **`round_budget` is the name of a member of this file and nothing else**: this record names no axis of the spend view and does not say that rounds are, or are not, such an axis.
- **Why a top-level integer and not an object for the budget** with one member per axis. FR-3 calls the four a vocabulary and S2 step 1 states two axes at once, so an object is the nearer picture. It is not chosen, for the reason of ADR-0023 decision 3 and ADR-0028 decision 3: no other member of such an object has a fixed form — whether tokens are one sum or split is #5 A-8, HW quota is OD-2, the target metric is #5 A-4 and OD-1, and wall-clock time has no fixed unit — so the object would be shaped by members that do not exist. A closed object would make each later axis a change of the form of the member, which raises `schema_version` (cited: ADR-0018 decision 2); an open one would need a rule of its own for a member it does not know. **This record therefore fixes no place and no name for any other axis and no rule that encloses them**: a later record states its axis in a member of its own or changes this one, and applies the version rule of ADR-0018 decision 2. The cost: a later record that wants one object for all axes moves this member and so raises the version (sub-question ㉙ (iii)).
- **The lower end is the number 1** — this record's own choice; no input states a lower end. Whether `0` could be a value is a question of meaning, and its meaning hangs on what decision 2 leaves open: if round 0 counts, a budget of 0 rounds would be at odds with FR-1, which has every instance carry out round 0; if it does not count, 0 would state a budget of no round after the bring-up round. 1 is the smallest number that states a budget under either answer. A record that settles the counting and finds that 0 must be a value changes the form of this member and applies the version rule. The owner's range begins at 5; this record does not rest the rule on that (next item).
- **No upper end below the *integer* range — the owner's "5–10" is not a rule of validity.** **Owner**: "Initial run caps: … budget 5–10 rounds". This record reads it as the owner's cap for the initial runs — a statement about what those runs are started with, not about what a file may state — as ADR-0028 decision 2 read "N = 1–2" of the same line. The other inputs set no end: FR-3 has the value given by the user, S1 step 2 uses 20, and "the tree sets no upper bound on rounds" (cited: ADR-0004 decision 3). The file is written once: a 10 or a 5 in its rule would turn a change of that cap into a change of the form of this member. **What follows, plainly: a valid file may state a value outside the owner's range (1, 20, 1000), and nothing in this record refuses it.** What applies the cap to the initial runs, and whether the start of an instance checks a chosen value against any range, is not decided (sub-question ㉙ (ii)).
- **A valid value is not thereby one a run can be carried out with** (decision 6).

### 4. A file without the member; the version

- **The member may be absent from a valid file, and `schema_version` stays `1`** — the first of the two choices ADR-0018 decision 2 leaves to the record of a member ("A later record that defines a top-level member which may be absent and may be passed over does not raise it"). A version 1 reader may pass over the member: no fixed rule makes anything a reader of today does depend on it, and a reader that needs the round budget of a run is one that knows the member. The inputs ask for it: the budget is optional at the start (UC-1 step 1, "(선택) budget"), FR-3 speaks of "복수 지정 시", and the instance of S2 step 1 is given two axes and no number of rounds.
- **A member that is present must be valid.** A file whose `round_budget` breaks decision 3 is **invalid** in the sense of ADR-0018 decision 2: a reader of this record reports it, uses no member of it — not its `hw_profile`, its `tolerance`, its `source_commit`, its `n_max`, its `candidates_per_round` or its `op_signature` either — and repairs nothing. This follows ADR-0020 decision 3, ADR-0022 decision 5, ADR-0023 decision 4, ADR-0028 decision 4 and ADR-0031 decision 5.
- **A valid file without the member states no round budget.** A reader of this record that is asked for the round budget of such a run finds that none is stated. **"Not stated" is not "unlimited", not a default and not zero**: the reader **never substitutes a value** — not a number of the owner's range (5, 10), not the 20 of S1, not the 5 of PLAN P2-5, not a constant of the source the reader runs from, not the `round` of `STATE.json`, not a count of round directories, and not a value from another run — and it does not conclude that the run may go on without end, nor that it may not begin.
- **No path yields a round budget the run did not state.** A reader of this record has the round budget of a run only when the file of that run is valid, is of version 1 and holds the member. A missing file, a file that cannot be read, an invalid file, a file of another version and a valid file without the member each leave it without one.
- **What this record does not say**: whether an instance may start with no budget axis at all, and what ends a run whose file states no round budget. FR-3 ends a run when a stated axis is used up and says nothing of a run that states none; UC-1 makes the budget optional and names a target reached early as the other end. A valid file is "not thereby enough to start a run" (cited: ADR-0018 decision 2). Whether the start of an instance refuses to begin without a budget is the writer's and is not decided (sub-question ㉙ (ii)).
- **Why not a required member and version 2.** Against UC-1, which makes the budget optional, and S2 step 1, which starts an instance without a number of rounds; and every file and every reader of today would be of another version before a first run exists, the record would have to say which layout version the new `schema_version` states (ADR-0024 decision 3), and reading another version is OD-11 (the cost ADR-0028 decision 4 and ADR-0031 decision 5 name).
- **The cost**: validity does not show that a round budget is stated. A file without the member and a file whose member name is misspelt look alike to a version 1 reader — both state none (decision 6).

### 5. The member, `STATE.json`, the spend view and the other members; how it is read

- **This record adds no rule between the member and the `round` of `STATE.json`.** No file is invalid, and nothing is reported, because `round` is at or beyond the stated number. A rule would be a rule of counting (decision 2) and of enforcement (OD-19), and ADR-0012 is not edited: `round` "names the round the run is at" and does not say "whether a turn runs at all" (cited: ADR-0012 decision 3).
- **No rule between the member and `budget_spent`.** `budget_spent.totals` "holds amounts accounted through the log only" (cited: ADR-0012 decision 4), and this record does not say that a round is such an amount (decision 3). Nothing of ADR-0011 or ADR-0012 changes.
- **No rule that anything is stopped.** "The accounting stops nothing: reaching or passing a budget has no effect by this record (OD-19)" (cited: ADR-0011 decision 9), and neither has it by this one: the member states a budget, and what compares anything with it and what ends a run is not decided here (OD-19).
- **No rule between the member and another member of the file.** `round_budget`, `candidates_per_round` and `n_max` are each valid by their own record, and no product or sum of them is a bound.
- **The round budget a run states is the one in this member of the file of that run**, `runs/<run_id>/instance.json` below the data root in use. A reader of this record reads the file as a whole, which must be valid (ADR-0018 decision 2), and **nothing is kept between calls** (cited: ADR-0010 decision 7; ADR-0018 decision 4): a later call reads the file again.
- **Today nothing reads or writes the member, and nothing reads or compares a budget of a run**: no tool, registry, backend, hook or module does, and `hilclaw/instance.py` passes the member over. **Not said here**: which component reads it, at which moment, and what follows when no round budget is stated (Boundaries).

### 6. Limits

- **Whoever can write the file changes the round budget the run states.** No access control exists and the tree does not enforce the single writer (cited: ADR-0004 decision 10); a file changed after the start is read as it is at that read (cited: ADR-0018 decision 6), so two reads of the file of one run can find two budgets.
- **The member stops nothing.** A run whose rounds go beyond the stated number is not prevented, reported or made invalid by this record (decision 5).
- **A misspelt name.** A top-level member that is not spelt `round_budget` (`rounds`, `budget`, `roundBudget`, `budget_rounds`) is passed over (cited: ADR-0018 decision 2, the cost) and the file states no round budget — which is not "unlimited" (decision 4).
- **Two processes, two sources** (cited: ADR-0010 decision 7; ADR-0018 decision 6): a source older than the code of this record passes over the member and takes as valid a file whose `round_budget` a newer source refuses.
- **A large value is a cost this member does not cap**: a round costs coder calls under the one subscription of C-7 ② and hardware time, the board being a shared and limited resource (C-4). Nothing here limits what a run may state below 2^53 − 1 — the 10 of the owner's range included.
- **A file written once cannot state a second budget** (decision 2). The name stands near `round` and `budget_spent` of `STATE.json`; it is neither the pointer nor a part of the spend view.

### Walk-through

What a reader of this record finds when it is asked for the round budget of the run `r1`.

| `runs/r1/instance.json` | What the reader finds |
|---|---|
| Valid, version 1, with `"round_budget": 8` | The round budget `r1` states: 8. Asked again in a later call, it reads the file again |
| Valid, version 1, without the member | No round budget is stated for `r1`. No value is substituted, and the reader concludes neither that the run is unlimited nor that it may not begin. The other members of the run can still be had |
| `"round_budget": "8"`, `8.0`, `8e0`, `-8`, `0`, `null`, `true`, `[8]` or `9007199254740992` | The file is invalid: no member of it is used, neither the round budget nor the `hw_profile` or any other |
| Valid, version 1, with `"rounds": 8` (or `"budget": 8`, `"budget_rounds": 8`) | As the second row: the member of a nearby name is passed over, and no round budget is stated |
| Valid, version 1, with `"round_budget": 20` (or `1`) | The round budget `r1` states: 20. The file is valid: the owner's 5 to 10 is no rule of this record |
| Missing, unreadable, or of another version | No round budget can be had, as ADR-0018 has it for the `hw_profile` |
| `r1` states `"round_budget": 8` and `runs/r1/STATE.json` holds `"round": 12` | The round budget `r1` states: 8. **By this record nothing follows from the two numbers together**: neither file is invalid, nothing is reported, and whether the budget is used up is not said (sub-question ㉙ (i)) |

## Consequences

- **The code slice that can now be cut** (within the size cap, code mode): in `hilclaw/instance.py`, the validity of the member by decision 3 and a reader of the round budget of a run beside `candidates_per_round_of`, with tests in `tests/test_instance.py`. The name and the return form of that reader and how "not stated" is told from a value are the code task's. **Binding the reader to `STATE.json`, to the spend view, to a tool or to anything that ends a run is not part of that slice**, and neither is writing the file. `hilclaw/instance_file.py` takes the validity of a content from `hilclaw.instance.parse`, so it refuses a content with an invalid member once the slice lands, without a change of its own.
- **Sentences of the code that then change**: in the docstring of `hilclaw/instance.py`, the list of the records in its first line and first paragraph, "Conventions of this module, which the seven records do not fix", the order of the checks, the sentences that say of `n_max` and of `candidates_per_round` that the module makes them "no budget member" (they stay true and stand beside a member that is one), and the descriptions of `Instance.others` in `parse` and of the records in `validate`. No case of `tests/test_instance.py` holds a top-level `round_budget` today — two cases of one parametrised test hold a member `budget` among members not defined, and that name stays not defined —, so none asserts a content valid that this record makes invalid; the assertion on `Instance._fields` and every case that builds an `Instance` positionally change only if the slice adds a field to that tuple.
