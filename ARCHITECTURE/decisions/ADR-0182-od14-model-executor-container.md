## Decision

A sentence is **cited** when a source is named with it; every other sentence is **this record's own**.

### 1. Scope

- **The runs**: every generation of the model executor at `cpu_standin` — the bf16 forward program of ADR-0166 (with the greedy mode of ADR-0176 decision 5) and the fp32 model program of ADR-0153 slice 1 — that runs a kernel an instance or a coder wrote. **Its builds and process**: the build of each kernel's shared library, the build of the program, and the one generation process (cited: ADR-0153 decision 1, "one process per generation").
- **Not in scope**: the driver's tests with kernels they write themselves (decision 7), targets other than `cpu_standin`, the exposure of the executor (OD-31 ⑩, OD-18, OD-23), and the P2-15 run on a runtime machine with real weights beyond what decisions 4 and 6 say of its size.

### 2. (a) Where they run: one new ADR-0144 container per build and per process, nothing on the host

- **Each kernel-library build, the program build and the generation process run in a new container of their own**, started and ended as ADR-0144 decision 3 (a) starts and ends one (cited): the client of the container runtime, a name used for that container only, `--rm` on a normal end, a forced removal by name at the limit. A generation with k distinct kernels starts k + 2 containers.
- **ADR-0144's properties carry over unchanged** (cited: its decisions 2 and 6): Q1 everything inside; Q2 the build directory as the one host path, writable, at a fixed path that is the working directory; Q3 crossing by copy, the kernel's copies in a sub-directory that holds nothing else; Q4 removal, the build directory only after the last container is gone; Q5 the `none` network; Q6 the numeric user and group with every capability dropped and no new privileges; Q7 no resource bound; the pull policy `never`; the entrypoint overridden; no variable handed in. These are the options `run_in_container` gives (observation), so the executor adds none and removes none.
- **No build or process of these runs on the host, ever** — ADR-0144 decision 4 applied to them (**owner**, K1, read as ADR-0144 decision 4 reads it: "names how these builds and runs are carried out, not a preference"). Where no image is named, the image is refused, the client is not found, the platform has no numeric user, or the container runtime refuses a build container, the generation ends with **container unavailable** (decision 8) and nothing falls back to a host build or process. **The reading that grounds it**: a model run executes generated kernel code as a correctness run does, so NFR-4's sandbox and K1 cover it — the reading ADR-0153 Consequences gave the owner to check (cited), which this record takes.
- **Three ways were weighed.** (i) **One container per build and per process** (taken): ADR-0144 decision 3 (a)'s reasons hold (cited): each limit bounds one container, its forced removal is expected to end every process inside it, and a process a compiler leaves behind does not share the generation's container. The cost: k + 2 container starts. (ii) **One container for the whole generation**, the builds and the process started inside it one after the other: ADR-0144 decision 3 (b)'s objections hold (cited) — a compiler's leftover beside the generation process, a container alive between started programs, limits that bound programs rather than the container — and it would need a program of the image to start the others, which ADR-0144 decision 5 does not require (no shell is in its list). (iii) **One container for all builds and one for the process**: the same objection for the builds, and the k kernel builds would lose the per-kernel outcome of ADR-0153 decision 5 ("build failed (kernel reference, compiler output)", cited) unless a program inside told them apart.

### 3. (b) The image: the one `HILCLAW_STANDIN_IMAGE` names, with ADR-0153's two loading needs as a requirement on it

- **The image is the one the user names in `HILCLAW_STANDIN_IMAGE`** (cited: ADR-0144 decision 5 (c), its name the code slice's — `hilclaw.standin_image.ENV_IMAGE`, observation). A second variable for the executor was weighed and not taken: the kernels a model run loads are the kernels the checks verified (FR-9), and one image keeps ADR-0144 decision 5's "one compiler … one environment" (cited, from ADR-0107 decision 3) between the check that verified a kernel and the run that uses it.
- **The two loading needs of ADR-0153 decision 2 become a requirement on that image, for the executor**: clang able to link a shared library (`-shared -fPIC`, `hilclaw.model_build.LIBRARY_FLAGS`, observation) and the POSIX dynamic-loading interface of `<dlfcn.h>` (`dlopen`, `dlsym`), with whatever trailing flag its C library needs (`-ldl` or none), which stays the caller's (cited: `hilclaw.model_build`, "adds no `-ldl` … that is the caller's `trailing_flags`"). They are added to ADR-0144 decision 6's list "Of the image" for the executor's runs only; the checks and run tools ask nothing more of it.
- **This is a requirement, not a change** (**owner**, K2, read as ADR-0144 decision 5 reads a change of the variable): the runtime installs, pulls, builds and updates no image; it uses the image the user named, already in the store (pull policy `never`). An image that lacks a loading need makes a build container fail (**build failed**) or the generation process end with a non-zero status (**run failed**), and nothing is repaired. **No concrete image is adopted.** Whether a C library of the POSIX.1-2008 kind that ADR-0144 decision 5 requires holds `<dlfcn.h>` is not stated by any record; this record's reading is that the common ones do, and it is runtime acceptance item (1).
- **Why this is not owner-only** (criterion 3 of the task that wrote this record): nothing here changes a user's image or asks the runtime to; it names what a user's image must hold for one more use, as ADR-0144 decision 5 named what it must hold for the checks. The reading is restated for the owner to check (Consequences), as ADR-0153 already listed it.

### 4. (c) What crosses into the container, and what comes out

- **The kernel sources, by copy** (cited for the manner: ADR-0144 Q3): the source files of each distinct `KernelReference`, read without following a link and written with their own bytes under their basenames into the sub-directory `kernel-<i>` of the build directory, which holds nothing else; two sources of one kernel with one basename are refused (a copy that cannot be written, `entry_exists`) rather than renamed. **A kernel's own headers are not copied**: a `KernelReference` names its compiled set "without its headers" (cited: `hilclaw.attempt_kernel`, observation), so a kernel that includes a header of its own fails its build in the container where the host build found the header beside its source. Carrying the headers is slice 2 (decision 9).
- **The program source, by copy**: `model_forward.c` (or `model_program.c`) beside the kernel sub-directories, as the harness program's copy lies beside the kernel's (cited: ADR-0144 Q3).
- **The input file, written by the host side into the build directory**: the bytes of `encode_input` (cited: ADR-0166 decision 4, what the host side hands over) as `input.bin`, read by the process through the one mount. No other channel is needed: the input is a file by ADR-0166's design (cited), and a file of some gigabytes is no command-line argument; standard input (ADR-0180 decision 3) was weighed and not taken — it adds `--interactive` and a pipe the program does not read, for no gain over the mount the build directory already is. The file is written in the build directory, so it is removed with it (ADR-0144 Q4).
- **Paths inside**: every path on a command line is the absolute path inside the container below `/build` (cited for the form: `hilclaw.standin_check.in_container`, observation) — the libraries `/build/kernel-<i>.so`, the executable `/build/model_forward`, the input `/build/input.bin`. The program `dlopen`s the libraries by those paths.
- **Out**: nothing crosses as a file. A build says its status and its log (the client's standard output then its standard error, ADR-0169 decision 2, cited); the generation process says its report on standard output (cited: ADR-0166 decision 7), as today. The libraries and the executable lie in the build directory between the containers of one generation and are used by no other.

### 5. (d) Time limits: the caller's, required, with no default; the forced removal 60 s

- **Each build container gets the caller's build limit and the process container the caller's run limit**, as `model_forward_execute.execute` takes them today (observation); neither has a default, and a limit that is not a positive finite number is refused before anything is made. NFR-4's timeout guard is held in that **every container has a finite limit**; its value is the caller's.
- **Why no source and first value as ADR-0117 and ADR-0179 gave the checks.** Their rule is tied to the call of a tool: the cap of 1500 s and the build's 60 s are set so that one call fits the MCP idle window (cited: ADR-0117 decision 5). The executor is no tool and no backend operation (cited: ADR-0153 decision 1), and who starts a model run, through what, under which window, is open (cited: ADR-0153 decision 1, OD-31 ⑩, OD-18, OD-23). A rule without that bound would be a work measure of a whole generation (the sum of ADR-0179's kind measures over every call of every pass) with a cap no source gives. The source and values go with the record of the exposure; until then the caller — a driver test, or the P2-15 runner on a runtime machine — states them.
- **The forced removal of each container is given 60 s** (cited: ADR-0169 decision 5, and its reason: "Nothing a removal does grows with the work of the kernel"), the constant `hilclaw.standin_check.REMOVAL_TIMEOUT_S` (observation). It lies after the container's limit and is part of neither (cited: ADR-0144 decision 3).
- **The longest generation** is k + 1 build limits and one run limit, plus at most one forced removal of 60 s (a forced removal ends the generation, decision 8), plus the host side's own work, which nothing bounds.

### 6. (e) Memory: no bound and no figure; stays open

- **No memory bound is set on any container of the executor**, as on those of the checks (cited: ADR-0144 Q7), and **no memory figure is taken**: ADR-0145's waiter reads the maximum resident set of a timing process for `memory_ceiling` (cited: ADR-0145 decision 3), a measurement of an attempt, not a guard, and a model run reports tokens and logits only (cited: ADR-0153 decision 4, "Report"). NFR-4's resource guard stays with OD-14's resource ceilings, as for every other run (cited: ADR-0117 decision 6, "resource caps … (OD-14)").
- **What follows for ADR-0153 runtime acceptance item (lxviii)** ("a generation at the dimensions of Llama 3.2 1B … fits the environment's memory limit", cited): with no bound set, the environment's memory is what the container runtime gives a container with no constraint — on Docker the host's (cited: ADR-0144 E9), on Docker Desktop its VM's — and the generation process holds the weights it reads (cited: ADR-0166 decision 2, buffers owned by the program) while the host side holds the bytes of the input file it wrote. Item (2) narrows (lxviii) to that.

### 7. (f) The host path: kept, only for kernels the caller wrote itself

- **`hilclaw.model_forward_execute.execute` (and `hilclaw.model_execute.execute`) stay**, building and running on the host, **for kernels the caller wrote itself** — the driver's tests, whose kernels are "hand-written by the test to each kind's contract" (cited: ADR-0153 decision 6), also when a test writes them into attempt directories it made. They are **not used for a kernel an instance or a coder wrote**; for such a kernel the container path of decision 2 is the only path (decision 2, ADR-0144 decision 4).
- **Why keep it**: the driver's tests run on development machines with no container runtime (D16; CLAUDE.md "개발 드라이버와 런타임의 구분"), and the host path is what lets them build and load the forward program with the real `clang`; it also gives the container path a bit-for-bit reference in its own test. Those kernels are not generated code, so K1 does not reach them.
- **Why the rule is not enforced by code**: a `KernelReference` names source paths, a contract and flags (observation) and nothing about who wrote them; a provenance member would be one a caller sets, so it would not stop a caller that breaks the rule. The rule is stated in the docstring of the host path, and a caller that hands it a generated kernel breaks this record. Removing the host path was weighed and not taken: every driver test of the forward program would then need a stub client that runs `clang` on the host anyway.

### 8. Outcomes

- **The five of ADR-0153 decision 5 stay** (cited): **no kernel**, **kernel unfit** and **invalid input** from the check, before anything is read, made or started; **build failed** for the first build container that times out, ends with a status other than 0 and 125 to 127, or ends with 0 and leaves no regular file at its output; **run failed** for a process container that times out, ends with a status other than 0, or leaves no complete report.
- **One outcome is added, container unavailable**, with five reasons: no image named, the image refused, the client not found, no numeric user, and a build container that ended with 125, 126 or 127. Nothing after it is started. It is an outcome of the executor's own, not a tool's kind: no `error.kind`, `condition` or data-plane value is added (ADR-0168 decision 6's concern does not arise; the executor answers no tool contract, cited: ADR-0153 decision 1).
- **The statuses 125 to 127 are read as ADR-0168 decision 3 reads them** (cited): for a build container the container runtime's — no code of the attempt runs in a build — so container unavailable, not build failed; for the process container the program's — the kernels run in it and can end it with any status — so run failed with the exit status, never container unavailable. A kernel therefore cannot turn its own failure into an environment failure.
- **Errors passed on** (cited for the manner: ADR-0168 C14, C18): any other `OSError` of the client's start or of reading its output is raised as it is, and the build directory is left, since a container may still run; a request to end passes after the forced removal `run_in_container` makes. A copy that cannot be read or written raises its copy error before any container is started.
- **The build directory** is removed after the last container only where every container of the generation is shown to be gone (cited: ADR-0168 decision 5); otherwise it is left, and the outcome says so.

### 9. (g) Code slices, in landing order

1. **The bf16 forward path in containers** (landed with this record): `hilclaw.model_forward_container.execute`, beside the host path, with the outcomes of decision 8. It reuses the check, the library table, `encode_input` and `parse_report`, `run_in_container`, `read_image`, the copy primitives and `build_dir_removable`.
2. **The kernel's own headers**: the kernel reference carries the headers the reader of ADR-0055 found beside its compiled set (`attempt_kernel` answers them), and slice 1 copies them into `kernel-<i>` beside the sources (ADR-0144 Q3's "The kernel's own headers are found as before, beside the kernel sources", cited). Needed before an instance kernel that includes a header of its own is run.
3. **The fp32 model program path** (`hilclaw.model_execute`, ADR-0153 slice 1) **follows the same rule**, in a slice of its own: its builds and process in containers as decisions 2 to 8 say, `model_program.c` the program source. P2-14 does not run it; the planner judges when.

Each slice is within DRIVER §5's cap. The exposure of the executor (OD-31 ⑩) and the time-limit record that goes with it (decision 5) are no slice of this record.
