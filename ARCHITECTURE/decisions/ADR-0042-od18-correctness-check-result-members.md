## Decision

A sentence is **cited** when a record and its decision, or a requirement, is named with it; it then says what that source says and adds nothing. Every other sentence is **this record's own** — among them every member name, type and value, when a member is present, that a result holds the counts, the dimensions, the number of draws and the tolerance and does not repeat the point, that the member list is closed, and every weighing. No sentence is the owner's.

### 1. Scope and terms

- This record is about **a result of a call of `correctness.check`**: what the tool function returns for a check — "one call that reaches ⑥" (cited: ADR-0021 decision 1) — whose judging ended in a pass, a fail or a broken run, each of which is a result (cited: ADR-0021 decision 5). The check is about one attempt of a run that ADR-0021 and ADR-0038 decision 6 cover and whose stated op_signature is covered; a call about a run that states none, or one that is not covered, reaches no check (cited: ADR-0041 decisions 4 and 5).
- **A result has one form at both execution points and for a run at the mock.** The judging is the tool function's part and "the same code for every backend" (cited: ADR-0021 decision 2), "the judging is the same code at both points" (cited: ADR-0038 decision 4), and a run at the mock is answered by the same contract (cited: ADR-0038 decision 6).
- **A tool failure is not a result and gets no member here.** Its form is the `kind` and the `message` of ADR-0010 decision 4 (cited). A call that is answered with a tool failure — before ⑥ or after it was reached — returns no result. A repeated call that the lookup answers from an end line that holds a result does not reach ⑥ and returns that result (decision 7).
- Of a result this record fixes **six points and nothing else**: how it reports which of pass, fail and broken it is (decision 2); how a broken result names its condition (decision 3); the per-draw counts (decision 4); what of the things the check was made with it names (decision 5); what it never holds (decision 6); and whether its member list is closed (decision 7). Decision 8 says what is thereby not decided.
- The terms of ADR-0017 (draw, report, completed, broken, pass, fail), ADR-0021 (the cut, a check), ADR-0040 (the two `step` values, `point`) and ADR-0041 (the dimensions of a check, covered) are used unchanged. A *name* is that of ADR-0001.
- **Form rules for every member below.** A result is one JSON object "(strict JSON, no non-finite number)" (cited: ADR-0010 decision 2). No member holds `null`: a member that does not apply is left out — the manner of the envelope of a line ("No member holds `null`; an absent member is left out", ADR-0006 decision 3) and of the result of ADR-0039 decision 4 ("left out otherwise, never `null`"), cited for the manner only. A string value is compared as it is; nothing is normalised.

### 2. Which of pass, fail and broken: the member `outcome`

- A result reports "which of **pass, fail, broken** it reports — exactly one" (cited: ADR-0021 decision 5).
- **The member is `outcome`, a string with exactly three values: `"pass"`, `"fail"` and `"broken"`. It is present in every result.**
- What each value says is cited, not re-decided: `"pass"` and `"fail"` are the verdict of a completed run — "**pass** iff the predicate of decision 5 holds for every element of every draw; otherwise **fail**" — and `"broken"` is a run that was not completed, which "is neither pass nor fail" (cited: ADR-0017 decision 7). "only a pass counts (FR-9)" (cited: ADR-0021 decision 5).
- **Three forms were weighed.**
  - **(a) One member with three values.** A reader cannot learn the outcome without meeting all three values, and no combination of members is possible that says two things.
  - **(b) Two members in the manner of `Judgement`** — a `verdict` and a `broken`, one of them absent (an observation of the code, which binds nothing here). The two fields serve Python code that tests for `None`. In a JSON object in which an absent member is left out, a broken result would lack `verdict`, and a reader that asks only whether `verdict` is `"fail"` would take a broken result for one that did not fail. The pair also has states (both present, both absent) that mean nothing and would need a rule.
  - **(c) A boolean** (for example `passed`). It does not tell a fail from a broken run, which ADR-0021 decision 5 requires of a result (cited), unless a second member is read — the form (b) again.
- **The choice is (a).** The name is not `verdict`: in ADR-0017 decision 7 a verdict is what a completed run has, so a member of that name with the value `"broken"` would give the word a third value. ADR-0021 decision 5 speaks of the "outcomes" that are results; the three values are the words of ADR-0017.

### 3. The condition of a broken result: the member `condition`

- For broken, a result lets a caller tell "**which one of the four conditions**: the first that fails in the order in which ADR-0017 decision 7 lists the conditions of a completed run — the time limit, the exit status, the form of the report, a check value" (cited: ADR-0021 decision 5; the order is that decision's own and is not re-decided).
- **The member is `condition`, a string with exactly four values, in that order:**

| Value | The condition that failed first | Found by (cited: ADR-0021 decision 5) |
|---|---|---|
| `"time_limit"` | The process did not end within its time limit; "a process that was ended for its time limit is reported as the time limit" (cited: ADR-0021 decision 2) | the operation |
| `"exit_status"` | "a non-zero status or a signal (told apart no further than ADR-0017 decision 7 does)" (cited: ADR-0021 decision 2) | the operation |
| `"report_form"` | The captured report is not "exactly of that form for the parameters given": "a short, long or malformed report" (cited: ADR-0017 decision 7) | the tool function |
| `"check_value"` | "a check value that disagrees" (cited: ADR-0017 decision 7) | the tool function |

- **It is present exactly when `outcome` is `"broken"`, and left out otherwise.** A value such as `"none"` or a `null` in a result that reports pass or fail was weighed and not taken: it would be a fifth value that names no condition, and by decision 1 no member holds `null`.
- Each value is a *name* (ADR-0001). The spellings follow the words of ADR-0021 decision 5; the enumeration `Broken` of the harness spells the first one `TIMEOUT` (observation — neither spelling binds the other).
- The member holds the condition and nothing of the run: not the exit status, not the signal, not a time (decision 6). It does not say whose defect it was: "A defect of the harness against a defect of the kernel: not told apart by either class; the condition is reported so that whoever acts on it can look" (cited: ADR-0021 decision 5).

### 4. The per-draw counts: the member `counts`

- "**The Python side returns**, for a completed run, the verdict and per draw the number of elements that failed the predicate and how many of those were non-finite" (cited: ADR-0017 decision 7).
- **A result holds these counts. The member is `counts`: an array with one entry for each draw of the check, in the order of the draws; each entry is an object with exactly the two members `failed` and `non_finite`, each a JSON integer of at least 0.** `failed` is the number of elements of the output of that draw that failed the predicate; `non_finite` is how many of those were non-finite.
- **It is present exactly when `outcome` is `"pass"` or `"fail"`. A broken result has no `counts`**, also for the draws its report did hold: "A run has no partial verdict", and a broken run is neither pass nor fail "also when the draws it did report contain an element outside the tolerance" (cited: ADR-0017 decision 7).
- What follows from the cited definitions and is no further rule: in every entry `non_finite` ≤ `failed` ≤ m·n (a non-finite element fails — cited: ADR-0017 decision 5); in a result that reports pass every `failed` is 0; in one that reports fail at least one `failed` is 1 or more; and the array has as many entries as `draws` (decision 5) says.
- **Weighed.**
  - *For.* NFR-2 asks that "모든 결정·산출물을 추적 가능해야 한다". "the outputs of a check are in the process of the tool function" (cited: ADR-0021 Boundaries), the records of this contract so far give them no place after the call, and "A fail cannot be reproduced as long as the seed is not recorded" (cited: ADR-0021 decision 6). What a result does not hold of a fail is therefore not to be had again from anything these records define. The counts are what the harness already establishes, and they tell a kernel that is wrong in one element from one that is wrong in all, and an output that is not finite from one that is finite and off.
  - *What a count is.* A number the tool function computes by its own comparison. "The harness itself puts no element of `a`, `b` or the reference into what it returns" (cited: ADR-0017 decision 7), and the counts are part of what it returns for a completed run. A count is no element, no index and no deviation.
  - *What a count shows beyond that.* How many elements failed, not which and not by how much. The number of entries shows the `draws` of the check. And **a count is a number the kernel can set**: the kernel determines its output and "can read the seed" (cited: ADR-0017 decision 10), so a kernel can choose how many elements of a draw it gets wrong and thereby write a value it holds during the check — the seed included — into `counts`, as it can, more narrowly, into `outcome` and `condition`. This is not the tool function recording a seed (decision 6), and "Knowing the seed of a finished check tells nothing about the inputs of a later one" (cited: ADR-0021 decision 3); it is a path from the kernel's process into the log that this member widens (decision 9).
  - *Who reads a count.* "Whether more (indices, the largest deviation) is returned or ever shown to a coder is not decided" (cited: ADR-0017 decision 7), and what a correctness failure report of a spec may say is a Boundary of ADR-0002 (cited). **This record says what a result holds, not which role reads it or what is passed on from it.**
- **The choice — a result holds the counts — is provisional in one respect.** NFR-2 and the loss of everything else of a fail carry it; setting them against the path the kernel is given is this record's own judgement. It is looked at again when OD-16 sub-question ⑤ is answered (decision 6).
- **A result that reports pass holds `counts` too**, all zero: the presence of the member then depends on one thing only — whether the run was completed.
- **Indices and the largest deviation are not members**: the cited sentence of ADR-0017 decision 7 leaves them undecided, and this record does not decide them (Boundaries).

### 5. What the check was made with: `shape`, `draws` and `tolerance`, and not the point

Each of four things was weighed on its own.

- **The dimensions: in. The member is `shape`, an object with exactly the three members `m`, `k` and `n` — the dimensions of the check (cited for what they are: ADR-0041 decision 2), each an integer of at least 1. It is present in every result.**
  - Why: "Two checks of one attempt — a further `execution`, the check at the other point — can then be about two shapes", and "Neither line of a step names the shape …, so the log does not show it unless a result does" (both cited: ADR-0041 decision 9); "A stored pass says nothing about another shape" (cited, same decision), so whoever reads a stored pass must be able to see which shape it is about.
  - The form is that of the member `shape` of the stated record, with the same three names, so the two can be compared. The result does not hold the record or its key: a check uses the three shape members, while `op_signature.key`, the `label` and an `ext` "are not used for the dimensions" (cited: ADR-0041 decision 2), and the `kind`, `dtype` and `layout` are the same for every covered record (cited: ADR-0041 decision 5).
- **The tolerance: in. The member is `tolerance`, an object with exactly the two members `rtol` and `atol` — the two numbers the tool function read in ④ for this check (cited for the read: ADR-0021 decision 4) and with which it judges a completed run. It is present in every result.**
  - Each is a JSON number whose binary64 value is the one the comparison is evaluated with (cited for the value: ADR-0020 decision 4, "read as a binary64 value"; "finite and not negative"). The spelling of the literal is the code task's. The form is that of the member `tolerance` of ADR-0020 decision 2.
  - Why: "a file changed between two checks gives them two tolerances" (cited: ADR-0021 decision 6), and a stored pass says nothing "about a tolerance the file states later" (cited: ADR-0040 decision 8). The tolerance sets the gate FR-9 calls a hard floor; a stored outcome that does not show its gate cannot be told from one judged under a looser one.
  - A broken result has no verdict; the member then says with which tolerance a completed run would have been judged. It is kept there so that its presence depends on nothing.
  - "An operation is never handed the tolerance" (cited: ADR-0021 decision 2) is untouched: a result goes to the caller, not to an operation. Whether a tolerance is shown to a coder stays open (cited: ADR-0002 Boundaries).
- **The number of draws: in. The member is `draws`, an integer of at least 1: the number of draws this check used — the number the operation was handed and the form of the report was judged for (cited for both uses: ADR-0021 decision 2, class (ii) and the table). It is present in every result.**
  - **It says what this check used, and nothing else: no value, no source and no default of `draws` is fixed here.** Where the number comes from is the slice of `draws` (OD-16 sub-question ⑤; Boundaries).
  - Why: the number is "a trade of cost against assurance that no source fixes" (cited: ADR-0017 decision 3), so a pass over more draws is another assurance than a pass over fewer, and a reader must see which. In a completed result the number of entries of `counts` shows it already; a broken result has no `counts`, and its time limit "bounds the process over all its draws" (cited: ADR-0017 decision 9).
  - **Provisional in one respect**: the member is fixed before the slice that says where `draws` comes from. If that slice gives a check something other than one number of draws, or makes the number a member of the request — so that the result would state a second time what the request states — it revisits this member.
- **The execution point: out. A result repeats none of the six members a request requires** (cited for the six: ADR-0040 decision 5) — not `point`, and not `run_id`, `round`, `candidate`, `attempt` or `execution`. The caller stated them. In the log the envelope numbers and the `step` and `execution` of the end line that holds the result say `round`, `candidate`, `attempt` and `execution` and, through the `step`, the point (cited: ADR-0011 decision 3; ADR-0040 decision 3, the `step` follows from the point), and the run is said by the path of the log: "The run is not named in a line: the path names it" (cited: ADR-0006 decision 3). A member of the result would be a second statement of one thing. The result of ADR-0039 decision 4 repeats its `sha256`; that call writes no line. **This says nothing of a member a later slice gives a request**: "The member list of a request is not closed by this record" (cited: ADR-0040 decision 5), and whether a request carries anything for `draws` is a later slice's (cited: ADR-0041 decision 6).
- **Nothing else of what a check was made with is a member under this record**: not the hw_profile or the backend, not the source commit, not the kernel of the attempt, a flag or a time limit. This follows from decision 7 and decides nothing about them: where each comes from is another record's or a later slice's (Boundaries).

### 6. What a result never holds

- Cited and not re-decided: a result must never contain "an element of the inputs or of the reference. And, until the question of decision 3 is answered: the seed, the command line or the standard error of the kernel's process, none of which is free of them" (cited: ADR-0021 decision 5).
- **OD-16 sub-question ⑤ is not closed by this record.** The question stands as ADR-0021 decision 3 worded it: "*after a check has ended, may its seed — or what the kernel's process wrote besides the report, which can hold the seed and the inputs — be returned in the result, kept in a line of the log or written to a result file, and if so by whom and readable by which role?*" This record builds on "Until it is answered" (cited, same decision) and adds no member that holds either.
  - **An answer "the seed may be recorded in a result" reopens the first sentence of decision 7** — "A result has the members of the table below and no other": the record that renders the answer adds the member. With a seed in the result a fail can be reproduced, so the weighing of decision 4, which rests on the opposite, is looked at again as well, and the limit of decision 9 that says a fail cannot be reproduced from a result no longer holds as written.
  - An answer under which nothing from which an input follows may reach the log adds no member and reopens the weighing of decision 4, where the path through `counts` is named. That path also runs, more narrowly, through `outcome` and `condition` (decision 9), which ADR-0021 decision 5 requires of a result, so such an answer reaches that decision as well.
- **Of what the runner captured for a broken run, a result holds nothing but the condition** (this record's own, as far as it follows from decisions 2 to 5): not the exit status, not the signal, not the time that passed, and no byte of the report. For the two conditions an operation finds, it returns "which of two conditions failed — the time limit, or a non-zero status or a signal (told apart no further than ADR-0017 decision 7 does)" (cited: ADR-0021 decision 2).
- **This closes nothing in either direction.** "What is kept of a broken run and what follows it is OD-10 and OD-14" (cited: ADR-0017 decision 7). The sentence above says what a result holds under this record; a later record may add a member for something of a broken run, or keep it elsewhere, or keep nothing.

### 7. The member list

- **A result has the members of the table below and no other.**

| Member | Type and values | Present | Source |
|---|---|---|---|
| `outcome` | string: `"pass"`, `"fail"` or `"broken"` | always | decision 2 (that it reports exactly one of the three: ADR-0021 decision 5) |
| `condition` | string: `"time_limit"`, `"exit_status"`, `"report_form"` or `"check_value"` | exactly when `outcome` is `"broken"` | decision 3 (the four conditions and their order: ADR-0021 decision 5) |
| `shape` | object with exactly `m`, `k`, `n`, each an integer ≥ 1 | always | decision 5 (what the dimensions are: ADR-0041 decision 2) |
| `draws` | integer ≥ 1 | always | decision 5 (no value and no source: Boundaries) |
| `tolerance` | object with exactly `rtol`, `atol`, each a JSON number, finite and not negative | always | decision 5 (the form: ADR-0020 decisions 2 and 4) |
| `counts` | array of `draws` objects, each with exactly `failed` and `non_finite`, each an integer ≥ 0 | exactly when `outcome` is `"pass"` or `"fail"` | decision 4 (what is counted: ADR-0017 decision 7) |

- **In which sense the list is closed.** A tool function that follows the records up to this one returns exactly these members. **Only a record adds a member**, and a record that does so amends this table. Questions that are registered as open and whose answer could do so: the seed and the standard error (OD-16 sub-question ⑤, decision 6), something more of a broken run (OD-10, OD-14), indices and the largest deviation (ADR-0017 decision 7). None of the remaining items of the list under Consequences names a member of a result, which keeps none of those slices from adding one in this way.
- **Why closed, where the list of a request stayed open** (cited: ADR-0040 decision 5; ADR-0041 decision 6). ADR-0021 decision 5 bound what a result "must never contain" while the list was open; with a closed list that rule can be checked member by member, for the six of today and for each member a later record adds, instead of resting on whatever a tool function comes to return. The default script of the mock and the conformance tests of P1-1 will be written against the form of a result. And a request is written by a caller, a result by the one tool function. With a closed list there is no text member — no `message`, `detail` or `note` — into which a tool function could put what decision 6 keeps out. What a kernel can put into `outcome`, `condition` and `counts` by what it does remains (decisions 4 and 9).
- **What a caller may rely on.** Of a result made under this record: the table, the presence rules and the relations of decision 4. **Not** that every result it is given was made under this record's table: a repeated call "returns what the end line holds" (cited: ADR-0011 decision 3), so a result that one source commit stored is returned, member for member, by a later one.
- **A result carries no version member.** "The convention carries **no version member**", and "in P1 that commit is the pin" (cited: ADR-0010 decision 7). The version of a line is "**not** raised by a new value of `kind`, nor by a change in the `data` of a kind; how such a change is told apart is left open" (cited: ADR-0006 decision 8), which ADR-0011 decision 3 repeats for its two kinds (cited: "how a later change in the `data` of these two is told apart, stays open (OD-8 sub-question ⑧)"). A version member in the result of one tool would answer that open question for one tool; it is not taken. **What follows**: a log can come to hold results of two member lists if the list is changed while a run lives. How a reader treats a result of another list is the open question just cited (OD-8 sub-question ⑧) and is not decided here; neither is whether a run may pass from one source commit to another at all: "whether a tool checks its own commit against the one a run recorded is OD-11" (cited: ADR-0010 decision 7).
- **Three examples.** Synthetic values. The shape is that of the walk-through of ADR-0041; the two tolerance numbers are the example values of ADR-0020, which "are not default, recommended or typical values". **`2` stands in for the number of draws only so that the array shows more than one entry: it is no proposed, default or typical number of draws.**


### 8. What is not decided by this

- **What anybody does after a fail or a broken result**: "What anybody does after a fail or a broken run is not decided" (cited: ADR-0021 decision 5, which names FR-1, OD-10, OD-14 and OD-19 for it). This record adds no rule on repair, elimination, retry or a further `execution`.
- **The result file of an attempt.** A result of this tool is not that file, and no member of `eval.json` or of another result file is named. "Who writes the result file of an attempt from an end line on resume stays open" (cited: ADR-0011 decision 4; PLAN P1-8, OD-23), and "Which results count as expensive beyond the board measurement, the members of a result, who writes a result file from a line on resume, and what is done when a line and a file differ, are not decided here" (cited: ADR-0006 decision 7) — of that sentence this record answers the members of the result of this one tool and nothing else. If the record of a result file needs of a check something a result does not hold, it revisits this one.
- **The `spend` of the end line** stays as ADR-0040 decision 6 left it; nothing of a spend is a member of a result.
- **How the operation reports to the tool function.** The four values of `condition` are values of a member of a result. They are not the spelling of what an operation returns: "The spelling of what is handed and returned is the second record's and the code task's" (cited: ADR-0021 decision 2), and that slice is the backends'.
- **Which role calls the tool, reads a result or is shown anything from it** (OD-23; OD-6).

### 9. Limits

- **A result is what the tool function returned at one source commit**, and a repeated call returns it unchanged (cited: ADR-0011 decision 3). Nothing in a result names that commit (decision 7).
- **A pass says nothing beyond the drawn range and shape**: "only for the drawn range and shape" (cited: ADR-0021 decision 6; ADR-0017 decision 10). `shape`, `draws` and `tolerance` say for which dimensions, over how many draws and under which gate; they do not say on which inputs.
- **A broken result does not tell a defect of the harness from one of the kernel** (cited: ADR-0021 decision 5).
- **A fail cannot be reproduced from a result**, which holds no seed (cited: ADR-0021 decision 6; decision 3).
- **A kernel can set what a result reports about it.** Which outcome, which condition and — with the widest range — which counts a result reports can each be brought about by what the kernel's process does, and that process holds the seed (cited: ADR-0017 decision 10). A result is therefore a path by which a kernel can put a value it holds into the log. Nothing here closes it; it is weighed in decision 4 and belongs to OD-16.
- **A result does not show which backend answered**: "a mock outcome is told apart by its hw_profile only" (cited: ADR-0038 decision 8), and the hw_profile is in the file of the run, not in the result.
- **`shape` shows three numbers, not the stated record.** An `ext` "is not looked at" (cited: ADR-0041 decision 5) and is not shown.
- **Nothing checks a stored result against this table.** The lookup returns what the end line holds; whoever can append a line to the log can store a result of any content (cited for the absence of access control: ADR-0021 decision 6).
- The limits of ADR-0021 decision 6, ADR-0038 decision 8, ADR-0040 decision 8 and ADR-0041 decision 9 stand unchanged.

## Consequences

- **What the next slices of the second record must still add** — the list of ADR-0041 Consequences, without the item that record struck off itself (the dimensions): every other member of the request, the input schema and the description; where `draws` comes from; where the kernel of the attempt, the flags and the time limits come from; ~~the members of the result~~ (this record) and the tool-failure kinds a backend may raise; the spend beyond ADR-0040 decision 6; the operation and the default script of the mock; and whether an operation is handed the point. Of OD-18 sub-question ⑩ the first three clauses, the kernel language and another accelerator.
- **Code** (observations; **this record binds no code**). The fields of `Judgement` and the tuple `Counts` hold what `outcome`, `counts` and the last two values of `condition` are made from, and the first two values of `condition` come from what an operation returns (ADR-0021 decision 2); `shape` and `tolerance` are what `hilclaw.instance.read` gives in ④. A default script of the mock that is to pass must lead to a result of the first example's form. **Not yet possible**: the tool function of `correctness.check` (after HQ-0012 and the later slices) and its registration.
- **Not edited and now less exact** (follow-ups for the integrator): ADR-0021 decision 1 (the item "the members of the result" of its list), its decision 5 ("Whether it holds more … and every name and type are the second record's") and its Boundaries ("every member, name and type of a result"); ADR-0040 decision 2 ("whatever a later slice makes a member of a result"), its Walk-through ("No member of a result is shown") and its Boundaries ("every member, name and type of a result"); ADR-0041 decision 2 (a) ("whether a result does is not decided"), its decision 7 (last bullet), its decision 9 (first bullet), its Walk-through ("No member of a result … is shown") and its Boundaries ("every member, name and type of a result, the dimensions among them"); ADR-0040 Consequences, ADR-0041 Consequences and ADR-0038 decision 7 (the item "the members of the result" of their lists), and in ADR-0041 Consequences also "Whether a result names the dimensions decides whether the log shows the shape of a check" (it names them); ADR-0020 Boundaries ("request and result members" of the contract of `correctness.check`); ADR-0011 Boundaries ("the request and result members of any tool") and its Example ("no result member" — it still proposes none); ADR-0006 decision 7 ("the members of a result … are not decided here"). Other records name the result members of a tool among what they do not decide; those sentences stay true of themselves. In `hilclaw/harness/verification.py` no docstring sentence becomes false. No sentence of UsageCases became false.
- **A-13 reading**: document mode; no code, dependency, settings file or schema file changes. A result of this tool is stored in one place: as the member `result` of the `data` of a `step_ended` line of `runs/<run_id>/events.ndjson`, and it is returned by the call and again by a repeated call that the lookup answers from that line. ADR-0011 decision 3 fixed that member — "`result` is the result object of the call itself" — and its Boundaries left "the request and result members of any tool" undecided, naming PLAN P1-1; this record fills that place for one tool. **No member of `STATE.json`, `instance.json`, a spec, `artifacts.json` or a result file of an attempt, and no member of the envelope or of the `data` of a line of `events.ndjson`, is added, removed or changed** in type, form or meaning: the `data` of a `step_ended` line holds `step`, `execution`, `spend` and exactly one of `result` and `failure`, as before. The version of a line "is **not** raised by a new value of `kind`, nor by a change in the `data` of a kind" (ADR-0006 decision 8), and here the `data` of the kind does not change. The result file of an attempt (`eval.json`, PLAN P1-8) is another file and is not defined here. **This is therefore read as no "데이터 plane 스키마 변경"**: the members inside `result` are the interface between layer 1 and layer 2 — what a tool function returns (ADR-0010 decision 2) — and no schema of a data-plane file existed for them or is changed by them. Unlike the result of ADR-0039, which is written nowhere, this one is stored in the log; the reading rests on the place ADR-0011 made for it, not on that it is not stored.
