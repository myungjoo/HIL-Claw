## Context

- **The loop** (cited: ADR-0118 decision 3): one function of `hilclaw/` repeats five steps on one run — step 1 "reads the run's files to tell whether a further turn is to run, and returns if not", then it prepares the session directory, starts one turn session, waits until it has ended and goes back to step 1. It "makes no judgement and calls no model itself", "never has two turn sessions of one run running at once", and is no FR-10 tool. "What it does after a turn session failed … is not decided: retry at once, wait, stop, notify, or a pause on a usage limit (an OD-19 proposal drawn from C-7 ②) (OD-10, rest of OD-17, OD-19, OD-27)". What starts the loop: a person or a CI, through a command-line entry; a loop that died "is started again by whatever started it: by hand (UC-2, UC-4) or by an OS schedule". Two loops on one run are the lock's matter (rest of OD-17).
- **How a turn ends** (cited: ADR-0118 decision 2): (i) with its round, after the write that ends it; (ii) before its round ends — the process dies or is stopped, the run waits for the user, or the session ends without that write "for any other reason, such as an error or a usage limit". In every case of (ii), `round` still names the round and the next turn goes on with it.
- **Step 1 today** (cited: ADR-0121 decision 5): for a run of this scope it answers P1 (fresh run directory — a further turn), P2 (`run_status` `"over"` — no further turn), P3 (any other `run_status` value — no further turn, and the value is reported) and P4 (valid `STATE.json` without `run_status` beside a valid `instance.json` with `round_budget` — a further turn, "whatever `round` is"). Open, and left to the caller's predicate: a run whose `instance.json` states no `round_budget` (㉙ (나)); a `STATE.json` or `instance.json` missing beyond P1, invalid or of another version; and what follows a failed turn — "P1 and P4 say a turn is due, not how often a failing one is retried". The loop "writes nothing into the run" (cited: ADR-0120 decision 2) and, by ADR-0121, compares no numbers.
- **The round pointer** (cited: ADR-0012): `round` names "the round that has not ended and that the next turn runs or goes on with"; it "changes only in the write that ends a round" (decision 3); "A write that does not end a round carries `round` … over unchanged" (decision 6). An invalid `STATE.json` is an error: "the reader reports it, uses no member of the file and repairs nothing. A turn has no other entry point, so it does not go on" (decision 6).
- **The exit status** (cited: ADR-0118 Context R7): "Claude Code exits with code 0 on success and a non-zero code when the run fails." Whether the exit status of a turn session tells a session that ended well from a failed one is runtime acceptance item (vi) of ADR-0118; that a `-p` turn session exits after the Round-Manager's last reply is item (v). Neither has been tried.
- **The spend** (cited: ADR-0011 decision 9): "The accounting stops nothing: reaching or passing a budget has no effect by this record (OD-19)." ADR-0032 decision 4: a valid `instance.json` may lack `round_budget`, and "not stated" is never "unlimited"; ADR-0076 decision 1 does not require it of a start.
- **Code, as observation only**: `hilclaw.turn_loop.run` calls `further_turn(None)` before the first turn and `further_turn(status)` with the exit status of the last turn session after each, and returns when it answers `False`; it starts `claude -p` with a fixed prompt and returns one record per turn. `hilclaw.further_turn.predicate` answers P1 to P4 and, for P1 and P4 after an exit status other than 0 and for every state it calls open, returns its caller's `fallback(previous)`; it keeps nothing between calls. **No command-line entry exists.** `orchestration/round-manager.md`, the placeholder definition, has every turn "end the session without writing any file". An entry whose `fallback` answered `True` would start turns without end on such a run, each a `claude -p` session that spends plan usage (NFR-5; C-7 ②; T-0336).

## Decision

A sentence is **cited** when a source is named with it. Every other sentence is **this record's own**.

### 1. Scope and terms

- **The runs of ADR-0120 decision 1** (new first-case runs of ADR-0076 decision 1 whose `instance.json` the start function of ADR-0115 writes), driven by the turn loop of ADR-0118 decision 3 through its command-line entry. Resumed, continued or branched runs (OD-8 ①) and every other run are outside; nothing here is required or allowed of them.
- **Kept, not changed** (cited): the loop makes no judgement and calls no model (ADR-0118 decision 3); **it writes nothing into the run** — no `run_status`, no other member, no file (ADR-0120 decision 2; ADR-0121 decision 3) — and is no second writer of `STATE.json` (ADR-0004; ADR-0012 decision 6); it is no FR-10 tool; two turn sessions of one run never run at once (ADR-0118 decision 3).
- **A start** is one call of the loop: from its first step 1 until it returns. **The starter** is whatever made that call — a person or a CI through the entry, or an OS schedule that starts the loop again (cited: ADR-0118 decision 3).
- **The state before a turn** is what step 1 read before that turn. **The state after it** is what step 1 reads next.

### 2. (a) After a turn whose exit status is not 0

- **The loop starts no further turn on its own. It returns, and its starter is told that the start stopped after a turn whose exit status was not 0, with that status** (decision 5). This holds in P1 and P4 and in every state ADR-0121 decision 5 leaves open. In P2 and P3 the loop returns as ADR-0121 decision 5 says, whatever the exit status.
- **No retry at once, no count of retries and no pause inside the loop.** Whether and when the run is driven again is the starter's: a person starts the loop again, or a schedule does at its next firing (cited: ADR-0118 decision 3, "What starts the loop"); a schedule that may fire while a loop still runs on the run needs the lock, which is open (cited: ADR-0118 decision 3, "Two loops on one run"; rest of OD-17). The next start goes on at the exact point the files say (NFR-1; cited: ADR-0012 decision 3, ADR-0118 decision 2 (ii), #4 §3b).
- **Why.** The loop cannot tell why a turn session failed: the exit status says at most that it failed (R7; item (vi)), and the loop makes no judgement and reads nothing else of the session (ADR-0118 decision 3; `hilclaw.turn_loop` does not read its streams). The causes ADR-0118 decision 2 (ii) names — a crash, a stop, an error, a usage limit — include ones that a turn started at once meets again (a usage limit, an expired login, a broken definition). A retry at once then spends a session for nothing; a count or a pause would set a value of plan usage that no source gives (O3, O4; NFR-5). Returning spends nothing further and loses nothing: no file is written, and the run goes on from its files at the next start.
- **The cost.** An unattended run (UC-3, S2 step 3) stands still from a failed turn until its starter starts the loop again. **Until the lock exists, a starter that cannot rule out a loop still running on the run cannot restart it on a schedule, so a person restarts an unattended first-case run after each failed turn.** A failure that a turn started at once would have passed (a passing fault) costs that wait.
- **"무정지" (FR-4, UC-3), read.** FR-4: "autonomous도 budget/종료 조건까지 무정지 실행, checkpoint는 gate에서 정지·승인 대기"; UC-3 step 1: "budget 소진/종료 조건까지 무정지로 라운드를 반복한다(첫 사례: … 루프 자신이 죽으면 cron 등의 재기동이나 사용자가 루프를 다시 시작한다 …)" (cited). **This record reads** FR-4's "무정지" as set against checkpoint mode — no stop at a gate for the user's approval — and not as a rule on what follows a failed process: UC-3 step 1 itself has a loop that ends before the budget (it dies) and goes on when cron or the user starts it again, and S2 step 3 relies on that restart. A start that returns after a failed or unchanged turn ends like a loop that died, and goes on in the same way; no gate and no approval is added. ADR-0118 Alternatives set aside "The user by hand for every turn" as "Not the '무정지' of UC-3"; here the user or a schedule starts the loop again only after a turn that failed or ended no round, not for every turn. **The cost against UC-3 is real** and stated above; an answer that keeps an unattended run going without a starter — a retry or a pause inside the loop — would set a value of plan usage that no source gives (Alternatives), and is left to a later record (Boundaries).

### 3. (b) After a turn whose exit status is 0 that left the run as it found it

- **"As it found it"** is defined on the reads step 1 already makes, of `runs/<run_id>/` at known paths (no listing — #4 §1; no new file):
  - the state before the turn was **P1** and the state after it is **P1** again (cited test: ADR-0120 decision 4 — still `instance.json` and no other file of the tree); or
  - the state before the turn was **P4** and the state after it is **P4** with **the same `round`**.
  By ADR-0012 decisions 3 and 6, the same `round` means that the turn ended no round (cited). The loop reads `round` from the `STATE.json` it already reads in P4 and compares the value after the turn with the value before for equality only. It does not compare `round` with `round_budget`; that comparison stays the Round-Manager's (cited: ADR-0121 decisions 4 and 5).
- **After such a turn the loop starts no further turn on its own. It returns, and its starter is told that the start stopped after a turn that exited with 0 and left the run as it found it** (decision 5). The next start goes on with the same round (cited: ADR-0118 decision 2 (ii)).
- **Every other change is progress for this decision**: P1 before and P4 after (the round-0 turn wrote the first file — ADR-0120 decision 2); P4 before and P4 after with another `round` (a round ended); a state after the turn that is P2, P3 or open is answered by decisions 4 and 5 and ADR-0121 decision 5. After a turn with progress and exit status 0, step 1 answers as ADR-0121 decision 5 does.
- **A narrowing of ADR-0121 decision 5, for this scope.** There, P1 and P4 answer "A further turn" (P4 "whatever `round` is"). By this record, after a turn that exited with 0 and left the run as it found it, P1 and P4 answer no further turn in that start. Before the first turn of a start, and after a turn with progress, they still answer a further turn. ADR-0121 is not edited (Consequences).
- **Why `round` and not the whole file.** A turn that writes inside its round and never ends it (a `phase` marker, #4 §3b) changes the file at every turn; with the whole file as the test, such a definition would start turns without end. With `round`, a start runs at most two turns that end no round: the round-0 turn that writes the first file and one more. The cost: a round that a definition deliberately spreads over several turns of one start ends that start after its first turn that ends no round, and goes on at the next start. ADR-0118 decision 2 (ii) knows a round that takes more than one turn only as a turn cut short, which this keeps.
- **Not the no-progress breaker of OD-19.** That proposal ("N라운드 연속 미개선 시 중단", § OD-19) is about rounds that end and do not improve the result. This decision is about turns that end no round. It does not answer the breaker, and it reads no result.

### 4. (c) In the states ADR-0121 decision 5 leaves open

- **The states**: a `STATE.json` missing beyond P1, invalid or of a version other than 1; an `instance.json` missing, invalid or of another version beside a valid version-1 `STATE.json` without `run_status`; a run whose valid `instance.json` states no `round_budget`.
- **Before the first turn of a start, and after a turn that exited with 0, the loop starts no turn in these states. It returns, and its starter is told that the run is in a state no record answers, and which of these it is** (decision 5). After a turn whose exit status is not 0 it starts none either (decision 2), and the starter is told the open state with that status (decision 5). The entry built on this record treats every run id it is given this way, since step 1 cannot tell from these states whether the run is of this scope; starting no turn requires nothing of any run.
- **Why not a turn anyway.**
  - An invalid `STATE.json` is an error after which "A turn has no other entry point, so it does not go on" (cited: ADR-0012 decision 6); one of another version is not interpreted (cited: same decision).
  - A directory with `instance.json`, other files of the tree and no `STATE.json`, or with other files and no `instance.json`, "is not produced by the order of decisions 2 and 3", and "what a Round-Manager does when it finds one" stays open (cited: ADR-0120 decision 4). No definition can be written against it yet.
  - Beside a valid `STATE.json`, an `instance.json` that is missing, invalid or of another version gives no `round_budget` that a Round-Manager can read (an invalid file is used for no member — cited: ADR-0032 decision 4), so the rule that ends a run of this scope (ADR-0121 decisions 3 and 4) cannot apply; this is this record's reading.
  - A valid `instance.json` with no `round_budget`: "not stated" is never "unlimited" (cited: ADR-0032 decision 4), and ADR-0121 ends a run on its round budget only.
  In each case a turn would either spend a session to find what step 1 already read, or run with no rule that ends the run in this scope.
- **This is no answer to OD-8 sub-question ㉙ (나).** It does not say that such a run is over, may not start or is invalid; it writes no `run_status`; it does not say what ends such a run. It says only that this loop does not drive it until a record answers ㉙ (나). A start function may still write such an `instance.json` (cited: ADR-0076 decision 1 does not require `round_budget`).

### 5. (d) What the starter is told

- **Outcomes of a start, told apart from each other**, in kind:
  1. **run over** — step 1 found P2 (cited: ADR-0121 decision 5);
  2. **unknown `run_status`** — step 1 found P3, with the value (cited: ADR-0121 decisions 2 and 5);
  3. **stopped after a failed turn** — decision 2, with the exit status;
  4. **stopped after an unchanged turn** — decision 3;
  5. **open state** — decision 4, naming which state.
  An **error** of the loop or the entry — a bad argument, a refused place, no `claude` found, or what `hilclaw.turn_loop.run` otherwise raises — is told apart from all five.
- **When two apply**, the order is: P2, then P3, then an open state, then decision 2, then decision 3. So a turn that failed after it wrote `"over"` ends its start as "run over", and a failed turn after which the files are in an open state ends it as "open state", told with the exit status.
- **How**: through the process only — the entry's exit status and its standard streams. "Run over" is the only outcome that says the run needs no further start; whether others share an exit status, and the concrete codes, texts and option names, are the code task's.
- **No notification channel is chosen** (FR-16; OD-27). Nothing is written into the run or anywhere else on the starter's behalf; a starter that wants to notify someone does so from what it is told.

### 6. The usage-limit pause and the exit status

- **The pause is left open** (OD-19). The proposal O3 has reaching the plan's usage limit be "a pause-and-resume condition, not a failure"; § OD-19 proposes "일시정지 → 한도 회복 후 재개".
- **The loop cannot tell a usage-limit end from another failure today, and this record does not presume that it can.** R7 says only that a failed run exits with a non-zero code. Whether a turn session that reaches the limit ends with 0 or not, and whether anything the loop could read tells it apart, has not been shown (ADR-0118 item (vi); Consequences).
- **How the answers here stand to the proposal.** A turn that ends on the limit ends its start under decision 2 (exit status not 0) or decision 3 (exit status 0 and no round ended). If it ended a round first, the next turn starts, meets the limit again and ends the start then. In every case nothing is written: the run is not marked over or failed, and the next start goes on at the exact point (NFR-1). So nothing here makes a usage limit a failure of the run. What the proposal adds — waiting until the limit recovers and then going on by itself — is not done by the loop. A schedule that starts it again gives a resume, at an interval the operator picks, not tied to the limit.

### Walk-through

| Situation | What follows |
|---|---|
| A fresh first-case run; the placeholder `orchestration/round-manager.md`; a person starts the entry | P1 before the first turn: one turn. It writes nothing and exits with 0; P1 again: stopped after an unchanged turn (decision 3). One session spent per start |
| The round-0 turn writes the first file, ends round 0 and exits with 0 | P1 → P4 with `round` 1: progress; P4: a further turn (ADR-0121 decision 5) |
| A turn in round 3 dies (exit status not 0) after `board_done` | Stopped after a failed turn, with the status (decision 2). At the next start the turn goes on with round 3 and skips the finished substeps (cited: ADR-0012 decision 3; #4 §3b) |
| A turn exits with 0 in round 3 without the write that ends it | P4 with `round` 3 before and after: stopped after an unchanged turn (decision 3) |
| The turn of round 4 (`round_budget` 5) ends the run: `round` 5, `run_status` `"over"` | P2: run over (ADR-0121 decision 5) |
| A turn meets the plan's usage limit | The start ends under decision 2 or 3, whichever its exit status gives — at once, or after one more turn if this one ended a round first; nothing written; a later start goes on (decision 6) |
| The entry is given a run whose `instance.json` states no `round_budget` | No turn: open state, "no `round_budget`" (decision 4) |
| The entry is given a run whose `STATE.json` is invalid | No turn: open state, "`STATE.json` invalid" (decision 4; ADR-0012 decision 6) |
| Once the lock of two loops exists (rest of OD-17), a schedule starts the entry hourly on a run whose turns keep failing | One failed turn per firing, each told to the starter; nothing written (decision 2). The interval is the operator's |

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| a | Retry at once, a fixed number of times | A cause that a fresh turn meets again (usage limit, expired login, broken definition) spends that many sessions for nothing (NFR-5; C-7 ②), and the number is a value of plan usage that no source gives (O3, O4). It would save a restart only for a passing fault. |
| a | Retry after a pause (fixed or growing) | The loop would then hold a process alive and waiting, and the pause length is again a value no source gives. Without a way to tell a usage limit from another failure (decision 6), a pause tuned to the limit would also delay every other failure. A schedule that starts the loop again already gives a pause, chosen by the operator. |
| a | Keep starting turns (today's P1 and P4, with a `fallback` that answers `True`) | Unbounded: a failing turn is followed by another without end, each spending plan usage, unattended (UC-3; S2 step 3) — the hole T-0336 found. |
| a | Stop and return to the starter (adopted) | Its cost: an unattended run stands still until its starter starts the loop again, and a person must restart it when no schedule does (decision 2). |
| b | Keep starting turns after an exit-0 turn that changed nothing (ADR-0121 decision 5 as it stands) | With the placeholder definition, or any definition that ends turns without a write, turns without end (T-0336). |
| b | A bound on the number of turns per start instead of a check on the run's files | It needs a number no source gives (O4 caps rounds, not turns), it stops a run that is making progress when the bound is reached, and with a large bound it still spends that many sessions on a run that changes nothing. |
| b | "As it found it" = the whole `STATE.json` the same | A definition that writes inside its round at every turn and never ends it would run without end (decision 3). |
| b | Stop after any turn that ends no round, with progress counted only as a round ended | The round-0 turn that writes the first file and then ends early would end the start although the run moved from P1; the first-file write of ADR-0120 decision 2 is progress. |
| b | Read a listing of the run tree or the log to see change | A listing is what #4 §1 forbids; the log is not read by step 1 today, and a fold for a fact `round` already gives is extra cost (as ADR-0121 Alternatives (c) weighed). |
| c | Start a turn anyway and let the Round-Manager decide | An invalid `STATE.json` stops the turn (ADR-0012 decision 6), and for a missing one beyond P1 the Round-Manager has no rule to go on by (ADR-0120 decisions 3 and 4), so a session is spent to find what step 1 read; with no `round_budget`, no rule ends the run in this scope, so turns are unbounded. |
| c | Answer ㉙ (나) here (refuse the start, or a default budget) | A default would read "not stated" as a value, against ADR-0032 decision 4; refusing the start is the start function's and ADR-0076's. Neither is needed to keep the loop bounded. |
| d | Write the outcome into the run (a `run_status` "stopped" or "failed") | A second writer of `STATE.json` (ADR-0004; W1 of ADR-0120) and a data-plane change; "stopped" would also say more than the loop knows (ADR-0121 decision 2 leaves the value open). |
| d | Choose a notification channel (a file, a message) | FR-16's channel is OD-27's, and OD-27 has no proposal yet. |
| d | Tell only "stopped" and "over" | The starter could not tell a run that needs a person (an open state, an unknown value) from one that a later start may carry on (a failed or unchanged turn); unattended starters would restart runs that no start can move. |

## Consequences

- **The code slice it enables** (code mode, a later task; names, modules and options are its own): the loop's command-line entry, which composes `hilclaw.turn_loop.run`, `hilclaw.turn_definition.put`, `hilclaw.further_turn.predicate` with a `fallback` that answers `False` in every case and records the outcome of decisions 2 and 4, a check of decision 3 kept between two step-1 calls, and `hilclaw.config` for the data root; it tells the outcomes of decision 5 by exit status and standard streams. Tested against a stub `claude` only (D16). **What it still waits on**: the lock of two loops on one run (rest of OD-17), before any starter may start the entry on a run where a loop may still be running — a schedule is one (ADR-0118 decision 3); until then the slice states that limit. ⑪ (the commit) and the round-0 part of the Round-Manager prompt (PLAN P2-1) are the definition's, not the entry's.
- **Less exact, not edited** (found by a search of `ARCHITECTURE/decisions/` for "failed turn", "what follows", "retry" and "caller's predicate"; follow-ups for the integrator). For the runs of decision 1, these say the point is open, and it is now answered:
  - ADR-0118 decision 3 ("What it does after a turn session failed … is not decided"; "Until a record answers it, the code slice takes from its caller a predicate"), Consequences (1), the second Walk-through row ("What it does next is open") and Boundaries ("what the loop does after a failed turn").
  - ADR-0120 decision 4 ("what the loop does after a turn session that failed and left the directory fresh stays the open point"), Consequences (3) ("a run whose directory is fresh gets a further turn … and what follows a failed turn on ADR-0118 decision 3") and Boundaries ("what the loop does after a failed turn that left the directory fresh"); its Walk-through row "A loop is started with an id whose directory has no `instance.json`": in this scope the loop starts no turn there (decision 4).
  - ADR-0121 decision 5: P1 and P4 ("A further turn", "whatever `round` is") are narrowed by decision 3; "it also compares no numbers" now has the equality of `round` of decision 3 beside it; the "Open" bullet ("what follows a failed turn", the open states, "ask its caller's predicate"); Consequences ("It still waits on … what follows a failed turn"); Boundaries ("What follows a failed turn").
  - In code: the docstrings of `hilclaw/turn_loop.py` ("no command-line entry, which waits on the OD-8 member …") and `hilclaw/further_turn.py` ("**Open** … what follows a failed turn …; and the loop's command-line entry"). The code task may correct them.
  - The list is not claimed to be complete.
- **UsageCases and StandardScenarios**: no sentence becomes false, under the reading of FR-4 and UC-3 in decision 2. UC-3 step 1 says what follows when the loop dies; by this record the loop also returns after a failed or unchanged turn, and the restart it names applies then too. S2 step 3 ("cron 재기동이 마지막 commit 지점에서 이어간다") is what decision 2 relies on, with the lock it needs still open.
- **A-13 reading.** Document mode. No code, test, setting or dependency changes. **No data-plane change**: no member, file, kind, value or version is added or changed, and no validator changes.
- **Runtime acceptance items** (D16; nothing was tried, and nothing is required of the development machine):
  - ADR-0118 items (v) and (vi) are used, not changed. If (vi) fails, this record's rules stay bounded in both directions: a failed session that exits with 0 and ends no round ends its start under decision 3; a session that ended well and exits with another status ends its start under decision 2, so the run moves at most one turn per start until a person or a later record sees it.
  - **New**, numbered after ADR-0118's (i) to (vii): (viii) how a `-p` turn session that reaches the plan's usage limit ends — its exit status, and whether anything in its output tells it from another failure. This record does not rely on it; a record that defines the pause of decision 6 would.
- **The cost, plainly.** A start spends at most two sessions that end no round — the round-0 turn that writes the first file, and one more (decision 3) — and a run whose turns keep failing spends one session per start (decision 2). A run that waits for the user, ended by a gate or by a request to change the toolchain (O5; OD-8 ㉝ (가)), is told as outcome 4 and costs one session per start until a record defines a waiting value. How often a start happens is the starter's (a person, or a schedule's interval). The bound on rounds rests on the Round-Manager's write of `"over"` (ADR-0121 decisions 3 and 4), not on the loop.

## Boundaries (not decided here)

- **The lock** of two loops on one run and fencing (rest of OD-17; #4 §2e).
- **The recovery of an open step inside a turn** and the declarative per-tool retry (OD-17, OD-10; #7 §5 G4).
- **Board failure and recovery** (OD-10; #5 B-2): a failed turn session is not a board failure, and nothing here is about boards.
- **The rest of OD-19**: caps per round and per coder call (the repair bound included), the single ledger, a check on the path of the next spend, the no-progress breaker on results, **the usage-limit pause** (decision 6), and non-convergence with UC-7.
- **Notification channels** and the end-of-run notification (OD-27; FR-16).
- **The commit step** and the commit owed by a run that is over (OD-8 ⑪).
- **Gates and waiting**: gates and the gate layer (OD-3 — owner-only; #5 A-5), and how a run waits for the user (OD-8 ㉝ (가)); a value of `run_status` for "waiting" or "stopped" (ADR-0121 decision 2). Until a record defines one, a turn that a gate or a wait ends with exit status 0 and no round ended is told as outcome 4 (decision 3), not as waiting.
- **Adding a retry or a pause inside the loop.** This record puts none in it (decision 2). Adding one, so that an unattended run goes on without its starter, sets a value of plan usage and is a later record's (OD-19; #5 A-8 where tokens are concerned).
- **㉙ (나)**: what ends a run that states no round budget, and whether such a run may start (decision 4).
- **Resumed, continued or branched runs** (OD-8 ①) and every run outside ADR-0120 decision 1.
- **What a starter does with the outcomes**, its schedule and interval, and whether the loop also calls the start function of ADR-0115 (ADR-0118 decision 3).
- Any change to an earlier record, FR or NFR text, UsageCases, `hilclaw/`, `orchestration/`, tests, CI, `.claude/`, any settings file or the `HIL-Claw-data` repository; any new external dependency.
