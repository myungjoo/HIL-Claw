## Decision

A sentence marked **owner** renders the HQ-0004 answer and quotes it. A value is **cited** when another source is named with it. Every other value is **this record's own** choice.

### 1. Scope and terms

- This record is about the **verification run of one built attempt** of a C kernel of ADR-0008 at `cpu_standin`, kind `gemm`, dtype fp32. It is not the timing run (ADR-0009) and not a mechanism for a simulator, a board or a remote machine; it holds for no other kind, dtype or kernel language.
- **It is not an FR-10 tool contract.** ADR-0016 makes `correctness.check` a HW tool that goes through a backend and leaves "the split between the one harness (FR-9) and the backend" to that tool's contract (its decision 3). This record defines a run that such a contract can be built from, as ADR-0009 did for timing. It decides nothing of that split, of whether the `cpu_standin` backend offers `correctness.check` (OD-18 sub-question ⑦), of a request, a result member or a failure kind. Below, "the Python side" means code of the harness sub-module; which of its parts a backend's operation calls and which a tool function calls is not said.
- **Verification program**: the C source of the harness that defines `main`, prepares the operands, calls the kernel and writes its output to the report. **Verification executable**: that program and the source of one kernel built into one executable. **Verification run**: one process of a verification executable, together with the work of the Python side on its report. **Draw**: one set of input values for `a` and `b`, used for one kernel call. **Python side**: the code of the harness that starts the run, regenerates the inputs, computes the reference and compares.

### 2. Program and process

- The harness provides `main` (FR-9; ADR-0008 decision 7). The verification program is **a second C source file under `hilclaw/harness/`, separate from the timing driver**, and a verification executable is built from it and all source files of **one** kernel by **one call of `clang_build.build`** with the caller's flags, exactly as ADR-0009 decision 2 builds a timing executable. It needs nothing beyond the C library and POSIX (no `-lm`), and it must stay correct under the caller's flags. One kernel per executable, so `hilclaw_gemm` is defined once.
- **A verification run is a process of its own**, started through `local_run.run`, for the reasons of ADR-0009 decision 2 (a crash or a hang ends its own process and is bounded by the runner's time limit; the kernel's threads stay out of the interpreter).
- **Nothing of ADR-0009 is reopened.** The timing driver, the timing executable and the timing run stay as they are: its decisions 5 (operands), 6 (the untimed call) and 8 (the report) are untouched, because no timing run draws a verification input, writes an output or is compared. The exclusions of ADR-0007 decision 2 hold trivially: the verification program reads no clock and yields no sample, and reference and comparison are not even in a process that times anything.
- **The cost of keeping them apart is stated, not hidden**: an attempt is built twice (one executable per program), and the executable that is verified is not the executable that is timed (decision 10).
- **Reading next to OD-14**, as ADR-0009 decision 2: a process per run is chosen as the mechanism of a verification run only. **No sandbox, isolation, resource limit or timeout hierarchy is adopted or rejected with it**; the process is as unprotected as `local_run` says.

### 3. Drawn inputs

- The values of `a` and `b` come from a **deterministic generator** and a **seed that is a parameter of the run**, never from a file (cited: FR-9; the principle of OD-16). The seed reaches the program as a command-line argument; no input value is written to any file by either side.
- **Every drawn element is finite** (**owner**, HQ-0004 (2): "the verification inputs of this case are drawn finite") and has a **magnitude in [0.5, 1) with either sign** (range: this record's own, the one of ADR-0009 decision 5). Reasons for the range: no input and no product is zero or subnormal; every term of an output element has a magnitude of at least 0.25, so a term left out or counted twice moves the element by at least that much before rounding; and every exact element of the product is bounded by `k` in magnitude, far inside the fp32 range, so a non-finite output is never the right answer (decision 5).
- **The generator is implemented twice, once in the verification program and once on the Python side, and both must give the same `float` bit patterns** (decision 4). It is therefore built from integer arithmetic and a conversion that is exact in binary32, in a form the Python side can compute with array operations (the value of an element follows from the seed, the draw and its index, not from a loop over the elements before it — an interpreter loop over the 1.8e7 elements of one draw at gate/up, M = 512, is ruled out as a pure-Python reference is). The algorithm is the code task's and is identified by the source commit. Whether it is the generator of the timing driver is not promised.
- **Number of draws**: `draws`, a parameter of the run, at least 1, given by the caller with no default. Draw *d* has values determined by the seed, *d* and the dimensions; two draws of one run differ. One draw is enough for the class V1 of ADR-0003; how many an instance uses is a trade of cost against assurance that no source fixes (sub-question ⑤).
- **Shapes**: one run has one `m`, `k`, `n`, given by the caller and restricted no further than ADR-0008 (each ≥ 1). **Whether a caller ever passes dimensions other than those of the `op_signature` stays open — OD-16 sub-question ① is not decided.** Reason: which other shapes, and whether a kernel specialised for its shape is wanted (the `private_metrics` note of OD-16), is a policy the fixed inputs do not carry; the mechanism allows either answer without change, and an answer of "yes" extends the calibration set (ADR-0003 decision 6 (c)).
- **Relation to a timing run of the same attempt** (OD-13 sub-question ⑦): **stays open.** The two runs are separate processes with separate seed parameters; nothing here makes their inputs equal or different.
- **No non-finite and no corner-case input is drawn.** Whether any ever is "stays with the rest of OD-16 and B-7" (**owner**, HQ-0004 (2)); no strengthened oracle of OD-16 (threat B ⑵) is adopted or rejected.
- **The seed must be one the author of the attempt could not know** — that is FR-9's "not exposed to the coder" applied to this parameter, and it binds the caller. Where the caller takes it from is not decided (sub-question ⑤).

### 4. The reference

- **Owner** (HQ-0004 (1)): the oracle is "NumPy float64"; "The reference is the float64 product of the drawn fp32 inputs widened to float64, computed on the Python side of the harness; the process that runs the kernel holds neither the reference nor the comparison." `numpy` "becomes the first runtime dependency of `hilclaw`", approved by that answer "with an exact pin": "the code task that adds it pins the newest release that ships wheels for the CPython versions CI runs (3.11 and 3.14), and any later bump is a deliberate task". The answer closes the "Still open" line of #5 A-7 "for `cpu_standin` only; it is not the general answer to B-7". **This record adds no pin and names no version.**
- **How the inputs reach the Python side: it regenerates them from the seed** (this record's own). The Python side runs its implementation of the generator of decision 3 for each draw and computes the reference from its own arrays. The reference then depends on nothing the kernel's process says, which is the strongest form of the owner's reason ("keeps the reference and the verdict out of the kernel's address space"): a kernel that overwrites its inputs changes nothing the reference is computed from.
- **Input check**: before each kernel call the verification program reports a check value of the bytes of `a` and `b` of that draw, and the Python side compares it with the check value of its regenerated arrays. A disagreement makes the run **broken** (decision 7), never a fail: what it is there to catch is a defect of the harness (two implementations that differ), which must not be reported as a wrong kernel. A kernel that damages the generator's state or the report can cause a disagreement as well (decision 10); the run is broken either way. The check function is the code task's; it is no protection against anything (decision 10).
- **How the kernel's output reaches the Python side: through the report channel, as bytes** (decision 7). No file is used.
- **Before each kernel call the program fills `c` with NaN**, written as a bit pattern so that no build flag changes it. ADR-0008 leaves the content of `c` on entry unspecified, so no obligation is added; an element the kernel did not write then fails the comparison instead of holding whatever the memory held.

### 5. The comparison

- **Owner** (HQ-0004 (2)): "per-element `rtol` and `atol`, both instance parameters (FR-9); pass iff |out − ref| ≤ atol + rtol·|ref| for every element of the output; any NaN or infinity in the output fails."
- The comparison is on the Python side: the kernel's process "holds neither the reference nor the comparison" (**owner**, HQ-0004 (1)). This record's own: it is evaluated in float64 on the reported output widened to float64 (widening fp32 is exact); `rtol` and `atol` are parameters of the run, given by the caller from the instance, and **neither is passed to the verification program**, so the kernel's process does not hold the tolerance either.
- Each must be a finite number that is not negative (this record's own validity rule; the answer names none). Anything else is refused before a process is started.
- The reference is itself rounded (float64). Its error is not accounted for separately: the predicate is applied to the reference as computed.
- **An observation for whoever sets a tolerance** (this record's own; it is no value and no default): the drawn signs are mixed, so an output element is a sum of `k` terms that partly cancel. Its magnitude is typically far below the sum of the magnitudes of its terms and can be arbitrarily close to zero, while the rounding error of a conforming fp32 kernel does not shrink with it. A tolerance with `atol` = 0 is therefore one a conforming kernel can fail. The calibration tests of decision 8 choose their values with this in mind.

### 6. Defaults

- **Owner** (HQ-0004 (3)): "none. An instance must state both `rtol` and `atol`; the harness has no default value, and the calibration tests pass their own values (ADR-0003 decision 7)."
- Accordingly no parameter of decision 9 that carries a policy has a default in the harness, and this record names no tolerance value anywhere.

### 7. The verdict and the report

- **Channel**, as ADR-0009 decision 8: the standard output the process was started with. Before the first kernel call the program keeps it under a descriptor of its own and points descriptor 1 at standard error (`dup`, `dup2`), so what a kernel prints does not disturb the report. Standard error is free text and is not parsed.
- **Content**, in this order and with nothing else: for each draw, the check value of decision 4 written before the call, then, after the call has returned, the m·n elements of `c` in the layout of ADR-0008 decision 2 as the bytes they have in memory (4·m·n bytes); after the last draw, an end mark. The Python side reads the bytes on the same host, so the representation is the one it uses itself (premise of this mechanism: both sides run on one machine). **The spelling and framing are the code task's**, under one rule: the length of a complete report follows from `m`, `n` and `draws` alone, so the Python side never interprets output bytes to find a boundary.
- A run is **completed** when it did not time out, its exit status is 0, the captured report is exactly of that form for the parameters given, and every check value agrees. **Every other run is broken**: a non-zero status or a signal, a timeout, a short, long or malformed report, a check value that disagrees.
- **Verdict of a completed run**: **pass** iff the predicate of decision 5 holds for every element of every draw; otherwise **fail**. A run has no partial verdict.
- **A broken run is neither pass nor fail** (this record's own; ADR-0009 decision 7 took the same line for a failed process). It is not a pass, so nothing counts as verified by it (FR-9); it is not a fail, because a crash or a timeout does not show that the comparison rejected an output (ADR-0003 decision 4). This holds also when the draws it did report contain an element outside the tolerance. **What is kept of a broken run and what follows it is OD-10 and OD-14**; what follows a fail is FR-1 and OD-19.
- **The Python side returns**, for a completed run, the verdict and per draw the number of elements that failed the predicate and how many of those were non-finite; for a broken run, that it is broken, which condition failed and what the runner captured apart from the report. **The harness itself puts no element of `a`, `b` or the reference into what it returns.** What the runner captured is passed on unfiltered and is not free of them: standard error holds whatever a kernel printed, its inputs included, and the command line holds the seed, from which every input follows. Whether a caller may keep either, and where, is sub-question ⑤ and OD-10; FR-9 binds the caller there. Whether more (indices, the largest deviation) is returned or ever shown to a coder is not decided (ADR-0002 Boundaries; OD-6).
- The form is an interface between two parts of the harness of one source commit (OD-11 confirmed part); it carries no version and **is not a file or a field of the data plane**.

### 8. Calibration

- The run distinguishes the three kernels of ADR-0003 decision 2 by its verdict alone, for any tolerance under which the conforming kernel passes and the wrong outputs lie outside (ADR-0003 decision 7): **conforming** → every element of every draw is within the tolerance → pass; **failing** → an output that does not follow the inputs is outside on a draw → fail; **violating** (right on inputs known in advance, wrong elsewhere) → the draw comes from a seed its author could not know → fail.
- **"The functional test on inputs fixed in advance" can be a verification run whose seed and dimensions are written in the test**: the generator is in the source, so those inputs are ones the author of a kernel can know, and the violating kernel is written to be right on exactly them. The contract half is the same run with a seed the test takes at run time. No fixed-input mode is added to the harness (ADR-0003 decision 2), and nothing more is required than ADR-0003 requires: its decision 7 still lets the code task take the expected outputs of the functional test from constants instead.
- The calibration kernels build and run to completion (ADR-0003 decision 4), so their runs are completed; a broken run shows nothing. The tests pass their own `rtol` and `atol` (decision 6).

### 9. Parameters

| Value | Given by | Source |
|---|---|---|
| `m`, `k`, `n` | the caller | restricted no further than ADR-0008 (each ≥ 1); other shapes: OD-16 sub-question ① |
| Seed | the caller, no default | this record's own parameter; the caller's obligation is FR-9 (decision 3); its source and recording: sub-question ⑤ |
| `draws` | the caller, no default, ≥ 1 | this record's own parameter; the number an instance uses: sub-question ⑤ |
| `rtol`, `atol` | the caller, from the instance, no default | **owner**, HQ-0004 (2) and (3); that they are not passed to the program is this record's own (decision 5) |
| Time limit of the process | the caller, no default | `local_run` requires one; it bounds the process over all its draws and nothing on the Python side; values and hierarchy: OD-14 |
| Flags, trailing flags, compiler, build time limit, path of the executable | the caller, handed to `clang_build.build` | build settings: Boundaries |
| Environment and working directory | the caller, handed on unchanged | thread settings travel here; none is set by the harness |
| One kernel call per draw; input magnitudes in [0.5, 1); `c` filled with NaN before a call | constants of the mechanism | this record's own |

- The program takes its parameters as command-line arguments and reads no standard input, no file and no environment variable of its own. **No flag, language standard, `-march`, thread count or time-limit value is decided here**, and neither is whether the two builds of an attempt use the same flags (sub-question ⑥).

### 10. Limits

- **The kernel shares its process with the verification program.** It can read the seed, print its inputs, write to the report channel or end the run. None of that yields a pass without the right product for inputs the Python side derives itself — but the process is not sandboxed, and a kernel that reaches outside it (the memory of the Python process, for example) is not stopped by anything here: OD-14, OD-8 and threat A of OD-16.
- **A pass says that the output is right, not how it was produced**: dispatch to a library (threat B ⑶) is not seen. **The verified executable is not the timed one**: a kernel can tell the two programs apart and compute properly only when it is verified, and two builds may differ. Nothing here detects either (rest of OD-16; sub-question ⑥).
- **A kernel that is right only for the drawn range or shape passes**: no zero, subnormal or non-finite input is drawn, none is constructed to cancel beyond what mixed signs give (decision 5), and no shape is used but the caller's (OD-16 threat B ⑵ and sub-question ①; #5 B-7).
- **Cost**: per draw one kernel call, one regeneration and one float64 product on the Python side, and 4·m·n bytes of report (16 MB for gate/up at M = 512, the largest output of the first instances); the runner returns the report after the process has ended, so it holds `draws`·4·m·n bytes at once. The time limit bounds the process only; **the Python-side work of a run is bounded by nothing here** (OD-14). All of it lies inside the wall clock of a round (OD-2, OD-19).
- **One machine**: the Python side reads raw `float` bytes produced on its own host. How an output travels from another machine or a board is not decided (#5 B-2, A-7 ③).

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 2 | One driver source with a timing and a verification mode, or one run serving both | Edits the timing driver and reopens ADR-0009 decisions 5, 6 and 8; an output written between repeats would have to be kept out of every timed interval. Its gain — verifying the very executable that is timed — is a defence this record may not adopt on its own (decision 10, sub-question ⑥). |
| 2 | The kernel loaded into the Python process (`ctypes`) | Against the owner's answer (the kernel's process would hold the reference) and ADR-0009's reasons. |
| 3 | A constant number of draws | A value no source gives; the instance or the tool contract is where the trade is made. |
| 3 | Uniform values in (−1, 1) | Admits zeros, subnormals and terms too small to show when one is dropped; whether such inputs are wanted is the corner-case question the owner left open. |
| 3 | Deciding sub-question ① here, either way | "Yes" needs a rule for which shapes, and "no" narrows FR-9's "shape/seed"; neither follows from the fixed inputs. |
| 4 | The program sends `a` and `b` through the pipe with the output | One generator instead of two, but the reference would rest on bytes that passed through the kernel's process, and the gate/up instance at M = 512 adds 68 MB per draw. |
| 4 | The Python side generates the inputs and hands them to the program | `local_run` gives a process no standard input, a file is excluded by FR-9 and the principle of OD-16, and a command line cannot hold them. |
| 4 | No input check | Two generators that differ on some host would turn every conforming kernel into a fail, silently. |
| 4 | `c` left as allocated | An unwritten element would hold stale memory — on a second draw, the output of the first. |
| 7 | The output as text, or in a file | Text multiplies the size and adds a parser of `float` text on both sides; a file needs a path, a writer rule and a clean-up, and would place kernel outputs where a coder may read them. |
| 7 | A broken run with a failing draw counts as fail | Two rules for one report; neither outcome is a pass, so the floor of FR-9 is the same. |
| 8 | A fixed-input mode of the harness for the functional test | ADR-0003 decision 2 does not require one, and the seed parameter already serves. |

## Consequences

- **Code tasks** (rest of PLAN P1-3, code mode, two or more slices): the verification program in C and the Python side under `hilclaw/harness/`, using `clang_build.build` and `local_run.run` as they are; the `numpy` pin in `pyproject.toml` by the owner's rule. Real-clang tests run on CI only; parsing, regeneration, reference and comparison can be tested everywhere with a stand-in program. That the two generators agree is shown by a test that needs clang.
- **`numpy`, ADR-0010 and ADR-0015**: the "standard library only" of those records was said of the exposure form and of the frame of a tool contract, and both left a new dependency to the owner, who has now approved one. The package gets a runtime dependency for the harness; where it is imported, and whether a front can start without it, is the code task's.
- **P1-4**: three C kernels for `gemm` and tests as decision 8 reads ADR-0003, each passing its own `rtol`, `atol`, seed and `draws`. **C gate** (PLAN P0.5-1): the "harness pass" half has a run to use; the gate is designed there.
- **The contract of `correctness.check`** (PLAN P1-1): of the work described here, only building, starting the process and reading its report touch the target; regeneration, reference and comparison do not. This is an observation for that contract, which alone places the cut (ADR-0016 decision 3).
- **Result files** (PLAN P1-8): a record of a verification should be able to hold the verdict or the broken state, and what the source commit does not determine — the dimensions, `draws`, `rtol`, `atol` and the per-draw counts. **No field is named.** An instance must state `rtol` and `atol`; no member of `instance.json` is named. Whether a seed may be recorded goes with sub-question ⑤, and whether a tolerance is shown to the coder stays open (ADR-0002).
- **Not edited and now less exact** (follow-ups): the "Owner-only" bullets of ADR-0002, ADR-0003, ADR-0007, ADR-0008, ADR-0009 and the Context of ADR-0016 that call the oracle and the tolerance vocabulary unanswered; the Context of ADR-0010 ("`pyproject.toml` declares no runtime dependency") and the "standard library only" among the fixed inputs of ADR-0015, once the pin exists; the unticked item B-7 and the "Still open" line of A-7 on issue #5.
- **A-13 reading**: document mode; no code, schema file, field or settings file changes. The dependency is approved by the owner and added by a later task. The report form is an internal interface of the layer-2 package, not a data-plane schema.

## Boundaries (not decided here)

- **Owner-only (DRIVER §9)**: everything of #5 B-7 beyond the answer — vendor golden outputs, downstream-metric thresholds, user-defined checks, tolerances of other dtypes; datasets (#5 B-8); the oracle of any backend other than `cpu_standin`; the measured quantity and its direction (OD-1, #5 A-4); OD-3; OD-25; C-6; how a backend is reached (#5 B-2).
- **OD-16, OD-14, OD-8**: every defence beyond the FR-9 minimum — strengthened oracles and corner-case inputs, static checks, profiler confirmation, order dependence, timing defences; every sandbox, isolation, resource limit and timeout hierarchy; the isolation means. OD-16 sub-questions ①-④ and OD-13 sub-question ⑦ stay as registered.
- **Sub-questions this record raises** (registered under OD-16): ⑤ the caller's policy of a verification — where the seed comes from and who draws it, how many draws a round or a promotion-level re-verification (FR-3 ④) uses, and whether a seed, or what the runner captured of a run (the command line with the seed, a kernel's standard error), is recorded after a run (with OD-13 sub-question ⑦; OD-10; PLAN P1-8). ⑥ Whether the verified and the timed executable of an attempt must be built with the same flags, or must be one executable (with the build settings; reopens decision 2 and ADR-0009 if the answer is one executable).
- **Build settings**: flags, the language standard, `-march`, the OpenMP runtime and thread count, `task.build` (OD-6 sub-question ②); whether a kernel may link another library.
- **The round**: the order of verification and timing, what follows a failed or a broken verification (FR-1, OD-10, OD-19), the execution points (sim, board) at which it is repeated.
- **Elsewhere**: fields and schemas of `eval.json`, `sim.json`, `board.json`, `instance.json` and every event kind or payload (PLAN P1-8); a tolerance field of the spec (ADR-0002); the FR-10 tool contract, the harness / backend split and the exposure form (PLAN P1-1, OD-18); the remote path; any kind other than `gemm`, any dtype other than fp32, any kernel language other than C.
- Code, C files, tests, CI changes, `pyproject.toml` and the `HIL-Claw-data` repository: later tasks.
