## Context

- ADR-0081 K4 found two sources of an `OSError` that `build` raises outside its five classes: "(i) A line of `build` before `subprocess.Popen` is called" and "(ii) Removing the temporary file, when an exception that is no `OSError` left the block that creates and runs the compiler before its end was recorded. The `finally` then raises the removal's error in that exception's place." ADR-0081 decision 5 and ADR-0082 decision 5 keep "the removal error raised in place of an exception that is no `OSError` (ADR-0081 K4 (ii))" open. ADR-0081 alternatives point 4 declined S3 or S5 for a plain `OSError` because "It still comes in one class for a source (S5) and for the output path (S3), and as a removal in place of another exception (K4 (ii))."
- Task T-0253 (PR #160, `0305d7b`) changed (ii) and placed nothing in a row.
- **Observations at `0305d7b`** (`hilclaw/clang_build.py`; no code is bound):
  - **P1.** The `build` docstring: "An exception that is not an `OSError` and leaves the build early, such as `KeyboardInterrupt`, is passed on unchanged; when removing the temporary file then fails, the removal's error is not raised but added to that exception as a note naming the temporary path." The code records the exception that leaves the `try` (`except BaseException` that re-raises), and its `finally` adds one note, `removing <path> failed: <repr of the error>`, and raises nothing in its place. T-0253's Result: the exception passes on as the same object, with its own traceback and chain.
  - **P2.** Every `OSError` inside the `try` is caught and raised in one of the five classes: from constructing `Popen` as `CompilerNotStartedError`, from `_communicate` as `CompilerRunError`, from the stat test (other than the two that read as no artefact) as `ArtefactNotCheckedError`, from `os.replace` as `ArtefactNotPlacedError`; a failed removal with nothing in flight becomes a `removal_error` or `TemporaryNotRemovedError`. **One line is the exception**: `duration_s = time.monotonic() - started` stands in the `else` of the `try` around `_communicate`, and no `except OSError` covers it. An `OSError` from it leaves `build` plain, after the compiler process ended and its output was read, and that output is dropped; when the removal then fails, it is added to that `OSError` as a note (P1). The lines after the `try` raise none. **So a plain `OSError` of `build` — one that is none of its five classes — comes from the lines before the `try`, all of which run before `Popen` is called, or from that one line.** T-0253's Result ("A plain OSError of build now comes only from the lines before subprocess.Popen") did not count it. `CompilerNotFoundError` is a `LookupError`, not an `OSError`.
  - **P3.** **The lines before the `try` that can raise an `OSError`**, confirmed from the code and not copied from K4 (i):
    - **(a) The path tests.** `_checked_sources` tests each source with `Path.is_file` and `Path.is_dir`; `build` tests the output with `is_dir`, `exists` and `is_dir`; they raise `FileNotFoundError`, `IsADirectoryError` or `NotADirectoryError` with a message and no `errno` (cited: ADR-0080 M4). The tests themselves raise any `OSError` but those whose `errno` is `ENOENT`, `ENOTDIR`, `EBADF` or `ELOOP` or whose `winerror` is 21, 123 or 1921 on 3.11, as on 3.12 and 3.13 by T-0246's Result, and none on 3.14 where the generic `os.path` functions apply (on Windows not read) (cited: ADR-0080 Context).
    - **(b) Forming the absolute paths.** `os.path.abspath` is called for each source, for the output and, in `_resolve`, for the path `shutil.which` found. In `posixpath` (3.11.9 and 3.14.4) it calls `os.getcwd()` (`os.getcwdb()` for a bytes path) for a path that is not absolute; in `ntpath` it calls `nt._getfullpathname` first and `os.getcwd()` only if that raises. The found path is relative when the `PATH` entry that holds it is relative, on Windows when `which` searched the current directory, or when `compiler` is itself a relative path with a directory part, which `which` returns relative, as given (on 3.14.4 rejoined from its parts, on Windows possibly with a `PATHEXT` extension).
    - **(c) The temporary name.** `secrets.token_hex(8)` calls `os.urandom` through `SystemRandom().randbytes` (3.11.9 and 3.14.4).
    - **(d) The start time.** `started = time.monotonic()`.
    - **(e) The search for the compiler.** In `_resolve`, `shutil.which` (3.11.9 and 3.14.4) calls `os.confstr("CS_PATH")` when `PATH` is unset and the command has no directory part, and catches only `AttributeError` and `ValueError` from it. It tests candidates with `os.path.exists`, `os.access` and `os.path.isdir`; the generic `exists` and `isdir` return false for an `OSError`, and `os.access`, the `nt` functions that serve `exists` and `isdir` on Windows and `_winapi.NeedCurrentDirectoryForExePath` (3.14.4, Windows) were not read.
    - `os.getcwd`, `os.urandom`, `time.monotonic` and the unread calls of (e) are C code this record did not read; it counts each as a possible source of an `OSError`, and on which systems and when one is raised is not established here. An `OSError` of `nt._getfullpathname` does not leave `abspath`: `ntpath` catches it and falls back (b).
    - **Not sources**: `_check_timeout` and `_checked_flags` raise `TypeError` or `ValueError` only; `with_name`, `os.getpid` and the forming of the command raise no `OSError`. `CompilerNotFoundError`, raised when `which` finds nothing, is no `OSError` (P2). Calls that only rework a path string — `normpath`, `normcase` and the root splitting under `abspath` and `which`, C code on some versions and platforms — are not counted. What iterating an argument or its `__fspath__` raises is the code of the object handed in and is not counted.
  - **P4.** So K4 (i) holds, refined, and K4's "No other line raises an `OSError` outside the five classes" does not: a plain `OSError` of `build` comes from the path tests and the three classes `build` raises for them (a), from `os.getcwd` while forming an absolute path of a source, the output or the found compiler (b), from `os.urandom` while naming the temporary file (c), from `time.monotonic` (d) or from the search for the compiler (e) — all before a compiler process exists — or from `time.monotonic` after the compiler ended (P2). Its class does not tell the last apart from the others.
- No owner comment on #5 speaks to ADR-0081, ADR-0082, T-0253 or ⑱ (마) (checked on 2026-10-17; every comment since 2026-10-16 carries the driver tail).

## Decision

### 1. Scope and terms

- A call of `correctness.check` as ADR-0081 decision 1 has it. The six kinds, S1 to S10 and the keeper are as ADR-0079 decision 1 has them. **A plain `OSError` of `build`** is an `OSError` that `build` raises and that is none of its five classes (ADR-0081 K4), the three classes the docstring names for the path tests included. Of these, a `NotADirectoryError` that `build` raises before it starts anything already has its row, S3 (cited: ADR-0060 decision 4); decisions 3 and 4 speak of the rest. **The mock** builds nothing and is unchanged.

### 2. The entry of ADR-0081 K4 (ii) is answered by landed rules

- **What the entry named no longer occurs.** `build` raises no removal error in place of an exception that is no `OSError` (P1); what leaves `build` is that exception itself. **This record reads the entry as answered** in the two ways below, and no part of it remains an `OSError` to place.
- **A request to end** — in Python a `BaseException` that is no `Exception`, such as `KeyboardInterrupt` or `SystemExit` (cited: ADR-0045 decision 1) — that an operation lets pass is "not answered: the tool function does not turn it into an end line, and it passes through the tool function unchanged"; the identity stays open and a later call is `step_open` (cited: ADR-0045 decision 5). **This record reads no row of S3 to S10 as covering it**: each names a situation of the build, and a request to end says "that the process is asked to end or was interrupted", and ADR-0045 "gives it no kind" (cited: ADR-0045 decision 5). Where the line between it and an error runs in code is the code task's (cited: ADR-0045 decision 1).
- **Another `Exception`** that `build` passes on — for example a `TypeError` or `ValueError` from inside the construction of `Popen` — is one of the entries already open under (마): "the `TypeError` of `clang_build.build`" and "whatever `clang_build.build` passes on from `subprocess` beyond the `OSError` its docstring names" (cited: ADR-0080 decision 4). An operation that lets it pass is answered `operation_answer_invalid` (cited: ADR-0045 decisions 4 and 5); "That says what the landed rules do with it; it is no answer of this record" (cited: ADR-0060 decision 4). This record does not answer those entries.
- **The note changes nothing.** It is text on the raised object, not an error the operation meets. The message of `operation_answer_invalid` shows "of what was raised, neither its message nor its arguments nor where it was raised" (cited: ADR-0045 decision 6), so the note, which names a path, reaches no message and no line. A request to end passes through with its note; "What a front or the process does with what passed through is not this record's" (cited: ADR-0045 decision 5), nor this one's. The failed removal is in no answer, as ADR-0081 decision 2 has it for `removal_error`: the file left behind is a file of the build directory, whose removal is ADR-0056 decision 4's and whose failure is ⑰ (다).

### 3. A plain `OSError` of `build` stays without a row

- **What the operation now observes** (P2, P4): mostly that the build failed before the compiler process was created, so that no compiler ran and there is no log (cited: ADR-0078 decision 2, "S3, S5, S6 and S4 found before the build start no compiler or none that ran, so they have no log"); but the same class can come from after the compiler ended (P2). The removal reason of ADR-0081 alternatives point 4 is gone.
- **Why that is not enough for a row.** "What the operation observes decides the row" (cited: ADR-0060 decision 4), and the observation fits more than one row and some sources fit none:
  - **One class serves two rows.** `FileNotFoundError` and `IsADirectoryError` come from the source test (S5) and from the output test (S3) (cited: ADR-0060 decision 4), and the other classes of the path tests (P3 (a)) from both. ADR-0081 alternatives point 4 gave this reason, and it still holds.
  - **Sources no row names.** S3 is "The build directory cannot be made or written", S5 "A file of the compiled set is no longer a regular file when the build is called, or the verification program is missing from the installation", S6 "The compiler is not found, or its process cannot be started" (cited: ADR-0060 decision 4). An `OSError` from `os.getcwd` (P3 (b)) says that the working directory of the process could not be read, one from `os.urandom` (P3 (c)) that the system could not give random bytes, one from `time.monotonic` (P3 (d)) that the clock could not be read, and one from the search for the compiler (P3 (e)) that the search failed, not that it ended without a find; **this record reads none of the three wordings as covering any of them**, the "not found" of S6 included. They can come in the classes of (a): a `FileNotFoundError` from `os.getcwd` is the class of a missing source.
  - **"Before the start" is several rows.** S3, S5 and the "not found" of S6 are all met before a compiler process exists (this record's reading of the moments "before the build", "before the compiler is started" and "at the start of the build" of ADR-0060 decision 4), so the moment alone places nothing.
  - **And not always before the start.** An `OSError` from `time.monotonic` after the compiler ended (P2) comes from a build whose status was known, so S7, S8 or S9 may hold for it, or the build may have ended ok, and nothing the class carries says which. **The cost, stated**: its log is dropped by `build` (P2), against the letter of ADR-0078 decision 2 ("The log of every build whose compiler process was started and has ended — by itself, or killed for its time limit — is kept"), and, for S7 and S8, also against O2 (**the owner's**: "Kept, not returned: in a file of the attempt, never in the result or in `events.ndjson`"); no row, chosen or open, brings it back. Where the build ended ok, the artefact is removed with the temporary file and the check that would have run it is answered by a tool failure. How often a machine's monotonic clock fails is not established here.
- **Unchanged.** The rows ADR-0060 decision 4 gives for what `build` raises before it starts — a `NotADirectoryError` for the output path (S3) and `CompilerNotFoundError` (S6) — are not revisited here. That a `NotADirectoryError` from an unread call of P3 (b) to (e), if one occurs, would meet that S3 row is not revisited either.
- **What would let it be placed** (named, not written here):
  - **A code change** of `clang_build.build` that tells, by class or by a member of the error, the source tests from the output tests, and both from the other lines before the start (P3 (b) to (e)). Then a record can weigh S5 and S3 for the first two.
  - **A code change** that raises no plain `OSError` after the compiler started, for example by reading the clock where a failure is caught or by raising it in a class that keeps the result (P2). Then the line after the end leaves this entry.
  - **A step of the operation's own**, as ADR-0060 decision 4 already allows: "An operation places such an error by the step of its own at which it met it". For example, absolute paths for the sources and the output take `os.getcwd` out of those two on POSIX (P3 (b)), not out of a relative found compiler. This record adds nothing to that rule.
  - **A record for the sources no row names** (P3 (b) to (e)), which reads one row's wording to cover them or adds the situation to the list of ADR-0056 decision 5. The second may need a new value of `error.kind`, which this record does not add.
- **Until then**, an operation that lets it pass is answered `operation_answer_invalid` (cited: ADR-0045 decisions 4 and 5), which says what the landed rules do and is no answer of this record. **The cost, stated**: a check whose source vanished before the build, S5 by its meaning, is answered by a tool failure of a kind that says the backend's answer had neither form; before the start no outcome changes, since S3, S5 and S6 are tool failures as well (cited: ADR-0060 decision 4), and a caller reads a different kind. After the end, a build that S7 or S8 would make a result is answered by a tool failure, against O1 (**the owner's**: "One each: `build_exit_status` for S7 and `build_time_limit` for S8.").
- **The classes of the path tests** (ADR-0080 decision 4) are not settled by this as their own entry: they are part of a plain `OSError` and stay open with it.

### 4. How far (마) is answered

- **Answered now, for `correctness.check` of the first case and of the mock**: the entry of ADR-0081 K4 (ii) (decision 2); where a plain `OSError` of `build` comes from, with its row left open for the reasons of decision 3.
- **Open under (마)**: the row of a `CompilerRunError` whose `timed_out` is false (ADR-0082 decision 4); a plain `OSError` of `build` (decision 3) — `FileNotFoundError` or `IsADirectoryError` for a source (S5) or for the output path (S3), the other classes of the path tests of ADR-0080 decision 4, an `OSError` from `os.getcwd`, `os.urandom`, `time.monotonic` or the search for the compiler before the start, and one from `time.monotonic` after the compiler ended; and the other entries ADR-0079 decision 5 names, as ADR-0080 decision 4 lists them — the `TypeError` of `clang_build.build`, whatever `clang_build.build` passes on from `subprocess` beyond the `OSError` its docstring names (now with a note when the removal fails), and the `ValueError` or `TypeError` and the `OSError` for "a `cwd` that does not exist" of `local_run.run`.

## Consequences

- **Code** (code mode, D12 rules; names and modules are the code task's; **this record binds no code**): the operation of `cpu_standin` for `correctness.check`, when it is written, applies ADR-0079 to ADR-0082 and this record; it lets a request to end from `build` pass, and leaves a plain `OSError` and another `Exception` of `build` to the landed rules until a record places them. No change of `clang_build.build` is needed for this. A code task may tell the source tests from the output tests and from the other lines before the start, and may make `build` raise no plain `OSError` after the compiler started (decision 3).
- **Not edited and now less exact.**
  - ADR-0081 K4 (ii) ("The `finally` then raises the removal's error in that exception's place."); decision 4 ("or it is a removal error raised in place of an exception that is no `OSError` (K4 (ii))" and "A removal error of K4 (ii) does not say whether a process was created"); decision 5's open entry for K4 (ii); alternatives point 4 ("and as a removal in place of another exception (K4 (ii))"); and Consequences, Code ("Telling the removal error of K4 (ii) apart is another code task"), which T-0253 answered by raising no such error.
  - ADR-0081 K4: "No other line raises an `OSError` outside the five classes", and decision 4: "It comes from before the creation of the compiler process (K4 (i))", both for the line after the end (P2, P4).
  - ADR-0078 decision 2 ("The log of every build whose compiler process was started and has ended — by itself, or killed for its time limit — is kept"), for the line after the end, whose log `build` drops (decision 3).
  - ADR-0082 decision 5's open entry for K4 (ii), and its Boundaries ("the removal error of ADR-0081 K4 (ii) included").
  - Of ADR-0080, no sentence beyond those ADR-0081 Consequences already lists (M3 and decision 4's first open entry).
  - ADR-0060 decision 4: "an `OSError` of `clang_build.build` from removing its temporary file (below), which comes up in the same class from the same call as S6 and S9", and "one from removing the temporary file" among the errors an operation lets pass, since `build` no longer raises a removal error as itself; and "a `FileNotFoundError` or `IsADirectoryError` for a source (S5) or for the output path (S3)", whose two rows are not all its sources (decision 3).
- **A-13 reading.** Nothing of the data plane is added or changed: no member, no value of `condition` or `error.kind`, no file, no version.
- **Runtime acceptance items**: none. Whether a real machine's `os.getcwd`, `os.urandom` or `time.monotonic` fails during a build is the code tasks' observation.
