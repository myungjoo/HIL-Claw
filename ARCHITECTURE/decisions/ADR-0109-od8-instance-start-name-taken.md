## Decision

### 1. Scope

- **The start of an instance of ADR-0076 decision 1, under a `run_id` that this start built by ADR-0027** (for a start that is tried again, the id it built at its first attempt counts as built by it), when the write of `runs/<run_id>/instance.json` by the steps of ADR-0025 decision 3 finds the final name taken (the report of ADR-0025 decision 4; today `NameTakenError`).
- **Outside**: a `run_id` the start did not build — given by a person or a caller (㉔), or taken from another run; instances outside ADR-0076 decision 1; every other failure of the write (they are reported apart — ADR-0025 Consequences; Alternatives, point 4); a branch, a continuation or a resume under the id of the run it comes from (①). Nothing here is required or allowed of them.
- **How the answer holds while ⑰'s first part and ⑩ stay open.** Decisions 2 to 4 bind "the start" as a role, as ADR-0076 does, whatever component performs it (⑰ first part, OD-23). They use only what the start holds at the moment of the finding — the report of the write, its own `run_id`, its content — and nothing of the order of its other writes: they hold whether the start wrote other files of the run before `instance.json` or writes them after it (⑩). What that order does to the other files is a finding, not an answer (decision 5).

### 2. The start stops

**When the write reports the final name taken, the start stops: it does not happen.** It writes nothing more under that `run_id`; it does not read, open, compare or remove the entry under the name; it does not build another `run_id` and try again; and it does not hand the run on to anything that would act as if the start had happened.

- **Why**: the start built the id itself, so an id in use is not a state this start expects. It is one of four things, and the start cannot tell them apart from the report: a repetition of ADR-0027 decision 5's improbable kind; a premise of ADR-0027 that failed (draws that were not independent, an id reused by a defect, two clones); a file put there by other means (cited: ADR-0004 decision 10, ADR-0018 decision 6); or an earlier attempt of this same start whose writer died after the last step and before its report, tried again with the id it kept (the case ADR-0025 decision 4 names; decision 4 below). Only the first is harmless to go around, and the start cannot know it is the first; the fourth is not told from the second or third by the report either, since the entry under the name was not read and an equal content would not show who wrote it (Alternatives, A). Stopping is the one answer that is safe in all four: it changes nothing of the run that holds the id, and it tells somebody; in the fourth, recovering the first attempt is left open (decision 4).
- **No "equal content" is defined.** This record adopts no notion under which the file under the name is the start's own write (Alternatives, A), so it needs none and defines none.
- **A stop is not a refusal of ADR-0076 decision 3**: no member is missing. It comes only after those checks have passed, so a start missing a member is refused by ADR-0076 and never reaches this decision; a start that is refused is not also reported here.

### 3. What the start reports and what it leaves

- **Report**: to whoever gave the values (as ADR-0076 decision 3 has its refusal go), that the start did not happen because the `run_id` it built is in use — the final name of `instance.json` was found taken — with that `run_id`, and that nothing was written under that name. It reports nothing of the entry under the name (it read none). It is told apart from a refusal of ADR-0076 decision 3 and from a failure of the file system. Its form is the code task's and the UI's (OD-23, UC-1), as ADR-0076 decision 3 leaves its own.
- **On disk, by this decision**: the entry under the name and every other entry of `runs/<run_id>/` are as the start found them; the write has removed its temporary file, or, if that removal failed, left it behind (a leftover by the definition of ADR-0025 decision 6; the removal is cited from ADR-0025 decision 4); and it created no directory, since the run directory held the name. **This decision removes nothing**, also not a file the start itself wrote into the directory before the write, if the order of ⑩ had it write any; what those files mean is ⑰'s third part and ⑩, not answered here (decision 5).
- **A run directory with other files and no `instance.json`** does not arise from a stop: at the finding the name was taken. It arises when a start dies before its write, or is refused by ADR-0076 after other files were written (an order ⑩ leaves open), and its meaning stays with ⑰'s third part.

### 4. What a second start under a `run_id` in use means

- **Within the scope, it means no run.** A start that finds its own id in use is not a new run, not the run that holds the id, and not a continuation, branch or resume of that run: it is a start that did not happen (decision 2). The run that holds the id is unchanged by it as far as `instance.json` goes.
- **The retried start** — a start whose writer died after the last step and before its report, tried again — falls under this only if the retry uses the same id, which something must have kept ("Nothing remembers an id that was built" — cited: ADR-0027 Limits). If it does, it stops and reports the id in use; the first attempt's file stays whole under the name. If it builds a new id, as a start that kept no id does, it does not meet the first attempt's file at all and starts a run of its own; the first attempt's directory stays as it was. In both cases the first attempt's directory holds `instance.json`, possibly a leftover of its write (a second name of the file — cited: ADR-0025 decision 6), and whatever the first attempt wrote before it if ⑩'s order had it write any. **Whether anything later takes such a directory up as a run** — for one, by writing its first `STATE.json` — is ⑩ (what a run directory that holds other files and no `STATE.json` means); this record neither gives nor excludes such a step, and that step would not be the start taking the file for its own write.
- **What is not decided**: whether a continuation or a branch is a new run (①, OD-20). The answer above holds under either answer of ①: if ① makes it a new run whose start builds a new id by ADR-0027 and writes an instance of ADR-0076 decision 1, it is a start of the scope and this decision applies to it as to any other; if ① makes it later rounds of the same run, it is under the id of the run it continues, which it did not build, and so is outside the scope (decision 1); whether such a continuation ever writes `instance.json` again is ① (ADR-0025 decision 3). Whether a run may have a caller-given name (㉔) is not decided either: such a start is outside the scope. Neither question is needed for the answer above.

### 5. Finding: the order of the first files is not fixed, and the stop protects `instance.json` only

- **If the start writes `instance.json` before any other file of the run**, the stop leaves the run that holds the id wholly unchanged.
- **If ⑩ lets the start write the first `STATE.json` (or another file) before `instance.json`**, then by the finding the start has already written into a directory whose `instance.json` this start's write did not put there, and the first `STATE.json` would have replaced that run's file if it had one, or put one into that run's directory, without a report (cited: ADR-0013 decisions 2 and 6 — the replacing rename, which does not refuse an existing file). The stop of decision 2 still holds then and still protects `instance.json`, but it cannot undo the earlier write.
- **This record does not choose the order** (⑩) and does not add a look at `runs/<run_id>/` before the first write (left open by ADR-0027 decision 5): a look is not a reservation (two steps), and requiring the directory to be missing is ADR-0025's rejected row 5. It hands the finding to ⑩: whichever order a later record fixes, it is to say what a start does when a file it wrote before `instance.json` turns out to be in a directory whose `instance.json` it did not write.

| At the start | What follows |
|---|---|
| A content of ADR-0076 decision 1 that passes its checks, a freshly built id, the name free | Written by ADR-0025; this record does not apply |
| The same, the name taken | Stop: report the id in use; nothing written under the name; nothing removed (decisions 2, 3) |
| A content missing `tolerance`, the name taken | Refused by ADR-0076 decision 3 (report `tolerance`); the write is not begun, so the name is never looked at |
| A retry that kept the id of a first attempt that died after its last step | Stop: report the id in use; the first attempt's file stays (decision 4) |

| An id given by a caller, or a continuation that reuses an id | Outside the scope (㉔, ①) |

## Consequences

- **The code slice it makes possible** (code mode, a later task): how a caller of `hilclaw.instance_file` answers `NameTakenError` once a start component exists — it stops, writes nothing more under that id, builds no other id, reads nothing under the name, and reports the id in use apart from a refusal of ADR-0076 and from an `OSError`. It waits on a start component (⑰'s first part, OD-23). No module or function is named here as binding; `hilclaw/instance_file.py` and `hilclaw/instance_start.py` need no change for it.
- **A-13 reading**: document mode. No member, file, kind of file, tool-failure kind, validity rule, `schema_version` or layout version changes; no code, `instance.json`, `STATE.json` or `events.ndjson` changes; no dependency is added. The report of decision 3 is no tool-failure kind: the start is not a tool by any record, and its report's form is left to the code task and the UI.
- **Sentences of accepted records that become less exact** (listed, not edited; found by a search of `ARCHITECTURE/decisions/` for "in use", "second start" and ㉓ (i)/(가)). For the scope of decision 1, these say that what the caller does or what a second start means is not decided; it now is: ADR-0025 decision 4 ("**Not decided** (sub-question ㉓, first part): what the caller does then … and what a second start with a `run_id` that is in use means"), decision 7 ("a caller that was not told (sub-question ㉓)"), its Boundaries ("what a second start with a `run_id` that is in use means", and the text of ㉓ (i)); ADR-0027 Status ("whether anything checks at the start of an instance that an id is not in use" — whether a look is made stays open), Context ("what a second start with a `run_id` that is in use means"), decision 5 ("by which step an id that is in use is noticed, and what is done then" — for the scope: the last step of the write, and a stop) and Boundaries ("A second start with a `run_id` in use"); ADR-0076 Boundaries ("a second start with a `run_id` in use (㉓ (가))"); the Alternatives of ADR-0025 (point 4: "it would decide that a second start with an equal content is the first one continuing (sub-question ㉓)") and of ADR-0027 (the digest row: "which decides what sub-question ㉓ leaves open"), whose rejections stand and which now point at a part that is answered for the scope; ADR-0030 Boundaries and ADR-0034 Context and Boundaries, which list ㉓ among what the start does. The list is not claimed to be complete. No sentence of UsageCases became false: UC-1 step 2 says the system creates the workspace and nothing of an id in use. In code, the last sentence of the module docstring of `hilclaw/instance_file.py` ("what a caller does with a taken name are open (OD-23, sub-questions 10, 17 and 23 of OD-8)") becomes less exact for the scope of decision 1 and stays true outside it; it is not edited.
- **Runtime acceptance items**: none. Nothing here needs a live Claude Code session or hardware to establish.
