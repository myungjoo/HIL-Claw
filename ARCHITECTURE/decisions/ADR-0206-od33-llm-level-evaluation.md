### 3. Time: what is timed, by which clock, where

- **Clock**: `CLOCK_MONOTONIC` through `clock_gettime`, read by the graph program in a **timed form** selected by its input (POSIX.1-2008, which the program already needs; no new dependency). The program also reports `clock_getres` of that clock in ns as `resolution`, as ADR-0183 decision 4 does for a timing run. The untimed form, which every existing caller uses, keeps its report byte for byte.
- **Readings**, in the generation mode at `lm_head_rows` `"last"`: `t_s` once, after the input file is read, the libraries are loaded, every buffer is allocated and initialised, immediately before the first step of pass 0; then `t_p` after the token selection of pass p, p = 0 … G − 1. **The timed form writes no logits rows**: its report is the S prompt ids, the G selected ids, the G + 1 readings and `resolution`, then the end mark, all written after `t_{G−1}`; its layout is slice 1's. So no write to the report, which in a container goes to the client's pipe and can block, falls inside an interval, and no buffer of rows adds to the memory figure. The timed runs need only the tokens (decision 5); the logits rows are the judged run's.
- **Intervals**: `d_0 = t_0 − t_s` (the prefill: the embedding of S prompt tokens, every layer, `lm_head` on the last row, the selection of the first generated token); `d_p = t_p − t_{p−1}` for p ≥ 1 (one decode pass: one token in, the selection of the next). **Outside every interval**, as ADR-0007 decision 2 keeps them outside a kernel's timing: starting the process, loading libraries, reading the weights, allocation, tokenisation, writing the report, the reference and the comparison.
- **`"last"`, not `"all"`**: `"all"` makes the prefill's `lm_head` compute S rows of V, a cost no generation pays; the judged run uses `"all"` only because the teacher-forced comparison reads every row (ADR-0192 decision 5). Decision 5 ties the two runs by their tokens.
- **The metrics** (per repetition r; G ≥ 2 for the decode metrics, which are absent for G = 1):

| Metric | Side | Definition |
|---|---|---|
| time to first token | latency | `d_0`, in ns |
| decode time per token | latency | `(d_1 + … + d_{G−1}) / (G − 1)`, in ns |
| prefill tokens per second | throughput | `S × 10⁹ / d_0` |
| decode tokens per second | throughput | `(G − 1) × 10⁹ / (d_1 + … + d_{G−1})` |

- **What "throughput side" means at batch 1 and one request** (**owner**: both 1 for now): the rates of one sequence, so the decode rate is the reciprocal of the decode time per token and the two sides carry the same information. **It is no measurement of batching or of concurrent serving**: no two sequences share a pass. The two sides are recorded separately so that a later batch size or request count above 1, where they part, fits the same metrics; what a pass of several sequences times is that later record's.
- **Time to first token here** is the time from the start of the prefill to the first selected token inside one process. It holds no queueing (one request), no tokenisation and no process start, and it is no serving latency.
- **Repetitions and warm-up**: R timed runs, each a new process with the same input file; every run's intervals are kept in order (ADR-0007 decision 3, applied by analogy) and none is discarded (its decision 6); no untimed warm-up run is made. Each run starts cold (new process, libraries loaded with `RTLD_NOW`, weights read and so resident before `t_s`); this is part of what the figures mean, not a member of the record. **Summary**: the two latency figures are each the median over the R runs of their per-run values (R is odd, below); the rates are derived from those summaries, `S × 10⁹ /` the summary time to first token and `10⁹ /` the summary decode time per token, so that the summarised decode rate stays the reciprocal of the summarised decode time and the prefill rate stays S × 10⁹ divided by the summarised time to first token; memory is the maximum (decision 4). Every run's per-pass intervals are kept beside them (decision 6). R is **odd** (1, 3, 5, …); whether the user gives it per evaluation with no default, as every value of `model_check` is (ADR-0192 decision 6), or the owner fixes it is HQ-B (6.2). With R odd the median is the middle run, and from R = 3 it is neither extreme (ADR-0007 decision 5 rules out either extreme as a summary); an even R would make R = 2 report the minimum.
- **The lengths**: S is the length of the tokenised prompt and G is `model_check`'s `n`. **Slices 1 and 2 take S, G and R as inputs of the program and its host side**, which either answer to HQ-B leaves as they are; the command's document (slice 4) waits for HQ-B. Whether the owner instead fixes an evaluation prompt or lengths, so that figures of two evaluations compare, is **HQ-B**; until then each record states S and G and figures of different S or G are not compared.
- **What the figures do not establish.** The floor is applied **by proxy**: the timed generation is tied to the judged one by its G tokens only; its own logits (from another program, at `"last"`) are compared with no reference, so a kernel whose `lm_head` row at `m` = 1 differs from its row at `m` = S within the token choice is not seen. The kernels run in the program's process (ADR-0182 Boundaries), so a kernel can disturb the readings as it can the report; the figures are evaluation figures, not an objective of any run, and no tool compares them. ADR-0103's grounds are not applied; the record holds `resolution` for a reader who applies them.

### 4. Peak memory

- **On `cpu_standin`: the maximum resident set size of the timed graph-program process** over its whole life, in bytes, read by the waiter of ADR-0145 that starts the program inside its container (W3: `wait4` on that child), by ADR-0052 decision 4's Linux rule (KiB × 1024; the container is Linux on every host). One figure per run; the summary is the maximum over the R runs.
- **What it covers**: the weights and tables the program reads into its own arrays (ADR-0166 decision 2 — the program owns them), the KV cache, every activation buffer, what the kernels allocate and touch, the loaded libraries' pages. **What it does not**: the container runtime, the host-side Python (which holds the input file's bytes and, in `model_check`, the reference — ADR-0182 decision 6), the build, the page cache. So it is the process's peak, weights included, not the model's minimum.
- **A run that fails yields no figure** (ADR-0052 decision 4: a broken run's usage is of no completed work), and it ends the evaluation (decision 5). In a completed run, a reported value that is not a positive integer gives `null` (ADR-0052 decision 4), the only case of `null`.
- **GPU and NPU memory stay open**: no vendor target takes a model run (decision 2), the owner's list of units does not reach a memory figure (**owner** HQ-0090 (가)), and a device memory figure has no form the owner has stated (ADR-0194 decision 4). The integrator's note in HQ-0090 says it is asked separately when needed; this record does not ask it, since nothing needs it before a vendor target has `model_run` true.

### 5. The quality floor

- **One evaluation is**: `model_check`'s whole check on its document (its steps, its verdict, unchanged); then, only if the check reached a verdict, `match` or `no_match`, the R timed runs. Any other outcome of the check ends the evaluation with that outcome and no figure.
- **A timed run that fails** — a failed build, the time limit, a status other than 0, a report or waiter line of the wrong form, an interval of 0 ns (a rate would be undefined; the clock did not advance across a pass) — **ends the evaluation with no figure**, as an outcome of its own carrying the failure as `model_forward_container`'s outcomes carry it (ADR-0182 decision 8): a record of fewer than R runs would be another measurement than the one asked. The time limits are the user's, as `model_check`'s are.
- **One binding throughout**: the command derives the binding (ADR-0189) before it calls `model_check` and again after the last timed run, and the timed runs use the first; if the two differ, the evaluation ends with no figure, as an outcome of its own. A run may be in progress (ADR-0189 decision 7), and its incumbent is the minimum (ADR-0189 decision 2) over attempts whose set only grows, since the journal is only appended to, so it never returns to an attempt it left, so two equal derivations mean `model_check`'s own derivation, made between them, named the same kernels.
- **Tokens tie the two programs**: each timed run's G selected tokens must equal the check's `executor_tokens`. A timed run whose tokens differ ends the evaluation with no figure, as an outcome of its own: its figures would be of a generation nobody judged (a kernel may round differently at `m` = 1 than at `m` = S in the prefill's `lm_head`, and a nondeterministic kernel may differ at all).
- **The verdict is kept with the figures, and gates their use**: figures of a `no_match` evaluation are recorded with `verdict` `no_match` (a failed evaluation is information, FR-6), and a reader does not present them as the code's performance or compare them with figures of a `match`. Only figures with `verdict` `match` meet the owner's floor.
- **Out**: perplexity and evaluation data (**owner**, HQ-0088 ④ as it is); any second quality predicate.

### 6. The form put to the owner (D23) — not decided

**Nothing in this section is decided or implemented until the owner answers.** It is the concrete content of two owner questions: **HQ-A** (`data-plane-schema-change`: 6.1, 6.3, 6.4 as its ①, ②, ③) and **HQ-B** (`owner-decision`: 6.2).

**6.1 Given whole-LLM code (OD-33 ①'s remainder; HQ-A ①).** (a) **Not now** (recommended): the first slices evaluate the model built from run kernels (decision 2); the form of a given whole program is asked by the task that first needs it, with the vendor program it would be. (b) **Now, as a program of the graph program's interface**: one C source file that implements the graph program's command line, input file and report (timed form included), stored as a blob as ADR-0200's bundle is, built with the target's flags and run in its place; the judged generation stays `model_check`'s, and the tokens tie (decision 5). The costs of (b): the interface is a call plan over kernel libraries (`<input file> <library> …`), so a given program either dispatches to the run kernels it is handed — then it is hardly whole-LLM code — or ignores them; either way the floor reaches it **by proxy only**: `model_check` judges the generation of the run kernels on `model_forward.c` (it needs a run for every call site and cannot change, ADR-0193 decision 5), and the given program is tied to it by its tokens; so an evaluation of given code still needs a binding of runs. Its record needs members 6.4 lacks (the blob's hash, a `program` value other than `"graph"`), which (b) would approve with it. The interface becomes a contract users write to, so its layout freezes; a vendor program (QNN, CUDA) cannot meet a CPU file interface without more.

**6.2 The lengths (decision 3; HQ-B).** (a) **The user's per evaluation** (recommended): S from the prompt, G = `n`, R (odd, decision 3), all with no default and stated in the record; figures of different S or G are not compared. **6.3 The key of LLM-wide code (OD-33 ⑥'s remainder; HQ-A ②).** The frame has none: a model has no op_signature, and `hw_profile` alone does not say which model or code was evaluated.
- (a) **`hw_profile` and a model identity, in the record, with no index** (recommended): the `hw_profile` key shared by every bound run (an evaluation whose bound runs have more than one `hw_profile` key is refused before the long work), and the evaluation document states the `hw_profile` record of the machine it runs on, in the form an instance states one (ADR-0018 decision 2, ADR-0076), so that the command refuses an evaluation whose stated key differs from the runs' — the figures are then of the machine the key names, as far as the user's statement goes (no probe derives a `hw_profile` from a machine today); the model identity `{"config_sha256", "tokenizer_sha256", "weights_sha256"}`, the SHA-256 of the model directory's `config.json` bytes, of its `tokenizer.json` bytes (the file `model_check`'s tokenizer reads, ADR-0192 decision 4; the tokenizer's other files in the directory are not hashed, and the input itself is fixed by `prompt_token_ids`) and of the concatenation of its safetensors files' bytes in name order (the files `hilclaw.model_files` reads; a shard index file is not hashed, the shards are; the directory stays outside the data plane, **owner** HQ-0084 ②); the code identity is the binding (each call site's run id and incumbent attempt). - (c) A model name the user gives (for example `llama-3.2-1b`) in place of the hashes.

It is a frame change: a further file of a key directory, which ADR-0004 decision 5 leaves to OD-20 and OD-7, written by a command that is neither the promotion step nor the creator of the directory named there.

- (c) A new fourth top-level directory `evals/<eval_id>.json` (ADR-0004 decision 1 requires a record for it; it has no layout stamp of its own).
- (d) **No data plane**: the members below printed as one JSON line on standard output, as `model_check` answers (ADR-0192 decision 7). It loses retrieval (FR-13), audit (NFR-2), progress comparison across evaluations (FR-19 ①) and reuse (FR-18): the figure lives only where the owner keeps the line.

**Which evaluations leave a line.** Under (a) to (c): (가) **only an evaluation that reached figures** (`verdict` `match` or `no_match`); one that ends earlier — the check's other outcomes, a failed timed run, a binding that moved, a token tie that fails — leaves no line, and its outcome is told on standard output only, as `model_check` tells it (recommended: the record is of figures, and those outcomes are failures of a command, not of the code's performance); (나) every evaluation whose check reached a verdict leaves a line, with a member `outcome` (the command's outcome name); one that ends before the verdict (the document, the model files, the key, the tokenizer, a build, the container, the reference) is told on standard output only, since members such as `prompt_length` and the compiler's version line may not be known then. | `peak_memory_bytes` | integer ≥ 1 in bytes, or `null` | the maximum of the integer entries of `run_memory_bytes`; `null` only when every entry is `null` |

- **Units**: times are ns, named with `_ns`, and integers except `decode_time_per_token_ns`, a mean of a run's decode intervals and so a number; rates are tokens per second; memory is bytes. The approved open list "측정 단위" (DRIVER §3) is the `unit` of `sim.run` and `board.run` results and reaches `intervals` and `resolution` only (**owner** HQ-0090 (가)); it does not reach this record, so no `unit` member is given and a later non-ns time here would be a frame change.
- **The summaries are derivable** from `pass_ns`, `run_memory_bytes`, S and G; they are stored so that a reader needs no rule, and a validator checks them against the raw members.
- **Readers**: one validator, strict on `schema_version`, members and types; a line it refuses is reported, not skipped silently.
