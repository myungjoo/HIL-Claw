The first `STATE.json` (`round` 0) is the first write of the round-0 turn into a fresh run directory (ADR-0120 decisions 2 and 4). ## Decision

A sentence is **cited** when a source is named with it. Every other sentence is **this record's own**.

### 1. Scope

- **The runs of ADR-0120 decision 1**, driven by the turn loop through `hilclaw.turn_start` (ADR-0122 decision 1), and their data repository's local checkout, the data root. Resumed, continued or branched runs (OD-8 ①) and every other run are outside; nothing here is required or allowed of them.
- **The commits answered**: the commit of a round end, made in its turn or owed after a death. Not answered: a commit of a turn that ends no round (decision 8).

### 2. (a) The actor and the means: the Round-Manager, through the tool `run.commit`

- **The Round-Manager makes every commit this record answers (decision 1), by calling the tool `run.commit` of decision 4 through the package's MCP front**, naming its run by `run_id`. No sub-agent, neither the turn loop nor the start function makes such a commit, and the Round-Manager makes it by no other means, Bash included. Who would make a commit of decision 8's open case, and whether a hook does anything with commits (PLAN P2-4), is not decided.
- **W1 (C2) under both readings.** For the commits answered here the manager is the one committer, which reading (i) asks; and within a Round no sub-agent commits, which reading (ii) asks. The loop's step 1 of decision 6 only reads.
- **Why a tool, not the model's own steps.** What the commit must keep — the torn-tail removal (ADR-0006 decision 6), no temporary file (ADR-0013 decision 3), only the run's paths, the rule of an owed round end — is done by code, not by the model's reading of a `git status`. ADR-0124 already gives the Round-Manager typed tools for `STATE.json`; this is one more, and agents call tools through the MCP front (cited: ADR-0010 decision 3). The commit is made by the server process below the front, so the session needs no Bash and no place of the run (ADR-0123 decision 2 unchanged).

### 3. (b) When

- **At the end of a round**: right after the write that ends the round (ADR-0012 decision 6), as the last act of the turn before its session ends (ADR-0118 decision 2 (i)). Nothing is written into the run between the write and the call. This is C3's "STATE.json 갱신 … → commit" and UC-3 step 2's commit of every round.
- **At the entry of every turn**: as its first step, before `STATE.json` is read, to make a commit that a death left owed (decision 5).
- **The first `STATE.json`** (ADR-0120 decision 2) gets no commit of its own: it ends no round. It enters the history, with `instance.json` and the rest of round 0, in the commit of the end of round 0, which holds them as they are then.
- **A run that is over gets a commit**: the write that ends its last round holds `"over"` (ADR-0121 decision 3) and is committed like every round end, in the same turn. If a death leaves that commit owed, decision 6 starts the turn that makes it. The write of `"over"` that ends no round (ADR-0121 decision 3, second case) is a turn of ADR-0118 decision 2 (ii) and is not committed by this record (decision 8).

### 4. (c) What the commit takes in: the tool `run.commit`

**A round end is owed** when the run's `runs/<run_id>/STATE.json` in the working tree is valid at version 1 (ADR-0012 decision 6) with `round` *W*, and either the commit `HEAD` holds no `STATE.json` for the run and *W* ≥ 1, or it holds one, valid at version 1, with `round` *H* and *W* > *H*. Then the rounds *H* to *W* − 1 (0 to *W* − 1 without a committed file) ended after the last commit (cited: ADR-0012 decision 3). A repository with no commit yet holds no file in `HEAD`, and the commit made is its first. No commit message, author or other trace is read for this; only `round` is.

| Tool (MCP name) | Request | Result | Failure kinds |
|---|---|---|---|
| `run.commit` (`mcp__hilclaw__run_commit`) | `run_id` | `committed`: a *boolean* — whether a commit was made | `invalid_request`, `no_data_root`, `no_repository`, `commit_refused`, `commit_not_made` |

- **The request is exactly `run_id`**, with the meaning and form of ADR-0015 decision 4; any other member is `invalid_request`. The data root comes from the data-root source and never from the request (cited: ADR-0015 decision 3). The name follows the rule of `hilclaw/tools.py` and its MCP name that of ADR-0010 decision 4.
- **Nothing owed**: no commit, `committed` false, nothing written. This holds for a run directory without `STATE.json` that `HEAD` does not hold either (a fresh one, or none), and inside a round (*W* = *H*). So the call is safe at every entry and repeats without effect.
- **Owed**: in this order, (1) a torn tail of `runs/<run_id>/events.ndjson` is removed, exactly those bytes (cited: ADR-0006 decision 6; the same removal its writer makes); (2) one commit is made that holds, against `HEAD`, every new or changed file below `runs/<run_id>/` and the case files `case-<run_id>-<RRRR>.json` of the rounds *H* to *W* − 1 in the key directory of the run's instance, where they exist (C4; ADR-0072 decision 1 — the path is formed from the keys of `instance.json`, with no listing); (3) `committed` true. The changes of no other path go into the commit, and whatever else the working tree or the index holds stays as it is.
- **What the case files need**: a case file is taken only if it exists when the commit of its round is made. One written after that commit joins no commit under this record, since the next commit begins at the new *H* — against ADR-0072 decision 1's "same commit". So the promotion step writes it before the round's commit is made. Written after the write that ends the round, it is lost to a death between the two writes as well: the next turn goes on with the next round, and no step of this scope writes it then. The order that avoids both is the promotion before the write that ends the round — the order of the agreed sketch of #4 §3c (C3), "promote … → db/" before "STATE.json 갱신 … → commit"; choosing it is not done here: the order itself is OD-23's, and whether every round is promoted is ADR-0072's open point (Boundaries).
- **`best.json` and `technique_stats.json`** of the key directory, which ADR-0004 decision 5 puts in "the same commit as the round it promotes", are **not taken in** by this record: their content and their write for a round are open (OD-20, OD-7), and, shared by every run of the key, they may hold another run's change, which a commit of this run would take. The record that defines their write for a round adds them to the round's commit. The key record files of the directory are not taken in either: they are written once, by whatever creates the key directory (ADR-0004 decision 5; ADR-0014 decision 3), and who commits them, and when, is open (OD-26).
- **Never taken in**: a file whose name ends with `.tmp` — every temporary-file form of the data plane (Context; ADR-0013 decision 3, "Git") — whatever the ignore file says; a path the repository ignores; anything below `blobs/`, so no blob byte (C5). The commit does not inspect content: a file a writer put into the run directory against ADR-0004 decision 7 is committed, and keeping binaries out stays the writers' rule.
- **`commit_refused`**, with nothing removed or committed: the working tree's `STATE.json` is invalid, of another version or unreadable; the one of `HEAD` is not valid at version 1; *W* < *H*; a file that `HEAD` holds below `runs/<run_id>/` is missing from the working tree; `events.ndjson` is not a regular file; or an owed commit needs the key directory and `instance.json` gives none. These are states the rules of ADR-0012, ADR-0006 and ADR-0013 do not produce, and the tool repairs nothing (as ADR-0012 decision 6 has a reader do). **When each is checked**: the conditions the rule itself needs — the two `STATE.json` files read, valid and of version 1, *W* < *H*, and a run whose `STATE.json` `HEAD` holds and the working tree does not — at every call; the others — a missing file, `events.ndjson`, the key directory — only when a round end is owed. So a call with nothing owed fails only on the first group, `invalid_request`, `no_data_root` or `no_repository`.
- **`no_repository`**: the data root is not the top directory of a git working tree, or `git` cannot be run. Committing into a repository that holds the data root lower down — the source checkout, for one — is refused by this. **`commit_not_made`**: the removal of a torn tail failed in the file system, or `git` did not make the commit; `HEAD` is as it was, and a torn tail already removed stays removed (it was no line — ADR-0006 decision 6).
- **Commit message and author**: not fixed. Nothing reads them; the rule of an owed round end reads `round` only, and the visibility of C1 (the unpushed count) is not this record's.
- **Not journaled, and no FR-10 tool**: a commit costs no limited resource and repeats without effect; it runs no experiment (as ADR-0124 decision 3 reads its four tools). It is added to `default_registry` in the source and in no other way (cited: #5 A-12 point 3). It runs the `git` program of the machine: the data repository is a git repository by C4 and D7, and A-3's boundary is its commit; no package is added.

### 5. (d) How a fresh turn learns that a commit is owed, and what follows

- **The Round-Manager's first entry step is `run.commit`**, before `mcp__hilclaw__state_read`. The tool tells by the rule of decision 4 — the working tree's `round` against that of `HEAD` — and makes the owed commit. With `committed` true or false the entry goes on with its steps as they stand.
- **If the call fails at the entry**, with any kind, the Round-Manager reports the kind in one line and ends the session. It begins no round and writes nothing further into the run (a torn tail the tool removed stays removed, decision 4) — the handling `orchestration/round-manager.md` already gives a failed read (ADR-0012 decision 6; ADR-0124 Walk-through). The reason it does not go on: a round begun on an owed round end would end in a commit that holds two round ends, and the commit point of the first would be lost. What the loop does after such a turn is ADR-0122's (decisions 2 and 3).
- **If the call fails at the end of a round**, the Round-Manager reports the kind in one line and ends the session, as it would anyway (ADR-0118 decision 2 (i)). The round end stays owed, and the next turn's entry tries again.
- **A death in a commit**: git moves `HEAD` in one step, so the commit was made or not, and the next entry finds nothing owed or makes it. A death after the torn-tail removal and before the commit leaves the round end owed with no torn tail.

### 6. Step 1 of the turn loop in P2

- **P2 is split for this scope.** Step 1 that finds P2 (ADR-0121 decision 5) applies the rule of decision 4 read-only, through a package function (Consequences, slice (1)): **P2 with no round end owed** is P2 as before — no further turn, "run over". **P2 with a round end owed** (owed P2) answers **as P4 does** under ADR-0122: a further turn before the first turn of a start and after a turn with exit status 0 that was no unchanged turn; that turn's entry makes the commit (decision 5) and then ends on `"over"` (ADR-0121 decision 3). This is the revision ADR-0121 decision 5 left to a record of ⑪.
- **The self-check**: when the first step 1 of a start finds owed P2, the check runs before that start's first turn (ADR-0125 decision 2, widened to owed P2): it is a turn due, and the check is run where a turn session is about to be spent, as that decision gives its reason. Between two turns of a start nothing runs it (ADR-0125 decision 4 (ii)), also when a start reaches owed P2 after a turn — for one, after a round-end commit that ended `commit_not_made`. A check that does not let the turn start leaves the commit owed, as it would leave a round undone in P4.
- **After a turn whose exit status is not 0**, owed P2 stops the start as P4 does (ADR-0122 decision 2), and the starter is told the failed turn; the owed commit is made at the next start's first turn. So a death between the last round's write and its commit is treated like every other death: no turn at once. ADR-0122 decision 2's "In P2 and P3 the loop returns … whatever the exit status" stays true of P2 with nothing owed.
- **After a turn that exited with 0 and began in owed P2**, owed P2 again counts as "as it found it" (ADR-0122 decision 3, widened to this state): the start stops after an unchanged turn. So such a run gets at most one turn per start.
- **If the rule cannot be applied** in P2 — the package function answers what the tool would answer there with nothing committed: `no_data_root`, `no_repository`, or `commit_refused` by the conditions decision 4 checks at every call, and by the others when a round end is owed — step 1 answers as in a state of ADR-0122 decision 4: no turn, and the starter is told which. "Run over" (ADR-0122 decision 5) is told only for P2 with nothing owed; in the order of ADR-0122 decision 5, owed P2 comes where P4 would, after the open states. The other outcomes stand.
- **The loop still writes nothing into the run** and makes no commit (ADR-0122 decision 1; decision 2 here). In P3 and in the open states of ADR-0122 decision 4 nothing changes: no turn runs, and a commit owed there stays owed until a record answers that state.

### 7. (e) What is not promised

- **The loss of the machine, the disk or the working tree before the commit** (cited: #5 A-3, "NFR-1의 보장 범위는 MVP에서 프로세스 사망·compaction까지"; ADR-0006 decision 10; ADR-0012 decision 7): what was not committed is lost, and what is recovered is the last commit. After the commit, only as far as the user pushes (#5 A-3).
- **No push**, no remote and no unpushed count: the system never pushes (cited: #5 A-3), and the visibility A-3 allows is not this record's (Boundaries).
- **What one repository cannot show**: a commit says what this one local checkout holds. Whether it was pushed, whether another clone or another machine holds other commits of the run, and whether the history was rewritten outside the system, are not shown by it and not checked here. Nor does a commit show that its content is right: the rule of decision 4 reads `round` only (ADR-0012 decision 6, what one file cannot show).
- **Two writers or two loops at once**: nothing orders two commits of one run (rest of OD-17; C-2); nor two runs, or a person's `git` command, in one data checkout at once (C-2): `git` locks the repository as a whole, so a commit may then end `commit_not_made` and stay owed for the next entry, and decision 4's "whatever else the working tree or the index holds stays as it is" is not promised then.

### 8. #5 A-3 and the turn that ends before its round ends

- **How this record reads "매 턴(=Round) 종료 시"** (C1): for a turn that ends with its round (ADR-0118 decision 2 (i)), the end of the turn is the end of the round, and the commit is made there (decision 3). The invariant and its scope otherwise stay as the owner wrote them.
- **A turn that ends before its round ends** (ADR-0118 decision 2 (ii)) — a death, a stop, a wait for the user, a gate, an error, a usage limit — **is left open**, and so is ADR-0121's own write of `"over"`, which ends no round. Whether such a turn's end, or the entry of the turn after it, commits what the run directory then holds turns on what "매 턴(=Round)" means when a turn and a round do not end together: every turn end, or every round end. ADR-0118 Boundaries read it as neither, and no record or owner sentence decides it. **This record commits nothing there and forbids nothing**: `run.commit` makes no commit inside a round (decision 4), and a record that answers the question may widen it. The driver asks the owner (DRIVER §8; owner-only, #5 A-3).

### Walk-through

| Situation | What follows |
|---|---|

| A turn dies inside round 3 (`board_done`) | The next turn: *W* 3 = *H* 3, nothing owed, no commit; it goes on with round 3 (ADR-0012 decision 3). What the dead turn wrote stays uncommitted (decision 8) |
| The last round (4 of `round_budget` 5) ends | The write holds `round` 5 and `"over"`; `run.commit` commits it; P2 with nothing owed: "run over" |
| The same, with a death before the commit | The start stops after a failed turn. At the next start, step 1 finds owed P2: the self-check runs (ADR-0125 decision 2), then a further turn; its entry commits and the turn ends on `"over"`; step 1: P2 with nothing owed, "run over" |
| A session ends with exit status 0 after the write that ends round 3, without calling `run.commit` | P4 with another `round`: progress, a further turn (ADR-0122 decision 3); its entry makes the commit |
| `run.commit` fails with `commit_not_made` at the entry | One line, the session ends, nothing written; the start stops after an unchanged turn (ADR-0122 decision 3) |
| The data root is not a git working tree | `no_repository` at every entry; no round begins |
| `events.ndjson` ends in a torn tail when a round end is owed | Those bytes are removed, then the commit is made (ADR-0006 decision 6) |
| `STATE.json.<token>.tmp` lies in the run directory | Never committed (ADR-0013 decision 3) |
| Another run's files or `db/` files of another key changed in the working tree | Not in this run's commit; left as they are |

- **Runtime acceptance items** (D16; nothing was tried, and nothing is required of the development machine). ADR-0118 item (vii) and ADR-0124 item (x) are used, not changed. **New**, numbered in the turn-session series of ADR-0118 (i) to (vii), ADR-0122 (viii), ADR-0123 (ix), ADR-0124 (x), (xi) and ADR-0126 (xii) to (xiv):
  - **(xv)** The main session of a `-p` turn session sees `mcp__hilclaw__run_commit` and may call it under the means item (vii) gets.
  - **(xvi)** On a runtime machine, the server process a turn session starts finds `git` and an author identity with which `git` makes a commit in the data checkout.
  - **(xvii)** A live Round-Manager calls `run.commit` as the first step of its entry and right after the write that ends its round.
- **The cost, plainly.** Work between two round ends is not in the history: a machine loss loses it (C1 accepts that), and a round cut short leaves it uncommitted until its round ends (decision 8). An owed last commit costs a start with the self-check's session and one turn session (NFR-5; ADR-0125 decision 2). A run whose data root is not a git working tree begins no round, and in P1 or P4 each start of it spends the self-check's session and one turn session before the entry finds `no_repository` and the start stops after an unchanged turn. A stale lock file that `git` leaves after a death makes `commit_not_made` until someone removes it; nothing here removes it. A secret or a binary that a writer puts into the run directory against ADR-0004 decision 7 enters a history that is not rewritten (NFR-2), since the commit inspects no content (decision 4). A case file can enter the history before the key record files of its directory do, if the step that created the directory did not commit them (decision 4).
