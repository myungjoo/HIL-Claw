## Decision

A sentence is **owner** where O1 to O10 is named, **cited** where another source is named, and **this record's own** otherwise. Every flag or value adopted below is either cited with what it does or marked as a provisional choice of this record with its reason.

### 1. Scope

- **One coder call of the first case** (ADR-0049 decision 1), behind `runtime.available()` and `runtime.run(scratch_root, coder_model=...)` of `hilclaw/coder_call.py`, **on Docker** (ADR-0049 "Docker first"; O3). The implementation of the seam is called *the Docker runtime* below. It runs in the process that runs the function, which for a turn session is the MCP front (O9; ADR-0141).
- **Outside**: the time limit of a call; the coder's output stream; the token record; everything under Boundaries.
- **`coder_call.call` and `coder.run` keep their contracts**: the request, the result, the failure kinds and their order (ADR-0126 decision 3, ADR-0136 decision 5, ADR-0141 decision 2) are unchanged.

### 2. (a) What `runtime.available()` checks

- **It returns true exactly when a `docker` program is found on the `PATH` of the process that runs the function and `docker version --format '{{.Server.Version}}'`, started from it, exits 0 within a short time limit and prints a non-empty line** (D12). Any other outcome — no `docker`, a start that fails, another exit status, an empty output, the time limit — returns false. The value of the limit is the code slice's.
- **Why the server's version**: a Docker client alone starts no container; the server section is the Engine's (D12). So `no_container_runtime` means "no container can be started here", which is what ADR-0049 decision 2 needs: without the boundary there is no call. Not verified: what `docker version` does when no daemon answers (D12); item (lxix).
- **It checks nothing else**: not the image, not the token. A missing image or token is found by `run` and reported as a start that failed (decision 7), after a scratch was made and before any container exists. What happens beyond `no_container_runtime` — asking the user, installing — stays OD-8 ㉝ (가).
- The Docker client talks to whatever daemon the environment selects (`DOCKER_HOST`, `DOCKER_CONTEXT`); the Docker runtime sets neither and reads neither (ADR-0049 L11 unchanged; ADR-0144 Boundaries ① (라) for the build and run containers).

### 3. (b) The container: start and removal (P1, P2, P4)

**The command.** The Docker runtime starts one process, `docker run` in the foreground (D6), from an argument vector and never through a shell, with exactly these options:

| Option | What it does (cited) | Why here (own) |
|---|---|---|
| `--name hilclaw-coder-<random>` | Names the container (D8) | So that the runtime can remove it by name when the wait is cut off. The random part is new per call; the prefix answers nothing of ㉝ (나) |
| `--rm` | Removes the container when it exits (D8) | P4 for the normal end |
| `--pull never` | Never pulls the image (D9; the default is `missing`) | The runtime installs or updates no image (O5: "only after approval"); a missing image is a failed start, not a download. As ADR-0144 decision 5 for the build and run containers |
| `--mount type=bind,source=<scratch>,target=/scratch` | A bind mount, read-write by default (D7) | **The one writable host path** (P2). `<scratch>` is the absolute host path of the scratch; it appears in this argument of `docker` only, never in the prompt (ADR-0126 decision 5). `/scratch` is a provisional name |
| `--workdir /scratch` | The working directory inside (D7) | The coder's working directory is the scratch (ADR-0126 decision 5) |
| `--user <uid>:<gid>` | Sets the user of the command (D11; the default is root) | The numeric ids of the process that runs the function, so that the coder can write in a scratch made with mode 0700 for that user, and that user can remove what it wrote (ADR-0049 L6, P4). Not root, so no root inside |
| `--entrypoint=` | Overwrites the image's entrypoint (ADR-0144 E12) | The program started is the coder's `claude` itself, so no program of the image runs before it or changes its environment — for example by setting a credential source of C4. As ADR-0144 decision 6 |
| `--env HOME=/tmp` | Sets a variable (D10) | A user given by number may have no home in the image; Claude Code keeps its configuration under `~/.claude` (C6), which is then in the container's own file system and goes with it (ADR-0049 D2). Provisional; the image must keep `/tmp` writable for every user (decision 4) |
| `--env CLAUDE_CODE_OAUTH_TOKEN` | Passes the value of that variable from the environment of the `docker` process; unset inside if unset there (D10) | The sign-in (decision 5, O10). The value is in no argument |
| `--env DISABLE_UPDATES=1` | Blocks every update of Claude Code (C8) | Claude Code "auto-updates itself inside the container by default" (C7); an update would change the coder's toolchain without the user's permission (O5) |
| `--cap-drop ALL` | Drops all Linux capabilities (D11) | "No added privilege" (P2), and D11's best practice; the coder needs none to write files and build and run C |
| `--security-opt no-new-privileges=true` | No process inside gains privileges (D11) | The same |
| the image named by decision 4, then the command of decision 6 | — | — |

- **Never given**: a second `--mount` or `--volume`, a mount of the Docker socket or of any other host path, `--privileged`, `--device`, `--cap-add`, `--network host`, `--pid host`, `--ipc host`, `--userns host`, `--env-file`, or any `--env` beyond the three rows above. So **no checkout is shown inside** (whether one should be is ㉝ (다), open) and no other variable of the runtime's environment reaches the container (D10). `--network` is not given: the container has Docker's default network and "can make outgoing connections" (D11), which the coder needs to reach Anthropic (ADR-0049 L4, unchanged). This is where it differs from ADR-0144's build and run containers, which get the `none` network.
- **Not taken**: `--read-only` (the container's own file system need not be read-only for P2, which is about the host); `--init`; resource limits (OD-14, ADR-0049 L7).
- **That these options give P1 and P2 is this record's expectation from D7 to D11 and is not verified** (ADR-0049 L1, L2): item (lxxii). P1 holds as far as every process of the coder is started from the container's command; whether a process can outlive the container is ADR-0049 L1's item.

**Removal (P4).** Whatever the outcome, `run` does not return before the container of the call is gone:

- after `docker run` returns, the container has been removed by `--rm` (D8) — **not verified** that this is complete when `docker run` returns, so `run` then also requests `docker container rm --force` by name, and a container that no longer exists counts as gone. **How `run` tells "no longer exists" from a removal that failed is the code slice's**: what `docker container rm --force` exits with and prints for a name that names no container is on no page read (item (lxxiii));
- when the wait is cut off in the function's process (an interruption or an exception), `run` requests `docker container rm --force` by name (D8: "uses SIGKILL") before it lets the interruption go on;
- **a container `run` cannot show gone** is a call that did not end normally: `run` returns no `0` (decision 7), so the function brings nothing in (ADR-0126 decision 3) and removes the scratch. A killed function process leaves the container (ADR-0049 L9; ㉝ (나)).

### 4. (c) The image: what it holds, and how the runtime is told which

- **What it must hold for the first case** (ADR-0049 L6): (i) the Claude Code program as `claude` on the image's `PATH`, of a version that accepts every flag of decision 6; (ii) clang and the C library and headers it needs to build and run a C program of the first case (the coder builds and tries its kernel inside — ADR-0049 L6); (iii) a POSIX shell for the coder's Bash tool; (iv) a `/tmp` writable by every user (decision 3); (v) no entrypoint the start depends on (decision 3). **It must hold no credential and set no credential source** — no `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `apiKeyHelper` or cloud-provider selection (`CLAUDE_CODE_USE_BEDROCK` and the like), each of which ranks above `CLAUDE_CODE_OAUTH_TOKEN` (C4) and would bring another provider or API cost (C-7 ②) —, and no Claude Code user or project settings, hooks, MCP servers or `CLAUDE.md` of its own; managed settings in the image act on the session whatever `--setting-sources` says (C11, not verified) and are the image's responsibility.
- **How the runtime is told**: the user names the image in the environment variable **`HILCLAW_CODER_IMAGE`** (a provisional name) of the process that runs the function, as an image reference Docker accepts — source (c) of ADR-0144 decision 5, chosen there for the build and run image for the reasons stated there, which hold here unchanged. The Docker runtime reads it at each `run` and refuses a value Docker would read as an option, as `hilclaw.standin_image.read_image` does; **the package holds no default image**. Unset or empty, the call is not started (decision 7). For a turn session it reaches the MCP front as `HILCLAW_STANDIN_IMAGE` does today: the turn loop copies a non-empty value into the server entry's `env`.
- **The runtime never pulls, builds or updates an image** (`--pull never`; O5). An image that is not on the machine is a failed start (D6: 125, not verified for this case — item (lxxiii)).
- **Not decided** (open): which base image, registry, Dockerfile or package versions — **no concrete image is adopted** (A-13: that would be a new external dependency of the runtime); whether the image is pulled or built on the machine, by whom, and when it is updated, and what P4 does with a built one (O3 speaks of "pulled images" only; O5 lets the runtime install or update one only after the user's permission; which part asks is ㉝ (가)); whether the image identity is recorded (OD-14 ① (나); no data-plane member is added); whether it is the image of the build and run containers (OD-14 ① (나); ADR-0144 decision 5 left it open, and the coder's image needs `claude` and the network, which that image need not have).

### 5. (d) How the sign-in reaches inside — the owner's decision (O10)

- **The means is the owner's** (O10, answer (a) to HQ-0053): a token that the owner creates with `claude setup-token` and gives to the runtime in the environment variable **`HILCLAW_CODER_OAUTH_TOKEN`**; the runtime passes it into each coder container as **`CLAUDE_CODE_OAUTH_TOKEN`** and writes it to **no file, argument or log**; the host turn session keeps its `/login` login (O7). Cited of that token: it "authenticates with your Claude subscription and requires a Pro, Max, Team, or Enterprise plan" and "can only make model requests" (C3), so the coder's usage is plan usage and no API cost arises (C-7 ②); it is the form the documentation gives for "environments where interactive browser login isn't available" and for a container (C3, C7).
- **What O10 does not answer** (O10's own words): the credential form of unattended runs on the host (O8; OD-18 sub-question ⑯ (다)), which stays open. This record decides nothing of the turn session's credential.
- **How the Docker runtime passes it** (own, within O10): it puts the value of `HILCLAW_CODER_OAUTH_TOKEN` into the environment of the `docker` child process only, under the name `CLAUDE_CODE_OAUTH_TOKEN`, and passes that name with `--env` and no value (decision 3; D10), so the value is in no argument of `docker`. Unset or empty, the call is not started (decision 7). The runtime never creates the token — `claude setup-token` is a browser authorization of the user (C3) — and puts it in no prompt, report, message or exception text.
- **How it reaches the process that runs the function** (own). For a turn session that process is the MCP front (O9). The turn loop's server entry is a file (Context), so the value must not be copied into it as the image's is. **The turn loop writes into the entry's `env` the member `HILCLAW_CODER_OAUTH_TOKEN` with the text `${HILCLAW_CODER_OAUTH_TOKEN}`** — the reference, never the value — and only when its own environment holds a non-empty value of that variable; the session, which gets the turn loop's environment, expands it when it starts the server (C13). The Docker runtime treats a value that is that unexpanded text as unset (C13: an unset reference is kept as-is). **Not verified**: that the expansion of C13 applies to a file named by `--mcp-config`, as it is documented for `.mcp.json` (item (lxxiv)). If it does not, the call is not started for want of a token, and no token is written anywhere; the remedy is a later record, not a value in the file.
- **No `ANTHROPIC_API_KEY` or `ANTHROPIC_AUTH_TOKEN` reaches inside**: they would rank above the token and cost API money (C4; C-7 ②), and only the three variables of decision 3 are passed (D10). The image must not set them (decision 4).
- **Why the host variable has another name than `CLAUDE_CODE_OAUTH_TOKEN`** (this record's reading, from C4, of why the name put to the owner differs; not the owner's stated reason): set where the turn loop runs, that name would change the credential of the turn session's own `claude -p` (C4: it ranks above the `/login` credential of O7), which O10 keeps and O8 leaves open.
- **What becomes readable inside** (ADR-0049 L5, L8): the token, in the environment of every process of the container, to a coder with a shell; with L4, a coder can send it wherever the network reaches, or write it into the scratch, from where the bring-in takes nothing but admitted names below `output` (ADR-0055 decision 5) — but an admitted file can hold it (L8). **Nothing of the host's login** — the Keychain entry or `.credentials.json` of C2 — is readable inside.
- **What becomes readable outside**: the value is in the environment of the turn loop, of the turn session's `claude -p`, of the MCP front and of the `docker` child, and of every other process started with those environments (hook processes among them). **No agent of a first-case turn session has a shell** — the main session's built-in tools are `Agent` and those the agents' lists hold (ADR-0139 decision 4), and the coder-driver has no Bash (O9) — **but that does not keep the value from them**: the bare `Read` and `Grep` are pre-approved in a turn session (ADR-0139; `hilclaw/turn_permissions.py`), so on Linux an agent with them can read a process's environment under `/proc` (not verified, no page read; item (lxxi)) — as the same tools can already read the host login file of C2. While the container exists, its configuration, the passed variable included, is held by the Docker daemon, so whoever can reach the daemon may read it, and whether the daemon keeps it on the host's disk is on no page read (item (lxxiii)). Neither is a file, argument or log written by the runtime (O10); both are costs of passing the token by environment, the owner's means.
- **The same on every platform of C-7 ①**: the host's login is kept differently on macOS, Linux and Windows (C2), and this means uses none of them. What differs per platform is only how the user sets the variable for the runtime, which is not decided here.
- **Under O5**: the token is something the user must create and give; the runtime cannot. A call that finds none is not started and the runtime tells the user what is needed (decision 7, `coder_not_started` with its message); how a run then waits for the user is ㉝ (가), cited as O5 says ("The request stops the run for the answer").
- **Not verified**: that the token authenticates the coder's `claude -p` in the container under the user's Max plan; whether and how it can be revoked before its year ends (the `authentication` page names `/logout` as revoking "the credential this sign-in wrote", which is not said of a `setup-token` token); what the session does when it has expired (C12: a non-zero exit is expected). Item (lxx).

### 6. (e) The coder's `claude -p` command

The command of the container is, as one argument vector (provisional order):

`claude -p <PROMPT> --model <coder_model> --permission-mode dontAsk --allowedTools Bash,Read,Edit,Write --setting-sources project --no-session-persistence`

- **The prompt is passed as the argument of `-p`**, not on standard input: `docker run` is started without `--interactive`, so the container has no standard input to read (C12 names stdin as an alternative and caps it), and the prompt is short. The argument reaches `claude` without a shell. O10's "no argument" is of the token; the prompt holds none (below).
- **The prompt is one fixed text of the package, the same for every call**, held by the module of the Docker runtime. It holds **no host path, no run id or tuple, no model and no credential**. It tells the coder, in the words of the code slice: to read the spec in `spec.json` of its working directory (ADR-0126 decision 5); to write the complete source of the kernel as files directly in the directory `output` of its working directory, creating it, under the rules a file must meet to be taken — the admitted names, flat, whole files, the bounds (ADR-0055 decisions 4, 5; ADR-0008 decision 7); that it may build and try its code with the tools of the image inside its working directory; and that nothing outside `output` is kept. **Fixed here**: the form (one text, argument of `-p`), what it must not hold, and those four contents; **the wording is the code slice's**. ADR-0126 decision 5's "The function composes that prompt" is read as "the package composes it on the function's behalf".
- **The model** (ADR-0136 decision 7): `--model <coder_model>`, the value `runtime.run` receives, unchanged. `--model` accepts "a model's full name" and overrides the `model` setting and `ANTHROPIC_MODEL` (C1), so no setting of the image can replace it. Not an environment variable: C1 makes the flag win over one.
- **The permission mode: `dontAsk`**, with `--allowedTools Bash,Read,Edit,Write`. In `dontAsk` "anything that would prompt is denied" and "the session never waits for input"; reads inside the working directory and pre-approved tools run (C9); `Bash` "Matches all Bash commands" (C10). **This record expects** that the coder can then read the spec, write its files and build and run its code without a prompt, and that every other tool that needs approval is denied; it is an expectation, not a cited consequence. A redirect in a command is checked "as if Claude wrote or read that file directly", and "A target outside the working directories needs your approval" for an input redirect, as a target that "starts with `~` or contains a glob character" does for an output one (C10, `permissions`, "Redirections"); in `dontAsk` such a command is denied. Item (lxx). **No web tool is pre-approved**; this is no answer to OD-12 or OD-16, and the coder's shell still reaches the network (ADR-0049 L4).
- **The reading of O6's "never with a bypass flag".** Its words are said of the self-check's "one throwaway `claude -p`", and (b-1) of the owner's check by hand; **they do not name the coder**, so by their words they do not bind its session. No owner sentence found permits a bypass flag for the coder either, and the documentation offers one for "Run fully unattended inside a container" (C9). **This record reads the question as unclear and respects O6**: the coder's session gets **no** `--dangerously-skip-permissions`, `--allow-dangerously-skip-permissions` or `--permission-mode bypassPermissions`. `dontAsk` with an allowlist is the form the documentation gives for "Run in CI with an exact allowlist" (C9) and the one O6 (b-1) names; ADR-0139 takes the same reading for turn sessions as its own choice. **The cost**: what `dontAsk` denies that the coder needs is not known (item (lxx)); `bypassPermissions` would also write to protected paths (C9), which the coder does not need.
- **No `--bare`**: bare mode reads neither `CLAUDE_CODE_OAUTH_TOKEN` nor any OAuth credential (C5), so the coder could not sign in by O10's means. **The cost, plainly**: the documentation announces `--bare` as the future default of `-p` (C5), and no page read names an option that switches it off (ADR-0054 K11); a Claude Code release that makes it the default would stop every coder call from signing in. `DISABLE_UPDATES=1` (decision 3) keeps the image's version until the image is changed, which O5 puts behind the user's permission.
- **No host settings, hooks, servers or instructions reach the session, by construction**: a session without `--bare` loads what is "configured in the working directory or `~/.claude`" (C6), and inside the container the working directory is the scratch, holding only `spec.json` at the start (ADR-0049 decision 4), and `~` is `/tmp` of the container's own file system (decision 3). Nothing of the host's `~/.claude`, of either checkout or of the turn session's directory is mounted (decision 3). **`--setting-sources project`** additionally leaves out user settings an image might carry (C11), as the self-check and the turn session do (ADR-0057; ADR-0139 decision 7); managed settings cannot be left out by it (C11). **`--no-session-persistence`** keeps the transcript off the disk (C11); it would otherwise go to the container's own file system and be removed with it.
- **Not used**: `--tools` (the allowlist and the mode decide what runs; restricting the built-in set further is OD-12 / OD-16 matter), `--strict-mcp-config` and `--mcp-config` (no server is given to the coder; whether a coder is given any tool stays OD-23 — ADR-0010 Consequences), `--max-turns` and any time limit (OD-14), `--output-format` and `--verbose` (the output stream, OD-23 ① (라)), `--append-system-prompt`.
- **The coder's standard output and standard error** are not passed to the standard output of the process that runs the function, which the MCP front uses for its protocol (ADR-0141), and are kept nowhere — the interim behaviour until the record on the output stream (ADR-0055 L7 already says the coder's whole output is not kept). Where they go meanwhile is the code slice's.

### 7. (f) What `runtime.run` returns and what it raises

| Situation | `runtime.run` | `coder_call.call` (cited: ADR-0126 decision 3) |
|---|---|---|
| `HILCLAW_CODER_IMAGE` or `HILCLAW_CODER_OAUTH_TOKEN` unset, empty or refused (decisions 4, 5) | Raises `CoderNotStartedError` naming which variable — never its value — before any process | `coder_not_started` |
| `docker` cannot be started | Raises `CoderNotStartedError` | `coder_not_started` |
| `docker run` exits 125, 126 or 127 (D6: the daemon's error — a missing image under `--pull never`, a mount refused —; the command cannot be invoked; `claude` not found in the image) | Raises `CoderNotStartedError` with the status | `coder_not_started` |
| `docker run` exits with any other status, and the container is gone | Returns that status: the exit status of the coder's `claude -p` (D6). `0` is success, any other is a failed run (C12), `143` a SIGTERM (C12) | `0`: the bring-in; otherwise `coder_not_ended` |
| The container cannot be shown gone (decision 3) | Returns a status other than `0`, fixed by the code slice | `coder_not_ended` |
| The wait is cut off | Removes the container by name, then lets the interruption go on | The function's own handling (ADR-0126 decision 3) |

- **The ambiguity, plainly**: a `claude` that itself exits 125, 126 or 127 would be read as not started. Whether Claude Code ever exits with those values is on no page read (item (lxxiii)); a call so misread brings nothing in, as `coder_not_ended` would.
- **The row "cannot be shown gone" is this record's reading** of ADR-0126 decision 3, which removes the container before the bring-in (P4): a coder that exited 0 is then reported as not `0`, so nothing is brought in from a scratch a container may still write.
- **This is item (xiv) of ADR-0126 narrowed**: the status `docker run` gives back is the coder's own (D6), and only `0` leads to a bring-in.

### Walk-through

| Situation | What follows |
|---|---|
| A first call on a Linux machine with Docker, the image and the token set | The coder-driver calls `coder.run` (O9). `available()` gets the server's version. `call` makes the scratch and calls `run`, which starts, with `CLAUDE_CODE_OAUTH_TOKEN` in the child's environment only, `docker run --name hilclaw-coder-… --rm --pull never --mount type=bind,source=<scratch>,target=/scratch --workdir /scratch --user 1000:1000 --entrypoint= --env HOME=/tmp --env CLAUDE_CODE_OAUTH_TOKEN --env DISABLE_UPDATES=1 --cap-drop ALL --security-opt no-new-privileges=true <image> claude -p <PROMPT> --model claude-opus-5-5 --permission-mode dontAsk --allowedTools Bash,Read,Edit,Write --setting-sources project --no-session-persistence`. The coder reads `spec.json`, builds and tries its kernel, writes `output/kernel.c` and exits 0. `docker run` returns 0, the container is gone, `run` returns 0, and the bring-in takes `kernel.c` |
| No daemon answers | `available()` is false; `no_container_runtime`; nothing is created (ADR-0126 decision 3) |
| The image is not on the machine | `docker run` fails without pulling (D9); 125 (not verified) → `coder_not_started`; the scratch is removed. Installing the image needs the user's permission (O5; ㉝ (가)) |
| The user has not set the token | The turn loop writes no reference; `run` raises before any process → `coder_not_started`, naming the variable; the scratch is removed. Creating one is the user's act (C3, O10) |
| The session does not expand the reference | The front sees the text `${HILCLAW_CODER_OAUTH_TOKEN}`; `run` treats it as unset → `coder_not_started` (item (lxxiv)) |
| The token has expired or been revoked | The coder's `claude -p` fails to authenticate and exits non-zero (C12, expected; item (lxx)) → `coder_not_ended` |
| The coder tries to write a file of the source checkout | No checkout is mounted; the write lands in the container's own file system, if anywhere, and disappears with it (ADR-0049 D2, G1 under its conditions) |
| The coder runs `docker` or `sudo` inside | No Docker socket is mounted; no capability, no new privileges (D11). Neither reaches the host (expected; item (lxxii)) |
| The `coder.run` call is cut off while the coder runs | If the front's process is interrupted, `run` removes the container by name; if it is killed, the container and the scratch remain (ADR-0049 L9; ㉝ (나); ADR-0141 item (xiii) as narrowed there) |

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| (a) | `docker info`, or only "a `docker` on the `PATH`" | `docker info` reads more than is needed and its failure output is on no page read either; a client without a daemon starts no container (D12) |
| (a) | `available()` also checks the image and the token | `no_container_runtime` would then mean three things, and ADR-0049 decision 2 is about the boundary only |
| (b) | `--pull missing` (the default) | Downloads an image without the user's permission (O5) |
| (b) | No `--user`; the image's user | On Linux the scratch is mode 0700 for the user who runs the function; another uid could not write it, and root (D11's default) could leave files that user cannot remove (ADR-0049 L6) |
| (b) | `--network none`, as for the build and run containers | The coder must reach Anthropic (ADR-0049 L4); restricting the network further is OD-12 |
| (b) | The image's entrypoint kept | A program of the image would run before `claude` and could change its environment, a credential source of C4 among it |
| (c) | A default image in the package, or a Dockerfile in the repository | Adopts a concrete base image and packages: a new external dependency of the runtime (A-13), and O5 puts every image change behind the user's permission |
| (c) | The image named in `instance.json` | A data-plane member (A-13); recording the image is OD-14 ① (나) |
| (c) | `HILCLAW_STANDIN_IMAGE` for the coder too | Would decide that the two images are one, which OD-14 ① (나) leaves open; the build and run image need not hold `claude` (ADR-0144 decision 5) |
| (d) | The other means weighed in HQ-0053 (mounting or copying the host's `~/.claude/.credentials.json`, a persistent login volume, a login per call, an API key) | Not taken: the owner chose (a) (O10). The reasons put to the owner are in HQ-0053's question |
| (d) | The token's value copied into the server entry's `env`, as the image is | The entry is a file; O10: "writes it to no file" |
| (d) | The front inherits the token from the session's environment with nothing in the entry | Whether a stdio server gets the session's environment beyond its `env` is on no page read (C13), and the turn loop's entry today copies nothing else; the reference is documented (C13) |
| (e) | `--dangerously-skip-permissions` (C9's container row) | The reading of O6 (decision 6); `dontAsk` gives the coder what it needs without it |
| (e) | `acceptEdits` | Auto-approves edits and some file commands only; any other Bash command would need a rule, and in `-p` a prompt cannot be answered |
| (e) | `auto` | A classifier model reviews each action, spending plan usage on another model, and what it blocks for a coder is not known |
| (e) | `--bare` | Reads no OAuth token (C5); O10's means needs it read |
| (e) | The prompt on standard input | Needs `--interactive` and a pipe; nothing in the prompt is large |
| (e) | The model by `ANTHROPIC_MODEL` | The flag wins over it (C1); one means is enough |
| (f) | Every non-zero `docker run` status as `coder_not_ended` | Would call a missing image or `claude` a coder that ran; D6 separates the three |

## Consequences

- **Code slices for the planner** (code mode; tested with stub `docker` executables only — no `docker` or `claude` is started, D16):

Bound to nothing yet. Within the D4 cap.
  2. **The binding and the turn loop**: `hilclaw.tools.default_registry` binds `coder.run` to the Docker runtime in place of `NoContainerRuntime` (ADR-0141 decision 3: "slice (d) replaces it"); `hilclaw/turn_loop.py` copies a non-empty `HILCLAW_CODER_IMAGE` into the server entry's `env` and writes the reference `${HILCLAW_CODER_OAUTH_TOKEN}` there when its environment holds a non-empty value (decision 5). `coder_call.call` and `coder.run` keep their contracts; the docstrings that call the runtime "slice (d)'s" are updated with it.

- **The cost, plainly.**
  - The user must create a one-year subscription token and give it to the runtime (O10); the coder, which has a shell and the network, can read it and send it anywhere, and with it spend the user's plan until it expires or is revoked (revocation not verified). This is ADR-0049 L5 with a credential that lives a year by itself (C3) and is independent of the host login, in exchange for keeping the host login and every file of `~/.claude` out of the container. On the host, an agent of the turn session with its pre-approved `Read` may read it from a process environment (decision 5; not verified), and the Docker daemon holds it with the container's configuration.

  - The user must provide an image with Claude Code and clang and name it; the runtime gives no default and never fetches one, so the first call on a machine waits for the user (O5).
  - A future Claude Code that makes `--bare` the default of `-p` would end the coder's sign-in by O10's means (C5) unless the documentation then offers a way out.
  - `dontAsk` may deny something a coder needs; the remedy is a change of the allowlist by a later record, never a bypass flag without the owner.
  - A coder's output stream is discarded until its record.

## Boundaries (not decided here)

- **The time limit of a call** (OD-14; ADR-0049 L7 "No ceiling"; ADR-0141 decision 4 for the session's side), including how long `docker run` may run and what a time limit does to the container.
- **The coder's output stream** (OD-23 ① (라)): what is kept of the coder's standard output and error, `--output-format`, and where it would be stored.
- **The token record and which usage counts** (HQ-0041 part (2), owner-answered, not recorded): how the call reads and reports the coder's usage.
- **The model that actually ran** (ADR-0136 Boundaries): remapping, fallback, `modelUsage`.
- **The credential form of unattended runs on the host** (O8; OD-18 ⑯ (다)), left open by O10.
- **Podman, and which runtime is used on Windows with WSL** (OD-8 ㉝ (라)): this record names the `docker` command only and tells no WSL runtime from another.
- **Leftovers of a dead process** (㉝ (나)): how a later turn finds and removes a container named `hilclaw-coder-…` and a scratch.
- **Whether a checkout is shown inside** (㉝ (다)): this record mounts none.
- **What part of the runtime asks the user** for the image, the token or a missing container runtime, and when (㉝ (가)).
- **The image**: base image, registry, Dockerfile, packages and versions; pulled or built; who updates it; P4 for a built one; recording its identity; whether it is the build and run image (OD-14 ① (나)).
- **The isolation of the measured build and run** (OD-14 ①; ADR-0144).
- **What a coder may read or search, and the network from inside** (OD-12, OD-16); resource limits (OD-14).
