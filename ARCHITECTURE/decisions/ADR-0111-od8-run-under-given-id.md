## Context

Its Limits: "Nothing remembers an id that was built". Its decision 6: the random part never comes "from a generator that a caller seeds".
- ADR-0004 decision 8: `run_id` "matches `[a-z0-9][a-z0-9_-]{0,63}` and is unique within `runs/` of a data repository". Decision 10: the tree "gives no concurrency control (the lock is OD-17; P1 assumes one run, C-2)".

Its decision 2 lists four things a taken name can be: "a repetition of ADR-0027 decision 5's improbable kind; a premise of ADR-0027 that failed …; a file put there by other means …; or an earlier attempt of this same start whose writer died after the last step and before its report". Its decision 5 finds that if ⑩ lets the start write a file before `instance.json`, that write could replace another run's file "without a report" (cited there: ADR-0013 decisions 2 and 6), and that "the stop protects `instance.json` only".
- ADR-0076 decision 3: a refusal "writes no `instance.json`", and "The report goes to whoever gave the values; its form is the code task's and the UI's (OD-23, UC-1)".
- UC-1 step 1 lists what the user gives to start an instance: "HW + 모델 + 최적화 target type + (선택) budget + (선택) gate 구성 + autonomy 모드 + 라운드당 후보 수 N + (선택) 참고 사례·자료 + (선택) 주입할 가설" — no name of the run. Step 2: "시스템이 instance용 작업공간(데이터 plane의 `runs/<run_id>/` …)을 만들고 STATE를 초기화한다". S2 step 1 has the CI start an instance with "(HW, 모델, target=throughput, budget=wall-clock 8h + 토큰 상한, autonomous)"; S2 step 3 and UC-4 resume a run that was stored before. ## Decision

### 1. Scope

- **The start of an instance of ADR-0076 decision 1**: the start that writes the `instance.json` of a new run, whatever component performs it.
- **Outside**: instances outside ADR-0076 decision 1; a branch, a continuation or a resume under the id of the run it comes from (①); every component that takes a `run_id` and is not the start — the write of ADR-0025 (`hilclaw.instance_file.write`), the paths of ADR-0004, a tool call that names its run (the example request of ADR-0015 uses `r1`), a reader, a test. Nothing here is required or allowed of them.
- **How the answer holds while ⑰'s first part stays open.** Decisions 2 to 4 bind "the start" as a role, as ADR-0076 and ADR-0109 do. They say what the start takes and what it gives back, not which component performs it, how it receives its inputs or in which form (⑰ first part, OD-23, UC-1). Any component that performs the start and any input form are bound alike.
- **How the answer holds while ① stays open.** If ① makes a branch or a continuation a new run whose start writes an instance of ADR-0076 decision 1, that start is in the scope and builds its own id, as any other. If ① makes it later rounds of the run it comes from, it runs under that run's id, it is no start of a new run, and it is outside the scope. **This record does not decide whether a branch or a continuation runs under the id it comes from**, and its answer needs neither outcome. A new run under the id of another run is excluded already by the uniqueness of ADR-0004 decision 8 (cited), not by this record.

### 2. The start runs only under an id it built

**The start takes no `run_id` from whoever gives the values. It builds the id of the new run by the rule of ADR-0027 (decision 2, with the sources of decision 6) and starts the run under that id only.**

- **An id built at an earlier attempt.** ADR-0109 decision 1 counts the id a start built at its first attempt as built by it when the start is tried again, and its decision 4 says only that "something must have kept" it. **For the scope of decision 1, this record narrows that count**: it covers an id the start kept itself, and not an id that reaches the start as one of its inputs. Such an id is taken from whoever gave it, even if an earlier attempt built it: the start cannot tell it from any other given name. No record yet provides a means by which a start keeps an id itself across attempts ("Nothing remembers an id that was built" — cited: ADR-0027 Limits; ⑩, ⑰), and this record adds none, so today the count of ADR-0109 decision 1 is reached by no defined path.
- **A given id.** If whoever gives the values gives a value as the id of the run, the start does not happen: it builds no id, fills in no `n_max`, makes no check against the required set of ADR-0076 and writes nothing. It reports to whoever gave the values that the start takes no `run_id`. The report is told apart from a refusal of ADR-0076 decision 3 and from the stop of ADR-0109; its form is the code task's and the UI's (OD-23, UC-1), as theirs are. Whether an input form has a place for such a value at all is that form's matter; the start does not drop a given id unreported and does not use it as the run's id. This look comes after the validity check and the reading of the scope of ADR-0076 decision 3, which tell whether this record applies, and before `n_max` is filled in and the content is checked against the required set; the order is unchanged for a start given no id. A start given an id and missing a member is therefore told of the id first and of the members only when it is started again without the id: the cost of one more refusal, taken because the required set does not bear on a start that will not happen.
- **Why the start does not go on under its own id instead**: a caller that gave a name expects to find the run under it. A run started under another name, with the given one dropped, would be found by nobody who kept only the given name (Alternatives, the row "The start goes on under its own id and drops a given one").
- **No extra requirement on a given name is fixed, and no checker**, because no given name is taken. **No requirement asks for a given name** (cited: ADR-0027 decision 1), and none of the inputs UC-1 step 1 or S2 step 1 lists is a name of the run, so the start loses no listed input.

### 3. The start makes the id it built known

**When the start has happened, it gives the id it built to whoever gave the values.** This is what lets a person or a CI find the run again (FR-6, UC-4, S2 step 3, S3). The form, the moment within the start and the channel are the code task's and the UI's (OD-23, UC-1); the order of the first files is ⑩ and is not fixed here. When the start stops by ADR-0109, it reports the id already (cited: ADR-0109 decision 3). How a caller keeps the id, and how a run is found without it (an index of runs, sub-question ②; OD-20), are not decided.

### 4. Readers and found ids are unchanged

- **ADR-0027 decision 1 stays as it is**: a found `run_id` that matches the pattern of ADR-0004 decision 8 and is not of the form of ADR-0027 is a valid `run_id` for every reader, and nothing refuses a run, or treats it differently, because of its id. This record binds only what the start takes.
- `hilclaw.layout.check_run_id`, every function that takes a `run_id`, every tool request, every literal id of a test (`run-a`, `synthetic-run_01`) and of a record (`r1`) stay valid. A run directory with a name not of the form, put there by other means (cited: ADR-0109 decision 2), is a run like any other for a reader; this record does not say how it came there.

### 5. Finding: a start that dies before its caller learns the id

A caller learns the id only from the start (decision 3). If the start, or the caller, dies after the start wrote its first file and before the caller kept the id, the caller cannot name the run, and a start tried again with nothing kept builds a new id and starts a run of its own; the first directory stays as it was (cited: ADR-0109 decision 4). What such a directory means, and whether anything takes it up, is ⑩ and the third part of ⑰. **This is a limit of the decision, not an answer**: alternative (b) gives no defined way to resume such a run either. If the first attempt had written `instance.json`, a retry under the same given name meets the name taken, and what it does then is ㉓ (가) outside ADR-0109's scope, which is open; nothing on record lets it take the file there for its own write (ADR-0109 rejected that within its scope, Alternatives A). If the first attempt had written only files before it (an order ⑩ leaves open), the retry writes into the first attempt's directory with nothing to tell that it is its own: a hazard, not a defined resume. And (b) adds risks of its own (Alternatives).

### Walk-through

| At the start | What follows |
|---|---|
| The values of an instance of ADR-0076 decision 1, no id given | The start builds an id by ADR-0027, checks by ADR-0076, writes by ADR-0025, and gives the id to whoever gave the values (decisions 2, 3) |
| The same, and a value given as the run's id | The start does not happen: no id built, no check against the required set, nothing written; reported that the start takes no `run_id` (decision 2) |
| A built id whose name turns out to be taken | ADR-0109 applies: stop, report the id in use |
| A retry after a death, with the id of the first attempt handed back by the caller | A given id: the start does not happen (decision 2) |
| A retry after a death, with nothing kept | A new id and a run of its own; the first directory stays (decision 5; ADR-0109 decision 4) |
| A reader finds `runs/run-a/` | A valid run; nothing refuses it (decision 4) |
| A continuation under the id of the run it comes from | Outside the scope (①) |

## Consequences

- **The code slice it makes possible** (code mode, a later task): a start component that has no `run_id` parameter, builds the id with `hilclaw.run_id`, refuses a given id as decision 2 says, and returns the built id to its caller; it calls the check of ADR-0076 and the write of ADR-0025 with that id. It waits on a start component (⑰'s first part, OD-23). No module or function is named here as binding; `hilclaw/run_id.py`, `hilclaw/layout.py`, `hilclaw/instance_start.py` and `hilclaw/instance_file.py` need no change for it.
- **A-13 reading**: document mode. No member, file, kind of file, tool-failure kind, validity rule, `schema_version` or layout version changes; no code, `instance.json`, `STATE.json` or `events.ndjson` changes; no dependency is added. The report of decision 2 is no tool-failure kind: the start is not a tool by any record, and the report's form is left to the code task and the UI.
- **Sentences of accepted records that become less exact** (listed, not edited; found by a search of `ARCHITECTURE/decisions/` for ㉔, "did not build", "given by a person" and "given by a caller"). For the scope of decision 1, these say that a run under an id the system did not build is not decided; it now is: ADR-0027 decision 1 ("**Whether a run may have an id the system did not build** … **is not decided** (sub-question ㉔)") and Boundaries (the text of ㉔); ADR-0109 Context ("Its decision 1 leaves an id the system did not build to sub-question ㉔"), decision 1 ("**Outside**: a `run_id` the start did not build — given by a person or a caller (㉔)"), decision 4 ("Whether a run may have a caller-given name (㉔) is not decided either"), its Walk-through row ("An id given by a caller … Outside the scope (㉔, ①)") and Boundaries ("**㉔** — a run under an id the system did not build"); ADR-0030 Boundaries and ADR-0034 Context and Boundaries, which list ㉔ among what the start does. ADR-0076 decision 3 ("Order of the checks at the start … the content composed from the start's inputs is checked for validity first") has the look of decision 2 inserted between its reading of the scope and the filling-in of `n_max` for a start given an id; its order stands otherwise. ADR-0109 decision 1, its parenthesis ("for a start that is tried again, the id it built at its first attempt counts as built by it"), is narrowed by decision 2 to an id the start kept itself. With it, ADR-0109 decision 4 ("falls under this only if the retry uses the same id, which something must have kept") and its Walk-through row "A retry that kept the id of a first attempt" become less exact: by decision 2 a retry that keeps the id only through its caller is a start given an id, so that row is reached only by a start that keeps the id itself, which no record yet provides. The list is not claimed to be complete. No sentence of UsageCases became false: UC-1 says that the system creates `runs/<run_id>/` and lists no name among what the user gives. In code, nothing becomes less exact: no docstring says whether a start may take a given id.
- **Name check**: a search of `hilclaw/`, `tests/` and `ARCHITECTURE/` for every identifier in code type in this record found each of them already defined or used there before this record; it adds no event kind, member, `step` value, blob `type`, spend axis or reserved kind, and none of the index documents (EventKinds, StepValues, BlobTypes, SpendAxes) changes.
- **Runtime acceptance items**: none. Nothing here needs a live Claude Code session or hardware to establish.

## Boundaries (not decided here)

- **⑰ first part** — what component performs the start and how it gets its inputs from the user (OD-23, UC-1); **⑰ third part** — what a run directory that holds other files and no `instance.json` means.
- **⑩** — who writes the first `STATE.json` and in which order against `instance.json`; what a run directory left by a start that died before its caller kept the id means (decision 5).
- **①** — whether a branch, a continuation or a resume is a new run, and under which id it runs (OD-20, FR-6, UC-4, S3).
- **㉓ (나)** — the rights of the writer in the run directory under the isolation means; **㉓ (가) outside ADR-0109's scope**; **㉔** for every start outside decision 1.
- **Instances outside ADR-0076 decision 1**: other accelerators, a stated op_signature that ADR-0041 decision 5 does not cover, every case other than the first.
- **A human-readable label for a run**, and any member that would hold one.
- **The lock and a second writer** (rest of OD-17; C-2); a look at or reservation of `runs/<run_id>/` before the first write; **OD-20**; **OD-23**; **OD-25** (owner-only), with uniqueness across clones; the other owner-only items (OD-3, C-6, the #5 A and B items).
- How a caller keeps the id; an index of runs (sub-question ②); the form of the reports of decisions 2 and 3; anything a UI shows.
- Any edit to an earlier record (decision 2 narrows the reading of ADR-0109 decision 1 for its scope and edits no text), any change to `hilclaw/`, to tests, to CI, to any settings file or to the `HIL-Claw-data` repository; any new external dependency.
