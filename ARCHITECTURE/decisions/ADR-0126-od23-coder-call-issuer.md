## Decision

A sentence is **cited** when a source is named with it. Every other sentence is **this record's own**.

### 1. Scope

- **One coder call of the first case** (ADR-0049 decision 1: one `claude -p` process for one spec, ADR-0002) that the turn session of a run of ADR-0120 decision 1 needs: round 0's bring-up call (FR-1) first, and any later call of the same kind.
- **Outside**: the composition and the writing of that call's `spec.json` (rest of OD-6; decision 4 names only the role); N > 1 and parallel calls (OD-29); repair calls and what is taken from a call that does not end normally (OD-19; OD-23 ①); every other backend (#5 B-1); everything under Boundaries.

### 2. (a) The issuer: the `coder-driver` sub-agent of the turn session

- **The Round-Manager delegates the call to one sub-agent of its turn session, `coder-driver`, and that sub-agent issues it.** The Round-Manager issues no coder call itself, and the turn loop issues none between turn sessions. K1 and K2 agree on this much.
- **The reading of K1**, marked as this record's: the coder-driver "invokes" `claude -p` by requesting the function of decision 3, which starts the coder process through the container runtime. Under ADR-0049 a coder process is never started by a host shell's `claude -p` in any case, so every form of the call is indirect.
- The coder-driver stays thin (K2): it codes nothing, writes no file of the run with its own file tools and performs none of the steps of decision 3 itself (K3).

### 3. (b) What performs the call: one deterministic function of the package

- **The whole call is one deterministic function of the layer-2 package**, in ADR-0049's order: the checks below; the scratch with the copy (`scratch.create`); the container and the coder process (slice (d)); the wait for its end; the removal of the container (P4); the bring-in (`bring_in.bring_in`); the removal of the scratch (`scratch.remove`). "Deterministic" as in ADR-0115 decision 2: no judgement, no model call of its own. The data root comes from the data-root source (ADR-0015 decision 3) and is never a member of the request.
- **Two forms are possible for how the coder-driver reaches it, and this record chooses neither (Q1)**: **(B)** a command-line entry of the package outside the registry, `python -m hilclaw.coder_call`, which the coder-driver runs through its Bash tool, following the convention of ADR-0010 decision 4 (the request on standard input; exit status 0 and one JSON object as the result; otherwise the error object); or **(T)** the tool `coder.run` (MCP name `mcp__hilclaw__coder_run`, ADR-0010 decision 4) of `default_registry`, which the coder-driver calls through the MCP front. Under (B) `coder.run` does not exist; under (T) it does. **Until Q1 is answered, neither the entry nor the registry entry is added**, and the function is written without a front.
- **The contract below holds under either form**, so the function slice does not wait for Q1:

| Part | Content |
|---|---|
| Request | Exactly `run_id`, `round`, `candidate`, `attempt`, with the meaning and form of ADR-0015 decision 4; all four required; any other member, or one missing, is refused |
| Result | `taken`: the names `bring_in` returned, in its order, an empty array when none was taken; `scratch_removed`: a *boolean*, what `scratch.remove` reported |
| Failure kinds, in the order of the checks | `invalid_request`, `no_data_root` (the reserved kinds of ADR-0015 decision 2, same meaning; see the bullet below); `output_exists` (the attempt directory lists an `output`); `spec_unreadable` and `spec_not_regular_file` (two of the values of `scratch.SCRATCH_FAILURES`, for the spec file of the tuple, a missing one included); `spec_invalid` (invalid by ADR-0029 decisions 2 and 3 as ADR-0051 carries them over, its `id` not the tuple of the request included); `spec_unsupported` (a `schema_version` other than 2, ADR-0051); `no_container_runtime`; `spec_changed` (the third value, from `scratch.create`); `coder_not_started` (the container or the coder process could not be started); `coder_not_ended` (last bullet); the five values of `bring_in.BRING_IN_FAILURES`; `output_not_written` (creating `output/` or writing a file failed) |

- **Every check before `no_container_runtime` creates and consumes nothing**, so a refused or impossible call costs no coder session. `output_exists` refuses before the call what `bring_in` would refuse after it (`OutputExistsError`); what a second call for one tuple means stays OD-23 ① (가).
- **The kinds are names of the report of the call**, like the tool-layer kinds of ADR-0124 decision 3: none of the new ones is reserved, and **none is a change of the data plane**. Under (T) `invalid_request` and `no_data_root` are the reserved kinds of ADR-0015 decision 2; under (B), where the function is no tool, using them with the same meaning is this record's reading.
- **The scratch is removed whatever happened after it was made**, and the container before the bring-in (ADR-0049 P4); a removal that fails is reported by `scratch_removed` or as text for a reader and is not retried later by the function (ADR-0049 sub-question ㉝ (나)).
- **A coder process that does not end normally** — it is killed or exits with a status other than 0 — gets **no bring-in**: the function gives the bring-in up, which P4 allows ("finished or been given up"), removes the scratch and fails with `coder_not_ended`. This is the function's interim behaviour and **not an answer to OD-19**: a later record that takes files from such a call changes the function.

### 4. (c) The `coder/` role

- **The coder-driver holds the `coder/` role of ADR-0004 decision 4** for these runs: it is "the side that issues coder calls: it writes the spec before the call and holds the output after it". The bring-in into `output/` is performed by the function it requests, acting for it as a tool acts for its caller; this record reads that as no split of the role.
- So **the spec of the call is the coder-driver's to have written before it requests the call**; how it is composed and by what means it is written stay open (rest of OD-6; ADR-0029 decision 4 gives the steps of the write). The coder process holds no role (cited: ADR-0004 decision 4).

### 5. (d) How the coder process is pointed at its spec copy and its place

- **The working directory of the coder process is the scratch, as the container shows it.** The coder prompt, whatever else it holds, names the copy by the relative name `spec.json` (`scratch.SPEC_COPY_NAME`) and the place by the relative name `output` (ADR-0055 decision 5), and **no host path**. Relative names hold inside the container, where the scratch need not have its host path, and keep the host's layout out of the prompt.
- **The function composes that prompt.** How the working directory is set inside the container, how the prompt reaches the process (an argument or standard input) and the rest of its text are not decided here (Consequences, "Open parts of the start"). No `claude -p` flag and no model is chosen. The scratch holds nothing but the copy at the start (ADR-0049 decision 4), so it gives the coder process no project instructions or settings of its own.

### 6. (e) The definition of the sub-agent

- **The definition is `orchestration/agents/coder-driver.md`**, copied into the session directory as `.claude/agents/coder-driver.md` by `LAYOUT` (ADR-0118 decision 5). It is written by a later code-mode slice, after Q1, not here.
- **It carries a fixed rule**: request the call once per delegation with the run id and the tuple it was given; report the result or the failure kind to the Round-Manager; code nothing and write nothing of the run itself.
- **The run id and the tuple reach it in the Round-Manager's delegation message**, never a place; the Round-Manager has the run id from its prompt (ADR-0123 decision 2) and the tuple from its round. The run it names is the session's run (ADR-0123 decision 4).

### 7. (f) What this record does not make of the call

- **The call is not a journaled step.** A coder session spends plan usage, and an end line would carry that spend (ADR-0011 decisions 6, 7); counting tokens as an axis, and whether orchestrator and coder share it, is K5. So no event kind, payload or spend axis is added (ADR-0098; ADR-0100), and **a call leaves no record in the data plane** besides what it brings into `output/`. This holds under (B) and (T) alike: under (T) the tool is a tool of the registry that is not journaled, as the four of ADR-0124 are not.
- **The start of the coder process stays open** (Consequences, "Open parts of the start").

## Consequences

- **Q1, the owner question** (DRIVER §9, the owner's reading of K2 and K4): does the coder-driver reach the call through its Bash tool (form (B): K2's words; it has a shell, and by this record's reading of K4 premise 2 its prompt is then too weak as a write zone), or as the typed registry tool `coder.run` through MCP (form (T): no shell for it; a hook sees the request and an allowlist names the tool alone)? The answer decides whether `coder.run` exists; the function, its contract and decisions 2, 4 to 7 stand under either answer. **An answer (B) also answers OD-18 sub-question ②** ("셸을 가진 에이전트가 명령줄 진입점을 호출해도 되는지") for the coder-driver, and makes the record that adds the entry revisit ADR-0010 decision 3 ("agents call tools through" the MCP front), whose reason — a hook sees the request, an allowlist names one tool — an entry outside the registry does not keep. An answer (T) needs neither.
- **Code slices it enables** (code mode, later tasks; tested with a stub `claude` and a stub container runtime only — D16):
  1. **Now**: a new module `hilclaw/coder_call.py` with `tests/test_coder_call.py`: the function of decision 3 over `scratch.create`, `bring_in.bring_in`, `scratch.remove`, `spec_file.parse` and `hilclaw.layout`, with the container start (slice (d)) behind a seam that the tests replace; no front.   2. **After Q1**: the front — under (B) the `python -m hilclaw.coder_call` entry and a way for the session's shell to find it from the session directory, in `hilclaw/turn_loop.py` beside the server configuration; under (T) the definition of `coder.run` and its registration in `default_registry` of `hilclaw/tools.py`.
