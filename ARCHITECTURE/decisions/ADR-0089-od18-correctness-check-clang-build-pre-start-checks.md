## Context

- ADR-0087 placed a `TypeError` of `build` that carries `parameter` and left open one from binding the call or from `subprocess.Popen` or later, "for example a `cwd` or an `env` that cannot be handed over", and the `TypeError` of `build_verification_executable` for `kernel_sources` (cited: ADR-0087 T4, T5 and decision 5). Tasks T-0267 (`e932bf3`), T-0268 (`8aee9ba`), T-0270 (`e2ae330`), T-0271 (`e6553a2`) and T-0272 (`57172c0`, a message only) then moved checks before the start; none placed anything in a row.
- **Observations at `57172c0`** (`hilclaw/clang_build.py`, `hilclaw/harness/verification_build.py`; no code is bound):
  - **P1. The order of `build`'s checks**: `timeout_s`, `flags`, `trailing_flags`, `sources` (with their path tests), `output` (with its path tests), `compiler` (with the search), then `env` and `cwd`; the first that fails is raised. So a flag with a NUL is raised before a missing source, and a missing compiler before a refused `env`.
  - **P2. `env` and `cwd`.** "After the compiler is found, and still before anything is started, `env` and `cwd` are checked as `subprocess` would refuse them, with the class it would raise for the same single defect" (cited: the docstring of `build`). An `env` with an `items` method has each key and value converted as on the platform (`os.fsencode` on POSIX — whose `UnicodeEncodeError` is a `ValueError` —, `str` only on Windows, else `TypeError`), and a NUL in either or a `=` after a key's first character is a `ValueError` whose message "may name the key but never the value"; "any other `env` is left to `subprocess`". A `cwd` that is not `None` must convert (`TypeError` or a `ValueError` such as `UnicodeEncodeError`), and a NUL in it is a `ValueError`. "any `TypeError` or `ValueError` from the checks of `env` and `cwd`, including one that Python itself raises inside them", carries `parameter` `"env"` or `"cwd"` (cited). "Whether `cwd` exists is not tested here: a missing one fails the start, as `CompilerNotStartedError`" (cited).
  - **P3. The pre-start `ValueError`s with no `parameter`** — "a `ValueError` from the other checks … carry no `parameter`" (cited): (V1) no source; (V2) a `timeout_s` that is no positive finite number, and (V3) one above (2**31 − 1) / 1000 s (T-0271); (V4) an empty compiler prefix; (V5) a flag or trailing flag that sets the output; (V6) a NUL in a flag, a trailing flag or a compiler part after the first; (V7) on POSIX the `UnicodeEncodeError` that `os.fsencode` raises for such a flag or part (T-0268). V2 to V7 are each about a setting of ADR-0060 decision 3 — the time limit of the build, the flags and trailing flags, the compiler; V1 is about the sources, an argument the operation forms (cited: ADR-0087 decision 1). A `ValueError` that the code of a handed object raises while a check iterates it carries none either, as only `TypeError` is tagged for the six checks.
  - **P4. `build_verification_executable`.** It tests `kernel_sources` "before every other argument": a `TypeError` while making a tuple of them carries `parameter` `"kernel_sources"`, and the `ValueError` for no kernel source "carries none" (cited: its docstring). It then calls `build` with the program source first among the sources, so `build` is never called with no source: **V1 cannot arise through it.** Whatever `build` raises is passed on unchanged.
  - **P5. The time limit.** `compiler_version` makes the same check of `timeout_s` (V2, V3). No value above the bound reaches `Popen` or the wait in `build`; T-0271 ran values at the bound on Windows and Linux with stub compilers (cited: its Result), not on macOS. "An exception that is not an `OSError` and leaves the build early … is passed on unchanged" (cited: the docstring of `build`); the wait kills the compiler first. `compiler_version` is not called by `correctness.check`; [ADR-0035](ADR-0035-od4-cpu-standin-hw-key-values.md) uses it for the hw_profile record.
- No owner comment on #5 speaks to ADR-0060 decision 4, ADR-0087, T-0267, T-0268, T-0270, T-0271 or ⑱ (마), and HQ-0027 is unanswered (checked on 2026-10-17: every comment since 2026-10-16 carries the driver tail).

## Decision

### 1. Scope and terms

- A call of `correctness.check`, the six kinds, S1 to S10 and the keeper, as ADR-0087 decision 1 has them. **A named error** is one that carries a `parameter`; **an unnamed `ValueError`** is one of P3 or the one of P4. **The mock** builds nothing and is unchanged. The operation reads `getattr(error, "parameter", None)` and the class, on the reading of ADR-0087 decision 2: what the operation observes is what the function states of the error.

### 2. `parameter` `"env"`: S4, `settings_refused`

- **A named `TypeError` or `ValueError` whose `parameter` is `"env"` is S4, `settings_refused`.** The environment is "the backend's own" (cited: ADR-0060 decision 3), and S4 names "an environment that cannot be handed over", found "before the process the refused setting belongs to is started" (cited: ADR-0060 decision 4). "whether the setting is refused for its value or for its type" (cited, same) covers both classes. One that Python or the handed object's code raises inside the check is read as ADR-0087 decision 3 read it for the four settings.
- **Weighed against leaving it open**: P2 states the parameter and decision 3 of ADR-0060 says whose it is, so the stop of ADR-0087 decision 5 ("an `env` is a setting (S4), a `cwd` is the operation's own") no longer holds for it. **The cost**: a fault in the code of a handed mapping is read as a refused setting, as in ADR-0087 decision 3.
- An `env` with no `items` method is not checked (P2) and stays under what `build` passes on from `subprocess` (decision 9).

### 3. `parameter` `"cwd"`: no row

- **A named `TypeError` or `ValueError` whose `parameter` is `"cwd"` is no row.** The working directory is "the operation's own" (cited: ADR-0060 decision 3), and it is the build directory the operation made for that call (cited: ADR-0079 decision 4). For a `TypeError`, "a `TypeError` for an argument that is no setting … is a defect of the operation's own code and is no row" (cited: ADR-0060 decision 4). **That a `ValueError` for that argument is no row as well is this record's reading**: the class follows how the path is wrong, not whose it is, and ADR-0060 decision 4 already lets "a `TypeError` or `ValueError` of `local_run.run` for an argument its own code formed" pass. An operation that lets it pass is answered `operation_answer_invalid` (cited: ADR-0045 decisions 4 and 5); that is what the landed rules do with it, not an answer of this record.
- **Not S4**: no setting of the backend's is in it. **Not S3**, "The build directory cannot be made or written" (cited: ADR-0060 decision 4): the operation made and holds that directory; a refused `cwd` says the path it handed is not one a process can be given, which this record reads as the operation's own code handing something other than the directory it made. **The cost**: if a platform lets a directory be made under a path the check refuses, a fault of the machine is answered as a defect of code; this record did not read that it cannot.
- **A missing `cwd`** is still `CompilerNotStartedError` (P2), the start error ADR-0079 decision 4 places in S6 (cited: ADR-0080 decision 2). This record does not place it again.

### 4. `parameter` `"kernel_sources"`: no row

- **A named `TypeError` of `build_verification_executable` whose `parameter` is `"kernel_sources"` is no row**, as ADR-0087 decision 4 has `"sources"`: the kernel sources are the compiled set the reader gave the operation, which the operation hands on (cited: ADR-0056 decisions 3 and 4); no setting is in them. Not S5, which names "A file of the compiled set is no longer a regular file" (cited: ADR-0060 decision 4); a value of the wrong type says nothing of a file.
- **What stays unnamed**: its `ValueError` for no kernel source (P4). By what it is for, it is the error "for no kernel source …, which the reader's non-empty compiled set rules out" and is no row (cited: ADR-0060 decision 4); by its class it is one of the unnamed `ValueError`s of decision 5.

### 5. An unnamed pre-start `ValueError` stays open

- **ADR-0060 decision 4 reaches V2 to V7 by what they are for**: "a `ValueError` or `TypeError` for a setting — a time limit, a flag, the compiler — … → S4" (cited), and its S4 row names "a flag that sets the output, a time limit that is no positive finite number, … an empty compiler prefix" (cited). V3, V6 and V7 are each a refused setting of the same three, which before T-0268 and T-0271 left `build` only from `subprocess`.
- **The operation cannot tell them apart by the class.** An unnamed `ValueError` it meets through `build_verification_executable` is one of: a refused setting (V2 to V7, S4); that function's own for no kernel source (P4, no row); one the code of a handed object raised while a check iterated it (a setting's or the operation's); or one that `build` passes on from `subprocess`, which "was not read" (cited: ADR-0060 decision 4) and stays open (cited: ADR-0083 decision 2). V1 is not among them (P4). The second the operation can rule out by a step of its own — it knows it handed a non-empty compiled set (cited for the step: ADR-0060 decision 4, "An operation places such an error by the step of its own at which it met it") — but no step of its own tells the first from the last.
- **So this record places no unnamed `ValueError`.** Reading every one of them as S4 would read an error that was not read into a row, which ADR-0087 decision 5 declined for the unnamed `TypeError`. Until then an operation that lets it pass is answered `operation_answer_invalid` (cited: ADR-0045 decisions 4 and 5). **The cost**: a refused setting, S4 by its meaning, is answered by a kind that says the backend's answer had neither form.
- **What would let it be placed** (named, not decided): a `parameter` on V2 to V7 — `"timeout_s"`, `"flags"`, `"trailing_flags"` or `"compiler"` —, as T-0267 did for `env` and `cwd`; a later record then places them. That is a code change of the code task's; this record binds none.

### 6. The time limit too long to wait for

- **It is now V3**, a pre-start `ValueError` of `build` (and of `compiler_version`), and stays open with decision 5.
- **An `OverflowError` after the start for this cause is not reachable from `build` on this record's reading**: no value above the bound reaches the start (P5). Should a platform still fail the wait for a value at or below it, what leaves `build` is no `OSError` and stands under what `build` passes on from `subprocess` (decision 9); T-0271 did not run macOS. ADR-0060 decision 4's `OverflowError` "from `local_run.run`" is not this record's.
- **`compiler_version`** stays a Boundary: no check of `correctness.check` calls it (P5).

### 7. No log, and the message

- **No log.** Every error of decisions 2 to 6 is raised before a compiler process exists (P1 to P4), and S4 "found before the build" has no log (cited: ADR-0078 decision 2); the operation hands nothing to the keeper.
- **The message of `settings_refused` for `"env"`** may say that the environment was refused and of which kind the error was, and shows "no text of an error, no value of a setting" (cited: ADR-0060 decision 5) — so not the message of the `ValueError`, which may name a key. No rule is added; the wording is the code's.

### 8. No data-plane change

- `parameter` is an attribute of a Python exception inside the tool function's process; it is no member of a file, a result, a request or a line. S4 is a kind already named and no row needs no kind. No value of `condition` or `error.kind` is added, no kind is reserved, and no `schema_version` or layout version changes. No case is left open for want of a new value: decision 5 is open for want of a way to tell the errors apart.

### 9. How far (마) is answered

- **Answered now, for `correctness.check` of the first case and of the mock**: a named error of the `env` check — S4 — and of the `cwd` check — no row —, and the named `TypeError` of `build_verification_executable` for `kernel_sources` — no row —, each with no log (decisions 2 to 4, 7). With it the entry of ADR-0087 decision 8, "of `build_verification_executable` for `kernel_sources`", is answered, and its entry "from `subprocess.Popen` or later" no longer holds a refused `env` or `cwd` that the check sees.
- **Narrowed**: "whatever `clang_build.build` passes on from `subprocess` beyond the `OSError` its docstring names" (cited: ADR-0086 decision 8; ADR-0087 decision 8) no longer holds a NUL or unencodable flag or compiler part, a refused `env` or `cwd`, or a time limit too long to wait for; each is now a check before the start (P2, P3).
- **Open under (마)**: an unnamed pre-start `ValueError` of `build` or of `build_verification_executable` (decisions 5 and 6); an unnamed `TypeError` — of `build`, from binding the call or from `subprocess.Popen` or later (cited: ADR-0087 decision 5), or from binding a call of `build_verification_executable`; whatever `clang_build.build` still passes on from `subprocess`, an `env` with no `items` method included; an unroled `OSError` of `build` — from `os.getcwd`, `os.urandom`, `time.monotonic` or the search for the compiler before the start (cited: ADR-0086 decision 6); the row of a `CompilerRunError` whose `timed_out` is false and whose `returncode` is `None` (cited: ADR-0085 decision 6, as ADR-0087 decision 8 lists it); and the `ValueError` or `TypeError` and the `OSError` for "a `cwd` that does not exist" of `local_run.run`.

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 2 to 5 | **(a)** S4 for `"env"`, no row for `"cwd"` and `"kernel_sources"`, unnamed `ValueError` open (chosen) | It applies ADR-0060 decisions 3 and 4 by what the functions now state. The costs: a handed mapping's fault is read as a refused setting (decision 2), a refused `cwd` as a defect of code (decision 3), and a refused setting with no `parameter` gets no S4 yet (decision 5). |
| 2 to 5 | **(b)** Leave all of them open | The stop for `env` and `cwd`, a class that says nothing of the argument (ADR-0087 decision 5), is gone for a named error (P2, P4). Left open, a refused environment, S4 by its meaning and named in S4's own wording, is answered as an answer of neither form. |
| 5 | **(c)** S4 for every pre-start `ValueError` of `build` by its class | The class also holds `build_verification_executable`'s own for no kernel source and whatever `subprocess` passes on, which was not read (decision 5); the same stop ADR-0087 decision 5 kept for the unnamed `TypeError`. |
| 3 | **(d)** S3 or S4 for `"cwd"` | S3 names a build directory that cannot be made or written, which the operation made; S4 a setting of the backend's, which the working directory is not (decision 3). |

## Consequences

- **Code** (code mode, D12 rules; names and modules are the code task's; **this record binds no code**): the operation of `cpu_standin` for `correctness.check`, when it is written, applies ADR-0079 to ADR-0087 and this record. It raises `settings_refused` for a named error with `parameter` `"env"`, hands no log over, and leaves `"cwd"`, `"kernel_sources"` and an unnamed `ValueError` to the landed rules. A code task that gives V2 to V7 a `parameter` (decision 5) is a candidate follow-up, not required by this record.
- **Not edited and now less exact.**
  - ADR-0060 decision 4: "what `clang_build.build` passes on from `subprocess` beyond the `OSError` its docstring names (an `env` that cannot be handed over, a time limit too long to wait for) was not read" — both examples are now refusals before the start (P2, P3); and "a `ValueError` or `TypeError` for a setting — a time limit, a flag, the compiler — … → S4", which an operation that sees an unnamed `ValueError` by its class alone cannot apply (decision 5).
  - ADR-0060 Consequences: "The errors decision 4 names as arising in one class in two rows … cannot be placed by an operation that sees the class alone", whose list did not name the unnamed pre-start `ValueError` that this record treats as such an error (decision 5).
  - ADR-0087 Status: "It leaves open a `TypeError` with no `parameter` (decision 5) and the rest decision 8 names", where the entry for `kernel_sources` is now answered.
  - ADR-0087 decision 1: "an unnamed `TypeError` is one with none (T4), and one of `build_verification_executable` itself (T5)", where that function's `TypeError` for `kernel_sources` is now named; decision 2: "A `ValueError` of the same checks carries no `parameter` (T4) and stays as ADR-0060 decision 4 places it, by what it is for", which by its class alone the operation cannot do (decision 5).
  - ADR-0087 T4: "one from `subprocess.Popen` or later (for example a `cwd` or an `env` that cannot be handed over), every `ValueError` … carry no `parameter`", where a refused `env` or `cwd` is now named before the start; T5: "It raises its own `TypeError`, with no `parameter`, for `kernel_sources`"; decision 5: "for it the class is still of two rows — an `env` is a setting (S4), a `cwd` is the operation's own" and "for `kernel_sources` (T5), which the operation cannot tell apart by the object"; decision 8: the open entries "of `build_verification_executable` for `kernel_sources`" and "from `subprocess.Popen` or later"; the walk-through row "An `env` that `Popen` cannot hand over"; Boundaries: "of whatever `build` passes on from `subprocess`".
  - ADR-0083 decision 2: "a `TypeError` or `ValueError` from inside the construction of `Popen`", which for a refused `env`, `cwd`, flag or compiler part now arises before it.
  - ADR-0079 decision 5, ADR-0080 decision 4, ADR-0083 decision 4, ADR-0084 decision 5, ADR-0085 decision 6 and ADR-0086 decision 8: the open entry "whatever `clang_build.build` passes on from `subprocess` beyond the `OSError` its docstring names", now narrower (decision 9).
