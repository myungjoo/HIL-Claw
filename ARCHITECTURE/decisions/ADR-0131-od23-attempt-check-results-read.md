## Context

- **The open points** (cited): what a record of the evaluator's role rests on "it gets through typed tools of the registry that take the `run_id`: an outcome, a standing, a comparison, the round's hypotheses" (ADR-0128 decision 4); slice 3 lists "a read of an attempt's journaled results" and "the standing of ADR-0110 as a tool (it gives the standings a form ADR-0110 did not give them as values)", each "after a record" (ADR-0128 Consequences); "Whether the tool also holds a `check` entry's `outcome` against the log is not decided" (ADR-0128 decision 6); "Whether the results read alone is enough for the verdicts work to be given — every verdict `inconclusive` until the comparison exists … — is that read's record" (ADR-0129 decision 5).
- **What exists** (code, as observation): `hilclaw.events.read` returns the complete lines of a run's log from a position, a missing or empty file giving none; it raises `CorruptEventsError` for a damaged line or a path that is no regular file and `UnsupportedVersionError` for another version. `hilclaw.check_standing.standing` computes the standing of one attempt at one `step` over parsed lines; it "reads no file and names no consumer", and no tool calls it. `correctness.check` journals a start line and an end line whose `result` is the result object of ADR-0042 or whose `failure` is a `kind` and a `message` (`hilclaw/check_tool.py`). `verdicts.write` checks a record against `hypotheses.json` and refuses any `comparison` entry, and reads no other file (`hilclaw/verdicts_tool.py`). `orchestration/agents/evaluator.md` answers a verdicts delegation with one line, that the verdicts "cannot yet be written because no tool reads the attempts' results", and on a check delegation reports no standing.
- **Constraints the means must keep** (cited): agents call tools through the MCP front (ADR-0010 decision 3); the data root is never a member of a request (ADR-0015 decision 3); the evaluator's prompt and delegation name the run id and no place (ADR-0123 decision 2; ADR-0128 decision 4); no read is restricted (K4 premise 1); the evaluator holds no file-writing means and no shell (ADR-0128 decision 3); the standing is found "in the complete lines of the run's `events.ndjson` alone", every end line of the attempt at the point counting, and its names are "words of this record, not values of any file or member" (ADR-0110 decisions 2, 3); a `check` entry has exactly `ref`, `point` and `outcome`, and "which execution of a check … an entry stands for" is not recorded (ADR-0071 decision 3); "All attempts of a candidate test the same hypotheses" (ADR-0059 decision 4).

## Decision

A sentence is **cited** when a source is named with it. Every other sentence is **this record's own**.

### 1. Scope

- **The read of the `correctness.check` lines of the evaluator's run**, by the `evaluator` sub-agent of a turn of a run of ADR-0120 decision 1, for the check work and the verdicts work of ADR-0128 decision 1; the check that `verdicts.write` makes of a record's `check` entries against the same lines; and what the evaluator's verdicts work becomes.
- **Outside**: the results of `sim.run` and `board.run`, the comparison of ADR-0007 decision 7 and the comparison record (HQ-0021); every other line kind and every other reader; everything under Boundaries.

### 2. (a) The means: a typed registry tool through the MCP front

- **The evaluator gets the results of an attempt's checks, and its standing, by calling one tool of the registry, `checks.read`, through the package's MCP front**, naming its run by `run_id`, the attempt by its numbers and the point by `point`. The check report and the verdicts record it composes rest on what this tool returns (ADR-0128 decision 4).
- **It is given no place for this**: the tool takes the `run_id` its delegation names, so ADR-0123 decision 2 and ADR-0128 decision 4 stand unchanged. It restricts no read (K4 premise 1): whatever else the evaluator reads with `Read`, `Grep` or `Glob` is not restricted, but no record of its role rests on it.

### 3. (b) and (c) The tool, with the standing folded in

| Part | Content |
|---|---|
| Name (MCP name) | `checks.read` (`mcp__hilclaw__checks_read`); the name holds no `_`, so the mapping of ADR-0010 decision 4 stays reversible |
| Request | `run_id`, `round`, `candidate` and `point`, required, and `attempt`, optional; any other member, or a required one missing, is refused. `run_id`, `round`, `candidate` and `attempt` have the meaning and form of ADR-0015 decision 4, `round` 0 admitted; `point` is the member of ADR-0040 decision 4, `"sim"` or `"board"`, compared as it is |
| Result | `{"attempts": [...]}`: one entry per attempt, in ascending `attempt`, each exactly `attempt`, `standing` and `checks` (below). With `attempt` in the request, exactly one entry, for that attempt; without it, one entry per attempt of the candidate for which the log holds a line of the point's `step`, possibly none |
| Checks, in order | the request (`invalid_request`, ADR-0015 decision 2); the data root (`no_data_root`); the read of the run's `events.ndjson` from its first line: a read that fails in the file system for a reason other than the file's not being there (`run_file_unreadable`), a damaged complete line, a path that is no regular file or a step line that breaks ADR-0011 (`run_file_invalid`), a complete line of another version (`run_file_unsupported`); an end line of the candidate at the point whose `result` has no `outcome` of ADR-0042 decision 2 (`check_result_invalid`) |

- **The `checks` of an entry**: one element per end line of that attempt at the point's `step` (`correctness_check_sim` or `correctness_check_board`, ADR-0040 decision 3), `{"execution": n, "state": "ended", "result": …}` or `{"execution": n, "state": "ended", "failure": …}` with the `result` or the `failure` as the line holds it, members as stored; and one element `{"execution": n, "state": "open"}` per identity of that attempt and point that has a start line and no end line. They stand in the order of their lines in the log (for an open identity, its first start line). **Every end line has its own element**: two end lines of one identity give two, and an end line without a start line gives one (cited: ADR-0110 decision 2, "both count here as well", "counts like any other end line"). `state` uses the words "open" and "ended" of ADR-0011 decision 4. The order carries no meaning for the standing (ADR-0110 decision 2).
- **The `standing` of an entry** is the standing of ADR-0110 decision 3 of that attempt at that point, computed by `check_standing.standing` over the same lines, as one of the strings `"verified"`, `"not_verified"` and `"undetermined"`. **The standing is folded into this read (point (c))**, so the outcomes and the standing an evaluator reports come from one read of the log and cannot disagree. This is the form ADR-0128 Consequences slice 3 says a standing tool would give them; no separate standing tool is created.
- **Why the strings are no change of the data plane** (this record's reading of ADR-0110). Its decision 3 makes the names "not values of any file or member", and its Alternatives reject storing the standing "in a member of a file or a result" as a data-plane change. A result of `checks.read` is stored nowhere: the tool is not journaled, so no line holds it, and no file holds it. The three strings are values of the tool layer, like a failure kind, spelled as ADR-0110's words in the *name* form of ADR-0001. **If the owner reads ADR-0110 decision 3 as forbidding any tool result that names a standing, that is an objection to decision 3 of this record**, whose fallback is the result without `standing`.
- **The candidate, not only the attempt.** The verdicts work starts from `tested_by`, which names candidates (ADR-0059 decision 4), and no tool tells which attempts a candidate has. With `attempt` left out the tool finds them in the log, so the evaluator does not guess numbers. A check delegation names the attempt and passes it.
- **A missing log is no failure**: it means "no event recorded" (cited: ADR-0006 decision 2; ADR-0019 decision 1). With `attempt` the entry then has no `checks` and the standing `"undetermined"`; without it, `attempts` is empty. The tool reads no `STATE.json`, as `hypotheses.read` reads none, so a `run_id` that names no run is answered like a run whose log has no line (Walk-through).
- **The reserved kinds of ADR-0019 for the log, widened.** ADR-0019 decision 2 has a tool function raise the four kinds "only at the lookup or the selection", and ADR-0124 decision 3 widened that sentence to `state.read` and `instance.read`. **This record widens it once more, to the read of `events.ndjson` by `checks.read` and by `verdicts.write` (decision 5)**: the log is a frame file (cited: ADR-0019 decision 1), the situations are those of its decision 3 for the log with the same meanings, and the property it states with them holds: such a call appended no line, selected or called no backend, ran no step and consumed nothing. `run_file_missing` is not raised for the log, which has no "not there" situation of its own (cited: ADR-0019 decision 1).
- **One new kind**, `check_result_invalid`: an end line of the candidate at the point holds a `result` without an `outcome` that is `"pass"`, `"fail"` or `"broken"`. ADR-0110 does not say what such a line means, `check_standing.standing` refuses it, and it is no step line that breaks ADR-0011, which does not look into a result (cited: ADR-0019 decision 3), so no reserved kind names it. It is a name of the tool layer, **not a change of the data plane**, and not reserved. A result whose other members differ from ADR-0042 decision 7's table is returned as stored (cited: ADR-0042 decision 7, "a log can come to hold results of two member lists").
- **Every line is read**, not only the attempt's: a damaged line anywhere, or a step line about another attempt that breaks ADR-0011, refuses the call, as `check_standing.standing` checks every line. The read is from the first line because an attempt of an earlier round needs lines before the stored position (cited: ADR-0110 Limits; ADR-0011 decision 6, "A fold from the first line is always allowed"). It is not a read at the entry of a turn and answers nothing of OD-17 sub-question ①.
- **Not journaled**: a read costs no limited resource and can be repeated (the reasoning of ADR-0124 decision 3). It appends no line and selects no backend. It is a tool of the registry beside the FR-10 tools, not an FR-10 tool. **Nothing is created** by a call, and nothing is kept between calls. The fixed tool set grows by it in the source (`default_registry`) and in no other way (cited: #5 A-12 point 3); it is reachable through the command-line front too (ADR-0010 decision 3).
- **It does not check that the run is one of ADR-0120 decision 1**; that scope is the caller's, as for `check_standing.standing` (its docstring).
- **Left to the code slice**: the module, the description and input schema, how the read shares code with `check_standing` and `verdicts.write`, and what a number beyond the float range in a stored result does to the result (for `state.read` it is `bad_result`).

### 4. (b) A `check` entry's single `outcome` against several results

- **A `check` entry names an outcome the log holds, chosen by one rule.** Let O be the outcomes of the end lines of the attempt `ref` at `point` that hold a `result`, every `execution` together (the counting of ADR-0110 decision 2). The entry's `outcome` is `"pass"` only when O is not empty and every element of O is `"pass"`; otherwise it is an element of O that is not `"pass"`. When O is empty — no line, only `failure` end lines, only open identities — **no `check` entry can be written for that attempt and point**, since `outcome` has only the three values (cited: ADR-0071 decision 3).
- **Why.** ADR-0071 decision 3 gives one entry per `ref` and `point` and records no execution; the rule chooses which of several outcomes that one entry carries without a new member. "Every ended check … counts" and "a fail stands" (cited: ADR-0110 decisions 2, 3): an entry that said `"pass"` beside a recorded fail would show a pass the floor does not give. A `failure` and an open identity establish no outcome (cited: ADR-0011 decision 4), so they give no entry.
- **What a `"pass"` entry does not say**: that the attempt is verified at that point. An open identity or a `failure` of class (ii) beside passes leaves the standing undetermined (cited: ADR-0110 decision 3) and still admits a `"pass"` entry under this rule. ADR-0071 decision 4 counts a comparison on `"pass"` entries; no comparison is admitted yet (ADR-0128 decision 6), so nothing is counted on such an entry today. **Whether a counted comparison must rest on the standing `"verified"`** is the comparison record's (Boundaries).
- **Which attempts and points a verdict's evidence names** stays the evaluator's judgement (ADR-0128 decision 2); the rule binds only the `outcome` of an entry it writes.

### 5. (d) `verdicts.write` holds each `check` entry against the log

- **Answered, not left open**: `verdicts.write` (ADR-0128 decision 6) refuses a record any of whose `check` entries breaks decision 4. Its checks become, in order: the request; the record's validity and `run_id` (both `invalid_request`); the data root (`no_data_root`); the round's `hypotheses.json` (the four `hypotheses_*` kinds); the rules of `verdicts_hypotheses.check` (`verdicts_mismatch`); no `comparison` entry (`comparison_not_given`); **the read of the run's `events.ndjson` from its first line, with the kinds and the widening of decision 3 (`run_file_unreadable`, `run_file_invalid`, `run_file_unsupported`) and `check_result_invalid` for an end line of an attempt and point a `check` entry names; every `check` entry founded by decision 4 (`check_unfounded`)**; the write (`verdicts_exist`, `verdicts_not_written`).
- **Why now.** The cost ADR-0128 names, "A `check` entry's `outcome` is the evaluator's copy and is not held against the log", is the "점수 레코드 조작" of OD-16 threat A in a weak form, and a prompt rule alone would be "너무 약하다" (K4 premise 2). With the read of decision 3 the check is a function over lines the package already parses; it needs no comparison, no `eval.json` and no hook.
- **`check_unfounded`** is a new name of the tool layer, not reserved, **not a change of the data plane**: no member, value or version of `verdicts.json` changes and `verdicts_file.validate` is unchanged; the rule is between two files and is held by the writing tool, as ADR-0128 decision 6 holds the rules between the record and `hypotheses.json`. **Every check before the write still creates nothing**, so a refused record can be corrected and sent again. `verdicts.write` now reads two files besides the one it writes; `verdicts_file.write` still reads none (cited: ADR-0071 decision 1).
- **What it does not hold**: that the evidence names every attempt of `tested_by`, a `"pass"` entry against the standing (decision 4), and anything of a comparison. The log can change between the check and a later check; what is held is the log as the call read it.

### 6. (e) The verdicts work is given

- **With `hypotheses.read`, `checks.read` and `verdicts.write`, the verdicts work is given to the evaluator**, and every verdict it writes is `inconclusive` until the comparison tool exists (cited: ADR-0128 decision 6; ADR-0071 decision 4, no counted comparison).
- **Weighed against FR-17.** "evaluate에 이른 라운드는 판정 없이 끝나지 않는다" (cited: FR-17) is kept only if a verdict is written; waiting for the comparison would end rounds 1 to 4 of P2-5 without verdicts. "**지지** 판정은 검증 하네스를 통과한 결과에만 기댄다" (cited: FR-17) is kept: `inconclusive` supports and refutes nothing, and each `check` entry is founded on the log (decision 5). An `inconclusive` verdict with no counted comparison is the value ADR-0071 decision 4 gives that case, not a placeholder.
- **The cost is permanent per round**: a verdicts file is "written once and never replaced" (cited: ADR-0071 decision 1), so a round judged before the comparison exists keeps `inconclusive` verdicts after it exists, and a case built from it (FR-18) carries them. Whether a later re-judgement exists is open (cited: ADR-0071 Boundaries). Weighed as the lesser cost: the alternative breaks FR-17's sentence for every such round, and the files it writes are true by the rule of ADR-0071.
- **What `orchestration/agents/evaluator.md` becomes in the code slice** (Consequences slice 3). Its `tools` list adds `mcp__hilclaw__checks_read`. **"A check"**: after `correctness.check`, call `checks.read` with the same `run_id`, `round`, `candidate`, `attempt` and `point`, and report the `outcome` and the `standing` it returns (ADR-0128 decision 5); the sentence that no tool gives the standing goes. **"Verdicts"**: the one-line "cannot yet" report goes; on a verdicts delegation the evaluator reads the round's hypotheses with `hypotheses.read`; for each candidate of each `tested_by` it calls `checks.read` without `attempt` at the points it judges; it composes one verdict per hypothesis, `verdict` `inconclusive`, `check` entries only, each by decision 4, a `cause` that says no comparison could be given and what the checks showed; and it sends the record with `verdicts.write`, correcting and sending again on a refusal. It still requests no check on a verdicts delegation (ADR-0128 decision 7), and it reports as ADR-0128 decision 5 says.

### 7. (f) Who may use it

- **The evaluator: `mcp__hilclaw__checks_read` is added to its `tools` list** (ADR-0128 decision 3: later tools are added "by the records or slices that create them"). It is a read and gives the evaluator no file-writing means and no shell.
- **The Round-Manager is not given it here.** What follows a standing — repair, elimination, the baseline — is the round steps' (P2-1; cited: ADR-0110 decision 3), and the Round-Manager gets the standing from the evaluator's report (ADR-0128 decision 5). Whether it reads the log itself belongs to P2-1 and the rest of OD-23.

### Walk-through

The run of ADR-0071's example; "lines" are the `correctness_check_board` lines of the named attempt unless the row says otherwise.

| Situation | What follows |
|---|---|
| A check delegation `0000/01/01`, `sim`; the check passes | `correctness.check` returns `pass`; `checks.read` with the tuple and `sim` returns one entry, `checks` `[{"execution": 1, "state": "ended", "result": {…"outcome": "pass"…}}]`, `standing` `"verified"`; the evaluator reports both |
| Lines: `execution` 1 fail, `execution` 2 pass | Two `checks` elements; `standing` `"not_verified"`; a `check` entry for this `ref` and `board` must say `"fail"` |
| Lines: `execution` 1 pass, `execution` 2 open | An ended and an open element; `standing` `"undetermined"`; a `"pass"` entry is founded (decision 4), and counts for nothing while no comparison is admitted |
| Lines: two end lines of `execution` 1, both pass (two turns at once) | Two elements with `execution` 1; `standing` `"verified"` |
| Lines: only `execution` 1 with `failure` `compiler_unavailable` | One element with that `failure`; `standing` `"undetermined"`; no `check` entry can be written for this attempt and point |
| Round 2 reaches evaluate; `h1` is tested by candidate 1, which has attempts 1 and 2 | `hypotheses.read`; `checks.read` for round 2, candidate 1, without `attempt`, at `sim` and `board`, returns both attempts; the evaluator writes `h1` `inconclusive` with founded `check` entries and calls `verdicts.write`; it reports the file written and `h1` `inconclusive` |
| The record says `"pass"` for an attempt whose board lines hold a fail | `check_unfounded`; nothing is written; the evaluator corrects and calls again |
| The record names an attempt and point with no result line | `check_unfounded` |
| A complete line of the log is damaged, anywhere | `run_file_invalid` from either tool; nothing is returned or written |
| A request without `point`, or with `attempt` but no `candidate` | `invalid_request`; the data root is not asked |
| `run_id` names a run with no log, or no run | `attempts` empty (with `attempt`: no `checks`, `"undetermined"`); `verdicts.write` for such a run fails earlier, `hypotheses_missing` |
| The evaluator names another run's id | The tool serves that run; nothing stops it (cited: ADR-0123 decision 4; ADR-0015 decision 7) |
