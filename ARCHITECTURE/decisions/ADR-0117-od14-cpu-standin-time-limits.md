## Decision

A sentence is **cited** when a record and its decision, or a requirement, is named with it; it says what that source says and adds nothing. A sentence marked **owner** quotes O4. Every other sentence is **this record's own**.

### 1. Scope and terms

- **The runs** are those of ADR-0116 decision 1: the hw_profile names `cpu_standin`, the first case (`gemm`, fp32, a C kernel), the local configuration. **The mock is out of scope**: it is given no setting (cited: ADR-0060 decision 3).
- **The four limits**: of `correctness.check`, the build of the verification executable (B_v) and its process (P_v); of `sim.run` and `board.run`, the timing build (B_t) and the timing run (P_t). A limit is the most time, in seconds of wall-clock time, one build or one process may take before it is ended.
- **Where they apply**: on the host, as the records still say, or in the container of O4 (**owner**: "The toolchain, the build of a kernel, its correctness run and its timing run use an isolated environment: a container …"), whose design is OD-14 sub-question ①. Every value is meant to hold in both: a limit bounds the process the operation starts, and nothing below depends on what starts inside it, under the condition that a container started per call (OD-14 ① (다)) adds seconds and no install or image pull to a build or process — an install or update needs the user's approval first (**owner**, O4 item 2), so it is no part of a call. A design that adds more revisits decisions 3 and 4.

### 2. The source: one rule in the package source, applied to what the operation is handed

- **The four limits are given by constants and one rule of the tool package, applied by the operation of `cpu_standin` for `correctness.check` and by its operations for `sim.run` and `board.run` alike, to the values the operation is handed.** They change only by a commit of the source repository. No operation reads one from a file, a variable or the hw_profile, and the tool function hands none over (ADR-0060 decision 3; ADR-0061 decision 3).
- **Four alternatives were weighed, against six tests.**

| | (a) Fixed constants of the package (the ADR-0116 pattern) | (b) A rule of the package from what the operation is handed (shape, `draws`, `n_max`) | (c) Read from a file of the run (a member of `instance.json`; the wall-clock budget of ADR-0033) | (d) A configuration file or an environment variable |
|---|---|---|---|---|
| NFR-7 ③ (which source commit made a result) | The commit names the values | The commit names the rule; the handed values are stated by the run's file and repeated in each result (ADR-0042 decision 5; ADR-0063 decision 5), so the limit of a call can be recomputed | The file names the value; no commit does | No commit names the values (cited: ADR-0116 decision 2 (b)) |
| C-7 (Linux, macOS, WSL alike) | One set on the three | One rule on the three | Per run | Per machine and shell |
| O4 item 2 (changes only after approval) | Changes arrive as a new source version only (cited: ADR-0116 decision 2) | The same | The run's writer sets it | An edit between calls changes it without approval |
| ADR-0060 decision 3 and its cost (i): "an operation is handed the output path, not the data root …, so a time limit stated in a file of the run has no way to an operation" | Kept | Kept: the operation reads no file; it computes from values it is handed for their own purpose | **Reopens decision 3**, and a new member of `instance.json` is a data-plane schema change (CLAUDE.md A-13); the wall-clock budget states no clock and no rule of counting (ADR-0033 decision 2), so a limit derived from it would decide a part of the counting | Kept, but a second source of settings |
| What a broken `time_limit` says about the attempt (ADR-0021 decision 5: a result is read as a property of the attempt) | Whether a correct kernel breaks depends on the run's `draws`, `n_max` and shape as much as on its speed | The limit grows with the work asked, so below the cap a break says the kernel was slower than one rate per call | As (a) or (b), by the file's value | As (a) |
| What a process that does not end costs | Always the one fixed value, at every shape | About the work the call asked for: seconds at a small shape, minutes at the largest | As the file says | As (a) |

- **The choice is (b) for the processes and (a) for the builds** — the builds compile one kernel source and one harness program, and nothing a build is handed says how long that takes (decision 3). (c) is not taken: it reopens ADR-0060 decision 3 or adds a member. (d) fails NFR-7 ③ and O4 item 2 as ADR-0116 decision 2 (b) found. (a) for the processes is not taken: every hang at a small shape would cost the whole value, and a correct kernel would break by the run's numbers.
- **This is no time limit "stated for a run"** in the sense of ⑱ (가): the file states `draws`, `n_max` and the shape for their own meaning, and the operation derives the limit from them after the tool function has handed them on. The cost: whoever starts an instance moves the process limits, up to the cap, through those numbers.

### 3. The two build limits: 60 s each

- **B_v = B_t = 60 s.** A build compiles the kernel's compiled set and one harness program of about 250 lines of C (observation: `verification_program.c`, `timing_driver.c`) with the flags of ADR-0116 at `-O2`, and links. **This record's estimate**: a few seconds on a C-7 machine, the compiler's start-up included, and more for a first start of the compiler after boot or after an update of the installation (on macOS the default `clang` is a shim of the developer tools). 60 s is more than ten times that estimate, so that the limit ends a compiler that does not end, not a build that is merely slow.
- **The same value for both**: they compile the same kernel beside harness programs of the same size; ADR-0107 decision 3 lets them differ "as each run needs", and nothing here needs it.
- **The cost**: a kernel source the compiler takes more than 60 s with — no record bounds the size of a source — is a broken result `build_time_limit` (decision 7).

### 4. The two process limits: one rule

- **P = min(1500 s, 10 s + c × (1 s + W / R))**, with W = 2·m·k·n, R = 2 × 10^8 per second and c the number of kernel calls the process makes: **c = `draws`** for the verification process (cited: one call per draw) and **c = `n_max` + 1** for the timing run (cited: one untimed call and up to `n_max` repeats of one call). The value is in seconds; it is always a positive finite number of at most 1500.
- **The terms.**
  - **10 s** for the process as a whole: its start, and in the timing run the generation of the inputs once and the clock's resolution (cited: ADR-0009 decision 10, "Untimed cost is still spent").
  - **1 s per call** for what a call costs besides the kernel: in the verification run, per draw, the generation of `a` and `b`, the check value of their bytes, the NaN fill of `c` and 4·m·n bytes of report (cited: ADR-0017 decisions 3, 4, 7, 9 and 10) — this record's estimate is well under a second at the largest shape.
  - **W / R per call** for the kernel. W counts the multiplications and additions of the textbook product; it is a nominal count, and a kernel may compute otherwise. **R is a floor, not a target** — this record's estimate: a straightforward single-thread loop at `-O2` reaches about 10^9 of them per second on a C-7 machine and some times less when it walks `b` by columns at n = 8192; R lies several times below that, so that the limit ends a kernel that does not end, not one that is untuned.
  - **1500 s, the cap**, follows from decision 5.
- **The stated worst case** is the largest work of the first instances: gate/up and down at M = 512 (2048→8192, 8192→2048; cited: ADR-0008 decision 9), W ≈ 1.72 × 10^10, per call 1 + 85.9 ≈ 86.9 s. A timing run at the default `n_max` = 10 (c = 11) gets ≈ 966 s; a verification run gets 10 + 86.9 × `draws` s, under the cap up to 17 draws. The cap is reached from 18 draws and from `n_max` = 17. The smallest work, O at M = 1 (W ≈ 8.4 × 10^6), gets ≈ 21.5 s for a timing run at `n_max` = 10 and ≈ 11 s for one draw.

### 5. The call limits Claude Code applies (OD-18 ③)

- **The longest call these limits allow**: one build and one process — a check holds one verification build and its process, a call of a run tool one timing build and its run; the two builds of an attempt are two calls — so at most 60 + 1500 = **1560 s**, plus the tool function's own work, which nothing here bounds (cited: ADR-0017 decision 10, "the Python-side work of a run is bounded by nothing here").
- **The MCP idle window, 30 minutes = 1800 s: the limits fit it, with 240 s left for the tool function's own work, and the whole call fits it while that work stays within those 240 s.** For a timing call that work is the replay of the stopping rule on every prefix of at most `n_max` intervals (cited: ADR-0009 decision 7), which grows with the square of `n_max` and is negligible at the default 10 (estimate). For a check it grows with `draws` when the process completes: per draw a regeneration and a float64 product on the Python side (cited: ADR-0017 decision 10), **this record's estimate** being up to about 3 s at the largest shape and under a second at the smaller ones, where the regeneration of `b` (k·n elements) still dominates. So a check of up to about 80 draws at the largest shape, and of some hundreds at the smaller ones, fits whatever the kernel's speed; a check of more draws fits only while its kernel is fast enough that process and own work together stay inside the window. A check whose process reached its limit is a broken result, which holds no counts (cited: ADR-0060 decision 4, from ADR-0042 decision 7), so none of its draws is judged. **What follows beyond that bound**: the call can outlast the idle window, and the client may then end it; what then holds for the call, its process and its log lines is OD-18 ③ and is not decided here, and neither is a progress notification or a wider window.
- **The Bash default limit, 10 minutes = 600 s: it does not fit for every call.** The timing call of the largest work at `n_max` = 10 is allowed 60 + 966 = 1026 s, a check of it from 7 draws more than 600 s. **What follows**: a call through the command-line front run by a Bash tool at its default can be ended by the client before these limits are reached, and what then holds for the call, its process and its log lines is not decided here (OD-18 ③; ADR-0010 Limits). Agents call through the MCP front (cited: ADR-0010 decision 3). A kernel that is not slow takes far less than its limit: at 10^9 per second (estimate) the timing run of the largest work takes about 11 × 17 s ≈ 3 minutes.

### 6. The rest of the hierarchy

- **Adopted, for these calls**: the call level, as one limit per build and per process of a call, enforced by ending the process at the limit. The kill is the code's (observation: the started process is killed, its children are not); this record adds no softer stage before it and no second limit after it. The proposal's two levels "호출 < 서브프로세스 SIGKILL" are taken here as one limit per process; their ordering is neither adopted nor refused, and **a limit of the whole call** — one that bounds the tool function's own work too — is not set (OD-14; OD-18 ③).
- **The kernel watchdog**: not adopted and not refused. The kernel of `cpu_standin` runs inside the process (cited: ADR-0017 decision 10; ADR-0009 decision 10), whose limit is its only guard; a watchdog of a board is the rest of OD-14.
- **Round and run**: no limit of either exists to nest the call limits in. The round budget counts rounds (cited: ADR-0032 decision 2) and the wall-clock budget seconds with no clock and no rule of counting (cited: ADR-0033 decision 2); nothing compares either with anything (cited: their decisions 5). **How the four limits stand to them**: none is derived from a budget and none is part of one. One call spends at most 1560 s of wall-clock time by these limits, plus its own work. Whether that time counts against a wall-clock budget is ADR-0033's sub-question ㉚ (i). A budget below it is valid (cited: ADR-0033 decision 3) and nothing refuses it.
- **Not touched**: one candidate = one process, resource caps, health checks, reset escalation and the blacklist (OD-14).

### 7. What a call answers when a limit is reached

- **No new answer.** `correctness.check`: a build past B_v is a broken result `build_time_limit` (S8; cited: ADR-0060 decision 4); a process past P_v is a broken result `time_limit`, as "a process that was ended for its time limit is reported as the time limit" (cited: ADR-0021 decision 2; ADR-0042 decision 3). `sim.run` and `board.run`: the build past B_t and the run past P_t are broken results, the first and the third condition of the order of ADR-0061 decision 7 (cited), spelt `build_time_limit` and `time_limit` (cited: ADR-0063 decision 3).
- **A value the functions refuse** is S4, `settings_refused`, for the check (cited: ADR-0060 decision 4); for the run tools the kind is ⑲ (나). The values of decisions 3 and 4 are positive, finite and at most 1500 s — far below the bound of `clang_build` and the platform bound of `local_run` (observations) — so S4 for a time limit can follow only from a defect of the code.
- **The cap, stated**: a correct kernel of a run whose `draws` or `n_max` puts the rule above 1500 s is a broken `time_limit` when it is slower than that cap allows; a caller then reads the run's numbers out of a result about the attempt.

### 8. Limits

1. **Nothing was built or run.** Every duration not cited — compile and start-up times, the rate of a straightforward loop, the per-call cost besides the kernel, the tool function's own work — is this record's estimate (Consequences: runtime acceptance items).
2. **One kernel, two machines**: the rule is the same on the three C-7 systems, their speed is not, so one kernel can complete on one and be broken `time_limit` on another.
3. **A correct but slow kernel breaks**: below R per call, or beyond the cap (decision 7). An untuned loop that walks `b` by columns at the largest shape may fall below R (decision 4 expects it to be some times slower than 10^9 per second); that is part of the runtime acceptance item.
4. **The children of a killed process survive** (observation), and where one keeps an output pipe open "the call can last longer than the limit" (`clang_build`). In a container the started process may be the container runtime's client; killing it need not end the kernel inside, which can then go on using the CPU that later timing runs measure. The values of decisions 3 and 4 hold there; that the work ends at them is the container design's (OD-14 sub-question ①).
5. **The tool function's own work is bounded by nothing**: it grows with `draws`, and the replay of a timing call with `n_max`, so a call of many draws or a very large `n_max` can outlast the MCP idle window (decision 5); the bound in draws rests on an estimate of that work.
6. **Scope**: shapes beyond those of ADR-0008 decision 9 reach the cap at fewer calls; other backends, a simulator, a board, the mock, `profiler.collect` and a remote machine are not covered.

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 2 | (a) Fixed constants for the processes | Every hang costs the whole value at every shape; a correct kernel breaks by the run's `draws` or `n_max`. |
| 2 | (c) A member of `instance.json`, or a value from the wall-clock budget | Reopens ADR-0060 decision 3, needs a member (a data-plane schema change) or decides part of ADR-0033's counting. |
| 2 | (d) A configuration file or an environment variable | No commit names the value; an edit changes it between calls without approval (ADR-0116 decision 2 (b)). |
| 3 | A build limit from the shape | A build compiles the same source whatever the shape. |
| 4 | No cap | The longest call would have no bound and could outlast the MCP idle window. |
| 4 | R = 10^8 per second | At the largest work and the default `n_max` the cap would already bind, so the rule would not reach its own worst case. |
| 5 | A cap that fits the Bash default (about 500 s) | The largest work at the default `n_max` would then need about 4 × 10^8 per second, within a factor of about 2.5 of the 10^9 this record expects of a straightforward loop and above what one that walks `b` by columns may reach. |
| 6 | A softer stage (SIGTERM) before the kill | A softer end saves nothing the call keeps: the output of a process is captured until the kill (observation: `local_run`) and a broken result holds none of it, and the log of a compiler killed for its time limit is kept as it was captured ([ADR-0078](ADR-0078-od18-correctness-check-compiler-log-file.md) decision 2). |

- **⑱ (가)**: a time limit stated for a run, and any other setting from a file of the run or the attempt, reaching an operation.
