## Context

- **What P is.** "The start position P is a parameter of the run, given by the caller with no default and held by the Python side only"; "For the op_signature shapes the caller passes … P = 0 for m ∈ {128, 2048}; P = 127 or P = 2047 for m = 1, one per run. Whether a check of an m = 1 op_signature runs both is the caller's policy, with the number of draws (OD-16 sub-question ⑤)"; "Another m … is admitted with any P the caller gives" (cited: ADR-0164 decision 4). The kernel's work does not depend on P (cited: ADR-0161 decision 3); it receives the rows, not P (cited: ADR-0164 decisions 3 and 7).
- **What a check holds.** The stated record holds `m`, `h`, `d` and no position (cited: ADR-0161 decision 3); an operation is handed the seed, `draws`, the `kind` and `dtype` and the dimensions in `task_contract` order (cited: ADR-0177 decision 3), as `Bf16CheckParameters` (observation); the result of a bf16 check holds `shape` with the kind's members and `counts` entries `failed` and `non_finite` (**owner**, HQ-0077, through ADR-0177 decision 3). The seed is drawn once per check by the tool function (cited: ADR-0021 decision 3, ADR-0048) from the system source, `secrets.randbits(64)` (observation: `hilclaw.harness.seed_source.system`).
- **The cost of the table** (cited: ADR-0164 decision 5): 0.107 s for 128 positions and 1.91 s for 2048 positions, measured on the Python side, which "is bounded by nothing" (cited: its Limit 4). Measured again for this record (Python 3.14.4, NumPy 2.5.2, Windows 11, the machine of ADR-0164): `table_rows` 1.85 s at m = 2048 and at m = 1 with P = 2047, 0.11 s at m = 1 with P = 127; one draw's regeneration, check value, reference and count at m = 2048, h = 32, d = 64: 0.18 s.
- **The program** (observation: `bf16_verification_rope.c`): it allocates `x`, `out`, a buffer of the received rows and the kernel's `freqs_cis` array, reads exactly 4·m·d bytes before the first draw and ends with status 5 for standard input that is short, longer or unreadable; it copies the rows into `freqs_cis` before each call.
- **The container.** `hilclaw.standin_container.run_in_container` starts the client with no standard input; `hilclaw.local_run.run` has `stdin_data` (observation), the code slice 1 of ADR-0164.

## Decision

A sentence is **cited** when a record and its decision is named with it; every other sentence is **this record's own**.

### 1. (a) The start position of a check of `rope`

- **The rule.** For a check of `rope` with dimensions `(m, h, d)` and seed `s`: **P = 0 when m ≥ 2; when m = 1, P = 127 when `s` is even and P = 2047 when `s` is odd.** It holds for every shape `rope_bf16_contract.covers` admits (every m, h, d ≥ 1 with d even), not only those of ADR-0154.
- **Who applies it, from what.** The tool package, from the two values every side of a check already has: the dimensions and the seed. It lives in the harness, as `hilclaw.harness.bf16_rope_verification.start_position(dims, *, seed)`, and **each of the three places that needs P computes it there**: the mock's default script, the `cpu_standin` operation (the next slice) and the judging of the report (`hilclaw.check_judging`). Nothing hands P on: `CheckParameters`, `Bf16CheckParameters` and the parameters of the other five bf16 kinds are unchanged, and `rope`'s are its seed, `draws`, kind, dtype and `(m, h, d)`. The harness's own functions keep `start` as a parameter with no default (cited: ADR-0164 decision 12), so a calibration test still passes its own P (cited: ADR-0164 decision 11, P = 0).
- **What it gives.** At the op_signature shapes (cited: ADR-0154 decision 1; ADR-0161 decision 13) every check with m ∈ {128, 2048} uses rows 0 … m − 1 and every check with m = 1 uses one of the two rows 127 and 2047, **one per check, each with probability 1/2 under the system source and independently of every other check**, since each check has a seed of its own. So the checks of a run reach both rows: of k checks of m = 1 the chance that one of the two rows was never used is 2^(1 − k) (1/2 for the two points of one attempt, under 0.1 % for eleven checks). At other shapes the same rule applies: P = 0 for a run of m ≥ 2 tokens from the start of a sequence, whose rows include row 0 where the calibration's failing kernel is outside every tolerance a conforming kernel passes (cited: ADR-0164 decision 11), and the same two rows for one token.
- **Refused.** `start_position` refuses what `program_arguments` refuses of `dims` and `seed`, and a P whose rows the table cannot have, (P + m)·d above 2^53 − 1 (cited for the bound: ADR-0164 decision 4), with `VerificationArgumentError`. Such a record can be covered (for example m = 1 and `d` above about 4.4 × 10^12 at P = 2047) and no check of it can be built: the mock and the judge raise, as they do for dimensions whose arrays cannot be allocated at the other kinds, and the call is answered by the landed rules for such an error. No new answer.
- **Why one P per check and not both rows** (weighed against (ii) below): one P per check keeps a check one process, one report and `draws` counts entries, which is the form the operation returns (cited: ADR-0043 decision 4) and the form of the result the owner gave (HQ-0077); the kernel's work does not depend on P (cited: ADR-0161 decision 3), so a second row in the same check tests the same code on other table values, which the next check of the run does at no extra cost.
- **Why the seed.** It is the one value of a check that is new for every check, that no agent chooses (cited: ADR-0021 decision 3, a source whose output "nobody can predict or influence before the draw"), and that every side already holds; its parity is uniform under the system source. A rule on the seed is not a choice made per call by anybody, so no default of P is invented and no record member is needed. **What it reveals**: the kernel can tell P from the rows it receives, and so learn the parity of a seed that is already on its process's command line (cited: ADR-0164 Limit 1, the kernel shares its process with the program); nothing new is exposed.
- **What a result does not say.** A result of a `rope` check holds no P, as it holds no seed (cited: ADR-0042 decision 6): a reader cannot tell which of the two rows an m = 1 check used. Whether a seed or what follows from it is kept after a check stays OD-16 sub-question ⑤ (Boundaries).

### 2. (b) The `cpu_standin` time limits of the `rope` verification build and process

- **ADR-0179's rule holds for `rope`, with its work measure** (cited: ADR-0179 decisions 2 and 3; the constants are ADR-0117's): **P_limit = min(1500 s, 10 s + `draws` × (1 s + W / R))**, R = 2 × 10^8 per second, W = A + 10 · E, with for `rope`:
  - **A = 0**: the work per output element is bounded (two products and one addition, cited: ADR-0164 decision 9) and is taken into the element term, as for the element-wise kinds of ADR-0179 decision 3;
  - **E = 2·m·h·d + 2·m·d**: `x` and `out`, the program's buffer of the received rows and the kernel's `freqs_cis` array (observation of the program). The bytes of the rows read on standard input once per run, 4·m·d, fall within the 10 s of the rule, which is per process, not per draw.
- **The build limit is B = 60 s**, ADR-0117 decision 3's value as ADR-0179 decision 4 keeps it: the program has 140 lines and the shared header 185, below `verification_program.c`'s 224. The header is copied beside the program and handed to the compiler as no source, as ADR-0179 decision 5 says for the other kinds (cited), with the same answers for its copy.
- **The values at the `rope` shapes of ADR-0152** (computed by the rule; `SHAPES` of `rope_bf16_contract`):

| Shape (m, h, d) | E | Per draw | One draw | Draws under the cap |
|---|---|---|---|---|
| (2048, 32, 64) | 8,650,752 | 1.433 s | 11.43 s | 1040 |
| (2048, 8, 64) | 2,359,296 | 1.118 s | 11.12 s | 1332 |
| (128, 32, 64) | 540,672 | 1.027 s | 11.03 s | 1450 |
| (1, 32, 64) | 4,224 | 1.000 s | 11.00 s | 1489 |

- **A kernel that is not slow** (ADR-0179's estimate: 10^9 operations per second and 5 ns per element) takes at (2048, 32, 64) about 0.06 s per draw with the program's work, so a check of any number of draws the cap admits completes well within it.
- **The MCP idle window** (cited: ADR-0179 decision 8; ADR-0117 decision 5): the longest call is 60 + 1500 = 1560 s, which leaves 240 s of the 1800 s window to the tool function's own work. For `rope` that work is the table, built once by the operation to send it and once by the judge to compare (1.85 s each at P + m = 2048, measured above; a code slice that hands the operation's rows to the judge saves one, ADR-0164 decision 5 leaving caching to the code), and 0.18 s per draw (measured above) at (2048, 32, 64). So about 3.7 s + 0.18 s × 1040 ≈ 191 s at the cap's 1040 draws: **every number of draws the cap admits fits the window on the machine measured**. The Bash default of 600 s fits up to about 320 draws at that shape; beyond it OD-18 ③ holds, as ADR-0179 decision 8 says.
- **What a call answers at a limit**: as ADR-0179 decision 7 — `build_time_limit` or `time_limit`, broken results of the owner's list, no new answer (cited).

### 3. (c) How the rows reach the `rope` process in the ADR-0144 container

- **The operation hands the rows to the container client as its standard input, and the client keeps the program's standard input open for them with Docker's `--interactive` option**: `run_in_container` gains an optional input of bytes, `None` by default; given, it adds `--interactive` to the options before the image and passes the bytes to `local_run.run` as `stdin_data`, which writes them while the output is drained and closes the pipe (cited: ADR-0164 Consequences, code slice 1). `--tty` is not given: a terminal would change the bytes. Without the input the command and the null-device standard input are what they are today, so every present caller — the first case's build and process, the five bf16 kinds, the timing run — is unchanged. **No build container gets an input.** Docker's documentation describes `--interactive` as keeping standard input open; whether the client passes every byte unchanged and closes the program's input at its end was not observed (runtime acceptance item 1).
- **No other channel is needed**: a file in the build directory, the only mount (cited: ADR-0144 decision 2), would be a file of input values, which ADR-0164 decision 3 weighed and rejected (cited: "for input values the principle of OD-16 keeps out of files"); the command line cannot hold the rows (cited: ADR-0164 decision 3).
- **Its situations are those of ADR-0168, with no new row and no new kind.**
  - The rows do not reach the program in full, or reach it with more bytes (a client or a daemon that does not pass them, a container that cannot be started): the program ends with status 5, or the client with 125 to 127, and **a process container's non-zero status is the program's, `exit_status`** (cited: ADR-0168 row C8 and decision 3). This is a broken result that counts, ADR-0168 decision 3's stated cost for a runtime failure at a process container's start, which this record takes for the input as well; a machine whose client never passes the input breaks every `rope` check at that point, which runtime acceptance item 1 is for.
  - The program or the kernel ends before reading all of it: the write side meets a broken pipe, which `local_run.run` takes as part of the result, not as an exception (cited: ADR-0164 Consequences, slice 1); the status answers as above.
  - The container passes its limit while the rows are written: C10, `time_limit` (cited: ADR-0168 decision 2).
  - An input that is not bytes is a defect of the operation's own arguments, C16 (cited: ADR-0168 decision 2).
- **What it lets a kernel do**: nothing new. The rows are a public function of `d` and the positions (cited: ADR-0164 decision 3), and the check value covers the kernel's copy of them (cited: ADR-0164 decision 9), so rows changed between the client and the kernel make the run broken (`check_value`), never a pass.

### A-13 reading

- **No data-plane schema change.** P is derived, not stored or requested: no member of `instance.json` or of the request holds it, no line of `events.ndjson` and no member of a result says it, and the result of a `rope` check is the owner's list for a bf16 kind — `shape` `m`, `h`, `d`, `counts` entries `failed` and `non_finite`, `failed` at most m·h·d, the output elements of `rope` (ADR-0161 decision 10) (**owner**, HQ-0077, through ADR-0177 decision 3). The limits read only values an operation is handed, and the input of the container is an internal interface of the harness (cited for the reading: ADR-0164 Status). Option (iv) below would be a schema change and is not taken.

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 1 | (ii) Both rows in every m = 1 check | Two processes per check, or both rows sent and a selection in the program (ADR-0164 Alternatives, row 4). Two processes give two reports where the operation returns one (ADR-0043 decision 4) and 2·`draws` counts where the owner's result holds `draws` (HQ-0077), or split `draws` so that `draws` = 1 covers one row anyway; the cost of the table at P = 2047 is paid by every m = 1 check. |
| 1 | (iii) One fixed P (0, or 2047 for m = 1) | Drops one of ADR-0161 decision 13's two rows from every verification (ADR-0164 Alternatives, row 4). |
| 1 | (iv) P as a member of `instance.json` or of the request | A new member of the data plane or of the request (CLAUDE.md A-13), and a value somebody must choose per run or per call with no rule to choose it by; the rule needs no member. |
| 1 | P from the point (sim 127, board 2047) | Every board check — the hard floor and the re-verification before promotion (FR-3 ④) — would use one row only; and the judge is not handed the point. |
| 1 | P handed in a widened `Bf16CheckParameters` | Changes the parameters of the other five kinds or adds a type for one kind; the three places can compute the same value from what they already have. |
| 1 | P drawn by a bit of a mixed seed or a second draw | The parity is already uniform and independent under the system source; a second draw is a second seed (ADR-0048). |
| 2 | A = 3·m·h·d (the operations per output element) | Bounded work per element is what the element term already covers (ADR-0179 decision 3); a nominal count adds nothing when R is a floor. |
| 2 | Bounding the Python side's table | Outside the call limit by ADR-0117's design; it fits the window here (decision 2), and OD-14 keeps the rest of the hierarchy. |
| 3 | The rows in a file in the build directory | A file of input values (ADR-0164 decision 3, OD-16 principle). |
