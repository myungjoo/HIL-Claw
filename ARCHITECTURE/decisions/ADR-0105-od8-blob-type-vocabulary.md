## Context

- **The open point.** "⑥ `type`의 어휘 — 형식(*name*)만 정해졌고 값 목록이 없어 두 도구가 같은 종류를 다른 이름으로 적을 수 있다. 어떤 바이너리가 blob이 되는지와 함께 정한다(OD-23)" (cited: OpenDecisionProposals OD-8, sub-question ⑥). ADR-0005 fixed "**the form only** (a *name*) and **no list**: which binaries the tools produce is not decided (A-2 says "binaries"; the files and tools of each role are OD-23), so a closed list would be invented. A reader treats an unknown value as an unknown kind, not as an error. The vocabulary stays open" (cited: ADR-0005 decision 5).
- **What a value is for.** "`type` says what kind of content the blob is, so that a reader can tell blobs apart without fetching them" (cited: ADR-0005 decision 5).
- **Why a value, once written, stays.** "`type` stays the first one given" when the same content is stored again (cited: ADR-0005 decision 6); changing `type` is allowed "never" (cited: ADR-0005 decision 7); a record is never removed (ADR-0005 decision 7), and the history of the data repository "is not rewritten (NFR-2)" (cited: ADR-0005 Context). "It is not raised by a new value of `type`" (cited: ADR-0005 decision 9, of `schema_version`). So a value written under a meaning that later changes, or under a second name for a kind that already has one, stays in every record and every commit that holds it.
- **The siblings.** For `kind` in `events.ndjson`: "A later record that wants lines with another definition **defines a new kind under a name no accepted record has used**"; "**A name is never reused** … This holds also for the name of a kind whose record is reverted" (cited: ADR-0097 decision 2); "The vocabulary of `kind` is the set of kinds whose defining record is accepted", with one index, `ARCHITECTURE/EventKinds.md` (cited: ADR-0098 decisions 2 and 3). ADR-0101 (decisions 7 and 8) and ADR-0102 (decisions 3, 6 and 7) did the same for `step` values and `spend` axes. ADR-0098 Boundaries left "**The `type` vocabulary of `artifacts.json`** (sub-question ⑥)" open as "a parallel question".

## Decision

Terms: **a value** is a value of the member `type` of a record of `runs/<run_id>/artifacts.json`. **Its definition** is what the value names: the kind of content (decision 3). **A defining record** is the accepted record that names a value and states its definition; a value defined by an owner decision has as its defining record the document commit that records that decision (decision 8); that commit counts as accepted while it is not reverted. **A taken value** is a value some record has defined, whether that record is still accepted or has been reverted.

### 1. What the code and the records hold today (observation, binds nothing)

- `hilclaw/artifacts.py`: `validate` checks `type` for the *name* form only (`"type": (str, _NAME.fullmatch, …)` with `_NAME` = `[a-z][a-z0-9_]{0,31}`), and its docstring says "``type`` is checked against no vocabulary"; `add_record` takes `type` from its caller as a keyword argument without a default and checks it by the same rule.
- **No module of `hilclaw/` calls `add_record`**: the only file other than `hilclaw/artifacts.py` that imports the module is `tests/test_artifacts.py`; `hilclaw/layout.py` names `artifacts.json` among the run files and touches no record; no module of `hilclaw/` other than `hilclaw/cas.py` itself stores a blob (`hilclaw/blob_tools.py` calls `cas.blob_path` only and copies nothing). The values in the tests (`example_kind`, `another_kind`, `a_kind_nobody_listed`) are placeholders, as `example_kind` is in ADR-0005's Example ("`example_kind` is not a proposed value of `type`", cited: ADR-0005).
- **No accepted record defines a value of `type`.** A search of `ARCHITECTURE/decisions/` for `artifacts.json` and for `type` finds no stated value of the member. Two records weighed and rejected making a file a blob, and named no value: the verification executable "kept as a blob of the CAS" (ADR-0056 Alternative 4) and the compiler log as "A blob of the CAS", which "needs a `type` no record names" (cited: [ADR-0078](ADR-0078-od18-correctness-check-compiler-log-file.md) Alternative 4). The word `type` names other things in the records — among them the `type` of an objective entry of a spec (`latency_minimisation`, `memory_ceiling`; [ADR-0050](ADR-0050-od6-task-objective-members.md), [ADR-0053](ADR-0053-od8-instance-record-objective.md)) and the `"type"` keyword of a JSON Schema ([ADR-0039](ADR-0039-od18-blob-push-fetch-local.md), [ADR-0069](ADR-0069-od18-correctness-check-request-schema.md)) — none of which is a value of the `type` of a blob record.

### 2. What the vocabulary is

- **The vocabulary of `type` is the set of values whose defining record is accepted.** A record whose `type` is in it says that the blob is content of that value's kind, as the definition states it. A record whose `type` is a value never defined, or a placeholder, has no definition, and a reader treats it as an unknown kind, not as an error (ADR-0005 decision 5, unchanged). A record written under a value whose defining record has been reverted has no definition that this record gives it either; what a reader does with it is OD-11's, as ADR-0098 decision 2 left it for lines of a reverted kind (Boundaries).
- **Today the vocabulary is empty** (decision 1).
- **The taken values are a superset of it**: every value of the vocabulary, every value that a later record says no writer writes any more (it stays in the vocabulary with its definition), and every value whose defining record has been reverted (out of the vocabulary, still taken).
- The placeholders of decision 1 are neither in the vocabulary nor taken; no defining record chooses them, so that the Example of ADR-0005 and the tests never read as records of a defined kind.

### 3. What a defining record states

- **The value**, a *name* of ADR-0001 chosen by decision 8.
- **The content it names, by what the content is**: which bytes are of this kind — for example by their format and what the run uses them for —, stated so that a writer holding a blob can tell whether the value applies without asking which tool, agent role or step produced it. A definition may name the producer that is known when the record is written, as an example, but it does not tie the value to a producer: content of that kind falls under the value whichever tool, agent role or step produces it (decision 6).
- **That no value in the state `defined` or `not written` names exactly its kind; and that no value in the state `defined` names any of its content**, other than the values it replaces by finer or coarser ones and sets to `not written` in its landing commit, and which values those are, if any (decision 6).
- What a defining record does **not** state here: a retention class or its policy (OD-20, OD-29, OD-23), which tool writes the record or when (OD-23), and anything of GC. Where a defining record also decides one of these, it does so under the OD that owns it.

### 4. The rule: the meaning of a value never changes, and a value is never reused

- **The definition of a value is fixed when its defining record is accepted, and it never changes.** It is the definition as that record states it when accepted; a later edit of that record that changes the definition is a change under decision 5 and is not allowed. A later record that wants another kind of content named **defines a new value** under decision 8 and states its definition in full (decision 3).
- **A value is never reused.** A value that no writer writes any more keeps its definition; no record gives it another one. This holds also for a value whose defining record is reverted: records may have been written under it, they are never removed and their `type` never changes (ADR-0005 decision 7), so the value stays taken.
- **How a record is told apart**: by its `type` alone. Two records with one `type` written after its defining record was accepted name content of one definition, in any run's file and at any time (a record written under the string before that is the limit stated in decision 6, last bullet). Nothing else in a record — no other member, and not `schema_version` — says which definition of a value applies; a record has no member for it (ADR-0005 decision 3) and none is added.
- **Why** (this record's own). A record's `type` is fixed for the life of the record (ADR-0005 decisions 6 and 7) and the history is never rewritten (NFR-2), so a meaning changed under an existing value would turn every earlier record of it into a statement about content it does not name, with nothing in the record to tell the two apart. A new value keeps the earlier records true and needs no new member or version.

### 5. What counts as a change

- **Any change of what the value names is a change**, with no distinction between kinds of change: a narrowing (content that was of the kind no longer is), a widening (content that was not of the kind now is), and a change of the format or the use in a run by which the content is told.
- **What is not a change**: a new tool, agent role or step that begins to record content of an existing value's kind, as long as the content is of that definition; code that changes and keeps the definition; a new value being defined; a value that no writer writes any more.
- **Why no distinction** (this record's own): a reader of an older record cannot tell whether the blob it names falls under the narrower or the wider meaning, because the content is not fetched to read `type` (ADR-0005 decision 5); a widening makes earlier records look complete that were written when the wider content went under another value or under none.

### 6. One kind, one value

- **A writer records content of a kind that a value in the state `defined` names under that value**, and no record defines a second value for it, other than by replacing it under the third bullet. A tool contract that comes to store content of such a kind cites the existing value; it defines none. **A kind that a `not written` value names exactly gets that value back**: the record sets its row to `defined` (decision 8) and defines no new value.
- **The values in the state `defined` name disjoint kinds**: a defining record states that no value in that state names any of its content, other than the values it sets to `not written` in its landing commit (decision 3), and is reviewed against the index (decision 7) for it. This is about kinds, not bytes: the same bytes may be content of two kinds ("The same bytes can legitimately be two kinds (an empty file)", cited: ADR-0005 Alternatives, point 6), and ADR-0005 decision 6 keeps the first `type` given.
- **A finer or coarser distinction later** — a value found too wide or too narrow once real binaries exist — is made by new values: the record that defines them sets the row of each value they replace to `not written` in its landing commit (decision 8) and links itself there; the earlier value keeps its definition and its records (decision 4). The kinds of `defined` values stay disjoint; a `not written` value may overlap them. The new values need not name all content of the values they replace: content that none of the `defined` values names has no value until a record defines one, and whether it is still stored as a blob is not decided here (OD-23).
- **What this rule can do**: it keeps two names for one kind out of the accepted records, `defined` and `not written` values alike, provided that every defining record checks the index and is reviewed. **What it cannot do**: stop a caller of `add_record` that passes a string no record defines; nothing in code detects it (decision 9), and such a record keeps its `type` (ADR-0005 decision 7); if the same string is later defined, such an earlier record reads as content of the new definition, since decision 8 searches `hilclaw/`, `tests/` and `ARCHITECTURE/` and not the data repository.

### 7. Where the values are listed: one index, `ARCHITECTURE/BlobTypes.md`

- **There is one list of values, the file `ARCHITECTURE/BlobTypes.md`**, created with this record. It is an **index**, not a second definition: one row per taken value, with three columns — the value, a link to the defining record (with the decision that states the definition), and the state.
- **The states**: `defined` — the defining record is accepted (the value is in the vocabulary); `not written` — still in the vocabulary, and an accepted later record, linked in the row, says that no writer writes it any more (for example when decision 6 replaces it); `reverted` — the defining record has been reverted (out of the vocabulary, still taken). A row is never removed and its value never changes.
- **What the index does not hold**: no description of the content, no producer, no retention class; the defining record is the only source of the definition and wins when the two disagree, and the index is then corrected by a document change, which defines nothing.
- **It has no row**: no value is defined (decision 1).
- **Why a separate index** (this record's own): the word `type` names other vocabularies in the records (decision 1), the records that will define values may belong to several ODs — OD-23 and the tool contracts of OD-18 among them —, so neither the OD-8 adopted lines nor a search finds the taken values reliably, and a reverted record's values are found only by reading it. Decision 6 needs, in addition, a place where the `defined` values can be read side by side against a new definition. One short index serves both.

### 8. How a value enters the index

- **A defining record** chooses a *name* of ADR-0001 that is not in the index and is no placeholder of a record or a test (decision 1), checks that the string is no other name in `hilclaw/`, `tests/` and `ARCHITECTURE/` (as ADR-0101 decision 8 asks of a `step` value), and **adds its row** with the state `defined` **in the commit that lands the record**. A value defined otherwise than by a record (an owner decision) enters by the document commit that records it, in the same way.
- A record that stops a value being written, or replaces it under decision 6, sets its row to `not written` and links itself; a record that lets a writer write a `not written` value again sets it back to `defined` and links itself, the definition unchanged, and only if its kind is disjoint from every `defined` value other than those it sets to `not written` in the same commit (decision 6); a task that reverts a defining record sets the row to `reverted`, and if that record had set rows to `not written`, sets them back to `defined` where decision 6 allows it (their kinds disjoint from every `defined` value) and otherwise leaves them `not written`; a task that reverts a record that only changed the state of rows restores their earlier states, under the same condition.
- No row is added by code, by a test or by a run, and the index is not read at run time.

### 9. Nothing checks a record's `type` against the index

- **No writer and no reader checks a record's `type` against the index**, and this record asks for no such check: `hilclaw/artifacts.validate` and `add_record` keep checking the *name* form only (decision 1), and a reader treats a value it does not know as an unknown kind, not as an error (ADR-0005 decision 5, kept).
- **The guard is the records and their review**: code passes a value to `add_record` only after its defining record is accepted, through a constant that the code task of that record adds where its writer needs it. The review of a defining record catches one that adds no row, reuses a taken value, names any content that a `defined` value names (other than the values it sets to `not written` in its landing commit), or names exactly the kind of a `not written` value.
- **Why ADR-0005 decision 5 is kept** (this record's own): a reader-side check would make a file holding a `reverted` or `not written` value, or a value of a record newer than the reader, invalid, while such records are never removed or changed (ADR-0005 decision 7). A writer-side check would need a copy of the index in `hilclaw/`, a second list that every defining record changes in a code task before the first blob of its kind can be recorded, and with the vocabulary empty it would refuse every call; it would also make `hilclaw/artifacts.py` know kinds, which ADR-0005 decision 5 avoids. Its one gain — a typo refused before it becomes permanent — is weighed again when the first value exists (Boundaries).

### 10. Why the vocabulary part is answered before OD-23

- The ⑥ text joins the vocabulary to "어떤 바이너리가 blob이 되는지" (OD-23). **Which values exist** stays there: every value is defined by a record under decision 3 — normally the one that decides that its content becomes a blob — and enters the index by decision 8. **What a value must state, that its meaning never changes, that it is never reused, that one kind has one value, and where the values are listed** depend on no binary, no roster and no producing tool.
- The reason to answer it now differs from ADR-0098 decision 6, where two kinds already existed and ADR-0097 already required a name not used before: here no value exists, and what makes the rule urgent is ADR-0005 itself. A `type` once written is never changed and the first one given is kept (decisions 6 and 7 of ADR-0005), so the first record written under an ill-chosen value stays in the history (NFR-2); `add_record` exists and takes any *name* (decision 1). The rule therefore has to precede the first value, and it can, because it constrains how values are defined and not which.
- What stays with OD-23 is exactly what the rule cannot give: whether two tools will in fact produce one kind, and so which kinds and values there are. Decision 6 makes sure that, once those are decided, they are recorded under one value each.

## Alternatives considered

| Alternative | Why |
|---|---|
| (a) A vocabulary of values that accepted records define, with one index | **Adopted** (decisions 2 to 8): it needs no value, follows the shape the siblings use (ADR-0098, ADR-0101, ADR-0102), and adds decision 6 for the question ⑥ names, two names for one kind. Its cost is in Consequences. |
| (b) A closed list fixed now (ADR-0005 Alternative 5) | No source gives a value, and which binaries the tools produce is OD-23's (decision 10); a list fixed now would be invented values, and since `type` never changes in a record (ADR-0005 decision 7), every invented value that is later found wrong stays in the records written under it. |
| (c) A check of `type` against a list in `hilclaw/` (at `add_record`, at `validate`, or both) | A check at `validate` or at a reader would make files with `reverted`, `not written` or newer values invalid, against ADR-0005 decision 5. A check at the writer needs a code copy of the index, kept in step with it by a code task per value, refuses every call while the vocabulary is empty, and guards against no failure that occurs today, since no module calls `add_record` (decisions 1 and 9). Left to a later record (Boundaries). |
| (d) Leave `type` open until OD-23 | Each record that makes a binary a blob would choose its value with no rule on what it states, whether its meaning may change, whether a value may be reused or how a second name for an existing kind is avoided — the risk ⑥ itself names — and the first such choice cannot be undone in records already written (ADR-0005 decision 7). The rule needs nothing of OD-23 (decision 10). |
| (e) A value tied to its producer (for example a prefix per tool or agent role) | It would make two tools that produce one kind write two values by construction, the outcome ⑥ is meant to prevent, and it would tie the vocabulary to the roster of OD-23. Rejected by decision 3; a definition may name a producer as an example only. |
| (f) A media type, or a hierarchical value (`<family>_<sub>` with a meaning per part) | A media type: rejected by ADR-0005 Alternative 5 ("nearly every binary would be `application/octet-stream`"). A hierarchy would give each part a meaning, a structure of values that no source asks for, and it would turn a finer distinction into a question of what the parts mean rather than a new value (decision 6); it also fixes a spelling, which decision 8 leaves to each defining record. |
| (g) The list as a section of this record, or of ADR-0005, edited by each later record | A record states its decision when accepted; a section edited by every later record would change the record's text with decisions it does not make (ADR-0098 Alternative (e)), and ADR-0005 is not edited. |

## Consequences

- **No code changes.** `hilclaw/artifacts.py` stays right: it checks the *name* form only and knows no value (decision 9); `tests/test_artifacts.py` keeps its placeholders. A later defining record brings its own code task where a writer needs its value. No code task follows from this record.
- **`ARCHITECTURE/BlobTypes.md` is created** with this record, with the rules of decisions 7 and 8 and no row.
- **For a defining record**: it states the content by what it is (decision 3), checks the index for a `defined` or `not written` value of the same kind and uses that one if there is one (decision 6), checks that no `defined` value names any of its content, other than the values it sets to `not written` in its landing commit (decisions 3 and 6), chooses and checks its value (decision 8), adds the row in its landing commit, and states its A-13 reading. The first defining record also weighs the writer-side check that decision 9 leaves open. A reviewer of such a record checks the row, the disjointness against the `defined` rows and the exact kinds of the `not written` rows.
- **Not edited and now less exact**: ADR-0005 decision 5 ("The vocabulary stays open (Boundaries)"), its Limits ("`type` is not checked against a vocabulary" — still true, and a vocabulary now exists) and its Boundaries ("the vocabulary of `type`"); ADR-0098 Boundaries ("The `type` vocabulary of `artifacts.json` (sub-question ⑥) … this record does not answer it"); ADR-0097 Boundaries and [ADR-0099](ADR-0099-od8-moment-form-of-other-files.md) Boundaries, which list ⑥ as open. No earlier ADR is edited.
- **The cost, stated**: one more document to keep in step with the records; values accumulate, since none is reused; a finer distinction made later splits the records of a kind across values, and a reader that wants the kind across the change must know both; disjointness is a judgement of review, which no code checks; and a caller that passes an undefined string to `add_record` is not stopped.
- **A-13 reading**: document mode; no code, dependency, settings file or schema file changes, and no member, value or version of the data plane is added or changed. The new document indexes no value.
- **Runtime acceptance items**: none.
- **Follow-up (document)**: link `ARCHITECTURE/BlobTypes.md` from the README document table, as `EventKinds.md`, `StepValues.md` and `SpendAxes.md` are.

## Boundaries (not decided here)

- **Which values exist**: which binaries the tools produce, which of them become blobs, and so which kinds there are (OD-23, with the tool contracts of OD-18); whole-model binaries (C-6); datasets (#5 B-8).
- **Sub-question ⑦** (whether a record names the candidate or the attempt), baseline blobs (OD-28), and the class policy (OD-20, OD-29, OD-23).
- **GC** (C-3 follow-up; no OD is registered for it), including whether a GC ever treats blobs by `type`.
- Whether a later record adds a code-side check of `type` at the writer (decision 9 asks for none); any such check would not change how a reader treats an unknown value (ADR-0005 decision 5).
- What a reader of an older `artifacts.json` version does, what it does with records written under a `reverted` value, and migration (OD-11).
- Code, tests, a JSON Schema file, CI, any settings file, and any change to the `HIL-Claw-data` repository.
