## Decision

A sentence is **cited** when a source is named with it. Every other sentence is **this record's own**.

### 1. Scope

- **The Round-Manager** — the main conversation of a turn session (ADR-0118 decision 2) — **of a run of ADR-0120 decision 1, driven through `hilclaw.turn_start`**.
- **The reads**: its run's `STATE.json` and `instance.json`, including telling a fresh run directory (ADR-0120 decision 4). **The writes**: its run's `STATE.json`, the first one (ADR-0120 decision 2) and those within and at the end of a round (ADR-0012 decision 6), `run_status` among them (ADR-0121 decision 3).
- **Outside**: sub-agents and how they reach anything; every other file of the run (`events.ndjson`, `artifacts.json`, `rounds/`, hypotheses, verdicts, cases); other runs; runs outside ADR-0120 decision 1 and sessions not started by the entry. Nothing here is required or allowed of them.

### 2. (a) The means: typed tools of the registry, through the MCP front

- **The Round-Manager reads its run's `STATE.json` and `instance.json`, tells a fresh run directory and writes its run's `STATE.json` only by calling the four tools of decision 3 through the package's MCP front**, naming its run by `run_id` in each request. It does not use a command-line entry through Bash, nor its own file tools on these two files.
- **No `--add-dir`** is given to a turn session for these reads and writes; neither checkout is added by this record. The session's working directory, definition, server and prompt stay as ADR-0118 and ADR-0123 have them.
- **What the rule is and is not.** It is a rule of the definition that the Round-Manager follows. It restricts no read: other files of the data plane may still be read by whatever means a later record gives (S3, premise 1). It takes no tool away from the session: whether a turn session has Bash, Write or Edit at all is the permission means, which stays open (rest of OD-18; PLAN P2-4). By S3 premise 2 it is **not** a write zone and **not** the run's protection against a write into another run (ADR-0123 decision 4); it keeps such a protection possible (decision 5).

### 3. (b) The tools

The names follow the rule of `hilclaw/tools.py`; the MCP names replace `.` by `_` (ADR-0010 decision 4), and no name holds `_`, so the mapping stays reversible.

| Tool (MCP name) | Over | Request | Result | Failure kinds |
|---|---|---|---|---|
| `state.read` (`mcp__hilclaw__state_read`) | `hilclaw.run_journal.read_state` | `run_id` | `state`: the content of `STATE.json` as one JSON object, its members as stored (ADR-0012 decisions 2 and 4) | `invalid_request`, `no_data_root`, `run_file_missing`, `run_file_invalid`, `run_file_unsupported`, `run_file_unreadable` |
| `instance.read` (`mcp__hilclaw__instance_read`) | `hilclaw.instance.read` | `run_id` | `instance`: the content of `instance.json` as one JSON object, its members as stored | the same six |
| `run.fresh` (`mcp__hilclaw__run_fresh`) | `hilclaw.fresh_run.is_fresh` | `run_id` | `fresh`: a *boolean* | `invalid_request`, `no_data_root`, `run_dir_unreadable` |
| `state.write` (`mcp__hilclaw__state_write`) | `hilclaw.run_state_file.replace` | `run_id`, `state`: the whole new content as one JSON object | the empty object | `invalid_request`, `no_data_root`, `state_not_written` |

- **Every request is exactly these members**; any other member is refused as `invalid_request`, as ADR-0039 decision 3 refuses one. `run_id` has the meaning and form of ADR-0015 decision 4; the data root comes from the data-root source and never from the request (ADR-0015 decision 3).
- **The content of `state.write` is one nested member.** So the `round` of the file is not a top-level member of the request and is not read as the `round` of ADR-0015 decision 4, which names what a call is about. The tool function takes from `state` the `round`, the view and the other members that `replace` takes. A `state` that is not valid by ADR-0012 decision 6 at version 1 is refused as `invalid_request` before the data-root source is asked and before anything is written (ADR-0013 step 1; ADR-0015 decision 2). The content written is exactly the content given; nothing is read or carried over (ADR-0013 decision 7).
- **The two reads reuse the kinds of ADR-0019 decision 3** — this record's own extension. ADR-0019 speaks only of the calls of its decision 1, leaves a frame file read at another moment outside (its Boundaries), and says of the four kinds that a tool function raises them "only at the lookup or the selection" (its decision 2). **This record widens that sentence to the reads of `state.read` and `instance.read`**, for which the property it states with it holds as well: such a call appended no line, selected or called no backend, ran no step and consumed nothing. `STATE.json` and `instance.json` are frame files there, and the four situations have the same meaning here: a missing file, an invalid one (a path that is no regular file included), another `schema_version` and a read that fails in the file system get `run_file_missing`, `run_file_invalid`, `run_file_unsupported` and `run_file_unreadable`. For `state.read` the missing file is a failure, not a result, so that it means what ADR-0019 gives it: no state was written for this `run_id`.
- **`run.fresh` reads no file**: it looks at five entries by their known paths, `artifacts.json` and `rounds/` among them, which are no frame files. A check that fails in the file system for a reason other than the entry's not being there is therefore its own kind, `run_dir_unreadable`, not the reserved `run_file_unreadable`, whose meaning is the read of a frame file (ADR-0015 decision 2: no reserved kind for another situation).
- **Two new kinds**: `state_not_written` — a step of the replacement failed in the file system, and `STATE.json` holds what it held (ADR-0013 decision 2, step 5); and `run_dir_unreadable` above. Each is a name of the tool layer, like `blob_unreadable` of `blob.fetch` (ADR-0039), **not a change of the data plane**; neither is reserved.
- **None of the four is journaled.** `state.write` cannot be: the first write is no step of a journaled call (ADR-0120 decision 2). None is a journaled step in the sense of ADR-0011 decision 1: a read costs no limited resource and can be repeated, and the outcome of a write is the file itself.
- **They are tools of the registry beside the FR-10 tools, not FR-10 tools**: FR-10 lists the HW experiment tools (cited: Requirements FR-10), and these run no experiment and select no backend. This record reads ADR-0010 decision 1 and ADR-0015 as covering them as tools of the registry (one tool function, one request and one result, the two fronts, the reserved kinds), not as making them FR-10 tools.
- **The fixed tool set grows by these four, in the source** (`default_registry`), and in no other way (cited: #5 A-12 point 3; `hilclaw/tools.py`). Each is reachable through the command-line front too (ADR-0010 decision 3), for people, tests and scripts; the Round-Manager uses the MCP front.
- **Left to the code slice**: the descriptions and input schemas, the module, the exact conversion between a stored object and the package's values (for example a total above `keys.MAX_INTEGER`), and whether the reads return the parsed object or the bytes' object.

### 4. (c) The place of the run: not needed

**The Round-Manager needs no place of the run**: every tool takes the `run_id`, which its prompt already holds, so ADR-0123 decision 2 (the run id and no place) stands unchanged and its prompt rule is not widened.

### 5. (d) What the means keeps

- **Hook visibility.** A later `PreToolUse` hook can match `mcp__hilclaw__state_write`, read its `tool_input` and so the `run_id`, and tell the calling agent (cited: ADR-0010 decision 6). Comparing that `run_id` with the session's run would need the second channel ADR-0123 left open (its Alternatives (2)); neither is adopted here.
- **Allowlists.** A per-agent allowlist can name `state.write` alone (cited: ADR-0010 decision 3, F3), so a later roster can leave it out of every sub-agent's `tools` and express the single writer of S2 per agent. No allowlist is adopted here (rest of OD-23).
- **NFR-6.** Method A can call the same tool functions or connect to the same server (cited: ADR-0010 decision 2), so these reads and writes of the Round-Manager are calls a node of method A can make without Claude Code's file tools.
- **NFR-1.** Nothing is written into the session directory; the tools read and write the data plane below the data root of the server.
- **ADR-0012 decision 6** is met by `replace`, below the front, and the validity check of ADR-0013 step 1 is code, not the model's reading of the bytes.

| Situation | What follows |
|---|---|

| Neither file is there | `state.read`: `run_file_missing`; `run.fresh`: false; the Round-Manager writes no `STATE.json` (ADR-0120 decision 3); what it reports stays open |
| A turn whose `STATE.json` holds `run_status` `"over"`, or a value it does not know | `state.read` shows it; the Round-Manager begins no round, writes nothing into the run and ends, reporting a value it does not know (ADR-0121 decisions 2, 3) |
| A turn that finds no `run_status`, a stated `round_budget` and `round` at or beyond it | `instance.read` gives `round_budget`; `state.write` writes `run_status` `"over"` with `round` and `budget_spent` copied from `state.read` unchanged, and no round begins (ADR-0121 decisions 3, 4) |
| `STATE.json` missing beside other files of the tree | `run.fresh` is false; no `STATE.json` is written; what the directory means stays open (ADR-0120 decision 4) |
| `STATE.json` invalid, or of another `schema_version` | `state.read`: `run_file_invalid` or `run_file_unsupported`; no member is used, nothing is repaired and the turn does not go on (ADR-0012 decision 6); `run.fresh` is false, so no first write follows |
| The data root cannot be had | `no_data_root` from every tool; nothing is read or written (ADR-0015 decision 3) |
| A Round-Manager names another run's id | The tools serve that run; nothing stops it (ADR-0123 decision 4; ADR-0015 decision 7). A later hook could see the `run_id` (decision 5) |

The rule of decision 2 is a model following its definition: a Round-Manager that writes `STATE.json` with its own Write tool, if it has one and learns a path, is not stopped until a hook or the isolation means exists (S3, premise 2).
