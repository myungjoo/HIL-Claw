## Decision

A value below is **cited** when a source is named with it; every other value is **this record's own** choice — among them the definition of a backend, the backend table and its key, the order of a call, the two reserved kinds, the rule of selection, and the script of the mock.

### 1. Scope and terms

- This record is about **the part that is the same for every HW tool and every backend**. It defines no tool and no backend: no argument, result member, failure kind or `step` value of a tool, and nothing of how any backend carries out an experiment or reaches its target.
- The terms of ADR-0010 decision 1, ADR-0011 decision 1 and ADR-0015 decision 1 are used unchanged.
- **HW tool**: one of the four HW experiment tools `sim.run`, `board.run`, `profiler.collect`, `correctness.check` (cited: FR-10). **Target**: what an experiment is carried out at — a board, a simulator, a stand-in. **Backend**, **operation**, **backend table**: decision 2. **Mock backend**, **script**: decision 5.

### 2. What a backend is and where it sits

- **A backend is the part of the package that carries out the experiments of HW tools at the targets of one `accelerator`.** It has a name, which is that `accelerator` value (the field and its double meaning are cited: ADR-0001 decision 1; `cpu_standin` names both in FR-10 and #5 A-7), and for each HW tool it offers it has one **operation** (which tools a backend offers: decision 3). The **backend table** maps a name to a backend; a name has one backend. Like the registry, the table is built when a registry is built — in the MVP from the source alone, with no option, environment variable or plugin that adds to it (cited for the tool set: #5 A-12 point 3; that the table follows it is this record's). Whether an entry later comes from an onboarding registry is OD-26; a table can be filled from one without changing a tool function (NFR-6).
- **A backend sits below the tool function of a HW tool, and a HW tool reaches a target through a backend only.** A front knows no backend (ADR-0010 decision 3); the table is bound to the tool functions of the HW tools when a registry is built, as a data-root source is (ADR-0015 decision 3).
- **(a) The tool function's part, the same for every backend**: the check of the request and `invalid_request`; the data root; the journaled path where the tool is journaled; the selection (decision 4); the form of the result and the kinds. **The backend's part**: carrying out the experiment at one target and returning to the tool function what the tool's contract lets a backend return.
- **The order of a call of a HW tool**: ① the request is checked; ② the data root is asked (both as ADR-0015 decisions 2 and 3); ③ for a journaled tool, the lookup — an ended or an open identity is answered from the log (cited: ADR-0011 decision 3), and **no backend is selected or called for it**; ④ the backend is selected and the operation of the called tool is looked up; ⑤ for a journaled tool, the start line; ⑥ the operation is called; ⑦ for a journaled tool the end line, and the result. **A call that fails in ④ has consumed nothing at any target and leaves no line.**
- Why ④ lies between the lookup and the start line. *After the lookup*: what an ended step returns "depends on the data plane only" (ADR-0011 decision 3); a stored result must stay obtainable when the table has changed since (a tool layer replaced at a round boundary, NFR-7 ①). *Before the start line*: a missing backend is a fault of registration, like `no_data_root` a fault of configuration; inside the step it would end the identity with a `failure`, and the corrected call would need a further `execution`, which nobody may yet grant (retry part of OD-17). **How this reads ADR-0011 decision 3 and ADR-0015 decision 5**, whose sequence for an identity with no line is the start line, the step, the end line: a call that fails in ④ has not started the step — like a call refused with `invalid_request` or `no_data_root` it leaves the identity with no line, and the same request can be repeated. Neither record is edited.
- **(b) A backend answers exactly the contract of the tool.** It adds no result member and no failure kind of its own; it may use fewer of the outcomes a contract names, never others. What is particular to one target fits a member the tool's contract provides for it, or is not returned. This is what "transport 무관" (FR-10) and "a tool does not depend on the front" (ADR-0010 decision 2) mean one level down: a caller need not know which backend answered, and the cases a contract test runs over the mock are the cases every backend is held to.
- **(c) No outcome depends on state a backend kept** in the front process from an earlier call (cited: ADR-0010 decision 7). A connection or a cache that can be built again is not such state; how long a connection lives, a reservation and a lock of a board are #5 B-2, OD-10 and OD-17 (cited, same decision) and are not restricted here.
- **(d) Who writes the data plane.** The two step lines are the tool function's (cited: ADR-0015 decision 5); a backend is called inside the step and appends neither of them. Who appends a line of another kind stays open as ADR-0015 decision 5 left it (PLAN P2-4). For every other file the fixed inputs name a role and no holder (ADR-0004 decision 4; ADR-0011 decision 4, last bullet), so whether an operation is handed the data root, and who writes a blob or a result file of an attempt, is each tool's contract.
- **What an operation is called with**: the request, and the hw_profile of the call (decision 4). For a call about a run, which hw_profile it is about, and with it which backend, comes from the run and never from the request (decision 4); a call about no run has no rule here (sub-question ⑥). **Which of several targets of one hw_profile a call goes to** — two machines with equal `host` members share one key (cited: ADR-0001 decision 5) — and whether a request may carry anything for that choice, such as a reservation, is how a backend is reached and is not decided here (#5 B-2, OD-10). What else an operation is handed and how the call is written are each tool's contract and the code task's.

### 3. Which tools go through a backend, and what one backend answers

- **The four HW tools go through a backend.** Which part of a tool's work is its backend's is the tool's contract — for `correctness.check` in particular the split between the one harness (FR-9) and the backend.
- **`blob.push` and `blob.fetch` are not HW tools**: they carry out no experiment at a target, and nothing here applies to them but the reservation of the two names below. The "backend" C-3 names for them is a store; it and their meaning on one machine are #5 B-2 and A-3.
- **A backend offers the operations it has; the frame requires none.** Whether every backend must offer all four is not decided: a HW onboarded with a simulator only is OD-26.
- **Two further reserved kinds** (in the sense of ADR-0015 decision 2: one meaning in every tool, raised for no other situation). Only a HW tool raises them, and no tool of the registry — `blob.push` and `blob.fetch` included — uses either name with another meaning:

| `kind` | Meaning, in every tool |
|---|---|
| `no_backend` | The backend table has no entry for the `accelerator` of the hw_profile of the call; nothing was consumed, no line appended |
| `not_offered` | The backend selected for the call offers no operation for the called tool; nothing was consumed, no line appended |

- Why reserve, and why two: neither situation belongs to one tool, and a caller acts differently on each — after `no_backend` no HW tool can work for that hw_profile with this table (in the MVP: the source that process loaded), after `not_offered` the tools that backend does offer can (the round loop of a sim-only target, OD-26, would rest on it). **How this reads ADR-0015 decision 2**: its table is "the part of every tool's contract that is common, not a closed list"; a later record of the frame may add to the common part as long as no tool's contract uses the name, and none exists. ADR-0015 is not edited.
- **Which of the four the `cpu_standin` backend offers is not carried by the fixed inputs.** #5 A-7 names one "run" in its loop, FR-1 has a sim step and a board step, and [ADR-0007](ADR-0007-od13-measurement-policy.md) decision 1 speaks of "the `cpu_standin` execution point" beside "a simulator and a board". Registered as sub-question ⑦.

### 4. How the backend of a call is selected

- **Nobody names a backend.** It is not a member of a request, not chosen by the calling agent, not read from the configuration or the environment of the front process, and not kept by a process.
- **The backend of a call follows from the hw_profile the call is about: it is the entry of the backend table under the `accelerator` of that hw_profile record.** No other key field selects a backend: a compiler upgrade or another host is a new key (cited: ADR-0001 decision 5) of the same backend.
- **For a call about a run, the hw_profile it is about is that of the run the request names** (`run_id`, ADR-0015 decision 4) — the one selected when the instance was started (cited: FR-14 ④, UC-1 step 1) — **read from the data plane at each call**. Which hw_profile that is is therefore the same through both fronts and depends on nothing kept (ADR-0010 decision 7); the table each process holds is decision 6. **The request of a HW tool whose call is about a run therefore carries `run_id`**, with the meaning and form of ADR-0015 decision 4, whether or not the tool is journaled.
- Why the run and not the request: a request that named a backend or a hw_profile would let the calling agent measure the attempt of one run at another target, and none of the members ADR-0011 decision 3 fixes for the two lines of a step names the target that was measured — the result would enter the knowledge of the run's hw_profile with nothing showing where it was measured. This is the reason #5 A-7 gave for keying `cpu_standin` separately, and the reasoning of ADR-0015 decision 3 for the data root.
- **What the fixed inputs do not carry: where a run states its hw_profile.** `instance.json` holds "What the instance was started with" (ADR-0004 decision 1) and has no fixed member (PLAN P1-8). The `spec.json` of an attempt embeds the record in full ([ADR-0002](ADR-0002-od6-codegen-spec.md) decision 2), but it exists per coder call only and is a copy composed by a role (OD-23). **This record defines no member of either file and chooses neither**: sub-question ⑥. The rule above is complete without it — a function from a hw_profile record to a backend — and the place is the one thing a code task must be given.
- A hw_profile that cannot be read or is no valid record is not `no_backend`: the run cannot be used, and that kind is open (sub-question ④ of ADR-0015).
- A call about no run — the smoke test of UC-0 step 5, whose existence is OD-26 — has no rule here (sub-question ⑥).

### 5. The mock backend

- **(a) What it is**: a backend of the package behind which there is no hardware, no simulator, no other process and no network; it is always present (cited: FR-10, #5 A-7). "Always" is read as: it is an entry of the backend table bound in every registry that `default_registry` builds, so both fronts have it.
- **(b) How it is selected: by the rule of decision 4 and in no other way.** Its entry has a name reserved for it — no hardware, simulator or stand-in is registered under that name — and a call reaches it only through a hw_profile that carries the name as its `accelerator` (decision 4). A second way in (a member of a request, a variable of the front process) would be a way to answer a call about a real target with a mock outcome. **What keeps its outcomes apart** is what keeps `cpu_standin` apart from an NPU (cited: #5 A-7): a run measured at the mock is about a hw_profile of its own, its knowledge is keyed under it, and the name of that key directory begins with the reserved name (cited: ADR-0001 decision 3). The spelling of the name is the code task's — the sources give "mock" as a word, not as a value of a record — and this record names **no value** of such a record; a test writes its own.
- **(c) How it is told what to produce: by a script it is bound to when the backend table is built.** A **script** is a function from a call — the called tool, the request, the hw_profile — to what the operation does; it is asked when the operation is called (⑥ of decision 2). A test builds a registry whose mock is bound to the script it needs, as it binds a data-root source of its own (ADR-0015 decision 3). The default registry of the two fronts holds the mock bound to **one script fixed in the source**; what that script answers for a tool is written with that tool's contract.
- **(d) What a script must be able to express**, for every HW tool the mock offers: everything a backend may return under the tool's contract — a result, a result that reports a failed experiment (ADR-0010 decision 4), and each tool-failure kind the contract lets a backend raise; and, for a journaled tool, the one of the three death points of ADR-0015's Walk-through that a backend can cause — the death of the process while the operation runs, after the start line and before the end line. The other two lie in the journaled path. **The two kinds of decision 3 come before any operation is called and are no matter of a script**: a test produces `not_offered` with a table whose mock was built without the operation of that tool, and `no_backend` with a table without the entry. The mock of the default registry offers every HW tool of that registry; it gains the operation of a tool with the record of that tool's contract. **It lists no fault of a real board or simulator** (OD-10, #5 B-2, B-3): when a tool's contract names a kind for one, the class of tool-failure kinds covers it.
- **(e) The outcome of a mock call depends on its script and its call alone**: no clock, no random source, no counter, no file of its own. A member a real backend would measure is derived from the call by a rule fixed with the tool's contract. "Fails first, then works" is therefore not a count of calls, which would be kept state (decision 2 (c)); for a tool whose request carries `execution` it is written over that member — a further execution is a new identity (cited: ADR-0011 decision 3).
- Not decided: how the mock of the default registry is made to inject a fault in a live session, where no test builds the registry (sub-question ⑧).

### Walk-through

Placeholders: the journaled HW tool `example.tool`; `acc` and `mockname` stand for two `accelerator` values and name no real one. The request is `{"run_id": "r1", "round": 3, "candidate": 2, "attempt": 1, "execution": 1, …}`.

| Moment | Through either front (the same code below it) |
|---|---|
| The call arrives | The front decodes the request, looks the name up and calls the tool function; it knows no backend |
| The request is checked, the data root is asked | As in ADR-0015: `invalid_request`, `no_data_root`; no backend is touched |
| The lookup | Ended: the stored `result` or `failure` is returned. Open: `step_open`. In both, nothing is selected and no operation runs |
| No line: the selection | The tool function reads the hw_profile of `r1` (the place: sub-question ⑥) and looks its `accelerator` up in the backend table |
| The backend cannot be selected | The table has no entry `acc` → `no_backend`; nothing appended; the same request can be repeated once the table has the entry |
| The backend does not offer the tool | The entry `acc` has no operation for `example.tool` → `not_offered`; nothing appended |
| The operation is called | The start line is appended and complete; the operation is called with the request and the hw_profile; it carries out the experiment at its target and returns; the end line is appended; the call returns what the end line holds |
| The hw_profile of `r1` has the `accelerator` `mockname` | The same path. The script is asked with the tool, the request and the hw_profile and answers a result, a result that reports a failed experiment, or a tool failure of the contract; it reads no clock, counter or random source (decision 5 (e)) |
| The script ends the process | The step is open; a repeated call through the other front is `step_open`, and no operation runs |

### 6. Limits

- **No access control** (ADR-0010 decision 8). A caller cannot name a backend, but it can name another run (ADR-0015 decision 7), and whoever can write the place of sub-question ⑥ changes the backend of a run.
- **The target reached is not checked against the key.** The selection reads `accelerator` only; that the machine, compiler or board a backend reaches is the one `revision`, `toolchain` and `host` describe is not established here (ADR-0001 Boundaries "How the values of the hw key fields are obtained", OD-26, #5 B-2). A result can still enter the knowledge of a key that describes another machine.
- **A backend that does not answer the contract** — another member, another kind, a reserved kind for another situation, kept state — is not detected by the frame.
- **Two calls at once at one target**: OD-10 and the rest of OD-17.
- **A mock outcome taken for a real one**: it is told apart by its hw_profile only. A result says which backend produced it only if a tool's contract gives it such a member.
- **Two processes, two tables**: an MCP server runs the table of the source it loaded at its start (ADR-0010 decision 7), a command-line call the table of the source as it is now.

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 2 | A backend per hw_profile key | A compiler upgrade or another host is a new key (ADR-0001 decision 5); the table would change with every registration, which is OD-26. |
| 2 | A backend per execution point (one for the simulator, one for the board of an accelerator) | The called tool already says which experiment is meant, and UC-0 registers both accesses with one hw_profile. |
| 2 | The selection inside the step, after the start line | See decision 2: a missing backend would use up the identity. |
| 2 | The selection before the lookup | A stored result would be unobtainable while the table lacks the entry. |
| 2 | A backend may add result members or kinds of its own | A caller and a contract test would have to know the backend; "transport 무관" would hold for no tool. |
| 3 | No reserved kind; each tool names the two situations itself | See decision 3; a conformance test could not recognise them without knowing the tool. |
| 3 | One kind for both situations | A caller could not tell "nothing works for this hw_profile" from "this backend does not offer this tool". |
| 4 | A member of the request names the backend | See decision 4: the calling agent chooses where a run is measured. |
| 4 | A member of the request names a hw_profile key (`hilclaw.key_records.load_hw_profile` could read it today) | The same, unless it is compared with the hw_profile of the run — and then the run's is the source. |
| 4 | The configuration or the environment of the front process names the backend | One backend for every run of a process; two fronts could disagree (ADR-0015 decision 7 "Two environments"); a member of `hilclaw.config.json` is not this record's to add. |
| 4 | Bound when the registry is built, as the data-root source is | The table is; which entry a call uses cannot be, since one process serves runs of several hw_profiles. |
| 5 | The mock is selected by a member of the request or by the front process | See decision 5 (b). |
| 5 | The mock exists only in registries a test builds | FR-10: the package always has it; layer 1 could never be run against it. |
| 5 | A member of the request tells the mock what to produce | The schema of a real tool would carry a member only one backend reads (against decision 2 (b)), and an agent could set it. |
| 5 | The environment of the front process tells it | Kept in a process: an MCP server could not be told between two calls, and the two fronts could differ. |
| 5 | A file of the data plane tells it | A data-plane schema; it may become the answer to sub-question ⑧ in a record that may define one. |
| 5 | Values of the mock's hw_profile record tell it (`revision`, `ext`) | It would give meaning to values of a key record, which no source gives. |

## Consequences

- **What the conformance tests of P1-1 can check of any backend** with this frame and ADR-0015 decision 6, by the same cases over each backend that offers a tool, through both fronts: that a refused request and a failing data-root source never reach a backend; that `no_backend` and `not_offered` leave the data plane untouched; that an ended and an open identity are answered without a backend; that every outcome is one the tool's contract names; and, over the mock, each class of decision 5 (d). Of a real backend the classes can be compared, not the measured values.
- **Code slices that can now be cut** (each within the size cap): ① the backend table, the selection as a function from a hw_profile record, and the two kinds beside the five of `hilclaw/tools.py`; ② the mock backend and its scripts; ③ the path of a HW tool over a backend, checked through both fronts by a test-only tool with the mock, as T-0055 did for the journaled path. Slice ③ takes the reader of a run's hw_profile as a parameter until sub-question ⑥ is answered. `hilclaw.journaled_step.run` has no place between its lookup and its start line today; slice ③ gives it one or builds the order of decision 2 otherwise.
- **Sentences of the code that then change**: in `hilclaw/tools.py`, the comment "The reserved kinds (ADR-0015 decision 2)" and, in the docstring of `default_registry`, the parameter list if the table is built there; in `hilclaw/journaled_tool.py`, the three-step order of a call, if the path of a HW tool is built on it.
- **Later records**: the contract of each HW tool, the mock's operation and default script for it, and the mechanism of the `cpu_standin` backend. PLAN P1-1 stays open.
- No sentence of UsageCases became false. **Not edited and now less exact** (follow-ups): ADR-0015 decision 6 ("the next record's, with the first tool") and its Consequences ("Then the record of the first tool with the mock backend") — this record came without a tool; the table of ADR-0015 decision 2, which no longer holds every reserved kind; the sequence of ADR-0015 decision 5 and the "no line" case of ADR-0011 decision 3, which for a HW tool have the selection before the start line; the provisional derivation in Requirements C-7 ("LAN 도구 접속은 FR-10 백엔드 선택에 따름") — in the terms of this record the selection reads `accelerator` only, and local or LAN is how a backend is reached.
- **A-13 reading**: document mode; no code, dependency, settings file or schema file changes. The record continues the interface between layer 1 and layer 2 and the inner structure of layer 2; it names no member of a data-plane file or of `hilclaw.config.json`, and the key records keep ADR-0001 as it is.
