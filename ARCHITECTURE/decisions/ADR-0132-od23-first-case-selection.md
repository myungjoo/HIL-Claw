## Decision

A sentence is **cited** when a source is named with it. Every other sentence is **this record's own**.

### 1. Scope

- **The selection work of a round ≥ 1 of a run of ADR-0120 decision 1**: forming the round's hypotheses (FR-17) and writing its `rounds/<RRRR>/decision/hypotheses.json` (ADR-0059 decision 1), and the order of that write against the round's other steps.
- **Outside**: round 0, which has no selection and no record (ADR-0059 decision 5); `decision/decision.md` beyond decision 2's consequence; which technique ids a round's specs carry and how they reach the coder-driver (Boundaries); everything under Boundaries.

### 2. (a) The holder: the `technique-selector` sub-agent

- **The Round-Manager delegates the selection work of a round ≥ 1 to one sub-agent of its turn session, `technique-selector`, which holds the selection role of ADR-0004 decision 4** for these runs. The Round-Manager forms no hypothesis and writes no hypothesis record itself.
- **Why a sub-agent** (K2 row): forming a hypothesis and choosing its basis is judgement, which K2 condition 4 keeps from no sub-agent — the converse of the promotion, which ADR-0133 decision 2 holds inline because it is determinate (cited). The agent that writes the record then holds no `state.write`, `round.end` or `run.commit`, and its reading of earlier rounds, attempts and cases stays out of the Round-Manager's context, as K2 meant.
- **The reload cost of the OD-23 note, weighed.** One more fresh context per round ≥ 1, and the reads it makes, is accepted for the reasons above. Inlining would save that context but none across rounds: every turn is a fresh session process (cited: ADR-0118 decision 2), so the Round-Manager starts each round fresh in any case.
- **`decision/decision.md`, the role's other file** (cited: ADR-0004 path table), **has no writer in these runs** until a record gives one: no record gives its content or form, so no tool could check it, and the selector holds no file-writing tool (decision 3; K4). For these runs the "왜" of FR-11's "어떤 기법을 왜 선택했는지" is read as recorded by the `statement` and `basis` of each hypothesis; the "어떤 기법" is what the round's specs carry (cited: ADR-0151 decision 2 (b)), and a hypothesis names no technique (cited: ADR-0059 decision 3).

### 3. Its tools

- **The technique-selector's `tools` list is exactly `Read`, `Grep`, `Glob`, `mcp__hilclaw__state_read`, `mcp__hilclaw__instance_read`, `mcp__hilclaw__hypotheses_read`, `mcp__hilclaw__checks_read` and `mcp__hilclaw__hypotheses_write`** (decision 4). The reads give it the run's state and instance — its `injections` among it — the records of earlier rounds, and the check results and standing of earlier attempts. Reading is not restricted (K4 premise 1).
- **No file-writing means and no shell**: no `Write`, `Edit`, `NotebookEdit`, `Bash` or delegating tool. Every entry is one `turn_permissions` accepts, so the session pre-approves the list by derivation with no change of ADR-0139 (cited: ADR-0139 decision 3), and the built-in set stays `Agent`, `Read`, `Grep`, `Glob` (cited: ADR-0139 decision 4).
- **`hypotheses.write` is held by the selector alone.** No other agent file and not `ROUND_MANAGER_TOOLS` lists it, so the caller check refuses its call by the Round-Manager or any other sub-agent (cited: ADR-0146 decisions 2, 3 and 6) — the separation ADR-0139 decision 5 found missing, held by a hook rather than a prompt. Whether a session honours the list is item (xxiii).
- **`Skill` is not listed**: the session has no `Skill` tool (cited: ADR-0139 decision 4; ADR-0150 Context, its reading of C2). Later reads are added by the records that create them (decision 5; Boundaries).

### 4. What writes the record: the registry tool `hypotheses.write`

| Part | Content |
|---|---|
| Name (MCP name) | `hypotheses.write` (`mcp__hilclaw__hypotheses_write`); the name holds no `_`, so the mapping of ADR-0010 decision 4 stays reversible |
| Request | Exactly `run_id` (ADR-0015 decision 4) and `record`: the whole content of the file as one JSON object; both required; any other member, or one missing, is refused |
| Result | The empty object |
| Checks, in order | ① the request, and `record` encoded into bytes that `hilclaw.hypotheses_file.parse` admits — round 0, another `schema_version` and every other refusal of `parse` among it — whose `run_id` is the request's (`invalid_request`, ADR-0015 decision 2); ② the data root (`no_data_root`); ③ the run's `STATE.json` read and parsed (`run_file_missing`, `run_file_invalid`, `run_file_unsupported`, `run_file_unreadable`) and its `round` equal to the record's (`round_not_current`); ④ **only when the record's `cases_read` holds an entry**, the rules between the record and the cases of its key, by the steps of `check_run` taken one by one so that their failures can be told apart: the read of `instance.json` (the four `run_file_*` kinds, as `instance.read` names them), any other failure of the file system in the lookup (`cases_unreadable`), a broken rule (`cases_mismatch`); ⑤ the write by `hilclaw.hypotheses_file.write` (`hypotheses_exist` for a taken final name, `hypotheses_not_written` for any other failure of the file system) |

- **It admits exactly what the validators on `main` admit**, whatever they admit when it runs: `parse`, and for a record that names cases `check_run`. It neither narrows nor widens `hypotheses.json`: an `injected` entry is admitted as `hilclaw.hypotheses` admits it, and the rules between files of ADR-0075 decision 3 and the rules of conduct of ADR-0112, which no code checks, are not held (cited: ADR-0112 decision 1, "nothing refuses to write it"). It does not hold `candidates` against `instance.json` or the specs, or a `ref` against the tree (ADR-0059 Boundaries; OD-8 ㉕).
- **③ is a precondition of the call, not a rule of the file**, held as `case.write` holds it (cited: ADR-0133 decision 3): the record is that of the round in progress (cited: ADR-0012 decision 3). A record for an earlier round would follow its experiment and one for a later round would precede the verdicts between, both against ADR-0059 decision 1's "before the experiment". `spec.write` does not hold its round so (cited: ADR-0151 decision 3), for reasons of the spec's order, which stays open there.
- **④ is skipped when `cases_read` is absent or empty**: such a record holds no `case` entry (cited: ADR-0073 decision 2), so no rule between files applies.
- **Every check before the write creates nothing**, so a refused record can be corrected and sent again. **A taken name is answered `hypotheses_exist`**, nothing replaced and the file under the name not read (cited: ADR-0059 decision 1).
- **Kinds.** Reused with their meanings: `invalid_request` and `no_data_root` (ADR-0015 decision 2); the four `run_file_*` kinds (ADR-0019 decision 3) for `STATE.json` and `instance.json` — **this record widens ADR-0019 decision 2 to these two reads**, as ADR-0124 decision 3 and ADR-0133 decision 3 did, and the property holds: such a call appended no line, selected no backend and wrote nothing; `round_not_current` of ADR-0133 decision 3. **None of the `hypotheses_*` kinds of ADR-0129 is reused**: they name failures of reading the file, which this tool never reads. **New**: `cases_unreadable`, `cases_mismatch`, `hypotheses_exist` and `hypotheses_not_written`, each a *name* of ADR-0001 decision 1, formed like `verdicts_mismatch`, `verdicts_exist` and `verdicts_not_written` of ADR-0128 decision 6 on purpose. Searched on 2026-10-26 in `hilclaw/`, `tests/`, `orchestration/` and `ARCHITECTURE/`: none occurs. They are names of the tool layer, not a change of the data plane; none is reserved.
- **Not journaled**: it costs no limited resource and its outcome is the file (as `verdicts.write`, ADR-0128 decision 6). It joins `default_registry` in the source and in no other way (cited: #5 A-12 point 3).
- **Left to the code slice**: the module, the description and input schema, and the encoding of `record` into the written form `hypotheses_file.write` requires (as `verdicts.write` fixes one, an observation).

### 5. The lookup output: a later read tool

- **The technique-selector reaches the output of the lookup of ADR-0073 decision 1 through a typed read tool of the registry that takes the `run_id`**, added to its list by the record that defines it — the case-lookup work of PLAN P2-7, which gives its name, result and kinds, how the lookup's reports are carried and whether a selection goes on after one (cited: ADR-0073 Boundaries).
- **`hypotheses.write` holds what a record says of cases** (check ④) but cannot give the selection the cases to read, so it is no answer to this point.
- **Until that tool exists**, the selector's definition has it write no `cases_read` and no `case` entry — a fixed rule of decision 7, not a refusal. An absent `cases_read` records no identification, never that no case was read (cited: ADR-0073 decision 3). ADR-0073 decision 1's input is then not met for these runs (Consequences).

### 6. When the record is written, and its presence

- **In a round ≥ 1, after step 1 of "The round steps" (`key.store`, ADR-0134 decision 5) and before any spec write or coder delegation of the round**: (2) the Round-Manager delegates the selection to the technique-selector; (3) when that sub-agent has returned, whatever its report says, the Round-Manager calls `hypotheses.read` with its run id and the round; (4) **only when that call returns the round's record do the round steps go on** to a spec write or coder delegation (P2-1).
- **When the read fails**, with any kind, the Round-Manager reports the kind in one line and comes to the stop: it writes nothing further, calls `run.commit` as "The end of a session" says and ends the session, the round not ended (cited: ADR-0143 decisions 2 and 7). The next turn goes on with the same round (cited: ADR-0012 decision 3); under these steps it delegates the selection again, which meets `hypotheses_exist` if a record was written, and goes on with that record. Whether a turn that re-enters a round skips the delegation, and any bound on turns that fail alike, are OD-17's and OD-19's.
- **Why this order**: a hypothesis states what an experiment is expected to show before the experiment (cited: ADR-0059 decision 1), and a spec write is that experiment's first step; a record written after a spec or kernel exists could be fitted to it (NFR-2). Reading the record rather than the report keeps the round off another agent's account (K2 condition 3). It also means every round that reaches promotion has a record, which a case needs (cited: ADR-0133 decision 4).
- **The Round-Manager gets `mcp__hilclaw__hypotheses_read`**, for step (3), with the reasoning of ADR-0129 decision 3; ADR-0129 decision 4 left its use to the round steps. It joins `ROUND_MANAGER_TOOLS` in the code slice that edits the prompt (cited: ADR-0139 decision 3).
- **What "가설 없는 기법 선택을 허용하지 않는다" (FR-17) becomes for these runs**: the selection's only write is the record, through a tool that admits only a valid record of the round in progress and that only the selector holds; and no spec write or coder call of a round ≥ 1 begins before the record is readable. The second is a rule of the Round-Manager's definition: a hook that refuses `spec.write` or `coder.run` for a round without a record is the rest of OD-18's (Boundaries).

### 7. The delegation, the report and the definition

- **The delegation message names the run id and the round, and no place** (ADR-0123 decision 2, as ADR-0128 decision 4 has it for the evaluator). The run it names is the session's run (ADR-0123 decision 4).
- **The report** is one final text message: one line per tool request, naming the tool and the result or the failure kind, and for a written record one line per hypothesis `id` with its `tested_by`. The message is not the record; the file is (K2 condition 3).
- **The definition is `orchestration/agents/technique-selector.md`**, copied into the session directory by `LAYOUT` (cited: ADR-0118 decision 5), with `name` `technique-selector` and the `tools` of decision 3; it names no model and sets no `permissionMode` (as the other two definitions; ADR-0139 decision 3). Its fixed rules: every request carries the run id it was given; write the record of the round it was given and nothing by any means but `hypotheses.write`; on `invalid_request` or `cases_mismatch` correct the record and send it again, and on any other kind send nothing further, report the kind and end (as `evaluator.md` does for `verdicts.write`, an observation); write no `cases_read` or `case` entry while no lookup tool is in its list (decision 5); **keep ADR-0112 decisions 2 and 3** — a system hypothesis in every round where one can be recorded, and the owner's pace for untested written inputs — as rules of conduct (cited: ADR-0112 decision 1 and Consequences); request no check, measurement, spec or coder call; report as above.
- **The Round-Manager's definition** gains the steps of decision 6 and `technique-selector` among the agents it delegates to with `Agent`.
