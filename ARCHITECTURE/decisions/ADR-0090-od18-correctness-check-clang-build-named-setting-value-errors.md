## Context

- ADR-0089 left open every pre-start `ValueError` of `build` with no `parameter`, because an operation that sees only the class cannot tell a refused setting (its V2 to V7) from the no-kernel-source error of `build_verification_executable` or from what `build` passes on from `subprocess`; it named a `parameter` on V2 to V7 as the way out, "a later record then places them" (cited: ADR-0089 decision 5). Task T-0274 (PR #174, `ecc319f`) made that change and placed nothing in a row.
- **Observations at `ecc319f`** (no code is bound):
  - **N1. What is named now.** The docstring of `build`: "any `TypeError` or `ValueError` (including a subclass such as `UnicodeEncodeError`) from the checks of `timeout_s`, `flags`, `trailing_flags`, `compiler`, `env` and `cwd`, including one that Python itself raises inside a check such as for a value that cannot be iterated, is raised with the attribute `parameter` set to the name of that parameter" (cited). Each of the four checks runs inside `_parameter(name, (TypeError, ValueError))`, which sets `parameter` on the caught object and re-raises it unchanged. So V2 to V7 of ADR-0089 P3 now carry `"timeout_s"` (V2, V3), `"compiler"` (V4, and V6 or V7 for a compiler part), or `"flags"` or `"trailing_flags"` (V5, and V6 or V7 for a flag). So does a `ValueError` that the code of a handed object raises inside one of these checks, for example while `tuple` iterates the flags or while a value of `timeout_s` is compared; and one Python raises in the search for the compiler (`shutil.which`, inside the check of `compiler`), which this record did not read as possible or impossible.
  - **N2. The order is unchanged** (cited: ADR-0089 P1): `timeout_s`, `flags`, `trailing_flags`, `sources`, `output` and its path tests, `compiler`, `env`, `cwd`; then the temporary name and the start. Every check of N1 ends before a compiler process is created. `CompilerNotFoundError` is a `LookupError`, not a `ValueError`, and is not tagged.
  - **N3. What stays unnamed.** "any `ValueError` from the checks of `sources` and `output`, such as the one for no source, and a `TypeError` or `ValueError` from anywhere else, such as binding the call or creating the compiler process, carry no `parameter`" (cited: the docstring of `build`). Read from the code, the pre-start `ValueError`s with no `parameter` are: (U1) no source; (U2) one raised inside the check of `sources` by Python or by a handed object's code (iterating the sources, a source's `__fspath__`, forming its absolute path; whether its path tests can raise one this record did not read); (U3) one raised while the output path is formed, where only a `TypeError` is given a `parameter`, or while it is tested, where nothing is (whether a test can raise one this record did not read); (U4) one from after the checks and before or at the start, including what `build` passes on from `subprocess` (an `env` with no `items` method is "left to `subprocess`" — cited; which class `subprocess` then raises was not read); and in `build_verification_executable` (U5) its own for no kernel source and (U6) one raised while it makes a tuple of `kernel_sources`, where only `TypeError` is tagged.
  - **N4. Through `build_verification_executable`.** It calls `build` with the program source first, so U1 cannot arise through it (cited: ADR-0089 P4); U2 to U6 can. It passes on what `build` raises unchanged.
  - **N5. `compiler_version`** raises the errors of `timeout_s` and `compiler` "except that they carry no `parameter`" (cited: its docstring). No module of `hilclaw/` besides `clang_build` calls it, and no check of `correctness.check` does (cited for the latter: ADR-0089 P5).

## Decision

### 1. Scope and terms

- A call of `correctness.check`, the six kinds, S1 to S10 and the keeper, as ADR-0087 decision 1 has them. **A named `ValueError`** is one that carries a `parameter` (N1); **an unnamed `ValueError`** is one of U1 to U6 (N3). The operation reads the class (`isinstance`, so a subclass such as `UnicodeEncodeError` counts) and `getattr(error, "parameter", None)`, on the reading of ADR-0087 decision 2: what it observes is what the function states of the error. An unnamed error that a handed object's code raised with a `parameter` of its own would be read by what it carries; such objects are the backend's or the operation's own, and this record does not guard against them. **The mock** builds nothing and is unchanged.

### 2. A named `ValueError` of the four settings is S4, `settings_refused`

- **The operation raises a `ValueError` whose `parameter` is `"timeout_s"`, `"flags"`, `"trailing_flags"` or `"compiler"` as S4, `settings_refused`.** The four are "the backend's own" (cited: ADR-0060 decision 3), and ADR-0060 decision 4 places "a `ValueError` or `TypeError` for a setting — a time limit, a flag, the compiler — … → S4, whether the setting is refused for its value or for its type" (cited). With `parameter` the operation now sees what the error is for, which ADR-0089 decision 5 found it could not see from the class.
- **Each case.** V2, a time limit that is no positive finite number, and V4, an empty compiler prefix, and V5, a flag that sets the output, are named in the S4 row itself (cited: ADR-0060 decision 4). V3, a time limit above (2**31 − 1) / 1000 s, V6, a NUL in a flag or a compiler part after the first, and V7, the `UnicodeEncodeError` on POSIX for such a flag or part, are refused for their value; the row's head, "A setting is one the functions refuse" (cited), covers them. All six are found "before the process the refused setting belongs to is started" (cited: same), as no compiler process exists yet (N2).
- **One raised inside a handed object's code, or by Python inside a check** (N1), is read as ADR-0087 decision 3 read the `TypeError` of the same four checks: the check could not take the value as the setting it must be, and the same setting gets the same answer whichever code raised. **The cost**: a fault in the code of a handed object — or, if the search for the compiler can raise one, a property of the machine's `PATH` — is answered as a refused setting; the handed objects are the backend's own settings, so S4 still "follows from the backend's own settings" (cited: ADR-0060 decision 4). An error that such code raised already carrying a `parameter` is overwritten by the check (N1), so the name the operation reads is the check's.
- **With ADR-0089 decision 2**, a named `TypeError` or `ValueError` with `parameter` `"env"` is S4 as well; the operation's test for S4 is one class test and one name test.

### 3. An unnamed pre-start `ValueError` stays open, narrowed

- **What can reach the operation**: U2 to U6 (N4). U5 the operation rules out by its own step, as it knows it handed a non-empty compiled set (cited for the step: ADR-0060 decision 4, "An operation places such an error by the step of its own at which it met it"; ADR-0089 decision 5).
- **What is left is no longer a refused setting of `build`'s checks.** U2, U3 and U6 arise while an argument the operation forms is checked — the sources, the output path, the kernel sources (cited: ADR-0087 decision 1; ADR-0056 decisions 3 and 4) — and on ADR-0089 decision 3's reading a `ValueError` for such an argument would be no row. U4 holds what `build` passes on from `subprocess`, which "was not read" (cited: ADR-0060 decision 4) and stays open (cited: ADR-0083 decision 2); it may hold a setting that `subprocess` refuses with a `ValueError`, which would be S4 by its meaning — whether one arises, for example for an `env` with no `items` method, this record did not read.
- **So this record places no unnamed `ValueError`.** The class still holds two rows — no row for U2, U3 and U6, S4 or something unread for U4 — and no step of the operation's own tells them apart. Reading all of them as no row would read U4 into a row unread, the stop ADR-0087 decision 5 and ADR-0089 decision 5 kept. Until then an operation that lets one pass is answered `operation_answer_invalid` (cited: ADR-0045 decisions 4 and 5); that is what the landed rules do, not an answer of this record. **The cost**: a setting that only `subprocess` refuses with a `ValueError`, if one arises, gets no S4.
- **What would let it be placed** (named, not decided): a `parameter` on a `ValueError` of the checks of `sources` and `output` and of the tuple of `kernel_sources`, as T-0274 did for the four settings; U1 would then carry `"sources"` as well, and what stays unnamed would be U5 and U4, of which the operation must place only U4, as it rules out U5 by its own step. That is a code task's change; this record binds none.

### 4. `compiler_version`

- **It stays a Boundary**: no check of `correctness.check` calls it (N5), so its unnamed errors reach no operation of a check.

### 5. No log, and the message

- **No log.** Every error of decision 2 is raised before a compiler process exists (N2), and S4 "found before the build" starts no compiler, "so they have no log" (cited: ADR-0078 decision 2); the operation hands nothing to the keeper.
- **The message of `settings_refused`** may say which setting it was — the operation has it from `parameter` — and of which kind the error was, and shows "no text of an error, no value of a setting" (cited: ADR-0060 decision 5). So it is not the message of the `ValueError`, which for V2 and V5 shows the refused value, for V7 a character of it, and for one raised by a handed object's code whatever that code wrote. No rule is added; the wording is the code's.

### 6. No data-plane change

- `parameter` is an attribute of an exception inside the tool function's process; it is no member of a file, a result, a request or a line. S4 is a kind already named. No value of `condition` or `error.kind` is added, no kind is reserved, and no `schema_version` or layout version changes. No case is left open for want of a new value: decision 3 is open because the errors cannot be told apart, and a new kind would not tell them apart either.

### 7. How far (마) is answered

- **Answered now, for `correctness.check` of the first case and of the mock**: a named `ValueError` of `build` with `parameter` `"timeout_s"`, `"flags"`, `"trailing_flags"` or `"compiler"` — S4, one raised inside the check by Python or a handed object's code included, with no log (decisions 2 and 5). With it, ADR-0089 decision 5 no longer holds V2 to V7, and the time limit too long to wait for that ADR-0089 decision 6 left open with decision 5 is S4.
- **Narrowed**: ADR-0089 decision 9's open entry "an unnamed pre-start `ValueError` of `build` or of `build_verification_executable`" now holds U1 to U6 only, of which the operation must place U2 to U4 and U6, as it rules out U5 by its own step (decision 3).
- **Still open under (마)**, as ADR-0089 decision 9 lists them on `main`: that unnamed pre-start `ValueError`; an unnamed `TypeError` — of `build`, from binding the call or from `subprocess.Popen` or later, or from binding a call of `build_verification_executable`; whatever `clang_build.build` still passes on from `subprocess`, an `env` with no `items` method included; an unroled `OSError` of `build` before the start; the row of a `CompilerRunError` whose `timed_out` is false and whose `returncode` is `None`; and the `ValueError` or `TypeError` and the `OSError` for "a `cwd` that does not exist" of `local_run.run`, which wait for the record of `local_run.run`.

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 2, 3 | **(a)** S4 for a named `ValueError` of the four settings, one from a handed object's code included; an unnamed one open (chosen) | It applies ADR-0060 decisions 3 and 4 by what `build` now states. The costs: a handed object's fault, or a machine's `PATH` if the search can raise, is read as a refused setting (decision 2), and a setting only `subprocess` refuses with a `ValueError`, if one arises, gets no S4 (decision 3). |
| 2 | **(b)** Leave the named `ValueError`s open | The stop of ADR-0089 decision 5, a class that does not say what the error is for, is gone for them (N1). Left open, an empty compiler prefix or an output flag, named in S4's own wording, is answered as an answer of neither form. |
| 2 | **(c)** S4 only for a `ValueError` the check itself raises; no row, or open, for one raised inside a handed object's code | Both carry the same `parameter` (N1); telling them apart needs where the error was raised (its traceback) or its message, neither of which `build` states of it; ADR-0087 decision 2 reads only the class and the documented members, and no message. It would also answer one setting two ways by how its value is wrong, against ADR-0087 decision 3 for the `TypeError` of the same checks. |
| 3 | **(d)** No row for every unnamed `ValueError` met, as the settings are now named | U4 holds what `subprocess` passes on, which was not read and may be a refused setting (decision 3); ADR-0083 decision 2 keeps it open. |
| 2, 3 | **(e)** A new kind for a named or an unnamed pre-start `ValueError` | A new value of `error.kind` is a data-plane change (CLAUDE.md A-13); S4 already fits the named ones, and a kind would not tell the unnamed ones apart. |

## Consequences

- **Code** (code mode, D12 rules; names and modules are the code task's; **this record binds no code**): the operation of `cpu_standin` for `correctness.check`, when it is written, applies ADR-0079 to ADR-0087, ADR-0089 and this record. It raises `settings_refused` for a `TypeError` or `ValueError` whose `parameter` is `"timeout_s"`, `"flags"`, `"trailing_flags"`, `"compiler"` or `"env"`, hands no log over, names the setting in the message and not the error's text, and leaves `"sources"`, `"output"`, `"cwd"`, `"kernel_sources"` and an unnamed `ValueError` to the landed rules. A code task that tags the `ValueError` of the `sources` and `output` checks and of the tuple of `kernel_sources` (decision 3) is a candidate follow-up, not required by this record.
- **Not edited and now less exact.**
  - ADR-0089 Status: "It leaves open a pre-start `ValueError` with no `parameter` (decisions 5 and 6)", where decision 6's case is now answered; Context P3: "a `ValueError` from the other checks … carry no `parameter`" and "as only `TypeError` is tagged for the six checks", where four of those checks now tag `ValueError`; decision 1: "an unnamed `ValueError` is one of P3 or the one of P4", where V2 to V7 are now named; decision 5, whose list of what an unnamed `ValueError` is no longer holds a refused setting of `build`'s checks, and "What would let it be placed", now done; decision 6: V3 "stays open with decision 5", now S4; decision 9: the open entry "an unnamed pre-start `ValueError`", now narrower; the walk-through rows for V3 and for V6 or V7 ("no `parameter`", "open under (마)"); Alternatives (a): "a refused setting with no `parameter` gets no S4 yet (decision 5)", which now holds only of one that `subprocess` refuses, if one arises (decision 3); Consequences: "leaves … an unnamed `ValueError` to the landed rules", which no longer holds V2 to V7, and "A code task that gives V2 to V7 a `parameter` … is a candidate follow-up", now landed as T-0274; Boundaries: "The row of an unnamed pre-start `ValueError` (decision 5)".
