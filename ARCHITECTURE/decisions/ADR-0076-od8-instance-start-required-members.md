The records of the six members below each chose the first and left the start open in the same words: ⑲ (`tolerance`, ADR-0020 decision 3), ㉑ (`n_max`, ADR-0023 decision 4), ㉕ (가) (`candidates_per_round`, ADR-0028 decision 4), ㉘ (가) (`op_signature`, ADR-0031 decision 5), ㉜ (`draws`, ADR-0046 decision 3), ㉞ (가) (`objective`, ADR-0053 decision 5).

So a run started without one of them gets as far as a coder call before any tool can measure or check it.
- ADR-0025 decision 2 has the writer hold the whole content, valid, before it touches the file system, and "fills in no value: … not the 10 of ADR-0007 decision 8"; "Whether the start of an instance may write one is sub-questions ⑲ to ㉑ and is not narrowed here in either direction."

## Decision

### 1. Scope

- **An instance whose `hw_profile.record` names `cpu_standin` or the mock as its `accelerator`** (the backends of ADR-0016 decisions 4 and 5), **and whose content either states no `op_signature` or states one that ADR-0041 decision 5 covers** (`gemm`, `fp32`, `row_major`, each of `m`, `k`, `n` at least 1). These are the runs the contracts of `correctness.check` (ADR-0046 decision 1, ADR-0038 decision 6) and of `sim.run` and `board.run` (ADR-0061 decision 1) cover; each required member below has a meaning there.
- **Every other instance is outside this record** — another accelerator, or a stated op_signature that is not covered: nothing is required of it here and nothing is allowed (Boundaries).
- The scope is read from what the file shows, as the tools read it. The kernel language is not shown (ADR-0041 decision 5), so for a run whose kernels are not those of ADR-0008 the checks of this record apply as the file shows; whether the start must do more or other for it stays open. Telling whether an instance is in scope is no refusal on coverage: what the start does with a stated op_signature that ADR-0041 decision 5 does not cover stays open (Boundaries).

### 2. The required set

**Before it writes `instance.json`, the start requires the content to state `op_signature`, `objective`, `candidates_per_round`, `n_max`, `draws` and `tolerance`.** None of them has a default except `n_max`.

| Member | Ground that the instance has it | When the content states none |
|---|---|---|
| `op_signature` | UC-1 step 1 (the model is given at start); FR-13 (the key is the pair); ADR-0031 decision 5 substitutes none | refuse |
| `objective` | FR-2; **owner** O1, and O3 as ADR-0053 decision 5 reads it (cited above); ADR-0053 decision 5 substitutes none, "not `latency_minimisation`" | refuse |
| `candidates_per_round` | **owner** #5 A-9; UC-1 step 1 without "(선택)"; ADR-0028 decision 4: "N = 1 as a special case" is no default | refuse |
| `draws` | ADR-0046 decision 2 (b) (i); no record gives a default (ADR-0046 decision 3: "There is no default") | refuse |
| `tolerance` | **owner** HQ-0004 (3) for the first case; for the mock the same member and meaning, **owner** HQ-0005 (4) as ADR-0038 decision 6 renders it — requiring it at the start of a mock instance is this record's own | refuse |
| `n_max` | ADR-0007 decision 8 | the start puts the default of ADR-0007 decision 8 into the content |

- **One op_signature.** Requiring the member in a version 1 content, which states at most one (ADR-0031 decision 4), reads nothing into whether an instance may cover several values of M (ADR-0031 decision 4; ADR-0041: "Nothing here may be read as 'an instance has one M'"); a record that lets a run state several says what the start then requires.
- **Where the start takes each value from is not decided**: from the user's input, derived from the model (#5 B-5, OD-9) or otherwise; for `draws`, "from what it takes the number, is not decided" (ADR-0046 decision 3) stays as it is (OD-23, UC-1, ⑰, ⑱). This record says only what the content must state before the write.
- **`n_max`: the start fills in the default.** ADR-0007 decision 8 makes the bound "per instance, default 10" and says the value "is then part of what the instance was started with and is recorded with it"; ADR-0023 decision 4 reads the two together — "the default belongs to where an instance comes by its parameters, before the file is written". So when the content composed from the start's inputs states no bound, the start puts that default into the content it then checks against the required set and writes (decision 3), and the file states it. The number is the owner's initial bound (**owner**, #5 B-4: "an initial upper bound of 10"); that it is a per-instance default is ADR-0007's choice under §9, not confirmed by the owner (ADR-0023 Status). It is not restated here as a constant of this record: the value is that of ADR-0007 decision 8, and where the code holds it is no architecture question; once written, the file states it, and a later change of a source constant changes nothing of the run (ADR-0023 decision 4, "a later change of `N_MAX_DEFAULT` therefore changes what no file states").
- This is no conflict with ADR-0025 or ADR-0023: the default enters the content **before** step 1 of ADR-0025, so the write still adds nothing to what it holds; and the file does not become silent-means-default, which ADR-0023 rejected (its Alternatives, (a)).
- **A value the user gives is never replaced**: an `n_max` given that breaks ADR-0023 decision 3 makes the content invalid, and an invalid content is not written (ADR-0025 decision 2); the start does not put the default in its place.
- **Not required here, with the reason**: `schema_version` and `hw_profile` (already required by validity, ADR-0018 decision 2); the layout version (follows from `schema_version`, ADR-0024 decision 3); `round_budget` and `wall_clock_budget_s` (UC-1 marks budget "(선택)"; whether a run with no budget may start is ㉙ (나), OD-19); `owner` and `project` (㉛ (다)); `source_commit` (#5 A-1 detail 3 says the file records it, but what the start does when the source is not exactly one commit is ⑳; requiring it would answer ⑳ with "refuse"); `injections` (optional, UC-1 "(선택) 주입할 가설", ADR-0075 decision 2).

### 3. What a refusal is

- **Order of the checks at the start** (this record's): the content composed from the start's inputs is checked for validity first (ADR-0025 decision 2; today `hilclaw.instance.parse`) — an invalid content is not written, as ADR-0025 already has it; a valid content is read for the scope of decision 1; **a valid content in scope has `n_max` filled in when none was given (decision 2) and is then checked against the required set**; only a content that passes is written by the steps of ADR-0025 decision 3. An invalid or out-of-scope content gets nothing filled in. The default neither makes an invalid content valid nor a valid one invalid, so every content in scope is written, refused or reported as it would be were the default filled in before the validity check.
- **A refusal writes no `instance.json`.** The check is made on the content held before step 1 of ADR-0025, so the write is not begun: no temporary file, no run directory created by it. **Whether other files of the run exist** (written before the check) is not changed by this record: the order of `instance.json` against the first `STATE.json` is ⑩, and what a run directory without `instance.json` means is ⑰ — neither is answered here, and this record adds no file.
- **It reports every missing member, in a fixed order**: `op_signature`, `objective`, `candidates_per_round`, `draws`, `tolerance` (`n_max` is never missing after decision 2). The order keeps the relative order the tools use — `op_signature` first, as both contracts ask for it first (ADR-0067 decision 5, ADR-0046 decision 5); `draws` before `tolerance` (ADR-0046 decision 5) — and puts the run-wide members before the check's. The report goes to whoever gave the values; its form is the code task's and the UI's (OD-23, UC-1).
- **Why every member, not the first** (the tools answer the first): a tool call returns one tool-failure kind, so its order is a rule for which one (ADR-0067 decision 5). The start answers a person who will give the values again; with the first only, a start missing three members would be refused three times.
- **The validity and the version of `instance.json` do not change.** A valid file without any of the six stays valid, is read as before and states none of them (ADR-0020, ADR-0023, ADR-0028, ADR-0031, ADR-0046, ADR-0053). This is **not** "a later record makes a further top-level member **required**" (ADR-0018 decision 2): that clause is about what a validator of the file accepts, and this record adds no rule to any validator or reader of the file. It adds a condition on what the start writes — the kind of condition ADR-0018 decision 2 foresaw ("A valid file is not thereby enough to start a run") and ADR-0020 decision 3 described ("The owner's 'must' binds whatever starts an instance of the first case").

### 4. The per-call answers stay

- `op_signature_not_stated`, `objective_not_stated`, `n_max_not_stated`, `draws_not_stated` and `tolerance_not_stated`, their place in ④ and their order, are unchanged (ADR-0041, ADR-0046, ADR-0061, ADR-0067).
- **Why both**: the start's check binds what the start writes. A file can reach a tool by other ways — written by a test or by hand, by a writer that does not follow this record, or changed after the start ("Immutable" is ADR-0004's word and nothing enforces it — ADR-0018 decision 6) — and a call reads the file as it is at that call and cannot tell where it came from. The start's check catches the omission before any coder call; the per-call answer keeps a tool from judging or measuring a run that states nothing.

### 5. Guarded exit

Nothing here needs an owner-only item, a change to a data-plane file, a new dependency, a named component for the start or a value no record gives. The N range and the initial caps, the objective menu, gates, the component, and budgets are in Boundaries; had any of them been needed, this record would not have been written.

### Walk-through

| Start given | What follows |
|---|---|
| A `cpu_standin` instance with a covered op_signature, objective, N, `draws`, `tolerance` and `n_max` 12 | Valid, nothing missing: this record's checks pass; written by ADR-0025 with `n_max` 12 (the open checks of Boundaries aside) |
| The same without `tolerance` | Refused: report `tolerance`; no `instance.json` |
| The same without `n_max`, `tolerance` given | The default of ADR-0007 decision 8 is put into the content; written; the file states it |
| A mock instance stating, of the six, only `objective` and `tolerance` | Refused: report `op_signature`, `candidates_per_round`, `draws`, in that order |
| An instance whose accelerator is neither `cpu_standin` nor the mock, or a `cpu_standin` one with an `fp16` op_signature | Outside this record: nothing required, nothing allowed (Boundaries) |

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 1 | Every instance, whatever the backend | `tolerance` and `draws` have a meaning only for the runs of decision 1 (ADR-0020 decision 2, ADR-0046 decision 3); other cases are #5 B-7. |
| 2 | `n_max`: refuse, as for the others | ADR-0007 decision 8 gives a default and has it recorded with the instance; a start that refused would make every user state a number that a record already gives — the default would never be used. |
| 2 | `n_max`: leave it out; tools fall back to 10 | Rejected by ADR-0023 (Alternatives (a)): the bound would be a constant of whichever source reads the file. |
| 2 | A default for `draws`, `N` or the objective | No record gives one (ADR-0046 decision 3; ADR-0028 decision 4; ADR-0053 decision 5); naming one would invent a value. |
| 2 | Also require `source_commit`, a budget, `owner`, `project` | Each would answer an open sub-question (⑳, ㉙ (나), ㉛ (다)). |
| 3 | Make the six members required in the file (version 2) | A data-plane schema change; every file and reader of today becomes another version and reading another version is OD-11 (the reason each member record gave). |
| 3 | Report the first missing member only | One refusal per missing member for a person; the one-answer rule of a tool call does not apply. |
| 4 | Drop the per-call answers now that the start checks | A file that did not come from such a start would be judged or measured with nothing stated. |

## Consequences

- **The code slice it makes possible** (code mode, a later task): a pure check of an instance content against the required set of decision 2 and the scope of decision 1, with the filling-in of `n_max`, in a new `hilclaw/` module with its own test file, reusing `hilclaw.instance.parse` without changing `hilclaw/instance.py`. Names, forms and the report's shape are that task's. Binding it to a component that performs the start is not part of it (OD-23).
- **A-13 reading**: document mode. No member, value, validity rule or version of any data-plane file changes, no tool's answer or order changes, and no dependency is added.
- **Sentences of accepted records that become less exact** (listed, not edited). For the instances of decision 1, these say that whether the start checks the member is not decided; it now is: ADR-0020 decision 3 ("where that is checked is not decided (sub-question ⑲)") and its Boundaries; [ADR-0021](ADR-0021-od18-correctness-check-split.md) decision 4 ("Whether the start of an instance checks it, and what anybody does after the answer, stay open" — the second half stays open); ADR-0023 decision 4 ("Whether the start of an instance writes the member … is not decided (sub-question ㉑)");
