## Decision

A sentence is **cited** when a record and its decision, or a requirement, is named with it; it then says what that source says and adds nothing. Every other sentence is **this record's own** — among them the source of the dimensions, that no further read is made, the two kinds `op_signature_not_stated` and `op_signature_not_covered` and their place in the order of a call, what "covered" means, that a request carries no member for the dimensions, and every weighing. No sentence is the owner's; where a cited record quotes the owner, that is said.

### 1. Scope and terms

- This record is about **a call of `correctness.check` about one attempt of a run that ADR-0021 and ADR-0038 decision 6 cover**: a run of the first case — `cpu_standin`, kind `gemm`, fp32, a C kernel (cited: ADR-0021 decision 1) — and a run whose hw_profile names the mock (cited: ADR-0038 decision 6, which renders the owner's answer HQ-0005 (4)). In decision 5 only, it is also about a run at `cpu_standin` or at the mock whose file states an op_signature that this contract does not cover; of such a run it says only that this contract has no check for it.
- Of the contract of that call it fixes **five points and nothing else**: where the `m`, `k` and `n` of a check come from (decision 2); at which moment and from which read (decision 3); what a call answers when the file of the run states no op_signature (decision 4); what it answers when the stated op_signature is one this contract does not cover (decision 5); and what this means for the request (decision 6). Decision 7 says what is thereby not decided, and decision 8 puts the order of a call together again.
- **Decisions 2, 3, 4 and 6 rest on nothing that only one backend has**: the read of the file and the check of what it states are the tool function's part, which is the same for every backend (cited: ADR-0016 decision 2 (a)). **What is particular to these runs**: decision 5 rests on the judging of the first case, a mechanism that "holds for no other kind, dtype or kernel language" (cited: ADR-0017 decision 1); and the whole record says nothing of a run whose hw_profile names an accelerator other than `cpu_standin` and the mock.
- The terms of ADR-0011 and ADR-0015 (identity, start line, end line, reserved kind), ADR-0016 (backend, operation, the moments ① to ⑦), ADR-0030 (the moment ⓢ), ADR-0021 (the cut, a check — "one call that reaches ⑥") and ADR-0031 (the op_signature a run states) are used unchanged. **The dimensions of a check**: the `m`, `k` and `n` of ADR-0017 decision 9 that the tool function judges with and hands to the operation (cited: ADR-0021 decision 2, class (ii) and the table).

### 2. Where the dimensions of a check come from

- **The `m`, `k` and `n` of a check are the `shape.m`, `shape.k` and `shape.n` of the op_signature the run states**: of `op_signature.record` in `runs/<run_id>/instance.json` of the run the request names. The tool function uses them for its own part and hands the same three numbers to the operation (the handing is cited: ADR-0021 decision 2, class (ii)). A check has one `m`, `k`, `n` (cited: ADR-0017 decision 3, "one run has one `m`, `k`, `n`"), and a file of version 1 states at most one op_signature (cited: ADR-0031 decision 4), so no choice among several arises.
- Of the stated record, a check uses the three shape members, and decision 5 looks at `kind`, `dtype` and `layout`. `op_signature.key`, the attribute `label` and an `ext` are not used for the dimensions: no file below `db/` and no spec is read for the dimensions (decision 3). Which files a check reads for anything else — the kernel of the attempt among it — is not said here (Boundaries).
- **Four sources were weighed, each against the fixed inputs.**
  - **(a) Members of the request, chosen by the calling agent.** The reasons that keep three other values out of a request carry over in part only. *The seed*: "The seed must be one the author of the attempt could not know" (cited: ADR-0017 decision 3, as ADR-0021 decision 3 cites it). **That reason does not carry over**: the dimensions of the op_signature are not secret — a spec shows them to the coder ("The coder needs the field values (shape, dtype, layout, toolchain versions, host)", cited: ADR-0002 decision 2). *The hw_profile*: "a request that named a backend or a hw_profile would let the calling agent measure the attempt of one run at another target", with nothing in the two lines of a step showing it (cited: ADR-0016 decision 4). *The tolerance*: "A check about a run whose verdict took its tolerance from the request would let the calling agent loosen the gate FR-9 calls a hard floor" (cited: ADR-0020 decision 5). **These two carry over**: a calling agent that named the shape would choose what the kernel is checked on. A pass would then be stored under the identity of an attempt of the run for a shape the run does not state, and none of the members ADR-0011 decision 3 fixes for the two lines of a step names a shape; whether a result does is not decided (decision 7). A request member beside the member of the file would also be a second statement of one thing, with a rule needed for their disagreement.
  - **(b) The member `op_signature` of the file of the run.** The file holds "What the instance was started with" and is written once (cited: ADR-0004, as ADR-0031 decision 2 cites it); the member is where "a run states its op_signature" (cited: ADR-0031 decision 1), in a form that is valid as a whole or makes the file invalid (cited: ADR-0031 decisions 3 and 5). The contract already reads this file once in ④ for the hw_profile and the tolerance (cited: ADR-0021 decision 4), `hilclaw.instance.read` returns the member from the same read (observation), and every situation of the file at that read has an answer (cited: ADR-0019 decision 3, the rows of ④).
  - **(c) The `task.op_signature` of the spec of the attempt.** It is the shape the attempt was written for ("A spec has exactly one, and so one value of M", cited: ADR-0002 decision 2). Against it: a spec "exists per coder call only and is a copy composed by a role (OD-23)" (cited: ADR-0016 decision 4), so the shape of a check would be set by whatever composes specs, which no record has named; ADR-0031 decision 6 "adds no rule between the member and the `task.op_signature` of a spec" (cited), so that shape need not be the one the run states; and it is one more file of the run, at a path that hangs on where the files of an attempt are (cited for the path: [ADR-0029](ADR-0029-od8-spec-file.md) decision 3), read at a moment for which no record gives an answer when the file is missing or invalid — "a file of the run other than the three frame files" is a Boundary of ADR-0019.
  - **(d) The stored record `db/<hw_profile_key>/<op_signature>/op_signature.json`.** "a stored record or a key directory need not exist for the key of a run" (cited: ADR-0031 decision 6), and the name of the directory would itself have to come from the file of the run; under one key the stored record can differ from the embedded one in `label` and not in key fields, short of a collision of the name (cited, same decision), so it adds a second file and nothing a check uses.
- **The choice is (b).** It is the one statement of the operation that the run itself makes, it is read where the hw_profile and the tolerance of the same check are read, and it needs no file and no rule that does not exist. **It is not taken as provisional**: for a file of version 1 the fixed inputs tell (b) from (c) by the three points above. **What would reopen it** is named in decision 7 — an instance that covers several op_signatures, and shapes outside the op_signature.
- **No other source stands in when the file gives none**: not the spec of the attempt, not a directory below `db/`, not a record of ADR-0008 decision 9, not a constant of the source and not a member of the request (cited: ADR-0031 decision 5, "never substitutes one"; "No path yields an op_signature the run did not state"). What the call answers then is decision 4.

### 3. At which moment, and from which read

- **The dimensions are taken in ④, from the one read of `instance.json` from which the hw_profile and the tolerance of the call are taken** (that read is cited: ADR-0018 decision 4; ADR-0021 decision 4, "this contract reads it once"). **No further read is made for them, and no other file is read for them.** The hw_profile, the op_signature and the tolerance of one check are therefore those of one content of the file — the reason ADR-0021 decision 4 gave for one read, which carries over unchanged, as does its reason about ADR-0019: a read after the selection or inside the step would be "a frame file it reads at another moment" (cited: ADR-0019 Boundaries).
- **The read of ⓢ is not used for them.** In ⓢ the file is read "as a whole" for the layout version stamp, and "④ is unchanged: the selection reads the file again" (both cited: ADR-0030 decisions 3 and 4). A file whose `op_signature` breaks ADR-0031 is invalid as a whole (cited: ADR-0031 decision 5), so such a file is already answered in ⓢ (decision 4, last bullet).
- **A call answered before ④ takes no dimensions**: a refused request, `no_data_root`, a kind answered in ⓢ, a situation of the lookup, an ended or an open identity (the moments are cited: ADR-0040 decision 7).
- **A repeated call under an ended identity is answered with what the end line holds** (cited: ADR-0040 decision 3; ADR-0021 Walk-through), whatever op_signature a valid file of version 1 then states: the lookup comes before ④, and nothing of the member is compared with anything in ③. When the file is then missing, unreadable, invalid or of another version, the call is answered in ⓢ and not from the log (cited: ADR-0030 decision 4).
- **A further `execution` reads the file again** and takes the dimensions it then states: it is "carried out as any call whose identity has no line" (cited: ADR-0040 decision 3). Nothing of an earlier read is used for it: "nothing is kept between calls", and "a later call reads the file again" (cited: ADR-0031 decision 6).

### 4. A run whose file states no op_signature

- **A valid file of version 1 without the member `op_signature`: a tool failure of this tool's own kind `op_signature_not_stated`.** No dimensions are substituted (decision 2, last bullet).
- **For it, this call called no operation, consumed nothing at any target, drew no seed and appended no line; the same request can be repeated and is answered by what the file then states.** It is answered in ④, before the start line, and this contract raises the kind in no other situation and never as the `failure` of an end line — the properties ADR-0021 decision 4 gave `tolerance_not_stated`, for the same reason: inside the step a missing statement would end the identity with a `failure`, and the corrected run would need a further `execution` (cited: ADR-0021 decision 4; ADR-0016 decision 2).
- **The name** is a *name* of ADR-0001 (`[a-z][a-z0-9_]{0,31}`; 23 characters), formed like `tolerance_not_stated` from the name of the member. Checked on 2026-10-12: no reserved kind (ADR-0015 decision 2; ADR-0016 decision 3; ADR-0019 decision 2; [ADR-0026](ADR-0026-od18-failed-step-line-append.md) decision 3), no kind of another record and no name in `hilclaw/` or `tests/` equals it or `op_signature_not_covered` (decision 5); neither string occurs in `ARCHITECTURE/` outside this record and the passages added with it.
- **Why this class — the reasons of ADR-0021 decision 4, each checked for whether it carries over.**
  - *Not a result*: carries over. No outcome was established about the attempt (cited: ADR-0010 decision 4, a tool failure "says that no outcome was established"), and a result of any shape could be taken for a verdict.
  - *Not `invalid_request`*: carries over. The request is not at fault, and a refusal reads nothing and is "the same on every machine" (cited: ADR-0015 decision 2).
  - *Not a kind of ADR-0019*: carries over. The file is there, was read, is valid and is of the supported version: "The member may be absent from a valid file" (cited: ADR-0031 decision 5).
  - *Not a check on some other dimensions*: carries over, with ADR-0031 decision 5 in the place of ADR-0020 decision 3 (decision 2, last bullet).
  - *Not a new reserved kind*: **carries over less far, and this part of the choice is provisional.** ADR-0021 wrote: "the situation belongs to one tool, and the kinds the frame reserved were reserved because their situations belong to no one tool". The member `tolerance` has a meaning for a correctness check only (cited: ADR-0020 decision 2). The op_signature is a statement about the run, and whether a call of `sim.run`, `board.run` or `profiler.collect` needs it is said by no record: today this contract is the only one that reads it. So the situation belongs to one tool **today**. If the contract of another tool comes to need the op_signature of a run, its record decides whether that tool has a kind of its own or the frame reserves one; no tool's contract may define the value of a reserved kind with another meaning (cited: ADR-0015 decision 2; ADR-0016 decision 3), so that record then revisits this one. A reserved kind is not taken here because it would speak for tools whose contracts do not exist.
- **Its place: after the selection, and before the tolerance.**
  - *After `no_backend` and `not_offered`*: "A call whose backend cannot be selected reaches no check, whatever the file states" (cited: ADR-0021 Alternatives), so the order of ADR-0019 decision 4 stands and this kind follows it.
  - *Before `tolerance_not_stated`*: the member `tolerance` has the meaning ADR-0020 decision 2 gives it "for a run of the first case" and "no meaning for any other run" (cited; for a run at the mock: ADR-0038 decision 6), and what the file shows of the case beyond the accelerator is in the op_signature (decision 5; the accelerator is in the `hw_profile` — cited: ADR-0021 decision 1). The tool function therefore looks at what operation the run states before it asks the file for a tolerance in that vocabulary; `tolerance_not_stated` then says, as before, that the tolerance is the one thing missing (cited: ADR-0021 Alternatives).
  - **A valid file that states neither an op_signature nor a tolerance is answered `op_signature_not_stated`.** The cost: whoever corrects such a run learns of the second missing member only from the next call.
- **OD-8 sub-question ㉘ part (가), as far as a call goes**: it is checked at every call of this tool that reaches ④, and what the call answers is the kind above. **Whether the start of an instance checks that an op_signature is stated, and what anybody does after the answer, stay open** (OD-8 sub-questions ⑰ and ㉘; OD-23; OD-10).
- **A member that is present and invalid is not this kind.** A file whose `op_signature` breaks ADR-0031 decision 3 "is **invalid**", and a reader "uses no member of it" (cited: ADR-0031 decision 5); the call answers `run_file_invalid`, by the rows ADR-0019 decision 3 has for `instance.json`, in ⓢ (cited: ADR-0030 decision 4) — so also for an ended identity. A member whose name is misspelt is passed over, and the file states none (cited: ADR-0031 decision 7).

### 5. A stated op_signature that this contract does not cover

- **What the file shows, exactly.** Where the member is present: the `kind`, the `shape`, the `dtype`, the `layout` and, where the record holds them, an `ext` and a `label`. **Never the kernel language, the kernel contract or a build setting** (cited: ADR-0031 decision 2; ADR-0008 decision 8).
- **What the reader's source already refuses.** A record whose `kind` the source does not know makes the member, and so the whole file, invalid (cited: ADR-0031 decision 7); today `hilclaw.keys.op_signature_key` knows `gemm` only (observation), so in this source a run that states another kind is answered `run_file_invalid` in ⓢ. Any *name* is accepted as `dtype` and as `layout`, and 0 as a shape value: "Validity of the record is not existence of the operation" (cited: ADR-0031 decision 7).
- **Covered.** The judging this contract has is that of the first case (cited: ADR-0021 decision 2; ADR-0017 decisions 4, 5 and 7): fp32 inputs, a float64 reference of the product, and a report that holds, for each draw, the m·n elements of the output "in the layout of ADR-0008 decision 2" (4·m·n bytes). It is the judging of a kernel of the contract of ADR-0008, which "is bound to kind `gemm`, dtype `fp32` …, layout `row_major` … and kernel language `c`", while "Another kind, dtype, layout or language has another contract, defined by its own record" (cited: ADR-0008 decision 1); and that contract "covers no shape that holds a 0" (cited: ADR-0037 decision 2). **A stated op_signature is covered by this contract when its `kind` is `gemm`, its `dtype` is `fp32`, its `layout` is `row_major` and each of `shape.m`, `shape.k` and `shape.n` is at least 1**. Without an `ext` (below), these are the records of the form of the rule of ADR-0008 decision 9, which that decision states for the twelve first instances; applying the form to any `m`, `k` and `n` of at least 1 is this record's own, as a check is "restricted no further than ADR-0008 (each ≥ 1)" (cited: ADR-0017 decision 3). Taking these four conditions from the binding of ADR-0008 and from ADR-0037 is this record's own reading; "covered" is the word of ADR-0037.
- **A valid file whose stated op_signature is not covered: a tool failure of this tool's own kind `op_signature_not_covered`** (a *name*; 24 characters; the collision check of decision 4). It has the properties of decision 4 — no operation called, nothing consumed, no seed drawn, no line appended, the same request can be repeated, never the `failure` of an end line — and its place is after `op_signature_not_stated` and before `tolerance_not_stated`, for the reasons given there.
- **Why an answer, and why this one.** Once decision 2 takes the dimensions from the stated record, the tool function holds the dimensions of whatever operation the run states. Without this answer a run that states an fp16 product, or one in another layout, would be judged with the first case's reference and predicate on those dimensions. **That would be a check under the first case's oracle for another case**, and the oracle and the tolerance vocabulary of every other case are the owner's (#5 B-7; cited: ADR-0021 Boundaries, "any tolerance vocabulary, oracle or check beyond the first case"; the owner's words of HQ-0004 (2), as ADR-0020 decision 2 quotes them, "other dtypes stay open under B-7"). A tool failure establishes no outcome (cited: ADR-0010 decision 4) and **defines no oracle, no tolerance vocabulary and no check for the other case**: it says that this contract has none. It is not `run_file_invalid`, since the file is valid, and not a result, for the reason of decision 4.
- **Why two kinds and not one**: the two answers say different things of the run — that it states no operation, or that it states one for which this contract has no check — and a caller that knows this contract can tell which "without reading the message" — the second half of the test of ADR-0019 decision 2 (cited), whose first half, "without knowing the tool", is said of reserved kinds and does not carry over to a kind of one tool; ADR-0016 decision 3 split its two kinds where "a caller acts differently on each" (cited), and this record does not say how a caller acts. What a caller does on either is not decided.
- **What stays open of OD-18 sub-question ⑩, in every case.**
  - **The kernel language.** The file never states it. A run at `cpu_standin` whose stated op_signature is covered and whose kernels are not C kernels of ADR-0008 is not told apart by anything here; what a call answers for it is not decided.
  - **A run whose hw_profile names another accelerator** than `cpu_standin` and the mock: this record says nothing of it, covered op_signature or not (#5 B-7).
  - The first three clauses of the sub-question (how an operation comes to the verification executable, what a call answers when none can be had, the tool-failure kinds of a backend) are later slices'.
- **An `ext` is not looked at.** No record gives an `ext` of a `gemm` record a meaning (ADR-0001 decision 2 calls it "Further identification fields of a kind"), and the binding of ADR-0008 decision 1 does not name it; whether a change of contract is marked by a member of `ext` is open (cited: ADR-0008 decision 8; OD-6 sub-question ④). The record that gives one a meaning says then what a check does.
- **For a run at the mock** the same conditions hold, since the same contract and the same judging answer it (cited: ADR-0038 decision 6). This says on which dimensions the tool function judges, and it has one consequence for the mock: a script is asked through this tool only for a run whose stated op_signature is covered, since no operation is called otherwise. Within that, "Which kind, dtype or kernel a script of the mock stands for is the script's and the second record's" (cited, same decision) stays for the slice of the mock.

### 6. What this means for the request

- **A request of this tool carries no member for the dimensions**: no `m`, `k` or `n`, no shape and no op_signature, key or record. A calling agent does not choose the shape of a check (decision 2 (a)). **A caller that wants a check on another shape has no way under this contract.**
- **The member list of a request stays open** after this record (cited: ADR-0040 decision 5, "The member list of a request is not closed by this record"): whether a request carries anything for `draws`, the kernel of the attempt, flags or time limits is a later slice's, and so are the input schema and the description. **This record does not say what the tool function does with a member no record names** — a member named `m` in a request included.

### 7. What is not decided by this

- **OD-16 sub-question ① is not closed, and FR-9's "shape/seed" is not read.** The minimum clause of FR-9 has a result re-verified on "코더에 노출되지 않은 입력(shape/seed)", while a spec shows the shape of the op_signature to the coder; whether that clause asks for shapes outside the op_signature is OD-16 sub-question ① as registered, and "not secret" in decision 2 (a) and "has no way" in decision 6 say what holds for the shape of the op_signature and under this contract, not what FR-9 asks. That a check under this record uses one `m`, `k`, `n` (cited: ADR-0017 decision 3) and takes them from the op_signature the run states says what this contract does today. "Whether a caller ever passes dimensions other than those of the `op_signature` stays open" (cited, same decision): whether verification should also draw shapes outside the op_signature, which shapes, and how a call would then state or obtain them, stays with OD-16. **A "yes" reopens the first sentence of decision 2** (the dimensions of a check are those of the stated op_signature) and, if those shapes must be ones the author of an attempt cannot know, the weighing of decision 2 (a), where the secrecy reason is said not to carry over.
- **No reading of #5 B-4.** This record builds on a file of version 1, which states at most one op_signature — "a rule about what a file of version 1 can state, not about what an instance may be" (cited: ADR-0031 decision 4). **Nothing here may be read as "an instance has one M".** If an instance may cover several op_signatures, a later record says how such a run states them (cited, same decision) and how a check names the one it is about; decisions 2 and 6 are then reopened, the choice between (b) and (c) included.
- **Nothing checks that the kernel of the attempt, or its spec, is of the stated operation.** "Nothing checks that the run concerns the stated operation: not that its specs carry it, not that its kernels compute it" (cited: ADR-0031 decision 7), and no rule ties the member to a spec (cited: ADR-0031 decision 6; OD-8 sub-question ㉘ part (나)). This record adds no such check. What follows for a check is in decision 9.
- **Whether the dimensions used are a member of a result** is the result slice's (cited: ADR-0021 decision 5, "Whether it holds more (… the dimensions, `draws`, the tolerance used) … are the second record's").

### 9. Limits

- **Whoever can write `instance.json` changes the shape a kernel is checked on.** "Whoever can write the file changes the op_signature the run states", and "two reads of the file of one run can find two op_signatures" (cited: ADR-0031 decision 7). Two checks of one attempt — a further `execution`, the check at the other point — can then be about two shapes, as they can have two tolerances (cited for the tolerance: ADR-0021 decision 6). Neither line of a step names the shape (cited: ADR-0011 decision 3), so the log does not show it unless a result does (decision 7).
- **A stored pass says nothing about another shape.** A pass says that the output is right "only for the drawn range and shape" (cited: ADR-0021 decision 6; ADR-0017 decision 10, "A kernel that is right only for the drawn range or shape passes"). The shape is the one the file stated at the read of that check.
- **The cost of a check follows from the stated shape, and nothing bounds it here.** Per draw one kernel call, one regeneration, one float64 product on the Python side and 4·m·n bytes of report; "the Python-side work of a run is bounded by nothing here" (cited: ADR-0017 decision 10; OD-14). A covered record may hold any `m`, `k` and `n` of at least 1; no upper bound is added.
- **A kernel or a spec of another operation.** The kernel of the attempt is carried out with the dimensions the run states, whatever its spec stated (decision 7). A check establishes, as for any kernel, whether the output is right for those dimensions; a kernel written for another shape can then fail or break, and nothing here tells that case from a wrong kernel. A kernel of another language, or of another contract under the same op_signature (cited: ADR-0031 decision 7), is not seen at all by decision 5.
- **Validity is not existence** (cited: ADR-0031 decision 7): "covered" says that the judging is defined for the stated record, not that a kernel, a build or a target exists for it.
- **Two sources, two answers.** A source that knows a `kind` this one does not takes a file that states it as valid (cited: ADR-0031 decision 7) and, by decision 5, answers `op_signature_not_covered` where this source answers `run_file_invalid`.
- **A misspelt member name** leaves the run without a stated op_signature (cited: ADR-0031 decision 7), and the answer is `op_signature_not_stated` at every call that reaches that answer in ④, for as long as the file is not changed; by ADR-0004 it is written once (cited as ADR-0031 decision 2 cites it).
- The limits of ADR-0021 decision 6, ADR-0038 decision 8 and ADR-0040 decision 8 stand unchanged.

## Boundaries (not decided here)

- **`draws` and the seed after a check**: the number of draws of a check of a round or of a promotion-level re-verification, and whether a seed is recorded (OD-16 sub-question ⑤).
- **Shapes outside the op_signature** (OD-16 sub-question ①): decision 7.
- **The rest of the request and the whole result**: every other request member, the input schema, the description, what is done with a member no record names; every member, name and type of a result, the dimensions among them.
- **The kernel of the attempt**: where it is, who builds it, how an operation comes to the verification executable and what a call answers when none can be had (OD-23; the first clauses of OD-18 sub-question ⑩; the isolation means, HQ-0010); flags and time limits (OD-14).
- **Backends**: the tool-failure kinds a backend may raise; the operation and the default script of the mock, and which kind, dtype or kernel a script stands for; whether an operation is handed the point; the operation of `cpu_standin`.
- **The start of an instance and the spec**: whether the start checks that an op_signature is stated or that it is covered; whether the `task.op_signature` of a spec must agree with the op_signature the run states, and what checks it (OD-8 sub-question ㉘; OD-23).
- **Several op_signatures in one instance** (OD-6 sub-question ③; #5 B-4 — owner-only as far as it is a reading of B-4).
- **Other cases**: a run at another accelerator; a kernel of another language; the oracle, the tolerance vocabulary and the check of any case other than the first (#5 B-7 — owner-only); the meaning of an `ext` (OD-6 sub-question ④).
- **What follows an answer**: what a caller, a role or a person does on `op_signature_not_stated` or `op_signature_not_covered`; recovery, retry and a further `execution` (OD-10, the rest of OD-17); OD-18 sub-questions ⑫ and ⑭.
- **Other tools**: `sim.run`, `board.run` and `profiler.collect`, among it whether any of them reads the op_signature of a run; hooks and gates (the rest of OD-18; OD-3).
- **Files and names**: any member of `instance.json`, `STATE.json`, `events.ndjson`, a spec or a result file; any change of the form or the validity of `op_signature`; any new reserved `kind`.
- **Owner-only (DRIVER §9)**: the #5 A and B items; OD-3; OD-25; C-6.
- **No sub-question is registered by this record.**
- Any change to ADR-0001 to ADR-0040, to UsageCases, to `hilclaw/`, to tests, to CI, to `pyproject.toml`, to any settings file, or to the `HIL-Claw-data` repository; any new external dependency.
