## Decision

### 1. Scope and terms

- **The runs**: a call of `sim.run` or `board.run` at a run whose hw_profile names `cpu_standin` (the local configuration of ADR-0038 decision 1, in the containers of ADR-0144) or the mock, whose stated `op_signature` is covered by one of the six bf16 entries of `contract_table` (ADR-0177 decision 1). This record changes nothing of the fp32 `gemm` run; its move to the v2 result and to the new `step` values (**owner**, HQ-0078 ①) is the v2 record's (decision 7).
- **Terms**: *bf16 timing program* — the C source of the harness for one kind that defines `main`, prepares the operands, calls the kernel and reads the clock; *bf16 timing executable* — that program and one kernel built into one executable; *bf16 timing run* — one process of it. The other terms are ADR-0009 decision 1's.

### 2. (a) The timing program per kind

- **One program per kind, six programs, sharing one header**; each holds exactly one kernel call site. *Why not one shared driver*: an executable holds the sources of one kernel (cited: ADR-0009 decision 2), and a program that references six symbols does not link with one kernel; weak references or a kind argument would let a kernel see which program it is in (the threat of ADR-0107 decision 5) for no gain. The fp32 `timing_driver.c` is not changed. File names and how the shared parts are factored are the code slice's, provided the report form below stays exactly ADR-0009 decision 8's.
- **Kept from ADR-0009 unchanged, for every kind**: the timer and what lies between its two readings, exactly the one kernel call (decision 3); one call per repeat (decision 4); exactly one untimed call before the first timed repeat (decision 6); the loop and the stopping rule run by the program with `n_min` and `cv_max` handed from `measurement.py` and `n_max` and the sample form handed by the caller, the Python side replaying it (decision 7); descriptor 1 pointed at standard error before the first call, and the report `resolution_ns`, `interval_ns` lines, `stop converged` / `stop not_converged` (decision 8); every repeat of a measurement uses the same arrays and values (decision 5); nothing beyond the C library and POSIX.1-2008 is needed by the program, which does no floating-point arithmetic on the operands. **No bf16-specific reason was found to change `n_min`, `cv_max` or the loop.**
- **Command line**: the kind's dimensions in `task_contract` order, then `n_min`, `n_max`, `cv_max`, the sample form and the seed, with ADR-0009 decision 9's spelling rules and the kind's rules between dimensions (`d` even for `rope`; `l` ≥ `m` and `h` a multiple of `h_kv` for `sdpa_kv_cache`; cited: ADR-0177 decision 1), refused with status 2 as the verification programs refuse them. The `rmsnorm` `eps` is the contract's constant (ADR-0158), compiled into the program as in its verification program.
- **Operands**: every input array is allocated once (one `malloc` each, ADR-0009 decision 5's promise and no more) and **filled once, before the untimed call, by the generator of `bf16_verification.h`** with the timing seed as `seed` and draw index 0, each operand from the kind's input value set as the verification draws it (cited: ADR-0163 decision 4; ADR-0165 decision 4). *Why*: the sets are the contracts' own (finite, the `gemm`, `rmsnorm`, `elementwise_add` and `up` sets of magnitude [0.5, 1) exactly as ADR-0009's range, the SwiGLU gate [0.5, 8)), so no slow subnormal path is timed and no second generator is written. The inputs are not tied to any check's (cited: ADR-0064 decision 6): the seeds are drawn separately. Output arrays are not initialised (as ADR-0009 decision 5 for `c`). No input value is written to a file (cited: ADR-0009 decision 5).
- **`rope`**: the program reads the 4·m·d bytes of the `freqs_cis` rows on standard input before the untimed call, exactly as the `rope` verification program does (cited: ADR-0164 decision 3; ADR-0180 decision 3), copies them into the kernel's `freqs_cis` array once, and ends with a non-zero status of its own (the code slice's) for an input that is short, longer or unreadable. **The start position of a timing run is ADR-0180 decision 1's rule applied to the timing seed**: P = 0 when m ≥ 2; when m = 1, P = 127 for an even seed and 2047 for an odd one; the operation computes the rows with `hilclaw.harness.bf16_rope_verification.start_position` and the table of ADR-0164 decision 5. *Why*: the kernel's work does not depend on P (cited: ADR-0161 decision 3), so any P times the same work; the rule gives the op_signature's positions, needs no new rule, no member and no parameter, and the seed is already in the operation's hands. The mock needs no rows.
- **`sdpa_kv_cache`**: each cache is **one allocation of exactly l rows** (no guard rows: they serve the verification's comparison, ADR-0165 decision 5, and a timing run compares nothing); rows 0 … P − 1 are drawn, P = l − m derived as ADR-0165 decision 3 derives it, rows P … l − 1 are not initialised. **Nothing is reset between repeats.** The untimed call writes rows P … l − 1 from `k_new` and `v_new`; each later call writes the same bits there again and leaves rows 0 … P − 1 unchanged (cited: ADR-0162 decision 4). So every timed repeat starts from the same cache state, which is one the contract admits on entry (rows 0 … P − 1 placed, rows P … l − 1 unspecified), and the repeats are repeats of one thing, as ADR-0009 decision 5 wants. A kernel that breaks the contract by changing rows 0 … P − 1 is caught by the check, not here (Limits).
- **What the program reports**: ADR-0009 decision 8's form, nothing else; the exit statuses are those of `timing_driver.c` plus the `rope` input status.

### 3. (b) The verification and timing build relation (OD-16 sub-question ⑥)

- **ADR-0107's rule extends to these runs**: the bf16 verification executable and the bf16 timing executable of an attempt stay two executables of two programs, each built at the call that uses it (ADR-0107 decision 2's choice (a)), and the kernel sources are built with one compiler, one list of flags and trailing flags and one environment in both builds, independent of tool, point and `execution` (ADR-0107 decision 3). At `cpu_standin` that set is ADR-0116 decision 2's fixed set as ADR-0177 decision 3 reads it for the bf16 verification builds (`-std=gnu11 -O2 -ffp-contract=off`, trailing `-lm`, which the SwiGLU kernel's `expf` needs in both builds). On the mock the rule is vacuous (cited: ADR-0107 decision 4).
- *Why*: none of ADR-0107's reasons depends on the kind or the dtype; its decision 1 limits the rule to the first case only because no other run existed (cited: ADR-0163 decision 2 left it there for that reason).
- **The shared header** is copied beside the program and handed to the compiler as no source, with the answers of its copy, as ADR-0179 decision 5 says for the verification header (cited). The waiter is built as today (cited: ADR-0170 decision 2).

### 4. (c) What the run tools take for a bf16 run

- **Admission**: `run_covers` (cited: ADR-0177 decision 1), in the place ADR-0061 decision 3 reads the op_signature, with the same tool failures `op_signature_not_stated` / `op_signature_not_covered`.
- **Dimensions**: all shape members of the stated record, in the order of the contract's `task_contract` parameters (as ADR-0177 decision 3 for the check); for fp32 `gemm` nothing changes.
- **`n_max`, the sample form and the seed**: unchanged — the member of ADR-0023, the form derived from the objective (ADR-0061 decision 4), the seed drawn per call (ADR-0064 decision 2), recorded nowhere (ADR-0064 decision 5).
- **What the operations are handed**: the request, the hw_profile, the output path and the keeper as today, and timing parameters that hold the `kind` and `dtype` of the covering entry, the dimensions, `n_max`, the sample form and the seed. **The Python form is the code slice's, provided the operations of fp32 `gemm` keep receiving `TimingParameters` as today** (the manner of `Bf16CheckParameters`).
- **The `step` value of the call** is the one new value of the tool and point that the v2 record spells (**owner**, HQ-0078 ①; decision 7), the same for fp32 `gemm` and the six bf16 kinds. No dtype chooses it, so the read of ⓢ that chooses the check's value until the v2 record (cited: ADR-0177 decision 3) has no counterpart here; what the result says of the covering entry is the v2 record's (decision 7).

### 5. (d) The memory figure

- **Kept as for fp32**: the bf16 timing executable runs under the waiter as process 1 of the timing process's container, which reports the child's `ru_maxrss` (cited: ADR-0145 decision 3), and the operation returns it as the figure (cited: ADR-0065 decision 4). *Why*: the waiter starts any executable with any arguments and inherits descriptor 0 to it (observation), so nothing kind-specific is needed; the figure is "no run of its own" (cited: ADR-0052 decision 4), and NFR-2 asks the same of every kind. `memory_ceiling` stays not admitted (cited: ADR-0063 decision 7), so every result says `"ceiling": "not_stated"`.

### 6. (e) The `cpu_standin` time limits

- **Build**: B = 60 s for the timing program's build and the waiter's build together, as today (cited: ADR-0117 decision 3; the waiter takes what is left, observation of `standin_run`). The programs are expected to be of the size of `timing_driver.c` (250 lines) with a shared header; ADR-0179 decision 4's reasoning holds.
- **Process**: **P = min(1500 s, 10 s + c × (1 s + W / R))** with **c = `n_max` + 1** (cited: ADR-0117 decision 4, one untimed call and up to `n_max` repeats), R = 2 × 10^8 per second and **W the kind's work measure of ADR-0179 decision 3 and ADR-0180 decision 2, unchanged**. The element term counts the verification program's arrays (with SDPA's guard rows), which the timing program draws once rather than per call; it over-allows, which only raises the limit, and one function serves both. The rows of `rope` reach the process once (inside the 10 s).
- **Values at `n_max` = 10** (the initial value of ADR-0007 decision 8, shown as an example; computed with `standin_settings._bf16_work`):

| Kind, shape | Per call (1 + W/R) | c = 6 (converged at `n_min`) | c = 11 |
|---|---|---|---|
| `gemm` 512 × 2048 → 128256 (lm_head) | 1362.3 s | 1500 s (cap) | 1500 s (cap) |
| `gemm` 512 × 2048 → 8192 | 88.0 s | 538.0 s | 978.0 s |
| `gemm` 1 × 2048 → 128256 | 16.8 s | 110.6 s | 194.4 s |
| `sdpa_kv_cache` (2048, 2048, 32, 8, 64) | 173.6 s | 1051.8 s | 1500 s (cap) |
| `rope` (2048, 32, 64) | 1.43 s | 18.6 s | 25.8 s |
| `swiglu` 512 × 8192 | 1.63 s | 19.8 s | 27.9 s |
| `elementwise_add` 512 × 2048 | 1.16 s | 16.9 s | 22.7 s |
| `rmsnorm` 512 × 2048 | 1.10 s | 16.6 s | 22.2 s |

- **A kernel that is not slow** (ADR-0179's estimate, 10^9 operations per second): `sdpa_kv_cache` at m = l = 2048 takes about 35 s per call, 385 s for c = 11, within the limit. **`gemm` lm_head at M = 512** takes about 270 s per call, so even the six calls of a run converged at `n_min` need about 1600 s, past the cap: **at that shape a timing run completes only for a kernel of at least about 1.1 × 10^9 operations per second**, and a slower one is a broken `time_limit`. The cap is not raised: it follows from the MCP idle window (cited: ADR-0117 decision 5; ADR-0179 decision 8) and is ADR-0117's, not this record's.
- **The MCP idle window** (OD-18 ③): the longest call is 60 + 1500 = 1560 s, as for every `cpu_standin` call; the tool function's own work for a timing run is the judging of the report and, for `rope`, the table of P + m positions (1.85 s at 2048, cited: ADR-0180 decision 2), well within the 240 s left.
- **At a limit**: `build_time_limit` or `time_limit`, existing values of `condition` (cited: ADR-0117 decision 7). The operation refuses before anything is started a kind outside the six, another `dtype`, and dimensions the kind's command line refuses (as ADR-0179 decision 7).

### 7. (g) The result of a bf16 run — the owner's v2, defined by a record of its own

- **Why it was the owner's.** ADR-0063's `shape` is "an object with exactly the three members `m`, `k` and `n`" (cited: ADR-0063 decision 5; decision 9's table), which no bf16 kind but `gemm` has; every other member of its list says of a bf16 run what it says of an fp32 one (`outcome`, the seven values of `condition` — a `rope` input failure is `exit_status` —, `n_max`, `sample_form`, `resolution_ns`, `intervals_ns`, `memory_bytes`, `ceiling`, `bound`). The list is closed and a change of it is a data-plane schema change (cited: ADR-0063 A-13 reading), which takes new `step` values (cited: ADR-0100 decisions 3 and 4). The owner's answer for the check (HQ-0077) did not cover `sim.run` / `board.run`, hence HQ-0078.
- **The answer** (**owner**, HQ-0078; quoted in Context): one v2 result format for `correctness.check`, `sim.run` and `board.run`; fp32 `gemm` migrated; the six step values of today retired and never reused; one new `step` value per tool and point; a member with the contract table's key; `shape` with all shape members of the kind; `counts` per output or inout operand; a unit member on the measured values, `ns` for now; the other members carried over; names, spellings and details left to "the ADR"; the v2 record and both tools' code land before the bf16 timing slices.
- **The result of a bf16 run is a v2 result of `sim.run` or `board.run`**, under the new `step` value of its tool and point, with `shape` holding the kind's shape members in the stated `op_signature` and the key of the covering entry of `contract_table` (ADR-0177 decision 1). Nothing else of the result is decided here.
- **The v2 format is defined by a record of its own, not by this one** (the "v2 record"). *Why*: the answer reaches far beyond these runs — the results of `correctness.check` for fp32 `gemm` and the six bf16 kinds, the `counts` that replace HQ-0077's `cache_differs`, the retirement of six `step` values, and the readers of check and run lines (`hilclaw.layout`, the `timings` readers, the hard floor of ADR-0110 and ADR-0178) — while this record is the timing run's (OD-13, OD-16 ⑥), and its task leaves the `correctness.check` path out of scope. The owner orders the v2 record and its code first, so a record of its own can be written, reviewed and landed on its own timetable, and its member names, spellings and `step` values are written once, in one place, for all three tools. Every decision of this record but this one is true for any spelling the v2 record chooses.
- **Order** (**owner**, HQ-0078): no slice of decision 8 lands before the v2 record and the v2 code of both tools; no bf16 timing slice is built on ADR-0063's list or under `sim_run_timing` / `board_run_timing`.

### 8. (h) The code slices, in landing order (for the planner)

0. **First, outside this record** (**owner** order, HQ-0078): the v2 record (a document task), then its code for `correctness.check` and for `sim.run` / `board.run`, fp32 `gemm` and the bf16 checks migrated. The v2 record lists and sizes those slices; this record does not.
1. **The timing programs of the four ADR-0163 kinds** (`gemm`, `rmsnorm`, `elementwise_add`, `swiglu`) and their shared header, with the Python side that forms their command lines and judges their reports through `hilclaw.harness.timing` unchanged; compiled and run with a stub kernel in the C gate. No tool path changes.
2. **The `rope` and `sdpa_kv_cache` timing programs** (decision 2), with the `rope` rows on standard input.
3. **The run tools for bf16 on the mock**: admission and the parameters per kind (decision 4), the v2 result of a bf16 run (decision 7) where the v2 code does not already produce it for a non-`gemm` kind, and the readers of run lines where they read only `m`, `k`, `n`; the mock's default script unchanged for bf16 calls (decision 9). No `timed` flag yet.
4. **The `cpu_standin` operation for bf16 runs**: the six programs built with the header copy (decision 3), the limits of decision 6 in `standin_settings`, the `rope` rows through the container client (ADR-0180 decision 3) — then the **`timed` flags** of the six entries (ADR-0177 decision 2), after which the instance start admits them with no change of its own. It may be cut in two along the size cap (the four ADR-0163 kinds first, `rope` and `sdpa_kv_cache` with the flags second).

Slices 1 and 2 may be one task under DRIVER §6 "task 단위" ③ if they fit the size cap together.

### 9. (f) The mock's default script

- **Unchanged**: it reads none of its parameters and answers ADR-0066 decision 4's report and no figure for every call (cited: ADR-0066 decisions 3 and 4), so a bf16 run on the mock is a converged result with no memory figure and the kind's `shape` (decision 7). The contract tests can therefore run a bf16 run on the mock; a script of a test can stand for any other kernel (cited: ADR-0066 decision 5).

- **What a bf16 run puts into that frame** — the kind, dtype and layout of the covering entry and the kind's shape member names — are **values of the approved open list "kernel contract table"** (`hilclaw.contract_table.TABLE`, ADR-0177; DRIVER §3, D23), entering the v2 members whose definition is "what the contract fixes" (the contract-key member and `shape`, HQ-0078 ② and ③, which D23 names). That is no schema change. No BLOCKED reason remains for this record.

## Alternatives considered

- **One shared bf16 timing driver with a kind argument** — rejected (decision 2): it cannot link with one kernel without weak symbols, and it gives a kernel a way to tell programs apart.
- **Reusing the bf16 verification programs with a timing mode** — rejected by ADR-0107 decision 2 (b) and (c) for the same reasons (cited).
- **Operands from ADR-0009's float generator rounded to bf16** — rejected: rounding can leave the contracts' sets (cited: ADR-0156 decision 9), and a second generator would be written for nothing.
- **A fixed P = 0 for every `rope` timing run** — weighed: the work is the same, but m = 1 at P = 0 is no op_signature position, and ADR-0180's rule costs nothing; taken the rule.
- **Resetting the `sdpa_kv_cache` rows P … l − 1 between repeats** — rejected: the reset would lie between repeats, outside the interval but touching the cache lines the next repeat reads (a caching effect of its own, OD-16 threat B ⑸), and the state the contract admits is already the same at every repeat.
- **No memory figure for bf16 runs** — rejected: it would need a reason specific to bf16, and there is none.
- **A process rule with the element term once rather than per call** — weighed: closer to the timing program's work, but a second function and a smaller limit for no gain in safety.
- **Mapping the bf16 shape onto `m`, `k`, `n`** to keep ADR-0063's list — rejected: it changes the meaning of the members (a change under ADR-0100 decision 4), and the owner chose v2 (HQ-0078).
- **Defining the v2 format as decision 7 of this record** — rejected (decision 7): v2 is the result of three tools and of fp32 `gemm` and the bf16 checks, outside this record's subject and its task's scope, and the owner orders it before every slice here; one record of its own keeps its names in one place.
- **Building the bf16 timing programs (slices 1 and 2) before the v2 code, since they do not touch a result** — rejected: the owner's order puts the bf16 timing slices on top of the v2 code (HQ-0078), and this record does not read an exception into it.
