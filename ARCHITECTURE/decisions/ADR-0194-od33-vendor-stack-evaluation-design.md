## Decision

### 1. Scope and terms

- A **vendor target** is a target (ADR-0016 decision 1) whose build or run needs a vendor toolchain in D29's sense. The target table holds none today.
- An **adapter** is the package code that does one of three things for one vendor target: **build** (sources and the target's values → one built artefact), **run** (an artefact → one ended process) and **measure** (the report of an ended timing process → the measurement of [ADR-0183](ADR-0183-od18-tool-result-format-v2.md) decision 4, or a broken condition).
- Each adapter has three parts: **assemble**, **execute** and **interpret** (decision 2).

### 2. The adapter boundary

- **Assemble** is a pure function: from the target's values and the attempt's inputs to an argument list, an environment and the files to place. It starts no process and reads no file, clock or variable.
- **Execute** is one of the existing executors, unchanged: on the host `clang_build.build` (for a compiler whose command takes its form) or `local_run.run`, or `standin_container.run_in_container` in a container. **No adapter starts a process of its own**, so the time limit, the killing of the process and the container's properties stay where ADR-0117, ADR-0144 and ADR-0168 put them. `run_in_container` gives a container no GPU or device; giving one is a change of that executor and is the rest of ⑨ (decision 8). Until a record makes it, a GPU or device is used only by a driver test's process on the host (decision 8), never by the runtime: the runtime builds and runs a kernel in the isolation environment (**owner**, 2026-10-15, NFR-4).
- **Interpret** is a pure function: from what the executor returned (status or time limit reached, output bytes, files at named paths) to one outcome of decision 3, with a message. It reads no clock, file or variable beyond the paths it is handed.
- **Why the split** (FR-19 ⑤): assembly and interpretation are tested on any machine with recorded inputs and no tool; only the execution needs the tool, and its tests are skipped where the tool is absent. A tool CI is to have (clang) stays a CI failure when absent (D29, cited).
- **How a vendor target attaches.** It gets a `Target` entry in `targets.py` with its values (ADR-0193 decision 3) and an entry in the backend table whose operations are built from that `Target` and its adapters, as each backend's operations are built with their `Target` (ADR-0193 decision 3, cited). Adapters are no member of `Target`. The program an adapter starts (for example `nvcc`) is that adapter's constant, as `clang` is `clang_build`'s; a driver test runs it on the host or in an image (D29), the runtime in an image (NFR-4), and which image is OD-14, as for `cpu_standin`.
- **What stays the tool function's and the harness's**: the request check, the selection, the step lines and the form of the result (ADR-0016 decision 2 (a)); the report form and the check values (FR-9's harness; ADR-0042 decision 3). An adapter adds no result member and no failure kind (ADR-0016 decision 2 (b)).
- **`cpu_standin` and `virtual_npu` are untouched.** Their operations are not moved onto the adapters in P3-8; no argument list, result or file of theirs changes, and their tests pass unchanged apart from D21 list assertions. A later record may move them if it shows no change.
- **A vendor `Target` has `instance_start` false and `model_run` false** until the owner answers what an instance at it evaluates (V1, V5), as ADR-0193 decision 4 did for `virtual_npu`. **Its backend enters the default backend table only once V6 (a) is answered (decision 3) and, for a target whose kernels use a GPU or device, a record has given the runtime's container that GPU or device (the rest of ⑨)**; until then tests build tables that hold it, as ADR-0016 decision 5 (c) has a test build its own registry. Its backend offers `correctness.check` only once the oracle at it is answered (V5).
- **P3-8 checks the frame with the real clang**: a test builds a target whose build adapter starts `clang`, the tool CI has. No vendor toolchain is needed for the frame and none is faked.

### 3. The outcomes the adapters distinguish

| Outcome | Found by interpret | Answer (existing) | Source |
|---|---|---|---|
| Build success | status 0 and the artefact at its path | go on to the run | ADR-0060 decision 4 (S7 to S9) |
| Compile or link failure | the compiler ends with a non-zero status | result, `outcome` `"broken"`, `condition` `build_exit_status` | ADR-0060 decision 4 (S7) |
| Build time-out | the executor reports the limit | broken, `build_time_limit` | ADR-0060 decision 4 (S8) |
| Status 0 and no artefact | as stated | tool failure `build_output_missing` | ADR-0060 decision 4 (S9) |
| Run failure | the process ends with a non-zero status or by a signal; a device out of memory that the program reports by its status is one | broken, `exit_status` | ADR-0042 decision 3, ADR-0063 decision 3; ADR-0168 (a kernel that exhausts memory) |
| Run time-out | the executor reports the limit | broken, `time_limit` | ADR-0042 decision 3, ADR-0063 decision 3 |
| Build tool missing | the compiler is not found or cannot start; in a build container, status 125 to 127 | tool failure `compiler_unavailable` | ADR-0060 decision 4 (S6); ADR-0168 C3, C5 |
| Run program missing (a vendor runner, an emulator) | on the host, the program is not found or cannot start, before any process; for a container, its client is not found | tool failure `executable_unstartable` | ADR-0060 decision 4 (S10); ADR-0168 C3 |

- **The reading of the last row**: a vendor runner or emulator is the program of the run's process, as the container client is in ADR-0168 C3, so S10 keeps its meaning. It covers only what is found before the process runs. **Inside a process container**, statuses 125 to 127 stay the program's and give `exit_status` (ADR-0168 decision 3), since the attempt's code may run in that process and could end it with 127 to turn its broken result into a tool failure (ADR-0110 decision 3). A runner or emulator missing from an image is found only by a probe that holds no code of the attempt, or by the environment check (decision 7), as an absent device is (below).
- **What fits no existing value: a device absent or unusable when the run starts** (no GPU, a device not reachable). The program starts, so neither S6 nor S10 applies; `exit_status` would be a broken result that counts against the attempt (ADR-0110 decision 3) although the run established nothing about it, which fails ADR-0021 decision 5's test; and a new kind is a data-plane change (ADR-0168 Alternatives). It is asked (V6 (a)). **How it is found, whatever the answer**: by a probe the operation runs before the attempt's process, in a process that holds no code of the attempt (a device query as the environment check's, decision 7). A status or output of the attempt's own process is never read as it: the kernel runs there and could write the same, turning its broken result into a tool failure, the hole ADR-0168 decision 3 and ADR-0110 decision 3 keep closed. A device lost after the probe passed is a run failure. **Until V6 (a) is answered**, the probe's finding is an outcome of interpret that no operation of the default table returns, since no vendor backend is in it (decision 2); P3-9 tests the probe's interpretation, and a fault script stands for the absent device (decision 6).
- **A device lost during a run** (a driver reset) is a run failure as above; whether a board fault is told apart from the attempt's is OD-10, not decided here.
- **The harness's and the waiter's statuses** keep ADR-0168 decisions 3 and 4 wherever the same harness and waiter are used.

### 4. What one timing includes (P3-13)

- **[ADR-0007](ADR-0007-od13-measurement-policy.md) decision 2 holds at every vendor target** (cited): inside the interval, the execution of the kernel on prepared operands and nothing else the harness can keep out; outside, starting and loading the process, building, allocation and input generation, the reference, the comparison and the recording.
- **Launch: inside.** This record reads the launch on an offloading device as part of "the execution of the kernel" of ADR-0007 decision 2: it is how the kernel is executed there, and an interval without it would time no execution the attempt's caller can make. How many launches one repeat holds is the harness design, the same for every repeat (ADR-0007 decision 2).
- **Completion of the GPU work: inside.** Kernel launches are asynchronous with respect to the host ([CUDA C++ Best Practices Guide](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html) v13.4, "Using CPU Timers", read 2026-11-03), so an interval that ends when the launch returns measures the launch only. **A repeat's interval starts after the device has completed all earlier work and ends only after the device has completed that repeat's work**; the harness waits for the device before each of the two clock readings.
- **Synchronisation**: the wait before the start reading is outside; the wait before the end reading is inside, as the way completion is observed, like the clock reading itself.
- **Clock**: the host's monotonic clock read around those waits, the guide's CPU-timer method; `resolution` is that clock's, in `ns` (ADR-0183 decision 4, HQ-0078 ⑤). Device event timers are not used: they leave the launch out and report another resolution.
- **Transfers: outside.** Operands are placed in device memory before the first repeat and read back after the last; those copies are input generation and comparison. A target whose operands stay in host memory is left to its own record.
- **Warm-up**: ADR-0007 decision 6 holds; no sample is discarded. One untimed execution before the first repeat is harness design and allowed; creating the device context and loading or compiling the module just in time are part of starting and loading the process, outside.
- **An emulator's or simulator's timing** is measured by the same definition at its point. Its samples are times of the emulation on the host and are no figure of the device (FR-19 ④); decision 5 keeps them apart.
- **Unchanged**: ADR-0103 (imprecise timing) and ADR-0007 decisions 3 to 9. `memory_bytes` keeps its definition (ADR-0052, the host process); a GPU or NPU memory figure is not reported until the owner states a form (HQ-0090 (나), cited).

### 5. Two measuring points of one target (FR-19 ④)

- **Which execution is which point is not decided here.** For a target with an emulator or simulator and a device it is the configuration HQ-0005 foresaw and OD-18 ⑫ holds, to be settled "together with what it needs and not before"; of what it needs, the emulator is now a toolchain D29 lets the driver obtain, while a hw_profile for code built on one machine and run on another (OD-4) and the access to a device (#5 B-2) stay open. It is asked (V4 ①).
- **The driver's part of OD-33 ④ and ⑥: how results keep the points apart, once assigned.** The `step` value of a result's line is one per tool and point (ADR-0183 decision 2), and an attempt's records are `sim.json` and `board.json` (ADR-0004). **No member or value is added.** `timings.compare` reads one point's value only (ADR-0183 decision 8, cited), so a figure of one point never enters a comparison of the other's.
- **Each operation is bound to one point's adapters**: the backend's `sim.run` operation is built with the run adapter of the means assigned to `sim`, and `board.run` with that of `board`. No request member, variable or fallback lets one point's means answer for the other, for the reason ADR-0016 decision 5 (b) keeps the mock's outcomes apart. When a point has no means, that operation is not offered (`not_offered`, ADR-0016 decision 3).
- **Not the mock's way** (PLAN P3-10's example). The mock keeps a whole target apart under its own `accelerator` and key. An emulator kept that way would be a target of its own, not a point of the device's target, and would split one target's key and knowledge in two; whether the owner wants that is an option of V4 ①.

### 6. The fault-injection script contract (FR-19 ⑤, D29)

- **What it is**: an executable written by a test that stands in for one external program (a vendor compiler, runner or emulator, or `nvidia-smi`) at one adapter's execute part, for one failure.
- **Where it lives**: written by the test into its own temporary directory at run time, or kept as a fixture file under `tests/`. Never under `hilclaw/`, on the machine's `PATH`, in an image or in the data plane.
- **How an adapter is pointed at it**: the adapter takes the program as an argument whose default is its constant, and its assemble part puts that program at the head of the argument list the executor starts, as `clang_build.build` takes `compiler`; the test passes the script's path there. No environment variable, configuration, `PATH` change or request member names a program, for the reason of ADR-0016 decision 5 (b).
- **What it emits**: what the real program emits in the case it stands for, as far as interpret reads it — the status (or no end, for a time limit), the output bytes, the files at named paths. It reads no clock, random source or counter (as ADR-0016 decision 5 (e)). The test names the documented behaviour it stands for, with its source. It is POSIX sh, or Python run by the test's own interpreter.
- **What it may stand for**: only failures hard to cause with the real tool on the machine — no device, a device out of memory, a device lost, the tool's own crash or hang. **Never a success, a compile failure, a version string or an argument the real tool accepts**: those are tested with the real tool where it is present and skipped where it is absent.
- **Never evidence**: a fault-script test shows how an adapter interprets an output, not how a tool behaves. No ADR, `Result`, runtime acceptance item or data-plane record cites it as a fact of the tool, and **it never replaces an absent toolchain**: a task whose toolchain is absent takes the D29 path, whatever fault-script tests pass.
- **Beside the mock** (FR-10): the mock stands in for a whole backend at a tool's contract (ADR-0016 decision 5); a fault script stands in for one program below an adapter. Neither is reachable in a live run; fault injection in a live session stays OD-18 ⑧.

### 7. The environment check command (P3-8): its boundary

- **It reads and never changes.** On the host it reports which toolchain components, drivers and devices are present and their versions; for each tool image named to a target, which toolchain components it holds and their versions. It starts each component's own version or query command with a time limit (for an image, in a container started as ADR-0144 starts one: no network, no pull). Devices are read on the host only, since a container of today is given none (decision 2). It installs, pulls, downloads, updates and writes nothing but its report, and starts no `claude`.
- **No second list of commands**: each probe is assembled and interpreted by the adapters' own parts (decision 2).
- **A missing component is a reported fact**, not a failure of the check; the check fails only when it cannot read.
- **One code for both users**: driver tasks (D29: the executor reads the machine before writing code) and the runtime (S12 step 1). Asking permission for what is missing stays the runtime's (FR-4, NFR-4), not the check's.
- **Where the report goes**: standard output, one JSON document, **outside the data plane**. A driver task copies what it needs into its `Result`. Whether the runtime stores a report, or fills a hw_profile's `toolchain` from it, is not decided here (OD-26, and the owner's where it would change a frame).
- **Version trace** (FR-19 ③, NFR-2): through the open map `toolchain` of the target's hw key, where a new component name is no schema change (ADR-0001 decision 6, cited). Which components a vendor target's `toolchain` holds, and how they are read, is each target's task under OD-26 (D29: not decided by that answer).

### 8. The driver's parts of OD-33 ⑧ and ⑨

- **⑧ This record is the ADR CLAUDE.md asks for a language outside {Python, POSIX sh, C}.** CUDA C++ (`.cu`) and C++ are admitted **as test fixtures only**: kernel sources under `tests/` that a test hands to a real vendor compiler. They are never the code of a layer-2 tool, harness or entry point. CLAUDE.md's per-language CI gates are not extended to them: a fixture is compiled only by an execution test, which runs where the vendor compiler is and is skipped elsewhere (FR-19 ⑤). This is a decision record of the usual form and place (`ARCHITECTURE/decisions/`, ADR-0001 "Record format"); CLAUDE.md asked for the form at the first need, and it is this. A harness for a GPU target is C against the vendor runtime's C interface where one exists; for a target with none, the harness language is a later record's. The layer-3 "C 커널" wording and the coder's role are not decided (HQ-0088 ③ asks, cited).
- **⑨ Driver checks.** D29 (cited) lets them use the host's tools or a tool image. **Reading**: a driver test runs a vendor tool where it is, on the host or in a tool image, as the existing clang tests run clang, and may use the development machine's GPU from a process on the host (decision 2). This is no reading of the runtime's isolation: NFR-4 and ADR-0144's container stay for the runtime. How the runtime's container is given a GPU or device is the rest of ⑨, for the target task's record under §9 (for CUDA: [ADR-0207](ADR-0207-od33-cuda-target-demonstration.md) decision 7); a device on another machine is OD-14 (board isolation) and #5 B-2.

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 2 | Each adapter starts its own process | A second runner beside `local_run` and the container, with its own time-limit and kill rules |
| 2 | Move `cpu_standin` onto the adapters in P3-8 | Churn in accepted records' cited code and a risk to the results of P2-15's check, for no new function |
| 2 | Adapters as members of `Target` | `Target` holds values, and its module states it starts no process; the backend is where operations are built |
| 3 | A new kind for a missing runner or emulator | S10 already means it (ADR-0168 C3's reading); a new kind is a frame change |
| 4 | End the interval at the launch's return | It measures the launch, not the kernel |
| 4 | Device event timers | They leave the launch out, which decision 4 reads as part of the execution, and report another resolution |
| 5 | Assign the emulator to `sim` and the device to `board` here | OD-18 ⑫ settles that configuration with what it needs; it is asked (V4 ①) |
| 5 | A result member naming the point | The `step` value already does; a member would be a frame change |
| 6 | Fake toolchains when the tool is absent | D29: "실제 툴체인이 있으면 그런거 다 필요없다"; absent tools take the HQ path |
| 7 | Write the environment report into the data plane | No use needs it now; it would be an owner question |
| 8 | Harnesses in CUDA C++ | A layer-2 language outside the set, while C reaches the CUDA runtime's C interface |

## Consequences

Which execution is which point (④, OD-18 ⑫), ①, ②, ⑤, the rest of ③ and the rest of ⑥ are not answered. OD-33 and OD-18 ⑫ stay open.
