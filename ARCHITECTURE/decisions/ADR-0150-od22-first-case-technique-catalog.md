## Decision

A sentence is **cited** when a source is named with it. Every other sentence is **this record's own**.

### 1. Scope and terms

- **The runs**: those of ADR-0120 decision 1 whose hw_profile's `accelerator` is `cpu_standin` and whose kernel is `gemm`, `fp32`, `row_major`, in C (`task.contract.language` `c`, ADR-0002 decision 2; ADR-0008 decision 4). **The mock is outside**: this record gives a run whose hw_profile names the mock no entry, and no catalog for it.
- **Terms.** The *catalog* is the set of entry files of decision 2. An *entry* is one technique. Its *id* names it (decision 3). Its *selection criteria* say when the technique is worth trying (FR-7, "언제 쓰면 좋은지"). Its *application guidance* says how to apply it in a kernel (FR-8, "적용 지침"); it is the `text` a spec copies.

### 2. (a) Place and form

- **Place: a top-level directory `catalog/` of the code repository**, beside `orchestration/` and `hilclaw/` and inside neither. Under it **the stand-in's directory, named by the `accelerator` value of ADR-0001 decision 1** (a *name*): `catalog/cpu_standin/`, and in it **one file per entry, named `<id>.md`** — the four files of decision 5; nothing else is under `catalog/`. **This record decides the stand-in's directory only**: a later record for another accelerator may take the pattern over (a directory of its own beside it), and decides that for itself.
- **The layer** (this record's reading of the three-layer model, #5 A-12 as CLAUDE.md states it): the entries are **layer-1 content** — Markdown knowledge that the orchestration uses, of the kind CLAUDE.md names in layer 1 ("기법 Skill, Markdown") — kept outside `orchestration/` because they are not part of the turn session's definition (below). They are not layer-2 code, so the language policy of layer 2 does not apply to them; the module that reads them (Consequences) is layer 2. A 기법 Skill, if the selection side makes one, is that record's.
- **Form of an entry file**: UTF-8, LF line ends, Markdown, in this order and with no other heading of level 1 or 2:
  1. the line `# <id>`, the id equal to the file name without `.md`;
  2. `## Applies to`, holding exactly four list lines `- kind: gemm`, `- dtype: fp32`, `- layout: row_major`, `- language: c` — the op_signature's `kind`, `dtype` and `layout` (ADR-0001 decision 2) and the contract's language (ADR-0002 decision 2);
  3. `## When`: the selection criteria, prose;
  4. `## Guidance`: the application guidance, prose, the last section.
- **The `text` of an entry** is the content of its `## Guidance` section, from the line after the heading to the end of the file, with leading and trailing line feeds removed and nothing else changed (Markdown stays as written); it holds at least one character, as *text* requires (ADR-0002 decision 2).
- **How A-7's "keyed separately" is met** (this record's reading of K3): the stand-in's catalog is its own directory. [ADR-0134](ADR-0134-od26-first-case-key-records-store.md) (O2) reads the same sentence as "a key of its own, not a means or a moment of registration", and that reading stands: every hw_profile of the stand-in names `accelerator` `cpu_standin`, a key field (cited: ADR-0001 decision 1, "for example `cpu_standin`"), so a directory named by the accelerator is reached from every key of the stand-in and from no key of another accelerator — the separation follows from the stand-in's own hw_profile, as A-7's "so" says. An entry of `catalog/cpu_standin/` is offered to no run whose hw_profile names another accelerator (decision 4), and the same id under another accelerator's directory would name an unrelated entry. **Not by the hw_profile key**: the key changes with every key field — `revision`, `toolchain`, `host` (cited: ADR-0001 decision 1) — so a catalog keyed by it would need a copy per clang version and host; FR-7 statistics stay keyed by the full key below `db/<hw_profile_key>/` (cited: ADR-0004, `technique_stats.json`), which this record does not touch.
- **Why the code repository**: K2 keeps the project's distilled catalog in the "upstream 소스 repo"; the stand-in's set is "not the project's optimization asset" (K3), so K2 does not bind it, and putting it in the same repository is this record's reading of K2; FR-8 and the glossary start P1 with "repo 내 문서"; a run's `instance.json` records the source commit (NFR-7 ③), so the catalog a run could read is named by that commit, as far as the source has not changed since the start (the same limit as ADR-0116 decision 2 states for the build flags); and a change of an entry is a reviewed commit. `catalog/` is not among the document-mode paths of CLAUDE.md A-13, so **an entry is added or changed in code mode** (Draft PR, review, tests) — this record's reading of A-13.
- **Why not under `orchestration/`**: everything there is the turn session's definition and is copied into the session (ADR-0118 decision 5; `turn_definition.put`), which refuses a top-level entry outside `LAYOUT` (Context); the application guidance is for the coder, which gets it only inside its spec (ADR-0002 decision 1), not for the session.
- **Why not under `hilclaw/`**: the package is the tool layer — "FR-10 도구·mock/`cpu_standin` 백엔드·CAS blob·스키마 검증(STATE/spec/eval/artifacts)·hook 진입점·검증 하네스 FR-9" (cited: FR-10, #5 A-12); an entry is prose, not a tool. A module that reads the entries belongs there (Consequences, slice 1), as `hilclaw.turn_definition` reads `orchestration/` from outside the package (observation: its `SOURCE`).
- **The FR-8 split on this place** (this record's reading of FR-7 with FR-8). The **application guidance** is the entry's `## Guidance` and travels into a spec (decision 4): "적용 지침은 코더 spec에" (FR-8). The **selection criteria** are kept with the entry in `## When`, which FR-7 asks for ("함께 저장"). FR-8's "선택 기준은 Orchestrator 세션에서 트리거에" — **whether a `Skill`, a tool, or another means brings them to the session that selects, and whether that session reads `catalog/` at all, is the record of the selection side's (HQ-0048)**; this record makes the `## When` section the place they are written and says nothing more of their way to a selection.

### 3. (b) An entry and its id

- **What an entry holds**: its id, the four values of `## Applies to`, its selection criteria and its application guidance — **nothing else**. No statistics (OD-7; `technique_stats.json` is per key in the data plane), no version number, no provenance member (the candidate A-11, K6) and no reference to external material (OD-12). A later record may add a section; it states whether that section travels into a spec.
- **The id is a *name* of ADR-0001 decision 1**, `[a-z][a-z0-9_]{0,31}`. Why: it is a *string* (ADR-0002 decision 2), so `guidance.techniques[].id` and `feedback.attempts[].techniques[]` hold it as it is; it is a valid file name on every system of C-7 and, with lower case only, cannot collide with another on a file system that ignores case (C-7 ①, macOS and Windows under WSL); and it has the form of the names of the key records. No prefix for the accelerator: the directory gives it, and a spec carries its accelerator in `hw_profile.record` (cited: ADR-0002 decision 2).
- **The first entries are candidates, not admitted knowledge.** They enter as FR-8's "P1에서는 기법 후보 = repo 내 문서로 시작": written by hand, not entries that met the entry criterion proposed under OD-7 (§ OD-7, "흡수: 카탈로그 진입 기준" — held-out correctness, a real board measurement and an isolated evaluator's PASS). Whether a catalog entry must later meet such a criterion, and what then becomes of these, is OD-7's.
- **An id is unique in its accelerator's directory** (it is the file name), so (accelerator, id) names one entry.
- **An id is never given to another technique.** Once an entry has landed on `main`, its id names that technique for good: a change that makes the entry a different technique takes a new id; an entry removed (UC-5, "삭제") leaves its id unused for good. Rewording, correcting or extending the criteria or the guidance of the same technique keeps the id. Whether a change keeps the technique is judged in the review of that change. Why: cases and statistics refer to what a spec applied by id (`feedback.attempts[].techniques`, ADR-0002 decision 2), and an id given again would join two techniques in them.
- **A change of an entry's text and the specs already written.** A written spec holds its own copy and is never changed (cited: ADR-0002 decisions 1 and 2, Consequences), so it keeps the text it was written with; two specs may carry one id with two texts. **The spec's copy is the record of what a call was given.** Whether statistics or cases treat the two as one technique is OD-7's and OD-30's.

### 4. (c) What an entry gives a spec

- **An entry gives exactly one member of `guidance.techniques`: `{"id": <its id>, "text": <its text>}`**, the form of ADR-0002 decision 2, unchanged: no new member, no new value, no new version. `## Applies to` and `## When` never travel into a spec.
- **An entry may be given only to a spec whose `hw_profile.record.accelerator` names the entry's directory, whose `task.op_signature.record` has the entry's `kind`, `dtype` and `layout`, and whose `task.contract.language` is the entry's language.** This rule is part of what an entry gives (answer (c) of this record), not a rule of composing a spec, and answers none of OD-6's open points; what checks it when a spec is composed is part of the composition (below).
- **Not decided here** (HQ-0048; rest of OD-6): which entries a spec of a round ≥ 1 carries, how many, in what order, who chooses them and by what means, how they reach `spec.write` or another writer, what `decision/decision.md` and `decision/hypotheses.json` say of them, and whether a hypothesis names one (ADR-0059 decision 3 stays as it is). **Round 0 carries none** (ADR-0138 decision 2 (b), unchanged).

### 5. (d) The first entries

- **Four entries in `catalog/cpu_standin/`**, a small set to exercise the loop (K3); none is claimed to be fast, and none is the project's optimization asset (K3):

| id | Gist |
|---|---|
| `loop_order_ikj` | Order the loops i, k, j so that the innermost loop walks a row of `b` and a row of `c` contiguously; set each row of `c` before accumulating into it. |
| `cache_blocking` | Split the i, k and j loops into blocks so that the parts of `a`, `b` and `c` one block uses can stay in cache, with remainder blocks for sizes that are not a multiple of the block. |
| `register_blocking` | Compute a small tile of `c` (a few rows by a few columns) in local accumulators across the k loop and store it once, with a remainder path for the edges. |
| `simd_baseline_intrinsics` | Compute several adjacent elements of a row of `c` at once with the SIMD intrinsics of the processor's baseline — SSE on x86-64, Advanced SIMD (NEON) on arm64 — selected by `#if defined(__x86_64__)` and `#elif defined(__aarch64__)`, with a scalar path for any other processor and for the remainders. |

- **Why each fits ADR-0008 and ADR-0116 on every machine kind of C-7** — Linux, macOS and WSL, on the host or in the container of ADR-0144, on an x86-64 or an arm64 processor:
  - **All four** keep the contract: one definition of `hilclaw_gemm` with the prototype of ADR-0008 decision 4, no `main`, no other external identifier starting with `hilclaw_`, and no header beyond the C standard library and the target's SIMD intrinsics headers — narrower than ADR-0008 decision 7, which allows `<omp.h>` as well (cited); leaving it out is this record's choice, with HQ-0034; every `m`, `k`, `n` ≥ 1 handled, `c` written before it is read, no alignment beyond that of `float` assumed (cited: ADR-0008 decision 6). **None needs a flag, a define, a library or a setting** beyond the fixed set (cited: ADR-0116 decisions 2 and 3), and **none uses OpenMP** (`-fopenmp`, `<omp.h>`, `#pragma omp`; HQ-0034) **or any other thread** — this record's choice, since ADR-0008 decision 6 allows threads ("Threads are allowed") and HQ-0034 asks of OpenMP only: the first set stays single-threaded, and whether a thread library is "another library" stays ADR-0008 decision 7's open point.
  - **`loop_order_ikj`, `cache_blocking`, `register_blocking`** are plain C under `-std=gnu11` and mean the same on both processor families.
  - **`simd_baseline_intrinsics`** uses only what each family has without a target flag. ADR-0116 decision 3 names SSE2 as the x86-64 baseline ("code the compiler vectorises by itself targets the baseline (SSE2 on x86-64)", cited — a sentence about the compiler's own vectorisation); that the SSE and SSE2 intrinsics, declared by `<immintrin.h>`, therefore build on x86-64 without a flag is this record's statement. On arm64, Advanced SIMD is part of the AArch64 baseline, declared by `<arm_neon.h>` (this record's statement, from the Arm architecture, not from a record). **Unaligned loads and stores** (`_mm_loadu_ps`, `vld1q_f32`) keep ADR-0008 decision 6's alignment row. **No function attribute and no feature beyond the baseline** (AVX, AVX2, AVX-512, SVE) is used, so no run-time processor check is needed and no instruction can be missing on a machine of either family. The explicit fused multiply-add of Advanced SIMD is allowed: ADR-0116 decision 3 keeps it open to a kernel ("a kernel can still ask for one explicitly"). The ordering of sums and the fusing differ from a scalar kernel; whether the result passes is the tolerance's (FR-9), and the text claims no equality.
- **Weighed and not in the first set**: an AVX2 path under `__attribute__((target("avx2")))` (cited as the means: ADR-0116 decision 3) — it needs a run-time check of the processor before the call, or an x86-64 machine without AVX2 stops on an illegal instruction, and the set is meant to be small; packing a block of `b` into the kernel's own scratch memory (allowed: ADR-0008 decision 6, "scratch memory of its own") — it can be a later entry; OpenMP or other threads (HQ-0034).
- **The full texts are left to the code slice** (Consequences, slice 1) **and reviewed against this record**; this record does not hold them, so an edit of a text later does not make the record false. **Each `## Guidance` text**:
  - **must** say what to change in the kernel and how; say, where the technique touches it, what keeps the kernel within ADR-0008 decisions 4, 6 and 7 (the remainders of every `m`, `k`, `n` ≥ 1; `c` set before it is read; no alignment beyond `float`); for `simd_baseline_intrinsics`, the two `#if` paths, the scalar path and unaligned access; be in English and be complete without any other file, entry or link (ADR-0002 decision 1: the spec is the whole input).
  - **must not** claim a measured speed-up, a measured or tuned value or a ranking, since the project has measured none (a block size or a tile size may be named only as a value to start from, so marked); ask for a compiler flag, a define, a library or a `task.build` member (ADR-0116 decision 2); mention OpenMP, threads or a feature beyond the baseline as something to use; hold a verification input, a seed or an expected value (ADR-0002 decision 2, "No field carries verification inputs"); or copy or name external code or material, nntrainer among them (K5; OD-12; K6).
- **Each `## When` text** states, in the terms of the op_signature's shape and of what an earlier attempt shows, when the technique is worth trying (for example `m` of 1 against `m` above 1), and claims no measured effect either.

### 6. (e) What follows

- **One code slice** (the entries and their reader), **no runtime acceptance item**, the sentences of earlier records made less exact, and the cost: Consequences. **What stays open**: Boundaries.

## Consequences

- **Code slice for the planner** (code mode — `catalog/` is not a document-mode path; tests with fixture directories only, no `claude`, D16):
  1. The four files of `catalog/cpu_standin/`, with texts that keep the rules of decision 5, and a new module `hilclaw/catalog.py` that reads an accelerator's directory and checks the form of decision 2 (the file name a *name*, the `# <id>` line equal to it, the sections and their order, the four `Applies to` lines, a non-empty text, UTF-8 and LF, no other file in the directory) and returns, for an accelerator and an id, the `{id, text}` of decision 4. It is **not a registry tool** and is added to no registry; what calls it is the selection side's and the rest of OD-6's. With `tests/test_catalog.py`: fixtures for each refusal, and a test that the committed `catalog/cpu_standin/` passes the check. **Test rules**: ①, ② and ③ apply to the module and ④ gives it its test file; the entry files are not modules; ⑤ does not arise (nothing tested is a test, CI or hook script). About 120 lines of entries and 100 of module in five files: within the D4 cap; the planner splits it in two (module with fixture tests, then entries with the test that the committed directory passes) if not.
- **Runtime acceptance items: none.** (lxvii) is not used: nothing here runs in a turn session, needs a board or asks anything of `claude`; whether a coder follows a guidance is what the loop measures, and a kernel that does not build is the ordinary broken result.
- **Less exact, not edited** (found by a search of `ARCHITECTURE/decisions/`, `hilclaw/`, `tests/` and `orchestration/` for "catalog", "OD-22" and "No catalog"; not claimed complete). Each stays true outside the scope of decision 1, and inside it says what was true when it was written:
  - ADR-0058 Context ("no file of the repository is a catalog entry and no record defines a catalog file"), decision 1 ("No source gives one"; "**This judgement does not close OD-22**"), L5 and Boundaries ("the stand-in catalog, how it is filled, its documents and any technique `id` or `text`"). Its committed example stays right to carry an empty list: it is not a real call.
  - ADR-0059 Context ("No catalog exists (OD-22)"), decision 3 ("no catalog entry exists"), and Alternatives ("No catalog entry exists (OD-22); any id would be invented"). Its rule that a hypothesis names no technique is not changed: that is a member of `hypotheses.json` (Boundaries).
  - ADR-0002 Boundaries ("a technique of the stand-in catalog", among the values no source gives); ADR-0008 Consequences and Boundaries ("a technique of the stand-in catalog", among what is still missing); ADR-0050 Example ("no source gives a technique of the stand-in catalog (OD-22)") and Boundaries ("OD-22: the stand-in catalog and any technique"); ADR-0035 Consequences and Boundaries ("a technique of the stand-in catalog"; "the stand-in catalog and any technique").
  - ADR-0138 Alternatives (f) ("a placeholder states a catalog entry that does not exist") and Boundaries ("the catalog and any entry (OD-22)"); its decision 2 (b) stays exact.
- **UsageCases and StandardScenarios**: no sentence becomes false. The glossary's "Phase 1에서는 repo 내 문서로 시작" and UC-5's "카탈로그에 추가" now have a first place for the first case; S1 step 4 ("카탈로그에서 기법을 랭킹·선택") has a catalog to select from, and its ranking and selection stay open (OD-7; the selection side); S4 stays supported. No verdict changes.
- **A-13 reading.** Document mode. No code, test, setting or dependency changes. **No data-plane schema change**: no member, file, kind, value or version of the data plane is added or changed. The slice adds a top-level directory of the source repository, not of the data repository.
- **The cost, plainly.** The first catalog is four hand-written entries for one accelerator, one operation and one language; it is not OD-22's cold start and says nothing measured. No agent reads it until the selection side's record and the rest of OD-6 say who does and how, so until then no spec carries an entry. "Never given again" is kept by review, not by a check: nothing in the slice remembers a removed id. A change of an entry needs a code-mode PR. The guidance does not guard the build: a coder may still write code outside it.
