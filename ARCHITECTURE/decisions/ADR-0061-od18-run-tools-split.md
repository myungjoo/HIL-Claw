### 1. Scope and terms

- **A call of `sim.run` or `board.run` about one attempt of a run** whose hw_profile names `cpu_standin` — the first case, kind `gemm`, fp32, a C kernel (cited: ADR-0021 decision 1), in the local configuration of ADR-0038 decision 1 — **or names the mock**. Of that call it fixes **six points and nothing else**: the operation (decision 2), the split (decision 3), the sample form (decision 4), the call that carries the figure (decision 5), the `bound` (decision 6) and the classes of outcome (decision 7).
- **The mock is this record's own scope.** The owner's answer that a run at the mock is answered by the first case's contract is about `correctness.check` (cited: ADR-0038 decision 6). This record takes the same for the run tools, for the reason that answer gave — "so that the contract tests of P1-1 run the whole judging over the mock" (**owner**, HQ-0005 point 4, at the link of O1) — and FR-10's mock "고장 주입·계약 테스트". For a run at the mock, decisions 3 to 7 hold for the tool function as they stand; the mock's operation, its script and what a default script returns are not decided (Boundaries).
- **One contract that both tools follow.** **Owner** (O1): "nothing but the execution point distinguishes the two operations." The two tools stay two tools with two operations (cited: ADR-0038 decision 2, "They stay two tools with two operations"; ADR-0016 decision 2), and every point of this record is stated once for both: they differ in the name of the tool and in the execution point it stands for (decision 5), and in nothing this record fixes. Two texts would be one contract twice and could drift. **What could split them** is a configuration in which the sim point is not the board point's run — the foreseen emulated `sim.run` (sub-question ⑫ of OD-18), a simulator or a board (#5 B-2, B-3); a record of such a configuration says whether this contract still answers both.
- The terms of ADR-0009 (driver program, timing executable, timing run, Python side, completed, broken), ADR-0016 (backend, operation, target, the moments ① to ⑦), ADR-0021 (the cut), ADR-0030 (ⓢ), ADR-0038 (execution point, sim point, board point, the local configuration), ADR-0052 (the figure; a verdict: *within*, *over*, *not judged*), ADR-0055 (the reader, the compiled set) and ADR-0056 (the output path, the build directory) are used unchanged. **The read of ④**: the read of `runs/<run_id>/instance.json` in ④ from which the hw_profile of the call is taken (cited: ADR-0018 decision 4; ADR-0016 decision 4).

### 2. What the operation of a call does at `cpu_standin`

- **The operation carries out exactly one timing run of ADR-0009 of the attempt's kernel at the call's execution point, and the figure of ADR-0052 decision 4 is obtained from that run.** One run is one process of one timing executable and takes the repeats of at most one measurement (cited: ADR-0009 decision 1); the figure is "a by-product; no run of its own and no change of that run" (cited: ADR-0052 decision 4). Each of the two operations carries out its run itself when it is called (cited: ADR-0038 decision 2, its reading of O1).
- **Who builds the timing executable, and when: the operation, at each call**, from the compiled set the reader of ADR-0055 decision 3 finds at the output path the tool function hands it (decision 3), with one call of `clang_build.build` over the driver source and the compiled set (cited: ADR-0009 decision 2), into a build directory of its own that lies outside both checkouts and that it removes before it returns or raises — the build of ADR-0056 decision 4, taken for the timing executable by this record. **Three ways were weighed.**
  - **(a) Built at each call.** No outcome depends on anything an earlier call left (cited: ADR-0010 decision 7; ADR-0016 decision 2 (c)); what is timed is built from what the reader saw at that call; and nothing is needed that is not decided.
  - **(b) Built once per attempt and used by both points.** The executable would have to outlive the call that built it. Kept in the process of the tool layer, an outcome would depend on state kept from an earlier call, which ADR-0010 decision 7 excludes. Kept in a file, it needs a holder of the build step ("No source says which agent or tool runs that build" — cited: ADR-0004 decision 3), a path that no record gives, a rule that ties it to the source and the settings it was built from, and a rule for a call of one point that finds none; and an executable is a binary, which goes into no git tree (cited: #5 A-2 as ADR-0056 decision 4 quotes it). A sim-point call would also leave something a board-point call reads, which ADR-0038 decision 2 left to "result files and members no record defines".
  - **(c) A cache keyed by the source**: allowed by the frame (cited: ADR-0016 decision 2 (c)), but its key would have to cover every input of the build, and "The sources of the settings are open, so the key cannot be stated" (cited: ADR-0056 decision 4). Not adopted; a later record may add one under that condition.
- **The choice is (a).** Its cost: an attempt that reaches the board point is built four times — the timing executable at each point and the verification executable at each check (cited for the latter: ADR-0056 decision 4) — and the file timed at one point is not the file timed at the other. ADR-0038 decision 8 named "a second build if each call builds" among what can differ between two runs of one attempt; under this record it does. **ADR-0055 decision 9, "Who builds the kernel of an attempt, when"**, is answered for the timing executable as ADR-0056 decision 8 answered it for the verification executable: the operation of the called tool, at each call.
- **The measurement policy of ADR-0007 applies at each point alike.** The run of one call is one measurement — "one uninterrupted sequence of repeats of one built attempt at one execution point" (cited: ADR-0007 decision 1) — under the same stopping rule and constants at both points, with the one `n_max` the run states (cited: ADR-0023 decision 2, "One value per run"). ADR-0007 decision 1 applies the policy "now to the `cpu_standin` execution point" and gives a simulator and a board "initial values only"; in the local configuration both points are `cpu_standin` carrying out "the same local run" (**owner**, O1), so this record reads the values as those of `cpu_standin` at both points, not as the initial values of a simulator and a board. The two measurements of one attempt are two measurements and "Samples of two measurements are never pooled into one" (cited: ADR-0007 decision 4). Which of them is compared with what, and which counts for promotion or improvement, is not said (OD-15, OD-29, OD-13 sub-question ①).

### 3. The split between the tool function and the operation

- **The tool function's part, the same for every backend**: besides what ADR-0016 decision 2 (a) gives it, it takes from the read of ④ the dimensions, `n_max` and the member `objective`; derives the sample form (decision 4) and reads the `bound` (decision 6); forms the output path; and, on what the operation returned, carries out **all of the judging of the run** — whether the report has the form of ADR-0009 decision 8, whether an interval is 0, the replay of the stopping rule with the sample form and `n_max` it handed over (ADR-0009 decision 7), and so completed (converged or not converged) or broken — and **computes the verdict** (below). It is carried out by the code of the harness, in the process of the tool function, as ADR-0021 decision 2 placed "all of the judging" of a check (cited).
  - **The dimensions** are the `shape.m`, `shape.k` and `shape.n` of the op_signature the run states, the source ADR-0041 decision 2 chose for a check, for its reasons that carry over to a timing run: it is the one statement of the operation that the run makes, it is read in the read of ④, and a member of the request would let a calling agent choose what the kernel is timed on (cited for the reasoning: ADR-0041 decision 2 (a) and (b)). **`n_max`** is the member of ADR-0023, the run's bound of the repeats of one measurement (cited: its decisions 2 and 5). **No value stands in when the file states neither**: not the spec, not a constant and not `N_MAX_DEFAULT` (cited: ADR-0031 decision 5; ADR-0023 decision 4). **What a call answers for a run whose valid file states no op_signature, an op_signature this contract does not cover, or no `n_max`, is not decided here**: ADR-0041 decision 4 asks the record of another tool that needs the op_signature to decide "whether that tool has a kind of its own or the frame reserves one" (cited), and this record leaves that, with `n_max`, to OD-18 sub-question ⑲ (가).
  - **The output path** is that of ADR-0056 decision 3 (b): the path of the `output/` of the attempt the request names, formed by the tool function, which reads nothing there; the operation applies the reader. The reasons of that decision carry over (the mock needs no source; the compiled set is the input of a build of one target).
- **What the operation is handed**, as classes: the request and the hw_profile (cited: ADR-0016 decision 2); the dimensions; `n_max`; the sample form; a seed; the output path. `n_min` and `cv_max` are not handed: "The Python side passes `n_min` and `cv_max` from the constants of `measurement.py`" (cited: ADR-0009 decision 7), which the operation's code does, and the tool function replays with the same constants. **The seed is an input the operation does not choose**, as a parameter of a timing run with no default (cited: ADR-0009 decision 9). **Where the tool function has it from** — fixed or drawn per call, its relation to the inputs of a verification run — **and whether it is recorded is OD-13 sub-question ⑦ and is not answered here.** **An operation is never handed the `bound` or the `objective`.**
- **The settings: the cut of ADR-0060 decision 3, taken for these tools.** The flags, trailing flags and compiler of the timing build, the time limit of the build, the time limit of the timing run and the environment are the backend's own; the tool function hands none of them over, and no value is given. The reasons carry over: the compiler is part of the isolated environment of O5, the time limits belong to a hierarchy OD-14 registers, and handing anything from `task.build` or `instance.json` needs a member name that no record gives (cited: ADR-0060 decision 3 (a) and (b)). So do its costs: a setting a later record prescribes in `task.build`, or one a coder chooses, does not reach the timing build (cited, same decision). **Whether the timing build and the verification build of one backend use the same values is not decided** (OD-16 sub-question ⑥; ADR-0060 decision 3, "only a record of theirs can say whether their settings are the same backend's own" — this record says they are the backend's own and nothing of their values). The values are sub-question ⑲ (라).
- **What the operation returns**, as classes, exactly one of: (A) **the report** — what the timing run's process wrote on its report channel, unchanged, when it ended by itself with exit status 0 within its time limit — **with the figure of that process or that there is none**; (B) **that there is no report, and which condition failed first**, in this order: the build past its time limit, the compiler ending with a non-zero status, the run past its time limit, the run ending with a non-zero status or a signal. The operation does not judge the form or the content of a report. It may also raise a tool failure where decision 7 lets it. The order of (B) is that of ADR-0060 decision 4 for the check — the build before the process, and within each the time limit first (cited) — taken here for the timing build and the timing run; the run's two conditions are the first two of ADR-0009 decision 8 (cited: "it did not time out, its exit status is 0").
- **Why the judging is the tool function's and the figure the operation's.** *The judging*: the reasons ADR-0021 decision 2 gave for the check carry over — what decides completed, converged or broken exists once and runs for every backend; over the mock the same parsing and replay run, so the contract tests run them; and a backend cannot make a run converged by saying so: it returns intervals, and the tool function replays them. The replay is a computation over the reported intervals, the sample form and the constants of `measurement.py` and does not depend on where the process ran. *The figure*: its unit rule depends on the platform the process ran on (cited: ADR-0052 decision 4), which is known where the process was waited for; so the operation converts the usage and returns a number of bytes or none. **A figure returned with (A) is used only if the tool function finds the run completed**: "A run that is not completed yields no figure" (cited: ADR-0052 decision 4), and whether it is completed is decided above the cut. With (B) no figure is returned. **An observation for the code** (binding nothing): `hilclaw.harness.timing.run_timing` does both halves in one function today, as `run_verification` did when ADR-0021 split the check; the code task splits it in the same way. The spelling of what is handed and returned is the next slices' and the code's.
- **Where the verdict of ADR-0052 decision 5 is computed: in the tool function**, from the figure or its absence that the operation returned and the `bound` the tool function read (decision 6). Both sides are "on the Python side, outside the kernel's process, which is handed neither the `bound` nor the figure" (cited: ADR-0052 decision 5), so the requirement holds either way. **The tool function is chosen** because: the `bound` then never crosses the cut; the three outcomes and the rule that *not judged* is never *within* (cited: ADR-0052 decision 5) are held by one code for every backend; over the mock the verdict is computed by the same code as over `cpu_standin`, so the contract tests run it; and a backend cannot answer *within* by saying so — it can only return a figure, and what that limits is Limit 7 below.

### 4. The sample form, from the run's objective

- **Owner** (O2): latency minimisation is "the time of the kernel call as the harness timing run measures it, lower is better." ADR-0050 decision 3 reads this as the interval lengths ("Of the two cases ADR-0007 decision 1 names (\"the time itself, or a rate derived from it\"), the owner's words are the first" — cited).
- **The tool function reads the member `objective` of the run (cited for the member: ADR-0053 decisions 4 and 7) in the read of ④, and derives the sample form from it: for a run whose `objective` states exactly one objective, of type `latency_minimisation`, the sample form is `interval`** (the name of ADR-0009 decision 7): the stopping rule is applied to the lengths of the timed intervals. It is derived at each call; no value is kept, and the request carries none (Alternatives).
- **Covered.** A present `objective` is covered by this contract when its `objectives` holds exactly that one entry and its `constraints` holds no entry of a type other than `memory_ceiling` (decision 6). By ADR-0053 decision 4 every valid member is covered today. **A valid file whose member is not covered** — once a later record admits a further type, more than one objective, a weight or a priority, or another constraint type under ADR-0050 decision 6 (cited), which a member of this file then follows (cited: ADR-0053 decision 4) — **is a tool failure of this contract's own kind `objective_not_covered`.** The record that admits such a step says what a run tool does with it; until it does, this is the answer. Throughput, which "an instance may state ... only once its quantity and unit are fixed" (**owner**, O2), is such a type.
- **A valid file without the member is a tool failure of this contract's own kind `objective_not_stated`.** Such a file "states no objective and no set of constraints", and a reader "never substitutes a value: not `latency_minimisation`" (cited: ADR-0053 decision 5); the sample form "the caller, no default" (cited: ADR-0009 decision 9) has none to come from.
- **Where in the order of a call.** Both are answered in ④, after the selection has succeeded — after `no_backend` and `not_offered`, so the order of ADR-0019 decision 4 stands — before the start line if the tool turns out journaled, and in every case before any operation is called. **For either, the call called no operation, built and ran nothing, consumed nothing at any target and appended no line; the same request can be repeated and is answered by what the file then states.** This contract raises neither in another situation and never as the `failure` of an end line. Their order relative to the answers of OD-18 sub-question ⑲ (가) is that sub-question's.
- **Why this class** — the reasons ADR-0021 decision 4 gave for `tolerance_not_stated`, each checked: *not a result* — no outcome was established about the attempt (cited: ADR-0010 decision 4); *not `invalid_request`* — the request is not at fault, and a refusal reads nothing (cited: ADR-0015 decision 2); *not a kind of ADR-0019* — the file is there, readable, valid and of the supported version (cited: ADR-0053 decision 5, "The member may be absent from a valid file"); *not a run under another form* — no default exists (above). **Why two kinds**: they say different things of the run — that it states no target, or that it states one this contract has no sample form or verdict for — and a caller that knows this contract can tell which without reading the message (the test ADR-0041 decision 5 applied, cited).
- **Not reserved, provisionally.** The kinds belong to the contract of the run tools, which both tools follow, with one meaning in both. Whether `profiler.collect` needs the objective is said by no record; if its record does, it decides whether that tool has kinds of its own or the frame reserves these, and no tool's contract may define a reserved kind with another meaning (cited: ADR-0015 decision 2; ADR-0016 decision 3) — the reasoning of ADR-0041 decision 4 (cited). **The names** are *names* of ADR-0001 (20 and 21 characters). Checked on 2026-10-15 in `hilclaw/`, `tests/` and `ARCHITECTURE/`: neither occurs, and neither equals a reserved kind, a kind of another record, a `step` value or a member name.

### 5. The call that carries the memory figure

- **At an execution point of the first case, the call of the run tool of that point is the call whose timing run's figure is judged**: `sim.run` at the sim point, `board.run` at the board point. The tool called says the point; no member of a request says it, as nothing but the point distinguishes the two operations (**owner**, O1). This is the first clause of OD-13 sub-question ⑩ for the runs of decision 1.
- **Each call judges the figure of its own run**: the ceiling "is judged at each execution point at which a timing run of the attempt is carried out, with the figure of that run", and "It is not judged once for both" (cited: ADR-0052 decision 6). Two calls about one attempt give two verdicts, each of its point; this record adds no rule by which one replaces the other (cited: ADR-0052 decision 5).
- **`correctness.check` carries no figure.** Its run is the verification run, which "is not the timing run" (cited: ADR-0017 decision 1; ADR-0021 decision 1), and the figure is of "one timing run of the attempt" (cited: ADR-0052 decision 3).

### 6. Where and how the `bound` is read

- **The tool function reads it, in ④, in the same read as decision 4**: the `bound` of the verdict is the `bound` of the entry of type `memory_ceiling` in `objective.constraints` of `runs/<run_id>/instance.json` of the run the request names (cited for the record: ADR-0053 decision 7; for the form of an entry: ADR-0050 decision 4). A set of constraints holds at most one entry of a type (cited: ADR-0050 decision 4). **No other source stands in**: not a member of the request — "A `bound` that a caller hands in a request would not meet (c)" (cited: ADR-0052 decision 7) —, not a spec, not a value kept from an earlier call and not a default. This is the second clause of OD-13 sub-question ⑩ for the runs of decision 1.
- **Why there and once.** The hw_profile, the dimensions, `n_max`, the objective and the `bound` of one call are then those of one content of the file; the call knows before anything is built whether it can answer; and every situation of the file at that read has an answer (cited: ADR-0019 decision 3, the rows of ④). A read after the selection's or inside the step would be "a frame file it reads at another moment" (cited: ADR-0019 Boundaries) — the reasons of ADR-0021 decision 4 for the tolerance (cited).
- **No valid file holds such an entry today**: "A file whose `objective.constraints` holds an entry ... is invalid today" (cited: ADR-0053 decision 4). The sentences above say what a call reads once `memory_ceiling` is admitted, and nothing admits it.
- **A present member whose `constraints` is empty: no ceiling is stated, and the result must say so as an outcome distinct from *not judged*.** "no constraint" is stated by a present member with an empty `constraints` "and by nothing else" (cited: ADR-0053 decision 5). The call carries out its run; no verdict is computed, since there is no `bound`; and a caller must be able to tell *no ceiling stated* from *within*, *over* and *not judged*. **Why distinct**: *not judged* is a stated ceiling that was not judged, and "No part of the runtime may treat a ceiling that was not judged as met" (cited: ADR-0050 decision 5); one outcome for both would either hold a run without a ceiling to that principle or let a ceiling that was not judged pass as none. How the result says it is the third clause of ⑩ (no member is named here).
- **A valid file without the member** is `objective_not_stated` (decision 4): it states no set of constraints either, and a reader "does not conclude that the run states an empty set of constraints" (cited: ADR-0053 decision 5).
- **`instance.json` missing, unreadable, invalid or of another version at that read**: the four kinds of ADR-0019 decision 2 by the rows of ④ of its decision 3, and in ⓢ by ADR-0030 decision 4 (cited). A file whose `objective` breaks ADR-0053 is invalid as a whole (cited: ADR-0053 decision 5) and is `run_file_invalid`. No new kind.
- **Condition (c) of ADR-0052 decision 7 is not met by this record.** It names the call and the place of the `bound`; no member of a result carries the verdict, no tool exists and no code was written. `memory_ceiling` stays not admitted.

### 7. Which outcomes are results and which are tool failures

- **Results** — an outcome was established about the attempt at the call's point (cited for the test: ADR-0010 decision 4; ADR-0021 decision 5):
  - **a completed measurement, converged or not converged**: "A measurement that reaches `n_max` without CV < `cv_max` is **usable and marked \"not converged\"**" (cited: ADR-0007 decision 4; ADR-0009 decision 8);
  - **broken** — one class, with the condition that failed first: a run that is not completed "yields no measurement" (cited: ADR-0009 decision 8). Why a result: the experiment was carried out at the target, and each condition can be caused by the kernel, which "shares the process with the driver" (cited: ADR-0009 decision 10) — the reasoning of ADR-0021 decision 5 (cited);
  - **a timing build that ended not ok** — a compile or link failure, or a build past its time limit — **is a result**: **owner** (O4), "yes, as the principle that such a build is a result; the members of their results stay with their records." The owner's answer to point 1 of HQ-0020 — for `correctness.check`, a `broken` result with the new values `build_exit_status` and `build_time_limit` of `condition` (cited: ADR-0060 decision 4, O1) — is an answer for that tool and its members, and O4 takes from it the principle only. **This record follows it as far as the class goes**: such a build is **broken**, in the one class above, with its own condition, and the two build conditions come first in the order of (B) (decision 3). This is the record's reading of O4 together with point 1, not the owner's: no member and no value of a member is taken over, and "the members of their results stay with their records" (**owner**, O4) — the third clause of ⑩.
- **The order of the conditions of broken**, the first that fails being the one reported: the build past its time limit, the compiler's non-zero status, the run past its time limit, a non-zero status or a signal (these four found by the operation, decision 3 (B)); then a report not of the form, an interval of 0, a replay that disagrees (found by the tool function). The last five are the conditions of ADR-0009 decision 8 in the order `run_timing` tests them today, an order of the code (its docstring calls it a convention) that this record takes as its own.
- **What a result must let a caller tell apart, at least**: which of converged, not converged and broken, and for broken which condition; and **where a ceiling is stated, which of *within*, *over* and *not judged***, exactly one — a broken run is *not judged*, as it yields no figure (cited: ADR-0052 decisions 4 and 5), and so, by this record's reading, is a broken result of a build, which carried out no run whose figure could be judged — **and where none is stated, that none is** (decision 6). No member of a result is named here.
- **What a result must never contain**: anything the kernel's process wrote but the report it is parsed from — the standard error, to which the driver points what a kernel prints (cited: ADR-0009 decision 8); the command line, which holds the seed (cited: ADR-0009 decision 5, "The seed travels as a command-line argument"); an input value (cited: ADR-0009 decision 5); and, until OD-13 sub-question ⑦ is answered, the seed or anything a caller could use to pick the seed of a later run. The compiler's log is not returned under this record; whether a timing build's log is kept, and where, is ⑲ (다) — the owner's keeping answer (HQ-0020 point 2) was given for the verification build.
- **Tool failures**: the reserved kinds at their moments (ADR-0015, ADR-0016, ADR-0019, ADR-0026); `objective_not_stated` and `objective_not_covered` (decision 4); the answers of ⑲ (가); and **every situation in which no timing executable can be had or started other than a build that ended not ok** — no kernel source, a reader that fails, a build directory that cannot be made, a setting refused, an input of the build missing, a compiler not found, no executable after a build that reported success, an executable that cannot be started (the situations S1 to S6, S9 and S10 of ADR-0056 decision 5, read for the timing build). **In each, no experiment was carried out**, the test by which ADR-0056 decision 6 and ADR-0060 decision 4 made the same situations of the verification build tool failures (cited). **Which kinds** — the eight backend kinds of `correctness.check` or kinds of this contract — is ⑲ (나). The costs those records stated carry over (cited: ADR-0060 decision 4, "The cost, stated").
- **What anybody does after any outcome** — after *over*, after *not judged*, after a broken run or a failed build — is not decided (FR-1, OD-10, OD-14, PLAN P2-1; Boundaries).

### 8. Limits

1. **A record, not code; nothing was built or run.** What a real compiler, timing run or container does was not tried.
2. **The container against the figure.** O5 has the build and the timing run use a container. ADR-0052 decisions 3 and 4 take the figure as the `ru_maxrss` "the operating system returns with the wait for the ended child process" (cited: ADR-0052 decision 4). Under a container the process the Python side starts and waits for may be a client of the container runtime and not the kernel's process, and its usage would then not be the figure of ADR-0052; the same holds for whether the intervals are those of ADR-0009. **Until OD-14 sub-question ① designs the container, this record is read against the host code**, as ADR-0060 decision 2 was. The question is held by OD-14 sub-question ① (마) — whether a timing and a maximum resident set obtained inside a container are the figures of ADR-0009 and ADR-0052. This record reads (마) as including where and how the figure is obtained under a container, the process whose usage is read among it; so no sub-question is registered for it.
3. **Imprecise timing.** O5, item 3, and sub-question ⑪ of OD-13 are untouched: nothing here detects such an environment or marks a result of it.
4. **A kernel can evade the figure and forge the timing** (cited: ADR-0052 L4; ADR-0009 decision 10). No defence is adopted (OD-16).
5. **No code of either side can be finished from this record alone**: the seed (OD-13 sub-question ⑦), the setting values (OD-14; ⑲ (라)), the container (OD-14 ①), the answers of ⑲ (가) and (나), the identity of a call and the result members are open.
6. **Two points on one machine** exercise no difference between a simulator and a board (cited: ADR-0038 decision 8; ADR-0052 L6); under decision 2 the two runs of an attempt are also two builds.
7. **The operation's answer is believed.** A backend that returns a report of intervals it did not measure or a figure it did not read is not detected: "A backend that does not answer the contract … is not detected by the frame" (cited: ADR-0016 decision 6). The judging and the verdict in the tool function keep a backend from answering *converged* or *within* by a word, not by a number.
8. **Whoever can write `instance.json` chooses the objective and the `bound`** (cited: ADR-0053 L2; ADR-0052 decision 7 does not exclude it).
