## Context

- **What ADR-0153 fixed** (cited): one process per generation runs every kernel call, the buffer work and the call order (decision 1); the model program owns every array, "allocated once for the largest T of the generation" (decision 4); the KV cache per layer is "allocated before the prefill to hold at least the positions the generation writes" and kept "until the process ends" (decision 4); the copies a contract leaves are the program's, and "Casts … are made only if the answer of sub-question 2 requires them; none is decided" (decision 4); the checks run "before anything is built", with five outcomes (decision 5); the driver's verification uses a small synthetic model, and "before their answers [sub-questions 2 and 3], a test checks the binding outcomes, the order of calls, the buffers and the cache across steps" (decision 6).
- **What ADR-0157 fixed** (cited): one dtype per generation, a model parameter; a weight array of another element type than its receiving operand's is invalid input (decision 1); no mixed dtypes and no cast between kernels from it (decision 2); a dtype at which some call site's kind has no contract is invalid input (decision 4), so a full generation is in range only at `bf16` (decision 5). "The element type of the embedding table, and any cast in the embedding row copy, are not decided here" (decision 1).
- **The contracts' call-site tables** (cited): the residual adds (ADR-0159 decision 12), the SwiGLU activation (ADR-0160 decision 12), the two RoPE calls (ADR-0161 decision 15) and the SDPA call (ADR-0162 decision 15) name the producer of each operand. The rotated Q and K and the SDPA output are read without a copy (ADR-0162 decision 5); the Q, K and V ranges of the QKV output are copied (ADR-0161 decision 6, ADR-0162 decision 5); the cache operand is the first l rows of a buffer whose capacity the kernel is never told (ADR-0162 decision 4). No contract allows an in-place call (ADR-0156 decision 7, ADR-0158 decision 7, ADR-0159 decision 8, ADR-0160 decision 8, ADR-0161 decision 11, ADR-0162 decision 11).
- **The landed code** (read): `hilclaw/model_binding.py` has the six kinds' checks (`check`, `check_rmsnorm`, `check_elementwise_add`, `check_swiglu`, `check_rope`, `check_sdpa`), each over its own call sites and not joined; `check` alone takes the prompt's token ids, the given tokens and `lm_head_rows`, the other five take `prompt_length`. `hilclaw/rope_table.py` builds the table from caller-given constants. `hilclaw/model_program.c` runs a list of independent GEMM calls and "is not yet a forward pass".

## Decision

A sentence is **cited** when a source is named with it. Every other sentence is **this record's own**.

Notation: D = `hidden`, F = `intermediate`, V = `vocabulary`, N = `layers`, H = `heads`, H_kv = `kv_heads`, d = `head_dim` (the fields of `ModelDimensions`); W = (H + 2·H_kv)·d, the QKV width; S = the prompt length, G = the generation length; one pass has T rows at positions P … P + T − 1. "bf16" as an element type is a `uint16_t` holding a bf16 pattern (ADR-0156 decision 2).

### 1. The program, the dtype and the order

- **A new model program for the pass**, of fixed source in the package beside `hilclaw/model_program.c`, which stays the GEMM-list program of ADR-0153 code slice 1 and of ADR-0157's fp32 path. The pass program is built at `bf16` only: it is the one dtype at which every call site's kind has a contract (cited, ADR-0157 decisions 4 and 5).
- **The order of one pass** is ADR-0152 decision 2's (cited), with the gate call before the up call in row 11 (this record's choice, the order of `model_binding.CALL_SITES`), `rope_q` before `rope_k` (ADR-0161 decision 15). **The order of a generation** is ADR-0153 decision 4's: one prefill pass (T = S, P = 0), then G − 1 decode passes (T = 1, P = S + k − 1 for decode pass k).
- **Entry points**: for each call, the symbol of its kind's contract — `hilclaw_gemm_bf16`, `hilclaw_rmsnorm_bf16`, `hilclaw_elementwise_add_bf16`, `hilclaw_swiglu_bf16`, `hilclaw_rope_bf16`, `hilclaw_sdpa_kv_cache_bf16` (ADR-0156 decision 5 and the prototypes of ADR-0158 to ADR-0162) — found with `dlsym` in the library bound to that call site at that call's shape. The host side builds one shared library per distinct kernel reference of the joined check's `calls` (decision 6; ADR-0153 decision 3) and hands the program, for each call site and each distinct shape of the generation, the index of its library. How that table is encoded is the code slices'.

### 2. The buffers of the program

Every buffer is allocated once per process, before the prefill, and freed at its end (ADR-0153 decision 4). Activation buffers are sized for T = S, the largest T of a generation, and **shared by all layers**; a decode pass uses their first rows.

- **`x` and `h` alternate** as ADR-0159 decision 8's example (cited, there "an example for the code slice"): this record takes it. `normed` serves the three RMSNorm calls of a pass in turn: each of its readers has returned before the next RMSNorm call writes it.
- **Every activation and cache element is set to the bf16 NaN pattern `0x7FC0` at allocation**, as `model_program.c` sets each output before its call, and not set again: a kernel that reads an output or a cache row before writing it, on that buffer's first use, is then likely to show NaN in the logits, and in any case gives the same result on every run rather than an arbitrary value. The contracts leave that content unspecified (ADR-0156 decision 7 and its peers; ADR-0162 decision 11), so any content is allowed; this one is chosen for being deterministic.

### 3. The operands of each call and the copies

For one pass of T rows at P, layer ℓ (cited: the producer of every operand is the contracts' call-site tables; this table gives it buffer names):

| Row | Call site, shape | Operands |
|---|---|---|
| 1 | embedding (once per pass) | row i of `x` ← row `id(P + i)` of `embedding`, D elements, i = 0 … T − 1 |
| 2 | `attention_norm` (T, D) | `x` = `x`, `w` = `w_attention_norm[ℓ]`, `y` = `normed`; `eps` |
| 3 | `qkv` (T, D, W) | `a` = `normed`, `b` = `w_qkv[ℓ]`, `c` = `qkv_out` |
| 4 | the range copies | row i of `q_in`, `k_in`, `v_in` ← columns [0, H·d), [H·d, H·d + H_kv·d), [H·d + H_kv·d, W) of row i of `qkv_out` |
| 5 | `rope_q` (T, H, d), `rope_k` (T, H_kv, d) | `x` = `q_in` / `k_in`, `freqs_cis` = `rope_table` from row P, `out` = `q_rot` / `k_rot` |
| 6, 7 | `sdpa` (T, P + T, H, H_kv, d) | `q` = `q_rot`, `k_new` = `k_rot`, `v_new` = `v_in`, `cache_k`, `cache_v` = the starts of layer ℓ's two cache buffers, `out` = `attn` |
| 8 | `o` (T, H·d, D) | `a` = `attn`, `b` = `w_o[ℓ]`, `c` = `o_out` |
| 9 | `attention_residual` (T, D) | `a` = `x`, `b` = `o_out`, `c` = `h` |
| 10 | `ffn_norm` (T, D) | `x` = `h`, `w` = `w_ffn_norm[ℓ]`, `y` = `normed`; `eps` |
| 11 | `gate`, `up` (T, D, F) | `a` = `normed`, `b` = `w_gate[ℓ]` / `w_up[ℓ]`, `c` = `gate_out` / `up_out` |
| 12 | `ffn_activation` (T, F) | `gate` = `gate_out`, `up` = `up_out`, `out` = `act` |
| 13 | `down` (T, F, D) | `a` = `act`, `b` = `w_down[ℓ]`, `c` = `down_out` |
| 14 | `ffn_residual` (T, D) | `a` = `h`, `b` = `down_out`, `c` = `x` |
| 15 | `norm` (T, D), after layer N − 1 | `x` = `x`, `w` = `w_norm`, `y` = `normed`; `eps` |
| 16 | `lm_head` | `"all"`: (T, D, V), `a` = `normed`; `"last"`: (1, D, V), `a` = row T − 1 of `normed`; `b` = `w_lm_head`, `c` = `logits` |

- **The copies, and why**: the embedding row copy (ADR-0153 decision 4; decision 5) and the three range copies of row 4. The Q and K ranges are copied because `row_major` has no stride and RoPE reads contiguous `[m, h, d]` arrays (cited, ADR-0161 decision 6); the V range because SDPA reads `v_new` the same way (cited, ADR-0162 decision 5). Each copy moves T rows of contiguous column blocks; head j of row i is columns j·d … j·d + d − 1 of its range, which makes the block of row i exactly row i of the `[m, h, d]` operand (ADR-0161 decision 6's index).
- **Read in place, no copy**: the RoPE outputs by SDPA and the SDPA output by `o` (cited, ADR-0162 decision 5); the cache as the first l rows from each buffer's start (cited, ADR-0162 decision 4); the rows P … P + T − 1 of the RoPE table, which in its row-major `[positions, d]` form are contiguous from row P, so `freqs_cis` is the table's address advanced by P·d (ADR-0161 decision 6: "row i is the table row of position P + i"); the last row of `normed` for `lm_head` `"last"`, contiguous in `row_major`; and every other producer–consumer pair of the table, whose output is the contiguous T × n matrix the consumer's operand is. So the copies of rows 1 and 4 are all the contracts leave.
- **Distinct arrays at every call**: no two operands of one call are the same buffer or overlap, which keeps ADR-0153 decision 3's "distinct arrays for each operand" and every `restrict`.
- **No cast between kernels.** Every array passed from one kernel to another is bf16, the type of both operands (cited, K3 (2) "입출력은 bf16"; ADR-0157 decision 2: one dtype, no cast between kernels). The RoPE table is `fp32` because the RoPE contract's operand is (cited, ADR-0161 decision 6); it is an input made by the host side (decision 4), not the output of a kernel converted. `eps` is the binary32 value of `model_binding.rmsnorm_eps`, which ADR-0158 decision 5 makes the parameter (cited). The embedding row copy makes no cast either (decision 5).

### 4. The KV cache and the other inputs

- **The cache.** Per layer, two buffers `cache_k` and `cache_v` of **C = S + G − 1** rows of H_kv·d bf16 elements: C is the largest l of the generation (cited, ADR-0162 decision 15: decode pass k has l = S + k), so it holds every position the generation writes and the guarantee C ≥ l (ADR-0162 decision 4) holds at every call. **Before the prefill** every row holds `0x7FC0` (decision 2); the prefill of layer ℓ writes rows 0 … S − 1 and decode pass k row S + k − 1, and rows 0 … P − 1 at a call hold what earlier calls of the same layer wrote, as ADR-0162 decision 4 lets the kernel assume (cited). **Lifetime**: from allocation to the end of the process, passed only to its layer's `sdpa` calls, not written by the program after allocation. C is a rule over the generation's own lengths, the least ADR-0153 decision 4's "at least the positions the generation writes" allows; **no capacity value and no longest sequence is chosen**, which ADR-0162 Boundaries ("the capacity value and the longest sequence") and ADR-0165 Boundaries ("The model program's cache capacity and longest sequence") give to sub-question 6 (cited).
- **What the host side hands over** (ADR-0153 decision 3, (a), (b) and (d)), and who makes it:
  - **the weights**, made by the caller (a test or a later loader, sub-question 5): `embedding` (V × D), per layer `w_attention_norm` (D), `w_qkv` (D × W), `w_o` (H·d × D), `w_ffn_norm` (D), `w_gate` and `w_up` (D × F), `w_down` (F × D), then `w_norm` (D) and `w_lm_head` (D × V), each a bf16 array in the layout of its operand (cited, ADR-0153 decision 3 (b), ADR-0157 decision 1). **The column order of `w_qkv`** is that of row 4: the Q range, then the K range, then the V range, head by head within each. It is the executor's input convention, needed because the copies of row 4 depend on it; how a model file's separate Q, K and V weights become it is sub-question 5 (ADR-0161 decision 6 gives that to "how the joined QKV weight is formed");
  - **`eps`**, a model parameter given by the caller, passed as `rmsnorm_eps(eps)`, computed by the host side;
  - **the RoPE table**, computed by the host side with `rope_table.build(head_dim=d, positions=S + G − 1, …)` from the five constants `theta`, `scale_factor`, `low_freq_factor`, `high_freq_factor` and `old_context_len`, which the caller gives as model parameters (ADR-0153 decision 3 (a), "the RoPE constants"; ADR-0161 decision 4: positions 0 to the last position of the generation). No constant is chosen here, Llama's included (HQ-0070);
  - **the token ids**, made by the caller (sub-question 5 for a real tokenizer): the prompt (S ids) and the given tokens (G ids, decision 7).
- **The binary form** of the program's input and report stays with the code slices (ADR-0153 Boundaries, ADR-0157 Boundaries).

### 5. The element type of the embedding table: bf16 patterns, copied with no cast

- **Decision**: the embedding table is a V × D `row_major` array of bf16 patterns, one `uint16_t` per element, row t the vector of token t; the row copy copies D patterns per row, with no arithmetic.
- **Derivation**, as a reading of K3 and ADR-0157 decision 1:
  1. The Llama goal is bf16 only (owner, K3 (1)); every kind's inputs and outputs are bf16 (owner, K3 (2)); a bf16 value crosses the kernel boundary as its 16-bit pattern and "변환은 커널이 한다" (owner, K3 (3)).
  2. The rows the copy writes are the operand `x` of layer 0's `attention_norm` (cited, ADR-0152 decision 2, rows 1 and 2) and the operand `a` of its `attention_residual` (cited, ADR-0159 decision 12), both bf16 in their contracts (ADR-0158 decision 6, ADR-0159 decision 7). So whatever the table holds, the copy must produce bf16 patterns.
  3. The host side holds a bf16 GEMM weight as its 16-bit patterns and does no arithmetic on it, and the other kinds' operands take the element types their contracts give (cited, ADR-0157 decision 1); a weight is in the element type of the operand that receives it (cited, ADR-0153 decision 3 (b)).
  4. A table held in any other element type would need a conversion into bf16 in the program, outside every kernel, which (3) of K3 does not give and ADR-0157 decision 1 avoids for weights. Held as bf16 patterns, the table is in the element type its rows' receiving operands already have, and the copy needs no conversion.
  So the reading takes **no new value**: bf16 is K3's dtype and `uint16_t` K3's representation. Converting a model file's table to bf16, and whether lm_head's weight is tied to it (then `w_lm_head` is its transpose, made by the caller), are sub-question 5's. **Listed under "Readings for the owner to check".**

### 6. The checks before anything is built

- **One whole-generation check** (ADR-0153 decision 5) takes the model parameters (the dimensions, the dtype, `eps`, the RoPE constants), the weights, one binding mapping over the fifteen call-site names of the six kinds, the prompt, the given tokens, the generation length and `lm_head_rows`. It splits the binding by call site and runs **all six** existing checks, in the order `check`, `check_rmsnorm`, `check_elementwise_add`, `check_swiglu`, `check_rope`, `check_sdpa` (the order of `model_binding`'s call-site tuples), with `prompt_length` = S for the five that take it.
- **Join: all, not first.** The outcomes are this record's own invalid-input outcomes (below) followed by the six checks' outcomes in that order; an invalid-input reason whose text equals an earlier one's (the lengths, which several checks report) is given once. `ok` holds exactly when there is no outcome; then the calls are the six checks' `calls` in the same order. Reason: every check is pure and builds nothing, so reporting every unfit entry and missing shape at once lets a caller correct a binding in one step, and ADR-0157 decision 4 already expects an unknown dtype to name each kind that lacks a contract. Errors the six checks raise for a malformed argument (the type of an argument, a malformed binding, an odd `head_dim` in the RoPE functions) are raised as they are; a binding key that is none of the fifteen call-site names makes the binding malformed, as a key outside its call sites does for each check. Reasons of different text for one cause (an empty prompt gives `check`'s "prompt: is empty" and the others' out-of-range `prompt_length`) are all kept.
- **The weights' check** (ADR-0157 decision 1 and Consequences): each weight of decision 4 must be an array (not an array: a malformed argument, raised); one whose element type is not `uint16` at `bf16`, or whose shape is not the one decision 4 gives from the dimensions, or a per-layer list that does not hold N arrays, is **invalid input** naming the weight and the layer. At a dtype outside the range of ADR-0157 decision 4 the element types are not checked, since no operand gives one to compare with; the shapes are. A shape is checked with the element type because both are properties of the operand that receives the array; a wrong shape is a well-formed input the program cannot run, as ADR-0157 decision 1 reads a wrong element type.
- **Run settings refused as invalid input**, beyond those the six checks refuse (an empty prompt, a token id outside the vocabulary, a generation length outside 1 to 2⁵³ − 1 or with S + G − 1 above it, `lm_head_rows` outside `"all"` and `"last"`, given tokens of another count than G, a dtype at which a kind has no contract): an `eps` whose value `rmsnorm_eps` refuses, RoPE constants (or a table size) whose values `rope_table.build` refuses, and **the generation mode** (no given tokens), which has no selection rule (decision 7).
- **No new outcome**: a wrong type is raised as those functions raise it; each value refusal is a well-formed input the executor cannot run, which ADR-0153 decision 5's invalid input covers as ADR-0157 decisions 1 and 4 read it.

### 7. Modes and the report

- **The driver's code slices build the given-sequence mode** (ADR-0153 decision 4): the prefill takes the prompt, and decode pass k takes given token k − 1 (0-based), k = 1 … G − 1. The last given token is fed to no pass; it is the token the last pass's last logits row predicts. The given tokens need no selection rule.
- **The generation mode** is refused as invalid input (decision 6) until sub-question 6 gives the selection rule; where the rule is applied (ADR-0153 decision 4) stays open with it. The draft question is in Consequences.
- **The report** (ADR-0153 decision 4; ADR-0157 decision 3): the token ids of the run, the prompt then the given tokens as the program read them, and the requested logits rows as bf16 patterns, pass by pass in pass order: for `"all"` the T rows of each pass (S + G − 1 rows), for `"last"` the last row of each pass (G rows). The report ends with the end mark of `model_program.c`'s form; its binary layout is the code slices'.
- **No model-level comparison, reference or tolerance is chosen** (sub-question 6).

### 8. The driver's test of the pass

- **What it checks** (ADR-0153 decision 6; K4): a generation of the synthetic model — small dimensions given by the test with at least two layers, H a multiple of H_kv and larger than it, S ≥ 2 and G ≥ 3, under both `lm_head_rows` values — whose reported logits rows and token ids **equal, bit for bit, a Python re-computation of the same generation with the same fixture kernels**; and the outcomes of the whole-generation check on bindings, weights and settings made wrong one at a time (the negative cases of CLAUDE.md's test rule).
- **The fixture kernels**: hand-written by the test to each kind's prototype and memory obligations (ADR-0153 decision 6). Each computes its kind's operation using binary32 additions, subtractions, multiplications, divisions and square roots in a fixed order, with any exponential (SiLU, softmax) computed by a fixed sequence of those operations, and rounds each output to bf16 with ties to even; built with floating-point contraction off. The re-computation performs the same operations in the same order on NumPy `float32` scalars. IEEE 754 rounds each of these operations correctly, so the expected patterns are exact and need no tolerance. Whether a fixture meets its kind's error bounds is not this test's question; kernels are verified by the kinds' runs (ADR-0163 to ADR-0165).
- **What a pass of this test shows**: a wrong buffer, a missing or shifted range copy, a wrong row of the RoPE table, a cache not kept from one pass to the next or a wrong embedding row changes the bits of some reported logits row for weights drawn from a seed. A test of this kind does not prove that no wiring error exists; it is not a model-level acceptance (Consequences).

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 1 | Extend `model_program.c` into the pass | It is the fp32 and bf16 GEMM-list program of ADR-0153 slice 1 and ADR-0157, with its own input form and tests; a pass program has another input, six entry points and buffers. Two programs keep both small. |
| 2 | One buffer per call site and layer | N times the activation memory for nothing: one pass runs one layer at a time and every reader has returned before the next layer writes. |
| 2 | Leave the initial content of outputs and caches to `malloc` | Allowed by the contracts, but a read before write would then show arbitrary values that differ between runs. |
| 3 | Three QKV GEMMs instead of copies | ADR-0152 decision 2 has one joined product (2048 → 3072); splitting it changes the call sites and their shapes. |
| 3 | A row stride in the RoPE and SDPA operands | Refused by those contracts (ADR-0161 decision 6, ADR-0162 decision 5). |
| 4 | A cache capacity fixed by the program (for example 2048) | A value no source gives; ADR-0162 and ADR-0165 Boundaries give the capacity value and the longest sequence to sub-question 6. The generation's own largest l is enough. |
| 4 | The RoPE table built by the program | The program would compute cosines in C, whose accuracy ADR-0161 decision 4 does not bound; the table is the host side's (ADR-0161 decision 4). |
| 5 | (b) Leave the table's element type to the owner | The reading follows from K3 and ADR-0157 decision 1 without a new value (decision 5); it is listed for the owner instead. |
| 5 | An fp32 table rounded to bf16 at the copy | A conversion outside every kernel, which K3 (3), placing conversion in the kernels, does not give, and a rounding rule no source gives. |
| 6 | Stop at the first failing check | Hides further unfit entries; the caller would correct a binding one kind at a time. |
| 6 | A new outcome for a wrong weight shape | ADR-0153 decision 5's invalid input covers a well-formed input the executor cannot run (ADR-0157 decisions 1, 4). |
| 7 | Greedy argmax as the generation mode's rule | A selection rule is sub-question 6 (owner); the given-sequence mode is enough for the driver's test. |
| 8 | (b) A per-kind float64 reference with bf16 rounding between calls | The fixtures accumulate in binary32 and the reference in float64, so single bf16 roundings differ and propagate through later layers; the test would need a tolerance with no source, and comparing a model run with a reference is sub-question 6's question. |
| 8 | (c) Checks of call order, buffers and cache only | Needs a trace in the program or kernels that do not compute their operation; it would not catch a wrong table row or a wrong copy offset that keeps the call order. |

## Consequences

- **A-13 reading**: no schema file, member, file, `kind` or `dtype` value, version or validator of the data plane changes. The executor writes nothing to the data plane (ADR-0153 Consequences); **a record of a model-level run** is left to sub-questions 6 and 8 and OD-8, as ADR-0153 leaves it.
- **Code slices** (for the planner), in landing order; module names are proposals of this record. They are units of work, not tasks: the planner groups consecutive slices into tasks within the size cap of DRIVER §5, as DRIVER §6 "task 단위" ③ says. Each slice is runnable and testable once those before it have landed, so the cut points are fixed here and a task chooses none.
  1. **The whole-generation check** of decision 6: a new module `hilclaw/model_forward_check.py` over `hilclaw/model_binding.py`'s six checks, with the weights', `eps`, RoPE-constant and mode refusals; with tests.
  2. **The program, prefill only**: a new C source `hilclaw/model_forward.c` — command line, input reading and its form checks, the library table and the six entry points, every buffer of decision 2 including the per-layer caches of decision 4 (the prefill's `sdpa` call needs them), the prefill pass of decision 3 and the report; it runs generations with G = 1 and refuses an input with G > 1 as an input-file error. Tested with hand-written fixtures and an input written by the test.
  3. **The program, decode passes**: in `hilclaw/model_forward.c`, the G − 1 decode passes with the given tokens of decision 7, the cache kept across them, and the token ids in the report; with tests.
  4. **The host side's input and report**: a new module `hilclaw/model_forward_run.py` — the input encoding (weights, the RoPE table built with `rope_table.build`, `eps` from `rmsnorm_eps`, token ids, the library table), one run of the program, the report's parsing; with tests that start a program built by the test.
  5. **The build-and-run path**: the forward program's source and flags in `hilclaw/model_build.py`, and a new module `hilclaw/model_forward_execute.py` that runs slice 1's check, builds one library per distinct kernel and the program, and runs slice 4's steps; with tests.
  6. **The synthetic-model test** of decision 8: tests and fixture kernels only.
- **Readings for the owner to check**, listed in the #5 notice: the embedding table as bf16 patterns and the row copy with no cast, read from K3 and ADR-0157 decision 1 (decision 5); no cast anywhere between kernels in the pass, read from K3 (2) (decision 3); the column order Q, K, V of the joined QKV weight as the executor's input, its forming from a model file left to sub-question 5 (decision 4); the cache sized to the generation's own largest l, with no Llama capacity (decision 4); the generation mode refused until sub-question 6 gives a selection rule (decisions 6 and 7); and the synthetic test compared bit for bit with a re-computation of its own fixtures, not with a model-level reference (decision 8).

- **Token selection** — the rule and where it is applied — and **the model-level comparison**: reference, metric, tolerance, prompts, generation lengths, the lm_head rows it reads, the longest sequence and a cache capacity for Llama 3.2 1B (OD-31 sub-question 6, owner).
- **The weights and tokenizer**: source, file form, conversion to bf16, forming the joined QKV weight, tied or untied embeddings, the RoPE pairing of a checkpoint (sub-question 5, owner; ADR-0161 Boundaries); the RoPE scale factor of Llama 3.2 1B (HQ-0070).

- **fp16** (owner, HQ-0065 (1)); an fp32 forward pass (no fp32 contracts of the other kinds, ADR-0157 decision 5).
- **The binary form** of the forward program's input, library table and report, and its build flags beyond what a shared library needs (code slices; ADR-0153 Boundaries).
- **The isolation** of the forward program's build and process, its time and memory limits (OD-14, NFR-4); **targets other than `cpu_standin`**; **deriving a binding from a key's best** (OD-20, OD-7).
