## Decision

Whose a sentence is: **the owner's** where O1 or O2 is named; **cited** where a requirement, a record with its decision number, a file of the code or W1, W2 is named; **this record's own** otherwise. The record's own design is what the objection window is for.

### 1. Scope and terms

- **Scope.** The content of the `output/` of one attempt of the first case after a bring-in of ADR-0049 that was carried out to its end into an `output/` that did not exist before it, and the rule by which that bring-in chooses what it takes.
- **Not this record**: the agent roster; who holds the `coder/` role or issues a call; how or when a coder is started and how it is told anything; when a bring-in is carried out or given up; what is taken from a call that did not end normally. Every other kernel language, operation kind, dtype and backend is outside.
- **Terms.** *The place*: the directory named `output` directly below the root of the scratch of a call (decision 5). *Admitted name*: decision 5. *Kernel files* of an attempt: the files decision 3 selects below its `output/`. *Compiled set*: the kernel files whose name ends in `.c`. *The reader*: anything that determines the compiled set from the path of an `output/`.

### 2. Limits (they hold for every statement of decisions 3 to 7)

- **L1 — Place, not honesty.** The form says where a reader finds the source of an attempt. It does not say that the source is correct, honest, the coder's own work, or free of anything the coder could read during its call: threat B of OD-16 is untouched, and L8 and L10 of ADR-0049 stand (a file can come to lie below an `output/` by another route than the bring-in, and nothing here detects it).
- **L2 — No check of content.** Nothing here reads the bytes of a file to judge them: not whether a file is C, is text, defines `hilclaw_gemm` once or defines a `main` (ADR-0008 decision 7 states the obligations; no record checks them). An admitted name is a name, not a kind: a file named `a.c` may hold any bytes up to the size bound.
- **L3 — A subset can be taken.** The bring-in takes file by file. A file the coder left under a name that is not admitted, or above the size bound, is not taken while its neighbours are; the kernel files of the attempt are then not the set the coder left. A build over such a set will usually fail and need not. What is measured and what is kept still agree as far as the working tree goes, because both are the content of `output/` (decision 3; for a commit see decision 6, "Git"); nothing here notices that something was left out.
- **L4 — A coder that leaves no admitted `.c` file in the place** produces an attempt without a kernel source (one that follows the form in part is L3). This record does not say what a round, a repair or a tool call does then.
- **L5 — An unfinished bring-in looks like a finished one.** A bring-in that died part-way leaves an `output/` that holds some of the files; the form has no mark that tells the two apart (sub-question ① (가)).
- **L6 — Nothing was run.** No coder has produced the place, no bring-in exists, and the two expectations marked "not verified" in decisions 3 and 5 are this record's own.
- **L7 — FR-6 is met only for what is taken.** FR-6 asks that "중간·최종·실패 전부" be kept. What a bring-in does not take is not kept: a source file under a name that is not admitted, a file above the size bound, every file of a call that left more than 16 (B3), and a coder's notes and logs. Whether the "에러 로그" of O1 means logs of a coder's own, or only those of the measured build, this record does not read; if it means the former, they are not kept by this record. The whole output of the coder process that the draft of #4 would capture is not kept by it either. This record keeps the source it can name safely and nothing else of a call; whether more is kept is registered (sub-question ① (나), (라)).

### 3. The kernel source of an attempt

**The rule of the reader.** Given the path of the `output/` of an attempt:

- **R1.** The `output/` of the attempt is the entry of the attempt directory — the parent of that path — whose name, exactly as the attempt directory lists it (no case folding, no normalisation), is `output`, the name `hilclaw/layout.py` builds (cited: `attempt_artefact`). If the attempt directory does not exist or is not a directory, or it has no such entry, or that entry is not itself a directory (a symbolic link is not, whatever it points to), the attempt has **no kernel source**; an entry listed as `Output` is not the `output/` of the attempt on any file system.
- **R2.** The **kernel files** are the entries **directly below** `output/` that are themselves regular files (a symbolic link is not) and whose name, exactly as the directory lists it — no case folding, no normalisation — is an admitted name (decision 5, N1 and N2). Nothing below a sub-directory is a kernel file.
- **R3.** The **compiled set** is the kernel files whose name ends in `.c`, **in ascending order of their names compared byte by byte**. It is the value handed as `kernel_sources` to the builds of ADR-0009 decision 2 and ADR-0017 decision 2, in that order.
- **R4.** **"This attempt has a kernel source"** means exactly: the compiled set is not empty. The predicate says nothing about what the files hold (L2).
- **R5.** A kernel file whose name ends in `.h` is a header of the kernel's own. It is never in the compiled set and is read only when a file of the compiled set includes it, directly or through another header of the kernel.
- **R6.** Any other entry below `output/` is not source: the reader does not read it, hand it to a compiler or execute it.
- **R7.** **The reader looks at neither the number nor the size of the files.** The two bounds of decision 6 are rules of the bring-in (B2, B3). An `output/` that holds more or larger kernel files than a bring-in of this record leaves — by another route (L1), or after the bounds were changed — is read by R1 to R6 all the same.
- **R8.** **What the reader cannot see is a failure, not an answer.** A directory that exists and cannot be listed — the attempt directory or `output/` — or an entry of either whose kind cannot be determined, is not "no kernel source" and is not passed over: it is a failure of the reader, and what a reader does then is the code task's.

**What follows, and why.**

- **A kernel may have more than one source file and its own headers** — the number ADR-0008 decision 7 left to this record: at least one file of the compiled set, and a bring-in of this record leaves at most 16 kernel files in all (decision 6).
- **A header of the kernel's own is a file of its source — a reading of this record.** ADR-0008 decision 7 says a source "may include the headers of the C standard library, `<omp.h>` and the SIMD intrinsics headers of the target". This record reads that list as being about headers that come from outside the kernel; a `.h` kernel file is one of the files of "the source of a kernel" and not such a header. ADR-0008 does not say so itself.
- **Flat, so that no flag is needed.** All kernel files lie in one directory. A file of the kernel names a header of its own as `#include "name.h"`. That clang looks for a header named in that form first in the directory of the including file is this record's expectation of the compiler (C calls the search "implementation-defined"); it is **not verified** here, and a test of a code slice can show it with clang alone. If it did not hold, a kernel would need an include path, and "the harness adds no flag" (cited: ADR-0009 decision 2). *Note of 2026-10-14 (T-0174):* the test `test_compiled_set_builds_with_clang_and_no_include_path` of T-0157 (`tests/test_kernel_source.py`) showed the expectation on the CI runner (Ubuntu, clang) only, in the push run of 2026-10-13 on `main` at `e8c19ce` (GitHub Actions run 38430280742, 0 skipped): the compiled set of an `output/` holding `a.c` with `#include "pack.h"`, `pack.c` and `pack.h`, built by `hilclaw.clang_build.build` with no include-path flag, gave an executable that starts and exits 0 (cited: T-0157 `## Result`). No other kind of machine of C-7 was observed, so for those the expectation stays not verified and the conditional "If it did not hold, ..." still stands.
- **Why an order.** No rule of C known to this record makes the result depend on the order of the translation units of one program. The order is fixed because a directory listing has none that is the same on every file system, and the kernel's source arguments of the compiler command, and their order, should be the same for the same `output/` on every machine, up to the location of the checkout (the sources are handed over as absolute paths) (NFR-2). The rest of that command — the compiler, the caller's flags, the name of the temporary artefact — is not this record's. Byte order is not the order of the parts before the dot: `a-b.c` < `a.c` < `a0.c` < `a_b.c`.
- **The same answer everywhere.** R1 to R4 use only the kind of an entry and its listed name, and an admitted name holds lower-case ASCII letters, digits, `_`, `-` and one `.` only. So for the same entries the rule gives the same compiled set in the same order on a case-sensitive and on a case-insensitive file system, and under any Unicode normalisation a file system applies. **Where that ends**: a directory that holds two names differing only in case (`a.c` and `A.c`) can exist on one kind of file system and not on the other; the bring-in never writes such a pair (decision 5), so it can arise only by another route (L1), and then the two machines do not hold the same entries. **And the same set is not the same build**: an include that spells a header in another case than its name (`#include "Pack.h"` for `pack.h`) resolves on a case-insensitive file system only, so one `output/` can build on one machine of C-7 and not on another; nothing here checks it (L2).

### 4. Whole files, never a diff

- **Every kernel file is a whole source file**: the complete text the compiler reads. No file below `output/` is a diff, a patch or a reference to a file elsewhere.
- **A repair attempt holds its own complete kernel source**: every file of it, also those that are byte for byte those of the attempt before. Nothing below the `output/` of one attempt refers to or is completed by another attempt's, so the compiled set of an attempt is found from its own directory alone (cited: ADR-0004 decision 3, "each attempt has its own").
- **Reason.** A build takes files. A diff needs a base, which the first attempt does not have and which for a repair would make a failed attempt unreadable without its predecessor; which earlier source a later one comes from is the lineage (OD-20) and is not decided here. A difference between two attempts can be computed from two whole sets; the reverse needs the base.
- **A reading of this record, not a statement of the owner.** O1 lists "소스 diff" among the knowledge texts that are kept in git, and the draft of #4 says "src diff 또는 ref". This record reads O1's list as naming what kind of thing is kept — the source, as text, in git — and not the form of the coder's output: with whole files of every attempt in git, the difference between any two is kept as well. If the owner meant the form, that is an objection to this decision.

### 5. What the bring-in takes

**Admitted names.** A file name is admitted when both hold:

- **N1.** It matches, in full, `[a-z0-9][a-z0-9_-]{0,61}\.[ch]`: lower-case ASCII letters, digits, `_` and `-`, not starting with `_` or `-`, then one dot and `c` or `h`; 3 to 64 characters.
- **N2.** The part before the dot is none of `con`, `prn`, `aux`, `nul`, `com1` to `com9`, `lpt1` to `lpt9`.

What N1 keeps out, weighed one by one: a path separator and `..` (no `/`, no `\`, one dot only); a leading dot, so every name `git` reads as its own (`.git`, `.gitignore`, `.gitattributes`, `.gitmodules`) and every hidden file; a leading `-`, which a command line could read as an option; upper case, so no two admitted names differ only in case; non-ASCII, so no name depends on a normalisation; spaces and control characters; a trailing dot or space; a second suffix; a length above 64. N2 follows W1 (cited): the checkout of a data repository may lie on a file system of Windows reached from WSL (this record's inference from C-7 ①, which says only that Windows is used with WSL). Whether those names do harm there was not tried; the cost of N2 is twenty-two stems a kernel cannot use. The length of a whole path — a `run_id` of up to 64 characters and the levels of the tree above the name — against a path-length limit of a file system was not examined. The length 64 and the character set are this record's own choice (the characters and the rule for the first one are those of a `run_id`, cited: ADR-0004 decision 8).

**The rule of the bring-in**, for one call, after the container of the call has been removed (cited: ADR-0049 decision 4):

- **B1 — One place.** It looks at the entries **directly below the place**: the entry directly below the root of the scratch of the call whose name, exactly as the scratch root lists it — no case folding, no normalisation —, is `output`, and that is itself a directory. If there is no such entry or it is not itself a directory (a symbolic link is not), nothing is taken; an entry listed as `Output` is not the place on any file system. Nothing else of the scratch is output: not a file directly below the scratch root, not anything below a sub-directory of the place.
- **B2 — Which entries.** An entry is taken when it is itself a regular file (a symbolic link is not, whatever it points to; a directory, a FIFO, a socket or a device is not), its name as listed is admitted (N1, N2), and it holds at most 262,144 bytes (decision 6).
- **B3 — All or none above the number.** If more than 16 entries satisfy B2, **nothing is taken**: no subset of them is "the" kernel.
- **B4 — Same name, same bytes, nothing else.** Each entry taken becomes a new regular file below the `output/` of the attempt under **the same name**, holding the same bytes. It is created as a new entry: the bring-in never writes through or over an entry that is already there under that name, a link least of all (what it does when it finds one is not decided — sub-question ① (가)). It is written, never linked and never moved; no mode bit, owner, time or other attribute of the scratch file is carried over, so a coder cannot make a file of the tree executable. The bound of B2 holds for the bytes written, whatever a query of the size said.
- **B5 — Not taken means not there.** An entry that is not taken is **never renamed, truncated or converted into something admitted**. It is lost when the scratch is removed (O2, **the owner's**; ADR-0049 P4). Whether what was not taken is reported, and to what, is not decided (sub-question ① (나)); the bring-in writes no record of it into the data plane.
- **B6 — `output/` only when something was taken.** The bring-in creates the `output/` of the attempt only if it takes at least one file (cited: ADR-0004 decision 1), so a call from which nothing is taken leaves a missing `output/`, and R1 answers "no kernel source".

**The place is told to the coder by PLAN P2-2, and the spec gains no field.** That a coder writes its result into the directory `output` below the root of its scratch, under admitted names, is something the start of the coder has to tell it — the prompt, or whatever P2-2 decides. No member of a spec says it (ADR-0002, ADR-0050 and ADR-0051 are unchanged), and what the issuing side copies into the scratch for the coder (ADR-0049 decision 4) is never placed in the place. That reading files written inside a container needs no more than the rights of the user who runs the instance is **not verified** (Consequences).

**Why one place and not the whole scratch.** The scratch also holds the copy of the spec and whatever the coder builds and tries (cited: ADR-0049 decisions 3 and 4). Without a place, every `.c` file of a coder's own experiments — a test program with a `main` among them — would be a kernel file. A place lets a coder work anywhere else in the scratch and state its result by where it puts it.

### 6. Files other than the kernel source, and C-3

- **Below `output/` there is nothing but kernel files** after a bring-in of this record: `.c` and `.h` files under admitted names. Notes of a coder, its own build and test logs and the executables it built are not taken; a coder that wants to explain its source does so in a comment. Whether a later record keeps such files, or the captured stream of the coder process (the draft of #4), and where, is not decided (sub-question ① (라)). **Every name that is not admitted stays free** for a later record: R2 and R6 make a reader of this record pass over it.
- **A `.h` kernel file** is read only by the compiler, through an include; **a reader of this record executes nothing below `output/`** (R6).
- **C-3, by the names and by two bounds, both.** By the names: no object file, library, executable or archive suffix is admitted, so what a build produces is not taken under its usual name. By the bounds, which are part of the form: **at most 16 kernel files** per attempt and **at most 262,144 bytes (256 KiB)** each, so an attempt adds at most 4 MiB to the tree. **Both values are this record's own and provisional; no source gives one and neither is the owner's.** Reason: a hand-written or generated GEMM kernel of ADR-0008 is expected to be a few files of some tens of KiB; the values leave a wide margin above that and still keep one attempt, and so N attempts per round (S8) over many rounds, from growing the repository by more than megabytes each. They are judged again when the first real kernels exist (sub-question ① (다)).
- **What that does not keep out** (L2): arbitrary bytes under an admitted name, up to the bound — a binary renamed `a.c`, or encoded as text, or a secret the coder could read (cited: ADR-0049 L8; ADR-0004 decision 7, "Secrets"). C-3 holds after this record for what a build names as its product and for size; it does not hold for what a coder deliberately disguises. A rule of the bytes — valid UTF-8, no NUL — was weighed and is registered, not decided (Alternatives; sub-question ① (다)).
- **Git, as far as it was examined** (cited: W2): no admitted name matches an ignore pattern of the data repository, so that file hides no kernel file from `git` (a user's own exclude files — `core.excludesFile`, `.git/info/exclude` — were not examined), and no name N1 admits is one `git` gives a meaning to. **Not examined, and a limit**: that repository has no `.gitattributes` (W2), so whether `git` converts line ends when a kernel file is committed or checked out is left to each user's `git` configuration. "The same bytes" (B4) therefore holds for the working tree the bring-in wrote; this record does not say that a commit, or the checkout of another machine, holds the same bytes as were measured (sub-question ① (마); the commit is OD-17 and OD-18). No change to the data repository is made by this record.

### 7. Stability

- **No rule of this record changes, adds or removes anything below the `output/` of an attempt after its bring-in** — the planner's expectation, confirmed as far as this record goes: it is the source of the attempt (cited: ADR-0004 decision 3), and what was taken is kept (FR-6, cited; L7 for what was not). A repair has the `output/` of the next attempt (decision 4). Whether a second bring-in may write there is not said (below).
- **No rule of this record places a build artefact below `output/`.** The bring-in takes none (decision 6), and `clang_build` writes only the artefact, at the path it is given, and its temporary file "next to" it (cited: `clang_build.py`). Where a build of the kernel writes its executable — and so whether that is ever below an `output/` — is not decided here (OD-18 sub-question ⑩).
- **Not said**: whether a second bring-in for one tuple can happen, what a bring-in does when it finds an `output/` already there, and how a reader tells a finished bring-in from one that died (L5). These are sub-question ① (가), with sub-question ㉖ (가) of OD-8, which asks the same of a second write of a spec (cited: ADR-0049 Boundaries).

### 8. Layout version

- **Unchanged: layout version 1, and no file changes its version.** "The version is raised when a path, file name or number form fixed here changes; it is not raised when a file is added in a place this record leaves open" (cited: ADR-0004 decision 9), and the path table of ADR-0004 leaves this place open ("Files and form: OD-23"). The precedent is [ADR-0029](ADR-0029-od8-spec-file.md) decision 6. This record adds no path outside `output/`, no member of any file, no record kind and no event kind; `hilclaw/layout.py` stays as it is.
- The place of decision 5 is a directory of the scratch, which is "no path of that tree" (cited: ADR-0049 decision 3).

### 9. How far earlier open points are answered

- **ADR-0049 decision 4**, "Which files it takes, in what form, under which names, with what bounds on number and size": **answered for the first case**, for a bring-in that is carried out (decisions 4 to 6). "whether anything is taken from a call that did not end normally": **not answered** (OD-19; this record does not say when a bring-in is carried out).
- **ADR-0008**, Boundaries "The coder's output: file names and form under `…/coder/…/output/`, how many source files a kernel has" and decision 7 "however many files it has": **answered for the first case** — a run whose hw_profile names `cpu_standin` or the mock — and for no other run of that contract (decisions 3, 5, 6).
- **ADR-0002**, Boundaries "what the coder returns, how it is captured": **answered as far as files of source go**, for the first case. "the record of the build settings actually used", how the spec is handed to `claude -p`, and the captured stream of the coder process: **not answered**.
- **OD-18 sub-question ⑩: no part is answered.** Who builds the kernel of an attempt, when, with which flags, how the operation reaches the verification executable, and what a call answers for an attempt without a kernel source all stay open. This record gives them one input only: the rule of decision 3.

### Walk-through (no step names an agent, a tool, a flag or a prompt)

1. **A call that follows the form.** The coder leaves, in the scratch, `output/gemm.c`, `output/pack.c`, `output/pack.h`, and elsewhere `try/test_main.c` and `a.out`. After the container is removed the bring-in looks at the place only: three entries, all regular, admitted and small. It writes `…/attempts/01/output/gemm.c`, `pack.c` and `pack.h`. The reader's compiled set is `gemm.c`, `pack.c`, in that order; `pack.h` is a kernel file outside it.
2. **Entries that are not taken.** The place also holds `Notes.md`, `Fast.c`, a sub-directory `old/` and a symbolic link `ref.c`. None is taken (name; name; kind; kind) and none is renamed. If `Fast.c` held code the kernel needs, the build of the attempt fails or builds something else (L3).
3. **Nothing in the place**, or no place: no `output/` is created; the attempt has no kernel source (L4).
4. **A repair.** Attempt `02` has its own scratch and its own `output/` with all files of its kernel; that call writes nothing below `…/attempts/01/output/` (decision 4).

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 3 | (a) Exactly one file of a fixed name (`kernel.c`) | The simplest predicate, and the planner's first candidate. It forbids a header of the kernel's own and a second translation unit; ADR-0008 decision 7 left the number of files open ("however many files it has") and the `kernel_sources` of the two builds take several; a kernel with a packing routine and several code paths would be one file by decree. The chosen rule contains it: one admitted `.c` file is a valid kernel. |
| 3 | (c) A fixed sub-directory of `output/` for the sources (`output/src/`) | Adds a level whose only use is to separate source from other files, and this record admits no other files. Left free: a later record that keeps other files can put them under names that are not admitted. |
| 3 | Sub-directories inside the kernel source | Need either an include path — a flag the harness does not add — or relative includes across directories, and make the reader walk a tree whose depth and names a coder chose. |
| 3 | (d) A manifest file the coder writes, listing the sources and their order | A second statement beside the directory that can disagree with it, content of a coder that a reader would have to parse and trust, and one more form to define. The order it would give is not needed. |
| 4 | A diff against the previous attempt or against a base | See decision 4. |
| 5 | The whole scratch, or its root, as the source of the bring-in | See decision 5, last paragraph. |
| 5 | Renaming an unsafe name into an admitted one (lower-casing, replacing characters) | Two names can map to one; includes between the files would no longer match; the tree would hold a name no coder wrote. |
| 5 | All or nothing for every rule: one entry that is not admitted voids the whole bring-in | Removes L3, and was weighed for that. It loses more of a failed attempt than FR-6 needs to lose (a stray note would void a kernel), and a build failure over a subset is itself kept as a failed attempt. Registered with the report (sub-question ① (나)). |
| 6 | A rule of the bytes: a file is taken only if it is valid UTF-8 without a NUL byte | It would make "source as text" true by construction, and it is cheap. It keeps no content out that can be encoded as text, and it would be the first rule here that reads bytes, next to the checks of OD-16 that are not decided. Registered (sub-question ① (다)). |
| 6 | No bound, or a bound without a value | A coder can then grow the git history without limit (cited: ADR-0049 L7 has no ceiling on the scratch); a bound without a value cannot be coded. |
| 6 | Asking the owner for the two values first | They are not value judgements about the product: nothing a user sees depends on them until a kernel exceeds them, and the objection window covers them. |

## Consequences

- **Code slices that can now be cut**, once CI runs again (code mode, D12 rules; names and modules are the code task's; each must behave the same on Linux, macOS and WSL): (a) the bring-in function — slice (b) of ADR-0049 — under B1 to B6 (and slice (a) of ADR-0049, the function that places copies in a scratch, places none in the place — decision 5); (b) a pure function of the admitted name (N1, N2); (c) a function from the path of an `output/` to the compiled set or "none" (R1 to R4). A test of (c) with clang can show the include expectation of decision 3.
- **Records that can now be written**: the first two parts of OD-18 sub-question ⑩, then the run-tool contracts of PLAN P1-1 with OD-13 sub-question ⑩.
- **Runtime acceptance items** (D16: facts only a coder call on a machine of C-7 can establish; none was tried, none is required of the development machine, and none is closed by a driver task). On each kind of machine of C-7: (i) the regular files a coder wrote into the place from inside its container can be read, after the container is removed, by the user who runs the instance (with L6 of ADR-0049, which asks the same of their removal); (ii) a coder that is told the place and the admitted names — by whatever PLAN P2-2 decides — leaves there a kernel source that the bring-in takes whole.
- **A-13 reading.** Document mode; no code, dependency, settings or schema file changes. No member of `STATE.json`, of a spec, of an eval record or of `artifacts.json` is added or changed; no path of the tree is added outside a place ADR-0004 left open; the layout version is unchanged (decision 8).
- **Sentences of earlier records that are now less exact** (none edited): ADR-0004, the `output/` row of the path table ("Files and form: OD-23"), the comment "what the call produced" in the tree and decision 3 ("builds the coder runs for itself during a call are part of its output" — nothing a coder built is taken); ADR-0008 decision 7 ("however many files it has (OD-23)", and the list of headers a source may include, which does not mention a header of the kernel's own) and its Boundaries bullet "The coder's output"; ADR-0002 Boundaries ("the layout of the coder's output (`coder/`)" and "what the coder returns, how it is captured"); ADR-0029 decision 6 ("whose files and form are OD-23"); ADR-0049 decision 2 (the row of ②: "Whether what is brought back is whole files or a diff is the form of `output/` (OD-23)"), decision 3 ("only as far as the bring-in takes them": it takes none of a coder's builds), decision 4 (the last bullet), step 3 of its Walk-through ("reads the regular files of the scratch": those of the place), L8 ("Names are as unfiltered as content … was not examined"), Consequences slice (b) ("under the rules of decision 4") and its Boundaries bullet "The files and form of `output/`"; `README.md`, the row of layer 3 (the files and form of `output/` named as OD-23). Each stays true of everything this record leaves.
- **The cost, plainly.** A coder must be told a place and a name form it could otherwise ignore, and a kernel that needs a seventeenth file, a file above 256 KiB or a sub-directory cannot be expressed. Every admitted `.c` file is compiled as a translation unit of its own (R3), so text that another file includes — a body included several times under different macros, for instance — must be named `.h`. A coder's notes and logs are lost with the scratch.

## Boundaries (not decided here)

- **The agent roster**, which agent or tool holds the `coder/` role, the per-agent allowlists, whether `coder.run` exists (rest of OD-23).
- **How the coder process is started and told where to write**: the prompt, the model, the flags, the image (PLAN P2-2, #5 A-8); what a coder is given besides the spec (OD-6, OD-12).
- **What is taken from a call that did not end normally**, when a bring-in is given up, and repair limits (OD-19).
- **Any check of the content**: forbidden patterns, calls into other libraries, a static check, the obligations of ADR-0008 decision 7 (OD-16).
- **Who builds the kernel, when, with which flags**; `build.json`; whether the coder may choose build settings (OD-18 sub-question ⑩, OD-6 sub-question ②, ADR-0004 decision 3); **what a tool call answers for an attempt without a kernel source** (OD-18); what a round does with one (PLAN P2-1, OD-19).
- **The lineage of a source** across attempts and rounds (OD-20); **the commit that carries `output/`** (OD-17, OD-18).
- **The output of any other kernel language, operation kind or backend** (#5 B-1). Code and tests.
- **Sub-question this record raises** (registered under OD-23): ① in five parts. (가) Whether a second bring-in for one tuple can happen, what a bring-in does when the `output/` already exists, and how a finished bring-in is told from one that died part-way (L5; with OD-8 sub-question ㉖ (가), OD-17, OD-19). (나) Whether what a bring-in did not take is reported, to what and in which record, and whether an entry that is not taken should void the whole bring-in (L3; with OD-19). (다) The two bounds — 16 files, 262,144 bytes — judged again with the first real kernels, and whether a rule of the bytes (valid UTF-8, no NUL) is added (with OD-16). (라) Whether anything of a coder call other than kernel files is kept — notes, its own build and test logs, the captured stream of the coder process — and where (with PLAN P2-2, NFR-5). (마) Whether the bytes of a kernel file are the same in a commit and in another checkout as in the working tree they were measured from — line-end conversion by `git`, the data repository having no `.gitattributes` (with OD-17, OD-18).
