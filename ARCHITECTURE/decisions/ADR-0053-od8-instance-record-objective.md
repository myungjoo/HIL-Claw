## Context

The glossary of [UsageCases](../UsageCases.md) lists "최적화 target" among what a Loop instance is given, without the "(선택)" it puts before the budget and the gates.
- **The owner's answer to HQ-0009** (2026-10-13). ADR-0050 quotes it in full as O1 to O5; the sentences this record uses, word for word:

The quantity and unit of (b) are not fixed here; an instance may state a type only once its quantity and unit are fixed, so until then latency minimisation is the only type an instance can state."
  - **O2** — "How it is stated: an instance states, beside its objectives, a set of constraints, each entry of one named constraint type." And: "A constraint is optional per instance."
  - **O3** — "An instance states a list of objective types, each with an optional weight or priority, beside a set of constraint types; the direction of each type is the type's own. Until the rule that combines more than one objective (priority order, weighted sum, Pareto) is decided under A-4, an instance states exactly one objective and neither a weight nor a priority; the members exist so that the schema does not change later."

ADR-0050 gave the value its form in version 2 of the spec and said in its L2: "no record gives `instance.json` a member that states objectives or constraints, so nothing can check that a spec carries what its instance stated, or that two specs of one run agree"; its Consequences name slice (c), "the record of the `instance.json` member that states objectives and constraints (PLAN P1-8), then its code", and its Boundaries "the member of `instance.json` the value is copied from, and what an instance start checks". ADR-0052 decision 7 admits `memory_ceiling` only when, among other things, a call returns the verdict "with the `bound` taken from what the run itself has recorded of its instance and not from a value the caller of that call chooses", and registered sub-question ⑩ of OD-13, one part of which is "from which record of the run that call takes the `bound`".

## Decision

Whose a sentence is: **the owner's** where O1, O2 or O3 is named with a quotation; **cited** where another source is named; **this record's own** otherwise.

### 1. Scope

This record fixes one thing of `runs/<run_id>/instance.json`: the member in which a run states its objectives and its constraints. Nothing else of the file is fixed and nothing of any other file. **A file that holds what the earlier records and this record define is still not a complete instance record, and no run can be started from it alone** (ADR-0018 decision 1).

### 2. Limits

Each limit stands before the decisions it limits and is referred to there by its number.

- **L1 — A record, not code; nothing was run.** Today nothing checks the member and nothing reads it (Context).
- **L2 — Whoever can write the file changes what the run states.** No access control exists and the tree "does not enforce the single writer" (cited: ADR-0004 decision 10); a file changed after the start is read "as it is at that call" (cited: ADR-0018 decision 6), so two reads of the file of one run can find two targets.
- **L3 — A misspelt name reads as an absent member.** A top-level member that is not spelt `objective` (`objectives`, `target`, `Objective`) is passed over (cited: ADR-0018 decision 2, the cost), and the file states no objective and no constraint — which is never a default and never "no constraint" (decision 5).
- **L4 — The member judges, measures and stops nothing.** It states a target. Nothing here compares a measurement with it, calls a candidate better, feasible or infeasible, or ends a run.
- **L5 — No instance can state a memory ceiling or throughput yet** (cited: ADR-0050 L6; ADR-0052 L9). Decision 4 changes nothing of that: the owner's vocabulary has a constraint type that no file can state.
- **L6 — Two sources of different age can differ in what they admit.** A source older than the code of this record passes the member over; and two sources that know it can differ in the type values they admit once a later record admits one (cited for the spec: ADR-0050 L5). A file one of them takes as valid the other may refuse.
- **L7 — A file written once states one target.** How a continuation or a branch with "다른 target" (StandardScenarios S3 step 3) relates to a file that is written once is OD-8 sub-question ① and is not decided: a new run has its own file; for later rounds of the same run no record gives a second target a place.
- **L8 — A spec can still state a target its run did not.** This record writes no rule about what writes a spec (decision 6). A valid version-2 spec carries exactly one value as its `task.objective` today (decision 4), so every valid spec written for a run whose file states no target carries a target that run did not state. Decision 5 keeps a reader of this record from substituting a value; it does not reach whatever writes a spec, and nothing here excludes that path. It is registered (sub-question ㉞ (ii)).
- **L9 — Form, not measurability.** A valid member does not show that the quantity of its type can be measured on the backend of the run (cited: ADR-0050 L1, which holds for this member as it does for the spec).

### 3. What the member states

- **The member states the target the instance was started with** (cited: FR-2; ADR-0004, "What the instance was started with"), **in the frame the owner fixed**: a list of objectives beside a set of constraints (**owner**, O3: "An instance states a list of objective types, each with an optional weight or priority, beside a set of constraint types"; O2: "an instance states, beside its objectives, a set of constraints"). This record gives that statement a place in the file of a run and adds nothing to the vocabulary: no type, no direction, no unit and no rule that combines objectives.
- **What a reader of this record may conclude** from a valid file that holds the member: that the run states these objectives and these constraints as the target it was started with. No more.
- **What a reader of this record may not conclude.** The member is not the target metric of FR-3 ④ — a value at whose reaching a run ends early — and no budget (FR-3; OD-2, OD-19). It is no tolerance (FR-9), no baseline (OD-28) and no margin of an improvement (`delta`, OD-13). It does not say that anything was measured, that a candidate was compared or judged, or that a constraint was judged or is met (L4). It does not say that a spec of the run carries the same value (decision 6), that the user chose it from a menu, or that the quantity of its type can be measured where the run executes (L9).
- **In version 1 a run states at most one target**: the member is one object (L7).

### 4. The member: name, place and form

- **The member is `objective`**, a top-level member, and its value is an object.
- **Its form is that of `task.objective` in version 2 of the spec, taken by citation and not stated again.** A value of this member is valid exactly when it is a value ADR-0050 accepts as the `task.objective` of a version-2 spec: its decisions 1 to 5 and its checks 1 to 3 ("What the validator of version 2 is to check"), and its check 4 from the moment that record and ADR-0052 decision 7 provide for and not before. To that the last bullet of this decision adds how a `bound` is written in this file, which binds nothing today. The types are those ADR-0050 uses (cited: its decision 1 — a *name* and an *integer* of ADR-0001 decision 1; "An object holds exactly the members listed for it").
- **What that gives today** (each item cited from the check named; none is a rule of this record): the value is an object with exactly the members `objectives` and `constraints` (check 1); `objectives` is an array of exactly one entry, the entry is an object with exactly the member `type`, and `type` is the name `latency_minimisation` (check 2); `constraints` is an array and it is empty (check 3). **So a valid member has one value today**: `{"objectives": [{"type": "latency_minimisation"}], "constraints": []}`.
- **Nothing else is a value today.** Among what is none: `null`, `true`, `false`, a number, a string (`"latency_minimisation"` included), an array, an object that lacks `objectives` or `constraints` or holds a third member, an `objectives` or a `constraints` that is no array, an `objectives` that is empty or holds two or more entries, an entry that is no object or holds `weight`, `priority`, a direction or any member besides `type`, a `type` that is no *name* or is any other name, and a `constraints` that holds any entry. The list is not the rule; the rule is the citation above.
- **`memory_ceiling` is not admitted here, because it is not admitted there.** "`memory_ceiling` is defined and is not yet an admitted value" (cited: ADR-0050 decision 5), and ADR-0052 decision 7 names the condition of its admission, which is not met (decision 7 below). **A file whose `objective.constraints` holds an entry — `{"type": "memory_ceiling", "bound": 123456789}` included — is invalid today.** The cost, plainly: an instance that is meant to run under a memory ceiling cannot record that in its file, and the file cannot be written first and judged later (L5).
- **Inside a present member, `constraints` is required and may be empty**, as in the spec: "The member is required and may be an empty array" (cited: ADR-0050 decision 4). An `objective` without `constraints` is invalid; the owner's "A constraint is optional per instance" (O2) is met by the empty array. No difference from the spec is argued.
- **Why by citation.** (i) ADR-0002 calls the value of a spec "copied from the instance record": with one form in both files a copy is a copy of one JSON value, and no rule of translation has to exist — such a rule would be a rule about what writes a spec, which is not this record's (decision 6). (ii) Two texts of one set of rules can drift, and each later admission would need two records. (iii) **The set of values a valid file may state is thereby the set a valid version-2 spec may carry as `task.objective`: no instance can state what no spec can carry, and nothing a spec may carry today is withheld from an instance.** Whether the second half still holds after a later step is decision 5 (first bullet).
- **What follows when a later record extends ADR-0050 under its decision 6** — (a) a further value of `type` is admitted, `memory_ceiling` among them; (b) the record of the combining rule gives `weight` and `priority` a type and a meaning or admits more than one objective entry. **The citation follows it: the same step extends this member, and the form is not stated a second time for this file.** What that step still has to judge for this file, and what holds if it raises the version of this file, is in decision 5 (first bullet). The owner's sentences behind that decision speak of the instance in their own words (O1: "an instance may state a type only once its quantity and unit are fixed"; O3: "Until the rule … is decided under A-4, an instance states exactly one objective and neither a weight nor a priority; the members exist so that the schema does not change later"). **That such a step does not raise the `schema_version` of this file is this record's reading and is provisional.** ADR-0018 decision 2 raises the version when "its type, form or meaning changes"; this record defines the form of the member as the citation itself, limits included, so a step that the cited record takes without a new version of the spec is, by this reading, no change of the form of this member. In each such step "the set of valid documents only grows" (cited: ADR-0050 decision 6), so a file that was valid stays valid with the same meaning. **This departs from a choice made for this file before**: ADR-0023 decision 3 wrote the lower end of `n_max` as "the number, not a reference to the constant", for the reason that "whether a file is valid is then a property of the file and of its `schema_version`, the same for every reader" (cited). Here validity is a property of the file, of its `schema_version` and of what ADR-0050 admits as later records leave it, so it is not the same for every reader (L6). What that record feared most does not follow — a file valid at the start of its instance does not become invalid, since the set only grows — and the reference is to a record, not to a constant of a source; the reason for giving the property up is that the frame of O3 is meant to grow without a change of schema, and a file whose rule stood still would fall behind the spec it is copied to. If the owner does not share the reading for exception (b) of ADR-0050 decision 6, "(b) falls and that later record raises the version" of the spec (cited: that decision), and this member follows the next item.
- **The citation is to version 2 of the spec and to no later version.** A record that changes the form of `task.objective` with a new version of the spec does not thereby change this member: it has to say what this member becomes, and a change of the form of this member raises the `schema_version` of this file (cited: ADR-0018 decision 2). That is registered (sub-question ㉞ (iii)).
- **The name** is this record's choice. `objective` is the name of the field of the spec the value is copied to, so the value can be followed from the file of the run to a spec without a mapping, and it is the owner's word for the vocabulary ("its objectives", O2). Weighed against it: `target` is FR-2's word, but FR-3 ④ uses it for a metric at which a run ends ("target-performance-metric"), which this member is not (decision 3); `goal` would read as a notion of the round loop; `task` is a section of the spec that holds more than this. The cost: the member named `objective` holds `constraints` too, and a constraint is no objective — the naming is ADR-0050's, taken with its form. `objective` is a *name* of ADR-0001 and no record defines a top-level member of this file under that name.
- **Why one top-level object and not two top-level members** (`objectives` and `constraints`). Each of two members could be absent or misspelt by itself (L3): a file with `objectives` and a misspelt `constraints` would be valid and would have lost its ceiling without a report. In one closed object a misspelt inner name makes the file invalid (the argument of ADR-0020 decision 2 for `tolerance`). And the copy to a spec would be a composition of two values.
- **The written form of a `bound` in this file** is the one this file has for its integers (cited: ADR-0023 decision 3) and the one ADR-0051 decision 2 gives a `bound` in a spec file: "a JSON number in decimal digits without sign, fraction or exponent". `5.0`, `1e3`, `-0` and a number above 2^53 − 1 are no values. **No valid file holds a `bound` today**, so the rule is written for the admission and binds nothing before it.

### 5. A file without the member; the version

- **The member may be absent from a valid file, and `schema_version` stays `1`** — the first of the two choices ADR-0018 decision 2 leaves to the record of a member: "A later record that defines a top-level member which may be absent and may be passed over does not raise it." A version 1 reader may pass over the member: no reader of today compares anything with an objective or judges a constraint (Context), and a reader that needs the target of a run is one that knows the member. **That judgement is made for the one value admitted today, and it is made again at each step that widens what the member may hold under ADR-0050 decision 6 (a) or (b).** After such a step a file can state what a reader which passes the member over would not see: a further objective type ("the direction of each type is the type's own", **owner**, O3), more than one objective, or a ceiling — the plainest case, since "No part of the runtime may treat a ceiling that was not judged as met" (cited: ADR-0050 decision 5) bears on such a reader. ADR-0018 decision 2 raises the version where "a reader that passes over the member would act wrongly" and leaves that judgement to the record of the member: the record that takes such a step makes it for this file. If it finds that the member may no longer be passed over, it raises the `schema_version` of this file and says to which version of this file the widened form belongs; the sentence of decision 4 that the same step extends this member holds only where it does not (sub-question ㉞ (iii)).
- **A member that is present must be valid.** A file whose `objective` breaks decision 4 is **invalid** in the sense of ADR-0018 decision 2: "A reader reports an invalid file, uses no member of it and repairs nothing" (cited) — not its `hw_profile` or any other member either. This follows ADR-0020 decision 3.
- **A valid file without the member states no objective and no set of constraints.** A reader of this record that is asked for the target of such a run finds that none is stated. **It never substitutes a value**: not `latency_minimisation` — although that is the only value a file can state today (decision 4), which is a fact about what is admitted and not about what this run chose ("which a run states is the user's choice per instance at run time", **owner**, O1) —, not a constant of the source the reader runs from, not the `task.objective` of a spec of the run, and not a value from another run. **And a reader of this record does not conclude that the run states an empty set of constraints**: "no constraint" is stated by a present member whose `constraints` is empty, and by nothing else (L3).
- **A reader of this record has no path to a target the run did not state.** It has the objectives and the constraints of a run only when the file of that run is valid, is of version 1 and holds the member. A missing file, a file that cannot be read, an invalid file, a file of another version and a valid file without the member each leave it without them. What a writer of a spec does for such a run is not covered by this sentence (L8).
- **What this record does not say**: where, and by what, it is checked that an instance states its target, and what the start of an instance does when it is given none. **That every instance has a target is not what is left open**: FR-2 has the user state the target for each Loop instance (cited), and this record reads the owner's "an instance states exactly one objective" (O3) by its letter, as excluding none as well as two — that reading of O3 is this record's. **This record reads both as binding whatever starts an instance, and not as a rule of the validity of the file** — the reading ADR-0020 decision 3 took for the owner's "An instance must state both `rtol` and `atol`" (cited: "The owner's \"must\" binds whatever starts an instance of the first case; where that is checked is not decided"). A valid file is "not thereby enough to start a run" (cited: ADR-0018 decision 2). Where the target is checked, and what the start of an instance does when none was given, is the writer's and is registered (sub-question ㉞ (i)). **Inside a present member the owner's "exactly one" holds without exception: no valid member states zero objectives or two** (decision 4). For the file as a whole validity does not show it: a valid file may lack the member (the cost, last bullet).
- **Why not a required member and version 2.** For it: FR-2, O3 and the glossary make the target a part of every instance, more plainly than they do the budget. Against it: every file and every reader of today would be of another version before a first run exists (the cost ADR-0020 decision 3 names); the record would have to say which layout version the new `schema_version` states (cited: ADR-0024 decision 3), and reading another version is OD-11, which is open; and the two members a run can as little do without — the op_signature and, for the first case, the tolerance the owner's "must" speaks of — may each be absent from a valid file. A new version of this file is also a change of a data-plane schema that this record does not take without the owner. **If the owner holds that O3 obliges every instance file to hold the member, that is an objection to this decision**: the member then becomes required by a record that raises the version, and nothing else of this record depends on it.
- **The cost**: validity does not show that a target is stated. A file without the member and a file whose member name is misspelt look alike to a version 1 reader — both state none (L3).

### 6. The member and the spec

- **"copied from the instance record" (cited: ADR-0002 decision 2) now points at a member**: the instance record is `runs/<run_id>/instance.json` and the value is that of its `objective`. Because the form is one (decision 4), the `task.objective` of a version-2 spec of a run that is such a copy is the same JSON value. A version-1 spec has "any JSON value" there and is not spoken of.
- **No more is said.** This record writes no rule about what writes a spec, when, from which read of the file, or what it does for a run whose file states no objective; and **no rule by which a spec is checked against its instance, or two specs of one run against each other**. No spec is invalid by this record, and the validator of a spec still checks the form of one document (ADR-0050 L1, in the words of ADR-0052 decision 7). That is registered (sub-question ㉞ (ii); OD-23; PLAN P2-2).
- **What of ADR-0050 L2 and ADR-0052 L10 stays true and what does not.** "no record gives `instance.json` a member that states objectives or constraints" (ADR-0050 L2; ADR-0052 decision 7 has "no record gives `instance.json` such a member") is no longer exact. "nothing can check that a spec carries what its instance stated" is less exact in one word: there is now a value to compare with, and still nothing compares. "Whether a spec and its instance agree is checked by nothing" (ADR-0052 L10) stays true as written.
- **Today nothing reads the member and nothing writes a spec from an instance** (L1).

### 7. The member and sub-question ⑩ of OD-13; how the member is read

- **The objectives and the constraints a run states are those in this member of the file of that run**, `runs/<run_id>/instance.json` below the data root in use. A reader of this record reads the file as a whole, which must be valid (ADR-0018 decision 2), and **keeps nothing from an earlier read** (cited: ADR-0010 decision 7; ADR-0018 decision 4): asked again, a reader of this record reads the file again. Which call, if any, is such a reader is not said (third bullet).
- **Sub-question ⑩ has three parts** (cited: ADR-0052 Boundaries): which call at an execution point carries out the timing run whose figure is judged; "from which record of the run that call takes the `bound`"; and which members of a result and of a result file carry the figure and the verdict. **This record answers the second part as far as naming the record, and nothing of the first and the third.** The record of a run in which a constraint is stated is this member, and no other record gives a file of a run a place where the run states one: what a spec holds in its `task.objective` is the value ADR-0002 calls copied from this record, and nothing checks that it is (L8; ADR-0052 L10). A `bound` read from this member is therefore taken "from what the run itself has recorded of its instance" in the words of ADR-0052 decision 7 (c), and is no member of a request ("A `bound` that a caller hands in a request would not meet (c)", cited). L2 limits this: a caller that can write the file can still choose the bound, which ADR-0052 does not exclude either.
- **Not said, also of the second part**: that any call reads the member, which call, at which moment and from which read, and what a call answers for a file that states no target, states no constraint, or cannot be used. No tool, request member, result member or tool-failure kind is named. Those are the contracts of the run tools (OD-18; PLAN P1-1).
- **Condition (c) of ADR-0052 decision 7 is not met by this record**, nor by this record with its code slice: (c) asks for "a record and its code by which a call that carries out a timing run at an execution point returns the verdict to its caller, at both points" (cited), and no such call has a contract. Conditions (a) and (b) are code that is not on `main`. `memory_ceiling` stays not admitted (decision 4).

### Example

The placeholders of the Example of ADR-0018 with the new member, so this is the shape of the member and **not a valid file** (`NOT-DECIDED-HERE` is no valid `hw_source`), and not a complete instance. **The value of `objective` is there because the file states it: it is no default, and no reader supplies it for a file that lacks the member.**

```json
{
  "schema_version": 1,
  "hw_profile": {
    "key": "cpu_standin-b0d8610d8f470856",
    "record": {
```

### Walk-through

What a reader of this record finds when it is asked for the target of the run `r1`.

| `runs/r1/instance.json` | What the reader finds |
|---|---|
| Valid, version 1, with the `objective` of the Example | `r1` states one objective, `latency_minimisation`, and an empty set of constraints. Asked again, it reads the file again |
| Valid, version 1, without the member | No target is stated for `r1`: no objective and no set of constraints. Nothing is substituted, and the reader does not conclude that `r1` has no constraint. The other members of the run can still be had |
| `"objective": "latency_minimisation"`, `null`, `{}`, an `objectives` with no entry or with two, an entry with `weight`, an `objective` without `constraints` | The file is invalid: no member of it is used |
| `"constraints": [{"type": "memory_ceiling", "bound": 123456789}]` inside `objective` | The file is invalid today (decision 4); it is not read as a run with a ceiling, nor as a run without one |
| Valid, version 1, with `"objectives": […]` or `"target": …` at the top level and no `objective` | As the second row: the member of a nearby name is passed over |
| Missing, unreadable, or of another version | No target can be had, as ADR-0018 has it for the `hw_profile` |
| `r1` states the `objective` of the Example and a spec of `r1` holds another `task.objective` | By this record nothing follows from the two together: neither is invalid and nothing is reported (decision 6) |

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 4 | Two top-level members, `objectives` and `constraints` | Each can be absent or misspelt by itself, and a lost `constraints` would pass unreported; see decision 4. |
| 4 | A form of this file's own (for example a type name and a map of bounds) that a spec writer translates | A rule of translation, which is a rule about what writes a spec; two vocabularies for the owner's one frame; an instance could state what no spec can carry. |
| 4 | The same form, with the rules of ADR-0050 written out again here | Two texts that can drift, and every later admission in two records. |
| 4 | Admit a well-formed `memory_ceiling` entry in this file now, ahead of the spec | A run would state a ceiling that nothing judges and that no spec can carry; ADR-0050 decision 5 declined that for the spec, and ADR-0052 decision 7 names the condition. |
| 4 | The names `target`, `goal`, `task` | See decision 4. |
| 4 | The rule of version 1 written as the one value of today, not as a reference (the choice of ADR-0023 decision 3 for the lower end of `n_max`) | Validity would be the same for every reader, but each admission under ADR-0050 decision 6 would change the form of this member and raise the version of a file that is written once; see decision 4. |
| 4 | Every later admission is a new version of this file | Against "so that the schema does not change later" (O3) as this record reads it for the file; a file written once would be of an old version at each admission, and reading another version is OD-11. |
| 5 | An absent member means `latency_minimisation` | A default the run did not state; a misspelt name would read as a chosen target, and the default would change meaning with the first further type. |
| 5 | An absent member means an empty set of constraints while the objective is "not stated" | Two meanings of one absence; a misspelt name would read as a run without a ceiling. |
| 5 | Required, with `schema_version` 2 | See decision 5; not taken without the owner. |
| 5 | Required without raising the version | Against ADR-0018 decision 2, which makes a further required top-level member a new version. |
| 5 | A present and invalid member leaves the file valid and counts as "not stated" | Two notions of validity for one file (ADR-0020 decision 3), and a damaged statement of a target would pass as none. |
| 6 | A spec whose `task.objective` differs from the member is invalid | A rule across two files that the validator of one document cannot check, and a rule about what writes a spec. |
| 7 | Name the call that reads the `bound` and what it answers | The contracts of the run tools, which no record has written. |

## Consequences

- **The code slice that can be cut once CI starts jobs again** (code mode): in `hilclaw/instance.py`, the validity of the member by decision 4 and a reader of the target of a run beside `draws_of`, with tests in `tests/test_instance.py`. The names, the return form and how "not stated" is told from a value are the code task's. **Whether the checks are shared with `hilclaw/spec.py` or repeated is the code task's too**; this record only observes that `_objective` and `_constraint` of that module are private and report places below `task.objective`, and that decision 4 asks for one set of accepted values in both modules at every source commit. Writing the file, writing a spec and binding the reader to a tool are not part of that slice.
- **Hints for that task** (observed, not decided): `tests/test_instance.py` asserts the exact `Instance._fields` and builds an `Instance` positionally, and `tests/test_check_admission.py` builds a `NamedTuple` type from `Instance._fields`; **two cases of `test_the_top_level_is_open` hold a top-level `objective` (`None` and `""`) among members not defined and assert the content valid** — by this record both contents are invalid.
- **Sentences of the code that then change**: in the docstring of `hilclaw/instance.py`, the list of records, "Conventions of this module, which the eleven records do not fix", the order of the checks and the descriptions of `Instance.others`; in the docstring of `hilclaw/spec.py`, "that ``task.objective`` is what the instance stated (ADR-0050 L2)" stays true (nothing checks it) and can name the member.
- **Not edited and now less exact** (follow-ups for the integrator): ADR-0050 L2, Consequences slice (c) and the Boundaries bullet "PLAN P1-8" (the member is recorded; "what an instance start checks" stays open); ADR-0052 decision 7 ("no record gives `instance.json` such a member"), its Consequences slice (2) and its Boundaries bullet on the member; the bullets that file the objective of an instance under what waits for the owner or has no form — ADR-0018 (Context, the Example's "no objective", Boundaries), ADR-0020, ADR-0023, ADR-0028, ADR-0031, ADR-0032, ADR-0033 and ADR-0034 (in their Context, decisions or Boundaries), as far as they speak of the objective and not of the target metric of FR-3 ④, which stays open; ADR-0012 Boundaries ("all of `instance.json` (target, budget, …)"); the lists of what makes `instance.json` invalid in ADR-0018 decisions 2 and 4 and in ADR-0019 decision 3, which an `objective` that breaks this record joins. ADR-0002 decision 2 stays exact. No sentence of UsageCases became false.
- **What of ADR-0052 decision 7 is still missing after this record and its code**: (a) the harness slice, (b) the verdict as code, and of (c) the record and the code of a call that carries out a timing run and returns the verdict at both points — with them the first and third parts of sub-question ⑩ and the rest of the second (decision 7). And one thing that record did not ask for: the judgement of decision 5 (first bullet) for this file at the step that admits a constraint type — "The admission raises no version" (ADR-0052 decision 7) speaks of the version of the spec.
- **A-13 reading.** Document mode; no code, dependency, settings file or schema file changes. The record adds one member that may be absent to a file whose frame says how later records add members (ADR-0018 decision 2), along the D6 route as the member records from ADR-0020 to ADR-0046 did; by that frame's own rule the version stays `1`. **The set of valid version 1 files becomes narrower without a new version**: a file with a top-level `objective` that breaks this record was valid before and is invalid now — the case ADR-0018 decision 6 named; no such file exists in a data plane, since nothing starts an instance yet. No member or rule of the spec, of `STATE.json`, `artifacts.json` or `events.ndjson` changes, and no layout version.

## Boundaries (not decided here)

- **Owner-only, the rest of #5 A-4 / OD-1**: the full list of objective and constraint types; the quantity and unit of throughput; the rule that combines more than one objective, and with it the type, meaning and values of `weight` and `priority`.
- **The admission of `memory_ceiling`** (ADR-0052 decision 7) and check 4 of ADR-0050 as code.
- **The contracts of the run tools** (OD-18; PLAN P1-1): the first and third parts of sub-question ⑩ of OD-13, and of the second everything beyond the naming of the record (decision 7).
- **The writer and the start of an instance**: what writes `instance.json`, from which input of the user it takes the target, what offers the menu to the user, and what a start checks or refuses (OD-8 sub-questions ⑩ and ⑰, and ㉞ below; OD-23; UC-1).
- **The spec**: what writes one and whether it is checked against the instance (OD-23; PLAN P2-2).
- **OD-13, OD-28, OD-15, OD-29**: `delta`, the baseline, promotion. **OD-2, OD-19**: budgets and the target metric of FR-3 ④. **OD-30**: how a hypothesis record names a metric. **OD-11**: reading a file of another version. **Other backends, kinds and kernel languages** (#5 B-1 to B-3): how the quantity of a type is measured there.
- **Sub-question this record raises** (registered under OD-8): ㉞ Three parts. (i) Where and by what it is checked that an instance states its target — that it states one is FR-2's and is not the question —, what the start of an instance does when it is given none, from which input of the user the member is taken and what offers the menu (with ⑰, OD-23, UC-1). (ii) What writes the `task.objective` of a spec from the member, from which read of the file, what it does for a run whose file states none, and whether anything checks that a spec carries what its instance states or that two specs of one run agree (with OD-23, PLAN P2-2; ADR-0050 L2, ADR-0052 L10). (iii) What this member becomes when a version of the spec after 2 changes the form of `task.objective`, whether the reading holds that a step taken under ADR-0050 decision 6 (a) or (b) raises no version of this file, and whether a reader may still pass the member over after each such step — a further objective type, more than one objective, a constraint type (decisions 4 and 5; with OD-11, OD-6).
