## Decision

Whose a sentence is: **the owner's** where O1, O2 or O3 is named; **cited** where a requirement, a record with its decision number or a file of the code is named with it — it then says what that source says and adds nothing; **this record's own** otherwise — among them which side reads the kernel source, the fourth thing an operation is handed, that the executable is built at each call, where it is written and for how long, the two kinds and their messages, and every weighing. The record's own design is what the objection window is for.

### 1. Scope and terms

- This record is about **a call of `correctness.check` about one attempt** of a run of the first case or of a run whose hw_profile names the mock (cited for the runs: ADR-0021 decision 1; ADR-0038 decision 6), **from the moment the tool function has selected a backend to the moment an operation has a verification executable it can start, or has none**.
- **Not this record**: the agent roster, who holds a role and who calls the tool; when in a round a check is made; the run tools `sim.run` and `board.run`, whose timing executable is theirs; any flag, compiler, language standard, thread setting or time-limit value, and the source of any; a sandbox.
- The terms of ADR-0016 (backend, operation, the moments ① to ⑦), ADR-0017 (verification program, verification executable), ADR-0021 (the cut, a check, class (iii)), ADR-0043 (the check parameters), ADR-0047 (a backend kind, a kind outside the contract) and ADR-0055 (kernel files, compiled set, the reader, R1 to R8) are used unchanged. **The output path**: decision 3. **The build directory**: decision 4.

### 2. Limits (they hold for every statement of decisions 3 to 8)

- **Nothing was built or run**, and the reader of ADR-0055 does not exist as code (Status).
- **Place, not honesty; no check of content** (cited: ADR-0055 L1 and L2). A build of decision 4 compiles whatever admitted `.c` files lie below the `output/` at the moment of the call, whoever put them there, and the executable it makes is as unprotected as before: "the process is as unprotected as `local_run` says" (cited: ADR-0017 decision 2; its decision 10: "the process is not sandboxed"), and so is the compiler's process, which reads files a coder wrote.
- **An unfinished bring-in matters here, and nothing detects it.** "A bring-in that died part-way leaves an `output/` that holds some of the files; the form has no mark that tells the two apart" (cited: ADR-0055 L5). A check that is called while a bring-in is under way, or after one died, reads what lies there: no kernel source, or a compiled set that is a part of the kernel (cited: ADR-0055 L3, "A build over such a set will usually fail and need not"). When a round calls the tool in relation to a bring-in is not this record's (OD-23 sub-question ① (가); PLAN P2-1).
- **Nothing ties a result to the bytes that were built.** Two checks of one attempt each read `output/` anew (decision 4); if its content changed between them by another route (cited: ADR-0055 L1), they verify two sources and nothing says so. No member of a result names the source or the settings of the build (sub-question ⑰ (다)).
- **A process that outlives its limit.** "On a timeout only the process it started is killed, not that process's children" (cited: `hilclaw/clang_build.py`; `hilclaw/local_run.py` says the like of its own process). A survivor of a build or of a verification process can hold the build directory, or write into it, while the operation removes it and after (decision 4).
- **A backend that reads or builds otherwise is not detected**: "A backend that does not answer the contract … is not detected by the frame" (cited: ADR-0016 decision 6).

### 3. Which side comes to the kernel source, and what crosses the cut

- **The tool function hands the operation one further thing, the output path: the path of the `output/` of the attempt the request names. The operation applies the reader of ADR-0055 decision 3 to it.**
- **What the output path is.** The path that ADR-0004 fixes for the `output/` of the attempt (cited: decision 3, "The tuple of ADR-0002 maps to a path by formatting alone"), formed from the data root of the call and the members `run_id`, `round`, `candidate` and `attempt` of the request (cited for the members: ADR-0040 decision 5). The tool function forms it and **reads nothing there**: it does not test whether the path, or anything between the run directory and it, exists. It is the thing R1 starts from: "Given the path of the `output/` of an attempt" (cited: ADR-0055 decision 3).
- **It is a further thing beside the check parameters, not a sixth value of them.** An operation of this tool is called with **four things: the request, the hw_profile of the call, the check parameters and the output path.** The check parameters stay "one value that holds exactly these five values and nothing else" (cited: ADR-0043 decision 2). Reasons: ADR-0043 decision 2 named the possibility that "what class (iii) needs is of another kind than five integers" (cited), and it is — a path, not a number the tool function judges with; and the default script of the mock keeps its sentence, "The answer depends on the check parameters and on nothing else the script is asked with" (cited: ADR-0044 decision 3), without a value in the check parameters that it must not read. The cost is the one ADR-0043 decision 2 named for its form (b): the number of things every operation and every script of this tool is called with changes once.
- **Three routes were weighed.**
  - **(a) The tool function applies the reader and hands over the compiled set.** The reader would run before the start line, so an attempt without a kernel source could be answered with no line and nothing consumed, as `tolerance_not_stated` is. Against it: for a run at the mock no kernel source need exist — the default script "stands for no kernel language, no source, no build and no flag" (cited: ADR-0044 decision 3) — so, under a tool function that answered for a missing source, a contract test over the mock would have to make up a kernel source for a backend that stands for none before any judging ran — this record's inference, set against the purpose O2 states (**the owner's**: "so that the contract tests of P1-1 run the whole judging over the mock") — or the tool function would have to treat the mock differently, and it is "the same code for every backend" (cited: ADR-0021 decision 2). And the compiled set is the input of a build of one kernel language at one target, which "is not the tool function's part" (cited, same decision).
  - **(b) The tool function hands over the path of the attempt's `output/`, and the operation applies the reader.** One formatting of members the tool function already has, the same for every backend; the side that builds is the side that reads what it builds from.
  - **(c) The backend comes to the source by a way of its own.** It would need the data root from a second source, which can disagree with the one the call asked (cited: ADR-0015 decision 3, the data root is asked at each call).
- **The choice is (b).** Its cost against (a): the reader runs inside the step, after the start line, so its two situations use up the identity (decision 6).
- **An operation is not handed the data root** — the question ADR-0016 decision 2 (d) left to this contract. It is handed one path below it. **Under this record an operation of this tool writes nothing below the data root**, and reads there what the reader reads — the listing of the attempt directory and of `output/` — and, through the compiler, the kernel files. A handed data root was weighed and not taken: it is more than the reader needs, and the formatting of the path would exist at two sides.
- **The moment.** The output path is handed over in ⑥, with the call of the operation. The reader is applied in ⑥ by the operation, before it makes the build directory and before any process is started.
- **The mock.** The mock's operation is called with the same four things and its script is asked with them, as they are, and with the called tool: five things, where ADR-0044 decision 2 has "the three things the operation was called with" and four (this record extends that sentence by one thing; ADR-0044 is not edited). **For a run at the mock no `output/` need exist**: the path is formed and handed over all the same, and nothing looks at it. **The default script does not read the output path**; its answer follows from the check parameters alone, and it still "never answers (B) and raises no tool failure" (cited: ADR-0044 decision 3). A script of a test is handed the path as a value and may raise one of the kinds of decision 6; the outcome of a mock call "depends on its script and its call alone" (cited: ADR-0016 decision 5 (e)), so a script answers from that value and not from what lies at the path.
- **What is fixed and what is the code task's.** Fixed: that there are four things, what the fourth is, that the tool function reads nothing at it, and which side applies the reader. The code task's: the Python type of the path and whether it is made absolute, by which position or name it reaches an operation and a script, and in which module the reader lives — a function of the package that every backend that builds uses, not a function of one backend.
- **What crosses the cut** — the table of ADR-0043 decision 7 as amended by this record (ADR-0043 is not edited; the added row is in bold):

| Direction | What | Kind of value | Source |
|---|---|---|---|
| to the operation | the request | the request of the call, the member `point` in it | ADR-0043 decision 7 |
| to the operation | the hw_profile of the call | the record of the run | ADR-0043 decision 7 |
| to the operation | the check parameters: the seed, `draws`, `m`, `k`, `n` | one value that holds exactly five integers | ADR-0043 decision 7 |
| **to the operation** | **the output path** | **a path: that of the `output/` of the attempt the request names** | **this record** |
| from the operation | (A) the report | a byte string | ADR-0043 decision 7 |
| from the operation | (B) the condition | the string `"time_limit"` or `"exit_status"` | ADR-0043 decision 7 |

- **Nothing else crosses as a value handed or returned.** No flag, compiler, time limit or environment is handed over under this record (decision 4), and nothing of a build is returned: no log of a compiler, no command, no path. A tool failure an operation raises is no row; the kinds are in decision 6.

### 4. Built at the call, and where the executable lies

- **The operation of `cpu_standin` builds the verification executable at each call, from the compiled set the reader gave it at that call**: "one call of `clang_build.build`" over the verification program and all files of the compiled set, in the order of R3 (cited: ADR-0017 decision 2; ADR-0055 R3). The kernel files are compiled where they lie; nothing is copied into the data plane.
- **Three ways were weighed.**
  - **(a) Built at each call.** No outcome depends on anything an earlier call left (cited: ADR-0016 decision 2 (c)); the executable is made from what the reader saw at that call; and nothing is needed that is not decided — no builder of the roster, no place in the tree, no record of a build.
  - **(b) Built before the call by another step, and handed over or found.** It needs a holder of that step ("No source says which agent or tool runs that build" — cited: ADR-0004 decision 3), a place where an executable outlives a call, and a rule that ties it to the source it was built from. Each is OD-23, a path of the data plane or the build record.
  - **(c) A cache keyed by the source.** "A connection or a cache that can be built again is not such state" (cited: ADR-0016 decision 2 (c)), so the frame allows one. Its key would have to cover every input of the build — the bytes of every kernel file, the headers among them, the verification program, the flags, the compiler and the environment — and no outcome might differ with and without it. The sources of the settings are open, so the key cannot be stated. **Not adopted; a later record may add one under that condition.**
- **The choice is (a).** **Its cost, stated as ADR-0017 decision 2 states its own**: every check builds. The two checks of an attempt (O1, **the owner's**) are two builds of the verification executable, beside whatever the run tools build for the timing executable, whose contracts are not written — "an attempt is built twice (one executable per program)" (cited: ADR-0017 decision 2) counted the two programs, not the calls — and each further `execution` is one more. The executable checked at one point is not the file checked at the other, and nothing here makes the two builds use the same settings (OD-16 sub-question ⑥).
- **Where the executable is written: in the build directory**, a directory the operation makes for that one call and that no other call uses. **It lies outside both checkouts — the source repository and the data repository — and inside neither's `.git/`**, as ADR-0049 decision 3 has it for the scratch of a coder call (cited for the wording; that record "settles ADR-0004 decision 7 for the coder call", and this one settles it for the build of this tool). So it is no path of the tree of ADR-0004 (cited: decision 7, "Scratch, temporary and build-cache directories: no path of this tree is one"), and it is not below the `output/` of any attempt, of which ADR-0055 decision 7 left open only "Where a build of the kernel writes its executable". The exact location and name are the code task's; this record adds no path, name or version to the layout.
- **How long it lives: the operation removes the build directory, with everything in it, before its call returns or raises** — after a report, a condition or a tool failure alike. What an operation does when that removal fails, in whole or in part, is not decided (sub-question ⑰ (다)): this record says neither that a failed removal changes the answer of a check nor that it does not.
- **Under this record the executable is not stored: it is no blob of the CAS, has no record in `artifacts.json` and is in no file of the data plane.** O3 (**the owner's**) keeps binaries out of git and says that they are not kept for good; that part of C-3 is met by where the directory lies, not by an ignore rule. **That the verification executable is not among the binaries C-3 puts into the CAS under a retention class is this record's own reading, and a contestable one.** C-3 says where binaries go and how long each class of them is kept, and "which binaries the tools produce is not decided" (cited: ADR-0005 decision 5). The reading rests on this: the executable is built again at every check, from a source that is kept. If the owner reads C-3 or FR-6 as asking that the executable of a failed or an intermediate attempt be kept for its retention period, that is an objection to this decision. Whether a later record keeps one — to reproduce a fail, for example — is sub-question ⑰ (다).
- **The working directory of the compiler's process and of the verification process is the build directory.** What either writes under a relative name then lies in a directory that is removed. Sources and the artefact are handed to the compiler as absolute paths, "so `cwd` does not change what is compiled" (cited: `hilclaw/clang_build.py`). This fixes no value of an environment and is no protection: a process that writes under an absolute name writes where it can (decision 2).
- **Nothing of the build reaches a file or the caller.** The log of the compiler and its command are not returned across the cut (decision 3), are in no message (decision 6) and are written to no file by the operation. Whether a later record keeps them is sub-question ⑰ (가), with `build.json`: #5 A-2 names "에러 로그" among the texts that are kept in git (the owner's word, at the link of O3), and this record neither reads that sentence nor decides that such a log is lost for good — under it the two situations that are answered start no compiler.
- **The settings: through which side the operation has each.** This record fixes no value and no source of any.

| Setting (ADR-0017 decision 9) | Through which side |
|---|---|
| Path of the executable; working directory | **The operation's own** (this decision) |
| Flags and trailing flags; compiler; time limit of the build; time limit of the process; environment | **Open.** The tool function hands over none of them under this record, and this record does not say that a backend holds them: whether each is handed by the tool function (and then from which file or member) or is the backend's own goes with its source (OD-6 sub-question ②, OD-14, OD-16 sub-question ⑥) — sub-question ⑰ (나) |

- **What follows.** An operation that builds needs a time limit and may need flags, so the operation of `cpu_standin` cannot be written to its end from this record. That is the third stop the planner named, and it is left standing rather than closed with a default.

### 5. The situations in which there is no executable

They are listed in the order in which an operation of decision 4 meets them.

|---|---|---|---|

| S2 | **The reader fails** (R8): a directory that exists cannot be listed, or the kind of an entry cannot be determined | the same | decision 6 |
| S3 | The build directory cannot be made or written | before the build | ⑰ (가) |
| S4 | A setting of the build or of the process is one the functions refuse (a flag that sets the output, a time limit that is no positive finite number, an environment that cannot be handed over) | before a process is started; for one bound of the time limit of the process, after it was started and killed | ⑰ (가), (나) |

| S8 | The build passes its time limit | the build ended; `ok` false | ⑰ (가) |

The death of the tool function's process while the operation runs is the death point a backend can cause, after which the step is open (cited: ADR-0016 decision 5 (d); ADR-0011 decision 3), and it may leave a build directory behind (sub-question ⑰ (다)).
- **A code task that finds a situation this list lacks registers it**; the list is closed for what this record read and for nothing else.

### 6. What the call answers

- **S1 is a tool failure of the backend kind `no_kernel_source`, and S2 one of the backend kind `kernel_source_unreadable`.** Each is raised by the operation and answered **from an end line with a `failure`** that holds the raised kind and message: "After an operation raised a tool failure, the tool function ends the step without an outcome", and "Where the raised kind is a backend kind, the `failure` holds that kind and the message that was raised" (cited: ADR-0047 decisions 3 and 4). The identity is then ended, and the `spend` of the line is that of ADR-0040 decision 6. When the append of that line fails the call is `end_line_failed` (cited: ADR-0026 decision 3).
- **They are the first two backend kinds of this contract** — kinds "a record of this contract names … with the situation it means" (cited: ADR-0047 decision 5). Any backend may raise them, a script of the mock included; the tool function raises neither itself, and neither is answered before the start line. A backend kind raised for a situation it does not mean "is taken as it is" (cited: ADR-0047 Limits).
- **The sentence a caller may rely on for `no_kernel_source`.** *In the check of this identity the operation applied the reader of ADR-0055 decision 3 to the output path, and by R1 to R4 the attempt had no kernel source at that read. The operation started no process. No result was made, and the identity is ended.* It does not say why: an attempt that does not exist, a coder that left nothing (ADR-0055 L4), a bring-in that took nothing (B6) and one that is not yet carried out or died (L5) are not told apart.
- **For `kernel_source_unreadable`.** *… the reader failed in the sense of R8: a directory that exists could not be listed, or the kind of an entry could not be determined. Whether the attempt has a kernel source is not known. The operation started no process. No result was made, and the identity is ended.*
- **Why a tool failure and not a result, for S1 — weighed, since it is the nearer call.** A tool failure "says that no outcome was established" (cited: ADR-0010 decision 4). ADR-0021 decision 5 made a broken run a result because "The experiment was carried out at the target", and warned that a tool failure, "said of a kernel that crashes or hangs, … would have a caller read a property of the attempt out of a failure of the tool" (cited). In S1 no experiment was carried out and there is no kernel that did anything; a result of this tool reports a run, with a `shape`, a number of draws and a tolerance (cited: ADR-0042 decision 7), and there was none. And the situation cannot be told from a call made about an attempt that is not there or not yet brought in, which is no outcome of an attempt. **The cost is stated, not hidden: `no_kernel_source` is a tool failure from which a caller does read something about the attempt directory** — that at one read it held no kernel source. If the owner reads that as an outcome of the attempt that belongs in a result, that is an objection to this decision. For S2 nothing about the attempt is established at all.
- **Why two kinds.** ADR-0055 keeps the two apart — "What the reader cannot see is a failure, not an answer" (cited: R8) — and this record splits as ADR-0019 decision 2 did: "it splits where the fixed records already say something different of each case" (cited). The cases of R1 to R4 are one predicate there and one kind here; the message may say which it was.
- **Why inside the step and not before the start line.** It follows from decision 3: the reader is the operation's, and the operation is called in ⑥. The cost is that of ADR-0047 decision 3: the identity is used up, and a later check of that attempt at that point — after a bring-in that had not finished, or after a directory became readable — "would need a further `execution`, which nobody may yet grant" (cited: ADR-0016 decision 2).
- **The message**, in the manner of ADR-0045 decision 6 and ADR-0048 decision 6. It may say which case it was — for S1, that there was no attempt directory, no `output` directory or no file of the compiled set; for S2, which of the two directories could not be listed or that the kind of an entry could not be determined, and of which kind the error was, as the code names kinds of values. **It shows no path, no name of an entry, no byte of a file and no text of an error.** The message is written to `events.ndjson` for good (cited: ADR-0006 decision 5): a path would put the location of a checkout on one machine there, and a name of an entry is a string that, by another route than the bring-in, anybody chose (cited: ADR-0055 L1). The wording is the code's; a caller tells the cases apart by the kind. A message that breaks this is not detected.
- **The names** are *names* of ADR-0001 (16 and 24 characters). Checked on 2026-10-13 in `hilclaw/`, `tests/` and `ARCHITECTURE/`: no reserved kind, no kind of another record of this contract, no other kind the code names, no `step` value, no value of `condition` and no member name equals either. `kernel_source_unreadable` occurred in none of the three trees; `no_kernel_source` occurs only as a part of the names of four test functions (`tests/harness/test_timing_build.py`, `tests/harness/test_verification_build.py`), which are no values.
- **S3 to S10 are given no answer here. The two stops, exactly.**
  - *S7 and S8.* A source that does not compile is a property of the attempt more plainly than a crash is, and "this attempt did not complete a verification under these parameters" (cited: ADR-0021 decision 5, of what a broken result establishes) is true of it; so the reasoning that made a broken run a result points to a result here. But it is none of the four conditions of a run, and `condition` is "a string with exactly four values" (cited: ADR-0042 decision 3) in a list only a record amends and whose results are stored in `events.ndjson`. A fifth value is a decision this record may not take as a side effect; a tool failure instead would be the reading ADR-0021 decision 5 warned against, taken without that question having been put. Neither is chosen.
  - *S3 to S6, S9 and S10.* Each looks like a tool that could not do its work. But "A kind becomes a backend kind when a record … names it with the situation it means" (cited: ADR-0047 decision 5), and what S4, S6 and S10 mean depends on where the settings come from — a compiler that is not found, or flags that produce no executable ("Flags that do not produce an executable … are not corrected" — cited: `hilclaw/harness/verification_build.py`), are a fault of the machine if the backend holds them and of whatever prescribed them if they are handed over (decision 4). S3, S5 and S9 do not depend on the settings and could have been answered here; this record does not, by its own choice and for no stop of a fixed input. All six are left with S7 and S8 so that the class of every answer of the build is decided in one place, by the record that also has the route of the settings.
- **Until ⑰ is answered** an operation that raises a tool failure in S3 to S10 of a kind other than the two named above raises a kind outside the contract and is answered `operation_failure_invalid`, and one that raises another error is answered `operation_answer_invalid` (cited: ADR-0047 decision 4; ADR-0045 decision 4); one that raised either of the two kinds there would raise a backend kind for a situation it does not mean, which "is taken as it is" (cited: ADR-0047 Limits). **That says what the landed rules do with such an operation; it is not this record's answer for those situations**, and no operation should be written to rely on it.
- **Nothing here says what anybody does after either answer** — repair, a further `execution`, dropping the candidate, which check counts (FR-1, OD-10, OD-17, OD-19; sub-questions ⑪ and ⑭).
