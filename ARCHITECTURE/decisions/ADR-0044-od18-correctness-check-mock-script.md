## Decision

A sentence marked **owner** renders the HQ-0005 answer and quotes it. A sentence is **cited** when a record and its decision is named with it; it then says what that source says and adds nothing. Every other sentence is **this record's own** — among them that the script is asked with the things the operation was called with, as they are; that the mock's operation does not look at what its script answers; that the default script answers a check with a report of a right product wherever it can compute one, and makes that answer depend on the check parameters alone; the rule of the product; and every weighing.

### 1. Scope and terms

- This record is about **the mock backend** and **a check** — "one call that reaches ⑥" (cited: ADR-0021 decision 1) — of `correctness.check` about one attempt of a run whose hw_profile names the mock. Such a run "is answered by the first case's `correctness.check` contract" (**owner**, HQ-0005 (4), as ADR-0038 decision 6 quotes it). Its stated op_signature is covered: "a script is asked through this tool only for a run whose stated op_signature is covered, since no operation is called otherwise" (cited: ADR-0041 decision 5).
- It fixes **three points and nothing else**: how the mock's operation of this tool asks its script (decision 2); what the default script answers for this tool (decision 3); and the rule by which the default script derives its report (decision 4). Decision 5 says what follows by citation and what is not decided.
- The terms of ADR-0016 (backend, operation, script, the moments ① to ⑦), ADR-0017 (draw, report, check value), ADR-0021 (the cut, a check, (A), (B)), ADR-0041 (covered) and ADR-0043 (the check parameters, an answer of an operation) are used unchanged. **The default script** is the "one script fixed in the source" to which the mock of the default registry is bound (cited: ADR-0016 decision 5 (c)); this record writes what it answers for this tool and for no other. **A script of a test** is a script to which a test binds the mock of a registry it builds (cited for the binding: ADR-0016 decision 5 (c)). **The default mock** is short for the mock of a registry that `default_registry` builds, bound to the default script. This record fixes no name of code, of a member or of a value.
- **The level of the contract**, as in ADR-0043 decision 1: this record fixes which things a script is asked with and what the default script's answer holds. What is "the code task's" is named with each decision.

### 2. How the mock's operation of this tool asks its script

- **Cited, not re-decided.** "An operation of this tool is called with three things: the request, the hw_profile of the call, and the check parameters" (ADR-0043 decision 2). "a script of this tool is asked with the called tool, the request, the hw_profile and the check parameters" (ADR-0043 decision 6, from ADR-0021 decision 2). A script is "a function from a call … to what the operation does; it is asked when the operation is called (⑥ of decision 2 [of ADR-0016])" (ADR-0016 decision 5 (c)). "The outcome of a mock call depends on its script and its call alone" (ADR-0016 decision 5 (e)), where "its call" includes what this contract hands an operation (ADR-0021 decision 2).
- **What those sentences leave, decided here.**
  - **The script is asked with the three things the operation was called with, as they are**: the request, the hw_profile and the check parameters of that call, none of them derived, replaced or left out, and nothing added to any of them. The fourth thing, the called tool, is the tool whose operation was called.
  - **The script is asked exactly once for each call of the operation and at no other moment.** A call that does not reach ⑥ asks no script.
  - **The mock's operation does not look at what the script answers.** What the script returned is what the operation returns, whatever it is, and what the script raised passes through the operation unchanged. The mock establishes no form: which of the two forms of ADR-0043 decision 4 an answer has is established by the tool function (cited: ADR-0043 decision 5).
- **Two choices were weighed for the last point.**
  - **(a) The operation passes the answer on unseen.** A script is then all of what the operation does, as ADR-0016 decision 5 (c) defines it. A script of a test can give an answer of neither form, so the part of the tool function that "establishes which of the two forms an answer has before it uses it" (cited: ADR-0043 decision 5) can be exercised over the mock.
  - **(b) The operation checks that the answer is a byte string or one of the two strings.** The form would be established at two places that can disagree, and the mock would have to do something with an answer of neither form: return something else, or raise. Either would be a statement on what follows such an answer, which is sub-question ⑮, and a raised tool failure would need a kind, which no record names.
- **The choice is (a).** It is how the operations of `hilclaw/mock_backend.py` treat their scripts today (observation).
- **A script of another tool is not touched.** What a script of `sim.run`, `board.run` or `profiler.collect` is asked with stays what ADR-0016 decision 5 (c) says by the frame until the contract of that tool says more.
- **What is fixed and what is the code task's.** Fixed: with which four things a script of this tool is asked; that three of them are the operation's own, as they are; that it is asked once for each call; that its answer is the operation's answer. The code task's: the Python names, positions and types by which the four reach a script; whether one script callable serves every tool with one signature or is asked differently for this tool; how the default script is laid out in the source and how a mock backend is built so that its operation of this tool takes a third thing ("how the call is written" — cited: ADR-0016 decision 2).

### 3. What the default script answers for this tool

- **Owner** (HQ-0005 (4), as ADR-0038 decision 6 quotes it): "The mock's script stands in for the kernel, not for the reference: it may compute the product for the seed of the call, and the reference stays with the tool function. What the default script answers is the second record's."
- **For every check whose check parameters it can compute a report for, the default script answers with a report: an answer of the form (A) of ADR-0043 decision 4 that is a complete report for the check parameters of the call and holds, for each draw, the right product by the rule of decision 4.** The last bullet of this decision says what is left for the other check parameters. A report of this kind is the answer of an operation whose kernel is right and whose process ended by itself with status 0 within its time limit.
- **The answer depends on the check parameters and on nothing else the script is asked with**: not on `point`, not on any other member of the request, and not on the hw_profile. It reads no clock, no random source, no counter and no file of its own (cited: ADR-0016 decision 5 (e)); "the seed reaches the script as a part of its call, and a script reads no random source itself" (cited: ADR-0021 decision 2).
  - What follows: the default script answers the two checks of an attempt by one rule, and its two answers differ only as the check parameters of the two calls differ. Each check has a seed of its own (cited: ADR-0021 decision 3).
- **What the default script stands for** — the point ADR-0038 decision 6 handed on. It stands for the output of a kernel that is right for the covered op_signature of the run: kind `gemm`, dtype `fp32`, layout `row_major`, and the `m`, `k`, `n` of the check parameters (cited for the four conditions: ADR-0041 decision 5). It stands for no kernel language, no source, no build and no flag: the mock has "no other process" (cited: ADR-0016 decision 5 (a)), so nothing is built or started.
- **Four answers were weighed.**
  - **(a) A report of a right product, for every check it can compute one for.** A run at the default mock then passes a check wherever the default script can compute its report and the tolerance of the run admits the difference between each reported element and its reference (decision 4), so the layer above — the loop that calls the check at both points — can, as far as this tool goes, be carried through against the mock, and the whole judging of the tool function runs on each answer (cited: ADR-0021 decision 2, "the whole judging runs over the mock as it does over a real backend").
  - **(b) An answer that depends on a member of the request**, so that some checks give a fail, a broken result or an open step — by `point`, by `candidate`, or by `execution` in the manner ADR-0016 decision 5 (e) describes for "Fails first, then works". In the default registry, where no test builds the table, this is fault injection in a live session, which is "Not decided" (cited: ADR-0016 decision 5; sub-question ⑧). A script of a test can do it (decision 2; ADR-0016 decision 5 (e)).
  - **(c) Always one of the two conditions, or always a tool failure.** No run at the default mock would ever pass a check, and a tool failure would need a kind, which no record names (cited: ADR-0021 decision 5, "is not listed").
  - **(d) No answer for this tool**, so that the mock of the default registry does not offer it. "The mock of the default registry offers every HW tool of that registry" (cited: ADR-0016 decision 5 (d)).
- **The choice is (a).** A record that answers sub-question ⑧ may make the answer of the default script depend on more than the check parameters; it then amends this decision.
- **The default script never answers (B) and raises no tool failure.** Not (B): the two strings say that a process failed a condition (cited: ADR-0043 decision 4), and the mock has no process. No tool failure: no record names a kind a backend may raise.
- **Check parameters the default script cannot compute a report for** — values outside what the generator of the source commit accepts, whose bounds ADR-0043 decision 2 observes and does not adopt, or a product too large for the front process to hold — **are given no answer here.** What the code does for them is the code task's. If it raises something that is no tool failure, that is an answer of neither form (cited: ADR-0043 decision 5), and what a call then answers is sub-question ⑮, of which this record says nothing.

### 4. The rule by which the default script derives its report

- **The form, cited.** A complete report holds, "in this order and with nothing else: for each draw, the check value of decision 4 [of ADR-0017] written before the call, then, after the call has returned, the m·n elements of `c` in the layout of ADR-0008 decision 2 as the bytes they have in memory (4·m·n bytes); after the last draw, an end mark" (ADR-0017 decision 7). "The spelling and framing are the code task's, under one rule: the length of a complete report follows from `m`, `n` and `draws` alone" (same decision). The form is "an interface between two parts of the harness of one source commit" (same decision).
- **The report of the default script is a complete report of that form for the `m`, `n` and `draws` of the check parameters, in the spelling and framing of the harness of its own source commit.** The mock has no kernel call and no memory of a kernel's process; for each draw, in the order of the draws, the report holds:
  - **the check value of the inputs of that draw** — the inputs the generator of the harness gives for the seed, the draw and the dimensions of the check parameters ("Draw *d* has values determined by the seed, *d* and the dimensions" — cited: ADR-0017 decision 3), and the check value "of the bytes of `a` and `b` of that draw" (cited: ADR-0017 decision 4);
  - **the product of those inputs**: m·n fp32 elements in the layout `row_major`, as the bytes those fp32 values have on the host of the script, **each element being the fp32 value nearest to the corresponding element of the float64 product of the inputs widened to float64**, a tie going to the value whose last significand bit is 0.
  After the last draw it holds the end mark, and it holds nothing else.
- **The host of the script is the host of the tool function**: the mock has "no other process and no network" (cited: ADR-0016 decision 5 (a)), so the premise of the form, "both sides run on one machine" (cited: ADR-0017 decision 7), holds for it.
- **The product has the definition of the reference.** The owner's HQ-0004 answer defines the reference as "the float64 product of the drawn fp32 inputs widened to float64" (cited: ADR-0017 decision 4). The inputs of the default script are fp32 values drawn by the generator, so its product has that definition and, after it, one rounding to fp32.
- **Three rules of the product were weighed.**
  - **(i) The float64 product, each element rounded to the nearest fp32 value.** It is defined in words the records already have. Of all fp32 values the element is the one nearest to the float64 element, so where the script's float64 product and the reference of the tool function agree, a tolerance under which an element of this report fails is one under which every other fp32 value fails at that element. It costs, for each draw, one regeneration and one float64 product, the work ADR-0017 decision 10 names for the Python side of a draw (cited: "one regeneration and one float64 product on the Python side").
  - **(ii) A product in fp32 arithmetic in one fixed order of summation.** It would be fixed bit for bit and would share no arithmetic with the reference. Against it: it is the output of one particular kernel — one order of additions, no fused operation — and carries that kernel's accumulated rounding error, which "does not shrink with" an output element whose terms cancel (cited: ADR-0017 decision 5). A run at the default mock would then fail under tolerances that other right kernels pass, and which tolerances those are would follow from an order chosen here.
  - **(iii) "Any product a right kernel could return", left to the code task.** The answer would follow from no "rule fixed with the tool's contract" (cited: ADR-0016 decision 5 (e)), and which outputs are right is said under a tolerance only (this record's reading of ADR-0017 decision 5), which a script never has. Whether its product shares anything with the reference would then be the code task's alone.
- **The choice is (i).**
- **What (i) means for the owner's sentence.** The script "may compute the product for the seed of the call" (**owner**): it computes one. "the reference stays with the tool function" (**owner**): the script returns fp32 outputs and no reference; the tool function regenerates the inputs itself, computes its reference itself and compares (cited: ADR-0021 decision 2), and uses nothing of the script but the report. **The roles are apart; the arithmetic is not independent.** By the rule the script draws the inputs the tool function regenerates — it must, or the check values disagree — and its product has the definition of the reference. Decision 7 states what that leaves unseen.
- **How far the answer is a function of the call.** The rule uses nothing but the check parameters. The float64 product is fixed no further than it is for the reference: the owner's oracle is "NumPy float64" (cited: ADR-0017 decision 4), and no record fixes the order of its additions. Two computations of it can therefore give two float64 values for one element, and the rounded elements can then differ: by one step of fp32 where the two values lie on the two sides of a midpoint between two fp32 values, and by more at an element whose terms cancel, because the difference between the two computations does not shrink with the element. This record reads ADR-0016 decision 5 (e) as met by that: the answer depends on the script — the arithmetic it is made of included — and on the call, and on no clock, random source, counter or file of its own. It does not promise equal bytes on two hosts or from two numeric libraries.
- **The default script is never handed the tolerance.** "An operation is never handed the tolerance, a reference or an expected output", and the check parameters "hold none of them" (cited: ADR-0021 decision 2; ADR-0043 decision 2). The report is the same whatever tolerance the run states, and **whether it is judged a pass depends on that tolerance**. Where the script's float64 product and the reference agree and an element of the reference is no fp32 value, the reported element differs from it by the rounding; a tolerance is valid when each of its two numbers is "a finite number that is not negative" (cited: ADR-0017 decision 5), so a run can state one that admits less than that difference at some element, and the judging then reports a fail. **This record names no tolerance value and adds no rule on what a run at the mock states.**
  - This differs from what ADR-0017 decision 5 observes of a kernel: "the rounding error of a conforming fp32 kernel does not shrink with" an output element, and "A tolerance with `atol` = 0 is therefore one a conforming kernel can fail" (cited). The one rounding of rule (i) does shrink with the element. A pass of the default script under a tolerance therefore does not show that a right kernel passes under it (decision 7).
- **What is fixed and what is the code task's.** Fixed: that the report is complete for the check parameters; which inputs, which check value and which product it holds for each draw; the rounding; that it holds nothing else. The code task's: the spelling and framing, with the harness of the same source commit (cited: ADR-0017 decision 7); which code computes the inputs, the check value and the float64 product — whether the functions of `hilclaw/harness/` or other code — and in which order of additions; how much is held at once; what is raised for check parameters it cannot compute for (decision 3). Observation, binding nothing: `draw_inputs`, `check_value` and `reference` of `hilclaw/harness/verification_arrays.py` compute the three, and NumPy's conversion of a `float64` array to `float32` rounds as rule (i) says under the default rounding mode.

### 5. What a script of a test can express, and what is not decided

- **By citation only.** For this tool "a script must be able to express each thing an operation may return: a report that the tool function judges a pass; one it judges a fail; a report whose form is wrong; a report with a check value that disagrees; no report for a time limit; no report for a non-zero status; each tool-failure kind the complete contract lets a backend raise; and, if the tool is journaled, the death of the process while the operation runs" (cited: ADR-0021 decision 2). Of these, "the four reports are byte strings and the two cases without a report are the two strings of decision 4 [of ADR-0043]" (cited: ADR-0043 decision 6). The tool is journaled (cited: ADR-0040 decision 2), and the death of the process is the one death point a backend can cause (cited: ADR-0016 decision 5 (d)).
- By decision 2 a script of a test can also give an answer of neither form. What the call then answers is sub-question ⑮.
- **The tool-failure kinds a backend may raise are not named**, here or elsewhere (cited: ADR-0021 decision 5; ADR-0043 decision 6). This record says of them only that the default script raises none (decision 3).
- **Not decided by this record.**
  - **Fault injection in a live session** (OD-18 sub-question ⑧): how the mock of the default registry is made to give a fail, a broken result, a tool failure or an open step where no test builds the registry.
  - **Class (iii)** of ADR-0021 decision 2 and the first clause of sub-question ⑩: the mock has no process, and nothing here says how a real operation comes to an executable, to flags, to a time limit or to an environment.
  - **The scripts, operations and contracts of `sim.run`, `board.run` and `profiler.collect`** (#5 A-4).
  - **`draws`**: the script is handed a number of draws and a seed; no value, source or default of the number is fixed (OD-16 sub-question ⑤), and neither is whether a seed or a standard error is recorded after a check (the same sub-question).
  - **A target on another machine** (#5 B-2).
  - **When the default registry comes to hold the mock with this operation.** It is "an entry of the backend table bound in every registry that `default_registry` builds", and the mock "gains the operation of a tool with the record of that tool's contract" (cited: ADR-0016 decision 5 (a) and (d)). This record is not the whole contract, the tool is not registered, and `default_registry` binds no backend table today (observation); the binding is code, and when it comes is not said here.

| The request; a script of a test returns the string `"pass"` | The mock's operation returns it as it is: an answer of neither form | Makes no result from it (ADR-0043 decision 5). What the call answers: sub-question ⑮ |
| A request about a run whose hw_profile names `cpu_standin` | No script is asked: a call reaches the mock "only through a hw_profile that carries the name as its `accelerator`" (ADR-0016 decision 5 (b)) | Calls the operation of the backend selected for that hw_profile (ADR-0016 decision 4) |
| A repeated call that is answered from the log | No script is asked: "no backend is selected or called for it" (ADR-0016 decision 2) | Returns what the log holds |

### 7. Limits

- **The default script proves nothing about any kernel.** "The judging over the mock proves the tool function and not a kernel or a backend" (cited: ADR-0038 decision 8), and a mock outcome "is told apart by its hw_profile only" (cited: ADR-0016 decision 6). A result of a check at the mock has the members of every other result (cited: ADR-0042 decisions 1 and 7) and none that says a script produced the report.
- **What the default script shares with the judging.** By the rule of decision 4 it rests on the same generator and check function as the tool function's regeneration, and its product has the definition of the reference. A defect both sides share — a generator that disagrees with the verification program, which the mock does not run, or a wrong float64 product computed by code both use — is not seen by a check at the default mock. "If it shared code with the reference of the harness, a passing test would show nothing about that code" (cited: ADR-0038 decision 8). Whether code is shared is the code task's (decision 4); a script of a test may compute its product otherwise.
- **A pass at the default mock under a tolerance does not show that a right kernel passes under it**: the script's error is one rounding of the float64 product, a kernel's is that of its own fp32 arithmetic (decision 4).
- **A run at the default mock can fail its checks by its tolerance alone** (decision 4), and nothing here tells that fail from the fail of a wrong kernel.
- **For check parameters it can compute a report for, the default script gives no fail of a wrong kernel and no broken result; and it never answers (B) and raises no tool failure (decision 3).** A fail of a wrong kernel, a condition and a tool failure are reached at the mock by a script of a test; how they are reached in a live session is sub-question ⑧. What follows for check parameters the default script cannot compute a report for is the code task's and, where it is an answer of neither form, sub-question ⑮ (decision 3).
- **The cost lies in the front process.** For each draw the default script regenerates the inputs and computes a float64 product, beside the regeneration and the product of the judging (cited for the judging: ADR-0017 decision 10); "The Python-side work stays bounded by nothing" (cited: ADR-0021 decision 2), and the mock has no process and so no time limit of a process. The report is "4·m·n bytes per draw …, held at once for all draws" (cited: ADR-0021 decision 6), and a byte string is returned whole (cited: ADR-0043 decision 8).
- **A script is handed the seed** (cited: ADR-0021 decision 2; "A backend is handed the seed" — ADR-0021 decision 6). "No outcome depends on state a backend kept in the front process from an earlier call" (cited: ADR-0016 decision 2 (c)), a kept seed included.
- **A script of a test that does not answer the contract is not detected by the mock** (decision 2; cited: ADR-0016 decision 6, "is not detected by the frame"). The tool function "establishes the form, not the truth" (cited: ADR-0043 decision 5): a script that returns `"exit_status"`, or a report of a product no kernel computed, is taken as it is.
- The limits of ADR-0016 decision 6, ADR-0021 decision 6, ADR-0038 decision 8 and ADR-0043 decision 8 stand unchanged.

## Consequences

- **What the next slices of the second record must still add** — the list of ADR-0043 Consequences, without the item that record struck off itself: every other member of the request, the input schema and the description; where `draws` comes from; where the kernel of the attempt, the flags and the time limits come from, and with them what class (iii) adds to the form of ADR-0043; the tool-failure kinds a backend may raise; the spend beyond ADR-0040 decision 6; ~~the operation and the default script of the mock~~ (this record, for this tool). Of OD-18 sub-question ⑩ the first three clauses, the kernel language and another accelerator; and sub-question ⑮.
- **Code** (observations; **this record binds no code**). *Possible after this record*: the mock's operation of this tool and the default script. `hilclaw/mock_backend.py` and `tests/test_mock_backend.py` pin the call of an operation at two arguments and that of a script at three today, so that task names those assertions as permitted edits or uses another module. *Not yet possible*: the operation of `cpu_standin`, the tool function of `correctness.check` and its registration.
- **Not edited and now less exact** (follow-ups for the integrator; the list holds what this record found). ADR-0016 decision 5 (c) — "what that script answers for a tool is written with that tool's contract" — is not among them: this record does for one tool what that sentence says. The sentences: ADR-0021 decision 2 ("The default script and the rule by which it derives a report are the second record's") and the item "the operation and the default script of the mock" of its decision 1; ADR-0038 decision 6 ("Which kind, dtype or kernel a script of the mock stands for is the script's and the second record's"), the same item in its decision 7 and "what a script is built from is the second record's and the code task's" in its decision 8; the item "the operation and the default script of the mock" in the Consequences of ADR-0040, ADR-0041, ADR-0042 and ADR-0043 and in the Boundaries of ADR-0040, ADR-0041 and ADR-0042; ADR-0043 decision 6 ("… are the next slice's") and its Boundaries ("The mock: its operation of this tool, the default script and the rule by which a script derives a report"). In `hilclaw/mock_backend.py` the docstring sentence "Not here yet: the script of the default registry, which comes with the contract of the first HW tool" stays true of the code, while a record now says what that script answers for one tool. No sentence of UsageCases became false.
- **A-13 reading**: document mode; no code, dependency, settings file or schema file changes. The record continues the inner structure of layer 2 — what lies between a tool function and the mock backend of one source commit — as ADR-0016 and ADR-0043 did. **It adds no member to a request or to a result and gives no value a place in a file of the data plane**: what a script is asked with and what it answers are values inside one call. Under the landed records, what of the check parameters and of a script's answer reaches a file does so as members of a result the tool function makes (ADR-0042), and this record puts nothing of them into a file; what of the request and of the hw_profile is in a file is there as the records before this one put it, unchanged by this record. No member of `STATE.json`, `instance.json`, a spec, `artifacts.json`, a result file or a line of `events.ndjson` is added, removed or changed, and no value of `error.kind` is added or given to a situation. **This is therefore read as no "데이터 plane 스키마 변경".**

- **The oracle, the tolerance vocabulary and the defaults of every other backend** (#5 B-7); which tolerance a run at the mock states.
