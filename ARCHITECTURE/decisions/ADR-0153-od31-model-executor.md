## Context

- **What is handed over** (cited, ADR-0152): the embedding lookup, the copies a contract leaves and the order of calls are executor work (decision 3); which rows lm_head gets is open between sub-questions 4 and 6 (decision 4); which kernel is called for a shape no instance ran, and what happens when none fits, is sub-question 4 (decision 7). The KV cache write is part of the SDPA kernel, which takes the cache as an operand it updates (decision 3).
- **The calling side of a kernel** (cited, ADR-0008): a contract binds "the harness, or any program that calls a kernel" (decision 1); the caller owns the arrays, guarantees no overlap and alignment for the element type, and calls an entry point again only after it has returned (decision 6); the kernel source defines no `main` — "the caller provides the program" — and "two kernels of this contract define the same symbol" (decision 7).
- **Isolation** (cited, Requirements NFR-4, owner 2026-10-15): the execution of generated kernel code has a sandbox, timeout and resource guard; the builds, correctness runs and timing runs of kernels use an isolated environment, a container. For the first case, [ADR-0144](ADR-0144-od14-first-case-build-run-container.md) gives the builds and processes of `cpu_standin` a new container per build and per process, whose image holds clang and a POSIX C library.
- **The existing pattern** (layer-2 code, `hilclaw/harness/`): a C program of the harness is built with the kernel's sources into one executable that runs as a process of its own, and the Python side starts it and reads its report (`verification_program.c`, `verification.py`; ADR-0017). `numpy` is the one pinned runtime dependency (`pyproject.toml`).
- **Scale** (derived from ADR-0152 decisions 2 and 5): one forward pass is 16 × 12 + 2 kernel calls (RoPE counted as one call; its contract may make it two); a generation is one prefill and one pass per new token, with the KV cache carried from pass to pass.

## Decision

A sentence is **cited** when a source is named with it. Every other sentence is **this record's own**.

### 1. Place: two parts of the layer-2 package

- **The executor is part of the layer-2 package `hilclaw/`**, in two parts. (i) The **host side**, a Python module: it takes the inputs (decision 3), checks the binding against every call of the generation (decision 5), builds the kernels and the program, hands the program its inputs, starts it and reads its report. (ii) The **model program**, a C program of fixed source in the package, as the harness's programs are: built with the bound kernels, it runs as **one process per generation** and does all kernel calls, buffer work and the call order (decision 4).
- **It is not an FR-10 HW tool and not a backend** of ADR-0016: it carries out no experiment of `sim.run`, `board.run`, `profiler.collect` or `correctness.check`, and adds no entry to the backend table. It reuses the package's build and run paths.
- **First and only target here: `cpu_standin`.** The model program runs on the stand-in's CPU. How kernels of another target are called from a model run — on a device, through a backend — is open (Boundaries).
- **How it is offered** — a function only, a command-line entry, a registry or MCP tool for the runtime orchestrator — is not decided: who starts a model run and when is the scenario (sub-question 10) and the tool set (OD-18, OD-23). The first code slice is a module function.

### 2. Language

- **Host side: Python** — it handles the token ids, weights and logits as arrays (`numpy`, pinned) and the process, as the harness's Python side does. **Model program: C** — the kernels are C (ADR-0008 decision 1), and the program's builds and process need only clang and a C library, with two needs of loading: clang able to link a shared library, and the POSIX dynamic-loading interface of `<dlfcn.h>` (`dlopen`, `dlsym`). No Python is needed where generated code runs. ADR-0144 decision 5 lists, for the first case's image, clang linking an executable with the flags of ADR-0116 and the POSIX.1-2008 interfaces the harness programs use (cited); **the two loading needs are not in that list and are this record's own** — a requirement on the image only if OD-14 places the model program in that container (Boundaries).
- **No new external dependency**: the Python standard library, `numpy`, clang and the C library. POSIX sh is not used.

### 3. Inputs, binding and the kernel call

- **Inputs of the host side**, all in memory: (a) the **model parameters** — the dimensions of ADR-0152 decision 5 as named values (hidden, intermediate, vocabulary, layers, H, KV heads, d_h, eps and the RoPE constants), never assumed by the executor; (b) the **weights**, one array per weight of ADR-0152 decision 2 (the embedding table, the joined QKV, O, gate, up, down, the RMSNorm weights, lm_head), each already in the dtype and layout of the operand that receives it, and, if the RoPE contract takes the frequency table as an operand, that table as one more array (who computes it, and in what precision, goes with the RoPE contract and sub-question 2); (c) the **binding** (below); (d) the **run settings** — the prompt as token ids, the generation length (the number of tokens after the prompt), the lm_head rows (decision 4) and the mode (decision 4). Reading weights from a file, the tokenizer, and turning text into ids and back are outside the executor (sub-question 5); a test or a later loader supplies the arrays and ids.
- **The binding** is explicit: for each **call site** — a row of ADR-0152 decision 2 that is an instance target, with its kind (lm_head and the QKV, O, gate, up and down projections are separate call sites) — it names a **kernel reference**, either for listed shapes or for every shape. A kernel reference is a kernel's source files with the `task.contract` of the spec it was written to (ADR-0002, ADR-0008 decision 8) and its build settings. The executor never chooses a kernel itself. **How a binding is derived from a key's best is open** — `best.json` has no content yet (ADR-0004 decision 5: OD-20, OD-7); before then a binding is given by its caller (a test, or whatever caller the open exposure of decision 1 brings).
- **Fit.** A kernel fits a call site when its `task.contract` is the contract of the call site's kind, dtype, layout and language, compared on the prototype text and the names, roles and dtypes of the operand entries (their shapes are those of the spec's own shape). A change of a guarantee or an obligation that the prototype text does not show is not detected by this check (cited: ADR-0008 decision 8; OD-6 sub-question 4). **A listed shape** other than the shape of the kernel's own spec is accepted under the same condition as a binding for every shape; otherwise the kernel is unfit for it. A binding "for every shape" is accepted only where that contract obliges a kernel to be correct at every shape it is called with — for fp32 `gemm` it does (cited: ADR-0008 decision 6); for every other kind, its contract record says.
- **Loading.** Each bound kernel is built into **a shared library of its own** with its build settings plus what a shared library needs, and the model program loads each with `dlopen` (local symbols) and finds the entry point with `dlsym`. Two kernels of one contract define the same symbol (ADR-0008 decision 7), so one library per kernel keeps them apart without touching the kernel source.
- **The call.** The model program calls an entry point through the prototype of its contract: `hilclaw_gemm` for fp32 `gemm` (cited: ADR-0008 decision 4); for other kinds, through the prototypes of their future contract records. It keeps the caller's guarantees of each contract: distinct arrays for each operand, alignment for the element type, one call at a time.

### 4. Work outside the kernels

- **Embedding lookup**: a copy of the table row of each token id into the hidden-state buffer, in the model program; a token id outside the vocabulary is refused before anything is built (decision 5).
- **Copies a contract leaves**: where a kind's contract reads or writes in an order other than the producer's (the Q, K and V column ranges of the QKV output, the SDPA output for the O projection), the model program copies; which copies exist follows from those contracts. **Casts** between kernels, or in the embedding row copy, are made only if the answer of sub-question 2 requires them; none is decided.
- **Buffers**: the model program owns every array of a generation, allocated once for the largest T of the generation and freed at the end of the process. **The KV cache**: per layer, the cache operands of the SDPA contract, owned by the model program, allocated before the prefill to hold at least the positions the generation writes, passed to each SDPA call of its layer and kept across layers and decode steps until the process ends. Its capacity, its layout and how the kernel is told the capacity are the SDPA contract's (cited: ADR-0152 Boundaries).
- **Order of one pass**: the calls of ADR-0152 decision 2 in its order, layer 0 to the last, with T new tokens at positions P … P + T − 1. **Order of a generation**: one prefill pass over the prompt (P = 0), then one decode pass per further token (T = 1, P the tokens before it), until the generation length.
- **Modes**: **given sequence** — every token is given and the next pass takes the next given token; **generation** — the next token is selected from the last logits row. The selection rule is sub-question 6; where it is applied — a fixed rule in the model program chosen by a run setting, or the host side through an exchange per step — depends on the rule's form and is left open with it.
- **lm_head rows**: a run setting, **all T rows** or **the last row** of each pass; both are GEMMs hidden → vocabulary with M rows (2048 → 128256 for Llama 3.2 1B, cited: ADR-0152 decision 4). Which one a model-level comparison needs is sub-question 6.
- **Report**: the token ids of the run and the requested logits rows, read by the host side. Comparison with a reference is not executor work (sub-question 6).

### 5. No fitting kernel: named outcomes, no fallback

- The shapes of every call of a generation follow from the prompt length and the generation length, so **the host side checks the binding against all of them before anything is built**. A call site whose shape has no binding is the outcome **no kernel** (call site, shape); a bound kernel that does not fit is **kernel unfit** (call site, reason); a run setting outside its range (a token id outside the vocabulary) is **invalid input**. None of them builds or starts anything.
- After the checks, a failed build is **build failed** (kernel reference, compiler output) and a process that times out or ends without a complete report is **run failed**. The spelling of the five is the code slice's.
- **No fallback.** No NumPy or reference implementation stands in for a missing kernel: K2 has the pass "run on those kernels", and a fallback's numerics would rest on sub-questions 2 and 3.

### 6. The driver's verification: a small synthetic model

- **Same architecture, reduced dimensions**: the operations and order of ADR-0152 decision 2 with the model parameters of decision 3 (a) given small values by the test — hidden, intermediate, vocabulary, layers, H, KV heads (H a multiple of them) and d_h. No value of Llama 3.2 1B is assumed.
- **Synthetic weights** generated by the test from a seed, as in-memory arrays; **a synthetic tokenizer** written by the test over its small vocabulary. **No real Llama file**, and no weight file format is fixed — the executor takes arrays.
- **Kernels**: hand-written by the test to each kind's contract, as the calibration fixtures of ADR-0003 are (cited: ADR-0008 decision 1). What the test compares the result with, and within what tolerance, follows sub-questions 2 and 3; before their answers, a test checks the binding outcomes, the order of calls, the buffers and the cache across steps.

## Alternatives considered

| Choice | Alternative | Why not |
|---|---|---|
| Python host side + C program | Python only, kernels loaded in the Python process (`ctypes`) | Generated code then runs in the Python process; under NFR-4 that process needs an isolated environment, and the first case's image is not stated to hold Python or `numpy` (ADR-0144 decision 5). Adding them asks more of the user's image than the two loading needs of decision 2. |
| One process per generation | A process per kernel call, through the existing run path | Some 200 calls per pass, each a new process (and under ADR-0144 a new container) that reloads its weights; the KV cache would have to leave the process between calls. |
| Inside layer 2 | A layer-1 skill or agent that runs the kernels | Running kernels is deterministic tool work (CLAUDE.md three-layer model); an agent adds nothing to it. |
| Not an FR-10 tool or backend | A new HW tool, or an operation of the `cpu_standin` backend | FR-10 names four tools for per-attempt experiments; a model run is no such experiment, and a backend answers exactly the contract of a tool (ADR-0016 decision 2 (b)). Exposure stays open (decision 1). |
| One shared library per kernel | All kernels linked into one executable, the symbol renamed per kernel (`-D` or `objcopy`) | A macro rename depends on how the source spells the name, and helpers with external linkage still clash; a rename in the object files needs a tool beyond clang (`objcopy`). |
| Explicit binding | The executor reads `best.json` of each key | Its content is open (OD-20, OD-7). |
| Explicit binding | The nearest-shape kernel for an unlisted shape | A selection rule no source gives; correctness at another shape is the contract's, which the "every shape" binding already uses. |
| Kernel source in the binding | A built binary from the CAS | An attempt keeps no loadable library: its verification executable is built per call (ADR-0056) and is an executable, not a library. The shared library is built for the executor. |
| Named outcome | A NumPy fallback | Decision 5. |
| Embedding lookup in the model program | On the host side, rows handed over per pass | The host side would have to exchange data with the process at every decode step. |

## Boundaries (not decided here)

- **Dtype, accumulation precision and the casts between kernels**, including the precision steps of Meta's `model.py` (OD-31 sub-question 2, owner; HQ-0065).
- **Oracle, tolerance and input distribution** of each kind and of the synthetic-model tests (sub-question 3, owner; #5 B-7; HQ-0066).
- **H, d_h, the KV-head count and any value of B-4** (owner; HQ-0064).
- **Weights and tokenizer**: source, file format, storage, loading, base or instruct, tied or untied embeddings, weight layout conversion (sub-question 5, owner; OD-9, OD-25).
- **Model-level reference, comparison metric, prompts, generation length, token selection and the lm_head rows a comparison uses** (sub-question 6, owner).
- **Any new external dependency** (sub-question 7, owner); **whether the executor's output is C-6's whole-model binary** (sub-question 8, owner); **model-level performance** (sub-question 9, owner); **the scenario** and who starts a model run (sub-question 10, owner).
- **Each kind's contract** — prototype, operands, layout, the Q/K/V and cache order, cache capacity (the extension of OD-6 sub-question 1); **one instance per shape or several** (OD-6 sub-question 3).
- **`best.json` and its content** (OD-20, OD-7), and so the derivation of a binding from a key's best.
- **The isolation of the model program's build and process** — whether ADR-0144's container is used for it, and then whether its image gains the two loading needs of decision 2; time and memory limits (OD-14, NFR-4).
- **Kernels share one process** with each other, the buffers and the report: a kernel that writes outside its operands can change another's data or the report. Tamper resistance of a model-level result (OD-16, threat A inside a process) is not addressed.
- **Whether verification draws the shapes the executor calls** a kernel at beyond its instance's (OD-16 sub-question 1).
- **Targets other than `cpu_standin`** and how a model run reaches a device (#5 B-2, OD-18, OD-26); **exposure** as a command-line entry or a registry tool (sub-question 10, OD-18, OD-23).
- Build flags of the shared libraries and of the model program beyond "what a shared library needs", and the form in which the host side hands the program its inputs (code slices).
