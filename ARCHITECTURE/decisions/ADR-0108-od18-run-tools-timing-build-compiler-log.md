## Decision

### 1. Scope and terms

- **A call**: a call of `sim.run` or `board.run` about one attempt of a run of ADR-0061 decision 1 — a run whose hw_profile names `cpu_standin` in the local configuration (the first case), or names the mock.
- **The timing build**: the one call of `clang_build.build` over the driver program and the compiled set that the operation of a call makes (cited: ADR-0061 decision 2; ADR-0107 decision 1); a call makes at most one. **The log**: everything the compiler process of that build wrote on its standard output and its standard error, as ADR-0078 decision 1 says of the check's build.
- **Not this record**: other backends, a simulator, a board, a remote machine, `profiler.collect`, the emulated `sim.run` of sub-question ⑫ and the isolated environment (OD-14 sub-question ①); what the timing run's process writes (its report and its standard error — cited: ADR-0061 decision 7); the build of `correctness.check` (ADR-0078).

### 2. Which timing builds' logs are kept

- **The log of every timing build whose compiler process was started and has ended — by itself, or killed for its time limit — is kept**: a build past its time limit and a compiler's non-zero status (the broken results `build_time_limit` and `build_exit_status` — cited: [ADR-0063](ADR-0063-od18-run-tools-result-members.md) decision 3), a build that reported success and left no executable (S9 read for the timing build — cited: ADR-0061 decision 7), and every build that ended ok, whatever followed: a completed or broken timing run, an executable that cannot be started, a setting of the timing run refused after the build, a tool failure, an answer of neither form. S1 to S3, S5, S6, and S4 found before the build starts — the situations of ADR-0056 decision 5 as ADR-0061 decision 7 reads them for the timing build (cited) — find no compiler or none that ran, and have no log; S4 found after a build that ended ok (as ADR-0060 decision 4 places it for the check: "a setting of the process was refused after a build", cited) follows a build whose log is kept.
- **The presence rule of ADR-0078 decision 2 holds for these identities** (cited, with this record's kind): an empty log is kept as an empty file; for an identity ended after its operation came back — with a result or a failure of any kind but `build_log_unwritable` (decision 7) — the file exists exactly when the operation handed over a log (decision 5).
- **Three answers were weighed.**
  - **(a) Kept as ADR-0078 keeps the check's: every build whose compiler ended.**
  - **(b) Kept only for builds that ended not ok** (`build_time_limit`, `build_exit_status`). It loses the warnings of the builds whose timing counts, and the only evidence of S9; a missing file would then mean either an ok build or no build.
  - **(c) Not kept, because the verification build's log of the same attempt covers the kernel** (ADR-0107 decision 3). It would miss: **an attempt that is timed and never checked**, or whose check never built — no record makes a check precede a timing call (which attempts are timed, at which point and in which order is FR-1's and the loop's, cited: ADR-0062 decision 4), and a check can end before its build (S1 to S3, S5, S6, and S4 found before the build, of ADR-0056 decision 5); **the other harness program** — the driver program is compiled in the same call (cited: ADR-0107 decision 3), so a link failure or a warning that arises only with it, the `build_exit_status` of a timing build whose verification build was ok included, shows in no other log; and **a change of the backend's source of settings between the check and the call** (ADR-0107 Limit 3), after which the verification build's log is of another build.
- **The choice is (a).** **Why keep it at all**: FR-6 asks that intermediate, final and failed results all be kept, and #5 A-2 keeps "에러 로그" in git for good; **ADR-0078 decision 2 read that word as including the compiler's log of a build of an attempt**, and the log of a timing build is a log of a build of an attempt. This record takes that reading for the timing build; **it is not the owner's, and O2 is not read as covering the timing build.** One rule for both tools keeps one presence rule for every file of this kind. **The cost**: every call at a real backend adds a file, usually small or empty, to the data repository: one per call that builds, so at most one per tool per attempt under `execution` 1 and one more per further `execution`. If the owner reads A-2 as not reaching the timing build, that is an objection to this decision.
- **The mock** builds nothing; its default script hands over no log (decision 8).

### 3. The path and the name

- **`runs/<run_id>/rounds/<RRRR>/measure/candidates/<CC>/attempts/<AA>/build-log-<step>-<EE>.txt`**, the form of ADR-0078 decision 3 (cited), where `<step>` is the `step` value of the call — `sim_run_timing` for `sim.run`, `board_run_timing` for `board.run` (cited: ADR-0062 decision 3) — and `<EE>` its `execution`, zero-padded to at least two digits and written in full.
- **One identity, one name, and never the check's.** "Two tools of the registry do not share a `step` value" (cited: ADR-0015 decision 4, as ADR-0062 decision 3 applies it), so no name of these tools equals one of `correctness.check` (`correctness_check_sim`, `correctness_check_board`); the two calls of an attempt differ in `<step>`, and a further `execution` in `<EE>`. A step runs at most once under an identity (cited: ADR-0011 decision 3), so the name is written at most once. **One rule names the file of every build of an attempt by the call that made it.**
- **Why below `measure/`, flat, with that name.** ADR-0004 decision 3 keeps "everything that comes from one source" per attempt, "the build record, the sim, board and profile results" among it, and decision 4 gives `measure/` the "build and execution on sim and board" — which a call of these tools is, more plainly than a check. The reading of ADR-0004 decision 4 that the tool function does the measurement role's write for this file, of decision 9 that a file added directly in the attempt directory leaves the layout version at 1, of decision 3's "`build.json` replaces the draft's `build.log`", and the reasons for `.txt` and for no subdirectory, are ADR-0078 decision 3's (cited, not restated); they hold for this file as for the check's. If a later record moves `build.json` below `coder/`, it says whether these files move with it.

### 4. The form, and what the log may hold

- **The form is that of ADR-0078 decision 4** (cited): a UTF-8 text file tracked in the data repository, not a blob; the log as the compiler wrote it, invalid bytes replaced by U+FFFD, nothing added, removed or changed; no bound of size set here (decision 6).
- **What it may hold is that of ADR-0078 decision 5** (cited), read for these calls: not filtered; machine-local paths kept with it — here also the path of the driver program in the installation; the settings and environment of a build are no place for a secret. **Seeds**: **an operation of either run tool hands the compiler nothing derived from the timing seed** — no flag, no definition, no environment value, no file — so the log cannot hold it. The operation is handed the seed among the timing parameters for the timing run (cited: ADR-0065 decision 2), where "The seed travels as a command-line argument" (cited: ADR-0009 decision 5), and the tool layer keeps it nowhere after the run (cited: ADR-0064 decision 5). This is this record's requirement on every operation of these tools; a backend that breaks it is not detected (cited: ADR-0016 decision 6).
- **Inside a container** the log holds that environment's paths, and its route out is the container's (OD-14 sub-question ①; ⑱ (다)), as ADR-0078 decision 5 says of the check's.

### 5. The writing side and the route: a fifth thing

- **The tool function of the called tool writes the file**, from a log the operation hands over through **a fifth thing it is called with, the log keeper**, with the properties of ADR-0078 decision 6 (cited): made by the tool function for the call; handed the log as text, at most once, before the operation returns or raises; refusing a second hand-over, a value that is no text and a text that cannot be encoded as UTF-8 by an error raised in the operation. An operation that lets that error pass raises something that is no tool failure, which these tools answer `operation_answer_invalid` (cited: ADR-0065 decision 7). It is a thing beside the timing parameters, not a seventh value of them: those hold "exactly these six values and nothing else" (cited: ADR-0065 decision 2). **Fixed**: that there is a fifth thing, what it carries and how often; **the code task's**: its form, its name and how it reaches an operation and a script.
- **Why this side and this route**: the reasons of ADR-0078 decision 6 hold here (cited for the reasoning): one write for every backend, the data plane's paths formed at one side, a contract test over the mock, a remote target that must bring the log back in any case; and a log returned with (A) or (B) would change the form of every answer, told apart "by the kind of value" (cited: ADR-0065 decision 4), and could not travel with a raised tool failure, so S9's log could not be kept. **Added here**: a backend that offers both kinds of HW tool meets one shape — five things, the fifth the same keeper — the reasoning ADR-0065 decision 2 (a) gave for four. **An operation of either run tool is still not handed the data root** (cited: ADR-0065 decision 2) **and writes nothing below it.**
- **This amends ADR-0065 decision 2** — "An operation of either tool is called with four things" — to five, and its table of decision 5, which is not edited; the added rows are in bold:

| Direction | What | Kind of value | Source |
|---|---|---|---|
| to the operation | the request; the hw_profile of the call; the timing parameters; the output path | as ADR-0065 decision 2 | ADR-0065 decisions 2 and 5 |
| **to the operation** | **the log keeper** | **a thing the operation hands the log of its timing build to** | **this record** |
| from the operation | (A) the report and the figure; (B) the condition | as ADR-0065 decision 4 | ADR-0065 decisions 4 and 5 |
| **from the operation, through the keeper** | **the compiler's log of its timing build** | **text, at most once** | **this record** |

- The log is **not returned** to the caller and is in no result, no message and no line of `events.ndjson`: "The compiler's log is not returned" (cited: ADR-0061 decision 7), and an answer of the form (A) or (B) holds "no compiler's log" (cited: ADR-0065 decision 4). Those sentences stand.

### 6. The size bound

- **Left open.** The log is kept whole, as ADR-0078 decision 4 keeps the check's; what bounds it today is what bounds that one (cited there). Whether a bound is added, with what value and what mark of a cut, stays open as **the rest of ⑲ (다)**, to be judged with the first real kernels, alongside the bound of ⑱ (나) and without tying the two answers.

### 7. When the file is written, and what the call answers if it cannot be

- **The order inside ⑥ and ⑦** of ADR-0062 decision 6: the operation is called with the five things; it returns or raises; **if it handed over a log, the tool function writes the file** — whatever the operation returned or raised; then it establishes the form and judges, computes the verdict where a ceiling is stated, and appends the end line of ⑦. A raised request to end passes through as before (cited: ADR-0065 decision 7) and nothing is written: the log of that build is not kept, and the identity stays open.
- **The write** is that of ADR-0078 decision 7 (cited): the whole text first, a temporary file `<final name>.<token>.tmp` beside it, stable storage, a last step that gives the final name only if it does not exist; missing directories up to the attempt directory may be created. Which step commits the file is not decided (OD-17; OD-8 sub-question ⑪).
- **If the write fails** — the file system refuses it, or the name is already taken — **the step ends with a `failure` of the kind `build_log_unwritable`, in place of whatever the operation returned or raised**: no form is established, nothing is judged, no verdict is computed, no result is made, and the identity is ended. Its `spend` is the empty object as long as no record names an axis accounted through the log (cited: ADR-0062 decision 5). When the append of that end line fails, the call is `end_line_failed` (cited: ADR-0026 decision 3).
- **The sentence a caller may rely on.** *In the call of this identity the operation built, its compiler ended, and the log it handed over could not be written to its file by this call. What the operation answered is not returned, no result was made, and the identity is ended.* It says nothing about the attempt.
- **The name.** **`build_log_unwritable`, a kind of the run tools' contract with the spelling and the meaning of the kind of `correctness.check` (ADR-0078 decision 7), defined again by this contract** in the manner of ADR-0064 decision 4 and ADR-0065 decision 7: "no record forbids two contracts from defining the same value with the same meaning; a value is reserved only by a record of the frame" (cited: ADR-0064 decision 4). It satisfies [ADR-0101](ADR-0101-od8-failure-kind-change-and-step-values.md) decision 3: a *name* of ADR-0001 (20 characters), used by no earlier record of the run tools' contract, and no reserved kind. Checked on 2026-10-19 in `hilclaw/`, `tests/` and `ARCHITECTURE/`: it occurs only in ADR-0078 and ADR-0101, as the kind of `correctness.check`, and equals no other kind of the run tools' contract (`objective_not_stated`, `objective_not_covered`, `seed_not_drawn`, `operation_answer_invalid`, `op_signature_not_stated`, `op_signature_not_covered`, `n_max_not_stated`), no kind the frame reserves (`invalid_request`, `no_data_root`, `step_open`, `tool_crashed` and `bad_result` of ADR-0015 decisions 2 and 3; `no_backend` and `not_offered` of ADR-0016 decision 3; `run_file_missing`, `run_file_unreadable`, `run_file_invalid` and `run_file_unsupported` of ADR-0019 decision 2; `start_line_failed` and `end_line_failed` of ADR-0026 decision 3), no `step` value, no value of `condition` and no member name. **Three names were weighed**: (a) the same name — one word for one situation of one kind of file at two contracts; (b) another spelling such as `timing_build_log_unwritable` — no landed record says anything different of the case at the two contracts, and two names would have a caller learn which tool answered before reading the kind (the reasoning of ADR-0064 decision 4, cited); (c) a reserved kind — it would speak for `profiler.collect`, whose contract does not exist (the reasoning of ADR-0041 decision 4, as ADR-0064 decision 4 applies it). **The choice is (a)**, provisional in the respect of (c) as ADR-0065 decision 7 is.
- **It becomes a stored kind** (cited for the term: ADR-0101 decision 2) **of `sim_run_timing` and `board_run_timing`**, its meaning fixed by this record's acceptance and never changed (cited: ADR-0101 decision 3).
- **Only the tool function raises it**, and only as the `failure` of an end line; a backend that raises it does not answer the contract (cited: ADR-0016 decision 6). **This binds the slice of ⑲ (나) in one case**, as ADR-0065 decision 8 bound it for three kinds (cited for the manner): when the operation handed over a log and its write fails, the step is ended with `build_log_unwritable` whatever the operation raised — neither left open nor ended under the raised kind. What the tool function does with a tool failure an operation raises in every other case stays ⑲ (나).
- **The message** follows ADR-0078 decision 7 (cited): it may say whether the operation had returned or raised and the kind of the error; it shows no path, no text of an error and no byte of the log — and so nothing from which the seed could be recovered.
- **Why a failure and not the outcome.** An end line that held a result while the log is missing would break the presence rule of decision 2 without a trace, and no member of a result may say so (the reasoning of ADR-0078 decision 7, cited). **For `build_time_limit` and `build_exit_status` this answers with a tool failure a build O4 (the owner's) classes as a result**, and here the keeping it is weighed against is this record's own, not the owner's. This record reads O4 as the class of the build, not as what a call answers when the tool layer cannot record it: a failed end line already answers such a build with a tool failure (cited: ADR-0026 decision 3), and a failed write of the log is a failure of the same layer in the same call. The check answers the same case the same way (ADR-0078 decision 7), so a caller meets one answer at both tools. **The cost, stated**: an outcome the experiment established is lost, and timing that attempt at that point again is a further `execution`, "a new measurement" (cited: ADR-0062 decision 3). **This reading and weighing are this record's own**; if the owner reads O4 as holding in this case too — the result, with the log lost — that is an objection to this decision.
- **The same request afterwards** is answered from the end line and writes nothing (cited: ADR-0011 decision 3); **a death** after the write and before the end line leaves the file and an open identity, as ADR-0078 decision 7 says of the check's.

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 2 | Keep only the logs of builds that ended not ok | Loses the warnings of the builds that are timed and the evidence of S9; a missing file becomes ambiguous. |
| 2 | Keep none; the verification build's log stands for it (ADR-0107 decision 3) | Misses an attempt timed and never checked, a failure that arises only with the driver program, and a change of the settings source between calls (ADR-0107 Limit 3). |
| 3 | A name of its own form (for example `timing-build-log-<point>.txt`) | A second naming rule for one kind of file; the point alone does not tell `execution`s apart. |
| 3 | One file per attempt for all builds, appended | A file written by more than one call, against the write of ADR-0029 decisions 4 to 6, and a death mid-append would leave a mixed file. |
| 4 | Filter the log (paths, flags) | The file would no longer be what the compiler wrote (ADR-0078 Alternatives, point 5). |
| 5 | The operation writes it, or the log returned with (A) or (B) | The reasons of ADR-0078 Alternatives, point 6; the run tools' answers would change form, and S9's log could not travel with a raised tool failure. |
| 7 | Keep the outcome and drop the log silently | Breaks the presence rule without a trace; the check answers the case otherwise. |
| 7 | Another spelling, or a reserved kind | Decision 7. |
