## Context

- **The open point** (cited: ADR-0127 decision 8): a turn that ends before its round ends — "a death, a stop, a wait for the user, a gate, an error, a usage limit" — "is left open, and so is ADR-0121's own write of `"over"`, which ends no round"; `run.commit` "makes no commit inside a round (decision 4), and a record that answers the question may widen it". ADR-0142 decision 1 and its Boundaries name this record as a separate task.
- **The commit step today** (cited: ADR-0127 decisions 2 to 5): the Round-Manager calls `run.commit` (`run_id` → `committed`) as entry step 0 of every turn and right after the write that ends its round. A round end is owed when the working tree's `round` *W* is beyond that of `HEAD` *H* (or `HEAD` holds no `STATE.json` and *W* ≥ 1); the commit then holds every new or changed file below `runs/<run_id>/`, the case files of rounds *H* to *W* − 1, and, by ADR-0134 decision 7, each key record file that `HEAD` does not hold. Nothing owed: no commit.
- **What ends a turn now** (code, as observation only — `orchestration/round-manager.md`), among others: an invalid run id in the prompt; a failed `run.commit` at entry step 0; entry steps 2 to 7 (no fresh directory, a failed read, `"over"`, another `run_status`, a failed or budget-less `instance.read`, ADR-0121's own `"over"` write, a failed `state.write`); "The stop" after round step 2, 3 or 4 in round 0 and after step 1 in other rounds ("no `round.end` and no `run.commit`"); and the closing steps, which no turn reaches yet. Every first-case turn today ends at a stop that ends no round, so no turn of a run commits anything (ADR-0142 decision 1), until `board.run` is registered (ADR-0142 slice 2; HQ-0021, unanswered).
- **The case file** (cited: ADR-0133 decision 5): in a round ≥ 1, `case.write` comes right before the write that ends the round, so a death between the two leaves `case-<run_id>-<W>.json` uncommitted in the key directory while `STATE.json` names round *W*.

## Decision

A sentence is **cited** when a source is named with it. Every other sentence is **this record's own**.

### 1. Scope

- **The runs of ADR-0120 decision 1** and their data root, as ADR-0127 decision 1 has them. Every other run is outside; nothing here is required or allowed of it.
- **The commits answered**: every commit `run.commit` makes for such a run — a round end's (ADR-0127, unchanged where not revised here) and, new, **a commit that ends no round**: one made while the working tree's `round` is that of `HEAD`, or while `HEAD` holds no `STATE.json` for the run and the working tree holds none or one with `round` 0.

### 2. (a) Which turn ends commit, and who commits

- **The Round-Manager calls `run.commit` as the last act before every end of its session that follows a successful entry step 0** — every entry step that ends the session (steps 2 to 7, ADR-0121's own `"over"` write included), every stop, a failed `round.end` (revising ADR-0135 decision 5) and the closing `run.commit` itself (ADR-0127 decision 3, which is that call). It writes nothing into the run after the call. **Why**: O1 has "such a turn's end" commit; a live session can make that commit only before it ends, and one rule for every end leaves the model nothing to judge, at the price of a call that finds nothing to commit when nothing was written since step 0 (decision 3).
- **Not called**: after a prompt with no valid run id (ADR-0123 decision 4: no tool request names a run); after a failed `run.commit` — at entry step 0 or at the end — the Round-Manager reports the kind in one line and ends without calling it again (ADR-0127 decision 5, unchanged). **Why**: a second call at once is a retry policy, OD-17's; what is uncommitted stays for the next turn's entry. When the call fails at entry step 0, the session ends also when what was owed was only a commit that ends no round (this record's own): a round gone on with would mix the dead turn's work and this turn's in one later commit, and one rule for every failure of step 0 leaves the model nothing to judge.
- **A turn that dies** — a crash, a kill, a usage limit or an error that ends the process before the model acts (ADR-0118 decision 2 (ii)) — commits nothing; **the next turn's entry step 0 commits what it left** (O1), by the widened rule of decision 3. A wait for the user or a gate that ends the session (ADR-0118 decision 2 (ii)) is a live end, and the definition that adds it calls `run.commit` there by this decision.
- **W1 (C2 of ADR-0127) under both readings.** Every commit is still the Round-Manager's, through `run.commit` only: reading (i) has the one committer; reading (ii) has no sub-agent commit within a round. The turn loop and `hilclaw.turn_start` still make none (ADR-0127 decision 2); step 1 only reads (decision 6).

### 3. (b) What `run.commit` takes in when no round end is owed

- **A commit is owed** when a round end is owed (ADR-0127 decision 4, unchanged), or when, with none owed, a file below `runs/<run_id>/` that the commit would take in is new or changed against `HEAD`, or a file `HEAD` holds below `runs/<run_id>/` is missing from the working tree (which the commit then refuses, below). The key record files alone make no commit owed, and neither does a torn tail alone: `events.ndjson` is compared with `HEAD` up to its last line feed. **Why**: O1 names "what the run directory then holds"; the key record files are shared by every run of the key (ADR-0134 decision 7), so they join a commit that is made and do not start one.
- **With no round end owed and a commit owed**, in this order: (1) a torn tail of `runs/<run_id>/events.ndjson` is removed, exactly those bytes (cited: ADR-0006 decision 6 — "a file is committed only when it is empty or ends with a line feed, and the step that commits establishes this by the same removal": it binds every commit); (2) one commit holds, against `HEAD`, every new or changed file below `runs/<run_id>/`, and each key record file of ADR-0134 decision 7 that `HEAD` does not hold (that decision, unchanged); (3) `committed` true. A removed tail stays removed even if the commit is then not made (it was no line — ADR-0006 decision 6).
- **No case file is taken into a commit that ends no round** (O2). The case files a commit takes are those of the rounds *H* to *W* − 1 (ADR-0127 decision 4), and that range is empty when no round end is owed, so `case-<run_id>-<W>.json` of the round in progress stays in the working tree and joins the commit of its round's end (cited: ADR-0133 decision 5, the round's end "whose commit takes the case in because it exists then"). **Why**: O2 keeps a round's promotion in the commit of the round it promotes (#5 A-1).
- **Unchanged from ADR-0127 decision 4**: a `.tmp` name, an ignored path and anything below `blobs/` are never taken in; the changes of no other path go in, and whatever else the working tree or the index holds stays as it is; no content is inspected beyond the line-feed check of `events.ndjson` (first bullet).
- **`commit_refused`**: the conditions ADR-0127 decision 4 checks at every call stay checked at every call. Of the others, a file `HEAD` holds below `runs/<run_id>/` that is missing from the working tree, and an `events.ndjson` that is not a regular file, are now checked **whenever a commit is owed**, round end or not, since a commit that ends no round would hold the one or read the other; the key-directory condition stays checked only when a round end from round 1 is owed (ADR-0134 decision 7 unchanged: no key, no record file, no refusal). **Why**: the same states the rules do not produce, now met by more commits.
- **So the call still repeats without effect**: a second call with nothing written in between finds nothing owed.

### 4. (c) The tool's surface

- **The request (`run_id`), the result (`committed`, whether a commit was made) and the failure kinds** (`invalid_request`, `no_data_root`, `no_repository`, `commit_refused`, `commit_not_made`) **stay as ADR-0127 decision 4 has them**; the MCP name stays `mcp__hilclaw__run_commit`. Only the cases in which `committed` is true widen. **Why**: the caller does the same at every call — go on or end — whatever the commit held.
- **The commit message** stays unfixed (ADR-0127 decision 4): nothing reads it. The present `MESSAGE` of `hilclaw/run_commit.py` ("Commit an owed round end (run.commit)") becomes inexact, and slice (1) may change it; a message, like every name of the tool, is of the tool layer, not of the data plane.

### 5. (d) The first `STATE.json` and a fresh run

- **A round-0 turn that writes the first `STATE.json` and then stops commits it at that stop**, with `instance.json`, `events.ndjson` and every other file below the run directory as they then are, and the key record files `key.store` wrote (decisions 2 and 3; revising ADR-0127 decision 3's "no commit of its own"). `HEAD` then holds a `STATE.json` with `round` 0, and the end of round 0 is owed as *W* 1 > *H* 0 (ADR-0127 decision 4, unchanged).
- **Entry step 0 on a fresh run directory** (cited: ADR-0120 decision 4 — `instance.json` and no other file of the tree) commits `instance.json` if `HEAD` does not hold it: it lies below the run directory and differs from `HEAD`. The same rule commits the files of a directory that holds no `STATE.json` and is not fresh; what such a directory means stays open (⑩, ADR-0120 decision 4), and step 1 starts no turn on it (ADR-0122 decision 4). **Why** (this record's own; O1 names a turn's work, and this file is the start function's): one rule at every call; the commit changes no file of the working tree, so the tests of P1 (ADR-0120 decision 4) and of "as it found it" (ADR-0122 decision 3) read the same files as before.

### 6. (e) Step 1 of the turn loop and the self-check

- **Owed P2 is P2 with a commit owed** (decision 3), not only a round end owed (revising ADR-0127 decision 6). The case it adds: a death after ADR-0121's own `"over"` write and before the call that follows it, which leaves `"over"` uncommitted with *W* = *H*. **Such a P2 starts a further turn** under the rules ADR-0127 decision 6 gives owed P2 — before the first turn of a start and after a turn with exit status 0 that was no unchanged turn; after a turn whose exit status is not 0 the start stops as in P4 (ADR-0122 decision 2), and the next start's first step 1 finds it. Its entry step 0 commits, and entry step 4 ends the session on `"over"`. **Why**: O1 has the next turn's entry commit what a dead turn left, and in P2 no next turn runs unless step 1 starts one.
- **The self-check** runs before that start's first turn, as ADR-0125 decision 2 as widened by ADR-0127 decision 6 has it for owed P2: it is a turn due. After a turn that exited with 0 and began in owed P2, owed P2 again counts as "as it found it" (ADR-0127 decision 6), so such a run gets at most one turn per start.
- **P3 and the open states of ADR-0122 decision 4** are unchanged: no turn runs, and a commit owed there stays owed until a record answers that state (ADR-0127 decision 6). **Why**: step 1 starts no turn there for reasons a commit does not touch (ADR-0122 decision 4).
- **"As it found it" (ADR-0122 decision 3) is not affected**: it reads `round` of P4 and the files of P1, and a commit that ends no round changes neither — only a torn tail of `events.ndjson`, which step 1 does not read, may be removed.
- **If the owed rule cannot be applied in P2**, step 1 answers as ADR-0127 decision 6 says, with the conditions of decision 3 here. Nothing of (e) is left open.

### 7. (f) What is not promised

- Everything ADR-0127 decision 7 does not promise stays unpromised (cited): the loss of the machine, the disk or the working tree before a commit; any push, remote or unpushed count; what one repository cannot show; two writers, two loops or a person's `git` at once.
- **What a dead turn left until the next entry**: a machine loss before that entry loses it (cited: #5 A-3, "NFR-1의 보장 범위는 MVP에서 프로세스 사망·compaction까지"). A run that is never started again keeps it uncommitted.
- **A writer still at work when the call is made**: the call assumes the session's own writes are done — it waits for the report of each delegation (`orchestration/round-manager.md`, round steps 2 to 4; ADR-0142 item (xlv)). A process the session left running that appends after the removal of a torn tail is two writers (ADR-0127 decision 7).
- **That every turn gets exactly one commit**: a turn that writes nothing makes none, and a turn may make two — its entry's and its end's (after a death, or on a fresh run directory, decision 5).

Step 1: P1 → P4, progress |
| Round-0 turn that stops after step 4 (board standing, `board.run` not registered) | The stop calls `run.commit`: the turn's spec, kernel, check results and events lines below the run directory are committed; round 0 is not ended, *W* = *H* = 0 |
| A turn dies inside round 3 | No commit by it. The next turn's entry step 0: no round end owed, a commit owed; the torn tail, if any, is removed and what the dead turn left below the run directory is committed; the turn goes on with round 3 |
| A round-3 turn dies after `case.write` and before `round.end` | The next entry commits the run directory's changes; `case-<run_id>-0003.json` is not taken in (O2) and stays in the working tree; the round's end commit takes it in (ADR-0133 decision 5) |
| `round.end` fails with any kind (ADR-0135 decisions 2 and 5) | The Round-Manager reports the kind, calls `run.commit` (a commit that ends no round; after `round_not_current`, possibly a round end's), then ends |
| ADR-0121's own `"over"` write (entry step 6) | Then `run.commit` commits `STATE.json` with `"over"`; the session ends. Step 1: P2 with nothing owed, "run over" |
| The same, with a death before that call | Exit status not 0: owed P2 stops the start as P4 does. Next start: owed P2, the self-check, one turn; entry step 0 commits `"over"`; entry step 4 ends; step 1: "run over" |

  - **(xlvii)** A live Round-Manager calls `run.commit` as its last act before every end of its session that follows a successful entry step 0 — a stop, an entry step that ends the session, a failed `round.end` — and not again after a failed call of it.
- **The cost, plainly.** One more tool call at every end of a turn, most of them committing a turn's partial work: the history of a run grows by one commit per turn that writes, and a round that takes several turns gets several commits (O1). A dead turn's work waits for the next start, which an unattended run may not get until someone starts it (ADR-0122 decision 2). An over run whose `"over"` commit a death left owed costs a start with the self-check's session and one turn session; so does a person's change below an over run's directory, which that turn commits as part of "what the run directory then holds". A missing tracked file, a non-regular `events.ndjson` or a stale `git` lock (`commit_not_made`) now fails entry step 0 even inside a round, whenever a commit is owed, so such a run begins no round until someone repairs it; before, it failed only where a round end was owed. A commit that ends no round may hold a file a writer put into the run directory against ADR-0004 decision 7, earlier than before (ADR-0127 Consequences).
