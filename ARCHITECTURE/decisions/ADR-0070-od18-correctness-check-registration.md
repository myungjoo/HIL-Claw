## Decision

A sentence is **cited** when a record and its decision, or a requirement, is named with it; it then says what that source says and adds nothing. Every other sentence is **this record's own** - among them the choice to register now, the content of the backend table, the reading of FR-10 in decision 3, the choice of the source of seeds, that `default_registry` keeps its parameter list, and every weighing.

### 1. Scope and terms

- This record is about **the registry that `default_registry` builds** - the registry both fronts serve - and fixes four points for `correctness.check` in it: whether it is registered now (decision 2); the backend table its tool function is bound to (decision 3); its source of seeds and its predicate "covered" (decision 4); and its tool definition and what follows for `default_registry` (decision 5).
- The terms of ADR-0010, ADR-0015 (tool definition, reserved kind), ADR-0016 (backend, operation, backend table, mock backend, script; the moments ① to ⑦, decision 2) and ADR-0044 (default script, default mock) are used unchanged. **The default table**: the backend table bound to the tool function of `correctness.check` in a registry that `default_registry` builds.
- **It says nothing of the registration of other tools**: not of `sim.run`, `board.run` or `profiler.collect`, and `blob.push` and `blob.fetch` are unchanged.

### 2. `correctness.check` is registered now, before the `cpu_standin` operation of the tool exists

- **The tool is registered in the registry that `default_registry` builds now, with the default table of decision 3.** It does not wait for the operation of `cpu_standin` for this tool.
- **The list of ADR-0021 decision 1 is complete.** That decision named what "a second record must add at least" before the tool can be registered (cited). Each item now has a record (all cited): journaled, `step` values and `execution` (ADR-0040 decisions 2 and 3); the execution point and which HW tools `cpu_standin` offers (ADR-0040 decision 4, ADR-0038 decision 2); the request, schema and description (ADR-0069); `draws` (ADR-0046), the dimensions (ADR-0041), the kernel of the attempt (ADR-0056 decision 3), flags and time limits ("Every setting is the backend's own", ADR-0060 decision 3); the result (ADR-0042) and the backend kinds - a kind becomes one when a record of this contract names it (ADR-0047 decision 5), as ADR-0056 and ADR-0060 did; the spend (ADR-0040 decision 6: "the empty object" as long as no axis is accounted through the log); the operation and default script of the mock (ADR-0044). What is missing is an operation of one backend, not a part of the contract.
- **Three answers were weighed.**
  - **(a) Register now, with a default table whose one entry offering the tool is the mock** (decision 3). Layer 1 and the conformance tests of P1-1 can call the tool through both fronts at once, which is why the mock exists: the alternative "The mock exists only in registries a test builds" was rejected because "layer 1 could never be run against it" (cited: ADR-0016 Alternatives), and the default script was chosen so that "the layer above ... can, as far as this tool goes, be carried through against the mock" (cited: ADR-0044 decision 3 (a)). A call about a `cpu_standin` run is answered `no_backend` until the entry exists (decision 3).
  - **(b) Wait until the operation of `cpu_standin` for this tool exists.** That operation waits for setting values (⑱ (라)), the two time limits (OD-14), a container design and the path of the compiler's log (⑱ (나)) (cited: ADR-0060 Consequences). The tool would stay unreachable through either front for all of that time, for runs at the mock too, where nothing of it is needed.
  - **(c) Register now with a `cpu_standin` entry whose operation of this tool raises a tool failure** until the real one exists. No record names a backend kind for "not written yet"; without one, the kind it raised is outside the contract and the call ends with `operation_failure_invalid`, or with `end_line_failed` when the append of its end line fails (cited: ADR-0047 decision 5). Either way it would start a step and end the identity with a `failure` (or, where that end line cannot be appended, leave it open or ended) for a fault of registration - what ADR-0016 decision 2 placed before the start line to avoid (cited, decision 3).
- **The choice is (a).** It replaces the sentences of ADR-0060 Consequences and ADR-0056 Consequences that tie the registration to the operation of `cpu_standin` (Status); what they say of that operation itself stands. ADR-0056 and ADR-0060 are not edited.
- **What need not be answered first** (each this record's own judgement, with the precedent where one applies).
  - **Sub-question ⑤** (what checks that a schema and a function agree; what Claude Code does with `inputSchema`): `blob.push` and `blob.fetch` were given a schema and registered while it was open, with the rule that a keyword not accepted is removed and the description says what the function refuses beyond the schema (cited: ADR-0039 decision 3 for the schema and the rule, and its Consequences for "their registration in `hilclaw.tools.default_registry`"); ADR-0069 decision 4 took that rule over (cited).
  - **Sub-question ①** (whether the MCP server of the standard library works in a live Claude Code session): the two blob tools are served by the MCP front while ① is open (observation of `main`; OpenDecisionProposals OD-18 ①, "①은 관찰이 생길 때까지 미결 그대로다"). It is a runtime acceptance matter (CLAUDE.md, DRIVER D16), and this record claims nothing about what a live session does with the tool.
  - **The spend beyond ADR-0040 decision 6**: a record that names an axis accounted through the log changes the end line of a registered tool from then on; end lines written before it hold the empty `spend` that was right when they were written (cited for the empty `spend`: ADR-0040 decision 6).
  - **Sub-question ⑱**: its parts (가) to (마) concern what reaches the operation and the compiler it uses, the compiler's log, the situations an isolated environment adds, the backend's own flags and environment, and errors of `clang_build.build` and `local_run.run` (cited: OpenDecisionProposals OD-18 ⑱) - each a matter of a real operation; the mock reads no setting and builds nothing (cited: ADR-0044 decision 3, "nothing is built or started"). One part reaches the request: if (가) is answered with a member a later record gives the request, that record extends the list and the schema, "and that is a change of this contract" (cited: ADR-0069 decision 2), of a registered tool from then on, as for the spend above.
  - **Sub-questions ⑧ and ⑭** stay open as they are; neither concerns whether a registry holds the tool (decision 3, Limits).

### 3. The default table

- **The default table holds exactly one entry, the mock backend under its reserved name, and that entry offers exactly `correctness.check`, whose operation is the mock's operation of this tool bound to the default script of ADR-0044.** "The mock of the default registry offers every HW tool of that registry" (cited: ADR-0016 decision 5 (d)); in this registry that tool is `correctness.check` alone.
- **It offers no operation of a tool the registry does not hold.** An operation of `sim.run` or `board.run` there could be reached by no tool function. When the default registry holds the mock with those operations is left open by ADR-0066 (cited: its Boundaries), and this record leaves it to the run tools' records; `profiler.collect` has no contract.
- **It holds no `cpu_standin` entry until the operation of `cpu_standin` for this tool exists in the source.** A call about a run whose hw_profile names `cpu_standin` is then answered in ④ with the reserved kind `no_backend`: "The backend table has no entry for the `accelerator` of the hw_profile of the call; nothing was consumed, no line appended" (cited: ADR-0016 decision 3), before any `op_signature_*`, `draws_not_stated` or `tolerance_not_stated` answer (cited for the order: ADR-0048 decision 10, row ④). No seed is drawn and no line is written, and "the same request can be repeated once the table has the entry" (cited: ADR-0016 Walk-through).
- **Weighed against an entry that offers nothing** (`not_offered`). `no_backend` says that the table has no backend for the `accelerator`; `not_offered` that a backend is there and does not offer the tool, after which "the tools that backend does offer can" work (cited: ADR-0016 decision 3). A `cpu_standin` entry that offers nothing would state of `cpu_standin` the opposite of ADR-0038 decision 2 and would point a caller to tools no entry offers. With no entry, the table says only what is so: the source has no `cpu_standin` backend yet. **The choice is no entry.** If a later record or task binds a `cpu_standin` entry to the default table for other tools before its operation of this tool exists, a call of this tool about a `cpu_standin` run is `not_offered` by ADR-0016 decision 3 (cited); this record neither causes nor forbids that.
- **How this reads ADR-0038 decision 2 and why it is no fault of the frame.** ADR-0038 decision 2 says what the `cpu_standin` backend offers; "The backend table maps a name to a backend" and is built "from the source alone" (cited: ADR-0016 decision 2), and no `cpu_standin` backend exists in the source. Both kinds lie before the start line because "a missing backend is a fault of registration, like `no_data_root` a fault of configuration" (cited: ADR-0016 decision 2), and that is the situation here; the identity is not used up.
- **How this reads FR-10.** FR-10 says that the tool contract always has a mock backend - "a mock backend that the package always has", as ADR-0016 Context reads it - and that the first registered backend is `cpu_standin` (cited). The default table holds no backend of a target at all, so `cpu_standin` stays the first one that will be registered; the mock is the entry the package always has (the reading of ADR-0016 decision 5 (a), cited above).
- **What layer 1 gets for a `cpu_standin` run in the meantime**: `no_backend` for every check, so no check of such a run is made through this registry. What layer 1 does after that answer is not decided (FR-1, OD-10, PLAN P2-1).
- **A run whose hw_profile names another accelerator**, neither `cpu_standin` nor the mock, is answered `no_backend` in the same way. This follows from the frame and the table and **does not answer the part of sub-question ⑩** about such a run (of which ADR-0041 decision 5 says "this record says nothing of it, covered op_signature or not (#5 B-7)", cited): this record reads that part as the question of what the contract answers where a table has an entry for that `accelerator` offering the tool.
- **How the "one script fixed in the source" is put together** with the per-tool operation of `hilclaw/mock_check.py` is the code task's: "whether one script callable serves every tool with one signature or is asked differently for this tool; how the default script is laid out in the source and how a mock backend is built so that its operation of this tool takes a third thing" (cited: ADR-0044 decision 2). An observation: `hilclaw.mock_backend.backend` builds operations called with two things and `hilclaw.check_operation.ask`, through which `hilclaw.check_tool` calls an operation, calls it with four, so the default table cannot be built with `mock_backend.backend` for this tool as the code stands.
- **The table is built in the source, when a registry is built**, with no option, environment variable or plugin that adds to it (cited: ADR-0016 decision 2), and nobody names a backend - not a request, not the configuration or the environment of the front process (cited: ADR-0016 decision 4) - nor tells the mock what to produce by a member of the request or the environment of the front process (cited: ADR-0016 Alternatives, rows of point 5).

### 4. The source of seeds and the predicate "covered"

- **The source of seeds of the default registry is the random generator of the operating system** - the one source the package offers today (observation: `hilclaw.harness.seed_source.system`, uniform over 0 to 2^64 - 1). It is fixed in the source: no request, option or variable of the front process sets it (cited: ADR-0021 decision 3).
- **The property it relies on** is the one of ADR-0021 decision 3 and nothing more: output that nobody can predict or influence before the draw, not derived from the request, the identity, a file, a clock, a counter or an earlier call, over the whole range of seeds the harness accepts (cited). This record reads the operating system's generator as having that property for every party that can call the tool or write an attempt; it fixes no algorithm, and how hard its output is to predict is what the platform gives (observation of the `system` docstring). "A source that draws badly ... is not detected by anything here" (cited: ADR-0021 Limits).
- **Weighed against** a source a variable or an option of the front process chooses (excluded by ADR-0021 decision 3, cited) and against a pseudo-random generator seeded in the source (its output follows from the source, which ADR-0021 decision 3 excludes, cited). **The choice is the operating system's generator.**
- **The predicate "covered" of the default registry is the one of ADR-0041 decision 5**: an op_signature with `kind` `gemm`, `dtype` `fp32`, `layout` `row_major` and each of `shape.m`, `shape.k` and `shape.n` at least 1 (cited). It is fixed in the source; no option or variable chooses another. Weighed against a predicate per backend: the judging is "The tool function's part, the same code for every backend" (cited: ADR-0021 decision 2), and "covered" says for which records this contract's judging is defined (ADR-0041 decision 5); a backend that chose its own would choose the judging.
- **A test binds its own** source of seeds, predicate, table or script by building a registry of its own from the same parts, as "a test builds a registry bound to a source of its own" for the data root (cited: ADR-0015 decision 3) and "a registry whose mock is bound to the script it needs" (cited: ADR-0016 decision 5 (c)). Both fronts take such a registry (observation). A test that binds a source of seeds so can "bind a source that fails or that names no seed" (cited: ADR-0048 decision 8).

### 5. The tool definition, and the parameter list of `default_registry`

- **The definition is: the name `correctness.check`; the tool function of decisions 3 and 4, bound to the data-root source `default_registry` is given; the input schema of ADR-0069 decision 4; and a description that tells at least what ADR-0069 decision 5 requires.** "Its text is the code task's" (cited: ADR-0069 decision 5), and so is the module that holds it.
- **Both fronts then list three tools**: `blob.fetch`, `blob.push` and `correctness.check`, the last as `mcp__hilclaw__correctness_check` through the MCP front (cited for the name: ADR-0010 decision 4).
- **`default_registry` keeps its one parameter, the data-root source.** The table, the source of seeds and the predicate are built or named in its body. Weighed against keyword parameters with defaults for the table, the source of seeds and the predicate (the case ADR-0016 Consequences foresaw, "the parameter list if the table is built there", cited): a registry built with other values would not be the default registry, and a test already builds its own (decision 4). **The choice is one parameter.**

### 6. Limits

- **No check of a `cpu_standin` run through the default registry** until its operation exists, and the round loop of FR-1 cannot be carried out at `cpu_standin` through this tool until then.
- **A check at the default mock does not fail** where the default script can compute a report and the tolerance admits it (cited: ADR-0044 decision 3); fault injection in a live session is sub-question ⑧. A test reaches the other outcomes with its own script.
- **Two processes, two tables**: "an MCP server runs the table of the source it loaded at its start" (cited: ADR-0016 Limits). Applied here (this record's own): an MCP server started before the source holds a `cpu_standin` entry keeps answering `no_backend` until it is started again.
- **What a live Claude Code session does with the tool** - its listing, its schema, its arguments - is not verified (sub-questions ① and ⑤); the limits of ADR-0069 decision 6 stand.
- The limits of ADR-0016 decision 6 and ADR-0021 Limits stand unchanged.
