### 1. Scope and terms

- **The calls**: a call of `correctness.check`, `sim.run` or `board.run` at a run of ADR-0144 decision 1, whose operation of `cpu_standin` carries out its builds and processes in containers as ADR-0144 decisions 2 to 6 and ADR-0145 decision 3 say. **A build container**: that of the verification build, of the timing build or of the waiter's build. **A process container**: that of the verification process or of the timing process (whose program is the waiter, ADR-0145 decision 3).
- **Every situation is found by the operation in ⑥, after the start line**, as ADR-0056 decision 5 and ADR-0068 decision 2 say of S1 to S10 (cited), because the image, the copies and the containers are the operation's. The tool function is unchanged: a backend kind the operation raises is ended as ADR-0047 decision 4 and ADR-0068 decision 4 say, a value of (B) becomes a broken result (cited: ADR-0043 decision 4; ADR-0065 decision 4), and an error it lets pass is answered `operation_answer_invalid` (cited: ADR-0045 decisions 4 and 5; ADR-0065 decision 7).
- **The S1 to S10 of ADR-0056 decision 5 stay the list** (cited), with ADR-0068 decision 2's readings for the timing build; this record adds no row S11 and places each situation a container adds in one of them, as ADR-0060 decision 4 placed the errors of the host code ("What the operation observes decides the row", cited). **Through a container, the compiler's start is the start of a build container, and the executable's start is the start of a process container** (this record's reading of ADR-0144 decision 3, "The operation starts one program on the host per build or process: the container runtime's command-line program").

- **Why C1 to C5 are S6 or S10 and not `settings_refused` (S4), a new kind, or `coder.run`'s `no_container_runtime`. Four answers were weighed.**
  - **(a) S6 for a build, S10 for a process.** The compiler of these runs "is the image's `clang`" and the program the operation starts for a build is the client, which starts the container, which starts `clang` (cited: ADR-0144 decisions 3 and 5). With no image named, a refused one, no client, no numeric user, or a client that reports its own failure (125 to 127), "the compiler is not found, or its process cannot be started" (cited: ADR-0056 decision 5, S6) holds of that compiler as the host code's `CompilerNotFoundError` held it of a host compiler; likewise S10, "The executable cannot be started: … refused by the system", for a process container. No process of the kernel was started, so class (i) is true of them, and a later call on a machine set right can verify the attempt.
  - **(b) S4 `settings_refused`**, reading the image as a setting the backend holds. It fits C2's refused value in words, but ADR-0110 puts `settings_refused` in class (ii), whose block "is permanent" (cited): a variable unset for an hour would leave every attempt checked in that hour unverifiable at that point for good, the outcome ADR-0110 (c⁗) refused for "one missing compiler" (cited). Not taken.
  - **(c) A new kind** (for example `no_container_image`): a new value of `error.kind` is a data-plane change (cited: ADR-0101 Consequences; CLAUDE.md A-13) that needs the owner, and S6 and S10 already mean these facts for the compiler and the executable of these runs. Not taken; no situation of this record needs one (decision 6).
  - **(d) `no_container_runtime` of `coder.run`**, for C3 and C5. Its spelling and meaning are already in the data plane, so taking it would not be a new value; but it would be a ninth backend kind of two contracts, a new stored kind of four `step` values (cited: ADR-0101 decision 2), and a kind ADR-0110 would place in (ii) unless placed in (i). Its text also "also mean[s] "the start is not built"" (cited: ADR-0141 decision 3), and through the client a missing daemon (125) cannot be told from a missing image (125) by the status (E7), so it would mean less here than its name. Not taken; a record of OD-8 ㉝ (가) that asks the user to install a runtime may reopen it with the code that tells the two apart.
  - **The choice is (a).** Its cost, stated: a caller cannot tell a machine without Docker from one without an image, nor either from a host compiler that is missing, by the kind; the message may say which case it was (decision 5). S6 and S10 "may follow from what the attempt's source made" is ADR-0060's cost for S10 (cited), which C5's 126 or 127 for a build does not reach: the build runs no code of the attempt (decision 3).
- **Why C12 is S5 and C13 is S3.** S5 is "a file of the compiled set is no longer a regular file when the build is called, or the verification program is missing from the installation" (cited: ADR-0056 decision 5), and ADR-0086 decision 3 reads it "as covering a file the build's test could not establish as one" (cited); the copy is the step that now establishes the input's bytes, so a kernel file or a harness program that the copy cannot establish as a regular file and read is S5 (this record's reading, the same reading as ADR-0086's for the step that now holds it). S3 is "The build directory cannot be made or written" (cited); a sub-directory or a copy that cannot be made in it is that. Both are class (i): no container was started.
- **Why C14 stays open.** `run_in_container` raises the `OSError` of its `os.stat` before the start and passes on the `OSError` of the client's start in one class, with no attribute that tells them apart (observation). An operation may still place it by a step of its own (cited for the manner: ADR-0060 decision 4) — for example its own test of the build directory just before the call — and then it is not this row.

### 3. The client's statuses 125 to 127: the container runtime's for a build, the program's for a process

- **For a build container, 125, 126 and 127 are the container runtime's (C5); for a process container they are the program's (C8).** The rule is by what can write the status: **no code of the attempt runs in a build container** — the compiler reads the copied source and the build runs nothing the attempt wrote (cited: ADR-0144 decision 2, Q1 and Q3) — **while the kernel's code runs in the process it measures or checks** and can end that process with any status and write the client's words (E7) on its own standard error (cited: ADR-0144 decision 3).
- **What the reading lets a kernel do.** In a process container: nothing new. A kernel that ends its process with 125 to 127 gets the broken result it would get for any non-zero status, `exit_status` (cited: ADR-0042 decision 3, "a non-zero status or a signal"); it cannot turn its fail or broken result into a tool failure, and so it cannot reopen what ADR-0110 decision 3 closed ("a kernel that crashes or hangs on some inputs could be re-checked until it passes", cited). In a build container: what the attempt controls is the source text the image's `clang` reads. Should a source make `clang` end with 125 to 127 (this record knows of no way; runtime acceptance item (lxxvi)), the answer would be `compiler_unavailable`, class (i): the attempt stays undetermined at that point and is never verified by it, and "The two build conditions involve no drawn input" (cited: ADR-0110 decision 3), so a further check builds the same bytes and meets the same status. **It can hide a compile failure as an unavailable compiler; it cannot make an attempt verified.** This is acceptable under FR-9's floor because the floor needs a counting pass (cited: ADR-0110 decision 3, "verified").
- **What the reading costs.** A failure of the container runtime at the start of a process container — the daemon gone, the image removed, the container not created between a build and its process, or the executable not invokable inside (126, 127) — gives a broken result `exit_status`, which counts: the check's attempt is "not verified" at that point for good (cited: ADR-0110 decision 3). ADR-0110 already takes this cost for "a defect of the harness, or an environment that slows a build past its limit" (cited) and weighs it as "the lesser one". The window is narrow: the build container of the same call was started by the same client a moment before. A machine whose runtime fails every start fails at the build first, with C3 or C5, in class (i).
- **Weighed and not taken.** (a) **Every 125 to 127 as the program's**, builds included: a machine without a reachable daemon or with no image would give every attempt `build_exit_status`, a broken result that counts, and every attempt it touched would be not verified for nothing. (b) **Every 125 to 127 as the container runtime's**, processes included: a kernel that fails could end its process with 126 and leave its attempt undetermined, then be checked again until it passes — the hole ADR-0110 closed. (c) **The client's standard error read to tell them apart**: a kernel can write the same words (cited: ADR-0144 decision 3). (d) **Another means** — a container identity file written by the client, an inspection of the container after its end, or a waiter for the verification process: none is in the landed slices, each is a design of OD-14 ① and OD-16 that this record does not make; **the reading above holds until a record adopts one**, and such a record revisits C8.
- **A status the slice hands back that is not exactly an `int`** (not given by `local_run`) is not placed (the module's own choice, as `check_build` makes it, decision 7).

### 4. The timing process: the waiter's line before the status

- **The operation looks for the waiter's line in the client's standard output first** (cited: ADR-0145 decision 6, "a code slice does not read such a status as the run's before it has looked for the waiter's line"), unless the container passed its time limit (C10, `time_limit`).
- **With a waiter's line**: the child was started and waited for (cited: ADR-0145 decision 3, W6, "a waiter's line therefore always means that its child was started and waited for"). Status 0: the operation goes on with the report before the line and the figure (cited: ADR-0145 decision 3, "What the operation takes"). Any other status, 125 to 127 included: `exit_status`, because a waiter that wrote its line ends non-zero only for a child that did not end by itself with 0 (cited: W6), and a status of the client after the program's end is the program's (E7).
- **With no waiter's line and a non-zero status**: `exit_status`. This takes in the waiter's own failures — W0's refusal outside process 1, W2's start or W3's wait failing — and the client's 125 to 127, which no line tells from a process ended by the operating system's out-of-memory handling or by a way of the kernel's not known (cited: ADR-0145 decision 5). **A tool failure here would let a kernel that makes its waiter die turn its own broken result into one**, which ADR-0145 decision 5 says the answer "must not" do (cited). The cost, stated: on a machine whose daemon puts an init before the waiter, every timing run is broken (cited for the machine: ADR-0145 decision 3, "on such a machine W0 refuses every timing call"); a call of the run tools gives a broken result, not a tool failure, and that is read only by what a comparison does with a broken run (ADR-0140, not changed here).
- **With no waiter's line and status 0: open.** The waiter ends with 0 only after W5 wrote its line (cited: W6), and after W4 no process of the kernel is left to write (cited: ADR-0145 decision 5), so this stream means a client that did not hand on the waiter's last line, which ADR-0145's item (liii) expects never to happen. This record knows of no way for a kernel to cause it and does not place it: answered as `exit_status`, the condition would say "a non-zero status" of a run whose status was 0; read as a report without a figure, a kernel that could cause it would keep its memory out of `memory_bytes`. **It stays open under ⑲ (나)**; let pass, it is answered `operation_answer_invalid` (the landed rule, cited: ADR-0065 decision 7).
- **The verification process has no waiter** (cited: ADR-0145 decision 3 starts the waiter only in a timing process container), so for the check C8 is read on the status alone.

### 5. ADR-0096 holds for the build directory given to a container

- **ADR-0096 decision 2 holds as written** (cited: "A failed removal, in whole or in part, changes no answer"; "what is left stays"), for the build directory that is the one host path of the containers of a call (cited: ADR-0144 Q2, Q4). It is a host directory given to a container as its one mount, which ADR-0144 Consequences already read as making ADR-0096 decision 2 hold (cited); this record confirms the reading for the situations of decision 2: **a forced removal of a container that fails, times out, raises or finds nothing changes no answer either** (C10). The reasons of ADR-0096 decision 2 hold unchanged: what the attempt's code started could otherwise steer the answer (cited).
- **Where the forced removal of a container is not shown to have succeeded — its `Removal` holds no status 0 within its limit, or it raised — the operation does not remove the build directory**, since a container that may still run would write to it after its removal (cited: ADR-0144 Q4, "only after the last container of the call has been removed"); the directory is then a leftover, which "stays where it is" (cited: ADR-0096 decision 2). A removal that found no container is not told apart from one that failed (cited: `Removal`, "a removal that found no container is not told apart"), so such a directory is left too. How a later turn finds and removes leftovers stays with ADR-0144 Boundaries (cited).
- **A failure of the `--rm` removal after a normal end** is not seen by the operation (observation: the client's status is all it has; runtime acceptance item (lxxvii)) and changes nothing here.

### 6. No new kind; the messages; the stop conditions

- **Every situation of decision 2 is placed under one of the eight backend kinds, under a value of `condition` both contracts already have, or under no row** (C14, C16, the open stream of decision 4) where the landed rules answer it. **No new value of `error.kind` is needed**: this is the answer to the first stop condition of the task that wrote this record; had one been needed, the record would have stopped for the owner.
- **No owner-only decision was met**: the value judgment about a kernel that fakes an infrastructure failure is made by ADR-0110 decision 3 and ADR-0145 decision 5 (cited), which this record applies (decision 3) and does not extend.
- **Messages** follow ADR-0060 decision 5 and ADR-0068 decision 6 (cited): the message of a kind may say which case of its row it was — for example "no container image is named", "the container runtime's client was not found", "the container runtime ended the build's container with a status of its own" — and shows no path, no image reference, no container name, no byte of a stream and no text of an error. **An image reference is not shown** (this record's own addition): it is a value of the user's environment that names a machine's store (cited for the reason's manner: ADR-0056 decision 6, "a path would put the location of a checkout on one machine there").
