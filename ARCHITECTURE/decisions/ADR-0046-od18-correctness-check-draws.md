## Decision

A sentence is **cited** when a record and its decision, or a requirement, is named with it; it then says what that source says and adds nothing. Every other sentence is **this record's own** — among them the source of the number, the member `draws` of `instance.json` with its name, place, form and validity, that no further read is made, the kind `draws_not_stated` and its place in the order of a call, that a request carries no member for the number, and every weighing. No sentence is the owner's.

### 1. Scope and terms

- This record is about **a call of `correctness.check` about one attempt of a run that ADR-0021 and ADR-0038 decision 6 cover**: a run of the first case — `cpu_standin`, kind `gemm`, fp32, a C kernel (cited: ADR-0021 decision 1) — and a run whose hw_profile names the mock (cited: ADR-0038 decision 6).
- Of the contract of that call it fixes **four points and nothing else**: where the number of draws of a check comes from (decision 2, with the member in decision 3); at which moment and from which read it is taken (decision 4); what a call answers when the file of the run states none (decision 5); and what this means for the request and for the result member `draws` (decision 6). Decision 7 says what is thereby not decided, and decision 8 puts the order of a call together again.
- The terms of ADR-0011 and ADR-0015 (identity, start line, end line, reserved kind), ADR-0016 (backend, operation, the moments ① to ⑦), ADR-0030 (the moment ⓢ), ADR-0017 (draw), ADR-0021 (the cut, a check), ADR-0040 and ADR-0041 are used unchanged. **The number of draws of a check**: the `draws` of ADR-0017 decision 9 that the tool function judges with and hands to the operation (cited: ADR-0021 decision 2, class (ii) and the table; ADR-0043 decision 2).
- **A verification about no run** — the calibration tests — reads no file: the harness keeps taking `draws` from its caller (cited: ADR-0017 decision 9), and those tests pass their own (cited: ADR-0017 Consequences, "each passing its own `rtol`, `atol`, seed and `draws`").

### 2. Where the number of draws of a check comes from

- **The number of draws of a check is the one the run states: the member `draws` of `runs/<run_id>/instance.json` of the run the request names** (the member: decision 3). The tool function uses it for its own part and hands the same number to the operation (the handing is cited: ADR-0021 decision 2, class (ii); ADR-0043 decision 2, "No value of the five is derived, rounded or replaced on its way across the cut").
- **Five tests**: (i) who thereby chooses how strong a check is, and whether the calling agent can lower it for a verdict that is stored under the identity of an attempt; (ii) whether the source needs a value that no fixed input gives; (iii) which read, file or answer it needs that no landed record has; (iv) what the log then shows of the number; (v) what bounds the cost. **(a), (b) and (d) are put to all five; (c) is not weighed; (e) is answered by what ADR-0041 said of the same places, which bears on (i) and (iii).**
- **(a) A member of the request, chosen by the calling agent.**
  - (i) The calling agent chooses, at each call. **Whether the reason of ADR-0020 decision 5 carries over is tested part by part.** That reason: "A check about a run whose verdict took its tolerance from the request would let the calling agent loosen the gate FR-9 calls a hard floor" (cited).
    - *The predicate*: **does not carry over.** A completed run passes "iff the predicate of decision 5 holds for every element of every draw" (cited: ADR-0017 decision 7). No number of draws puts an output that is outside the tolerance inside it, and "One draw is enough for the class V1 of ADR-0003" (cited: ADR-0017 decision 3): a check over one draw is a check.
    - *What a pass assures*: **carries over.** "a pass over more draws is another assurance than a pass over fewer" (cited: ADR-0042 decision 5), and "A kernel that is right for some inputs and wrong for others can pass one check and fail the next" (cited: ADR-0021 decision 6). A check over fewer draws puts such a kernel to fewer inputs, and it also costs less (cited for the cost per draw: ADR-0017 decision 10). A calling agent that named the number would set, for each check, what its pass assures, and the cheaper choice would be the one that asks less of the kernel. The pass is stored under the identity of an attempt of the run, like a pass over any other number.
    - *That nothing shows it* — the ground of ADR-0016 decision 4 ("none of the members ADR-0011 decision 3 fixes for the two lines of a step names the target that was measured", cited) and of ADR-0041 decision 2 (a) for the shape: **does not carry over.** A result states `draws` (cited: ADR-0042 decision 5), so the log shows over how many draws an ended check was judged. Showing is not refusing: no landed record says that a pass over some number of draws does not count, and which ended check counts for the hard floor is open (OD-18 sub-question ⑭).
    - *FR-9's sentence on who chooses* ("얼마나 잃을지를 시스템이 고르지 않는다") is said of the tolerance. **This record does not read FR-9 as saying who chooses the number of draws**; the weighing rests on the second part above.
  - (ii) No value is needed. (iii) A member of the request, with a name and a form; no file. (iv) The result states the number. (v) Nothing: the calling agent could also name any number, however large.
- **(b) A member of the file of the run, stated when the instance is started.**
  - (i) Whoever starts the instance states the number, once for the run: the file holds "What the instance was started with" and is written by "The start of the instance, once" (cited: ADR-0004 decision 1, as ADR-0023 Context cites it). The calling agent does not choose it at a call. Whoever can write the file can change it (decision 9).
  - (ii) No value is needed: the file states the number or states none, and nothing stands in (decision 3).
  - (iii) One member of a file this contract already reads once in ④ (cited: ADR-0021 decision 4; ADR-0041 decision 3), and one more answer for a valid file that lacks it (decision 5). No further read and no further file.
  - (iv) The result states the number a check used, and the file states the number of the run, in one form, so the two can be compared.
  - (v) Nothing bounds the number below the range of its form (decisions 3 and 9). The share of the cost of a check that comes from the number of draws and the shape follows from the file, and not from a choice made at the call.
- **(c) A constant of the contract or of the source: not weighed.** It is "A value no source gives" (cited: ADR-0017 Alternatives), and naming one would have this record choose how strong the verification of every instance is — the second limit of Status.
- **(d) A member of the file as a floor, and a member of the request that may only raise it.** (i) The calling agent cannot lower the number; it can raise it. (ii) No value is needed. (iii) What (a) and (b) need together, and a rule for a request that names less than the file. (iv) The result states the number. (v) Nothing: the calling agent would hold the cost of a check. **Against it**: the request half answers a question nobody has asked yet — a heavier check for some calls — with a mechanism, and the one known candidate for such a call is the re-verification before a target counts as reached, which is the third limit of Status.
- **(e) The spec of the attempt, a stored record below `db/`, or the backend** — by what ADR-0041 said of the same places for the dimensions. A spec "exists per coder call only and is a copy composed by a role (OD-23)" (cited: ADR-0016 decision 4), and it is "one more file of the run … read at a moment for which no record gives an answer when the file is missing or invalid" (cited: ADR-0041 decision 2 (c)). A key record stored below `db/` need not be there for a run: of the op_signature record, "a stored record or a key directory need not exist for the key of a run" (cited: ADR-0031 decision 6, as ADR-0041 decision 2 (d) cites it), and of the hw_profile record, "a stored record may not exist at all for the key of a run" (cited: ADR-0018 decision 6); a number of draws is no field of either. A backend that stated the number would say on how many draws its own answer is judged: "the judging is above the cut so that no backend holds a part of what decides a verdict" (cited: ADR-0041 Alternatives, from ADR-0021 decision 2).
- **The choice is (b).** It is the one source under which the number is a statement of the run and not of a call, it needs no value, and it uses a read that exists. ADR-0017 already speaks of the number "an instance uses" (cited: its decisions 3 and 9) and names "the instance or the tool contract" as where the trade is made (cited: its Alternatives); (b) puts it with the instance. It is this record's design and is not taken as provisional.
- **What the choice costs.**
  - **One number for every check of the run, for as long as the file is not changed** (decision 9): the checks of every round, of every attempt, and at both execution points each take the number the file states at their read. A caller that wants a check over more draws, or a quick one over fewer, has no way under this contract (decision 6; what whoever can write the file can do is decision 9).
  - **A run that states no number gets no check** (decision 5), and nothing here says which number to state: every instance of these runs must be started with a number that no record recommends.
  - **The number is fixed before the run has shown anything** — how long a check takes at the stated shape, or how its kernels fail — and the file is written once (cited: ADR-0004, as above).
- **What would reopen it.** A record that gives a promotion-level re-verification, a gate or the hard floor a number of its own (the third limit of Status) — for example by a member or a request member of its own, or by making this member a floor; in the last case it changes the meaning of the member and applies the version rule of ADR-0018 decision 2. A record that needs two numbers for the two execution points. A statement of the owner on who sets the strength of a verification. None of these is decided or excluded here.
- **No other source stands in when the file gives none**: not a member of the request, not a constant of the source, not a value kept from an earlier call, not a number of another run. What the call answers then is decision 5.

### 3. The member `draws` of `instance.json`

- **The member is `draws`**, a top-level member: an *integer* of ADR-0001 (cited for the form: its decision 1, "in the range 0 to 2^53 - 1"; the form ADR-0018 decision 2 uses for `schema_version`) that is **at least 1** (cited for the lower end: ADR-0017 decision 3, "at least 1", and the row `draws` of its decision 9, "≥ 1"). The written form is that of ADR-0023 decision 3 (cited): a JSON number in decimal digits without sign, fraction or exponent.
- **Nothing else is a value**: `true`, `false`, `null`, a number with a fraction or an exponent (`2.0` and `2e0` included, though both denote an integer), a string (`"2"` included), an array, an object, `0`, `-0`, every negative number and an integer above the *integer* range.
- **No lower end above 1 and no upper end below the *integer* range is added.** The end of that range is a property of the form ADR-0001 gives an *integer*; it is not a bound chosen for a number of draws. **A valid value is not thereby one a check can be carried out with** (decision 9).
- **What it states**: the number of draws of a check of `correctness.check` about an attempt of the run. **This record gives the member that meaning for a run of decision 1 and gives it no meaning for any other run** — as ADR-0020 decision 2 does for `tolerance` (cited: "gives it no meaning for any other run"): a draw is a term of the verification run of the first case (cited: ADR-0017 decision 3), and the check of every other case is the owner's (#5 B-7). The file does not say whether a run is one of decision 1, so a validator of the file cannot check that and does not.
- **In version 1 a run states at most one number**: the member is one integer. It is no budget member and no bound: it states no amount of time, of hardware quota or of tokens, and it is none of the four axes of FR-3.
- **The name.** `draws` is the word of ADR-0017 decision 9, of the check parameters (ADR-0043 decision 2) and of the member of a result (ADR-0042 decision 5); all name one quantity, and one name lets the number be followed from the file to the result without a mapping — as ADR-0042 decision 5 gave the member `shape` of a result the form of the member of the file, "so the two can be compared" (cited). It is a *name* of ADR-0001 (`[a-z][a-z0-9_]{0,31}`; 5 characters). Searched on 2026-10-12 in `hilclaw/`, `tests/` and `ARCHITECTURE/`: the word occurs there as the parameter of the harness, as a check parameter, as the member of a result and in the prose about them, and nowhere as a member of `instance.json` — no record from ADR-0018 to ADR-0034 defines a top-level member of this file under that name, `hilclaw/instance.py` defines none, and no case of `tests/test_instance.py` holds a top-level `draws`. **The same word is the name of a member of a result and of a check parameter; neither is a member of this file, so this is no collision, and it is meant.** The cost: the name does not say draws of what; a later record that needs a number for another kind of drawing takes another name.
- **The member may be absent from a valid file, and `schema_version` stays `1`** — the first of the two choices ADR-0018 decision 2 leaves to the record of a member ("A later record that defines a top-level member which may be absent and may be passed over does not raise it", cited). A version 1 reader may pass over the member: a reader that needs the number is one that knows the member.
- **A member that is present must be valid.** A file whose `draws` breaks this decision is **invalid** in the sense of ADR-0018 decision 2 (cited: "A reader reports an invalid file, uses no member of it and repairs nothing") — not its `hw_profile`, its `tolerance` or its `op_signature` either. This follows ADR-0020 decision 3 and ADR-0023 decision 4.
- **A valid file without the member states no number. There is no default, and no reader substitutes a value**: not 1, not a constant of the source the reader runs from, and not a value from another run. A reader of this record has the number of a run only when the file of that run is valid, is of version 1 and holds the member; a missing file, a file that cannot be read, an invalid file, a file of another version and a valid file without the member each leave it without one.
- **Whether the start of an instance checks that a number is stated, and from what it takes the number, is not decided**: sub-question ㉜ (Boundaries), with what writes the file (OD-8 sub-question ⑰).

**Example.** The placeholders of the Example of ADR-0023, without its `source_commit` and `n_max` and with the new member, so this is the shape of the member and **not a valid file** (`NOT-DECIDED-HERE` is no valid `hw_source`), and not a complete instance. **`2` stands in for the number of draws only, as it does in ADR-0042 decision 7: it is no proposed, default or typical number, and no reader supplies it for a file that lacks the member.**

### 4. At which moment, and from which read

- **The number is taken in ④, from the one read of `instance.json` from which the hw_profile, the op_signature and the tolerance of the call are taken** (that read is cited: ADR-0018 decision 4; ADR-0021 decision 4, "this contract reads it once"; ADR-0041 decision 3). **No further read is made for it, and no other file is read for it.** The four are therefore those of one content of the file — the reason ADR-0021 decision 4 gave for one read, which carries over unchanged.
- **The read of ⓢ is not used for it** (cited: ADR-0030 decisions 3 and 4, "④ is unchanged: the selection reads the file again"). A file whose `draws` is invalid is invalid as a whole (decision 3), so such a file is already answered in ⓢ (decision 5, last bullet).
- **A call answered before ④ takes no number**: a refused request, `no_data_root`, a kind answered in ⓢ, a situation of the lookup, an ended or an open identity (the moments are cited: ADR-0040 decision 7).
- **A repeated call under an ended identity is answered with what the end line holds** (cited: ADR-0040 decision 3), whatever number a valid file of version 1 then states: the lookup comes before ④. The stored result states the number that check used (cited: ADR-0042 decision 5).
- **A further `execution` reads the file again** and takes the number it then states: it is "carried out as any call whose identity has no line" (cited: ADR-0040 decision 3), and "nothing is kept between calls" (cited: ADR-0020 decision 5).

### 5. A run whose file states no number of draws

- **A valid file of version 1 without the member `draws`: a tool failure of this tool's own kind `draws_not_stated`.** No number is substituted (decision 2, last bullet).
- **For it, this call called no operation, consumed nothing at any target, drew no seed and appended no line; the same request can be repeated and is answered by what the file then states.** It is answered in ④, before the start line, and this contract raises the kind in no other situation and never as the `failure` of an end line — the properties ADR-0021 decision 4 gave `tolerance_not_stated` and ADR-0041 decision 4 gave `op_signature_not_stated`, for the same reason (cited: both). That no seed is drawn is also what ADR-0021 decision 3 says of every such call: "A call that does not reach ⑥ draws no seed" (cited).
- **The name** is a *name* of ADR-0001 (16 characters), formed like `tolerance_not_stated` from the name of the member. Checked on 2026-10-12 in `hilclaw/`, `tests/` and `ARCHITECTURE/`: no reserved kind (ADR-0015 decision 2; ADR-0016 decision 3; ADR-0019 decision 2; ADR-0026 decision 3), no kind of another record (`tolerance_not_stated`, `op_signature_not_stated`, `op_signature_not_covered`, `operation_answer_invalid`), no `step` value and no member name equals it, and the string occurred in none of the three trees before this record.
- **Why this class — the reasons of ADR-0021 decision 4, each checked for whether it carries over.**
  - *Not a result*: carries over. No outcome was established about the attempt (cited: ADR-0010 decision 4, as ADR-0041 decision 4 cites it), and a result of any shape could be taken for a verdict.
  - *Not `invalid_request`*: carries over. The request is not at fault, and a refusal reads nothing and is "the same on every machine" (cited: ADR-0015 decision 2).
  - *Not a kind of ADR-0019*: carries over. The file is there, was read, is valid and is of the supported version (decision 3).
  - *Not a check over some other number*: carries over, with decision 3 in the place of ADR-0020 decision 3.
  - *Not a new reserved kind*: carries over as it stood for the tolerance. "the situation belongs to one tool, and the kinds the frame reserved were reserved because their situations belong to no one tool" (cited: ADR-0021 decision 4): the member has a meaning for a check of this tool only (decision 3). The part of ADR-0041 decision 4 that made this reason provisional for the op_signature — a statement about the run that other tools may come to need — does not arise for a number of draws of a correctness check.
- **Its place: after the two kinds of ADR-0041, and before `tolerance_not_stated`.**
  - *After `no_backend` and `not_offered`*: "A call whose backend cannot be selected reaches no check, whatever the file states" (cited: ADR-0021 Alternatives, as ADR-0041 decision 4 cites it).
  - *After `op_signature_not_stated` and `op_signature_not_covered`*: the member has its meaning for a run of decision 1 only (decision 3), and what the file shows of the case beyond the accelerator is in the op_signature (cited: ADR-0041 decision 4). The tool function looks at what operation the run states before it asks the file for a number of draws, as it does before it asks for a tolerance.
  - *Before `tolerance_not_stated`*: no fixed input orders the two members by need — neither is needed to read the other. **One landed sentence does prefer an order**: "`tolerance_not_stated` then says, as before, that the tolerance is the one thing missing" (cited: ADR-0041 decision 4; ADR-0021 Alternatives has "the kind says that the tolerance is the one thing missing"). With the number asked for first, that sentence stays true of the kind: a call answered `tolerance_not_stated` is about a file that states a covered op_signature and a number of draws. The other order would keep another thing — that a file which states a covered op_signature and no tolerance is answered `tolerance_not_stated` whatever else it lacks, as the row of the Walk-through of ADR-0041 for such a file reads — and would give the sentence up: the kind would also be answered for a file that lacks the number. **This record keeps what the kind says**, since a caller that knows this contract is to tell its kinds apart "without reading the message" (cited: ADR-0019 decision 2, as ADR-0041 decision 5 cites it), and lists the rows that then presume a stated number (Consequences).
  - **So a file with several of these faults has one answer**: the first, in the order of decision 8, whose condition holds. A valid file that states a covered op_signature and neither a number of draws nor a tolerance is answered `draws_not_stated`. The cost, as in ADR-0041 decision 4: whoever corrects such a run learns of the missing tolerance only from the next call.
- **It is checked at every call of this tool that reaches that answer in ④** — not at the first only, since nothing is kept. **What anybody does after the answer stays open** (OD-10; OD-23).
- **A member that is present and invalid is not this kind.** The file is invalid as a whole (decision 3); the call answers `run_file_invalid`, by the rows ADR-0019 decision 3 has for `instance.json`, in ⓢ (cited: ADR-0030 decision 4) — so also for an ended identity, as ADR-0041 decision 4 has it for an invalid `op_signature`. A member whose name is misspelt is passed over (cited: ADR-0018 decision 2, the cost), and the file states none.

### 6. What this means for the request and for the result

- **A request of this tool carries no member for the number of draws.** A calling agent does not choose it (decision 2 (a)). **A caller that wants a check over another number has no way under this contract** (what whoever can write the file can do is a limit: decision 9).
- **The member list of a request stays open** after this record (cited: ADR-0040 decision 5, "The member list of a request is not closed by this record"): whether a request carries anything for the kernel of the attempt, flags or time limits is a later slice's, and so are the input schema and the description. **This record does not say what the tool function does with a member no record names** — a member named `draws` in a request included.
- **The result member `draws` stands as ADR-0042 decision 5 fixed it, and this record does not revisit it.** Its provisional clause names two cases: "If that slice gives a check something other than one number of draws, or makes the number a member of the request — so that the result would state a second time what the request states — it revisits this member" (cited). **Neither is the case**: a check has one number, and the request does not carry it. By decisions 2 and 4 the number a result states is the one the file stated at the read of ④ of that check.

### 7. What is not decided by this

- **Which number an instance or a caller should use.** No value, default, recommended or typical value is fixed, and no bound beyond the 1 of ADR-0017 and the range of the *integer* form (decision 3); "how many an instance uses is a trade of cost against assurance that no source fixes" (cited: ADR-0017 decision 3) stays as it is.
- **A promotion-level re-verification, gates and the hard floor.** FR-9 has an early reach of the target of FR-3 ④ counted only after "승격 게이트 수준의 재검증". Whether that re-verification is a call of this tool, whether it or any gate uses another number than a check of a round, and which ended check counts for the hard floor are not decided: OD-3 is owner-only (#5 A-5), and OD-18 sub-question ⑭ stays as registered. **This record adds no rule for any of them and does not say that one number is enough for all.**
- **The rest of OD-16 sub-question ⑤**: whether a seed, or what a kernel's process wrote besides the report, is recorded after a check stays open as ADR-0021 decision 3 worded it. **Sub-question ⑥** (the builds of the verified and the timed executable) and **sub-question ①** (shapes outside the op_signature) are untouched.
- **Any upper bound** of the number below the range of its form, of the size of a report or of the cost of a check (OD-14).
- **Whether the two execution points should use two numbers.** ADR-0038 decision 5 renders the owner's reading of "동일 검증을 반복한다" as "the same harness, predicate and tolerance with inputs drawn anew for each check" (cited) and leaves `draws` with OD-16 sub-question ⑤ (cited, same decision); this record does not read that answer as naming the number of draws. Under this record both checks take the number the file states.

### 9. Limits

- **Whoever states the number sets what a pass of the run assures, and a valid number can be 1.** A pass says over how many draws it was judged only through the `draws` of its result (cited: ADR-0042 decision 5); nothing in this record says that a number is enough for anything.
- **Whoever can write `instance.json` changes the number**, as the tolerance and the shape (cited: ADR-0021 decision 6; ADR-0041 decision 9). **Two checks of one attempt can have used two numbers** — a further `execution`, the check at the other point — when the file was changed between their reads; each result states its own. While the file is not changed and the calls are given the same data root and run the same source, every check of the run takes the same number.
- **The cost of a check grows with the number, and nothing below the range of the form bounds the number here.** "per draw one kernel call, one regeneration and one float64 product on the Python side, and 4·m·n bytes of report"; the report is held "at once" for all draws; "the Python-side work of a run is bounded by nothing here" (cited: ADR-0017 decision 10; OD-14). The harness of this source commit refuses a `draws` of 2^64 or more (observation; ADR-0043 decision 2 observed it and adopted nothing); every valid value of the member lies below that.
- **The calling agent is kept from one thing only: naming the number of a check in a request.** It can still ask for a further `execution` (cited: ADR-0040 decision 8; sub-question ⑭), and nothing here keeps a caller from asking until a check passes.
- **A misspelt member name** leaves the run without a stated number, and the answer is `draws_not_stated` at every call that reaches that answer, for as long as the file is not changed.
- **Two processes, two sources** (cited: ADR-0018 decision 6): a source older than the code of this record passes over the member and takes as valid a file whose `draws` a newer source refuses.
- The limits of ADR-0021 decision 6, ADR-0040 decision 8, ADR-0041 decision 9 and ADR-0042 decision 9 stand unchanged.
