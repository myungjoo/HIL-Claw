## Decision

### 1. Scope and terms

- A call of `correctness.check` as ADR-0060 decision 1 has it: about one attempt of a run of the first case or of a run whose hw_profile names the mock.
- **A build**: the build of the verification executable an operation carries out in ⑥ (cited: ADR-0056 decision 4); one check makes at most one. **The log**: everything the compiler process of that build wrote on its standard output and its standard error.
- **Not this record**: the timing build of `sim.run` / `board.run` (sub-question ⑲ (다)); what the verification process writes (OD-16 sub-question ⑤); a coder's own logs (OD-23 sub-question ① (라)); the command and the settings of a build (⑰ (다); OD-6 sub-question ②).

### 2. Which builds' logs are kept

- **The log of every build whose compiler process was started and has ended — by itself, or killed for its time limit — is kept**: S7 and S8 (O2, **the owner's**, as ADR-0060 decision 5 applied it), S9, and every build that ended ok, whatever followed it (S10, S4 for a setting of the process refused after the build — cited: ADR-0060 decision 4 —, a report or a condition). S3, S5, S6 and S4 found before the build start no compiler or none that ran, so they have no log.
- **A log that is empty is kept as an empty file.** So, for an identity whose end line holds a result or a failure of the operation's, **the file exists exactly when the operation handed over a log** (decision 6), and a missing file says that no compiler of that check ran or that its log did not reach the tool function — never that it said nothing.
- **Why more than S7 and S8.** FR-6 asks that intermediate, final and failed results all be kept, and A-2 counts "에러 로그" among the texts kept in git — **this record reads that word as including the compiler's log of a build of an attempt**, a reading ADR-0055 L7 declined to make ("Whether the "에러 로그" of O1 means logs of a coder's own, or only those of the measured build, this record does not read"); the warnings of a build that ended ok, and the output of a compiler that reported success but left no executable (S9), are the same kind of text, and for S9 the only evidence of what happened. One rule for every build that ran keeps the presence rule above simple. The cost: every check of a real backend adds a file, usually small or empty, to the data repository. **Keeping the logs of S9 and of ok builds is this record's own extension of O2**; if the owner reads O2 as limited to S7 and S8, that is an objection to this decision.
- **The mock** builds nothing; the default script hands over no log (decision 6), so a run at the mock leaves no such file. A script of a test may hand one over, and it is then kept as any other.

### 3. The path and the name

- **`runs/<run_id>/rounds/<RRRR>/measure/candidates/<CC>/attempts/<AA>/build-log-<step>-<EE>.txt`**, where the first five parts are the request's run and attempt as ADR-0004 decisions 2 and 3 format them, `<step>` is the `step` value of the call (cited: ADR-0040 decision 3 — `correctness_check_sim` or `correctness_check_board`), and `<EE>` is its `execution` in decimal, zero-padded to at least two digits and written in full, never truncated (the number form of ADR-0004 decision 3, taken for this number).
- **One identity, one name.** The two checks of an attempt (O5, **the owner's**) differ in `<step>`, and a further `execution` in `<EE>`. A step runs at most once under an identity (cited: ADR-0011 decision 3, a repeated call is answered from the log), so the name is written at most once. Which of several checks counts is not touched (sub-question ⑭): all are kept.
- **Why below `measure/`.** O2 names `build.json` with the file, and ADR-0004 decision 3 placed that file under `measure/` "because it describes the build whose binary is executed"; decision 4 gives `measure/` the "build and execution on sim and board", and a check is a build and an execution at one of the two points. The log of the run tools' timing build would then lie in the same directory, a candidate for ⑲ (다) and not decided here. The file is written by the tool layer inside the call (decision 6), as `events.ndjson` is, so no agent needs write access to `measure/` for it; which agent calls the tool (OD-23) does not move it. **How this reads ADR-0004 decision 4**: the tool function of this tool does the measurement role's write for this one file; the role directory says to which role the file belongs, and "Which agent or tool holds a role" stays OD-23's — this record does not say that the measurement role is the tool layer's or that the caller of the tool holds it. It is the first file below a role directory the tool layer writes; ADR-0004 decision 4 names only run-level files for it. If a later record moves `build.json` below `coder/` (ADR-0004 decision 3), it says whether this file moves with it.
- **ADR-0004 decision 3's "`build.json` replaces the draft's `build.log`"** is read as it gives its reason — "the settings an attempt was actually built with need a structured record" —: the structured record of a build stays `build.json`, and this file holds no setting and is no record of a build, only the text the compiler wrote (decision 4).
- **Why a flat name and no subdirectory.** A file added directly in the attempt directory is "a file … added in a place this record leaves open", and **the layout version stays 1** (this record's reading of ADR-0004 decision 9, as ADR-0072 read it for a key directory); a directory level would be more than that. **The ground of the reading**: ADR-0004 closes its top level in words ("A fourth data directory needs a new record", decision 1) and has no such sentence for an attempt directory, and decision 3 makes the attempt the unit of "everything that comes from one source", which the log of a build of that source is. If the owner reads the file as a change of the layout that raises its version, that is an objection to this decision. It is no "further record" of a step in the sense of ADR-0004 decision 3, which speaks of the result files of `sim.json`, `board.json`, `profile.json` and `eval.json`: it is no record of a result.
- **Why `.txt` and not `.log`.** W1 ignores neither, but `*.log` is a pattern commonly found in a user's own exclude file (`core.excludesFile`), which would hide the file from a commit unnoticed. The name holds only lowercase ASCII letters, digits, `_`, `-` and one dot, the characters ADR-0055 N1 admits for a kernel file; the prefix `build-log-` keeps it apart from `build.json` and from every name of `ATTEMPT_ARTEFACTS`.

### 4. The form

- **A text file tracked in the data repository, not a blob.** A-2 (**the owner's**) keeps "에러 로그" in git for good (read as in decision 2), and C-3 sends binaries, not texts, to the CAS. A blob would fall under a retention class of C-3, and `intermediate` and `failed` are collected after a grace period, which "Kept" (O2) does not allow; its `artifacts.json` record would need a `type` no record names (cited: ADR-0005 decision 5, "which binaries the tools produce is not decided").
- **The bytes**: the log as text, encoded as UTF-8 without a byte order mark; a byte sequence of the compiler's output that is no valid UTF-8 is replaced by U+FFFD, as the code decodes it today (observation). **Nothing is added, removed or changed**: no header, no command, no setting, no time, no status, no line-end conversion and no final newline that the compiler did not write. The identity of the build is the path; the command and the settings are ⑰ (다) and `build.json` (OD-6 ②).
- **No size bound is set by this record.** The log is kept whole. What bounds it today is the compiler's own limit on errors, the bounds of ADR-0055 decision 6 on the kernel files and the time limit of the build; none bounds the number of warnings. **Whether a bound is added, with what value and with what mark of a cut, stays open as the rest of ⑱ (나)**, to be judged with the first real kernels, as ADR-0055 left its own bounds (its sub-question ① (다)).
- **Git, as far as examined** (cited: W1): the name matches no ignore pattern of the data repository. That repository has no `.gitattributes`, so whether `git` converts line ends of the file in a commit or in another checkout is the limit ADR-0055 decision 6 names for kernel files (its sub-question ① (마)); this record says the same of this file and changes nothing in that repository.

### 5. What the log may hold

- **It is kept as the compiler wrote it, not filtered.** Readings against [ADR-0004](ADR-0004-od8-data-plane-layout.md) decision 7:
  - **Seeds**: **an operation hands the compiler nothing derived from the seed of the check** — no flag, no definition, no environment value, no file — so the log cannot hold one. This is this record's requirement on every operation; an operation is handed the seed in the check parameters for the verification process (cited: ADR-0043 decision 2; ADR-0021 decision 3). A backend that breaks it is not detected (cited: ADR-0016 decision 6).
  - **Secrets**: a compiler may echo its command, its environment-derived search paths and its flags. **The settings and the environment a backend holds for a build (ADR-0060 decision 3) are therefore no place for a secret**; nothing here detects one.
  - **Machine-local paths**: the log will usually hold the absolute paths of the kernel files in the checkout of the data repository, of the build directory, of the verification program in the installation and of the toolchain's directories, with any user name in them. Decision 7 does not list them. ADR-0060 decision 5 keeps every path out of a message because "The message is written to `events.ndjson` for good", and O2 keeps the log out of that file. **They are kept with the log.** The cost, stated: the data repository's history holds such paths for good (NFR-2). If the owner reads a machine-local path as something decision 7 keeps out, that is an objection to this decision.
  - **Lines of the kernel files** quoted in diagnostics are bytes the attempt's `output/` already holds in the same tree.
- **Inside a container** (O4, **the owner's**, cited from ADR-0060 Context: "builds run in a container"; its design is OD-14's) the log holds the paths of that environment. How the log reaches the operation from it is the container's route (OD-14 ①; ⑱ (다)); this record requires only that it is handed over as decision 6 says.

### 6. The writing side and the route of the log

- **The tool function writes the file.** **The operation hands the log over through a fifth thing it is called with, the log keeper**: something the tool function makes for the call, to which the operation hands the log of its build, as text, **at most once, before it returns or raises**. The keeper holds what it was handed and writes nothing; the tool function writes after the operation came back (decision 7). The keeper refuses a second hand-over and a value that is no text by an error raised in the operation; an operation that lets that error pass raises something that is no tool failure and is answered `operation_answer_invalid` (cited: ADR-0045 decision 4). **What is fixed**: that there is a fifth thing, what it carries and how often; **the code task's**: its Python form, its name and how it reaches an operation and a script.
- **Why the tool function.** The writing is then the same code for every backend (cited for the principle: ADR-0021 decision 2, "the same code for every backend"); the tool function already holds the data root and forms the attempt's paths (ADR-0056 decision 3), so the formatting of a path of the data plane stays at one side; a contract test over the mock can test the write through a script that hands a log; and a backend whose target is another machine (#5 B-2) has to bring the log back to the tool function's process in any case. Under this record **an operation of this tool still writes nothing below the data root** (cited: ADR-0056 decision 3).
- **Why a keeper and not a member of the answer.** (A) and (B) are told apart "by the kind of value" (cited: ADR-0043 decision 4); a log returned with them would change that form for every operation and every script, and could not travel with a raised tool failure, so the log of S9 (raised as `build_output_missing`, ADR-0060 decision 4) could not be kept. The keeper changes the number of things an operation is called with, once more — the cost ADR-0043 decision 2 named for adding a thing.
- **The mock.** The mock's operation is called with the five things and asks its script with them and with the called tool: six things where ADR-0056 decision 3 has five. The default script hands over no log and still answers as ADR-0044 decision 3 says.
- **What crosses the cut** — the table of ADR-0043 decision 7 as amended by ADR-0056 decision 3 and ADR-0060 decision 4 (none of them is edited; the added rows are in bold):

| Direction | What | Kind of value | Source |
|---|---|---|---|
| to the operation | the request; the hw_profile of the call; the check parameters; the output path | as ADR-0056 decision 3 | ADR-0043 decision 7; ADR-0056 decision 3 |
| **to the operation** | **the log keeper** | **a thing the operation hands the log to** | **this record** |
| from the operation | (A) the report; (B) the condition | as ADR-0060 decision 4 | ADR-0043 decision 7; ADR-0060 decision 4 |
| **from the operation, through the keeper** | **the compiler's log of its build** | **text, at most once** | **this record** |

- The log is **not returned** to the caller, is in no result, no message and no line of `events.ndjson` (O2).

### 7. When the file is written, and what the call answers if it cannot be

- **The order inside ⑥ and ⑦** (the rest of the order is ADR-0060 decision 6): the operation is called with the five things; it returns or raises; **if it handed over a log, the tool function writes the file** — whatever the operation returned or raised, a tool failure or another error — then judges, as it does today, and appends the end line of ⑦. A raised request to end passes through as before (cited: ADR-0060 decision 6), and nothing is written.
- **The write** is that of ADR-0029 decisions 4 to 6, cited with this final name: the whole text held first; a temporary file `<final name>.<token>.tmp` beside it (the form of ADR-0014 decision 4, matched by W1's `*.tmp`, never committed); stable storage; **a last step that gives the final name only if it does not exist**, with no replacing rename; missing directories up to the attempt directory may be created. Which step commits the file is not decided (OD-17; OD-8 sub-question ⑪).
- **If the write fails** — the file system refuses it, or the name is already taken — **the step ends with a `failure` of the new kind `build_log_unwritable`, in place of whatever the operation returned or raised.** No result is made, the identity is ended, and its `spend` is that of ADR-0040 decision 6. When the append of that end line fails, the call is `end_line_failed` (cited: ADR-0026 decision 3).
- **The sentence a caller may rely on.** *In the check of this identity the operation built, its compiler ended, and the log it handed over could not be written to its file by this call. What the operation answered is not returned, no result was made, and the identity is ended.* It says nothing about the attempt.
- **Why a failure and not the outcome.** O2 makes keeping the log part of the check; an end line that holds a result while the log is missing would break the presence rule of decision 2 without a trace, and no member of a result may say so. **The cost, stated**: an outcome the experiment established is lost, and checking that attempt at that point again "would need a further `execution`, which nobody may yet grant" (cited: ADR-0016 decision 2). A file system that refuses this write will usually refuse the end line too, which is `end_line_failed`. **For S7 and S8 this answers with a tool failure a build O1 (the owner's) classes as a result**: the record weighs O1 against O2's "Kept" for the case in which both cannot hold, and the weighing is its own, not confirmed by the owner. If the owner reads O1 as holding in this case too — the result, with the log lost — that is an objection to this decision.
- **It is this tool's own kind**, raised only by the tool function and only as the `failure` of an end line, as `operation_answer_invalid` is (cited: ADR-0045 decision 4); a backend that raises it does not answer the contract (cited: ADR-0016 decision 6). **The name** is a *name* of ADR-0001 (20 characters); checked on 2026-10-17 in `hilclaw/`, `tests/` and `ARCHITECTURE/`: it occurs nowhere, and is no reserved kind, no kind of another record, no `step` value, no value of `condition` and no member name.
- **The message** follows ADR-0060 decision 5: it may say whether the operation had returned or raised, and the kind of the error as the code names kinds of values; **it shows no path, no text of an error and no byte of the log.**
- **The same request afterwards** is answered from the end line and writes nothing (cited: ADR-0011 decision 3). **A death** after the write and before the end line leaves the file and an open identity: the log of a check whose outcome is in no line, which nothing tells apart (cited for the open identity: ADR-0011 decision 3).

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 2 | Keep the logs of S7 and S8 only | The minimum O2 binds; it loses the warnings of ok builds and the evidence of S9, and leaves a missing file ambiguous. |
| 3 | The log as a member of `build.json` | Its members are OD-6 sub-question ②, open; one `build.json` per attempt would need a list for two checks, further executions and the timing build; a log escaped in JSON makes unreadable diffs; and its writer, the measurement role, is not the tool function. |
| 3 | Below `eval/`, by the roster's evaluator | The roster is OD-23; O2 points to `build.json`, which is under `measure/`. |
| 3 | Inside `coder/…/output/` | That is the coder's product, read by the reader of ADR-0055; a log there would mix two roles. |
| 3 | A subdirectory such as `build-logs/` | A directory level, which ADR-0004 decision 9 does not cover as "a file added" (ADR-0072). |
| 4 | A blob of the CAS | Subject to GC under C-3's retention classes, against "Kept"; needs a `type` no record names; A-2 keeps error logs in git. |
| 5 | Replace known path prefixes by placeholders | The file would no longer be what the compiler wrote; it would miss the toolchain's and the user's paths; a prefix can occur in a diagnostic for another reason. |
| 6 | **The operation writes it**, handed the path of the file | Amends ADR-0056 decision 3 ("writes nothing below the data root"); every backend repeats a write of the data plane; a write that fails inside the operation needs a backend kind; a mock run could not test the tool function's part. |
| 6 | The log returned with (A) or (B) | Changes the form of every answer, and cannot travel with a raised tool failure (S9). |
| 7 | Write after the end line | The answer must be what the line holds (ADR-0026 decision 4), so a failed write could not be reported. |
| 7 | Keep the outcome and drop the log silently | Breaks O2 and the presence rule without a trace (decision 7). |
| 7 | Append no end line and leave the identity open | The outcome is then in no line either, and "an open step is a point the run does not pass by itself" until a recovery rule exists (cited: ADR-0040 decision 2); the call would still need a kind for its own answer, and the same request afterwards is `step_open`, which says nothing of why. An ended identity with a kind of its own says what happened. |

## Consequences

- **Code slices** (code mode, D12 rules; names and modules are the code task's; **this record binds no code**). (1) A path function for the file in `hilclaw/layout.py`, beside `attempt_artefact`, taking the `step` value and `execution` — the closed list `ATTEMPT_ARTEFACTS` and its tests in `tests/test_layout.py` either stay as they are or change. (2) In the tool function of `correctness.check`: the keeper, the fifth argument of `hilclaw/check_operation.py` `ask`, the write of decision 7 and the kind `build_log_unwritable`, with tests over the mock using a script that hands a log. (3) The mock's operation and the default script asked with the keeper.
