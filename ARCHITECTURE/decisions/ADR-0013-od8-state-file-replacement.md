# ADR-0013: How the runtime `STATE.json` of a run is replaced on disk (one more part of the rest of OD-8)

## Status

- **Accepted on 2026-10-07** under [PROCESS/DRIVER.md](../../PROCESS/DRIVER.md) §9 (owner decision D6): written by the development driver's executor and accepted by the approval of a context-isolated reviewer. The owner has not confirmed it.
- Closes **one more part of the rest of OD-8** (Open Decisions register in [Requirements](../Requirements.md)): how `runs/<run_id>/STATE.json` comes to be on disk — the steps that meet the requirement of [ADR-0012](ADR-0012-od8-runtime-state-file.md) decision 6, the temporary file they use, what a leftover of it is, and the part of sub-question ⑩ that the write itself meets.
- What stays open of OD-8: **the isolation means** (candidates ① and ②, both kept), every member of `STATE.json` that ADR-0012 does not define, `instance.json`, the result files, the event kinds and payloads, the form of `run_id`, and the registered sub-questions — among them the rest of ⑩ and, of ⑫, whether a writer must keep a member it does not know (decision 7).
- It builds on ADR-0012 (decisions 2, 6 and 7), [ADR-0004](ADR-0004-od8-data-plane-layout.md) (decisions 1, 2, 4, 7, 9 and 10) and [ADR-0006](ADR-0006-od8-events-log.md) (decisions 6 and 10), whose objection windows run until 2026-10-14. If one of them is reverted, this record is revisited with it.
- The owner is notified on issue #5. The owner may object within 7 days of that notice; an objection creates a task that reverts this record and the edits made with it.
- The format follows the "Record format" section of [ADR-0001](ADR-0001-od4-key-schema.md).

## Context

- ADR-0012 decision 6 fixed that the file is replaced as a whole by its one writer and set a **requirement without a way to meet it**: "a death of the writing process leaves the previous content or the new content, never a part of one. The technique, and whether the agent writes through a tool of the package, are left to the code task and to OD-23." The file is the only entry point of a turn (#4 §1), an invalid file is reported and not repaired, and what is recovered is the file of the last commit (ADR-0012 decision 6). A half-written file therefore stops the run until someone restores it.
- ADR-0004 fixed the path, one file per run and the Round-Manager as its only writer (decision 4). It says that directly under `runs/<run_id>/` are the four run-level files and `rounds/` (decision 2); that scratch, temporary and build-cache *directories* are no path of the tree, that their content is never committed, and that where they are is decided with the isolation means (decision 7); and that the tree "makes no write atomic beyond what a git commit gives" (decision 10). It already has temporary files of a writer inside the data repository: those `hilclaw.cas` creates under the ignored `blobs/sha256/` (decision 6).
- The systems of C-7 are POSIX environments (Linux, macOS, WSL). There, `rename()` replaces an existing file in one step — the name refers to the old file or to the new one at every moment — but only inside one file system; a move between two file systems is a copy. So every portable way to meet the requirement that leaves a reader nothing to repair puts a second, short-lived file next to the final one, and that file is a statement about what may exist in the data plane, what a commit takes and what a reader makes of a leftover: a rule of the kind ADR-0006 decision 6 wrote for a torn tail.
- NFR-1 covers the death of a process, not the loss of the machine; the local commit is the durability boundary (#5 A-3). ADR-0006 decision 10 claims nothing beyond process death for an appended line. P1 assumes one run (C-2); the lock is the rest of OD-17.
- Facts of the code and of the data repository, none of them changed here. `hilclaw/cas.py` and `hilclaw/clang_build.py` write a temporary file named with the process id and a random part and move it with `os.replace`; `hilclaw/artifacts.py` writes `artifacts.json` in place. `hilclaw/run_journal.py` reads the final name only: a missing file raises `MissingStateError`, and a path that is not a regular file — a symbolic link is not followed — is invalid. `hilclaw/run_state.py` `dump` writes exactly the members it is given. The `.gitignore` of `HIL-Claw-data` (created by the owner's D7) holds `blobs/sha256/` and, under "Local scratch", `*.tmp`.
- ADR-0012 registered sub-question ⑩ (what writes the first file, and a run directory without it) and ⑫ (whether a writer keeps a top-level member it does not know). A function that writes the file meets both at once: there may be no previous file, and it is given some members and not others.

## Decision

A value below is **cited** when a source is named with it; every other value is **this record's own** choice — among them the five steps and their order, that the content is checked before a file is touched, that the content is brought to stable storage and the directory entry is not, the place and the name form of the temporary file and that the name differs per write, the readings of ADR-0004 decisions 1, 2, 7 and 9, the rules for a leftover, that a replacement may create the run directory, and that sub-question ⑫ stays open.

### 1. Scope

This record fixes how `runs/<run_id>/STATE.json` is replaced on disk, so that the requirement of ADR-0012 decision 6 holds. It fixes **nothing else** of the file — no member, type or validity rule of ADR-0012 changes — nothing of any other file, and nothing of who performs the replacement.

### 2. The technique

A replacement is these steps, in this order:

1. **The content first.** The writer holds the whole new content as bytes before it touches the file system, and that content is valid by ADR-0012 decision 6. A content that is not valid is not written: the replacement would destroy the last valid content of the working tree, and an invalid file stops the run.
2. **A new file beside the final one.** The writer creates the temporary file of decision 3 in `runs/<run_id>/` — as a new file, never by opening an existing one — and writes the whole content into it.
3. **Stable storage.** The writer asks the operating system to bring the content of the temporary file to stable storage (`fsync` or its equivalent) and closes it.
4. **The move.** The writer renames the temporary file to `STATE.json` with the operation that replaces an existing file in one step (POSIX `rename`). This is the only step that changes what the final name holds.
5. **A failure while the writer lives.** If a step fails, the writer removes its temporary file and reports the failure. The final name is as it was.

The writer never opens the final name for writing, keeps no backup copy and writes no marker. Steps 1 to 3 do not touch the final name, and step 4 changes it in one step (cited: POSIX `rename` — the name refers to the old file or to the new one throughout). So, whenever the writing process dies:

| The writing process dies | On disk | The next reader of `STATE.json` finds |
|---|---|---|
| Before the temporary file is complete (steps 2 and 3) | The final name holds the previous content, or does not exist when there was none (decision 6). A temporary file holds a part of the new content | The previous content, or a missing file |
| After the temporary file is complete and before the move | The same, and the temporary file holds the whole new content | The previous content, or a missing file. The replacement did not happen (as an append that did not finish did not happen — ADR-0006 decision 6); the leftover is not used (decision 4) |
| After the move | The final name holds the new content. No temporary file of this write exists | The new content |

There is no moment "during the move": at none of the moments above does the final name hold a part of a content.

### 3. The temporary file

- **Place**: the directory of the final file, `runs/<run_id>/`. Two files of one directory are on one file system, which is what makes step 4 one step; and it is the directory in which the writer of `STATE.json` writes anyway.
- **Name form**: `STATE.json.<token>.tmp`, where `<token>` matches `[a-z0-9-]{1,64}` and is chosen by the writer so that two replacements do not use the same name. How it is built (a process id, a random part) is the code task's.
- **Why the name differs per write.** With one fixed name, two writers at once (decision 5) would write into one temporary file, and a move could put a mix of two contents under the final name — worse than the limit ADR-0012 decision 7 states for that case ("the later write wins and the other is lost"). With a name per write and a file that is always created new, each move carries one whole content and that limit stays as it is. The cost: leftovers do not overwrite each other (decision 4).
- **It cannot be mistaken for a file of the tree.** The name is none of the four run-level names and is not `rounds`; it is no member of `layout.RUN_FILES`, so `layout.run_file` refuses it; it starts with the name of the file it belongs to and ends with `.tmp`, so a person and a pattern both recognise it.
- **Reading of ADR-0004 decision 2** ("Directly under `runs/<run_id>/` are the four run-level files and `rounds/`"). This record reads that sentence as a statement about the **tree**: the files that have a meaning, that a reader may look for and that a commit holds. A temporary file is none of these — nothing reads it, it has no meaning, it is never committed, and it exists only while a replacement runs or as the leftover of a death. At every commit the run directory holds what decision 2 lists. ADR-0004 already has temporary files of a writer that are no files of the tree, those of `hilclaw.cas` beside the blobs (decision 6) — a precedent, not the same case: those lie inside a directory that is ignored as a whole, this one beside tracked files. The sentence is not edited; it is less exact for a working tree between two commits (Consequences).
- **Reading of ADR-0004 decision 7.** That decision is about scratch, temporary and build-cache **directories** — the places where an actor works, whose location "is decided with the isolation means". The temporary file is not such a place: no actor works in it, and it is one step of the write of one file by the writer of that file, in the directory of that file. It shares the two properties decision 7 gives: no path of the tree is one, and it is never committed. **Where scratch and build-cache directories are — outside the checkout, or inside it under an ignored name — is not decided or narrowed here.**
- **Layout version** (ADR-0004 decision 9): unchanged, version 1. No path, file name or number form of ADR-0004 changes, and the temporary file is not a file of the tree.
- **Git.** A temporary file is **never committed**. The rule binds whatever step commits, as ADR-0006 decision 6 binds it for a torn tail; which step that is stays undecided. The ignore file of the data repository already ignores `*.tmp` (cited as a fact, see Context), which the name form matches: a second guard, and the rule does not rest on it. **No change to the data repository is made or required.**

### 4. A leftover

- A **leftover** is a file of the name form of decision 3 in a run directory whose replacement is no longer running: the writer died before step 4, or died before it could remove the file in step 5.
- **It is not state.** It may hold a part of a content or a whole valid one; in both cases it is not the state of the run. It is **never read in the place of `STATE.json`** — not when the final file is missing, and not when it is invalid — and **never moved over the final name**: the replacement it belonged to is over, and the file under the final name may be newer. It is never committed (decision 3).
- **A reader needs no listing.** A reader opens the final name and nothing else; whether leftovers exist changes nothing in what it concludes, so the entry of a turn lists no directory because of them (#4 §1). `STATE.json` missing beside a leftover is a missing file (ADR-0012 decision 2).
- **Removal.** A writer removes its own temporary file when a replacement fails (step 5). A leftover of a dead writer **may** be removed by the writer of the file — finding it takes a listing of the one run directory, a directory of known path (ADR-0004 decision 3) — and **nothing requires it**: no rule of this record depends on a leftover being gone, and a reader removes nothing (ADR-0012 decision 6: it repairs nothing). The cost of not requiring it: one small file per death of a writer stays in the working tree until someone removes it.

### 5. What the rule promises and what it does not

- **Promised — the death of the writing process**, at any moment, and of the agent that asked for the write: the final name holds the previous content or the new one, whole (the table of decision 2). This is the requirement of ADR-0012 decision 6 and no more.
- **A reader during a replacement**: a reader that opens the final name gets the old file or the new one, never a mixture, and the name is never absent once a first file exists. A reader that opened the old file before the move reads the old content to its end.
- **Not promised — the loss of the machine, of power or of the working tree** before the next commit (cited: #5 A-3; ADR-0006 decision 10; ADR-0012 decision 7). Step 3 is required nevertheless. Without it, a file system may make the new name durable before the content, and a power loss could leave an empty or partial file under the final name: the half-written file the technique exists to prevent, by another road. The cost is one flush of a small file per replacement, and replacements are few per round. **The directory entry is not required to be brought to stable storage**: without it, a power loss right after the move may bring back the previous content, which is whole, and losing what was not committed is inside #5 A-3. A writer may do it. Whatever a file system or a disk does with either request is not tested and not promised here; after a machine loss, what is recovered is the last commit.
- **The environments.** The rule holds where a rename inside one directory replaces a file in one step: POSIX, on the native file systems of the environments of C-7. Limits: a data repository on a network file system, or on a Windows drive seen from WSL, gets whatever that file system gives a rename, and nothing here verifies it. Native Windows is outside C-7; the documentation of Python describes the atomicity of `os.replace` as a POSIX requirement, and what holds on Windows — atomicity, and replacing a file a reader holds open — is not stated by this record.
- **The new file is a new file**: it has the attributes of the temporary file (mode, owner), not those of the file it replaces, and a symbolic link under the final name is replaced, not followed. No rule of the data plane rests on either.
- **Two writers at once** are a limit, not solved here (the lock, rest of OD-17; C-2): each moves a whole content, the later move wins and the other content is lost, as ADR-0012 decision 7 says. A writer that removes leftovers (decision 4) can remove the temporary file of another live writer, whose move then fails with an error and changes nothing.
- **Not said**: that the content is right. Step 1 checks what a validator of the file alone can check (ADR-0012 decision 6) and nothing more. No atomicity with `events.ndjson`, `artifacts.json` or a commit is added (ADR-0006 decision 10; sub-question ⑪). Bringing the file of the last commit back from the history (ADR-0012 decision 6) is not a replacement by the writer; who does it, and how, stays undecided.

### 6. The first file

- When no `STATE.json` exists, **"the previous content" is the missing file**: no state was written and no round has begun (cited: ADR-0012 decision 2). The first file is written by the same five steps; step 4 then creates the final name instead of replacing it. A death leaves no `STATE.json`, or the whole first file.
- **A replacement may create `runs/<run_id>/`** (and `runs/` above it) when it does not exist, and does not require another file to be there. ADR-0004 decision 1 says that "a directory exists only when something was written into it": a directory comes to exist with the first write into it, and this is such a write. Requiring the directory would decide that another file is written first, which is the open part of sub-question ⑩.
- **Reading of ADR-0004 decision 1.** A death after the directory was created and before the move leaves a run directory that holds no file of ADR-0004, or a leftover only — a state that sentence, read by the letter, excludes. This record reads the sentence as one about the tree as it is committed and as a reader may rely on it: git holds no empty directory and no temporary file, so no commit has such a directory, and for a reader of `STATE.json` it is a missing file, as a missing directory is. The window is not new: `hilclaw/events.py` and `hilclaw/artifacts.py` create the directory before they open their file.
- **Not decided** (the rest of sub-question ⑩, with OD-23): who writes the first file; when, in relation to `instance.json`; and what a run directory means that holds other files, or nothing, but not this one. What the first file holds is ADR-0012's (`round` 0, the start values of its decision 4).

### 7. A member the writer does not know (sub-question ⑫)

- **The replacement keeps nothing and drops nothing by itself**: the content moved under the final name is exactly the content of step 1. A function of the package that performs the replacement writes what its caller gives it — as `run_state.dump` does today — and does not read the previous file to carry members over.
- **Whether the writer must put into that content the top-level members it read and does not know stays open**, with OD-11. No rule is chosen because either rule is wrong for some member that later records may define, and none is defined yet: a writer that drops what it does not know loses a member another component relies on, and one that carries everything over keeps a member whose value was only true before the write (a marker of the progress inside a round, as the draft of #4 §3b names one, would survive the write that ends the round). Which holds for a member is that member's record's to say, or a general rule of OD-11.
- ADR-0012 decision 6 is unchanged: a write that does not end a round carries `round` and `budget_spent` over. Since nothing is carried over by a package function, the limits of the round trip through `hilclaw/run_state.py` (a number of an undefined member that is read and cannot be written back exactly) are not met by it; what the validator accepts does not change.

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 2 | Write in place: open the final name, truncate, write (as `artifacts.json` is written today) | A death between the truncation and the last byte leaves an empty or partial file under the final name — the case ADR-0012 decision 6 excludes. |
| 2 | A backup copy beside an in-place write, restored by the next reader or writer | The final name is still torn for a while, so a reader would have to tell a torn file from a damaged one and repair it, against "reported and not repaired" (ADR-0012 decision 6); and the backup is a second file with a meaning, which the temporary file is not. |
| 2 | The temporary file outside the data repository (the system's temporary directory) | It may be another file system; the move is then a copy, and a death inside the copy tears the final file. |
| 2 | No technique: rely on the last commit | Every death inside a write would cost the uncommitted state of the round in progress and need a manual restore; ADR-0012 already rejected "no requirement on the write". |
| 2 | No check of the content before the write | An invalid content moved in one step is still an invalid file, and it replaces the last valid one of the working tree. |
| 3 | One fixed name (`STATE.json.tmp`): at most one leftover, found without a listing | Two writers would share the file (see decision 3); and nothing needs a leftover to be found. |
| 3 | A hidden name (a leading dot), or a subdirectory for temporary files | A hidden file is easier to overlook when a run directory is inspected; a subdirectory would be a directory of the run tree that ADR-0004 does not have, and a temporary *directory* in the sense of its decision 7. |
| 3 | Rest on the ignore file alone to keep the file out of a commit | The ignore file belongs to another repository and can change; the rule binds the committing step and holds without it. |
| 4 | The next writer or reader completes the move of a whole leftover | The replacement it belonged to did not happen, and the final file may be newer than the leftover. |
| 4 | The writer must remove every leftover before it writes | A listing on every write and a duty nothing depends on; allowed, not required. |
| 5 | Leave the flush of step 3 to the writer (as ADR-0006 decision 10 does for an append) | A lost append is a line that did not happen and a torn tail has a rule; this file has no such rule, and the cost of the flush is small. |
| 5 | Require the directory entry to be flushed as well | It would only move the loss of uncommitted state by one write, inside what #5 A-3 already accepts. |
| 6 | A replacement refuses when the run directory is missing | It would fix that `instance.json`, or something else, comes first (sub-question ⑩). |
| 7 | A rule now: unknown members are carried over as read (NFR-7 ①), or are dropped | See decision 7; carrying over would also meet the round-trip limits of `hilclaw/run_state.py`, and removing those limits changes what the validator accepts. |

## Consequences

- **The code slice of PLAN P1-8 can implement the write**: a function over `layout.run_file` and `run_state.dump` that performs the five steps. `dump` is step 1 (it refuses what it cannot write before a file is touched). It needs to report: a failure of the creation, the write, the flush or the move (with its temporary file removed), a final name that cannot be replaced (a directory in its place), and a data root that does not exist (the convention of the package's other writers, which never create it). In which module it lives is that task's choice, and it is a library function: registering it as a tool is OD-23.
- **The steps need a process that can create, flush and rename a file.** A write not made of these steps does not meet ADR-0012 decision 6. Whether that makes the Round-Manager write through a tool of the package is not concluded here (OD-23).
- **Handed to the isolation decision** (sub-question ⑭): the writer of `STATE.json` must be able to create, rename and remove entries of the name form of decision 3 in the run directory — a right to write the one file name alone is not enough. Neither registered candidate is chosen or excluded by this.
- `hilclaw/run_journal.py` already matches: it reads the final name only, reports a missing file without answering start values in its place, does not follow a symbolic link, and lists nothing. `hilclaw/run_state.py` and `hilclaw/layout.py` are unchanged and consistent; `RUN_FILES` keeps its four names.
- **As long as the file is written by replacements of this record only, a commit taken at any moment takes a whole `STATE.json`**: the working tree then never holds a part of one. A write that does not follow this record, and the restore of the file from the history (decision 5: not a replacement, undecided), are outside that statement. Whether that content and the log of the same commit fit together is ADR-0011 decision 6 and sub-question ⑪, unchanged.
- **Not edited and now less exact** (follow-ups for the integrator): ADR-0012 decision 6 ("The technique … left to the code task") and its Alternatives row "No requirement on the write"; ADR-0004 decision 2 ("Directly under `runs/<run_id>/` are the four run-level files and `rounds/`" — true of every commit, and a working tree may hold a temporary file beside them) and decision 1 ("A directory exists only when something was written into it" — after a death inside a first replacement a working tree may hold a run directory with a leftover only, or with nothing); the README of `HIL-Claw-data`. No sentence of UsageCases became false: UC-1, UC-3 and UC-4 say nothing of how the file is written.
- **`artifacts.json` is written in place today** (`hilclaw/artifacts.py`), and a death inside that write can leave a file that its reader reports as corrupt. ADR-0005 left atomic writes open for that file. This record changes nothing there; whether the same technique is taken for it and for the key record files is sub-question ⑮.
- **A-13 reading**: document mode; no code, dependency or schema file changes. No member, type or validity rule of the runtime `STATE.json` changes, so this is not a schema change of STATE: the record adds a rule about how the file comes to be on disk.

## Boundaries (not decided here)

- **Owner-only (DRIVER §9)**: OD-3 / #5 A-5 (gate status), OD-25, C-6, the #5 A and B items.
- **The isolation means** (rest of OD-8, OD-14; waits for #5 B-1 and container availability): candidate ① versus candidate ②, the write roots of actors, where the scratch and build-cache directories of builds and coder calls are.
- **Who performs the replacement**: whether the agent writes through a tool of the package, the tool's name and contract, how a result reaches the Round-Manager (OD-23, OD-18).
- **Concurrency and commits**: the lock, fencing, a second writer (rest of OD-17); when a round ends and which step commits; sub-question ⑪ (an owed commit); sub-question ⑬ (the byte offset).
- **Members and other files**: every member of `STATE.json` that ADR-0012 does not define (gate status, `best_ref`, `lock`, `phase`, `next_action`, a time member); `instance.json`; the result files; `run_id`; how `artifacts.json`, the key record files or any other file is written.
- **Versions**: reading or migrating a file of another version, and the rest of sub-question ⑫ (OD-11).
- **Sub-questions this record raises** (registered under OD-8): ⑭ how the isolation means, once chosen, gives the writer of `STATE.json` the right to create, rename and remove entries in the run directory (with the isolation means). ⑮ Whether the other files that are rewritten as a whole — `artifacts.json`, the key record files — are written by the same technique (ADR-0005 Boundaries; with OD-17).
