Requirements C-3 mirrors both.
- **What no input carried**: what a local push and a local fetch do on one machine. ADR-0005 (Boundaries) and ADR-0016 (Context, decision 3 and Boundaries) filed "their meaning on one machine" as the owner's, and ADR-0004 (Boundaries) listed it as open. It was asked as HQ-0008 and answered on 2026-10-12 (decision 2).
- **What exists** (facts, none changed here). `hilclaw/cas.py` is the local store: a blob is "a file named after the SHA-256 of its content, kept outside git at `<data_root>/blobs/sha256/<hh>/<digest>`, where `<digest>` is 64 lowercase hexadecimal characters and `<hh>` its first two". `blob_path` refuses any other digest with `ValueError`. `has_blob` returns whether a file is at that place. `verify_blob` re-hashes the stored file and returns whether "the content matches its name", and raises `BlobNotFoundError` when `has_blob` is false. `put_bytes` and `put_file` write through a temporary file and `os.replace`, "so a reader never sees a partial blob under its final name", and "Storing content that is already present keeps the stored file as it is". The module "reads no configuration, runs no `git` and writes nowhere else".
- **The frame** (cited, not re-decided). A tool is a tool function that takes one request and returns one result or raises a tool failure (ADR-0010 decision 2); the two tools have the names `blob.push` / `blob.fetch` and the MCP names `mcp__hilclaw__blob_push` / `mcp__hilclaw__blob_fetch` (ADR-0010 decision 4). A tool is registered with a description and an input schema, checks its own request, refuses with `invalid_request`, and obtains the data root from the source it is bound to or fails with `no_data_root` (ADR-0015 decisions 2 and 3). "`blob.push` and `blob.fetch` are not HW tools" (ADR-0016 decision 3). `hilclaw.tools.default_registry` holds no tool today.

## Decision

A sentence below is the **owner's** when it is marked **owner** and quoted; it is **cited** when a record, a requirement or a file is named with it; every other sentence is **this record's own** design.

### 1. Scope and terms

- This record is the contract of the two tools `blob.push` and `blob.fetch` **for the MVP's local implementation on one machine**. It is not the contract of a remote backend, and it says nothing of who calls the pair.
- The terms of ADR-0010 (tool function, request, result, tool failure, front) and of ADR-0015 (tool definition, data-root source, reserved kind, journaled tool) are used unchanged. **The local store**: the directory `blobs/sha256/` under the data root, with the layout of `hilclaw/cas.py` (cited: ADR-0004 decision 1). **The place of a hash**: the path `blobs/sha256/<hh>/<hash>` under the data root that `hilclaw.cas.blob_path` gives for it. **The look**: asking the file system whether a regular file is at the place of a hash, symbolic links followed; decision 4 says which answers of the file system are which answer of the call. `hilclaw.cas.has_blob` — `Path.is_file()` — computes the look wherever the file system answers it.

### 2. What a local push and a local fetch do — the owner's answer

- **Owner** (HQ-0008 (1), answer (a)): "nothing is copied; the local store `blobs/sha256/` under the data root is the only store. `blob.push(hash)` and `blob.fetch(hash)` each look at the local store and answer whether a blob of that hash is there. Whether the content is also re-hashed is left to the record."
- **Owner** (HQ-0008 (2)): "not applicable — there is no second store under (1)(a)."
- **Owner's note on scope** (the same answer): "the sharing and propagation of the knowledge that arises while the system is used is to be considered later; nothing of it is decided here." This record decides nothing of it.
- **What follows at once** (this record's own, from the answer): in the local implementation the two tools do the same thing. They stay two tools with two names (cited: #5 A-2 "2-함수 계약"; ADR-0010 decision 4), and decisions 3 to 6 hold for each of them alike; that the two tool functions may be one piece of code is the code task's.

### 3. A call: the request

- **The request has exactly one member, `sha256`**: a string of exactly 64 characters, each one of `0`–`9` and `a`–`f` — the form `hilclaw.cas` uses for a digest and [ADR-0005](ADR-0005-od8-artifacts-record.md) decision 3 uses for the member of the same name in a blob record (both cited). The owner's contract gives the tool one argument, the hash (cited: #5 A-2 `blob.push(hash)`); the member name is this record's, chosen so that a blob record and a request name a blob by one member of one form.
- **A refused request is `invalid_request`** (cited: ADR-0015 decision 2), raised before the data-root source is asked and before anything is looked at. Refused are: a request without `sha256`; a `sha256` that is not a string of that form — an uppercase digit, another length, a prefix such as `sha256:` and a value that is no string included, and nothing is normalised; and **a request with any other member**. The last is this record's choice: the five member names of ADR-0015 decision 4 (`run_id` and the rest) are among the refused ones, so that a caller is told that the call is not about a run (decision 5) instead of having the member ignored.
- **The input schema** the tool definition states (cited: ADR-0015 decision 2 — a statement to the caller, not a check) says the same: `{"type": "object", "properties": {"sha256": {"type": "string", "pattern": "^[0-9a-f]{64}$"}}, "required": ["sha256"], "additionalProperties": false}`. Which keywords Claude Code accepts in a schema is not verified (cited: ADR-0015 F14, sub-question ⑤); if one of these is not accepted, the schema is reduced and the description says what the function refuses beyond it. The text of the two descriptions is the code task's; each says that the tool looks at the local store only and copies nothing.
- **The data root** comes from the data-root source the tool function is bound to, asked at each call after the request was checked, and never from the request; when it cannot be obtained the call is the tool failure `no_data_root` (all cited: ADR-0015 decision 3).

### 4. A call: what it answers

- **The answer to "whether a blob of that hash is there" is a result in both cases** — there and not there. The owner's sentence makes that answer what each tool exists to give in the local implementation (decision 2), and "a result says what the … operation established, its failure included" (cited: ADR-0010 decision 4). A hash the local store does not hold is therefore **not** a tool failure.
- **The content is re-hashed at every call that finds a file** — this record's own choice on the point the answer leaves to it. The reason: a blob is "a file named after the SHA-256 of its content" (cited: `hilclaw/cas.py`), so the name alone does not show that what is at the place is that content; ADR-0005 decision 10 says a record "does not guarantee that a blob is present, intact or reachable from another machine", and decision 8 names `has_blob` and `verify_blob` as what answers instead. With the re-hash one call answers both.
- **The result** has these members and no other:

| Member | Value | When |
|---|---|---|
| `sha256` | The `sha256` of the request, unchanged | always |
| `present` | `true` when the look found a regular file at the place of the hash and the file was still there when the call read it; `false` when no regular file is there ("What counts as not there", below) | always |
| `intact` | `true` when the SHA-256 of the content this call read from that file is the hash, `false` when it is not — what `hilclaw.cas.verify_blob` answers | only when `present` is `true`; left out otherwise, never `null` |

- **How the members stand to the owner's sentence** (this record's reading, to be checked by the owner — Consequences, provisional choices). `present` is the answer of the look, which is what the owner's sentence gives the tools; `intact` is the answer of the re-hash, which the owner's sentence calls "also" and leaves to the record. The record does not fold the two into one member: a file whose content is not its name is reported as `present` `true` and `intact` `false`, not as absent, because the two situations ask different things of whoever acts next — and storing the content again does not replace such a file (cited: `hilclaw/cas.py`, "keeps the stored file as it is"). A caller that needs "the content of this hash is here" reads both members.
- **Three outcomes, all results**: `present` `true` with `intact` `true`; `present` `true` with `intact` `false`; `present` `false`. Through the command-line front each is exit status 0, through the MCP front `isError` false (cited: ADR-0010 decision 4): a caller reads the members, not the status.
- **What counts as not there.** `present` is `false` whenever the file system answers the look with "no regular file is there": a place that holds nothing; a local store or a `<hh>` directory that does not exist yet (cited: ADR-0004 decision 1, "a missing directory means "nothing yet""); a part of the path that is no directory; a symbolic link that leads nowhere; and a place that holds something that is no regular file after links are followed — a directory, for one. A file that the look found and that is gone when the call comes to read it is `present` `false` as well: the file system then answers that no file is there, nothing failed, and the answer is of the moment of the call. **Every other failure of the look** — no permission to search a directory, a loop of links, an I/O error — is not an answer of the file system about the place and is the tool failure below.
- **Why a place that holds something else is answered as not there** (this record's choice). The owner's sentence asks whether a blob is there, and a blob is a file (cited: `hilclaw/cas.py`); what is at such a place is none, so `present` `false` is the true answer of the look, and it is what `has_blob` answers. The record relies on the word "file" of that sentence only: read in full — "a file named after the SHA-256 of its content" — it would also make a file that is not intact no blob, which supports the alternative this record rejects (a file that is not intact answered `present` `false`); the record keeps `present` to the look for the reason given above and says so to the owner. The cost is stated plainly: the answer does not show that the place is occupied, and the content cannot be stored there while it is. That differs from a file that is not intact, which the call can only tell from a good one by reading it and reports with a member that exists for it; no member exists for an occupied place, and none is added for a state that `hilclaw.cas` never produces — it arises only by a hand or a defect outside the package. What is done about it is part of sub-question ⑬.
- **One tool failure of the pair's own: `blob_unreadable`.** The look or the read of the content failed in the file system for a reason other than there being no file — the tool "could not do its work" (cited: ADR-0010 decision 4) and the call says nothing about the blob. Both tools use the kind with this one meaning. The text of the `message` of this failure and of a refusal is the code task's. It is not a reserved kind and is not `run_file_unreadable`, which speaks of a frame file of a run (cited: ADR-0019 decision 2).
- **The kinds a call of the pair can answer** are therefore `invalid_request`, `no_data_root` and `blob_unreadable`, in the order in which a call can meet them, and beyond them only `tool_crashed` and `bad_result`, with which `tools.call` answers a defect (cited: ADR-0015 decision 2). **No call of the pair answers** `step_open`, `start_line_failed`, `end_line_failed` or one of the four `run_file_…` kinds (the kinds are cited: ADR-0015 decision 2, ADR-0026 decision 3, ADR-0019 decision 2; that none is answered follows from decision 5: no lookup, no line, no file of a run), nor `no_backend` or `not_offered` ("Only a HW tool raises them" — cited: ADR-0016 decision 3). No reserved kind is given another meaning.

### 5. Not a journaled tool, and not a call about a run

- **Neither tool is a journaled tool, and a call names no run.** The request carries none of the five members of ADR-0015 decision 4, the contract fixes no `step`, and a call reads no file under `runs/` and appends no line to any `events.ndjson`.
- Why, from the fixed inputs alone: the owner's contract gives the tool a hash and nothing else (cited: #5 A-2); "The same `sha256` may be recorded in the files of two runs", and of a blob in the store without a record in one run's file "another run may record it" (cited: ADR-0005 decisions 6 and 8), so a hash names no run; and a journaled step is "one execution of a step whose repetition costs a limited resource, or whose outcome must survive the death of the process that obtained it" (cited: ADR-0011 decision 1), while a local look copies nothing (owner, decision 2), consumes nothing at any target, and has an outcome that must **not** be kept — a repeated call that was answered from a stored end line would report the store as it was, not as it is.
- **This does not depend on who calls the pair.** Whether a person, a command of layer 1 or an agent makes the call (OD-23, #5 A-3), the call is the same request with the same answer; this record states no rule on the caller (Boundaries).
- "Journaling is not a property of every tool. For which tools it holds is each tool's contract" (cited: ADR-0015 decision 5); for these two, in the local implementation, it does not hold.

### 6. What a call touches, and what it leaves

- **A call writes nothing.** It asks the file system for the look of decision 1 and, when a file is there, reads the content of that one file. It does not create `blobs/sha256/` or any directory, and it stores, copies, moves, repairs and deletes no blob (owner, decision 2: "nothing is copied").
- **It reads and writes no `artifacts.json`**, changes no retention class, writes no `gc_at`, reads no other file of the data plane, and never runs `git`. The record of a blob stays what ADR-0005 decision 8 says it is; a call of the pair neither consults nor confirms one, and a hash that no record names is answered like any other.
- **Nothing is kept beyond the call**: no file, no line, and no state in the process (cited: ADR-0010 decision 7). A call that dies has left nothing, and a repeated call looks again. Nothing is guaranteed beyond the death of the process that `hilclaw.cas` does not already guarantee, because the pair adds nothing to the store.
- **A concurrent store.** `hilclaw.cas` moves a complete file into place (cited: Context), so a call that runs while a blob is being stored finds it either not there or there whole; an `intact` `false` is not produced by that.

### 7. The later backend (#5 B-2)

- **Owner** (#5 A-2, supplement 1): "board farm 접근 방식(B-2) 확정 시 rsync/S3/사내 스토리지 백엔드를 꽂는다 — "HW 도착 시 어댑터만 꽂는다" 철학과 동일 패턴."
- This record's own, and an intention only: the request of decision 3, the line between result and tool failure of decision 4 and the placement outside any run of decision 5 are written so that they **are meant to hold unchanged** when a backend is plugged in. Whether they can — what a push or a fetch does with a second store, what it answers, whether it then spends something that must be journaled — is the record of that backend, and nothing of it is decided here.

### 8. Limits

- **A local push protects nothing.** After `blob.push` answered `present` `true` and `intact` `true` there is still one copy of the blob, on one machine (owner, decision 2: "the local store … is the only store"). **A local fetch obtains nothing**: a blob that is not there stays not there.
- **The answer is of the moment of the call.** Nothing says the blob is there afterwards (cited: ADR-0005 decision 8).
- **A file that is not intact is reported and left as it is, and a place occupied by something that is no regular file is answered as not there and left as it is** (decisions 4 and 6; sub-question ⑬).
- **The re-hash reads the whole file at every call**, so the time of a call grows with the size of the blob. No time limit of a call is decided (cited: ADR-0010 decision 8, sub-question ③), and no source bounds the size of a blob.
- **No access control and no rule on the caller** (cited: ADR-0010 decision 8). The owner's "자동 호출하지 않으며, 사용자 명령으로 실행" (#5 A-3) is neither enforced nor weakened by this record: a tool of the registry can be called by whoever can call a tool.
- **No trace**: nothing records that a push or a fetch was called, for which hash or with what answer.

### Walk-through

`H` is `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`, the SHA-256 of the empty content; its place is `blobs/sha256/e3/H` under the data root. Every row holds for `blob.push` and for `blob.fetch` alike, through either front.

| Call and state | Answer | What was touched |
|---|---|---|
| `{"sha256": "H"}`; the place holds an empty regular file | Result `{"sha256": "H", "present": true, "intact": true}` | The file was read |
| `{"sha256": "H"}`; the place holds nothing (or `blobs/sha256/` does not exist) | Result `{"sha256": "H", "present": false}` — exit status 0, not a tool failure | Nothing read beyond the look; nothing created |
| `{"sha256": "H"}`; the place holds a regular file of one byte | Result `{"sha256": "H", "present": true, "intact": false}` | The file was read and is left as it is |
| `{"sha256": "H"}`; the place holds a directory | Result `{"sha256": "H", "present": false}` — the answer does not show that the place is occupied | Nothing read beyond the look; the directory is left as it is |
| `{"sha256": "E3B0…B855"}` (uppercase), a hash of 63 characters, `{}`, or `{"sha256": "H", "run_id": "r1"}` | Tool failure `invalid_request` | The data-root source was not asked; nothing looked at |
| `{"sha256": "H"}`; the configuration cannot be read, or the directory it names does not exist | Tool failure `no_data_root` | Nothing looked at |
| `{"sha256": "H"}`; the file is there and reading it fails (an I/O error, no permission) | Tool failure `blob_unreadable` | Nothing changed |
| The first row again, after the file was removed by hand | Result `{"sha256": "H", "present": false}`: no earlier answer is kept | Nothing read beyond the look |

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 3 | The member is named `hash`, the owner's word | A blob record names the same value `sha256` (ADR-0005 decision 3); two names for one value in a record and a request. The name is provisional (Consequences). |
| 3 | A `sha256` in another spelling — uppercase, or with a prefix — is normalised and accepted | Two spellings of one blob in a request and a record; `hilclaw.cas.blob_path` refuses them, and ADR-0005 decision 3 fixes the one form. |
| 3 | Other members are ignored | A caller that sent `run_id` would believe the call was about that run. |
| 3 | The request also carries `run_id`, and the tool checks the hash against the `artifacts.json` of the run | Not in the owner's contract (a hash only), and it would make the pair read a record — the answer says the tools look at the local store. |
| 4 | No re-hash: `present` only | The answer would rest on a file name; a damaged file would be answered like a good one, and the caller would need a second tool to learn what `verify_blob` already computes. |
| 4 | Re-hash only when the request asks for it | A second member and a default to choose; the owner's contract carries a hash only. Reconsidered if the size of blobs makes the read costly (Limits). |
| 4 | A file that is not intact is `present` `false` | It would narrow the owner's sentence by the re-hash the owner left apart ("also"), and hide that a file is in the way at that place. |
| 4 | A file that is not intact, or a hash that is not there, is a tool failure | Both are outcomes the look and the re-hash established (ADR-0010 decision 4); the owner's sentence makes "whether it is there" the answer. |
| 4 | A place that holds something that is no regular file is the tool failure `blob_unreadable` | The look did not fail: it established that no file is there. The kind would then mean both "could not look" and "looked and found no blob". |
| 4 | A further result member, or a third value, for an occupied place | A member for a state the store never produces by itself; `present` would no longer be what `has_blob` answers. Left with sub-question ⑬. |
| 4 | A symbolic link at the place is not followed (answered as not there, or as a tool failure) | `hilclaw.cas` follows links when it decides whether a blob is stored already (`is_file()` in `has_blob` and in the store step), so the pair would call absent what the store treats as present. |
| 4 | A file that is gone between the look and the read is the tool failure `blob_unreadable` | Nothing failed: the file system answered that no file is there, which is the answer the tool exists to give, and it is true at the end of the call. |
| 4 | The result does not repeat `sha256`; an absent `intact` is `null` | A result that names its blob can be read without its request; an absent member is left out as in the envelope (ADR-0015 decision 4). Matters of form. |
| 4 | An unreadable file is `tool_crashed` | That kind says the tool is defective (ADR-0015 decision 2); a caller could not tell a disk fault from a bug. |
| 5 | Journaled, with a `step` of each tool | See decision 5: no run in the request, nothing consumed, and a stored answer would be stale. |
| 6 | A push that finds the file not intact removes or repairs it | A deletion, and a repair needs the content from somewhere; removal belongs with retention and GC (C-3), which are not decided. Registered as sub-question ⑬. |
| — | A second directory on the same machine, or no tool until #5 B-2 | Options (b) and (c) of HQ-0008; the owner chose (a). |

## Consequences

- **The code slice that can now be cut** (code mode, one task; nothing is written here): the two tool functions of decisions 3 to 6 over `hilclaw.cas` — `blob_path` gives the place, and `has_blob` and `verify_blob` compute the look and the re-hash where the file system answers the look (see the next point) — bound to the data-root source through `hilclaw.data_root_source.obtain`; their registration in `hilclaw.tools.default_registry` with the descriptions and the schema of decision 3, as the first tools of the fixed set; and tests through both fronts of the rows of the walk-through, of each refused request, and of the fact that a call leaves the data root unchanged — the `blob_unreadable` row through a front where the platform can produce a failing read in a child process, and below the fronts otherwise. `hilclaw/cas.py` needs no change for it.
- **Two things the code slice has to see to.** First, that a look which fails for a reason other than "no regular file is there" is answered `blob_unreadable` and not `present` `false` (decision 4). `has_blob` is `Path.is_file()`, and `verify_blob` makes the same look before it reads. On one interpreter the package supports that look does not tell the two apart: in Python 3.14.4 `Path.is_file()` returns `os.path.isfile()`, and the Python source of that function, `genericpath.isfile`, answers false for every `OSError` (read on 2026-10-12; on Windows `os.path.isfile` is a built-in function whose source was not read; the package supports Python 3.11 and later — cited: `pyproject.toml`; no other version was read). Where that holds, `has_blob` answers false, and `verify_blob` raises `BlobNotFoundError`, for a failed look as well. The tool function therefore makes the look itself in a way that reports why it failed, and decision 4, not `has_blob`, is the rule; it may hand the re-hash to `verify_blob` only after its own look. If the property cannot be had with the standard library, the slice reports back instead of weakening the answer silently. Second, the file that is gone between the look and the read: the `open` inside `verify_blob` then raises `FileNotFoundError`, not `BlobNotFoundError`, and the tool function answers it as `present` `false`. A `BlobNotFoundError` that `verify_blob` raises after the tool function's own look found a file comes from the look `verify_blob` repeats and says only that this second look did not find one; the tool function classifies it by decision 4 — by looking again itself, or by hashing without `verify_blob`.
- **Provisional choices.** Everything in decisions 3 to 6 that is not marked owner or cited is this record's own and open to the owner's objection. The choices on which another choice was at hand: the member names `sha256`, `present` and `intact`; that a `sha256` in another spelling is refused and not normalised; that a request with another member is refused; that a hash the local store does not hold is a result and not a tool failure; that the content is re-hashed at every call; that a file which is not intact is `present` `true` with `intact` `false`; that a place which holds something that is no regular file is `present` `false`, that a symbolic link that leads to a regular file counts as one, and that a file gone between the look and the read is `present` `false`; that the result repeats `sha256` and leaves `intact` out instead of giving `null`; the kind name `blob_unreadable`; that neither tool is journaled and that a call names no run; the keywords of the schema.
- **Not edited and now less exact** (follow-ups for the integrator). Requirements C-3: "동기화는 `blob.push`/`blob.fetch` 2-함수 계약(MVP 로컬 구현, …)" — in the MVP's local implementation the pair synchronises nothing.
