## Decision

A value below is **cited** when a source is named with it; every other value is **this record's own** choice — among them every rule of the text form (decision 2), the rule between the `id` and the path and that a write derives its final name from the content (decision 3), the requirement, that this file takes the steps of ADR-0025 decision 3, that the write reads no other file, what a write that finds the name taken reports and what it leaves open (decision 4), the rule for the directories and that none is added against `STATE.json` (decision 5), the name form of the temporary file, that the readings of ADR-0004 made by ADR-0013 are followed for an attempt directory, the rules for a leftover (decision 6), and that the flush is required (decision 7).

### 1. Scope

This record fixes three things of the file `…/coder/candidates/<CC>/attempts/<AA>/spec.json`: what its bytes are (decision 2), how the `id` of its content stands to its path (decision 3), and by which steps the bytes come under the final name (decisions 4 to 7). It fixes **nothing else**: no section, field, type, value list or cross-field rule of ADR-0002 changes, and nothing `hilclaw.spec.validate` accepts for a parsed document changes. It says nothing of what composes or writes a spec, of when, of how the coder gets it, of `output/`, or of any other file.

### 2. The text form

- **A spec file is one JSON object**: exactly one JSON text, in UTF-8 without a byte order mark, with no member name twice in any object — the embedded records and the values of `task.objective`, `profile` and `ext` included (as ADR-0012 decision 2 and ADR-0018 decision 2 have it for their files). **The document it parses to is valid by ADR-0002** as that record stands; `schema_version` 1 is the only version a record defines.
- **Today's check of a parsed document** is `hilclaw.spec.validate`, cited as today's code with the limits of its docstring: it does not check what "one spec does not show" (that a ref names an earlier call, that a repair spec copies the sections of attempt 1, that no field carries verification inputs, among others). The three named here stay rules of ADR-0002; where they are checked is not decided here.
- **Numbers.** A number at a place where ADR-0002 or ADR-0001 gives *integer* — as the type of a member, of a value of a map or of an entry of an array, alone or as one of several types (`task.build`, `host`, a `shape`) — is written as a JSON number in decimal digits without sign, fraction or exponent (the words of ADR-0023 decision 3). `1.0` and `1e0` are no *integer*, though both denote one: one spelling per value, and it agrees with `hilclaw.spec`, which takes an integer member as exactly an `int`. `-0` is no *integer* either (as ADR-0023 decision 3 has it for its member): this one is a rule of the bytes only — an interpreter reads `-0` as the `int` 0, so the parsed document is one `hilclaw.spec.validate` accepts, and the file is invalid by its text. A number above 2^53 − 1 is no *integer* (cited: ADR-0001). **Where a number of another form can occur**: by the tables of ADR-0002 and its decision 4 only inside `task.objective` ("any JSON value"), inside a `profile` object (its members "are not listed and not validated in version 1") and inside a value of `ext` ("any JSON value"); `task.build` holds strings, integers and arrays of strings, and the embedded records hold names, strings and integers (cited: ADR-0001 — key fields hold "no float, boolean, null or array", and the attributes are a value list and a *string*). For those three places **this record adds no rule for a number beyond the grammar of JSON** (`NaN` and `Infinity` are no JSON): which numbers are values there belongs to the records that define those members (#5 A-4 and OD-1; OD-13; a later record of an `ext` member). The cost: two readers may hold a number of those places differently (a magnitude no double holds, an integer above 2^53 − 1), and nothing here says which is right.
- **Written form**: LF line ends and a final line feed bind the writer; a reader accepts any JSON text of this shape (as ADR-0018 decision 2). **No member order is fixed**, for the reason ADR-0018 gives for `instance.json`: an order serves line-wise diffs between the contents of a file that is rewritten (NFR-2), and a spec file has one content (cited: ADR-0002 decision 1). The specs of two attempts are two files; comparing them is not a diff of the history.
- **A file that is not valid.** The file is invalid when it is not UTF-8 without a byte order mark, is not exactly one JSON text that is an object, holds a member name twice in any object, writes a number of an *integer* place in another spelling than the one above, parses to a document that breaks a rule of ADR-0002, or breaks decision 3. An empty file is invalid, not missing. A reader of this record concludes from an invalid file that it is not the spec of any coder call: it is reported, no member of it is used, and nothing is repaired. **A file whose `schema_version` is an *integer* other than `1` is set apart**: it is not called damage and that conclusion is not drawn for it — what such a file is and how it is read is OD-11 (cited: ADR-0002 decision 7, "Reading older versions is OD-11"). A write by decision 4 writes a content of version 1 only, the one version a record defines.
- **The `schema_version` of the spec stays 1.** ADR-0002 decision 7 raises it "when a field outside `ext` and outside the embedded records is added or removed, or changes its type, meaning or requirement". None does: the rules above are about the bytes that carry a document. For `1.0` and `1e0` the written form of an *integer* is what the validator's `int` already implies; for `-0` it is a rule of spelling that changes no value a document holds.
- **A missing file** means that the tree holds no spec under that path (cited: ADR-0004 decision 1 — a missing directory means "nothing yet"). **It says nothing more** — in particular not that no coder call was made for that tuple, and not that the tuple is none of its round.

### 3. The `id` of the content and the path

- **The rule.** A file under a path `…/attempts/<AA>/spec.json` of the tree is a valid spec file only when the tuple of its `id` — `id.run_id`, `id.round`, `id.candidate`, `id.attempt` — formats to that path by ADR-0004 decisions 2, 3 and 8: `id.run_id` is the run directory name, and the three numbers are the round, candidate and attempt directory names in the digits fixed there (the path `hilclaw.layout.attempt_artefact` builds for the tuple, cited as today's code). It follows from the two cited sentences read together: the path is "the spec of" its tuple (ADR-0004 decision 3), and a spec "is found by that tuple" (ADR-0002 decision 1). The rule itself is this record's.
- **It is a rule about a file at a path, not about the payload.** A document that is valid by ADR-0002 and whose `id.run_id` is no run directory name (Context) stays a valid document: `hilclaw.spec.validate` accepts it as before. It has no path in the tree, so no file of the tree is a spec file with that content.
- **A write derives its final name from its content**: the final name of a write (decision 4) is the path the `id` of the held content formats to, below the data root the write is given. A write is given no other final name, so no write by the steps of this record puts a spec under the path of another tuple. Whether a function also takes the tuple as arguments and compares it with the content is the code task's; the final name is the same in both cases.
- **What a reader of this record concludes from a file whose `id` does not format to its path**: the file is invalid (decision 2). It is neither the spec of the tuple of its path nor the spec of the tuple it states. **What a component that finds such a file does next is not decided.**
- **Not said by the rule**: that the content belongs to the run in any other sense. The `hw_profile` of a spec is not compared with that of the run's `instance.json` (sub-question ⑱), and `id.candidates` is tied to nothing ([ADR-0028](ADR-0028-od8-instance-record-candidates-per-round.md) decision 5; sub-question ㉕ (ii)).

### 4. The requirement, the steps and a taken name

- **Requirement**: the death of the writing process leaves **no file under the final name or the whole one**, never a part of one — the requirement of ADR-0025 decision 2, taken for this file because a spec, too, has one content (cited: ADR-0002 decision 1) and no next write replaces a partial file.
- **The content first.** The writer holds the whole content as bytes before it touches the file system. That content is valid by decisions 2 and 3 as far as one content shows it, and is in the written form of decision 2. A content that is not valid is not written.
- **The write adds, substitutes and checks nothing beyond that.** The bytes that come under the final name are exactly those held first; no member is put in, taken out or filled in. **The write reads no other file and checks the content against none**: not the `instance.json` of the run, not `STATE.json` (decision 5), not the spec of an earlier attempt, not the `candidates_per_round` of ADR-0028, not a key record under `db/`. Each such check would fix an order of writes (sub-question ⑩) or a rule that ADR-0002, ADR-0018 or ADR-0028 left open (sub-questions ⑱ and ㉕ (ii); where a repair spec is compared with the spec of attempt 1, which no record says). Whether a function takes the content as bytes or builds the bytes from a document is the code task's.
- **The steps are those of ADR-0025 decision 3 with this file's values**: (1) the content first; (2) a new temporary file (decision 6) beside the final name, created new, holding the whole content; (3) its content brought to stable storage; (4) **a last step that gives the final name to the complete file only if that name does not exist, in one step, and otherwise changes nothing** — POSIX `link()` followed by the removal of the temporary name, or an operation of the platform that renames without replacing, the choice being the code task's, with **no fallback to a replacing rename**; (5) a failure before the final name is given removes the temporary file and is reported, and once the name is given the write has happened. The writer never opens the final name for writing.
- **Why the last step cannot replace.** A spec is "never changed afterwards" and "every spec is kept" (cited: ADR-0002 decision 1), and nothing enforces either (cited: ADR-0004 decision 10). With the replacing rename of ADR-0013, every write by the technique would be a means to replace a spec that was already there — silently, the earlier content gone from the working tree — and the file found by a tuple would no longer be the one first written under it (NFR-2). A look at the name followed by a replacing rename is two steps. The step is not a lock.
- **When the last step finds the name taken**: the write has written nothing under the final name, removes its temporary file, and **reports to its caller that the name was taken and that its content was not written** — told apart from the other failures, never as a write that happened. **This record decides no more about that report.** The write does not read the file under the name and compares nothing: no record defines a canonical form of a spec (ADR-0001 decision 3 defines one for the embedded key records only), no member order is fixed (decision 2) and three places of the payload hold values no record defines, so equal bytes are not what equal contents would mean. The form of the report is the code task's.
- **Not decided** (sub-question ㉖ (i)): what the caller does then, and **what a second write for a tuple means** — the first one continuing after a death, a call that takes the next attempt number, or a stop. It is the repeat rule of the coder call (OD-23, OD-19, OD-10; ADR-0011 only if a later record makes the call a journaled step).

### 5. The directories

- **The write may create every missing directory between the data root and the final name** (`runs/`, the run directory, `rounds/`, the round directory, `coder/`, `candidates/<CC>/`, `attempts/<AA>/` and those between): "a directory exists only when something was written into it" (cited: ADR-0004 decision 1), and this is such a write. **It requires neither the presence nor the absence of any of them, nor of any other file**: not `instance.json`, `STATE.json` or `decision/decision.md`, not the directory of an earlier attempt, not `output/`. Each such requirement would fix which file of a run or of a round is written first (sub-question ⑩), as ADR-0013 decision 6 and ADR-0025 decision 5 say for their files. **No sentence of this record fixes that order, or says which rounds, candidates or attempts exist.**
- **What follows from ADR-0012 decision 3, stated as it is.** By that decision "the round `round` itself has begun or not — which its directory at a known path shows". A write of a spec of round *r* by these steps can be the write that creates `rounds/<RRRR>/`. **This record adds no rule between the write and the `round` of `STATE.json`**: the write reads no file, so a spec whose `id.round` is not the round the run is at can be written by these steps, and nothing here refuses it. The sentences of ADR-0012 decision 3 about which rounds are over and which have not begun are not checked, narrowed or extended by this write. Whether anything must hold between the two, and what checks it, is sub-question ㉖ (iii). ADR-0004 decision 2 ("no file fixed here needs a write into the directory of an earlier round") is unchanged: this record requires no such write.
- **What a death leaves of the directories**: those that were created, holding no file of ADR-0004 or a leftover only. This record follows the reading of ADR-0004 decision 1 in ADR-0013 decision 6 without change (a statement about the tree as it is committed and as a reader may rely on it; no commit holds an empty directory, or a temporary file by decision 6). For a reader of the spec it is a missing file. **A round directory that exists in a working tree and holds no file of the tree is such a case; what it shows for ADR-0012 decision 3 is not decided here** (sub-question ㉖ (iii)). Whether a failed write removes the directories it created is the code task's.

### 6. The temporary file and a leftover

- **Place and name**: the attempt directory of the final name (one file system, the condition of `link()` as of `rename()` — cited: ADR-0013 decision 3, ADR-0014 decision 4), and the name `spec.json.<token>.tmp`, with `<token>` matching `[a-z0-9-]{1,64}` and different for every write: the form of ADR-0014 decision 4 with this final name.
- **It cannot be mistaken for a file of the tree**: the name is neither `spec.json` nor `output`, and it is no member of `layout.ATTEMPT_ARTEFACTS`, so `layout.attempt_artefact` refuses it.
- **Beside `spec.json`, not inside `output/`.** The attempt directory below `coder/` also holds `output/`, whose files and form are OD-23 and for which "how it gets there" is the isolation means (cited: ADR-0004, path table). The write creates no `output/`, puts nothing into it and neither reads nor lists it. **Nothing of `output/` is decided here.**
- **Readings of ADR-0004.** ADR-0013 decision 3 read decisions 2 and 7 for a temporary file in a run directory, and ADR-0014 decision 4 read the same way for `db/`. **For an attempt directory, which neither covered, this record reads the same way**: the tree and the path table of decision 1 list the files that have a meaning, that a reader may look for and that a commit holds, and a temporary file is none of them; decision 7 is about scratch, temporary and build-cache *directories* in which an actor works. **Where such directories are, and where the coder process works, is not decided or narrowed here.** The layout version (ADR-0004 decision 9) is unchanged, version 1.
- **Git.** A temporary file is **never committed**; the rule binds whatever step commits, and which step that is stays undecided. The `*.tmp` line of the data repository's ignore file matches the form (cited as a fact): a second guard, on which the rule does not rest. **No change to the data repository is made or required.**
- **A leftover** — a file of this name form whose write is no longer running — is ADR-0014 decision 5's and ADR-0025 decision 6's, with this final name: it is not the spec, is never read in the place of `spec.json`, is **never given the final name** (also when it holds a whole valid content: a write that did not reach the last step did not happen), and is never committed. A reader opens the final name only (#4 §1). A writer removes its own temporary file on a failure; a leftover of a dead writer **may** be removed and nothing requires it; a reader removes nothing. With `link()`, a death between the link and the removal leaves the temporary name as a second name of the written file, removed like any other leftover.
- **An attempt directory that holds a leftover and no `spec.json`** states what a missing file states (decision 2) and nothing more: a leftover is no sign that a call was tried.

### 7. What the rule promises and what it does not

| Moment (the final name not taken before the write) | On disk | The next reader of `spec.json` finds |
|---|---|---|
| The writing process dies before the temporary file is complete | No file under the final name; a temporary file holds a part of the content; directories as created (decision 5) | A missing file |
| It dies after the temporary file is complete and before the last step | The same, and the temporary file holds the whole content | A missing file. The write did not happen; the leftover is not used |
| It dies after the last step | The final name holds the whole content. With `link()`, a death before the removal leaves a second name: a leftover | The whole content |
| A step fails before the final name is given and the writer lives | No file under the final name; the temporary file removed where that is possible | A missing file; the caller is told of the failure |

At none of these moments does the final name hold a part of a content. When the name was taken before the write, it holds at every moment what it held.

- **Promised — the death of the writing process**, at any moment: the final name holds nothing or the whole content. **A reader during the write** finds a missing file or the whole file, never a part (cited: POSIX `link()` gives the name in one step).
- **Not promised — the loss of the machine, of power or of the working tree** before the next commit (cited: #5 A-3). The flush of step 3 is required nevertheless, for the reason of ADR-0013 decision 5 as ADR-0025 decision 7 weighs it for a file no next write replaces. The directory entry need not be flushed.
- **The environments**: as ADR-0025 decision 7 — the native file systems of the POSIX environments of C-7 that give the non-replacing step; a network file system, a Windows drive seen from WSL and native Windows are limits about which nothing is stated.
- **Two writers at once are a limit, not solved here** (the lock, rest of OD-17; C-2): each writes its own temporary file, one is given the name and the other finds it taken; the file is never a mixture.
- **"Never changed" is kept by the last step only against another write by these steps.** Nothing prevents a process from writing, replacing or removing the final name by other means (cited: ADR-0004 decision 10), and after a removal a write by these steps gives the name again.
- **Not said**: that the content is right beyond decisions 2 and 3; that a coder was called with it; **that the coder reads this file**; that the call the spec is for was or will be made. No atomicity is added between this file and any other file or a commit. A death after the last step and before the report leaves the whole file and a caller that was not told (sub-question ㉖ (i)).

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 2 | No text form: any bytes a JSON parser accepts | Two parsers differ on a byte order mark and on a member name twice; the file kept for NFR-2 would not have one reading. |
| 2 | A fixed member order, as ADR-0012 has | It serves diffs between versions of one file, and this file has one version; it would bind every composer for no reader. |
| 2 | A rule for every number (no fraction anywhere, or doubles only) | It would rule on values of `task.objective`, `profile` and `ext`, whose members wait for #5 A-4, OD-13 and later records. |
| 2 | The text rules as a new `schema_version` | No field changes by ADR-0002 decision 7's own rule; a new version before a first spec exists would only add a case to OD-11. |
| 3 | The write takes a path and a content and trusts both | A spec under another tuple's path would be a valid file, and "found by that tuple" would rest on every caller. |
| 3 | No rule between `id` and path | The same, for a reader: one path could hold the spec of another call without any file being invalid. |
| 3 | The path wins: a reader takes the tuple of the path and passes over `id` | It would make four required fields of ADR-0002 carry no meaning in a file, which that record does not say. |
| 4 | The replacing rename of ADR-0013 | See decision 4: every write could replace a spec that was already there, silently. |
| 4 | Exclusive creation of the final name in place | A death inside the write leaves a partial file under the final name, which nothing rewrites. |
| 4 | The write checks the content against `instance.json`, `STATE.json` or the spec of attempt 1 | Each would fix an order of writes or a rule the records left open (decision 4), and none is about how a content reaches the disk. |
| 4 | A taken name with equal bytes, or an equal document, is reported as written | No record says what "the same spec" is, and it would decide that a second write for a tuple is the first one continuing (sub-question ㉖ (i)). |
| 5 | The write refuses when the round directory is missing, or when `id.round` is not the `round` of `STATE.json` | The first would fix that another file of the round is written first; the second makes the write read `STATE.json` and fixes its order against the write that ends a round (sub-questions ⑩ and ㉖ (iii)). |
| 6 | The temporary file inside `output/`, or in a scratch directory | `output/` is OD-23's and the isolation means'; a scratch directory may be on another file system, where the last step is not one step. |
| 7 | Drop the flush | A power loss could leave an empty file under the final name, which no next write replaces (as ADR-0025). |

## Consequences

- **A code slice can now be cut** (code mode, within the size cap): a new module of the package that turns the bytes of a spec file into a document by the text rules of decision 2 and writes a valid content under the path of its tuple by the steps of decision 4, with its test file. Where it lives, its names, its call forms and what it raises are that task's; `hilclaw/instance_file.py` and `_store` of `hilclaw/key_records.py` hold the landed technique, and whether a helper is shared is that task's choice. It needs to tell apart: a content that is not valid, has no path or is not in the written form (before the file system is touched), a failure of a step, a name found taken, and a data root that does not exist (the convention of the package's other writers). **Binding it to a tool, to a coder call or to any caller is not part of that slice.**
- **Docstring sentences that then change**: in `hilclaw/spec.py`, the last paragraph — "The file name and location of a spec are not part of it (OD-8)" (the path is ADR-0004's and the file is this record's), and "This module reads and writes no file and builds no spec" only if the functions land in that module. `hilclaw/layout.py` stays true as it is.
- **The steps need a process that can create, flush, link or rename, and remove a file.** Whether that makes the writer go through a tool of the package is not concluded here (OD-23).
- **Handed to the isolation decision** (sub-question ㉖ (ii), beside ⑭, ⑯ and ㉓ (ii)): whatever writes a spec must be able to create, link or rename, and remove entries of the name form of decision 6 in the attempt directory, and to create the directories above it when they are missing. Neither candidate is chosen or excluded by this.
- **As long as the file is written by the steps of this record only, a commit taken at any moment takes no `spec.json` of a tuple or a whole one.** A write that does not follow this record is outside that statement.
