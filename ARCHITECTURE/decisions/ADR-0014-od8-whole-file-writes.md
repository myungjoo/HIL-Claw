# ADR-0014: How `artifacts.json` and the two key record files come to be on disk (sub-question ⑮ of OD-8)

## Status

- **Accepted on 2026-10-07** under [PROCESS/DRIVER.md](../../PROCESS/DRIVER.md) §9 (owner decision D6): written by the development driver's executor and accepted by the approval of a context-isolated reviewer. The owner has not confirmed it.
- Closes **sub-question ⑮ of OD-8** (Open Decisions register in [Requirements](../Requirements.md); registered by [ADR-0013](ADR-0013-od8-state-file-replacement.md)) for the three files that sub-question names: `runs/<run_id>/artifacts.json`, `db/<hw_profile_key>/hw_profile.json` and `db/<hw_profile_key>/<op_signature>/op_signature.json`. The "with OD-17" of its registration — two writers of one file — is **not** closed; it stays a stated limit (decision 6).
- What stays open of OD-8: **the isolation means** (candidates ① and ②, both kept), the members of `STATE.json` that ADR-0012 does not define, `instance.json`, the result files, the event kinds and payloads, the form of `run_id`, and the other registered sub-questions.
- It builds on ADR-0013 (decisions 2 to 6), [ADR-0005](ADR-0005-od8-artifacts-record.md) (decisions 2, 6, 7, 8 and 10), [ADR-0004](ADR-0004-od8-data-plane-layout.md) (decisions 1, 2, 5, 7, 9 and 10) and [ADR-0001](ADR-0001-od4-key-schema.md) (decision 3). The objection windows of ADR-0001 run until 2026-10-13 and those of the other three until 2026-10-14. If one of them is reverted, this record is revisited with it.
- The owner is notified on issue #5. The owner may object within 7 days of that notice; an objection creates a task that reverts this record and the edits made with it.
- The format follows the "Record format" section of ADR-0001.

## Context

- ADR-0013 fixed how `STATE.json` is replaced (the whole content first, a new temporary file beside the final one, stable storage, one rename, removal on a failure) and asked, as sub-question ⑮, whether "the other files that are rewritten as a whole — `artifacts.json`, the key record files" are written by the same technique. ADR-0005 left "atomic writes" open for `artifacts.json` (Boundaries) and ADR-0004 decision 10 says the tree "makes no write atomic beyond what a git commit gives".
- **`artifacts.json` is rewritten often.** `hilclaw/artifacts.py` rewrites the whole file for every record it adds and every class it replaces (not for a repeated add of a known hash, and not for a class that is already the given one). It opens the final name truncating, writes, and flushes the content to stable storage. A process killed inside that write leaves an empty or partial file. From then on every read and every write of the run's records raises `CorruptArtifactsError`, the module repairs nothing, and what is recovered is the file of the last commit — so **the records added since that commit are lost with the file**, although their blobs are in the store (ADR-0005 decision 8: blob first, then record).
- **A key record file is created once.** `hilclaw/key_records.py` creates each of the two files exclusively (a creation that fails when the name exists), writes, and flushes. It never modifies, replaces or deletes a stored record file; whether a stored attribute may be updated is OD-26. A process killed inside the write leaves a partial file, which is reported as `CorruptKeyRecordError` "until it is removed by hand" and blocks the key until then. So the wording of ⑮ ("rewritten as a whole") fits these two files only loosely: the question for them is how a file that must appear once, whole, comes to exist.
- ADR-0001 decision 3: "A tool that finds an existing directory whose stored canonical form differs from its own reports an error and writes nothing." ADR-0004 decision 5: the two files "are written when the directory is created", by "whatever creates its directory"; "a file name contains a dot and a key directory name never does"; of `best.json` and `technique_stats.json`, "their content, and any further file of a key directory, is OD-20 and OD-7".
- Both modules give "no path of `runs/` (`db/`) is a scratch location (ADR-0004 decision 7)" as the reason for writing without a temporary file. ADR-0013 decision 3 has since read that decision as one about scratch *directories*, for `STATE.json` only; it did not cover `db/`.
- Unchanged inputs: NFR-1 covers the death of a process; the local commit is the durability boundary (#5 A-3); P1 assumes one run (C-2) and the lock is the rest of OD-17; the environments of C-7 are POSIX; no directory is scanned at the entry of a turn (#4 §1). POSIX `rename()` replaces an existing name in one step; POSIX `link()` "atomically" creates a new name for an existing file and fails when that name exists. The `.gitignore` of `HIL-Claw-data` holds `blobs/sha256/` and, under "Local scratch", `*.tmp` and `.DS_Store`.

## Decision

A value below is **cited** when a source is named with it; every other value is **this record's own** choice — among them that both kinds of file take the steps of ADR-0013, that the last step of a key record file must be one that cannot replace an existing name and has no replacing fallback, the name form of the three temporary files, the readings of ADR-0004 decisions 1, 2, 5, 7 and 9 for them, the rules for a leftover in a key directory, and that the flush stays required.

### 1. Scope

This record fixes how the bytes of `artifacts.json` and of the two key record files come to be under their final names. It fixes **nothing else**: no member, value list or validity rule of ADR-0005 or ADR-0001 changes and nothing `hilclaw.artifacts.validate` or `hilclaw.keys` accepts changes; it says nothing of who writes either file, of any other file, of the lock, or of when a blob is removed.

### 2. `artifacts.json`: every rewrite is a replacement

A write of `artifacts.json` — the first one included — is a replacement by the five steps of ADR-0013 decision 2, with this file's values: (1) the whole new content is held as bytes before the file system is touched and is valid by ADR-0005 decisions 2, 3 and 6; (2) it is written into a new temporary file (decision 4) in `runs/<run_id>/`; (3) that content is brought to stable storage; (4) the temporary file is renamed over `artifacts.json` (POSIX `rename`); (5) a writer that lives through a failure removes its temporary file and reports. The final name is never opened for writing.

- **What the new content is** stays ADR-0005's: the previous records with one record appended or one allowed edit (decision 7). The writer therefore reads the file before it writes; this record adds no rule for a previous file that is invalid (today's module reports it and writes nothing).
- **The first file**: the "previous content" is the missing file, which means "no blob recorded" (cited: ADR-0005 decision 2). The replacement may create `runs/<run_id>/` and `runs/`, as ADR-0013 decision 6 allows for `STATE.json` and as the module does today.
- **Gained beyond the case of `STATE.json`**: this file accumulates between commits. Under the in-place write, the death of the writer of the k-th record of a round destroys the k − 1 records before it in the working tree; under a replacement they stay. "Blob first, then record" is unchanged: a death before step 4 leaves a blob without a record, which ADR-0005 decision 8 calls harmless.

### 3. The key record files: created once, by a step that cannot replace

- **Requirement**: the death of the writing process leaves **no record file or the whole one** under the final name, never a part of one. A partial file blocks its key until a person removes it.
- **Steps 1 to 3 and 5 are those of ADR-0013 decision 2**: the whole content, valid by ADR-0001 (what `hilclaw.keys` accepts), is held first; it is written into a new temporary file (decision 4) in the key directory of the record; it is brought to stable storage; a writer that lives through a failure removes its temporary file. The writer still looks for a stored record first and applies ADR-0001 decision 3 to what it finds; that check is unchanged.
- **The last step gives the final name to the complete file only if that name does not exist, in one step, and otherwise changes nothing.** A rename that replaces is **not** this step. Reason: a replacing move would put the writer's record over a record that appeared after the writer's check. With an equal canonical form and other attributes that is an update of a stored attribute, which OD-26 has not allowed; with another canonical form it is a write where ADR-0001 decision 3 says "writes nothing". The exclusive creation of today's module already has the property (of two creators, one fails and nothing is replaced); the requirement keeps it and adds nothing to it. It is not a lock: it orders nothing and makes no writer wait.
- **How**: POSIX `link()` from the temporary name to the final name, followed by the removal of the temporary name, is such a step (cited: it fails when the final name exists). An operation of the platform that renames without replacing is another. Which one is used is the code task's. **There is no fallback to a replacing rename**: where no such operation works (a file system without hard links), the write fails with an error and stores nothing.
- **When the last step finds the name taken**, the writer has written nothing under it and removes its temporary file. The record now under the name is a stored record like any other the writer could have found before it started, and ADR-0001 decision 3 applies to it: a canonical form that differs from the writer's is an error. Only the form of what the function reports is the code task's.
- **The directories.** The write may create the directories above the final name that are missing (`db/`, the hw_profile directory, the op_signature directory), since "a directory exists only when something was written into it" (ADR-0004 decision 1). A death after a directory was created and before the last step leaves a key directory that holds no record file — empty, or with a leftover only. This record reads ADR-0004 decision 1, and "written when the directory is created" of its decision 5, as ADR-0013 decision 6 read decision 1: as statements about the tree as it is committed and as a reader may rely on it. Git holds no empty directory and no temporary file, so no commit has such a directory. The window exists today (the module creates the directories before the file). For a reader, such a directory is a key that is not stored — a convention of `hilclaw/key_records.py` ("a key is stored if and only if its record file exists as a regular file"), cited as such and unchanged by a leftover. Whether a failed write removes the directories it created is the code task's; whether an op_signature directory may exist below a hw_profile that has no record is not decided here.

Whenever the writing process dies:

| The writing process dies | The next reader of `artifacts.json` finds | The next reader of a key record file finds |
|---|---|---|
| Before the temporary file is complete | The previous records, or a missing file (no blob recorded) | No record file: the key is not stored |
| After the temporary file is complete and before the last step | The same. The write did not happen; the leftover is not used (decision 5) | The same |
| After the last step | The new records. No temporary file of this write exists | The whole record. With `link()`, a death before the removal leaves the temporary name as a second name of the record file: a leftover (decision 5) |

At none of these moments does a final name hold a part of a content.

### 4. The temporary files

- **Place**: the directory of the final file, for the reason of ADR-0013 decision 3 (one file system; `link()` has the same condition as `rename()`).
- **Name form**: `<final name>.<token>.tmp` — `artifacts.json.<token>.tmp`, `hw_profile.json.<token>.tmp`, `op_signature.json.<token>.tmp` — with `<token>` matching `[a-z0-9-]{1,64}` and different for every write. This is the form of ADR-0013 decision 3 with another final name, and "why the name differs per write" holds as written there: with one fixed name two writers would share a temporary file.
- **They cannot be mistaken for a file of the tree.** In a run directory: the name is none of the four run-level names and no member of `layout.RUN_FILES`. In a key directory: the name contains a dot, so it is no key directory name (cited: ADR-0004 decision 5) and `hilclaw.layout` refuses it as one; a reader that lists a hw_profile directory to find its op_signature directories passes over it as it passes over `hw_profile.json`. It is none of `hw_profile.json`, `op_signature.json`, `best.json`, `technique_stats.json`. This record reserves no name: a later record that gave a file of the tree a name of this form would have to say how that file is told from a leftover, and the naming of such files stays with their records.
- **Readings of ADR-0004.** For `runs/<run_id>/`, this record follows the readings of decisions 2 and 7 in ADR-0013 decision 3 without change. **For `db/`, which that record did not cover, it reads the same way**: decision 5 lists the files of a key directory that have a meaning, that a reader may look for and that a commit holds, and its sentence that any further file of a key directory is OD-20 and OD-7 is about such files; a temporary file is none of them, so nothing of OD-20 or OD-7 is decided or narrowed. Decision 7 is about scratch, temporary and build-cache *directories* in which an actor works; a temporary file of the write of one file, in the directory of that file, is not one. **Where scratch and build-cache directories are is not decided or narrowed here.**
- **Layout version** (ADR-0004 decision 9): unchanged, version 1; `db/` still needs no stamp of its own. No path, file name or number form changes.
- **Git.** A temporary file is **never committed**, in `runs/` or in `db/`. The rule binds whatever step commits; which step that is stays undecided. The `*.tmp` line of the data repository's ignore file matches the form (cited as a fact): a second guard, on which the rule does not rest. **No change to the data repository is made or required.**

### 5. A leftover

- A **leftover** is a file of the name form of decision 4, in a run directory or a key directory, whose write is no longer running.
- **It is not a record.** Whether it holds a part of a content or a whole valid one, it is never read in the place of the final file — not when that file is missing, and not when it is invalid — and **never given the final name**: the write it belonged to is over, and for `artifacts.json` the final file may hold records the leftover lacks. It is never committed.
- **A key is stored if and only if its record file exists** (the module's convention, decision 3). A leftover in a key directory, alone or beside other files, does not make the key stored and does not make a stored key anything else.
- **A reader needs no listing**: it opens the final name only, so no directory is listed because of a leftover (#4 §1).
- **Removal**: a writer removes its own temporary file on a failure. A leftover of a dead writer **may** be removed by a writer of that file, and **nothing requires it**; a reader removes nothing. A leftover that is a second name of a stored record file (decision 3, `link()`) is removed like any other: the record keeps its final name. No writer opens an existing temporary name, so such a leftover is never written through.

### 6. What the rule promises and what it does not

- **Promised — the death of the writing process**, at any moment: for `artifacts.json` the final name holds the previous records or the new ones, whole; for a key record file it holds nothing or the whole record. **A reader during a write** sees one of these two states and never a mixture.
- **Not promised — the loss of the machine, of power or of the working tree** before the next commit (cited: #5 A-3). The flush of step 3 is required for all three files nevertheless, for the reason of ADR-0013 decision 5; the directory entry need not be flushed. Both modules already flush the content on every write today, so the rule adds one creation and one rename (or link and removal) per write, not a flush.
- **Cost for `artifacts.json`**: one replacement — a whole-file write and a flush — for every blob a run records for the first time and for every class change. How many that is per round no record says (which binaries are blobs is OD-23). The whole-file rewrite and its growth with the number of records exist today and are ADR-0005 decision 2's shape; they are named here as a cost and not measured.
- **The environments**: as ADR-0013 decision 5 — the native file systems of the POSIX environments of C-7; a network file system, a Windows drive seen from WSL and native Windows are limits about which nothing is stated. For a key record file the file system must also give the non-replacing step of decision 3.
- **Two writers at once are a limit, not solved here** (the lock, rest of OD-17; C-2). For `artifacts.json`: each writer reads, builds and moves a whole content, the later move wins, and a record the other added in between is missing afterwards although its blob is stored. This lost update exists today and remains (ADR-0005 decision 10: "the file may therefore miss a blob that was stored"); what changes is that the file is never a mixture of two writes. For a key record file: the first writer's record stays and the other writes nothing, as today. A writer that removes leftovers can remove the temporary file of a live writer, whose last step then fails and changes nothing.
- **No atomicity is added** between the store and the file, between `artifacts.json` and `STATE.json` or `events.ndjson`, between the two key record files, or between any file and a commit (ADR-0005 decisions 8 and 10 and ADR-0004 decision 10 unchanged). Nothing says the content is right beyond what step 1 checks. Bringing a file back from the history is not a write of this record.

### 7. Other files

This record covers **three files** and states no rule for "every file of the data plane". Whether `instance.json`, `spec.json`, the result files, `best.json` or `technique_stats.json` are written this way is **not decided**: their content, their writers and whether they are ever rewritten are open (OD-20, OD-7, OD-23, OD-11). A later record for such a file may refer to ADR-0013 and to this record instead of repeating them. `events.ndjson` is an append (ADR-0006) and `STATE.json` is ADR-0013's.

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 2 | Keep the in-place write and rely on the last commit (today) | A death inside one write costs every record added since the last commit and stops the run's blob records until a person restores the file. |
| 2 | A recovery rule: rebuild a partial file from the store or from the files of the rounds | Not possible from what exists. The store holds bytes by hash for all runs: it has no `type`, `round` or class, and "a blob in the store without a record in this file" may be another run's (ADR-0005 decision 8). A record "does not say which attempt, file or tool" uses its blob (decision 10), the files that name a blob by hash are not defined (OD-23), and the class is state that no other file holds. A repairing reader is also against the convention of today's module ("nothing is written or repaired"), and no record gives a reader that duty. |
| 2 | An append-only form of the file (one record per line) | A change of ADR-0005 decision 2, which rejected that form because records are edited; outside what this record may do. |
| 3 | The replacing rename for a key record file as well, the window stated as a limit of two writers | It would turn "the second writer writes nothing" into "the second writer's attributes win", an update rule OD-26 has not given, and it gives up a property the code has today. |
| 3 | Accept the replacement when the content is equal | The comparison and the move are two steps; the file compared is not necessarily the file replaced. |
| 3 | Keep the exclusive creation of the final name and add a recovery rule for a partial file | A reader would have to tell a partial file from a damaged one and remove it, and a second creator would meet the partial file. |
| 3 | A replacing rename where the non-replacing step is unavailable | The same write would then keep or lose the property depending on the file system, silently. |
| 4 | One fixed temporary name per final file; a hidden name; a subdirectory | As ADR-0013 (Alternatives, point 3). In a key directory a subdirectory without a dot would also be a key directory name candidate. |
| 5 | A complete leftover is given the final name by the next writer | For `artifacts.json` it may lack records added since; for a key record the write it belonged to did not happen (ADR-0013 decision 4). |
| 6 | Drop the flush for `artifacts.json` because it is rewritten often | It is done today; without it a power loss can leave an empty file under the final name (ADR-0013 decision 5). |
| 7 | One rule for every file of the data plane that is written as a whole | It would decide for files whose content, writer and lifetime are open. |

## Consequences

- **A code slice can now implement both writes**: `_write` of `hilclaw/artifacts.py` as a replacement and `_store` of `hilclaw/key_records.py` by the steps of decision 3. Docstring sentences that then change: "written in place, without a temporary file: no path of `runs/` is a scratch location", "a file that existed stays as the failed write left it, possibly partial; so can a process killed while it writes" (`artifacts.py`); "created exclusively, without a temporary file (no path of `db/` is a scratch location …)", "can leave a partial file, which is then reported … until it is removed by hand" (`key_records.py`). `hilclaw/artifacts.py` is at 298 of 300 lines, so how the slice is cut is the planner's. Whether the three writers (`run_state_file`, `artifacts`, `key_records`) share a helper is that task's choice.
- **Handed to the isolation decision** (sub-question ⑯, beside ⑭): a writer of `artifacts.json` or of a key record file must be able to create, rename or link, and remove entries of the name form of decision 4 in the run directory and in the key directories, and to create those directories and `runs/` or `db/` above them when they are missing. Neither candidate is chosen or excluded by this.
- **The steps need a process that can create, flush, link or rename a file.** Whether that makes a writer go through a tool of the package is not concluded here (OD-23).
- `hilclaw/layout.py` is consistent and unchanged; the readers of both modules already open the final name only and follow no symbolic link.
- **Not edited and now less exact** (follow-ups for the integrator): ADR-0005 Boundaries ("Locking, concurrency and atomic writes (OD-17, C-2)" — the write of the file itself is now fixed; decision 10 stays true as written); ADR-0013 Consequences ("`artifacts.json` is written in place today … sub-question ⑮") and Boundaries (⑮ is answered); ADR-0004 decision 5 ("written when the directory is created" and the list of files, for a working tree between two commits) and decisions 1 and 2 as in ADR-0013; the two docstrings above; the README of `HIL-Claw-data`. No sentence of UsageCases became false.
- **A-13 reading**: document mode; no code, dependency or schema file changes. No member, type or validity rule of `artifacts.json` or of a key record changes, so this is not a schema change of artifacts: the record adds a rule about how the files come to be on disk.
