## Decision

A sentence marked **owner** renders one of the two sentences quoted in Context. A value is **cited** when another source is named with it. Every other value is **this record's own** choice — among them the name `candidates_per_round`, its place, the written form, that the rule of validity starts at 1 and has no end below the *integer* range, that the member may be absent, that an absent member means "not stated" and never 1, that a present and invalid member makes the file invalid, that no rule ties the member to a spec, and the list of limits.

### 1. Scope

This record fixes one thing of `runs/<run_id>/instance.json`: the member in which a run states its number of candidates per round. Nothing else of the file is fixed and nothing of any other file. **A file that holds what ADR-0018, ADR-0020, ADR-0022, ADR-0023, ADR-0024 and this record define is still not a complete instance record, and no run can be started from it alone** (ADR-0018 decision 1).

### 2. What the member states

- **The member states the N of FR-1 for the run**: the number of candidates per round the instance was started with. **Owner**: N is "a Loop-instance parameter chosen by the user at instance start". The meaning is the owner's and FR-1's; this record gives it a place and adds nothing to it.
- **What a reader of this record may conclude** from a file that states the member: that the run states this number as its candidates per round. No more.
- **What it may not conclude.** The member is not k, the number of candidates promoted to the board (OD-29, OD-15). It is not a number of coder calls or of specs: a round with N candidates and r repair calls has N + r specs (cited: ADR-0002 decision 1). It is not a number of attempts, of rounds or of measurements. It says nothing about parallel or sequential coder calls and is no cap of cost per candidate (OD-29, OD-19). It does not say that any round of the run had, has or will have that many candidates: nothing checks it (decision 6), and what a spec says of its round is the spec's (decision 5).
- **It is no budget member** — a reading of this record, the one ADR-0023 decision 2 made of the same heading for `n_max`. The member states no amount of time, of hardware quota or of tokens (OD-2, OD-19), and it is none of the four axes FR-3 lists today (loop iterations, tokens, wall-clock time, a target metric): FR-3 ends a run when an axis is used up, and N is not used up. **Owner**: the line of #5 B-4 stands under a heading that has cost "controlled by instance parameters (FR-3)". This record takes the run caps of that line for such parameters and reads the heading as saying that N is an instance parameter that controls cost — which the member is (decision 6) — and not as making it an axis of the budget vocabulary; the owner's line itself names "budget 5–10 rounds" beside N and apart from it.
- **The "N = 1–2" of that line** is read as the owner's cap for the initial runs — a statement about what those runs are started with, not about what a file may state. This record takes no number from it, and what applies that cap is not decided (sub-question ㉕).
- **One value per run, and what that covers.** The inputs carry one value per instance (**owner**: an instance parameter, chosen at instance start) and the file is written once (cited: ADR-0004 decision 4). They do **not** carry, and this record does not decide: whether round 0 (bring-up and baseline) has N candidates (OD-28; ADR-0002 Boundaries, "what round 0 does beyond FR-1"); whether a round may hold fewer candidates than N, for example when a budget is used up inside it (OD-19, OD-29); and how a continuation or a branch of a run under another N relates to a file that is written once (OD-8 sub-question ①; FR-6). A record that gives a run more than one N changes this member or adds one, and applies the version rule of ADR-0018 decision 2.

### 3. The member

- **The member is `candidates_per_round`**, a top-level member: an *integer* of ADR-0001 (0 to 2^53 − 1, the form ADR-0018 decision 2 uses for `schema_version`) that is **at least 1**.
- **Written form**: that of ADR-0023 decision 3 — a JSON number in decimal digits without sign, fraction or exponent. **`2.0` and `2e0` are no values**, though both denote two: one spelling per value, and it agrees with what `hilclaw/instance.py` accepts for `n_max` and `hilclaw/spec.py` for `id.candidates` (exactly an `int`).
- **Nothing else is a value**: `true`, `false`, `null`, a string (`"2"` included), an array, an object, `0`, `-0`, every negative number and an integer above 2^53 − 1.
- **The name** is this record's choice. "Candidates per round" are the owner's words for N, FR-1's ("라운드당 후보 수") and ADR-0001's (decision 5, among the instance parameters that are not key fields); the name says what is counted and per what. Weighed against it:
  - `candidates`, the word of `id.candidates`: one name would let the number be followed from the file to a spec. But at the top level of this file the bare word does not say "per round", and one name in two files would suggest the rule between the two numbers that decision 5 does not make.
  - `n`: the letter of the documents. It says nothing by itself and would stand beside `n_max`, which does not bound it (ADR-0023 decision 6, "The name is near N").
  - A member inside an object that groups search parameters or run caps: no other member of such an object has a fixed form — k, the execution mode and every budget member are open — so the object would be shaped by members that do not exist (the reason of ADR-0023 decision 3).
- **The lower end is the number 1.** The number is ADR-0002's for `id.candidates` — an integer of at least 1, with `id.candidate` counting from 1 (decision 2). Taking it as the rule of this member is this record's own choice, since no input states a lower end for the instance parameter itself: a round of FR-1 generates candidates, and a file that stated 0 would describe an instance no round of which generates code. The range the owner names for the initial UI begins at the same number; this record does not rest the rule on that (see the next item).
- **No upper end below the *integer* range — the 1-to-5 range is not a rule of validity.** **Owner**: "the initial UI offers 1 ≤ N ≤ 5 (policy may change later)". That sentence speaks of what the initial UI offers and calls it a policy that may change; it does not say what a file may state. The other inputs set no end: `id.candidates` has "no upper bound" in the schema (cited: ADR-0002 decision 2), "the tree sets no upper bound on … N" (cited: ADR-0004 decision 3), and N is taken as a parameter "that nothing may hard-code" (cited: ADR-0002 Context). The file is written once: a 5 in its rule would turn a change of that policy into a change of the form of this member, which raises `schema_version` (ADR-0018 decision 2), and a version 1 reader would then refuse the whole file of a run started under the wider policy. So the rule of version 1 is "at least 1" and no more. **What follows, plainly: a valid file may state a value the initial UI would not offer (6, 100), and nothing in this record refuses it.** The range belongs to whatever offers the user the choice at the start; what that is, with which range, and whether anything at the start checks the chosen value against it is **not decided** (sub-question ㉕). With this rule every value of the member is also a value `id.candidates` may hold.
- **A valid value is not thereby one a run can be carried out with**: every candidate is at least one coder call, and Claude Code is used under one Max subscription (C-7 ②; that nested coders share its limit is how the OD-29 row reads it) (decision 6).
- **In version 1 a run states at most one N**: the member is one integer.

### 4. A file without the member; the version

- **The member may be absent from a valid file, and `schema_version` stays `1`** — the first of the two choices ADR-0018 decision 2 leaves to the record of a member ("A later record that defines a top-level member which may be absent and may be passed over does not raise it"). A version 1 reader may pass over the member: no fixed rule makes anything a reader of today does depend on it, and a reader that needs the N of a run is one that knows the member.
- **A member that is present must be valid.** A file whose `candidates_per_round` breaks decision 3 is **invalid** in the sense of ADR-0018 decision 2: a reader of this record reports it, uses no member of it — not its `hw_profile`, its `tolerance`, its `source_commit` or its `n_max` either — and repairs nothing. This follows ADR-0020 decision 3, ADR-0022 decision 5 and ADR-0023 decision 4.
- **A valid file without the member states no N.** A reader of this record that is asked for the candidates per round of such a run finds that none is stated and **never substitutes a value — in particular not 1**, not a number of the owner's ranges (5, 2), not a constant of the source the reader runs from, not a number taken from a spec or counted from the directories of the run, and not a value from another run.
- **Why "N = 1 as a special case" is no default.** The phrase (ADR-0002 Context; the design constraint listed with OD-29) asks that everything work when N is 1 — `single` is that case in a spec. It does not say that an instance which names no N has N = 1, and no source does: **owner**, N is "chosen by the user at instance start", and UC-1 lists it without "(선택)".
- **How the owner's sentence reads with an absent member allowed.** It is about what the start of an instance has from the user. A valid file is "not thereby enough to start a run" (cited: ADR-0018 decision 2), and by this record a valid file that is silent gives a round of the run no N. Whether the start of an instance refuses to begin without an N, and where it is checked that an instance states one, is the writer's and is not decided (sub-question ㉕).
- **No path yields an N the run did not state.** A reader of this record has the N of a run only when the file of that run is valid, is of version 1 and holds the member. A missing file, a file that cannot be read, an invalid file, a file of another version and a valid file without the member each leave it without one.
- **Why not a required member and version 2.** The inputs would bear a required member better here than for the earlier members: the user states N at the start. It is still not chosen: every file and every reader of today would be of another version before a first run exists, the record would have to say which layout version the new `schema_version` states (ADR-0024 decision 3), and reading another version is OD-11. Whether an instance without an N may start is then answered where the start is decided, not by the validity of the file.
- **The cost**: validity does not show that an N is stated. A file without the member and a file whose member name is misspelt look alike to a version 1 reader — both state none (decision 6).

### 5. The member and `id.candidates` of a spec; how the N of a run is read

- **This record adds no rule between the member and `id.candidates`.** The member is where the instance parameter is recorded; a spec says what its round has ("N of this round", cited: ADR-0002 decision 2). What FR-1 and ADR-0002 say stands as they say it, and ADR-0002 is not edited: a spec is valid or invalid by ADR-0002 alone, whatever the file of its run states, and no validator of this record reads a spec.
- **Why none.** A rule "equal in every round" would decide what round 0 does (OD-28) and that no round is cut short (OD-19, OD-29); a rule "equal in the rounds after round 0" would decide the same for those rounds, and either would bind whatever issues the specs, which no record has named (OD-23; PLAN P2). The member has its meaning without such a rule (decision 2). So a reader of this record may not conclude the `id.candidates` of any spec from the member, nor the N a run states from a spec. Whether the two must be equal, for which rounds, and what checks it is registered (sub-question ㉕).
- **The N a run states is the one in this member of the file of that run**, `runs/<run_id>/instance.json` below the data root in use. A reader of this record reads the file as a whole, which must be valid (ADR-0018 decision 2), and **nothing is kept between calls** (cited: ADR-0010 decision 7; ADR-0018 decision 4): a later call reads the file again.
- **A value from elsewhere is not what the run states and does not stand in for it**: the `id.candidates` of a spec, a count of `candidates/<CC>/` directories, a value kept from an earlier call, a constant of the source the reader runs from.
- **Today nothing reads or writes the member**: no tool, registry, backend, hook or module does, `hilclaw/instance.py` passes it over, and nothing in `hilclaw/` issues a spec. **Not said here**: which component reads it, at which moment, and what follows when no N is stated (Boundaries).

### 6. Limits

- **Whoever can write the file changes the N of a run.** No access control exists and the tree does not enforce the single writer (cited: ADR-0004 decision 10); a file changed after the start is read as it is at that read (cited: ADR-0018 decision 6), so two reads of the file of one run can find two values.
- **Nothing checks that a round had the stated number of candidates**, and no file records the N a round was carried out under beyond what the specs of the round say of themselves (Boundaries).
- **A misspelt name.** A top-level member that is not spelt `candidates_per_round` (`candidates`, `n`, `candidatesPerRound`) is passed over (cited: ADR-0018 decision 2, the cost) and the file states no N — never 1.
- **Two processes, two sources** (cited: ADR-0010 decision 7; ADR-0018 decision 6): a source older than the code of this record passes over the member and takes as valid a file whose `candidates_per_round` a newer source refuses.
- **A large value is a cost this member does not cap**: every candidate is at least one coder call under the one subscription of C-7 ② (that nested coders share its limit is how the OD-29 row reads it), the board is a shared and limited resource (C-4), and nothing here limits what a run may state below 2^53 − 1 — the 5 of the initial UI included. Limiting the cost of a run is the budget (FR-3, OD-2, OD-19), which this member is not.
- **The member does not say how many candidates reach the board** (k: OD-29, OD-15).

### Walk-through

What a reader of this record finds when it is asked for the candidates per round of the run `r1`.

| `runs/r1/instance.json` | What the reader finds |
|---|---|
| Valid, version 1, with `"candidates_per_round": 2` | The N `r1` states: 2. Asked again in a later call, it reads the file again |
| Valid, version 1, without the member (or with `"candidates": 2`) | No N is stated for `r1`. No value is substituted, 1 included. The `hw_profile`, the `tolerance`, the `source_commit` and the `n_max` of the run can still be had |
| `"candidates_per_round": 0`, `-1`, `2.0`, `2e0`, `"2"`, `true`, `null`, `[2]` or `9007199254740992` | The file is invalid: no member of it is used, neither the N nor the `hw_profile`, the `tolerance`, the `source_commit` or the `n_max` |
| Valid, version 1, with `"candidates_per_round": 6` (or `100`) | The N `r1` states: 6. The file is valid: the 1-to-5 range of the initial UI is no rule of this record, and nothing here refuses the value or says what a round does with it |
| Missing, unreadable, or of another version | No N can be had, as ADR-0018 has it for the `hw_profile` |
| `r1` states `"candidates_per_round": 1` and `runs/r2/instance.json`, below the same data root, states `"candidates_per_round": 3` | Asked for `r1` the reader finds 1, asked for `r2` it finds 3: each from the file of the run it is asked about, and nothing of one is used for the other |

## Consequences

- **The code slice that can now be cut** (within the size cap, code mode): in `hilclaw/instance.py`, the validity of the member by decision 3 and a reader of the N of a run beside `n_max_of`, with tests in `tests/test_instance.py`. The name and the return form of that reader and how "not stated" is told from a value are the code task's. **Binding the reader to a spec, to a tool or to anything that issues specs is not part of that slice**, and neither is writing the file. `hilclaw/instance_file.py` takes the validity of a content from `hilclaw.instance.parse`, so it refuses a content with an invalid member once the slice lands, without a change of its own.
- **Sentences of the code that then change**: in the docstring of `hilclaw/instance.py`, "It defines no member besides the five (`schema_version`, `hw_profile`, `tolerance`, `source_commit` and `n_max`) and interprets no other", "Conventions of this module, which the five records do not fix", the order of the checks, and the descriptions of `Instance.others` in `parse` and of the records in `validate`. No case of `tests/test_instance.py` holds a `candidates_per_round` member today, so none asserts a content valid that this record makes invalid; the assertion on `Instance._fields` and every case that builds an `Instance` positionally (among them `test_members_not_defined_are_returned_as_parsed_and_not_interpreted` and the three cases `test_a_top_level_member_of_another_name_states_no_tolerance`, `..._no_source_commit` and `..._no_bound`) change only if the slice adds a field to that tuple.
- **Not edited and now less exact** (follow-ups for the integrator): ADR-0018 Boundaries and ADR-0023 Boundaries, which list "N per round and its bounds (OD-21, OD-29)" among the members of later records, and through the list of ADR-0018 the Boundaries of ADR-0020 and ADR-0022; ADR-0023 decision 3 ("No name is given here for N") and reading 2 of its notice on #5; the list of what makes `instance.json` invalid in ADR-0018 decisions 2 and 4 and in ADR-0019 decision 3, which a `candidates_per_round` that breaks this record joins; ADR-0020 decision 3, ADR-0022 decision 5 and ADR-0023 decision 4, where the members of an invalid file that are not used now have one more beside them; ADR-0025 decision 2 and its Boundaries, where the members a valid content may lack now have one more. - **A-13 reading**: document mode; no code, dependency, settings file or schema file changes.
