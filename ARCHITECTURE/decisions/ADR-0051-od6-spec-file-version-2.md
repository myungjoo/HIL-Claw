## Context

- **What ADR-0029 fixed, and for which version.** It fixed three things of the file `…/coder/candidates/<CC>/attempts/<AA>/spec.json`: its bytes, how the `id` of its content stands to its path, and the steps by which the bytes come under the final name. In it `task.objective` is an object with defined members, one of which, the `bound` of a constraint entry, is an *integer*. "This record is about the parsed document, not about a file." Its limit L8: it "does not say how it is spelt in a file", nor that the rules of ADR-0029 carry over. It registered the gap as sub-question ⑤ of OD-6, in three parts: whether the rules of ADR-0029 carry over, the spelling of `bound`, and what a writer and a reader of version 1 and of version 2 do beside each other.
- **What is open beside it and is not an input.** ADR-0002 decision 7: "Reading older versions is OD-11." OD-11 is open. NFR-7 ② asks that for every persistent artefact "구버전 데이터의 읽기 또는 마이그레이션이 보장"; and, in its next sentence, that "FR-6 재개는 시스템 버전이 달라진 후에도 성립". Which of the two means, and from when, is the owner's: the registered proposal of OD-11 narrows that wording and is, by its own text, not to be reflected in NFR-7 ② "오너 확정 없이" ([OpenDecisionProposals OD-11](../OpenDecisionProposals.md#od-11)).

## Decision

A value below is **cited** when a source is named with it and is the **owner's** where O4 is named; every other value is **this record's own** choice — among them that the rules of ADR-0029 are carried over by reference and with which changes (decision 1), that the spelling rule of an *integer* place reaches `bound` (decision 2), which version a write under these rules writes, the wording of what a reader concludes from a file of another version and that nothing is said of two versions in one run (decision 3), and the reading of the layout version (decision 4).

**Words used below.** A *version-1 file* and a *version-2 file* are files under a spec path whose `schema_version` is the *integer* `1` or `2`. *The rules of version 1* are ADR-0029 as it stands. *The rules of version 2* are this record: ADR-0029 by reference with the changes of decisions 1 to 3. A reader or a writer *of version N* is one that follows the rules of version N.

### Limits

What the statements of this record do not cover, stated before them.

- **L1 — A record, not code.** Nothing accepts, reads or writes a version-2 spec file today: the package follows the rules of version 1 until the code slice of Consequences lands. No file, schema file or example is added.
- **L2 — The validity of a file reaches no further than the validity of its document.** A version-2 file is valid only when its document is valid by ADR-0050, and what that record leaves outside validity stays outside (its L1 to L3). In particular "Two readers of version 2 can differ in the type values they admit" (cited: ADR-0050 L5): a file one reader of version 2 holds valid another may hold invalid, the number 2 in the file does not tell the two readers apart, and **this record does not change that**.
- **L3 — The promises of the write are those of ADR-0029 decision 7 and no more.** The death of the writing process is covered; the loss of the machine, of power or of the working tree before the next commit is not. The environments are the native file systems of the POSIX environments of C-7 that give the non-replacing step; "a network file system, a Windows drive seen from WSL and native Windows are limits about which nothing is stated" (cited). "Two writers at once are a limit, not solved here" (cited).
- **L4 — No reading of another version.** This record gives no guarantee that a spec of an older version is read, no migration, and no rule for a run that meets a file of another version. For spec files it therefore **does not meet NFR-7 ② and does not claim to** — neither its guarantee of a reading or a migration nor its sentence that a resumption under FR-6 holds after the system version has changed; that requirement stands as written, and how it is met is OD-11. Nor does it claim that a move of the package to version 2 while a run is in progress meets the second half of NFR-7 ①, that a replaced component must not break such a run: by decision 3 the earlier specs of that run are then interpreted by no reader of these rules, and whether that breaks the run is OD-11 and OD-18.
- **L5 — Two places keep numbers without a rule.** Inside a `profile` object and inside a value of `ext` this record adds no rule for a number, as ADR-0029 did not: two readers may hold a number of those places differently.
- **L6 — Nothing was run.** No validator of version 2 exists, no version-2 file was written or parsed, and no test was added. The statements about the code are read from the sources of `main`.
- **L7 — The facts of today are not rules.** That no spec file is stored anywhere (Context) is true on the day it was checked and binds nothing.

### 2. Numbers in a version-2 file

- **The rule of ADR-0029 decision 2 for an *integer* place holds for a version-2 file, and `bound` is such a place.** ADR-0029 binds "A number at a place where ADR-0002 or ADR-0001 gives *integer*"; for a version-2 file this record reads the phrase with ADR-0050 added, which gives *integer* at one place more: the `bound` of a constraint entry ("an *integer* of ADR-0001" — cited: ADR-0050 decisions 1 and 4). A `bound` is written as a JSON number in decimal digits without sign, fraction or exponent. `5.0` and `1e3` are no *integer*, though each denotes one; `-0` is no *integer*; a number above 2^53 − 1 is no *integer* (the rule is cited with its sources: ADR-0029 decision 2, whose examples are `1.0` and `1e0`; the examples `5.0` and `1e3` are those of ADR-0050 L8). A version-2 file that spells a `bound` otherwise is invalid by its text.
- **`schema_version` is an *integer* place as before**: the value of a version-2 file is spelt `2`. A file that writes `2.0` there has no *integer* as its `schema_version`; it is not a version-2 file and is not set apart by decision 3, it is invalid (cited: ADR-0029 decision 2 sets apart only a file whose `schema_version` "is an *integer*"). The `schema_version` of the spec "is independent of the version of the embedded key records, which carry their own" (cited: ADR-0002 decision 7): in a file of either version an embedded record keeps the version ADR-0001 gives it.
- **A rule of the bytes, not of the document.** The argument is that of ADR-0029 decision 2: "the rules above are about the bytes that carry a document". For `-0` the rule changes no value a document holds: an interpreter reads it as 0, and a `bound` of 0 "is a valid form" (cited: ADR-0050 decision 4) — the file is invalid by its text although its document would not be. For `5.0` and `1e3` this record says only what the file is; whether a parsed document that holds at `bound` a number not spelt as an integer is a valid version-2 document is ADR-0050's ("`bound` is an integer") and is not touched here.
- **What is left of the three places.** ADR-0029 named three places "Where a number of another form can occur": `task.objective`, a `profile` object and a value of `ext`. **For a file of version 2 as ADR-0050 leaves it two are left**: a `profile` object and a value of `ext`. `task.objective` is no such place there: it is an object with exactly the listed members (cited: ADR-0050 decision 1; "An object holds exactly the members listed for it" — ADR-0002 decision 2), whose only member of a number type is `bound`, so a number anywhere else inside it makes the document invalid and a number at `bound` stands at an *integer* place. For `profile` and `ext` nothing changes: this record "adds no rule for a number beyond the grammar of JSON" there (the words of ADR-0029), and the cost ADR-0029 states for them stays (L5).
- **`weight` and `priority` get no rule here.** They have no JSON type yet, and a spec that carries either is invalid (cited: ADR-0050 decision 2). The record of the combining rule is meant to give them a type without a new version (cited: the same decision and exception (b) of its decision 6), and that type may be a number that is no *integer*. How a number of theirs is spelt in a version-2 file is for that record to say; the reading of the first bullet adds ADR-0050 and no later record, so it does not reach them.
- **No valid version-2 file holds a `bound` today.** "In version 2 as this record leaves it, no value of the `type` of a constraint entry is admitted, so a valid spec has an empty `constraints`" (cited: ADR-0050 decision 5). The rule above is written for the admission that decision provides for: when the record of sub-question ⑨ of OD-13 admits `memory_ceiling`, the spelling of its `bound` in a file is already fixed here, and that record needs no further rule of spelling for it. A later constraint type whose bound is not one integer needs a new member and a new version (cited: ADR-0050 decision 4), and with them its own rule.

### 3. A writer and a reader beside a file of the other version

- **(a) A write under the rules of version 2 writes a content of version 2 only.** A write under the rules of version 1 writes a content of version 1 only (cited: ADR-0029 decision 2). No write under either writes both. The reasons for version 2 only: the owner made version 2 the version in which the members of `task.objective` are "checked by the validator" (owner, O4), and a version-1 content carries there a value nothing checks; and a writer of both would need a rule that says which version a given call gets, which no record gives.
- **When the package moves.** The package is a writer and a reader of version 1 until the code slice of Consequences lands, and that slice moves it to version 2 in one commit. This record defines no state in which the package reads or writes both versions; a later record of OD-11 may define one. **This record names no writer of version 1 after that and forbids none**: a process started from an older source writes version 1 as before, and nothing checks which source writes into a tree (cited: ADR-0004 decision 10, the tree "does not enforce the single writer" and "does not check the content of any file").
- **(b) A file of another version, for a reader of version 2.** The sentence of ADR-0029 decision 2 holds with `2` in the place of `1`: **a file whose `schema_version` is an *integer* other than `2` is set apart** — "it is not called damage and that conclusion is not drawn for it — what such a file is and how it is read is OD-11" (cited; "that conclusion" is that the file is not the spec of any coder call). **A version-1 file is such a file.** A reader of version 2 has no rule by which to read it: it uses no member of it, repairs nothing and does not take it for a version-2 file. That it uses no member is this record's wording; ADR-0029 says of such a file only the sentence quoted, and `hilclaw.spec_file.parse` returns nothing for such a content (cited as today's code, for version 1).
- **For a reader of version 1** the sentence of ADR-0029 holds as written, and a version-2 file is a file "other than `1`": it is set apart. This record changes nothing of what a reader of version 1 does.
- **The plain cost, in both directions.** After the package has moved, a version-1 spec file is still kept and still found by its tuple (cited: ADR-0002 decision 1), and no reader that follows this record interprets it. Before it has moved, and for any process of an older source afterwards, a version-2 file is one more file of an unsupported version: a reader of version 1 cannot tell version 2 from any other number.
- **This is not a statement that a version-1 file need not be read.** Whether some component must read specs of both versions, whether a file is migrated, from when either is guaranteed, and what a run does when it meets a file of another version are **not decided** (L4; OD-11, whose tie to NFR-7 ② is the owner's). A later record of OD-11 may define a reader of both; nothing here excludes one. The carried-over write is no means of migration: its last step gives a name only if that name does not exist, so it cannot put a version-2 content in the place of a version-1 file — a fact of ADR-0029 decision 4, not a decision about migration.
- **No stored file waits on (b) today** (Context): no spec file of any version is committed in either repository. **This is a fact of 2026-10-13, not a rule** (L7): a data plane this record's author cannot see, or any run started before the package moves, can hold version-1 files.
- **(c) Two versions in one run directory.** **This record says nothing about it: it neither forbids nor allows it, and no rule here can produce a refusal.** The carried-over write "reads no other file and checks the content against none" (cited: ADR-0029 decision 4), so a write of a version-2 spec does not look at the specs the run already holds, and every file is judged by itself. A run whose earlier specs were written under version 1 and whose later ones under version 2 is therefore not prevented by these rules. NFR-7 ① asks that components can be replaced at a round boundary and that the replacement does not break a run in progress; this record says only that its rules do not stand in the way of the first, and claims nothing for the second (L4). Whether such a run is in order, may be resumed (FR-6) or must stop is OD-11 and sub-question ① of OD-8. One case is named so that it is not read as settled: a repair spec has "all other sections copied unchanged from the spec of attempt 1" (cited: ADR-0002 decision 5), and whether it must also have the `schema_version` of that spec is said by no record and not here.
- **An order this record does not fix.** A file that both breaks a rule of the text as a whole and states another version: ADR-0029 does not say which of the two a reader reports, and neither does this record. The order in `hilclaw.spec_file.parse` (the rules for the whole text before the version) is a convention of that module (cited: its docstring, "Conventions of this module, which the record does not fix").

### 4. The layout version

- **A version-2 spec file under the unchanged path does not raise the layout version.** "The version is raised when a path, file name or number form fixed here changes; it is not raised when a file is added in a place this record leaves open" (cited: ADR-0004 decision 9). None of the three changes: the path and the file name are those of ADR-0004 decision 3 for both versions (decision 1 above carries ADR-0029 decision 3 unchanged), and the number forms ADR-0004 fixes are those of directory names, which no rule here touches. The content of the file is not counted: ADR-0004 "fixes no field of any file" (cited: its decision 1). The tree stays layout version 1, and the `schema_version` of `instance.json` is not raised by this record (cited: ADR-0024 decision 3 raises it with the layout version).
- **What the layout stamp of a run says about its spec files: their paths, and nothing of their version.** From a valid `instance.json` that states layout version 1 a reader may conclude where the spec of a tuple is; it may conclude "Nothing about the content of any file" — "A file whose record defines a `schema_version` carries its own" (cited: ADR-0024 decision 2). ADR-0024 names three files whose version is "independent of the layout version" and the spec file is not among them; that the general sentence covers a spec file is this record's reading. **The version of a spec file is found in that file alone.** Nothing in the stamp excludes a run of layout version 1 whose spec files are of version 1, of version 2 or of both, and the stamp does not say which; of a run that holds both, decision 3 (c) says nothing either way.

### 5. The `schema_version` of the spec is not changed by this record

- **Owner** (O4, as quoted in ADR-0050): "version 2 of the spec, with the members of `task.objective` defined by the record and checked by the validator."
- **Version 2 is the owner's, with the members of ADR-0050. This record adds no version and changes none.** No field of the spec is added or removed or changes its type, meaning or requirement (the rule of ADR-0002 decision 7, with what ADR-0050 decision 6 replaces in it): the rules of decisions 1 to 3 are about the bytes that carry a document, which is the argument of ADR-0029 decision 2 for the rules of version 1.
- **No rule here changes what a parsed version-2 document is valid as.** The set of valid version-2 documents is ADR-0050's before and after this record. Among the rules for a number, `-0` at an *integer* place is the one case of which this record itself says that the file is invalid although its document would be valid, as in version 1; whether a document that holds `5.0` or `1e3` at an *integer* place is valid is ADR-0050's and ADR-0002's (decision 2). The rules of the text as a whole and the rule between the `id` and the path are rules of the file in both versions.

## Alternatives considered

| Point | Alternative | Why not |
|---|---|---|
| 1 | A new self-contained record that restates every rule of ADR-0029 for version 2 | Two texts of the same rule drift apart, and each restated sentence would be a new sentence to check against the old; nothing of the text form, the path rule or the steps depends on the members of `task.objective`. The cost of the reference: a reader of version 2 needs two records, and this record falls with ADR-0029. |
| 1 | Edit ADR-0029 so that it speaks of both versions | Earlier records are not edited; its sentences stay true of version 1. |
| 2 | Leave the numbers of `task.objective` without a spelling rule, as ADR-0029 did | That left the place free because its members were undefined; they are defined now, and `bound` would be the one *integer* of a spec with several spellings. |
| 2 | Leave the spelling of `bound` to the record that admits `memory_ceiling` | That record is about a measurement; it would have to reopen the text form of the spec file for one member. |
| 2 | Allow `5.0` for a `bound`, since byte counts can be large | One spelling per value is the rule of every other *integer* of the file, and an *integer* of ADR-0001 holds every byte count up to 2^53 − 1 exactly. |
| 3 | A writer of both versions | It needs a rule that chooses the version per call, which no record gives, and it would keep writing the unchecked objective O4 moved away from. |
| 3 | A reader of version 2 that reads version 1 as well | That is a guarantee of reading an older version: OD-11, tied to the owner's wording of NFR-7 ②. It is not taken and not excluded; while no stored version-1 file exists it would also be a reader with nothing to read. |
| 3 | A reader of version 2 holds a version-1 file invalid | It would call a kept and once valid spec damage, against the distinction ADR-0029 drew, and would pre-empt OD-11 in the other direction. |
| 3 | Forbid two versions in one run directory | It would make the write read other files of the run, against ADR-0029 decision 4, and would decide what a run does after a change of version (OD-11). |
| 4 | Raise the layout version with the version of the spec | No path, file name or number form changes (ADR-0004 decision 9); it would raise the `schema_version` of `instance.json` for a change the stamp does not speak of. |

## Consequences

- **The code slice the planner can now cut** (code mode; no module, function or exception is decided here). Version 2 in `hilclaw/spec.py`: the checks ADR-0050 lists under "What the validator of version 2 is to check", on a parsed document. With it, by this record, `hilclaw/spec_file.py`: its comparison of the version (a content whose `schema_version` is an *integer* other than `2` is set apart, a version-1 content among them, and a write writes version 2 only — decision 3); the list of places below which the spelling of a number is not checked, which loses `task.objective` for version 2 as ADR-0050 leaves it (decision 2; a later type of `weight` or `priority` brings its own rule); and its messages and docstring, which say "version 1", "not 1", "ADR-0002" and "three places". The tests that build a spec follow: `tests/test_spec.py`, `tests/test_spec_file.py`, `tests/test_gemm_contract.py`, `tests/test_instance.py`.
- **One task, not two.** `hilclaw/spec_file.py` takes its version from `hilclaw/spec.py`, so the two modules cannot move at different commits without a state in between that no record defines or that carries wrong messages. Outside tests the slice touches two files and, by an estimate that was not measured, well under 300 changed lines; tests are outside the size cap. If the planner finds it larger, the cut that keeps every commit defined is by checks inside the one move, not by module.
- **Until that slice lands** the package writes and accepts version 1 only, as ADR-0050 says.
- **Sentences of earlier records and of docstrings that are now less exact** (none edited; each stays true of version 1 or of what remains open):
  - ADR-0029 — decision 2: "`schema_version` 1 is the only version a record defines"; "A write by decision 4 writes a content of version 1 only, the one version a record defines"; "The `schema_version` of the spec stays 1"; the list of three places and "which numbers are values there belongs to the records that define those members" as far as `task.objective` goes. Decision 4: "three places of the payload hold values no record defines". Decision 6: "The layout version (ADR-0004 decision 9) is unchanged, version 1" (true; decision 4 here says it for version 2). Alternatives: "a new version before a first spec exists would only add a case to OD-11". Boundaries: "`task.objective` (#5 A-4, OD-1)" among what waits for the owner.

- **The admission of `memory_ceiling` and the memory measurement** (sub-question ⑨ of OD-13); any further constraint or objective type, `weight` and `priority` (rest of #5 A-4 and OD-1, owner-only); the spelling of a number of `weight` or `priority` in a file, which the record that gives them a type says (decision 2).

- **Sub-question ㉖ of OD-8**, in its three parts, as ADR-0029 registered it; the isolation means and the lock.
- **What a reader of a spec file does** beyond what the rules say a file is: which component reads it, when, and what it does with a missing, an invalid or a set-apart file (OD-18, OD-11).
