## Decision

A sentence marked **owner** quotes #5 A-7 ② or O4. A sentence is **cited** when a record and its decision, or a requirement, is named with it; it says what that source says and adds nothing. Every other sentence is **this record's own**.

### 1. Scope and terms

- **The runs**: those of ADR-0107 decision 1 whose hw_profile names `cpu_standin` — the first case (`gemm`, fp32, a C kernel) in the local configuration of [ADR-0038](ADR-0038-od18-cpu-standin-execution-points.md) decision 1. **The mock is out of scope**: it is given no setting (cited: ADR-0060 decision 3).
- **The settings** of this record: the flags, the trailing flags and the environment (thread settings travel in it — cited: ADR-0017 decision 9) of the verification build and process and of the timing build and process, in the sense of ADR-0107 decision 1. The compiler and the two time limits are rows of the same table and are not answered here.
- **Where the build runs**: on the host, as the records still say (cited: ADR-0038 decision 1, "built and run on the machine of the tool function"; ADR-0060 decision 2), or in the container of O4, whose design is OD-14 sub-question ①. Every value below is meant to hold in both; one that does not is left open (decision 6).

### 2. The source: one fixed set in the package source

- **The flags, the trailing flags and the rule of the environment are constants of the tool package, read by the operation of `cpu_standin` for `correctness.check` and by its operations for `sim.run` and `board.run` alike.** They change only by a commit of the source repository. No operation adds one per tool, per point or per `execution` (ADR-0107 decision 3), and none is read from a file, a variable or the hw_profile.
- **Three alternatives were weighed, against four tests.**

| | (a) Fixed in the package source | (b) A configuration file (such as `hilclaw.config.json`) or an environment variable | (c) Derived from the hw_profile the operation is handed |
|---|---|---|---|
| NFR-7 ③ (which source commit made a result) | The commit names the values. A result is traced to them as far as the source has not changed since the start (cited: ADR-0022 decision 6) | The file is ignored by git and a variable is part of no commit: no commit names the values | The hw_profile record names them, but it has no member for them: flags "are not key fields" (cited: ADR-0001 decision 5) |
| C-7 (Linux, macOS, WSL alike) | One set on the three systems, if the set holds no per-system value (decision 3) | Each machine may hold its own file or shell variables; nothing keeps them alike | One set per profile; alike only if every profile holds the same |
| ADR-0107 Limit 3 (a change between two calls) | Only a new source between the calls — two processes of two versions (cited: ADR-0016 decision 6, "Two processes, two tables") | Also an edit of the file, or two processes started from two shells, with no commit between them | Only a change of the profile, which is a new record |
| O4 item 2 (toolchain and environment change only after approval) | The runtime never changes them; a change arrives as a new source version, which the runtime does not install or update | A user or an agent can edit the file or the variable between calls; the runtime does not ask for anything, and nothing stops it | A change is a new hw_profile record, whose registration is the onboarding's (FR-14 ④; who and when: OD-26), not an install or update by the runtime; no record says whether that registration asks for the user's approval |
| Earlier records | None reopened | None reopened, but a second source of settings beside the package, for the user to keep alike | Reopens ADR-0060 decision 3 ("an operation reads no setting … from the hw_profile it is handed") and needs a member of the hw_profile: a data-plane schema change (CLAUDE.md A-13) |

- **The choice is (a).** Its cost: changing a value needs a commit, a review and a new process; a user cannot try another flag for one run. A change leaves the hw key unchanged although measured performance may change (cited: ADR-0001 decision 5), so results from before and after a change are kept under one key, and the only trace of the change is the source commit of each run's start (ADR-0022). ADR-0001 left a way for settings that turn out fixed per profile to enter the key through `ext` (Alternatives, point 5); this record does not take it — that would be a member of the hw_profile.

### 3. The flags

- **The flags are `-std=gnu11`, `-O2` and `-ffp-contract=off`, in that order, and nothing else.** They apply to the harness program as well (cited: ADR-0009 decision 2; ADR-0107 decision 3).
- **The language standard: `-std=gnu11`.** No record fixes one beyond "C" (**owner**, #5 A-7 ②). It is stated because the default of clang differs between clang versions, so a set without one would not mean the same on two machines of C-7. **Why GNU and not strict `c11`**: under a strict standard the C library on Linux and WSL (glibc) hides POSIX declarations that macOS still shows, so the same kernel source could build on one system and fail on another; under `gnu11` both show them. **Why C11 and not C99 or C17**: C11 adds `_Alignas` and `aligned_alloc`, which a SIMD kernel may want; C17 adds no feature, so C17 would do as well; C11 is this record's choice, as the revision nearest to the C99 the harness programs are tested under. The harness programs, built under `-std=c99 -Wpedantic` in their tests, set their own feature macro and use no feature C11 removed (an observation; not built under `gnu11` — Limit 1).
- **The optimisation level: `-O2`.** It is the level at which the tests build the harness programs and the timing driver's calls are checked to stay observable (observation; cited for the risk: ADR-0009 decision 10, "depends on the flags (link-time optimisation)"). How fast a kernel is, is the coder's work; the level only has to be one, the same for every kernel (ADR-0107 decision 3).
- **Floating-point contraction: `-ffp-contract=off`.** Whether the compiler fuses a multiply and an add into one instruction is a default this record does not rely on across clang versions, and where it fuses depends on the target: on arm64 an FMA instruction is in the baseline, on x86-64 it is not (decision 3, target-specific flags). With contraction off, one kernel source rounds its products and sums the same way on both, which removes one difference between C-7 systems from the numerics the check compares against the tolerance; it does not remove others (the mathematical functions of the C library differ, Limit 4). Its cost: no automatic FMA on arm64; a kernel can still ask for one explicitly, with `fmaf` or an intrinsic.
- **What the flags need from the installation.** `-std=gnu11`, `-O2` and `-ffp-contract=off` are options of the compiler itself, and `-lm` names a library of the C library of each system (decision 4); none of them asks for a component beyond the clang and the C library a system has, macOS with its default clang included. That was not tried (Limit 1; the runtime acceptance item of Consequences).
- **Not in the set, with the reason for each.**
  - **`-ffast-math` and its parts**: one flag of the set would impose finite-math assumptions and reassociation on every kernel, also on one whose correctness rests on IEEE semantics; whether a kernel gives up those semantics is a choice its author can make in the source, not one the backend makes for all (this record's reason). The harness programs are not the reason: they are tested to keep their bit patterns under `-ffast-math` (observation: `tests/harness/test_verification_program.py`).
  - **Link-time optimisation**: it lets the build see across the harness program and the kernel, which ADR-0107 decision 5 names as a reason the same settings need not give the same machine code, and ADR-0009 decision 10 as a way an unread call could be removed.
  - **A target-specific flag (`-march=native`, `-mavx2`, `-mcpu=…`)**: one flag string would make different code on different machines — `-march=native` follows the build machine, and `-mavx2` has no meaning on arm64 — so the set would hold a per-system value against decision 2, and the commit would not name the instruction set the kernel was built for. Besides, its meaning is the CPU the compiler sees, and inside a container — whose design is open (OD-14 sub-question ①) — that need not be the host's CPU; the value would then hold in one place and not the other (decision 1). A kernel stays able to use the SIMD intrinsics of a feature beyond the target's baseline: a function attribute of the source (for example `__attribute__((target("avx2")))`) selects it without a flag, so the ADR-0008 decision 7 allowance is met by source, not by a flag. Its cost: code the compiler vectorises by itself targets the baseline (SSE2 on x86-64). Whether a later set adds one is open with OD-14 sub-question ① (decision 6).
  - **Warnings and `-Werror`**: a warning does not change what is compiled, and `-Werror` would turn a kernel within its contract into a broken result `build_exit_status` (cited: ADR-0060 decision 4).
  - **Defines (`-D…`)**: none; a define reaches the kernel's translation units, where a kernel could test it (cited: ADR-0107 decision 3).
  - **OpenMP (`-fopenmp`, `-Xpreprocessor -fopenmp`)**: not chosen and not refused — open (decision 6).

### 4. The trailing flags

- **The trailing flags are `-lm`, and nothing else.** A kernel may include the headers of the C standard library (cited: ADR-0008 decision 7); on Linux and WSL the mathematical functions of `<math.h>` are in a library of their own (`libm` of glibc) that a link must name, and on macOS the same flag names the system library that holds them. So one flag gives the same result on the three systems. No harness program needs it — each "needs the C library and POSIX.1-2008 only (no -lm)" (observation: the head comments of `timing_driver.c` and `verification_program.c`); naming the library changes nothing they compute.
- **No OpenMP runtime (`-lomp`, `-lgomp`)**: open with OpenMP (decision 6). The sentence that the hw key's `toolchain` has no member for an OpenMP runtime, because "a runtime exists only for a build whose flags ask for one" (cited: ADR-0035 decision 3), stays exact: no build of this set asks for one. The sentence beside it, that flags "may differ between the candidates of one pair", does not (Consequences).

### 5. The environment

- **The environment of every build and every process of these runs is the environment of the process that starts it, where it runs — on the host the environment of the operation's process, in the container the one OD-14 sub-question ① gives it — with no variable added, changed or removed by the backend.** It is one environment for the build and the process (cited: ADR-0107 decision 3).
- **Thread settings: none is set.** No OpenMP runtime is linked by the set of decisions 3 and 4, so no OpenMP variable is read by a runtime of the build; which thread variable and which value go with OpenMP is open with it (decision 6). Threads are allowed (cited: ADR-0008 decision 6); that a kernel which starts threads of its own chooses their number in its source is this record's reading for the set without OpenMP. **Not alike on C-7**: among the headers a kernel may include (cited: ADR-0008 decision 7) the only other way to start a thread is C11 `<threads.h>`, which the C library of macOS does not provide and which glibc lacks before 2.28 and links only with `-lpthread` before 2.34. So under this set a kernel that starts threads builds on some C-7 systems and not on others; that is part of the open OpenMP question (decision 6) and Limit 4.
- **Three ways were weighed.**
  - **(a) Inherited, unchanged.** It holds on the host and in the container, since it says nothing that only one of them can give. **Its cost**: no commit names the environment (NFR-7 ③ reaches the flags, not it); two processes started from different shells can build the two builds of one attempt with different environments — a further case of ADR-0107 Limit 3; and the three systems of C-7 have different environments. Variables the compiler or the loader reads (for example `CPATH` or `LD_PRELOAD`) reach the build or the process when the user has set them. **Against O4 item 2**: the runtime changes no variable, but the environment is whatever the process was started with — fixed for the life of an MCP server process, and new at each command-line call, which is a new process (cited: ADR-0010 decision 7) — so a change the user makes in a shell reaches the next command-line call without the runtime asking. This record reads that as the user's own change, not one O4 item 2 asks the runtime to seek approval for; if the owner reads it otherwise, it is an objection to this decision.
  - **(b) A fixed environment.** It needs at least the variables by which the compiler and its linker are found and run (`PATH` among them), whose values depend on the compiler installation and on host or container — OD-14 sub-question ①. A fixed `PATH` would choose the compiler, which is not this record's.
  - **(c) Inherited, with a fixed list of variables removed or set.** It would close the cost of (a) for the variables on the list. No complete list of the variables that change a build or a process on the three systems is at hand, and a partial one would promise more than it gives. Left open (decision 6).
- **The choice is (a).** The code defaults (`env=None`, "inherits") are thereby the value of this record for the environment; ADR-0060 decision 3 said they were "no values of this record", and this record makes the inherited environment the value by its own choice.

### 6. What stays open, as parts of ⑱ (라)

- **OpenMP**: whether the set enables it, with which flag and runtime, and the thread setting and value that go with it. **Why it is not chosen here**: with the clang macOS has by default (**owner**: "macOS default") `-fopenmp` is refused and the runtime is not installed — a build with OpenMP needs a separately installed runtime (`libomp`) and another spelling of the flag (`-Xpreprocessor -fopenmp … -lomp`); on Linux and WSL the OpenMP runtime of clang comes, on some distributions, as a package of its own beside the compiler. Choosing it needs an install on at least one C-7 system, which this record may not choose (a new external dependency; O4 item 2). **Why it is not refused here**: OpenMP is allowed in stand-in kernels (**owner**, #5 A-7 ②) and a kernel may include `<omp.h>` (cited: ADR-0008 decision 7); whether it must be usable by every kernel on every C-7 system is the owner's reading of #5 A-7, not this record's. **Until it is answered**, a kernel that calls the OpenMP runtime fails to link on every C-7 system, and a kernel that only includes `<omp.h>` fails to compile where no OpenMP header is installed (macOS with its default clang) and may build where one is (a Linux or WSL system with clang's OpenMP package). Each failure is stored as a broken result `build_exit_status` — the cost ADR-0060 decision 3 already states for "a kernel within its contract that needs a flag the backend does not give" (cited); `#pragma omp` alone is ignored and the kernel runs on one thread. That one kernel can be broken on one system and complete on another is Limit 4.
- **A target-specific flag** after OD-14 sub-question ① (decision 3).
- **A list of inherited variables to remove or set** (decision 5 (c)).

- **⑲ (라)**: its source and values are those of decisions 2 to 5 for the runs of decision 1 — the same set, read by the run tools' operations, as ADR-0107 decision 3 requires. What stays open is decision 6.
- **OD-16 sub-question ⑥**: nothing beyond ADR-0107. **OD-6 sub-question ②**: nothing; this record gives no member of `task.build`, says nothing of a setting the coder chooses and records no setting (⑱ (가), ⑰ (다)).

### 8. Limits

1. **Nothing was built or run.** That each flag is accepted by the clang of each C-7 system, and that the harness programs build under `-std=gnu11`, was not tried here (Consequences: the tests of the code slice, and a runtime acceptance item for the systems the development machine and CI do not have).
2. **The inherited environment is unguarded** (decision 5 (a)): a variable the compiler or the loader reads can change a build or a run, and two processes can differ.
3. **A change of the package between two calls** makes two builds of one attempt differ, as ADR-0107 Limit 3 says; nothing records which build came before.
4. **Not every outcome is alike on C-7 under this set** (decisions 3, 5 and 6): a kernel that includes `<omp.h>` or starts threads through `<threads.h>` can build on one system and fail on another, and the mathematical functions of the C library are not the same implementation on glibc and on macOS, so their results can differ in the last bits. The claim of decision 2, one set alike on the three systems, holds for the flags, not for every kernel built with them.
5. **Scope**: other backends, a simulator, a board, a remote machine, OD-18 sub-question ⑫ and `profiler.collect` are not covered.
