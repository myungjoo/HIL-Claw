## Decision

Whose a sentence is: **owner** where K1, K3 or the answer to HQ-0025 is named; **cited** where another source is named; **this record's own** otherwise.

### 1. Scope

- **The runs** are those of ADR-0144 decision 1 (cited): the first case on `cpu_standin`, carried out locally, every build and process in a new container of the image the user names. **The process concerned is the timing process** of an operation of `sim.run` or `board.run`; the verification process of `correctness.check` yields no figure (cited: ADR-0052 Alternatives, "The verification run of ADR-0017") and is not changed. Docker is the runtime (cited: ADR-0144 decision 4); nothing of Podman was read.
- **The two kinds of machine** this record distinguishes, because the documentation does: **a Linux kernel that runs the container directly** (Docker Engine on Linux; F1, containers "share the same kernel"), and **a Linux VM that runs it** (Docker Desktop on macOS and Windows; D3). Whether Docker inside a WSL 2 distribution is the second kind's VM is ADR-0103's reading ("This includes … WSL 2", its decision 4), not this record's.

### 2. (i) The timing samples are those of ADR-0009

- **They are the samples ADR-0009 defines**: the same driver program and kernel built into one executable (cited: ADR-0009 decision 2), the same clock call around the same one kernel call (decision 3), the same report on the same channel (decision 8), handed to the operation through the client's standard output and judged by the same code of `hilclaw.harness.timing` above the cut (cited: ADR-0061 decision 3). Decision 3 below does not touch the driver, its arguments or its report: the bytes the timing process writes on its standard output are what the operation receives (that the client hands them on unchanged is ADR-0144 runtime acceptance item (lii)). **The timing run of ADR-0009 is not changed.**
- **On a Linux kernel that runs the container directly**, the timing process is a process of that kernel (F1), and `CLOCK_MONOTONIC` is that kernel's clock. A time namespace, if the container runtime made one, moves that clock by an offset (F2), and an interval is the difference of two readings, so an offset does not enter it (this record's reading; Docker's documentation read here does not say whether it makes one). No processor bound throttles the process (cited: ADR-0144 Q7). So the samples are taken as on the host; what the container adds is noise the measured ground of ADR-0103 sees like any other (this record's expectation; whether CV and resolution differ from a host run is ADR-0103 Limit 2, a runtime acceptance item already listed there).
- **On Docker Desktop's VM** the timing process is a process of the VM's own kernel (F1, "an entire operating system with its own kernel"; D3), and `CLOCK_MONOTONIC` is that guest kernel's clock. The samples are still those of ADR-0009 by every element above — the same report, judged the same way — but taken in a VM guest, which is the environment K3 (**owner**) names as one "where it is hard or imprecise", and the class of ADR-0103 decision 4 (cited: "the VM of Docker Desktop on macOS or Windows"). **What follows is K3's rule and nothing new**: the run continues on relative numbers under ADR-0007, with the warning (**owner**, K3). This record does not say how far such samples differ from the host processor's; ADR-0144 decision 5 requires that the image is not emulated (cited), which this record reads as the VM running the host's processor natively.
- **This does not produce the input of ADR-0103's class ground.** To know that a timing run executed in a VM guest, the operation would need a reading of the machine that no accepted record defines — what the container runtime reports about where its daemon runs, or what the processor or the guest kernel reports — and a Linux host that is itself a guest (a WSL 2 distribution, a cloud VM) would have to be told apart too. ADR-0103 decision 4 refuses `host.os` as the input (cited). So the class ground stays "not yet active" (cited: ADR-0103 Limit 1), and producing its input stays OD-13 ⑪ (가) (Boundaries).

### 3. (ii) The memory figure: read by a wait-and-report program of the harness, process 1 of the timing process's container

- **The waiter.** The harness gets one further C program (this record's name for it: *the waiter*), one source file of the harness beside the timing driver (C is in the layer-2 set; as ADR-0009 decision 2 places its driver). It is not the kernel's: no kernel file is compiled into it. **The timing process container starts the waiter in place of the executable**, with the path of the timing executable and the driver's arguments as its arguments; the waiter then does, in this order:
  - **W0** — it checks that it is process 1 of its PID namespace (below); when it is not, it starts nothing and ends with a non-zero status;
  - **W1** — it makes itself not dumpable (F8, `PR_SET_DUMPABLE` 0) and establishes no signal handler;
  - **W2** — it starts the timing executable as its one child, handing on unchanged the arguments, the environment, the working directory and the standard output and standard error it was given;
  - **W3** — it waits for that child and keeps the `ru_maxrss` of the resource usage returned with that wait (F9; the interface of ADR-0052 decision 4, `wait4`, which is the C library's and "nonstandard"); no other child is waited for first, and `RUSAGE_CHILDREN` is not used (cited: ADR-0052 decision 4, "The cumulative figure for all children is not used");
  - **W4** — it sends `SIGKILL` to every other process it may signal (F7, `kill(-1, …)`, which spares process 1) and reaps its children, sending it again while any is left, until it has no child, so that no other process of the container is left to write;
  - **W5** — it makes its standard output blocking again (the child shares that open file and may have changed its flags) and writes on it, until every byte is written or a write fails, **one line feed and then one last line, ended by a line feed**: the raw `ru_maxrss` of W3 where it was compiled for Linux, and a line that says there is none otherwise; its form is none of the line forms of the report of ADR-0009 decision 8 (cited), and is an interface between two parts of the harness of one source commit, carries no version and is no file or field of the data plane, as the report of ADR-0009 decision 8 (cited); its spelling is the code slice's;
  - **W6** — it ends with status 0 exactly when the child ended by itself with status 0 and W3 to W5 succeeded, and with a non-zero status otherwise. **A step that fails ends the waiter at once** with a non-zero status, and no later step is done: a waiter's line therefore always means that its child was started and waited for.
- **Process 1.** Docker gives each container its own PID namespace by default (F5), and the program a container starts is its first process, so the waiter is process 1 of that namespace (F6; that it is so with the options of ADR-0144 decision 6 is runtime acceptance item (liii)). **W0 keeps W4 inside a container**: a process 1 of a new PID namespace can signal only processes of that namespace and its descendants (F6), and a waiter that is not process 1 starts nothing and signals nothing, so that it can never signal processes outside its container (that a faulty W0 cannot do so in a test either is how slice (5) is tested, Consequences). **The start must not put an init of the container runtime before it** (F5, `--init`, which makes `docker-init` process 1): the waiter would then be refused by W0 at every call. ADR-0144 decision 6 names no init among its options (this record's reading of its list), but a daemon started with its own `--init` (F5) may put one there for every container; whether the client can then keep it out was not read here. **The cost**: on such a machine W0 refuses every timing call and no timing result is had until the daemon's setting changes; that no init is there is runtime acceptance item (liii). What a call answers when the waiter ends that way is decision 6.
- **The waiter's build.** The waiter's source is copied into the build directory with the harness program, never as a link and outside the kernel's sub-directory (cited: ADR-0144 Q3, the reason given there for the harness program's copy), and is compiled into the waiter's executable by a build of its own in a new container of the same image, with the flags of [ADR-0116](ADR-0116-od18-cpu-standin-build-settings.md) decision 3, under ADR-0144 decisions 2, 3, 5 and 6 as a build of the timing call; it includes no header but the system's. It is made after the timing build and before the timing process. **One time limit covers both builds**: B_t of ADR-0117 (cited: 60 s) bounds the timing build and the waiter's build together, the second getting what the first left (whether the operation's own work between the two counts against it is the code slice's), so the longest call of ADR-0117 decision 5 (cited: 60 + 1500 = 1560 s) does not grow. **The cost**: a timing build that took nearly the whole 60 s, which completed before, can now leave the waiter's build too little time; what the call then answers is decision 6. It is built at each call, not kept (cited: ADR-0056 decision 4 (a), "No outcome depends on anything an earlier call left").
- **What the operation takes.** From the client's standard output it takes the last line as the waiter's, removes exactly the one line feed of W5 before it, and returns **the bytes before that line feed as the report**, unchanged as (A) of ADR-0061 decision 3 (cited) with the figure: where the waiter's line carries a raw value, the figure is that value times 1024 if it is an integer of at least 1, and there is none otherwise (cited: ADR-0052 decision 4, "A reported value that is not a positive integer yields no figure"); where the line says there is none, there is none. A figure is never taken from any other line, and a stream whose last line is empty, is not ended by a line feed or has no line feed before it has no waiter's line. Everything after the cut is unchanged: the judging of the report, "A figure returned with (A) is used only if the tool function finds the run completed", and the verdict (cited: ADR-0061 decision 3).

### 4. What the figure is, and its unit

- **It is the figure ADR-0052 decision 3 defines** — the maximum resident set size of the process of one timing run, over its whole life, as the operating system reports it for the ended process, in bytes — **with "the operating system" being the Linux kernel that runs the container**: on a Linux machine the host's kernel (F1), on Docker Desktop the VM's kernel (F1, D3). This is this record's reading of decision 3, which names no machine. On Docker Desktop "resident" therefore means resident in the VM's memory; whether the VM's memory is itself resident on the host is not seen, which makes the figure looser in the direction of ADR-0052 L3 (this record's reading).
- **The unit rule is the container's system, never the host's `sys.platform`.** The waiter runs where the timing process runs and was compiled by the image's compiler for the image's platform (cited: ADR-0144 decision 5, native platform); it writes a raw value only where it was compiled for Linux, where `ru_maxrss` is in KiB (F9), so the Linux rule of ADR-0052 decision 4 applies. On a macOS host the darwin rule of the host would make the figure 1024 times too small, and a candidate over its ceiling would be called within (cited: ADR-0052 decision 4 names that consequence for a wrong unit). ADR-0061 decision 3's "the platform the process ran on" (cited) is read as the container's system. An image of another platform yields no figure (W5), as ADR-0052 decision 4 says of "any other platform" (cited).
- **The floor of ADR-0052 L2 changes.** L2 cites that Linux folds "the peak of the address space a process had before the program was loaded" into the maximum (cited); here that address space is the waiter's after it started its child (W2), a small C program, not the starting Python process. **This record's reading, not observed**: the floor is smaller than on the host and the same at each start of one image; how large it is joins runtime acceptance item (liv). L2's other parts (the driver, the C library, the sample array), L3, L5 and L6 hold as written (cited).

### 5. What a kernel inside the container can do to the figure, and what the waiter protects

- **What the waiter protects** (this record's expectation from F5 to F8, not verified — runtime acceptance item (liii)). The figure is read by the operating system for the ended process (W3) and written by a program the kernel's code is not part of (W5), after every other process of the container has ended (W4), and it is taken only from the last line. So: a kernel that writes a line of the waiter's form on the report channel — which it can reach, sharing the process with the driver (cited: ADR-0009 decision 10, "write to the report channel") — gives no figure: that line lies before the waiter's line, inside the report, which then is a report of another form and broken (cited: ADR-0009 decision 8, "a line of another form"); and bytes it leaves without a line feed after the driver's last line (from a function run at the process's exit, for example) cannot join the waiter's line, because the line feed W5 writes first ends them, and they stay in the report, which is then broken too. So the kernel can break its run, as it always could, but neither give, raise nor remove a figure of a completed run. A kernel cannot end the waiter by a signal (F6: only signals it has a handler for reach process 1 from inside, and W1 establishes none), cannot reach its descriptors or memory through `/proc` (F8: the waiter is not dumpable, and every capability is dropped — cited: ADR-0144 Q6 — so `CAP_SYS_PTRACE` is not held), and cannot leave a process that writes after the waiter's line (W4; F6, the ending of process 1 ends the rest). Changing the waiter's executable file in the build directory, which the timing process can write (cited: ADR-0144 Q2), changes nothing that is running and nothing used later in that call. With these, the figure keeps the property ADR-0052 L4 states for the host — **a kernel cannot state it; it can only keep memory out of it** (cited) — on another ground: L4's "through no channel the kernel writes to" (cited) does not hold here, and the last-line rule with W4 and W5 takes its place.
- **What it does not protect.** Everything ADR-0052 L4 lists stays (cited): spreading memory over processes of its own — which W4 now ends before the line is written, but whose peak never entered the child's usage — holding memory only in a run that is not measured, telling a timing run from another, and resetting its own peak through `/proc/pid/clear_refs`. After W4 no process of the kernel is left and W5 restores blocking writes, so this record knows of no way for a kernel to make W5 fail. A stream with no waiter's line can still occur — the waiter ended by the operating system, for example by its out-of-memory handling, since no memory bound is set (cited: ADR-0144 Q7), or a way of the kernel's not known here — and it is a situation of decision 6 whose answer must not let a kernel turn its own broken result into a tool failure (the caution ADR-0144 decision 3 gives for the client's statuses, cited). A kernel that leaves its container, or a Linux security module or kernel that does not behave as F6 to F8 say, is outside what the documentation shows. **The comparison stays on the Python side** (cited: ADR-0052 decision 5): the waiter compares nothing and is handed no `bound`. No defence of OD-16 is adopted or rejected.

### 6. What follows for ADR-0052 decision 7, ADR-0063 decision 6 and the tools' answers

- **Condition (a) of ADR-0052 decision 7** — "the harness slice that takes the figure as decision 4 says" (cited) — is read, for the runs of ADR-0144 decision 1, as **met when the code of decisions 3 and 4 is on `main`** (the waiter, its build, and the operation's reading by the Linux rule), decision 4 of ADR-0052 being replaced for these runs as Status says. Until then it is not met for them, as ADR-0144 decision 3 reads it (cited). The landed code (T-0173) meets it for host runs, which the first case no longer has (cited: ADR-0144 decision 4, "No build or process on the host, ever, for these runs"). Conditions (b) and (c) are untouched; **nothing is admitted** (cited: ADR-0052 decision 7, "This record admits nothing itself").
- **`memory_bytes`** (cited: ADR-0063 decision 6) keeps its form and its rule: it is present exactly when the run is completed and yielded a figure, which for these runs is the figure of decision 3; it is absent where the waiter's line says there is none or carries no positive integer. The figure the answer to HQ-0025 (**owner**) counts among what the run tools return is this one.
- **No answer, situation or kind is added.** The status alone does not tell the waiter's own failure from the timing process's — both end the waiter with a non-zero status (W0, W6) — so a code slice does not read such a status as the run's before it has looked for the waiter's line (this record's rule; ADR-0144 decision 3 says of the client's statuses 125 to 127 only that "the status alone does not tell the two apart", cited). The waiter ending with a non-zero status without a child that did so (outside process 1, or unable to start or wait), a waiter's build that fails or passes the limit, and a client's stream with no waiter's line are situations of the run tools whose answers and kinds are OD-18 sub-question ⑲ (cited: ADR-0144 decision 7); a code slice that meets one registers it there. HQ-0021 and HQ-0026 are not crossed.

### Walk-through (one call of `sim.run` at a run of ADR-0144 decision 1 on Docker Desktop on macOS; no step names a module)

1. The operation copies the kernel files into their sub-directory, and the timing driver and the waiter's source beside it (ADR-0144 Q3). The timing build compiles driver and kernel in one container; the waiter's build compiles the waiter in a second, both inside 60 s.
2. A third container starts the waiter as process 1 with the timing executable and the driver's eight arguments. The waiter makes itself not dumpable, starts the executable, and waits. The kernel writes a line of the waiter's form on the driver's report channel, leaves a process of its own behind, and tries to kill process 1: nothing happens.
3. The executable ends with status 0. The waiter keeps the `ru_maxrss` its wait returned (in KiB, the VM's Linux), kills the process the kernel had left behind, writes its line, and ends with 0.
4. The operation takes the last line, multiplies its value by 1024, and returns the bytes before it as the report. The tool function finds a line of another form in the report — the kernel's — so the run is broken and the figure is not used. Had the kernel written nothing there, the run would be completed with that figure, and the result carries `memory_bytes`, never the darwin rule of the host.

## Alternatives considered

| Alternative | Why not |
|---|---|
| **No figure for a container run** | Every first-case run is a container run (ADR-0144 decision 4), so the run tools would never return the figure HQ-0025 (**owner**) counts among their results, and condition (a) of ADR-0052 decision 7 could never be met for the first case. Taken only if no sound means exists; the waiter is one. |
| **A figure the container runtime reports** (`docker stats`, or the container's cgroup `memory.peak` read from the host) | Another quantity: a cgroup's figure for the whole container — `docker stats` with the cache subtracted (F3), `memory.peak` with page cache included (F4) — not the maximum resident set of one process, so it would need a record that re-decides ADR-0052 decision 3. `docker stats` is a live stream that gives nothing for a stopped container (F3), so it samples and misses a peak (ADR-0052 Alternatives, "Sampling the resident set during the run"). The cgroup's path depends on cgroup version and driver (F3), lies inside the VM under Docker Desktop (D3), and goes with a container removed at its end (ADR-0144 E4). |
| **A report by the timing driver itself** (`getrusage(RUSAGE_SELF)`, or the driver forking and waiting for a child that runs the kernel) | The kernel's code is linked into the same executable and runs in that process, so it can state the figure; refused by ADR-0052 Alternatives, and it reopens ADR-0009 decision 8, which this record does not change. |
| **The waiter compiled into the timing executable**, to save its build | The same: the kernel's code would be part of the waiter's process. |
| **A waiter from the image or the container runtime** (a `time` program with a resident-set option, Docker's `--init`) | A program the image need not hold beyond ADR-0144 decision 5 is a new external dependency (CLAUDE.md A-13); `--init` is the daemon's `docker-init` (F5), which the documentation describes as reaping; that it reports no usage is this record's reading. |
| **The timing build and the waiter's build in one container** | The program a build container starts is `clang` itself (ADR-0144 decision 6), and one start of it links one executable; a shell to run two would be a program the image need not hold (ADR-0144 decision 5). |
| **The waiter built once and kept across calls** | State between calls (ADR-0056 decision 4 (a)). |
| **The waiter's build with a time limit of its own** | A new value of OD-14's hierarchy, and the longest call of ADR-0117 decision 5 would grow past what that record weighed against the MCP idle window. |
| **The waiter relaying the child's output through a pipe** instead of handing on its own descriptors | Not needed once W4 leaves no writer behind; a relay would add a copy of the report that must be shown byte-exact. |
| **The host's `sys.platform` for the unit** | Wrong by 1024 on a macOS host (decision 4). |

## Consequences

- **Slices for the planner** (code mode; no module or signature is decided here), each bound to nothing when it lands: **(5)** the waiter, one C source file of the harness, W0 to W6 — tested only inside a new Linux PID namespace (its refusal with another process as process 1 there, so that a faulty W0 cannot signal outside it; its run as process 1), on a CI runner allowed to make such a namespace, as ADR-0052 Consequences places real-clang tests on CI, never with a container runtime on the development machine (D16); **(6)** the operation's reading of the client's output — the last line, the report before it, the Linux rule — a pure function over stated bytes, testable everywhere. **ADR-0144 slice (4)** then copies the waiter's source, makes the waiter's build within B_t and starts the timing process container with the waiter, tested with the stub container runtime of slice (1); it still waits on ADR-0144 decision 7's open answers (HQ-0021, HQ-0026), and the memory figure no longer waits on ① (마).
