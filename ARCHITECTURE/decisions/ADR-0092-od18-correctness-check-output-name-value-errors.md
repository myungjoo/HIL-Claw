## Context

- ADR-0091 made a `ValueError` whose `parameter` is `"output"` no row, with U3, "one raised while the absolute artefact path is formed", as its case, and kept U4 open: "a `ValueError` from after the checks up to and including the start, which holds what `build` passes on from `subprocess`" (cited: ADR-0091 decisions 2 and 3). It named a way out: "a code change that makes `build` refuse such a setting in a named check before the start" (cited, same). Task T-0278 (PR #176, `304a8fc`) made a code change of that kind for one value that is no setting, the output file name; its task file says "It records no row of `correctness.check`" (cited).
- **Observations at `304a8fc`** (no code is bound):
  - **J1. The new step.** The docstring of `build`: "Once the output path has passed its tests, its absolute path is checked the same way: on POSIX it must convert with `os.fsencode`, else its `UnicodeEncodeError` is passed on, and a NUL character in it raises `ValueError`", and "The check of `output` forms its absolute path and, after the tests of that path below, which are not part of it, checks it on POSIX with `os.fsencode` and then for a NUL character" (cited). In the code a second `_parameter("output")` step runs `_check_argument(str(target), "output contains a NUL character")` after the path tests and before the compiler lookup; `_check_argument` calls `os.fsencode` when the platform is not Windows and then tests for `"\0"`, and `_parameter` sets `parameter` on a `TypeError` or `ValueError` and re-raises it unchanged. **The name error** of this record is what that step raises: a `ValueError` with that message, or on POSIX the `UnicodeEncodeError` of `os.fsencode` — a subclass of `ValueError` (cited: the Python documentation of the built-in exceptions) —, each with `parameter` `"output"` and no `path_role`.
  - **J2. Where in the path it is met.** The step tests the whole absolute path, but the path tests run first: `is_dir` and `exists` of the parent, then `is_dir` of the path. On the `pathlib` statement ADR-0091 K2 cites — these methods "return `False` instead of raising" for a path holding characters the operating system cannot represent — a NUL or unrepresentable character in a directory part makes the parent tests false, and `build` raises `FileNotFoundError` with `path_role` `"output"`; the same character in the file name alone leaves the parent tests true and `is_dir` of the path false, so the path reaches J1. T-0278's task file says that before the change such a name "reaches the command line" through the temporary name and that `subprocess.Popen` "then refuses it" with an error that "carries no `parameter`, so it is part of U4" (cited). This record did not establish either by running code.
  - **J3. What runs after J1, up to the start.** The named steps of `compiler`, `env` and `cwd`; then, outside any step, the temporary name `target.with_name(f"{target.stem}.tmp-{os.getpid()}-{secrets.token_hex(8)}{target.suffix}")`, the command `(*prefix, *flags, *source_paths, *trailing_flags, "-o", str(temporary))`, `time.monotonic()`, and `subprocess.Popen` with that command, `cwd` and `env`.
  - **J4. Documentation read for J3** (cited, not established here): `PurePath.with_name` — "If the original path doesn't have a name, ValueError is raised"; `PurePath.parent` — "You cannot go past an anchor"; `secrets.token_hex` — "Return a random text string, in hexadecimal". Nothing else of `pathlib`, `secrets`, `time` or `subprocess` was read.
  - **J5. `build_verification_executable`** is unchanged since `1d61696`: between that commit and `304a8fc` only `hilclaw/clang_build.py` changed under `hilclaw/`. It hands `output` to `build` unchanged and passes on what `build` raises (cited: ADR-0091 K3).
- No owner comment on #5 speaks to ADR-0091, T-0278 or ⑱ (마), and HQ-0027 is unanswered (checked on 2026-10-18: the last comment without the driver tail is of 2026-10-15).

## Decision

### 1. Scope and terms

- A call of `correctness.check`, the six kinds, S1 to S10 and the keeper, as ADR-0091 decision 1 has them; the operation reads the class (`isinstance`) and `getattr(error, "parameter", None)` (cited: ADR-0087 decision 2, as ADR-0091 decision 1 applies it). **The artefact path** is the operation's own (cited: ADR-0060 decision 3, the row "Path of the executable; working directory"). **U4** is now a `ValueError` with no `parameter` from after the check of `cwd` up to and including the start (J3). **The mock** builds nothing and is unchanged.

### 2. The name error is no row

- **The operation lets it pass: no row.** By its class and `parameter` it is a named `ValueError` of `"output"`, which ADR-0091 decision 2 makes no row. The operation cannot tell it from U3: both are a `ValueError` with `parameter` `"output"`, and telling them apart would need the message or where it was raised, which the functions do not state — the stop ADR-0091 decision 2 met for an error raised inside a handed object's code. So any other answer would also move U3. An operation that lets it pass is answered `operation_answer_invalid` (cited: ADR-0045 decisions 4 and 5); that is what the landed rules do with it, not an answer of this record.
- **A reason of ADR-0091 does not carry, and this record gives its own.** ADR-0091 kept S3 off because "A `ValueError` of these steps refuses a value before the file or directory of that value is tested" (cited: decision 2). The name error is raised after the tests, for a path whose directory they found an existing directory and which they found no directory (J2). S3 is "The build directory cannot be made or written" (cited: ADR-0060 decision 4), and the tests found nothing of that. What is refused is the name as a value a process can be given. The operation chose that name in the directory it made for the call (cited: ADR-0056 decision 4), so **this record reads the refusal, as ADR-0089 decision 3 read a refused `cwd`, as the operation's own code handing something other than a path it can use** — a defect of code, no row. That the step runs after the tests changes when the value is refused, not whose it is.
- **Not S4.** ADR-0090 decision 2 made the same two refusals, a NUL and on POSIX an `os.fsencode` failure, S4 for a flag or a compiler part, because those are "the backend's own" settings (cited: ADR-0060 decision 3) and S4 "follows from the backend's own settings" (cited: ADR-0060 decision 4). The artefact path is in the other row of that table; no setting of the backend's — flags, compiler, time limits, environment — is in it. **The same defect gets a different answer because the row follows whose the value is**: ADR-0060 decision 4 gives S4 to a `ValueError` or `TypeError` for a setting and no row to a `TypeError` for an argument that is no setting, and ADR-0089 decision 3 reads a `ValueError` for such an argument the same way, as "the class follows how the path is wrong, not whose it is" (cited).
- **The cost, stated.** (i) If the operation forms the name from something it is handed, a character there that the platform cannot take is answered as a defect of code; what the operation forms the name from is the code task's, and this record did not read it. (ii) On POSIX, a file system encoding that cannot hold a name the operation chose is a property of the machine answered as a defect of code; this record did not read which encodings a machine may use. (iii) The same character gets S3 in a directory part (J2; ADR-0086 decision 4) and no row in the file name, so the answer depends on where in the path it stands; this record accepts that, as the tests found the directory unusable in the first case and nothing unusable in the second.

### 3. What is left of U4

- **Removed**: a NUL character, or on POSIX one `os.fsencode` cannot convert, in the output file name, which before J1 reached the command through the temporary name (J2). U4 holds neither now; whether it holds another defect of the name is the unread part of `with_name` below.
- **The steps of J3, read from the code and J4**:
  - **The temporary name.** Its text is the stem and the suffix of a name that passed J1, `.tmp-`, the decimal pid and a hexadecimal string; so it holds no NUL. Whether a POSIX file system encoding could fail to convert the added characters was not read. The `ValueError` J4 documents for `with_name` is for a path with no name, which is an anchor; an anchor is its own parent (J4), so the path tests have already refused it — as a directory where it is one (`IsADirectoryError`), and by the parent test where it is not (`FileNotFoundError` or `NotADirectoryError`), each with `path_role` `"output"`. **This record reads that case as unable to reach `with_name`.** What else `with_name` may refuse in the new name was not read; that may include a defect of the output file name that J1 does not test.
  - **The command and the clock.** The command is a tuple of values the steps before already made and the text of a `Path`; this record reads no `ValueError` from it. For `time.monotonic` this record read no `ValueError` and did not establish that none arises.
  - **`subprocess.Popen`.** What it raises for the command, `cwd` and `env` that `build` hands it stays unread (cited: ADR-0060 decision 4, "was not read"; ADR-0091 decision 3), an `env` with no `items` method included.
- **So U4 now holds**: a `ValueError` from `with_name` other than its documented case or from `time.monotonic`, if one arises, and one from `subprocess.Popen` for what `build` hands it. **It stays open, with the reason of ADR-0091 decision 3**: placing it in any row would read what `subprocess` raises into a row unread. Until it is placed, an operation that lets it pass is answered `operation_answer_invalid` (cited: ADR-0045 decisions 4 and 5), which is what the landed rules do. **The cost**, as there: a setting that only `subprocess` refuses with a `ValueError`, if one arises, gets no S4.
- **What would let it be placed** (named, not decided): a reading of `pathlib`'s `with_name` and of what `subprocess.Popen` raises for the arguments `build` hands it, in a later record; or a code change that makes `build` refuse an `env` with no `items` method, or another such value, in a named check before the start. Either is a later task's.

### 4. No log, and the message

- **No log.** The name error is raised before the compiler lookup and before any process exists (J1), so no compiler of that check ran; the file of ADR-0078 is absent, which says "that no compiler of that check ran or that its log did not reach the tool function" (cited: ADR-0078 decision 2).
- **No message of `settings_refused`.** The operation raises no kind; the message is that of `operation_answer_invalid`, which shows "of what was raised, neither its message nor its arguments nor where it was raised" (cited: ADR-0045 decision 6). The message of the NUL refusal, "output contains a NUL character", shows no path; the `UnicodeEncodeError` is that of `os.fsencode`, whose attribute `object` holds the string it could not convert (cited: the Python documentation of `UnicodeError`), and under ADR-0045 decision 6 neither reaches the log. No rule is added; the wording is the code's.

### 5. No data-plane change

- `parameter` is an attribute of an exception inside the tool function's process; it is no member of a file, a result, a request or a line. No row needs no kind. No value of `condition` or `error.kind` is added, no kind is reserved, and no `schema_version` or layout version changes. No case is left open for want of a new value: U4 is open because it was not read, and a new kind would not read it.

### 6. How far (마) is answered

- **Answered now, for `correctness.check` of the first case and of the mock**: the name error — no row, with no log (decisions 2 and 4). ADR-0091 decision 2 is confirmed for it, with this record's reason in place of its "Not S3" for this case.
- **Narrowed**: the open entry of ADR-0091 decision 7, "that unnamed pre-start `ValueError`, now U4", now holds U4 as decision 3 reads it — `with_name` beyond its documented case, the clock and `subprocess.Popen`; no NUL character, or on POSIX unencodable one, of the output file name is in it. ADR-0091 decision 3's "What would let it be placed" named a code change for a setting; T-0278 made one of that kind for the output file name, which is no setting (decision 2), so that way out stays open for what U4 still holds.
- **Still open under (마)**, as ADR-0091 decision 7 lists them on `main`: that unnamed pre-start `ValueError`, U4 as narrowed here; an unnamed `TypeError` — of `build`, from binding the call or from `subprocess.Popen` or later, or from binding a call of `build_verification_executable`; whatever `clang_build.build` still passes on from `subprocess`, an `env` with no `items` method included; an unroled `OSError` of `build` before the start; the row of a `CompilerRunError` whose `timed_out` is false and whose `returncode` is `None`; and the `ValueError` or `TypeError` and the `OSError` for "a `cwd` that does not exist" of `local_run.run`, which wait for the record of `local_run.run`.

## Consequences

- **Code** (code mode, D12 rules; names and modules are the code task's; **this record binds no code**): the operation of `cpu_standin` for `correctness.check`, when it is written, applies ADR-0079 to ADR-0087, ADR-0089 to ADR-0091 and this record. It lets a `TypeError` or `ValueError` whose `parameter` is `"output"` pass whichever step of `build` raised it, and needs no step of its own for the name error. A reading of `with_name` and `subprocess`, or a code change for what is left of U4 (decision 3), is a candidate follow-up, not required by this record.
- **Not edited and now less exact.**
  - ADR-0091 Status: "It narrows, and leaves open, the pre-start `ValueError` that still carries no `parameter` (decision 3)", now narrower; K1: the cited "The check of `output` forms its absolute path; the tests of that path below are not part of it", "Inside `_parameter("output")` runs only the forming of the absolute path" and "So U3 carries `"output"` where the path is formed", where a second step now refuses the name too (J1); K2: the tests "run after that step and outside any", now followed by another `"output"` step; K4: the list of U4, "the temporary name, the command, the clock, `subprocess.Popen`", through which the output file name no longer carries a NUL or an unencodable character; decision 1: "the unnamed rest is U4 and U5", U4 now narrower; decision 2: "U3, one raised while the absolute artefact path is formed" as the only case of `"output"`, and "Not S5 and not S3", whose reason does not hold of the name error (decision 2 here); decision 3: "What is left is U4 alone" and "What would let it be placed", where T-0278 made a change of that kind for the output file name, which is no setting; decision 7: "that unnamed pre-start `ValueError`, now U4"; Consequences: "A reading of `subprocess` or a code change for U4 (decision 3) is a candidate follow-up", where T-0278 has since narrowed U4 by a change for a value that is no setting; Boundaries: "The row of U4 (decision 3)", now narrower.
