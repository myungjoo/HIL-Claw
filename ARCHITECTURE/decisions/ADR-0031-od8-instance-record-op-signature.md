## Decision

A sentence marked **owner** renders C-6 or one of the two bullets quoted in Context. A value is **cited** when another source is named with it. Every other value is **this record's own** choice — among them the name `op_signature`, its place, the two-member form, the rule of validity as a rule of this file, that the member may be absent, that an absent member means "not stated", that a present and invalid member makes the file invalid, that a file of version 1 states at most one op_signature, that no reading is made of the owner's line about M, that no rule ties the member to a spec, to `db/`, to `hw_profile` or to `tolerance`, and the list of limits.

### 1. Scope

This record fixes one thing of `runs/<run_id>/instance.json`: the member in which a run states its op_signature. Nothing else of the file is fixed and nothing of any other file. **A file that holds what ADR-0018, ADR-0020, ADR-0022, ADR-0023, ADR-0024, ADR-0028 and this record define is still not a complete instance record, and no run can be started from it alone** (ADR-0018 decision 1).

### 2. What the member states

- **The member states the op_signature of the run**: the op_signature record (cited: ADR-0001 decision 2) that the file records for the instance at its start, and the key derived from it. The file holds "What the instance was started with" and is written once (cited: ADR-0004). That knowledge is kept per (hw_profile, op_signature) is FR-13 and FR-7; this record gives the second half of the pair a place in the file of the run and adds nothing to its meaning.
- **What a reader of this record may conclude** from a file that states the member: that the run states this record and this key as its op_signature; the fields of that record — its `schema_version`, the kind, the shape (for `gemm` the `m`, `k` and `n` of ADR-0001 decision 2, so one value of M), the dtype, the layout and, where the record holds them, the further identification fields of `ext` and the attribute `label` — as the record gives them; and, with `hw_profile.key` of the same file, the name `db/<hw_profile.key>/<op_signature.key>/` that FR-13 and ADR-0004 decision 5 give to the directory of the knowledge of that pair. No more.
- **What it may not conclude.**
  - **How the start came to the record** — from a model, a kernel spec file or a frontend (#5 B-5, OD-9). The member says what was recorded, not where it came from.
  - **The kernel contract, the kernel language or a build setting** of the run: neither the prototype nor the language is in the key (cited: ADR-0008 decision 8), and the record holds no build setting (cited: ADR-0001 decisions 2 and 5 — no field of the record is one, and such settings "are not key fields in version 1").
  - **That a stored record or a directory exists below `db/`** for the key or for the pair (decision 6).
  - **What a spec of the run carries** in `task.op_signature` (decision 6).
  - **That a spec, a measurement or a result of the run concerns the stated operation**: nothing checks it (decision 7).
  - **That the run is "of the first case"** in the sense of ADR-0020 decision 2 and ADR-0021 decision 1: the kind and the dtype are visible where the member is present, the kernel language is not, and the member may be absent.
  - **That an instance concerns no more than one op_signature** (decision 4).
- **What becomes less exact in earlier records, which are not edited.** ADR-0020 decision 2 ("no member states the kind, the dtype or the kernel language") and ADR-0021 decision 1 ("does not state the kind, the dtype or the kernel language") hold as written for a file without the member; for a file that states it, the kind and the dtype are stated and the kernel language is still not. **Nothing of either record changes by this**: a validator of the file still does not check that a run is of the first case, the member `tolerance` keeps the meaning ADR-0020 gave it and no other, and what a call of `correctness.check` does with this member is not said here (Boundaries).

### 3. The member

- **The member is `op_signature`**, a top-level member (the name of the record in ADR-0001, of the path level of FR-13 and of the section of a spec), an object with **exactly** the two members below. The object is **closed**.

| Member | Type and form |
|---|---|
| `op_signature.key` | *string*: the `<op_signature>` directory name of ADR-0001 decision 3 |
| `op_signature.record` | object: the full op_signature record of ADR-0001 decision 2, key fields and the attribute `label` where it has one |

- **Valid** when `record` is a valid record by ADR-0001 (what `hilclaw.keys.op_signature_key` accepts) and `key` is the name derived from it; **a file whose `key` is not that name is invalid**, so neither is trusted over the other. This is the form and the rule of `hw_profile` in this file (cited: ADR-0018 decision 3) and of `task.op_signature` in a spec (cited: ADR-0002 decision 2), which `hilclaw/spec.py` already checks; nothing of ADR-0001, ADR-0002 or ADR-0018 changes.
- **Nothing else is a value**: `null`, a string (the key alone included), a number, a boolean, an array (of one object included), an object that lacks one of the two members or holds a third.
- **Why the full record** — the reasons of ADR-0018 decision 3, as far as they carry over. The name cannot be read back: "the remaining fields cannot be recovered from the digest" (cited: ADR-0001 decision 3). A stored record need not exist for the key of a run (decision 6), and the attribute `label` may differ under one key (cited: ADR-0001 decision 5; whether a stored attribute may be updated is OD-26): only a copy made at the start keeps what the run was started with (NFR-2). A reader then has the shape and the dtype of the run from one file of the run and no file of `db/`, which #5 A-1 keeps apart from `runs/`.
- **Why the key beside it.** It names the `<op_signature>` level of the run's knowledge without a derivation — with `hw_profile.key`, a reader that looks for the runs of a pair reads two members of one file — and its form is that of the same section of a spec. A disagreement of the two is found by one derivation and makes the file invalid.
- **Weighed against it:**
  - *The key alone.* A reader would need `db/` for every field of the operation, a run would not hold the `label` it was started with, and a run whose key has no stored record — which no record excludes (OD-26) — would state a name from which nothing can be recovered.
  - *The record alone.* Works; the key beside it costs one derivation at validation and gives the join to `db/` and the form of a spec section (ADR-0018 Alternatives, the same case).
  - *A member inside `hw_profile`.* "a member is added inside `hw_profile`" raises the version (cited: ADR-0018 decision 2), that object is closed, and an op_signature is no part of a hw_profile record.
  - *A new object that encloses both keys, or a `task` object as in a spec.* The first would move or duplicate `hw_profile`, a change of a member that exists; the second would be shaped by members that have no fixed form in this file — the objective (#5 A-4, OD-1) and the contract (decision 2).
  - *A name other than `op_signature`* (`op`, `operation`, `kernel`): the documents, the path level and the spec use this word, and "kernel" is what a run produces, not what it is keyed by.

### 4. One op_signature per file of version 1; sub-question ③ of OD-6

- **In version 1 a run states at most one op_signature**: the member is one object, and no other member of the file states one.
- **Why one is the form that can be fixed.** Each thing the fixed inputs define is defined for one op_signature: the knowledge is kept per pair (FR-13, FR-7), a spec "has exactly one, and so one value of M" (cited: ADR-0002 decision 2), and one best reference and one set of statistics are kept per (hw, op) directory (cited: ADR-0001 decision 2). So a statement of one op_signature has a meaning by records that exist. A file that stated two would state something no record gives a meaning to: which spec, which measurement, which objective, which tolerance and which best belongs to which entry (ADR-0018 decision 5 names the same consequence for one hw_profile, "no call has to tell which"; its reason, that the inputs carry one HW, is not claimed here for the op_signature).
- **What this does not answer: whether one instance may cover several values of M, or several of the projections.** **Owner**: "M (tokens) ∈ {1, 32, 512} as instance parameter (decode / small batch / prefill)", and the bullet before it names four projections as the "Kernels" of the first spec example. **This record makes no reading of either bullet**: that an instance takes one value of the set and one projection, or that an instance may cover several, is each a reading the words admit, and choosing between them is the owner's (#5 B-4). That M is a field of the key, so that two values of M are two op_signatures, is ADR-0001's choice and "not a statement of B-4" (cited: ADR-0001 decision 2). **Owner**: the MVP is the optimisation of a single compute kernel (C-6); whether "a single compute kernel" is one op_signature in the sense of ADR-0001 is not said by C-6, and this record does not read it either way.
- **So the member is a rule about what a file of version 1 can state, not about what an instance may be.** A reader of this record may not conclude from the form of the member that an instance is limited to one op_signature. If the answer to sub-question ③ is "one", nothing here changes. If it is "several", a later record says how such a run states them: it changes this member or adds one, and applies the version rule of ADR-0018 decision 2; reading a file of another version is OD-11. Until then no record gives a run of several op_signatures a way to state them, and this record does not say what the file of such a run would hold.
- **In the register**: of sub-question ③ of OD-6, answered is where and in which form the instance side is stated (this member, at most one per file of version 1); open, as registered, is the question itself.

### 5. A file without the member; the version

- **The member may be absent from a valid file, and `schema_version` stays `1`** — the first of the two choices ADR-0018 decision 2 leaves to the record of a member ("A later record that defines a top-level member which may be absent and may be passed over does not raise it"). A version 1 reader may pass over the member: no fixed rule makes anything a reader of today does depend on it, and a reader that needs the op_signature of a run is one that knows the member.
- **A member that is present must be valid.** A file whose `op_signature` breaks decision 3 is **invalid** in the sense of ADR-0018 decision 2: a reader of this record reports it, uses no member of it — not its `hw_profile`, its `tolerance`, its `source_commit`, its `n_max` or its `candidates_per_round` either — and repairs nothing. This follows ADR-0020 decision 3, ADR-0022 decision 5, ADR-0023 decision 4 and ADR-0028 decision 4.
- **A valid file without the member states no op_signature.** A reader of this record that is asked for the op_signature of such a run finds that none is stated and **never substitutes one**: not the `task.op_signature` of a spec of the run, not the name of a directory below `db/<hw_profile_key>/`, not the op_signature of another run, not a record of ADR-0008 decision 9, not a constant of the source the reader runs from, and nothing inferred from another member of the file.
- **No path yields an op_signature the run did not state.** A reader of this record has the op_signature of a run only when the file of that run is valid, is of version 1 and holds the member. A missing file, a file that cannot be read, an invalid file, a file of another version and a valid file without the member each leave it without one.
- **A valid file is "not thereby enough to start a run"** (cited: ADR-0018 decision 2). Whether the start of an instance refuses to begin without an op_signature, and where it is checked that an instance states one, is the writer's and is not decided (sub-question ㉘).
- **Why not a required member and version 2.** The inputs would bear it: `hw_profile` is required, and the pair is what the knowledge is keyed by. It is still not chosen: every file and every reader of today would be of another version before a first run exists; the record would have to say which layout version the new `schema_version` states (ADR-0024 decision 3); reading another version is OD-11; and a member that every file of the version must hold, in the form of decision 3, would settle by the validity of a file what decision 4 leaves open — that every instance of that version has exactly one.
- **The cost**: validity does not show that an op_signature is stated. A file without the member and a file whose member name is misspelt look alike to a version 1 reader — both state none (decision 7).

### 6. The member, `task.op_signature` of a spec, `hw_profile`, `tolerance` and `db/`; how it is read

- **This record adds no rule between the member and the `task.op_signature` of a spec.** A spec is valid or invalid by ADR-0002 alone, whatever the file of its run states, and no validator of this record reads a spec; ADR-0002 is not edited. **Why none**: a rule "equal in every spec of the run" would answer sub-question ③ of OD-6 with "one" (decision 4), would have to say whether the attribute `label` counts, and would bind whatever issues the specs, which no record has named (OD-23). So a reader of this record may not conclude the `task.op_signature` of any spec from the member, nor the op_signature a run states from a spec. Whether the two must agree, in what, and what checks it is registered (sub-question ㉘).
- **No rule that a stored record exists, and no check against `db/`.** The embedded record and `db/<hw_profile_key>/<op_signature>/op_signature.json` can differ in `label` — not in key fields under one key, short of a collision of the name (ADR-0001 decision 3) — and a stored record or a key directory need not exist for the key of a run: a reader of this record does not look. Who registers a key, and when, is OD-26; how the two records relate is registered beside sub-question ⑱ (sub-question ㉘).
- **No rule between the member and another member of the file.** The pair of `hw_profile` and `op_signature` is not checked for anything beyond the validity of each, and a `tolerance` beside an `op_signature` of any kind or dtype is valid as before (decision 2).
- **The op_signature a run states is the one in this member of the file of that run**, `runs/<run_id>/instance.json` below the data root in use. A reader of this record reads the file as a whole, which must be valid (ADR-0018 decision 2), and **nothing is kept between calls** (cited: ADR-0010 decision 7; ADR-0018 decision 4): a later call reads the file again.
- **Today nothing reads or writes the member**: no tool, registry, backend, hook or module does, and `hilclaw/instance.py` passes it over. **Not said here**: which component reads it, at which moment, and what follows when no op_signature is stated (Boundaries).

### 7. Limits

- **Whoever can write the file changes the op_signature the run states.** No access control exists and the tree does not enforce the single writer (cited: ADR-0004 decision 10); a file changed after the start is read as it is at that read (cited: ADR-0018 decision 6), so two reads of the file of one run can find two op_signatures.
- **A misspelt name.** A top-level member that is not spelt `op_signature` (`op`, `opSignature`, `task`) is passed over (cited: ADR-0018 decision 2, the cost) and the file states no op_signature.
- **Nothing checks that the run concerns the stated operation**: not that its specs carry it, not that its kernels compute it, not that its measurements or results are of it. No file records the op_signature a round was carried out under beyond what the specs of the round say of themselves.
- **The member does not state the contract.** Two runs that state the same op_signature can hold kernels of different contracts or languages (cited: ADR-0008 decision 8; sub-question ④ of OD-6).
- **A kind the reader's source does not know.** A new `kind` does not raise the version of the key schema (cited: ADR-0001 decision 6), and `hilclaw.keys.op_signature_key` knows `gemm` only. A source that does not know the kind of the embedded record takes the member, and so the whole file, as invalid — its `hw_profile` included (decision 5) — where a source that knows the kind takes it as valid: the case ADR-0018 decision 6 named ("Two processes, two validators"). The same holds between a source older than the code of this record, which passes over the member, and a newer one, which refuses a file whose `op_signature` breaks decision 3.
- **Validity of the record is not existence of the operation**: a valid `gemm` record of any `m`, `k` and `n`, any name as `dtype` and any name as `layout`, with or without an `ext`, is a value, whether or not a contract, a harness or a backend exists for it.

### Walk-through

What a reader of this record finds when it is asked for the op_signature of the run `r1`. "The member above" is the `op_signature` of the Example.

| `runs/r1/instance.json` | What the reader finds |
|---|---|
| Valid, version 1, with the member above | The op_signature `r1` states: that record, with the key `gemm-485b9bc494d477eb`. Asked again in a later call, it reads the file again. It does not look below `db/` and reads no spec |
| Valid, version 1, without the member (or with the same object under the name `op`) | No op_signature is stated for `r1`. None is substituted. The `hw_profile`, the `tolerance`, the `source_commit`, the `n_max` and the `candidates_per_round` of the run can still be had |

## Alternatives considered

## Consequences

- **The code slice that can now be cut** (within the size cap, code mode): in `hilclaw/instance.py`, the validity of the member by decision 3 and a reader of the op_signature of a run beside `hw_profile_of`, with tests in `tests/test_instance.py`. The names, the return form of that reader and how "not stated" is told from a value are the code task's; the check can be the one the module has for `hw_profile`, with `hilclaw.keys.op_signature_key`. **Binding the reader to a spec, to a tool or to `db/` is not part of that slice**, and neither is writing the file. `hilclaw/instance_file.py` takes the validity of a content from `hilclaw.instance.parse`, so it refuses a content with an invalid member once the slice lands, without a change of its own.
- **Sentences of the code that then change**: in the docstring of `hilclaw/instance.py`, the list of the records in its first line and first paragraph, "Conventions of this module, which the six records do not fix", the order of the checks, "It defines no member besides the six (…) and interprets no other", and the descriptions of `Instance.others` in `parse` and of the records in `validate`. No case of `tests/test_instance.py` holds a top-level `op_signature` member today, so none asserts a content valid that this record makes invalid; the assertion on `Instance._fields` and every case that builds an `Instance` positionally change only if the slice adds a field to that tuple.
- **Not edited and now less exact** (follow-ups for the integrator): ADR-0018 decision 3 ("no file states the op_signature of a run yet") and the Boundaries of ADR-0018, ADR-0023 and ADR-0028, which list the op_signature of the run among the members of later records, and through the list of ADR-0018 the Boundaries of ADR-0020 and ADR-0022; ADR-0020 decision 2 and ADR-0021 decision 1 as decision 2 above says; ADR-0021 Boundaries ("no member of `instance.json` names the op_signature of a run"); ADR-0002 Boundaries ("Whether one instance may cover several values of M is a question of `instance.json`" — the file now has the member, and the question is open as before); the lists of what makes `instance.json` invalid in ADR-0018 decisions 2 and 4 and in ADR-0019 decision 3, which an `op_signature` that breaks this record joins; ADR-0020 decision 3, ADR-0022 decision 5, ADR-0023 decision 4 and ADR-0028 decision 4, where the members of an invalid file that are not used now have one more beside them; ADR-0025 decision 2 and its Boundaries, where the members a valid content may lack now have one more. No sentence of UsageCases became false: the glossary and UC-1 step 1 could name the member.
- **A-13 reading**: document mode; no code, dependency, settings file or schema file changes. The record adds one member that may be absent to a file whose frame says how later records add members (ADR-0018 decision 2), along the D6 route as ADR-0020, ADR-0022, ADR-0023 and ADR-0028 did; by that frame's own rule the version stays `1`. **The set of valid version 1 files becomes narrower without a new version**: a file that holds an `op_signature` breaking this record was valid before and is invalid now — the case ADR-0018 decision 6 named; no such file exists in a data plane, since nothing starts an instance yet. No member, value list or validity rule of `hw_profile`, of `tolerance`, of `source_commit`, of `n_max`, of `candidates_per_round`, of the key records or of `STATE.json`, `spec.json`, `artifacts.json` or `events.ndjson` changes.

## Boundaries (not decided here)

- **Owner-only or waiting for the owner (DRIVER §9)**: how an instance comes to its op_signature — the model input, a kernel spec file, frontends, `model_ref` (#5 B-5, OD-9); which of the B-4 operations and which M a first run takes (the owner's B-4 excludes lm_head from the first runs and puts GEMM before the attention family; this record takes nothing from either); whether one instance may cover several values of M or several projections, as far as that is a reading of #5 B-4 (sub-question ③ of OD-6); anything that widens or narrows C-6; the objective (#5 A-4, OD-1).
- **The kernel contract, the kernel language and the build of a run** (ADR-0008; sub-questions ② and ④ of OD-6), and whether the file states any of them.
- **Every other member of `instance.json`** (PLAN P1-8), none of which is named here, and no object that would enclose one: the round budget and every budget member (FR-3, OD-2, OD-19); owner and project; any time member (OD-8 sub-question ⑨); gates and the autonomy mode (#5 A-5, OD-3); the coder model and the token budget (#5 A-8); datasets (#5 B-8); tolerance vocabularies beyond the first case (#5 B-7).
- **The writer and the start of an instance**: what writes `instance.json`, from which input it takes the op_signature, whether the start refuses to begin without one, and whether it stores a record below `db/` or requires one (OD-8 sub-questions ⑩, ⑰ and ⑱, and ㉘ below; OD-23; OD-26; UC-1).
- **Any tool's contract** (OD-18): no tool, moment of a call, request or result member or tool-failure kind is given here — in particular not where the dimensions of a `correctness.check` come from (OD-16 sub-question ①), not what a call answers for a run that is not of the first case (OD-18 sub-question ⑩), and nothing HQ-0005 asks.
- **The index from a key to its runs** (OD-8 sub-question ②; S5 step 1; OD-20); similarity between keys and the use of the statistics of another M (rest of OD-4); a resume, a continuation or a branch under another op_signature (FR-6; OD-8 sub-question ①); reading or migrating a file of another version (OD-11); the `shape` members of another kind (ADR-0001 Boundaries).
- **Sub-question this record raises** (registered under OD-8): ㉘ Three parts. (i) Where it is checked that an instance states its op_signature — whether the start of an instance refuses to begin without one — and what follows for a run whose valid file states none (with ⑰, OD-23, UC-1; how the start comes to the record is #5 B-5 and OD-9). (ii) Whether the `task.op_signature` of the specs of a run must agree with the op_signature the run states — in the key or in the whole record, `label` included —, and what checks it (with OD-23 and sub-question ③ of OD-6). (iii) How the record embedded in `instance.json` relates to the stored record `db/<hw_profile_key>/<op_signature>/op_signature.json`: whether the start of an instance stores it or requires it to exist, and what holds once their `label` differs (beside ⑱; with OD-26).
