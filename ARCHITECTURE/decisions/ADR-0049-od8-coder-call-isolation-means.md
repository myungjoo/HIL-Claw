## Decision

Whose a sentence is: **the owner's** where O1 to O4 is named; **cited** where another source is named; **this record's own** otherwise.

### 1. Scope

- One coder call of the first case — one `claude -p` process started for one spec (FR-5; one spec is one call, [ADR-0002](ADR-0002-od6-codegen-spec.md)) on a machine of C-7 where the kernel is C built with clang (#5 A-7) — and the files of the data plane around that call.
- Not in scope: any other actor (the selection, measurement and evaluation roles, the Round-Manager, the tool layer), the execution of a generated kernel, and everything under Boundaries.

### 2. The means, and the outcome for each registered item

**The means.** A coder call runs **inside one container**, started by the container runtime of the machine (O1 names Docker and Podman). The means is these four properties, and names no image, no flag and no product feature beyond them:

- **P1 — everything inside.** The coder process and every process it starts run inside that container, from their start to their end.
- **P2 — one writable host path.** Exactly one directory of the host is writable from inside: the scratch directory of this call (decision 3). Nothing else of the host is given to the container in a form that lets it change the host: no second writable mount, no means to direct the container runtime, no added privilege, no file system of the host other than what is mounted. P2 is about file systems and the control of the container runtime; **the network is not part of it** (L4).
- **P3 — crossing by copy.** What the coder is given is copied into the scratch before the call; what it produced is brought from the scratch into the tree after the call, by the side that holds the `coder/` role (decision 4).
- **P4 — removed afterwards.** The container is removed when the call has ended, and the scratch is removed once the bring-in for the call has finished or been given up; anything else the means created on the machine for that call ("containers, scratch directories and the like" — O3) is removed at the same time. The removal of a scratch follows no symbolic link: it removes what lies below the scratch and nothing a name in it points to. This is this record's reading of O3 ("cleaned up after the work completes") for one call; "the installed runtime package and pulled images stay" (O3).

**Without the boundary there is no call.** Where no container runtime is available to the user who runs the instance, a coder call is not started; it is never run without P1 and P2 as a fallback. That the runtime "may ask the user for permission and install the package" is O1, and O2 says the like of a set-up step (this record reads "the runtime" there as the HIL-Claw runtime, the reading O4 suggests with "the runtime machines of C-7"; the words themselves are only "the runtime"); what asks, when, and what an unattended instance (S2) does is not decided (sub-question ㉝).

**Docker first.** For Docker, D1 shows that a mount of a host directory can be writable or read-only, and D2 that what is written elsewhere inside a container does not outlive it. **That is all the cited sentences show**: that a container started with one such mount and nothing else added leaves no other way to change the host — the rest of P2 — is this record's expectation and is **not verified** (L1). Nothing was read of Podman, so the first implementation is Docker-based, which O3 lets this record take; Podman is admitted when the four properties are shown for it.

**The comparison under the owner's facts.** Candidate ② alone leaves the coder process a shell of the same user on the host: it then ensures that nothing written elsewhere is read as output, but prevents no write — the harness in the source checkout stays writable by that process, which is not what FR-9 asks ("코더가 수정할 수 없는"). Candidate ① item 4 prevents the write, under the conditions of G1 (decision 5), but was held back by "컨테이너(Docker/Podman) 가용성은 미확인" (cited: [OpenDecisionProposals OD-14](../OpenDecisionProposals.md#od-14); the OD-14 row said the same before this record); O1 removes that reason. Candidate ①'s own prerequisite (out-of-tree builds) is met by clang for the first case (cited: `clang_build.py`) and is otherwise not needed, because P3 copies instead of mounting a checkout for building. The two candidates are therefore not alternatives here: ① gives the boundary and ② gives the crossing.

### 3. The write root

- **One scratch directory per coder call**, new for that call and used by no other call. It is the write root of the coder process and the only one on the host.
- **It lies outside both checkouts** (the source repository and the data repository) and inside neither's `.git/`. This settles ADR-0004 decision 7 for the coder call. Reasons: a directory inside a checkout would put coder-written names and bytes under a tree that `git` walks and that a commit step keeps out only by an ignore rule; it would need a change of a `.gitignore`; and its removal (P4) would be a recursive removal inside a checkout.
- **No path of the tree of ADR-0004 is inside it, and it is no path of that tree** (cited: decision 7). The exact location and name are the code slice's; this record adds no path, name or version to the layout (layout version 1 unchanged).
- **Temporary files and build caches of the call** (candidate ① item 2) are inside the scratch or in the container's own file system, which does not outlive the container (D2). The coder's own builds during a call "are part of its output" (cited: ADR-0004 decision 3) only as far as the bring-in takes them.
- **What is visible inside is not decided by the means.** Whether a checkout is additionally shown read-only inside the container changes none of P1 to P4; it is a question of what a coder may read (OD-12, OD-16) and is registered (sub-question ㉝).

### 4. What crosses the boundary

**In, before the call** (by the side that issues the call):

- **A copy of the bytes of the spec file of the call** — the `spec.json` of the tuple (cited: ADR-0029 decision 2 for the bytes). ADR-0029 left "how a spec reaches the coder" open; this record says only that the coder reads a copy in its scratch and never the file in the tree. How the coder process is pointed at it is PLAN P2-2.
- **Any further kind of file is a later record's** (OD-23, OD-6, OD-12). Whatever is placed is a **copy with its own bytes** — never a symbolic link or a hard link to a file of a checkout. A hard link is another name of the same file ("creates a new name for an existing file" — POSIX `link()`, cited: ADR-0014 Context), so a write through it would be a write to the checkout's file; what a symbolic link resolves to inside a container is **not verified**, and the rule is the one of the bring-in: no link crosses the boundary in either direction.
- **Never placed**: the harness, its reference and the calibration kernels (cited: FR-9; ADR-0003 decision 5). Runtime seeds and input values "do not exist as files" (cited: ADR-0004 Context, the confirmed parts of OD-16) and are never a file of the data plane (cited: ADR-0004 decision 7).

**Out, after the call** (by the side that holds the `coder/` role — cited: ADR-0004 decision 4; the coder process writes nothing in the tree):

- The bring-in starts only after the container of the call has been removed (P4), so that nothing inside is left to change what is read. That a removed container leaves no process of its own running is what this record expects of a container runtime; it is **not verified** (L1).
- It reads **regular files below the scratch only**: it follows no symbolic link, executes nothing it finds and treats every name as data. It writes **only below the `output/` of the attempt of that call**; no name it meets can make it write elsewhere.
- Which files it takes, in what form, under which names, with what bounds on number and size, and whether anything is taken from a call that did not end normally: OD-23 and OD-19.

### 5. What the means guarantees, and its limits

**Guarantees.**

- **G1 (prevention, conditional on L1, L2, L4 and L5).** While P1 and P2 hold, the coder process and everything it starts can change, **through the file systems the container is given**, no file of the host outside its scratch: not the harness or any other file of the source checkout, not a file of the data checkout (records, logs, `STATE.json`), not the `.git/` of either. G1 says nothing of a change made by another route (L4).
- **G2 (a property of the bring-in, not of the host).** The bring-in of a call reads the scratch of that call and nothing else, so the means itself never takes a file from anywhere else as that call's output. G2 does not say that no file can come to lie below an `output/` by another way (L10).

**Limits.**

- **L1 — The boundary is the container runtime's, and it was not tried.** This record defends against nothing that escapes the container runtime, and no machine was used to check P1 or P2 (this record's own statement; the reason is O4 and D16). Whether they hold on a machine of C-7 is a **runtime acceptance item** (Consequences).
- **L2 — Docker's documentation only.** D1 to D5 are Docker's; for Podman nothing is verified. The daemon "requires root privileges unless you opt-in to Rootless mode" (D4): a mistake in how the container is started (a wider mount, the container runtime's control given inside) undoes G1, and the means has no second line behind it.
- **L3 — The coder's product is outside the boundary.** A generated kernel is built and executed by processes on the host that are "not sandboxed" (cited: `local_run.py`; ADR-0017 decision 10 — and ADR-0009 decision 10 has "No protection against forged timing" for the timing run). Code a coder wrote can therefore do, when it is built or run, everything G1 keeps the coder process from doing — and possibly more (L11). **Threat A of OD-16 is not removed**: what G1 keeps out, under its conditions, is harness or timer patching and score or log tampering *by the coder process during its call*; the same acts by a generated kernel, and buffer theft, stay with the rest of OD-14 and OD-16.
- **L4 — The network is not restricted.** A coder call needs to reach Anthropic (C-7 ②, ④). Whatever else the machine lets a container reach — LAN tools (C-7 ⑤), the internet — a coder can reach, and it can ask a reachable service to act: where such a service runs on the host or on a LAN machine and writes files there, G1 does not cover the change (OD-12, OD-14).
- **L5 — What is readable inside.** Whatever the coder process needs in order to run — the Claude Code program, its configuration and its sign-in (C-7 ②) — is readable by a coder with a shell; together with L4, a coder can send what it can read, the user's sign-in included, to wherever the network reaches. **Not verified**: whether a `claude -p` process runs when the only writable host path is the scratch. If it needs a second writable host path, P2 does not hold as written and this record is revisited.
- **L6 — Per platform** (C-7 ①). On every platform the compiler and the libraries inside a container are those of its image, and the measured build uses those of the host (L3): whether what a coder builds and tries inside behaves like the measured build is not verified anywhere, and which image is used is PLAN P2-2. Linux: not verified — whether files in the scratch end up owned by another user than the one who runs the instance or carry mode bits that user would not have set, and whether P4 can then remove them. macOS: with Docker Desktop "the daemon runs inside a Linux VM" (D3), so a coder inside builds and runs for Linux, **not for the platform on which the kernel is measured**: it cannot try its kernel on the measured platform at all (this record's inference from D3; not tried). Windows: C-7 presumes WSL, so the measured platform is Linux; whether the container runtime is one inside the WSL distribution or Docker Desktop is not decided, and nothing about either is verified. On macOS and Windows alike, which host paths can be mounted into a container, and at what speed, is not verified.
- **L7 — No ceiling.** No time limit, no bound on processor, memory or the size of the scratch: a coder can fill the disk the scratch is on (rest of OD-14).
- **L8 — The content is untrusted and unfiltered.** G2 says where output comes from, not that it is honest: threat B of OD-16 is untouched. The bring-in does not inspect what it takes, so anything a coder could read inside (L5: the user's sign-in included) can be written into the scratch and brought into `output/`; once committed it stays (cited: ADR-0004 decision 7, "Secrets"). Names are as unfiltered as content: the bring-in keeps a name from leading outside `output/` (decision 4) and nothing more, and whether a name a coder chose can mean something to `git` or to another tool that walks the data checkout was not examined. What is taken, under which names, and whether it is checked is OD-23 and OD-16.
- **L9 — Leftovers.** If the process that issued the call dies, a container and a scratch can remain. They are not state: nothing reads them as output or resumes from them. How a later turn finds and removes them is registered (sub-question ㉝). Whether a container runtime leaves anything of its own on the machine after a container is removed, beyond the container's own file system (D2), is not verified.
- **L10 — When the boundary fails, nothing here notices.** If G1 does not hold on a machine (L1, L2, L5) or does not apply to the route taken (L4), a coder process could write directly below an `output/` of the tree, where a reader of `output/` would take the file for output, or into the scratch of another call (S8: N calls), from where that call's bring-in would take it. This record has no check that detects either.
- **L11 — The means puts control of a container runtime in the hands of the user who runs the instance.** A coder call can be started only if that user can start containers. For Docker, whoever controls the daemon "can start a container where the `/host` directory is the `/` directory on your host; and the container can alter your host filesystem without any restriction" (D5), and the daemon "requires root privileges unless you opt-in to Rootless mode" (D4). A process outside the boundary that runs as that user — a generated kernel when it is built or run (L3), an actor this record does not confine — may therefore reach, through the container runtime, more of the host than that user's own files. Whether it can on a given machine of C-7 (Rootless mode, Docker Desktop's VM, Podman) is **not verified**. This exposure comes with requiring a container runtime at all.

### 6. Sub-questions ⑭, ⑯, ㉓ (나) and ㉖ (나)

These asked how "the isolation means, once chosen" gives a writer the right to create, rename or link, and remove temporary entries beside a final name and to create missing directories above it.

|---|---|---|
| ⑭ `STATE.json` | Round-Manager | **Answered for this means, open for the rest.** This record puts no writer inside the container and confines only the coder process; P1 to P4 take no right from this writer and give it none. What it may do is what the file-system rights of the process it runs in allow, as today. |
| ⑯ `artifacts.json`, key record files | Tool layer; whatever creates the key directory | The same. |

| ㉖ (나) `spec.json` | Coder-call role | The same; the temporary entry lies beside `output/` in the tree, never in the scratch (cited: ADR-0029 decision 6). |

**What stays open in all four**: if a later record confines in-process actors (candidate ① item 4, second half, or item 5), it must allow each writer the entries its write procedure needs. They no longer wait for the choice between the candidates or for container availability; they wait for OD-18 and OD-23.

### Walk-through (one call; no step names a tool, a flag or a file beyond the records)

1. **Before.** The coder-call role has written `…/coder/candidates/01/attempts/01/spec.json` (ADR-0029). The side that issues the call creates a new scratch directory outside both checkouts and copies the bytes of that spec into it.
2. **During.** A container is started with that scratch as its only writable host path, and the coder process runs inside. It writes sources, builds and tries them inside, and creates temporary files — all in the scratch or in the container's own file system. An attempt to change a file of the harness leaves the host's file unchanged: no path of the host but the scratch is writable inside (G1, under its conditions). Whether the attempt itself fails or lands in the container's own file system depends on what is visible inside (sub-question ㉝ (다)).
3. **After.** The coder process ends and the container is removed. The `coder/` role side reads the regular files of the scratch and writes what it takes below `…/attempts/01/output/`. The scratch is removed.
4. **The coder process dies, or is stopped.** The container is removed all the same. Whether anything is brought in from that scratch is OD-23 and OD-19; the scratch is removed once that is settled for the call (P4).
5. **A file left outside the scratch.** Inside the container's own file system: it disappears with the container (D2) and was never output. On the host: G1 is meant to prevent it. Should it happen all the same — G1 not holding (L1, L2, L5) or not applying (L4) — the bring-in still reads only the scratch of the call (G2), so the file is not brought in — unless it lies below an `output/` or in another call's scratch (L10) — and the change itself is detected by nothing in this record.

## Alternatives considered

| Alternative | Why not |
|---|---|
| Candidate ② alone, no container | Prevents no write by a coder with a shell (decision 2); under O1 the reason to prefer it — "컨테이너를 요구하지 않는" — no longer decides. It remains what the crossing is. |
| Candidate ① item 4 as written, as a requirement of the means: both checkouts mounted read-only, the coder reading them in place | Not taken as a requirement; whether a checkout is shown inside at all stays open (sub-question ㉝ (다)). ## Consequences

- **Slices for the planner** (code mode; no module is named or decided here), each bound to nothing when it lands: (a) a function that creates the scratch of a call — refusing a location inside a given checkout — and places copies in it; (b) a function that brings regular files from a scratch into the `output/` of an attempt under the rules of decision 4; (c) a function that removes a scratch without following a link out of it (P4); (d) the start and removal of the container, with PLAN P2-2. (a) to (c) need no container runtime to test. (d) can be tested against a stub runtime only; what it does on a real one is the runtime acceptance item below.
- **Runtime acceptance items** (CLAUDE.md "개발 드라이버와 런타임의 구분"; not driver tasks — to be notified by DRIVER §8, reason `runtime-acceptance`): on each kind of machine of C-7, that a `claude -p` call runs inside a container whose only writable host path is the scratch (L5); that after a call in which the coder tried to change files of both checkouts, neither checkout has changed (P2, L1); that the scratch can be removed afterwards by the user who runs the instance (L6); that the container can reach Anthropic (L4).
- **A-13 reading.** Document mode; no code, dependency, settings or schema file changes, and no data-plane file, path or member is added. The container runtime is an external requirement **of the runtime**, permitted by O1; no image is adopted. Nothing is required of the development machine (O4).
- **Sentences of earlier records that are now less exact** (none edited): ADR-0004 Status ("**the isolation means** (candidates ① and ② of OD-8, both kept)"), Context (the last bullet), decision 4 ("How its files reach `output/` is the isolation means"), decision 7 (the last sentence), the `output/` row of the path table, Boundaries (the first bullet, "Waits for two facts from the owner"); ADR-0003, the row of threat A ("which are OD-8 and OD-14 and open") and its Boundaries; ADR-0010, "That candidate is a registered proposal and **not chosen**" and the two consequences headed "Under OD-8 candidate ①" and "Under OD-8 candidate ②"; the Boundaries bullets "The isolation means (… waits for #5 B-1 and container availability)" of ADR-0013 and ADR-0014 and "The isolation means and the rights of a writer …" of ADR-0025 and ADR-0029, the sentences "Where scratch and build-cache directories are … is not decided or narrowed here" of ADR-0013 decision 3, ADR-0014 decision 4 and ADR-0025 decision 6, and "Where such directories are, and where the coder process works, is not decided or narrowed here" of ADR-0029 decision 6. Each stays true of everything this record leaves.
- **The cost, plainly.** A coder call now needs a container runtime, an image that holds what the coder needs, and a way for its sign-in to reach inside; on macOS the coder cannot try its kernel on the measured platform (L6); and the user who runs an instance must be able to control a container runtime, which is itself a way to change the host (L11). None of these existed under candidate ② alone.

## Boundaries (not decided here)

- **The agent roster**, which agent holds which role, the per-agent tool allowlists, whether `coder.run` exists (OD-23); **the `PreToolUse` path check and every hook** (OD-18, PLAN P2-4); the check of a round's diff against allowed paths.
- **How the coder process is started**: the image and what provides it, the container runtime's flags, the prompt, the model and permissions of `claude -p`, how its sign-in reaches inside; whether an image is pulled or built on the machine, and what P4 does with one that was built there — O3 speaks of "pulled images" only (PLAN P2-2, #5 A-8).
- **The files and form of `output/`**, and what is taken from a call that failed (OD-23, OD-19); a second bring-in for one tuple (with sub-question ㉖ (가), which asks the same of a second write of a spec).
- **Time limits, resource ceilings, health checks, the blacklist** (rest of OD-14); **the isolation of the execution of a generated kernel** — this means covers only what a coder builds and runs for itself inside its own container during its call, and nothing of the measured build or run (L3).
- **What a coder may read or search**, the network from inside (OD-12, OD-16); the defences of OD-16 beyond the FR-9 minimum.
- **Every other backend and toolchain** (#5 B-1, B-2); a coder call on a machine other than the one that holds the checkouts.
- **The lock and a second writer** (rest of OD-17); parallel coder calls beyond "one scratch each" (OD-29); which step commits.
- **Sub-question this record raises** (registered under OD-8): ㉝ in four parts. (가) What part of the HIL-Claw runtime asks the user for permission and installs a missing container runtime, at which moment, and what an unattended instance does (O1, O2; with OD-23, UC-3). (나) How a later turn finds and removes a container and a scratch left by a dead process (with OD-17, OD-23). (다) Whether a checkout is shown read-only inside the container (with OD-12, OD-16). (라) Whether Podman gives P1 to P4, and which runtime is used on Windows with WSL.
