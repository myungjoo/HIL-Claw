## Context

- **The threat**, in ADR-0017 decision 10: "**The verified executable is not the timed one**: a kernel can tell the two programs apart and compute properly only when it is verified, and two builds may differ. Nothing here detects either (rest of OD-16; sub-question ⑥)." ADR-0017 decision 2 kept the two programs apart and stated the cost: "an attempt is built twice (one executable per program), and the executable that is verified is not the executable that is timed".
- **Since then each tool has its settings without a relation between the two.** For the check: "Every setting is the backend's own", and "Whether the verification build and the timing build use the same settings is open as before: the timing build is the run tools', and only a record of theirs can say whether their settings are the same backend's own" (ADR-0060 decision 3). For the run tools: the settings of the timing build and run are the backend's own, and "Whether the timing build and the verification build of one backend use the same values is not decided" (ADR-0061 decision 3). Both operations build at each call, into a build directory of their own that they remove (ADR-0056 decision 4; ADR-0061 decision 2), so an attempt that reaches the board point is built four times (ADR-0061 decision 2).
- **The inputs have their answer and it is not reopened**: "the inputs of a timing run are not tied to the verification inputs of the same attempt" (ADR-0064 decision 6).
- **What the code has today** (observations at `c26a834`). `hilclaw/harness/verification_build.py` and `hilclaw/harness/timing_build.py` each hand the harness program's source and the kernel sources to one call of `clang_build.build`, the program source first, with flags, trailing flags, compiler, working directory, environment and time limit "handed over unchanged"; "The harness adds no flag", and the caller's flags "apply to the program source as well" (in the timing module: "to the driver source as well"). The verification module says it "does not make the flags of this build equal to those of a timing build, with which it shares nothing". No operation of `cpu_standin` exists for either tool, and nothing in the package holds a setting value. `hilclaw/check_build.py` places the answers of a verification build and holds no setting.
- **Not available, and not used**: any setting value or its source (⑱ (라), ⑲ (라), OD-14); the design of the container (OD-14 sub-question ①); the members of `build.json` (OD-6 sub-question ②); the record of a build's command and settings (⑰ (다)); the compiler log of the timing build (⑲ (다)); ⑲ (나); #5 A-4, B-2, B-3 and B-7.

## Decision

A sentence marked **owner** quotes O1 or O4. A sentence is **cited** when a record and its decision, or a requirement, is named with it; it then says what that source says and adds nothing. Every other sentence is **this record's own** — among them the choice of two executables kept, the sameness rule and its granularity, which settings it covers, the reading of the threat, and every weighing.

### 1. Scope and terms

- **The runs**: a run whose hw_profile names `cpu_standin` — the first case (`gemm`, fp32, a C kernel), in the local configuration of [ADR-0038](ADR-0038-od18-cpu-standin-execution-points.md) decision 1 — or names the mock; the runs for which both `correctness.check` (cited: ADR-0056 decision 1; ADR-0060 decision 1) and `sim.run` / `board.run` (cited: ADR-0061 decision 1) have contracts. **Owner** (O1): "In the first case (the owner's local PC, native build and run) the two carry out the same local run; nothing but the execution point distinguishes the two operations."
- **Verification build**: the one call of `clang_build.build` an operation of `correctness.check` makes over the verification program and the compiled set (cited: ADR-0056 decision 4). **Timing build**: the one call an operation of `sim.run` or `board.run` makes over the driver program and the compiled set (cited: ADR-0061 decision 2). **Harness program**: the verification program or the driver program. **Build settings**: the rows of the settings table of ADR-0060 decision 3, as ADR-0061 decision 3 takes them for the run tools — flags and trailing flags; compiler; time limit of the build and of the process; environment (thread settings travel here) — and the operation's own path of the executable and working directory.
- The terms of ADR-0016 (backend, operation), ADR-0038 (execution point, sim point, board point), ADR-0055 (the reader, the compiled set) and ADR-0056 (the output path, the build directory) are used unchanged.

### 2. Two executables, as before

- **The verification executable and the timing executable of an attempt stay two executables of two programs** (cited: ADR-0017 decision 2; ADR-0009 decision 2), each built at the call that uses it (cited: ADR-0056 decision 4; ADR-0061 decision 2). Nothing of either record is reopened.
- **Three ways were weighed.**
  - **(a) Two programs, two executables.** No earlier decision moves. Its cost is the threat this record narrows but does not remove (decision 5).
  - **(b) One program that both verifies and times, in one run.** It edits the timing driver and reopens ADR-0009 decisions 5, 6 and 8 (cited: ADR-0017 Alternatives) and ADR-0017 decision 2 (as OD-16 sub-question ⑥ says of one executable); verification output written between repeats would have to be kept out of every timed interval (ADR-0007 decision 2), and it would tie the inputs, which ADR-0064 decision 6 does not. And it would not give what it seems to: a kernel in a process that verifies and times can still tell a verified call from a timed one — by the number of calls or the clock — so the computation that is timed is still not shown to be the one that is checked.
  - **(c) The verification program linked into the timing executable, a mode chosen by an argument.** One program source with two modes; but **a check and a run tool call are two calls, and each builds** (ADR-0056 decision 4 (a); ADR-0061 decision 2 (a)). One *file* verified and timed would need an executable that outlives the call that built it, which both records weighed as their way (b) and rejected — state kept between calls (ADR-0010 decision 7), a holder of the build step, a path no record gives, a binary in no git tree (cited: ADR-0061 decision 2 (b)). Without that, (c) yields two files of one program, which the sameness of decision 3 already gives for the kernel's part. And the mode is an argument in the kernel's process, which the kernel can read as it can read the seed (cited: ADR-0017 decision 10).
- **The choice is (a).** (b) and (c) would reopen ADR-0017 decision 2 and ADR-0009, which this record may not do, and neither closes the threat; this record takes the narrower step of decision 3.

### 3. The kernel sources are built with the same settings in both builds

- **For every attempt of a run of decision 1, the backend builds the kernel sources with one compiler, one list of flags, one list of trailing flags and one environment in the verification build of every check and in the timing build of every call of `sim.run` or `board.run`.** None of these settings, and no value of one, depends on **which tool builds**, on **the execution point**, or on **the `execution` number** of the call. The backend has no "verification flags" and no "timing flags".
- **The granularity, stated.** A check and a timing run of one attempt at the same point: the same. At the sim point and the board point: the same — in the local configuration both are "the same local run" (**owner**, O1), and nothing motivates a set per point. Across `execution` numbers: the same. **What makes two calls differ is only a change of the backend's source of the settings between them** — for example a toolchain update the user approved (**owner**, O4 item 2: "only after approval does it install or update"). This record does not forbid such a change; after it, every build of either tool uses the new settings alike. That a run holds builds of one attempt from before and after a change is Limit 3.
- **The environment covers the processes too.** The environment is one setting for the build and for the process (cited: ADR-0009 decision 9, "handed to `clang_build.build` and to `local_run.run` unchanged"; ADR-0017 decision 9, "handed on unchanged"; ADR-0060 decision 3, one row). So the verification process and the timing process of an attempt run with the same environment, thread settings among them. Reason: an OpenMP kernel that is right with one thread count and wrong with another — a race, a reduction order beyond the tolerance — would otherwise pass at the count it is verified with and be timed at another.
- **What may differ, and what must not.**
  - **The harness program**: its source file differs (that is decision 2), and so does what it does at run time. Its source is compiled in the same call with the same flags (cited: ADR-0009 decision 2; ADR-0017 decision 2), so **no flag or define reaches one harness program and not the other**: a define for the harness alone would be a flag of the command and reach the kernel's translation units as well, where a kernel could test it.
  - **The arguments** each program is started with (cited: ADR-0009 decision 9; ADR-0017 decision 9) and **the time limits** of the build and of the process: they differ as each run needs (a timing run takes up to `n_max` repeats) and they are outside this rule. A time limit bounds a process; it is not an input of what is compiled. Their values stay with OD-14.
  - **The path of the executable and the working directory**: the operation's own, per call (cited: ADR-0056 decision 4); sources are handed as absolute paths, "so `cwd` does not change what is compiled" (cited, same decision, from `hilclaw/clang_build.py`). This record does not hold them equal.
  - **The compiled set** is what the reader finds at each call (cited: ADR-0056 decision 4); whether the attempt's `output/` can change between two calls is not this record's (OD-23).
- **"One compiler"** means one installation at one version, the same program at both builds. Under the container of O4 (**owner**: "The toolchain, the build of a kernel, its correctness run and its timing run use an isolated environment: a container") it is the one toolchain the two builds use; **this constrains the design of the container (OD-14 sub-question ①) only in that the two builds of an attempt get the same compiler and the same environment**; its image, lifetime and runtime stay there.
- **Three answers were weighed, and two more.**
  - **(a) The same, required of the backend.** The two builds differ in the harness program only; the operations of both tools take their settings from one place.
  - **(b) No relation stated** (today, ADR-0060 decision 3). A backend could verify at `-O0` and time at `-O3 -ffast-math`: the numerics that pass the check would not be those that are timed, a kernel's undefined behaviour could show in one build and not in the other, and a thread count could differ. Nothing in the contracts would say this is wrong.
  - **(c) The same for the kernel's translation units only.** It would let the harness program get flags of its own; but under one call of `clang_build.build` every flag applies to every source (cited: ADR-0009 decision 2), so (c) needs the program and the kernel compiled separately — the way ADR-0009 Alternatives rejected ("Three compiler processes and two sets of flags to keep apart") — and no harness program needs a flag of its own ("The harness adds no flag", observation). Under one call, (a) and (c) coincide.
  - **(d) The same per point only.** Nothing distinguishes the points but the point (O1); a set per point is a difference no source asks for. A configuration in which the points differ (OD-18 sub-question ⑫, #5 B-2, B-3) is outside decision 1.
  - **(e) The same, and checked by the tool function.** It needs the settings of each build handed back across the cut or recorded — a member of a result, of `build.json` or a file — which no record has (OD-6 sub-question ②; ⑰ (다)) and which this record may not add (A-13 reading).
- **The choice is (a).** Its cost: a backend may not use cheaper settings for verification than for timing (a debug build, fewer threads); a verification takes as long per draw as the timed configuration does. **The values stay open**: this record says that the two builds use the same values, not which.

### 4. Who guarantees it, and what detects a breach

- **It is a requirement on the backend, held by its code, and nothing detects a breach.** "A backend that does not answer the contract … is not detected by the frame" (cited: ADR-0016 decision 6); this rule is one more such requirement. The tool functions hand no setting (cited: ADR-0060 decision 3; ADR-0061 decision 3) and are returned none: no log, command or setting crosses the cut (cited: ADR-0056 decision 3), apart from the compiler's log of ADR-0078, which is the check's and is no record of settings.
- **Nothing records the settings of a build**: the members of `build.json` are OD-6 sub-question ②, a record of a check's source bytes and settings is ⑰ (다), and whether a result file of the run tools holds settings is that file's record (cited: [ADR-0063](ADR-0063-od18-run-tools-result-members.md) decision 4, of the settings: "Whether a result file needs them, and from where, is for the record of that file … No member of a result file is named."). **This record adds no file and no member.** A detection, if one is wanted, comes with those records; it needs no new sub-question.
- **For `cpu_standin` the rule can hold by construction**: the operations of the two tools take their build settings from one source and add none per tool, point or `execution`. That is the shape the code of those operations must have; their module, names and the source itself are the code task's (Consequences).
- **For the mock** the rule has nothing to apply to: its operations and scripts are given no setting (cited: ADR-0060 decision 3) and build nothing — the default script "stands for no kernel language, no source, no build and no flag" (cited: ADR-0044 decision 3).

### 5. What this does to the threat of ADR-0017 decision 10

- **Narrowed**: "two builds may differ". For the runs of decision 1, a difference of compiler, flags, trailing flags or environment between the verification build and the timing build of an attempt is excluded by rule — not by detection.
- **Remains**, and stays with the rest of OD-16 (the defences beyond the minimum clause of FR-9; threat B), **with no new sub-question**:
  - **A kernel that tells the two programs apart** — at link time (a weak reference to a symbol only one harness program defines), or at run time (its arguments, the number and pattern of its calls, the clock) — and computes properly only when verified. Equal settings do not prevent it; neither would one executable (decision 2 (b), (c)). Defences such as checking the output of a timed run or confirming the kernel's execution by a profiler (threat B ⑶) are neither adopted nor rejected here.
  - **The same settings do not promise the same machine code of the kernel**: optimisation across translation units (link-time optimisation, if the flags ask for it) sees a different harness program in each build.
  - **A breach by the backend** (decision 4) and **a change of its source between calls** (Limit 3).
- ⑥ asked two things — the same flags, or one executable — and both are answered for these runs. The remaining threat is not a narrower form of ⑥ but the general question of defences, which OD-16 already holds.

### Walk-through

The attempt `round` 3, `candidate` 2, `attempt` 1 of a run `r1` at `cpu_standin`, unless said otherwise. "S" is the backend's one source of settings; its values are not given here.

| Case | What is built | Settings | What remains |
|---|---|---|---|
| A check at the sim point and `sim.run`, `execution` 1 | A verification build and a timing build, each in its own build directory, each removed | Both from S: one compiler, flags, trailing flags, environment; time limits and arguments differ | The kernel can still tell the programs apart (decision 5) |
| A check at the sim point and `board.run`, `execution` 1 | The same, the timing build at the board point | The same as above: no set per point | The same |
| `sim.run` with `execution` 2 after `execution` 1 | One more timing build | The same as `execution` 1 and as the checks, if S did not change between the calls | If S changed (an approved toolchain update), both tools build with the new values from then on; nothing records which builds came before (Limit 3) |
| A backend that builds the check with `-O0` and the run with `-O3 -ffast-math` | As above | A breach of decision 3 | Not detected (decision 4); the results are stored as any others |
| A run at the mock, check and `sim.run` | Nothing | No setting is given (decision 4) | The rule is vacuous; the outcome follows from the script |

### 6. Limits

1. **A record, not code; nothing was built or run.** That a compiler produces the same code for the kernel under the same settings was not tried.
2. **A breach is not detected** (decision 4), and **the rule does not stop a kernel that tells the programs apart** (decision 5).
3. **Change between calls.** A change of the backend's source of settings between two calls of one attempt — an approved toolchain update, an edited configuration, or two processes holding two versions of the source ("Two processes, two tables" — cited: ADR-0016 decision 6) — makes the builds before and after differ, and no file says which builds came before. Who may change the toolchain during a run is O4 item 2 and OD-14.
4. **Scope.** Other backends, a simulator, a board, a remote machine and the emulated `sim.run` of OD-18 sub-question ⑫ are not covered; neither is `profiler.collect`.

## Consequences

- **Code**: **no code slice follows now.** The rule binds the code task that writes the operations of `cpu_standin` for `correctness.check` and for the run tools: they take their build settings from one source shared by both and add none per tool, point or `execution`. That task waits on the setting values (⑱ (라), ⑲ (라)), the container (OD-14 sub-question ①) and, for the run tools, ⑲ (나); no module or function is named here.
- **For later records**: a record that answers ⑱ (라) or the rest of ⑲ (라) gives one source and one set of values for both builds. A record that lets a setting reach an operation from a file or the request (⑱ (가)) lets it reach both tools' builds alike, or reopens decision 3 for that setting.
- **Not edited and now less exact** (follow-ups for the integrator; found by grep on 2026-10-19 for "sub-question ⑥", "OD-16 ⑥", "⑲ (라)", "same flags", "same settings" and "same values"): ADR-0017 decision 9 ("neither is whether the two builds of an attempt use the same flags (sub-question ⑥)"), decision 10 ("two builds may differ.
