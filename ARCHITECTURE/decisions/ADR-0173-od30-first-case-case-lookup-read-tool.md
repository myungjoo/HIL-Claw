## Context

- **The open points** (cited): the selector "reaches the output of the lookup of ADR-0073 decision 1 through a typed read tool of the registry that takes the `run_id`, added to its list by the record that defines it — the case-lookup work of PLAN P2-7, which gives its name, result and kinds, how the lookup's reports are carried and whether a selection goes on after one" (ADR-0132 decision 5); "how a report of a set-apart or invalid case is carried and whether a selection may go on after it; … how a selection is made to take the lookup's output and record `cases_read`" (ADR-0073 Boundaries); "The lookup read tool" (ADR-0171 Boundaries).
- **What exists** (code on `main`, as observation): `hilclaw.case_lookup.find` and `lookup` give a `Found` of the key, the cases and the reports (`key_record`, `invalid`, `set_apart`, `unreadable`), and raise for a bad argument, for a data root that is no directory and with the `OSError` of listing the key directory; `case_lookup.cases_read` gives the `cases_read` value of a `Found`; its docstring says "How a report is carried to the selection, and whether a selection may go on after one, is not decided". `hypotheses.write` check ④ holds a record's `cases_read` and `case` entries against `find` (`cases_unreadable`, `cases_mismatch`) and does not judge the reports. `orchestration/agents/technique-selector.md` says "Write no `cases_read` and no basis entry of kind `case`: no lookup tool is in your list". Step 1 of a round stores the run's two key record files (cited: ADR-0134 decision 5), so a first-case round ≥ 1 normally meets a hit.
- **Constraints the means must keep** (cited): the lookup is deterministic and its output does not depend on a model's choice of what to open (ADR-0073 decision 1); a delegation names no place (ADR-0123 decision 2); the data root is never a request member (ADR-0015 decision 3); the record is written once (ADR-0059 decision 1); an absent `cases_read` records no identification, never that no case was read, and a present empty one says the selection read no case, whatever the reason (ADR-0073 decision 3).

## Decision

A sentence is **cited** when a source is named with it. Every other sentence is **this record's own**.

### 1. Scope

- **How the selection of a round ≥ 1 of a run of ADR-0120 decision 1 takes the output of the lookup of ADR-0073 decision 1**, how that output's reports, a miss and a failure reach it, and what it records of them in the round's `hypotheses.json`.
- **Outside**: round 0, which has no selection (cited: ADR-0059 decision 5); everything under Boundaries.

### 2. (a) The tool `cases.lookup`

| Part | Content |
|---|---|
| Name (MCP name) | `cases.lookup` (`mcp__hilclaw__cases_lookup`); the name holds no `_` (ADR-0010 decision 4) |
| Request | Exactly `run_id` (ADR-0015 decision 4), required; any other member is refused |
| Result | `{"key": …, "cases": […], "cases_read": […], "reports": […]}`: `key` is `{"hw_profile": <name>, "op_signature": <name>}`, the two key directory names, on a hit and `null` otherwise; `cases` is every case the lookup gives, each the parsed document whole, in the lookup's order; `cases_read` is the value of ADR-0073 decision 3 for those cases (`hilclaw.case_lookup.cases_read`), one `{"run_id", "round"}` per case in the same order; `reports` is one `{"path", "kind", "reason"}` per report, as the lookup gives them |
| Checks, in order | ① the request (`invalid_request`); ② the data root (`no_data_root`); ③ the run's `instance.json` read and parsed (`run_file_missing`, `run_file_invalid`, `run_file_unsupported`, `run_file_unreadable`, as `instance.read` names them); ④ the lookup by `hilclaw.case_lookup.find` for the records it states and the run id — any failure of the file system in it (`cases_unreadable`) |

- **It is the lookup of ADR-0073 decision 1 and no second one**: the same key, files, order and treatment of the reader's own run, so its output depends only on what that decision names (cited: NFR-2 there). It adds nothing, filters nothing and summarises nothing.
- **The result carries `cases_read`** so that the selector copies the identification rather than composes it: ADR-0073 decision 3 has `cases_read` name every case the lookup gave the selection, and `hypotheses.write` check ④ holds that each entry names a stored case but cannot hold that none is missing (cited: `hilclaw/hypotheses_cases.py`, "a case of `found.cases` that `cases_read` does not name is no mismatch"). The cost is a second copy of each pair in the result, which `cases` already holds.
- **Kinds.** Reused with their meanings: `invalid_request` and `no_data_root` (ADR-0015 decision 2); the four `run_file_*` kinds for `instance.json` (ADR-0019 decision 3) — **this record widens ADR-0019 decision 2 to this read**, as ADR-0171 decision 3 did, and the property holds: such a call appended no line, selected no backend and wrote nothing; `cases_unreadable` with the meaning ADR-0132 decision 4 gives it for the same lookup ("the lookup of the cases of the run's key failed in the file system"). **No new kind.** A data root that is gone by step ④ is that kind, its message saying so.
- **Not journaled**: it costs no limited resource and keeps nothing. It reads `instance.json`, the two key record files and the counted entries of the key directory, and creates nothing. It joins `default_registry` in the source and in no other way (cited: #5 A-12 point 3).
- **The size of the result.** Every case of the key except the reader's own run's is returned, as ADR-0073 decision 1 has it ("No cap"); a case copies a hypothesis record and a verdict record whole (cited: ADR-0072 decision 3), so the result grows with the cases of the key. **No landed record states a limit Claude Code puts on the result of an MCP tool call**, and this record states none: ADR-0141 cites the MCP documentation for the idle window only. So no bound is set here; the selection rule for many cases stays OD-30's and the result size of a call OD-18 sub-question ③'s, and whether the largest result reaches the selector whole is item (lxxxviii).

### 3. (b) How the lookup's reports and a miss are carried

- **A report is part of the result, not a failure.** Each `Report` of the lookup becomes one element of `reports` with its `path` (relative to the data root), `kind` and `reason` unchanged and in the lookup's order (cited: `hilclaw/case_lookup.py`, "ascending byte order of their `path`"). The four kinds stay those of the lookup: `key_record`, `invalid`, `set_apart`, `unreadable`. One report does not hide the other cases (cited: ADR-0073 decision 1), so a result may hold both.
- **A reported file is no case**: it is not in `cases` or `cases_read`, so no `case` entry can name it (cited: ADR-0073 decision 1, "none of its members is used"; `hypotheses.write` ④ refuses such an entry with `cases_mismatch`).
- **A miss** — no key record file, or no key directory (cited: ADR-0073 decision 1) — **and a run that states no op_signature** give `key` `null` and three empty arrays. A stored key record that collides or is not valid gives `key` `null`, no case and one `key_record` report. A hit with no case of another run gives the key and empty `cases` and `cases_read`.
- **The reports reach no file.** No member of `hypotheses.json` holds them, and adding one would be a data-plane change (A-13); they reach the selector's report (decision 5) and the turn's transcript. ADR-0073 decision 3 identifies the cases read, not the files reported.

### 4. (c) Whether a selection goes on

- **After a result — a hit with cases, a hit without, a miss, with reports or none — the selection goes on** and its record carries **`cases_read` equal to the result's `cases_read`**, whole and in its order, **an empty array included**. A present empty `cases_read` then says what ADR-0073 decision 3 says of it: the selection read no case, whatever the reason (cited). No absent `cases_read` is written by these runs once the tool is in the selector's list.
- **After `invalid_request`** the selector corrects its request and sends it again (its own error, as for `hypotheses.write`, ADR-0132 decision 7).
- **After any other kind** (`no_data_root`, a `run_file_*` kind, `cases_unreadable`) **the selection writes no record**: it sends no `hypotheses.write` and no further request, reports the kind and ends. The Round-Manager's read then finds no record and comes to the stop (cited: ADR-0132 decision 6), and the next turn delegates the selection again. Reasons: the record is written once (cited: ADR-0059 decision 1), so a record written without the lookup's output would stay without it for that round; a record with an absent `cases_read` would keep ADR-0073 decision 3's meaning but would not meet its decision 1 ("takes the lookup's output as input before it writes"); and the kinds name a broken run or data plane, which a later turn may meet repaired.
- **When the round's record already exists** (a re-entered round, cited: ADR-0132 decision 6), the selector still calls the tool first; its `hypotheses.write` then meets `hypotheses_exist` and nothing is replaced (cited: ADR-0132 decision 4).

### 5. (d) The holder and the selector's use

- **The technique-selector alone holds `cases.lookup`.** Its `tools` gain `mcp__hilclaw__cases_lookup`, which ADR-0132 decision 3 foresaw ("Later reads are added by the records that create them", cited). No other agent file and not `ROUND_MANAGER_TOOLS` lists it: the Round-Manager forms no hypothesis and the cases would enter its context, which ADR-0132 decision 2 rejected (cited); no other sub-agent holds selection work (cited: ADR-0132 decision 2, the selector holds the selection role). The entry is an exact `mcp__hilclaw__<name>`, so the derived pre-approval takes it with no change (cited: ADR-0139 decision 3), and the caller check lets it through for the selector and refuses it for the main session and every other sub-agent (cited: ADR-0146 decisions 2, 3 and 6).
- **When**: once in its work, **before it sends the round's record** with `hypotheses.write`, since `cases_read` and the `case` entries are written with the record, once (cited: ADR-0059 decision 1; ADR-0073 decision 1). The `catalog.read` call and the choice of techniques stay after the record (cited: ADR-0171 decision 2).
- **Its fixed rules, replacing "Write no `cases_read` and no basis entry of kind `case`"**: call `mcp__hilclaw__cases_lookup` with the run id before the record; after a result, give the record `cases_read` equal to the result's `cases_read`, whole and in its order, also when it is empty; a basis entry of kind `case` names a case of the result's `cases` by its `run_id` and `round` and an `id` of a hypothesis in its `hypothesis_record` (cited: ADR-0073 decision 2); on `invalid_request` correct the request and send it again; on any other kind of `cases_lookup` send no record and no further request, report the kind and end.
- **A case is a hint** (cited: FR-15, FR-18; ADR-0073 decision 1, "How the output is used"): a past rejection forbids no retry and past performance is no target. Whether to rest a hypothesis on a case, on which and why stays the selector's judgement; a refuted or inconclusive case can be named as well as a supported one (cited: ADR-0073 decision 2).
- **Its report gains** one line for the `cases_lookup` request, as every tool request has (cited: ADR-0132 decision 7), naming the number of cases or the failure kind, and one line per report with its `kind` and `path`.

### Walk-through

| Situation | What follows |
|---|---|
| Round 1 of the first run of a key | `key.store` stored the key; `cases.lookup` returns the key, `cases` `[]`, `cases_read` `[]`, `reports` `[]`. The record has `"cases_read": []`; `hypotheses.write` skips ④ (cited: ADR-0132 decision 4) and writes |
| A later run; the key holds (`X`, 1), (`X`, 2) and the run's own (`R`, 1) | The result holds `X`'s two cases in name order and their `cases_read`; `R`'s is left out. The selector copies `cases_read` and may rest its `h1` on (`X`, 2)'s `h1`; ④ finds both and the file is written |
| The key directory also holds a case of another `schema_version` and a file `case-x.json` | Two reports, `set_apart` and `invalid`; the other cases are returned. The selection goes on; its report names both files |
| The stored `op_signature.json` collides | `key` `null`, one `key_record` report; `"cases_read": []` |
| The run's instance states no op_signature | `key` `null`, nothing else; `"cases_read": []` |
| Listing the key directory fails | `cases_unreadable`; the selector writes no record, reports the kind and ends; step 7 answers `hypotheses_missing`; the stop; the next turn tries again |
| A case is promoted between the lookup and the write | It is not in `cases_read`; the write passes, since ④ holds entries, not completeness; the record names what the lookup gave (cited: ADR-0073 decision 3) |
| The selector names a hypothesis id that the case does not hold | `cases_mismatch`; it corrects the record and sends it again (cited: ADR-0132 decision 7) |
| The Round-Manager or the evaluator calls `cases.lookup` | The caller check refuses it (cited: ADR-0146 decision 6) |

- **Runtime acceptance items** (D16; nothing was tried, nothing is required of the development machine). They go to [PROCESS/RuntimeAcceptance.md](../../PROCESS/RuntimeAcceptance.md) (DRIVER §8, D22), not to an HQ. ADR-0132 items (xxiii) and (xxiv) and ADR-0171 item (lxxxiii) are used, not changed. **New**:

  - **(lxxxviii)** The result of `cases.lookup` for the largest key directory a first-case data root holds reaches the selector whole, within any limit Claude Code puts on the result of an MCP tool call; and the selector writes the result's `cases_read` into the record unchanged and before the record, as decision 5 says.
- **The cost, plainly.** The result grows with every promoted round of the key and no bound holds it (OD-30; OD-18 ③). A run whose lookup fails in the file system writes no round ≥ 1 record and stops every turn until the cause is gone — in a re-entered round whose record exists too, since the selector then gives no `techniques:` line and step 8 stops (cited: ADR-0171 decision 6); a bound on turns that fail alike is OD-17's and OD-19's. The reports stay in the selector's message and the transcript, in no file. That the selector called the tool, copied `cases_read` and called it before the record rests on its definition: `hypotheses.write` admits a record with no `cases_read` as the validator does (cited: ADR-0132 decision 4), and no hook checks the order.

- **Hooks beyond the caller check**: one that refuses a record without `cases_read` or a record written before the lookup, and a check of a request's `run_id` against the session's run (rest of OD-18; PLAN P2-4).

- **Owner-only**: #5 A and B items, the models of the orchestration's agents (#5 A-8); C-6, OD-25, OD-3.
