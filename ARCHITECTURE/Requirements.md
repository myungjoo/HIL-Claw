# 0. 범위 (Scope)

- 본 문서는 **MVP "방법 B"(Claude Code Orchestrator)** 만 다룬다.
- **방법 A(DeepAgents/LangGraph)는 "HIL-Claw 2"로 이연**하며 요구사항에서 제외한다(→ C-5). 단, 방법 B의 인터페이스는 미래 승격이 쉽도록 외부화한다(→ NFR-6).
- **세 층 모델**(#5 A-12): 저장소는 **1층** = Claude Code 오케스트레이션(프롬프트·스킬·에이전트 정의·기법 Skill, Markdown), **2층** = 1층이 호출하는 결정적 도구 패키지(FR-10), **3층** = 코더가 산출하는 C 커널(FR-5, A-7)로 나뉜다. 본 문서의 "1층/2층" 표기는 이 정의를 따른다.

| **FR-9** | **correctness 검증**을 제공한다(비트정확 아님; reference numeric / downstream metric / user-defined + tolerance). **정확도는 hard floor(게이트)이며 점수의 한 축이 아니다** — 실패는 감점이 아니라 복귀·탈락이다(오너 결정 2026-10-01, #5 A-6 → OD-5 확정). **tolerance는 사용자가 instance 파라미터로 지정·변경**한다(어휘: 첫 사례 — `cpu_standin`·`gemm`·fp32·C 커널 — 에 한해 원소별 `rtol`·`atol`이며, 출력의 모든 원소에서 |out − ref| ≤ atol + rtol·|ref|일 때만 통과하고 출력의 NaN·무한대는 실패다; 기본값은 없어 instance가 둘 다 명시한다 — [오너 답변 HQ-0004](https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6052377983)(2026-10-08), [ADR-0017](decisions/ADR-0017-od16-cpu-standin-verification-run.md); 그 밖의 어휘(벤더 golden output·downstream 지표 임계·user-defined 검사·다른 dtype의 tolerance)는 #5 B-7 미결 그대로); 손실 허용 기법(양자화·근사 연산 등)은 사용자가 정한 tolerance 안에서만 허용되며, 얼마나 잃을지를 시스템이 고르지 않는다 — 더 느슨한 tolerance에서 더 빠른 후보가 있으면 시스템은 **보고만** 하고 채택하지 않으며, 채택은 사용자가 tolerance를 바꾼 새 instance로 한다. **실행 지점은 sim·board 두 곳이며 동일 검증을 반복한다** — sim은 조기 필터, **board가 최종 판정**(수치 결과가 HW마다 달라질 수 있으므로 sim 통과가 board를 보장하지 않는다; `cpu_standin`에서도 시도마다 검사는 둘 — sim 지점의 검사 하나와 board 지점의 검사 하나 — 이며 두 지점이 같은 로컬 실행인 곳에서도 그렇고, 그 두 검사에서 "동일 검증"은 같은 하네스·판정식·tolerance를 뜻하며 입력은 검사마다 새로 뽑는다 — [오너 답변 HQ-0005](https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6117798837)(2026-10-12)로 `cpu_standin`에 한해 확정, 다른 백엔드에 대한 답은 아님; [ADR-0038](decisions/ADR-0038-od18-cpu-standin-execution-points.md)). 실패 시 처리와 sim/board 불일치 처리는 FR-1 참조. **최소 강건성 조항(MVP)**: 최적화 과정에서 코더에 노출되지 않은 입력(shape/seed)으로, 코더가 수정할 수 없는 격리된 검증 하네스에서 재검증한다. 검증을 통과하지 못한 결과는 best·통계에 반영하지 않는다. FR-3 ④ target 조기 달성은 승격 게이트 수준의 재검증을 통과한 뒤에만 종료로 인정한다. 전면 하드닝(정밀도 검사·타이밍 동기화·정적 검사·LLM 검증자)은 확장(S7) → OD-16. **검증 하네스**(입력 생성·f64 reference(`cpu_standin`의 오라클은 NumPy float64 — 뽑은 fp32 입력을 float64로 넓혀 곱한 값을 하네스의 Python 쪽에서 계산하고, 커널을 실행하는 프로세스는 reference도 비교도 갖지 않는다; 오너 답변 HQ-0004(2026-10-08)로 `cpu_standin`에 한해 확정, B-7의 일반 답은 아님)·tolerance 비교·타이밍·프로파일·eval/event 기록)는 도구 패키지(FR-10) 안의 **단일 하위 모듈**에 모여 있고 코더의 scratch에 포함되지 않으며, P1에서 그 버전은 `instance.json`의 소스 commit 해시다(오너 결정 2026-10-02, #5 A-12; OD-11 측정 계약 pin의 P1 구현). | UC-2, Issue#2 §C.2, S7 (B1), #5 A-6·A-12 *(검증 방식 어휘는 §B.3 도구 계약에서 유래하나 §B.3은 방법 A 절이므로 C-5에 따라 근거에서 제외)* | 공통 |
| **FR-10** | **HW 실험 도구**를 MCP/Bash로 노출한다: `sim.run`(저비용 조기검증), `board.run`(고비용·공유·quota), `profiler.collect`, `correctness.check`. 도구 계약은 **transport 무관**(로컬 실행·LAN 원격 — C-7 ⑤·⑥의 귀결)이며 mock 백엔드(고장 주입·계약 테스트)를 항상 갖는다. 첫 등록 백엔드는 **CPU 스탠드인 `cpu_standin`**(#5 A-7)으로, 실 HW 도착 전에 FR-1 전 루프를 실물로 검증한다 — `cpu_standin`은 `sim.run`과 `board.run`을 **둘 다** 제공하며, 오너의 로컬 PC에서 네이티브로 빌드·실행하는 경우 둘은 같은 로컬 실행을 수행하고 두 동작을 가르는 것은 실행 지점뿐이다; hw_profile이 mock을 가리키는 run의 `correctness.check` 호출은 첫 사례의 계약(HQ-0004의 오라클, `instance.json`의 `tolerance` 멤버)이 답한다([오너 답변 HQ-0005](https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6117798837)(2026-10-12), [ADR-0038](decisions/ADR-0038-od18-cpu-standin-execution-points.md); 한 지점이 없는 대상의 라운드 루프 규칙은 답해지지 않았다 — OD-26). 도구 계층(2층) 전체는 **단일 패키지**(가칭 `hilclaw/`; FR-10 도구·mock/`cpu_standin` 백엔드·CAS blob·스키마 검증(STATE/spec/eval/artifacts)·hook 진입점·검증 하네스 FR-9)로 제공되며 1층(Claude Code 오케스트레이터 — 프롬프트·스킬·에이전트 정의)이 호출하는 도구다; **MVP에서 런타임 오케스트레이터는 미리 만들어진 도구 집합만 사용하고 run 중 도구를 생성하지 않는다**(오너 결정 2026-10-02, #5 A-12; 런타임 도구 생성은 post-MVP 확장 → NFR-6). | **FR-17** | **가설–실험–판정 사이클**([오너 결정 2026-10-13](https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6136462569), #5): 라운드의 기법 선택은 **가설 레코드**를 남긴다 — ① **가설**(무엇을 바꾸면 무엇이 나아진다는 진술) ② **근거**(프로파일 관측·과거 사례(FR-18)·외부 자료(FR-14·15) 가운데 무엇에 기대는지) ③ **예상 효과**(어느 지표가 어느 방향으로 움직일 것인지) ④ **출처**(시스템이 세운 것인지 주입된 것인지를 구분 — FR-15; 값의 어휘 = OD-30). 가설은 기본적으로 **시스템이 스스로 세운다**. 주입된 가설이 있어도 시스템은 라운드마다 앞선 판정·프로파일·과거 사례에서 교훈을 얻어 **스스로 추가 가설을 세우는 일을 멈추지 않으며**, 라운드마다 서로 다른 가설을 시험할 수 있다([오너 2026-10-13 보충](https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6136597638), #5). evaluate는 가설마다 **판정**(실험 결과가 가설을 지지하는지 기각하는지, 또는 판정할 수 없는지 — 어휘 = OD-30)과 **원인**(예상과 측정이 왜 일치·불일치했는지)을 그 가설과 측정 결과에 이어 기록한다. 가설 레코드와 판정은 자유 서술이 아닌 **구조화된 기록**이며, 가설 없는 기법 선택을 허용하지 않고, evaluate에 이른 라운드는 판정 없이 끝나지 않는다(강제 수단 = OD-18; budget 소진·프로세스 사망으로 evaluate에 이르지 못한 라운드의 가설 = OD-30). **지지** 판정은 검증 하네스를 통과한 결과에만 기댄다 — 검증에 실패한 후보의 측정값은 지지의 근거가 되지 못하고(FR-9), FR-1 ⑶으로 격리된 측정은 지지의 근거도 기각의 근거도 되지 못한다(검증 실패로 측정에 이르지 못한 가설의 판정 값 = OD-30). 다음 라운드 결정은 앞선 판정을 입력으로 삼는다. *(필드·판정 어휘·파일 자리, 가설과 기법·후보(N)의 대응, 주입 가설과 시스템이 세운 가설의 배분(순서·비율), 라운드 0의 취급 = OD-30)* | 오너 결정(2026-10-13), S0-6·8, UC-2·6 | 공통 |

# Open Decisions (미결 — 구체 설계 단계에서 확정)

발명하지 않고 명시적으로 남긴다. 각 항목은 관련 FR 및 Issue#2 결정 ID와 연결된다.

**본 표가 미결 항목의 단일 등록부(registry)다.** 논의가 이슈에 흩어져도 각 항목의 현재 상태와 논의 위치는 여기서 확인할 수 있어야 한다.

**이슈 역할 분담**: **#4** = 아키텍처·실행모델 결정 스레드 · **#5** = 사용자만 답할 수 있는 입력 대기(A/B 항목) · **#7** = 외부 시스템 조사·분석(상설) · **#8** = 문서·이슈 간 모순 트래커 · **#1** = 참고문헌 메모.

**상태 어휘**: `미착수` 논의 없음 · `논의중` 논의 진행, 제안 미수렴 · `제안됨` 구체 제안 존재, 오너 확정 대기 · `차단됨` #5의 사용자 입력 대기 · `확정` 결정 완료(본문 반영 커밋 링크 필수).

**갱신 규칙**: 상태가 바뀌면 **본 표를 같은 커밋에서 갱신**한다. 확정 시 행을 지우지 말고 상태를 `확정`으로 바꾸고 반영 위치를 남긴다(감사성 NFR-2).

**정본 규칙**: **OD 항목의 상태·논의 위치는 본 표가 정본**이다. 이슈·코멘트에는 **표를 복제하지 말고 링크만** 둔다. (사본을 두었더니 등록부 개편 직후 번호가 어긋나 별도 정정이 필요했고, 2026-09에는 미merge PR과 main이 같은 번호를 다른 뜻으로 써 5주간 분기했다 — #8 M19, #5 A-9.)

**제안 상세**: 각 항목의 구체 제안·근거 본문은 [OpenDecisionProposals.md](OpenDecisionProposals.md)의 같은 번호 절에 둔다. 본 표에는 **한 줄 요약**만 적어 표가 읽히도록 유지한다. 제안 본문의 정본은 Proposals 문서, 상태·논의 위치의 정본은 본 표다.

**행 형식**(2026-10-16 정리): 마지막 칸은 한 줄로 쓴다 — 원 제안의 요지, `**확정분**:` 뒤에 ADR 링크와 각 몇 단어의 주제(오너가 직접 확정한 것은 `**확정분(오너 …)**`이나 `**오너 결정(날짜, 링크)**`으로 한 구절), `**잔여**:` 뒤에 열린 부분(하위 질문 번호), 끝에 `[상세]` 링크. ADR이 정한 내용(멤버·규칙·한계)을 다시 서술하지 않고 "…도 같은 경로로 확정" 같은 날짜별 사슬을 늘이지 않는다 — 새 ADR은 `**확정분**:`에 링크 하나를 더하고 `**잔여**:`를 그 자리에서 고쳐 쓴다. 상태 칸은 상태 어휘 하나와 날짜·경로만 짧게 적는다. 지난 서술은 git 이력에 있다.

**등록 범위**: 본 표는 **미결 "결정"** 만 담는다. 결정이 아닌 **작업**(예: 부트스트랩 골격 작성)은 여기 넣지 않고 이슈에서 작업 항목으로 추적한다 — 섞으면 표가 진척 관리용으로 변질된다.

**첫 커밋(P0 골격) 전에 확정해야 하는 항목**: OD-4 · OD-6 · OD-8. 사용자 입력(#5 A-1·A-2·B-4)은 2026-10-02에 모두 확보되었고, 세 항목의 P1 최소분은 PROCESS/DRIVER.md §9 경로로 [ADR-0001](decisions/ADR-0001-od4-key-schema.md) (2026-10-06)·[ADR-0002](decisions/ADR-0002-od6-codegen-spec.md) (2026-10-06)·[ADR-0004](decisions/ADR-0004-od8-data-plane-layout.md) (2026-10-07)로 확정되었다. 그 뒤의 확정분과 잔여는 각 행에 있다.
