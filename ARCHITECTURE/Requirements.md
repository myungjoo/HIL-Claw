# 0. 범위 (Scope)

- 본 문서는 **MVP "방법 B"(Claude Code Orchestrator)** 만 다룬다.
- **방법 A(DeepAgents/LangGraph)는 "HIL-Claw 2"로 이연**하며 요구사항에서 제외한다(→ C-5). 단, 방법 B의 인터페이스는 미래 승격이 쉽도록 외부화한다(→ NFR-6).
- **세 층 모델**(#5 A-12): 저장소는 **1층** = Claude Code 오케스트레이션(프롬프트·스킬·에이전트 정의·기법 Skill, Markdown), **2층** = 1층이 호출하는 결정적 도구 패키지(FR-10), **3층** = 코더가 산출하는 C 커널(FR-5, A-7)로 나뉜다. 본 문서의 "1층/2층" 표기는 이 정의를 따른다.

| **FR-9** | **correctness 검증**을 제공한다(비트정확 아님; reference numeric / downstream metric / user-defined + tolerance). **정확도는 hard floor(게이트)이며 점수의 한 축이 아니다** — 실패는 감점이 아니라 복귀·탈락이다(오너 결정 2026-10-01, #5 A-6 → OD-5 확정). **tolerance는 사용자가 instance 파라미터로 지정·변경**한다(어휘: 첫 사례 — `cpu_standin`·`gemm`·fp32·C 커널 — 에 한해 원소별 `rtol`·`atol`이며, 출력의 모든 원소에서 |out − ref| ≤ atol + rtol·|ref|일 때만 통과하고 출력의 NaN·무한대는 실패다; 기본값은 없어 instance가 둘 다 명시한다 — [오너 답변 HQ-0004](https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6052377983)(2026-10-08), [ADR-0017](decisions/ADR-0017-od16-cpu-standin-verification-run.md); 그 밖의 어휘(벤더 golden output·downstream 지표 임계·user-defined 검사·다른 dtype의 tolerance)는 #5 B-7 미결 그대로); 손실 허용 기법(양자화·근사 연산 등)은 사용자가 정한 tolerance 안에서만 허용되며, 얼마나 잃을지를 시스템이 고르지 않는다 — 더 느슨한 tolerance에서 더 빠른 후보가 있으면 시스템은 **보고만** 하고 채택하지 않으며, 채택은 사용자가 tolerance를 바꾼 새 instance로 한다. **실행 지점은 sim·board 두 곳이며 동일 검증을 반복한다** — sim은 조기 필터, **board가 최종 판정**(수치 결과가 HW마다 달라질 수 있으므로 sim 통과가 board를 보장하지 않는다). 실패 시 처리와 sim/board 불일치 처리는 FR-1 참조. **최소 강건성 조항(MVP)**: 최적화 과정에서 코더에 노출되지 않은 입력(shape/seed)으로, 코더가 수정할 수 없는 격리된 검증 하네스에서 재검증한다. 검증을 통과하지 못한 결과는 best·통계에 반영하지 않는다. FR-3 ④ target 조기 달성은 승격 게이트 수준의 재검증을 통과한 뒤에만 종료로 인정한다. 전면 하드닝(정밀도 검사·타이밍 동기화·정적 검사·LLM 검증자)은 확장(S7) → OD-16. **검증 하네스**(입력 생성·f64 reference(`cpu_standin`의 오라클은 NumPy float64 — 뽑은 fp32 입력을 float64로 넓혀 곱한 값을 하네스의 Python 쪽에서 계산하고, 커널을 실행하는 프로세스는 reference도 비교도 갖지 않는다; 오너 답변 HQ-0004(2026-10-08)로 `cpu_standin`에 한해 확정, B-7의 일반 답은 아님)·tolerance 비교·타이밍·프로파일·eval/event 기록)는 도구 패키지(FR-10) 안의 **단일 하위 모듈**에 모여 있고 코더의 scratch에 포함되지 않으며, P1에서 그 버전은 `instance.json`의 소스 commit 해시다(오너 결정 2026-10-02, #5 A-12; OD-11 측정 계약 pin의 P1 구현). | UC-2, Issue#2 §C.2, S7 (B1), #5 A-6·A-12 *(검증 방식 어휘는 §B.3 도구 계약에서 유래하나 §B.3은 방법 A 절이므로 C-5에 따라 근거에서 제외)* | 공통 |

# Non-Functional Requirements

| ID | 요구사항 | 근거 |
|---|---|---|

# Open Decisions (미결 — 구체 설계 단계에서 확정)

발명하지 않고 명시적으로 남긴다. 각 항목은 관련 FR 및 Issue#2 결정 ID와 연결된다.

**본 표가 미결 항목의 단일 등록부(registry)다.** 논의가 이슈에 흩어져도 각 항목의 현재 상태와 논의 위치는 여기서 확인할 수 있어야 한다.

**이슈 역할 분담**: **#4** = 아키텍처·실행모델 결정 스레드 · **#5** = 사용자만 답할 수 있는 입력 대기(A/B 항목) · **#7** = 외부 시스템 조사·분석(상설) · **#8** = 문서·이슈 간 모순 트래커 · **#1** = 참고문헌 메모.

**상태 어휘**: `미착수` 논의 없음 · `논의중` 논의 진행, 제안 미수렴 · `제안됨` 구체 제안 존재, 오너 확정 대기 · `차단됨` #5의 사용자 입력 대기 · `확정` 결정 완료(본문 반영 커밋 링크 필수).

**갱신 규칙**: 상태가 바뀌면 **본 표를 같은 커밋에서 갱신**한다. 확정 시 행을 지우지 말고 상태를 `확정`으로 바꾸고 반영 위치를 남긴다(감사성 NFR-2).

**정본 규칙**: **OD 항목의 상태·논의 위치는 본 표가 정본**이다. 이슈·코멘트에는 **표를 복제하지 말고 링크만** 둔다. (사본을 두었더니 등록부 개편 직후 번호가 어긋나 별도 정정이 필요했고, 2026-09에는 미merge PR과 main이 같은 번호를 다른 뜻으로 써 5주간 분기했다 — #8 M19, #5 A-9.)

**제안 상세**: 각 항목의 구체 제안·근거 본문은 [OpenDecisionProposals.md](OpenDecisionProposals.md)의 같은 번호 절에 둔다. 본 표에는 **한 줄 요약**만 적어 표가 읽히도록 유지한다. 제안 본문의 정본은 Proposals 문서, 상태·논의 위치의 정본은 본 표다.

**등록 범위**: 본 표는 **미결 "결정"** 만 담는다. 결정이 아닌 **작업**(예: 부트스트랩 골격 작성)은 여기 넣지 않고 이슈에서 작업 항목으로 추적한다 — 섞으면 표가 진척 관리용으로 변질된다.

**첫 커밋(P0 골격) 전에 확정해야 하는 항목**: OD-4 · OD-6 · OD-8. 이들의 사용자 입력(#5 A-1·A-2·B-4)은 2026-10-02 기준 모두 확보되었으므로 남은 것은 설계 확정(#4)이다. OD-4의 P1 최소분은 2026-10-06에 [ADR-0001](decisions/ADR-0001-od4-key-schema.md)로 확정되었다(PROCESS/DRIVER.md §9 경로). OD-6의 P1 최소분도 같은 날 같은 경로로 [ADR-0002](decisions/ADR-0002-od6-codegen-spec.md)로 확정되었다. 아무것도 소비하지 않고 줄도 남기지 않는다), **mock 백엔드**는 같은 규칙으로만 선택되는 표의 한 항목으로서 표를 만들 때 묶인 스크립트(호출 → 산출의 함수; 시계·난수·호출 횟수에 기대지 않음)가 무엇을 낼지 정한다 — 어떤 도구의 계약도, 백엔드에 닿는 방법(#5 B-2)·시뮬레이터(#5 B-3)·board 고장과 회복(OD-10)·등록 스키마(OD-26)도, run이 자기 hw_profile을 적는 파일·멤버도 정하지 않았다(반영: [ADR-0016](decisions/ADR-0016-od18-backend-frame.md)). **run이 자기 hw_profile을 적는 자리**(ADR-0016이 넘긴 하위 질문 ⑥의 첫 부분)는 그 뒤 같은 날 같은 경로로 확정: `runs/<run_id>/instance.json`의 `hw_profile` 멤버(키 이름 + 레코드 전체)이며 run에 관한 호출은 백엔드를 선택할 때마다 그 파일을 읽는다 — 한 run이 둘 이상의 hw_profile을 가질 수 있는지, run에 관한 것이 아닌 호출, 그 파일에서 hw_profile을 얻지 못한 호출의 `kind`(하위 질문 ④)는 정하지 않았다(반영: [ADR-0018](decisions/ADR-0018-od8-instance-record-hw-profile.md), OD-8). **쓸 수 없는 run에 관한 호출의 답**(ADR-0015가 넘긴 하위 질문 ④)도 그 뒤 같은 날 같은 경로로 확정: 저널 대상 도구의 조회나 run에 관한 HW 도구의 백엔드 선택이 그 run의 `STATE.json`·`events.ndjson`·`instance.json`에서 찾은 상황은 예약된 `kind` 넷 가운데 하나로 답한다 — `run_file_missing`(필요한 파일이 없음)·`run_file_unreadable`(파일이 없다는 것 말고 다른 이유로 읽기가 파일 시스템에서 실패함 — 내용은 판정되지 않음)·`run_file_invalid`(파일이 유효하지 않거나, 로그의 완결된 줄이 손상되었거나 ADR-0011을 어긴 단계 줄이거나, 저장된 위치가 로그를 넘거나, 파일 자리에 일반 파일이 아닌 것이 있음)·`run_file_unsupported`(이 소스가 읽는 것과 다른 정수 `schema_version`)이며, 넷 모두 그 호출이 줄을 남기지 않았고 백엔드를 선택하지 않았고 단계를 실행하지 않았다는 뜻을 함께 갖는다(조회에서 난 답이면 앞선 호출이 그 단계를 실행했는지는 정해지지 않는다) — 그 답 뒤에 누가 무엇을 하는지(복구·재시도·재시작 등 — OD-10·OD-17 잔여)도, 시작 줄·끝 줄의 추가가 실패한 호출의 답(하위 질문 ⑨)도 정하지 않았다(반영: [ADR-0019](decisions/ADR-0019-od18-unusable-run-kind.md)). 잔여(제안 유지): hook의 종류와 검사 내용(호출 전 검사를 두는 위치 포함), 라운드 = 프로세스 경계(#8 M4), 불변식 목록, default-FAIL, kill switch, ADR-0010이 넘긴 하위 질문 3건, ADR-0015가 넘긴 2건 가운데 ⑤, ADR-0016이 넘긴 3건(그 가운데 ⑥은 첫 부분만 답해짐), ADR-0019가 넘긴 1건(⑨).
