## 3. 진단

1. **이 프로젝트의 핵심 불확실성은 실험으로만 답할 수 있다.** 코더가 baseline을 넘는 커널을 내는가, 기법 선택·가설 기록·사례 조회가 라운드 수를 줄이는가, evaluator가 계약 위반을 잡는가, 라운드당 비용·시간은 얼마인가 — 모두 실제 `claude`가 1층 프롬프트를 수행해야 측정된다. ADR과 스텁 테스트로는 답할 수 없다.
2. **스텁 end-to-end가 검증하는 것은 배관이다.** T-0491의 스텁 `claude`는 Round-Manager가 해야 할 호출 순서를 테스트가 정한 대로 재생한다. 2층 도구·hook·상태 파일이 그 순서를 받아내는지와 정의 문서의 정적 형태는 확인하지만, 실제 모델이 631줄의 프롬프트를 읽고 그 순서대로 행동하는지는 확인하지 않는다. 결과를 가르는 부분이 가장 작고, 실제 모델 동작의 검증은 0건이다.
3. **피드백 루프가 설계상 끊겨 있다.** D16(드라이버는 `claude`를 시작하지 않음)과 D22(라이브로만 확인되는 사실은 체크리스트로 미룸)는 각각 타당하지만, 함께 작동하면 시간당 드라이버는 스텁으로 닫히는 일 — 계약·검사·스키마 — 만 계속 만든다. 실제 run의 정식 경로인 D17 nightly는 HQ-0076에서 멈춰 있고, 그동안 PLAN 순서(D18)는 P2-10을 건너 P2-11~P2-14로 진행한다.
4. **깊이보다 폭이 먼저 자라고 있다.** 실제 run 한 번 없이 연산 kind·dtype이 늘면서, 첫 사례에 맞춘 형식을 넓히는 일(결과 형식 v2 — D23 행: bf16 연산이 fp32 GEMM의 고정 `shape`에 맞지 않음)과 연산 kind마다 평균 7~8 task(rope는 11개)의 계약·검증·calibration이 쌓이고 있다. 이 일들 자체는 필요하지만, 실제 run이 1층·2층의 계약을 바꾸게 되면 넓어진 만큼 고칠 곳도 많아진다. 실제 run이 무엇을 바꿀지는 아직 알 수 없다 — 그것이 §3-1의 요점이다.
5. **작은 task 절차 자체는 문제가 아니다.** 리뷰·테스트를 거친 2층 부품(CAS, 하네스, 백엔드 계약, hook)은 실제 run에서도 그대로 쓰이는 자산이다. 문제는 단위의 크기가 아니라 **무엇을 다음에 만들지 정하는 입력**이 실험 결과가 아니라 PLAN 체크리스트와 문서 정합성이라는 점이다.

## 4. 두 방식 비교

| | 현행 (PLAN 체크리스트를 작은 task로) | 실제 run 우선 (본 제안) |
|---|---|---|
| 다음 task의 근거 | PLAN 항목, OD 하위 질문, follow-up | 실제 run에서 깨진 것·부족한 것 + PLAN |
| 첫 실제 run | P2-10(P2-5 다음 순서)이지만 HQ-0076에 막힌 동안 P2-11~P2-14가 계속 진행된다 | P2-10을 관문으로 둔다 — 첫 실제 run 전에는 폭을 넓히지 않는다 |
| 수용 기준 측정(P2-9) | 변화 없음 | 변화 없음 — 실제 run의 결과는 D17 ②대로 회귀 신호다 |
| 품질 게이트 | 유지 | 유지(§6 E4에서 오너 선택) |
| 실패 양상 | 부품은 견고하나 전체가 실제 모델로는 안 돌 수 있고, 그것을 늦게 안다 | 첫 run이 여러 곳에서 깨진다 — 그 목록이 곧 backlog |
| 위험 | 방향 오류를 늦게 발견 | 동결 중 드라이버 유휴(§6 E6); 빅뱅이 되면 미검증 덩어리가 커짐 → 범위를 P2-5 구성으로 묶어 막는다 |

빅뱅식 "MVP를 다 만들고 나서 돌리기"는 권고하지 않는다. 그것은 현행의 미검증 기간을 다시 만드는 것이다. 권고는 **이미 있는 가장 작은 구성(P2-5: `cpu_standin` × GEMM fp32, N=1, 5라운드)을 지금 실제 `claude`로 돌리는 것**이다.

## 5. 제안 — 단계

- **R0 실제 run 열기 (즉시)**: HQ-0076에 답해 T-0493을 푼다. T-0493은 nightly 루틴의 절차 문서(예: `PROCESS/NIGHTLY.md`)와 진입점을 만든다 — 오너가 run을 시작하는 절차는 아직 이것 말고는 없다. T-0493이 착지하면 오너가 루틴을 등록하거나, 같은 절차로 첫 run을 수동으로 한 번 돌린다(D16 (b)의 오너 수동 확인 경로). 실행 머신의 전제: 로그인된 `claude`, Docker, 코더·stand-in 이미지(`HILCLAW_CODER_IMAGE`·`HILCLAW_STANDIN_IMAGE`), 코더 토큰(`HILCLAW_CODER_OAUTH_TOKEN`) — HQ-0076 (5).
- **R1 폭 확장 동결 (R0와 동시)**: planner는 R3의 해제 전까지 **폭을 넓히는 task**를 만들지 않는다. 진행 중인 task(현재 T-0511)는 마무리한다. 동결 범위는 §6 E3, 동결 중 고를 task가 없을 때와 해제의 대안은 §6 E6.
- **R2 결과를 backlog로 (첫 실제 run 뒤)**: 실패는 D17 ④대로 이슈가 되어 시간당 드라이버의 task가 된다. 오너는 수동 run이나 수동 확인으로 **그 run이 거친 RuntimeAcceptance 항목만** `확인됨`/`실패`로 바꾼다 — nightly run의 결과만으로는 항목을 닫지 않는다(D17 ①, RuntimeAcceptance 머리말). 머신 종류별 항목(예: RA-0002)과 bf16·Llama·macOS·WSL 항목(예: RA-0035, RA-0045~RA-0054)은 이 run으로 닫히지 않는다. `실패`는 이미 planner의 입력이다(D22). 이 단계의 task 순서는 §6 E5.
- **R3 같은 방식으로 Llama 3.2 1B로 넓히기**: 해제 조건(§6 E6)이 충족되면 동결을 풀고 P2-11~P2-14를 이어 가되, 연산 계약을 모두 갖춘 뒤가 아니라 **최소 연산 세트로 먼저 실제 run**을 하고 깨지는 곳을 채운다. 연산 세트와 그 순서는 OD-31의 결정을 따른다.

## 6. 오너 결정 항목

권고는 각 항목의 첫 선택지다. 이 권고는 통합자의 제안이며 오너의 결정이 아니다.

- **E1 채택**: (a) 채택 — §5의 R0~R3 (b) R0만 — 실제 run을 여는 것만 우선하고 PLAN·우선순위는 그대로 (c) 기각.
- **E2 실제 run의 기동**: (a) D17 그대로 — 별도 nightly 루틴만 실제 `claude`를 쓰고, 첫 1회는 T-0493의 절차로 오너가 수동으로 앞당긴다 (b) D17 확장 — R2 동안은 오너가 지정한 빈도(예: 수정이 착지할 때마다 on-demand)로 돌린다; 사용량 상한은 HQ-0076 (4)의 답을 따른다 (c) D16 개정 — 드라이버가 실제 `claude`를 쓸 수 있게 한다(권고하지 않음: D16의 이유인 비용·개발 머신 요건이 그대로다). 어느 쪽이든 T-0493이 먼저 착지해야 하고, T-0493은 HQ-0076 전체에 막혀 있다. 수동 run만 먼저 하려면 HQ-0076 가운데 (1) 구성·(5) 머신만 답하고 나머지를 nightly 등록 때 답하는 것도 오너가 고를 수 있다 — 그 경우 T-0493의 범위에서 HQ-0076의 (2) 실제 가중치 run·(3) 실행 시각·(4) 사용량 상한·(6) 가드 공존을 빼고, 그것들은 뒤의 별도 task로 다룬다.
- **E3 동결 범위(R1)**: (a) 폭 확장 task 전부 — 새 연산 계약·검증 run·calibration, 결과 형식 v2의 남은 slice, 그 밖에 P2-5 구성의 실제 run에 필요하지 않은 task (b) 새 연산 계약만 동결하고 v2 이관은 계속 (c) 동결 없이 우선순위만 바꿈.
- **E4 R2 동안의 품질 게이트**: (a) 그대로 — 테스트 규칙(D12)·리뷰·ADR 경로 모두 유지 (b) 실제 run 실패를 고치는 task에 한해, OD를 닫지 않는 결정은 근거를 ADR 대신 commit 본문과 이슈에 남기는 것을 허용 — OD를 닫는 결정은 여전히 DRIVER §9의 ADR을 거치고, D12 테스트 규칙·리뷰·BLOCKED 사유는 유지. (a)를 권고하는 이유: 지금의 병목은 게이트가 아니라 입력이다.
- **E5 backlog의 정본(R2)**: (a) PLAN은 유지하고, 실제 run 실패 이슈를 PLAN 항목보다 먼저 task로 만든다 (b) R2가 끝난 뒤 PLAN P2의 남은 항목을 실제 run 결과로 다시 쓴다(통합자 세션이 제안하고 오너가 승인) (c) 현행 — D17 (나)가 정하는 순서에 맡긴다.
- **E6 동결 중 대체 경로와 해제**: R0는 오너의 행동(HQ-0076 답, 루틴 등록, 실행 머신 준비)을 기다리므로, 동결 중 드라이버가 고를 task가 없을 수 있다(D23 행의 약 30시간 유휴와 같은 상황).
  - 고를 task가 없을 때: (a) 유휴를 허용한다 — 동결의 목적은 실제 run 결과 전에 폭을 넓히지 않는 것이고, 유휴의 비용은 R0를 앞당겨 줄인다 (b) 동결을 E3 (b) 수준으로 자동 완화한다 (c) 동결 범위 밖이면서 P2-5 구성의 실제 run에 도움이 되는 일(예: RuntimeAcceptance 항목을 닫는 런타임 자체 점검 코드)을 planner가 찾게 한다.
  - 해제 조건: (a) P2-5 구성이 실제 run에서 5라운드를 끝까지 돌고 baseline 대비 결과를 내거나, 오너가 정한 기한이 지나는 것 가운데 먼저 오는 것 (b) 앞의 실제 run 조건만 (c) 오너가 수동으로 해제.

E2의 어느 선택지든 R0는 HQ-0076의 답으로 시작된다. HQ-0076은 본 제안과 무관하게 지금 답할 수 있다.
