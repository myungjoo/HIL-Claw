## Why

**PLAN P3-16** (line ~80; DRIVER §6 D31 ①: P3-15 to P3-17 come after P3-11 and P3-12, and first while those wait on the owner) asks to show, on this PC's GPU, that one kind (`gemm`) of CUDA kernel goes through build, correctness, measurement and record with the real `nvcc` and GPU (D29). P3-11 is checked. P3-12 slices 3 and 4 wait on HQ-0102 and HQ-0103, so P3-16 is the item to plan now. Its owner answers are in:

- **HQ-0095 ② (a)** (2026-11-12): both points of the local CUDA GPU are the same local GPU run.
- **HQ-0096 ② (a) and its addition** (2026-11-14, [#5 comment 6874292829](https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6874292829)): the oracle of a vendor target is the contract's existing reference with the user's tolerance. Instance start opens at the CUDA target. The integrator's reading (the HQ's `decision`, not the owner's words) is that this opens given-code evaluation only, `model_run` stays false, and the coder writing CUDA kernels waits for HQ-0088 ① (c). How "given-code evaluation only" is written into the target table is for P3-16's §9 ADR, and an HQ if it is a frame change. A CUDA C++ bundle is another language's bundle (ADR-0200 decision 2) and needs an HQ. Until then the demonstration uses a kernel that a test places.
- **HQ-0097 (a)** (2026-11-12): a new backend kind `device_unavailable`, a tool failure meaning the probe found no usable device, common to `correctness.check`, `sim.run` and `board.run`, and stored in the end line's `failure`. Its `decision` says the task that adds it puts it into both `BACKEND_KINDS` sets, fixes the refusal in `hilclaw.vendor_adapter.tool_failure` (`tests/test_vendor_adapter.py`), and writes the orchestrator's handling in its §9 ADR under the existing tool-failure rules. PLAN P3-16 says the absent-device classification follows this answer. The PLAN hold line for this follow-up (보류 절, "HQ-0097 답 … (a) follow-up") is P3-16's own work now. The driver marks it `(→ T-0572)` in the state commit.
- **HQ-0093 ①**: CUDA records the toolkit version of the machine per run as a `toolchain` member of the hw_profile (an open map, ADR-0001). The target task's §9 ADR names that member and the GPU's `revision` value.

> (OD-33 ①·⑥, PLAN P3-16; ADR-0207 결정 5. HQ-0088 ① (c)는 다시 묻지 않는다) [쟁점] PLAN P3-16은 테스트가 둔 CUDA `gemm` 커널이 빌드·correctness·측정·기록까지 도는 것을 요구하고, HQ-0096 덧붙임은 CUDA 대상에서 주어진 코드의 평가를 연다. 오늘의 틀에서 시도의 `output/`은 `.c`·`.h` 이름만 받고 `.c` 파일만 컴파일하며(ADR-0055 N1·N2·R3), 주어진 코드는 C 파일 하나를 `given.c`로 두고(ADR-0200 결정 2), `candidate_kind`가 없는 `instance.json`은 C 커널 run이다(ADR-0198 결정 4, HQ-0089 ④). CUDA C++ 커널을 run에 기록하는 것과 CUDA C++ 주어진 코드 묶음은 이 틀을 바꾼다(D23). [선택지] (a) `cuda_gpu` 대상의 run에 한해 시도의 `output/` 허용 이름에 `.cu`로 끝나는 이름을 더하고 그 대상의 컴파일 집합은 `.cu` 파일로 한다(`.c`는 그 대상에서 컴파일하지 않음; 정렬·크기·개수 규칙은 그대로); 그 대상의 주어진 코드 묶음은 CUDA C++ 파일 하나이고 `given.cu`로 놓인다; 그 run의 `instance.json`은 지금처럼 `candidate_kind` 없이 쓰고, 그 없음을 "대상의 계약 언어(`cuda`)로 쓴 커널"로 읽는다(기존 값의 읽기 변경). (b) (a)와 같되 승인된 열린 목록 "후보 종류"에 새 값(예: `cuda_kernel`)을 더해 `instance.json` 버전 2로 적는다 — 값의 내용은 오너 몫이고 코더의 벤더 언어 커널 종류와 같은 값을 미리 정하게 된다. (c) 이름은 `.c` 그대로, 대상 플래그 `-x cu`로 CUDA C++로 컴파일한다 — 틀은 그대로이나 `.c` 파일과 C 커널 run이 CUDA C++를 담고 C 하네스도 CUDA C++로 컴파일된다. NVIDIA GPU와 Docker가 있는 C-7의 각 머신 종류(native Linux, WSL2의 Docker Engine, Windows의 Docker Desktop)에서: (1) `--gpus all`로 시작한 `cuda_gpu`의 빌드·프로세스 컨테이너가 GPU를 쓰는 동안 어느 checkout 경로도 보이지 않고, 드라이버 마운트가 읽기 전용이며, 빌드 디렉토리 밖에 쓸 수 있는 호스트 경로가 없고, ADR-0144의 다른 성질(네트워크 없음, 숫자 사용자, capability 없음)이 그대로인가; (2) NVIDIA Container Toolkit이 없거나 GPU를 줄 수 없는 머신에서 probe 컨테이너가 125로 끝나고 연산이 시도의 프로세스 전에 `device_unavailable`로 답하는가; (3) NVIDIA GPU가 없는 머신(macOS 포함)에서 `cuda_gpu`의 세 HW 도구가 `device_unavailable`로 답하는가. 실패로 드러나면 ADR-0207 결정 6·7(probe 컨테이너, `--gpus all`)을 다시 본다.
