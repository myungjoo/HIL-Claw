Any example is fenced as `json` or `text`, never as Python or shell that `ruff format --check .` would read. **Three kinds of content, said at the head of the Decision section**: the owner's sentences (quoted, marked **owner**, linked; not subject to the objection window), what an earlier record, a requirement or a documentation page says (**cited**, source and reading date named; "not verified" where no page carries it), and the record's own design (not confirmed by the owner). The Decision section answers these points and only these:
1. **Scope and terms.** The self-check of the package: what it is (a check a runtime machine runs on itself at the bring-up of an instance), and what it is not - not an FR-10 tool and not in the registry unless the record argues otherwise (weigh ADR-0015's definition of a tool), not a hook, not a test of the development driver, not the nightly end-to-end run of D17, not the owner's check by hand (b-1). State the D16 line in one sentence: the runtime starts `claude`; the driver that builds the check never does.
2. **Limits**, each written before the statement it limits (the manner of ADR-0049 decision 5 and ADR-0053 decision 2): it is a record, not code, and nothing was run; a pass shows one version of Claude Code, one machine, one moment and one way of giving the server; the model's part of the session is not deterministic; a logged-in command line at the start says nothing of the end of the run; the check spends plan usage (C-7 ②); whoever can replace the `claude` found on the PATH or the environment of the bring-up decides what the check sees.
3. **Step one - the login.** How the answer of `claude auth status` is read (exit status, its output, or both - cite the documentation; the one output T-0106 recorded is an observation under conditions) and what counts as "nothing is logged in"; the outcome and the text shown then (owner: stop with the instruction to run `claude auth login`; **the check never runs `claude auth login` itself** - say so and why); what the check does when no `claude` is found, or when the status call fails or answers something the record does not know (an outcome of its own, never read as logged in). **The report repeats nothing of the status output that names an account, an organisation, an e-mail address or a credential** - state the rule and its reason.
4. **Step two - the throwaway session.** What is the owner's (the five items quoted above) and what is the record's own: which further options pin the session down and why (candidates, each to be weighed against the documentation and not assumed: built-in tools switched off, an explicit non-bypass permission mode, an allow list naming only the check's tools, no session persistence, which setting sources are read, the output format the check reads, the working directory, no model name - the default model), where the configuration file passed by `--mcp-config` lives (outside both checkouts; created for the check and removed after it - cite the owner's HQ-0010 sentence on cleaning up only as an analogy, it speaks of coder calls) and that it is no registration for a run (the reading of T-0106's pre-check consultation, to be confirmed or corrected). Whether a time limit bounds the session is said here; a value may be left to the code task. Exactly one session per check unless the record argues for a bounded retry (weigh plan usage).
5. **Which server and which tools.** "The package's own MCP front" (owner): the unchanged `hilclaw.mcp_front` over which registry? Weigh at least (a) the registry of a run (`tools.default_registry`) with a real tool for the call and for the failure - what that needs (a data root, a run) and what it risks; (b) the unchanged front over a registry that holds only tools of the check itself (one that answers a result, one that raises a tool failure), started by an entry of the package - what that leaves unshown about real tools; (c) both. Whatever is chosen: the front's rules are not changed for the check, tools of the check never appear in the registry of a run, and their names obey ADR-0010 decision 4 (no `_` in a registry name unless the record reopens the mapping, which it must not).
6. **What is observed, where it is read, and the outcomes.** For each thing the owner lists - the `server/discover` probe, the revisions of `initialize`, `tools/list`, the tool listing, one call, one tool failure "as they reach the model" - say from which side it is read (the lines the server process received and wrote; the events of the session's output; the model's reply) and what the check does to be able to read it without changing a rule of the front. Then the outcomes, as a closed list with the condition of each: at least **passed**, **front refused** (owner: fails the bring-up) and **not logged in** (owner: stops), and - the record's own - what holds when the session ran but the model made no call, when the session failed for a reason that is not the front (usage limit, network, an option the installed version does not know), and when the server answered something the check did not foresee (for example a method later versions add after `server/discover`). **For each outcome the record says only what the check reports; what round 0 does after any outcome other than the owner's two is P2-1's and is registered, not decided.** A check that could not be carried out is never reported as passed.
