### The new builder (in `hilclaw/hw_tool.py`; a shared part in `hilclaw/journaled_tool.py` as far as the check of the request needs it)
One new public function that returns the tool function of a journaled HW tool. Recommended form, **not binding**: `hw_tool.stepped_tool_function(*, tool, steps, step_of, numbers, source, table, read, hw_profile_in, check, admit, perform)`, over a variant of `checked_function` that takes the `step` of a call from the request. Whatever the form, the function it returns has these properties, for a request `r`:

1. **Moment 1, the request check.** The frame members are checked exactly as `checked_function` checks them today (`run_id`, `execution`, the required prefix of `round` / `candidate` / `attempt`, a number the contract does not require refused, the same messages), and the tool's own `check(r)` is called. **The `step` of the call is obtained from the request only after both passed**, by a callable the contract hands over (recommended: `step_of(r)`), and the identity is formed from it. Every refusal is a `ToolFailure` of kind `invalid_request`, raised before the data-root source is asked and before anything is read; for a refused request the callable that gives the `step` is not called. The request carries no `step` member that the builder reads (ADR-0015 decision 4).
2. **The `step` values are stated when the function is built** (recommended: `steps`, a non-empty `tuple` of distinct *names*, checked when built as `step` is checked today). A value the callable returns that is none of them is a defect of the tool's contract, not of the caller: it must not become an identity, no line is appended and nothing is read for it. Which exception says so is the task's choice (it is `tool_crashed` at `hilclaw.tools.call` unless it is a `ToolFailure`); do not answer it as `invalid_request`. With one stated value the builder behaves, for a caller, as `tool_function` does with that `step`.
3. **Moments 2, s and 3** exactly as today: the data root asked once (`no_data_root` passes through); the layout stamp read by the same code, with the four `run_file_*` kinds; the lookup under the identity of the numbers, the `step` obtained in 1 and `execution`. An ended identity is answered with what its end line holds, an open one with `step_open`; for neither is the file read for moment 4, a backend selected, the place of property 5 called, the step or an operation called, or anything appended.
4. **Moment 4, one read.** For an identity with no line, one reader is called **once** (recommended: `read(data_root, run_id)`, answered under `run_files.reading(...)` with the same three classes and the same four kinds as `hw_profile_of` is today). What it returns is the source of both the hw_profile record handed to `backends.select` and whatever else the contract takes from the file (recommended: `hw_profile_in(value)` gives the record). The file is not read a second time in the call by the builder. `no_backend` and `not_offered` pass through as the selection raises them.
5. **The place between the selection and the start line.** After the selection has succeeded and before the start line is appended, a callable the contract hands over is called once (recommended: `admit(r, value)`, with the request and what the one read returned). **What it raises passes through unchanged** - a `ToolFailure` of the tool's own kind is the intended use - and then no line was appended, neither the step nor an operation was called, and the same request can be repeated and is answered by what the file then states. It is **not** called when the selection failed (ADR-0021 decision 4: such a kind follows `no_backend` and `not_offered`). What it returns reaches the step (property 6). The classes of `hilclaw.instance` and an `OSError` raised by it are not turned into a `run_file_*` kind (only the read of the stamp and the call of the reader are, as the module docstring says today).
6. **Moments 5 to 7** through `journaled_step.run_prepared`, unchanged: the start line with exactly `step` and `execution`; the step called once with the data root, the request as the caller gave it, the hw_profile record, the selected operation and what the place of 5 returned (the order and form of these arguments are the task's); the end line with what the step returned or with the `failure` of a `StepFailed`.
7. **Two requests that differ only in what the `step` follows from are two identities**: the second is not answered from the first, each has two lines of its own with its own `data.step`, and `execution` is counted apart for each (ADR-0040 decision 3). A further `execution` of one of them is a new identity and is carried out in full, the one read and the place of 5 included.
8. The builder does not modify the request or what the reader returned, keeps nothing between calls, and when built calls none of the callables, reads no file and asks the table nothing. The errors of building (a `tool` that is no HW tool, a `table` that is no `BackendTable`, a bad `steps` or `numbers`, a parameter that is not callable) are `TypeError` / `ValueError` in the manner of the existing builders; state the order in the docstring.
