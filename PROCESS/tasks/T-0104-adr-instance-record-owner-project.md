What the ADR **decides**. The content of each decision is the executor's to work out and justify from the fixed inputs; the reviewer's Approve confirms it. For every point give the choice, the alternatives considered and one or two lines of reason; mark each value as **cited** (#4 or an earlier record - say which) or as **this record's own**:
1. **Scope**: of `runs/<run_id>/instance.json`, the two members in which a run states its owner and its project; nothing else of the file and nothing of any other file. State that the file is still not a complete instance record.
2. **What each member states.** The planner's expectation, to be confirmed or corrected with reasons: the name the instance was started under as its owner, and the name of the project it was started under, **as given at the start and uninterpreted**. Say exactly what a reader of this record may conclude and what it may not: no identity of a person or an account is established (not an OS user, a git author, a GitHub account or the account of a Claude Code session; nothing checks the value against any of them); no right to read, write, resume, share or promote anything follows (ADR-0010 decision 8; OD-25); the value is no path level and no part of a `run_id`; two runs with equal values are not thereby related by any rule of this record, and two spellings are two values. **The hard part is the meaning**: #4 says what the fields replaced, not what an owner or a project is, and calls the name of a CI or autonomous actor ambiguous. Weigh whether the inputs carry (a) no more than "a name given at the start" for each - then what name a CI actor gives, whether an owner is a person or an account, and what a project groups are left open by name - or (b) a rule. **Do not write a definition of an owner or of a project the inputs do not carry.** If you conclude that a member whose meaning is that thin cannot be defined at all, return BLOCKED with the exact question instead of choosing one.
3. **The members: names, place and form.** Weigh at least: (a) two top-level members `owner` and `project` (the names of #4) against one enclosing object (for example a meta object) - weigh ADR-0032 decision 3 and ADR-0033 decision 3 on enclosing objects and what an object would shape for members that are not this record's; (b) the form of a value: the *string* of ADR-0001 (1 to 255 printable ASCII), its *name*, or a wider text (other scripts - a person's or a project's name need not be ASCII; weigh what the data plane holds today, what `label` takes, one spelling per value, and what a later DB column needs); (c) whether an empty string, leading or trailing spaces, `null`, a number or an array is a value. Say what is no value. **Do not make the form carry a meaning** (an e-mail address, an account syntax, a path-safe token) that point 2 did not establish.
4. **A file without a member; the version.** By ADR-0018 decision 2's own rule and consistent with the precedents unless a reason is given: (a) each member may be absent from a valid file, independently of the other, the version stays 1, absent means "not stated" - no default, and a reader of this record substitutes nothing (not the OS user, not a git identity, not the name of a directory or of the data repository, not the value of another run); or (b) required and version 2 - weigh #4's "불변 입력" list against the files that are valid today. A present and invalid member: say whether it makes the file invalid as a whole (the precedents).
5. **How the members stand to everything else**, only as far as it follows from the fixed inputs. The planner's expectation: **no rule** between the two members, none with `hw_profile` (its attribute `hw_source` is about the hardware), none with `source_commit`, with `db/`, with a spec or with `STATE.json`; nothing is looked up, grouped, counted or refused by them. Reading: from the file of the run, read as a whole, nothing kept between calls. State truthfully that no tool, hook or module reads either member today. Do not say which component reads them or at which moment.
6. **Limits**, in the manner of ADR-0033's: whoever can write the file states any owner; a misspelt top-level name reads as an absent member; a file written once cannot change its owner or project (a hand-over or a renamed project has no form); **a name committed to the data repository stays in its history** (ADR-0004 line 124: the history is the audit log and is not rewritten) and the repository may be shared at the project owner's decision (OD-25) - say it as a limit and decide nothing; without a rule of spelling, equal names need not mean the same person or project and different ones need not mean different ones.
