## Why
**ADR-0017** (accepted 2026-10-08, with the owner's HQ-0004 answers) fixed the verification run of a C `gemm` kernel at `cpu_standin`: a *verification program* in C — a second source under `hilclaw/harness/`, separate from the timing driver — is built with one kernel into a *verification executable* and run as a process of its own. The program draws the inputs from a seed, reports a check value of them, calls the kernel and writes the kernel's output to the report. Reference, comparison and verdict are on the Python side. **None of this code exists yet.** PLAN P1-3 (the harness) stays open for it, and P1-4 (the three-state calibration), the "harness pass" half of the C gate (P0.5-1, the only open item of the current phase that is not the owner's) and P2-3 / P2-5 all wait for it.

ADR-0017 Consequences asks for "two or more slices". The planner's split (DRIVER §6), following the route of the timing run (T-0032 / T-0033 / T-0034):
- **This task (slice ①)**: the one C source file and its tests. The tests build a verification executable by calling `clang_build.build` **directly** and run it with `local_run.run`. No Python module is added or edited, `numpy` is not added.
- **Slice ② (not this one)**: the Python side without a process — the second implementation of the generator and of the check value with NumPy array operations, the float64 reference, the `rtol` / `atol` comparison — together with the exact `numpy` pin the owner approved in HQ-0004.
- **Slice ③ (not this one)**: building the verification executable (one `clang_build.build` call) and the run itself: start the process, read the report, completed / broken, the verdict and the per-draw counts.

Why the C side first: it has no dependency question, and ADR-0017 hands the generator, the check function and the framing of the report to "the code task". Whichever slice comes first fixes them; the C file states them in its header so exactly that slice ② can write the second implementation against it, and the tests of this task prove the header by an independent implementation in the test file (standard library only).

**This task ticks no PLAN checkbox** (P1-3 is ticked when the whole verification code is on `main`).

A-13 check (planner's reading — the reviewer is asked to re-check): the program uses the C library and POSIX.1-2008 only (no `-lm`), `pyproject.toml` and `.github/` are unchanged, so no new dependency; no data-plane file or field is read, written or named. The file adds **no rule and no value** to ADR-0008 / ADR-0017. ADR-0017 leaves to "the code task": the file name, the generator algorithm (decision 3), the check function (decision 4), the spelling and framing of the report (decision 7) and the exit status values. They are fixed here as **provisional conventions of the source**.

### The C source — each item is a requirement
1. **Self-contained**: `#define _POSIX_C_SOURCE 200809L` before the first include; headers of the C library and POSIX only; no call into the mathematics library, so that it links without `-lm`; **no clock is read** (decision 2). It declares the kernel with the prototype of ADR-0008 decision 4, **byte for byte on one line**: `void hilclaw_gemm(size_t m, size_t k, size_t n, const float *restrict a, const float *restrict b, float *restrict c);`. It defines `main` and no other identifier with external linkage.
2. **Portable C99**: compiles without a diagnostic under `-std=c99 -Wall -Wextra -Wpedantic -Werror` with clang at `-O0` and at `-O2` (the job `C gate (clang)` compiles it with exactly these flags at `-O2`). No compiler extension, no `__attribute__`, no `#pragma`.
3. **Command line** (decision 9): the dimensions, the number of draws and the seed, and nothing else — recommended `<m> <k> <n> <draws> <seed>`, exactly five arguments. **No `rtol`, no `atol`** (decision 5), no flag, no default. It reads no standard input, no file and no environment variable. Integers are accepted only as decimal digits (no sign, no space, not empty, no leading zero) that fit their type, with overflow detected and not wrapped; `m`, `k`, `n` and `draws` at least 1; `seed` any value of `uint64_t` (0 and 2^64 - 1 included).
4. **Operands**: the byte sizes of m·k, k·n and m·n `float` elements are checked against `SIZE_MAX` before allocating; `a`, `b` and `c` are three separate allocations made once and used for every draw; no input value is written to any file, and none is written to the report or to standard error by the program.
5. **Generator** (decision 3): deterministic; the value of an element is a **closed-form function of the seed, the draw number and the element's index**, built from unsigned 64-bit integer arithmetic only, with no dependence on the elements before it — so that slice ② can compute a whole draw with NumPy `uint64` array operations. Every element is finite with a magnitude in [0.5, 1) and both signs occur; two draws of one run have different values. **The element is formed as its binary32 bit pattern from integers and stored with `memcpy`**, so that no build flag of the caller changes a value. Recommended (provisional): the splitmix64 output function `mix(x)` of `timing_driver.c`; `base(d) = mix(seed + (d + 1) * G)` for draw `d` counted from 0 and `G = 0x9E3779B97F4A7C15`; word of element `e` = `mix(base(d) + (e + 1) * G)`, where `e` counts the m·k elements of `a` in storage order and then the k·n elements of `b`; bit pattern = `(word & 1) << 31 | 126 << 23 | word >> 41`, that is ±(0.5 + u·2^-24) with u of 23 bits. Whether it equals the generator of the timing driver is not promised and not required.
6. **Check value** (decision 4): before each kernel call the program reports a check value of the bytes of `a` followed by the bytes of `b` of that draw. It must be computable on the Python side without an interpreter loop over the elements (a standard-library function over a buffer, or integer array operations). Recommended (provisional): CRC-32 as `zlib.crc32` computes it (the table or the bitwise form written in the file), reported as the four bytes of a `uint32_t` as they are in memory. It is no protection against anything (decision 10); say nothing more of it.
7. **`c` before a call** (decision 4): before each kernel call every element of `c` is set to one NaN **written as a bit pattern** (recommended `0x7FC00000`, by `memcpy` of a `uint32_t`), not through `NAN`, a division or any floating-point expression.
8. **Report channel and form** (decision 7): before the first kernel call the program keeps the standard output it was started with under a descriptor of its own (`dup(1)`) and points descriptor 1 at standard error (`dup2(2, 1)`). For each draw, in this order: the check value, written completely **before** the kernel is called; the one call `hilclaw_gemm(m, k, n, a, b, c)`; then the m·n elements of `c` in the layout of ADR-0008 decision 2 as the 4·m·n bytes they have in memory. After the last draw an end mark of a fixed length (recommended: a short fixed ASCII word ending in LF, named in the header). Nothing else is written to that descriptor, and **the length of a complete report follows from `m`, `n` and `draws` alone**. Writes go through a `write` loop that handles a short write and `EINTR` (an output of 16 MB does not go out in one call), never through a buffered stream.
9. **Exit status**: 0 after the end mark and in no other case. Failures of the program itself end with a non-zero status and one line on standard error, and write no end mark. Recommended values, as in the timing driver: 2 the command line, 3 a size that cannot be held or an allocation, 4 a descriptor or a write of the report. They are listed in the header.
10. **What the program does not hold** (decisions 4-6): no reference, no comparison, no tolerance, no verdict; it does not read `c` except to write it out.

### Tests (`tests/harness/test_verification_program.py`; excluded from the size cap)
Kernels are short C sources held as strings in the test file and written to a temporary directory. Each (kernel, flags) pair is built **once** per test session with `clang_build.build((program, kernel), output, timeout_s=..., flags=...)`, the program path being `Path(hilclaw.harness.__file__).parent / "verification_program.c"`, and the test asserts `result.ok` with `result.log` as the message. Runs go through `local_run.run((<path of the executable>, <arguments...>), timeout_s=...)` — the executable itself, no prefix. Build-and-run tests use a fixture that skips when `os.name != "posix"` or clang is absent, and calls `pytest.fail` when `GITHUB_ACTIONS == "true"` and clang is absent.

The test file holds its **own implementation of the generator and of the check value, written from the header comment with the standard library only** (`struct`, `zlib`, integers masked to 64 bits; no `numpy` — it is not a dependency yet), and a function that splits a report by lengths computed from `m`, `n` and `draws`. Use small shapes so that this implementation stays fast.

- everywhere (no compiler; runs on Windows too): the source exists, is ASCII, and contains the ADR-0008 prototype line byte for byte.
- happy:
  - a kernel that copies elements of `a` into `c` and one that copies elements of `b` into `c` (no floating-point arithmetic), at a non-square shape with m, k, n all different, for `draws` 1 and 3 and seeds `0`, `1`, `2**63` and `2**64 - 1`: exit status 0; the report has exactly the computed length and ends with the end mark; every check value equals the test's own; **every output element equals the expected bit pattern** (this shows the generator, the storage order of `a` and `b`, the order of the draws and the layout of `c` bit for bit); every element is finite with magnitude in [0.5, 1) and both signs occur; the draws of one run differ; the same seed twice gives the same report and another seed a different one;
  - a plain triple-loop `gemm` kernel under `-std=c99 -Wall -Wextra -Wpedantic -Werror` at `-O0` and at `-O2`: the output agrees with the product the test computes in Python floats from its own generator, within a margin the test chooses for itself (it is a test value, not a tolerance of the harness; mind the cancellation observation of decision 5);
  - a kernel that writes one line to standard error per call: the number of lines equals `draws`;
  - a kernel that prints to its standard output: the report is undisturbed and the text is found in `stderr`;
  - a kernel that `abort`s unless its arguments are the given `m`, `k`, `n` and every element of `c` holds the NaN bit pattern on entry: the run completes for `draws` > 1.
- branch:
  - a kernel that writes nothing: every reported element of every draw is the NaN bit pattern; the same with the program built with `-O2 -ffast-math` (the bit patterns of the inputs and of the fill survive the caller's flags);
  - a kernel that writes only the first row: the rest of each draw is the NaN bit pattern, also in the second draw (no stale output of the first);
  - `draws` = 1 and a shape with a dimension of 1.
- error / negative:
  - a kernel that never returns from its first call, small `timeout_s` → `timed_out`, and `stdout` is exactly the first check value (written before the call);
  - a kernel that `abort`s in its second call → a status that is not 0, and `stdout` is the complete block of the first draw plus the check value of the second, with no end mark;
  - dimensions whose arrays cannot be held (for example m = k = n = 2**40, and a product that overflows `size_t`) → the documented status, empty `stdout`, a message on `stderr`;
  - malformed command lines, each asserting the documented status, an empty standard output and a non-empty standard error: no argument, one too few, one too many (so a sixth argument such as a tolerance is refused); `m` = `0`, empty, `-1`, `+1`, `1x`, ` 1`, `01`, a 30-digit number; `draws` = `0`; `seed` = `18446744073709551616` and `-1`.
- Test rules of CLAUDE.md / DRIVER §5 (D12): ① and ③ concern Python modules — only a docstring of `hilclaw/harness/__init__.py` changes, so the coverage of `hilclaw/` is unchanged (say so; the job `Coverage gate (hilclaw)` must stay green); ② happy, error, branch and negative cases as above; ④ the C file has its test file by the same naming rule; ⑤ no tests for test code (the fixture kernels, the test's own generator), CI workflows or helper scripts.
- Keep the file's CI run time under about 30 s: small shapes, one timeout test of a few seconds. The tests run in three jobs (two Python gates and the coverage gate).
