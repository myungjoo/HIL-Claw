## Acceptance Criteria
What is **fixed** and taken as input, not re-decided:
- FR-10: the four HW experiment tools `sim.run`, `board.run`, `profiler.collect`, `correctness.check`; a tool contract that does not depend on where a backend runs (local or LAN — C-7 ⑤ ⑥); a mock backend that always exists, for fault injection and contract tests; the first registered backend is `cpu_standin`; the MVP uses a fixed tool set and creates no tool during a run (#5 A-12).

- ADR-0010 and ADR-0015 as they stand: one tool function per tool below two fronts; a front holds no tool logic; the tool definition; the reserved kinds; the data root never in a request; no outcome depends on state a server process kept; the five common request members; the journaled path below the fronts; standard library only. ADR-0011 (journaled step). ADR-0004 decision 4 (writer roles).

What the ADR **decides**. The content of each decision is the executor's to work out and justify from the fixed inputs; the reviewer's Approve confirms it. For every point give the choice, the alternatives considered and one or two lines of reason; mark each value as **cited** or as **this record's own**:
1. **Scope and terms**: the part that is the same for every HW tool and every backend, and nothing of any single tool or of any single backend's mechanism. Reuse the terms of ADR-0010 decision 1, ADR-0011 decision 1 and ADR-0015 decision 1; add a term only where one is needed (for example "HW tool", "backend").
2. **What a backend is and where it sits**: below the tool function of a HW tool. Work out (a) which part of a call belongs to the tool function for every backend (the check of the request and `invalid_request`, the data root, the journaled path where the tool is journaled, the form of the result and the kinds) and which part is the backend's (carrying out the experiment at one target); (b) what FR-10's "the contract does not depend on where a backend runs" means for a backend — whether a backend may add a result member or a failure kind of its own, or answers exactly the contract of the tool; (c) what ADR-0010 decision 7 means for a backend (a connection that can be made again is allowed; its lifetime is #5 B-2 / OD-10 — cite, do not decide); (d) whether the data plane is written by the tool function with what a backend returned or by the backend itself — **only as far as the fixed inputs carry it** (ADR-0004 decision 4, ADR-0011 decision 2); otherwise say that it is each tool's contract.
3. **Which tools go through a backend, and what one backend answers**: the four HW tools; `blob.push` / `blob.fetch` are not HW tools, and their storage backend is C-3 / #5 B-2 / A-3 and is not this record's. Work out what a call answers when the backend selected for it does not offer the called tool (a tool failure — whether the frame reserves a kind for it, in the manner of ADR-0015 decision 2). **Do not decide** whether every backend must offer all four (sim-only onboarding is OD-26), and decide which of the four the `cpu_standin` backend offers **only if** the fixed inputs carry it (#5 A-7, FR-10, FR-1, ADR-0007 decision 1, ADR-0009 decision 1); otherwise register the exact question as a sub-question.
4. **How the backend of a call is selected**: who or what names it. Alternatives to weigh at least: a member of the request that names a backend (the calling agent chooses the target — compare the reasoning of ADR-0015 decision 3 and the reason A-7 gives for a hw_profile of its own); derived from the hw_profile the call is about (FR-14 ④, UC-0 step 3, the `accelerator` field of ADR-0001) — and then from where a call knows that hw_profile with what exists today (a member of the request naming a hw_profile key; the `hw_profile` section of the attempt's `spec.json`, ADR-0002; `instance.json`, which has no fixed member yet); the configuration of the front process; bound when the registry is built, as the data-root source is. What must hold: the same answer through both fronts, nothing kept between calls, and a result that cannot land in the knowledge of another target without anyone seeing it. **The record must not define a member of `instance.json`, of a key record or of any other data-plane file, nor a member of `hilclaw.config.json`, nor a registration store for endpoints (OD-26).** If the rule needs one of these, fix the rule as far as the fixed inputs carry it ("the backend of a call follows from …") and register the missing piece as an exact sub-question with the place where it is decided (PLAN P1-8, OD-26).
5. **The mock backend**: (a) what it is — a backend of the package with no hardware behind it, always present (cited: FR-10, A-7); (b) how it is selected — by the rule of point 4 or by a way of its own, and what keeps its outcomes out of the knowledge of a real target (A-7's reason for `cpu_standin`); name **no value** of a hw_profile record beyond what a source gives; (c) how it is told what to produce — alternatives to weigh at least: a member of the request (the schema of a real tool would carry a test member, and an agent could choose it), the environment or configuration of the front process (ADR-0015 decision 7 "Two environments"), a file of the data plane (a data-plane schema — not here), bound when a registry is built (a test builds its own registry; say what the default registry of the two fronts then holds), derived from the request by a fixed rule; (d) what it must be able to produce — every class of outcome the contract of a tool names (a result, a result that reports a failed experiment, each tool-failure kind) and, for a journaled tool, the three death points of ADR-0015's Walk-through as far as a backend can cause them; it lists **no fault of a real board or simulator** (OD-10, #5 B-2, B-3); (e) that its outcome depends on its input alone (no clock, no random source), or the reason why not.

### Decisions of ADR-0016 (`ARCHITECTURE/decisions/ADR-0016-od18-backend-frame.md`, 150 lines; the whole change is 161 insertions and 8 deletions in the 4 files of `touchesFiles`)
1. **Scope and terms**: the part that is the same for every HW tool and every backend; new terms *HW tool* (FR-10's four, cited), *target*, *backend*, *operation*, *backend table*, *mock backend*, *script*.
2. **What a backend is and where it sits** (own): the part of the package that carries out the experiments of HW tools at the targets of one `accelerator`, named by that value (field cited: ADR-0001 decision 1), with one operation per HW tool it offers; the backend table maps a name to a backend and is built when a registry is built, in the MVP from the source alone. It sits below the tool function; the check of the request, the data root, the journaled path, the selection and the form of the result are the tool function's for every backend. **Order of a call**: check → data root → (journaled) lookup, where an ended or open identity is answered from the log and no backend is selected or called → selection → start line → operation → end line. A call that fails in the selection has consumed nothing and leaves no line. Reason for the place: after the lookup so that a stored result stays obtainable when the table changed; before the start line so that a missing backend does not use up the identity. The reading of ADR-0011 decision 3 and ADR-0015 decision 5 is stated (such a call has not started the step). **A backend answers exactly the tool's contract** (no result member or kind of its own) — what "transport 무관" means one level down. No outcome depends on state a backend kept (cited: ADR-0010 decision 7; connection lifetime, reservation and lock stay with #5 B-2, OD-10, OD-17). The two step lines are the tool function's; who writes every other file is each tool's contract.
3. **Which tools go through a backend**: the four HW tools; `blob.push` / `blob.fetch` are not HW tools (their "backend" is a store — #5 B-2, A-3). The frame requires no operation of a backend (whether all four must be offered is OD-26). **Two further reserved kinds** (own): `no_backend` and `not_offered`, reserved for the whole registry; the reading of ADR-0015 decision 2 ("not a closed list") is stated. Which of the four `cpu_standin` offers is **not carried by the fixed inputs** → sub-question ⑦.
4. **Selection** (own): nobody names a backend — not the request, the calling agent, the configuration or environment of a front process, nor anything kept. The backend follows from the `accelerator` of the hw_profile the call is about; for a call about a run that is the hw_profile of the run the request names (cited: FR-14 ④, UC-1), read from the data plane at each call, so such a request carries `run_id`. Reason: a request naming a backend or a hw_profile would let an agent measure one run's attempt at another target unseen (the reason A-7 gave for a hw_profile of its own; the reasoning of ADR-0015 decision 3 for the data root). **Left open**: where a run states its hw_profile (no member of `instance.json` or `spec.json` is defined) and a call about no run → sub-question ⑥.
