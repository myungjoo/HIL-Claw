## Why

PLAN P1-1 (FR-10 tool contracts + mock backend) is open. `correctness.check` now has on `main` a tool function (`hilclaw/check_tool.py`, `tool_function(*, source, table, seeds, covers)`), a closed request with its input schema and description (`hilclaw/check_definition.py`, ADR-0069, landed by T-0211/T-0212/T-0213), the mock's operation and default script (`hilclaw/mock_check.py`, ADR-0044), a seed source (`hilclaw/harness/seed_source.py`, `system`), and the predicate "covered" of ADR-0041 decision 5 (`hilclaw/gemm_contract.py`, `covers`). It is still not offered by any registry: `hilclaw.tools.default_registry` holds only `blob.fetch` and `blob.push`, and `tests/test_check_definition.py` asserts that the default registry holds no definition of the tool.

ADR-0069 Consequences names what is left: "**What still stands between that and a registered tool**: the binding of a backend, a source of seeds and the predicate "covered" (`hilclaw/check_tool.py` takes each as a parameter without a default), and the registration itself. Also open: the spend beyond ADR-0040 decision 6, sub-question ⑤, and ⑱." Its Boundaries list "The registration of `correctness.check`, and the binding of a backend, a source of seeds and the predicate "covered"" as not decided.

Some of this is fixed by earlier records and some is not:
- ADR-0016 decision 5 (a)/(c): the mock is "an entry of the backend table bound in every registry that `default_registry` builds", and "The default registry of the two fronts holds the mock bound to one script fixed in the source; what that script answers for a tool is written with that tool's contract." Decision 2: the table is built "in the MVP from the source alone".
- ADR-0021 decision 3: the property a source of seeds must have, and "In a registry that `default_registry` builds, no request, option or variable of the front process sets it. How the source is bound, and whether a test binds one of its own, …" is left; ADR-0048 Boundaries (line 197) leave "how a registry or a test binds one".
- ADR-0041 decision 5 defines "covered".
- **Not fixed, and a real design question**: ADR-0038 decision 2 says "`cpu_standin` offers `correctness.check`", while ADR-0060 Status says "the operation of `cpu_standin` for this tool still cannot be written to its end" (no setting has a value, the container the owner decided on has no design, the log file has no path). So the question is whether the tool is registered now with a table whose only working entry for it is the mock, and if so what a call about a `cpu_standin` run answers until that operation exists (no `cpu_standin` entry, so `no_backend`; or an entry that offers nothing, so `not_offered`; or something else), or whether the registration waits, and for what.

This is part of OD-18, a design-level OD, not owner-only (DRIVER §9: owner-only means #5 A/B items, C-6, OD-25 and OD-3). Under DRIVER §6 and §9 this task writes the ADR; the code that registers the tool is a later code task.

**Numbering.** ADR-0068 is held by the unlanded branch `claude/T-0210-od18-run-tools-operation-tool-failure` (BLOCKED, HQ-0021) and ADR-0069 is on `main`. This task uses **ADR-0070** and must not take ADR-0068. Do not read that branch for content, depend on it, or reconcile with it; it is about `sim.run` / `board.run`, and this task decides nothing about them.

**Why this item now.** No lock, no TODO or INTERRUPTED task, and no open PR (checked at `97bbd23`). The open HQs are HQ-0013, HQ-0014, HQ-0016..HQ-0019 (`runtime-acceptance` items on DONE tasks) and HQ-0021 (T-0210); none bears on this task. The run tools' next slices wait for HQ-0021, so the `correctness.check` line is the one P1-1 line that can move.
