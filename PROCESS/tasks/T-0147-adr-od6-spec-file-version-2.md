## Why
PLAN P1-5 ("GEMM spec 예시 ... 와 `spec.json` 스키마") is open. ADR-0050 (T-0117, landed as `fd337bd` on 2026-10-13) defined the members of `task.objective` in version 2 of the spec, on the repository owner's answer to HQ-0009. It is a record about the **parsed document** only. Its limit L8 and its Consequences say what is missing before any code can move to version 2:

- ADR-0029 gives the text form and the write of a spec file **for version 1 only**: "`schema_version` 1 is the only version a record defines", a file of another version "is set apart", and "A write by decision 4 writes a content of version 1 only" (its decision 2).
- `hilclaw/spec_file.py` has no version of its own: it compares with `spec.SCHEMA_VERSION` and calls `spec.validate`. Changing the validator's version alone would make the package write and accept version-2 spec files and set version-1 files apart - a state no record defines.
- ADR-0029 leaves the numbers inside `task.objective` to "the records that define those members"; ADR-0050 makes `bound` an *integer* of the parsed document and "does not say how it is spelt in a file".

ADR-0050 registered this as **sub-question 5 of OD-6** ("하위 질문 ⑤", OpenDecisionProposals.md, section OD-6): whether the rules of ADR-0029 carry over to a version-2 file, the spelling of `bound` in a file, and what a writer and a reader of version 1 and of version 2 do beside each other (with OD-8 and OD-11; "설계 수준 — PROCESS/DRIVER.md §9"). **This task is the record that answers it.** It ticks **no PLAN checkbox**: the validator code and the committed example are later slices.

Authority: OD-6 and OD-8 are design-level under DRIVER §9 (neither is on the owner-only list), so the executor writes the record and a context-isolated reviewer accepts it. The change of the spec schema to version 2 itself is the owner's (the answer to HQ-0009, part 4, quoted as O4 in ADR-0050) and is **not re-decided here**. This record adds what a byte sequence under a spec path must be for a version-2 content and how it comes there, as ADR-0029 did for version 1; by ADR-0029's own A-13 reading that is not a schema change of the data plane. If the record turns out to need more than that (see "Do not invent"), it is BLOCKED.

The one place where the question meets something that is not design-level: **OD-11** (reading older versions, migration) is open, and OpenDecisionProposals.md section OD-11 says its proposal narrows the owner's wording of NFR-7 (2) and is not to be reflected "오너 확정 없이". This record therefore may say what a file of another version *is called* by a reader of its rules (ADR-0029 already "sets apart" such a file and hands it to OD-11) but must not decide a guarantee of reading or a migration.

### The answer to each part of sub-question 5, as landed
- **Which rules of ADR-0029 hold (decision 1)**: carried over by reference, nothing restated. Unchanged for a version-2 file: the text (one JSON object, UTF-8 without a byte order mark, no member name twice), the written form, a missing file, the `id` and the path (decision 3), the requirement, the steps and a taken name (decision 4), the directories (5), the temporary file and a leftover (6), the promises and limits (7). With a named change: "The document it parses to is valid by ADR-0002" becomes validity by ADR-0050 for a version-2 file (ADR-0002 stays the record for version 1); the *integer* places gain `bound`; the file of another version and the version a write writes (decision 3 of the record). Not holding: "today's check is `hilclaw.spec.validate`" (no check of a version-2 document exists) and the other today's-code citations, which describe version-1 code. Not carried: "The `schema_version` of the spec stays 1".
- **Numbers (decision 2)**: `bound` is an *integer* place; decimal digits without sign, fraction or exponent; `5.0`, `1e3`, `-0` and a number above 2^53 - 1 are no *integer*, and a version-2 file that spells a `bound` so is invalid by its text. A rule of the bytes: what a parsed version-2 document is valid as is not changed. A file with `2.0` as `schema_version` is neither a version-2 file nor set apart; it is invalid. Of ADR-0029's three places, two are left for version 2 as ADR-0050 leaves it (`profile`, `ext`; untouched). No valid version-2 file holds a `bound` today (empty `constraints`); the rule is written for the admission of `memory_ceiling`, so the record of OD-13 sub-question 9 needs no further spelling rule. The spelling of a number of `weight` or `priority` is left to the record that gives them a type.
- **Writer and reader beside the other version (decision 3)**: (a) a write under the rules of version 2 writes version 2 only, a write under ADR-0029 version 1 only, none both; the code slice moves the package in one commit, and the record defines no state in which the package reads or writes both (a later OD-11 record may).
