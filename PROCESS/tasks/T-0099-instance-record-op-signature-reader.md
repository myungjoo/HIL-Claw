## Why
ADR-0031 (landed as `dedadda`, T-0098) fixed the member of `runs/<run_id>/instance.json` in which a run states its op_signature: the top-level member `op_signature`, a closed object of `key` and `record`. Its Consequences cut one code slice:

> **The code slice that can now be cut** (within the size cap, code mode): in `hilclaw/instance.py`, the validity of the member by decision 3 and a reader of the op_signature of a run beside `hw_profile_of`, with tests in `tests/test_instance.py`. The names, the return form of that reader and how "not stated" is told from a value are the code task's; the check can be the one the module has for `hw_profile`, with `hilclaw.keys.op_signature_key`. **Binding the reader to a spec, to a tool or to `db/` is not part of that slice**, and neither is writing the file. `hilclaw/instance_file.py` takes the validity of a content from `hilclaw.instance.parse`, so it refuses a content with an invalid member once the slice lands, without a change of its own.

**This task is that slice.** Today `hilclaw/instance.py` defines six members (`schema_version`, `hw_profile`, `tolerance`, `source_commit`, `n_max`, `candidates_per_round`); an `op_signature` of any value - a string, `null`, an object whose `key` is not the name of its `record` - is handed back uninterpreted in `Instance.others`, the file counts as valid, and nothing in the package can answer "which op_signature does this run state".

It serves PLAN P1-8 ("런타임 STATE/instance/events 스키마"). It ticks **no PLAN checkbox**: P1-8 stays open (further members, the writer and the start of an instance, the result files, the rest of `STATE.json`, the event kinds).

### The validity of the member (ADR-0031 decisions 3 and 5)
- `op_signature` joins the members the module defines (`_DEFINED`), so it is no longer handed back in `others`.
- A present member is valid exactly when it is an object with **exactly** the two members `key` and `record`, `record` is an object that `hilclaw.keys.op_signature_key` accepts, and `key` is a `str` equal to the `name` that function derives. Nothing else is a value: `null`, a string (the key alone included), a number, a boolean, an array (of one such object included), an object that lacks one of the two members or holds a third.
- **The record is judged by `hilclaw.keys.op_signature_key` and by nothing written here**: the module holds no list of kinds, dtypes, layouts or shapes and no value of M. A record of a kind that function does not know is invalid and makes the content invalid (decision 7); a valid `gemm` record of any `m`, `k`, `n`, any name as `dtype` and `layout`, with or without `ext` and `label`, is a value. A change of `label` keeps the key; a change of a key field (`shape.m` among them) does not.
- A present and invalid member raises `InvalidInstanceError` naming the place (`op_signature`, `op_signature.key`, `op_signature.record` or `op_signature.record.<field>`); nothing is returned, so no member of that content is used (`hw_profile`, `tolerance`, `source_commit`, `n_max` and `candidates_per_round` included), and nothing is repaired: neither half is trusted over the other. Recommended: the order and the messages of `hw_profile` with the other place name - an object, no member besides `key` and `record`, both present, `key` a `str`, `record` an object, the record valid, `key` the derived name; the first rule found broken is reported.
- The member is checked after `candidates_per_round` (recommended: the order in which the records defined the members, as the module docstring says of the others). Another `schema_version` is still `UnsupportedVersionError` before the member is looked at. The text rules (a member name twice in any object, the member name twice at the top level, an integer too long for the interpreter, nesting too deep) stay text rules.
- A content without the member is valid and states no op_signature: `None` in its place. **Nothing stands in - no record, no key, no constant of this module, nothing taken from `hw_profile`, from another member, from another run, from a spec or from `db/`.** No function of the module has a default argument, and no named tuple of the module has a field default.
- The module does not import `hilclaw.spec` or `hilclaw.key_records`, reads no file besides the instance file and compares the member with nothing (decision 6). No rule between `op_signature` and `hw_profile` or `tolerance` is added: each is valid by itself.
- **Recommended shape** (the task's choice; another shape is acceptable with one line of reason): a public named tuple `OpSignature(key: str, record: dict)` in the manner of `Tolerance`; one field `op_signature: OpSignature | None` of `Instance` after `candidates_per_round` and before `others` (`others` stays last); a private check beside `_hw_profile`; no new module-level `int` or `float` (so the expected dictionary of `test_nothing_of_the_module_holds_a_tolerance_value` stays unedited). The alternative the planner weighed is two fields `op_signature_key` and `op_signature` as `hw_profile` has them, both `None` together; one field keeps "both or neither" out of the type. The record is handed out as the `dict` parsed from the content, the key as the `str` of the file.
