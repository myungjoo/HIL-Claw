## Why
PLAN P1-1 (the FR-10 tool contracts, the mock backend, the conformance tests) is open. For `correctness.check` the code on `main` is a row of pure modules bound to no tool: `hilclaw.check_result`, `hilclaw.check_judging`, `hilclaw.check_answer` (from a returned answer to a result; an answer of neither form raises `NeitherFormError`, "no tool failure, no `kind`"), `hilclaw.check_parameters` and `hilclaw.mock_check` (T-0135). Since T-0136 a record says what a call answers for an answer of neither form: **ADR-0045** - a returned value of neither form and a raised error end the step without an outcome, with a `failure` of the tool's own kind `operation_answer_invalid`; a raised request to end is not caught; the message carries nothing of the content of the answer.

Nothing in the package renders that record. ADR-0045 Consequences names the code as an observation ("The tool function of `correctness.check` can now say what its step does with `hilclaw.check_answer.NeitherFormError` and with an error an operation raised"), and hands three points to "the code task" by name: the wording of the message; "where the code draws the line between what an operation raised and what the tool function's own code raised"; and the line between a raised error and a raised request to end. T-0136 `## Result` lists the criteria a code task should carry (its Follow-ups, third item, (i) to (v)).

**This task carries that part into the package as one function, ahead of the tool function** - the same kind of slice as T-0129, T-0130, T-0131, T-0133 and T-0135. ### The module
Recommended public names, and no other: `KIND_OPERATION_ANSWER_INVALID`, `OperationAnswerInvalid`, `ask`.

- **`KIND_OPERATION_ANSWER_INVALID`** - the string `"operation_answer_invalid"` (ADR-0045 decision 4), spelt once in the package. It is a name of ADR-0001 and **not** a member of `hilclaw.tools.RESERVED_KINDS`, which is not edited.
- **`OperationAnswerInvalid`** - the module's exception for a returned value of neither form and for a raised error:
  - A direct subclass of `Exception`; **no** `ToolFailure`, **no** `StepFailed`, no subclass of either. It carries `kind` (always the constant above) and `message` (exactly a `str`), and no amount: no attribute `spend`. It does not hold the answer, the raised error, or anything of either, in any attribute of its own. Recommended: it is raised with `from None` for a raised error, and the docstring says so (observation, not a rule: Python still sets `__context__`).
  - `hilclaw.tools.ToolFailure(error.kind, error.message)` can be built from every instance the module raises (the kind is a name, the message a `str`).
  - Its docstring says what it means in the words of the sentence a caller may rely on (ADR-0045 decision 4), that the code which ends the step states the spend, and **nothing of what a caller does after it**.
- **`ask(operation, request, hw_profile, parameters, *, rtol, atol)`** - calls the operation once and returns the result of the check, a new `dict`:
  1. **Before the operation is called** (recommended): `parameters` whose type is not exactly `hilclaw.check_parameters.CheckParameters`, and an `operation` that is not callable, raise `TypeError`; the operation is then not called. The five values are **not** validated here (who checks them is the caller - T-0133 follow-up; say so in the docstring).
  2. **The call**: `operation(request, hw_profile, parameters)` - exactly these three positional arguments, the same objects, once (ADR-0043 decision 2; T-0135 "The interface as landed").
  3. **A raised error** - an `Exception` that is no `hilclaw.tools.ToolFailure`, raised by that call: `OperationAnswerInvalid`, whatever the class is. This includes a `hilclaw.check_answer.NeitherFormError`, an `OperationAnswerInvalid` and a `hilclaw.journaled_step.StepFailed` that an operation raises itself: none of them passes through as it is, so a backend cannot state a kind or an amount by raising one.

### The interface as landed

- `hilclaw.check_operation` - public names: `KIND_OPERATION_ANSWER_INVALID`, `OperationAnswerInvalid`, `ask`, and no other. Imports: `hilclaw.check_answer`, `hilclaw.check_parameters`, `hilclaw.tools`, nothing else. No other module of the package imports it.
- `KIND_OPERATION_ANSWER_INVALID` is the string `operation_answer_invalid`, spelt once in the package; a name of ADR-0001, not in `hilclaw.tools.RESERVED_KINDS`, which is unchanged.
- `OperationAnswerInvalid(message)` - a direct subclass of `Exception`; neither a `ToolFailure` nor a `StepFailed`. `kind` is a class attribute, always the constant; `message` is an instance attribute, exactly a `str` (the constructor raises `TypeError` otherwise); `args` is `(message,)`. No attribute `spend`, no other attribute. `hilclaw.tools.ToolFailure(error.kind, error.message)` and `hilclaw.journaled_step.StepFailed(spend, error.kind, error.message)` can be built from every instance.
- `ask(operation, request, hw_profile, parameters, *, rtol, atol)` - four ordinary parameters, `rtol` and `atol` keyword-only, no default. It returns the `dict` that `hilclaw.check_answer.from_answer` returns, as it is.
- Before the call, in this order: `TypeError` when `operation` is not callable; `TypeError` when the type of `parameters` is not exactly `CheckParameters` (a plain tuple, a `dict`, an instance of a subclass included). The operation is then not called. The five values and the tolerance are not validated by `ask`.
- The call: `operation(request, hw_profile, parameters)`, three positional arguments, the same objects, once.
- What is caught: an `Exception` that is no `ToolFailure` out of that one call becomes `OperationAnswerInvalid`, whatever its class (a `NeitherFormError`, a `StepFailed` and an `OperationAnswerInvalid` an operation raises included; the real type decides, not `__class__`). A returned value of neither form becomes `OperationAnswerInvalid`.
- What passes through as the same object: a `ToolFailure` an operation raises, of any kind and of any subclass (re-raised with a bare `raise`; no `__cause__` added) - this is no rule of a record, and the docstring says that it is open (ADR-0045 decision 8; OD-18 sub-question 10, third clause); a `BaseException` that is no `Exception` (not caught at all); and everything `from_answer` raises other than `NeitherFormError` - for a value of the five or of the tolerance it refuses (`VerificationArgumentError` beside a report, `ValueError` / `TypeError` beside one of the two strings) - which is the caller's own part.
- The two lines: only the one call of the operation and the one call of `from_answer` are inside a `try`. The line between a raised error and a raised request to end is `Exception`.
- The message: one of a fixed set of constants built when the module is imported, so composing one calls no code of the answer and cannot raise. A returned value: "the operation returned W, which is neither a report nor one of the two conditions"; a raised error: "the operation raised W, which is no tool failure". W is a word of the module's own for a closed list of exact built-in types (values: `None`, `bool`, `int`, `float`, `str`, `bytearray`, `memoryview`, `list`, `tuple`, `dict`; errors: `TypeError`, `ValueError`, `KeyError`, `IndexError`, `AttributeError`, `RuntimeError`, `NotImplementedError`, `OSError`, `MemoryError`, `OverflowError`, `ZeroDivisionError`, `AssertionError`), matched with `type(x) is T`, and one word for everything else ("a value of another type", "an error of another class"). No type name is read (the task's option 2). Longest message under 120 characters. Nothing may depend on the wording; the tests pin only that the two ways differ and that nothing of the answer is in it.
- **Differs from the recommendation (1)**: `__cause__` and `__context__`. The exception is raised after the handler has been left, not with `from None` inside it, so both are `None` when `ask` is called outside a handler (inside a handler of the caller, `__context__` is the caller's own exception, never the operation's error).
