### The builder (`hilclaw/journaled_tool.py`)
- One public function that returns a tool function (one request in, one result out or a `ToolFailure`), ready for `Registry.register`. Recommended: `tool_function(step, numbers, data_root_source, check, perform)`:
  - `step`: the `step` name the tool's contract fixes (a *name*; checked when the function is built, not at a call).
  - `numbers`: those of `round`, `candidate`, `attempt` the tool's contract requires — "which numbers a tool requires is its contract". Recommended form: a tuple that is a prefix of `("round", "candidate", "attempt")`, the empty one included (the envelope rule "`candidate` only with `round`, `attempt` only with `candidate`" makes every valid set a prefix).
  - `data_root_source`: the data-root source the tool is bound to (ADR-0015 decision 3); asked through `hilclaw.data_root_source.obtain` only.
  - `check`: the tool's own check of the members of its request beyond the five; it raises `ToolFailure` of kind `invalid_request` to refuse. It is called with the request, before the data root is asked.
  - `perform`: the step. Recommended: called as `perform(data_root, request)`, returning `(spend, result)` or raising `hilclaw.journaled_step.StepFailed`, exactly as the `step` callable of `journaled_step.run` does.
  - A wrong argument of the builder (a `step` that is no name, `numbers` of another form, a value that is not callable) raises `TypeError` or `ValueError` when the function is **built**: a defect of the tool's author, not a tool failure. Building calls neither the source, `check` nor `perform`.
- **A call of the returned function, in this order:**
  1. **The request is checked; any refusal is a `ToolFailure` of kind `hilclaw.tools.KIND_INVALID_REQUEST`** whose message names the member: `run_id` missing or not a `run_id` (`hilclaw.layout.check_run_id`); `execution` missing, not an `int` (a `bool` is not one), below 1 or above the largest integer; a required number missing; a number that is not a valid envelope number, or `null`; `attempt` without `candidate`, `candidate` without `round`. The existing checks are reused (`layout.check_run_id`, `journal.step_identity`) and their `InvalidPathValueError`, `JournalError` and `InvalidEventError` are turned into `invalid_request`, chained to the cause; no second copy of a rule is written. Then the tool's own `check` runs. The request is not modified.
  2. **Only then the data root is asked**, once, through `data_root_source.obtain(source)`; its `no_data_root` passes through.
  3. The identity is `journal.step_identity(step, execution, …)` of the tool's `step` and the request's `execution` and numbers — nothing of it comes from the tool layer, a clock or a random source.
  4. `hilclaw.journaled_step.run(data_root, run_id, identity, …)` carries out the step: `perform` is called only for an identity with no line. What `run` returns is returned; what it raises passes through unchanged — the `ToolFailure` of an ended step with a `failure`, `step_open`, and every other exception (see sub-question ④ below).
- **Nothing is read from or written to the data plane and no resource is consumed before step 1 has passed**, and for a refused request neither the source, `perform` nor any file is touched ("the refusal is therefore the same on every machine and leaves no trace").
- **No way around**: the module exposes no function that calls `perform` without `journaled_step.run`, the returned function holds `perform` privately (a closure), and `perform` is not registered. Nothing is kept between calls (ADR-0010 decision 7): no cache of the data root, of a state or of a result.
- `hilclaw/journaled_tool.py` registers nothing and names no real tool, `step` value, axis or result member. It imports from `hilclaw` only `data_root_source`, `journal`, `journaled_step`, `layout`, `tools` (and `events` for its error class if needed); it reads no configuration itself.

### Sub-question ④ stays open (do not decide it)
- For a run that cannot be used — no run directory, no `STATE.json`, an invalid or unsupported `STATE.json`, a damaged log, a stored position beyond the log — what `journaled_step.run` raises (`MissingStateError`, `InvalidStateError`, `UnsupportedVersionError`, `CorruptEventsError`, `PositionBeyondLogError`, `OSError`, …) **passes through the tool function unchanged**. The module catches none of them, maps none to a kind, adds no kind and no constant for it. Through `tools.call` such a call is a tool failure as every exception of a tool function is.
- `invalid_request` is for what the request itself shows without reading anything. A well-formed `run_id` that names no run is **not** `invalid_request` (it is found only by reading).
- The docstring states this in one or two sentences as a limit, naming OD-18 sub-question ④.

### Public API as landed
- `hilclaw/journaled_tool.py` (new, 128 lines). One public name:
  - `tool_function(*, step, numbers, source, check, perform)` -> the tool function of a journaled tool (`function(request)` -> `dict`), ready for `Registry.register`. All five are keyword-only and required.
    - `step`: the `step` name of the tool's contract.
    - `numbers`: a `tuple`, a prefix of `("round", "candidate", "attempt")`; `()` for none.
    - `source`: the data-root source (a callable without arguments), asked through `hilclaw.data_root_source.obtain` only.
    - `check`: called as `check(request)` after the five members are checked and before the data root is asked.
    - `perform`: called as `perform(data_root, request)` with a `pathlib.Path` and the request object the caller gave, only for an identity with no line; returns `(spend, result)` or raises `hilclaw.journaled_step.StepFailed`.
    - Building raises `ValueError` for a `step` that is no name (the `JournalError` of `journal.step_identity`) or `numbers` that is no prefix, and `TypeError` for `numbers` that is no `tuple` or a part that is not callable. Building calls none of the three.
  - A call of the returned function: (1) the request is checked — a `dict`; `run_id`, `execution` and the required numbers present; no number the contract does not require; no required number `null`; then `layout.check_run_id` and `journal.step_identity`; then `check(request)`; (2) `data_root_source.obtain(source)`, once; (3) `journaled_step.run(data_root, run_id, identity, lambda: perform(data_root, request))`. The `run_id` and the identity are the values checked in (1); the request is not read again for them after `check`.
  - Refusals are `ToolFailure(KIND_INVALID_REQUEST, message)`. Messages: `<member>: is required`, `<member>: is no member of a request of this tool`, `<member>: must be an integer, got null`, `the request must be an object, got <type>`, and the message of the reused check (`run_id: must be a str matching …`, `execution: must be an int from 1 to …`, `round: must be an int from 0 to …`), chained to its error.

### Provisional choices (the records leave them to the code task)
- One builder rather than a text in each tool function: the five members and the order are the same for every journaled tool, and only what the builder returns is registered.
- The name `tool_function` and five keyword-only parameters without a default: three are callables and easy to swap by position.
- The parameter is `source`, not `data_root_source`: the module of that name is imported there.
- `check` is required and may not be `None`: a tool function checks its own request (decision 2), so a tool with no member of its own says so with a check.
- `numbers` is a tuple that is a prefix of `("round", "candidate", "attempt")`: the envelope rule makes every valid set a prefix. Every number in it is required.
- A number the contract does not require is refused with `invalid_request`, also as `null`: the identity must not drop what the caller stated.
- A required number given as `null` is refused in this module: `step_identity` reads `None` as an absent number and a request never states `null`.
- No other member is looked at, `step` included: it is the own check's. A request carrying `step` does not change the identity.
- What `check` raises passes through unchanged: another kind is the tool's contract, another exception a defect that `tools.call` reports as `tool_crashed`.
- `perform` gets the request object the caller gave, not a copy: `tools.call` hands it over uncopied too.
- A request that is no `dict` is `invalid_request`: a direct caller gets the same answer as one behind `tools.call`.
- The message of a refusal is that of the reused check without the prefix `data.` of a line, so it starts with the member of the request.
- The identity is formed while the request is checked (it is the check), before the data root is asked: a pure computation, so the order a caller can observe is that of decision 5.
- A `perform` that raises a plain `ToolFailure` or another exception, returns no pair, or states a reserved kind with `StepFailed`: as `journaled_step.run` treats it; nothing was added.
- No criterion disagreed with a record.
