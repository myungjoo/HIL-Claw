### The three kernels (ADR-0003 decisions 2, 4, 5, 7)
Each is small, deliberately unoptimised C99, defines `hilclaw_gemm` and no `main`, needs only the C library, builds without a diagnostic under `-std=c99 -Wall -Wextra -Wpedantic -Werror -O2`, **runs to completion for every input** (no crash, no exit, no output on the report channel - a broken run shows nothing, decision 4) and writes every element of `c`. One short header comment per file says which state it is and that it is calibration test data of ADR-0003, not a reference, a baseline or a catalog entry.
1. **Conforming**: computes the product C = A·B of ADR-0008 (plain triple loop).
2. **Failing**: "computes something else on every input". Its wrong output must lie outside the tolerance for every draw, not merely with high probability if a choice that guarantees it is as simple. Recommended: every element of `c` is set to `(float)k + 1.0f` - ADR-0017 decision 3 bounds every exact element of the product by `k` in magnitude, so no element can be within a small tolerance. It must also fail the functional test.
3. **Violating** (class V1, threat B (1)): "is right on the fixed inputs of the functional test and wrong elsewhere". Recommended form, the literal hard-coded output: the kernel ignores `a` and `b` and writes a constant table that is the product for **one known draw** - the shape, the seed and draw 0 that the functional test of the test file uses - and is written for that shape (for another `m`, `n` it still writes every element, with anything). The table constants are computed once by the executor with `verification_arrays.draw_inputs(m, k, n, seed=<known seed>, draw=0)` and `verification_arrays.reference(a, b)`, rounded to binary32, and committed as C99 hexadecimal floating constants or bit patterns (state in `## Result` the exact snippet that produced them, so they can be regenerated). An equally acceptable form is a kernel that recognises the known inputs (bit patterns of a few elements) and computes the product only then; choose one and say why. The kernel must not read the seed from the process, a file or the environment.
- No kernel for any other class (ADR-0003 decision 3 table), none that is "right only at known shapes" (OD-16 sub-question 1 is open), none for a second dtype, layout or language.

### The tests (`tests/harness/test_calibration.py`; ADR-0017 decision 8)
All of them use real clang (fixture as in `tests/harness/test_verification_build.py`: skip when `os.name != "posix"` or clang is absent; `pytest.fail` when `GITHUB_ACTIONS == "true"` and clang is absent). Write this file's own fixture; import nothing from another test module.
- **Build**: each kernel is built once per session with `verification_build.build_verification_executable(<kernel file>, <output in a tmp directory>, timeout_s=..., flags=...)` with the tests' own flags (recommended `-std=c99 -Wall -Wextra -Wpedantic -Werror -O2`, as the other harness tests); `result.ok` is asserted with `result.log` as the message.
- **Two kinds of run**, both `verification.run_verification(<executable path>, m=..., k=..., n=..., draws=..., seed=..., rtol=..., atol=..., timeout_s=...)` at one small non-square shape (the one the violating kernel's table is written for):
  - the **functional test**: the seed is a constant written in the test file (inputs the author of a kernel can know) - with `draws=1` if the violating kernel holds one draw;
  - the **contract run**: the seed is taken at run time (for example `secrets.randbits(64)`), is not the known seed, and appears in the assertion message so that a failure can be reproduced; `draws` is the test's choice (at least 1). The test never selects or filters a seed to make a kernel fit (ADR-0003 decision 4) beyond excluding the known seed itself.
- **Assertions** - for every run first `result.broken is None` (a completed run; with `result.run.stderr` and `result.run.returncode` in the message), then the verdict only (ADR-0003 decision 4; do not assert a cause or per-element indices; the per-draw `counts` may be shown in a message):
  - happy: conforming -> functional test `PASS`, contract run `PASS`;
  - negative: failing -> functional test `FAIL` and contract run `FAIL`;
  - negative, **both halves shown** (ADR-0003 decision 2): violating -> functional test `PASS`, contract run `FAIL`. The two halves are either one test or two tests named so that the pair is obvious; without the first half the third state is a second failing kernel.
  - branch: the contract run of each kernel with more than one draw (a completed run has no partial verdict: the violating and the failing kernel fail, the conforming one passes).
- **Tolerance**: every run passes `rtol` and `atol` explicitly, the same pair for the functional test and the contract run (ADR-0003 decision 7), with `atol` > 0 (ADR-0017 decision 5, the observation on cancellation). Recommended `rtol=1e-5`, `atol=1e-3` (the values the real-kernel tests of T-0061 / T-0062 use). They are test values, not tolerances of the harness; say so in a short comment or the test name, not in a long one.
- Keep the file small and quick: three builds, about six to nine runs at a small shape, no timeout case. No test of the fixtures themselves, of the clang fixture or of any helper (test rule 5). No test here repeats what `tests/harness/test_verification.py` already covers (report form, broken conditions, argument errors).
