### The tool functions (ADR-0039 decisions 3 to 6)
- `hilclaw/blob_tools.py` provides what `default_registry` needs to register the two tools bound to one data-root source (recommended: one public function such as `definitions(data_root_source)` or `register(registry, data_root_source)`, plus the public constant of the kind `blob_unreadable`; the form is the task's choice). The two tools do the same thing and may be one piece of code; they stay two tools with the names `blob.push` and `blob.fetch`.
- **Request**: exactly one member, `sha256`, a `str` of exactly 64 characters of `0`-`9`, `a`-`f`. Refused with a `ToolFailure` of kind `invalid_request`, **before the data-root source is asked and before anything is looked at**: no `sha256`; a `sha256` that is not such a string (uppercase, another length, a prefix such as `sha256:`, a trailing newline, a non-string such as a number, `null`, a list or a bool); any other member beside it (`run_id`, `round`, `candidate`, `attempt`, `execution` included). Nothing is normalised. Mind that `re` `$` matches before a trailing newline; use a full match.
- **Data root**: obtained through `hilclaw.data_root_source.obtain` from the bound source at each call, after the request was checked; its `no_data_root` failure passes through unchanged. The source is not called when the registry is built, and its answer is not kept between calls.
- **Result** (a new `dict` with these members and no other): `sha256` (the request's value), `present` (`bool`), and `intact` (`bool`) only when `present` is true - left out otherwise, never `None`.
  - `present` true: the look found a regular file at `hilclaw.cas.blob_path(data_root, sha256)`, symbolic links followed, and the file was still there when the call read it. `intact`: whether the SHA-256 of the content this call read equals `sha256`; every call that finds a file re-hashes it (read in chunks, not the whole file at once).
  - `present` false: the file system answers "no regular file is there" - the place holds nothing; `blobs/`, `blobs/sha256/` or the `<hh>` directory does not exist; a part of the path is no directory; a symbolic link that leads nowhere; the place holds something that is no regular file (a directory); or a file the look found is gone when the call comes to read it (`FileNotFoundError` at the open).
- **Tool failure `blob_unreadable`** (the pair's own kind, not in `tools.RESERVED_KINDS`, not added to it): the look or the read failed in the file system for any other reason (no permission, a loop of links, an I/O error). The message names the hash and the reason; its text is the task's.
- **The look is made by the tool function itself, in a way that reports why it failed** (ADR-0039 Consequences, "Two things the code slice has to see to"): `Path.is_file()` / `cas.has_blob` answer false for every `OSError` and so cannot tell a failed look from "nothing there". Decision 4 is the rule, not `has_blob`. Which standard-library calls are used is the task's choice (for example `os.stat` with `FileNotFoundError` / `NotADirectoryError` as "not there", `stat.S_ISREG`, any other `OSError` as `blob_unreadable`); the re-hash may be handed to `cas.verify_blob` only after the function's own look, and a `BlobNotFoundError` raised then must be classified by decision 4 (by looking again, or by hashing without `verify_blob`). **If the property cannot be had with the standard library on a supported platform, report back in `## Result` (or BLOCKED) instead of weakening the answer silently.** Where a case is not named by the record (for example what the open raises on Windows when a directory replaced the file between the look and the read), follow the sentence "Every other failure of the look ... is the tool failure" and list the case in `## Result`; do not add a rule to the record.
- **A call writes nothing**: it creates no directory (not `blobs/`, not `blobs/sha256/`), stores, copies, moves, repairs and deletes nothing, reads and writes no `artifacts.json`, reads nothing under `runs/`, appends no event line, never runs `git`, starts no process and keeps no state between calls. The module does not import `hilclaw.artifacts`, `hilclaw.journaled_tool`, `hilclaw.journaled_step`, `hilclaw.hw_tool`, `hilclaw.backends` or `subprocess`.
- **Input schema** of both definitions, exactly: `{"type": "object", "properties": {"sha256": {"type": "string", "pattern": "^[0-9a-f]{64}$"}}, "required": ["sha256"], "additionalProperties": false}`. (Whether Claude Code accepts each keyword is ADR-0015 F14 and waits on T-0106 / HQ-0006; do not reduce the schema here.)
- **Descriptions**: one for each tool, the task's text; each says that in this implementation the tool looks at the local store only, copies nothing, and what the three result members mean. They do not promise a remote store, a backup or a transfer, and state no rule on who may call the tool.
