## Why
PLAN P1-1 ("FR-10 도구 계약 인터페이스 + mock 백엔드 + 백엔드 적합성 테스트") has on `main` the whole path of a journaled HW tool over a backend and the reader of the hw_profile of a run (`hilclaw/journaled_tool.py`, `hilclaw/hw_tool.py`, `hilclaw/instance.py`), and one point of the frame is still open in all three: **what a call answers when the run its request names cannot be used.** ADR-0015 registered it as OD-18 sub-question 4, and two later records added situations to it without answering it:

- ADR-0015 decision 7 (Limits): "**A run that cannot be used** - no valid `STATE.json`, a damaged log - is a tool failure (ADR-0010 decision 4) whose kind this record does not fix (sub-question 4)." Boundaries: "4 what a call answers for a run that cannot be used - no valid `STATE.json`, a damaged log, a stored position beyond the log - and whether the frame reserves a kind for it (with OD-10 and the code slice of the journaled path)."
- ADR-0016 decision 4: "A hw_profile that cannot be read or is no valid record is not `no_backend`: the run cannot be used, and that kind is open (sub-question 4 of ADR-0015)."
- ADR-0018 decision 4: "**Situations in which the hw_profile of the run cannot be had**: the file is missing; it cannot be read; it is invalid by decision 2 ...; its `schema_version` is an *integer* other than `1`. In each the call has not started the step ... and it is not `no_backend`. **Which tool-failure kind such a call answers is not decided**: it is sub-question 4 of OD-18, which these situations join."

**What the code does today** (T-0055, T-0064 and T-0067 `## Result`): none of the three modules catches or maps anything for such a run. The exceptions pass through the tool function unchanged - `hilclaw.run_journal.MissingStateError`, `hilclaw.run_state.InvalidStateError` and `UnsupportedVersionError`, `hilclaw.events.CorruptEventsError`, `PositionBeyondLogError` and `UnsupportedVersionError`, `hilclaw.instance.MissingInstanceError`, `InvalidInstanceError` and `UnsupportedVersionError`, `hilclaw.keys.InvalidRecordError` from `backends.select`, and an `OSError` of the file system - and `hilclaw.tools.call` reports each as the reserved kind `tool_crashed`, whose reserved meaning is "the tool function raised something that is no tool failure" (ADR-0015 decision 2: "the tool is defective"). A caller cannot tell a missing or damaged run from a defect of the tool layer, and every test of these paths was told **not to pin** the kind. The conformance tests of P1-1 (ADR-0018 Consequences: "Their kind stays unpinned until sub-question 4 is answered") and the contract of the first HW tool wait for the answer.

DRIVER §6: a task that needs a design-level decision carries the record that closes it; the route used so far is two tasks (record, then code). **This task writes the record**, ADR-0019. It ticks **no PLAN checkbox** (P1-1 and P1-8 stay open).

Planner's judgements (2026-10-08 UTC, from the files; the reviewer is asked to re-check each):
- **Design-level, not owner-only.** The question is a part of the frame every tool contract shares (ADR-0015 decision 2: the table of reserved kinds is "the part of every tool's contract that is common, not a closed list", and ADR-0016 already added two kinds to it by the same route). It is none of DRIVER §9's owner-only items (#5 A / B items, C-6, OD-25, OD-3). That such a call is a tool failure is already fixed (ADR-0015 decision 7); open is only which kind, reserved or not, for which situations, and where it is given.
- **"With OD-10" does not make it wait for the owner.** OD-10 (the failure and recovery model of a board; it needs #5 B-2) is about what is done after a fault at a target. This record says what a call **answers**; what anybody does on that answer - repair, a restart, a further `execution`, a health check - stays with OD-10, the retry part of OD-17 and the layer-1 tasks of P2, and is a boundary of the record.
- **The inputs are complete on the code side**: the exception classes above, one per situation, are listed in three `## Result` sections. The reviewers of T-0067 added a caveat the record must face: a data root that vanished after the source answered and a file that disappears between the check and the read are also `FileNotFoundError`, so "cannot be read" cannot be told from the other situations by the class `OSError` alone.
- **OD-18 sub-question 7** (which of the four HW tools the `cpu_standin` backend offers) was the other candidate. It was not chosen now: ADR-0016 itself marks it "an HQ if it needs the owner's reading of #5 A-7", while sub-question 4 needs no owner item and is selectable (DRIVER §6: prefer the item that can be carried out).

Why this item now: no lock, no unresolved HQ, no TODO / INTERRUPTED / IN_PROGRESS / BLOCKED task file and no open PR at planning time (`main` at `b966e76`). The only unchecked item of the current phase (P0.5) is P0.5-4, whose rest is the owner's hook registration: the driver may not edit `.claude/settings.json` (DRIVER §1-5), so no task can be made of it; P1 items are selected across the phase boundary (DRIVER §6). P1-1 is the first unchecked P1 item, and this record is the first follow-up of T-0067 and the note of the last journal entry. The last comment on #5 is the ADR-0018 notice (https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6057754907); no objection to ADR-0001 to ADR-0018. Issues #4 (last comment 2026-07-31), #7 (2026-09-07) and #8 (2026-10-03) hold nothing newer about OD-18.

## Acceptance Criteria
What is **fixed** and taken as input, not re-decided:
- A call for a run that cannot be used is a **tool failure** (ADR-0015 decision 7; the form is ADR-0010 decision 4). The reserved kinds as they stand and their meanings (ADR-0015 decision 2, ADR-0016 decision 3): `invalid_request`, `no_data_root`, `step_open`, `tool_crashed`, `bad_result`, `no_backend`, `not_offered`. A later record of the frame may add to the common part "as long as no tool's contract uses the name, and none exists" (ADR-0016 decision 3).
- The order of a call (ADR-0015 decisions 2 to 5; ADR-0016 decision 2): the request, the data root, the lookup, the selection, the start line, the step, the end line. An ended or an open identity is answered from the log; a call that fails in the selection has not started the step.
- What makes each file invalid, missing or of an unsupported version: `STATE.json` (ADR-0012), `events.ndjson` (ADR-0006; a torn tail is skipped and is no damage), `instance.json` (ADR-0018). Nothing is repaired by a reader. Nothing is kept between calls (ADR-0010 decision 7).
- The situations registered with sub-question 4: no valid `STATE.json`, a damaged log, a stored position beyond the log (ADR-0015); a hw_profile that cannot be read or is no valid record (ADR-0016); the four of ADR-0018 decision 4.

What the ADR **decides**. The content of each decision is the executor's to work out and justify from the fixed inputs; the reviewer's Approve confirms it. For every point give the choice, the alternatives considered and one or two lines of reason; mark each value as **cited** or as **this record's own**:
1. **Scope and the term**: what "a run that cannot be used" means for a call of a tool about a run - a property found **at that call**, from the files the call reads, not a state that anything stores. List the situations it covers, each against the record that defines it, and say which are found before the lookup can answer (so that an ended identity is not answered either) and which only in the selection.
2. **Whether the frame reserves a kind, and how many.** Weigh at least: (a) no reserved kind, each tool names the situations itself; (b) one reserved kind for every situation, the message saying which; (c) more than one, split by what a caller can do - for example a run of which no record was written (a wrong `run_id`, or a run not started yet) against a run whose files are damaged, against a file of a version this source does not read (OD-11); (d) the situations stay `tool_crashed`. Apply the test ADR-0015 decision 2 and ADR-0016 decision 3 gave for reserving and for splitting: can a caller tell the cases it must act on differently, in the same way for every tool. Give each kind a name (check that no reserved kind and no name in `hilclaw/` collides) and a one-line meaning in the manner of the two tables.
3. **Which situation gets which answer** - a table over the situations of point 1. For each: the kind; what has been read, written and consumed when it is raised (planner's reading of the code: files of the run were read, nothing was appended, no backend was selected or called, the step did not run - verify it per situation, in particular a failure **inside** the append of the start or the end line, which `journaled_step.py` describes as leaving the identity with no line, open or ended); and whether the same request can be repeated once the cause is gone, with the same `execution`.
4. **The borders to the existing kinds**, each stated as a rule or left open with the exact question:
   - `no_data_root`: a data root that is an existing directory when the source is asked and is gone at a later read of the same call (the T-0067 reviewers' note).
   - "Cannot be read": an `OSError` of the file system that is not "missing" (permissions, an I/O error) - a property of the run, of the machine, or a defect; and that `FileNotFoundError` alone does not tell a missing data root, a missing run and a file that vanished between the check and the read apart.
   - `invalid_request`: a well-formed `run_id` that names no run is not a refused request (ADR-0015 decision 2: a refusal reads nothing and is the same on every machine) - confirm or correct.
   - `tool_crashed`: what stays a defect - for example a reader handed to `hw_tool.tool_function` that returns what is no valid record although the file was valid (`keys.InvalidRecordError` from `backends.select`), or raises something that is no situation of point 1.
   - `step_open`, `no_backend`, `not_offered`: unchanged; say in which order they and the new answer can occur for one call.
5. **Where the answer is given**: below the fronts (ADR-0010 decision 3: a front holds no check) and, as far as the record must fix it, at which level - the tool function of a tool about a run, or `tools.call` for every tool. Planner's reading: fix the **property** (a tool about a run answers these situations with the kind, through both fronts alike, and no situation of the table reaches a caller as `tool_crashed`) and leave to the code task how the exception classes are mapped, as ADR-0015 decision 5 did for the journaled path; confirm or correct. Say whether the rule holds for every tool whose request carries `run_id` or for a journaled tool only (ADR-0016 decision 4: the request of a HW tool about a run carries `run_id` whether or not it is journaled; no tool exists yet).
6. **What the message carries**, only as far as a rule is needed: for example that it names the file by its path relative to the data root and the broken rule, as the readers already do. Do not define a new member of the error object (ADR-0010 decision 4 fixes its form) unless you argue that the form allows it; an added member is a change of ADR-0010 and is out of scope.
7. **Consequences**, not decisions: the code slice that can now be cut within the size cap (the kind or kinds beside the seven of `hilclaw/tools.py`, the mapping in the path of a journaled tool and of a HW tool, the tests that today assert "none of the reserved kinds" and can then pin the kind; which docstring sentences change - `hw_tool.py` lines 34-37, `journaled_tool.py` and `journaled_step.py` where they name sub-question 4, `instance.py`); what the conformance tests of P1-1 gain.
8. **Limits**: what the record does not protect against, in the manner of ADR-0015 decision 7 and ADR-0018 decision 6 (two fronts with two sources can judge one file differently; a file that changes between two reads of one call; a damaged line before the stored position is not interpreted and so not found; a caller that names another run; nothing repairs or marks the run).

1. **Scope and the term.** The record is about a call whose tool function carries out the lookup of a journaled tool or the selection of a HW tool about a run. The **frame files** are `STATE.json` and `events.ndjson` (read at the lookup) and `instance.json` (read at the selection). "A run cannot be used" is a property found at that call, from what that call reads; nothing stores it. Not a situation: a torn tail, a missing or empty log (unless the stored position is beyond it), an unknown top-level member. A situation of `STATE.json` or of the log is found before the lookup can answer, so an ended or an open identity is not answered either; a situation of `instance.json` is found in the selection only (for a journaled tool: for an identity with no line).
2. **Four reserved kinds** (not one, not three, not `tool_crashed`): `run_file_missing`, `run_file_unreadable`, `run_file_invalid`, `run_file_unsupported`. Each also says that **this call** appended no line, selected or called no backend, did not run the step and consumed nothing; a kind raised at the lookup does not say whether an earlier call ran the step. Why reserve: the situations belong to no tool, `tool_crashed` says the tool is defective and it is not, and a kind each tool named could also stand in the `failure` of an end line. Why four: split where the fixed records already say something different of each case (missing = nothing was written for the `run_id`; invalid = an error the reader reports and does not repair; another version "is not damage"; unreadable = not judged), not by what a caller does.
3. **The table** (below), what was read at each moment, and that the same request with the same `execution` is answered later as if the failed call had not been made.
4. **Borders.** A well-formed `run_id` that names no run is `run_file_missing`, not `invalid_request`. `no_data_root` is the answer of moment ② only: a data root gone at a later read of the same call is `run_file_missing`. For `STATE.json` and `instance.json`, "not there" is `run_file_missing` at whatever read it is found; a log that is not there below an existing data root is no situation by itself; every other file-system failure at the read of a frame file is `run_file_unreadable`, so the class `OSError` alone does not decide the kind. `tool_crashed` stays the answer for an exception that is no tool failure and none of these situations. Order of the kinds for one call: `invalid_request`, `no_data_root`, a situation of ③, the stored result or `failure` or `step_open`, a situation of ④, `no_backend`, `not_offered`.
5. **Where.** Below the fronts, in the tool function, at the lookup and at the selection. The property is fixed (no such situation reaches a caller as `tool_crashed`, alike through both fronts); how the classes are mapped is the code task's. Not in `tools.call` by class: that level does not know the moment, and the same classes can come out of the step or of an append. Every tool function that carries out the lookup answers the rows of ③; every one that carries out the selection for a call about a run answers the rows of ④, journaled or not.
6. **The message** names the frame file by its path relative to the data root and says what was found; no member is added to the error object; a caller tells the cases by the kind.
7. **Limits**: nothing repairs or marks the run; found only in what a call reads (damage before the stored position is not found for an identity of the stored round, and is found for every other identity, so one run can answer one request and refuse another); two processes with two sources can judge one file differently; a stored `result` nested too deeply to copy at the lookup still arrives as `tool_crashed`; a file that changes during a call; a step or tool that states one of the four kinds for something else.
