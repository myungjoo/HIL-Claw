## Why
PLAN P1-1 ("FR-10 도구 계약 인터페이스 + mock 백엔드 + 백엔드 적합성 테스트") has its two fronts and its library parts on `main`, and **no tool**: `hilclaw.tools.default_registry()` is empty. Five planners in a row (T-0038, T-0039, T-0048, T-0049, T-0051 Follow-ups) wrote the same sentence: the mock backend and the first tool wait "once a tool has a fully decided contract (how the data root and the identity reach a tool function, where a tool states its description and input schema)". Those points are common to every tool, were each left open by a record on purpose, and are what a code task would otherwise have to invent:

- **Description and input schema.** ADR-0010 decision 4: "A tool is listed with its MCP name, a description and an input schema (F8); the content of both is each tool's (P1-1)". `Registry.register(name, function)` carries neither; `hilclaw/mcp_front.py` lists every tool with `{"type": "object"}` and no description. T-0039 review F5: "the first tool slice must not ship with this placeholder".
- **The data root.** ADR-0010 decision 5: "A front obtains the data root as the existing loader gives it ... The modules below keep taking `data_root` from their caller ...; the front is that caller", while decision 2 says "A tool function takes one request and returns one result" and `tools.call(registry, name, request)` hands over the request only. Neither front calls `hilclaw.config.load_data_repo()` today (T-0038 and T-0039 left it "to the first slice that registers a tool that needs one — do not choose it here").
- **The run and the identity.** ADR-0011 decision 3: "The identity is **given by the caller** ... How a request carries it is the tool's contract (PLAN P1-1)". `hilclaw.journaled_step.run(data_root, run_id, identity, step)` exists and "is not a tool and not a hook: nothing registers or calls it".
- **Where the two step lines are appended.** ADR-0010 decision 6: "a check that must hold on every path has two possible places — a hook on the typed tool, together with no shell for the agents concerned, or the tool layer below the fronts. ... **Where a check or the append is placed is not decided here.**" ADR-0011 decision 2: "Whether the appending part of the tool layer is a hook or the code below the fronts is the rest of OD-18 and is not chosen here", with the observation in decision 3 that "a part that runs only after a call cannot carry it out alone". OpenDecisionProposals OD-18 registers it as open ("hook에 둘지 진입점 아래의 도구 계층에 둘지는 미결이다").

DRIVER §6: a task that needs a design-level decision carries the record that closes it; the route used so far is two tasks (record, then code). **This task writes the record**, ADR-0015. It ticks **no PLAN checkbox** (P1-1 stays open: a tool, the mock backend and the conformance tests remain).

## Acceptance Criteria
What is **fixed** and taken as input, not re-decided:
- ADR-0010 as it stands: one tool function per tool below the fronts, one JSON object each way, two fronts over one registry, a front that "holds no tool logic, no default, no check and no side effect" for a call that reaches a tool function, the names, result versus tool failure and the form of the error object, no list of kinds, decision 5 on configuration, decision 7 (no outcome depends on state a server process kept; no version member), the fixed tool set of the MVP (#5 A-12 point 3), standard library only.

ADR-0006 (line, envelope, append only). ADR-0012 decision 3. ADR-0004 decision 4 (the tool layer, never an agent, appends).
- FR-10 (the tool names; a contract independent of where a backend runs; a mock backend always present), C-3, C-7, NFR-6, NFR-7 ①, #4 §1 (no whole-directory scan at the entry of a turn).

What the ADR **decides**. The content of each decision is the executor's to work out and justify from the fixed inputs; the reviewer's Approve confirms it. For every point give the choice, the alternatives considered and one or two lines of reason; mark each value as **cited** or as **this record's own**:
1. **Scope and terms**: the part of a tool's contract that is the same for every tool of the registry — the frame — and nothing of any single tool. Reuse the terms of ADR-0010 decision 1 and ADR-0011 decision 1; add a term only where one is needed (for example "tool definition", "journaled tool").
2. **What a registered tool states besides its function**: the description and the input schema that ADR-0010 decision 4 requires in the list of the MCP front. Work out: (a) where they are stated — once, with the tool, below the fronts, so that neither front holds a text or a schema of its own (decision 3 of ADR-0010); (b) what the input schema is as a value (a JSON object in the sense of F8) and **whether anything checks a request against it**, where (not in a front), and by which means given the standard library only — alternatives to weigh at least: the schema is a description only and each tool function checks its own request; a named small subset of JSON Schema that the package checks itself; a full validator (a new dependency — the owner's, so name it only as a rejected alternative); (c) how a refused request is reported — it is a tool failure by ADR-0010 decision 4; whether the frame reserves a `kind` for it, and whether the two kinds `hilclaw/tools.py` already uses (`tool_crashed`, `bad_result`) become reserved by this record or stay conventions of the code (T-0038 follow-up); (d) whether the command-line front has a way to show the description and the schema to a person, or that this is left to the code task. The record fixes the form; the text and the schema of each tool stay that tool's.
3. **How the data root reaches a tool function**: reconcile ADR-0010 decision 5 ("the front is that caller") with decision 2 ("takes one request") and with the landed `tools.call`. Alternatives to weigh at least: a member of the request (the calling agent would choose the tree — say what that means for a hook and for candidate ① / ②, without choosing a candidate); a context given to the tool function beside the request; tool functions bound to a context when the registry is built; the tool function reading the configuration itself (contradicts "the modules below ... read no configuration"?). Work out: when the configuration is read (a command-line call is one process; an MCP server lives as long as its session — ADR-0010 decision 7 and F7), what a call answers when the configuration cannot be read or the data root is no directory (a tool failure of which form; for every tool or only for one that needs the tree), that tests and a person redirect a call with the two existing variables, and that the outcome of a call still depends on the data plane only. **If the choice gives a tool function more than the request, state explicitly how the record reads ADR-0010 decision 2** — ADR-0010 is not edited.
4. **How a request names the run and carries the identity of a journaled step**: whether the frame fixes common member names (for `run_id`, and for `round`, `candidate`, `attempt`, `execution`) or leaves the names to each tool; where `step` comes from (the tool's contract fixes it, or the request carries it) — the record lists **no value** of `step`; what `execution` is when the request does not state it, if that is allowed at all (ADR-0011 decision 3: "it is 1 unless a decision outside this record asked for a further execution"; decision 9: a caller that raises it by itself is not stopped — do not add a rule that stops it, name the limit); how an invalid run or identity is reported and that nothing is read or appended before that check (the order `hilclaw/journaled_step.py` already has is a convention of the code — cite it as such); and the limit T-0048 review F1 found (an identity about a round above the stored `round`): state it as a limit or as a refusal **only if** the fixed inputs carry it (ADR-0012 decision 3), otherwise leave it with sub-question ① of OD-17.
5. **Where the two step lines and the lookup of a journaled tool are carried out**: a hook around the typed tool, or the tool layer below the fronts (this is the open sentence of ADR-0010 decision 6 and ADR-0011 decision 2, for the journaled step only). Weigh at least: a `PostToolUse` hook alone (the proposal of OD-18 and the wording of PLAN P2-4; ADR-0011's observation); a `PreToolUse` + `PostToolUse` pair (a call through the command-line front is not seen — ADR-0010 decision 6; whether a hook can settle what a call returns; a `claude -p` child has its own hooks — F6); below the fronts, in the tool function or in the path every call takes to it (`hilclaw.journaled_step.run` is the landed library form). State what the choice means for both fronts being identical, for ADR-0010 decision 7, for the window "between the outcome and the completed end line" (ADR-0011 decision 2), and **what is left for P2-4** (which checks and which journaling of other events a hook may still do — not decided). The record does not say which tools are journaled beyond what the sources name, and does not make journaling a property every tool has.
6. **What follows for the conformance tests and for the mock backend** — as Consequences, not decisions: what a test can check of any registered tool with the frame alone (listed with a description and a schema in both fronts, the same outcome through both fronts, the three states of ADR-0011 decision 4 and the three death points for a journaled tool), and that what a backend is, how a tool selects one and what the mock injects are the next record's (with the first tool).
7. **Limits**: what the frame does not protect against (no access control — ADR-0010 decision 8; an agent that supplies a wrong identity; two calls at once — rest of OD-17; a tool that does not use the frame), in the manner of ADR-0010 decision 8 and ADR-0011 decision 9.
