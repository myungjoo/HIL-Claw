## Why
Three accepted records say what a timing sample is and how a kernel is called, and all three leave open **how a sample is actually taken**:
- ADR-0007 (OD-13) decision 2: a sample covers "the execution of the kernel on operands that are already prepared"; "How many calls of the kernel one repeat times is the harness design (PLAN P1-3) ... The clock, the mechanism that keeps the interval clean and the calling convention of a kernel are not decided here." Decision 6: "Whether the harness executes the kernel before the first timed repeat is its design."
- ADR-0008 (OD-6 / OD-4) fixed the calling convention (`hilclaw_gemm`, three caller-owned arrays) and lists under Boundaries: "The harness mechanism: linking, loading or a separate process, the driver program, how two kernels of one contract are kept apart, the timer, calls per repeat, reuse of inputs, how the arrays are allocated".
- OpenDecisionProposals OD-13 "하위 질문" ⑤ registers part of it: calls per repeat, whether repeats reuse the same inputs, an execution before the first repeat.

The pieces a timing run would be built from exist: `hilclaw/clang_build.py` (T-0013, builds what the caller's flags say), `hilclaw/local_run.py` (T-0019, runs one process under a time limit) and `hilclaw/harness/measurement.py` (T-0029, the stopping test and the summary). What is missing is the design that joins them, and a code task cannot write a C timing driver without choosing it. DRIVER §6 says that a task needing a design-level decision carries the record that closes it; the route used so far is two tasks (record, then module: ADR-0005 → T-0025, ADR-0006 → T-0027, ADR-0007 → T-0029). **This task writes the record**: ADR-0009, closing one part of the rest of OD-13 — sub-question ⑤ and the mechanism by which the samples of one measurement are taken from a C kernel of ADR-0008 at the `cpu_standin` execution point. It ticks **no PLAN checkbox** (prerequisite slice of P1-2 and of the timing half of P1-3).

1. **Scope and terms**: the record is about taking the timing samples of one measurement of one built attempt of a C kernel of ADR-0008 at `cpu_standin`; it is not the verification run, not an FR-10 tool contract and not a simulator or board mechanism. 4. **Calls per repeat** (OD-13 sub-question ⑤): one, a fixed number, or a parameter; "the same for every repeat of a measurement" (ADR-0007 decision 2) must hold. Consider the smallest first instance (M = 1) against the resolution of the clock.

6. **An execution before the first timed repeat** (sub-question ⑤; ADR-0007 decision 6): whether there is one, and that it yields no sample.
7. **Who runs the repeat loop and applies the stopping rule**: ADR-0007 decision 4 stops "at the first n" that meets the rule, inside "one uninterrupted sequence of repeats", and `stopping_state` is Python while the kernel is C. Choose and argue one design — for example the rule evaluated inside the driver program, the driver steered by the Python side during the run, or another — and show that it satisfies decisions 1, 3 and 4 of ADR-0007 literally (in particular: no sample of the measurement is dropped, and no repeat is taken after the stop is due unless the record argues why that is still the same policy). If no design satisfies ADR-0007 as written, do not bend it: return BLOCKED ("requirement unclear") with the exact conflict.
8. **What the driver program reports and how**: the samples in order, what else the Python side needs to tell a completed run from a broken one (exit status, a run that ends early), and the channel. Fix as little of the text form as the code task needs; it is an internal interface, versioned by the source commit (OD-11 confirmed part), and no data-plane field.
9. **Parameters and what stays the caller's**: which values the timing run takes from its caller (the dimensions, `n_max`, a time limit — `local_run` requires one — the build flags and thread settings) without choosing any of them. No flag, no language standard, no `-march`, no thread count and no time-limit value is decided.
10. **Limits**: what the mechanism does not show or protect against (a kernel that forges its timing, noise from other processes, the cost of process start being outside the interval but still spent), each with the place where it is decided.

### Decisions of ADR-0009 (`ARCHITECTURE/decisions/ADR-0009-od13-cpu-standin-timing-run.md`, 166 lines — 6 above the "about 120-160" of the task, inside the 300 LOC / 5 files cap; the reviewers of rounds 4-7 saw nothing to cut)
1. **Scope and terms**: the timing samples of one measurement of one built attempt of a C kernel of ADR-0008 at `cpu_standin`; terms *driver program*, *timing executable*, *timing run*, *Python side*.
2. **From source to a call**: the harness provides `main` in one C source under `hilclaw/harness/`; that source and all files of one kernel go through **one `clang_build.build` call** into one executable with the caller's flags (so the driver needs nothing beyond the C library — no `-lm` — and the flags must produce an executable); one kernel per executable keeps two kernels apart; the kernel runs in **a process of its own** via `local_run.run` (a crash or hang ends its own process and is bounded by the runner's limit). Explicit statement: no proposal of OD-14 is adopted or rejected.
3. **Timer**: `clock_gettime(CLOCK_MONOTONIC, …)` (`<time.h>`, POSIX.1-2008 Monotonic Clock option; the driver defines `_POSIX_C_SOURCE 200809L` itself); exactly the one kernel call between the readings; reported as whole nanoseconds plus `clock_getres`; elapsed, not processor time; POSIX only, no native Windows. Obtaining the quantity from the interval stays with OD-1.
4. **Calls per repeat**: exactly one, a constant (the smallest first instance reads a 16 MB weight array per call — estimated at 1 ms or more against an expected resolution of 1 µs or less; both are estimates). An interval of 0 ns breaks the run.
5. **Operands**: three separate `malloc` calls (only `float` alignment promised); `a` and `b` filled once by a deterministic generator in the driver from a caller-given seed, finite, magnitude in [0.5, 1) with either sign (no subnormal inputs or sums); no value written to a file; every repeat reuses the same arrays and values. No OD-16 defence adopted or rejected; verification inputs and the seed policy are left open by name.
6. **Before the first repeat**: exactly one untimed call, no sample, duration not read (first-call costs — page allocation of `c`, lazy binding, thread start — are what ADR-0007 decision 2 excludes). Adopting drop detection (OD-16 B ⑸) or steady-state labelling reopens it.
7. **Loop and stopping rule**: the driver runs the loop and evaluates the rule after each repeat, outside every interval, with `n_min` / `cv_max` passed from `measurement.py` and the caller's `n_max`; the *sample form* (`interval` or `reciprocal`) is a caller's parameter without default, so the rule is applied to the samples without choosing the quantity (OD-1). The Python side is the authority: it replays `stopping_state` on every prefix and accepts only on agreement; it never repairs by dropping or adding a sample. Shown against ADR-0007 decisions 1, 3, 4. `local_run.run` and `stopping_state` serve unchanged.
8. **Report**: lines on the standard output the process was started with — `resolution_ns <int>`, `interval_ns <int>` per repeat, `stop converged|not_converged` — flushed as taken; descriptor 1 is pointed at standard error before the first kernel call (`dup`, `dup2`), so a kernel that prints does not break its run and no obligation is added to ADR-0008. *Completed* = no timeout, exit 0, exact form, replay agrees; every other run is *broken* and yields no measurement (what is kept and what happens next: OD-10, OD-14). Not a data-plane file or field.
9. **Parameters**: dimensions, `n_max`, sample form, seed, run time limit, flags / trailing flags / compiler / build time limit / executable path, environment and working directory are the caller's; constants of the mechanism: one call per repeat, one untimed call, ns, magnitude range. No flag, standard, `-march`, thread count or time-limit value decided.
10. **Limits**: no protection against forged timing (the kernel shares the process); noise of other processes not removed; untimed cost still spent; the driver never reads `c` (the code task keeps calls observable without judging the output).
