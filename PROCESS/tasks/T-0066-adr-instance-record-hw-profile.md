ADR-0016 registered that as OD-18 sub-question ⑥:

- ADR-0016 decision 4: "**What the fixed inputs do not carry: where a run states its hw_profile.** `instance.json` holds "What the instance was started with" (ADR-0004 decision 1) and has no fixed member (PLAN P1-8). ## Acceptance Criteria
What is **fixed** and taken as input, not re-decided:
- FR-14 ④, UC-0, UC-1: a hw_profile is registered with its tool access information and **selected when an instance starts**. FR-13 and ADR-0004: the path `runs/<run_id>/instance.json`, one per run, "What the instance was started with; source commit (#5 A-1); layout version", written once at the start of the instance, immutable; the constraints of `run_id`; the tree gives no concurrency control and no atomicity.
- ADR-0001: the hw_profile record (key fields and attributes), its key and the name of its key directory; a record stored at `db/<hw_profile_key>/hw_profile.json` (ADR-0004 decision 5; ADR-0014 for how it is written); attributes may change under the same key (decision 5).
- ADR-0016 decision 4: the backend of a call follows from the `accelerator` of the hw_profile of the run the request names, **read from the data plane at each call**; nobody names a backend; the answer is the same through both fronts and depends on nothing kept.
- ADR-0002 decision 2: a spec carries the key name and the full record of the hw_profile, per coder call, composed by a role. ADR-0012: the frame of the runtime `STATE.json` (the model, not a rule for this file). NFR-7 ②: every persistent artefact has a `schema_version`. NFR-2 / NFR-7 ③ / #5 A-1 detail 3: `instance.json` records the source commit.

What the ADR **decides**. The content of each decision is the executor's to work out and justify from the fixed inputs; the reviewer's Approve confirms it. For every point give the choice, the alternatives considered and one or two lines of reason; mark each value as **cited** or as **this record's own**:
1. **Scope**: of `runs/<run_id>/instance.json`, the file as a whole and the statement of the hw_profile of the run; nothing else of the file. State that the file is not complete with this record and that a run cannot be started from it alone.
2. **The file as a whole**: the encoding and form (compare ADR-0012 decision 2 and say where this file differs because it is written once and never replaced); `schema_version` — its place, type and first value, and what it covers; **how a reader of this version treats a top-level member the record does not define** (the later records for the objective, the tolerance, the budget and the rest will add members: say whether adding one changes the version, and what a validator of today must do with a member it does not know — weigh at least "exactly the listed members" as ADR-0002 does for a spec, against "unknown members are carried and not interpreted"; compare sub-question ⑫ of OD-8, which is about a file that is rewritten and is not answered here); what a missing file and an empty file mean **only as far as the fixed inputs carry it** (ADR-0004 decision 1; ADR-0012 decision 2 left "when in relation to `instance.json`" to sub-question ⑩ — do not answer ⑩).
3. **Where a run states its hw_profile** (sub-question ⑥, first part): which file — `instance.json` or the `spec.json` of an attempt (ADR-0016 decision 4 names the reasons against the spec: it exists per coder call only and is a copy composed by a role; confirm or correct them) — and **in which member and in which form**. Alternatives to weigh at least: (a) the key name only, the record being read from `db/<hw_profile_key>/hw_profile.json` at each call (what a HW tool call then depends on: the knowledge tree of the same data root; `hilclaw.key_records.load_hw_profile` exists); (b) the full record embedded (the run is self-contained; the attributes `hw_source` / `label` may later differ from the stored record — ADR-0001 decision 5); (c) the key name and the full record together, as ADR-0002 decision 2 does for a spec, and then which of the two a reader trusts when they disagree. What must hold: the answer is the same through both fronts and at every call of a run; a finished run stays auditable (NFR-2); nothing in the request names it (ADR-0016 decision 4). Give the member a name and a type; say what a valid value is in terms of ADR-0001 (do not restate its field list).
4. **How a HW tool reads it at each call**, as far as it follows from point 3 and ADR-0016: which file or files are read, in which order relative to the lookup of the journaled path (ADR-0016 decision 2: the selection is ④, after the lookup and before the start line — cited, not changed), and that nothing is kept between calls. **Do not decide the tool-failure kind** of a run whose `instance.json` is missing, unreadable or not valid: that is OD-18 sub-question ④ (ADR-0015 Boundaries; ADR-0016 decision 4: "the run cannot be used, and that kind is open"). Say only which situations exist.
5. **The second and third part of sub-question ⑥**, only as far as the fixed inputs carry them: whether a run has exactly one hw_profile in this version of the file (FR-14 ④, UC-1 step 1), and that a call about no run has no rule (OD-26). If the inputs do not carry "exactly one", say so and leave the part registered as open.
6. **Consequences**, not decisions: the code slice that can now be cut within the size cap (a module for `instance.json` — validity of a content and the reader of the hw_profile of a run with the signature `hw_tool.tool_function` already takes — with its tests; whether writing the file belongs to that slice or to the instance-start task is said, not decided); which docstring sentences of `hilclaw/hw_tool.py` then change; what the conformance tests of P1-1 gain.
7. **Limits**: what the record does not protect against, in the manner of ADR-0012 decision 7 and ADR-0016 decision 6 (whoever can write the file changes the backend of a run; a file changed after the start although it is "immutable" — nothing enforces it; under alternative (a) a key record that is missing, or under (b) / (c) a copy that differs from the stored record; two runs, two hw_profiles, one data root).

### Decisions of ADR-0018 (`ARCHITECTURE/decisions/ADR-0018-od8-instance-record-hw-profile.md`, 157 lines; the whole change is 171 insertions and 12 deletions in the 4 files of `touchesFiles` — inside the 300 LOC / 5 files cap)
1. **Scope**: of `runs/<run_id>/instance.json`, the file as a whole and the member that states the hw_profile of the run. Every other member is not fixed; a file with only these members is not a complete instance record and no run can be started from it alone.
2. **The file as a whole** (the record's own, modelled on ADR-0012 decision 2): one JSON object, UTF-8 without a byte order mark, no member name twice; LF and a final line feed bind the writer; **no member order is fixed** (the file is written once, so there is no diff between two contents — the difference from ADR-0012). `schema_version` is a top-level member, the integer `1`, the version of the schema of this file (the embedded record carries its own). Required in version 1: `schema_version` and `hw_profile`. **The top level is open**: a reader does not interpret a member it does not know and does not treat it as an error; a validator of today checks the two members and the rules for the whole text. The version is raised when a defined member is removed, renamed or changed, a member is added inside `hw_profile`, a later record makes a member required, or a later record judges that a reader must not pass over its member. Why open and not "exactly the listed members" as a spec: every later record would be a new version before a first run exists, and reading another version is OD-11. Cost: a misspelt optional member is not detected and stays for the life of the run. A valid file is not thereby enough to start a run. An invalid file (an empty one included) is reported, no member of it is used, nothing is repaired; another integer version is "unsupported", not damage. A missing file means no instance record was written for this `run_id` (ADR-0004 decision 1) and nothing more.
3. **Where a run states its hw_profile**: `instance.json`, not the `spec.json` of an attempt (the two reasons of ADR-0016 confirmed — per coder call only, composed by a role; a third: ADR-0002 already treats the instance record as the source of `task.objective`). The member is **`hw_profile`**, required, a closed object with exactly `key` (the `<hw_profile_key>` directory name of ADR-0001 decision 3) and `record` (the full record of ADR-0001 decision 1, key fields and attributes, as the instance was started with). Valid when `record` is valid by ADR-0001 and `key` is the name derived from it; a disagreement makes the file invalid, so neither is trusted over the other (the form and rule of ADR-0002 decision 2 for the same section of a spec; ADR-0002 unchanged). Alternatives rejected: (a) the key only, the record read from `db/` at each call (every call would depend on the knowledge tree, a finished run would not hold the attributes it started with, a missing stored record would stop a started run); (b) the record only (works; the key costs one derivation and gives the join to `db/<hw_profile_key>/` and the form of a spec section); (c) with one side winning; reading and comparing the stored record at each call; a member of `STATE.json`.
4. **How a HW tool reads it**: the order of ADR-0016 decision 2 is cited and unchanged; in ④ the tool function reads `runs/<run_id>/instance.json` of the data root of the call and takes `hw_profile.record` as the hw_profile of the call; no other file is read for the selection and the stored record is not read or compared; nothing is kept between calls. A call answered in the lookup does not read the file **for the hw_profile** (whether a call reads it for another member, such as the layout version stamp, is that member's record). The same through both fronts and at every call **as long as** both fronts are given the same data root, run the same source, and the file is not changed. Situations listed **without a kind**: the file is missing; cannot be read; is invalid (empty, partial, a `hw_profile` that breaks decision 3); has another integer `schema_version`. Each is a call that has not started the step and is not `no_backend`.
5. **Second and third part of sub-question ⑥**: a version 1 file states exactly one hw_profile (the inputs carry one: FR-14 ④, UC-1 step 1, the glossary). Whether a run may ever hold more than one is **not decided**; a call about no run has no rule (OD-26). Both parts stay registered.
6. **Limits**: whoever can write the file changes the backend of a run; nothing enforces "immutable" (a file changed after the start is read as it is at each call); the embedded and the stored record can differ in attributes, and a run whose key has no stored record is not noticed by the selection; the target reached is not checked against the record; a caller can name another run; two processes can run two validators; a member passed over.
