## Acceptance Criteria
What is **fixed** and taken as input, not re-decided:
- **ADR-0004 decision 8**: a `run_id` matches `[a-z0-9][a-z0-9_-]{0,63}` and is unique within `runs/` of a data repository; every such value is a *string* of ADR-0002. Decision 9: layout version 1. Decision 1: a directory exists only when something was written into it. Decision 10 and C-2: P1 assumes one run; the tree gives no concurrency control.
- **#4**: `run_id` is the id of one Loop instance; owner and project are meta fields, not path levels; no whole-directory scan.
- **ADR-0013, ADR-0018, ADR-0025**: what a missing `STATE.json` / `instance.json` states; that either write may create the run directory; that the last step of the write of `instance.json` is not, by ADR-0025, the means of uniqueness; that the order of the two first files is open (sub-question 10).
- **#5 A-1 and A-3**: the data plane is a separate git repository; the durability boundary is the local commit.

What the ADR **decides**. The content of each decision is the executor's to work out and justify from the fixed inputs; the reviewer's Approve confirms it. For every point give the choice, the alternatives considered and one or two lines of reason; mark each statement as **cited** (with the record and the decision) or as **this record's own**:
1. **Scope: which ids the form applies to.** The form of an id **the system builds for a new run**. Decide and say plainly whether the form is also a rule of validity for every `run_id` - that is, whether a reader may refuse or must accept a name that meets ADR-0004 decision 8 and is not of the form. Planner's suggestion, to be weighed and not taken on trust: the form binds what builds an id and is no rule for a reader, so `hilclaw.layout.check_run_id`, every reader on `main` and every existing test literal stay as they are, and the layout version is not raised. **Whether a person may give a run a name of their own is not decided here** unless a requirement sentence carries it (the planner found none); name it as a boundary.
2. **How a new id is built.** The parts of an id, their order, their notation and the length, all inside `[a-z0-9][a-z0-9_-]{0,63}`; an example. Weigh at least: (a) a time part and a random part; (b) a random part only; (c) a running number obtained by listing `runs/` (weigh against two clones of one data repository and against #4 "no whole-directory scan" - listing one directory of known path is allowed by ADR-0004 decision 3, line 89); (d) an id derived from the content of the instance (weigh against ADR-0025: no canonical form of `instance.json` exists, and two instances with equal content are two runs); (e) parts that name the owner, the project, the hw_profile or the kernel (weigh against #4 "meta, not path" and against ADR-0001 keys already being directory names under `db/`). Say what an id **states** and what it does not: by which record is anything a reader may take from an id carried? Planner's suggestion: an id is opaque to every reader - nothing parses it, and no fact of a run (its start time included) is read from its name.
3. **Whether ids sort by time** (the third open point of ADR-0004 decision 8), and exactly what "sort" promises: in which order (byte order of the names), for whom (a person listing `runs/`; no component may depend on it, if point 2 keeps ids opaque), and under which premise (the clock of the machine that built the id; two machines; a clock set back). If a time part is chosen: which time (UTC), which notation, which resolution, and that it is no record of when the run started.
4. **What uniqueness rests on.** State the promise in the words of ADR-0004 ("unique within `runs/` of a data repository") and what this record adds to it: (i) what the form contributes - for a random part, how many bits and from what kind of source (a property: the operating system's randomness, not a seeded generator), and the order of magnitude of a collision under C-2 (one run at a time in P1) and across two clones of the data repository that are later brought together by git; (ii) **what the form does not give**: it is no check. Whether something looks at `runs/<run_id>/` before the first write, by which step a taken id is noticed, and what is done then are the start of an instance (sub-questions 10, 17, 23 (i)) - state this as open, cited, with nothing added. Say whether two runs started on two clones with equal ids (improbable) would be noticed by anything on `main` today (a git merge of the data repository) - as a limit, not as a rule.
5. **The sources as properties, not code**: the time comes from the clock of the machine that builds the id and is not trusted for anything; the random part comes from a source no caller seeds. Whether a caller may hand in the two (for tests) is the code task's.
6. **Limits**: an id built on a machine whose clock is wrong; two machines; ids that exist only in an uncommitted working tree (#5 A-3); a `run_id` not of the form (per point 1); nothing here makes two runs at once safe (C-2, OD-17).
7. **Consequences**, not decisions: the code slice that can now be cut within the size cap (a function of the package that builds an id of the form, probably a new small module with its test file, `check_run_id` unchanged unless point 1 says otherwise - where and how is the code task's); what becomes of `"run_id": "NOT-DECIDED-HERE"` in the example of ADR-0002 and of the open value of PLAN P1-5 (follow-ups for the integrator and the P1-5 task, not edits); which sentences of other records and docstrings become less exact (ADR-0004 decision 8 last sentence, ADR-0002 lines 47, 130 and 164, ADR-0012 lines 7 and 146, ADR-0025 lines 19, 53 and 122, `hilclaw/layout.py` lines 22 and 64) - named, not edited.
