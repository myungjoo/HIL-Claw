## Why
PLAN P1-1 (the FR-10 tool contracts, the mock backend, the conformance tests) is open. ADR-0062 (T-0195, landed on `main` as `02b35d1`) fixed the identity of a call of `sim.run` and `board.run`:

- decision 2: both tools are journaled tools;
- decision 3: "Each tool has exactly one `step` value: `sim_run_timing` for `sim.run` and `board_run_timing` for `board.run`"; the request carries no `step`; the value "follows from the tool and not from anything a request says" (decision 1);
- decision 4: a request of either tool requires the five members `run_id`, `round`, `candidate`, `attempt`, `execution`; "All three numbers are required"; no member states the point; the member list is not closed.

ADR-0062 Consequences, "Code slices that can now be cut": "the identity part of the run tools - the two `step` values and the check of the five members of decision 4 - with its tests, as `hilclaw/check_identity.py` is for the check." Checked on 2026-10-15 at `main` `35dae00`: neither `sim_run_timing` nor `board_run_timing` nor the name `run_identity` occurs in `hilclaw/` or `tests/`; no open PR.

**This task carries those values into the package as one small pure module**, the same kind of slice as T-0142 (`hilclaw/check_identity.py` for `correctness.check`) and T-0192 (`hilclaw/run_objective.py` for the run tools' objective). **It builds no tool function, no builder, no step, no registration, no identity object and no operation.** It ticks **no PLAN checkbox**: P1-1 stays open.

Planner's judgements (from the files at `main` `35dae00`, 2026-10-15; **the reviewer is asked to re-check each**):
- **Code over a landed record; no ADR needed (DRIVER §9).** The two values, which tool has which, the required numbers and the place where the five members are checked (the frame, in moment 1) are fixed by ADR-0062 decisions 3, 4 and 6 (with ADR-0015 decision 4, which it cites). This task decides only Python names, parameters, message texts and the treatment of a value that is no tool name. Nothing owner-only (#5 A/B items, OD-3, OD-25, C-6) is needed.
- **No tool's own `check` of the request.** Unlike ADR-0040, ADR-0062 names no member beyond the frame's five: they are checked by the frame (`hilclaw.journaled_tool`), and "what the tool function does with a member no record names" - a member `point` among them - is "a later slice's" (decision 4, Boundaries). So this module has **no** `check(request)` and looks at no request at all. It does not say that a member `point` is refused, passed over or meaningful.
- **The `step` follows from the tool.** The module may therefore offer the value of a tool by the tool's name (recommended `step_of(tool)` below). That is a rendering of decision 3 and no new rule; that it refuses `correctness.check`, `profiler.collect` and any other value is the module's own choice (those tools' values are not this contract's: ADR-0040 for the check; none for `profiler.collect`).
- **Which builder the tool functions use is not decided here** (ADR-0062 Consequences: `hilclaw.hw_tool.tool_function` takes one `step` but has no place for the answers of ADR-0061 decision 4; `stepped_tool_function` has both places and takes a tuple of `step` names). The module's constants must fit both forms (`STEPS` as a tuple; each value alone as a `str`), and it imports neither builder.
- **A-13 reading**: code mode. No new external dependency (`pyproject.toml` unchanged). "데이터 plane 스키마 변경" does not apply: no data-plane file is read or written, no line is built; ADR-0062 Consequences ("A-13 reading") holds the reading for the two `step` values themselves. A reviewer result starting with `SECURITY` is BLOCKED.
- **Why this item now**: no lock, no TODO / INTERRUPTED / BLOCKED task file, no open PR; the last comment on #5 is the ADR-0062 notice (issuecomment-6189063464). The other follow-ups of T-0195 (the result members, the timing seed) are document-mode slices that this code slice does not wait on and that do not wait on it.

### The module
Recommended public names, and no other: `STEP_SIM_RUN`, `STEP_BOARD_RUN`, `STEPS`, `NUMBERS`, `step_of`.

- **`STEP_SIM_RUN`** and **`STEP_BOARD_RUN`** - the strings `"sim_run_timing"` and `"board_run_timing"` (ADR-0062 decision 3), each spelt once in the package. **`STEPS`** - the `tuple` `(STEP_SIM_RUN, STEP_BOARD_RUN)`: the `step` values of the two tools, each once, in the order sim, board, an order that means nothing (the docstring says so; it is no list of one tool's values - each tool has one).

- **`step_of(tool)`** - the one `step` value of the run tool named `tool` (ADR-0062 decision 3: it "follows from the tool"): `STEP_SIM_RUN` for exactly `"sim.run"`, `STEP_BOARD_RUN` for exactly `"board.run"`.
  1. Any other value is refused with `ValueError` (recommended; another exception type is the executor's choice, stated): `"correctness.check"`, `"profiler.collect"`, `"sim_run"`, `"board_run"`, `"SIM.RUN"`, `" sim.run"`, `""`, the `step` values themselves. The docstring says the refusal of those tools is the module's own choice: their `step` values are not this contract's.
  2. A value whose type is not exactly `str` (a `str` subclass included) is refused with `TypeError` (recommended), **without calling any code of the value** (no `==`, `hash`, `str()` / `repr()` of it): an unhashable or hostile value gives that refusal and no other exception.
