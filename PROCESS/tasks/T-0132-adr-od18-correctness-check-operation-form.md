## Why
PLAN P1-1 (the FR-10 tool contracts, the mock backend, the conformance tests) is open: none of the four HW tools has a complete contract. `correctness.check` is the furthest. ADR-0021 fixed the split, the seed, the tolerance and the classes of outcome; ADR-0038 the execution points and that a run at the mock is answered by this contract; ADR-0040 the identity of a call; ADR-0041 the dimensions; ADR-0042 (T-0128) the members of a result. On the code side the judging (`hilclaw.harness.verification.judge_report`), the seed source, the result builder (`hilclaw.check_result`, T-0130) and the join from a judged report to a result (`hilclaw.check_judging`, T-0131) are on `main`.

What nothing fixes yet is the line those pieces meet at: **the form between the tool function and an operation**. ADR-0021 decision 2 gave it as classes only - what an operation is handed, "(i) the seed of the call; (ii) `draws` and the dimensions `m`, `k`, `n`; (iii) what it needs to obtain and run the verification executable", and what it returns, "(A) the report ... (B) that there is no such report, and which of two conditions failed" - and said: "The spelling of what is handed and returned is the second record's and the code task's". ADR-0042 decision 8 repeated it: "The four values of `condition` are values of a member of a result. They are not the spelling of what an operation returns ... and that slice is the backends'." ADR-0042 Consequences still lists "whether an operation is handed the point" among what the next slices must add.

**This task is the fourth slice: that form, for classes (i) and (ii) and for the answers (A) and (B), and nothing else.** It is the first item of the T-0131 follow-up for the planner. After it, a code task can write the part of the tool function that turns what an operation returned into a result (over `check_judging.from_report` and `check_result.broken`), and the slice of the mock (its operation of this tool and the default script) has the form a script is asked with and answers in.

The task ticks **no PLAN checkbox**: P1-1 stays open, and the tool still cannot be registered after this record.

### The form as landed (the code and the slice of the mock are written against this)

All of it is the record's own design (DRIVER §9); no sentence of the owner is used as a decision. Scope: a check (a call that reached moment 6) about one attempt of a run that ADR-0021 and ADR-0038 decision 6 cover and whose stated op_signature is covered, **carried out by an operation that runs on the host of the tool function or by an operation of the mock**. One form at both execution points. The record fixes no form for an operation whose target is another machine.

| Direction | What | Kind of value | Source |
|---|---|---|---|
| to the operation | the request | the request of the call, the member `point` in it | ADR-0016 decision 2; ADR-0040 decisions 4 and 5; ADR-0043 decision 3 |
| to the operation | the hw_profile of the call | the record of the run | ADR-0016 decision 2 |
| to the operation | **the check parameters**: the seed, `draws`, `m`, `k`, `n` | one value that holds exactly five integers and nothing else: the seed of the call (of the whole range of seeds the harness accepts), `draws` (at least 1), `m`, `k`, `n` (each at least 1) | ADR-0043 decision 2 (the classes (i) and (ii): ADR-0021 decision 2) |
| from the operation | (A) the report | a byte string: the bytes the process wrote on its report channel, in their order, none added, removed or changed. Every byte string is (A), also a short, long, malformed or empty one | ADR-0043 decision 4 |
| from the operation | (B) the condition | the string `"time_limit"` (the process did not end within its time limit) or `"exit_status"` (a non-zero status or a signal); compared as it is | ADR-0043 decision 4 |

- **An operation is called with three things**, and under the record nothing else crosses in either direction as a value handed or returned; only a record adds a row.
- **The five values are the ones the tool function judges with**; none is derived, rounded or replaced on its way.
- **How the two conditions are spelt**: `"time_limit"` and `"exit_status"`, the first two values of the member `condition` of a result (ADR-0042 decision 3), taken on purpose - they are the first two items of `hilclaw.check_result.CONDITIONS`. From ADR-0043 on the two spellings are tied.
- **How the two forms are told apart**: by the kind of value. A byte string is a report whatever its bytes are (the bytes `time_limit` as a byte string are a report of the wrong form); one of the two strings is a condition.
- An answer of the form (B) holds the condition and nothing else, one of the form (A) the report and nothing else: no exit status, no signal, no time, no command line, no standard error, and with (B) no byte of what the process wrote.
- **The execution point** reaches an operation as the member `point` of the request and in no other way (not in the check parameters; the request is not handed over without it). An operation may make where and how the kernel is carried out depend on it; the form of what it returns does not depend on it. Which target a call goes to stays #5 B-2 / OD-10.
- **An answer of neither form** (a returned value that is neither a byte string nor one of the two strings - `None`, a number, `"report_form"`, `"pass"`, a pair - or something raised that is no tool failure) **is never made into a result**: no pass, no fail, no broken, in particular no broken result with `"report_form"`. The tool function establishes which of the two forms an answer has before it uses it: it judges nothing but a byte string, and without judging it makes a broken result from nothing but one of the two strings. It establishes the form, not the truth. Not meant by "neither form": a tool failure an operation raises, and the death of the process while the operation runs.
- **Left to the code task** (the record says so by name): the Python type of the check parameters; by which name or position code reaches each of the five; whether the third thing is passed by position or by keyword and the name of the parameter (`seed`, `draws`, `m`, `k`, `n` are the words of ADR-0017 decision 9, not names of code); which Python types count as a byte string (observation: `judge_report` takes exactly `bytes`) and as a string; how the tool function tests for the two forms; what the code raises for an answer of neither form (what the *call* then answers is sub-question 15, not the code task's); when the tool function checks values its own judging would refuse (the upper bounds of the harness, 2^64 for the seed and `draws`, are observed and not adopted).
