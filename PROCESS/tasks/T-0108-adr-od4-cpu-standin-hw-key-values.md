- **ADR-0001 Boundaries, line 129**: "**How the values of the hw key fields are obtained** (onboarding, OD-26, and the task that registers `cpu_standin`): which components are members of `toolchain` (for example whether an OpenMP runtime is one), the form of version strings, the source and normalisation of the `host.cpu` and `host.os` strings, which optional `host` members a profile carries, what `revision` holds for hardware without a revision of its own, the `hw_source` of a stand-in, and who fills in the record (probing or by hand). What the ADR **decides**. The content of each decision is the executor's to work out and justify from the fixed inputs; the reviewer's Approve confirms it. For every point give the choice, the alternatives considered and one or two lines of reason; mark each value as **cited** (an owner answer or an earlier record - say which) or as **this record's own**:
1. **Scope**: the values of the key fields `revision`, `toolchain` and `host` (and what is said about the attribute `hw_source`) of a hw_profile whose `accelerator` is `cpu_standin`, for a stand-in that builds and runs the kernel on one machine. Say whether any rule is meant for other accelerators as well (the planner's expectation: none - a real accelerator's values are OD-26 and #5 B-1).
2. **Which machine the values describe.** The planner's expectation: the machine on which the kernel is built and run; for the local stand-in that is the machine the package runs on. Say what the record does not cover (a build on one machine and a run on another; a remote stand-in).
3. **`toolchain`: its members and the form of a version string.** Weigh at least: (a) `clang` only against further members - an OpenMP runtime, the C library, the linker - by ADR-0001's own wording ("every software component between the kernel source and its execution") and by its criterion (what changes measured performance), against what can be identified in the same way on Linux, macOS and WSL and against decision 5 (build settings such as flags and thread count are no key fields: whether a kernel uses OpenMP differs between candidates of one pair); (b) the string for `clang`: the whole first line of `clang --version` (what `clang_build.compiler_version` returns today) against a normalised version (for example the dotted number only), against the vendor and target as well (an Apple clang and an LLVM clang with the same number are different compilers) - name the cost of each for key stability and for telling two compilers apart; (c) what is stated when a component's version cannot be had. A value must be a *string* of ADR-0001 (1 to 255 printable ASCII characters): say what is done with a fact that is not.
4. **`host.cpu` and `host.os`: source and normalisation.** For each, the fact it is taken from on Linux, on macOS and under WSL, and the spelling rule (whitespace, case, characters outside printable ASCII, length). Weigh for `host.os` what "operating environment" must tell apart (a kernel release changes with every update and would start a new key each time; a distribution name and version; WSL against native Linux) against the criterion. Say whether a profile of `cpu_standin` carries further `host` members in the first instance (the planner's expectation: none unless argued - memory size, core count, frequency policy and SMT are candidates UC-0 and ADR-0001 name or imply; weigh at least core count) and name what is thereby not in the key.
5. **`revision`.** ADR-0001 requires it and asks "what `revision` holds for hardware without a revision of its own". Weigh a fixed word against a fact of the CPU (for example family, model and stepping, or a microcode revision) and against repeating `host.cpu`; say what the accelerator **is** for a stand-in in relation to `host` (the CPU is both), so that one fact is not required twice in two spellings without a reason.
6. **`hw_source`.** One of the outcomes named in `## Why` (stated by whoever registers and never probed; or `external`, argued; or left open by name). No handling per source is decided (OD-26).
7. **One spelling per machine.** State the property the rules are meant to give - two tools, or a tool and a person, that follow the record on the same machine at the same state arrive at byte-equal canonical forms - and the **limits**: what changes the key although performance does not, what leaves the key unchanged although performance may (BIOS and power settings, thermal state, co-running load, the flags of a build), a virtual machine or container that hides the CPU, heterogeneous cores. Decide none of them beyond naming them.
8. **Consequences**, not decisions: the code slice that can now be cut within the size cap (a function of the package that returns the hw_profile record of the local `cpu_standin` by these rules, a new small module with its test file, using `clang_build.compiler_version`, bound to no tool, no start and no registration; names and the return form are the code task's); what P1-5 still lacks after this record (`task.objective`, a technique); which sentences of other documents become less exact (follow-ups for the integrator: ADR-0001 decision 7 and Boundaries, ADR-0002 decision 8, ADR-0018 Example).
