### The capability (recommended signature)
`run(data_root, run_id, identity, step)` carries out the journaled step `identity` (a `journal.Identity`) of the run `run_id`, where `step` is a callable without arguments that performs the step. By ADR-0011 decision 3:
1. **The state first.** The state of the identity is established from the files of the run before anything is appended or run.
2. **No line** — the start line is appended (`kind` `step_started`; the envelope numbers of the identity that are not `None`; `data` exactly `step` and `execution`) and is complete **before** `step` is called; then `step` is called exactly once; then the end line is appended (`kind` `step_ended`, the same envelope numbers, `data` exactly `step`, `execution`, `spend` and exactly one of `result` and `failure`) as soon as `step` returned its outcome. The call returns the `result`, or raises the tool failure when the step ended without an outcome.
3. **Ended** — `step` is **not** called and **nothing is appended** (the log file is byte-for-byte unchanged). The call returns what the first end line holds: its `result`, or the same tool failure again (`tools.ToolFailure` with the `kind` and `message` of its `failure`).
4. **Open** — `step` is **not** called and nothing is appended. The call raises a tool failure (`tools.ToolFailure`) that reports that the step is open; its `kind` is a name chosen by this task (recommended `step_open`) and its message names the identity.

Fixed by the record and to hold in the code:
- **A first call and a repeated call give equal outcomes**: the result a first call returns equals what a later call with the same identity returns from the end line, and a failure has the same `kind` and `message` both times (decision 3; ADR-0010 decision 7).
- **An identity is never started twice** by this function: it appends a start line only in the state "no line", never raises `execution` and never derives an identity (decision 3: the identity is given by the caller).
- **The amounts are the caller's**: `spend` on the end line is what `step` stated, for a result and for a failure alike (decision 7). The function states no amount of its own.
- **Where the lookup reads** (decision 6, last bullet; ADR-0012 decision 3): when the identity's `round` equals the `round` stored in `STATE.json`, the stored view and the tail decide (`run_journal.step_state`, or the same public functions it uses). For every other identity — an earlier or later round, or no round — the log is read from its first line (`events.read` at position 0 with `journal.step_state` and `journal.EMPTY`). Assert both paths, in particular that **an identity of an earlier round that ended before the stored position is answered as ended and is not run again**.
- `STATE.json` is required as `run_journal.read_state` requires it: `run_journal.MissingStateError`, `run_state.InvalidStateError` and `run_state.UnsupportedVersionError` pass through, with nothing appended and `step` not called (what a run directory without the file means is sub-question ⑩ of OD-8 — not answered here).

### Cases the record leaves to this task — choose, implement, test and list each with one line of reason
- **How `step` states its outcome.** Recommended: it returns a pair `(spend, result)`; to end without an outcome it raises an exception type of this module that carries `spend`, `kind` and `message` (for example `StepFailed`). Another shape is fine with a reason, as long as **an end line is written only when `step` stated its amounts explicitly**.
- **Any other exception out of `step`** — a plain `tools.ToolFailure` without amounts included, and a `BaseException` such as `KeyboardInterrupt`: recommended that it passes through unchanged and **no end line is appended**, so the step stays open (the second death point: outcome and amount unknown). Writing an end line with an empty `spend` there would state that nothing was consumed (sub-question ② of OD-17). Say what you chose.
- **An outcome the end line cannot hold** (a `result` that is no `dict` or not strict JSON, a `spend` that is no object of axis *name* to *integer* ≥ 0, a failure `kind` that is no *name*): recommended an error of this module (or `journal.JournalError`) with no end line appended, the step left open. Say which error.
- **The start line could not be appended** (an `OSError`, `events.CorruptEventsError`): the error passes through and `step` is not called.
- **The end line could not be appended** after `step` returned: the error passes through; the step is open (or ended, when the failure came after the line feed — `hilclaw.events` docstring); the outcome is not returned in the place of the error. Say what you chose.
- **The order of the checks**: recommended `run_id`, the identity (an invalid one is reported before any file is read, as in `run_journal.step_state`), that `step` is callable, then `data_root`, then the files. Say what you chose and assert it.
- **Errors of the lookup** (`events.PositionBeyondLogError`, `events.CorruptEventsError`, `events.UnsupportedVersionError`, `journal.JournalError` for a malformed step line in the lines read): pass through; nothing appended; `step` not called.
- **What the first call returns**: recommended the `result` as the end line holds it (the copy `events.append` returns), so that it equals what a repeated call returns.
- **The failure raised for an ended step that holds `failure`** and the one raised when `step` ended without an outcome: recommended both a `tools.ToolFailure` of the same `kind` and `message`, so a caller cannot tell a first call from a repeated one.
- **A torn tail in the log**: `events.read` skips it and `events.append` removes it; say that the function adds nothing to that.
- Anything else you meet. If you read one as a rule about what the log may hold, about an open step, or about placement that no record states, return BLOCKED with the exact question.

### Tests (excluded from the size cap; `tests/test_journaled_step.py`)

- happy: no line → the log holds exactly the two lines of the Example of ADR-0011 (apart from `time`), each accepted by `journal.check_step`, `step` called once, the result returned; afterwards `run_journal.current` shows the amounts in the totals and no open step; a step that ended without an outcome → an end line with `failure` and its `spend`, the tool failure raised; an identity with `round`, `candidate` and `attempt`, with `round` only and with none; an empty `spend`; `data_root` as `str`; a second run untouched.
- the three states (decision 4): **ended with a result** → equal result, `step` not called, the log bytes unchanged; **ended with a failure** → the same `kind` and `message`, `step` not called, bytes unchanged; **open** → the tool failure of the chosen kind, `step` not called, bytes unchanged; a higher `execution` of the same step is a different identity and runs.
- the three death points (the table at lines 128-134 of ADR-0011), simulated by an exception at that moment (through `monkeypatch` on `events.append`, or by `step` raising): before the start line is complete → the next call finds no line and runs; after the start line and before the end line (`step` raises; the append of the end line fails) → the next call reports open and does not run; after the end line → the next call returns the outcome without running, and the amounts are counted once by `run_journal.current`.
- order: the start line is complete in the file when `step` is called (observe the file from inside `step`); the end line is appended after `step` returned; nothing is appended before the state is established.
- branch — where the lookup reads: an identity of the stored `round` whose lines are in the tail; **an identity of an earlier round whose two lines lie before the stored position → ended, not run** (with a `STATE.json` whose position is after them); an identity without a round with lines before the position; an identity of an earlier round with no line anywhere → runs; lines before the position are not interpreted on the tail path (a damaged line before the position does not disturb an identity of the stored round) and are on the other path (`events.CorruptEventsError`).
