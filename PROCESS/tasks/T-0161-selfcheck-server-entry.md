## Why

Its design record is ADR-0054 (T-0153, `a5ed142`). It is the only remaining slice that depends on no other, and step two cannot be written before it (step two reads the wire copy and writes the server entry into the configuration file). ## Acceptance Criteria
### Fixed by the record (not re-decided; implement exactly)
1. **The server is the unchanged `hilclaw.mcp_front`.** The entry calls `mcp_front.main` with a registry and streams of its own; `hilclaw/mcp_front.py` is not edited and no rule of the front is changed, replaced or bypassed (no second JSON-RPC implementation, no pre-reading or filtering of a line).
2. **The registry holds exactly two tools, named `selfcheck.token` and `selfcheck.fail`** (the front lists and calls them as `selfcheck_token` and `selfcheck_fail`). `selfcheck.token` **returns a result that holds the first token**; `selfcheck.fail` **raises a tool failure whose message holds the second token** (through the front: `isError` false and `isError` true).
3. **The tokens are given to the entry from outside** ("the check creates [them] for one session and hands [them] to the server entry"); the entry creates none and has no default for one. **A token is in nothing the model is shown before it calls**: not in a tool's name, description or input schema (so not in the answer to `tools/list`), not in the answer to `initialize`. The first token is in no answer of `selfcheck.fail`, the second in no answer of `selfcheck.token`.
4. **These tools never appear in the registry of a run**: `hilclaw/tools.py` is not edited, `tools.default_registry` does not hold them, and nothing registers them into a registry the module did not make.
5. **The wire copy.** The entry gives `mcp_front.main` streams that **pass every line through unchanged** and **copy it, with its direction, to one file** whose place the entry was given. Both directions are copied: each line the client sent (as `readline` returned it, byte for byte) and each line the front wrote. Standard error is not copied.
6. **The values of the server entry** - what step two will write under the name `hilclaw` into its configuration file as `command`, `args` and `env` - hold **only values the check itself made**: the two tokens, the place of the wire copy, and what the server process needs to find the package. **Never a copy of the environment of the calling process**, in whole or in part, and no credential.
7. **Not an FR-10 tool, no backend, no data plane**: the module registers nothing in `default_registry`, reaches no backend (the mock included), reads no data root and no `hilclaw.config`, and writes no file other than the wire copy at the place it was given.

### Left to this task (Python form only; decide, say each in the module docstring as a convention of the module, test it, and list each choice in `## Result`)
- **The public names**: the module's entry `main` (signature in the manner of `mcp_front.main`: `argv`, the three streams, and whatever source the tokens and the wire-copy place come from, injectable for tests), the function that builds the two-tool registry from two tokens, the function that returns the values of the server entry, the reader of a wire copy, the constants of the two registry names. Planner's suggestion, not required: `registry(token, fail_token)`, `server_entry(*, token, fail_token, wire_copy)` returning a `dict` with exactly `command` (`str`), `args` (`list[str]`) and `env` (`dict[str, str]`), `read_wire_copy(path)`, `TOKEN_TOOL = "selfcheck.token"`, `FAIL_TOOL = "selfcheck.fail"`, and the command line `python -m hilclaw.selfcheck_server`.
- **How the tokens and the place of the wire copy reach the entry**: arguments, or variables of the entry's `env`. Planner's reading: variables of `env` with a `HILCLAW_SELFCHECK_` prefix and an empty argument list - arguments of a process are visible in the process listing of the machine and `mcp_front.main` takes none; say which you took and why. Whatever is chosen, `server_entry` and `main` are the two ends of one convention and a test starts the entry from what `server_entry` returns.
- **How the server process finds the package from a working directory outside the checkout** (hint (f) of T-0153; "the first thing the server-entry slice must settle"): the interpreter (planner's reading: `sys.executable` of the process that builds the entry) and the place of the package (planner's reading: `PYTHONPATH` in `env`, set to the directory that holds the `hilclaw` package, derived from the package's own location and **not** from the caller's `PYTHONPATH`; weigh it against a `-c` argument that extends `sys.path`, and do not run the module file by its path - `hilclaw/` holds modules whose names would then shadow others). It must not rest on the working directory, on an installed distribution or on the caller's environment, and it must work when the path holds a space or a non-ASCII character. Say plainly in the docstring what is shown (a child process of the tests, Linux and Windows) and what is not (macOS, WSL, a start by Claude Code itself - runtime acceptance item (vii)).
- **The form of a token the entry accepts.** It travels through an argument or a variable and through JSON text and must be found again, literally, in a reply. Planner's reading: a non-empty bounded string of a small alphabet (for example 32 lowercase hexadecimal characters), the two tokens different from each other; a missing, malformed or repeated token ends the entry before anything is served. You may add the generator of such a token (`secrets`) to this module so that the form and the generator stand together, or leave it to step two; say which.
- **The members of the two answers**: the name of the member of the result that holds the first token; the kind (a name per `tools.ToolFailure`, **not one of `tools.RESERVED_KINDS`**) and the wording of the failure message around the second token; the description and the input schema of each tool (text written for a model, bounded, holding no token, no path and no name of a user). The prompt of the session is step two's and is not written here.
- **What each tool does with its request.** The model chooses the arguments. Planner's reading: each tool accepts any request object and ignores its members, so that a stray argument of the model does not turn the expected result into an `invalid_request` failure and the expected failure into another one; say it.
- **The form of the wire copy** and its reader. Requirements: for any bytes at all in either direction (invalid UTF-8, a NUL, a CR, a last line without LF, a line of a megabyte) the reader returns exactly the sequence of (direction, line) that was copied, in order; each record is on the disk when the line has been handled (the server process may be killed at the time limit), so a reader after a kill sees every complete record; **a torn or malformed last record and a file that is no wire copy are told by a stated rule and never read as a line that was not sent**; a file that is not there or cannot be read is an error of its own, distinct from an empty wire copy. The reader never raises on the content of a file except as that rule says. It only returns the lines: it parses no JSON-RPC and judges nothing.
- **The order of copy and pass-through**, and what a failed copy does. Planner's reading: a client line is copied before the front gets it (a line the front fails on is then in the copy); a server line is copied only after it was written and flushed to the real output (the copy never holds an answer that was not sent); a wire copy that cannot be created ends the entry before a line is read; a copy that fails later surfaces to `mcp_front.main` as the `OSError` of the stream, on which the front gives up by its own rule - **nothing is ever served that the copy does not show**. Whether an existing file at the place is refused (exclusive creation; planner's reading) or extended, say which.
- **The exit statuses of the entry**: follow `mcp_front` (0 at the end of input, 4 when the entry or the front gives up), never 1 or 2. One line of free text on standard error when the entry gives up, **holding no token and no path**.
- **What the functions raise for bad arguments** (a token of the wrong type or form, equal tokens, a wire-copy place that is not a path): `TypeError` / `ValueError`, with no token in the message.
- Nothing else.

**Conventions chosen under "Left to this task"** (each is in the module docstring and tested):
- *How the values reach the entry*: variables of `env`, no argument (arguments show in the process listing; `mcp_front.main` takes none). An argument ends the entry with status 4 before the wire copy is created.
- *How the server process finds the package*: `<sys.executable> -I -c "import sys; sys.path.insert(0, sys.argv.pop(1)); from hilclaw.selfcheck_server import main; raise SystemExit(main())" <package directory>`, the directory derived from the module's own `__file__`. **This departs from the planner's reading (`-m` with `PYTHONPATH`)** after weighing: with `-m` the working directory is first on the module path (a `hilclaw` directory there would be served), `PYTHONPATH` splits at the path separator, and any `PYTHON*` variable of whoever starts the server acts on it. With `-I -c` none of the three holds, an installed distribution does not win, and `env` holds only the three values of the check. There is no `-m` form (no `__main__` block). Cost, stated in the docstring: modules beside the package directory come before the standard library on the module path of the server process.
- *The form of a token*: exactly 32 lowercase hexadecimal characters (`re.fullmatch`), the two different. The generator `new_token` is in this module so that the form and the generator stand together. A missing, empty, malformed, wrongly typed or repeated token ends the entry (status 4) before the wire copy is created and before a line is read.
- *What each tool does with its request*: accepts any request object and ignores its members. Description of each tool: one short text for the model, no token, no path; input schema `{"type": "object", "properties": {}}`.
- *The wire copy*: created exclusively (`open(place, "xb", buffering=0)`; an existing file is refused, never extended); the magic line, then one record per line: `C` or `S`, a space, the decimal length, LF, the bytes, LF. Each record is one unbuffered write (looped on a short write).
- *Order*: a client line is copied before the front gets it; a server line after it was written and flushed to the real output. A copy that fails surfaces as `OSError("the wire copy cannot be written")` of the stream (no path), on which the front gives up with status 4. **Consequence for step two: the last answer sent can be missing from the copy** - when its copy failed, or when the process was killed between the flush and the record (round-2 finding M1). Every earlier line is there. A session ended by the time limit is `session_failed` anyway.
- *The reader*: a file that does not begin with the whole magic line (an empty file, a torn magic line and any foreign file included) raises `WireCopyError`; after the magic line reading stops at the first place where no whole well-formed record stands, the records before it are returned and `torn` is true when bytes are left (a cut record and a malformed one are not told apart). A missing or unreadable file is the system's `OSError` (its message may name the path); a `path` that is no `str`/path is `TypeError`. A wire copy with the magic line alone is `WireCopy((), False)`. The reader reads the whole file into memory and parses no JSON-RPC.
- *Exit statuses and standard error*: 0 and 4 as the front; one fixed line `hilclaw.selfcheck_server: <text>` when the entry gives up (three texts: an argument, an unusable token or place, a wire copy that cannot be created or written), holding no token and no path.
