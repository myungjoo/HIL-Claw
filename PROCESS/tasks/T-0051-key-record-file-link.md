### The write (ADR-0014 decision 3)
A store call that finds no stored record (the check through `_read` with the caller's key comes first and is unchanged) does:
1. **The content first**: the whole text is built as bytes before the file system is touched by the write.
2. **A new file in the key directory**: `hw_profile.json.<token>.tmp` or `op_signature.json.<token>.tmp` beside the final name, `<token>` matching `[a-z0-9-]{1,64}` and different per write, **created as a new file** (exclusive creation), holding the whole content. Recommended token: the one of `hilclaw/run_state_file.py`.
3. **Stable storage**: `flush` and `os.fsync` on the temporary file, which is closed before the last step.
4. **The last step — one that cannot replace**: recommended `os.link(temporary, path)` followed by the removal of the temporary name (the operation the record cites). The final name is **never opened for writing** and **`os.replace` / `os.rename` are never called**. **No fallback**: when the operation fails for a reason other than the name being taken (for example a file system without hard links), its `OSError` is raised, the temporary file is removed and nothing is stored.
5. **A failure while the writer lives**: the temporary file this call created is removed and the exception raised again; the final name is as it was (absent).

**When the last step finds the name taken** (`FileExistsError`): the writer removes its temporary file, has written nothing under the final name, and treats what is now there as a stored record it could have found before it started — ADR-0001 decision 3 applies. Recommended form: read it again through `_read(root, path, derive, key)`; an equal canonical form gives `Stored(key, False)` (the stored attributes stay, as for a repeated store today); a canonical form that differs raises `KeyCollisionError`; a file that is no valid record raises `CorruptKeyRecordError`. If the name is absent again at that read, recommended: raise the `FileExistsError` of the last step unchanged (no retry loop).

To hold in the code:
- **Unchanged public behaviour**: the signatures, results and error types of `store_hw_profile`, `store_op_signature`, `load_hw_profile`, `load_op_signature` and `lookup`; the order of the checks; the bytes of a written file; a store of a stored key writes nothing and creates no temporary file; `store_op_signature` still requires the stored hw_profile; `_read` (a missing file is no record; a symbolic link or a directory under the final name is `CorruptKeyRecordError`).
- A key is stored if and only if its record file exists as a regular file. A leftover (a file of the name form) in a key directory, alone or beside other files, does not make the key stored and is never read in the place of the record, never given the final name (decision 5). The readers open the final name only and list nothing.
- The directory entry is not flushed (decision 6). `data_root` is never created.

### Provisional choices of this task (ADR-0014 does not fix them; also in the commit and PR body)
- **The non-replacing step** is `os.link` followed by the removal of the temporary name: the operation the record cites, standard library, fails when the final name exists.
- **`<token>`** = the process id, a hyphen, `secrets.token_hex(8)`: the form of `hilclaw/run_state_file.py`, inside `[a-z0-9-]{1,64}`.
- **The name found taken** (`FileExistsError` of the link): the file now there is read once more through `_read(root, path, derive, key)`. Equal canonical form → `Stored(key, False)`, the stored attributes stay; another canonical form → `KeyCollisionError`; no valid record → `CorruptKeyRecordError` (ADR-0001 decision 3 applied to a record that could have been found before the write). The temporary file is removed in each case. The collision or corruption error keeps the `FileExistsError` as its implicit context (round 1, Nit 2: kept, it shows how the stored record was met).
- **The name absent again at that reading**: the `FileExistsError` of the link is raised unchanged, no retry loop (the call cannot spin against another process). Said in the module docstring (round 2, Nit 1).
- **A failed step** (creation of a directory or of the temporary file, write, flush, link): its `OSError` passes through unchanged. A link that fails for another reason than a taken name (no hard links) stores nothing.
- **The directories a failed write created** are still removed where possible: only those this call created, innermost first, `rmdir` only, a failing removal not reported. Keeps today's behaviour and the three existing tests that assert it.
- **Which file is removed on a failure**: only the temporary file this call created (`created` flag); a temporary name found in use is another writer's and stays (tested with a fixed token); a removal that fails is not reported in the place of the failure it follows.
- **`BaseException`** (`KeyboardInterrupt`): the temporary file and the created directories are removed then as well.
- **After the link succeeded** the record is stored: a failing removal of the temporary name is not an error, the result is `Stored(key, True)`, the name stays as a second name of the record (decision 5); nothing the call created is removed.
- **Leftovers of other writes** are not listed, read, removed or given the final name (decision 5 allows a removal and requires none; decision 6: a removal can hit a live writer).
- **Mode and link count**: no test asserts either.
- No shared helper with the two other writers (the planner's cut).
- No criterion disagreed with a record, and no case was read as a rule about what may exist in `db/` that no record states (`store_op_signature` still requires the stored hw_profile through the unchanged `_load` call).
