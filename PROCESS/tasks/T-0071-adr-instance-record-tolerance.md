## Why
PLAN P1-8 ("런타임 STATE/instance/events 스키마 - OD-8 종결 필요(§9 ADR 경로)") has `instance.json` with its frame and exactly one member, `hw_profile` (ADR-0018, `hilclaw/instance.py`). ADR-0018 said how the file grows: "Later records add the other members one at a time under the version rule of decision 2", and listed the first candidate that needs no further owner item: "the tolerance members of the first case (the vocabulary is the owner's answer HQ-0004, ADR-0017; the member is a later record's)".

The fact is fixed and has no place:
- FR-9: "tolerance는 사용자가 instance 파라미터로 지정·변경한다", with the vocabulary of the first case - `cpu_standin`, `gemm`, fp32, C kernel - per-element `rtol` and `atol`, "기본값은 없어 instance가 둘 다 명시한다" (owner, HQ-0004 (2) and (3)).
- ADR-0017 decision 5: `rtol` and `atol` "are parameters of the run, given by the caller from the instance"; Consequences: "An instance must state `rtol` and `atol`; no member of `instance.json` is named."
- The code takes them as arguments and reads them from nowhere: `hilclaw.harness.verification.run_verification(..., rtol, atol)` and `hilclaw.harness.verification_arrays.check_tolerance(rtol, atol)` (each "a finite int or float that is not negative"). The reviewers of T-0062 noted that "reading them from `instance.json` belongs to P1-8".

Why it is needed now: the contract of `correctness.check` (PLAN P1-1) is the one HW tool contract that does not depend on the open half of OD-18 sub-question 7 (see the planner's judgement below), and it cannot be written while the tolerance of a run has no place - the same position the path of a HW tool was in before ADR-0018 gave the hw_profile of a run its place.

DRIVER §6: a task that needs a design-level decision carries the record that closes it; the route used so far is two tasks (record, then code). **This task writes the record**, ADR-0020. It ticks **no PLAN checkbox** (P1-8 and P1-1 stay open).

The planner returned that question to the driver for the owner; this task does not touch it. The part that needs no reading - that a correctness check is carried out at `cpu_standin` (A-7 lists "correctness"; HQ-0004 fixed its oracle and tolerance) - is what makes this record the next step.

## Acceptance Criteria
What is **fixed** and taken as input, not re-decided:
- **Owner (HQ-0004)**: for the first case - `cpu_standin`, kind `gemm`, fp32, C kernel - the tolerance is per-element `rtol` and `atol`, "both instance parameters (FR-9)"; pass iff |out - ref| <= atol + rtol * |ref| for every element; any NaN or infinity in the output fails; "Defaults: none. An instance must state both `rtol` and `atol`; the harness has no default value". Vendor golden outputs, downstream-metric thresholds, user-defined checks and other dtypes "stay open under B-7".
- FR-9: the user sets and changes the tolerance as an instance parameter; the system does not choose how much accuracy to give up; a candidate that would pass under a looser tolerance is only reported, and adopting it is "사용자가 tolerance를 바꾼 새 instance".
- ADR-0004: `runs/<run_id>/instance.json`, one per run, "What the instance was started with", written once, immutable; nothing enforces it. ADR-0018: the frame of the file (decision 2), the member `hw_profile`, the open top level of version 1 and **the rule of what raises `schema_version`**, and that "what a run needs in order to start is said by the records of those members, each of which chooses between a member that may be absent from a valid file and a new version".
- ADR-0017 decisions 5 and 6: the values are given by the caller from the instance, are not passed to the verification program, and are valid when each is finite and not negative (as `check_tolerance` has it).
- Nothing is kept between calls (ADR-0010 decision 7).

What the ADR **decides**. The content of each decision is the executor's to work out and justify from the fixed inputs; the reviewer's Approve confirms it. For every point give the choice, the alternatives considered and one or two lines of reason; mark each value as **cited** or as **this record's own**:
1. **Scope**: of `runs/<run_id>/instance.json`, the one member in which a run states the tolerance of its correctness check, for the vocabulary of the first case only; nothing else of the file and nothing of any other file. State that the file is still not a complete instance record.
2. **The member: its name, place and form.** Weigh at least: (a) one top-level object (for example `tolerance`) with the members `rtol` and `atol`; (b) two top-level members; (c) an object that also names its vocabulary, so that a later vocabulary of #5 B-7 (a golden output, a downstream metric, a user-defined check, another dtype) can be told from this one by a reader of today. What must hold: a reader can tell "this instance states the per-element tolerance of the first case" from "this instance states something this reader does not know"; nothing in the form pretends that the first case's vocabulary is the general one (HQ-0004: "not the general answer to B-7"); the object is closed or open, said explicitly as ADR-0018 decision 3 says it for `hw_profile`. If (c) is chosen, the record names **no value for any other vocabulary**.
3. **Whether a valid version 1 file may lack the member, and whether adding it raises `schema_version`** - by ADR-0018 decision 2's own rule, which leaves exactly this choice to the record of the member. Weigh: (a) the member may be absent from a valid file and the version stays 1 - then say what "an instance must state both" (owner) means: a valid file is not thereby enough to start a run or to carry out a correctness check (ADR-0018 decision 2), and a reader that asks for the tolerance of a run whose file lacks it reports that it is not stated and **never substitutes a value**; (b) the member becomes required and the version becomes 2 - then every file and reader of today is of another version before a first run exists, and reading another version is OD-11. State which, and that **no path yields a default** (owner). 4. **Validity of the values**: the JSON type and form of `rtol` and `atol` (a JSON number; whether an integer literal such as `0` is accepted beside a number with a fraction or an exponent; booleans and strings are none), the range (finite and not negative - cited: ADR-0017 decision 5 and `check_tolerance`; whether zero is allowed for one or for both is cited from there, not re-decided), and what a reader does with a literal no float holds (`1e999`, which the JSON parser of the frame reads as an infinity today - see the conventions in the docstring of `hilclaw/instance.py`).
