## Why
ADR-0021 (landed as `691870d`, T-0073) placed the cut of `correctness.check` for the first case: an operation of a backend starts the verification process at its target and returns **the report, uninterpreted**, or says that there is none and why; **all of the judging** - the form of the report, the regeneration of the inputs, the check values, the float64 reference, the predicate with the tolerance, completed / broken, pass / fail - is the tool function's part, "carried out by the code of the harness sub-module (FR-9), in the process of the tool function", the same code for every backend (decision 2).

Its Consequences cut one code slice that needs no further record:

> *Possible after this record alone* (code mode, within the size cap): the judging half as a function of the harness that takes what an operation returns - the form check and the loop over the draws that are inside `run_verification` today - with `run_verification` kept for a verification about no run (the calibration tests); and a source of seeds with the property of decision 3.

Today `hilclaw.harness.verification.run_verification` does both halves in one function (lines 180-208): it starts the process, then judges. The pieces of the judging are public in `verification_arrays.py`, but **the form check and the loop over the draws exist only inside `run_verification`**, behind a process start. A tool function that is handed a report by an operation cannot call them, and a second copy of them elsewhere would be a second harness (FR-9: one).

**This task is the first half of that slice: the judging function.** The source of seeds is the next task (see `## Follow-ups`); it is a new module with its own design choices and is kept apart so that each review stays narrow.

It serves PLAN P1-1 (the contract and code of the FR-10 tools). It ticks **no PLAN checkbox**: P1-1 stays open (the second record of the contract, the tool function, the mock's operation, the conformance tests).

Planner's judgements (2026-10-09 UTC, from the files; the reviewer is asked to re-check each):
- **No record is needed.** The function is inner structure of the harness sub-module that ADR-0021 decision 2 describes and its Consequences name as a slice. Its name, its parameters and its return form are "the code task's" (ADR-0021 decision 2: "The spelling of what is handed and returned is the second record's and the code task's") and are provisional.
- **The function is bound nowhere.** No tool, registry, backend, table or front is touched; `tools.default_registry` stays empty. Nothing here says whether the tool is journaled, what its `step` is, at which execution point a call is made, or what a request or a result of the tool holds.
- **It judges a report and defines no type for "what an operation returns".** ADR-0021 decision 2 gives that as two classes: (A) the report, (B) no report, for the time limit or for a non-zero status or a signal. Class (B) needs no computation - the two conditions are `Broken.TIMEOUT` and `Broken.EXIT_STATUS`, which exist - and how an operation says (B) is the spelling of the second record and of the tool's code task. So the new function takes a report (class A) and can only find the two conditions the tool function finds: `Broken.REPORT_FORM` and `Broken.CHECK_VALUE`. If you find that the slice cannot be cut without a type for (B), do not invent one silently: choose the smallest form, mark it provisional and say so in `## Result`.
- **The behaviour of `run_verification` does not change**, and it stays public with its signature, its result type and the order in which it raises: it is "kept for a verification about no run" (the calibration tests of T-0063, `tests/harness/test_verification_build.py`, the `C gate (clang)` job). Every existing test passes without an edit of its assertions.
- **What the function returns holds no `run`.** `VerificationResult.run` is the capture of the runner (command line, standard error), which ADR-0021 decisions 3 and 5 keep out of a result of the tool "until the question of decision 3 is answered". A judging function has no process and returns the judgement alone.

### The judging function
Recommended shape (names yours): a public **`judge_report(report, *, m, k, n, draws, seed, rtol, atol)`** returning a public `NamedTuple` **`Judgement(broken, verdict, counts)`** - the first three fields of `VerificationResult`, with the same meaning and no `run`.
- It **starts no process, reads and writes no file, reads no environment variable, clock or random source, and keeps nothing between calls**. Its outcome is a function of its arguments alone.
- It takes the report as the bytes a verification process wrote on its report channel (the form of the module docstring) and carries out exactly what `run_verification` does today after the exit-status test, in the same order: the length of a complete report computed from `m`, `n` and `draws` alone and compared before any byte is read, the end mark, then draw by draw the regeneration of the inputs from `seed`, the comparison of the check value, the reference and the counts. A report of another form is `Broken.REPORT_FORM`; the first check value that disagrees is `Broken.CHECK_VALUE` and drops the counts taken so far; otherwise `Verdict.PASS` when no element of any draw failed and `Verdict.FAIL` otherwise, with one `Counts` per draw in order.
- It never returns `Broken.TIMEOUT` or `Broken.EXIT_STATUS`: those are found by whoever ran the process (ADR-0021 decision 2 (B)). The `Broken` and `Verdict` enumerations keep their members, names and order (decision 5: the order time limit, exit status, form, check value).
- It returns no index, deviation or element of the inputs, the reference or the output, and nothing that holds the seed (ADR-0017 decision 7; ADR-0021 decisions 3 and 5).
- **All parameters besides the report are keyword-only and none has a default**: no tolerance, seed, number of draws or dimension is held by the module (the module docstring's "What this module does not do" stays true).
- Arguments are refused before any byte of the report is looked at, with the rules the module already has: `m`, `k`, `n`, `draws` and `seed` by the rule of `program_arguments` and the tolerance by `check_tolerance`, both as `VerificationArgumentError`, in that order. What is accepted as a report (exactly `bytes`, or other bytes-like objects) and what a value of another type raises is yours to choose; state it in the docstring and test it. A wrong type must not come out as `Broken.REPORT_FORM`: that condition is a statement about a process.
- What NumPy raises for arrays it cannot allocate is passed on, as today.
