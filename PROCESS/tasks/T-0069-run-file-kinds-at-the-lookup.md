## Why
ADR-0019 (landed as `cd19c48`, T-0068) answered OD-18 sub-question 4: a call of a tool for a run that cannot be used is a tool failure of one of four reserved kinds - `run_file_missing`, `run_file_unreadable`, `run_file_invalid`, `run_file_unsupported` - given in the tool function at the lookup (moment 3) and at the selection (moment 4), and never as `tool_crashed`. Its Consequences cut the code slice:

> **The code slice that can now be cut** (code mode, within the size cap; whether it is one task or two is the planner's): the four kinds beside the seven of `hilclaw/tools.py` and in `RESERVED_KINDS`; the mapping of the rows at the lookup and at the selection in the path of a journaled tool and of a HW tool - at the moment, not by class at the level of `tools.call`, with "not there" told from the other `OSError`s, and with the three `UnsupportedVersionError` classes of `run_state`, `events` and `instance`; and the tests that today assert only that the kind is none of `invalid_request`, `no_data_root`, `step_open` (...) which can then pin the kind of each row.

Today on `main` (`e35391d`) none of this exists: `hilclaw/tools.py` names seven kinds, `hilclaw/journaled_step._state` lets every error of the lookup pass through, and `hilclaw.tools.call` reports each as `tool_crashed`.

**This task is the first of two halves of that slice: the four kinds, and the rows of moment 3 (the lookup).** The lookup is `hilclaw.journaled_step._state`, which both builders reach (`journaled_tool.tool_function` through `run`, `hw_tool.tool_function` through `run_prepared`), so after this task every journaled tool, a journaled HW tool included, answers the rows of moment 3 with their kinds. The rows of moment 4 (`instance.json`, in `hilclaw/hw_tool.py`) are the second half, the next task; until then a situation of `instance.json` still arrives as `tool_crashed`, exactly as today.

It serves PLAN P1-1 and ticks **no PLAN checkbox** (P1-1 stays open: the selection half, every tool and its contract, the `cpu_standin` backend, the default table, the conformance tests). `hilclaw.tools.default_registry` stays empty.

### The answer at the lookup (`hilclaw.journaled_step._state`, reached by `run` and `run_prepared`)
For each row the lookup raises a `hilclaw.tools.ToolFailure` of the kind, chained to the error it answers for (`raise ... from error`), before `before_start` is called and before anything is appended:

| What the lookup meets | Kind |
|---|---|
| `run_journal.MissingStateError` | `run_file_missing` |
| `FileNotFoundError` or `NotADirectoryError` out of the read of `STATE.json` (the data root gone since moment 2; the file gone between the check and the read) | `run_file_missing` |
| `run_state.InvalidStateError` (an empty file and a path that is no regular file included) | `run_file_invalid` |
| `run_state.UnsupportedVersionError` | `run_file_unsupported` |
| `events.CorruptEventsError` (a damaged complete line; a log path that is no regular file) | `run_file_invalid` |
| `events.PositionBeyondLogError`, from `events.read` and from the check of `_state` itself | `run_file_invalid` |
| `events.UnsupportedVersionError` | `run_file_unsupported` |
| `journal.JournalError` out of the `journal.step_state` call over the lines read (a step line whose `data` breaks ADR-0011) | `run_file_invalid` |
| `FileNotFoundError` or `NotADirectoryError` out of the read of the log, **the data root no longer an existing directory** | `run_file_missing` |
| the same, **the data root still an existing directory** (the log removed between the check and the read) | no situation: the lookup goes on as for a log that is not there (decision 4), so a stored position above 0 is then `run_file_invalid` and a position 0 answers "no line" |
| any other `OSError` out of the read of `STATE.json` or of the log | `run_file_unreadable` |

- **Only the lookup is mapped.** Unchanged and unmapped, whatever their class: what `run_id`, `identity`, `step` and `before_start` are refused with before any file is read (`InvalidPathValueError`, `JournalError`, `InvalidEventError`, `TypeError`); what `before_start` raises; what the step raises; `InvalidOutcomeError`; what either `events.append` raises (ADR-0019 decision 3, last bullet: a failed append gets none of the four kinds - OD-18 sub-question 9); a `RecursionError` of the copy of a stored `result` (decision 7); every `BaseException` that is no `Exception`. A class that is no row is not caught.
- **Order**: the situation found first is answered - `STATE.json`, then the log, then the lines (decision 3).
- **Message** (decision 6): it starts with the path of the frame file relative to the data root (`runs/<run_id>/STATE.json` or `runs/<run_id>/events.ndjson`) and says what was found. The readers' messages for the `Missing`, `Invalid`, `Corrupt`, `PositionBeyond` and `UnsupportedVersion` rows already have that form and are used as they are. For the three rows whose error names no frame file - the `JournalError` (it says `line N: ...`), an `OSError`, a vanished data root - this task composes it; the wording is yours. Tests may check that the message starts with the relative path and holds the line number or the reader's text; nothing else in the package may depend on the wording.
- `STEP_OPEN`, the answer of an ended identity, the first-call path and `KIND_STEP_OPEN` are unchanged.
