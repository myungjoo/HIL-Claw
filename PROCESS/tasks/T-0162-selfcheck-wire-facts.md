## Why
PLAN P1-9 is the runtime self-check the owner ordered in the answer to HQ-0006 (b-2): a check of the `hilclaw` package that the bring-up of an instance runs **on the runtime machine**. Its design record is ADR-0054 (T-0153). ADR-0054 Consequences cut the code into four slices: "the two tools and the server entry with its wire copy; step one; step two with the outcome table; the report." Step one landed with T-0160 (`hilclaw/selfcheck_login.py`), the server side with T-0161 (`hilclaw/selfcheck_server.py`, `b4f7c7d`).

What is left is step two with the outcome table, and the report. Step two is too large for one task under the size cap, so the planner cuts it by **where the evidence comes from** (decision 6, "Three sides"):

1. **this task** - the *server side* as evidence: what the wire copy says, as named facts. It is a pure function over the lines `read_wire_copy` already returns. It needs no child process and nothing of Claude Code that the record marks "not verified": every rule it applies is a rule of the package's own front (`hilclaw/mcp_front.py`) or a sentence of decision 6 or 7.
2. the outcome table of decision 6 as a pure function over these facts, the login status and the session-side and model-side evidence handed in as already-read values;
3. the session itself against a stub `claude` the tests write (the directory of the check, the configuration file, the options of decision 4, the reading of the session's output);
4. the report and the command of the package, which ticks PLAN P1-9.

The previous planner's idea was (1) and (2) as one task ("the pure outcome table over the wire copy and the session evidence"). The planner of this task splits them: the reading of untrusted JSON-RPC lines with its bounded strings, plus the seven-row table, plus two docstrings of the length this package writes, would not stay within 300 lines, and `hilclaw/selfcheck_server.py` already stands at exactly 300 lines and must not grow. ## Acceptance Criteria
### Fixed by the record and by the code on `main` (not re-decided; implement exactly)
1. **A pure reading.** The module turns the copied lines of one wire copy - the `lines` of a `selfcheck_server.WireCopy` - into one value of named facts. It opens no file, starts no process, reads no environment variable, no clock and no configuration, keeps no state between calls and prints nothing. The same input gives the same value.
2. **It reads the wire copy and nothing else**: not the session's output, not a `system/init` event, not the model's reply, not the login status, **not the two tokens** (no parameter takes one; the tokens are judged on the model side by a later slice).
3. **The facts, each as decision 6 names it** (lines 108-115, 124, 125):
   - *the server was reached*: the copy "holds the client's `initialize` request";
   - *`server/discover`*: "whether that request came before `initialize`, the revision it names, and the error the front answered"; "Its absence is not a fault";
   - *the `initialize` revisions*: "the revision asked for and the one answered" (the request's `params.protocolVersion`, the result's `protocolVersion` - the members `mcp_front._initialize` reads and writes), and whether `initialize` was answered with a result;
   - *`tools/list`*: the request, whether it was answered with a result, "that the answer listed both tools", and - for condition (b) of `front_refused` - whether a `tools/list` request stands **after** the answered `initialize`;
   - *one call*: "a `tools/call` of `selfcheck_token`, answered with `isError` false"; *one tool failure*: "a `tools/call` of `selfcheck_fail`, answered with `isError` true". The two MCP names are derived from `selfcheck_server.TOKEN_TOOL` / `FAIL_TOOL` through `mcp_front.mcp_name`, not spelt a second time;
   - *the errors that condition (a) names*: every "JSON-RPC error written by the front other than a -32601 answered to a method outside the four it serves (so: an error answered to `initialize`, `ping`, `tools/list` or `tools/call`, or a -32700 or -32600 for a line of the client that the front could not read as a message)". "The four" are the keys of the front's method table; a -32601 answered to `server/discover` or to any other method outside them is **not** among these errors.
4. **The wire-side members of decision 7** (line 137): "the Claude Code version as the client states it in `clientInfo` of its `initialize` request"; "the revisions asked for and answered, and what was seen of `server/discover`"; "for each tool, whether its call ... [was] seen"; "every unforeseen method name" - a method of a client line "beyond `server/discover`, `initialize`, `notifications/initialized`, `ping`, `tools/list` and `tools/call`" (line 130). An unforeseen method **changes no other fact** (line 130).
5. **"Strings the client supplied are bounded"** (line 138): the version of `clientInfo` and an unforeseen method name leave the module "only when [they are] short and made of letters, digits and the characters `.`, `_` and `-` - for a method name also `/`; otherwise the word `other` stands in [their] place". Hint (a) of T-0153, which this task applies: **the same rule holds for the revision strings** of `initialize` (asked and answered) and of `server/discover`. A value that is absent or is no string is told apart from `other` (planner's reading: `None`).
6. **"Built from named members, never copied text"** (line 139): no line of the wire copy, no fragment of one, no error `message` of the front (it echoes the client's method or tool name), no `content` text of a call answer (it holds a token), no `id`, no `clientInfo.name` and no other member is in the returned value, in its `repr`, or in the message of an exception. What leaves the module is: booleans, the bounded strings of point 5, the names of the front's own methods, and error codes.
7. **No judgement.** The module names no outcome (`passed`, `no_call`, `front_refused`, `session_failed` and the three of step one appear in no identifier and no returned value), decides nothing about a `torn` copy, a missing file or a `WireCopyError`, and has no exit status. It reports the wire half of a condition and leaves the combining to the next slice.
8. **Nothing of the front changes**: `hilclaw/mcp_front.py`, `hilclaw/selfcheck_server.py` and `hilclaw/tools.py` are not edited, and no private name of theirs (a leading `_`) is imported.

### Left to this task (Python form only; decide, say each in the module docstring as a convention of the module, test it, and list each choice in `## Result`)
- **The public names**: the function, the type it returns and the constants. Planner's suggestion, not required: `read(lines) -> WireFacts`, `WireFacts` a `NamedTuple` whose members are immutable (tuples, not lists), the stand-in word `OTHER = "other"`, the tuple of the six foreseen methods, the length bound. Whether the function takes the `lines` tuple or the whole `WireCopy`; if the latter, `torn` is passed through untouched and unjudged.
- **Which server line answers which client line.** Planner's reading, from the code: the front reads one line, writes at most one line and only then reads the next (`mcp_front.main`), a client line is copied before the front gets it and a server line after it was sent (`selfcheck_server._Copied`), so in a wire copy **a server line answers the client line that stands immediately before it**, and pairing is by position - not by the `id`, which the client supplies and may repeat. Weigh pairing by `id` and say which you took and why. A request whose answer is missing (the last line of a killed or failed copy - T-0161 Result) is simply "not answered".
- **A copy the front could not have written** - a server line that follows no client line or another server line, a server line that is not one JSON object with exactly one of `result` and `error`, an unknown direction. The lines are bytes of a file in a directory the check made, yet the function is public and must not trust them. Planner's reading: such lines establish no fact of point 3, and one boolean fact says that the copy held a line the module could not place, for the next slice to treat under "left no readable wire copy"; **they are never read as an answer, and never as an error of condition (a)**. Say the rule.
- **How a client line is read.** Planner's reading: as the front reads it (`tools.decode_request`; a line that fails there has no method and is no request - the front's own answer to it, -32700 or -32600, is what counts), and a line is a **request** exactly when the front would answer it: an object with a string `method` and an `id` member. Follow the front's classification (`mcp_front._result`) so that the module and the front never disagree about which line is a request, a notification or a response; state the rule in words rather than importing a private name. The method of a notification counts for the unforeseen-method list as that of a request does (line 130 says "a request method"; say how you read it).
- **Several requests of one method** (two `initialize` requests, several `tools/list`, many calls). Planner's reading: the revisions and the version are those of the **first** `initialize` request; "came before `initialize`" and "after the answered `initialize`" are positions relative to it; a call fact is true when **at least one** call of that tool was answered as point 3 says ("at least one `tools/call` of each tool", line 125). Whether a call that was requested but answered otherwise, or not answered, is carried as a separate fact (decision 7: "whether its call ... [was] seen") - planner's reading: yes, requested and answered-as-expected are two booleans per tool.
- **What "answered with `isError` false / true" requires** of the result. Planner's reading: a `result` object whose `isError` is exactly the JSON `false` / `true`; nothing of `content` is read.
- **What "the answer listed both tools" requires.** Planner's reading: `result.tools` is an array in which both MCP names occur as the `name` of an object; other entries do not matter.
- **Where `server/discover` names its revision.** The record says only "the revision it names" (K15). The one observation (T-0106 line 107) had it in `params._meta["io.modelcontextprotocol/protocolVersion"]`. Read it there, bounded as point 5 says, and say in the docstring that the place is observed once and on no page; when it is not there, the fact is the absent value, not an error. Do not look for it in any other member.
- **The form of an error of condition (a)** as it leaves the module. Planner's reading: a tuple, in the order of the copy, of pairs (the code, the served method it answered or `None` for a line the front could not read as a message); the code is carried only when it is one of the four codes `mcp_front` defines and otherwise by a stated stand-in; the list is bounded in length by a stated rule.
- **The length of a bounded string** ("the length is the code task's") and **how many unforeseen method names are kept** (distinct names, in the order first seen; a stated cap and what tells that more were dropped). The client is not trusted (L6): a copy with a million distinct method names must not make the returned value large.
- **What the function raises**: `TypeError` for an argument that is not the stated form (not a tuple or list of pairs, a line that is not `bytes`), with nothing of the content in the message; **for bytes of any content it never raises** - not for invalid UTF-8, deep nesting, a huge number, a megabyte line or a member of an unexpected type at any depth it looks at.
- Nothing else.

**Rules**
- **Pairing** is by position: a server line answers the client line immediately before it. The front reads one line, writes at most one and then reads the next, and the entry copies a client line before the front gets it and a server line after it was sent. Pairing by `id` was weighed and not taken: the client supplies it and may repeat it. A request with no server line after it is not answered.
- **Client line**: read with `tools.decode_request`. A request of a method is one JSON object with a string `method` and an `id` member, whatever `jsonrpc` and the `id` value are.
- **Server line**: an answer only when it directly follows a client line, is one JSON object with exactly one of `result` and `error`, and is what the front can write to that line.
- **Unplaceable**: every other server line and any line of an unknown direction. It sets the flag, is never an answer and never an error of condition (a), and the client line before it stays unanswered. No error code outside the front's four leaves the module, so no stand-in code exists.
- **Bounded string**: 1 to 64 characters of ASCII letters, digits, `.`, `_`, `-` (a method name also `/`); any other string, the empty one included, is `other`; absent or no string is `None`. The rule covers the three revisions.
- **Raises**: `TypeError` with one of three fixed texts for an argument of another form; the bytes of a line never raise.
