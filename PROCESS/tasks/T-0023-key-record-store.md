## Why
ADR-0001 (`ARCHITECTURE/decisions/ADR-0001-od4-key-schema.md`) fixed the fields of the `hw_profile` and `op_signature` records, their canonical form and the directory names derived from it, and said in decision 3: "The full record (key fields and attributes) must therefore be stored with the data so that it can be found from the directory name" and "A tool that finds an existing directory whose stored canonical form differs from its own reports an error and writes nothing". Decision 4 defines the P1 lookup: a hit when `db/<hw_profile_key>/<op_signature>/` exists and the stored canonical forms equal the ones looked up. ADR-0004 (`ARCHITECTURE/decisions/ADR-0004-od8-data-plane-layout.md`) decision 5 fixed the place: `db/<hw_profile_key>/hw_profile.json` and `db/<hw_profile_key>/<op_signature>/op_signature.json` "hold the full [...] record of ADR-0001 (key fields and attributes). They are written when the directory is created; the stored canonical form that ADR-0001 compares on a lookup is derived from them". Its Consequences name what is still missing: "a module that builds paths [done: T-0022, `hilclaw/layout.py`], the writer of the two key record files with the collision check of ADR-0001, and the `artifacts.json` record".

`hilclaw/keys.py` (T-0016) validates a record and derives its name but stores nothing; `hilclaw/layout.py` (T-0022) builds the two file paths but touches no file. This task joins them: a small library that stores a key record under a caller-given data root, reads it back, refuses a collision, and answers the exact-match lookup. It is the first reader and writer of the knowledge tree `db/`, and everything that later registers `cpu_standin`, promotes a round into `db/`, or asks "is there stored knowledge for this pair" (FR-15, S5) goes through it.

It is a prerequisite slice of PLAN P1-8 / P1-1 and ticks **no PLAN checkbox**.

Constraints:
- **Standard library only** (`json`, `os`, `pathlib`, `reprlib` as needed) plus `hilclaw.keys` and `hilclaw.layout`. Adding any package is the BLOCKED reason "new external dependency". `pyproject.toml` stays unchanged.
- Runs on CPython 3.11 and 3.14 (both are CI matrix entries) and behaves the same on POSIX and Windows hosts (the driver machine is Windows; the targets are POSIX, C-7). The bytes of a written file are the same on every host (no `\r`, no platform default encoding).
- `data_root` is always given by the caller and must be an existing directory (as in `hilclaw.cas`); the module reads no configuration and no environment variable, runs no `git`, commits nothing and writes nowhere but the two record files and the directories above them inside `data_root/db/`.
- **Validation and naming come from `hilclaw.keys`, paths from `hilclaw.layout`**: the module repeats no field rule, no pattern and no path segment, and edits neither module.
- The stored object holds **exactly the members of the given record** (key fields and attributes) — nothing added (no timestamp, no writer, no digest, no canonical form, no layout version), nothing dropped, no value changed.
- **No temporary or scratch file inside `db/`** (ADR-0004 decision 7: no path of the tree is one, and `db/` is tracked, unlike `blobs/sha256/`). The tree gives no atomicity beyond a git commit (decision 10); a record file is created with an exclusive create, and if writing it fails the partial file is removed where possible and the error is raised.
- **An existing record file is never modified, replaced or deleted** by any function of the module.
- The module does not read or write `best.json` or `technique_stats.json`, registers no key on its own initiative, lists no directory to find keys, and does no nearest-neighbour or similarity matching (rest of OD-4).
- No command line entry point, no `main` (OD-18 is open).
- No value of a real machine or a real run is written into the module or its tests as a fact; tests use clearly synthetic records.

Module (new, `hilclaw/key_records.py`; provisional name, flat next to the sibling modules. Python because the package is Python and JSON and file handling are in the stdlib — one line in the commit body and `## Result`):
- Module docstring that names ADR-0001 decisions 3 and 4 and ADR-0004 decision 5 as the rules it implements and says what it does not do (see Constraints and Out of Scope), and docstrings on the public names (external API, CLAUDE.md "코멘트 최소화" exception); no other comments unless the code cannot say it.
- Public API (provisional names and shapes; the executor may rename or regroup them, but every public function must be tested and each capability below must exist):
  - **Store a hw_profile record**: `store_hw_profile(data_root, record)` — validates with `keys.hw_profile_key`, and creates `db/<hw_profile_key>/hw_profile.json` (with the directories above it) when the record file does not exist. Returns the `keys.Key` and whether the file was created by this call.
  - **Store an op_signature record**: `store_op_signature(data_root, hw_profile_key, record)` — `hw_profile_key` is the directory **name** (as in `hilclaw.layout`); validates with `keys.op_signature_key` and creates `db/<hw_profile_key>/<op_signature>/op_signature.json` when it does not exist. It requires the hw_profile record of that directory to be stored and readable; otherwise it raises and writes nothing, so that no key directory is ever created without its record (ADR-0004 decision 5: "written when the directory is created"). Returns as above.
  - **Read back**: `load_hw_profile(data_root, hw_profile_key)` and `load_op_signature(data_root, hw_profile_key, op_signature)` — return the stored record as plain `dict` / `str` / `int` values after checking it (below).
  - **Lookup** (ADR-0001 decision 4): `lookup(data_root, hw_record, op_record)` — validates both records, and returns the two `keys.Key` values when both record files exist and the canonical forms derived from the stored records are byte-equal to the ones looked up; returns `None` (a miss) when either record file does not exist. It reads nothing but the two record files: a hit says that stored knowledge of the pair **may** exist as a hint (FR-15), and the module neither reads nor interprets it.
  - Error types (provisional names): `KeyRecordNotFoundError(LookupError)` for a load of a record that is not stored; `KeyCollisionError(Exception)` for a stored canonical form that differs from the one being written or looked up (ADR-0001 decision 3); `CorruptKeyRecordError(Exception)` for a stored file that cannot be used (below). Messages name the path relative to `data_root` and the rule, show values with `reprlib.repr`, and never dump a whole file. Errors of `hilclaw.keys` (`InvalidRecordError`) and `hilclaw.layout` (`InvalidPathValueError`) for the **caller's** arguments pass through unchanged, and so do `FileNotFoundError` / `NotADirectoryError` for a `data_root` that is not an existing directory.
- Rules for the cases the ADRs leave unsaid (provisional; one line of reason each in `## Result`):
  - **A key is stored if and only if its record file exists.** A key directory without its record file (for example after an interrupted write) counts as not stored: a store call writes the file, a load raises not-found, a lookup misses. Reason: the directory name is derived from the record, so writing the record that derives that name is always consistent, and a retry after a crash must not fail forever.
  - **Existing record, equal canonical form**: the store call writes nothing and reports "not created". If the **attributes** (`hw_source`, `label`) of the given record differ from the stored ones, the stored file still stays as it is and no error is raised — ADR-0001 decision 5 says an attribute change is the same key, and whether and by whom a stored attribute is updated is not decided (OD-26). The caller can see the stored record with the load function. State this limit in the docstring.
  - **Existing record, different canonical form** (a 64-bit prefix collision, or a file placed in the wrong directory): `KeyCollisionError`, nothing written (ADR-0001 decision 3). The same in `lookup`.
  - **A stored file that is not a usable record** — not UTF-8, not JSON, not a JSON object, an object with a repeated member name at any level, a value `hilclaw.keys` rejects (a float, `true`, `null`, an array, an unknown field, a `schema_version` other than `keys.SCHEMA_VERSION`): `CorruptKeyRecordError`, nothing written. Reading a record of another schema version is OD-11 and is **not** attempted; say so in the docstring.
  - A stored record whose derived name differs from the name of its directory is reported as a collision or as corrupt — choose one, say which and why, and test it.
  - Text form of a written file: UTF-8 JSON of the record with members sorted by name at every level, an indentation of two spaces, `\n` line ends and one final newline. Reason: deterministic bytes and line-wise diffs in the data repository's history (NFR-2). **No reader, test of another module or later tool may depend on this form**: the load function accepts any JSON text of a valid record (for example the compact canonical-style text, or members in another order). Say so in the docstring.
- The record arguments are not modified, and a mapping type other than `dict` (as `hilclaw.keys` accepts) is stored as a JSON object.
- No function follows or resolves anything outside `data_root`: every path comes from `hilclaw.layout`, whose results cannot leave `data_root`.

Tests (new, `tests/test_key_records.py`; excluded from the size cap). Every test works under `tmp_path`; compare paths as `Path` objects or through `relative_to(tmp_path).as_posix()`. Records are synthetic and labelled as such (for example `accelerator: "synthetic_hw"`, `revision: "synthetic-r1"`); the example of ADR-0001 decision 7 is not a valid record and is not used as one.
- happy:
  - Storing a hw_profile record creates exactly `db/<name>/hw_profile.json` (assert the full list of files under `tmp_path`), returns the `Key` of `keys.hw_profile_key(record)` and "created"; loading it returns a value equal to the record, with attributes and an optional `ext` / `label` preserved.
  - Storing an op_signature record below a stored hw_profile creates exactly `db/<hw>/<op>/op_signature.json`; loading returns the record.
  - `lookup` returns both keys for a stored pair, with `canonical` equal to `keys.*_key(record).canonical`.
  - The written bytes are valid UTF-8 JSON, contain no `\r`, end with exactly one `\n`, and parse to the record. (Do not assert the indentation or the member order beyond what the docstring promises to callers — it promises none.)
  - The argument record is unchanged after a store call; a `types.MappingProxyType` record is accepted.
- branch:
  - Storing the same record twice: the second call reports "not created" and the file's bytes and modification are unchanged (compare the bytes).
  - Storing a record with the same key fields and a different `label` or `hw_source`: no error, "not created", stored file unchanged, load still returns the first record.
  - A key directory that exists without its record file: store writes the file; load raises not-found; lookup misses.
  - A stored file written by hand in another valid JSON form (compact, members in another order, CRLF line ends) is loaded and matches in `lookup`.
  - `lookup` misses when nothing is stored, when only the hw_profile is stored, and for a second op_signature (same shape, another `m`) next to a stored one; two op_signatures below one hw_profile are stored and loaded independently.
  - `data_root` given as `str` and as `Path`.
- negative (assert the error type, that the message names the path or the field, and — for every case — that **no file or directory was created or changed** under `tmp_path`):
  - Invalid records for both store functions and for `lookup`: a missing required field, an unknown field, a float, `True`, `None`, an empty `ext`, `schema_version` 2, a non-mapping → `keys.InvalidRecordError`.
  - Invalid `hw_profile_key` / `op_signature` names for the functions that take a name: no digest part, upper case, a name with `/` or `..`, `None`, a `keys.Key` instead of its name → `layout.InvalidPathValueError`.
  - `data_root` that does not exist, and one that is a file.
  - `store_op_signature` below a hw_profile that is not stored; below a hw_profile directory that exists without its record file; below a hw_profile whose record file is corrupt.
  - Collision: a record file holding a **valid** record with a different canonical form, placed by the test under the directory name of another record (for hw_profile and for op_signature) → store and lookup raise the collision error; the file's bytes are unchanged.
  - Corrupt stored files, each for load, store and lookup: empty file, invalid UTF-8, invalid JSON, a JSON array, a JSON string, an object with a repeated member name (top level and nested), a float value, `true`, `null`, `NaN`, an unknown field, `schema_version` 2, and the non-record example of ADR-0001 decision 7 (`layout: "NOT-DECIDED-HERE"`).
  - A record file path that is a directory.
  - Loading a record that is not stored → the not-found error (a `LookupError`).
  - A failing write (for example `os.fsync` or the file write made to raise through `monkeypatch`) leaves no record file behind and raises the original error.

- Provisional choices (conventions of this task, not requirements; the ADRs fix the fields, the canonical form, the collision and lookup rules, the two paths and that each file holds the full record):
  - Module `hilclaw/key_records.py`, flat next to the sibling modules: there is no sub-package layout to follow.
  - API grouping and return values: directory names in, as in `hilclaw.layout`, so a name read from a listing can be loaded; a store call returns the key and whether this call created the file; `lookup` returns a plain tuple of the two keys.
  - Three error types: a caller can tell "not stored" from "stored but unusable" from "another key is stored here". Messages start with the path relative to `data_root`; a collision message shows the two SHA-256 digests (fixed length) instead of the canonical forms; a corrupt message carries the bounded message of `hilclaw.keys` or of the JSON decoder and never the file content.
  - Errors about the caller's arguments (`InvalidRecordError`, `InvalidPathValueError`) are raised before the file system is looked at, then `FileNotFoundError` / `NotADirectoryError` for `data_root`: argument checks are pure and cheap.
  - **A key is stored if and only if its record file exists as a regular file.** A key directory without its record file counts as not stored: the directory name is derived from the record, so writing the record there is consistent, and a retry is possible after a failed write that left only the directory.
  - **An existing record with an equal canonical form is never rewritten**, also when `hw_source` or `label` differ: ADR-0001 decision 5 makes that the same key, and whether a stored attribute may be updated is OD-26. Observed behaviour until OD-26 is closed: the attributes written first stay.
  - **Name mismatch**: a valid stored record that derives another name than its directory is a `KeyCollisionError` in every function (load included), not a corrupt file — the file is a well-formed record, store and lookup already report that state as a collision by comparing canonical forms, and one state on disk then has one error type.
  - A stored file that is not a valid record of schema version 1 is a `CorruptKeyRecordError` (not UTF-8, not JSON, not an object, a repeated member name at any level, any value `hilclaw.keys` rejects, a UTF-8 BOM, JSON nested too deeply for the interpreter). Reading another `schema_version` is OD-11 and is not attempted; once OD-11 is closed the name "corrupt" may be inexact for an older version.
  - A record path that is not a regular file (a directory, a symbolic link) is a `CorruptKeyRecordError`; a link in the place of the record file is not followed (`os.lstat`). The directories above the file are used as they are, as in `hilclaw.cas`; isolation is the rest of OD-8.
  - A file occupying the place of `db/` or of a key directory: the store call passes the `FileExistsError` of `mkdir` through, load reports not-found and lookup misses (the record file does not exist).
  - Text form: UTF-8 JSON, members sorted by name at every level, two spaces, `\n`, one final newline — deterministic bytes and line-wise diffs (NFR-2). No reader may depend on it: any JSON text of a valid record is read (tests read compact, reordered and CRLF texts).
  - Exclusive create (`open(..., "xb")`, flush, `fsync`) without a temporary file: no path of `db/` is a scratch location (ADR-0004 decision 7). On a failed write the partial file **and the directories this call created** are removed where possible (the second half goes beyond the task text; reason: ADR-0004 decision 1, "a directory exists only when something was written into it"), and the original error is raised.
  - `store_op_signature` requires the stored, readable hw_profile record, so that no key directory is created below a hw_profile without a record; a library precondition, not a registration policy (OD-26).
