### Protocol facts (planner's reading of revision 2025-06-18; verify if you can fetch it)
- Transport: the client writes JSON-RPC 2.0 messages to the server's standard input, one per line; the server answers on standard output; the server ends when its standard input is closed.
- A **request** has `jsonrpc: "2.0"`, an `id` (string or number, not null), a `method` and optional `params`; it gets exactly one response with the same `id` and either `result` or `error` (`code`, `message`). A **notification** has no `id` and never gets a response. A message with `result` or `error` and no `method` is a response from the client and is not answered.
- `initialize`: params carry `protocolVersion`, `capabilities`, `clientInfo`. The result carries `protocolVersion` (the requested one if the server supports it, otherwise a revision the server supports), `capabilities` (for this server `{"tools": {}}`) and `serverInfo` (`name`, `version`). Then the client sends the notification `notifications/initialized`.
- `ping` → an empty result object.
- `tools/list` → `{"tools": [...]}`, each entry with `name`, optional `description`, and `inputSchema` (a JSON Schema object).
- `tools/call` with params `name` and `arguments` → `{"content": [...], "isError": false | true}`. An unknown tool and invalid arguments are protocol errors (JSON-RPC error `-32602`); a failure inside the tool is reported in the result with `isError: true`.
- JSON-RPC codes: `-32700` parse error (response `id` null), `-32600` invalid request, `-32601` method not found, `-32602` invalid params, `-32603` internal error. Revision 2025-06-18 has no batches: a JSON array is not a message.

### Capabilities of `hilclaw/mcp_front.py` (provisional names; each must exist and every public name must be tested)
1. `main(argv=None, *, registry=None, stdin=None, stdout=None, stderr=None) -> int` (shape provisional, mirroring `hilclaw.__main__.main`): serves until the end of standard input and returns the exit status; `registry=None` means `tools.default_registry()`; the stream arguments exist so that tests run in process and default to the **binary** standard streams. `if __name__ == "__main__": raise SystemExit(main())`.
2. **Server name and names of tools** (decision 4): `serverInfo.name` is `hilclaw`; a tool's MCP name is its registry name with each `.` replaced by `_` (`sim.run` → `sim_run`; agents see `mcp__hilclaw__sim_run`, the prefix is Claude Code's). The way back from an MCP name to a registry name goes through a table built from `registry.names()`, not through string replacement. A public function for the mapping is welcome.
3. **`tools/list`** lists every tool of the registry by its MCP name — today an empty list for the fixed set.
4. **`tools/call`**: the request is the `arguments` object; the call is `tools.call(registry, name, arguments)`. A **result** → `isError` false and exactly **one text block holding the result as JSON text**. A **tool failure** (`ToolFailure`, the shared level's `tool_crashed` and `bad_result` included) → `isError` true and one text block holding the error object `{"error": {"kind": …, "message": …}}`. What never reaches a tool function — an unknown tool name, arguments that are not a request, a malformed message — is a **JSON-RPC error**.
5. **`initialize`**, `notifications/initialized` and `ping` as the protocol requires, so that a client following the specification can complete the handshake and list the (empty) tool set.

### Cases the records leave unsaid — choose, implement, test and list each with one line of reason
- **Description and input schema of a tool.** ADR-0010: "A tool is listed with its MCP name, a description and an input schema; the content of both is each tool's (P1-1)" — and `Registry.register(name, function)` carries neither. Recommended for this slice, since no tool exists: do **not** extend the registry; list each tool with `inputSchema` `{"type": "object"}` and no `description` (or the first line of the tool function's docstring — say which), and record as a follow-up that the first tool slice decides where a tool states its description and schema. Do not validate `arguments` against a schema in the front (that would be tool logic). If you or the reviewer read this as a design choice that needs a record, return BLOCKED with the exact question.
- The **text of the text block**: recommended the same compact ASCII JSON text that the command-line front writes (`tools.encode` without its LF), so that the two fronts give the same characters for the same outcome. Whether **`structuredContent`** is sent as well (ADR-0010: "the code task's"; F10 not verified): recommended not, since no tool declares an output schema — say what you chose.
- **Protocol revisions**: which revisions the server accepts and what it answers to one it does not know (recommended: answer the requested revision when it is one of a small list that includes `2025-06-18`, otherwise answer `2025-06-18`; no behaviour differs by revision in this slice).
- `serverInfo.version`: recommended `hilclaw.__version__`; it is not a pin (decision 7). `instructions`: recommended none.
- A request other than `initialize` or `ping` **before** `initialize`, and a second `initialize`: recommended to serve them (no kept state decides an outcome) — or refuse and say why.
- `capabilities`: recommended `{"tools": {}}` without `listChanged` (the set does not change while the process lives).
- Notifications other than `notifications/initialized` (`notifications/cancelled`, any unknown one): ignored without an answer. A request whose `_meta.progressToken` asks for progress: no progress is sent.
- A line that is not UTF-8, not JSON, a JSON value that is not an object, a JSON array (batch), a missing or wrong `jsonrpc`, a `method` that is not a string, an `id` that is `null`, a boolean, a float or an object, `params` that is not an object, `tools/call` without `name` or with a `name` that is not a string, `arguments` missing (recommended: the empty request `{}`) or not an object, a duplicate member name in a message or in `arguments`, `NaN` / `Infinity`, an empty or whitespace-only line, a very long line, a deeply nested message (`RecursionError`), a UTF-8 byte order mark: choose the answer and the code for each; none may end the server or put anything but one protocol message on standard output.
- An unknown method (`resources/list`, `prompts/list`, …): `-32601`.
- A tool function that raises `KeyboardInterrupt` or `SystemExit` (not caught by `tools.call`): say what the server does.
- End of input, also in the middle of a line without LF; standard input or output that is `None`, closed or fails (follow `hilclaw/__main__.py`: count it as closed, never an uncaught exception); a write to a closed standard output (`BrokenPipeError`); the exit status values (recommended: 0 for a clean end of input, the same non-zero value as `hilclaw.__main__.EXIT_FRONT_FAILURE` — or a constant of this module — when the server cannot read or write).
- Standard input must be a blocking stream (T-0038 reviewer P1): say what the module assumes; do not build non-blocking support.
- Anything else you meet. If you read one as a rule for **tools** rather than for this front, or as a choice ADR-0010 lists under Boundaries, return BLOCKED with the exact question.
