## Why
PLAN P1-1 (the FR-10 tool contracts, the mock backend, the conformance tests) is open. For `correctness.check` the code on `main` is a row of pure modules bound to no tool. Two of them each render one half of "what a check that reached the call of its operation ends with":

- `hilclaw.check_operation.ask` (T-0137; ADR-0045): calls the operation once. It returns the result, or raises `OperationAnswerInvalid` (kind `operation_answer_invalid`, a message of that module) for a returned value of neither form and for a raised error. **A `ToolFailure` passes through it as the same object**, and a raised request to end is not caught.
- `hilclaw.check_failure.ended_with` (T-0140; ADR-0047): from a tool failure "an operation raised" to the pair `(kind, message)` the `failure` of the end line holds. **That an operation raised it "is the caller's statement and is not checked".**

Nothing in the package says which `ToolFailure` that comes out of `ask` was raised by the operation. Both records hand exactly that to the code: ADR-0047 Limits, sixth bullet ("a tool failure the tool function's own code raises in its part of ⑥ is not what this record is about, and where the code draws that line is the code task's") and ADR-0045 Limits ("Where the code draws the line between what an operation raised and what the tool function's own code raised is the code task's, and an error on that line can fall on either side"). T-0140 `## Follow-ups`, first item, names this task.

**This task carries that join into the package as one small module, ahead of the tool function** - the same kind of slice as T-0130, T-0131, T-0133, T-0135, T-0137 and T-0140. ### The module
Recommended public names, and no other: `EndedWithoutOutcome`, `carry_out`.

- **`EndedWithoutOutcome`** - the module's one exception for a check whose step ends without an outcome, for both causes:
  - A direct subclass of `Exception`; **no** `ToolFailure`, **no** `StepFailed`, no `OperationAnswerInvalid`, no subclass of any of them. It carries `kind` and `message`, each exactly a `str` (its constructor raises `TypeError` otherwise, as `OperationAnswerInvalid` does for its message), and no amount: no attribute `spend`. It holds neither the answer, nor a raised error, nor the raised tool failure, nor anything of them beyond the two strings.
  - `hilclaw.tools.ToolFailure(error.kind, error.message)` and `hilclaw.journaled_step.StepFailed(spend, error.kind, error.message)` can be built from every instance `carry_out` raises.
  - Its docstring says that the two strings are what the `failure` of the end line holds (ADR-0045 decision 3; ADR-0047 decisions 3 and 4), that the code which ends the step states the spend, and **nothing of what anybody does after it**.
- **`carry_out(operation, request, hw_profile, parameters, *, rtol, atol)`** - the signature of `ask`, no parameter with a default. It calls the operation once, through `hilclaw.check_operation.ask`, and:
  1. **Returns the result** `ask` returned, as it is (the same `dict` object or an equal one; say which).
  2. **`OperationAnswerInvalid` out of `ask`** (a returned value of neither form, a raised error): raises `EndedWithoutOutcome` with the `kind` and the `message` of that exception, unchanged.
  3. **A `ToolFailure` the one call of the operation raised** (an instance of a subclass included, of any kind): raises `EndedWithoutOutcome` with the pair `hilclaw.check_failure.ended_with(raised)` returns - today always the kind of ADR-0047 decision 4 with a message of that module; for a member of `BACKEND_KINDS` the raised kind and message. **How it is known that the operation raised it** (recommended): `ask` is handed a callable of this module that calls `operation(request, hw_profile, parameters)` with the three objects as they are, remembers the `ToolFailure` that call raised and raises it again as the same object; a `ToolFailure` out of `ask` is the operation's exactly when it **is** (identity) that remembered object. Another way is allowed if it draws the same line and the tests below pass.
  4. **A `ToolFailure` out of `ask` that the call of the operation did not raise**: not caught - the same object passes through. It is an error of this side (ADR-0047 Limits, sixth bullet; ADR-0045 Limits), and out of a step it leaves the step open by the convention of `hilclaw.journaled_step`. The docstring states this line as the module's own choice that the two records hand to the code, and says that an error on the line can fall on either side.
  5. **Everything else passes through unchanged**: the `TypeError` of `ask` for `parameters` that are not exactly a `CheckParameters`; what `from_answer` raises for a refused value of the five or of the tolerance; a `BaseException` that is no `Exception` out of the operation (ADR-0045 decision 5); a `BaseException` that is no `Exception` out of a read inside `ended_with`; the `TypeError` of `EndedWithoutOutcome` itself.
  6. **An `operation` that is not callable** raises `TypeError` before anything is called - the module's own check, since with the recommended wrapper `ask` would no longer see the object (keep the behaviour of `ask`).
  - **The raised exception holds nothing of what the operation raised**: `EndedWithoutOutcome` is raised after the handler has been left, so that neither its `__cause__` nor its `__context__` is the raised tool failure or the `OperationAnswerInvalid`, and (recommended, as `ask` does it) the frame of `carry_out` in its traceback no longer holds the raised tool failure. ADR-0047 decision 4: "Not decided: whether anything keeps the raised tool failure outside the log" - the module keeps nothing: no module variable, no file, no log call, nothing between calls.
  - No argument is modified; no file is read or written; no clock or random source is read; the operation is called exactly once per call of `carry_out`, and not at all when the check of point 6 or the `TypeError` of `ask` for `parameters` comes first.
- Docstrings: the module docstring says what the module renders (the rows of the table of ADR-0047 decision 8 that have an end line, by record and decision number), the choices that are the module's own (one exception for both causes; where the line is drawn and how the operation's own tool failure is told; that nothing of what was raised is kept), and what the module does not do: it is no tool and no step and is bound to none; it appends no line and states no spend; it selects no backend, draws no seed, reads no tolerance and no file of a run; it names no kind and no backend kind; it is this tool's and gives no rule for another tool; it says nothing of what anybody does after the answer.
