## Why
PLAN P1-1 (the FR-10 tool contracts, the mock backend, the conformance tests) is open. For `correctness.check` the landed records are ADR-0021 (the split, the seed, the tolerance), ADR-0038 (the execution points), ADR-0040 (the identity of a call), ADR-0041 (the dimensions), ADR-0042 (the members of a result), ADR-0043 (the form between the tool function and an operation), ADR-0044 (the mock's side), ADR-0045 (an answer of neither form), ADR-0046 (the number of draws) and ADR-0047 (a tool failure the operation raises). The code on `main` renders nearly all of them as pure modules bound to no tool; the last was `hilclaw/check_admission.py` (T-0144), the four answers between the selection and the start line.

**One stretch of a call has no rule: the draw of the seed.** Two things are open in it, and the tool function cannot be written - nor the last pure slice ahead of it cut - without them:

1. **Where the seed is drawn relative to the start line.**
   - ADR-0021 decision 3 (line 56): "The tool function draws the seed, once for each check, after ④ and after the answer of decision 4, and before the operation is called. A call that does not reach ⑥ draws no seed."
   - ADR-0040 decision 7 (line 103): "ADR-0021 decision 3 does not say whether the seed is drawn before or after the start line, and this record does not either: in both orders the start line holds no seed and the operation is called after both." Its table (line 98) has a row without a moment number for the draw, and its Walk-through (line 112) writes "④, the seed and the start line (their order: decision 7)". ADR-0041 (line 120) and ADR-0046 (line 160) repeat "The seed and the start line".
   - PROCESS/tasks/T-0126 (line 77) leaves it "to the callables of the later tool function", and the last follow-up of T-0144 asks the planner to judge "whether such a module would fix that order" before cutting the module that joins an `Admitted`, a seed source and an operation.
2. **What a call answers when no seed can be had.** ADR-0021 decision 3 fixes the source "as a property and not an algorithm" and says "How the source is bound, and whether a test binds one of its own, is the code task's"; no record says what a call answers when the source fails or names what is no seed. The code can already tell the case: `hilclaw.harness.seed_source.draw` raises `SeedSourceError` for it (an observation; the module "names no tool and no kind of tool failure"). T-0075 `## Result` handed the question on: "the task that adds the tool function of `correctness.check` ... decides what a call answers for `SeedSourceError`, and should not log a traceback of `draw` unfiltered."

The two hang together: before the start line, a failed draw can be answered with no line and the same request can be repeated; after it, a start line of the identity already stands, so the identity is open or must be ended. What a caller sees and what `events.ndjson` holds differ between the orders, so this is a part of the tool's contract and not a choice of names. **This task is the record for that one stretch.**

The task ticks **no PLAN checkbox**: P1-1 stays open, and the tool still cannot be registered after this record.
