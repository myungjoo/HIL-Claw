### Decisions of ADR-0003 (`ARCHITECTURE/decisions/ADR-0003-od16-harness-calibration.md`, 135 lines)
1. **Adoption and unit**: three-state calibration is adopted as an acceptance criterion of the verification harness; the unit is the **operation kind** (`kind` of ADR-0001), at any shape the tests choose. Reason: input generation and the reference differ per kind; "the harness as a whole" would let a calibrated `gemm` stand for the next kind, and "per rule" would follow the internal design of P1-3. Repetition per `dtype` / `layout` is left open (round-1 finding).
2. **The three states**: *the functional test* = the fixed-input check of S7 step 1 (inputs the author of a kernel can know), run by the calibration tests; *the contract* = the FR-9 clause (right within the tolerance on inputs the kernel could not know, those a verification run draws). Conforming: both hold. Failing: both fail. Violating: passes the functional test, violates the contract. The tests must show both halves for the violating kernel, otherwise it is a second failing kernel. The record neither requires nor excludes a fixed-input mode of the harness or a fixed-input step of a round.
3. **Required class in P1**: exactly one — **V1, output right only on inputs known in advance** (threat B ⑴), obliged by the FR-9 words "코더에 노출되지 않은 입력(shape/seed)으로 … 재검증". So a kind has at least the three kernels of PLAN P1-4. Not required, each with its reason in a table: B ⑵ (no separate kernel; the strengthened oracle is not adopted), B ⑶ (output is correct; static checks / profiler not adopted), B ⑷ ⑸ (forge the timing, not the output; OD-13 / rest of OD-16), B ⑹, threat A (process separation and write isolation are OD-8 / OD-14, open; "cannot modify" is a property of placement, not a verdict on a kernel), precision downgrade (outside the tolerance it is the failing state, inside it FR-9 admits it), the other S7 / B1 / B8 extensions, early-stop re-verification (a rule on when to verify, not a kind of kernel). The record adopts none of these defences and rejects none.
4. **"Caught"**: the correctness verdict only — conforming → pass, failing → fail, violating → fail. The harness need not name the cause nor tell failing from violating (failure-type tagging stays S7 step 3). A rejection by build error, crash or timeout is no evidence. The verdicts must not depend on a draw chosen to suit a kernel; reproducibility (whether a seed can be supplied) is the harness API and the code task.
5. **Nature and place**: hand-written, small, unoptimised test data of the harness's tests, in the kernel language of the backend (C for `cpu_standin`, #5 A-7 ②); not coder output, catalog entries, references or baselines; never in the data plane, the catalog or a spec; nothing depends on hiding them. Test rule ⑤ reading (rule unchanged): the verification harness is layer-2 product code, so its calibration tests are ordinary product tests under rules ①-④, with the failing and violating states as negative cases; no test targets a fixture or a test helper.
6. **When**: the calibration tests are part of the ordinary suite of the package. The set is extended in the same change that (a) adds an operation kind, (b) implements a later-adopted defence that changes the correctness verdict, or (c) makes verification draw shapes outside the op_signature. A skipped test is no evidence; calibration is a candidate content of the P0.5-1 C gate (workflow designed there). Not run per instance or round; the link to the pinned harness version is OD-11.
7. **Independence**: stated for any oracle and any tolerance under which the conforming kernel passes and the wrong outputs lie outside the tolerance; a test passes its tolerance explicitly (as an instance does) and never uses a default; no value or vocabulary is named. Where the functional test takes its expected outputs from is the code task's choice.
8. **Limits**: shows that the listed violations are caught on the kernels written for them, not that no loophole exists; says nothing about the classes not required, about timing, about seeds not being files or about the harness being unmodifiable. Hacker-fixer (complement) and the strength of the pre-promotion re-verification stay open.
