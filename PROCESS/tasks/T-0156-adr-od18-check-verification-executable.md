## Why

- `ARCHITECTURE/decisions/ADR-0021-od18-correctness-check-split.md` decision 2: "**The build of the verification executable is not the tool function's part.** ... Whether an operation builds at each call or is given something built, by whom and from which source, is not decided (ADR-0004 decision 3; OD-23; sub-question ⑩); neither is what a call answers when no verification executable can be had." and, of class (iii): "whether the tool function hands it over or the backend obtains it otherwise, and whether an operation is handed the data root (ADR-0016 decision 2 (d)), is the second record's".

- The one input that was missing is there since the last iteration: `ADR-0055-od23-coder-output-form.md` decision 3 (R1 to R8) gives, from the path of the `output/` of an attempt alone, the compiled set handed as `kernel_sources`, the predicate "this attempt has a kernel source", and a third outcome (a failure of the reader). The planners of T-0152 to T-0154 had each declined this record because it "would have to invent" where the kernel is; that reason is gone.

### The record (one new file `ARCHITECTURE/decisions/ADR-NNNN-od18-correctness-check-verification-executable.md`, next free number on `origin/main` at execution time)
English; the "Record format" of ADR-0001 as ADR-0043 and ADR-0047 use it (Status with its limits, Context, Decision, a short Walk-through, Limits, Alternatives considered, Consequences, Boundaries, References); about 150 to 200 lines. Any example is fenced as `text` or `json`, never as C, Python or shell that a gate would read. **Three kinds of content, said at the head of the Decision section**: the owner's sentences (quoted, marked **owner**, linked; not subject to the objection window), what an earlier record or a requirement says (**cited**, with its decision number), and the record's own design (not confirmed by the owner). For every point give the choice, the alternatives weighed and one or two lines of reason.

The Decision section answers these points and only these:
1. **Scope and terms.** A call of `correctness.check` about one attempt of a run that ADR-0021 and ADR-0038 decision 6 cover (the first case, and a run at the mock), from the moment the tool function has selected a backend to the moment an operation has a verification executable it can start - or has none. Say what the record is not: not the roster, not who holds a role, not when a round calls the tool, not the run tools (`sim.run`, `board.run`: the timing executable is theirs), not any flag, compiler, language standard or time-limit value, not a sandbox.
2. **Limits**, each written before the statement it limits: nothing was built or run; the reader of ADR-0055 does not exist as code; what is found below `output/` is a place, not an honest source (ADR-0055 L1, L2), and a build compiles whatever is there; a finished bring-in cannot be told from a dead one (ADR-0055 L5; T-0155 note (4)) - say whether that matters for a build started from `output/` or register it; the kernel's process stays as unprotected as ADR-0017 decision 10 says.
3. **Which side comes to the kernel source of the attempt.** Weigh at least: (a) the tool function applies the reader of ADR-0055 to the `output/` of the attempt (it has the data root and the three numbers) and hands the operation the compiled set; (b) the tool function hands the operation the data root, or the path of the attempt's `output/`, and the operation applies the reader; (c) the backend obtains it by a way of its own. For the choice say: **what crosses the cut** and, as ADR-0043 decision 2 asks, for each thing handed over whether it is a further value of the check parameters or a further thing beside them, with the table of ADR-0043 decision 7 restated as amended (ADR-0043 itself is not edited); what the mock's operation and a script are then called with (ADR-0044 decisions 2 and 6; a run at the mock has no kernel source and no `output/` need exist - say what is handed for it and what the default script does with it, or that it is not looked at); whether an operation is handed the data root (ADR-0016 decision 2 (d)); and at which moment of ① to ⑦ the reader is applied.
4. **Built at the call or before it, and where the executable lies.** Weigh at least: (a) the operation of `cpu_standin` builds at each call (two checks of an attempt are then two builds, beside the builds of the run tools - state the cost as ADR-0017 decision 2 states its own); (b) something built before the call by another step is handed over or found; (c) a cache keyed by the source that can be built again (ADR-0016 decision 2 (c) allows one - say what would have to hold). For the choice say **where the executable is written and how long it lives**, in a way that keeps it out of every git-tracked tree (C-3; ADR-0004 decision 7; ADR-0055 decision 7) - whether it is ever a blob of the CAS or is removed when the call ends is part of the answer or is registered - and what is true of the directory the build and the process run in. **Flags, trailing flags, the compiler, the build time limit, the process time limit and the environment**: say for each *through which side* the operation has it (handed, or the backend's own) or that this stays open, and **fix no value and no source** (OD-6 sub-question ②, OD-14, OD-16 sub-question ⑥).
5. **The situations in which there is no executable, as a closed list.** At least: the attempt has no kernel source (ADR-0055 R1 to R4, including no attempt directory and no `output/`); the reader fails (R8); the compiler is not found; the build ends not ok - a compile or link failure; the build passes its time limit; the place for the executable cannot be made or written; the built executable cannot be started. Say for each which side finds it and at which moment.
6. **What the call answers in each situation.** For each: a **result** or a **tool failure**; if a tool failure, its kind and whether it is answered **before the start line** (no line, nothing consumed, the same request can be repeated - like the answers of ④ and `seed_not_drawn`) or **from an end line with a `failure`** (the identity is ended and a further check is a further `execution` - ADR-0047 decision 3), and whether the kind is one the tool function raises or a **backend kind** in the sense of ADR-0047 decision 5 (named "with the situation it means"). Weigh the reasoning of ADR-0021 decision 5 for both readings of a compile failure: it is a property of the attempt ("said of a kernel that crashes or hangs, [a tool failure] would have a caller read a property of the attempt out of a failure of the tool"), and it is not one of the four conditions of a verification run. **If the defensible answer for a situation is a result, it needs a value or member ADR-0042 does not have - that is the guarded exit of that situation, not a decision of this record.** State what a message may carry (the manner of ADR-0045 decision 6 and ADR-0048 decision 6: nothing of the compiler's log or of a path below the attempt, or say which and why) and that nothing is said about what anybody does after the answer.
7. **The order of a call**, the table of ADR-0048 decision 10 again with the rows this record changes or adds marked in bold and every other row abridged by citation; and, separately, what a repeated call finds for each new answer.
8. **How far OD-18 sub-question ⑩ is answered.** One line per clause: the first (how an operation comes to the executable) and the second (the answer when none can be had) - answered, or which part; the third (backend kinds) - which kinds this record names, and that the kinds of a board, a simulator or another machine stay open (OD-10, #5 B-2); the kernel-language clause and the other-accelerator clause - **not answered**. Also one line each for ADR-0055's "who builds, when" (which part is answered for this tool; the run tools are not) and for T-0155 note (1) (the reader's three outcomes).
9. **Consequences**, not decisions: what the next slices of the contract must still add (the list of ADR-0048 Consequences with what this record strikes off); the code slices that can be cut once CI runs again (the reader of ADR-0055 first; then the operation of `cpu_standin` for this tool and the last part of `hilclaw.check_tool` - names and modules are the code task's; D12 rules; what `hilclaw/check_operation.py`, `hilclaw/check_parameters.py` and `hilclaw/mock_check.py` pin today that such a slice changes); the sentences of earlier records and docstrings that become less exact (listed, none edited); the A-13 reading, said precisely as ADR-0047 says its own; any **runtime acceptance item** (a fact only a real machine of C-7 with a compiler and a real kernel can show and that no test in CI could - list in the form of ADR-0055's bullet, or say there is none; a fact a test with clang alone can show is a note for the code task, not such an item).
