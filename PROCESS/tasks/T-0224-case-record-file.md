## Why

## Acceptance Criteria

### `hilclaw/cases_file.py` (new; Python, as the rest of the package)

Public names are the executor's; the suggested ones mirror `hilclaw.verdicts_file`. The reasons for any departure go into the commit body.

- **Exceptions**: `InvalidCaseFileError(ValueError)` (a content breaks the text form or a rule of ADR-0072 decisions 2 and 3; what `hilclaw.cases.validate` raises is wrapped with its message unchanged and chained), `UnsupportedVersionError(Exception)` (no `ValueError`), `WrittenFormError(ValueError)` (no `InvalidCaseFileError`), `NameTakenError(Exception)` (no `OSError`). Import nothing private from `hilclaw.verdicts_file`, `hilclaw.hypotheses_file`, `hilclaw.spec_file` or `hilclaw.cases`: small private helpers of its own. A shared helper module is **out of scope**.
- **`parse(content)`** returns the document of `content`, the bytes of a case file, as `json.loads` gives it (a new `dict`; nothing added, defaulted or repaired; `content` not kept or modified). In this order, as `verdicts_file.parse`:
  - `TypeError` for a `content` that is not exactly `bytes`;
  - `InvalidCaseFileError` for a UTF-8 byte order mark; for a content that is not UTF-8 or not exactly one JSON text (`NaN`, `Infinity`, `-Infinity` refused; an empty content is invalid, ADR-0072 decision 2 line 49); for a member name twice **in any object**, unknown members and both copies included; for nesting too deep or an integer literal this interpreter cannot read (a limit of the reader, said so in the docstring); for a text that is no object;
  - `UnsupportedVersionError`, before anything else is validated: when the case's `schema_version` is an `int` from 0 to `hilclaw.keys.MAX_INTEGER` other than 1 and is not written `-0`; then, the case's version being 1, when `hypothesis_record` is an object whose `schema_version` is such an `int`; then likewise for a present `verdict_record` (ADR-0072 decision 2 line 48; OD-11). The message names the field path (`schema_version`, `hypothesis_record.schema_version`, `verdict_record.schema_version`). Nothing else of such a content is interpreted;
  - `InvalidCaseFileError` for a document `hilclaw.cases.validate` refuses (message unchanged, chained);
  - `InvalidCaseFileError` for `-0` at an *integer* place: below the case's defined top-level members `schema_version`, `run_id`, `round`, and below the **defined top-level members of each copy** (hypothesis record: `schema_version`, `run_id`, `round`, `candidates`, `hypotheses`; verdict record: `schema_version`, `run_id`, `round`, `verdicts`), with the field path prefixed by the member name (`hypothesis_record.hypotheses[0].basis[0].ref.round: ...`). Below an unknown top-level member of the case or of a copy, ADR-0072, ADR-0059 and ADR-0071 set no rule for a number: a sign, a fraction, an exponent, `-0` or a large integer there is accepted and returned as parsed (state this in the docstring, as `verdicts_file` does). This keeps the copies under the same text rule their source files obey through `hypotheses_file` / `verdicts_file`.
- **`final_name(data_root, hw_profile_key, op_signature, document)`** (suggested signature; ADR-0072 line 31: "derived from the content's `run_id` and `round` below the key directory the write is given") validates the document with `hilclaw.cases.validate` (its `InvalidCaseError` passes through, a document of another `schema_version` included) and returns `hilclaw.layout.case_record(data_root, hw_profile_key, op_signature, document["run_id"], document["round"])`. A bad key name or a valid `run_id` that is no run directory name raises `hilclaw.layout.InvalidPathValueError` (passes through). This is the rule "the name is formed from its `run_id` and `round`" of ADR-0072 decision 2 line 47 for whoever holds both: `final_name(...) == path`; no function takes a path. Nothing is read, created or resolved; the document is not modified. Whether the key directory is that of the run's instance (decision 1 line 24) is a rule between files and is not checked (docstring).
- **`write(data_root, hw_profile_key, op_signature, content)`** puts `content` under `final_name(data_root, hw_profile_key, op_signature, parse(content))` if that name is free and returns `None` - the steps of ADR-0029 decisions 4, 6 and 7 with this final name, **without** decision 5 (ADR-0072 line 31). In this order, nothing created at any point except the temporary file: what `parse` raises; what `final_name` raises (`InvalidPathValueError`; `TypeError` for a `data_root` that is no path); `WrittenFormError` when the content does not end with a line feed or holds a carriage return byte; `FileNotFoundError` / `NotADirectoryError` when the **key directory** `layout.op_signature_dir(...)` is not an existing directory - a missing `data_root`, `db/`, hardware directory or key directory included; **no directory is ever created** (ADR-0072 line 32). Then `hilclaw.once_write.write_once(path, content)` gives the name - temporary file `case-<run_id>-<RRRR>.json.<token>.tmp` in the key directory, stable storage, hard link with no fallback to a replacing rename, temporary file removed. A taken name raises `NameTakenError` (equal bytes reported as any other; the entry under the name never opened, read or compared; nothing retried). Any other failing step raises its `OSError` unchanged. **The write reads no other file** (ADR-0072 line 31): not the source files in `runs/`, not `instance.json`, not `op_signature.json` / `hw_profile.json` - so a case can be written into a key directory that holds no record file (the limit ADR-0072 line 32 states; say so in the docstring).
- **Module docstring** in the style of `hilclaw/verdicts_file.py`, no longer than it needs to be (it may refer to `hilclaw/verdicts_file.py` or `hilclaw/hypotheses_file.py` for a convention stated there): which record and decisions it implements; the rules `parse` holds and their order, the copy versions set apart, the number rule below unknown members; the steps `write` holds and that it creates no directory; the limits of `write` (ADR-0029 decision 7: POSIX systems with hard links; nothing stated for a network file system, WSL on a Windows drive or native Windows; two writers not prevented); and what it does **not** do: no file read, no directory listed or created, no "same content", no content composed (`hilclaw.cases.build` gives a document; turning it into bytes is the caller's), no lock, no commit; it does not check that the key directory is that of the run's instance, that the copies equal the source files in `runs/`, or that a *ref* names an attempt that exists; it reads no other version (OD-11); and promotion (whether, when and by whom a round is promoted, whether a round without verdicts is promoted, what a second case write after a taken name means; OD-29, OD-23, OD-25, NFR-1, OD-17), the lookup and the `basis` kind `case` are open (ADR-0072 Boundaries). It is no tool, no hook and no CLI entry. No comment beyond the docstrings (CLAUDE.md "코멘트 최소화").
- **No change** to `hilclaw/cases.py`, `hilclaw/layout.py`, `hilclaw/once_write.py`, `hilclaw/verdicts_file.py`, `hilclaw/hypotheses_file.py`, `hilclaw/spec_file.py` or any other module. If the slice cannot stand without such a change, stop and report why in `## Result` (BLOCKED "requirement-unclear" if needed).
