## Why
ADR-0034 (landed as `576ea8c`, T-0104) fixed the two members of `runs/<run_id>/instance.json` in which a run states its owner and its project: the top-level members `owner` and `project`, each a *string* of ADR-0001. Its Consequences cut one code slice:

> **The code slice that can now be cut** (within the size cap, code mode): in `hilclaw/instance.py`, the validity of the two members by decision 3 and readers of the owner and of the project of a run beside `wall_clock_budget_s_of`, with tests in `tests/test_instance.py`. The names and the return form of the readers and how "not stated" is told from a value are the code task's. **Binding a reader to a tool, to a hook, to `db/`, to `STATE.json` or to anything that lists, groups or allows is not part of that slice**, and neither is writing the file. `hilclaw/instance_file.py` takes the validity of a content from `hilclaw.instance.parse`, so it refuses a content with an invalid member once the slice lands, without a change of its own.

**This task is that slice.** Today `hilclaw/instance.py` defines nine members (`schema_version`, `hw_profile`, `tolerance`, `source_commit`, `n_max`, `candidates_per_round`, `op_signature`, `round_budget`, `wall_clock_budget_s`); an `owner` or a `project` of any value - `""`, `7`, `null`, a string with a line feed included - is handed back uninterpreted in `Instance.others`, the file counts as valid, and nothing in the package can answer "which owner, which project does this run state".

It serves PLAN P1-8 ("런타임 STATE/instance/events 스키마"). It ticks **no PLAN checkbox**: P1-8 stays open (further members, the writer and the start of an instance, the result files, the rest of `STATE.json`, the event kinds).

The second says nothing about the first, and "project" never means this repository.

### The validity of the members (ADR-0034 decisions 3 and 4)
- `owner` and `project` join the members the module defines (`_DEFINED`), so neither is handed back in `others` any more.
- A present member is valid exactly when it is a `str` (exactly `str`: for a value built in memory a subclass of `str` and a `bytes` are none) of 1 to 255 characters, each one from U+0020 to U+007E. `"example-owner"`, `"Example-Owner"`, `"a b"`, `"x/y"`, `"user@example.invalid"`, `" "`, a string of spaces only, `"~"`, a string of one character and a string of exactly 255 characters are values. `""`, a string of 256 characters, a string that holds a line feed, a carriage return, a tab, U+007F, U+0000, U+00E9 or a Hangul letter - **at any position, the last included** -, `null`, `true`, `false`, `7`, `0`, `1.5`, an array and an object are none.
- **The whole string must match**: a value followed by a line feed (`"example-owner\n"` after decoding) is none. A pattern used with `match` and `$` would accept it; use a whole-string match, as `hilclaw/keys.py` does.
- **The value is the string after JSON decoding** (ADR-0034 decision 3): the text `"A"` states the value `A` and is valid; the text `"\u000a"`, `"\t"`, `"é"` and an escaped lone surrogate (`"\ud83d"`) each decode to a character outside the range and make the content invalid. No rule of the text beyond that is added.
- A present and invalid member raises `InvalidInstanceError` naming the place `owner` or `project`; nothing is returned, so no member of that content is used (the other of the two, `hw_profile` and every other member included), and nothing is repaired. Recommended message, in the manner of the module and of `hilclaw/keys.py`: `owner: must be a str of 1 to 255 printable ASCII characters, got <type name>` (a `str` shown as the module shows every `str`, through `reprlib.repr`, a long one shortened), and the same with `project`.
- The two are valid independently of each other: a file may state either, both or neither, with equal or with different values (`owner` and `project` of the same string is valid). No pair is refused.
- The members are checked after `wall_clock_budget_s`, `owner` before `project` (recommended: the order in which the records defined the members and in which ADR-0034 names the two). When both are invalid, the first is reported. Another `schema_version` is still `UnsupportedVersionError` before either member is looked at. The text rules (a member name twice) stay text rules.
