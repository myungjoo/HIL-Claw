## Why
ADR-0004 (`ARCHITECTURE/decisions/ADR-0004-od8-data-plane-layout.md`) fixed the **place** and the writer of the event log: `runs/<run_id>/events.ndjson`, "events of the run in the order they happen; an expensive result is appended as soon as it exists (#4 §3b)", written by the tool layer, append only. It fixed **no field**: its path table says "Fields: PLAN P1-8, OD-17", and its Boundaries and the OD-8 register row list "각 파일의 필드·스키마" as the open rest of OD-8.

So nothing says how one event is written down: what a line is, which members every line carries, how the line says what it is about (round, candidate, attempt), what a reader does with a line a dying process left half written, and what "append only" allows. PLAN P1-8 (runtime `STATE.json` / `instance.json` / `events.ndjson` schemas) cannot start in code without these choices, and the FR-10 tools of PLAN P1-1 need the log to journal an expensive result (#4 roster revision: "비싼 결과의 저널링은 도구 계층에서").

Owner decision D6 (DRIVER §9) lets the driver close **design-level** ODs by a decision record (ADR) + a context-isolated reviewer's Approve + an owner notice with a 7-day objection window. This task writes that record for **one part of the rest of OD-8: the line format and the envelope of `events.ndjson`**, and keeps the ARCHITECTURE documents consistent with it. It is the first slice of the PLAN P1-8 schemas and ticks **no PLAN checkbox**. The appender / reader module is a later code task. ## Acceptance Criteria
What is **fixed** and must be taken as input, not re-decided:
- ADR-0004: the path `runs/<run_id>/events.ndjson`, one file per run; written by the tool layer, append only; it holds the events of the run in the order they happen; an expensive result is appended as soon as it exists; appends happen at run level, also after a round has ended (decision 2); the layout version is in `instance.json` (decision 9); the tree gives no concurrency control and no atomicity (decision 10).
- #4 §3b and the roster revision: the purpose of the immediate append is that an expensive result (a board measurement, C-4) is **not lost** when the process dies between the measurement and the round's commit, so that a fresh turn can skip the finished substep. Journaling is done by the tool layer, not by a model's action.
- #4 §1: `STATE.json` is the single entry point; no whole-directory scan.
- ADR-0002: `round` is a non-negative integer (`0` = bring-up), `candidate` and `attempt` are integers starting at 1. ADR-0001: the *name* form.
- NFR-7 ②: a persistent artefact carries a `schema_version`. NFR-2: the history of the data repository is the audit record and is not rewritten. #5 A-3: the local commit is the durability boundary; nothing pushes automatically. C-2: P1 assumes a single run.
- The file name says NDJSON: newline-delimited JSON.

What the ADR **decides** (this part of the rest of OD-8: the line format and the envelope). The content of each decision is the executor's to work out and justify from the fixed inputs; the reviewer's Approve is what confirms it. For every point give the choice, the alternatives considered and one or two lines of reason; mark every choice no source gives as this record's own:
1. **Scope**: the record fixes what one line of `runs/<run_id>/events.ndjson` is and which members every line carries — and no event type, no payload and nothing of any other file.
2. **Line format**: one JSON value per line and of which kind, the encoding, the line terminator, whether blank lines or a header line may exist, and that the first line is an event like any other or not (a header line would be a second kind of line — argue it together with point 8).
3. **Envelope members**: for each member — name, value type and form, required or optional, and whether a source gives it or it is this record's own. Consider at least: the kind of event (the form only — for example the *name* form of ADR-0001 — and **no list of values**); what the event is about (`round`, and `candidate` / `attempt` where the event concerns one, as the integers of ADR-0002; whether an event may concern the run as a whole); one member that holds everything specific to the kind (its content left entirely to the tasks that define kinds); a time. For the time: whether the envelope has one and in which form — ADR-0005 left the time form of `gc_at` open, so say whether this record fixes a form for the log only or leaves it open too, and why. Prefer the minimum: add a member only if a reader could not otherwise do something a requirement asks for.
4. **Order**: what the order of lines means (the order of appending), whether a sequence member is needed in addition, and what a reader may and may not conclude from the order (single run, C-2; no lock yet).
5. **Append only**: which changes the file may undergo — a line is added at the end and is never edited, removed or reordered (NFR-2) — and how a later fact about an earlier event is recorded (a new line). State the one exception point 6 may need, if any.
6. **A torn last line** (NFR-1): a process can die in the middle of an append. Say what a reader does with a last line that is not terminated or does not parse, what the next writer does before it appends, and that a damaged line anywhere else is an error. The choice must keep "never rewritten" true for everything that was ever committed.
7. **The log and the result files**: ADR-0004 also gives each attempt `sim.json`, `board.json`, `profile.json` and `eval.json`. Fix only the relation that #4 §3b needs: what must be true of the event of an expensive result so that the result can be recovered from the log alone after a process death (it carries the result or it names where the result already is — choose and argue), and that the log does not replace those files. Which results count as "expensive" beyond the board measurement, and the fields of the result itself, are **not** decided here.
8. **Versioning**: where `schema_version` stands for a file that is a sequence of lines (per line, a first line, or `instance.json`), version 1, when it is raised, its relation to the layout version of ADR-0004 decision 9, and that reading an older version is OD-11 — refer, do not decide.
9. **Room for OD-17**: show in two or three lines that the envelope does not exclude the registered proposal (an `intent` event before a spend and a `result` event after it tied by an idempotency key; a budget derived by folding the log; fold snapshots) — **without adopting, rejecting or detailing any of it**.
10. **Durability and limits**: what an appended line guarantees before the next commit and what it does not (process death versus machine loss, #5 A-3), and what the format does not guarantee (no concurrency control, no atomicity with the result files or with `STATE.json`, no completeness check).
