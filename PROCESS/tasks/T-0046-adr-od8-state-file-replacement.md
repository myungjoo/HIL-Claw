## Why
PLAN P1-8 ("런타임 STATE/instance/events 스키마 — OD-8 종결 필요(§9 ADR 경로)") has, for the runtime `runs/<run_id>/STATE.json`: the record of the file (ADR-0012), the pure functions (`hilclaw/run_state.py`, T-0043) and the reader over the files of a run (`hilclaw/run_journal.py`, T-0045). **Nothing writes the file to disk yet**, and the write cannot be coded without choices that no record makes:

- **ADR-0012 decision 6** states a requirement and no way to meet it: "a death of the writing process leaves the previous content or the new content, never a part of one. The technique, and whether the agent writes through a tool of the package, are left to the code task and to OD-23."
- Every portable way to meet it puts a second, short-lived file next to the final one (a rename is one step only inside one file system). **ADR-0004** says of that place: decision 2, "Directly under `runs/<run_id>/` are the four run-level files and `rounds/`"; decision 7, scratch and temporary *directories* are no path of the tree, "their content is never committed", and where they are "is decided with the isolation means" — which waits for owner facts. Decision 10: the tree "makes no write atomic beyond what a git commit gives". So a temporary file beside `STATE.json` is a statement about what may exist in the data plane, what a commit takes and what a reader makes of a leftover — the kind of rule ADR-0006 decision 6 wrote for a torn tail. A code task that chose it as a "provisional convention" would be deciding a rule of the data plane without a record.
- **Sub-question ⑩** (what writes the first file; a run directory without it) and **⑫** (whether a writer keeps a top-level member it does not know) were registered by ADR-0012; a write function meets both on its first line (no previous file; the members it was not given). 1. **Scope**: the replacement of `runs/<run_id>/STATE.json` on disk — how the requirement of ADR-0012 decision 6 is met — and nothing else of the file, of other files or of who writes.
2. **The technique**, as a rule and not as code: the sequence of steps that makes a death of the writing process leave the previous or the new content (for example: the whole new content into another file of the same directory, brought to stable storage, then moved over the final name in one step). 5. **What the rule promises and what it does not**: the death of the writing process versus the loss of the machine or of power (ADR-0006 decision 10; #5 A-3); whether bringing the content, and the directory entry, to stable storage is required or left to the writer, with the cost stated; whether the writer must hold a content valid by ADR-0012 before it replaces the file; what a reader sees while a replacement is in progress; the environments of C-7 (say what holds outside them, for example on Windows, only as far as you can state it from the documentation of the platform — otherwise name it as a limit). ### Decisions of ADR-0013 (`ARCHITECTURE/decisions/ADR-0013-od8-state-file-replacement.md`, 139 lines; the change is 151 insertions, 10 deletions, 4 files — inside the 300 LOC / 5 files cap)
1. **Scope**: how `runs/<run_id>/STATE.json` is replaced on disk so that the requirement of ADR-0012 decision 6 holds; no member, type or validity rule, no other file, nothing of who writes.
2. **Technique** (the record's own; POSIX `rename` cited): ① the writer holds the whole new content, valid by ADR-0012 decision 6, before it touches the file system (an invalid content would replace the last valid one of the working tree); ② it creates the temporary file in the same directory as a new file and writes the whole content; ③ it brings the content to stable storage (`fsync`) and closes it; ④ it renames the temporary file over `STATE.json` in one step — the only step that changes what the final name holds; ⑤ on a failure while it lives it removes its temporary file and reports. The final name is never opened for writing; no backup, no marker. Alternatives rejected: writing in place, a backup beside an in-place write, a temporary file on another file system, relying on the last commit alone, no check of the content.
3. **Temporary file**: place `runs/<run_id>/` (one file system, so the move is one step); name form `STATE.json.<token>.tmp` with `<token>` = `[a-z0-9-]{1,64}`, **different per write** — with one fixed name two writers would share the file and a mix of two contents could reach the final name, worse than the limit ADR-0012 decision 7 states. It is none of the four run-level names, not `rounds`, and no member of `layout.RUN_FILES`. **Readings of ADR-0004** (argued, nothing edited): decision 2 is a statement about the tree (files with a meaning, that a reader looks for, that a commit holds); decision 7 is about scratch, temporary and build-cache *directories* in which an actor works, and their place is neither decided nor narrowed; decision 9: layout version 1 unchanged. Never committed: the rule binds the committing step; the existing `*.tmp` line of the data repository's `.gitignore` is cited as a fact and is a second guard only. No change to the data repository is made or required.
4. **A leftover** is not state: never read in the place of `STATE.json` (also when that file is missing or invalid), never moved over the final name, never committed. A reader opens the final name only and lists nothing (#4 §1). A writer removes its own file on a failure; removing a dead writer's leftover is allowed to the writer and not required (cost: one small file per death stays until removed).
5. **Promised**: the death of the writing process (and of the agent that asked). A reader during a replacement sees the old or the new file. **Not promised**: machine, power or working-tree loss (#5 A-3; ADR-0006 decision 10). The flush of the content is required nevertheless (a file system may make the name durable before the content; cost: one flush of a small file per write); the flush of the directory entry is not. Holds on the native file systems of the C-7 environments; a network file system, a Windows drive seen from WSL and native Windows are limits. Two writers stay a limit (rest of OD-17). The restore of the file from the history is not a replacement and stays undecided.
6. **First file**: "the previous content" is the missing file (ADR-0012 decision 2); the same five steps; a replacement **may create** `runs/<run_id>/` and requires no other file (requiring it would decide the open part of sub-question ⑩). Reading of ADR-0004 decision 1: a death inside a first replacement can leave a run directory with a leftover only, or with nothing, in the working tree; no commit holds one, and for a reader it is a missing file. Who writes the first file, when in relation to `instance.json`, and what a run directory without the file means stay open.
7. **Sub-question ⑫ stays open** (outcome (b) of the task): the replacement and a package function performing it write exactly what they are given, as `run_state.dump` does. No rule "keep" or "drop" is chosen: either is wrong for some member later records may define (a dropped member another component relies on; a carried-over marker that was only true before the write). A member's own record or OD-11 decides. The round-trip limits of `hilclaw/run_state.py` are therefore not met by a package function, and what the validator accepts does not change.

### Death moments (table in the record; throw-away script outside the repository, not committed)
The script performed the five steps with `layout.run_file`, `run_state.dump` and `run_state.parse` on a temporary directory and stopped at each moment, for a first file and for a later one: stopped with a partial temporary file → the final name is missing (first) / parses as the old content (later), one leftover; stopped with a complete temporary file → the same; after the move → the new content, no leftover. At no moment did the final name hold a part of a content; no leftover name is in `layout.RUN_FILES`. The script simulates a death by returning between steps (on native Windows, the machine of this clone); it does not kill a process.
