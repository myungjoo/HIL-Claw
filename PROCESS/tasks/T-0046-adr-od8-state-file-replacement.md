## Why
PLAN P1-8 ("런타임 STATE/instance/events 스키마 — OD-8 종결 필요(§9 ADR 경로)") has, for the runtime `runs/<run_id>/STATE.json`: the record of the file (ADR-0012), the pure functions (`hilclaw/run_state.py`, T-0043) and the reader over the files of a run (`hilclaw/run_journal.py`, T-0045). **Nothing writes the file to disk yet**, and the write cannot be coded without choices that no record makes:

- **ADR-0012 decision 6** states a requirement and no way to meet it: "a death of the writing process leaves the previous content or the new content, never a part of one. The technique, and whether the agent writes through a tool of the package, are left to the code task and to OD-23."
- Every portable way to meet it puts a second, short-lived file next to the final one (a rename is one step only inside one file system). **ADR-0004** says of that place: decision 2, "Directly under `runs/<run_id>/` are the four run-level files and `rounds/`"; decision 7, scratch and temporary *directories* are no path of the tree, "their content is never committed", and where they are "is decided with the isolation means" — which waits for owner facts. Decision 10: the tree "makes no write atomic beyond what a git commit gives". So a temporary file beside `STATE.json` is a statement about what may exist in the data plane, what a commit takes and what a reader makes of a leftover — the kind of rule ADR-0006 decision 6 wrote for a torn tail. A code task that chose it as a "provisional convention" would be deciding a rule of the data plane without a record.
- **Sub-question ⑩** (what writes the first file; a run directory without it) and **⑫** (whether a writer keeps a top-level member it does not know) were registered by ADR-0012; a write function meets both on its first line (no previous file; the members it was not given). 1. **Scope**: the replacement of `runs/<run_id>/STATE.json` on disk — how the requirement of ADR-0012 decision 6 is met — and nothing else of the file, of other files or of who writes.
2. **The technique**, as a rule and not as code: the sequence of steps that makes a death of the writing process leave the previous or the new content (for example: the whole new content into another file of the same directory, brought to stable storage, then moved over the final name in one step). 5. **What the rule promises and what it does not**: the death of the writing process versus the loss of the machine or of power (ADR-0006 decision 10; #5 A-3); whether bringing the content, and the directory entry, to stable storage is required or left to the writer, with the cost stated; whether the writer must hold a content valid by ADR-0012 before it replaces the file; what a reader sees while a replacement is in progress; the environments of C-7 (say what holds outside them, for example on Windows, only as far as you can state it from the documentation of the platform — otherwise name it as a limit).
