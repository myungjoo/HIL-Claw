### The choice as landed (`ARCHITECTURE/decisions/ADR-0049-od8-coder-call-isolation-means.md`, 169 lines)
- **Scope**: one coder call of the first case (`cpu_standin`, C kernel, clang) and the files of the data plane around it; judged again when #5 B-1 is answered. Builds on and falls with ADR-0004; decision 4 and the row of sub-question 26 (ii) are revisited if ADR-0029 is reverted.
- **The means (the record's own design)**: four properties. P1 the coder process and everything it starts run inside one container. P2 exactly one host directory is writable from inside, the scratch of the call, and nothing else that lets the container change the host is given to it (the network is not part of P2). P3 what the coder is given is copied into the scratch before the call, and what it produced is brought from the scratch into `output/` after the call by the side that holds the `coder/` role. P4 the container is removed when the call has ended and the scratch once the bring-in has finished or been given up, without following a link out of the scratch. Without a container runtime no coder call is started; there is no fallback without the boundary. Docker first, because only Docker's documentation was read (the owner's part 3 allows a Docker-based means).
- **Per registered item**: candidate ① item 1 - already a property of paths (ADR-0004), enforcement left; item 2 - taken for the coder process, left for other actors; item 3 - taken for the coder process, left for other actors; item 4 first half (coder behind an OS boundary) - taken in its container form, "read-only mount of the repository" not taken as a requirement; item 4 second half (`PreToolUse` path check) - left (OD-18); item 5 (per-agent allowlists) - left (OD-23). Candidate ② - taken as the crossing; its "no container needed" property is not used; whole files or a diff is the form of `output/` (OD-23).
- **Write root**: one new scratch directory per call, outside both checkouts and no path of the tree of ADR-0004 (this settles ADR-0004 decision 7 for the coder call); temporary files and build caches are in the scratch or in the container's own file system. Location and name are the code slice's.

### The limits (decision 5 of the record)
- G1 is conditional: while P1 and P2 hold, the coder process can change no host file outside its scratch *through the file systems the container is given*. G2 is a property of the bring-in only (it reads the scratch of its call and nothing else).
- L1 the boundary is the container runtime's and was tried on no machine. L2 only Docker's documentation was read; a mistake in how the container is started undoes G1 and there is no second line. L3 a generated kernel is built and run outside the boundary by unprotected processes, so **threat A of OD-16 is not removed**. L4 the network is not restricted; a change made through a reachable service is not covered. L5 what the coder process needs to run (its sign-in included) is readable inside and can be sent out; whether `claude -p` runs with one writable host path is not verified. L6 per platform: image toolchain against host toolchain not verified; file ownership and mode bits on Linux not verified; on macOS a coder cannot try its kernel on the measured platform (the record's inference from one Docker sentence); the runtime on Windows with WSL is not decided. L7 no time or resource ceiling. L8 content and names are untrusted and unfiltered; what a coder could read can be brought into `output/` and committed. L9 leftovers of a dead process. L10 when the boundary fails nothing in the record notices. L11 the user who runs an instance must control a container runtime, which is itself a way to change the host.
