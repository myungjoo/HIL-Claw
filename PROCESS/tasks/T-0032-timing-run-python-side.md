## Why
**ADR-0009** (`ARCHITECTURE/decisions/ADR-0009-od13-cpu-standin-timing-run.md`, landed as `39660cf`, T-0031) fixed how the timing samples of one measurement are taken from a C kernel at `cpu_standin`: a C driver program built with one kernel into a *timing executable*, run as a process of its own, which reports `resolution_ns` / `interval_ns` / `stop` lines; and a *Python side* that starts the run, reads the report and is **the authority** on the stopping rule by replaying `stopping_state` on every prefix (decisions 7 and 8). Its Consequences name the code task: "the driver source in C and the Python side under `hilclaw/harness/`" and add: "The parsing and the replay can be tested everywhere with a stand-in program."

That code task does not fit one task: the C source plus the Python side exceed the cap of 300 LOC (DRIVER §5, D4), and the two halves are verified differently. So it is split (planner, DRIVER §6):
- **This task (slice 1)**: the Python side for an *already built* timing executable — the argument list handed to the driver program, the run through `hilclaw/local_run.py`, the parser of the report, the replay, and the completed / broken result. It is fully verifiable in the driver clone's environment, which has **no C compiler** (`clang`, `gcc`, `cc` absent on PATH, checked 2026-10-07): the tests use a stand-in program written in Python.
- **Next task (slice 2, not this one)**: the C driver source under `hilclaw/harness/`, the function that builds a timing executable with `clang_build.build`, and tests with a real clang, which run on CI only (the `ubuntu-latest` runner has clang: the 5 real-clang tests of `tests/test_clang_build.py` run there). It writes the C side against the command line this task fixes.

Doing the Python side first means the interface between the two halves (the command line and the report) is pinned by tests before a C file exists, and the C task has an oracle for its output.

**It ticks no PLAN checkbox** (P1-2 "타이밍 수집" and the timing half of P1-3 stay open until slice 2; P1-3 as a whole stays "오너 확정 필요" for its oracle and tolerance).

In P1 the verification half of P1-3 and P1-4 wait for owner items (#5 A-7 oracle, B-7), P1-1 for OD-10 / OD-18 / OD-23, the rest of P1-8 for OD-17 / #8 M7. Capabilities (provisional names and shapes; the executor may rename or regroup, but each capability must exist and every public function must be tested):
1. **The command line of the driver program** (ADR-0009 decision 9: "All parameters of the driver are command-line arguments ... Their spelling and order are the code task's"). Recommended: eight positional arguments in a fixed order, `<m> <k> <n> <n_min> <n_max> <cv_max> <sample_form> <seed>`, integers as decimal digits without sign, `cv_max` as `repr(measurement.CV_MAX)` (`0.05`; the C side can read it with `strtod`, which needs no `-lm`), the sample form as the word `interval` or `reciprocal`. A function returns this argument tuple (for example `driver_arguments(*, m, k, n, n_max, sample_form, seed)`), so that it can be tested without a process.
2. **One timing run**, for example `run_timing(executable, *, m, k, n, sample_form, seed, timeout_s, n_max=N_MAX_DEFAULT, cwd=None, env=None)`: starts `<executable> <arguments of 1>` with `local_run.run` — one process, `cwd` / `env` / `timeout_s` handed over unchanged — and returns the result of capability 4. `executable` is a path, or (recommended, as `compiler` in `clang_build.build`) a sequence used as a command prefix, which is what lets the tests run a stand-in as `(sys.executable, script)`; a prefix decides nothing about pinning or isolation. If you choose another way to make a stand-in runnable on Windows and POSIX alike, say why.
3. **The parser of the report** (decision 8), a public pure function on the captured standard output (`bytes`), for example `parse_report(stdout)`: accepts exactly — one line `resolution_ns <integer>`, then zero or more lines `interval_ns <integer>`, then one last line `stop converged` or `stop not_converged`, every line ASCII and ended by LF, nothing before, between or after. Everything else is "a line of another form": a CR, a missing final LF, an empty output, a blank line, a second `resolution_ns` or `stop` line, text after `stop`, two spaces, a sign, a decimal point, non-ASCII bytes, another keyword. An `interval_ns` of 0 is broken (decision 4). It must never raise on any `bytes` (a digit string too long for `int()` on CPython 3.11+ included) — it reports the report as not of the form.
4. **Completed or broken** (decisions 7 and 8). A run is **completed** only when all hold: it did not time out; its exit status is 0; the standard output is of the form of 3; and the **replay** agrees — with the samples derived from the intervals in order (`interval`: the interval lengths; `reciprocal`: their reciprocals), `stopping_state(prefix, n_max=n_max)` is `CONTINUE` for **every proper prefix** (the empty one included) and the state of the whole sequence equals the one the `stop` line reports. The replay must not let an `InvalidSamplesError` escape (more intervals than `n_max` is a disagreement). **Every other run is broken.** The result (for example a `NamedTuple`) gives: for a completed run the intervals in order (`int` nanoseconds), the resolution, and the state (`State.CONVERGED` or `State.NOT_CONVERGED` — a run the rule ended at `n_max` is completed and carries that mark); for a broken run that it is broken, **which condition failed** (a small closed set, for example timeout / exit status / report form / zero interval / replay disagreement — an `enum` or equivalent, with `enum.auto()` values so that no stored form is implied), and what the runner captured (the `RunResult`, also present for a completed run). A broken run **offers no intervals as a measurement** (those fields are `None` or empty); the raw capture is all that is passed on. Standard error is never parsed.
5. **Caller errors raise before anything is started** and are not results: `m`, `k`, `n` not exactly `int` or below 1 (ADR-0008 decision 6); `n_max` not an `int` of at least `N_MIN`; a sample form that is not one of the two; a seed that is not exactly `int` or outside the range the module states (recommended `0 <= seed < 2**64`, so that the C side can hold it in `uint64_t`); `bool` is not an `int` here. One `ValueError` subclass or `TypeError` / `ValueError` as in the sibling modules — say which. `timeout_s` and `executable` errors are those of `local_run.run` (`TypeError`, `ValueError`, `ProgramNotFoundError`) and are passed on.
