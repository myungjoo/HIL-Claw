## Acceptance Criteria
What is **fixed** and taken as input, not re-decided:
- ADR-0004: the path `runs/<run_id>/STATE.json`; one per run; mutable; written by the Round-Manager only; the layout version is in `instance.json`; the tree gives no concurrency control and no atomicity.
- #4 §1 [합의]: one small `STATE.json` is the entry point of every turn; only artefacts it refers to are loaded; no whole-directory scan. #4 §3 [합의]: turn ≡ round. #4 §3c: the file is updated at the end of a round and the commit of the round takes it. #5 A-3: the local commit is the durability boundary.
- ADR-0011: `budget_spent` is, for amounts accounted through the log, the stored spend view of a prefix of the log — totals per axis, the position (number of complete lines folded), the open steps at that position; taken when a round ends, empty at position 0 when a run starts, not moved in between; kept in `STATE.json` and nowhere else; the log is authoritative; a position beyond the end of the log is an error of the kind of a damaged line. An identity = the envelope numbers a line carries + `step` (*name*) + `execution` (*integer* ≥ 1). An amount is a non-negative *integer*; an axis is a *name*; no axis is named.
- ADR-0002: `round` is a non-negative integer, 0 = bring-up. NFR-7 ②: a persistent artefact carries a `schema_version`. C-2: one run at a time in P1.

What the ADR **decides**. The content of each decision is the executor's to work out and justify from the fixed inputs; the reviewer's Approve confirms it. For every point give the choice, the alternatives considered and one or two lines of reason; mark each value as **cited** or as **this record's own**:
1. **Scope**: what of the file this record fixes (the file as a whole, the round pointer, the stored spend view) and that every other member is not fixed here.
2. **The file as a whole**: one JSON object; encoding and text form (argue from ADR-0005 / ADR-0006 what is taken over: UTF-8, no byte order mark, no member name twice, the final line feed); `schema_version` (place, first value, what raises it); and **the rule for members this record does not define** — the excluded members will be added by later records, so say whether the member set is closed until then, what a reader does with a member it does not know, and whether adding a member raises the version. Say what a missing file means (ADR-0004 decision 1 on a missing directory; a run that has started versus one that has not) only as far as the sources allow; otherwise name it as a boundary.
3. **The round pointer**: the member name, its type (the `id.round` of ADR-0002) and — the actual decision — **what it points at** (the round the next turn runs, the last round that ended, or another form), stated so that it is unambiguous at the three moments the sources give: before the bring-up round, inside a round after a process death, and after a round's commit. It must be consistent with the snapshot rule (the stored view is taken in the write that ends a round) and with "which rounds exist is known from `STATE.json`" (ADR-0004). Do not define how a round is chosen, ended or abandoned.
4. **The stored spend view** (`budget_spent` — keep the name unless a reason is given): the member names and JSON forms of the totals (axis *name* → amount), of the position and of the open steps. Decide and state:
   - the written form of an identity (which members, how an absent envelope number is written — ADR-0006: "no member holds `null`; an absent member is left out"), whether the open steps have a fixed order, and that no identity occurs twice;
   - the range of a stored total, given that a sum of amounts can exceed the *integer* range of ADR-0001 (T-0041): a rule, not a silent cap;
   - whether an axis whose amounts are all 0 is written;
   - the value at the start of a run (ADR-0011: the empty view at position 0).
   The form must be able to carry every view `hilclaw.journal.fold` can return, and must not settle the question T-0041 raised for a later revision of ADR-0011 (whether an identity started again after it ended is among the open steps): say that both answers fit.
5. **The byte offset** (ADR-0011 decision 6, *Bound*): whether the stored view also holds the byte offset at which the folded prefix ends; if yes, its member, its relation to the position (which of the two is authoritative, and what a reader does when they disagree or when the offset is not at a line start); if no, the stated cost (a reader counts line feeds from the start of the file). Either choice is acceptable when argued.
6. **Writing and reading the file as a rule, not as code**: the file is replaced as a whole by its one writer; what a reader does with a file that is not valid by this record (ADR-0006 decision 6 treats damage of the log as an error that is reported and not repaired — say whether the same holds here and what is recovered from where, #5 A-3); what a validator of this file alone can and cannot check (ADR-0011 Consequences: it cannot check the view against the log). Do not prescribe an implementation technique for an atomic replacement beyond naming the requirement, if one is stated at all.
7. **Limits**: what the rules do not protect against (two writers — the lock; a `STATE.json` written between two round ends; machine loss before the commit; a stored view that disagrees with the log — ADR-0011 decision 6 already says what happens), each with the place where it is decided.

### Decisions of ADR-0012 (`ARCHITECTURE/decisions/ADR-0012-od8-runtime-state-file.md`, 160 lines; the change is 174 insertions, 12 deletions, 4 files — inside the 300 LOC / 5 files cap)
1. **Scope**: the file as a whole, the round pointer, the stored spend view; every other member is not fixed.
2. **The file**: one JSON object, UTF-8 without a byte order mark, no member name twice in any object. `schema_version` is the *integer* 1 at the top level of this file (not in `instance.json`, which is written once while the writer of this file may be replaced at a round boundary). Required: `schema_version`, `round`, `budget_spent`. The written form (LF, final line feed, the orders of members, axes and open steps) binds the writer only and is no part of validity. **The top level is open in version 1**: a reader does not interpret a member it does not know and does not treat it as an error; the version is raised when a member of this record changes, when a member is added inside `budget_spent`, or when a later record makes a top-level member required — not when it defines one that may be absent. Reason: the writer is an agent of the first layer and the validator code of the second, and either may be replaced at a round boundary (NFR-7 ①). Stated cost: a misspelt optional member is not detected. A missing file means no state was written and no round has begun; an empty file is invalid.
3. **The round pointer**: `round`, the `id.round` of ADR-0002. It names **the round the run is at** — not ended, the one the next turn runs or goes on with. 0 at the start; changed only in the write that ends a round (the write that takes the stored view), to the next integer. "The next round is the next integer" is the record's own reading of ADR-0004. Rounds 0 to `round` − 1 are over and none above has begun, known without a listing. Not said by it: whether a turn runs at all, what ends a round, what is finished inside the round.
4. **The stored spend view**: `budget_spent`, a closed object with `totals`, `position`, `open_steps`, all always present (start: `{}`, `0`, `[]`). A total is a non-negative JSON integer **of any size** (a sum of *integer* amounts can leave the range of ADR-0001 and the view is exact; a reader that cannot represent it reports an error, never rounds). An axis is written exactly when an end line of the prefix named it, total 0 included. An identity object has `step`, `execution` and those of `round`, `candidate`, `attempt` the lines carry; an absent number is left out, no `null`; no identity twice; the writer sorts by `round`, `candidate`, `attempt`, `step`, `execution` (absent first) and a reader accepts any order. The T-0041 question (an identity started again after it ended) is not answered; both answers fit.
5. **No byte offset**: the position is the line count alone. Cost stated: a reader counts line feeds from the start of the file. Reasons: a second statement of one position can disagree; checking it against the count needs the count; a reader accepts CR before LF, so an offset holds for one byte form only; nothing measured shows the need.
6. **Writing and reading**: replaced as a whole by the one writer; a write that does not end a round carries `round` and `budget_spent` over unchanged; requirement that a death of the writer leaves the old or the new content (no technique named). An invalid file is an error like damage of the log: reported, no member used, nothing repaired; recovered from the last commit, whose view is still the view of a prefix of the working-tree log. A validator of this file alone cannot check the view against the log, the position against the end of the log, or the pointer.
7. **Limits**: two writers (lock, rest of OD-17); a write between round ends that moves the pointer or the view; the end of a round written and its commit not made; machine loss before the commit; a view that disagrees with the log (ADR-0011 decision 6); a wrong pointer.

### Three moments (also a table in the record)
- **Start of a run, before the bring-up round**: the file holds `round` 0 and the empty view at position 0; a fresh turn concludes that the round to run is 0, nothing has ended and nothing was spent.
- **Process death inside round *k* after a `step_ended` line was appended**: the file still holds `round` *k* and the view of the end of round *k* − 1; the tail holds the line. The turn goes on with round *k*; the current view is the stored view folded over the tail, so the amount is counted once, and the identity is ended and skipped (ADR-0011 decision 4).
- **Just after the commit of round *k***: `round` is *k* + 1 and the view was folded to a position the log had reached; rounds 0 to *k* are over and the round to run is *k* + 1.
