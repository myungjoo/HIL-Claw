## Acceptance Criteria
What is **fixed** and taken as input, not re-decided:
- **Owner (#5 A-9 sub-decision 2; FR-1; OD-21 `확정`)**: N, the number of candidates per round, is a parameter of the Loop instance chosen by the user at instance start; the initial UI offers 1 ≤ N ≤ 5; that policy may change later. **Owner (#5 B-4)**: the initial run caps name N = 1-2. Nothing else of the owner's speaks of the value. No source gives a default.
- **Open and not touched (OD-29, OD-15, OD-19)**: parallel or sequential coder calls, k and how it is chosen, per-candidate cost and caps, the promotion criterion, the repair bound.
- ADR-0002 (accepted under §9; its own choices): `id.candidates` of a spec is "N of this round", an integer of at least 1 without an upper bound in the schema; `single` exactly when it is 1. ADR-0004: `runs/<run_id>/instance.json`, one per run, "What the instance was started with", written once, immutable, nothing enforces it; the tree sets no upper bound on N. ADR-0018: the frame of the file (decision 2), the open top level of version 1 and **the rule of what raises `schema_version`**. ADR-0020, ADR-0022, ADR-0023, ADR-0024: the existing members and the layout stamp. Nothing is kept between calls (ADR-0010 decision 7).

What the ADR **decides**. The content of each decision is the executor's to work out and justify from the fixed inputs; the reviewer's Approve confirms it. For every point give the choice, the alternatives considered and one or two lines of reason; mark each value as **cited** (owner, or an earlier record - say which) or as **this record's own**:
1. **Scope**: of `runs/<run_id>/instance.json`, the one member in which a run states its number of candidates per round; nothing else of the file and nothing of any other file. State that the file is still not a complete instance record (ADR-0018 decision 1).
2. **What the member states.** The N of FR-1 as the user chose it at instance start (OD-21). Say exactly what a reader of this record may conclude and what it may not: it is not k, not the number of coder calls (a round with N candidates and r repair calls has N + r specs - ADR-0002), not a number of attempts, rounds or measurements, not a statement about parallel or sequential execution, and not a cap of cost per candidate. **Whether it is a budget member**: FR-3 lists four axes and N is none of them; the owner's B-4 line lists N among the "Initial run caps" under a heading that names FR-3 - state the reading and keep it consistent with ADR-0023 decision 2, which read the same heading for `n_max`. Say what the fixed inputs carry about one value per run (FR-1: "instance 파라미터", chosen "at instance start"; the file is written once) and leave by name what they do not carry: whether round 0 (bring-up, baseline) has N candidates (OD-28; ADR-0002 Boundaries), and whether a round may hold fewer candidates than N (a budget used up inside a round - OD-19; OD-29).
3. **The member: its name, place and form.** Weigh at least: (a) one top-level *integer* member with a descriptive name (for example `candidates_per_round`); (b) the word the spec uses (`candidates`, as in `id.candidates`) - weigh that one name for the same number lets it be followed from the file to the spec, against the fact that at the top level of the instance file the bare word does not say "per round"; (c) `n` - weigh it against `n_max` standing beside it (ADR-0023: "The name is near N"); (d) a member inside an object that groups search parameters or run caps - weigh it against the fact that no other member of such an object has a fixed form (k, the execution mode and the budget members are open), so the object would be shaped by members that do not exist. The value form: a JSON integer written as ADR-0023 decision 3 writes one (confirm or say where it differs, with what `hilclaw/instance.py` accepts for `n_max` as the code's reading), lower bound 1 (cited: owner; ADR-0002). **The upper bound is the hard point**: the owner's sentence speaks of what "the initial UI offers" and says the policy may change later; ADR-0002 and ADR-0004 set no upper bound and OD-29's design constraint asks that N be hard-coded nowhere. Weigh at least: (i) validity carries 5 - then a later policy change needs a new record and, by ADR-0018 decision 2, possibly a new `schema_version`, and a file written once under a wider policy would be invalid for a reader of this version; (ii) validity carries no upper bound below the *integer* range of ADR-0001, and the 1-to-5 range is a rule of what offers the choice at the start (the UI, the writer), which this record does not decide - then say plainly that a valid file may state a value the initial UI would not offer and that nothing in this record refuses it. Whichever is chosen, **attribute to the owner exactly the sentence quoted above and no more**, and do not present a bound as the owner's rule of validity. Say what is no value: another JSON type, a boolean, a number with a fraction or an exponent, a string of digits, zero, a negative number.
4. **A file without the member; the version.** By ADR-0018 decision 2's own rule, which leaves this choice to the record of the member. Inputs: no source gives a default; FR-1 and UC-1 have the user state N at the start (UC-1 does not mark it optional); ADR-0020 decision 3 is the precedent for a value an instance must state while a valid file may lack the member. Weigh at least: (a) the member may be absent from a valid file, the version stays 1, absent means "not stated", and a reader of this record substitutes no value (not 1, although N = 1 is "a special case" - say why that phrase of OD-29 and ADR-0002 is no default); (b) the member becomes required and the version becomes 2 - then every file and reader of today is of another version before a first run exists, ADR-0024 decision 3 obliges the record to say which layout version the new `schema_version` states, and reading another version is OD-11. If the member is present it must be valid; say whether a present and invalid member makes the file invalid as a whole (ADR-0020 decision 3, ADR-0022 decision 5 and ADR-0023 decision 4 are the precedents; confirm or correct). **Whichever is chosen, no sentence may make the N of a run depend silently on something the run did not record.**
5. **How the member stands to `id.candidates` of a spec and how it is read**, only as far as it follows from the fixed inputs. ADR-0002 calls `id.candidates` "N of this round" and says the two `id` members "describe the round without fixing N". Decide only whether this record adds a rule between the two numbers; the planner's expectation, to be confirmed or corrected with reasons, is that it adds **none**: the member is where the instance parameter is recorded, a spec says what its round has, and whether the two must be equal for every round is the business of whatever issues the specs (PLAN P2-1, P2-2; OD-28 for round 0; OD-29) and of no validator here. If you find that the member cannot be given a meaning without such a rule, state the smallest rule the fixed inputs carry and mark what stays open - or return BLOCKED with the question. Reading: from this member of the file of the run, at each use, nothing kept between calls. Observation to state truthfully: no tool, hook or module reads the member today, and nothing that issues specs exists. Do not say which component reads it or at which moment.
6. **Limits**, in the manner of ADR-0018 decision 6 and ADR-0023 decision 6: whoever can write the file changes N; a misspelt top-level name is passed over and reads as an absent member (with the consequence of point 4); nothing checks that the rounds of a run in fact had the stated number of candidates; a large value is a cost (C-4, C-7: the coder calls share one subscription limit) that this member does not cap; the member does not say how many candidates reach the board.
7. **Consequences**, not decisions: the code slice that can now be cut within the size cap (in `hilclaw/instance.py`: the validity of the member and a reader beside `n_max_of`, with tests in `tests/test_instance.py`; names and the return form are the code task's; **binding the reader to a spec, to a tool or to anything that issues specs is not part of that slice**); which docstring sentences and test cases change (find the existing test cases that hold a member of the chosen name or lean on "no member besides ..." and name them); which sentences of other documents become less exact (follow-ups for the integrator: the Boundaries of ADR-0018 / 0020 / 0022 / 0023 that list "N per round" as open, the ADR-0023 notice reading 2). An **example** of a file content with the placeholders of ADR-0023's Example plus the new member, fenced as `json`, **never as Python** (`ruff format --check .` reads Markdown on CI).
