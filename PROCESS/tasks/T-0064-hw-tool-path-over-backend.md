## Why
ADR-0016 (landed as `7220fb4`, T-0056) cut three code slices in its Consequences:

> ① the backend table, the selection as a function from a hw_profile record, and the two kinds beside the five of `hilclaw/tools.py`; ② the mock backend and its scripts; ③ the path of a HW tool over a backend, checked through both fronts by a test-only tool with the mock, as T-0055 did for the journaled path. Slice ③ takes the reader of a run's hw_profile as a parameter until sub-question ⑥ is answered. `hilclaw.journaled_step.run` has no place between its lookup and its start line today; slice ③ gives it one or builds the order of decision 2 otherwise.

Slice ① is on `main` as `hilclaw/backends.py` (T-0057, `3bc6821`), slice ② as `hilclaw/mock_backend.py` (T-0058, `0339bfb`). **This task is slice ③.** Today nothing joins `backends.select` to a tool function: `hilclaw/journaled_tool.py` builds the tool function of a journaled tool with the order check → data root → step, and `hilclaw/journaled_step.run` goes from its lookup straight to the start line.

ADR-0016 decision 2 fixes the order of a call of a HW tool:

> ① the request is checked; ② the data root is asked; ③ for a journaled tool, the lookup — an ended or an open identity is answered from the log, and **no backend is selected or called for it**; ④ the backend is selected and the operation of the called tool is looked up; ⑤ for a journaled tool, the start line; ⑥ the operation is called; ⑦ for a journaled tool the end line, and the result. **A call that fails in ④ has consumed nothing at any target and leaves no line.**

It ticks **no PLAN checkbox**: P1-1 stays open (every tool and its contract, the `cpu_standin` backend, the default table and script, the conformance tests remain). `hilclaw.tools.default_registry` keeps its signature and keeps returning an empty registry.

Planner's judgements (2026-10-08 UTC, from the files; the reviewer is asked to re-check each):
- **The journaled path only.** ADR-0016 words ③, ⑤ and ⑦ "for a journaled tool" and leaves "whether it is journaled" to each tool's contract (Boundaries, "Each tool"). No record says that any HW tool is not journaled, and the walk-through of the record is a journaled tool. The path ① ② ④ ⑥ of a HW tool that is not journaled is left out and listed in `## Follow-ups`; it is cut when a contract names such a tool. Building it now would add a request rule (`run_id` without `execution`) that has no caller.
- **`journaled_step.run` gets a place between its lookup and its start line** (the first of the two ways the record names). Building the order "otherwise" would mean a second implementation of the lookup or a start line appended before the selection, which decision 2 excludes.
- **The reader of the hw_profile of a run is a parameter of the builder.** Where a run states its hw_profile is OD-18 sub-question ⑥, open; this task writes no reader, names no file and no member, and the tests use a reader of their own that returns a record the test holds. The call form of the reader is a code-task choice (below).
- **When the reader is asked: in ④, for an identity with no line only.** The walk-through row "No line: the selection" reads "The tool function reads the hw_profile of `r1` … and looks its `accelerator` up", and decision 2 says an ended step's answer "depends on the data plane only" and must stay obtainable; an ended or an open identity therefore asks neither the reader nor the table.
- **What the reader or `backends.select` raises for a record that cannot be read or is not valid passes through unchanged, with no kind given.** ADR-0016 decision 4: "A hw_profile that cannot be read or is no valid record is not `no_backend`: the run cannot be used, and that kind is open (sub-question ④ of ADR-0015)." It is raised before the start line, so nothing is appended.
- **Who calls the operation.** Decision 2 (a) gives the tool function "the form of the result and the kinds" and the backend "returning to the tool function what the tool's contract lets a backend return"; ADR-0011 decision 7 has the step state its own amounts. No record says that an operation returns the pair `(spend, result)`. The recommended form therefore hands the selected operation to the contract's `perform`, which calls it as `operation(request, hw_profile)` (the form T-0058 landed) and turns what it returns into `(spend, result)` or `StepFailed`. The frame then decides nothing about what a backend returns. This is the one choice of this task that later tools are written against: it is listed under the provisional choices and the reviewer is asked to check it against decision 2.

Why this item now: no lock, no unresolved HQ, no TODO / INTERRUPTED task file and no open PR at planning time. In P0.5 the remainder of P0.5-4 is the owner's hook registration. The "harness pass" half of P0.5-1 is not planned in this iteration: since T-0063 both Python gates build the conforming calibration kernel with the runner's clang and run the harness against the float64 reference with no skip, and neither #9 ("`clang` build of the stand-in kernels + harness pass (correctness against the f64 reference)") nor the PLAN wording says whether that already is the gate or whether the `C gate (clang)` job must run it itself; the planner reported that question to the driver instead of guessing. ### The place in `journaled_step.run`
Recommended shape (name and form are yours): one optional keyword-only parameter, for example `run(data_root, run_id, identity, step, *, before_start=None)`, a callable without arguments.
- It is called **exactly once, only for an identity with no line, after the state was established and before the start line is appended**. For an ended or an open identity it is not called.
- What it raises passes through unchanged (a `ToolFailure` of any kind, any other `Exception`, a `BaseException`): **nothing is appended and `step` is not called**; the identity still has no line and the same call can be repeated.
- A value that is neither `None` nor callable is refused with `TypeError` together with the check of `step`, before any file is read.
- Without the parameter `run` behaves exactly as today: **every existing test of `tests/test_journaled_step.py` and `tests/test_journaled_tool.py` passes unmodified**.
- How what was prepared reaches the step (a closure of the caller, or a value handed on to `step`) is yours to choose; if `step` receives an argument only when the parameter is given, say so in the docstring.
- The module docstring gains the convention in one or two sentences (ADR-0016 decision 2, why ④ lies there) and every existing sentence of it stays true; `run`'s docstring states the parameter and what it raises.

### The builder (`hilclaw/hw_tool.py`)
Recommended shape (names yours): one public function, keyword-only parameters without defaults, for example
`tool_function(*, tool, step, numbers, source, table, hw_profile_of, check, perform)`, which returns the tool function of the journaled HW tool `tool`, ready for `Registry.register`.
- `tool`: one of `backends.HW_TOOLS`; anything else is refused when built with what `backends` raises for it (`TypeError` / `ValueError`).
- `step`, `numbers`, `source`, `check`: as in `journaled_tool.tool_function` (same meaning, same refusals when built).
- `table`: a `backends.BackendTable`, bound when the tool function is built (ADR-0016 decision 2: "the table is bound to the tool functions of the HW tools when a registry is built"); anything else is a `TypeError` when built.
- `hw_profile_of`: the reader of the hw_profile of a run, a callable; recommended call form `hw_profile_of(data_root, run_id)` with the data root of this call and the checked `run_id`, returning a hw_profile record. Not callable → `TypeError` when built.
- `perform`: the step of the tool's contract; recommended call form `perform(data_root, request, hw_profile, operation)` with the very record the reader returned and the very operation `backends.select` returned. It returns `(spend, result)` or raises `journaled_step.StepFailed`, as in `journaled_tool`. The builder itself calls no operation (see the last judgement in `## Why`); if you choose that the frame calls the operation, say why and what an operation then returns, and ask the reviewer to check it against decision 2 (a) and (b).
- Building calls none of the callables, reads no file and asks the table nothing.

A call of the returned function, **in this order** (ADR-0016 decision 2):
1. The request is checked exactly as `journaled_tool` checks it (`run_id`, `execution`, the required numbers, then `check(request)`); a refusal is `invalid_request`. **One implementation of that check**: reuse it (build on `journaled_tool.tool_function`, or share its checker) rather than copying its text. Neither the source, the reader nor the table is asked for a refused request.
2. The data root is asked once through `data_root_source.obtain(source)`; `no_data_root` passes through and neither the reader nor the table is asked.
3. The lookup: an ended identity is answered with what its end line holds, an open one with `step_open`. **The reader is not asked, nothing is selected, `perform` is not called**, nothing is appended. A stored result stays obtainable with a table that no longer has the entry and with a reader that would fail.
4. For an identity with no line: the reader is asked once, then `backends.select(table, hw_profile, tool)`. `no_backend` and `not_offered` pass through as `select` raises them; what the reader raises, and the `keys.InvalidRecordError` of `select` for a record that is not valid, pass through unchanged with **no kind given here**. In every one of these cases **no line was appended, `perform` and the operation were not called**, and the same request can be repeated and runs once the cause is gone.
5. The start line is appended, 6. `perform` is called once, 7. the end line is appended and the result returned - all three by `journaled_step.run`, unchanged in what it writes.
- Nothing is kept between calls (ADR-0010 decision 7): the reader is asked at each call that reaches ④, so a change of what it returns between two calls is seen.
- The request is not modified; `run_id` and the identity are the values checked in 1 (T-0055 review round 1).
- The module defines no tool, no backend, no table, no reader, no script and no default; it imports nothing that reads the data plane beyond what `journaled_step.run` already does, reads no configuration and no variable of the process, and does not touch `tools.default_registry`.
