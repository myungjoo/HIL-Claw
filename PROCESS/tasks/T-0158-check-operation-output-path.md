## Acceptance Criteria
### Fixed by the record (not re-decided; implement exactly)
1. **Four things.** An operation of `correctness.check` is called with the request, the hw_profile of the call, the check parameters and the output path, each as the same object the caller of that layer handed in. The check parameters stay `hilclaw.check_parameters.CheckParameters` with exactly five values; the output path is **no** sixth value of it, and `hilclaw/check_parameters.py` is not edited.
2. **What the output path is.** The path ADR-0004 fixes for the `output/` of the attempt the request names, formed from the data root of the call and the members `run_id`, `round`, `candidate` and `attempt` of the request: `hilclaw.layout.attempt_artefact(data_root, run_id, round, candidate, attempt, "output")`. The tool function forms it; no other module of the chain forms or changes it.
3. **The tool function reads nothing there.** No module of the chain tests whether the path or anything above it exists, lists it, opens it, resolves it or makes it absolute. For a run at the mock no `output/` need exist, and a call is answered all the same.
4. **The moment.** The path is handed over with the call of the operation (moment 6 of ADR-0016 decision 2). Nothing changes at moments 1 to 5 or at the draw: every answer before the start line (`invalid_request`, the four kinds of `hilclaw.check_admission.KINDS`, `seed_not_drawn`, the frame's kinds) is given as today, with no line appended and no operation called. A repeated call of an ended identity is answered from the log; no backend is selected and no path needs to reach anybody.
5. **The mock.** The mock's operation is called with the same four things and asks its script with them, as they are, after the called tool: five things. `default_script` does not read the output path; its answer follows from the check parameters alone and it still returns only `bytes` and raises what it raises today.
6. **Nothing else changes.** What becomes of a returned report, a condition, a value of neither form, a raised error, a raised tool failure and a raised request to end is exactly as `hilclaw.check_operation`, `hilclaw.check_ending` and `hilclaw.check_failure` have it today. In particular the exception hygiene of `ask` and `carry_out` (no `__cause__`, no `__context__`, nothing of the answer kept) holds, and **no message of any tool failure or ending shows the output path or any part of it** (ADR-0056 decision 6, "The message": a message is written to `events.ndjson` for good).
