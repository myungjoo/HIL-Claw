### The function (recommended shape; names yours)
One public function, for example `write(data_root, run_id, content)`, returning `None`, and one public error class for a taken name, for example `NameTakenError`.

1. **The content first (decision 2), before the file system is touched.**
   - `run_id` is checked by `hilclaw.layout` (`InvalidPathValueError`), then the content, then `data_root`, then the file system - the order of `hilclaw/run_state_file.py`, unless you have a reason for another; say which order landed.
   - The content is valid by the records as they stand: it is given to `hilclaw.instance.parse`, and what `parse` refuses is not written (`TypeError` for what is not exactly `bytes`, `InvalidInstanceError`, `UnsupportedVersionError` - a content of another `schema_version` is not valid by the records that define the file today). Whether these errors pass through unchanged or are wrapped is yours.
   - The content is in the written form of ADR-0018 decision 2: LF line ends and a final line feed. Check exactly that and nothing more: no member order, no indentation, no number of lines, no canonical form. The planner's reading of "LF line ends" for bytes, to confirm or correct: a content that ends with a line feed and holds no carriage return byte (in a JSON text `parse` accepts, an unescaped carriage return can only be white space between tokens, so this refuses no valid value of any member). Which error reports a content that is valid and not in the written form is yours; it must be raised before the file system is touched.
   - **The write adds, substitutes and checks nothing beyond that.** A valid content without `tolerance`, `source_commit` or `n_max` is written as it is; no member is put in or taken out, no default is filled in, nothing is normalised or re-serialised: the bytes under the final name are exactly the bytes given. A content with members no record defines is written as it is (the top level is open).
2. **The data root** is used as given, must be an existing directory (`FileNotFoundError` or `NotADirectoryError` otherwise, as the other writers of the package report it) and is never created.
3. **The run directory (decision 5).** `runs/` and `runs/<run_id>/` are created when missing. The function requires neither that the run directory is missing nor that it is there, and looks at no other file of the run: it writes the same way into an empty run directory, into one that holds `STATE.json`, `events.ndjson` or a leftover, and into none. Whether a failed write removes the directories it created is yours (`run_state_file.replace` keeps them, `key_records._store` removes them) - choose, give the reason, test it.
4. **The temporary file (decisions 3 and 6).** `instance.json.<token>.tmp` in the run directory, `<token>` matching `[a-z0-9-]{1,64}` and different for every write (the two landed writers use the process id, a hyphen and 16 random hexadecimal characters). It is created as a new file (`"xb"`), never by opening an existing one; a temporary name that is in use is an error and that file stays. The whole content is written, flushed and brought to stable storage (`os.fsync`), and the file is closed.
5. **The last step (decision 3 step 4).** One step that gives the final name only if it does not exist and otherwise changes nothing: `os.link` from the temporary name to the final name, then removal of the temporary name (or another non-replacing operation, with a reason). **No `os.replace`, no `os.rename`, no look at the final name before the step, no fallback**: where the step is not possible the write fails with the error of the step and nothing is under the final name. The final name is never opened for writing and never opened for reading.
6. **A failure while the writer lives (decision 3 step 5).** A step that fails before the final name is given: the temporary file of this call is removed, the failure is reported (the `OSError` of the step, unchanged, unless you have a reason), the final name is as it was. The same for an interrupt (`BaseException`) before the final name is given. A removal that fails does not replace the failure it follows. **Once the final name is given the write has happened**: a removal of the temporary name that fails then is not reported, the function returns as for a write that happened, and the temporary name stays as a leftover.
7. **A taken name (decision 4).** When the last step finds the final name taken (a regular file, a directory, a symbolic link - also a dangling one -, whatever is there): nothing is written under the name and what is there is unchanged, the temporary file is removed, and the caller is told **that the name was taken and that its content was not written** - by an error (recommended) or a returned value that cannot be mistaken for a write that happened, and that a caller can tell from every other failure of the file system (if it is an exception, say in `## Result` whether it is an `OSError` and why; a caller that catches `OSError` for "the disk failed" must not take a taken name for that by accident, or the docstring must say how the two are told apart). **The function does not read the file under the name, compares nothing and reports no "same content"**: a second write with the same bytes is reported exactly as one with other bytes. It retries nothing and chooses no other `run_id`.
8. **A leftover (decision 6).** A file of the name form that another write left is not listed, read, removed, opened or given the final name, whether it holds a part or a whole valid content; the function lists no directory.
9. Nothing is kept between calls; the function takes no lock, makes no commit, runs no `git`, reads no configuration and writes no other file.

### Public API as landed
- Module `hilclaw/instance_file.py`. Public names: `WrittenFormError(ValueError)`, `NameTakenError(Exception)`, `write(data_root, run_id, content)`.
- `write` returns `None` after it gave the final name `runs/<run_id>/instance.json` to a file of exactly the bytes of `content`.
- Order of the checks: `run_id` (`hilclaw.layout.InvalidPathValueError`), then the validity of the content (`hilclaw.instance.parse`: `TypeError` for what is not exactly `bytes`, `InvalidInstanceError`, `UnsupportedVersionError`, all passed through unchanged), then the written form (`WrittenFormError`: the content does not end with a line feed, or holds a carriage return byte), then `data_root` (`FileNotFoundError` or `NotADirectoryError`; never created), then the file system. Nothing is created before the last of them.
- `runs/` and the run directory are created when missing (`mkdir(parents=True, exist_ok=True)`) and **stay** when a later step fails.
- The temporary file is `instance.json.<token>.tmp` in the run directory, `<token>` = the process id, a hyphen and 16 random hexadecimal characters; opened with `"xb"`, written, flushed, `os.fsync`, closed.
- The last step is `os.link(temporary, final)`, then `os.unlink(temporary)`. A `FileExistsError` of the link raises `NameTakenError` (message: the path relative to the data root and "the name is taken; the content was not written"). Every other failing step raises its `OSError` unchanged (a temporary name in use and a file in the place of `runs/` or of the run directory are an `OSError`, possibly a `FileExistsError`, never `NameTakenError`).
- After any exception before the name is given (an interrupt included) the temporary file of the call is removed where possible; a removal that fails is not reported in the place of the failure. A removal that fails after the name was given is not reported: the function returns `None` and the temporary name stays as a second name of the file.
- `NameTakenError` is **not** an `OSError`: a caller that catches `OSError` for a failed disk does not catch it. Nothing under the final name is opened, read, examined or compared; equal bytes get the same type and message as other bytes.

### Provisional choices (each left to the code task by ADR-0025; one line of reason)
- Module `hilclaw/instance_file.py`: after `run_state_file.py`; `hilclaw/instance.py` stays a module that writes no file and is not edited.
- `write(data_root, run_id, content)` returning `None`: the call form of `run_state_file.replace` with the content in the place of the values.
- Bytes, not a document: the module chooses no text form, and "the bytes written are the bytes given" is tested byte for byte.
- The errors of `parse` pass through unchanged: they already name the place in the content.
- `WrittenFormError(ValueError)`, not `InvalidInstanceError`: a content not in the written form is valid, so the other class would say the wrong thing.
- The reading of "LF line ends" for bytes is the planner's, re-checked by the reviewer: the content ends with a line feed and holds no carriage return byte (in a content `parse` accepts, a raw carriage return can only be white space between tokens). Nothing else of the form is checked.
- `NameTakenError(Exception)`, no `OSError`: see above; a `FileExistsError` of another step cannot be mistaken for it.
- Order of the checks as in `run_state_file.replace`.
- `os.link` then removal: the step the record cites and `key_records._store` uses; standard library only.
- The directories stay on a failure (as `run_state_file.replace`, unlike `key_records._store`): removing them could take the directory from another writer of the run, and an empty run directory is a missing file for a reader (ADR-0025 decision 5).
