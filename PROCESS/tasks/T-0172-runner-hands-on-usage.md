## Why

Decision 4 (line 62) adds: "How `hilclaw/local_run.py` hands the usage of the process it waited for to the Python side of the harness is the code task's. ... the runner waits through `subprocess.run` today, which returns no usage, so the slice changes how `local_run.run` waits for its process and ends it at the time limit."

It ticks **no PLAN checkbox** and changes no OD.

## Acceptance Criteria
1. **One new member of `RunResult`**, appended after `duration_s` with the default `None` (suggested name `max_rss`; the name is the executor's), so that every existing positional construction stays valid. Its value is the `ru_maxrss` of the `rusage` returned by `os.wait4` for the process that `run` started, as an `int`, **unconverted** (the platform's unit), or `None` where `run` did not obtain a usage. The `RunResult` docstring states this, that the unit is the platform's and the runner converts nothing, and that whether the value is a figure is the caller's (ADR-0052 decision 4).
2. **Where `os.wait4` exists** (`hasattr(os, "wait4")`, i.e. POSIX), `run` reaps its process with `os.wait4(pid, 0)` - the usage of that one process (and the descendants it waited for, as the system reports it), never `resource.getrusage(resource.RUSAGE_CHILDREN)` and never a value read about the calling process. The value is handed on in every case in which the wait succeeded: normal exit, non-zero exit, death by signal, and after a kill at the time limit.
3. **Where `os.wait4` does not exist** (native Windows), `run` behaves exactly as today and the new member is `None`. Tests may simulate this branch on POSIX (e.g. `monkeypatch.delattr(os, "wait4")`) so that CI covers it.
4. **Every existing behaviour of `run` is kept**, on both branches: the argument checks and their exceptions before anything is started; no shell, standard input at end of file; stdout and stderr captured apart as undecoded bytes, including what was written before a kill at the time limit; `returncode` as today (exit status, negative signal number on POSIX, `None` on a timeout) - computed from the `wait4` status with `os.waitstatus_to_exitcode` or an equivalent that gives the same values; `timed_out`; `command`; `duration_s` measured as today around the whole process; the documented passing-on of `OSError`, `ValueError`, `TypeError` from starting the process. The documented `OverflowError` for a finite `timeout_s` longer than the platform can wait for either stays as documented or the docstring is changed to say exactly what the new code does, and a test pins it. Every existing case of `tests/test_local_run.py` passes **without modification**.
5. **The wait is correct.** The child is reaped exactly once: no zombie is left, the `Popen` object (if one is used) is not left to reap the already-reaped pid again (set its public `returncode`, or avoid `Popen` waiting at all), no `ResourceWarning` for unclosed pipes is emitted (a test runs under `-W error::ResourceWarning` or checks with `pytest.warns`/`recwarn`), and no private attribute of `subprocess` is used. The output pipes are drained while the process runs so a child writing more than one pipe buffer does not deadlock (a test writes at least 1 MiB to each stream). At the time limit only the started process is killed, as today; the module docstring's "Known limits" stay true and are updated if the new wait changes any of them (for example how long the call can outlast the limit when a descendant keeps a pipe open).
6. **A failed wait is not a new exception.** If `os.wait4` raises `ChildProcessError` (the child was reaped by someone else, e.g. `SIGCHLD` ignored), `run` returns a result as `subprocess` would in the same situation, with the new member `None`; it raises nothing the current `run` would not raise. The docstring states the choice; a test pins it with a monkeypatched `os.wait4`.
7. **Module docstring**: names ADR-0052 decision 4 as the reason for the usage, states that the value is raw and unconverted, that native Windows yields `None`, and that the runner still sets no resource limit and interprets nothing. The sentence "sets ... no resource limit ... and interprets neither the output nor the exit status" stays true. Keep within the comment-minimisation rule otherwise.
8. **Tests** (`tests/test_local_run.py`, D12 ②-④; POSIX-only cases use the existing `posix_only` marker):
   - happy (POSIX): a child that allocates and touches about 64 MiB (e.g. `bytearray(64 << 20)` and writes to each page) yields an `int` value greater than the value of a child that allocates nothing, and on Linux at least 64 MiB / 1024 (KiB); a quiet child yields a positive `int`;
   - branch (POSIX): the value is an `int` also for a non-zero exit, a death by signal and a run killed at the time limit, with every other member as the existing tests expect;
   - branch (any platform): with `os.wait4` absent (monkeypatched), the member is `None` and every other member is as today; on native Windows the member is `None` without monkeypatching;
   - negative: `os.wait4` raising `ChildProcessError` (monkeypatched) - no exception, member `None`; a `RunResult` built positionally with six values has the member `None`;
   - no deadlock: a child writing at least 1 MiB to stdout and to stderr completes with all bytes captured, on both branches;
   - no leaked resources: no `ResourceWarning` and no zombie (`os.waitpid(pid, os.WNOHANG)` on the reported pid raises `ChildProcessError` where the executor can obtain the pid, or an equivalent check).
9. Local gates: `python -m pytest`, `ruff check .`, `ruff format --check .` pass (the POSIX branch is skipped on the Windows development machine and runs on CI); CI green on all jobs; coverage gate (line and function >= 80 %) holds, `local_run.py` at or near 100 % on CI.
