## Why
PLAN P1-5 ("GEMM spec 예시 ... 와 `spec.json` 스키마") is open. Its validator is on `main` (`hilclaw/spec.py`, T-0018), and the records that give the committed example its values were closed one by one: ADR-0008 (the op side), ADR-0027 (the form of a `run_id`), ADR-0035 / ADR-0036 (the hw side). What the example still lacks is `task.objective` and a technique of the stand-in catalog. **This task is `task.objective`.** It ticks **no PLAN checkbox**: the example itself and the validator of version 2 are later slices, and the technique is still open.

What the fixed inputs carried before the answer:
- FR-2: the target is not fixed by the system; the user states it per loop instance, from a menu of target types.
- ADR-0002 decision 2: `task.objective` is required, "any JSON value", "the target of the instance (FR-2), copied from the instance record. Not validated in version 1"; its example writes `NOT-DECIDED-HERE` there. Decision 7: `schema_version` "is raised ... when `profile` or `task.objective` get defined members".
- ADR-0007 decision 1: the measurement policy "chooses neither the quantity nor its direction (OD-1)". ADR-0009 decision 3: the timing run reports the length of an interval and "names no quantity, no unit of a quantity and no direction".
- The register row OD-1 is "차단됨" on #5 A-4; ADR-0002, ADR-0007, ADR-0008 and ADR-0009 file the target under "owner-only".

**The repository owner answered HQ-0009 on 2026-10-13**: https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6136238336 (the question: https://github.com/myungjoo/HIL-Claw/issues/5#issuecomment-6096527683). That comment is the source of every owner statement below; the summary here is the planner's and **the comment's words win**.

- **A1 (part 1, the target)**: latency minimisation - "the time of the kernel call as the harness timing run measures it, lower is better". Both latency minimisation and throughput maximisation are to be offered, the choice is the user's per instance (FR-2); the quantity and unit of throughput are not fixed, "an instance may state a type only once its quantity and unit are fixed, so until then latency minimisation is the only type an instance can state".
- **A2 (part 2, constraints)**: an instance states, beside its objectives, a set of constraints, each entry of one named constraint type. The first type is the memory ceiling: "an upper bound, in bytes, on the memory the kernel's execution uses at the execution point that measures it, operands included". The first committed example carries no value. "Which measurement of the first case stands for that memory on `cpu_standin`, how it is taken, and at which of the two execution points (HQ-0005) it is judged, is the record's design." A candidate over its ceiling is infeasible and is not compared on the objectives; what the round loop then does is what FR-1 does with a failed correctness check at the same execution point. A constraint is optional per instance. Further types come by later records under #5 A-4.
- **A3 (part 3, scope)**: the frame of the MVP menu is fixed, the rest of #5 A-4 stays open. The proposal "a single objective plus an optional memory ceiling" is **not** confirmed. "An instance states a list of objective types, each with an optional weight or priority, beside a set of constraint types; the direction of each type is the type's own." Until the combining rule (priority order, weighted sum, Pareto) is decided, an instance states exactly one objective and neither a weight nor a priority; "the members exist so that the schema does not change later". The full list of types is decided later; the types of A1 and A2 are a minimum, not the list. The OD-1 row takes the status "확정" for this frame with the rest listed as remaining, as the OD-13 row did for its P1 minimum. The README's goal stands as the final goal; the MVP is a subset (#8 M15).
- **A4 (part 4, the version)**: version 2 of the spec, "with the members of `task.objective` defined by the record and checked by the validator. A new objective type or a new constraint type is a new value of a member, not a new member, and does not raise the version; this replaces the corresponding clause of ADR-0002 decision 7."
- **A5 (owner's note)**: "no record is to assume that the other operations are negligible, that latency and throughput coincide in general, or that the objective vocabulary is narrowed to kernel latency."

**A4 is the owner approval of the data-plane spec schema change** (CLAUDE.md A-13, BLOCKED reason "데이터 plane 스키마 변경"): for what A4 names - version 2 and defined members of `task.objective` - that reason no longer applies to this record. It still applies to anything A4 does not name (see "Do not invent").

**The cut the planner chose** (the executor does not re-decide it):
- **In this task**: the members of `task.objective` in version 2 (the list of objectives, the set of constraints, the reserved weight and priority, the entry form of a memory ceiling), the first-case value, the frame of A3 as the owner fixed it, what replaces the clause of ADR-0002 decision 7, the register edits of OD-1 and OD-6, the coverage re-check.
- **Not in this task, a later record** (Follow-ups): which measurement stands for the memory of A2 on `cpu_standin`, how it is taken, and at which execution point it is judged. A2 leaves it to "the record's design", so it is design-level under DRIVER §9 and needs no further owner answer; it is cut because it is a design of the harness (ADR-0009, ADR-0017) and of the execution points (ADR-0038) of its own size, and the members of the spec do not depend on it. This record defines the *form* of a memory-ceiling entry and says plainly that nothing judges one yet.
- **Not in this task, code**: version 2 in `hilclaw/spec.py` (Follow-ups).

Once the owner's part is given, how the frame is spelt inside `task.objective` is the design of a record inside ADR-0002, design-level under DRIVER §9 (OD-6 is not on the owner-only list). That part is this task's record.
