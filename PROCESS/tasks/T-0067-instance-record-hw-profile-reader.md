## Why
ADR-0018 (landed as `566113b`, T-0066) fixed the file frame of `runs/<run_id>/instance.json` and the member `hw_profile` {`key`, `record`} in which a run states the hw_profile it was started with, and cut one code slice in its Consequences:

> **The code slice that can now be cut** (within the size cap, code mode): a module for `instance.json` — the validity of a content by decision 2 and 3, and the reader of the hw_profile of a run with the signature `hilclaw.hw_tool.tool_function` already takes, `hw_profile_of(data_root, run_id)`, over the path `layout.run_file(data_root, run_id, "instance.json")` — with its tests. It needs a JSON parser that reports a repeated member name, as `hilclaw/run_state.py` has, and can share the check of `hilclaw/spec.py` for the section. **Writing the file is not part of that slice**: it needs the answers to sub-questions ⑩ and ⑰ and belongs with the start of an instance; a test writes its own file.
>
> **Sentences of the code that then change**: in the docstring of `hilclaw/hw_tool.py`, "Where a run states its hw_profile is open (OD-18 sub-question 6), so this module reads no file for it and names none", and "no reader" in its last paragraph if the module comes to name one. The reader may stay a parameter; binding the real one is the task of the first HW tool.

**This task is that slice.** Today `hilclaw.layout.run_file` builds the path of the file and no module of `hilclaw/` reads it; `hilclaw.hw_tool.tool_function` (T-0064) takes the reader as the parameter `hw_profile_of` and every test hands it a reader of its own.

It serves PLAN P1-8 ("런타임 STATE/instance/events 스키마") and PLAN P1-1 (the path of a HW tool gets a real reader) and ticks **no PLAN checkbox**: P1-8 stays open (the other members of `instance.json`, its writer, the result files), and P1-1 stays open (every tool and its contract, the `cpu_standin` backend, the default table, the conformance tests). `hilclaw.tools.default_registry` keeps its signature and keeps returning an empty registry.

Planner's judgements (2026-10-08 UTC, from the files; the reviewer is asked to re-check each):
- **The reader is not bound anywhere.** ADR-0018 Consequences: "The reader may stay a parameter; binding the real one is the task of the first HW tool." `hw_tool.tool_function` keeps its eight parameters; no tool, table or registry is touched.
- **No tool-failure kind.** ADR-0018 decision 4 lists four situations in which the hw_profile of a run cannot be had (the file is missing; it cannot be read; it is invalid; its `schema_version` is another integer) and says "Which tool-failure kind such a call answers is not decided" (OD-18 sub-question ④). The reader therefore raises plain exceptions of its own module, one class per situation it can tell apart, none of them a `hilclaw.tools.ToolFailure`; `hw_tool` lets them pass through, as its docstring already says of what a reader raises.
- **The stored record of `db/` is not read or compared** (decision 4: "no other file is read for the selection, and the stored record `db/<hw_profile_key>/hw_profile.json` is not read or compared"). The module does not import `hilclaw.key_records`.
- **No writer.** No function writes, creates or replaces `instance.json`, and none composes a content (no `dump`): who writes the file and by which steps is OD-8 sub-questions ⑩ and ⑰, and with no writer there is no written form to produce. The tests write their own files.
- **One module, pure functions and the file side together**, as far as it fits the cap. `run_state.py` (pure) and `run_journal.py` (files) are two modules because the first is at 285 lines; this file has one member, so one module of about 200 lines is enough. If it does not fit, see "Size" below.
- **The check of the `hw_profile` section is the module's own few lines over `hilclaw.keys.hw_profile_key`**, not an import of the private `hilclaw.spec._keyed` (T-0064 left a follow-up about private names of sibling modules; `hilclaw/spec.py` is not edited here). The rule is the one ADR-0018 decision 3 states and `_keyed` implements for a spec: `record` valid by ADR-0001, `key` the name derived from it.
- **The docstring of `hilclaw/hw_tool.py` is corrected in the same PR** (docstring lines only), because the first of the two sentences the record names is false once ADR-0018 is on `main`. ### The pure half - the validity of a content (ADR-0018 decisions 2 and 3)
Recommended shape (names yours), following `hilclaw/run_state.py`: `SCHEMA_VERSION = 1`; `InvalidInstanceError(ValueError)`; `UnsupportedVersionError(Exception)` of this module; `parse(content)` over the bytes of a content; `validate(document)` over a parsed document; a small result type of `parse` (for example a `NamedTuple` with the key name, the record and the members not defined) or the checked document itself.
- **The rules for the whole text come first, whatever the version**: a content is exactly `bytes` (`TypeError` otherwise); UTF-8; no byte order mark; exactly one JSON text (`NaN` and the infinities are none); that text an object; no member name twice **in any object**, the members this record does not define and the embedded record included. Each broken rule is the invalid-content error and names what is broken. An empty content and a partial one are invalid, not missing.
- **Then `schema_version`**: absent, or a value that is no *integer*, is invalid; an *integer* other than 1 is the unsupported-version error **before any other member is looked at** (decision 2: "not damage … interprets nothing"), also when `hw_profile` is absent or broken. What an *integer* is follows ADR-0001 and `hilclaw.keys` (exactly `int`, so `true` and `1.0` are none; say in the docstring which range you take and why, as `run_state` does).
- **Then `hw_profile`** (version 1): required; an object with **exactly** `key` and `record` (a further member, a missing one, a value that is no object are invalid); `record` valid by ADR-0001, that is, accepted by `hilclaw.keys.hw_profile_key` (its `InvalidRecordError` becomes the invalid-content error with the path below `hw_profile.record`, as `spec._keyed` reports it); `key` a `str` equal to the name derived from the record, **a disagreement makes the content invalid and neither is trusted**.
- **The top level is open**: a member not defined by the record is not interpreted and is no error, whatever its name and value (an object, an array, `null`, a name that looks misspelt such as `hw_profiles`); it is checked only by the rules for the whole text. If `parse` returns such members, they are returned as parsed.
- No member order is required and any white space of JSON is accepted (decision 2: "a reader accepts any JSON text of this shape").
- An error names the place of the broken rule (for example `hw_profile.record.accelerator`), in the manner of `run_state`.
- Nothing is repaired, defaulted or returned from an invalid content.
- The pure functions read no file and know no path.

### The file half - the reader (ADR-0018 decision 4)
Recommended shape (names yours): `read(data_root, run_id)`, which returns what `parse` returns for `runs/<run_id>/instance.json`, and **`hw_profile_of(data_root, run_id)`**, which returns the `hw_profile.record` of that file - the exact call form `hilclaw.hw_tool.tool_function` uses for its parameter, so that the function itself can be handed over as `hw_profile_of=`.
- The path is `hilclaw.layout.run_file(data_root, run_id, "instance.json")`; `run_id` is checked first by `layout` (its error passes through), then the file system. `data_root` is used as given and must be an existing directory (`FileNotFoundError` / `NotADirectoryError`, as the sibling modules do).
- **One error per situation of decision 4, none of them a `ToolFailure`, no kind given**:
  - the file is missing (no file, no run directory, a file in the place of a directory above it): an error class of this module (for example `MissingInstanceError`), which says only that no instance record was written for this `run_id` - nothing about `STATE.json`, about a run directory that holds other files, or about what the caller should do (sub-questions ⑩ and ⑰);
  - it cannot be read: the `OSError` of the file system passes through unchanged;
  - it is invalid: the invalid-content error, the file named by its path relative to the data root in front of the parser's message;
  - another integer `schema_version`: the unsupported-version error, named the same way.
- A path that is not a regular file (a directory, a symbolic link - not followed): choose and state the convention; recommended as `run_journal.read_state` has it, the invalid-content error.
- The whole file is read at each call and **nothing is kept between calls** (no cache, no module state): a file changed between two calls is seen at the second.
- The record returned is a `dict` the caller may hand to `backends.select`; say in the docstring whether it is a fresh object per call.
- It reads **no other file**: not `STATE.json`, not `events.ndjson`, not `db/<hw_profile_key>/hw_profile.json`, no configuration and no variable of the process. It writes, creates and removes nothing.

### Public API as landed (`hilclaw.instance`)
- `SCHEMA_VERSION = 1`.
- `Instance` - `NamedTuple(hw_profile_key: str, hw_profile: dict, others: dict)`: `hw_profile.key`, `hw_profile.record`, and every top-level member ADR-0018 does not define, as parsed and not interpreted.

- `validate(document)` - a parsed document; returns `None`; the same checks without the text rules.
- `read(data_root, run_id)` - returns `Instance` for `runs/<run_id>/instance.json`; one `os.lstat` and one read per call, nothing kept, new objects at each call.
- `hw_profile_of(data_root, run_id)` - returns `read(...).hw_profile`, a `dict` valid by ADR-0001; the call form of the parameter `hw_profile_of` of `hilclaw.hw_tool.tool_function`. It is bound nowhere.
- Error classes, none a `hilclaw.tools.ToolFailure`, no kind given:
  - `InvalidInstanceError(ValueError)` - an invalid content (the text rules, `schema_version` absent or no integer of ADR-0001, `hw_profile` absent or breaking decision 3), and by convention a path that is not a regular file. From `read`, the message starts with the path relative to the data root, for example `runs/run-a/instance.json: hw_profile.record.hw_source: must be ...`.
  - `UnsupportedVersionError(Exception)` - `schema_version` is an integer other than 1, raised before any other member is looked at; of this module, not that of `run_state`.
  - `MissingInstanceError(Exception)` - no file, no run directory, or a file in the place of a directory above it. Message: `<file>: is missing: no instance record was written for this run_id`.
  - "cannot be read" - the `OSError` of the file system, unchanged.
  - Arguments: `layout.InvalidPathValueError` for a `run_id` (before the file system); `FileNotFoundError` / `NotADirectoryError` for a data root that is no existing directory.

### Provisional choices (ADR-0018 does not fix them)
- Module name `instance`, after the file; one module for the pure and the file half, since the file has one member.
- `validate` exists beside `parse`, as in `run_state`, for a document in memory.
- Order: the whole text, then `schema_version`, then `hw_profile`; inside it the closed object, `key` a `str`, `record` an object and valid, `key` equal to the derived name. The first broken rule is reported, so a broken record is named before a key that cannot match it.
- `schema_version` is an integer of ADR-0001 (0 to 2**53 - 1); a value outside is invalid, not another version. `-0` is read as 0 and is then the unsupported version 0.
- A content the interpreter cannot read (an integer too long, nesting too deep) is `InvalidInstanceError`, stated as a limit of the reader.
- A number beyond the float range in a member not defined (`1e999`) is read as an infinity and is no error, as `run_state` has it; the tokens `NaN`, `Infinity`, `-Infinity` are refused.
- An empty `key` and a `key` of another form are reported as not the derived name: one rule, one message.
- A message shows the type of the refused value, and the value only when it is a `str`, shortened by `reprlib` - so a long key is shown shortened, while the expected name is shown in full.
- The file side follows `run_journal.read_state`: only the last path component is refused as a symbolic link; a link at `runs/` or `runs/<run_id>` is followed.
- A record error is reported as `hw_profile.record.<message of keys>`, for example `hw_profile.record.'example': unknown field`.
