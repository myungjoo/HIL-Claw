## Why
PLAN P1-1 ("FR-10 도구 계약 ... 인터페이스 + mock 백엔드 + 백엔드 적합성 테스트") has on `main` the whole frame of a HW tool - the two fronts, the tool definition, the data-root source, the journaled path, the backend table and its selection, the mock backend, the path of a journaled HW tool over a backend, the answers for a run that cannot be used (ADR-0010, ADR-0015, ADR-0016, ADR-0019) - and **no tool**: `hilclaw.tools.default_registry` is still empty. Every record of the frame handed the same thing on: "Later records: the contract of each HW tool, the mock's operation and default script for it, and the mechanism of the `cpu_standin` backend" (ADR-0016 Consequences).

`correctness.check` is the tool whose inputs are now the most complete:
- The verification run of the first case - `cpu_standin`, kind `gemm`, fp32, a C kernel - is fixed and implemented (ADR-0017; `hilclaw/harness/verification*.py`, `verification_program.c`; the three-state calibration of T-0063).
- The tolerance of a run has a place and a reader (ADR-0020; `hilclaw.instance.tolerance_of`, T-0072), and ADR-0020 decision 5 already fixed a property the contract must respect: no request carries the tolerance that decides the verdict.
- The hw_profile of a run has a place and a reader, and the situations of its file have kinds (ADR-0018, ADR-0019).

What no record says, and what every further step of this tool needs first, is the cut ADR-0016 decision 3 left open by name: "Which part of a tool's work is its backend's is the tool's contract - for `correctness.check` in particular the split between the one harness (FR-9) and the backend." The owner's answer HQ-0004 left it open too ("Nothing in this answer decides that split"), and ADR-0017 Consequences offers only an observation ("of the work described here, only building, starting the process and reading its report touch the target; regeneration, reference and comparison do not ... that contract ... alone places the cut"). The cut decides what an operation of a backend is handed and returns, so the mock's operation, the `cpu_standin` operation and the conformance tests all wait for it. It also carries two questions with it: who holds the seed (OD-16 sub-question 5 - a side that regenerates the inputs must know it), and who reads the tolerance and what a call answers when the instance states none (OD-8 sub-question 19; ADR-0019 Boundaries "a frame file it reads at another moment").

**This task writes that record, ADR-0021, and only that part of the contract.** It ticks **no PLAN checkbox** (P1-1 stays open).

Planner's judgements (2026-10-09 UTC, from the files; the reviewer is asked to re-check each):
- **The whole contract is too much for one record; this is its first part.** A full contract also needs the identity of a check (journaled or not, the `step` value, how the two execution points of FR-9 - "실행 지점은 sim·board 두 곳이며 동일 검증을 반복한다" - are told apart in an identity), the source of `draws` and of the dimensions, the build inputs of an attempt (where the kernel source of an attempt is: `coder/.../output/`, "Files and form: OD-23", ADR-0004), flags and time limits (OD-6 sub-question 2, OD-14), the result file (`eval.json`, OD-23), the spend axes (OD-2, OD-19). ## Acceptance Criteria
What is **fixed** and taken as input, not re-decided:
- **FR-9 and #5 A-12**: correctness is a hard floor; the same verification is repeated at the sim point and the board point; the verification harness (input generation, f64 reference, tolerance comparison, ...) is **one sub-module** of the package, outside the coder's scratch, which the coder cannot modify; a result is re-verified on inputs not exposed to the coder; no input value exists as a file (principle of OD-16).
- **Owner (HQ-0004)**: for the first case the oracle is the NumPy float64 product "computed on the Python side of the harness; the process that runs the kernel holds neither the reference nor the comparison"; per-element `rtol` and `atol`, both instance parameters, no default; "Nothing in this answer decides that split".
- **FR-10 and ADR-0016**: the tool contract is "transport 무관"; a HW tool reaches a target through a backend only; the tool function's part and the backend's part as decision 2 (a) has them; a backend answers exactly the contract of the tool and adds no member and no kind; no outcome depends on kept state; an operation is called with the request and the hw_profile of the call, and "What else an operation is handed and how the call is written are each tool's contract"; the mock's outcome depends on its script and its call alone, "no clock, no random source".
- **ADR-0017**: the verification run as it is - the seed "must be one the author of the attempt could not know" and binds the caller; regeneration on the Python side; the input check; completed / broken; pass / fail; what is returned; the parameter table of decision 9.
- **ADR-0020 decision 5**: the tolerance that decides the verdict of a correctness check of a run of the first case is the one in `instance.json` of that run; no default, no value kept, no value carried by a request stands in for it; a valid file may state none.
- **ADR-0010 decision 4**: a result says what the experiment established, "its failure included: a candidate that fails verification ..."; a tool failure says that no outcome was established. **ADR-0015 decision 2**: the reserved kinds have one meaning in every tool; the list is not closed; other kinds are each tool's. **ADR-0019**: the four run-file kinds are raised at the lookup or the selection, and what a tool answers for a frame file read at another moment is left to the tool's contract.

What the ADR **decides**. The content of each decision is the executor's to work out and justify from the fixed inputs; the reviewer's Approve confirms it. For every point give the choice, the alternatives considered and one or two lines of reason; mark each value as **cited** or as **this record's own**:
1. **Scope and terms**: of the contract of `correctness.check`, for a call about one attempt of a run of the first case, the four points below and nothing else. State that this is **not the whole contract** and list what a second record must add before the tool can be registered (the list under "must not decide").
2. **The split between the one harness and a backend** (ADR-0016 decision 3). Of the work of a verification (ADR-0017: build of the verification executable, start of the process, reading the report, the input check, regeneration of the inputs, the reference, the comparison, the verdict), say which is the tool function's part - the same code for every backend - and which is the operation's. Weigh at least: (a) the operation carries out the kernel on drawn inputs at its target and returns what the kernel produced, and the tool function regenerates, computes the reference, compares and gives the verdict; (b) the operation calls the harness as a library and returns a verdict; (c) the operation returns the inputs it used together with the outputs. What must hold: FR-9's one harness and "the same verification" at every point and target; the owner's sentence about the process that runs the kernel; ADR-0016 decision 2 (b) (the cases a contract test runs over the mock are the cases every backend is held to); what a backend that does not answer the contract can and cannot make pass. Then state, **as classes and not as spelt members unless you decide the spelling**, what an operation of this tool is handed beyond the request and the hw_profile (ADR-0016 decision 2, last bullet) and what it returns, and which of the parameters of ADR-0017 decision 9 each side must hold (the seed, `draws` and the dimensions are needed by whoever regenerates; `rtol` and `atol` by whoever compares; flags, time limits and the environment by whoever builds and runs). **Where `draws`, the dimensions, the flags and the time limits come from is not decided** (see below); the record says only which side needs each. Say what the cut means for the mock (ADR-0016 decision 5 (d), (e): what a script must then be able to express for this tool, and that its outcome may read no random source) without writing the default script.
3. **The seed of a call** (the seed part of OD-16 sub-question 5). Who draws it and when; that it is - or is not - a member of a request, with the reason (compare ADR-0016 decision 4 and ADR-0020 decision 5: a calling agent that names the seed can know every input before the attempt is written); from what kind of source it is drawn (a property, not an algorithm: what "one the author of the attempt could not know" requires); that it is not kept between calls and is written to no file before or during the check (cited: principle of OD-16). **Whether it is recorded after the check** - in a result, on an end line, anywhere - is the hard part: NFR-2 and a stored result of a journaled step pull one way, the principle of OD-16, FR-9 and ADR-0017 decision 7 ("Whether a caller may keep either, and where") the other, and a repair attempt of the same candidate is written after the check. Decide it only if the fixed inputs carry the answer; otherwise leave it open with the exact question and state what the record does require in the meantime. Do not decide `draws` (how many a round or a promotion-level re-verification uses): cite it as open.
4. **The tolerance in a call, and a run that states none** (OD-8 sub-question 19 as far as a call of this tool; ADR-0019 Boundaries). Which side reads the tolerance (it follows from point 2), through which rule (cited: ADR-0020 decision 5; the reader on `main` is `hilclaw.instance.tolerance_of`, named as an observation, not bound by the record), and **where in the order of a call** - stated relative to the moments ADR-0016 decision 2 already has (before any operation is called; whether before a start line is said conditionally, since this record does not decide whether the tool is journaled). What a call answers when the file is valid and states no tolerance: weigh a tool failure of a kind of this tool's own, a new reserved kind, an existing reserved kind (`invalid_request` is about the request; the run-file kinds say the file is missing, unreadable, invalid or of another version - a valid file without the member is none of these by ADR-0020 decision 3), and a result; say whether anything was consumed at the target and whether a line was left. What a call answers when `instance.json` is missing, unreadable, invalid or of another version at this read: the planner's reading is that the four kinds of ADR-0019 fit and that this is the tool's contract using them at one more moment, as ADR-0019 Boundaries leaves it - **confirm or correct, and do not edit ADR-0019**. Sub-question 19 also asks whether the start of an instance checks it: that half stays open (OD-8 sub-question 17, OD-23) and the record says so.
5. **Which outcomes are results and which are tool failures** (ADR-0010 decision 4). Pass and fail are results by the fixed inputs (cite). Decide the class of a **broken** run (ADR-0017 decision 7: neither pass nor fail; its conditions - a non-zero status or a signal, a timeout, a malformed report, a check value that disagrees): a result that reports it, or a tool failure, and whether all its conditions are one class. Weigh what each choice means for a stored outcome of a repeated call, for a caller that must not count it as verified (FR-9), and for a defect of the harness against a defect of the kernel (ADR-0017 decision 4, "Input check"). Say what a result must at least let a caller tell apart (pass, fail, and broken if it is a result) and what it must never contain (cited: ADR-0017 decision 7 - no element of the inputs or the reference from the harness itself; the unfiltered capture of the runner is not free of them). **Naming and typing the result members is allowed only for what this point decides; if you do not need names, give classes and leave the spelling to the second record.** What anybody does after a fail or a broken run is not decided (FR-1, OD-10, OD-19).
6. **Consequences**, not decisions: what the second record of this contract must add; the code slices that become possible once both exist (the tool function of `correctness.check` over `hilclaw.hw_tool.tool_function` or otherwise, the mock's operation and script cases, the conformance tests of P1-1) and which of them could already be cut after this record alone; which docstring sentences of `hilclaw/harness/verification.py`, `hilclaw/hw_tool.py` or `hilclaw/instance.py` become less exact, if any. A short **walk-through** in the manner of ADR-0016: a call whose run states a tolerance and whose kernel is right; one whose kernel is wrong; one whose run states no tolerance; one whose `instance.json` is invalid; one whose verification process dies - each saying which side does what and which class of outcome the caller gets, with placeholders and without a `step` value, a member of an identity or an execution point.
